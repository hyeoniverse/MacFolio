## 편집기를 메모 앱 수준으로

### 표 손잡이가 13px 어긋난 원인

표 손잡이는 표의 행·열 옆에 표시되는 작은 막대로, 누르면 그 행이나 열 전체를 선택한다. 첫 구현의 손잡이는 열 위가 아니라 머리글 셀을 덮고 있었고, 계산한 위치보다 약 13px 아래에 그려졌다. 본문에는 "두 번째 이후의 직계 자식 요소에 0.9em 위 여백"을 주는 문단 간격 규칙이 있었다. 손잡이를 편집기의 직계 자식으로 렌더링했기 때문에 손잡이도 이 규칙에 해당해 0.9em(약 13px)의 위 여백을 받았다. 손잡이와 테두리에 `margin: 0`을 지정해 해결했다.

![형제 선택자 여백이 표 핸들에 적용된 과정](./images/notes-polish-sibling-margin.svg '손잡이도 본문의 직계 자식이라 0.9em 위 여백을 받아, 계산한 위치보다 약 13px 아래에 그려졌다')

### 찾기·대치는 뒤에서부터

찾기·대치는 글에서 검색어를 모두 찾아 일치 위치(문자열의 몇 번째 글자에서 시작하는지)를 기록한 뒤, 그 위치의 글자를 다른 글자로 바꾸는 기능이다. 바꿀 글자가 원래 글자보다 길거나 짧으면, 바꾼 위치보다 뒤에 있는 글자는 모두 앞이나 뒤로 이동한다. 그래서 ==찾기·대치는 뒤에서부터 교체해야 앞쪽 일치 위치가 밀리지 않는다.==

![앞에서부터 교체하면 위치 0을 바꾼 뒤 문자열이 2글자 늘어나 기록한 위치 2에 c가 오고, 뒤에서부터 교체하면 늘어난 글자가 모두 뒤쪽에 생겨 위치 0과 2가 그대로다](./images/day-0930-replace-order.svg '"a a a"의 a 세 개를 abc로 바꾸는 예. 왼쪽은 두 번째 교체부터 엉뚱한 글자를 바꾸고, 오른쪽은 기록한 위치를 그대로 사용한다')

```text
"a a a"에서 "a"를 "abc"로 모두 대치 (일치 위치: 0, 2, 4)
앞에서부터: 위치 0 교체 → 문자열이 2글자 길어짐 → 위치 2, 4가 실제로는 4, 6으로 이동 → 잘못된 자리 교체
뒤에서부터: 위치 4 → 2 → 0 순서로 교체 → 앞쪽 위치는 변하지 않음 → 기록한 위치 그대로 사용
```

### E2E 시험 추가

새 기능마다 E2E 시험을 추가해 브라우저 E2E가 131개가 되었다. 관리자 기능은 로그인이 필요하므로, 시험에서는 실제 API 서버 대신 가짜 API(`e2e/fakeApi.ts`)를 사용한다. 가짜 API는 브라우저가 보내는 `/auth/me` 같은 요청을 가로채 "로그인한 관리자"라는 응답을 돌려주므로, GitHub 로그인 없이도 관리자 화면에서 클릭·드래그를 시험할 수 있다.

글이 늘어나자 "목록의 세 번째 글을 연다"처럼 글 순서에 의존하던 시험이 실패했다. 새 글이 추가되면 세 번째 글이 바뀌기 때문이다. 순서 대신 제목으로 글을 찾도록 고쳤다.

## API 서버 배포

### 배포 구성

로컬에서만 동작하던 로그인을 실제 사이트에서도 동작하게 하려면 API 서버를 인터넷에서 접근할 수 있는 컴퓨터에 올려야 한다. Oracle Cloud의 Always Free VM(무료로 계속 사용할 수 있는 가상 머신)에 Postgres(DB), API, cloudflared 세 컨테이너를 docker compose로 실행했다. docker compose는 여러 컨테이너의 이미지·환경 변수·연결 관계를 `compose.yml` 한 파일에 적어 두고 한 명령으로 함께 실행하는 도구다.

SSH(원격 접속, 22번 포트) 외에는 인바운드 포트를 하나도 열지 않았다. 인바운드 포트는 외부 컴퓨터가 먼저 연결을 시작할 수 있도록 열어 둔 번호다. 일반적인 웹 서버는 80·443번을 열어 두고 요청을 기다리지만, 이 구성에서는 서버 안의 cloudflared가 Cloudflare로 **나가는** 연결(아웃바운드)을 먼저 만들고, 외부 요청은 그 연결을 거꾸로 타고 들어온다. 이 방식을 Cloudflare Tunnel이라고 한다([Oracle 무료 VM과 Cloudflare Tunnel로 인바운드 포트 없이 API 서버 배포하기](/memo/deploy-api-oracle-tunnel)).

![nginx 구성은 80·443 인바운드를 열고, 터널 구성은 cloudflared가 아웃바운드 연결을 먼저 만들어 그 연결로 요청을 받는다](./images/deploy-api-oracle-tunnel-inbound-outbound.svg '두 구성의 연결 방향 비교. 터널 구성은 방화벽에 웹 포트를 열지 않는다')

### 막힌 단계와 해결

배포하면서 다음 단계마다 막혔다.

| 단계 | 증상                                                                                            | 원인과 해결                                                                                                                                          |
| ---- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 로컬 Mac에서 `docker run --env-file /etc/macfolio/api.env …` 실행 → `no such file or directory` | 서버에 있어야 할 파일을 로컬 Mac에서 찾았다. 서버부터 생성해야 했다                                                                                  |
| 2    | VM 생성 화면의 보안 항목                                                                        | Shielded instance와 Confidential computing은 함께 활성화할 수 없다. 기본값을 유지했다                                                                |
| 3    | "공인 IPv4 자동 할당" 체크박스가 비활성                                                         | 안내 문구 `You must select a public subnet to assign a public IPv4 address.`대로, 기존 서브넷 대신 **새 공인 서브넷 만들기**를 선택하자 활성화되었다 |
| 4    | SSH 키 파일 접속                                                                                | 내려받은 키를 `~/.ssh/`로 옮기고 `chmod 600`으로 권한을 제한했다. 절대 경로(`~/Downloads` → `~/.ssh`)를 써서 실행 위치와 관계없이 동작했다           |
| 5    | 서버 사양 확인                                                                                  | `free -h` 결과 메모리 954Mi, 스왑 0. 무료 VM의 사양이다                                                                                              |
| 6    | 비밀 값 보관 위치                                                                               | `.env`·`api.env`는 저장소 밖 `~/deploy/`에 보관하고 `chmod 600`으로 제한했다                                                                         |

3단계의 서브넷은 클라우드 안의 가상 네트워크(OCI에서는 VCN)를 다시 나눈 주소 구역이다. OCI의 서브넷은 생성 시점에 공인(public)과 사설(private) 중 하나로 정해지고, 사설 서브넷에 놓인 VM에는 공인 IP를 붙일 수 없다. 기존 서브넷이 사설이었기 때문에 체크박스가 비활성이었다.

![VCN 안의 공인 서브넷에서는 VM에 공인 IPv4를 붙일 수 있어 체크박스가 활성화되고, 사설 서브넷에서는 공인 IP가 금지되어 체크박스가 비활성이다](./images/day-0930-public-subnet.svg '공인 서브넷과 사설 서브넷. 공인 IP 자동 할당은 공인 서브넷에서만 선택할 수 있다')

4단계와 6단계의 `chmod 600`은 파일 권한을 "소유자만 읽기·쓰기 가능, 그 밖의 사용자는 접근 불가"로 바꾸는 명령이다. 숫자 6은 읽기(4)+쓰기(2)이고, 세 자리는 차례로 소유자·그룹·기타 사용자를 뜻한다. `ls -l`로 확인하면 `-rw-------`로 표시된다. SSH는 개인 키 파일을 다른 사용자가 읽을 수 있으면 접속을 거부하므로 이 권한이 필요하다.

6단계에서 비밀 값을 저장소 밖에 둔 이유는 두 가지다. 저장소 폴더 안에 있으면 실수로 커밋될 수 있고, `git pull`이나 저장소를 다시 받는 작업이 파일을 덮어쓸 수 있다.

![서버 홈 폴더에 코드가 있는 ~/macfolio Git 저장소와, .env·api.env·compose.yml이 있는 ~/deploy 폴더가 나란히 있다](./images/day-0930-secrets-layout.svg '코드와 비밀 값을 서로 다른 폴더에 보관한다. git pull은 ~/macfolio만 갱신한다')

```bash
ssh -i ~/.ssh/<키 파일> ubuntu@<서버 IP>
free -h                       # 메모리·스왑 확인
mkdir ~/deploy && cd ~/deploy # 비밀 값은 저장소 밖에
chmod 600 .env api.env
```

### 가장 오래 걸린 단계: 빌드 변수

가장 오래 걸린 단계는 서버가 아니라 프론트엔드였다. API의 `/docs`(Swagger 문서 화면)는 열리는데, 사이트에는 "관리자 서버가 아직 연결되지 않았습니다"가 표시되었다. 서버와 터널은 정상이고, 프론트엔드가 API 주소를 모르는 상태였다.

프론트엔드는 `VITE_API_URL` 변수로 API 주소를 받는다. Vite는 `vite build`를 실행하는 시점에 코드 안의 `import.meta.env.VITE_API_URL`을 실제 문자열로 바꿔 번들에 넣는다. 예를 들어 빌드 시점에 값이 `https://macfolio-api.hyeoniverse.com`이면 번들에는 그 문자열이 그대로 들어가고, 값이 없으면 빈 값이 들어간다. ==Cloudflare의 런타임 변수로 등록했던 것이 원인이었다.== 런타임 변수는 Worker가 요청을 처리하는 시점에 Worker 코드만 읽을 수 있고, 이미 만들어진 브라우저 번들에는 반영되지 않는다. 빌드 변수로 옮기자 바로 해결되었다.

| 변수 종류   | 읽는 시점                                  | `VITE_API_URL`에 적합한가          |
| ----------- | ------------------------------------------ | ---------------------------------- |
| 빌드 변수   | `vite build` 실행 중, 번들에 문자열로 포함 | 적합                               |
| 런타임 변수 | Worker가 요청을 처리할 때                  | 부적합 (브라우저 번들은 읽지 못함) |

![VITE_API_URL은 빌드 단계에서 JS 문자열이 된다. 실행 변수는 Worker 코드만 읽는다](./images/deploy-api-oracle-tunnel-env.svg '빌드 변수와 런타임 변수가 사용되는 위치. 정적 사이트의 환경 변수는 빌드 시각에만 의미가 있다')

![로그인된 계정 화면](./images/admin-signed-in.jpg '배포 환경에서 로그인한 뒤의 시스템 설정 → 계정. 서버 줄에 API 주소가 표시된다')

배포 절차는 VM 생성부터 OAuth App, 터널, 환경 변수, 막혔던 증상과 해결 방법까지 `docs/deployment.md`에 기록했다. 무료 서버는 사용하지 않으면 회수될 수 있으므로, 서버가 사라져도 이 문서만으로 다시 구축할 수 있어야 한다.

## 코드로 찍는 스크린샷

화면 캡처를 수동으로 찍지 않고, E2E의 가짜 API로 화면 상태(로그인 여부, 글 목록, 열린 창)를 구성한 뒤 Playwright로 캡처하게 했다. 같은 스크립트를 다시 실행하면 같은 화면이 나오므로, 화면이 바뀐 뒤에도 캡처를 다시 만들 수 있다. 이 과정에서 창 밖으로 잘린 메뉴, 깨진 이미지 아이콘으로 표시된 계정 사진(캡처 환경에서 GitHub 이미지 요청이 차단된 경우)도 발견해 고쳤다([Playwright와 E2E 가짜 API로 블로그 스크린샷 생성하기](/memo/screenshots-with-playwright)).

## 브랜치·커밋 규칙의 CI 검사

브랜치·커밋·PR 이름 규칙이 문서로 정해져 있지 않았다. 지금까지 사용한 형식(예: 브랜치 `feat/memo-tags`, 커밋 `feat(memo): 태그 필터 추가`)을 규칙으로 정리하고, PR을 올릴 때마다 CI가 정규식으로 형식을 검사하게 했다([정규식 검사 워크플로와 Rulesets로 커밋·PR 규칙을 CI에서 강제하기](/memo/commit-conventions-ci)).

## 이미지만 추가한 PR에서 실패한 E2E

코드를 바꾸지 않고 이미지만 추가한 PR에서 이미지 드래그 E2E가 실패했다. 확인해 보니 `main` 브랜치에서도 ==특정 조건에서 실패하는 불안정한 시험이었다==. 시험이 이미지를 다 불러오기 전에 끌어 놓을 위치의 좌표를 측정했고, 이미지가 늦게 표시되면서 목표 위치가 아래로 밀려났다. 또한 마지막 마우스 이동이 요소 경계를 넘으면 브라우저가 `dragover` 이벤트를 보내지 않아 놓을 위치 표시가 사라졌다([이미지 로드 전 좌표와 누락된 dragover로 흔들린 끌기 E2E](/memo/flaky-drag-e2e)).

![위치를 측정한 뒤 밀린 소제목](./images/flaky-drag-e2e-layout-shift.svg '이미지 높이가 확정되기 전에 측정한 좌표로 드래그하면 목표가 창 밖으로 밀려 있다')

## 돌아보며

- **좌표를 측정하는 시험**: 드래그 E2E가 이미지를 다 불러오기 전에 좌표를 측정해, 이미지만 추가한 PR에서 실패했다. 이미지 로드, 스크롤 같은 조건이 끝난 뒤에 측정해야 한다.
- **수동 배포**: 서버에 접속해 `git pull`하고 메모리 1GB 서버에서 이미지를 빌드한다. 배포가 잦아지면 이 단계가 먼저 병목이 된다.
- **배포 절차 문서**: 무료 서버는 회수될 수 있어서, 문서만으로 다시 구축할 수 있게 배포 절차를 단계별로 기록했다.
