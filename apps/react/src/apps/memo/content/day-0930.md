커밋 기록을 다시 보면 규칙 하나가 일관되게 지켜졌다. **기능 커밋과 블로그 글 커밋이 함께 들어간다.** `feat:` 커밋 바로 다음에 `docs: …를 블로그 글에` 커밋이 있다. 구현 중 막혔던 지점은 작업 직후에 기록하지 않으면 빠르게 잊힌다. 표 손잡이가 13px 어긋난 원인(본문 문단 간격 규칙)과, 찾기·대치에서 뒤에서부터 교체해야 앞쪽 위치가 밀리지 않는다는 점도 작업 직후 기록해서 남았다.

```text
"a a a"에서 "a"를 "abc"로 모두 대치 (일치 위치: 0, 2, 4)
앞에서부터: 위치 0 교체 → 문자열이 2글자 길어짐 → 위치 2, 4가 실제로는 4, 6으로 이동 → 잘못된 자리 교체
뒤에서부터: 위치 4 → 2 → 0 순서로 교체 → 앞쪽 위치는 변하지 않음 → 기록한 위치 그대로 사용
```

E2E도 함께 늘었다. 새 기능마다 가짜 API로 관리자 로그인 상태를 만들고 클릭·드래그를 수행하는 테스트를 추가해, 브라우저 E2E가 131개가 되었다. 같은 날 글이 늘어나자 글 순서에 의존하던 테스트가 실패해서, 순서에 의존하지 않게 수정했다.

## API 서버 배포

로컬에서만 동작하던 로그인을 배포 환경으로 옮겼다. Oracle Cloud Always Free VM에 Postgres, API, cloudflared를 docker compose로 실행하고, SSH 외에는 인바운드 포트를 하나도 열지 않았다. 외부 요청은 Cloudflare Tunnel(cloudflared)이 VM에서 바깥으로 연결한 터널로 들어온다. 자세한 과정은 [API 서버를 무료로 띄우기](/memo/deploy-api-oracle-tunnel)에 정리했다.

배포 과정에서 다음 단계마다 막혔다.

1. 처음에는 로컬 Mac에서 `docker run --env-file /etc/macfolio/api.env …`를 실행해 `no such file or directory` 오류가 발생했다. 서버에 있어야 할 파일을 로컬에서 찾고 있었다. 서버를 먼저 생성해야 했다.
2. Oracle Cloud에서 VM을 생성할 때 보안 항목(Shielded instance와 Confidential computing은 함께 활성화할 수 없다)은 기본값을 유지했다.
3. 네트워크 설정에서 "공인 IPv4 자동 할당" 체크박스가 활성화되지 않았다. `You must select a public subnet to assign a public IPv4 address.` 안내대로, 기존 서브넷 대신 **새 공인 서브넷 만들기**를 선택하자 활성화되었다.
4. 내려받은 SSH 키를 `~/.ssh/`로 옮기고 권한을 `chmod 600`으로 제한한 뒤 접속했다. 키 이동 명령은 절대 경로(`~/Downloads` → `~/.ssh`)를 사용해서, 실행한 디렉터리와 관계없이 동작했다.
5. 접속 후 `free -h`로 확인한 메모리는 954Mi, 스왑은 0이었다. 무료 VM의 사양이다.
6. `.env`와 `api.env`는 저장소 안이 아니라 서버의 `~/deploy/`에 별도로 보관하고 권한을 `chmod 600`으로 제한했다. 비밀 값이 `git pull`로 덮어쓰이거나 커밋되지 않게 하기 위해서다.

```bash
ssh -i ~/.ssh/<키 파일> ubuntu@<서버 IP>
free -h                       # 메모리·스왑 확인
mkdir ~/deploy && cd ~/deploy # 비밀 값은 저장소 밖에
chmod 600 .env api.env
```

전체 절차는 저장소의 [docs/deployment.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/deployment.md)와 [Oracle Cloud Always Free 문서](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)에 있다.

가장 오래 걸린 단계는 서버가 아니라 프론트엔드였다. API의 `/docs`는 열리는데 사이트에서는 "관리자 서버가 아직 연결되지 않았습니다"가 표시되었다. `VITE_API_URL`은 빌드 시점에 번들에 포함되는 값인데, Cloudflare의 런타임 변수로 등록했던 것이 원인이었다. 빌드 변수로 옮기자 바로 해결되었다.

| 변수 종류   | 읽는 시점                                  | `VITE_API_URL`에 적합한가          |
| ----------- | ------------------------------------------ | ---------------------------------- |
| 빌드 변수   | `vite build` 실행 중, 번들에 문자열로 포함 | 적합                               |
| 런타임 변수 | Worker가 요청을 처리할 때                  | 부적합 (브라우저 번들은 읽지 못함) |

## 문서 재작성과 코드로 찍는 스크린샷

배포 후 README를 확인하니 앱 목록과 폴더 구조가 모두 오래된 내용이었고, API는 언급조차 없었다. 새로 작성했다.

- **README**: 대표 스크린샷, 둘러보기 표(메모·메시지·댓글·관리자 로그인·모바일·프로젝트), 방문자와 관리자로 나눈 사용법, API까지 띄우는 로컬 실행
- **docs/deployment.md**: VM 생성부터 OAuth App, 터널, 환경 변수, 막혔던 증상과 해결 방법까지. 서버가 회수되어도 이 문서만으로 다시 구축할 수 있게 작성했다

스크린샷은 수동으로 캡처하지 않고, E2E의 가짜 API로 화면 상태를 구성해 Playwright로 캡처했다. 잘린 메뉴, 깨진 아바타 등을 수정한 과정은 [블로그 스크린샷을 테스트 코드로 찍기](/memo/screenshots-with-playwright)에 정리했다.

## 브랜치·커밋 규칙의 CI 검사

문서를 정리하면서 브랜치·커밋·PR 규칙이 문서화되어 있지 않다는 것을 확인했다. 지금까지 사용한 형식을 규칙으로 정리하고 PR마다 CI가 검사하게 했다([커밋 규칙을 문서 대신 CI로 지키기](/memo/commit-conventions-ci)).

## 이미지만 추가한 PR에서 실패한 E2E

이미지만 추가한 PR에서 E2E가 실패했다. 코드는 변경하지 않았는데 이미지 드래그 테스트가 실패했고, 확인해 보니 `main`에서도 특정 조건에서 실패하는 불안정한 테스트였다. 원인 분석 과정은 [글 한 편 추가했더니 E2E가 깨졌다](/memo/flaky-drag-e2e)에 정리했다.

## 돌아보며

- **잘한 점: 기능과 글을 함께 기록했다.** 막혔던 지점을 작업 직후 기록해서, 하루가 끝난 뒤에도 무엇을 왜 그렇게 구현했는지 다시 확인할 수 있었다
- **잘한 점: 배포 문서를 단계별로 기록했다.** 무료 서버는 회수될 수 있으므로, 문서만으로 다시 구축할 수 있어야 한다
- **아쉬운 점: 레이아웃에 의존하는 테스트.** 좌표를 측정하는 테스트는 글 한 편, 이미지 하나에도 결과가 달라진다. 측정 전에 완료되어야 하는 조건(이미지 로드, 스크롤)을 먼저 정의해야 했다
- **아쉬운 점: 배포가 아직 수동이다.** 서버에 접속해 `git pull`하고 1GB 메모리로 빌드한다. 배포 빈도가 늘면 가장 먼저 병목이 될 단계다
