## 들어가기 전에

정보처리기사 실기에는 회차마다 SQL 문제가 여러 개 나온다. 형식은 크게 세 가지다. 테이블과 SQL 문을 주고 실행 결과(값이나 행 수)를 쓰게 하는 문제, SQL 문의 빈칸에 들어갈 키워드를 쓰게 하는 문제, 요구사항을 주고 SQL 문 전체를 작성하게 하는 문제다. 세 형식 모두 보기가 없으므로, 키워드 철자와 NULL 처리 규칙까지 정확히 알아야 점수를 받는다.

SQL(Structured Query Language)은 관계 데이터베이스에서 데이터를 정의하고 조회·변경하는 표준 언어다. 관계 데이터베이스는 데이터를 행(Row)과 열(Column)로 이뤄진 테이블에 보관하고, 테이블끼리는 같은 값을 가진 열(키)로 연결한다. 엑셀 시트 여러 장을 "학번" 열로 서로 이어 붙여 놓은 구조를 떠올리면 된다.

이 글은 학생·학과·과목·수강 네 테이블로 된 예제 스키마를 직접 만들고, 모든 쿼리를 SQLite에서 실제로 실행한 결과를 싣는다. SQLite가 지원하지 않는 GRANT·REVOKE 같은 문법은 표준 SQL로 설명하고 실행 결과는 싣지 않는다. 실기 시험 전체 구조는 [정보처리기사 실기 시험 구조와 답안 작성](/memo/eip-practical-overview)에서 다룬다.

## 예제 스키마

### 네 테이블의 구조

![예제 스키마의 네 테이블과 외래 키 관계](./images/eip-practical-sql-schema.svg '화살표는 외래 키가 참조하는 기본 키를 가리키고, 화살표 옆 글자는 참조되는 행을 삭제하는 경우의 동작이다')

| 테이블 | 무엇을 보관하는가                | 기본 키          | 외래 키                                     |
| ------ | -------------------------------- | ---------------- | ------------------------------------------- |
| 학과   | 학과 코드와 이름                 | 학과코드         | 없음                                        |
| 학생   | 학생 기본 정보                   | 학번             | 학과코드 → 학과, 멘토학번 → 학생(자기 자신) |
| 과목   | 개설 과목과 학점                 | 과목코드         | 없음                                        |
| 수강   | 누가 어떤 과목을 들었는지와 점수 | (학번, 과목코드) | 학번 → 학생, 과목코드 → 과목                |

기본 키(PK, Primary Key)는 테이블에서 행 하나를 유일하게 식별하는 열이다. 같은 학번을 가진 학생이 두 명일 수 없으므로 학번이 학생 테이블의 기본 키다. 외래 키(FK, Foreign Key)는 다른 테이블의 기본 키를 참조하는 열로, 수강 테이블의 학번에는 학생 테이블에 실제로 있는 학번만 들어갈 수 있다. 수강 테이블은 (학번, 과목코드) 두 열을 합쳐 기본 키로 쓴다. 한 학생이 같은 과목을 두 번 수강할 수 없다는 규칙을 이 복합 키가 보장한다.

### SQL 명령어 분류

![SQL 명령어의 네 분류](./images/eip-practical-sql-categories.svg 'DDL은 테이블 구조, DML은 행 데이터, DCL은 권한, TCL은 트랜잭션을 다룬다')

| 분류 | 영문                         | 명령어                         | 다루는 대상           |
| ---- | ---------------------------- | ------------------------------ | --------------------- |
| DDL  | Data Definition Language     | CREATE, ALTER, DROP, TRUNCATE  | 테이블·뷰·인덱스 구조 |
| DML  | Data Manipulation Language   | SELECT, INSERT, UPDATE, DELETE | 테이블 안의 행        |
| DCL  | Data Control Language        | GRANT, REVOKE                  | 사용자 권한           |
| TCL  | Transaction Control Language | COMMIT, ROLLBACK, SAVEPOINT    | 트랜잭션              |

국내 수험서는 COMMIT과 ROLLBACK을 DCL에 넣어 세 분류로 설명하는 경우가 많다. 시험에서 "DCL 명령어를 모두 쓰시오"라고 하면 문제가 어느 분류 체계를 따르는지 확인해야 하는데, 세 분류 체계에서는 GRANT, REVOKE, COMMIT, ROLLBACK이 DCL이다.

## DDL: 구조 정의

### CREATE TABLE과 제약 조건

예제 스키마를 만드는 DDL은 다음과 같다. SQLite는 외래 키 검사가 기본으로 꺼져 있어 `PRAGMA foreign_keys = ON;`을 먼저 실행해야 한다. 다른 DBMS(Oracle, PostgreSQL, MySQL InnoDB)는 기본으로 검사한다.

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE 학과 (
  학과코드 CHAR(2) PRIMARY KEY,
  학과명   VARCHAR(20) NOT NULL UNIQUE
);
CREATE TABLE 학생 (
  학번     INTEGER PRIMARY KEY,
  이름     VARCHAR(10) NOT NULL,
  학과코드 CHAR(2) REFERENCES 학과(학과코드) ON DELETE SET NULL,
  학년     INTEGER NOT NULL CHECK (학년 BETWEEN 1 AND 4),
  멘토학번 INTEGER REFERENCES 학생(학번),
  연락처   VARCHAR(13)
);
CREATE TABLE 과목 (
  과목코드 CHAR(5) PRIMARY KEY,
  과목명   VARCHAR(20) NOT NULL,
  학점     INTEGER DEFAULT 3
);
CREATE TABLE 수강 (
  학번     INTEGER REFERENCES 학생(학번) ON DELETE CASCADE,
  과목코드 CHAR(5) REFERENCES 과목(과목코드) ON DELETE RESTRICT,
  점수     INTEGER CHECK (점수 BETWEEN 0 AND 100),
  PRIMARY KEY (학번, 과목코드)
);
```

| 제약 조건                | 뜻                                            | 예제에서               |
| ------------------------ | --------------------------------------------- | ---------------------- |
| PRIMARY KEY              | 기본 키. NULL 불가, 중복 불가                 | 학번, (학번, 과목코드) |
| FOREIGN KEY / REFERENCES | 다른 테이블의 기본 키 값만 허용 (참조 무결성) | 수강.학번 → 학생.학번  |
| UNIQUE                   | 중복 불가. NULL은 허용 (DBMS마다 처리 차이)   | 학과명                 |
| NOT NULL                 | NULL 불가                                     | 이름, 학년             |
| CHECK                    | 조건식을 만족하는 값만 허용 (도메인 무결성)   | 학년 1~4, 점수 0~100   |
| DEFAULT                  | 값을 생략하면 넣을 기본값                     | 학점 3                 |

제약 조건을 어기는 INSERT는 실패한다. 실제로 실행하면 다음 오류가 난다.

```sql
INSERT INTO 학생 VALUES (2408,'윤가람','CS',5,NULL,NULL);
INSERT INTO 학생 (학번, 이름, 학년) VALUES (2401,'중복',1);
INSERT INTO 수강 VALUES (2499,'DB101',70);
```

```text
Error near line 1: CHECK constraint failed: 학년 BETWEEN 1 AND 4
Error near line 2: UNIQUE constraint failed: 학생.학번
Error near line 3: FOREIGN KEY constraint failed
```

첫 줄은 학년 5가 CHECK를 어겼고, 둘째 줄은 이미 있는 학번 2401을 넣으려 해 기본 키 중복으로 실패했고, 셋째 줄은 학생 테이블에 없는 학번 2499를 수강에 넣으려 해 참조 무결성을 어겼다.

### 참조 동작: CASCADE, SET NULL, RESTRICT

외래 키에는 참조되는 행이 삭제·변경되면 참조하는 행을 어떻게 처리할지 정하는 참조 동작을 붙인다.

| 옵션        | 참조되는 행을 삭제하면                                             |
| ----------- | ------------------------------------------------------------------ |
| CASCADE     | 참조하는 행도 함께 삭제한다                                        |
| SET NULL    | 참조하는 행의 외래 키 값을 NULL로 바꾼다                           |
| SET DEFAULT | 참조하는 행의 외래 키 값을 기본값으로 바꾼다                       |
| RESTRICT    | 참조하는 행이 있으면 삭제를 거부한다                               |
| NO ACTION   | 문장이 끝나는 시각에 참조 무결성을 검사해 어기면 거부한다 (기본값) |

![CASCADE로 학생을 삭제할 때와 RESTRICT로 과목을 삭제할 때](./images/eip-practical-sql-cascade.svg '왼쪽은 수강 3행이 함께 삭제되고, 오른쪽은 참조하는 수강 행 때문에 삭제 자체가 거부된다')

```sql
SELECT COUNT(*) AS 수강행수 FROM 수강;
DELETE FROM 학생 WHERE 학번 = 2405;
SELECT COUNT(*) AS 수강행수 FROM 수강;
DELETE FROM 과목 WHERE 과목코드 = 'DB101';
DELETE FROM 과목 WHERE 과목코드 = 'AI401';
SELECT changes() AS 삭제행수;
```

| 수강행수 (삭제 전) |
| ------------------ |
| 12                 |

| 수강행수 (2405 삭제 후) |
| ----------------------- |
| 9                       |

```text
Error near line 4: FOREIGN KEY constraint failed
```

| 삭제행수 (AI401) |
| ---------------- |
| 1                |

학생 2405를 삭제하자 수강.학번의 `ON DELETE CASCADE` 때문에 정민서의 수강 3행이 함께 삭제되어 12행이 9행이 됐다. 과목 DB101은 수강 4행이 참조하고 있어 `ON DELETE RESTRICT`가 삭제를 거부했고, 아무도 수강하지 않은 AI401은 정상 삭제됐다. 학과 EE를 삭제하면 `ON DELETE SET NULL` 때문에 박서준과 한유진의 학과코드가 NULL로 바뀐다(실행 확인).

같은 방식으로 학번 2401을 삭제하면 실패한다. 이도윤과 정민서의 멘토학번이 2401을 참조하는데, 멘토학번 외래 키에는 참조 동작을 지정하지 않아 기본값 NO ACTION이 적용되기 때문이다. 수강 쪽의 CASCADE만 보고 "삭제된다"고 답하면 틀린다.

### ALTER TABLE과 DROP

```sql
ALTER TABLE 학생 ADD COLUMN 이메일 VARCHAR(40);
ALTER TABLE 학생 RENAME COLUMN 연락처 TO 전화번호;
ALTER TABLE 학생 DROP COLUMN 이메일;
ALTER TABLE 과목 RENAME TO 교과목;
SELECT 학번, 이름, 전화번호 FROM 학생 LIMIT 2;
```

| 학번 | 이름   | 전화번호      |
| ---- | ------ | ------------- |
| 2401 | 김하늘 | 010-1111-2222 |
| 2402 | 이도윤 | 010-3333-4444 |

| 명령                                         | 하는 일                                             |
| -------------------------------------------- | --------------------------------------------------- |
| `ALTER TABLE 테이블 ADD 열 타입`             | 열 추가                                             |
| `ALTER TABLE 테이블 ALTER 열 SET DEFAULT 값` | 열 기본값 변경 (표준 SQL)                           |
| `ALTER TABLE 테이블 DROP COLUMN 열`          | 열 삭제                                             |
| `DROP TABLE 테이블 CASCADE`                  | 테이블과 이 테이블을 참조하는 뷰·제약 조건까지 삭제 |
| `DROP TABLE 테이블 RESTRICT`                 | 다른 개체가 참조하고 있으면 삭제 거부               |
| `TRUNCATE TABLE 테이블`                      | 구조는 남기고 모든 행 삭제                          |

DROP 문의 CASCADE·RESTRICT는 표준 SQL 문법이고 SQLite는 지원하지 않는다. 외래 키의 `ON DELETE CASCADE`와 이름은 같지만 대상이 다르다. 외래 키의 CASCADE는 행을 연쇄 삭제하고, DROP의 CASCADE는 테이블에 의존하는 개체(뷰, 다른 테이블의 제약 조건)를 연쇄 삭제한다.

DELETE, TRUNCATE, DROP은 모두 무언가를 삭제하므로 한 표로 비교한다.

| 명령     | 분류 | 삭제 대상      | 구조 | WHERE 조건 | ROLLBACK             |
| -------- | ---- | -------------- | ---- | ---------- | -------------------- |
| DELETE   | DML  | 조건에 맞는 행 | 남음 | 가능       | 가능                 |
| TRUNCATE | DDL  | 모든 행        | 남음 | 불가       | 대부분 DBMS에서 불가 |
| DROP     | DDL  | 테이블 자체    | 삭제 | 불가       | 대부분 DBMS에서 불가 |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> ALTER 문의 빈칸을 채우게 한다. 예: "학생 테이블에 VARCHAR(40) 타입의 이메일 열을 추가하는 SQL을 완성하시오. `( ① ) TABLE 학생 ( ② ) 이메일 VARCHAR(40);`" 정답은 ① ALTER, ② ADD.

## DML: 데이터 조작

### INSERT, UPDATE, DELETE

| 명령   | 기본 형식                                          |
| ------ | -------------------------------------------------- |
| INSERT | `INSERT INTO 테이블 (열1, 열2) VALUES (값1, 값2);` |
| UPDATE | `UPDATE 테이블 SET 열 = 값 WHERE 조건;`            |
| DELETE | `DELETE FROM 테이블 WHERE 조건;`                   |

```sql
INSERT INTO 학생 (학번, 이름, 학년) VALUES (2408,'윤가람',2);
SELECT 학번, 이름, 학과코드, 학년 FROM 학생 WHERE 학번 = 2408;
INSERT INTO 과목 (과목코드, 과목명) VALUES ('OS202','운영체제');
SELECT * FROM 과목 WHERE 과목코드 = 'OS202';
```

| 학번 | 이름   | 학과코드 | 학년 |
| ---- | ------ | -------- | ---- |
| 2408 | 윤가람 | NULL     | 2    |

| 과목코드 | 과목명   | 학점 |
| -------- | -------- | ---- |
| OS202    | 운영체제 | 3    |

열 목록에서 생략한 열은 DEFAULT가 있으면 기본값(학점 3), 없으면 NULL(학과코드)이 들어간다.

```sql
UPDATE 수강 SET 점수 = 점수 + 5 WHERE 과목코드 = 'NW201';
SELECT changes() AS 바뀐행수;
SELECT * FROM 수강 WHERE 과목코드 = 'NW201';
DELETE FROM 수강 WHERE 점수 < 70;
SELECT changes() AS 삭제행수;
```

| 바뀐행수 |
| -------- |
| 4        |

| 학번 | 과목코드 | 점수 |
| ---- | -------- | ---- |
| 2401 | NW201    | 85   |
| 2402 | NW201    | NULL |
| 2405 | NW201    | 95   |
| 2406 | NW201    | 60   |

| 삭제행수 |
| -------- |
| 2        |

UPDATE는 NW201 4행 모두에 적용됐지만 NULL에 5를 더한 결과는 여전히 NULL이다. NULL이 들어간 산술 연산의 결과는 항상 NULL이다. 이어서 `점수 < 70` 조건의 DELETE는 2404의 SE301(67)과 2406의 NW201(60) 2행을 삭제했고, NULL인 행은 삭제하지 않았다. `NULL < 70`은 참도 거짓도 아닌 UNKNOWN이고, WHERE는 결과가 참인 행만 대상으로 삼기 때문이다.

### SELECT 기본 구조

```sql
SELECT [DISTINCT] 열 목록
FROM 테이블
[WHERE 행 조건]
[GROUP BY 그룹 기준 열]
[HAVING 그룹 조건]
[ORDER BY 정렬 기준 [ASC | DESC]];
```

![SELECT 문의 작성 순서와 논리적 처리 순서](./images/eip-practical-sql-execution-order.svg 'SELECT는 맨 앞에 쓰지만 처리 순서로는 다섯 번째다')

DBMS는 SELECT 문을 쓴 순서가 아니라 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY 순서로 처리한다고 보면 결과를 정확히 예측할 수 있다. 이 순서 때문에 WHERE에서는 집계 함수를 쓸 수 없고(아직 그룹이 없다), 집계 조건은 HAVING에 쓴다.

```sql
SELECT DISTINCT 학과코드 FROM 학생;
```

| 학과코드 |
| -------- |
| CS       |
| EE       |
| BM       |
| NULL     |

DISTINCT는 중복을 제거한다. NULL도 하나의 값처럼 한 번 나온다.

### WHERE 조건식

| 연산자                   | 뜻                         | 예                              |
| ------------------------ | -------------------------- | ------------------------------- |
| `=`, `<>`, `<`, `>=`     | 비교                       | `학년 >= 2`                     |
| `AND`, `OR`, `NOT`       | 논리 결합                  | `학과코드 = 'CS' AND 학년 >= 2` |
| `LIKE`                   | 문자열 패턴                | `이름 LIKE '%서%'`              |
| `IN (…)`                 | 목록 중 하나와 같음        | `학과코드 IN ('EE','BM')`       |
| `BETWEEN a AND b`        | a 이상 b 이하 (양 끝 포함) | `점수 BETWEEN 80 AND 90`        |
| `IS NULL`, `IS NOT NULL` | NULL 여부                  | `연락처 IS NULL`                |

LIKE의 와일드카드는 두 가지다. `%`는 0개 이상의 임의 문자, `_`는 정확히 1개의 임의 문자를 뜻한다.

```sql
SELECT 이름, 학년 FROM 학생 WHERE 학과코드 = 'CS' AND 학년 >= 2;
SELECT 이름 FROM 학생 WHERE 이름 LIKE '%서%';
SELECT 이름 FROM 학생 WHERE 이름 LIKE '_도_';
SELECT 이름, 학과코드 FROM 학생 WHERE 학과코드 IN ('EE','BM');
```

| 이름   | 학년 |
| ------ | ---- |
| 김하늘 | 2    |
| 정민서 | 3    |

| 이름 (`'%서%'`) |
| --------------- |
| 박서준          |
| 정민서          |

| 이름 (`'_도_'`) |
| --------------- |
| 이도윤          |

| 이름   | 학과코드 |
| ------ | -------- |
| 박서준 | EE       |
| 최지우 | BM       |
| 한유진 | EE       |

`'%서%'`는 "서"가 어디에든 있는 이름이므로 박서준(가운데)과 정민서(끝)가 나온다. `'_도_'`는 세 글자이면서 가운데가 "도"인 이름이다.

```sql
SELECT 학번, 과목코드, 점수 FROM 수강 WHERE 점수 BETWEEN 80 AND 90;
SELECT 이름 FROM 학생 WHERE 연락처 IS NULL;
SELECT 이름 FROM 학생 WHERE 연락처 = NULL;
```

| 학번 | 과목코드 | 점수 |
| ---- | -------- | ---- |
| 2401 | NW201    | 80   |
| 2401 | SE301    | 88   |
| 2403 | DB101    | 85   |
| 2405 | NW201    | 90   |
| 2405 | SE301    | 83   |

| 이름 (`IS NULL`) |
| ---------------- |
| 박서준           |
| 정민서           |
| 오세아           |

`연락처 = NULL`은 결과가 0행이다. NULL과의 비교는 `=`든 `<>`든 항상 UNKNOWN이 되므로, NULL 여부는 반드시 `IS NULL`로 검사한다. BETWEEN은 양 끝값 80과 90을 포함한다.

> [!WARNING] NULL과 3값 논리
> SQL의 조건식은 TRUE, FALSE, UNKNOWN 세 값을 가진다. NULL과 비교하면 UNKNOWN이 되고, `TRUE AND UNKNOWN`은 UNKNOWN, `TRUE OR UNKNOWN`은 TRUE, `NOT UNKNOWN`은 UNKNOWN이다. WHERE와 HAVING은 TRUE인 행만 통과시킨다.

```sql
SELECT 학번, 과목코드, 점수 FROM 수강 ORDER BY 과목코드 ASC, 점수 DESC;
```

| 학번 | 과목코드 | 점수 |
| ---- | -------- | ---- |
| 2401 | DB101    | 95   |
| 2403 | DB101    | 85   |
| 2405 | DB101    | 78   |
| 2402 | DB101    | 72   |
| 2405 | NW201    | 90   |
| 2401 | NW201    | 80   |
| 2406 | NW201    | 55   |
| 2402 | NW201    | NULL |
| 2403 | SE301    | 91   |
| 2401 | SE301    | 88   |
| 2405 | SE301    | 83   |
| 2404 | SE301    | 67   |

첫 번째 기준(과목코드 오름차순)으로 정렬하고, 과목코드가 같은 행끼리만 두 번째 기준(점수 내림차순)을 적용한다. ASC는 생략할 수 있다. NULL의 정렬 위치는 DBMS마다 다르다. SQLite와 MySQL은 NULL을 가장 작은 값으로 보아 내림차순에서 맨 뒤에 두고, Oracle과 PostgreSQL은 NULL을 가장 큰 값으로 보아 내림차순에서 맨 앞에 둔다. 표준 SQL의 `NULLS FIRST`, `NULLS LAST`로 위치를 직접 지정할 수 있다.

## 집계 함수와 GROUP BY

### 집계 함수와 NULL

| 함수         | 하는 일                       | NULL 처리      |
| ------------ | ----------------------------- | -------------- |
| `COUNT(*)`   | 행 수                         | NULL 행도 집계 |
| `COUNT(열)`  | 그 열이 NULL이 아닌 행 수     | NULL 제외      |
| `SUM(열)`    | 합계                          | NULL 제외      |
| `AVG(열)`    | 평균 (합계 ÷ NULL 아닌 행 수) | NULL 제외      |
| `MAX`, `MIN` | 최댓값, 최솟값                | NULL 제외      |

```sql
SELECT COUNT(*) AS 전체행, COUNT(점수) AS 점수있는행, SUM(점수) AS 합계,
       AVG(점수) AS 평균, MAX(점수) AS 최고, MIN(점수) AS 최저
FROM 수강;
```

| 전체행 | 점수있는행 | 합계 | 평균              | 최고 | 최저 |
| ------ | ---------- | ---- | ----------------- | ---- | ---- |
| 12     | 11         | 884  | 80.36363636363636 | 95   | 55   |

평균은 884 ÷ 12가 아니라 884 ÷ 11이다. AVG는 NULL인 행을 분모에서도 뺀다. 이도윤(2402)의 평균을 구하면 이 차이가 분명해진다.

```sql
SELECT AVG(점수) FROM 수강 WHERE 학번 = 2402;
```

| AVG(점수) |
| --------- |
| 72.0      |

이도윤의 수강 행은 DB101(72)과 NW201(NULL) 2행이지만 평균은 72 ÷ 1 = 72.0이다. NULL을 0점으로 처리하려면 `AVG(COALESCE(점수, 0))`처럼 NULL을 다른 값으로 바꾸는 함수를 써야 한다.

### GROUP BY와 HAVING

GROUP BY는 지정한 열의 값이 같은 행끼리 묶어 그룹마다 집계 함수를 적용한다. HAVING은 그룹을 만든 뒤 그룹 단위로 조건을 건다.

```sql
SELECT 과목코드, COUNT(*) AS 수강인원, ROUND(AVG(점수),1) AS 평균
FROM 수강 GROUP BY 과목코드;
```

| 과목코드 | 수강인원 | 평균 |
| -------- | -------- | ---- |
| DB101    | 4        | 82.5 |
| NW201    | 4        | 75.0 |
| SE301    | 4        | 82.3 |

NW201의 평균은 (80 + 55 + 90) ÷ 3 = 75.0이다. 수강인원은 `COUNT(*)`라서 NULL 행을 포함한 4다.

```sql
SELECT 학번, COUNT(*) AS 과목수, SUM(점수) AS 총점
FROM 수강 GROUP BY 학번 HAVING COUNT(*) >= 2 ORDER BY 총점 DESC;
```

| 학번 | 과목수 | 총점 |
| ---- | ------ | ---- |
| 2401 | 3      | 263  |
| 2405 | 3      | 251  |
| 2403 | 2      | 176  |
| 2402 | 2      | 72   |

WHERE와 HAVING을 함께 쓰면 WHERE가 먼저 행을 거르고, 남은 행으로 그룹을 만든 뒤 HAVING이 그룹을 거른다.

```sql
SELECT 과목코드, ROUND(AVG(점수),1) AS 평균
FROM 수강 WHERE 점수 >= 70 GROUP BY 과목코드 HAVING AVG(점수) >= 85;
```

| 과목코드 | 평균 |
| -------- | ---- |
| NW201    | 85.0 |
| SE301    | 87.3 |

계산 과정을 단계로 따라가면 다음과 같다.

1. WHERE `점수 >= 70`이 55점(2406 NW201), 67점(2404 SE301), NULL(2402 NW201) 행을 제외한다.
2. 남은 행을 과목코드로 묶는다. DB101은 95, 72, 85, 78이고 NW201은 80, 90이고 SE301은 88, 91, 83이다.
3. 그룹별 평균을 계산한다.

```math
\text{DB101} = \frac{95+72+85+78}{4} = 82.5,\quad \text{NW201} = \frac{80+90}{2} = 85.0,\quad \text{SE301} = \frac{88+91+83}{3} \approx 87.3
```

4. HAVING `AVG(점수) >= 85`가 DB101(82.5)을 제외한다.

| 과목코드 | WHERE 후 행 수 | 평균 | HAVING 통과 |
| -------- | -------------- | ---- | ----------- |
| DB101    | 4              | 82.5 | 아니오      |
| NW201    | 2              | 85.0 | 예          |
| SE301    | 3              | 87.3 | 예          |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> GROUP BY 결과를 표로 쓰거나, `COUNT(*)`와 `COUNT(열)`의 차이를 이용해 값을 쓰게 한다. "WHERE 절에 집계 함수를 쓸 수 없으므로 그룹 조건에 쓰는 절"을 묻는 빈칸 문제도 나온다. 정답은 HAVING.

## 조인

### 조인의 종류

조인(Join)은 두 테이블의 행을 조건에 따라 이어 붙여 하나의 결과로 만드는 연산이다. 학생 테이블에는 학과코드만 있으므로, 학과명을 함께 보려면 학과 테이블과 조인해야 한다.

![학생과 학과의 조인에서 짝이 없는 행](./images/eip-practical-sql-joins.svg '주황색 두 행은 짝이 없어서 조인 종류에 따라 결과에 포함되거나 빠진다')

| 조인             | 결과                                                         |
| ---------------- | ------------------------------------------------------------ |
| INNER JOIN       | 조인 조건을 만족하는 짝이 있는 행만                          |
| LEFT OUTER JOIN  | 내부 조인 결과 + 왼쪽 테이블의 짝 없는 행 (오른쪽 열은 NULL) |
| RIGHT OUTER JOIN | 내부 조인 결과 + 오른쪽 테이블의 짝 없는 행                  |
| FULL OUTER JOIN  | 내부 조인 결과 + 양쪽의 짝 없는 행 모두                      |
| NATURAL JOIN     | 이름이 같은 열을 자동으로 동등 조인, 공통 열은 한 번만 표시  |
| CROSS JOIN       | 조건 없이 모든 행의 조합 (행 수 = 왼쪽 × 오른쪽)             |
| SELF JOIN        | 같은 테이블을 별칭 두 개로 조인                              |

### 내부 조인과 외부 조인 실행 결과

```sql
SELECT s.이름, d.학과명 FROM 학생 s INNER JOIN 학과 d ON s.학과코드 = d.학과코드;
```

| 이름   | 학과명     |
| ------ | ---------- |
| 김하늘 | 컴퓨터공학 |
| 이도윤 | 컴퓨터공학 |
| 박서준 | 전자공학   |
| 최지우 | 경영학     |
| 정민서 | 컴퓨터공학 |
| 한유진 | 전자공학   |

학과코드가 NULL인 오세아는 `NULL = 'CS'`가 UNKNOWN이라 어떤 학과와도 짝이 되지 않고, 학생이 없는 수학과도 빠져 6행이다.

```sql
SELECT s.이름, d.학과명 FROM 학생 s LEFT OUTER JOIN 학과 d ON s.학과코드 = d.학과코드;
SELECT s.이름, d.학과명 FROM 학생 s RIGHT OUTER JOIN 학과 d ON s.학과코드 = d.학과코드;
SELECT s.이름, d.학과명 FROM 학생 s FULL OUTER JOIN 학과 d ON s.학과코드 = d.학과코드;
```

LEFT OUTER JOIN 결과 (내부 조인 6행 아래에 1행 추가, 7행):

| 이름   | 학과명 |
| ------ | ------ |
| …      | …      |
| 오세아 | NULL   |

RIGHT OUTER JOIN 결과 (내부 조인 6행 아래에 1행 추가, 7행):

| 이름 | 학과명 |
| ---- | ------ |
| …    | …      |
| NULL | 수학   |

FULL OUTER JOIN 결과 (내부 조인 6행 아래에 2행 추가, 8행):

| 이름   | 학과명 |
| ------ | ------ |
| …      | …      |
| 오세아 | NULL   |
| NULL   | 수학   |

세 결과 모두 앞 6행은 내부 조인 결과와 같아 `…`로 줄였다. RIGHT·FULL OUTER JOIN은 SQLite 3.39.0부터 지원한다.

외부 조인은 "짝이 없는 행 찾기"에 자주 쓴다. 아무도 수강하지 않은 과목을 찾으려면 과목을 왼쪽에 두고 LEFT JOIN한 뒤, 오른쪽 열이 NULL인 행만 남긴다.

```sql
SELECT 과목명 FROM 과목 c LEFT JOIN 수강 e ON c.과목코드 = e.과목코드 WHERE e.학번 IS NULL;
```

| 과목명   |
| -------- |
| 인공지능 |

### 3개 테이블 조인

```sql
SELECT s.이름, c.과목명, e.점수
FROM 수강 e
JOIN 학생 s ON e.학번 = s.학번
JOIN 과목 c ON e.과목코드 = c.과목코드
WHERE s.학과코드 = 'CS'
ORDER BY s.이름, c.과목명;
```

| 이름   | 과목명         | 점수 |
| ------ | -------------- | ---- |
| 김하늘 | 네트워크       | 80   |
| 김하늘 | 데이터베이스   | 95   |
| 김하늘 | 소프트웨어공학 | 88   |
| 이도윤 | 네트워크       | NULL |
| 이도윤 | 데이터베이스   | 72   |
| 정민서 | 네트워크       | 90   |
| 정민서 | 데이터베이스   | 78   |
| 정민서 | 소프트웨어공학 | 83   |

### 자연 조인, 교차 조인, 셀프 조인

```sql
SELECT 이름, 학과명 FROM 학생 NATURAL JOIN 학과;
SELECT COUNT(*) AS 행수 FROM 학생 CROSS JOIN 과목;
```

NATURAL JOIN은 두 테이블에 공통으로 있는 열 이름(학과코드)으로 자동 조인해 내부 조인과 같은 6행을 돌려준다. 열 이름만 같고 의미가 다른 열이 있으면 의도하지 않은 조건이 붙으므로 실무에서는 잘 쓰지 않는다. CROSS JOIN은 학생 7행 × 과목 4행 = 28행이다.

| 행수 (CROSS JOIN) |
| ----------------- |
| 28                |

셀프 조인은 같은 테이블에 별칭 두 개를 붙여 한쪽을 후배, 다른 쪽을 멘토로 본다.

![멘토학번으로 학생 테이블을 자기 자신과 조인](./images/eip-practical-sql-self-join.svg '후배 쪽 행의 멘토학번이 멘토 쪽 행의 학번과 같으면 짝이 된다')

```sql
SELECT 후배.이름 AS 후배, 멘토.이름 AS 멘토
FROM 학생 후배 JOIN 학생 멘토 ON 후배.멘토학번 = 멘토.학번;
```

| 후배   | 멘토   |
| ------ | ------ |
| 이도윤 | 김하늘 |
| 정민서 | 김하늘 |
| 한유진 | 박서준 |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 두 테이블과 조인 SQL을 주고 결과 행 수를 쓰게 한다. 외부 조인에서는 짝이 없는 행이 추가되는지, 조인 조건 열에 NULL이 있는지를 먼저 확인한다. CROSS JOIN의 행 수는 곱, 카티션 프로덕트의 차수(열 수)는 합이다.

## 서브쿼리

서브쿼리(Subquery, 하위 질의)는 SQL 문 안에 들어간 또 다른 SELECT 문이다. 괄호로 감싸며, 바깥 쿼리(메인 쿼리)가 서브쿼리의 결과를 조건이나 값으로 사용한다.

| 종류             | 결과                  | 함께 쓰는 연산자             |
| ---------------- | --------------------- | ---------------------------- |
| 단일 행 서브쿼리 | 값 1개                | `=`, `>`, `<`                |
| 다중 행 서브쿼리 | 값 여러 개            | `IN`, `ANY`, `ALL`, `EXISTS` |
| 상관 서브쿼리    | 바깥 행마다 다시 실행 | 바깥 테이블의 열을 참조      |
| 스칼라 서브쿼리  | SELECT 절에서 값 1개  | 열처럼 사용                  |

```sql
SELECT 이름 FROM 학생 WHERE 학번 IN (SELECT 학번 FROM 수강 WHERE 과목코드 = 'SE301');
SELECT 학번, 과목코드, 점수 FROM 수강 WHERE 점수 > (SELECT AVG(점수) FROM 수강);
```

| 이름 (SE301 수강생) |
| ------------------- |
| 김하늘              |
| 박서준              |
| 최지우              |
| 정민서              |

| 학번 | 과목코드 | 점수 |
| ---- | -------- | ---- |
| 2401 | DB101    | 95   |
| 2401 | SE301    | 88   |
| 2403 | DB101    | 85   |
| 2403 | SE301    | 91   |
| 2405 | NW201    | 90   |
| 2405 | SE301    | 83   |

두 번째 쿼리의 서브쿼리는 앞에서 구한 전체 평균 80.36…을 돌려주고, 바깥 쿼리는 그보다 큰 6행을 남긴다(80점은 평균보다 작아 빠진다).

상관 서브쿼리는 서브쿼리 안에서 바깥 쿼리의 열(`e1.과목코드`)을 참조하므로, 바깥 행 하나마다 서브쿼리가 다시 계산된다. 과목별 최고점 행을 찾는 쿼리가 대표적이다.

```sql
SELECT 학번, 과목코드, 점수 FROM 수강 e1
WHERE 점수 = (SELECT MAX(점수) FROM 수강 e2 WHERE e2.과목코드 = e1.과목코드);
```

| 학번 | 과목코드 | 점수 |
| ---- | -------- | ---- |
| 2401 | DB101    | 95   |
| 2403 | SE301    | 91   |
| 2405 | NW201    | 90   |

EXISTS는 서브쿼리 결과가 한 행이라도 있으면 참이다. 수강 기록이 없는 학생은 NOT EXISTS로 찾는다.

```sql
SELECT 이름 FROM 학생 s WHERE NOT EXISTS (SELECT 1 FROM 수강 e WHERE e.학번 = s.학번);
SELECT 이름, (SELECT COUNT(*) FROM 수강 e WHERE e.학번 = s.학번) AS 수강과목수 FROM 학생 s;
```

| 이름 (수강 기록 없음) |
| --------------------- |
| 오세아                |

| 이름   | 수강과목수 |
| ------ | ---------- |
| 김하늘 | 3          |
| 이도윤 | 2          |
| 박서준 | 2          |
| 최지우 | 1          |
| 정민서 | 3          |
| 한유진 | 1          |
| 오세아 | 0          |

### NOT IN과 NULL 함정

멘토가 아닌 학생(누구의 멘토도 아닌 학생)을 NOT IN으로 구하면 예상과 다른 결과가 나온다.

```sql
SELECT COUNT(*) FROM 학생 WHERE 학번 NOT IN (SELECT 멘토학번 FROM 학생);
SELECT COUNT(*) FROM 학생 WHERE 학번 NOT IN (SELECT 멘토학번 FROM 학생 WHERE 멘토학번 IS NOT NULL);
```

| 첫 번째 COUNT(\*) |
| ----------------- |
| 0                 |

| 두 번째 COUNT(\*) |
| ----------------- |
| 5                 |

![NOT IN 목록에 NULL이 있으면 결과가 비는 이유](./images/eip-practical-sql-not-in-null.svg 'NOT IN은 목록의 모든 값과 다르다는 AND 조건이라서, 하나라도 UNKNOWN이면 전체가 TRUE가 되지 못한다')

서브쿼리 `SELECT 멘토학번 FROM 학생`의 결과에는 NULL이 4개 들어 있다. `학번 NOT IN (2401, 2403, NULL)`은 `학번 <> 2401 AND 학번 <> 2403 AND 학번 <> NULL`과 같은데, 마지막 항이 항상 UNKNOWN이라 전체가 TRUE가 되는 행이 없다. 서브쿼리에서 NULL을 걸러 내면 2401과 2403을 뺀 5명이 나온다. NOT EXISTS는 이 문제가 없다.

## 집합 연산

집합 연산자는 두 SELECT 결과를 집합처럼 합치거나 비교한다. 두 SELECT의 열 개수와 각 열의 자료형이 맞아야 한다.

![DB101 수강생과 SE301 수강생의 집합 연산](./images/eip-practical-sql-set-ops.svg '두 원이 겹치는 부분의 학번 3개가 INTERSECT 결과다')

| 연산자    | 결과                    | 중복 |
| --------- | ----------------------- | ---- |
| UNION     | 합집합                  | 제거 |
| UNION ALL | 합집합                  | 유지 |
| INTERSECT | 교집합                  | 제거 |
| EXCEPT    | 차집합 (Oracle은 MINUS) | 제거 |

```sql
SELECT 학번 FROM 수강 WHERE 과목코드 = 'DB101'
UNION
SELECT 학번 FROM 수강 WHERE 과목코드 = 'SE301';
```

| UNION | UNION ALL | INTERSECT | EXCEPT |
| ----- | --------- | --------- | ------ |
| 2401  | 2401      | 2401      | 2402   |
| 2402  | 2402      | 2403      |        |
| 2403  | 2403      | 2405      |        |
| 2404  | 2405      |           |        |
| 2405  | 2401      |           |        |
|       | 2403      |           |        |
|       | 2404      |           |        |
|       | 2405      |           |        |

위 표는 연산자만 바꿔 네 번 실행한 결과를 열로 나란히 놓은 것이다. UNION ALL은 DB101 수강생 4명 다음에 SE301 수강생 4명을 그대로 이어 8행이 되고, UNION은 중복을 제거해 5행이다. EXCEPT는 DB101은 들었지만 SE301은 듣지 않은 2402 한 명이다.

## 뷰와 인덱스

### 뷰

뷰(View)는 SELECT 문에 이름을 붙여 테이블처럼 쓰는 가상 테이블이다. 뷰 자체는 데이터를 보관하지 않고, 조회할 때마다 정의된 SELECT를 실행한다.

```sql
CREATE VIEW 우수수강 AS
SELECT s.이름, e.과목코드, e.점수 FROM 수강 e JOIN 학생 s ON e.학번 = s.학번 WHERE e.점수 >= 85;
SELECT * FROM 우수수강;
UPDATE 수강 SET 점수 = 86 WHERE 학번 = 2401 AND 과목코드 = 'NW201';
SELECT * FROM 우수수강;
UPDATE 우수수강 SET 점수 = 100;
```

학생 2405를 삭제한 뒤의 상태에서 실행한 결과다.

| 이름 (갱신 전) | 과목코드 | 점수 |
| -------------- | -------- | ---- |
| 김하늘         | DB101    | 95   |
| 김하늘         | SE301    | 88   |
| 박서준         | DB101    | 85   |
| 박서준         | SE301    | 91   |

| 이름 (갱신 후) | 과목코드 | 점수 |
| -------------- | -------- | ---- |
| 김하늘         | DB101    | 95   |
| 김하늘         | NW201    | 86   |
| 김하늘         | SE301    | 88   |
| 박서준         | DB101    | 85   |
| 박서준         | SE301    | 91   |

```text
Parse error near line 9: cannot modify 우수수강 because it is a view
```

원본 테이블의 점수를 86으로 바꾸자 뷰를 다시 조회하자 그 행이 나타났다. 뷰가 데이터를 복사해 두지 않고 매번 원본에서 계산하기 때문이다. 조인으로 만든 뷰는 SQLite에서 수정할 수 없다(INSTEAD OF 트리거를 따로 만들면 가능하다).

| 장점                                                | 단점                                                         |
| --------------------------------------------------- | ------------------------------------------------------------ |
| 복잡한 쿼리를 단순하게 재사용                       | 독립적인 인덱스를 가질 수 없다                               |
| 필요한 열만 보여 줘 보안(접근 제어)에 유리          | 정의를 바꾸려면 삭제 후 다시 만들어야 한다 (ALTER VIEW 없음) |
| 원본 구조가 바뀌어도 뷰 이름은 유지 (논리적 독립성) | 조인·집계 뷰는 INSERT·UPDATE·DELETE에 제약                   |

뷰를 삭제하면 그 뷰를 기반으로 만든 다른 뷰도 함께 삭제된다(`DROP VIEW … CASCADE`). 국내 시험에서는 "뷰는 ALTER 문으로 정의를 변경할 수 없다"를 특징으로 묻는다. 실제 DBMS 중 MySQL과 SQL Server는 `ALTER VIEW`를 제공하므로, 이 특징은 표준 SQL과 시험 기준으로 기억해 둔다.

### 인덱스

인덱스(Index)는 특정 열의 값과 그 값이 있는 행의 위치를 정렬해 보관하는 별도 자료 구조다. 책 뒤의 "찾아보기"처럼, 전체를 처음부터 읽지 않고 원하는 값을 빠르게 찾게 한다. 대부분의 DBMS는 B-트리 계열 구조로 인덱스를 만든다.

```sql
CREATE INDEX idx_수강_과목 ON 수강(과목코드);
EXPLAIN QUERY PLAN SELECT * FROM 수강 WHERE 과목코드 = 'DB101';
DROP INDEX idx_수강_과목;
EXPLAIN QUERY PLAN SELECT * FROM 수강 WHERE 과목코드 = 'DB101';
```

```text
QUERY PLAN
`--SEARCH 수강 USING INDEX idx_수강_과목 (과목코드=?)

QUERY PLAN
`--SCAN 수강
```

`EXPLAIN QUERY PLAN`은 DBMS가 쿼리를 어떻게 실행할지 보여 준다. 인덱스가 있으면 인덱스로 해당 값만 찾는 SEARCH, 인덱스를 삭제한 뒤에는 테이블 전체를 처음부터 읽는 SCAN으로 바뀌었다.

| 구분              | 설명                                                        |
| ----------------- | ----------------------------------------------------------- |
| 조회 성능         | WHERE·JOIN·ORDER BY에 쓰는 열에 만들면 빨라진다             |
| 변경 성능         | INSERT·UPDATE·DELETE 때마다 인덱스도 갱신해야 해서 느려진다 |
| 저장 공간         | 별도 공간을 차지한다                                        |
| 기본 키·UNIQUE    | 대부분의 DBMS가 자동으로 인덱스를 만든다                    |
| 클러스터드 인덱스 | 인덱스 순서대로 실제 행을 정렬해 보관. 테이블당 1개         |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> `CREATE ( ① ) idx_이름 ( ② ) 학생(이름);`처럼 인덱스 생성문의 빈칸을 채우게 한다. 정답은 ① INDEX, ② ON. 고유 인덱스는 `CREATE UNIQUE INDEX`로 만든다.

## DCL과 TCL

### GRANT와 REVOKE

DCL은 사용자에게 권한을 주고 회수한다. SQLite는 파일 하나를 직접 여는 내장형 DBMS라 사용자 계정 개념이 없고, GRANT를 실행하면 구문 오류가 난다.

```text
Parse error in 2nd command line argument: near "GRANT": syntax error
```

따라서 아래는 표준 SQL 문법 설명이며 실행 결과는 싣지 않는다.

```sql
GRANT SELECT, INSERT ON 학생 TO kim;
GRANT SELECT ON 수강 TO lee WITH GRANT OPTION;
REVOKE INSERT ON 학생 FROM kim;
REVOKE SELECT ON 수강 FROM lee CASCADE;
```

| 구문                              | 뜻                                                            |
| --------------------------------- | ------------------------------------------------------------- |
| `GRANT 권한 ON 개체 TO 사용자`    | 권한 부여. 권한은 SELECT, INSERT, UPDATE, DELETE, ALL 등      |
| `WITH GRANT OPTION`               | 받은 권한을 다른 사용자에게 다시 부여할 수 있는 권한까지 준다 |
| `REVOKE 권한 ON 개체 FROM 사용자` | 권한 회수. GRANT는 TO, REVOKE는 FROM                          |
| `CASCADE`                         | 회수 대상이 다른 사용자에게 재부여한 권한까지 연쇄 회수       |
| `RESTRICT`                        | 재부여한 권한이 있으면 회수를 거부                            |
| `GRANT OPTION FOR`                | 권한 자체는 두고 재부여 권한만 회수                           |

예를 들어 lee가 WITH GRANT OPTION으로 받은 SELECT 권한을 park에게 다시 줬다면, `REVOKE SELECT ON 수강 FROM lee CASCADE`는 lee와 park의 권한을 모두 회수한다.

롤(Role)은 권한을 묶은 이름이다. 사용자가 많으면 권한을 사용자마다 주는 대신 롤에 권한을 모아 두고, 사용자에게 롤을 부여한다.

```sql
CREATE ROLE 조교;
GRANT SELECT, UPDATE ON 수강 TO 조교;
GRANT 조교 TO kim, lee;
```

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> GRANT·REVOKE 문의 빈칸이 자주 나온다. 예: "사용자 kim에게 학생 테이블의 UPDATE 권한을 부여하고, kim이 이 권한을 다른 사용자에게 부여할 수 있게 하시오. `GRANT UPDATE ( ① ) 학생 ( ② ) kim ( ③ );`" 정답은 ① ON, ② TO, ③ WITH GRANT OPTION.

### 트랜잭션과 TCL

트랜잭션(Transaction)은 데이터베이스의 상태를 바꾸는 하나의 논리적 작업 단위다. 계좌 이체는 "A 계좌에서 출금"과 "B 계좌에 입금" 두 UPDATE로 이뤄지는데, 출금만 되고 입금 전에 서버가 멈추면 돈이 사라진다. 두 UPDATE를 한 트랜잭션으로 묶으면 둘 다 반영되거나 둘 다 취소된다.

| 명령                        | 하는 일                                               |
| --------------------------- | ----------------------------------------------------- |
| `BEGIN` (START TRANSACTION) | 트랜잭션 시작                                         |
| `COMMIT`                    | 트랜잭션의 모든 변경을 확정해 영구 반영               |
| `ROLLBACK`                  | 트랜잭션의 모든 변경을 취소하고 시작 전 상태로 되돌림 |
| `SAVEPOINT 이름`            | 트랜잭션 중간에 되돌아갈 지점을 표시                  |
| `ROLLBACK TO 이름`          | 표시한 지점 이후의 변경만 취소                        |

```sql
BEGIN;
UPDATE 수강 SET 점수 = 0 WHERE 과목코드 = 'DB101';
ROLLBACK;
SELECT 학번, 점수 FROM 수강 WHERE 과목코드 = 'DB101';
```

| 학번 | 점수 |
| ---- | ---- |
| 2401 | 95   |
| 2402 | 72   |
| 2403 | 85   |
| 2405 | 78   |

ROLLBACK으로 DB101 점수를 0으로 바꾼 UPDATE가 취소되어 원래 점수가 그대로다.

![SAVEPOINT와 ROLLBACK TO의 동작](./images/eip-practical-sql-savepoint.svg 'ROLLBACK TO sp1은 sp1 이전의 OS202 추가는 남기고 그 뒤의 작업만 취소한다')

```sql
BEGIN;
INSERT INTO 과목 VALUES ('OS202','운영체제',3);
SAVEPOINT sp1;
INSERT INTO 과목 VALUES ('CG303','컴퓨터그래픽스',3);
SAVEPOINT sp2;
DELETE FROM 과목 WHERE 과목코드 = 'AI401';
ROLLBACK TO sp1;
COMMIT;
SELECT 과목코드, 과목명 FROM 과목;
```

| 과목코드 | 과목명         |
| -------- | -------------- |
| DB101    | 데이터베이스   |
| NW201    | 네트워크       |
| SE301    | 소프트웨어공학 |
| AI401    | 인공지능       |
| OS202    | 운영체제       |

ROLLBACK TO sp1이 CG303 추가와 AI401 삭제를 취소했고, sp1 이전에 넣은 OS202만 COMMIT으로 확정되어 5행이 됐다.

### 트랜잭션 특성 ACID

| 특성           | 영문        | 뜻                                                                             | 담당 기능 예           |
| -------------- | ----------- | ------------------------------------------------------------------------------ | ---------------------- |
| 원자성         | Atomicity   | 트랜잭션의 연산은 모두 반영되거나 하나도 반영되지 않아야 한다 (All or Nothing) | COMMIT, ROLLBACK, 회복 |
| 일관성         | Consistency | 트랜잭션이 끝나면 데이터베이스는 무결성 제약을 만족하는 상태여야 한다          | 제약 조건 검사         |
| 격리성(독립성) | Isolation   | 동시에 실행되는 트랜잭션은 서로의 중간 결과를 볼 수 없다                       | 잠금(Lock), 병행 제어  |
| 영속성(지속성) | Durability  | COMMIT된 결과는 장애가 나도 사라지지 않아야 한다                               | 로그, 회복 기법        |

트랜잭션은 실행 중 다음 상태를 거친다.

| 상태      | 영문                | 뜻                                   |
| --------- | ------------------- | ------------------------------------ |
| 활동      | Active              | 트랜잭션이 실행 중                   |
| 부분 완료 | Partially Committed | 마지막 연산까지 실행했지만 COMMIT 전 |
| 완료      | Committed           | COMMIT으로 성공적으로 종료           |
| 실패      | Failed              | 오류로 더 이상 정상 진행할 수 없음   |
| 철회      | Aborted             | ROLLBACK으로 시작 전 상태로 복구됨   |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> ACID 각 특성의 설명을 주고 이름을 쓰게 한다. 예: "이체 도중 장애가 발생해도 출금과 입금 중 하나만 반영되는 일이 없어야 한다는 특성을 쓰시오." 정답은 원자성(Atomicity).

## 관계대수

### 연산자와 SQL 대응

관계대수(Relational Algebra)는 원하는 결과를 얻기 위해 어떤 연산을 어떤 순서로 적용하는지 기술하는 절차적 언어다. SQL은 원하는 결과가 무엇인지만 적는 비절차적 언어이고, DBMS는 내부에서 SQL을 관계대수 연산으로 바꿔 실행 계획을 세운다. 무엇을 원하는지 기술하는 관계해석(Relational Calculus)은 비절차적 언어로, 관계대수와 짝으로 나온다.

![관계대수 연산자와 SQL 대응](./images/eip-practical-sql-relational-algebra.svg '위 네 개는 관계 데이터베이스용으로 만든 연산자, 아래 네 개는 수학의 집합 연산을 그대로 쓴 연산자다')

| 기호 | 이름                       | 표기 예                                | 같은 SQL                                        |
| ---- | -------------------------- | -------------------------------------- | ----------------------------------------------- |
| σ    | 셀렉트 (Select)            | `σ 학년=1 (학생)`                      | `SELECT * FROM 학생 WHERE 학년 = 1`             |
| π    | 프로젝트 (Project)         | `π 이름 (학생)`                        | `SELECT DISTINCT 이름 FROM 학생`                |
| ⋈    | 조인 (Join)                | `학생 ⋈ 학과코드 학과`                 | `SELECT * FROM 학생 JOIN 학과 USING (학과코드)` |
| ÷    | 디비전 (Division)          | `수강[학번,과목코드] ÷ 과목[과목코드]` | NOT EXISTS 이중 부정 (아래)                     |
| ∪    | 합집합 (Union)             | `R ∪ S`                                | `UNION`                                         |
| ∩    | 교집합 (Intersection)      | `R ∩ S`                                | `INTERSECT`                                     |
| −    | 차집합 (Difference)        | `R − S`                                | `EXCEPT`                                        |
| ×    | 교차곱 (Cartesian Product) | `R × S`                                | `CROSS JOIN`                                    |

시험에서 혼동이 잦은 짝은 σ와 π다. 셀렉트(σ)는 SQL의 SELECT가 아니라 WHERE에 해당해 ==행을 고르고==, 프로젝트(π)가 SELECT 열 목록에 해당해 ==열을 고른다==. 관계대수의 결과는 릴레이션(집합)이라 중복이 없으므로 π는 DISTINCT를 붙인 SELECT와 같다.

교차곱의 결과 크기는 다음과 같이 계산한다. 학생(열 6개, 행 7개)과 과목(열 3개, 행 4개)의 교차곱이라면 다음과 같다.

| 기호                    | 뜻          | 값             |
| ----------------------- | ----------- | -------------- |
| 차수(Degree)            | 열(속성) 수 | 학생 6, 과목 3 |
| 카디널리티(Cardinality) | 행(튜플) 수 | 학생 7, 과목 4 |

```math
\text{차수} = 6 + 3 = 9,\qquad \text{카디널리티} = 7 \times 4 = 28
```

카디널리티 28은 앞의 CROSS JOIN 실행 결과와 같다.

### 디비전

디비전(÷)은 "B의 모든 값과 짝을 이루는 A의 값"을 구한다. 수강[학번, 과목코드] ÷ 3학점과목[과목코드]는 3학점 과목 세 개(DB101, NW201, SE301)를 모두 수강한 학번이다.

![수강 ÷ 3학점 과목](./images/eip-practical-sql-division.svg '학번마다 세 과목 칸이 모두 채워졌는지 확인하면 디비전 결과가 나온다')

SQL에는 디비전 연산자가 없어 "수강하지 않은 3학점 과목이 하나도 없는 학생"이라는 이중 부정으로 쓴다.

```sql
SELECT 이름 FROM 학생 s
WHERE NOT EXISTS (
  SELECT * FROM 과목 c
  WHERE c.학점 = 3
    AND NOT EXISTS (SELECT * FROM 수강 e WHERE e.학번 = s.학번 AND e.과목코드 = c.과목코드)
);
```

| 이름   |
| ------ |
| 김하늘 |
| 정민서 |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 기호를 주고 이름을 쓰게 하거나("σ의 이름을 쓰시오"), 관계대수식을 SQL로 바꾸게 한다. 교재와 시험지에서는 조건과 속성을 기호 오른쪽 아래에 작게 적는다(σ 아래 첨자로 학년=1). 순수 관계 연산자 4개(셀렉트, 프로젝트, 조인, 디비전)와 일반 집합 연산자 4개(합집합, 교집합, 차집합, 교차곱)로 분류하는 문제도 나온다.

## 이상 현상과 정규화

### 이상 현상

정규화하지 않은 테이블에 여러 종류의 정보를 한꺼번에 보관하면 데이터를 넣고 지우고 고칠 때마다 문제가 생긴다. 예제의 네 테이블을 조인해 하나로 합친 표를 만들어 보면 그 이유가 보인다.

```sql
SELECT e.학번, s.이름, s.학과코드, d.학과명, e.과목코드, e.점수
FROM 수강 e JOIN 학생 s ON e.학번 = s.학번 LEFT JOIN 학과 d ON s.학과코드 = d.학과코드
WHERE e.학번 IN (2401, 2402, 2406);
```

| 학번 | 이름   | 학과코드 | 학과명     | 과목코드 | 점수 |
| ---- | ------ | -------- | ---------- | -------- | ---- |
| 2401 | 김하늘 | CS       | 컴퓨터공학 | DB101    | 95   |
| 2401 | 김하늘 | CS       | 컴퓨터공학 | NW201    | 80   |
| 2401 | 김하늘 | CS       | 컴퓨터공학 | SE301    | 88   |
| 2402 | 이도윤 | CS       | 컴퓨터공학 | DB101    | 72   |
| 2402 | 이도윤 | CS       | 컴퓨터공학 | NW201    | NULL |
| 2406 | 한유진 | EE       | 전자공학   | NW201    | 55   |

이 표가 실제 저장 구조(가칭 수강신청 테이블, 기본 키는 (학번, 과목코드))라고 하면 다음 세 가지 이상 현상(Anomaly)이 생긴다.

| 이상 현상 | 뜻                                                           | 이 표에서의 예                                                               |
| --------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 삽입 이상 | 원하지 않는 값까지 함께 넣어야 저장할 수 있다                | 학생이 없는 수학과(MA)를 저장하려면 학번과 과목코드가 필요해 넣을 수 없다    |
| 삭제 이상 | 행을 삭제하면 남겨야 할 정보까지 사라진다                    | 한유진의 NW201 수강을 취소하면 EE가 전자공학이라는 정보도 함께 사라진다      |
| 갱신 이상 | 같은 정보가 여러 행에 중복되어 일부만 바뀌면 불일치가 생긴다 | 컴퓨터공학 학과명을 바꾸면서 5행 중 일부만 고치면 같은 CS가 두 이름을 가진다 |

### 함수 종속과 정규형

함수 종속(Functional Dependency)은 한 속성 값이 정해지면 다른 속성 값이 하나로 정해지는 관계로, `X → Y`라고 쓰고 "X가 Y를 결정한다"고 읽는다. X를 결정자, Y를 종속자라고 한다. 수강신청 테이블의 함수 종속은 다음과 같다.

| 함수 종속                | 종류                                                 |
| ------------------------ | ---------------------------------------------------- |
| (학번, 과목코드) → 점수  | 완전 함수 종속: 기본 키 전체가 있어야 결정된다       |
| 학번 → 이름, 학과코드    | 부분 함수 종속: 기본 키의 일부(학번)만으로 결정된다  |
| 학번 → 학과코드 → 학과명 | 이행 함수 종속: A → B이고 B → C라서 A → C가 성립한다 |

![정규화 단계별 제거 대상](./images/eip-practical-sql-normalization.svg '아래로 내려갈수록 제거하는 종속이 바뀐다. 실기에는 1NF부터 BCNF까지가 주로 나온다')

| 정규형 | 조건                                                    | 수강신청 테이블에 적용                                                            |
| ------ | ------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1NF    | 모든 속성의 도메인이 원자값만으로 되어 있다             | 한 칸에 과목 여러 개(`DB101, NW201`)를 넣지 않고 행으로 나눈다 (위 표는 이미 1NF) |
| 2NF    | 1NF이고 부분 함수 종속을 제거해 완전 함수 종속만 남는다 | 학생(학번, 이름, 학과코드, 학과명)과 수강(학번, 과목코드, 점수)으로 분해          |
| 3NF    | 2NF이고 이행 함수 종속을 제거한다                       | 학생(학번, 이름, 학과코드)과 학과(학과코드, 학과명)로 분해                        |
| BCNF   | 모든 결정자가 후보 키다                                 | 3NF 결과에서 이미 만족                                                            |
| 4NF    | BCNF이고 다치 종속(MVD)을 제거한다                      |                                                                                   |
| 5NF    | 4NF이고 후보 키를 통하지 않는 조인 종속을 제거한다      |                                                                                   |

3NF까지 분해한 결과가 이 글의 예제 스키마(학생, 학과, 수강)와 같다. 학과명은 학과 테이블에 한 번만 보관하므로 이름을 바꾸려면 한 행만 고치면 되고(갱신 이상 해결), 학생이 없는 수학과도 학과 테이블에 넣을 수 있고(삽입 이상 해결), 수강을 취소해도 학과 정보는 남는다(삭제 이상 해결).

정규화 단계는 각 단계에서 무엇을 제거하는지의 첫 글자로 "도부이결다조"라고 외운다. 도메인 원자값, 부분 함수 종속 제거, 이행 함수 종속 제거, 결정자이면서 후보 키가 아닌 것 제거, 다치 종속 제거, 조인 종속 이용이다.

<details>
<summary>반정규화</summary>

정규화로 테이블을 잘게 나누면 조회할 때마다 조인이 늘어 성능이 떨어질 수 있다. 반정규화(De-Normalization)는 성능 향상과 개발 편의를 위해 정규화된 테이블을 의도적으로 합치거나 중복 열을 추가하는 기법이다. 테이블 병합·분할, 중복 테이블(집계 테이블) 추가, 중복 속성(조인 없이 학과명을 학생 테이블에 함께 보관) 추가가 있으며, 대신 데이터 일관성을 유지하는 처리(트리거 등)가 추가로 필요하다.

</details>

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 테이블과 함수 종속을 주고 "이 테이블은 몇 정규형인가" 또는 "다음 정규형으로 가려면 무엇을 제거해야 하는가"를 쓰게 한다. 2NF는 부분 함수 종속 제거, 3NF는 이행 함수 종속 제거가 정답의 핵심 단어다.

## 확인 문제

모든 문제는 이 글의 초기 데이터(학과 4행, 학생 7행, 과목 4행, 수강 12행)를 기준으로 하며, 정답은 SQLite로 실행해 확인했다.

<details>
<summary>문제 1. 결과 행 수: NULL과 부정 조건</summary>

```sql
SELECT COUNT(*) FROM 학생 WHERE 학과코드 <> 'CS';
```

정답: 3. CS가 아닌 학생은 박서준(EE), 최지우(BM), 한유진(EE), 오세아(NULL)로 보이지만, 오세아는 `NULL <> 'CS'`가 UNKNOWN이라 빠진다.

</details>

<details>
<summary>문제 2. COUNT의 세 가지 형태</summary>

```sql
SELECT COUNT(학과코드) FROM 학생;
SELECT COUNT(DISTINCT 학과코드) FROM 학생;
```

정답: 6, 3. `COUNT(열)`은 NULL인 오세아를 제외하고, `COUNT(DISTINCT 열)`은 CS·EE·BM 세 값만 집계한다(NULL은 제외).

</details>

<details>
<summary>문제 3. OR와 IS NULL</summary>

```sql
SELECT COUNT(*) FROM 수강 WHERE 점수 >= 80 OR 점수 IS NULL;
```

정답: 8. 80점 이상 7행(95, 80, 88, 85, 91, 90, 83)과 NULL 1행.

</details>

<details>
<summary>문제 4. 외부 조인 결과 행 수</summary>

```sql
SELECT COUNT(*) FROM 학생 s LEFT JOIN 수강 e ON s.학번 = e.학번;
```

정답: 13. 수강 12행은 모두 학생과 짝이 있고, 수강 기록이 없는 오세아가 1행 추가된다.

</details>

<details>
<summary>문제 5. HAVING과 MIN</summary>

```sql
SELECT COUNT(*) FROM (SELECT 과목코드 FROM 수강 GROUP BY 과목코드 HAVING MIN(점수) >= 60);
```

정답: 2. 과목별 최저점은 DB101 72, NW201 55, SE301 67이다(NULL은 MIN에서 제외). 60 이상인 DB101과 SE301 두 그룹이 남는다.

</details>

<details>
<summary>문제 6. 서브쿼리와 BETWEEN</summary>

```sql
SELECT COUNT(*) FROM 수강
WHERE 과목코드 IN (SELECT 과목코드 FROM 과목 WHERE 학점 = 3)
  AND 점수 BETWEEN 70 AND 89;
```

정답: 6. 3학점 과목은 DB101, NW201, SE301이고, 그중 점수가 70 이상 89 이하인 행은 80, 88, 72, 85, 78, 83이다.

</details>

<details>
<summary>문제 7. 빈칸에 키워드 쓰기</summary>

학과별 학생 수가 2명 이상인 학과코드와 학생 수를 학생 수가 많은 순으로 조회한다.

```sql
SELECT 학과코드, COUNT(*) AS 인원
FROM 학생
( ① ) 학과코드
( ② ) COUNT(*) >= 2
ORDER BY 인원 ( ③ );
```

정답: ① GROUP BY, ② HAVING, ③ DESC

</details>

<details>
<summary>문제 8. UPDATE 결과 행 수</summary>

```sql
UPDATE 학생 SET 학년 = 학년 + 1 WHERE 학년 < 4;
```

정답: 6행이 변경된다. 학년이 4인 최지우만 제외된다. 실행 후 학년은 2401부터 순서대로 3, 2, 4, 4, 4, 2, 2다.

</details>
