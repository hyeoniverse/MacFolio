## 머지 뒤 연달아 실패한 CI

24일 새벽 [#368](https://github.com/hyeoniverse/MacFolio/pull/368)을 머지한 뒤 main과 main을 합친 PR의 CI가 서로 다른 이유로 네 번 실패했다. E2E 세 건은 macOS에서 `--repeat-each 6`으로 반복해도 재현되지 않아, CI가 남긴 Playwright trace와 실패 화면으로 원인을 확인했다.

| 원인                                                                                                | 실패한 곳                                  | 수정                                                                                                                     |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 휴대폰 홈 아이콘 이름의 `line-height: normal`이 글꼴마다 달라, Linux에서 웹 글꼴 적용 전후 2px 차이 | `mobile.spec.ts` 위젯 크기 (115px → 117px) | `line-height: 1.25` 고정, `ResizeObserver`가 첫 아이콘도 관찰 ([#369](https://github.com/hyeoniverse/MacFolio/pull/369)) |
| 저장소 글 청크(약 2MB)가 서버 글보다 늦게 도착해, 클릭하는 사이 메모 목록이 재정렬                  | `markdown-safety.spec.ts`, `memo.spec.ts`  | 저장소 글이 도착하기 전(`status === 'loading'`)에는 목록을 비운다 (#369)                                                 |

| 시험이 `scrollTop`을 바꾼 직후 새 답글을 받아 scroll 이벤트보다 먼저 처리                           | `live-refresh.spec.ts`                     | 스크롤 직후 scroll 이벤트를 바로 보내도록 시험 수정 ([#370](https://github.com/hyeoniverse/MacFolio/pull/370) 안의 커밋) |

## 휴대폰 음악: 지금 재생 중 ([#366](https://github.com/hyeoniverse/MacFolio/pull/366))

23일 회고에 진행 중으로 적은 PR을 24일 0~1시에 마무리해 08:09에 머지했다. iOS 18 음악 앱 화면 3장을 기준으로 요소마다 이 앱에 있는 기능만 연결했다. 즐겨찾기 별, 무손실 배지, 가사·AirPlay처럼 기능이 없는 요소는 버튼을 만들지 않았다.

![지금 재생 중 전후](./images/music-now-playing-ios18-compare.jpg '왼쪽이 이전 화면이다. 이전 시트는 다음 재생 목록이 flex-shrink로 12px까지 줄어 보이지 않았다')

24일 0시 이후에 더한 것은 네 가지다.

| 항목                    | 전                                      | 후                                                                |
| ----------------------- | --------------------------------------- | ----------------------------------------------------------------- |
| 대기열 아이콘 오른쪽 끝 | 진행 막대 끝보다 47px 안쪽 (390px 화면) | 보이는 픽셀 끝이 진행 막대 끝과 1px 이내                          |

| 손잡이 위치             | 상태 표시줄 아래 19.5px                 | 상태 표시줄 아래 6px (iOS 7pt)                                    |

아이콘 끝은 글리프 상자가 아니라 캡처의 밝은 픽셀 끝으로 측정했다. Font Awesome 글리프는 상자 안에서 좌우에 여백을 두고 그려져, 상자를 맞춰도 보이는 끝은 맞지 않는다.

같은 PR에서 휴대폰 배경 음악이 재생되지 않던 원인도 고쳤다. 코드가 휴대폰에서는 일부러 재생하지 않았고, 조건만 없애도 iPhone Safari는 사용자 제스처 처리 중에 처음 `play()`한 요소만 재생을 허용한다. 로딩 화면 탭 처리 안에서 배경 음악 요소를 `play()` 후 바로 `pause()`해 허용받고, 2.5초 뒤 실제 재생한다. 자세한 내용은 [휴대폰 음악의 지금 재생 중을 iOS 18 구성으로](/memo/music-now-playing-ios18)에 적었다.

## 문제 알리기를 메시지 앱으로 ([#370](https://github.com/hyeoniverse/MacFolio/pull/370))

메뉴 막대 도움말 › 문제 알리기…가 GitHub 새 이슈 화면을 새 탭으로 열어, 남기려면 GitHub 로그인이 필요했다. 이제 메시지 앱의 새 피드백 화면을 열고 입력 칸에 초점을 둔다. 앱 사이 요청은 기존 `openRequest.ts`를 메시지 앱으로 넓혀 처리했다.

## 위젯

### 갤러리의 단추 안 단추 ([#368](https://github.com/hyeoniverse/MacFolio/pull/368))

위젯 갤러리와 휴대폰 위젯 시트는 '위젯 더하기' `<button>` 안에 실제 위젯을 미리보기로 렌더링했다. 음악 위젯처럼 자기 단추가 있는 위젯은 단추 안에 단추가 들어가 React 개발 모드 경고가 반복되었다. HTML 명세상 `<button>` 안에는 대화형 요소가 올 수 없다. 미리보기를 단추 밖 `<div>`로 옮기고, 단추를 `position: absolute; inset: 0`으로 칸 전체에 겹쳤다. 미리보기 안의 `z-index` 요소가 단추 위로 올라오는 문제는 미리보기에 `isolation: isolate`를 주어 쌓임 맥락(stacking context)을 분리해 해결했다.

### 사진 위젯 사이트 기본 앨범 ([#380](https://github.com/hyeoniverse/MacFolio/pull/380), 25일)

노트북에서 고른 사진 위젯 앨범이 아이폰 Safari에서는 적용되지 않았다. 고른 값이 브라우저의 `localStorage`에만 저장되기 때문이다. 관리자가 고른 앨범을 서버 `SiteContent`의 새 칸 `widgets JSONB`에 사이트 기본값으로 저장하고(`PUT /site/widgets`), `GET /site` 응답에 실었다. Worker가 이 응답을 첫 HTML에 넣으므로 추가 요청은 없다.

| 우선순위 | 값                          | 저장 위치                          |
| -------- | --------------------------- | ---------------------------------- |
| 1        | 이 브라우저에서 고른 앨범   | `localStorage`의 위젯 자리         |
| 2        | 관리자가 고른 사이트 기본값 | `GET /site`의 `widgets.photoAlbum` |
| 3        | 모든 앨범                   | 코드 기본 동작                     |

방문자가 '모든 앨범'을 직접 고르면 `'all'`로 저장해 2보다 우선하게 했다. 새 칸은 비워 둘 수 있어 배포가 실패해 이전 이미지로 되돌아가도 이전 코드가 그대로 동작한다. [아이폰에서 사진 위젯 폴더가 적용되지 않던 이유](/memo/photo-widget-site-album)에 적었다.

![사진 위젯 전후](./images/photo-widget-site-album-mobile.jpg '고르지 않은 브라우저에서도 관리자가 고른 앨범을 보인다')

## 첫 화면 CSS를 두 번 받던 문제 ([#375](https://github.com/hyeoniverse/MacFolio/pull/375))

배포 사이트를 Safari로 열면 "preloaded using link preload but not used" 경고가 CSS 5개에 표시되었다. 23일 #367에서 추가한 `bootPreloadPlugin`이 CSS `preload`에 `crossorigin`을 붙이지 않아 요청 모드가 no-cors였고, Vite preload helper가 붙이는 stylesheet는 cors였다. 모드가 달라 preload 응답이 쓰이지 않고 같은 CSS를 다시 요청했다.

![preload와 stylesheet의 요청 모드](./images/day-1024-css-preload.svg '#375 본문 도식을 SVG로 다시 그렸다. 같은 출처라 두 요청 모두 성공해 화면에는 차이가 없었다')

| `vite preview` 첫 화면 5초 | Chromium 전 | Chromium 후 | WebKit 전 | WebKit 후 |
| -------------------------- | ----------: | ----------: | --------: | --------: |
| CSS 요청 수                |          10 |           5 |        10 |         5 |
| preload 경고               |          10 |           0 |         5 |         0 |
| CSS 응답 크기 합계         |    55,836 B |    50,176 B | 100,092 B |  50,176 B |

WebKit은 두 번째 요청도 본문을 다시 받아 CSS 전송량이 두 배였다. E2E에 preload CSS가 모두 `crossorigin`이고 CSS마다 요청이 1번인지 확인하는 시험을 더했다.

## 라이선스와 보안 정책 ([#377](https://github.com/hyeoniverse/MacFolio/pull/377))

저장소 첫 화면에 License·Security 탭이 생기도록 `LICENSE`(MIT 원문)와 `SECURITY.md`를 추가했다. GitHub의 라이선스 판별은 본문이 원문과 거의 같아야 MIT로 인식하므로, 코드에만 MIT가 적용된다는 범위는 `LICENSE-CONTENT.md`로 분리했다. 글·이미지·이력서는 작성자 콘텐츠, 글꼴·음원·배경화면은 제3자 자산으로 구분했다. `SECURITY.md`는 비공개 취약점 제보 경로와 응답 목표(접수 확인 7일, 판정 회신 14일)를 적었다.

## 분석: 검색어 탭에서 페이지 열기 ([#378](https://github.com/hyeoniverse/MacFolio/pull/378), 25일)

검색어 탭 페이지 표의 이름을 누르면 검색어 표가 그 페이지로 필터링될 뿐이라, 검색으로 들어온 글을 확인하려면 메모 앱에서 제목을 다시 찾아야 했다. 이름 뒤에 ↗ 버튼을 더해 `/memo/<글>`은 메모 앱에서, `/safari/<프로젝트>`는 Safari 탭으로 연다. Search Console의 주소는 배포 주소이므로 출처 비교 대신 경로만 `parseAppPath`로 판단해 개발 서버에서도 열린다. 이름 누르기는 기존 필터 동작을 유지했다.

![검색어 탭 페이지 표](./images/day-1024-search-page-open.jpg '#378 본문의 고친 뒤 캡처. 글 페이지 줄에만 ↗가 있고 첫 화면 줄에는 없다. 가짜 API 자료다')

## 돌아보며

**macOS에서 재현되지 않는 실패는 CI 아티팩트부터 확인했다.** 위젯 2px과 메모 목록 재정렬은 로컬에서 여러 번 반복해도 통과했고, trace에 남은 측정값과 요청 순서로만 원인이 드러났다. 두 원인 모두 Linux의 웹 글꼴 적용 시각, 느린 청크 도착처럼 방문자 기기에서도 생기는 동작이라 시험이 아니라 앱을 고쳤다.

**코드를 바꾸지 않아도 CI가 막힌다.** 하루에 두 번 새 권고 공개로 의존성 검사가 실패했다. 두 번 모두 `overrides`에 버전 선택자를 더해, 실패를 확인한 시각부터 각각 25분, 31분 뒤에 머지했다. 권고 공개와 `pnpm audit` 반영 사이에 1시간 넘는 차이가 있어, 한 번 통과한 검사도 다음 실행에서 실패할 수 있다.

**전날 추가한 코드에서 다음 날 문제가 나왔다.** CSS preload 중복 요청은 23일 #367의 `bootPreloadPlugin`에서 생겼다. CI 성능 예산은 전송 크기만 검사해, 같은 파일을 두 번 받는 요청 수는 잡지 못했다. 이번에 요청 횟수를 확인하는 E2E를 함께 넣었다.
