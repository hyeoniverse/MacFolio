관리자는 메모를 열면 편집 버튼 없이 바로 편집 상태가 된다(macOS 메모와 같은 방식). 작성 중에는 편리하지만, 완성한 글을 읽다가 키를 잘못 누르면 그 입력이 본문에 반영되고 자동 저장된다. 그래서 잠금 기능을 추가했다([#63](https://github.com/hyeoniverse/MacFolio/pull/63)).

![메모 잠그기](./images/memo-lock.jpg '메뉴로 잠그면 편집기 대신 읽기 화면이 표시되고, 삭제가 비활성화된다')

10월 1일 저녁, 표 선택 표시를 수정하던 중에 태그·최근 삭제된 항목과 함께 "메모 수정을 막는 잠금 기능"을 작업 목록에 추가했다. 완성한 글을 읽으며 검토하는 일이 늘었는데, 관리자 화면은 열자마자 편집 상태라 읽는 중에 잘못 누른 키가 그대로 저장될 위험이 있었다.

## 잠금 상태의 동작

| 항목           | 잠금 전 | 잠금 후                                                    |
| -------------- | ------- | ---------------------------------------------------------- |
| 본문           | 편집기  | **읽기 화면**, 상단에 "잠긴 메모입니다"와 '잠금 풀기' 버튼 |
| 버전 기록 버튼 | 표시    | 숨김                                                       |
| 삭제 버튼·메뉴 | 활성    | 비활성                                                     |
| 목록의 제목 앞 | 없음    | 자물쇠 아이콘                                              |

잠그는 방법은 우클릭 메뉴나 ••• 메뉴의 '메모 잠그기'다.

macOS 메모는 도구 막대에 자물쇠 버튼이 있다. 처음에는 같은 위치에 추가했는데, E2E 시험 하나가 실패했다. 검색 칸에 포커스가 가면 도구가 접히고 검색 칸의 오른쪽 끝 좌표는 유지되어야 하는데, 11px 이동했다. 편집 중의 도구 막대는 서식 도구(가가, 체크리스트, 표, 이미지, 첨부)와 버전 기록, 삭제, 고정, 정렬, 보기 방식 버튼으로 이미 가득 차 있었다. 자물쇠 버튼 하나가 추가되자 폭을 넘쳤다. 그래서 잠그기는 메뉴로, 잠금 풀기는 잠긴 글 상단의 버튼으로 옮겼다. 잠긴 글에서 사용자가 가장 먼저 찾는 동작이 잠금 풀기이므로, 본문 상단 배치가 더 적합하기도 하다.

macOS 메모의 잠금은 암호로 내용을 숨긴다. 이 블로그의 글은 방문자에게 공개된 글이라 숨길 내용이 없다. 방지하려는 대상은 **관리자 자신의 실수**라서, 암호 없이 메뉴로 잠그고 버튼 하나로 풀도록 했다.

| 방법                                | 장점                                       | 단점                                                                                   |
| ----------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------- |
| macOS처럼 암호 잠금                 | macOS 메모와 동작이 같다                   | 공개 글이라 숨길 내용이 없고, 관리자는 이미 로그인한 상태다. 암호 입력 단계만 늘어난다 |
| 모든 글을 "편집" 버튼을 눌러야 수정 | 실수가 거의 없다                           | 작성 중에도 매번 버튼을 한 번 더 누른다. macOS 메모와 다르다                           |
| **완성한 글만 잠근다**              | 작성 중인 글은 기존 방식, 완성한 글만 보호 | 잠그는 것을 잊으면 보호되지 않는다                                                     |

## 저장 위치

잠금은 글의 내용이 아니라 글의 관리 상태다. 고정과 성격이 같다. 고정은 이미 메모 정리 내용(폴더, 옮긴 글, 고정)에 `pins`로 저장되어 있었다. 잠금도 같은 객체에 `locks`로 추가했다.

```ts
export interface Organization {
	folders: string[];
	posts: Record<string, string>;
	moves: { from: string; to: string }[];
	pins: Record<string, boolean>;
	/** 잠근 글: slug → true */
	locks: Record<string, boolean>;
}
```

따라서 DB 스키마는 변경하지 않았다. 정리 내용은 JSON 열 하나에 전체를 저장한다. 대신 이전에 저장한 정리 내용에는 `locks`가 없다. 그래서 세 곳에서 "없으면 빈 값"으로 읽도록 했다.

| 위치                               | 처리                                                                               |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| 서버 검증(`parseOrganization`)     | `locks`가 없으면 `{}`로 처리. 이전 버전 화면이 `locks` 없이 보내도 거절하지 않는다 |
| 서버 응답                          | 빈 정리 내용 위에 저장된 값을 병합해 `locks: {}`를 채운다                          |
| 화면 수신(`normalizeOrganization`) | 형식이 다르면 빈 값                                                                |

## 서버에서도 차단

화면에서는 편집기를 렌더링하지 않으므로 수정할 수 없다. 하지만 요청은 화면을 거치지 않고 직접 보낼 수도 있다. 그래서 글 API가 수정·삭제를 처리하기 전에 정리 내용의 잠금 상태를 확인한다.

```ts
private async checkUnlocked(slug: string) {
	const row = await this.prisma.memoOrganization.findUnique({ where: { id: 1 } });
	const locks = (row?.data as { locks?: Record<string, boolean> } | undefined)?.locks;
	if (locks?.[slug]) throw new ConflictException('잠긴 메모입니다. 잠금을 풀고 고치세요.');
}
```

임시 저장, 게시, 임시 저장 버리기, 삭제에 모두 적용한다. 응답은 [409 Conflict](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/409)다. 요청 형식은 올바르지만 현재 리소스 상태와 충돌한다는 뜻이라 400(요청 형식 오류)보다 적합하다. API 시험에 "잠그면 네 가지가 모두 409, 풀면 다시 게시된다"를 추가했다.

![잠금을 확인하는 두 곳](./images/memo-lock-checks.svg '화면은 편집기를 렌더링하지 않고, 서버는 수정·삭제를 409로 차단한다')

잠금 해제는 글 API가 아니라 정리 내용 저장(`PUT /memo/organization`)으로 처리한다. 따라서 잠긴 글의 잠금을 푸는 요청은 `checkUnlocked`에 차단되지 않는다. 잠금을 확인할 때마다 DB에서 정리 내용 한 행(`id: 1`)을 조회하지만, 수정·삭제는 관리자만 요청하므로 요청 수가 적어 부하는 무시할 수준이다.

## 확인

PR의 변경 규모는 17개 파일, 238줄 추가, 16줄 삭제다.

- 서버 단위: `organization.test.ts`의 "잠금: 없으면 빈 값, 있으면 slug → true/false". 글 주소 형식이 아닌 키는 거절한다.
- 서버 E2E: `posts.e2e.test.ts`의 "잠근 글은 임시 저장·게시·버리기·지우기를 409로 막고, 잠금을 풀면 다시 된다".
- 화면 단위: `organize.test.ts`에 `setLocked` 시험을 추가했다.
- 화면 E2E: `e2e/memo-admin.spec.ts`의 "메모를 잠그면 고치거나 지울 수 없고, 잠금을 풀면 다시 고친다". 메뉴로 잠그고, 읽기 화면과 "잠긴 메모입니다"가 표시되는지, 삭제가 비활성화됐는지, 풀면 편집기로 돌아오는지 확인한다.

## 남은 것·정리

- 서버가 차단하는 것은 글 API(내용)뿐이다. 폴더 이동이나 고정은 정리 내용 저장 요청이라 서버의 잠금 확인을 거치지 않는다.
- 도구 막대에 버튼 하나를 추가해 폭이 넘친 문제는, 막대에 배치할 버튼 목록을 미리 정하지 않으면 반복된다. 이번에는 검색 칸 좌표를 비교하는 시험이 11px 이동을 검출했다.
- 저장 형식에 필드를 추가할 때는 "이전 데이터에는 그 필드가 없다"를 먼저 고려한다. 이번에는 세 곳에서 빈 값으로 읽도록 했다.
