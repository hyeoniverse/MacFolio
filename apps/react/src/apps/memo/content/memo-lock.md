관리자는 메모를 열면 편집 버튼 없이 바로 고친다(macOS 메모처럼). 쓰는 동안은 편하지만, 다 쓴 글을 읽다가 키를 잘못 누르면 그대로 고쳐지고 자동으로 저장된다. 그래서 잠금을 붙였다([#63](https://github.com/hyeoniverse/MacFolio/pull/63)).

![메모 잠그기](./images/memo-lock.jpg '메뉴로 잠그면 편집기 대신 읽기 화면이 되고, 지우기가 꺼진다')

10월 1일 저녁, 표 선택 표시를 고치던 중에 태그·최근 삭제된 항목과 함께 "메모를 고치지 못하게 잠그는 기능"을 할 일로 올렸다. 다 쓴 글을 읽으며 확인하는 일이 늘었는데, 관리자 화면은 열자마자 편집 상태라 읽다가 잘못 누른 키가 그대로 저장되는 것이 불안했다.

## 잠그면

- 우클릭 메뉴나 ••• 메뉴의 '메모 잠그기'로 잠근다
- 편집기 대신 **읽기 화면**을 보여 준다. 위에 "잠긴 메모입니다"와 '잠금 풀기' 버튼이 붙는다
- 버전 기록 버튼이 사라지고, 지우기 버튼과 메뉴 항목이 꺼진다
- 목록의 제목 앞에 자물쇠가 붙는다

macOS 메모는 도구 막대에 자물쇠 버튼이 있다. 처음에는 그렇게 붙였는데, E2E 시험 하나가 깨졌다. 검색 칸에 초점이 가면 도구가 접히고 검색 칸의 오른쪽 끝은 그대로여야 하는데, 11px 밀렸다. 편집하는 동안의 도구 막대는 서식 도구(가가, 체크리스트, 표, 이미지, 첨부)와 버전 기록, 지우기, 고정, 정렬, 보기 방식으로 이미 꽉 차 있었다. 자물쇠 하나가 더해지자 넘쳤다. 그래서 잠그는 것은 메뉴로, 푸는 것은 잠긴 글 위의 버튼으로 옮겼다. 잠긴 글에서는 푸는 것이 가장 먼저 찾는 일이라, 그 자리에 두는 편이 낫기도 하다.

macOS 메모의 잠금은 암호를 걸어 내용을 가린다. 이 블로그의 글은 방문자에게 공개된 글이라 가릴 것이 없다. 막고 싶은 것은 **관리자 자신의 실수**라서, 암호 없이 메뉴로 잠그고 버튼 하나로 풀게 했다.

| 방법                                  | 좋은 점                                   | 걸리는 점                                                              |
| ------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| macOS처럼 암호 잠금                   | 실제와 같다                               | 공개 글이라 가릴 것이 없고, 관리자는 이미 로그인했다. 암호는 일만 는다 |
| 모든 글을 "편집" 버튼을 눌러야 고치게 | 실수가 거의 없다                          | 쓰는 동안 매번 한 번 더 누른다. macOS 메모와 다르다                    |
| **다 쓴 글만 잠근다**                 | 쓰는 중인 글은 지금처럼, 끝난 글만 지킨다 | 잠그는 것을 잊으면 그대로다                                            |

## 어디에 두나

잠금은 글의 내용이 아니라 글을 다루는 방법이다. 고정과 성격이 같다. 고정은 이미 메모 정리 내용(폴더, 옮긴 글, 고정)에 `pins`로 들어 있었다. 잠금도 그 옆에 `locks`로 두었다.

```ts
export interface Organization {
	folders: string[];
	posts: Record<string, string>;
	moves: { from: string; to: string }[];
	pins: Record<string, boolean>;
	/** 잠근 글: slug → true */
	locks: Record<string, boolean>;
}
```

덕분에 DB 구조는 바꾸지 않았다. 정리 내용은 JSON 한 칸에 통째로 저장한다. 대신 예전에 저장한 정리 내용에는 `locks`가 없다. 그래서 세 곳에서 "없으면 빈 값"으로 읽게 했다.

- 서버의 검사(`parseOrganization`): `locks`가 없으면 `{}`로 받는다. 예전 화면이 `locks` 없이 보내도 거절하지 않는다
- 서버가 읽어 줄 때: 저장된 값 앞에 빈 정리 내용을 깔아 `locks: {}`를 채운다
- 화면이 받을 때(`normalizeOrganization`): 모양이 다르면 빈 값

## 서버에서도 막는다

화면에서는 편집기를 아예 그리지 않으니 고칠 수 없다. 하지만 요청은 화면을 거치지 않고 보낼 수도 있다. 그래서 글 API가 고치고 지우기 전에 정리 내용의 잠금을 확인한다.

```ts
private async checkUnlocked(slug: string) {
	const row = await this.prisma.memoOrganization.findUnique({ where: { id: 1 } });
	const locks = (row?.data as { locks?: Record<string, boolean> } | undefined)?.locks;
	if (locks?.[slug]) throw new ConflictException('잠긴 메모입니다. 잠금을 풀고 고치세요.');
}
```

임시 저장, 게시, 임시 저장 버리기, 지우기에 모두 건다. 응답은 409(Conflict)다. 요청 자체는 올바르지만 지금 글의 상태와 맞지 않는다는 뜻이라 400보다 알맞다. API 시험에 "잠그면 네 가지가 모두 409, 풀면 다시 게시된다"를 더했다.

![잠금을 확인하는 두 곳](./images/memo-lock-checks.svg '화면은 편집기를 그리지 않고, 서버는 고치기·지우기를 409로 막는다')

잠금을 푸는 것은 글 API가 아니라 정리 내용 저장(`PUT /memo/organization`)이다. 그래서 잠긴 글의 잠금을 푸는 요청은 `checkUnlocked`에 막히지 않는다. 잠금을 확인할 때마다 DB에서 정리 내용 한 줄(`id: 1`)을 읽는다. 고치기·지우기는 관리자만 하는 일이라 요청 수가 적다.

## 확인

PR은 17개 파일, 238줄 더하기, 16줄 지우기다.

- 서버 단위: `organization.test.ts`의 "잠금: 없으면 빈 값, 있으면 slug → true/false". 글 주소 모양이 틀린 키는 거절한다.
- 서버 E2E: `posts.e2e.test.ts`의 "잠근 글은 임시 저장·게시·버리기·지우기를 409로 막고, 잠금을 풀면 다시 된다".
- 화면 단위: `organize.test.ts`에 `setLocked`를 더했다.
- 화면 E2E: `e2e/memo-admin.spec.ts`의 "메모를 잠그면 고치거나 지울 수 없고, 잠금을 풀면 다시 고친다". 메뉴로 잠그고, 읽기 화면과 "잠긴 메모입니다"가 보이는지, 지우기가 꺼졌는지, 풀면 편집기로 돌아오는지 본다.

## 남은 것·배운 것

- 서버가 막는 것은 글 API(내용)뿐이다. 폴더 옮기기나 고정은 정리 내용 저장이라 서버의 잠금 확인을 지나지 않는다.
- 도구 막대에 버튼 하나를 더했다가 넘친 일은, 막대에 무엇이 들어갈지 미리 정해 두지 않으면 계속 생긴다. 시험이 11px 밀린 것을 잡아 줬다.
- 저장 모양에 칸을 더할 때는 "예전 데이터에는 그 칸이 없다"를 먼저 생각한다. 이번에는 세 곳에서 빈 값으로 읽게 했다.
