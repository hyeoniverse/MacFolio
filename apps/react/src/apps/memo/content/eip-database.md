## 3과목은 무엇을 묻는가

3과목 데이터베이스 구축은 필기 100문항 가운데 20문항을 차지한다. 시험 전체 구조와 합격 기준은 [연재 첫 글](/memo/eip-overview)에 정리했다.

데이터베이스(database)는 여러 사람과 여러 프로그램이 함께 쓰려고 한곳에 통합해 저장한 데이터의 모음이다. 은행의 계좌 잔액, 쇼핑몰의 주문 내역, 학교의 수강 신청 기록이 모두 데이터베이스에 저장된다. 이 데이터를 저장하고 꺼내 주는 소프트웨어를 DBMS(Database Management System)라고 하며, MySQL, PostgreSQL, Oracle, SQLite가 대표적이다. 3과목은 이 데이터베이스를 어떤 순서로 설계하고, 어떤 규칙으로 테이블을 나누며, 여러 사용자가 동시에 쓸 때 데이터가 어떻게 지켜지는지를 묻는다.

지금 적용되는 한국산업인력공단 출제기준(2023년 1월부터 2025년 12월까지)의 주요항목은 다음 다섯 개다.

| 주요항목               | 다루는 내용                                                              |
| ---------------------- | ------------------------------------------------------------------------ |
| SQL 응용               | 절차형 SQL(프로시저, 트리거, 사용자 정의 함수), 응용 SQL(그룹·윈도 함수) |
| SQL 활용               | DDL·DML·DCL, 트랜잭션, 뷰, 인덱스, 집합 연산자, 조인, 서브쿼리           |
| 논리 데이터베이스 설계 | 데이터 모델, E-R 모델, 관계 데이터 모델, 관계대수·관계해석, 정규화       |
| 물리 데이터베이스 설계 | 스토리지, 분산 데이터베이스, 접근 제어, 파티션, 클러스터, 반정규화, CRUD |
| 데이터 전환            | 초기 데이터 구축, ETL, 데이터 검증, 데이터 정제                          |

문항 수로 보면 논리 데이터베이스 설계(관계 모델, 키, 관계대수, 정규화)와 트랜잭션이 가장 자주 나온다. SQL 문법 자체는 실기에서 훨씬 비중이 크므로 필기에서는 개념 위주로 공부하고, 문법은 실기를 준비하며 다시 익힌다. 이 글은 다음 순서로 진행한다.

## 데이터베이스 설계 순서

### 스키마

스키마(schema)는 데이터베이스에 어떤 데이터를 어떤 구조로 저장하고 어떤 제약 조건을 걸지 기술한 설계도다. "학생 테이블에는 학번, 이름, 학년 열이 있고, 학번은 중복될 수 없으며, 학년은 1~4다"라는 정의가 스키마다. 스키마에 맞춰 실제로 저장된 값(학번 1001, 김민준, 3학년)은 인스턴스(instance)라고 부른다.

ANSI/SPARC 위원회는 같은 데이터베이스를 바라보는 관점을 세 단계로 나눴다. 이 구조를 3단계 스키마라고 한다.

| 스키마                    | 관점                      | 내용                                                           |
| ------------------------- | ------------------------- | -------------------------------------------------------------- |
| 외부 스키마 (서브 스키마) | 개별 사용자·응용 프로그램 | 각자 필요한 부분만 본 논리 구조. 하나의 DB에 여러 개 존재      |
| 개념 스키마               | 조직 전체                 | 모든 데이터와 관계, 제약 조건, 접근 권한을 담은 전체 논리 구조 |
| 내부 스키마               | 저장 장치                 | 레코드 형식, 인덱스, 저장 순서 같은 물리적 저장 구조           |

세 단계를 나눈 목적은 ==데이터 독립성==이다. 내부 스키마를 바꿔도(예: 디스크를 바꾸거나 인덱스를 추가해도) 개념 스키마와 응용 프로그램은 그대로인 성질을 물리적 독립성, 개념 스키마를 바꿔도(예: 테이블에 열을 추가해도) 외부 스키마와 응용 프로그램은 그대로인 성질을 논리적 독립성이라고 한다.

### 설계 5단계

데이터베이스 설계는 요구 조건 분석, 개념적 설계, 논리적 설계, 물리적 설계, 구현의 다섯 단계로 진행한다.

![요구 조건 분석, 개념적 설계, 논리적 설계, 물리적 설계, 구현이 화살표로 이어지고, 각 단계 아래에 요구 조건 명세서, E-R 다이어그램, 릴레이션 스키마, 인덱스와 저장 구조, DDL 실행이 산출물로 붙어 있다](./images/eip-database-design-process.svg '개념적 설계는 DBMS와 무관하고, 논리적 설계부터 특정 데이터 모델에 맞춘다')

1. **요구 조건 분석**: 사용자를 인터뷰해 어떤 데이터가 필요하고 어떤 처리를 하는지 정리한다. 산출물은 요구 조건 명세서다.
2. **개념적 설계**: 현실 세계의 정보를 개체와 관계로 추상화한다. 어떤 DBMS를 쓸지는 아직 정하지 않는다. 산출물은 E-R 다이어그램이며, 개념 스키마 모델링과 트랜잭션 모델링을 함께 수행한다.
3. **논리적 설계**: 개념 모델을 목표 DBMS가 지원하는 데이터 모델(대부분 관계형)로 변환한다. 테이블, 속성, 기본키·외래키를 정하고 정규화를 수행한다. 산출물은 릴레이션 스키마다.
4. **물리적 설계**: 논리 스키마를 실제 저장 장치에 어떻게 둘지 정한다. 레코드 크기, 인덱스, 파티션, 접근 경로를 결정하고 응답 시간·저장 공간 효율·트랜잭션 처리량을 기준으로 평가한다.
5. **구현**: 목표 DBMS의 DDL(데이터 정의어)로 테이블과 인덱스를 생성하고 데이터를 적재한다.

> [!TIP] 시험에서는 이렇게 묻는다
> "트랜잭션 인터페이스 설계, 정규화 수행이 포함되는 단계는?"처럼 작업을 주고 단계를 고르게 한다. DBMS와 무관하면 개념적 설계, 특정 데이터 모델(관계형)에 맞추면 논리적 설계, 저장 장치와 접근 경로를 다루면 물리적 설계다. ==정규화는 논리적 설계, 인덱스와 레코드 집중 분석은 물리적 설계==에 속한다.

## 데이터 모델과 E-R 모델

### 데이터 모델의 구성 요소

데이터 모델(data model)은 현실 세계의 정보를 컴퓨터에 표현하기 위해 단순화한 표현 방식이다. 어느 데이터 모델이든 세 가지 요소로 구성된다.

| 구성 요소              | 뜻                                     | 관계 데이터 모델에서의 예          |
| ---------------------- | -------------------------------------- | ---------------------------------- |
| 구조 (Structure)       | 데이터를 어떤 모양으로 담는가          | 테이블(릴레이션)과 열(속성)        |
| 연산 (Operation)       | 데이터를 어떻게 조회·변경하는가        | 관계대수, SQL의 SELECT·UPDATE      |
| 제약 조건 (Constraint) | 저장할 수 있는 값에 어떤 제한을 거는가 | 기본키 중복 금지, 외래키 참조 규칙 |

데이터 모델은 추상화 수준에 따라 개념적 데이터 모델(E-R 모델처럼 사람이 이해하기 쉬운 모델)과 논리적 데이터 모델(DBMS가 구현하는 모델)로 나뉜다. 논리적 데이터 모델에는 다음 세 가지가 있다.

| 논리적 데이터 모델 | 구조                                    | 관계 표현                             |
| ------------------ | --------------------------------------- | ------------------------------------- |
| 계층형             | 트리. 부모 하나에 자식 여러 개          | 1:N만 직접 표현. 대표 DBMS는 IBM IMS  |
| 망형 (네트워크형)  | 그래프. 자식이 여러 부모를 가질 수 있다 | N:M을 오너·멤버 관계로 표현 (CODASYL) |
| 관계형             | 2차원 테이블                            | 외래키 값으로 관계 표현               |

### E-R 모델

E-R 모델(Entity-Relationship model)은 1976년 피터 첸(Peter Chen)이 제안한 개념적 데이터 모델이다. 현실 세계를 개체(entity), 개체가 가진 속성(attribute), 개체 사이의 관계(relationship)로 표현하고, 이것을 그림으로 나타낸 것이 E-R 다이어그램이다.

![학과와 학생이 소속 관계로 1 대 N, 학생과 과목이 수강 관계로 N 대 M으로 연결되고, 각 개체에 학과코드, 학번, 과목코드 같은 밑줄 친 키 속성과 이름, 학점 같은 속성 타원이 붙어 있다. 학생의 전화번호는 이중 타원, 수강 관계에는 성적 속성이 붙어 있다](./images/eip-database-erd.svg '수강처럼 N:M 관계는 관계 자체가 성적 같은 속성을 가질 수 있다')

| 기호         | 뜻                                                |
| ------------ | ------------------------------------------------- |
| 사각형       | 개체 (학생, 과목)                                 |
| 이중 사각형  | 약한 개체 (다른 개체의 키가 있어야 식별되는 개체) |
| 마름모       | 관계 (수강, 소속)                                 |
| 타원         | 속성                                              |
| 밑줄 친 타원 | 기본키 속성                                       |
| 이중 타원    | 다중값 속성 (전화번호를 여러 개 가질 수 있음)     |
| 점선 타원    | 유도 속성 (생년월일로 계산하는 나이)              |
| 선, 링크     | 개체와 속성, 개체와 관계를 연결                   |

관계의 대응 수(cardinality ratio)는 한 개체가 상대 개체 몇 개와 연결되는지를 나타낸다.

| 대응 수 | 예                                                   |
| ------- | ---------------------------------------------------- |
| 1:1     | 사람과 주민등록번호. 한 사람은 번호 하나만 가진다    |
| 1:N     | 학과와 학생. 학과 하나에 학생 여럿, 학생은 학과 하나 |
| N:M     | 학생과 과목. 학생은 여러 과목, 과목은 여러 학생      |

N:M 관계는 관계형 데이터베이스에서 바로 표현할 수 없어서, 논리적 설계 단계에서 양쪽 기본키를 외래키로 가진 별도 테이블(위 그림의 수강 테이블: 학번, 과목코드, 성적)로 바꾼다. E-R 다이어그램을 테이블로 바꾸는 규칙은 [E-R 다이어그램을 릴레이션으로 사상하는 7단계](/memo/db-er-to-relational)에 자세히 정리했다.

> [!TIP] 시험에서는 이렇게 묻는다
> E-R 다이어그램의 기호와 뜻을 짝짓는 문제가 매번 나온다. 마름모는 관계, 사각형은 개체, 타원은 속성이다. 데이터 모델의 3요소(구조, 연산, 제약 조건)를 고르거나, "개체 간의 관계를 트리로 표현하는 모델"처럼 계층형·망형·관계형을 구분하는 문제도 나온다.

## 관계 데이터 모델

### 릴레이션의 구성 요소

관계 데이터 모델(relational data model)은 1970년 에드거 F. 코드(Edgar F. Codd)가 제안한 모델로, 데이터를 릴레이션(relation)이라는 2차원 표로 표현한다. 일상적으로 테이블이라고 부르는 것이 릴레이션이다.

![학번, 이름, 학과, 학년 네 열과 네 행으로 된 학생 표에서, 열 하나는 속성, 행 하나는 튜플이고, 행의 수 4가 카디널리티, 열의 수 4가 차수로 표시되어 있다](./images/eip-database-relation-terms.svg '차수는 열의 수, 카디널리티는 행의 수다')

| 용어                     | 뜻                                                   | 그림에서                     |
| ------------------------ | ---------------------------------------------------- | ---------------------------- |
| 속성 (attribute)         | 열. 데이터의 가장 작은 논리적 단위                   | 학번, 이름, 학과, 학년       |
| 튜플 (tuple)             | 행. 하나의 레코드                                    | (1002, 이서연, 경영, 2)      |
| 도메인 (domain)          | 한 속성이 가질 수 있는 원자값의 집합                 | 학년의 도메인 {1, 2, 3, 4}   |
| 차수 (degree)            | 속성의 수                                            | 4                            |
| 카디널리티 (cardinality) | 튜플의 수                                            | 4                            |
| 릴레이션 스키마          | 릴레이션 이름과 속성 이름의 집합. 거의 바뀌지 않는다 | 학생(학번, 이름, 학과, 학년) |
| 릴레이션 인스턴스        | 어느 시점에 저장된 튜플의 집합. 계속 바뀐다          | 표 안의 네 행                |

릴레이션은 수학의 집합에서 출발한 개념이라 다음 특징을 가진다.

- 한 릴레이션에 ==똑같은 튜플이 두 번 나올 수 없다== (튜플의 유일성).
- 튜플 사이에 순서가 없다. 1004번 행을 맨 위로 옮겨도 같은 릴레이션이다.
- 속성 사이에도 순서가 없다. 단, 속성 이름은 한 릴레이션 안에서 유일해야 한다.
- 모든 속성 값은 더 쪼갤 수 없는 원자값(atomic value)이다. 한 칸에 "DB, OS"처럼 값 두 개를 넣지 않는다.
- 튜플을 삽입·삭제하면 인스턴스는 계속 바뀌지만 스키마는 그대로다.

### 키의 종류

키(key)는 튜플을 서로 구별하는 기준이 되는 속성 또는 속성의 집합이다. 키를 구분하는 기준은 두 가지 성질이다. ==유일성(uniqueness)==은 그 속성 값으로 모든 튜플을 하나씩 구별할 수 있다는 뜻이고, ==최소성(minimality)==은 속성을 하나라도 빼면 유일성이 깨진다는 뜻이다.

![회원 릴레이션에서 가장 바깥 타원이 유일성만 만족하는 슈퍼키, 그 안의 타원이 유일성과 최소성을 만족하는 후보키이고, 후보키 안에 기본키 회원번호와 대체키 이메일이 있다](./images/eip-database-keys.svg '모든 후보키는 슈퍼키지만, 모든 슈퍼키가 후보키인 것은 아니다')

회원(회원번호, 이메일, 이름, 전화번호) 릴레이션에서 회원번호와 이메일이 각각 중복되지 않는다고 하자.

| 키                     | 조건                                           | 예                                                                                     |
| ---------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------- |
| 슈퍼키 (super key)     | 유일성만 만족                                  | {회원번호, 이름}: 회원번호만으로 이미 구별되므로 이름은 불필요하지만 유일성은 만족한다 |
| 후보키 (candidate key) | 유일성과 최소성을 모두 만족                    | {회원번호}, {이메일}                                                                   |
| 기본키 (primary key)   | 후보키 중 대표로 고른 키. NULL 불가, 중복 불가 | {회원번호}                                                                             |
| 대체키 (alternate key) | 기본키로 고르지 않은 나머지 후보키             | {이메일}                                                                               |
| 외래키 (foreign key)   | 다른 릴레이션의 기본키를 참조하는 속성         | 주문 릴레이션의 회원번호                                                               |

외래키는 릴레이션 사이의 관계를 표현하는 유일한 수단이다. 학생 릴레이션의 학과코드가 학과 릴레이션의 기본키 학과코드를 참조하면, 두 릴레이션을 학과코드로 연결해 "김민준 학생의 학과명"을 조회할 수 있다.

### 무결성 제약

무결성(integrity)은 데이터베이스에 저장된 값이 현실 세계의 실제 값과 일치하고 서로 모순되지 않는 정확성을 뜻한다. DBMS는 다음 제약 조건을 검사해 잘못된 값이 들어오지 못하게 막는다.

| 무결성        | 규칙                                                                    |
| ------------- | ----------------------------------------------------------------------- |
| 개체 무결성   | 기본키를 구성하는 속성은 NULL이나 중복 값을 가질 수 없다                |
| 참조 무결성   | 외래키 값은 참조되는 릴레이션의 기본키 값 중 하나이거나 NULL이어야 한다 |
| 도메인 무결성 | 속성 값은 정의된 도메인에 속해야 한다 (학년은 1~4)                      |
| 키 무결성     | 한 릴레이션에는 최소 하나의 키가 있어야 한다                            |
| NULL 무결성   | NOT NULL로 지정한 속성은 NULL을 가질 수 없다                            |
| 고유 무결성   | UNIQUE로 지정한 속성 값은 서로 달라야 한다                              |
| 관계 무결성   | 릴레이션에 튜플을 삽입할 수 있는지 여부를 규정한다                      |

NULL은 "값이 아직 없음" 또는 "해당 없음"을 뜻하는 특수한 표시로, 0이나 빈 문자열과 다르다.

![학생 릴레이션의 학과코드가 학과 릴레이션의 학과코드를 가리키며, CS와 BA는 학과에 있어 허용되고 EE는 학과에 없어 거부되며 NULL은 허용된다](./images/eip-database-integrity.svg '참조되는 쪽에서 행을 삭제할 때의 처리 방식도 외래키에 함께 정의한다')

SQLite에서 네 가지 제약을 걸고 규칙을 어기는 행을 넣어 보면 DBMS가 어떻게 거부하는지 확인할 수 있다.

```sql
PRAGMA foreign_keys = ON;  -- SQLite는 외래키 검사를 켜야 동작한다
CREATE TABLE 학과(학과코드 TEXT PRIMARY KEY, 학과명 TEXT NOT NULL);
CREATE TABLE 학생(
  학번 INTEGER PRIMARY KEY,
  이름 TEXT NOT NULL,
  학년 INTEGER CHECK (학년 BETWEEN 1 AND 4),
  학과코드 TEXT REFERENCES 학과(학과코드) ON DELETE RESTRICT
);
INSERT INTO 학과 VALUES ('CS','컴퓨터공학'),('BA','경영');
INSERT INTO 학생 VALUES (1001,'김민준',3,'CS');   -- 성공
INSERT INTO 학생 VALUES (1001,'이서연',2,'BA');   -- 기본키 중복
INSERT INTO 학생 VALUES (1002,'이서연',5,'BA');   -- 학년 도메인 위반
INSERT INTO 학생 VALUES (1003,'박도윤',4,'EE');   -- 없는 학과 참조
DELETE FROM 학과 WHERE 학과코드='CS';              -- 참조 중인 행 삭제
```

```text
Error near line 13: UNIQUE constraint failed: 학생.학번
Error near line 14: CHECK constraint failed: 학년 BETWEEN 1 AND 4
Error near line 15: FOREIGN KEY constraint failed
Error near line 16: FOREIGN KEY constraint failed
```

첫 번째 오류는 개체 무결성, 두 번째는 도메인 무결성, 세 번째와 네 번째는 참조 무결성 위반이다. 마지막 DELETE가 거부된 이유는 `ON DELETE RESTRICT`로 "참조하는 행이 있으면 삭제를 거부한다"고 정했기 때문이다. 참조되는 행을 삭제하거나 기본키를 바꿀 때의 처리 방식은 다음 중에서 고른다.

| 옵션        | 학과 CS를 삭제하면                        |
| ----------- | ----------------------------------------- |
| RESTRICT    | 학생 1001이 참조하고 있으므로 삭제를 거부 |
| CASCADE     | 학과 CS와 함께 학생 1001도 삭제           |
| SET NULL    | 학생 1001의 학과코드를 NULL로 변경        |
| SET DEFAULT | 학생 1001의 학과코드를 기본값으로 변경    |

> [!TIP] 시험에서는 이렇게 묻는다
> 표를 보여 주고 차수와 카디널리티를 쓰게 하거나, "유일성은 만족하지만 최소성은 만족하지 못하는 키"(슈퍼키)를 고르게 한다. "기본키는 NULL 값을 가질 수 없다"는 개체 무결성, "외래키 값은 참조 릴레이션의 기본키 값과 같거나 NULL"은 참조 무결성이다. 두 문장을 바꿔 놓은 오답 보기가 자주 나온다.

## 관계대수와 관계해석

관계 데이터 언어는 릴레이션에서 원하는 데이터를 얻는 방법을 기술하는 언어다. 관계대수와 관계해석 두 가지가 있고, 둘은 표현할 수 있는 질의의 범위가 같다(관계적으로 완전하다). SQL은 이 두 언어를 바탕으로 만든 실용 언어다.

| 구분 | 관계대수 (relational algebra)                      | 관계해석 (relational calculus)            |
| ---- | -------------------------------------------------- | ----------------------------------------- |
| 성격 | ==절차적 언어==: 어떤 연산을 어떤 순서로 할지 기술 | ==비절차적 언어==: 무엇을 원하는지만 기술 |
| 기반 | 집합 연산과 관계 연산자                            | 수학의 프레디킷 해석(술어 논리)           |
| 표기 | σ, π, ⋈, ÷, ∪, −                                   | ∀(모든), ∃(어떤 것이 존재), ∧, ∨, ¬       |
| 제안 | 코드(1970년대 초)                                  | 코드(1972년)                              |

### 일반 집합 연산자

관계대수의 연산 결과는 항상 릴레이션이다. 결과를 다시 다른 연산의 입력으로 쓸 수 있는 이 성질을 폐쇄 성질(closure property)이라고 한다. 집합 연산자 네 개는 수학의 집합 연산을 릴레이션에 적용한 것이다.

예제로 쓸 릴레이션은 다음과 같다.

| 학번 | 이름   | 학과   | 학년 |
| ---- | ------ | ------ | ---- |
| 1001 | 김민준 | 컴퓨터 | 3    |
| 1002 | 이서연 | 경영   | 2    |
| 1003 | 박도윤 | 컴퓨터 | 4    |
| 1004 | 최지우 | 수학   | 3    |

코딩동아리 회원의 학번은 {1001, 1003}, 밴드동아리 회원의 학번은 {1003, 1004}다.

| 연산자                     | 기호 | 뜻                           | 코딩동아리 ○ 밴드동아리 결과    | SQL          |
| -------------------------- | ---- | ---------------------------- | ------------------------------- | ------------ |
| 합집합 (Union)             | ∪    | 어느 한쪽에라도 있는 튜플    | {1001, 1003, 1004}              | `UNION`      |
| 교집합 (Intersection)      | ∩    | 양쪽에 모두 있는 튜플        | {1003}                          | `INTERSECT`  |
| 차집합 (Difference)        | −    | 왼쪽에만 있는 튜플           | {1001}                          | `EXCEPT`     |
| 교차곱 (Cartesian Product) | ×    | 두 릴레이션 튜플의 모든 조합 | 학생(4행) × 필수과목(2행) = 8행 | `CROSS JOIN` |

합집합, 교집합, 차집합은 두 릴레이션의 속성 수가 같고 대응하는 속성의 도메인이 같아야 계산할 수 있다. 이 조건을 합병 가능(union-compatible)이라고 한다. 교차곱은 조건이 없으며, 결과의 ==차수는 두 릴레이션 차수의 합, 카디널리티는 두 릴레이션 카디널리티의 곱==이다. 차수 4, 카디널리티 4인 학생과 차수 1, 카디널리티 2인 필수과목의 교차곱은 차수 5, 카디널리티 8이다. SQLite에서 `SELECT count(*) FROM 학생, 필수;`를 실행하면 실제로 8이 나온다.

### 순수 관계 연산자

순수 관계 연산자는 릴레이션 구조를 다루기 위해 새로 정의한 연산자다.

| 연산자             | 기호 | 하는 일                                                 | SQL 대응                |
| ------------------ | ---- | ------------------------------------------------------- | ----------------------- |
| 실렉트 (Select)    | σ    | 조건을 만족하는 ==튜플(행)==을 고른다. 수평 연산        | `WHERE`                 |
| 프로젝트 (Project) | π    | 지정한 ==속성(열)==만 남기고 중복을 제거한다. 수직 연산 | `SELECT DISTINCT 열`    |
| 조인 (Join)        | ⋈    | 공통 속성으로 두 릴레이션의 튜플을 연결한다             | `JOIN … ON`             |
| 디비전 (Division)  | ÷    | 오른쪽 릴레이션의 값을 ==모두== 가진 왼쪽 튜플을 고른다 | `NOT EXISTS` 두 번 중첩 |

![실렉트는 학생 표에서 컴퓨터학과 3학년 이상인 두 행을 고르고, 프로젝트는 학과 열만 골라 중복을 없앤 세 행을 만들며, 디비전은 수강 표를 필수 과목 DB와 OS로 나눠 두 과목을 모두 들은 학번 1001과 1003을 남긴다](./images/eip-database-ra-operators.svg '실렉트는 행을, 프로젝트는 열을 고른다')

각 연산을 SQL로 바꿔 SQLite에서 실행한 결과는 다음과 같다. 수강 릴레이션은 (1001, DB), (1001, OS), (1001, NW), (1002, DB), (1003, DB), (1003, OS), (1004, NW)의 일곱 행이고, 필수 릴레이션은 DB와 OS 두 행이다.

```sql
-- σ 학과='컴퓨터' ∧ 학년≥3 (학생)
SELECT * FROM 학생 WHERE 학과='컴퓨터' AND 학년>=3;
```

| 학번 | 이름   | 학과   | 학년 |
| ---- | ------ | ------ | ---- |
| 1001 | 김민준 | 컴퓨터 | 3    |
| 1003 | 박도윤 | 컴퓨터 | 4    |

```sql
-- π 학과 (학생): 릴레이션은 중복 튜플을 허용하지 않으므로 DISTINCT가 필요하다
SELECT DISTINCT 학과 FROM 학생;
```

| 학과   |
| ------ |
| 컴퓨터 |
| 경영   |
| 수학   |

```sql
-- π 학번, 이름, 과목 (σ 과목='DB' (학생 ⋈ 학번=학번 수강))
SELECT 학생.학번, 이름, 과목 FROM 학생 JOIN 수강 ON 학생.학번=수강.학번 WHERE 과목='DB';
```

| 학번 | 이름   | 과목 |
| ---- | ------ | ---- |
| 1001 | 김민준 | DB   |
| 1002 | 이서연 | DB   |
| 1003 | 박도윤 | DB   |

```sql
-- 수강 ÷ 필수: 필수 과목 중 "이 학생이 듣지 않은 과목"이 하나도 없는 학번
SELECT DISTINCT s.학번 FROM 수강 s
WHERE NOT EXISTS (
  SELECT 과목 FROM 필수 p
  WHERE NOT EXISTS (SELECT 1 FROM 수강 t WHERE t.학번=s.학번 AND t.과목=p.과목)
);
```

| 학번 |
| ---- |
| 1001 |
| 1003 |

디비전의 SQL이 복잡한 이유는 SQL에 "모두"를 뜻하는 연산자가 없기 때문이다. "필수 과목을 모두 들었다"를 "듣지 않은 필수 과목이 존재하지 않는다"로 바꿔 NOT EXISTS를 두 번 겹친다. 디비전 결과의 속성은 왼쪽 릴레이션 속성에서 오른쪽 릴레이션 속성을 뺀 것({학번, 과목} − {과목} = {학번})이다.

조인은 비교 조건에 따라 다시 나뉜다.

| 조인                     | 조건                                     | 결과                       |
| ------------------------ | ---------------------------------------- | -------------------------- |
| 세타 조인 (θ-join)       | =, ≠, <, ≤, >, ≥ 중 하나로 비교          | 조건을 만족하는 튜플 쌍    |
| 동등 조인 (equi-join)    | = 비교만 사용                            | 공통 속성이 두 번 나온다   |
| 자연 조인 (natural join) | 같은 이름의 속성을 = 로 비교             | 공통 속성을 한 번만 남긴다 |
| 외부 조인 (outer join)   | 짝이 없는 튜플도 NULL을 채워 결과에 포함 | LEFT, RIGHT, FULL 세 종류  |

외부 조인의 예로, 장학 릴레이션에 (1001, 100), (1004, 50)만 있을 때 학생과 LEFT JOIN하면 장학금이 없는 학생도 결과에 남고 금액 칸이 NULL(빈칸)이 된다.

```sql
SELECT 학생.학번, 이름, 금액 FROM 학생 LEFT JOIN 장학 ON 학생.학번=장학.학번;
```

| ---- | ------ | ---- |
| 1001 | 김민준 | 100  |
| 1002 | 이서연 |      |
| 1003 | 박도윤 |      |
| 1004 | 최지우 | 50   |

### 관계해석

관계해석은 "어떤 조건을 만족하는 튜플의 집합"을 수식으로 쓴다. 튜플 변수를 쓰는 튜플 관계해석과 도메인(속성 값) 변수를 쓰는 도메인 관계해석으로 나뉜다. 앞의 "OS를 수강한 학생의 이름"을 튜플 관계해석으로 쓰면 다음과 같다.

```math
\{\, s.\text{이름} \mid \text{학생}(s) \land \exists t\,(\text{수강}(t) \land t.\text{학번} = s.\text{학번} \land t.\text{과목} = \text{'OS'}) \,\}
```

"학생 s 중에서, 학번이 s와 같고 과목이 OS인 수강 튜플 t가 존재하는 s의 이름"이라는 뜻이다. 어떤 순서로 찾을지는 적지 않고 결과가 만족할 조건만 적는다. 같은 질의를 SQL로 실행하면 김민준과 박도윤이 나온다.

| 기호  | 이름                      | 뜻                                |
| ----- | ------------------------- | --------------------------------- |
| ∀     | 전칭 정량자 (universal)   | 모든 것에 대하여 (for all)        |
| ∃     | 존재 정량자 (existential) | 어떤 것이 존재한다 (there exists) |
| ∧ ∨ ¬ | 논리 연산자               | AND, OR, NOT                      |

> [!TIP] 시험에서는 이렇게 묻는다
> 기호와 연산자 이름을 짝짓는 문제(σ 실렉트, π 프로젝트, ⋈ 조인, ÷ 디비전)와 "관계해석은 비절차적, 관계대수는 절차적"을 바꿔 놓은 보기를 고르는 문제가 가장 많다. 교차곱의 차수·카디널리티 계산, "릴레이션 A의 속성 중 B의 모든 속성 값을 가진 튜플"이 무슨 연산인지(디비전) 묻는 문제도 나온다.

## 이상 현상과 함수 종속

### 이상 현상

테이블 하나에 여러 주제의 데이터를 섞어 두면 행을 삽입·삭제·갱신할 때 의도하지 않은 문제가 생긴다. 이것을 이상(anomaly) 현상이라고 한다. 도서 대여 기록을 한 테이블에 담은 예로 확인해 보자. 회원은 등급(일반, 우수)에 따라 대여 한도가 정해지고, 같은 회원이 같은 도서를 두 번 빌리지 않는다고 가정한다.

![회원별로 한 행에 대여 도서 여러 권이 들어 있는 비정규 릴레이션을 행으로 펼쳐 1NF 대여 릴레이션으로 만들고, 대여한도 3인 칸들은 갱신 이상, M02 행은 삭제 이상, 신규 회원은 삽입 이상의 예로 표시되어 있다](./images/eip-database-nf-1nf.svg '한 테이블에 회원·등급·도서·대여 정보가 섞여 있어 세 가지 이상이 모두 생긴다')

| 이상      | 이 테이블에서 생기는 일                                                                            |
| --------- | -------------------------------------------------------------------------------------------------- |
| 삽입 이상 | 아직 책을 빌리지 않은 신규 회원 M04를 넣으려면 기본키의 일부인 도서번호가 NULL이 되어 넣을 수 없다 |
| 삭제 이상 | M02의 유일한 대여 기록을 삭제하면 오세진 회원 정보와 "우수 등급 한도 5"라는 사실도 함께 사라진다   |
| 갱신 이상 | 일반 등급 한도를 3에서 4로 바꾸려면 네 행을 모두 고쳐야 하고, 하나라도 빠뜨리면 값이 서로 모순된다 |

세 이상의 공통 원인은 ==서로 다른 사실이 한 행에 묶여 중복 저장==된다는 점이다. "일반 등급의 한도는 3"이라는 사실 하나가 네 행에 반복 저장되어 있다. 이 원인을 정확히 짚어 내는 도구가 함수 종속이다.

### 함수 종속

속성 X의 값 하나에 속성 Y의 값이 항상 하나만 대응하면 "Y는 X에 함수적으로 종속된다"고 하고 `X \rightarrow Y{:math}`로 쓴다. X를 결정자(determinant), Y를 종속자(dependent)라고 한다. 회원번호가 M01이면 이름은 항상 김하늘이므로 회원번호 → 이름이다. 반대로 이름이 같은 회원이 여럿 있을 수 있으므로 이름 → 회원번호는 성립하지 않는다.

1NF 대여 릴레이션의 함수 종속은 다음과 같다.

| 함수 종속                     | 종류                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| {회원번호, 도서번호} → 대여일 | 완전 함수 종속: 기본키 전체가 있어야 결정된다                   |
| 회원번호 → 이름, 등급         | 부분 함수 종속: 기본키의 일부(회원번호)만으로 결정된다          |
| 도서번호 → 도서명             | 부분 함수 종속: 기본키의 일부(도서번호)만으로 결정된다          |
| 등급 → 대여한도               | 회원번호 → 등급 → 대여한도로 이어지는 이행적 함수 종속을 만든다 |

==완전 함수 종속==은 Y가 X 전체에 종속되고 X의 어떤 진부분집합에도 종속되지 않는 경우, ==부분 함수 종속==은 X의 일부만으로 Y가 결정되는 경우다. ==이행적 함수 종속==은 `X \rightarrow Y{:math}`이고 `Y \rightarrow Z{:math}`일 때 `X \rightarrow Z{:math}`가 성립하는 경우다.

<details>
<summary>암스트롱의 추론 규칙</summary>

주어진 함수 종속에서 새 함수 종속을 이끌어 내는 규칙이다. 앞의 세 개가 기본 규칙이고 나머지는 기본 규칙에서 유도된다.

| 규칙          | 내용                        |
| ------------- | --------------------------- |
| 재귀 (반사)   | Y ⊆ X이면 X → Y             |
| 증가 (첨가)   | X → Y이면 XZ → YZ           |
| 이행          | X → Y이고 Y → Z이면 X → Z   |
| 합집합 (결합) | X → Y이고 X → Z이면 X → YZ  |
| 분해          | X → YZ이면 X → Y이고 X → Z  |
| 의사 이행     | X → Y이고 WY → Z이면 WX → Z |

</details>

## 정규화

정규화(normalization)는 이상 현상이 생기지 않도록 함수 종속을 기준으로 릴레이션을 더 작은 릴레이션으로 분해하는 과정이다. 분해 단계마다 만족해야 하는 조건을 정규형(normal form)이라고 하며, 1NF에서 5NF로 갈수록 조건이 엄격해진다. 정규화의 원칙은 다음 세 가지다.

- ==무손실 분해==: 분해한 릴레이션을 자연 조인하면 원래 릴레이션이 그대로 복원되어야 한다.
- 정보의 중복을 줄인다. 하나의 사실은 한 곳에만 저장한다.
- 분리의 원칙: 하나의 독립된 관계성은 하나의 릴레이션으로 표현한다.

### 제1정규형(1NF)

1NF는 ==모든 속성의 도메인이 원자값==만으로 된 릴레이션이다. 앞 그림 위쪽의 비정규 릴레이션은 "대여 도서" 칸 하나에 도서 여러 권의 정보가 들어 있다. 이처럼 한 칸에 반복되는 값의 묶음을 반복 그룹(repeating group)이라고 한다. 반복 그룹을 행으로 펼치면 그림 아래쪽의 1NF 대여 릴레이션이 되고, 이제 한 행은 "회원 한 명이 도서 한 권을 빌린 기록"이 되므로 기본키는 {회원번호, 도서번호}다.

1NF는 관계 데이터 모델의 최소 조건이라 이상 현상은 그대로 남는다. 다음 단계에서 함수 종속을 하나씩 정리한다.

### 제2정규형(2NF)

2NF는 1NF를 만족하고, ==기본키가 아닌 모든 속성이 기본키에 완전 함수 종속==인 릴레이션이다. 다시 말해 부분 함수 종속을 제거한다.

![1NF 대여 릴레이션의 함수 종속 그림에서 회원번호가 이름과 등급을, 도서번호가 도서명을 결정하는 부분 종속이 주황색으로, 회원번호와 도서번호 전체가 대여일을 결정하는 완전 종속이 파란색으로 표시되고, 아래에 회원, 도서, 대여 세 릴레이션으로 분해한 결과가 있다](./images/eip-database-nf-2nf.svg '부분 종속을 만드는 결정자마다 릴레이션을 하나씩 떼어 낸다')

1. 부분 함수 종속을 찾는다. 회원번호 → 이름, 등급, 대여한도와 도서번호 → 도서명이다(대여한도는 등급을 거쳐 회원번호에 종속된다).
2. 결정자와 종속 속성을 새 릴레이션으로 떼어 낸다. 회원(회원번호, 이름, 등급, 대여한도), 도서(도서번호, 도서명)가 생긴다.
3. 원래 릴레이션에는 기본키와 완전 종속 속성만 남긴다. 대여(회원번호, 도서번호, 대여일)이 된다.

이제 신규 회원은 회원 릴레이션에만 넣으면 되므로 삽입 이상이 사라지고, M02의 대여 기록을 삭제해도 회원 정보는 남는다. 하지만 회원 릴레이션에는 "일반 등급의 한도는 3"이 두 행에 여전히 중복되어 있다.

### 제3정규형(3NF)

3NF는 2NF를 만족하고, ==기본키가 아닌 속성이 기본키에 이행적으로 종속되지 않는== 릴레이션이다.

![2NF 회원 릴레이션에서 회원번호가 등급을 결정하고 등급이 대여한도를 결정하는 이행 종속이 표시되고, 회원(회원번호, 이름, 등급)과 등급(등급, 대여한도)으로 분해한 결과가 아래에 있다](./images/eip-database-nf-3nf.svg '중간 결정자 등급을 기본키로 하는 릴레이션을 떼어 낸다')

1. 이행 종속을 찾는다. 회원번호 → 등급, 등급 → 대여한도이므로 회원번호 → 대여한도는 이행 종속이다.
2. 중간 결정자인 등급과 그 종속 속성을 등급(등급, 대여한도)으로 떼어 낸다.
3. 회원 릴레이션에는 회원(회원번호, 이름, 등급)만 남긴다. 등급은 이제 등급 릴레이션을 참조하는 외래키다.

분해가 무손실인지 SQLite로 확인해 보자. 3NF까지 분해한 네 릴레이션(대여, 회원, 등급, 도서)을 자연 조인하면 1NF 대여 릴레이션의 다섯 행이 그대로 나와야 한다.

```sql
SELECT 회원번호, 이름, 등급, 대여한도, 도서번호, 도서명, 대여일
FROM 대여 NATURAL JOIN 회원 NATURAL JOIN 등급 NATURAL JOIN 도서
ORDER BY 회원번호, 도서번호;
```

| 회원번호 | 이름   | 등급 | 대여한도 | 도서번호 | 도서명   | 대여일 |
| -------- | ------ | ---- | -------- | -------- | -------- | ------ |
| M01      | 김하늘 | 일반 | 3        | B11      | DB 개론  | 03-02  |
| M01      | 김하늘 | 일반 | 3        | B20      | 운영체제 | 03-05  |
| M02      | 오세진 | 우수 | 5        | B11      | DB 개론  | 03-04  |
| M03      | 한유나 | 일반 | 3        | B20      | 운영체제 | 03-07  |
| M03      | 한유나 | 일반 | 3        | B35      | 네트워크 | 03-06  |

다섯 행이 모두 복원된다(정렬 순서만 다르다). 이어서 `UPDATE 등급 SET 대여한도 = 4 WHERE 등급 = '일반';`을 실행하면 `changes()`가 1을 돌려준다. 정규화 전에는 네 행을 고쳐야 했던 갱신이 이제 한 행 수정으로 끝나고, 값이 서로 모순될 여지도 없다.

### 보이스·코드 정규형(BCNF)

BCNF(Boyce-Codd Normal Form)는 ==모든 결정자가 후보키==인 릴레이션이다. 3NF는 "기본키가 아닌 속성"에 대한 조건이라서, 키 속성끼리의 종속은 검사하지 않는다. 그 빈틈을 메운 것이 BCNF다.

![레슨 릴레이션에서 회원과 종목이 코치를 결정하고, 코치가 종목을 결정하는 함수 종속이 있으며, 코치는 후보키가 아니어서 박코치의 종목이 두 행에 중복된다. 코치배정(코치, 종목)과 수강(회원, 코치)으로 분해한 결과가 아래에 있다](./images/eip-database-nf-bcnf.svg '결정자인데 후보키가 아닌 속성이 있으면 BCNF가 아니다')

레슨(회원, 종목, 코치) 릴레이션을 보자. 회원은 종목마다 코치 한 명에게 배우고, 코치 한 명은 한 종목만 가르친다.

1. 함수 종속은 {회원, 종목} → 코치와 코치 → 종목이다. 후보키는 {회원, 종목}과 {회원, 코치}다.
2. 모든 속성이 어떤 후보키에 속하므로(키가 아닌 속성이 없으므로) 2NF와 3NF 조건은 자동으로 만족한다.
3. 그러나 결정자 코치는 후보키가 아니다. 그래서 "박코치는 수영 코치"라는 사실이 두 행에 중복되고, 정코치의 유일한 회원 오세진이 레슨을 그만두면 "정코치는 수영 코치"라는 사실도 사라진다.
4. 결정자 코치를 기본키로 하는 코치배정(코치, 종목)을 떼어 내고, 나머지는 수강(회원, 코치)로 남긴다.

### 제4정규형(4NF)과 제5정규형(5NF)

4NF와 5NF는 함수 종속이 아닌 종속을 다룬다.

==다치 종속(MVD, Multi-Valued Dependency)==은 속성 A의 값 하나에 속성 B의 값 집합이 대응하고, 그 집합이 다른 속성 C와 무관한 경우로 `A \twoheadrightarrow B{:math}`로 쓴다. 개발자(이름, 사용언어, 자격증) 릴레이션에서 김하늘이 Java와 Python을 쓰고 정보처리기사와 SQLD 자격증을 가졌다면, 언어와 자격증은 서로 관계가 없는데도 모든 조합을 저장해야 한다.

| 이름   | 사용언어 | 자격증       |
| ------ | -------- | ------------ |
| 김하늘 | Java     | 정보처리기사 |
| 김하늘 | Java     | SQLD         |
| 김하늘 | Python   | 정보처리기사 |
| 김하늘 | Python   | SQLD         |

자격증을 하나 더 따면 언어 수만큼 행을 추가해야 한다. 4NF는 ==다치 종속을 제거==한 릴레이션으로, 개발자언어(이름, 사용언어)와 개발자자격(이름, 자격증)으로 나누면 행이 2 + 2 = 4개로 같지만, 언어와 자격증이 늘어날 때 행 수가 곱이 아니라 합으로 늘어난다.

==조인 종속(JD, Join Dependency)==은 릴레이션을 세 개 이상으로 분해한 뒤 다시 조인해야만 원래 릴레이션이 복원되는 경우다. 공급(업체, 부품, 프로젝트)에서 "업체가 부품을 공급하고, 그 부품이 프로젝트에 쓰이며, 그 업체가 프로젝트에 참여하면 반드시 그 조합이 존재한다"는 업무 규칙이 있으면, 두 개로는 무손실 분해가 안 되고 (업체, 부품), (부품, 프로젝트), (업체, 프로젝트) 세 개로 나눠야 한다. 5NF는 ==후보키를 통하지 않는 조인 종속을 제거==한 릴레이션이다. 실무에서는 보통 3NF나 BCNF까지 정규화한다.

### 정규화 단계 요약

| 정규형 | 이전 단계에서 제거하는 것               | 외우는 머리글자 |
| ------ | --------------------------------------- | --------------- |
| 1NF    | 도메인이 원자값이 아닌 속성 (반복 그룹) | 도              |
| 2NF    | 부분 함수 종속                          | 부              |
| 3NF    | 이행적 함수 종속                        | 이              |
| BCNF   | 결정자이면서 후보키가 아닌 것           | 결              |
| 4NF    | 다치 종속                               | 다              |
| 5NF    | 후보키를 통하지 않는 조인 종속          | 조              |

머리글자를 이으면 "도부이결다조"가 된다. 정규화 문제의 절반은 이 표 한 장으로 풀린다.

### 반정규화

정규화를 많이 할수록 테이블이 잘게 나뉘어, 화면 하나를 그리려고 테이블 대여섯 개를 조인해야 하는 경우가 생긴다. 반정규화(denormalization)는 ==성능과 개발 편의를 위해 정규화된 모델을 의도적으로 통합·중복·분리==하는 과정이다. 데이터 일관성이 깨질 위험이 생기므로, 조회 성능 문제가 실제로 확인된 곳에만 적용한다.

| 기법             | 내용                                                         | 예                            |
| ---------------- | ------------------------------------------------------------ | ----------------------------- |
| 테이블 통합      | 1:1이나 1:N 관계의 테이블을 하나로 합친다                    | 회원과 회원상세를 회원 하나로 |
| 수평 분할        | 행 단위로 나눈다                                             | 주문을 연도별 테이블로        |
| 수직 분할        | 자주 쓰는 열과 드물게 쓰는 열을 나눈다                       | 게시글 목록 열과 본문 열 분리 |
| 중복 테이블 추가 | 집계 테이블, 진행 테이블, 특정 부분만 담은 테이블을 추가한다 | 일별 매출 합계 테이블         |
| 중복 속성 추가   | 조인 없이 조회하도록 다른 테이블의 속성을 복사한다           | 주문 테이블에 회원 이름 저장  |

> [!TIP] 시험에서는 이렇게 묻는다
> 정규형과 제거 대상을 짝짓는 문제가 거의 매번 나온다. "부분 함수 종속 제거"는 1NF에서 2NF로 가는 단계, "결정자이면서 후보키가 아닌 것 제거"는 3NF에서 BCNF로 가는 단계다. 이상의 종류(삽입·삭제·갱신)를 고르는 문제와 반정규화 기법이 아닌 것을 고르는 문제도 나온다.

## SQL의 분류와 절차형 SQL

### SQL 명령의 분류

SQL(Structured Query Language)은 관계 데이터베이스의 표준 질의어다. 명령은 하는 일에 따라 세 종류로 나뉜다.

| 분류                             | 명령                                    | 하는 일                           |
| -------------------------------- | --------------------------------------- | --------------------------------- |
| DDL (Data Definition Language)   | `CREATE`, `ALTER`, `DROP`, `TRUNCATE`   | 테이블, 뷰, 인덱스 같은 객체 정의 |
| DML (Data Manipulation Language) | `SELECT`, `INSERT`, `UPDATE`, `DELETE`  | 데이터 조회와 변경                |
| DCL (Data Control Language)      | `GRANT`, `REVOKE`, `COMMIT`, `ROLLBACK` | 권한 부여·회수, 트랜잭션 제어     |

`COMMIT`과 `ROLLBACK`은 트랜잭션 제어어(TCL)로 따로 분류하기도 한다. `DROP TABLE`은 테이블 정의까지 삭제하고, `TRUNCATE`는 정의는 남기고 모든 행을 삭제하며, `DELETE`는 조건에 맞는 행을 삭제한다(DML이라 롤백 가능). `DROP` 뒤의 `CASCADE`는 삭제할 객체를 참조하는 다른 객체까지 함께 삭제하고, `RESTRICT`는 참조하는 객체가 있으면 삭제를 거부한다.

### 절차형 SQL

절차형 SQL은 일반 프로그래밍 언어처럼 변수, 조건문(IF), 반복문(LOOP), 예외 처리를 SQL 안에서 쓸 수 있게 확장한 것이다. Oracle의 PL/SQL, SQL Server의 T-SQL이 대표적이며, DBMS 안에 저장되어 서버에서 실행되므로 응용 프로그램과 DB 사이를 오가는 통신량이 줄어든다.

| 종류                 | 실행 시점                                             | 반환값      | 예                                |
| -------------------- | ----------------------------------------------------- | ----------- | --------------------------------- |
| 프로시저 (procedure) | `CALL`이나 `EXECUTE`로 직접 호출할 때                 | 없어도 된다 | 월말 정산 작업 일괄 처리          |
| 사용자 정의 함수     | SQL 문 안에서 호출할 때                               | 반드시 하나 | `SELECT 세금계산(금액) FROM 주문` |
| 트리거 (trigger)     | 지정한 테이블에 INSERT·UPDATE·DELETE가 일어날 때 자동 | 없음        | 잔액이 바뀌면 변경 이력을 기록    |
| 이벤트 (event)       | 지정한 시각이나 주기가 되었을 때 자동                 | 없음        | 매일 새벽 3시에 오래된 로그 삭제  |

트리거는 사용자가 직접 호출하지 않아도 이벤트가 발생하면 DBMS가 자동으로 실행한다. 트리거 안에서는 `COMMIT`이나 `ROLLBACK` 같은 트랜잭션 제어 명령을 쓸 수 없다. SQLite에는 프로시저가 없지만 트리거는 지원하므로, 계좌 잔액이 바뀔 때마다 변경 로그를 남기는 트리거를 만들어 실행해 보았다.

```sql
CREATE TABLE 계좌(번호 TEXT PRIMARY KEY, 잔액 INTEGER CHECK (잔액 >= 0));
CREATE TABLE 변경로그(번호 TEXT, 이전 INTEGER, 이후 INTEGER);
CREATE TRIGGER 잔액변경 AFTER UPDATE OF 잔액 ON 계좌
BEGIN
  INSERT INTO 변경로그 VALUES (OLD.번호, OLD.잔액, NEW.잔액);
END;
INSERT INTO 계좌 VALUES ('A',10000),('B',0);
BEGIN;
UPDATE 계좌 SET 잔액 = 잔액 - 3000 WHERE 번호='A';
UPDATE 계좌 SET 잔액 = 잔액 + 3000 WHERE 번호='B';
COMMIT;
SELECT * FROM 변경로그;
```

| 번호 | 이전  | 이후 |
| ---- | ----- | ---- |
| A    | 10000 | 7000 |
| B    | 0     | 3000 |

`OLD`와 `NEW`는 트리거 안에서만 쓰는 이름으로, 각각 변경 전 행과 변경 후 행을 가리킨다. UPDATE를 두 번 실행했으므로 트리거도 두 번 실행되어 로그가 두 행 남았다. 이 계좌 예제는 뒤의 트랜잭션 절에서 다시 쓴다.

### 그룹 함수와 윈도 함수

그룹 함수(집계 함수)는 `GROUP BY`로 묶은 행 묶음마다 값 하나를 계산한다. `COUNT`, `SUM`, `AVG`, `MAX`, `MIN`이 있고, 그룹에 조건을 걸 때는 `WHERE`가 아니라 `HAVING`을 쓴다. 윈도 함수(window function)는 행을 묶어 없애지 않고, 각 행 옆에 순위나 누적값을 붙인다. `OVER` 절 안의 `PARTITION BY`가 묶을 기준, `ORDER BY`가 순서 기준이다.

```sql
SELECT 이름, 학과, 점수,
  RANK()       OVER (ORDER BY 점수 DESC) AS 전체순위,
  DENSE_RANK() OVER (ORDER BY 점수 DESC) AS 밀집순위,
  ROW_NUMBER() OVER (PARTITION BY 학과 ORDER BY 점수 DESC, 이름) AS 학과내번호
FROM 성적 ORDER BY 점수 DESC, 이름;
```

| 이름   | 학과   | 점수 | 전체순위 | 밀집순위 | 학과내번호 |
| ------ | ------ | ---- | -------- | -------- | ---------- |
| 김민준 | 컴퓨터 | 92   | 1        | 1        | 1          |
| 한유나 | 컴퓨터 | 92   | 1        | 1        | 2          |
| 오세진 | 경영   | 88   | 3        | 2        | 1          |
| 박도윤 | 컴퓨터 | 85   | 4        | 3        | 3          |
| 이서연 | 경영   | 78   | 5        | 4        | 2          |

92점 동점자 두 명이 있을 때 `RANK`는 다음 순위를 3으로 건너뛰고, `DENSE_RANK`는 2로 이어 붙이며, `ROW_NUMBER`는 동점이어도 1, 2처럼 서로 다른 번호를 매긴다. 같은 데이터에 `SELECT 학과, COUNT(*), ROUND(AVG(점수), 1) FROM 성적 GROUP BY 학과 HAVING AVG(점수) >= 85;`를 실행하면 평균 89.7인 컴퓨터학과(3명) 한 행만 나온다. 경영학과 평균 83은 HAVING 조건에서 걸러진다.

### 시스템 카탈로그

시스템 카탈로그(system catalog)는 DBMS가 스스로 관리하는 데이터베이스로, 테이블·열·인덱스·뷰·사용자·권한 같은 ==데이터베이스 객체에 대한 정보(메타데이터)==를 저장한다. 데이터 사전(data dictionary)이라고도 한다. 사용자는 SQL로 카탈로그를 조회할 수 있지만(SQLite의 `sqlite_schema`, PostgreSQL의 `information_schema`), `INSERT`·`UPDATE`로 직접 고칠 수는 없다. `CREATE TABLE`을 실행하면 DBMS가 카탈로그를 자동으로 갱신한다.

> [!TIP] 시험에서는 이렇게 묻는다
> 명령어를 주고 DDL·DML·DCL 중 어디에 속하는지 고르게 한다. `ALTER`는 DDL, `GRANT`·`REVOKE`는 DCL이다. 트리거의 정의(이벤트가 발생하면 자동 실행), 시스템 카탈로그의 특징("사용자가 직접 갱신할 수 있다"는 틀린 보기), `DROP … CASCADE`와 `RESTRICT`의 차이도 자주 나온다.

## 물리 데이터베이스 설계

### 인덱스

인덱스(index)는 책 뒤의 찾아보기처럼 ==키 값과 그 행의 저장 위치를 짝지어 정렬해 둔 별도의 자료 구조==다. 인덱스가 없으면 DBMS는 조건에 맞는 행을 찾으려고 테이블의 모든 행을 처음부터 끝까지 읽는다. 이것을 전체 테이블 스캔(full table scan)이라고 한다. 대부분의 DBMS는 인덱스를 B+ 트리로 구현한다.

![B+ 트리 인덱스에서 루트 노드 30, 60을 거쳐 30 이상 60 미만 범위의 리프 노드 30, 40, 50으로 내려가 키 50을 찾고, 리프의 각 키가 테이블의 행을 가리키며 리프끼리는 화살표로 연결되어 있다](./images/eip-database-index-btree.svg '트리 높이만큼만 노드를 읽으므로 행이 많아져도 찾는 시간이 크게 늘지 않는다')

SQLite에서 주문 10만 행을 만들고 고객ID로 검색하는 질의의 실행 계획을 인덱스 생성 전후로 비교했다.

```sql
EXPLAIN QUERY PLAN SELECT * FROM 주문 WHERE 고객ID = 42;
-- 인덱스 생성 전
-- `--SCAN 주문
CREATE INDEX idx_주문_고객 ON 주문(고객ID);
EXPLAIN QUERY PLAN SELECT * FROM 주문 WHERE 고객ID = 42;
-- 인덱스 생성 후
-- `--SEARCH 주문 USING INDEX idx_주문_고객 (고객ID=?)
```

`SCAN`은 전체 행을 읽는다는 뜻이고, `SEARCH … USING INDEX`는 인덱스로 해당 행만 찾아간다는 뜻이다. 같은 질의(결과 20행)의 실행 시간은 `.timer on`으로 측정했을 때 약 1.6ms에서 약 0.01ms로 줄었다. 측정값은 실행 환경에 따라 달라지지만, 읽는 행 수가 10만에서 20으로 줄어드는 차이는 같다.

인덱스는 공짜가 아니다. INSERT·UPDATE·DELETE를 할 때마다 인덱스도 함께 갱신해야 하므로 쓰기 작업은 느려지고 저장 공간도 더 든다. 그래서 검색 조건과 조인에 자주 쓰이고 값의 종류가 많은(선택도가 좋은) 열에 만들고, 성별처럼 값이 두세 종류뿐인 열이나 자주 바뀌는 열에는 만들지 않는다.

| 인덱스 종류         | 특징                                                                  |
| ------------------- | --------------------------------------------------------------------- |
| 클러스터드 인덱스   | 인덱스 키 순서대로 테이블 행 자체를 정렬해 저장. 테이블당 하나만 가능 |
| 넌클러스터드 인덱스 | 행은 그대로 두고 키와 행 위치만 따로 정렬. 테이블당 여러 개 가능      |
| 결합 인덱스         | 열 두 개 이상을 묶어 만든 인덱스. 선행 열이 조건에 있어야 효과적      |
| 해시 인덱스         | 해시 함수로 위치를 계산. = 비교는 빠르지만 범위 검색은 못 한다        |
| 비트맵 인덱스       | 값마다 비트 배열을 둔다. 값의 종류가 적은 열의 분석 질의에 쓴다       |

### 뷰

뷰(view)는 하나 이상의 기본 테이블에서 유도한 ==가상 테이블==이다. 저장 장치에 데이터를 따로 갖지 않고, 정의(SELECT 문)만 시스템 카탈로그에 저장해 두었다가 조회할 때마다 기본 테이블에서 계산한다.

| 장점                                                                | 단점                                            |
| ------------------------------------------------------------------- | ----------------------------------------------- |
| 논리적 데이터 독립성 제공 (기본 테이블이 바뀌어도 뷰 이름은 그대로) | 독립적인 인덱스를 가질 수 없다                  |
| 사용자마다 필요한 열·행만 보여 줘 보안에 유리                       | 정의를 `ALTER`로 바꿀 수 없어 삭제 후 다시 생성 |
| 복잡한 조인 질의를 이름 하나로 간단히 사용                          | 삽입·갱신·삭제에 제약이 많다                    |

뷰를 삭제하면 그 뷰를 바탕으로 만든 다른 뷰도 함께 삭제된다(`CASCADE`). SQLite는 뷰에 직접 INSERT하는 것을 허용하지 않는다.

```sql
CREATE VIEW 큰주문 AS SELECT 주문번호, 고객ID, 금액 FROM 주문 WHERE 금액 >= 99990;
INSERT INTO 큰주문 VALUES (1, 2, 3);
-- Parse error: cannot modify 큰주문 because it is a view
```

다른 DBMS에서도 뷰가 집계 함수, `DISTINCT`, `GROUP BY`, 조인을 포함하면 갱신할 수 없다. 갱신 가능한 뷰의 조건은 [SQL 뷰의 갱신 가능 조건과 삽입 SQL의 커서](/memo/db-sql-view-cursor)에 정리했다.

### 파티션

파티션(partition)은 큰 테이블이나 인덱스를 ==논리적으로는 하나로 두고 물리적으로는 여러 조각으로 나눠 저장==하는 기법이다. 주문 테이블이 수억 행이 되면 2023년 주문만 조회해도 전체를 뒤져야 하는데, 연도별 파티션으로 나눠 두면 해당 연도 파티션만 읽는다. 오래된 파티션만 통째로 백업하거나 삭제하기도 쉽다.

| 파티션 종류           | 나누는 기준                          | 예                                     |
| --------------------- | ------------------------------------ | -------------------------------------- |
| 범위 분할 (range)     | 열 값의 범위                         | 주문일 2023년, 2024년, 2025년          |
| 목록 분할 (list)      | 열 값의 목록                         | 지역 = {서울, 경기} / {부산, 울산}     |
| 해시 분할 (hash)      | 해시 함수 결과. 데이터를 고르게 분산 | 회원번호의 해시값을 4로 나눈 나머지    |
| 조합 분할 (composite) | 두 기준을 겹쳐 사용                  | 연도별 범위 분할 안에서 다시 해시 분할 |

### 클러스터와 데이터 지역화

클러스터(cluster)는 ==자주 함께 조회하는 행을 디스크의 같은 블록(또는 가까운 블록)에 모아 저장==하는 기법이다. 학과와 학생을 학과코드 기준으로 클러스터링하면, "컴퓨터학과와 소속 학생"을 조회할 때 디스크 블록 한두 개만 읽으면 된다. 같은 키 값을 가진 행들이 한곳에 있어 조인과 범위 검색이 빨라지지만, 키 값이 바뀌면 행을 다른 블록으로 옮겨야 하므로 갱신이 잦은 테이블에는 맞지 않다.

이처럼 함께 쓰는 데이터를 가까이 두어 디스크 접근을 줄이는 설계를 데이터 지역화(locality)라고 한다. 프로그램이 최근에 접근한 주소 근처를 다시 접근하는 경향을 이용하는 원리로, 운영체제의 페이지 교체에서 쓰는 지역성과 같은 개념이다.

### 분산 데이터베이스와 접근 제어

분산 데이터베이스는 네트워크로 연결된 여러 위치에 데이터를 나눠 저장하되, 사용자에게는 하나의 데이터베이스처럼 보이게 하는 시스템이다. 이 "하나처럼 보이게 하는 성질"을 투명성(transparency)이라고 한다.

| 투명성      | 사용자가 몰라도 되는 것                                     |
| ----------- | ----------------------------------------------------------- |
| 위치 투명성 | 데이터가 어느 서버에 저장되어 있는지                        |
| 중복 투명성 | 같은 데이터가 여러 곳에 복제되어 있는지                     |
| 병행 투명성 | 다른 트랜잭션이 동시에 같은 데이터를 다루고 있는지          |
| 장애 투명성 | 일부 서버나 통신망에 장애가 났는지 (트랜잭션은 정확히 처리) |

데이터베이스 접근 제어는 누가 어떤 데이터에 무엇을 할 수 있는지 정하는 정책이다.

| 접근 제어                  | 권한을 정하는 주체·기준                                        |
| -------------------------- | -------------------------------------------------------------- |
| 임의 접근 제어 (DAC)       | 데이터 소유자가 다른 사용자에게 권한을 부여 (SQL의 `GRANT`)    |
| 강제 접근 제어 (MAC)       | 시스템이 데이터의 보안 등급과 사용자의 인가 등급을 비교해 결정 |
| 역할 기반 접근 제어 (RBAC) | 사용자에게 역할(관리자, 조회 전용)을 주고 역할에 권한을 부여   |

장애에 대비해 데이터베이스를 두 대 이상으로 복제해 두는 구성을 이중화라고 하고, 백업 계획을 세울 때는 장애 후 서비스를 다시 시작하기까지 허용하는 시간(RTO, Recovery Time Objective)과 장애 시 잃어도 되는 데이터의 시간 범위(RPO, Recovery Point Objective)를 먼저 정한다. RPO가 1시간이면 적어도 1시간마다 백업이나 로그 복제를 해야 한다.

### CRUD 분석

CRUD 분석은 프로세스(업무 기능)와 테이블 사이에 어떤 연산(Create 생성, Read 조회, Update 갱신, Delete 삭제)이 일어나는지 행렬로 정리하는 기법이다. 물리 설계 단계에서 트랜잭션이 몰리는 테이블을 찾아 인덱스나 파티션을 결정하는 근거로 쓴다.

| 프로세스 \ 테이블 | 회원 | 도서 | 대여 |
| ----------------- | ---- | ---- | ---- |
| 회원 가입         | C    |      |      |
| 도서 등록         |      | C    |      |
| 대여 처리         | R    | R    | C    |
| 반납 처리         |      |      | U    |
| 회원 탈퇴         | D    |      | R    |

행렬을 검토할 때는 C가 하나도 없는 테이블(데이터를 누가 만드는가), R이 하나도 없는 테이블(쓰지 않는 테이블인가), 아무 연산도 없는 프로세스가 있는지 확인한다.

> [!TIP] 시험에서는 이렇게 묻는다
> 뷰의 특징 중 틀린 것("뷰는 ALTER로 정의를 변경할 수 있다", "뷰는 독립적인 인덱스를 가진다")을 고르는 문제가 매년 나온다. 파티션 종류(범위, 목록, 해시, 조합)를 고르거나, 분산 데이터베이스 투명성 네 가지에 속하지 않는 것(예: "규모 투명성")을 고르는 문제, CRUD의 각 글자 뜻을 묻는 문제도 나온다.

## 데이터 전환

데이터 전환은 기존 시스템(원천 시스템)의 데이터를 새 시스템(목적 시스템)의 구조에 맞게 옮기는 작업이다. 10년 동안 쓰던 학사 시스템을 새로 만들면, 기존 학생·성적 데이터를 새 테이블 구조로 바꿔 넣어야 새 시스템을 바로 쓸 수 있다. 이 작업을 초기 데이터 구축이라고도 한다.

데이터 전환의 핵심 기술은 ETL이다.

| 단계                  | 하는 일                                    | 예                                          |
| --------------------- | ------------------------------------------ | ------------------------------------------- |
| 추출 (Extraction)     | 원천 시스템에서 데이터를 읽어 낸다         | 구 시스템 DB를 덤프하거나 파일로 내보낸다   |
| 변환 (Transformation) | 목적 시스템 형식에 맞게 정제·변환·통합한다 | 날짜 `20240208` → `2024-02-08`, 코드값 매핑 |
| 적재 (Loading)        | 변환한 데이터를 목적 시스템에 저장한다     | 새 DB에 일괄 INSERT                         |

전환은 보통 다음 순서로 진행한다.

1. **전환 계획 수립**: 대상 테이블, 전환 규칙(구 열 → 새 열), 일정, 체크리스트, 실패 시 복구 방법을 정한다.
2. **데이터 정제**: 원천 데이터의 품질을 분석해 오류 데이터를 찾고 고친다. 같은 고객이 두 번 등록된 중복 데이터, 필수 값이 비어 있는 결측 데이터, 주민번호 자릿수가 틀린 형식 오류 등을 측정해 정제 대상을 정한다.
3. **전환 수행**: ETL 프로그램을 실행한다. 실제 전환 전에 모의 전환을 여러 번 수행해 시간을 측정하고 오류를 고친다.
4. **데이터 검증**: 원천과 목적의 데이터가 일치하는지 확인한다. 건수 비교(구 시스템 학생 12,345명 = 새 시스템 12,345명), 금액 합계 비교, 표본 데이터 대조, 응용 프로그램으로 화면을 띄워 확인하는 방법을 함께 쓴다.

> [!TIP] 시험에서는 이렇게 묻는다
> ETL의 세 글자가 무엇의 약자인지, 데이터 전환 계획서에 들어가는 항목, 데이터 정제와 데이터 검증의 순서를 묻는다. 문항 수는 다른 주요항목보다 적다.

## 트랜잭션

### 트랜잭션과 ACID

트랜잭션(transaction)은 데이터베이스의 상태를 바꾸기 위해 ==한꺼번에 모두 수행되어야 하는 연산들의 묶음==이자 작업의 논리적 단위다. 계좌 A에서 B로 3,000원을 이체하는 작업은 "A에서 3,000원 빼기"와 "B에 3,000원 더하기" 두 UPDATE로 이루어진다. 첫 번째만 실행되고 시스템이 멈추면 3,000원이 허공으로 사라진다. 그래서 두 UPDATE를 하나의 트랜잭션으로 묶어, 둘 다 반영하거나 둘 다 취소한다.

트랜잭션이 지켜야 하는 네 가지 성질을 머리글자를 따서 ACID라고 한다.

| 성질                       | 뜻                                                                 | 계좌 이체에서                                                   |
| -------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------- |
| 원자성 (Atomicity)         | 모두 반영(COMMIT)되거나 전혀 반영되지 않아야(ROLLBACK) 한다        | 빼기만 반영되고 더하기가 빠지는 일이 없다                       |
| 일관성 (Consistency)       | 실행 전후 모두 데이터베이스가 무결성 제약을 만족하는 상태여야 한다 | 두 계좌 잔액의 합은 이체 전후에 같고, 잔액은 음수가 되지 않는다 |
| 독립성·격리성 (Isolation)  | 실행 중인 트랜잭션의 중간 결과를 다른 트랜잭션이 볼 수 없다        | 이체 도중에 잔액을 조회한 다른 사용자가 중간 값을 보지 않는다   |
| 영속성·지속성 (Durability) | 성공적으로 완료된 결과는 장애가 나도 영구히 유지된다               | COMMIT 직후 정전이 나도 이체 결과는 남는다                      |

원자성이 실제로 동작하는지 SQLite로 확인했다. 앞 절의 계좌 테이블(A 7,000원, B 3,000원, 잔액 CHECK ≥ 0)에서 20,000원을 이체하는 트랜잭션을 실행하면, B에 더하는 UPDATE는 성공하지만 A에서 빼는 UPDATE는 잔액이 음수가 되어 CHECK 제약에 걸린다.

```sql
BEGIN;
UPDATE 계좌 SET 잔액 = 잔액 + 20000 WHERE 번호='B';  -- 성공
UPDATE 계좌 SET 잔액 = 잔액 - 20000 WHERE 번호='A';  -- CHECK constraint failed: 잔액 >= 0
ROLLBACK;
SELECT * FROM 계좌;
```

| 번호 | 잔액 |
| ---- | ---- |
| A    | 7000 |
| B    | 3000 |

ROLLBACK으로 이미 성공한 B의 UPDATE까지 취소되어 두 계좌 모두 이체 전 값으로 돌아왔다.

| 성질   | 보장하는 DBMS 구성 요소  |
| ------ | ------------------------ |
| 원자성 | 회복 관리자 (로그, UNDO) |
| 일관성 | 무결성 제약 검사         |
| 독립성 | 병행 제어 (로킹)         |
| 영속성 | 회복 관리자 (로그, REDO) |

### 트랜잭션의 상태

![활동 상태에서 마지막 연산을 실행하면 부분 완료, COMMIT하면 완료가 되고, 활동 중 오류가 나거나 부분 완료에서 반영 중 장애가 나면 실패, ROLLBACK하면 철회 상태가 된다](./images/eip-database-tx-states.svg '부분 완료는 마지막 연산까지 실행했지만 아직 COMMIT하지 않은 상태다')

| 상태      | 뜻                                                 |
| --------- | -------------------------------------------------- |
| 활동      | 트랜잭션이 실행 중인 상태                          |
| 부분 완료 | 마지막 연산까지 실행했지만 COMMIT 직전인 상태      |
| 완료      | COMMIT으로 결과를 데이터베이스에 반영한 상태       |
| 실패      | 오류나 장애로 실행을 계속할 수 없는 상태           |
| 철회      | ROLLBACK으로 트랜잭션 실행 이전 상태로 되돌린 상태 |

==부분 완료와 완료의 구분==이 시험에 자주 나온다. 부분 완료는 연산은 다 끝났지만 아직 영구 반영을 확정하지 않은 상태다.

### 병행 제어

여러 트랜잭션을 동시에 실행하면 CPU와 디스크를 놀리지 않아 처리량이 늘어난다. 하지만 같은 데이터를 동시에 다루면 문제가 생긴다. 재고가 10개인 상품을 T1이 3개, T2가 2개 판매하는 경우를 보자.

![왼쪽은 로킹 없이 T1과 T2가 모두 재고 10을 읽고 각자 7과 8을 써서 최종 재고가 8이 되는 갱신 분실, 오른쪽은 T1이 lock을 잡는 동안 T2가 대기했다가 7을 읽어 5를 쓰는 정상 실행이다](./images/eip-database-lost-update.svg '로킹은 한 트랜잭션이 데이터를 쓰는 동안 다른 트랜잭션의 접근을 막는다')

로킹이 없으면 두 트랜잭션이 모두 10을 읽은 뒤 각자 계산한 값을 쓰므로, 나중에 쓴 T2의 8만 남고 T1의 판매 기록이 사라진다. 정답은 10 − 3 − 2 = 5다. 병행 실행으로 생기는 문제는 다음 네 가지다.

| 문제                                   | 상황                                                                                                        |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 갱신 분실 (Lost Update)                | 두 트랜잭션이 같은 데이터를 갱신해 한쪽의 갱신 결과가 사라진다                                              |
| 비완료 의존성 (Uncommitted Dependency) | 아직 COMMIT하지 않은 다른 트랜잭션의 값을 읽었는데 그 트랜잭션이 철회된다. 오손 읽기(dirty read)라고도 한다 |
| 모순성 (Inconsistency)                 | 한 트랜잭션이 여러 데이터를 읽는 도중 다른 트랜잭션이 값을 바꿔 서로 맞지 않는 값을 읽는다                  |
| 연쇄 복귀 (Cascading Rollback)         | 한 트랜잭션이 철회되면 그 값을 읽은 다른 트랜잭션들도 줄줄이 철회해야 한다                                  |

병행 제어의 목표는 여러 트랜잭션을 동시에 실행해도 ==어떤 순서로 하나씩 차례대로 실행한 것(직렬 실행)과 같은 결과==가 나오게 하는 것이다. 이 성질을 직렬 가능성(serializability)이라고 한다.

| 병행 제어 기법          | 원리                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 로킹 (Locking)          | 데이터에 lock을 걸어 lock을 가진 트랜잭션만 접근한다. 공유 lock(읽기)과 배타 lock(쓰기)                          |
| 2단계 로킹 (2PL)        | lock을 얻기만 하는 확장 단계와 풀기만 하는 축소 단계로 나눈다. 직렬 가능성을 보장하지만 교착 상태는 생길 수 있다 |
| 타임스탬프 순서         | 트랜잭션이 시작한 시각 순서대로 접근을 허용하고, 순서를 어기면 철회한다. 교착 상태가 없다                        |
| 낙관적 검증 (검증 기법) | 일단 검사 없이 실행하고 끝날 때 충돌을 검사해 문제가 있으면 철회한다                                             |
| 다중 버전 (MVCC)        | 데이터를 갱신할 때 새 버전을 만들고, 읽는 트랜잭션에게는 자기 시작 시각의 버전을 보여 준다                       |

로킹 단위(lock을 거는 데이터의 크기)는 데이터베이스 전체, 테이블, 페이지, 행, 필드 중에서 고른다.

| 로킹 단위     | lock 수 | 병행성 | 관리 부담 |
| ------------- | ------- | ------ | --------- |
| 크다 (테이블) | 적다    | 낮다   | 작다      |
| 작다 (행)     | 많다    | 높다   | 크다      |

==로킹 단위가 작을수록 병행성은 높아지고 관리는 복잡해진다==는 관계를 반대로 바꾼 보기가 단골 오답이다.

SQL 표준은 독립성을 얼마나 엄격히 지킬지 네 단계의 격리 수준(isolation level)으로 정의한다. 아래로 갈수록 엄격하고 느리다.

| 격리 수준        | 오손 읽기 | 반복 불가능 읽기 | 팬텀 읽기 |
| ---------------- | --------- | ---------------- | --------- |
| READ UNCOMMITTED | 발생      | 발생             | 발생      |
| READ COMMITTED   | 방지      | 발생             | 발생      |
| REPEATABLE READ  | 방지      | 방지             | 발생      |
| SERIALIZABLE     | 방지      | 방지             | 방지      |

반복 불가능 읽기는 같은 행을 두 번 읽는 사이에 다른 트랜잭션이 값을 바꿔 결과가 달라지는 현상, 팬텀 읽기는 같은 조건으로 두 번 조회하는 사이에 다른 트랜잭션이 행을 추가해 처음 없던 행이 나타나는 현상이다.

### 회복

회복(recovery)은 트랜잭션 실행 중 장애가 발생했을 때 데이터베이스를 장애 발생 이전의 일관된 상태로 되돌리는 작업이다. 장애는 트랜잭션 장애(잘못된 입력, 제약 위반), 시스템 장애(전원 차단, 운영체제 오류로 메모리 내용 손실), 미디어 장애(디스크 손상)로 나뉜다.

회복의 기본 도구는 로그(log)다. DBMS는 데이터를 바꾸기 전에 "트랜잭션 T2가 X를 10에서 7로 바꿈"처럼 변경 전 값과 변경 후 값을 로그에 먼저 기록한다(WAL, Write-Ahead Logging). 장애가 나면 로그를 읽어 두 가지 연산을 수행한다.

| 연산          | 하는 일                             | 대상                        |
| ------------- | ----------------------------------- | --------------------------- |
| REDO (재실행) | 로그의 변경 후 값으로 다시 반영한다 | COMMIT 기록이 있는 트랜잭션 |
| UNDO (취소)   | 로그의 변경 전 값으로 되돌린다      | COMMIT 기록이 없는 트랜잭션 |

로그를 처음부터 끝까지 다 읽으면 회복이 오래 걸리므로, DBMS는 주기적으로 메모리의 변경 내용을 디스크에 모두 기록하고 그 시점을 로그에 남긴다. 이 시점을 검사점(checkpoint)이라고 한다. 장애가 나면 마지막 검사점 이후의 로그만 조사하면 된다.

![검사점 tc와 장애 tf 사이에 트랜잭션 다섯 개가 있다. 검사점 전에 끝난 T1은 처리가 필요 없고, 장애 전에 COMMIT한 T2와 T3는 REDO, 장애 시각까지 COMMIT하지 못한 T4와 T5는 UNDO 대상이다](./images/eip-database-recovery.svg '검사점 이전에 완료된 트랜잭션은 이미 디스크에 반영되어 있어 회복 대상이 아니다')

| 회복 기법                     | 원리                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| 즉시 갱신 (Immediate Update)  | 트랜잭션 실행 중에도 변경 내용을 바로 DB에 반영. 장애 시 REDO와 UNDO 모두 필요                           |
| 지연 갱신 (Deferred Update)   | COMMIT될 때까지 변경을 로그에만 기록하고 DB 반영을 미룬다. 장애 시 REDO만 필요(UNDO 불필요)              |
| 검사점 (Checkpoint)           | 로그 기반 회복에서 조사 범위를 마지막 검사점 이후로 줄인다                                               |
| 그림자 페이징 (Shadow Paging) | 로그 없이 페이지 테이블을 두 개 둔다. 실행 중에는 사본만 고치고, 장애 나면 원본 페이지 테이블로 돌아간다 |
| 미디어 회복                   | 디스크 손상에 대비해 주기적으로 백업(덤프)해 두고 백업 이후 로그로 REDO                                  |

> [!TIP] 시험에서는 이렇게 묻는다
> ACID의 네 성질 설명을 주고 이름을 고르는 문제가 3과목에서 가장 자주 나오는 문제 중 하나다. "모두 반영되거나 전혀 반영되지 않아야 한다"는 원자성이다. 그 밖에 트랜잭션 상태(부분 완료), 로킹 단위와 병행성의 관계, "지연 갱신 기법은 UNDO가 필요 없다", 2PL의 두 단계 이름(확장, 축소)이 자주 나온다.

## 헷갈리는 짝 정리

| 짝                        | 구분                                                                     |
| ------------------------- | ------------------------------------------------------------------------ |
| 차수 / 카디널리티         | 차수는 속성(열)의 수, 카디널리티는 튜플(행)의 수                         |
| 슈퍼키 / 후보키           | 슈퍼키는 유일성만, 후보키는 유일성과 최소성                              |
| 개체 무결성 / 참조 무결성 | 개체는 기본키의 NULL·중복 금지, 참조는 외래키가 있는 기본키 값 또는 NULL |
| 실렉트 / 프로젝트         | 실렉트(σ)는 행을 고르는 수평 연산, 프로젝트(π)는 열을 고르는 수직 연산   |
| 관계대수 / 관계해석       | 관계대수는 절차적, 관계해석은 비절차적                                   |
| 2NF / 3NF                 | 2NF는 부분 함수 종속 제거, 3NF는 이행적 함수 종속 제거                   |
| 3NF / BCNF                | 3NF는 키가 아닌 속성만 검사, BCNF는 모든 결정자가 후보키                 |
| 정규화 / 반정규화         | 정규화는 이상 제거를 위한 분해, 반정규화는 성능을 위한 통합·중복         |
| 원자성 / 일관성           | 원자성은 전부 또는 전무, 일관성은 실행 전후 무결성 유지                  |
| 즉시 갱신 / 지연 갱신     | 즉시 갱신은 REDO·UNDO 모두, 지연 갱신은 REDO만                           |
| 로킹 단위 큼 / 작음       | 크면 병행성 낮고 관리 쉬움, 작으면 병행성 높고 관리 복잡                 |
