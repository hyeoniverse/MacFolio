## desktop-core: 네 단계

#16의 목표는 "로직은 한 번 작성하고, UI 프레임워크는 교체할 수 있게"였다. 기능이 거의 정해진 뒤로 미뤄 둔 일이다. 네 단계로 나눠 PR 하나씩 올렸다.

1. **창 관리** — 어떤 앱이 켜져 있고 어떤 창이 맨 앞인지 정하는 로직이 React Context 안에 `useState`·`useCallback`으로 있었다. 이것을 store로 꺼내고, React는 `useSyncExternalStore`로 구독만 한다. 패키지가 `react`나 `window`를 쓰면 타입 검사에서 바로 걸리게 막았다 ([창 관리를 React 밖으로](/memo/desktop-core-windows)).
2. **메모** — 글 읽기·정렬, 태그, 폴더 정리, 찾기, 글 검사. 대부분 처음부터 순수 함수라 경로만 바뀌었다. `localStorage`를 직접 읽던 세 파일은, 값을 검사하는 일은 core에, 브라우저에 읽고 쓰는 일은 앱에 나눴다 ([메모 로직을 desktop-core로](/memo/desktop-core-memo)).
3. **음악** — `MusicContext` 하나가 "무엇을 틀지"와 "audio를 어떻게 할지"를 함께 했다. 앞쪽을 플레이어 store로 옮기고, 동작마다 `moved`, `stopped`, `restart` 같은 결과를 돌려주게 했다. React는 그 결과를 보고 audio만 다룬다 ([음악 플레이어를 둘로 나누기](/memo/desktop-core-music)).
4. **화면과 서버가 같은 규칙** — 폴더 3단, 이름 30자, 제목 100자 같은 규칙이 화면과 서버에 따로 적혀 있었다. desktop-core 한 곳에 두고, 화면(Vite)은 TypeScript 소스를, 서버(Node)는 빌드한 JS를 읽게 `package.json`의 `exports` 조건으로 나눴다. 배포 이미지에서 서버가 이 규칙을 실제로 불러오는지도 확인했다 ([화면과 서버가 같은 규칙을 쓰기](/memo/desktop-core-shared-rules)).

## 인라인 스타일과 블로그 폴더

자정 무렵에는 컴포넌트 곳곳의 `style={{...}}`를 세 가지로 나눴다. 늘 같은 값은 CSS 파일로, 데이터에 따라 바뀌는 색·크기는 `cssVars()`로 CSS 변수만 넘기고, 메뉴 위치처럼 계산된 좌표만 인라인에 남겼다. 바꾸기 전후 화면 37장을 찍어 픽셀이 하나도 다르지 않은지 확인했다([style={{...}} 정리](/memo/inline-style-cleanup)).

밤에는 블로그 글 84개의 폴더를 다시 나눴다. 전날 나눈 폴더는 모두 '개발기/MacFolio' 아래에 있어서, 3단까지인 폴더 중 두 단을 늘 같은 이름이 차지했다. 나눈 기준도 앱(메모), 화면(휴대폰), 계층(백엔드), 글 종류(회고)가 섞여 있었다. 프론트엔드·백엔드·인프라·회고로 나누고, 프론트엔드는 어떤 종류의 문제였는지로 다시 나눴다([블로그 폴더 다시 나누기](/memo/memo-folders-reorg)).

## 돌아보며

구조를 바꾸는 날은 "바뀐 것이 없다"를 보여 주는 것이 일이다. 인라인 스타일은 화면 37장의 픽셀 비교로, desktop-core는 기존 E2E가 그대로 통과하는 것으로 보였다. 창 store, 메모 목록 계산(`noteView`), 음악 플레이어 store에는 단위 시험이 새로 생겼다. React 안에 있을 때는 컴포넌트를 그려야 시험할 수 있던 로직이 이제 함수 하나로 시험된다.

아쉬운 것은 쌓아 올린 PR이다. 음악(#141)은 새 글이 새 폴더 구조를 써야 해서 블로그 폴더 PR(#143)의 브랜치 위에 쌓았다. 이날은 #143이 나중에 main에 들어가며 #141도 함께 들어갔다. 그런데 바로 다음 날 같은 방식으로 쌓은 휴지통 PR 두 개는 main에 들어가지 못했다. 쌓은 PR은 아래 PR이 머지되는 순서에 따라 결과가 달라진다. 이날 운 좋게 맞았던 순서가 다음 날에는 틀렸다.
