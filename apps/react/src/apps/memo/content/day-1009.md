## desktop-core: 네 단계 분리

### 목표와 의존 방향

#16의 목표는 "로직은 한 번 작성하고, UI 프레임워크는 교체할 수 있게"였다. 로직이 React 컴포넌트 안에 있으면 두 가지가 어렵다. 첫째, 서버(Node)는 React를 실행하지 않으므로 같은 규칙을 서버에서 쓰려면 다시 작성해야 한다. 둘째, 규칙 하나를 시험하려면 컴포넌트를 렌더링해야 한다. 기능이 거의 확정될 때까지 일부러 미룬 작업이다.

모노레포(저장소 하나에 여러 패키지를 함께 두는 구성)에 `packages/desktop-core` 패키지를 만들고 로직을 옮겼다. 분리한 뒤의 의존 방향은 다음과 같다.

```text
apps/react (화면)  ──구독(useSyncExternalStore)──▶  packages/desktop-core (로직)
apps/api   (서버)  ──빌드한 JS를 import──────────▶  packages/desktop-core/memo (규칙)

desktop-core가 react나 window를 사용하면 타입 검사에서 실패한다
```

화살표는 한 방향이다. 화면과 서버가 desktop-core를 사용하고, desktop-core는 둘 중 어느 쪽도 알지 못한다. 이 방향을 지키게 하는 장치는 설정이다. desktop-core의 `tsconfig.json`에는 브라우저 타입(`DOM`)이 없어서 `window`나 `localStorage`를 쓰면 `Cannot find name` 오류가 나고, 의존성에 `react`가 없어서 React를 불러올 수도 없다. 규칙을 어긴 코드는 리뷰 전에 빌드 단계에서 실패한다.

### React가 바깥 store를 구독하는 방법

React 컴포넌트의 상태(`useState`)는 그 컴포넌트 안에만 있다. 로직을 React 밖으로 옮기면 상태도 밖으로 나가므로, React가 바깥 상태의 변화를 알아야 다시 렌더링할 수 있다. 이를 위한 React 공식 훅이 `useSyncExternalStore`다. 바깥 저장소(store)가 두 함수를 제공하면 된다.

| 함수        | 역할                                                   |
| ----------- | ------------------------------------------------------ |
| `subscribe` | 변경되면 호출할 함수를 등록하고, 등록 해제 함수를 반환 |
| `getState`  | 현재 상태를 반환 (React 문서에서는 `getSnapshot`)      |

desktop-core의 `createStore`는 이 두 함수와 상태 변경 함수(`setState`)만 가진 28줄짜리 저장소다. 창 store, 음악 플레이어 store가 이것을 기반으로 만들어진다.

![desktop-core의 창 store와 음악 플레이어 store, React의 useSyncExternalStore 구독과 audio 제어의 관계](./images/day-1009-store-subscribe.svg 'store는 상태와 결과 값만 내놓는다. 화면을 다시 그리고 audio 요소를 제어하는 일은 React 쪽에 남는다')

| 1    | 창 관리   | 실행 중인 앱과 맨 앞 창을 정하는 로직이 React Context 안의 `useState`·`useCallback`에 있음 | store로 분리하고 React는 `useSyncExternalStore`로 구독만. 패키지가 `react`나 `window`를 사용하면 타입 검사에서 실패                                                                   | [창 관리 규칙을 useSyncExternalStore로 구독하는 프레임워크 무관 패키지로 옮기기](/memo/desktop-core-stores#창-관리-작은-store와-usesyncexternalstore) |

2단계의 메모 로직은 대부분 이미 순수 함수(같은 입력에 항상 같은 결과를 반환하고 외부 상태를 바꾸지 않는 함수)여서 파일 위치만 옮기면 되었다. 걸린 곳은 `localStorage`를 읽고 쓰는 함수 세 개였다. 이 함수들을 "저장된 값이 올바른 모양인지 검사하는 부분"과 "브라우저 저장소에서 읽고 쓰는 부분"으로 나눠, 앞쪽만 desktop-core로 옮겼다.

3단계의 음악은 "다음 곡" 버튼 하나에도 두 가지 일이 섞여 있었다. 다음에 재생할 곡을 정하는 일(대기열·셔플·반복 상태만 있으면 계산 가능)과 실제 `<audio>` 요소를 재생·정지하는 일(브라우저 필요)이다. 앞쪽을 store로 옮기고, store는 결과만 반환한다. 예를 들어 지금 곡을 3초 넘게 들은 상태에서 "이전 곡"을 누르면 `previous(초)`가 `'restart'`를 반환하고, React는 그 값을 보고 지금 곡을 처음부터 재생한다. `next()`가 `'stopped'`를 반환하면 `audio.pause()`를 호출한다.

### 화면과 서버가 같은 규칙 파일을 쓰는 방법

4단계에서는 같은 파일을 두 환경이 다른 형태로 불러와야 했다. 화면을 빌드하는 Vite는 TypeScript 소스를 바로 처리할 수 있어, desktop-core를 고치면 다시 빌드하지 않아도 화면에 즉시 반영된다. 서버의 Node는 빌드한 JavaScript가 필요하다. `package.json`의 `exports` 필드는 불러오는 환경이 내세우는 조건 이름에 따라 다른 파일을 가리킬 수 있다.

![apps/react는 source 조건으로 src의 TypeScript를, apps/api는 default 조건으로 dist의 JS를 불러오는 구조](./images/day-1009-package-exports.svg '같은 import 문(@macfolio/desktop-core/memo)이 환경에 따라 다른 파일로 연결된다')

예를 들어 폴더 이름 30자 제한은 desktop-core에 한 번만 정의된다. 관리자가 화면에서 31자 이름을 입력하면 화면이 이 규칙으로 바로 오류를 표시하고, 요청을 조작해 서버에 직접 보내도 서버가 같은 규칙으로 거절한다. 그전에는 한쪽 규칙만 30자에서 40자로 바꾸면 화면은 허용하고 서버는 거절하는 불일치가 생길 수 있었다.

desktop-core에는 단위 시험 129개가 새로 생겼다. API 단위 시험은 7개 줄었는데, 서버에 따로 있던 메모 규칙 시험이 desktop-core로 이동해 같은 규칙을 한 곳에서 한 번 시험하게 되었기 때문이다.

## 인라인 스타일 정리

인라인 스타일은 JSX에서 `style={{ color: '#0a84ff' }}`처럼 요소에 직접 붙이는 스타일이다. CSS 파일의 규칙과 달리 다크 모드나 화면 폭에 따른 규칙(미디어 쿼리)을 적용할 수 없고, 우선순위가 높아 CSS 파일에서 덮어쓰기 어렵다. 컴포넌트 곳곳의 `style={{...}}`를 세 가지로 분류했다([#138](https://github.com/hyeoniverse/MacFolio/pull/138), [인라인 style을 CSS 클래스와 CSS 변수 전달 함수 cssVars()로 옮기기](/memo/inline-style-cleanup)).

| 종류                                    | 처리                          | 예                                                 |
| --------------------------------------- | ----------------------------- | -------------------------------------------------- |
| 항상 같은 값                            | CSS 파일로 이동               | 어느 화면에서나 같은 여백·정렬 값 → CSS 클래스     |
| 데이터에 따라 바뀌는 색·크기            | `cssVars()`로 CSS 변수만 전달 | 저장소 언어 색 → `--color`, CSS에서 `var(--color)` |
| 실행 중에 계산되는 좌표 (예: 메뉴 위치) | 인라인 스타일 유지            | `style={{ top, left }}`                            |

두 번째 방식은 값만 CSS 변수(`--이름`)로 넘기고, 그 값을 어디에 어떻게 쓸지는 CSS 파일이 정한다. GitHub 앱의 저장소 언어 표시가 그 예다.

```tsx
<span className="gh-language-dot" style={cssVars({ color: LANGUAGE_COLORS[repo.language] })} />
```

```css
.gh-language-dot {
	background-color: var(--color, var(--gh-muted));
}
```

TypeScript 저장소면 `--color`에 파란색이 전달되어 파란 점이 되고, 색 표에 없는 언어면 `cssVars()`가 키를 빼므로 `var()`의 기본값인 회색이 적용된다.

## 돌아보며

구조를 바꿀 때는 "동작이 바뀌지 않았다"를 증명하는 데 가장 공을 들였다. 인라인 스타일은 화면 37장의 픽셀 비교로, desktop-core는 기존 E2E가 그대로 통과하는 것으로 증명했다. 창 store, 메모 목록 계산(`noteView`), 음악 플레이어 store에는 단위 시험을 새로 붙였다. React 안에 있던 로직은 컴포넌트를 렌더링해야 시험할 수 있었지만, 이제 함수 단위로 시험한다.

### 스택 PR은 머지 순서에 따라 결과가 달라진다

스택 PR은 PR 하나를 다른 PR의 브랜치 위에 쌓는 방식이다. 아래 PR이 아직 머지되지 않았는데 그 변경이 필요한 작업을 이어서 할 때 쓴다. 위 PR의 대상 브랜치(base)를 main이 아니라 아래 PR의 브랜치로 지정하면, 위 PR의 화면에는 위 PR이 추가한 변경만 표시된다.

음악(#141)은 글 폴더 구조를 바꾼 PR(#143)의 브랜치 위에 쌓았다. 음악 글이 새 폴더 구조를 사용해야 했기 때문이다.

```text
main ◀── #143 (블로그 폴더, 대상: main) ◀── #141 (음악, 대상: #143 브랜치)

순서 A (이날): #141을 #143 브랜치에 머지 → #143을 main에 머지 → 둘 다 main에 반영
순서 B (다음 날): 아래 PR을 main에 먼저 머지 → 위 PR은 이미 머지된 브랜치에 머지 → main에 반영되지 않음
```

![스택 PR에서 위 PR을 먼저 머지하면 둘 다 main에 반영되고, 아래 PR을 먼저 머지하면 위 PR이 main에 반영되지 않는 비교](./images/day-1009-stacked-pr-order.svg '머지 버튼은 PR의 대상 브랜치에 합칠 뿐이다. 대상이 아래 PR의 브랜치로 남아 있으면 main에는 들어가지 않는다')

이날은 #143을 나중에 main에 머지해서 #141도 함께 반영되었다. 그러나 바로 다음 날 같은 방식으로 쌓은 휴지통 PR 두 개는 main에 반영되지 않았다. ==이날 결과가 맞았던 것은 머지 순서가 우연히 맞았기 때문이다.==

> [!WARNING] 스택 PR의 대상 브랜치
> 스택 PR을 사용할 때는 아래 PR이 머지된 뒤 위 PR의 대상 브랜치를 main으로 변경한다. GitHub PR 화면의 제목 옆 Edit 버튼에서 base 브랜치를 바꿀 수 있다.
