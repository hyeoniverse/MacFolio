## desktop-core: 네 단계 분리

### 목표

#16의 목표는 "로직은 한 번 작성하고, UI 프레임워크는 교체할 수 있게"였다. 기능이 거의 확정된 뒤로 미뤄 둔 작업이다. 분리 후의 의존 방향은 다음과 같다.

```text
apps/react (화면)  ──구독(useSyncExternalStore)──▶  packages/desktop-core (로직)
apps/api   (서버)  ──빌드한 JS를 import──────────▶  packages/desktop-core/memo (규칙)

desktop-core가 react나 window를 사용하면 타입 검사에서 실패한다
```

## 인라인 스타일 정리

컴포넌트 곳곳의 `style={{...}}`를 세 가지로 분류했다([인라인 style을 CSS 클래스와 CSS 변수 전달 함수 cssVars()로 옮기기](/memo/inline-style-cleanup)).

| 종류                                    | 처리                          |
| --------------------------------------- | ----------------------------- |
| 항상 같은 값                            | CSS 파일로 이동               |
| 데이터에 따라 바뀌는 색·크기            | `cssVars()`로 CSS 변수만 전달 |
| 실행 중에 계산되는 좌표 (예: 메뉴 위치) | 인라인 스타일 유지            |

변경 전후 화면 37장을 캡처해 픽셀 단위로 차이가 없는지 비교했다.

## 돌아보며

**구조 변경에서는 "동작이 바뀌지 않았다"를 증명하는 것이 핵심 작업이다.** 인라인 스타일은 화면 37장의 픽셀 비교로, desktop-core는 기존 E2E가 그대로 통과하는 것으로 증명했다. 창 store, 메모 목록 계산(`noteView`), 음악 플레이어 store에는 단위 시험이 새로 생겼다. React 안에 있을 때는 컴포넌트를 렌더링해야 시험할 수 있던 로직을 이제 함수 단위로 시험한다.

**스택 PR은 머지 순서에 따라 결과가 달라진다.** 음악(#141)은 글 폴더 구조를 바꾼 PR(#143)의 브랜치 위에 쌓았다. 음악 글이 새 폴더 구조를 사용해야 했기 때문이다.

```text
main ◀── #143 (블로그 폴더, 대상: main) ◀── #141 (음악, 대상: #143 브랜치)

순서 A (이날): #141을 #143 브랜치에 머지 → #143을 main에 머지 → 둘 다 main에 반영
순서 B (다음 날): 아래 PR을 main에 먼저 머지 → 위 PR은 이미 머지된 브랜치에 머지 → main에 반영되지 않음
```

이날은 #143이 나중에 main에 머지되면서 #141도 함께 반영되었다. 그러나 바로 다음 날 같은 방식으로 쌓은 휴지통 PR 두 개는 main에 반영되지 않았다. 이날 결과가 맞았던 것은 머지 순서가 우연히 맞았기 때문이다. 스택 PR을 사용할 때는 아래 PR이 머지된 뒤 위 PR의 대상 브랜치를 main으로 변경해야 한다.
