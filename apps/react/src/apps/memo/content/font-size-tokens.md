## 배경

[z-index](/memo/z-index-layers)와 [모서리 둥글기](/memo/radius-tokens)에 이어 글자 크기에도 이름을 붙였다. [리팩터링 계획](/memo/refactor-step5-styles)의 스타일 단계에서 "되풀이되는 숫자를 theme.css의 이름으로"를 차례로 하던 중이었다.

숫자만 보면 12px와 13px 중 무엇이 "날짜 크기"인지 알 수 없다. 이름이 있어야 "날짜는 caption"이라고 정하고 따를 수 있다. 같은 쓰임에 다른 숫자가 섞여 있어도 숫자로는 그것이 실수인지 의도인지 가려지지 않는다.

## 세어 보기

`apps/react/src` 아래 CSS에서 `font-size`는 958곳이었다. 자주 나온 값은 이렇다.

| 값   | 곳  |
| ---- | --- |
| 12px | 156 |
| 13px | 130 |
| 15px | 99  |
| 11px | 88  |
| 14px | 85  |
| 17px | 60  |
| 16px | 57  |
| 20px | 39  |
| 18px | 32  |
| 22px | 15  |

위 열 값이 761곳으로 전체의 80%쯤이다. 나머지는 em·rem, 10px 이하나 26px 이상의 큰 제목, 소수점 값 등이다.

MacFolio는 macOS와 iOS 화면을 흉내 내는 사이트라, 이 값들은 대부분 Apple이 정한 글자 크기에서 왔다. 그래서 숫자보다 Apple의 이름이 더 많은 것을 알려 준다.

## 이름을 어디서 가져올까

| 후보                      | 예                              | 좋은 점                                            | 걸리는 점                                                 |
| ------------------------- | ------------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| 숫자 그대로               | `--text-13`                     | 바꾸기 쉽다                                        | 숫자를 이름으로 옮겼을 뿐, 쓰임새를 알려 주지 않는다      |
| 크기 단계                 | `--text-xs`·`sm`·`md`·`lg`      | Tailwind 등에서 익숙하다                           | 여덟 단계면 `xs`·`2xs`처럼 이름이 억지스러워진다          |
| **Apple HIG 글자 스타일** | `--text-footnote`·`--text-body` | 흉내 내는 대상과 이름이 같다, 쓰임새가 이름에 있다 | iOS 기준이라 macOS 화면에서는 이름과 쓰임이 조금 어긋난다 |

세 번째를 골랐다. HIG(Human Interface Guidelines)는 Apple이 앱 화면을 만드는 방법을 적어 둔 안내서다. 글자 쓰임새마다 이름과 크기가 정해져 있다. iOS 기준으로 본문(Body)은 17pt, 보조 문구(Footnote)는 13pt, 가장 작은 설명(Caption 2)은 11pt다. 화면을 흉내 내다 막히면 HIG를 열어 보는데, 거기 적힌 이름이 CSS에도 그대로 있으면 오가기 쉽다.

| 이름              | 크기 | 쓰임                                 |
| ----------------- | ---- | ------------------------------------ |
| `--text-caption2` | 11px | 가장 작은 설명, 배지                 |
| `--text-caption`  | 12px | 날짜, 작은 설명                      |
| `--text-footnote` | 13px | 보조 문구 (macOS 앱에서는 본문 크기) |
| `--text-subhead`  | 15px | 휴대폰 목록의 둘째 줄                |
| `--text-callout`  | 16px | 강조한 설명                          |
| `--text-body`     | 17px | 휴대폰 본문                          |
| `--text-title3`   | 20px | 작은 제목                            |
| `--text-title2`   | 22px | 중간 제목                            |

macOS 앱의 본문은 13px이라 데스크톱 창 안에서는 `--text-footnote`가 사실상 본문이다. 이름과 쓰임이 어긋나는 곳이지만, 휴대폰 화면과 같은 이름 체계를 쓰는 쪽을 택했다.

![여덟 글자 크기 이름과 실제 크기](./images/font-size-tokens-scale.svg '이름마다 실제 크기와, 바꾸기 전 그 값이 나온 곳 수')

## 구현

### 1. theme.css에 여덟 이름

```css
:root {
	/*
	 * 글자 크기. Apple HIG의 글자 스타일 이름을 빌려, 자주 쓰는 여덟 값에 이름을 붙였다
	 * (14·18px 등 그 밖의 값과 em·rem은 각 CSS에 그대로)
	 */
	--text-caption2: 11px;
	--text-caption: 12px;
	--text-footnote: 13px;
	--text-subhead: 15px;
	--text-callout: 16px;
	--text-body: 17px;
	--text-title3: 20px;
	--text-title2: 22px;
}
```

다크 모드에서 글자 크기가 바뀔 일은 없으니 색 이름과 달리 다크 짝은 없다.

### 2. 값 하나만 적힌 곳만 바꾼다

`font-size: 13px;`처럼 값 하나만 적힌 줄만 바꿨다. `font: 600 13px/1.2 …` 같은 줄임 속성, `calc()` 안의 값, `clamp()`는 건드리지 않았다. 줄임 속성 안의 값은 다른 값과 묶여 있어서, 바꾸면 한 줄이 오히려 읽기 어려워진다.

```css
/* Memo.css */
-	font-size: 13px;
+	font-size: var(--text-footnote);

-	font-size: 12px;
+	font-size: var(--text-caption);
```

45개 CSS 파일에서 645곳을 바꿨고, 커밋은 47개 파일 712줄 더하기, 645줄 지우기다. 더한 줄 중 13줄은 `theme.css`, 54줄은 이 글의 첫 판이다.

## caption2를 caption으로 합칠까

작업 중에 `--text-caption2`(11px)를 `--text-caption`(12px)으로 아예 합쳐 버리는 편이 간단하지 않은지 따져 봤다. 합치면 이름은 하나 줄지만 11px로 그린 배지·작은 설명 88곳이 1px씩 커져 화면이 바뀐다. 이번 일은 값을 그대로 두고 이름만 붙이는 것이 목표라 둘을 그대로 두었다.

## 이름을 붙이지 않은 값

- **14px(85곳)·18px(32곳)**: HIG에 딱 맞는 이름이 없다. 대부분 데스크톱 앱에서 눈대중으로 고른 크기라, 둘 중 가까운 이름으로 합칠지는 화면을 보며 하나씩 정한다. 한꺼번에 13이나 15로 바꾸면 화면이 1px씩 달라진다. 이번 일은 "화면은 그대로"가 원칙이라 손대지 않았다.
- **em·rem**: 부모 글자 크기를 따라가라는 뜻이라 고정된 이름으로 바꾸면 안 된다.
- **10px 이하·26px 이상**: 쓰는 곳이 적고 앱마다 모양이 달라 그대로 두었다.

## 확인

- 값이 그대로라 화면이 달라지면 안 된다. 바꾸기 전후 커밋에서 `font-size`가 숫자인 곳(여덟 값)은 645 → 0, `var(--text-*)`는 0 → 645로 정확히 맞았다. `git grep -hE 'font-size:\s*(11|12|13|15|16|17|20|22)px'`로 셌다.
- 이름이 잘못 적히면(`--text-captoin` 같은 오타) 브라우저는 그 값을 버리고 물려받은 크기를 쓴다. 화면에서는 1~2px 차이라 눈으로 찾기 어렵다. 그래서 `var(--text-`로 시작하는 값을 모두 모아 이름별로 셌고, 여덟 이름 밖에는 원래 있던 `--text-scale` 하나뿐이었다.
- PR의 CI(타입 검사·단위 시험·E2E)가 모두 통과했다.

## 사흘 뒤 다시 세어 보니

10월 19일에 다시 세면 이름으로 쓴 곳은 646곳, 여덟 값을 숫자로 쓴 곳은 375곳이다.

![숫자와 이름의 곳 수](./images/font-size-tokens-counts.svg '#234 직후에는 숫자가 0이었지만, 다른 브랜치의 CSS가 합쳐지며 375곳이 다시 들어왔다')

숫자 375곳 중 253곳이 Safari 프로젝트 템플릿 다섯 개(`repo`·`devtool`·`friendly`·`keynote`·`paper`)와 `Settings.css`다. 이 CSS는 #234와 같은 무렵 다른 브랜치에서 만들어져서, #234가 머지된 뒤에 합쳐졌다. 이름을 정해 두기만 해서는 새로 쓰는 코드가 따라오지 않는다는 것을 숫자로 보게 됐다.

## 남은 것·배운 것

- 막는 장치가 없다. Stylelint 규칙(`declaration-property-value-disallowed-list`)으로 `font-size`에 여덟 값을 숫자로 쓰면 경고하게 하면 다시 들어오지 않는다. 다음 단계로 남겼다.
- 14px·18px는 화면을 보며 하나씩 정한다.
- 이름이 붙으니 "이 날짜 글자가 왜 12px이지?"라는 질문에 "caption이라서"라고 답할 수 있게 되었다. 숫자를 이름으로 바꾸는 일은 기준을 코드에 적는 일이다.
