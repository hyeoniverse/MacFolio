## 들어가기 전에

네트워크로 주고받는 데이터는 목적지에 도착하기까지 같은 LAN의 다른 컴퓨터, 스위치, 라우터, 무선 구간을 지난다. 이 경로 위에 있는 누군가는 데이터를 엿보거나(스니핑), 주소를 속여 데이터가 자기에게 오게 만들거나(스푸핑), 대량의 요청으로 서비스를 마비시킬 수 있다(서비스 거부). 이 글은 세 가지 공격이 각각 어떤 프로토콜의 어떤 성질을 이용하는지 따라가고, 이를 막는 장비와 설정을 정리한다.

필요한 배경은 두 가지다. 하나는 정보보호의 세 가지 목표인 기밀성(허가받지 않은 사람이 내용을 볼 수 없음), 무결성(허가받지 않은 변경이 없음), 가용성(필요한 시각에 서비스를 쓸 수 있음)이다. 다른 하나는 데이터가 응용 → 전송(TCP·UDP) → 네트워크(IP) → 데이터 링크(이더넷) 계층을 거치며 각 계층의 헤더를 덧붙여 전송된다는 [TCP/IP 계층 모델](/memo/net-tcpip-model)이다. 이 글에서는 특히 두 종류의 주소를 구분해야 한다.

| 주소     | 계층        | 길이   | 예시                | 쓰임                                 |
| -------- | ----------- | ------ | ------------------- | ------------------------------------ |
| MAC 주소 | 데이터 링크 | 48비트 | `00-0c-29-44-2c-ea` | 같은 LAN 안에서 장치(NIC)를 구분     |
| IP 주소  | 네트워크    | 32비트 | `192.168.0.1`       | 인터넷 전체에서 목적지 호스트를 구분 |

MAC 주소는 NIC(네트워크 인터페이스 카드) 제조 시 부여되는 물리 주소이고, IP 주소는 네트워크 설정으로 정하는 논리 주소다. 같은 LAN 안에서 실제로 프레임을 배달할 때는 MAC 주소를 쓰므로, ==IP 주소를 MAC 주소로 바꾸는 단계(ARP)가 반드시 필요하다==. 이 변환 단계가 뒤에서 다룰 스푸핑 공격의 표적이 된다.

## 위협의 분류

보안 공격은 공격자가 통신에 개입하는 방식에 따라 두 가지로 나뉜다[^x800].

| 분류        | 공격자가 하는 일                        | 예                                   | 탐지 난이도                        | 기본 대책        |
| ----------- | --------------------------------------- | ------------------------------------ | ---------------------------------- | ---------------- |
| 수동적 공격 | 통신을 관찰만 하고 데이터를 바꾸지 않음 | 도청(스니핑), 트래픽 분석            | 데이터가 변하지 않아 탐지가 어려움 | 암호화로 예방    |
| 능동적 공격 | 데이터를 위조·변조·재전송하거나 방해함  | 신분 위장(스푸핑), 변조, 서비스 거부 | 흔적이 남아 탐지는 가능            | 탐지와 복구 중심 |

==트래픽 분석은 내용을 읽지 못해도 누가 누구와 언제, 얼마나 자주 통신하는지를 알아내는 공격이다==. 암호화된 통신이라도 이 정보는 남는다.

## 스니핑

### 스니핑의 정의

스니핑(sniffing)은 영어 sniff(냄새를 맡다, 킁킁거리다)에서 온 말로, 네트워크를 지나는 패킷을 가로채 내용을 확인하는 도청(eavesdropping) 공격이다. 공격자는 패킷을 바꾸거나 새로 보내지 않고 받아 보기만 하므로 수동적 공격에 속한다. ==피해자 쪽에서는 통신이 평소와 똑같이 동작하므로 스니핑 사실을 알아채기 어렵다==.

![컨베이어 벨트로 서류가 전달되는 동안 옆 사람이 서류를 들여다본다](./images/csintro-network-security-sniffing-cartoon.jpg '스니핑은 전달되는 데이터를 바꾸지 않고 엿본다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

### 무차별 모드

일반적인 NIC는 수신한 프레임의 목적지 MAC 주소를 확인해, 자기 MAC 주소이거나 브로드캐스트(`ff-ff-ff-ff-ff-ff`), 가입한 멀티캐스트 주소인 프레임만 운영체제로 올리고 나머지는 하드웨어 수준에서 버린다. 불필요한 프레임 때문에 CPU가 일하지 않도록 하는 기능이다.

NIC를 **무차별 모드**(promiscuous mode)로 설정하면 이 필터링을 끄고, MAC 주소와 IP 주소에 관계없이 수신한 모든 프레임을 운영체제로 올린다. Wireshark나 tcpdump 같은 패킷 캡처 도구는 이 모드를 켠 뒤 커널의 패킷 캡처 인터페이스(리눅스의 `AF_PACKET`, BSD·macOS의 BPF)로 프레임을 복사해 받는다.

![일반 모드의 NIC는 목적지 MAC이 자기 주소인 프레임만 올리고, 무차별 모드는 받은 프레임을 모두 올린다](./images/csintro-network-security-promiscuous.svg 'NIC의 일반 모드와 무차별 모드')

| 운영체제 | 무차별 모드 설정                                                 | 캡처 라이브러리     |
| -------- | ---------------------------------------------------------------- | ------------------- |
| 리눅스   | `ip link set eth0 promisc on` 또는 캡처 도구가 자동 설정         | libpcap             |
| macOS    | 캡처 도구가 BPF 장치(`/dev/bpf*`)를 열 때 설정. 관리자 권한 필요 | libpcap             |
| 윈도우   | 운영체제 기본 기능에 없어 캡처용 드라이버를 따로 설치            | Npcap(과거 WinPcap) |

==무차별 모드 설정에는 관리자 권한이 필요하다==. 일반 사용자 프로그램이 다른 사람의 패킷을 몰래 볼 수 없게 하기 위해서다.

### 바이패스 모드

**바이패스 모드**(bypass mode)는 패킷 분석 기능까지 하드웨어로 구현한 전용 캡처 카드를 가리킨다. 초당 수십 기가비트의 트래픽이 흐르는 백본망에서는 일반 NIC와 소프트웨어로는 패킷을 놓치므로, 분석 장비나 보안 장비가 이런 고가의 전용 장비를 쓴다. 보안 장비에서 바이패스라는 말은 장비에 전원이 끊기거나 장애가 나도 회선이 끊기지 않도록 트래픽을 그대로 통과시키는 기능(하드웨어 바이패스)을 가리키기도 한다.

### 스니핑 준비와 도구

스니핑을 하려면 먼저 자신의 네트워크 인터페이스 정보를 확인한다.

| 운영체제 | 명령                   | 확인할 항목                        |
| -------- | ---------------------- | ---------------------------------- |
| 리눅스   | `ip addr` (`ifconfig`) | 인터페이스 이름, IP 주소, MAC 주소 |
| macOS    | `ifconfig en0`         | `ether`(MAC), `inet`(IP)           |
| 윈도우   | `ipconfig /all`        | 물리적 주소(MAC), IPv4 주소        |

대표 캡처 도구는 다음 두 가지다.

- **tcpdump**: 명령줄에서 동작하는 패킷 캡처 도구다. 원래 네트워크 관리와 장애 분석을 위해 1988년 로런스 버클리 연구소에서 만들어졌고, 지금도 서버 장애 분석의 기본 도구다. 리눅스·macOS에 기본으로 들어 있는 경우가 많고, 윈도우용 이식판으로 WinDump가 있다. 캡처 결과를 pcap 파일로 저장해 두면 침해사고 조사에서 당시 통신을 재구성하는 증거 자료로 쓰인다.
- **Wireshark**: 그래픽 화면으로 패킷을 계층별로 펼쳐 보여 주는 분석 도구다. 리눅스·macOS·윈도우에서 모두 동작하며, 수천 개 프로토콜의 해석기를 갖추고 있다.

```bash
# en0 인터페이스에서 TCP 80번 포트 패킷 20개를 내용(-A)과 함께 출력
sudo tcpdump -i en0 -c 20 -A 'tcp port 80'
```

HTTP처럼 암호화하지 않는 프로토콜로 로그인하면 아이디와 비밀번호가 평문으로 전송되어 캡처 화면에 그대로 나타난다. Wireshark에서 `http` 필터를 걸고 HTTP 요청을 펼치면 `GET /index.do HTTP/1.1`, `Host:`, `User-Agent:`, `Cookie:` 헤더가 글자 그대로 보이고, 쿠키에 세션 식별자가 들어 있으면 공격자가 그 값을 자기 브라우저에 넣어 로그인 상태를 가로챌 수 있다(세션 하이재킹). ==HTTPS(TLS)를 쓰면 패킷은 캡처되지만 내용은 암호문이라 읽을 수 없다==. Wireshark로 HTTP 트래픽을 분석하는 과정은 [Wireshark로 HTTP 트래픽과 TCP 핸드셰이크 분석하기](/memo/net-wireshark-http)에, libpcap으로 스니퍼를 직접 만드는 방법은 [패킷 스니핑과 스푸핑, pcap과 원시 소켓의 이해](/memo/net-sniffing-spoofing)에 정리했다.

### 스위치 환경과 스니핑

무차별 모드만으로 남의 트래픽을 볼 수 있는 곳은 허브처럼 받은 프레임을 모든 포트로 복제하는 공유 매체다. 스위치는 포트마다 연결된 장치의 MAC 주소를 학습해 MAC 주소 테이블을 만들고, 프레임을 목적지 MAC이 연결된 포트로만 보낸다. 다른 호스트끼리 주고받는 프레임은 공격자 포트에 아예 도착하지 않으므로, 무차별 모드를 켜도 볼 것이 없다.

![허브는 A가 B에게 보낸 프레임을 공격자 포트에도 복제하지만, 스위치는 B의 포트로만 보낸다](./images/csintro-network-security-hub-switch.svg '허브와 스위치의 프레임 전달')

스위치는 원래 충돌을 줄이고 대역폭을 나누기 위한 장비이지 스니핑을 막으려고 만든 장비는 아니다. ==결과적으로 스니핑을 어렵게 만들 뿐이다==. 그래서 스위치 환경의 공격자는 다음 방법으로 트래픽이 자기에게 오게 만든다.

| 방법                       | 원리                                                                                         |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| ARP 스푸핑(ARP 리다이렉트) | 피해자의 ARP 캐시를 조작해 게이트웨이로 갈 프레임을 공격자에게 보내게 함                     |
| MAC 플러딩                 | 가짜 MAC 주소로 스위치의 MAC 테이블을 가득 채워, 스위치가 허브처럼 모든 포트로 내보내게 만듦 |
| 포트 미러링 악용           | 관리자가 분석용으로 설정한 미러 포트에 접근                                                  |

## 스푸핑

### 스푸핑의 정의

스푸핑(spoofing)은 '속이다'라는 뜻으로, 주소나 신원을 위조해 상대를 속이는 공격이다. 인터넷이나 LAN에서 존재하는 거의 모든 연결(MAC 주소, IP 주소, 포트, DNS 이름, 이메일 발신자)이 위조 대상이 된다. 스푸핑은 그 자체로 목적이 되기보다 정보를 얻기 위한 중간 단계로 많이 쓰인다. 예를 들어 ARP 스푸핑으로 트래픽을 자기에게 돌린 뒤 스니핑하거나, DNS 스푸핑의 사전 작업으로 쓴다. 출발지 IP를 위조한 패킷으로 시스템을 마비시키는 데도 쓴다.

### ARP의 동작과 약점

ARP(Address Resolution Protocol)는 같은 LAN 안에서 IP 주소에 대응하는 MAC 주소를 알아내는 프로토콜이다[^arp].

1. PC가 `192.168.0.1`로 보낼 패킷이 있는데 MAC 주소를 모르면 "192.168.0.1을 가진 장치는 MAC을 알려 달라"는 ARP 요청을 브로드캐스트한다.
2. 해당 IP를 가진 장치가 자기 MAC 주소를 담은 ARP 응답을 유니캐스트로 보낸다.
3. PC는 응답 내용을 ARP 캐시에 일정 시간(수십 초~수 분) 저장하고, 이후에는 캐시를 보고 프레임을 만든다.

==ARP에는 인증 기능이 없다==. 응답을 보낸 장치가 정말 그 IP의 주인인지 확인하지 않고, 운영체제에 따라서는 요청하지 않은 응답(gratuitous ARP)도 캐시에 반영한다. ARP 스푸핑은 이 점을 이용한다. MAC 주소를 속이는 공격이므로 2계층(데이터 링크)에서 동작하며, ==공격자와 피해자가 같은 LAN에 있어야 한다==.

### ARP 스푸핑(ARP 리다이렉트) 과정

라우터(게이트웨이)와 공격자의 주소가 다음과 같다고 하자. 주소는 사설 대역 예시다.

| 장치       | IP 주소         | MAC 주소            |
| ---------- | --------------- | ------------------- |
| 게이트웨이 | `192.168.0.1`   | `00-0c-29-44-2c-ea` |
| 공격자     | `192.168.0.201` | `00-0c-29-ad-25-88` |
| 피해자     | `192.168.0.23`  | (생략)              |

1. 공격자는 게이트웨이의 진짜 MAC 주소를 먼저 알아 둔다. 받은 프레임을 진짜 게이트웨이로 넘겨줘야 하기 때문이다.
2. 공격자가 피해자에게 "192.168.0.1의 MAC은 `00-0c-29-ad-25-88`이다"라는 위조 ARP 응답을 몇 초 간격으로 계속 보낸다. 정상 응답에 의해 캐시가 원래대로 돌아가지 않게 하기 위해서다.
3. 피해자의 ARP 캐시에서 게이트웨이 항목이 공격자의 MAC으로 바뀐다. 이제 피해자가 인터넷으로 보내는 모든 프레임은 공격자에게 간다.
4. 공격자는 받은 프레임을 진짜 게이트웨이로 다시 전달(릴레이)한다. 리눅스라면 `net.ipv4.ip_forward=1`로 IP 포워딩을 켠다. 피해자는 인터넷이 평소처럼 되므로 이상을 느끼지 못한다.

게이트웨이에도 같은 방식으로 "192.168.0.23의 MAC은 공격자 MAC"이라고 속이면 응답 방향까지 공격자를 지나게 된다. 이처럼 ==통신 양 끝 사이에 끼어들어 내용을 보거나 바꾸는 상태==를 중간자(man-in-the-middle, MITM) 공격이라 한다.

![피해자가 게이트웨이로 보낼 프레임이 공격자를 거쳐 릴레이되고, ARP 캐시에서 게이트웨이 IP가 공격자 MAC을 가리킨다](./images/csintro-network-security-arp-spoofing.svg 'ARP 스푸핑 전후의 경로와 ARP 캐시. 주소는 예시')

![공격 전에는 192.168.0.1의 MAC이 00-0c-29-44-2c-ea이고, 공격 후에는 공격자 192.168.0.201과 같은 00-0c-29-ad-25-88로 바뀐 윈도우 arp -a 출력](./images/csintro-network-security-arp-tables.jpg 'ARP 스푸핑 전(위)과 후(아래)의 피해자 ARP 테이블. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

### ARP 스푸핑 탐지와 대비

| 대책               | 방법                                                                                                      | 한계                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| ARP 캐시 점검      | `arp -a`로 게이트웨이 IP의 MAC이 실제 라우터 MAC과 같은지, 서로 다른 IP가 같은 MAC을 가리키지 않는지 확인 | 사람이 직접 보아야 함                             |
| 정적 ARP 항목      | `arp -s <IP> <MAC>`(윈도우는 `netsh interface ip add neighbors`)로 게이트웨이 항목을 고정(static)         | 호스트마다 설정해야 하고 재부팅 시 사라질 수 있음 |
| MAC 주소 목록 관리 | 관리하는 시스템의 IP·MAC 대응을 미리 표로 만들어 두고, 브로드캐스트 ping에 응답한 장치의 MAC과 비교       | 장치가 바뀔 때마다 갱신 필요                      |
| 동적 ARP 검사(DAI) | 스위치가 DHCP 스누핑으로 학습한 IP·MAC 대응과 다른 ARP 응답을 차단                                        | 관리형 스위치 필요                                |
| 종단 간 암호화     | TLS, SSH, VPN을 쓰면 트래픽이 공격자를 지나도 내용을 읽거나 바꿀 수 없음                                  | 인증서 경고를 사용자가 무시하면 무력화            |

==기업망에서는 개별 PC 설정보다 스위치의 DHCP 스누핑과 DAI가 현실적인 대책이다==. ARP의 패킷 구조는 [IP 헤더와 서브넷, ARP 주소 변환](/memo/net-ip-arp)에서 다룬다.

### DNS의 구조

DNS(Domain Name System)는 숫자로 된 IP 주소 대신 사람이 기억하기 쉬운 도메인 이름을 쓸 수 있게, 이름을 IP 주소로 바꿔 주는 분산 데이터베이스 시스템이다. 이름은 오른쪽에서 왼쪽으로 갈수록 상위 단계인 트리 구조를 이룬다.

![루트 도메인 아래에 com, org, kr 같은 최상위 도메인이 있고, 그 아래로 2단계, 3단계 도메인과 호스트가 이어진다](./images/csintro-network-security-dns-tree.jpg 'DNS의 계층 구조. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

| 단계               | 예 (`www.google.com.`)   | 관리 주체                                             |
| ------------------ | ------------------------ | ----------------------------------------------------- |
| 루트               | `.`                      | 루트 서버 13개 이름(A~M), 전 세계 1,000곳 이상에 복제 |
| 최상위 도메인(TLD) | `com`, `org`, `kr`       | 각 TLD 등록 기관                                      |
| 2단계 도메인       | `google`, `co`(`.co.kr`) | 도메인 소유자 또는 레지스트리                         |
| 호스트             | `www`, `ftp`             | 도메인 소유자의 네임서버                              |

사용자가 `www.example.com`에 접속하면 PC는 먼저 hosts 파일과 자체 캐시를 보고, 없으면 설정된 재귀 DNS 서버(통신사나 공용 DNS)에 질의한다. 재귀 서버는 캐시에 없으면 루트 → `com` → `example.com` 네임서버 순서로 물어 답을 찾고, 결과를 캐시에 저장한 뒤 PC에 돌려준다. 질의와 응답은 대부분 UDP 53번 포트로 오가며, 응답은 질의에 담긴 16비트 트랜잭션 ID가 같아야 받아들여진다.

DNS 레코드에는 여러 종류가 있다.

| 레코드 | 뜻                                    | 예                                             |
| ------ | ------------------------------------- | ---------------------------------------------- |
| A      | 도메인 이름 → IPv4 주소 (정방향 조회) | `www.example.com → 93.184.215.14`              |
| AAAA   | 도메인 이름 → IPv6 주소               | `www.example.com → 2606:2800:…`                |
| PTR    | IP 주소 → 도메인 이름 (역방향 조회)   | `14.215.184.93.in-addr.arpa → www.example.com` |
| NS     | 그 도메인을 담당하는 네임서버         | `example.com → a.iana-servers.net`             |
| MX     | 메일 서버                             | `example.com → mail.example.com`               |

### DNS 스푸핑 과정

DNS 스푸핑은 DNS 응답을 위조해, 사용자가 정상 도메인을 입력해도 공격자가 지정한 IP로 접속하게 만드는 공격이다. 같은 LAN에 있는 공격자의 전형적인 과정은 다음과 같다.

1. 공격자는 ARP 스푸핑 같은 사전 작업으로 클라이언트의 패킷이 자기를 지나게 만들고, 클라이언트가 DNS 서버로 보내는 DNS 질의 패킷을 확인한다.
2. 진짜 DNS 서버의 응답이 도착하기 전에, 질의와 같은 트랜잭션 ID·포트를 맞춘 위조 DNS 응답을 클라이언트에게 보낸다. 응답에는 공격자 서버의 IP가 들어 있다.
3. 클라이언트는 먼저 도착한 위조 응답을 정상 응답으로 받아들이고 공격자 서버에 접속한다. ==뒤늦게 도착한 정상 응답은 이미 처리한 질의에 대한 것이므로 버린다==.

![클라이언트의 질의를 엿본 공격자가 위조 응답을 먼저 보내고, 늦게 온 정상 응답은 버려진다](./images/csintro-network-security-dns-spoofing.svg 'DNS 스푸핑의 시간 순서. IP는 문서용 예시 대역')

공격자 서버가 은행 사이트와 똑같이 꾸민 로그인 화면을 보여 주면 사용자는 주소창의 도메인이 정상이므로 의심 없이 계정 정보를 입력한다. 이렇게 DNS나 hosts 파일을 조작해 정상 도메인으로 가짜 사이트에 접속하게 만드는 공격을 파밍(pharming)이라고도 한다.

클라이언트 하나가 아니라 재귀 DNS 서버의 캐시에 위조 레코드를 넣는 공격은 캐시 오염(cache poisoning)이라 하며, 그 서버를 쓰는 모든 사용자에게 영향을 준다. 2008년 댄 카민스키(Dan Kaminsky)가 발표한 공격은 존재하지 않는 하위 도메인을 대량으로 질의해 트랜잭션 ID를 맞힐 기회를 무한히 늘리는 방식으로, 당시 대부분의 DNS 서버가 영향을 받았다.

### DNS 스푸핑 대비

**hosts 파일.** 운영체제는 DNS 질의 전에 hosts 파일을 먼저 확인한다(리눅스·macOS `/etc/hosts`, 윈도우 `C:\Windows\System32\drivers\etc\hosts`). 자주 접속하는 중요 서버의 이름과 IP를 hosts 파일에 적어 두면 그 이름은 DNS 질의 없이 해석되므로 DNS 스푸핑의 영향을 받지 않는다. 하지만 접속하는 모든 서버를 등록할 수는 없고, 서버의 IP가 바뀌면 직접 고쳐야 하므로 근본 대책은 아니다. 거꾸로 악성코드가 hosts 파일에 은행 도메인과 피싱 서버 IP를 적어 넣는 공격도 흔해, 이 파일은 관리자 권한으로만 수정할 수 있고 백신이 변경을 감시한다.

**DNS 서버 소프트웨어 갱신.** 가장 널리 쓰이는 DNS 서버 소프트웨어인 BIND(Berkeley Internet Name Domain)의 오래된 판에는 위조 응답을 쉽게 받아들이는 취약점이 여러 번 발견되었다. 최신 판으로 올리면 다음과 같은 방어가 적용된다.

- 질의마다 출발지 UDP 포트와 트랜잭션 ID를 무작위로 골라, 공격자가 맞혀야 하는 경우의 수를 16비트(65,536)에서 약 32비트로 늘린다(카민스키 공격 이후 표준 대책).
- 역방향 조회(PTR 레코드)로 얻은 이름을 다시 정방향 조회(A 레코드)해 원래 IP와 일치하는지 확인하는 방식으로, 위조된 이름 정보를 걸러 낸다.
- DNSSEC 검증을 지원한다.

**DNSSEC.** DNS 응답에 전자서명을 붙여, 응답이 해당 도메인 관리자가 만든 것이고 전송 중에 바뀌지 않았음을 검증한다. 위조 응답은 서명 검증에 실패한다. 자세한 공격 과정과 DNSSEC의 서명 체인은 [DNS의 계층 구조와 캐시 오염 공격, DNSSEC 방어](/memo/net-dns-attack)에 있다.

**HTTPS 인증서 검증.** DNS가 조작되어 공격자 서버에 접속해도, 공격자는 정상 도메인의 TLS 인증서와 개인키를 갖고 있지 않으므로 브라우저가 인증서 경고를 띄운다. ==이 경고를 무시하지 않는 것이 사용자 쪽의 마지막 방어선이다==.

## 서비스 거부 공격(DoS)

### 정의와 유형

서비스 거부(DoS, Denial of Service) 공격은 공격 대상이 처리할 수 있는 능력 이상의 요청을 보내거나, 사용자 또는 네트워크의 용량을 초과시켜 시스템이 정상적으로 동작하지 못하게 하는 공격이다. ==정보를 훔치는 것이 아니라 가용성을 깨는 것이 목적이다==.

| 유형               | 방법                                                 | 예                                  |
| ------------------ | ---------------------------------------------------- | ----------------------------------- |
| 파괴 공격          | 디스크, 데이터, 시스템 자체를 파괴                   | 하드디스크 덮어쓰기, 부팅 영역 손상 |
| 시스템 자원 고갈   | CPU, 메모리, 디스크를 과도하게 사용하게 해 부하를 줌 | 프로세스 무한 생성, 디스크 채우기   |
| 네트워크 자원 고갈 | 쓰레기 데이터로 네트워크 대역폭이나 연결 자원을 소진 | ICMP·UDP 플러딩, SYN 플러딩         |

### Ping of Death

`ping`은 ICMP 에코 요청을 보내고 에코 응답을 받아 상대가 살아 있는지 확인하는 명령이다. Ping of Death는 이 ICMP 패킷을 비정상적으로 크게 만들어 보내는 공격이다.

1. 공격자는 ping으로 ICMP 패킷을 정상(기본 56바이트 데이터)보다 매우 크게 만든다.
2. 큰 패킷은 네트워크를 지나는 동안 링크의 최대 전송 단위(MTU, 이더넷은 1,500바이트)에 맞게 아주 작은 단편(fragment)으로 나뉜다.
3. 공격 대상은 단편들을 모두 받아 원래 패킷으로 재조립해야 하므로, 정상 ping보다 처리 부하가 훨씬 크다.

![작은 미사일 여러 개가 한 사람에게 쏟아지는 그림](./images/csintro-network-security-ping-cartoon.jpg '큰 패킷 하나가 작은 단편 여러 개로 나뉘어 대상에 도착한다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

패킷이 왜 나뉘는가? 라우팅되는 경로는 특성이 같은 네트워크만 지나지 않는다. 네트워크마다 한 번에 보낼 수 있는 패킷의 최대 길이가 달라서, MTU가 작은 네트워크를 지나면 데이터는 더 작게 나뉜다. ==IPv4에서 한 번 나뉜 단편은 중간 라우터에서 다시 합치지 않고 최종 목적지에서만 재조립한다==. 라우터가 재조립하려면 단편을 모두 보관했다가 나중에 온 단편과 합쳐야 하는데, 그러면 라우터 성능에 치명적인 부하가 걸리기 때문이다.

![4,000바이트 ICMP 패킷이 1,500바이트 MTU 링크에서 세 단편으로 나뉘고, 단편 오프셋 합이 65,535바이트를 넘으면 재조립 버퍼가 넘친다](./images/csintro-network-security-ping-of-death.svg 'IP 단편화와 Ping of Death')

이름의 '죽음'은 부하보다 더 직접적인 문제에서 왔다. IP 패킷의 길이 필드는 16비트라 최대 65,535바이트인데, 단편 오프셋을 조작하면 재조립했을 때 이보다 큰 패킷을 만들 수 있다. 1996년 당시 윈도우 95, 여러 유닉스, 프린터, 라우터가 이런 패킷의 재조립 과정에서 버퍼 오버플로를 일으켜 멈추거나 재부팅되었다[^cert96]. 각 운영체제가 재조립 길이를 검사하도록 패치된 뒤로 원래의 Ping of Death는 현재 운영체제에서 통하지 않는다. 다만 2020년 윈도우의 IPv6 ICMP 처리 취약점(CVE-2020-16898)처럼 비슷한 구조의 결함은 지금도 발견된다.

**대책.** 반복적으로 들어오는 일정 수 이상의 ICMP 패킷을 무시하도록 방화벽이나 라우터에 속도 제한을 걸고, 운영체제 보안 패치를 적용한다. ==가장 일반적이고 확실한 대책은 패치다==. ICMP를 통째로 막으면 경로 MTU 탐색(PMTUD)이 깨져 일부 통신이 실패할 수 있으므로, 에코 요청만 제한하는 편이 안전하다.

### SYN 플러딩

TCP는 데이터를 보내기 전에 3-way 핸드셰이크로 연결을 맺는다. 클라이언트가 SYN을 보내면 서버는 SYN-ACK로 답하고 연결 정보를 백로그(backlog) 큐에 넣은 채 `SYN_RECEIVED` 상태로 클라이언트의 ACK를 기다린다. ACK가 오면 연결이 `ESTABLISHED`가 되어 큐에서 빠진다.

서버의 백로그 큐는 크기가 정해져 있다. SYN 플러딩은 존재하지 않거나 응답하지 않는 출발지 IP로 위조한 SYN 패킷을 대량으로 보내, 큐를 `SYN_RECEIVED` 항목으로 가득 채우는 공격이다.

1. 공격자는 많은 수의 SYN 패킷을 서버에 보낸다.
2. 서버는 받은 SYN마다 SYN-ACK를 각 클라이언트(위조된 출발지)로 보낸다.
3. 위조된 주소에서는 ACK가 오지 않는다.
4. 서버는 연결을 기다리며 큐 항목을 시간 초과(수십 초)까지 유지하고, 큐가 가득 찬 동안 정상 사용자의 SYN을 받지 못한다.

![정상 연결은 ACK를 받아 큐에서 빠지지만, SYN 플러딩에서는 ACK가 오지 않아 큐가 가득 찬다](./images/csintro-network-security-syn-flooding.svg '3-way 핸드셰이크와 SYN 플러딩의 백로그 큐')

공격을 받는 서버에서 `netstat -an`을 실행하면 같은 서버 포트(80)에 대해 출발지가 제각각인 `SYN_RECEIVED` 연결이 수십~수백 개 나열된다. 이런 상태를 흔히 '백로그에 빠졌다'고 표현한다.

![웹 서버의 80번 포트에 대해 서로 다른 출발지의 SYN_RECEIVED 연결이 줄지어 있다](./images/csintro-network-security-syn-received.jpg 'SYN 플러딩을 받는 서버의 netstat 출력. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

리눅스에서는 다음 명령으로 같은 상태를 집계한다.

```bash
ss -tan state syn-recv | wc -l     # SYN_RECV 상태 연결 수
sysctl net.ipv4.tcp_max_syn_backlog # 백로그 큐 크기
```

실습 도구 `hping3`는 `hping3 <대상 IP> -S -p 80 --flood`처럼 SYN 플래그(`-S`)를 단 패킷을 최대 속도로 보낼 수 있다. 공격 도구로도 쓰일 수 있으므로 자신이 관리하는 시험 환경에서만 사용해야 하며, 허가 없이 남의 시스템에 실행하면 정보통신망법 위반이다.

**대책.**

| 대책                          | 설명                                                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- |
| SYN 쿠키                      | 큐에 상태를 저장하지 않고 연결 정보를 SYN-ACK의 초기 순서 번호에 담아 보냄. 리눅스 `net.ipv4.tcp_syncookies=1` |
| `SYN_RECEIVED` 대기 시간 단축 | 반쯤 열린 연결을 빨리 정리해 큐를 비움 (`tcp_synack_retries` 감소)                                             |
| 백로그 큐 확대                | `tcp_max_syn_backlog`를 늘려 버티는 시간을 늘림                                                                |
| IDS·IPS 설치                  | 짧은 시간에 같은 형태의 패킷을 보내는 공격을 탐지해 해당 IP 대역 접속을 방화벽이나 라우터에서 차단             |
| 운영체제 패치                 | 커널의 TCP 처리 개선 사항 적용                                                                                 |

출발지 IP가 위조되어 매번 다르므로 IP 차단만으로는 효과가 제한적이다. ==SYN 쿠키처럼 서버가 상태를 저장하지 않게 만드는 방식이 핵심이다==. 상세는 [TCP 프로토콜을 겨냥한 공격과 방어](/memo/net-tcp-attacks)에 있다.

## 분산 서비스 거부 공격(DDoS)

### DDoS의 구성

분산 서비스 거부(DDoS, Distributed Denial of Service) 공격은 DoS를 여러 대의 컴퓨터가 동시에 수행하도록 발전시킨 공격이다. 피해 규모가 크지만 공격 트래픽이 수많은 정상 IP에서 오므로 공격자의 위치와 실제 발원지를 찾기 어렵고, 확실한 대책이 없어 지금도 대응이 어려운 공격으로 꼽힌다. 대부분의 DDoS 공격은 자동화된 도구를 사용한다.

| 구성 요소        | 역할                                                          |
| ---------------- | ------------------------------------------------------------- |
| 공격자(attacker) | 공격을 주도하는 컴퓨터                                        |
| 마스터(master)   | 공격자에게 직접 명령을 받는 시스템. 여러 대의 에이전트를 관리 |
| 핸들러(handler)  | 마스터 시스템에서 마스터 역할을 수행하는 프로그램             |
| 에이전트(agent)  | 공격 대상에 직접 공격을 가하는 시스템                         |
| 데몬(daemon)     | 에이전트 시스템에서 에이전트 역할을 수행하는 프로그램         |

![공격자가 마스터 세 대에 명령하고, 각 마스터가 에이전트 여러 대를 움직여 한 대상을 동시에 공격한다](./images/csintro-network-security-ddos-structure.jpg 'DDoS 공격의 구성. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

이 계층 구조에서 ==마스터와 에이전트는 공격자이면서 동시에 피해자다==. 대부분 공격자가 미리 침투해 핸들러·데몬 프로그램을 몰래 설치해 둔 일반 사용자의 컴퓨터이기 때문이다. 1999~2000년 무렵의 Trinoo, TFN(Tribe Flood Network), TFN2K, Stacheldraht가 이런 마스터·에이전트 구조의 대표 도구였고, 2000년 2월 야후·이베이·아마존·CNN이 TFN 계열 도구로 공격받아 몇 시간씩 서비스가 중단되었다.

### 악성코드와 봇넷을 이용한 DDoS

지금의 DDoS는 사람이 마스터를 일일이 침투하는 대신 악성코드로 에이전트를 확보한다.

1. 공격자가 웹 서버(악성 스크립트를 심은 사이트), 이메일 첨부 파일, USB 등으로 악성코드를 배포한다.
2. 악성코드에 감염된 PC는 좀비 PC(봇)가 되어 공격자의 명령 제어(C&C, Command and Control) 서버에 접속해 명령을 기다린다. 이 봇의 집합을 봇넷(botnet)이라 한다.
3. 공격자가 C&C 서버를 통해 공격 대상과 시각을 지정한 명령을 내린다.
4. 봇 수천~수십만 대가 동시에 공격 대상에 트래픽을 보낸다.

| 사례                  | 시기              | 내용                                                                                                                         |
| --------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 7·7 DDoS              | 2009년 7월 7~10일 | 청와대·국회·포털·은행 등 한미 주요 사이트를 사흘간 세 차례 공격. 감염 PC는 마지막에 하드디스크를 손상시키도록 설계됨[^ahn77] |
| 3·4 DDoS              | 2011년 3월        | 국내 주요 사이트 40여 곳 공격, 역시 감염 PC의 디스크 파괴 기능 포함                                                          |
| Mirai                 | 2016년 10월       | 기본 비밀번호를 쓰던 IP 카메라·공유기 등 IoT 기기 수십만 대로 DNS 업체 Dyn을 공격, 미국 동부의 대형 사이트 접속 장애         |
| GitHub Memcached 증폭 | 2018년 2월        | 공개된 Memcached 서버에 출발지를 위조한 작은 요청을 보내 수만 배로 증폭된 응답(최대 1.35Tbps)을 대상에 쏟아냄                |

7·7 DDoS의 좀비 PC는 공격이 끝난 뒤 스스로 하드디스크의 데이터를 덮어써 부팅할 수 없게 만들었다. 공격 도구가 증거를 지우면서 피해자 PC까지 파괴한 셈이다.

## DoS와 DDoS의 탐지와 예방

### 방화벽 설치와 운영

방화벽(firewall)은 보호할 내부 네트워크와 외부 네트워크의 경계에 가장 먼저 설치하는 장비다. 출발지 주소, 목적지 주소, 서비스(포트 번호), 프로토콜을 기준으로 패킷을 허용하거나 차단한다. 다만 포트와 주소만 보는 방화벽이 막을 수 있는 침입은 전체의 일부다. 허용한 웹 포트(80, 443) 안에 담겨 오는 공격은 방화벽이 구분하지 못하므로 IDS·IPS·웹 방화벽과 함께 운영한다.

방화벽 규칙셋은 다음 원칙으로 작성한다.

| 원칙                                 | 의미                                                                                          |
| ------------------------------------ | --------------------------------------------------------------------------------------------- |
| 최소한의 서비스만 제공               | 쓰지 않는 서비스의 포트는 닫는다                                                              |
| 위조된 내부 주소 차단                | 외부에서 들어온 패킷의 출발지 주소가 내부 네트워크 대역이면 위조로 보고 차단한다(진입 필터링) |
| 내부 구성 요소 간 무조건적 신뢰 금지 | 내부 장비라도 필요한 통신만 허용한다                                                          |
| 인증 없는 접속 금지                  | 인증 없이 시스템에 접속할 수 있는 내부·외부 사용자를 허용하지 않는다                          |
| 기본 거부                            | 명시적으로 허용한 서비스 외의 모든 서비스를 금지한다                                          |

방화벽은 규칙을 위에서부터 차례로 비교해 ==처음 일치한 규칙을 적용하고, 마지막에 "모두 거부" 규칙을 둔다==. 순서가 잘못되면 의도와 다르게 동작한다. 예를 들어 "모두 거부"가 맨 위에 있으면 모든 통신이 막히고, 넓은 허용 규칙이 좁은 거부 규칙보다 위에 있으면 거부 규칙은 영원히 적용되지 않는다.

![외부에서 웹 서버 443 포트로 오는 패킷은 2번 규칙에서 허용되고, 3389 포트로 오는 패킷은 마지막 5번 규칙에서 거부된다](./images/csintro-network-security-firewall-rules.svg '방화벽 규칙셋의 평가 순서')

리눅스 iptables로 같은 정책을 쓰면 다음과 같다.

```bash
iptables -P INPUT DROP                                   # 기본 거부
iptables -A INPUT -i eth0 -s 192.168.0.0/24 -j DROP      # 외부 인터페이스로 들어온 내부 대역 위조 차단
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -s 203.0.113.5 -j ACCEPT   # 관리자 PC만 SSH
iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 1/s -j ACCEPT
```

방화벽의 종류(패킷 필터, 상태 기반, 애플리케이션 게이트웨이)와 iptables 체인의 동작은 [방화벽의 종류와 iptables 규칙](/memo/net-firewall)에서 이어서 다룬다.

### 침입 탐지 시스템과 침입 방지 시스템

침입 탐지 시스템(IDS, Intrusion Detection System)은 네트워크로 들어오는 공격을 탐지해 관리자가 능동적으로 대응할 수 있게 하는 시스템이다. 실제 공격 시점이나 그 이전에 공격 양상을 탐지할 수 있다. 새로운 공격 패턴을 인식할 수 있도록 탐지 규칙(시그니처)을 지속적으로 업데이트하고 관리해야 한다. 탐지된 공격의 출발지 주소를 방화벽이나 라우터에서 영구적으로 차단하는 것도 예방책이 된다.

| 탐지 방식                | 원리                                               | 장점                    | 단점               |
| ------------------------ | -------------------------------------------------- | ----------------------- | ------------------ |
| 오용 탐지(시그니처 기반) | 알려진 공격 패턴과 비교                            | 오탐이 적고 원인이 명확 | 새로운 공격을 놓침 |
| 이상 탐지(행위 기반)     | 평소 트래픽의 통계적 기준선에서 벗어난 행위를 찾음 | 알려지지 않은 공격 탐지 | 오탐이 많음        |

==IDS는 스위치의 미러 포트로 트래픽 사본을 받아 분석하므로 경보만 울리고 직접 차단하지는 않는다==. 침입 방지 시스템(IPS, Intrusion Prevention System)은 트래픽 경로 위(인라인)에 놓여 탐지한 패킷이나 세션을 즉시 차단한다. 대신 오탐하면 정상 트래픽까지 막고, IPS 장비 자체가 장애 지점이 될 수 있다. 오픈소스 IDS·IPS로는 Snort와 Suricata가 널리 쓰인다.

```text
alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (msg:"SYN flood"; flags:S; \
  detection_filter:track by_dst, count 200, seconds 1; sid:1000001;)
```

위 Snort 규칙은 1초 안에 같은 목적지 80번 포트로 SYN 패킷이 200개를 넘으면 경보를 낸다.

### 시스템 패치

시스템에서 바이러스나 해킹 공격에 취약한 점이 발견되면 운영체제·소프트웨어 제조사가 보안 패치를 발표한다. Ping of Death나 여러 TCP 스택 결함이 그랬듯, 프로토콜 처리의 버그를 노린 DoS는 패치로 막힌다. 다만 패치가 어떤 기능을 바꾸는지 먼저 이해한 뒤 적용해야 한다. 패치 때문에 기존 서비스가 동작하지 않는 경우가 있으므로, 시험 환경에서 확인하고 적용 전에 반드시 백업한다.

### 스캐닝

스캐닝은 포괄적인 의미의 시스템 분석이다. 관리자가 자기 네트워크를 정기적으로 점검해 열려 있는 포트, 동작 중인 서비스와 판, 알려진 취약점을 찾아 두면 공격자보다 먼저 약점을 막을 수 있다. 포트 스캐너 nmap(`nmap -sV <대상>`)과 취약점 스캐너 OpenVAS가 대표 도구다. 같은 도구를 공격자도 공격 대상 정찰에 쓰므로, IDS에서 외부의 스캔 시도를 탐지하는 것도 조기 경보가 된다.

### 서비스별 대역폭 제한

서비스마다 쓸 수 있는 대역폭을 정해 두면(QoS, 트래픽 셰이핑), ==특정 서비스가 공격받아도 나머지 서비스에 미치는 영향을 줄일 수 있다==. 공격받는 서비스도 공격이 성공하는 데 필요한 대역폭을 다 차지하지 못하므로 공격 효과가 줄어든다.

| 서비스         | 회선 1Gbps 중 할당 | 공격 시 결과                          |
| -------------- | ------------------ | ------------------------------------- |
| 웹(HTTP/HTTPS) | 600Mbps            | 웹이 공격받아도 600Mbps 안에서만 포화 |
| 메일           | 200Mbps            | 웹 공격과 관계없이 200Mbps 보장       |
| 내부 업무망    | 200Mbps            | 웹 공격과 관계없이 200Mbps 보장       |

대규모 DDoS는 회선 자체를 넘치게 하므로 조직 내부 장비만으로는 막을 수 없다. 통신사나 CDN의 트래픽 세척(scrubbing) 서비스, 클라우드 DDoS 방어 서비스, KISA의 사이버 대피소처럼 공격 트래픽을 회선 바깥에서 걸러 내는 서비스를 함께 쓴다.

## 직접 해 보기

### ARP 테이블 확인

윈도우 명령 프롬프트나 macOS·리눅스 터미널에서 실행한다.

```bash
arp -a
```

윈도우에서는 다음 형식으로 출력된다(주소는 예시).

```text
인터페이스: 192.168.219.184 --- 0x6
  인터넷 주소           물리적 주소           유형
  192.168.219.1         00-27-1c-7b-78-9c     동적
  192.168.219.21        98-93-cc-22-59-9e     동적
  192.168.219.255       ff-ff-ff-ff-ff-ff     정적
  224.0.0.22            01-00-5e-00-00-16     정적
  239.255.255.250       01-00-5e-7f-ff-fa     정적
  255.255.255.255       ff-ff-ff-ff-ff-ff     정적
```

| 항목                            | 의미                                                                    |
| ------------------------------- | ----------------------------------------------------------------------- |
| `192.168.219.1`                 | 기본 게이트웨이(공유기). ARP로 학습한 동적 항목                         |
| `192.168.219.255`               | 서브넷 브로드캐스트 주소. MAC도 브로드캐스트(`ff-…`)                    |
| `224.0.0.22`, `239.255.255.250` | 멀티캐스트 주소(IGMP, SSDP). MAC은 `01-00-5e`로 시작하는 멀티캐스트 MAC |
| 동적 / 정적                     | ARP 응답으로 학습한 항목 / 운영체제나 관리자가 고정한 항목              |

게이트웨이 IP는 `ipconfig`(윈도우) 또는 `netstat -rn | grep default`(macOS)로 확인하고, 그 IP의 MAC 주소가 공유기 라벨이나 관리 화면의 MAC과 같은지 비교한다. 다른 IP와 같은 MAC을 가리키고 있으면 ARP 스푸핑을 의심한다.

같은 화면에서 `ping <도메인>`을 실행하면, 응답이 오지 않더라도 첫 줄에 `Ping <도메인> [IP 주소]`가 표시되어 DNS가 그 이름을 어떤 IP로 해석했는지 확인할 수 있다. 서버가 ICMP를 차단하면 "요청 시간이 만료되었습니다"가 나오고 손실률이 100%가 되는데, 이는 서버가 꺼졌다는 뜻이 아니라 방화벽이 ICMP 에코 요청을 버렸다는 뜻일 수 있다.

### hosts 파일로 이름 해석 바꾸기

hosts 파일에 줄을 추가하면 그 이름은 DNS 질의 없이 적은 IP로 해석된다. 존재하지 않는 도메인에 실제 웹 서버의 IP를 대응시키면, 브라우저 주소창에 그 가짜 도메인을 입력해도 해당 웹 사이트가 열린다. DNS 스푸핑과 파밍이 사용자에게 어떻게 보이는지 확인하는 실험이다.

1. 접속할 웹 사이트의 IP를 확인한다: `ping www.example.com` 또는 `nslookup www.example.com`.
2. 관리자 권한으로 hosts 파일을 연다. 윈도우는 메모장을 관리자 권한으로 실행해 `C:\Windows\System32\drivers\etc\hosts`를 열고, macOS·리눅스는 `sudo nano /etc/hosts`.
3. 파일 끝에 `<1번의 IP> myname.test`처럼 한 줄을 추가하고 저장한다.
4. 윈도우는 `ipconfig /flushdns`, macOS는 `sudo dscacheutil -flushcache`로 DNS 캐시를 비운다.
5. 브라우저에서 `http://myname.test/`에 접속한다.

```bash
sudo sh -c 'echo "93.184.215.14 myname.test" >> /etc/hosts'
ping -c 1 myname.test
```

```text
PING myname.test (93.184.215.14): 56 data bytes
```

`ping` 결과의 IP가 hosts 파일에 적은 값과 같다면 DNS 질의 없이 해석된 것이다. 브라우저 주소창에는 `myname.test`가 표시되지만 실제로는 다른 사이트의 화면이 뜬다. 웹 서버가 `Host` 헤더로 사이트를 구분하는 가상 호스팅 환경이면 오류 페이지가 나올 수도 있고, HTTPS로 접속하면 인증서의 도메인이 `myname.test`와 달라 브라우저가 경고를 띄운다. ==이 경고가 DNS 조작을 알아챌 수 있는 단서다==. 실험이 끝나면 추가한 줄을 지우고 DNS 캐시를 다시 비운다.
