관리자 글쓰기를 메모 앱처럼 바꿨다. 편집 버튼 없이 글을 누르면 바로 고치고, 멈추면 알아서 저장한다. 쓰기는 편해졌는데 곧 두 가지가 걸렸다.

- **저장하는 순간 방문자에게 보인다.** 쓰다 만 글도, 반쯤 고친 문장도 그대로 공개된다
- **되돌릴 수 없다.** 잘못 지운 문단은 저장되는 순간 사라진다

따로 편집 모드를 두는 쪽으로 돌아갈까도 생각했지만, 바로 고치는 편함은 그대로 두고 **저장과 공개를 나누기로** 했다. 서버 쪽은 [#44](https://github.com/hyeoniverse/MacFolio/pull/44)에 들어갔다.

| 방법                                      | 좋은 점                     | 나쁜 점                                                             |
| ----------------------------------------- | --------------------------- | ------------------------------------------------------------------- |
| 편집 모드로 돌아간다 (편집 → 저장)        | 저장 = 공개가 분명하다      | 메모 앱처럼 바로 고치는 편함을 버린다. 저장 전에 창을 닫으면 잃는다 |
| 글을 두 행으로 (공개 글·초안 글)          | 표 구조는 단순              | 주소(slug)가 둘. 공개와 초안을 오갈 때 행을 옮겨야 한다             |
| **한 행에 두 벌 (게시한 내용·임시 저장)** | 주소 하나. 게시는 "칸 복사" | 칸이 두 배. "둘 다 비었거나 둘 다 맞다"를 DB가 지켜야 한다          |

## 임시 저장과 게시

![게시한 내용과 임시 저장 두 벌, 그리고 게시할 때 쌓이는 버전](./images/drafts-and-versions-states.svg '자동 저장은 임시 저장에만, 게시하면 임시 저장이 게시한 내용이 되고 버전이 하나 쌓인다')

글 하나에 내용을 두 벌 둔다.

- **게시한 내용**: 방문자가 보는 것
- **임시 저장**: 관리자가 고치고 있는 것

자동 저장은 임시 저장에만 쓴다. 날짜 줄 오른쪽의 **게시**를 눌러야 임시 저장이 게시한 내용이 되고, 그때 방문자에게 보인다. 게시하지 않은 편집은 **변경 사항 버리기**로 버리고 게시한 내용으로 돌아갈 수 있다.

새 메모는 임시 저장으로 시작한다. 게시하기 전에는 아무에게도 보이지 않으니 며칠에 걸쳐 써도 된다.

관리자 목록에는 상태를 붙였다.

- **임시 저장**: 한 번도 게시하지 않은 글
- **점**: 게시한 글에 게시하지 않은 편집이 있다
- **예약**: 게시했지만 날짜가 아직 안 된 글

![관리자 목록의 게시 상태](./images/drafts-status.jpg '예약한 글은 예정 묶음에, 게시하지 않은 편집은 제목 옆 점으로, 새 메모는 임시 저장 표시로 보인다')

저장소의 Markdown 글도 같다. 고치면 임시 저장만 생기고, 방문자는 게시할 때까지 원래 파일 내용을 본다.

## 버전 기록

게시할 때마다 그 내용을 버전으로 남긴다(글마다 최근 50개, `MAX_REVISIONS`). 자동 저장마다 남기지 않은 것은 그러면 몇 초마다 버전이 쌓여 목록이 쓸모없어지기 때문이다. "게시"가 관리자가 스스로 정한 마디라서 그 순간만 남긴다. 도구 막대의 시계 버튼을 누르면 버전 목록이 열리고, 고르면 미리 보고, **이 버전으로 되돌리기**를 누르면 그 내용이 편집기에 들어간다. 되돌려도 바로 공개되지는 않는다. 임시 저장으로 들어가서, 확인하고 게시하면 된다. 저장소 글이면 목록 맨 아래에 **원본**이 있어서 처음 파일 내용으로도 돌아갈 수 있다.

![버전 기록](./images/memo-versions.jpg '게시할 때마다 남은 버전과 저장소 원본. 고르면 미리 보고 되돌릴 수 있다')

되돌리기는 편집기를 새로 그리는 대신 **편집기 스스로 내용을 바꾸게** 했다. 바깥에서 새 내용으로 편집기를 다시 그리면, 사라지는 편집기가 마지막 편집을 저장하는 요청과 되돌린 내용을 저장하는 요청이 경쟁한다. 늦게 도착한 쪽이 이기므로 되돌린 내용이 덮일 수 있다. 편집기 안의 저장 줄에 되돌린 내용을 세우면 차례가 지켜진다.

## 예약 발행

날짜를 미래로 고르면 게시 버튼이 **예약**으로 바뀐다. 누르면 게시는 되지만, 방문자에게는 그 날짜부터 보인다.

예약을 위해 따로 도는 작업(스케줄러)은 두지 않았다. 방문자가 글 목록을 받을 때 서버가 **게시한 날짜가 오늘(서울 기준) 이후인 글을 뺀다.** 날짜가 지나면 다음 요청부터 저절로 보인다. 저장소 글을 미래 날짜로 다시 게시했다면, 원래 파일 내용도 그날까지 가린다.

관리자 목록에서는 미래 날짜 글이 '오늘'로 묶이던 문제도 고쳤다. 날짜로 묶을 때 미래는 **예정**으로 따로 모은다.

## 서버: 두 벌의 내용과 CHECK 제약

`Post` 테이블에 게시한 내용(`title`…`body`, `publishedAt`)과 임시 저장(`draftTitle`…`draftBody`, `draftUpdatedAt`)을 나란히 두고, 버전은 `PostRevision`에 쌓는다.

```text
GET    /posts                    누구나: 게시한 글 중 날짜가 된 것, 가릴 표시
GET    /posts/admin              관리자: 게시한 내용과 임시 저장
POST   /posts                    새 글 (임시 저장으로)
PUT    /posts/:slug/draft        임시 저장 (자동 저장)
DELETE /posts/:slug/draft        변경 사항 버리기
POST   /posts/:slug/publish      게시 (버전이 하나 남는다)
GET    /posts/:slug/revisions    버전 목록, /:id 로 내용
```

DB에는 "두 벌 모두 **다 비었거나, 다 규칙에 맞는다**"는 CHECK 제약을 걸었다. 여기서 한 번 틀렸다. 처음에는 이렇게 썼다.

```sql
("title" IS NULL AND ... ) OR (length(btrim("title")) BETWEEN 1 AND 100 AND length(btrim("body")) > 0 ...)
```

제목만 있고 본문이 `NULL`인 행을 넣어 보는 시험이 **통과해 버렸다.** `btrim(NULL)`은 `NULL`이고, `NULL > 0`도 `NULL`이라 뒤쪽 식 전체가 `NULL`이 된다. 그런데 CHECK 제약은 결과가 `false`일 때만 거절하고 **`NULL`이면 통과시킨다.** 각 칸이 `IS NOT NULL`인지 먼저 따지게 고쳤다.

```sql
ALTER TABLE "Post" ADD CONSTRAINT "Post_published_fields" CHECK (
  ("title" IS NULL AND "date" IS NULL AND … AND "publishedAt" IS NULL)
  OR (
    "title" IS NOT NULL AND "date" IS NOT NULL AND "category" IS NOT NULL AND "body" IS NOT NULL
    AND length(btrim("title")) BETWEEN 1 AND 100 AND … AND "publishedAt" IS NOT NULL
  )
);
```

임시 저장 칸에도 같은 모양의 `Post_draft_fields`를 걸고, 셋째로 `Post_has_content`(지운 글이 아니면 두 벌 중 하나는 있어야 한다)를 걸었다. 앱 코드가 검사를 빠뜨려도 DB가 이상한 행을 받지 않는다.

| 식                          | 결과    | CHECK    |
| --------------------------- | ------- | -------- |
| `length(btrim('제목')) > 0` | `true`  | 통과     |
| `length(btrim('')) > 0`     | `false` | 거절     |
| `length(btrim(NULL)) > 0`   | `NULL`  | **통과** |
| `NULL IS NOT NULL AND …`    | `false` | 거절     |

이미 있던 글은 마이그레이션에서 옮겼다. 지운 표시는 내용을 비우고, 나머지는 게시한 글로 보고 지금 내용을 첫 버전으로 남긴다. 옛 모양의 행을 넣은 빈 DB에 마이그레이션을 차례로 적용해서 결과를 확인했다. 이주 파일(`20260929162900_post_drafts_revisions`)은 87줄이고, 그중 `UPDATE` 두 줄과 `INSERT` 하나가 옛 글을 옮긴다.

## 확인

API e2e `apps/api/test/posts.e2e.test.ts`가 실제 Postgres로 이 흐름을 지나간다. 이 기능에 해당하는 시험만 추리면 이렇다.

- "새 글은 임시 저장으로 시작해서, 게시하기 전에는 방문자에게 보이지 않는다"
- "게시한 글을 고쳐도 게시할 때까지 방문자는 게시한 내용을 본다. 버리면 게시한 내용으로 돌아간다"
- "게시한 적 없는 글의 임시 저장을 버리면 글이 없어진다 (저장소 글이면 원래대로 보인다)"
- "관리자 목록은 게시한 내용과 임시 저장을 따로 보여 준다"
- "날짜가 미래인 글은 게시해도 그날까지 가려진다 (예약 발행, 저장소 글도 가린다)"
- "게시할 때마다 버전을 남기고, 버전의 내용을 읽을 수 있다", "버전은 글마다 최근 50개만 남긴다"
- "규칙을 어기면 관리자라도 400 (임시 저장도 같은 규칙)"

서버 커밋은 파일 5개, +550/−102다.

## 남은 것과 배운 것

- 예약 발행은 "다음 요청부터 보인다"라서, 정해진 시각에 알림을 보내거나 RSS를 갱신하는 일은 할 수 없다. 지금은 그럴 곳이 없어서 스케줄러를 두지 않은 것이 맞았다.
- 버전 비교(두 버전의 차이 보기)는 없다. 고르면 통째로 미리 볼 뿐이다.
- 이 뒤에 [최근 삭제된 항목](/memo/memo-recently-deleted)과 잠금이 더해지면서 `deletedAt`과 잠금 검사(409)가 같은 표에 붙었다.

배운 것: SQL의 CHECK는 "참이어야 통과"가 아니라 "거짓이 아니면 통과"다. NULL이 섞일 수 있는 칸은 `IS NOT NULL`을 먼저 따져야 한다. 이것을 알게 해 준 것은 "틀린 행을 넣으면 거절되는가"를 묻는 시험이었다. 맞는 행만 넣어 보는 시험이었다면 몰랐을 것이다.

## 직접 써 보기

관리자로 로그인해야 하는 기능이라 로컬에서 띄워 본다([관리자 로그인 붙이기](/memo/admin-login-github-oauth)의 개발용 OAuth App이 필요하다).

```bash
pnpm --filter @macfolio/api db:up
pnpm dev:all
```

1. 메모 앱에서 새 글을 쓴다. 저장하면 임시 저장이라 방문자 창(시크릿 창)에는 보이지 않는다
2. 게시한다. 시크릿 창을 새로고침하면 보인다
3. 고쳐서 다시 게시하고, 버전 기록에서 앞 버전을 고른다. 되돌리기는 그 버전 내용을 새 버전으로 게시하는 것이라 기록이 지워지지 않는다

같은 흐름을 시험으로 돌리려면 `pnpm --filter @macfolio/api test:e2e test/posts.e2e.test.ts`. 두 벌의 내용을 지키는 DB CHECK 제약은 [Prisma 마이그레이션](https://www.prisma.io/docs/orm/prisma-migrate)으로 넣었다.
