## 시험과 CI를 기능보다 먼저

9월 28일에는 Firebase를 제거해 호스팅을 Cloudflare Workers로 옮기고, pnpm workspaces와 Turborepo로 모노레포를 구성했다. 이어서 ESLint·Prettier, Playwright E2E, GitHub Actions CI를 PR 하나([#26](https://github.com/hyeoniverse/MacFolio/pull/26))로 도입했고, 처음 실행한 시험에서 음악 창을 닫으면 Dock까지 화면 전체가 사라지는 버그를 바로 찾았다. 창 위치·크기와 쌓임 순서 계산은 순수 함수로 분리해 Vitest로 검증하고, 앱 하나의 오류가 화면 전체를 멈추지 않게 Error Boundary를 추가했다. ==E2E는 이날 0개에서 78개가 되었고, 주 마지막 날에는 204개였다.== 같은 날 메모·메시지 앱을 여러 번 다시 작성하는 동안 이 시험이 회귀를 먼저 검출했고, 모노레포 덕분에 다음 날 API 서버를 같은 저장소에 추가했다.

## API 서버와 관리자 로그인, 인바운드 포트 없는 배포

9월 29일 저녁에 NestJS + Prisma + PostgreSQL로 API 서버를 만들고, GitHub OAuth와 DB 세션, 관리자만 통과하는 `AdminGuard`를 넣었다. 제목·날짜·폴더·본문 같은 필수 항목은 화면의 입력 검사, API의 400 응답, DB의 CHECK 제약 세 계층에서 검증한다. 로그인은 처음에 관리자 여부를 변경 가능한 GitHub 아이디(`login`)로 판단해서, 관리자가 아이디를 바꾸면 이전 아이디를 등록한 다른 사람이 관리자가 될 수 있었다. 세 시간 만에 ==판단 기준을 바뀌지 않는 숫자 ID로 바꾸고==, 로그인 요청에 IP별 횟수 제한을 적용했다.

9월 30일에는 Oracle Cloud Always Free VM에 Postgres·API·cloudflared를 docker compose로 실행하고, SSH 외에는 인바운드 포트를 열지 않았다. 외부 요청은 VM이 바깥으로 연결한 Cloudflare Tunnel로 들어온다. 가장 오래 걸린 문제는 빌드 시점에 번들에 포함되는 `VITE_API_URL`을 Cloudflare의 런타임 변수로 등록해서 사이트가 API 주소를 읽지 못한 것이었다.

## @layer로 !important 72개 정리

10월 1일에 집계해 보니 코드에 `!important`가 72개 있었다. 버튼 색이나 아이콘 크기가 적용되지 않을 때마다 하나씩 추가한 것이다. 원인은 하나였다. 앱 루트의 기본값 `.memo button`(명시도 0,1,1)이 버튼 클래스 `.memo-copy-button`(0,1,0)보다 명시도가 높았다. 기본값을 `@layer reset`으로 옮기면 레이어 밖의 규칙이 명시도와 관계없이 우선하므로, 그 뒤로는 `!important`를 삭제하기만 하면 된다.

작업은 레이어 이동([#57](https://github.com/hyeoniverse/MacFolio/pull/57)), 메뉴 다섯 종을 `Menu`·`useDismiss`·`placement`로 통합([#59](https://github.com/hyeoniverse/MacFolio/pull/59)), `IconButton` 통합과 `!important` 삭제([#60](https://github.com/hyeoniverse/MacFolio/pull/60)), `Button` 통합([#61](https://github.com/hyeoniverse/MacFolio/pull/61)) 순서로 나눴다. 남은 `!important`는 `prefers-reduced-motion`용 2개뿐이고, ==원인을 먼저 확인하고 순서대로 진행해 되돌린 커밋이 0개==였다.

## 이름·비밀번호 칸 대신 방문자 쿠키

10월 2일에는 휴대폰 메시지 화면의 이름·비밀번호 입력 칸을 네 번 고쳤지만 여전히 본문 입력창보다 눈에 띄었다. 칸이 필요했던 이유는 작성자가 나중에 자기 글을 삭제할 수 있도록 작성자를 식별하는 것 하나였고, 이 목적에는 사용자 입력이 필요하지 않았다. 그래서 칸을 없애고, 서버가 처음 방문한 브라우저에 httpOnly 쿠키를 발급해 그 값의 HMAC만 저장하게 했다. 표시 이름("🦊 날쌘 여우")도 쿠키 값으로 정한다. 같은 브라우저면 언제 방문해도 같은 이름이 되고, 작성한 브라우저에서 자기 글을 삭제할 수 있다.

메시지도 이때 처음 서버에 저장했다. 프론트엔드만 먼저 배포된 상태에서 이전 서버가 "이름을 입력해 주세요" 오류를 반환한 일을 겪고, 서버에 연결할 수 없으면 메시지 앱을 여는 단계에서 차단하게 했다.

## 시험을 통과한 커밋만 배포

![Cloudflare Workers 사용량](./images/day-1003-workers-usage.jpg#float-right '빌드 실패 시각에 확인한 Workers 사용량. 빌드 시간 150/3,000분으로 한도와 관계없었다')

10월 3일, PR [#80](https://github.com/hyeoniverse/MacFolio/pull/80)의 `Workers Builds` 검사가 `Build failed to initialize and was timed out`으로 실패했다. 사용량은 이번 달 빌드 시간 3,000분 중 150분이어서 한도가 아니라 Cloudflare 측 빌드 환경 문제였다. 이를 검토하다가 더 큰 구조 문제를 찾았다. 시험(GitHub Actions)과 배포(Cloudflare Workers Builds)가 서로 독립적으로 실행되어, ==시험이 실패한 커밋도 사이트에 배포될 수 있었다.==

배포용 API 토큰을 새로 발급하고 Cloudflare의 Git 연결을 해제한 뒤, GitHub Actions에서 wrangler로 배포하되 배포 작업은 시험 작업이 통과한 뒤에만 실행되게 했다([#82](https://github.com/hyeoniverse/MacFolio/pull/82)). 이틀 뒤 API 자동 배포도 같은 구조로 만들었다.

| 항목               | 변경 전 (Cloudflare Git 연결)  | 변경 후 (GitHub Actions)                   |
| ------------------ | ------------------------------ | ------------------------------------------ |
| 시험과의 관계      | 시험 결과와 관계없이 빌드·배포 | 배포 작업은 시험 작업이 통과한 뒤에만 실행 |
| 시험이 실패한 커밋 | 배포될 수 있음                 | 배포되지 않음                              |

자세한 내용: [10월 3일 회고](/memo/day-1003), [Workers Builds 대신 GitHub Actions와 wrangler로 시험을 통과한 커밋만 배포하기](/memo/deploy-github-actions)

## 돌아보며

- 시험을 기능보다 먼저 도입한 덕분에 한 주 내내 회귀를 잡았다. 앱을 여러 번 다시 작성해도 실패한 곳이 바로 드러났다.
- 인증은 로그인 성공보다 관리자가 아닌 사람이 확실히 차단되는지를 먼저 확인해야 한다. 변경 가능한 값(아이디)을 권한 판단에 쓰지 않는다.
- 원인을 먼저 확인한 작업(`@layer`)은 되돌린 커밋이 없었고, 화면을 보며 결정한 작업(메시지 앱 방향 다섯 번, 최근 삭제된 항목 안내 상자, 저장소 선택 화면 21분에 세 번)은 같은 결정을 반복해 바꿨다. UI를 바꾸기 전에 참고할 실제 화면을 먼저 확보한다.
- 요소를 고치기 전에 그 요소가 왜 필요한지 확인한다. 이름 칸을 네 번 수정하기 전에 물었다면 처음부터 쿠키를 선택했다.
- 10월 4일에는 커밋 83개를 PR [#88](https://github.com/hyeoniverse/MacFolio/pull/88) 하나에 담았고, E2E는 6개만 늘렸다. 그래서 다음 주 트래픽 분석은 처음부터 PR 네 개로 나눴다.
