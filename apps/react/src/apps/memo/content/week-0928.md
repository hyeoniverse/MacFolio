### 관리자 판정 기준: 아이디 대신 숫자 ID

> [!CAUTION] 변경할 수 있는 아이디로 관리자 판정
> 로그인을 처음 구현하고 세 시간 만에 다시 수정했다. 관리자 여부를 GitHub **아이디(login)**로 판단하고 있었는데, 아이디는 변경할 수 있다. 관리자가 아이디를 변경하면 이전 아이디를 다른 사람이 등록할 수 있고, 그 사람이 로그인하면 관리자로 인식된다.

| 기준             | 변경 가능 | 위험                                           |
| ---------------- | --------- | ---------------------------------------------- |
| 아이디 (`login`) | 가능      | 이전 아이디를 등록한 다른 사람이 관리자가 된다 |
| 숫자 ID (`id`)   | 불가능    | 계정마다 고정                                  |

변경되지 않는 **숫자 ID**로 판단하도록 수정하고, 로그인 요청에는 IP별 횟수 제한을 적용했다. ==인증은 로그인 성공 여부보다, 관리자가 아닌 사람이 확실히 차단되는지를 먼저 확인해야 한다.==

API PR 네 개([#41](https://github.com/hyeoniverse/MacFolio/pull/41)~[#44](https://github.com/hyeoniverse/MacFolio/pull/44))는 서로 의존하고 있어서 9월 30일 새벽 4시 반에 한꺼번에 머지했다. 이렇게 이어진 PR은 리뷰와 머지 순서를 모두 복잡하게 만든다.

## API 서버 배포와 서버 반영

### Oracle Cloud VM과 Cloudflare Tunnel

9월 30일에 로컬에서만 동작하던 로그인을 배포 환경으로 옮겼다. Oracle Cloud Always Free VM에 Postgres, API, cloudflared를 docker compose로 실행하고, SSH 외에는 인바운드 포트를 하나도 열지 않았다. 외부 요청은 Cloudflare Tunnel(cloudflared)이 VM에서 바깥으로 연결한 터널로 들어온다. 자세한 과정은 [Oracle 무료 VM과 Cloudflare Tunnel로 인바운드 포트 없이 API 서버 배포하기](/memo/deploy-api-oracle-tunnel)에 정리했다.

<details>
<summary>배포 단계마다 막힌 곳</summary>

1. 처음에는 로컬 Mac에서 `docker run --env-file /etc/macfolio/api.env …`를 실행해 `no such file or directory` 오류가 발생했다. 서버에 있어야 할 파일을 로컬에서 찾고 있었다. 서버를 먼저 생성해야 했다.
2. Oracle Cloud에서 VM을 생성할 때 보안 항목(Shielded instance와 Confidential computing은 함께 활성화할 수 없다)은 기본값을 유지했다.
3. 네트워크 설정에서 "공인 IPv4 자동 할당" 체크박스가 활성화되지 않았다. `You must select a public subnet to assign a public IPv4 address.` 안내대로, 기존 서브넷 대신 **새 공인 서브넷 만들기**를 선택하자 활성화되었다.
4. 내려받은 SSH 키를 `~/.ssh/`로 옮기고 권한을 `chmod 600`으로 제한한 뒤 접속했다. 키 이동 명령은 절대 경로(`~/Downloads` → `~/.ssh`)를 사용해서, 실행한 디렉터리와 관계없이 동작했다.
5. 접속 후 `free -h`로 확인한 메모리는 954Mi, 스왑은 0이었다. 무료 VM의 사양이다.
6. `.env`와 `api.env`는 저장소 안이 아니라 서버의 `~/deploy/`에 별도로 보관하고 권한을 `chmod 600`으로 제한했다. 비밀 값이 `git pull`로 덮어쓰이거나 커밋되지 않게 하기 위해서다.

```bash
ssh -i ~/.ssh/<키 파일> ubuntu@<서버 IP>
free -h                       # 메모리·스왑 확인
mkdir ~/deploy && cd ~/deploy # 비밀 값은 저장소 밖에
chmod 600 .env api.env
```

</details>

전체 절차는 저장소의 [docs/deployment.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/deployment.md)와 [Oracle Cloud Always Free 문서](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm)에 있다. 무료 서버는 회수될 수 있으므로, VM 생성부터 OAuth App, 터널, 환경 변수, 막혔던 증상과 해결 방법까지 문서만으로 다시 구축할 수 있게 기록했다.

### 빌드 변수와 런타임 변수

가장 오래 걸린 단계는 서버가 아니라 프론트엔드였다. API의 `/docs`는 열리는데 사이트에서는 "관리자 서버가 아직 연결되지 않았습니다"가 표시되었다. `VITE_API_URL`은 빌드 시점에 번들에 포함되는 값인데, ==Cloudflare의 런타임 변수로 등록했던 것이 원인==이었다. 빌드 변수로 옮기자 바로 해결되었다.

| 변수 종류   | 읽는 시점                                  | `VITE_API_URL`에 적합한가          |
| ----------- | ------------------------------------------ | ---------------------------------- |
| 빌드 변수   | `vite build` 실행 중, 번들에 문자열로 포함 | 적합                               |
| 런타임 변수 | Worker가 요청을 처리할 때                  | 부적합 (브라우저 번들은 읽지 못함) |

### 수동 반영 절차의 오류

이 주의 API 배포는 서버에 접속해 `git pull`하고 1GB 메모리로 빌드하는 수동 절차였다. 새 코드를 반영할 때마다 실행 위치를 틀리는 오류가 반복되었다.

| 날짜     | 명령                | 오류                        | 원인                                                      |
| -------- | ------------------- | --------------------------- | --------------------------------------------------------- |
| 10월 2일 | `pg_dump` (백업)    | `no such file or directory` | 서버가 아니라 로컬 Mac에서 실행했다                       |
| 10월 3일 | `pg_dump`           | 명령을 찾을 수 없음         | 서버 호스트에는 `pg_dump`가 없고, DB 컨테이너 안에만 있다 |
| 10월 3일 | `git pull`          | 저장소 폴더가 아님          | 저장소는 `~/macfolio`에 있다                              |
| 10월 3일 | `docker compose up` | compose 파일이 없음         | compose 파일은 `~/deploy`에 있다                          |

올바른 순서로 다시 실행한 뒤 `docker compose logs -f api`로 확인하니 `Applying migration 20261002150000_wallpapers` 다음에 `All migrations have been successfully applied.`가 기록되고 Nest가 시작되었다. 마이그레이션을 컨테이너 시작 시점에 실행하는 방식은 [Prisma Migrate 배포 문서](https://www.prisma.io/docs/orm/prisma-client/deployment/deploy-database-changes-with-prisma-migrate)를 따랐다.

```bash
ssh ubuntu@<서버>
cd ~/deploy
docker compose exec -T db pg_dump -U macfolio macfolio > ~/backup-$(date +%F).sql
(cd ~/macfolio && git pull)
docker compose up -d --build api
docker compose logs -f api   # "All migrations have been successfully applied." 확인
```

현재는 백업을 [ops/backup.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/backup.sh)가 수행하고, API 배포도 이틀 뒤 GitHub Actions로 자동화했다.

## 프론트엔드 배포: 시험을 통과한 커밋만

10월 3일, PR #80의 `Workers Builds: macfolio` 검사가 실패했다. 로그에는 `Initializing build environment...`가 5분 간격으로 두 번 기록된 뒤 `Build failed to initialize and was timed out`만 남아 있었다. 처음에는 빌드 한도를 초과했다고 판단했지만, 대시보드의 사용량을 확인해 보니 이번 달 빌드 시간은 3,000분 중 150분이었다. 한도 문제가 아니라 Cloudflare 측 빌드 환경이 시작되지 않은 것이다.

![Cloudflare Workers 사용량](./images/day-1003-workers-usage.jpg '빌드 실패 시각에 확인한 Workers 사용량. 빌드 시간 150/3,000분으로 한도와 관계없었다')

빌드 실패 상태로 머지해도 되는지 검토하다가 더 큰 구조 문제를 확인했다. 시험(GitHub Actions)과 배포(Cloudflare Workers Builds)가 서로 독립적으로 실행되어, 시험(`check`)이 ==실패한 커밋도 사이트에 배포될 수 있었다.==

| 항목               | 변경 전 (Cloudflare Git 연결)    | 변경 후 (GitHub Actions)                   |
| ------------------ | -------------------------------- | ------------------------------------------ |
| 빌드 실행 위치     | Cloudflare 빌드 서버             | GitHub Actions                             |
| 시험과의 관계      | 시험 결과와 관계없이 빌드·배포   | 배포 작업은 시험 작업이 통과한 뒤에만 실행 |
| 시험이 실패한 커밋 | 배포될 수 있음                   | 배포되지 않음                              |
| 빌드 환경 장애     | Cloudflare 빌드 서버 상태에 의존 | GitHub Actions 러너에서 빌드               |

배포를 GitHub Actions로 이전했다([Workers Builds 대신 GitHub Actions와 wrangler로 시험을 통과한 커밋만 배포하기](/memo/deploy-github-actions), [#82](https://github.com/hyeoniverse/MacFolio/pull/82)).

1. 배포용 Cloudflare API 토큰을 기존 토큰과 별도로 새로 발급해 저장소 시크릿에 저장했다
2. Cloudflare의 Git 연결을 해제(Disconnect)했다
3. 배포 작업이 시험 작업 뒤에만 실행되도록 워크플로를 구성했다

절차는 [Cloudflare의 GitHub Actions 배포 문서](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)와 저장소의 [.github/workflows](https://github.com/hyeoniverse/MacFolio/tree/main/.github/workflows)에 있다. 같은 날 conventions 검사에 "Node.js 20 is deprecated" 경고가 표시되어, 액션 버전을 Node 24로 올리는 PR을 별도로 제출했다([#83](https://github.com/hyeoniverse/MacFolio/pull/83)). 백엔드 설계도 이날 한 장으로 정리했다([요청 계층과 위험별 설계 결정으로 정리한 MacFolio 백엔드 구성도](/memo/backend-design), [#84](https://github.com/hyeoniverse/MacFolio/pull/84)).

## 공통 컴포넌트: !important 72개를 0개로

### 원인: 앱 루트 기본값의 명시도

10월 1일 기준 코드에 `!important`가 72개 있었다. 버튼 색이나 아이콘 크기가 적용되지 않을 때마다 하나씩 추가한 것이었다. 계기는 메모 앱의 작은 불일치였다. 코드 블록의 복사 버튼과 이미지의 다운로드 버튼이 같은 역할인데 모양과 스타일이 서로 달랐고, 공유 아이콘도 macOS의 "상자에서 화살표가 나오는" 모양이 아니었다. 클래스와 스타일 구조를 도식으로 정리해 보니, 공통 버튼 컴포넌트가 없고 앱마다 같은 버튼을 따로 구현하고 있었다.

72개의 원인은 하나였다. ==앱 루트에 지정한 기본값이 버튼마다 지정한 클래스보다 명시도(specificity)가 높았다.==

```css
/* 앱 루트의 기본값: 명시도 (0,1,1) */
.memo button {
	color: inherit;
}

/* 버튼 클래스: 명시도 (0,1,0) → 위 규칙에 밀려 적용되지 않는다 */
.memo-copy-button {
	color: var(--ui-accent);
}
```

### 조치: @layer reset부터 순서대로 PR 네 개

기본값을 먼저 CSS 캐스케이드 레이어(`@layer reset`)로 옮기면, 레이어 안의 규칙은 레이어 밖의 규칙보다 우선순위가 낮아져 명시도와 상관없이 버튼 클래스가 적용된다. 그 뒤로는 필요 없어진 `!important`를 삭제하기만 하면 된다. 삭제하면서 생긴 화면 차이는 변경 전후 스크린샷을 비교해 찾았다.

| 순서 | 작업                                                                     | 글                                                                                                          | PR                                                     |
| ---- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 1    | 앱 루트의 버튼·링크 기본값을 `@layer reset`으로 이동                     | [CSS @layer로 명시도와 무관하게 앱 기본값의 우선순위 낮추기](/memo/css-layer-reset)                         | [#57](https://github.com/hyeoniverse/MacFolio/pull/57) |
| 2    | 앱마다 따로 있던 메뉴 다섯 종을 `Menu`, `useDismiss`, `placement`로 통합 | [placement·useDismiss·Menu 세 모듈로 중복된 메뉴 구현 합치기](/memo/shared-menu)                            | [#59](https://github.com/hyeoniverse/MacFolio/pull/59) |
| 3    | `!important`를 삭제하고 아이콘 버튼을 `IconButton`으로 통합              | [계산된 스타일 비교로 !important를 일괄 삭제하고 IconButton·Button 공통 버튼 추출하기](/memo/shared-button) | [#60](https://github.com/hyeoniverse/MacFolio/pull/60) |

남은 `!important`는 동작 줄이기(`prefers-reduced-motion`) 설정의 2개뿐이다. 사용자의 접근성 설정이 모든 애니메이션 규칙보다 우선해야 하는 경우다. 원인(명시도)을 먼저 확인하고 레이어 이동 → 메뉴 → 아이콘 버튼 → 글자 버튼 순서로 진행해 되돌린 커밋은 0개였다. 이 작업은 이슈 [#15](https://github.com/hyeoniverse/MacFolio/issues/15)(기능·UI 개선과 리팩터링)의 한 갈래이고, 같은 날 연 [#58](https://github.com/hyeoniverse/MacFolio/pull/58)은 범위를 다시 나눠 [#59](https://github.com/hyeoniverse/MacFolio/pull/59)로 제출했다.

## 메시지·댓글의 방문자 쿠키

### 이름·비밀번호 입력 칸 제거

10월 2일 오후, 휴대폰 메시지 화면의 이름·비밀번호 입력 칸을 네 번(15:49, 16:06, 18:06, 19:09) 수정했다. 입력창과 높이·간격을 맞췄지만, 두 칸이 본문 입력창보다 더 눈에 띄었다. 19:36에 입력 칸 자체를 제거했다. ==문제는 칸의 모양이 아니라 칸이 존재한다는 것이었다.==

입력 칸이 필요했던 이유는 하나다. 작성자가 나중에 자기 글을 삭제하려면 누가 썼는지 식별해야 한다. 이 목적이라면 사용자 입력이 아니어도 된다.

| 항목           | 변경 전                          | 변경 후                                      |
| -------------- | -------------------------------- | -------------------------------------------- |
| 작성자 식별    | 사용자가 입력한 이름·비밀번호    | 서버가 처음 방문한 브라우저에 발급하는 쿠키  |
| 표시 이름      | 입력한 이름                      | 쿠키 값으로 정하는 이름 (예: "🦊 날쌘 여우") |
| 같은 사람 판별 | 같은 이름·비밀번호를 입력해야 함 | 같은 브라우저면 언제 방문해도 같은 이름      |
| 자기 글 삭제   | 비밀번호 입력                    | 작성한 브라우저에서 삭제                     |

자세한 구조는 [httpOnly 방문자 쿠키의 HMAC 해시로 가입 없이 방문자 식별하기](/memo/visitor-identity)에 정리했다([#70](https://github.com/hyeoniverse/MacFolio/pull/70)). 메시지도 이때 처음 서버에 저장하게 해서 이슈 [#9](https://github.com/hyeoniverse/MacFolio/issues/9)의 남은 항목 하나를 완료했다. 같은 화면에서 안내 문구와 빈 카드, "방문자 (나) ›" 캡슐의 간격을 넓히고, "누구나 답글을 달 수 있어요"처럼 정보가 없는 안내 문구는 삭제했다.

### 서버 미배포 상태의 오류와 PR 순서

- **서버 미배포 상태:** 머지 후 메모에 댓글을 작성해 보니 "이름을 입력해 주세요", "비밀번호는 4~20자로…" 오류만 표시되고 입력 칸은 없었다. 프론트엔드는 새 코드인데 서버는 아직 이전 코드였기 때문이다. 서버가 응답하지 않으면 메시지는 조회도 작성도 할 수 없으므로, 오류 문구를 수정하는 대신 앱을 여는 단계에서 차단했다([첫 요청 실패와 사용 중 연결 끊김을 구분하는 메시지 앱 오류 처리](/memo/messages-offline), [#73](https://github.com/hyeoniverse/MacFolio/pull/73)). 개발 모드에서는 `.env` 설정으로 이 화면을 확인할 수 있게 하고, "서버에 연결할 수 없습니다" 문구가 표시될 때 레이아웃이 이동하지 않게 했다
- **PR 순서:** UI 작업(#69)을 끝내기 전에 쿠키 작업을 새 브랜치로 시작했고, 계획 단계였던 #70을 충분히 확인하지 않고 머지했다. GitHub의 머지 기록은 삭제할 수 없어 이력에 남았다. 작업이 겹치면 먼저 시작한 작업을 마무리한 뒤 나중 작업을 리베이스한다

## 개발 규칙과 시험

### 브랜치·커밋 규칙의 CI 검사 (9월 30일~10월 1일)

브랜치·커밋·PR 규칙이 문서화되어 있지 않았다. 지금까지 사용한 형식을 규칙으로 정리하고 PR마다 CI가 검사하게 했고, 10월 1일 아침에는 main 브랜치에 필수 검사(Ruleset)를 설정해 검사를 통과하지 않은 PR은 머지할 수 없게 했다. 문서로만 적은 규칙은 지켜지지 않을 때 알려 주는 장치가 없기 때문이다([정규식 검사 워크플로와 Rulesets로 커밋·PR 규칙을 CI에서 강제하기](/memo/commit-conventions-ci), [#48](https://github.com/hyeoniverse/MacFolio/pull/48), [#53](https://github.com/hyeoniverse/MacFolio/pull/53)).

### 레이아웃에 따라 실패한 끌기 E2E

이미지만 추가한 PR에서 E2E가 실패했다. 코드는 변경하지 않았는데 이미지 드래그 테스트가 실패했고, 확인해 보니 `main`에서도 특정 조건에서 실패하는 불안정한 테스트였다([이미지 로드 전 좌표와 누락된 dragover로 흔들린 끌기 E2E](/memo/flaky-drag-e2e), [#51](https://github.com/hyeoniverse/MacFolio/pull/51)). 같은 날 글이 늘어나자 글 순서에 의존하던 테스트도 실패해서, 순서에 의존하지 않게 수정했다. 좌표를 측정하는 테스트는 글 한 편, 이미지 하나에도 결과가 달라지므로 측정 전에 완료되어야 하는 조건(이미지 로드, 스크롤)을 먼저 정의해야 한다.

새 기능마다 가짜 API로 관리자 로그인 상태를 만들고 클릭·드래그를 수행하는 E2E를 추가했다. 같은 가짜 API로 화면 상태를 구성해 Playwright로 스크린샷을 생성하는 방법도 이때 만들었다([Playwright와 E2E 가짜 API로 블로그 스크린샷 생성하기](/memo/screenshots-with-playwright), [#47](https://github.com/hyeoniverse/MacFolio/pull/47)).

## 돌아보며

**원인부터 확인한 작업은 되돌린 커밋이 없었다.** 공통 컴포넌트는 명시도라는 원인을 먼저 확인하고 순서를 정해 PR 네 개로 진행했다. 배포 구조도 빌드 실패 하나를 계기로 시험과 배포의 관계를 확인해, 시험이 실패한 커밋이 사이트에 배포되지 않게 했다.

**화면을 보면서 결정한 작업은 같은 결정을 여러 번 되돌렸다.** 메시지 입력 칸은 네 번, 최근 삭제된 항목의 안내 상자는 세 번, 저장소 선택 화면은 21분에 세 번, 새싹 농장 아이콘은 20분에 네 번 바뀌었다. 모두 참고할 실제 화면(macOS·iOS)이나 "이 요소가 왜 필요한가"를 먼저 정하지 않고 구현을 시작한 경우이고, 되돌린 커밋은 23시~새벽 5시에 몰려 있었다. ==UI를 바꿀 때는 참고 화면과 요소의 목적을 먼저 확정한다.==

**서버 반영이 아직 수동이었다.** 실행 위치를 틀리는 오류가 이틀 연속 발생했고, 프론트엔드만 먼저 배포되어 서버와 맞지 않는 오류 문구가 표시되기도 했다. 다음 주에는 main에 머지하면 GitHub Actions가 API 이미지를 빌드해 배포하고, Postgres를 매일 백업해 서버 외부에 보관하는 작업이 이어졌다.
