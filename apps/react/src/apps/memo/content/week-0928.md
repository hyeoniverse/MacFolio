## 시험과 CI를 기능보다 먼저

CI(Continuous Integration)는 커밋을 push할 때마다 서버가 빌드와 시험을 자동으로 실행해 결과를 기록하는 체계다. 이 저장소는 GitHub Actions에서 실행한다. E2E(End-to-End) 시험은 실제 브라우저를 띄워 사용자처럼 창을 열고 버튼을 눌러 화면 결과를 확인하는 시험이고, Playwright로 작성한다.

9월 28일에는 Firebase를 제거해 호스팅을 Cloudflare Workers로 옮기고, pnpm workspaces와 Turborepo로 모노레포를 구성했다. 모노레포는 화면 앱과 서버, 공용 패키지를 저장소 하나에 보관하는 구조다. 이어서 ESLint·Prettier, Playwright E2E, GitHub Actions CI를 함께 도입했고([#26](https://github.com/hyeoniverse/MacFolio/pull/26)), 처음 실행한 시험에서 음악 창을 닫으면 Dock까지 화면 전체가 사라지는 버그를 찾았다.

창 위치·크기와 쌓임 순서 계산은 순수 함수로 분리해 Vitest로 검증했다. 순수 함수는 같은 입력에 항상 같은 값을 반환하므로, 예를 들어 "창 세 개 중 두 번째를 클릭하면 그 창이 맨 위가 된다"를 브라우저 없이 확인할 수 있다. 앱 하나에서 렌더링 오류가 발생해도 화면 전체가 멈추지 않게 React Error Boundary를 추가했다. ==E2E는 이날 0개에서 78개가 되었고, 주 마지막 날에는 204개였다.== 같은 날 메모·메시지 앱을 여러 번 다시 작성하는 동안 이 시험이 회귀를 먼저 검출했고, 다음 날 API 서버를 같은 저장소에 추가했다.

## API 서버와 관리자 로그인, 인바운드 포트 없는 배포

9월 29일 저녁에 NestJS + Prisma + PostgreSQL로 API 서버를 만들었다. 관리자 로그인은 GitHub OAuth로 구현했다. OAuth는 사이트가 비밀번호를 직접 받지 않고 GitHub이 사용자를 확인한 결과만 넘겨받는 인가 규격이다. 로그인에 성공하면 DB에 세션을 저장하고, 관리자 경로는 `AdminGuard`가 그 세션을 확인한 뒤에만 통과시킨다.

제목·날짜·폴더·본문 같은 필수 항목은 세 계층에서 검증한다. 화면의 입력 검사만 있으면 `curl`로 API를 직접 호출하는 요청을 막지 못하고, API 검증만 있으면 서버 코드의 버그나 직접 실행한 SQL을 막지 못하기 때문이다.

![제목이 빈 글을 화면, API, DB 세 계층이 각각 거부하는 위치](./images/week-0928-validation-layers.svg '같은 규칙을 세 계층에 둔 이유. 앞 계층을 거치지 않는 요청은 다음 계층에서 거부된다')

로그인은 처음에 관리자 여부를 변경 가능한 GitHub 아이디(`login`)로 판단했다. 이 방식에서는 관리자가 아이디를 바꾸면, 이전 아이디를 새로 등록한 다른 사람이 관리자가 될 수 있다. 세 시간 만에 ==판단 기준을 바뀌지 않는 숫자 ID로 바꾸고==, 로그인 요청에 IP별 횟수 제한을 적용했다.

9월 30일에는 Oracle Cloud Always Free VM에서 Postgres·API·cloudflared를 docker compose로 실행하고, SSH 외에는 인바운드 포트를 열지 않았다. 인바운드 포트는 외부에서 서버로 들어오는 연결을 받는 포트다. 대신 VM의 cloudflared가 Cloudflare로 나가는 연결(Cloudflare Tunnel)을 먼저 만들고, 외부 요청은 이미 열려 있는 그 연결을 통해 들어온다.

![nginx 구성은 80·443 인바운드를 열고, 터널 구성은 cloudflared가 아웃바운드 연결을 먼저 만들어 그 연결로 요청을 받는다](./images/deploy-api-oracle-tunnel-inbound-outbound.svg '두 구성의 연결 방향 비교. 터널 구성은 방화벽에 웹 포트를 열지 않는다')

가장 오래 걸린 문제는 환경 변수의 적용 시점이었다. Vite는 `VITE_API_URL`을 빌드할 때 번들 코드에 문자열로 넣는데, 이 값을 Cloudflare의 런타임 변수로 등록해서 빌드된 사이트가 API 주소를 읽지 못했다.

![로그인된 계정 화면](./images/admin-signed-in.jpg '배포 환경에서 로그인한 뒤의 시스템 설정 → 계정')

## @layer로 !important 72개 정리

CSS는 한 요소에 여러 규칙이 걸리면 명시도(specificity)로 우선순위를 정한다. 명시도는 선택자에 든 ID, 클래스, 태그의 개수이고 `(ID, 클래스, 태그)` 순서로 비교한다. `!important`는 이 비교를 무시하고 규칙을 강제로 적용하는 표시라서, 한 번 쓰면 그 규칙을 덮으려는 다음 규칙에도 `!important`가 필요해진다.

10월 1일에 집계해 보니 코드에 `!important`가 72개 있었다. 버튼 색이나 아이콘 크기가 적용되지 않을 때마다 하나씩 추가한 것이다. 원인은 하나였다. 앱 루트의 기본값 `.memo button`(명시도 0,1,1)이 버튼 클래스 `.memo-copy-button`(0,1,0)보다 명시도가 높았다. `@layer`는 규칙을 이름 있는 묶음(레이어)에 넣는 문법이고, 브라우저는 레이어 순서를 명시도보다 먼저 비교한다. 레이어에 넣지 않은 규칙은 모든 레이어보다 우선한다. 그래서 기본값을 `@layer reset`으로 옮기면, 그 뒤로는 `!important`를 삭제하기만 하면 된다.

![@layer 전후의 우선순위 비교](./images/week-0928-specificity.svg '전에는 태그 하나만큼 명시도가 높은 기본값이 이겼다. 기본값을 레이어에 넣자 레이어 밖의 버튼 클래스가 명시도와 관계없이 적용된다')

작업은 레이어 이동([#57](https://github.com/hyeoniverse/MacFolio/pull/57)), 메뉴 다섯 종을 `Menu`·`useDismiss`·`placement`로 통합([#59](https://github.com/hyeoniverse/MacFolio/pull/59)), `IconButton` 통합과 `!important` 삭제([#60](https://github.com/hyeoniverse/MacFolio/pull/60)), `Button` 통합([#61](https://github.com/hyeoniverse/MacFolio/pull/61)) 순서로 나눴다. 남은 `!important`는 `prefers-reduced-motion`용 2개뿐이고, ==원인을 먼저 확인하고 순서대로 진행해 되돌린 커밋이 0개==였다.

## 이름·비밀번호 칸 대신 방문자 쿠키

10월 2일에는 휴대폰 메시지 화면의 이름·비밀번호 입력 칸을 네 번 고쳤지만, 여전히 본문 입력창보다 눈에 띄었다. 칸이 필요했던 이유는 작성자가 나중에 자기 글을 삭제할 수 있도록 작성자를 식별하는 것 하나였고, 이 목적에는 사용자 입력이 필요하지 않았다.

그래서 칸을 없애고, 서버가 처음 방문한 브라우저에 httpOnly 쿠키를 발급하게 했다. httpOnly 쿠키는 브라우저가 요청마다 서버로 보내지만 페이지의 JavaScript는 읽을 수 없는 쿠키라, 페이지에 주입된 스크립트가 값을 가져가지 못한다. 서버는 쿠키 값 원문 대신 HMAC만 저장한다. HMAC은 서버만 아는 비밀 키와 값을 함께 해시한 결과라서, DB가 유출되어도 원래 쿠키 값을 복원하거나 다른 방문자를 흉내 낼 수 없다.

표시 이름("🦊 날쌘 여우")도 쿠키 값으로 정한다. 같은 브라우저면 언제 방문해도 같은 이름이 되고, 작성한 브라우저에서 자기 글을 삭제할 수 있다.

메시지도 이때 처음 서버에 저장했다. 프론트엔드만 먼저 배포된 상태에서 이전 서버가 "이름을 입력해 주세요" 오류를 반환한 일을 겪고, 서버에 연결할 수 없으면 메시지 앱을 여는 단계에서 차단하게 했다.

## 시험을 통과한 커밋만 배포

![Cloudflare Workers 사용량](./images/day-1003-workers-usage.jpg '빌드 실패 시각에 확인한 Workers 사용량. 빌드 시간 150/3,000분으로 한도와 관계없었다')

10월 3일, PR [#80](https://github.com/hyeoniverse/MacFolio/pull/80)의 `Workers Builds` 검사가 `Build failed to initialize and was timed out`으로 실패했다. 사용량은 이번 달 빌드 시간 3,000분 중 150분이어서, 한도가 아니라 Cloudflare 측 빌드 환경 문제였다.

이를 검토하다가 더 큰 구조 문제를 찾았다. 시험(GitHub Actions)과 배포(Cloudflare Workers Builds)가 같은 push를 각자 받아 독립적으로 실행되어, ==시험이 실패한 커밋도 사이트에 배포될 수 있었다.==

배포용 API 토큰을 새로 발급하고 Cloudflare의 Git 연결을 해제한 뒤, GitHub Actions에서 wrangler로 배포하게 했다([#82](https://github.com/hyeoniverse/MacFolio/pull/82)). GitHub Actions의 `needs`는 한 작업(job)이 다른 작업의 성공을 기다린 뒤 시작하게 하는 설정이다. 배포 작업에 `needs`로 시험 작업을 지정해, 시험이 실패하면 배포 작업은 실행되지 않는다. 이틀 뒤 API 자동 배포도 같은 구조로 만들었다.

![시험이 실패한 커밋의 처리 전후](./images/week-0928-deploy-gate.svg '전에는 두 실행이 서로의 결과를 확인하지 않았다. 후에는 배포 작업이 시험 작업의 성공을 기다린다')

| 항목               | 변경 전 (Cloudflare Git 연결)  | 변경 후 (GitHub Actions)                   |
| ------------------ | ------------------------------ | ------------------------------------------ |
| 시험과의 관계      | 시험 결과와 관계없이 빌드·배포 | 배포 작업은 시험 작업이 통과한 뒤에만 실행 |
| 시험이 실패한 커밋 | 배포될 수 있음                 | 배포되지 않음                              |
