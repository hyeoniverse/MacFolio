## 들어가기 전에

TCP는 신뢰성 있는 바이트 스트림을 보장하려고 연결 상태, 시퀀스 번호, 수신 창 같은 정보를 양쪽 커널에 보관한다. 이 상태 정보는 성능과 신뢰성의 바탕이면서 동시에 공격 표면이기도 하다. 서버가 아직 완성되지 않은 연결 정보를 큐에 쌓아 두는 설계는 정상 동작에 필요하지만, 공격자가 그 큐를 의도적으로 가득 채우면 정상 사용자가 연결하지 못한다.

구체적인 예로 텔넷 서버 하나를 생각한다. 공격자는 서버에 부하를 줄 만큼 트래픽을 보낼 자원이 없어도, 핸드셰이크를 끝까지 마치지 않는 SYN 패킷만 빠르게 보내 서버의 half-open 연결 큐를 포화시킬 수 있다. 서버의 CPU는 한가한데도 새 텔넷 연결만 받지 못한다. 자원이 부족한 공격자가 서버의 약점에 자원을 집중한 전형적인 서비스 거부(DoS, denial of service) 사례다.

이 글이 답하려는 질문은 두 가지다. TCP의 어떤 상태와 필드가 공격에 악용되는가, 그리고 각 공격을 프로토콜 수준에서 어떻게 막는가.

## TCP 헤더와 시퀀스 번호

TCP 세그먼트는 헤더와 데이터로 이루어진다. 헤더는 출발지·목적지 포트(각 16비트), 시퀀스 번호(32비트), 확인 응답 번호(32비트), 헤더 길이(4비트), 예약(6비트), 코드 비트(6비트: URG, ACK, PSH, RST, SYN, FIN), 윈도우 크기(16비트), 체크섬(16비트), 긴급 포인터(16비트), 그리고 가변 길이 옵션으로 구성된다.

![TCP 헤더 필드 구조: 출발지·목적지 포트, 시퀀스 번호, 확인 응답 번호, 헤더 길이, 예약, 플래그 6비트, 윈도우 크기, 체크섬, 긴급 포인터, 옵션](./images/net-tcp-attacks-header.svg '32비트 단위로 배치된 TCP 헤더 필드')

==시퀀스 번호는 세그먼트가 담은 데이터의 첫 옥텟(octet) 번호를 가리키며, SYN 비트가 켜져 있으면 초기 시퀀스 번호(ISN, initial sequence number)를 뜻한다.== 각 옥텟은 고유한 시퀀스 번호를 가지고, 수신 측은 이 번호로 수신 버퍼 안에서 순서를 맞춘다. 확인 응답 번호는 수신 측이 다음에 받기를 기대하는 시퀀스 번호다.

연결이 설정되면 커널은 송신·수신 버퍼를 할당한다. 응용 프로그램은 패킷을 직접 만들지 않고 버퍼에 쓰기만 하고, TCP가 세그먼트로 나눠 보낸다. 수신 버퍼에 도착한 패킷은 순서대로 정렬된 뒤 경계 없는 바이트 스트림으로 응용에 전달된다.

![TCP 송신·수신 버퍼: 클라이언트 응용이 송신 버퍼에 쓴 데이터가 TCP·IP 계층을 거쳐 전송되고, 순서가 바뀌어 도착한 패킷을 서버의 수신 버퍼에서 재정렬](./images/net-tcp-attacks-buffers.svg '응용은 버퍼에 쓰고, 재정렬은 수신 측 TCP가 담당한다')

시퀀스 번호와 확인 응답 번호의 관계를 작은 예로 확인한다. 어떤 세그먼트의 첫 옥텟 시퀀스 번호가 `x{:math}`이고 그 세그먼트가 100옥텟을 싣는다면, 수신 측은 `x`부터 `x+99`까지 받은 것이므로 다음에 기대하는 번호, 즉 확인 응답 번호는 `x+100{:math}`이 된다.

> [!NOTE] 핸드셰이크에서의 시퀀스 번호
> SYN과 FIN 비트는 데이터가 없어도 시퀀스 번호를 하나 소비한다. 그래서 초기 SYN의 시퀀스 번호가 `x{:math}`이면 상대는 `x+1{:math}`을 확인 응답 번호로 돌려준다.

## SYN 플러딩

3-방향 핸드셰이크는 세 패킷으로 이루어진다. 클라이언트가 무작위 초기 시퀀스 번호 `x{:math}`를 담아 SYN을 보내고, 서버가 자신의 무작위 번호 `y{:math}`와 `ack = x+1{:math}`을 담아 SYN+ACK로 답하며, 클라이언트가 `ack = y+1{:math}`로 ACK를 보내 핸드셰이크를 마친다.

![3-방향 핸드셰이크 시퀀스와 서버의 TCB 저장·제거 과정](./images/net-tcp-attacks-handshake.svg '서버는 SYN을 받으면 TCB를 큐에 보관하고, 마지막 ACK를 받으면 제거한다')

서버는 초기 SYN을 받으면 연결 정보를 담은 전송 제어 블록(TCB, transmission control block)을 만들어 half-open 연결 큐에 보관한다. 이 시점의 연결은 클라이언트에서 서버 방향만 열린 half-open 상태다. 서버는 클라이언트의 ACK가 도착하면 TCB를 큐에서 제거하고, ACK가 오지 않으면 SYN+ACK를 재전송하다가 시간 초과(time-out) 시 TCB를 버린다.

SYN 플러딩은 이 큐를 노린다. 공격자가 SYN 패킷만 계속 보내 TCB 레코드를 큐에 쌓되 핸드셰이크의 세 번째 단계를 완료하지 않으면, 큐가 가득 차 서버는 새 SYN을 받아들일 공간을 잃는다.

![SYN 플러딩: 공격자 A가 보낸 다수의 위조 SYN마다 서버 B가 IP/포트·MSS 상태를 쌓아 메모리가 소진되고, 정상 호스트 C의 SYN이 거부되는 시퀀스](./images/net-tcp-attacks-synflood.svg 'TCB가 쌓여 half-open 큐가 포화되면 정상 SYN이 거부된다')

TCB가 큐에서 빠지는 조건은 세 가지다. 핸드셰이크를 정상적으로 마치거나, 시간 초과까지 큐에 머물거나, 해당 half-open 연결에 대한 RST 패킷을 받는 경우다. 공격자가 효과를 보려면 이 세 경로로 TCB가 빠지는 속도보다 빠르게 큐를 채워야 한다.

출발지 IP는 무작위로 위조한다. 위조하지 않으면 서버의 SYN+ACK가 공격자에게 되돌아오고, 공격자의 커널이 알지 못하는 연결이므로 RST로 응답해 TCB가 큐에서 빠진다. 또한 실재하는 주소로 위조하면 그 호스트가 RST를 보내 역시 TCB가 빠진다. 무작위 주소 대부분은 응답할 기기가 없어 TCB가 큐에 남는다.

위조 SYN 패킷은 출발지 IP와 포트, 시퀀스 번호를 매번 무작위로 채우고 SYN 비트만 세운 형태다. 위조한 주소 중 실재하는 호스트가 돌려보내는 RST가 큐에서 TCB를 다시 빼므로, 공격이 성립하려면 단위 시간당 들어오는 SYN 수가 되돌아오는 RST 수를 크게 웃돌아야 한다. 이 속도 조건이 핵심이어서, 느린 전송으로는 되돌아오는 RST에 밀려 큐를 채우지 못한다.

### SYN 쿠키 방어

큐 크기를 늘리거나 시간 초과를 줄이는 방법은 근본 해결책이 아니다. 핸드셰이크가 끝난 연결만 저장해 큐 자체를 없애는 방법도, SYN 요청을 저장하지 않으면 도착한 ACK의 유효성을 검증할 수 없어 위조 ACK로 Accept 큐를 채우는 ACK 플러딩에 다시 뚫린다.

표준 방어는 SYN 쿠키(SYN cookie)다. 서버는 SYN을 받으면 큐에 상태를 저장하는 대신, 패킷의 정보(IP 주소, 포트 번호)와 서버만 아는 비밀 키로 계산한 키 해시 `H{:math}`를 초기 시퀀스 번호로 돌려보낸다. 이 `H{:math}`가 SYN 쿠키다. half-open 연결을 큐에 저장하지 않으므로 큐가 포화될 수 없다.

![SYN 쿠키: SYN+ACK의 시퀀스 번호를 f(data)로 만들고, 32비트를 5비트 느리게 바뀌는 타임스탬프, 3비트 MSS, 24비트 보안 해시로 구성](./images/net-tcp-attacks-syncookie.svg '연결에 필요한 상태를 시퀀스 번호 안에 담는다')

정상 클라이언트는 `H+1{:math}`을 확인 응답 번호로 보낸다. 서버는 돌아온 ACK의 번호로 쿠키를 다시 계산해 유효성을 검증하고, 맞으면 그때 연결 상태를 복원한다. 공격자는 위조한 출발지로 보냈으므로 `H{:math}`를 받지 못해 올바른 ACK를 만들 수 없다. 리눅스와 FreeBSD의 표준 기능이고, 우분투에서는 기본으로 켜져 있다.

> [!TIP] SYN 쿠키의 비용
> 32비트 시퀀스 번호 안에 상태를 압축하므로 연결 정보를 완전히 담을 수는 없다. 그래서 SYN 쿠키는 큐가 포화되는 상황에서만 발동하도록 구현하는 경우가 많다. 자세한 완화 방안은 RFC 4987에 정리돼 있다.[^rfc4987]

## TCP 리셋 공격

RST 비트가 켜진 패킷 하나는 "네가 말하는 연결을 나는 모르니 지역 상태를 모두 삭제하라"는 뜻이다. 정상 종료가 FIN·ACK를 주고받는 4-방향(또는 3-방향) 절차인 것과 달리, 한쪽이 RST를 보내면 연결이 즉시 끊긴다.

![TCP 연결 종료 방식: 4-방향 FIN 종료, 3-방향 종료, RST를 이용한 즉시 종료](./images/net-tcp-attacks-close.svg 'RST는 핸드셰이크 없이 연결을 끊는다')

리셋 공격은 통신 중인 A와 B 사이에 위조 RST 패킷을 끼워 넣어 연결을 강제로 끊는다. 공격자는 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트, 그리고 수신 창 안에 드는 시퀀스 번호를 올바르게 맞춰야 한다. 중간자(MITM) 위치나 스니퍼로 트래픽을 가로채면 이 값들을 알아낼 수 있다.

![위조 RST 패킷으로 established 연결을 끊는 구조: 공격자가 스니핑 후 RST를 스푸핑](./images/net-tcp-attacks-rst.svg '올바른 네 튜플과 시퀀스 번호를 맞춘 RST 한 개로 연결이 끊긴다')

스니핑으로 네 튜플과 시퀀스 번호를 얻으면, 같은 값들을 채우고 RST 플래그만 세운 위조 패킷 하나로 연결을 끊을 수 있다. 암호화 계층의 위치가 공격 성패를 가른다. 네트워크 계층에서 암호화하는 IPsec은 TCP 헤더까지 암호화하므로 스니핑과 스푸핑이 어렵다. 반면 SSH는 전송 계층에서 암호화하므로 TCP 헤더는 평문으로 남고, RST 패킷에는 헤더만 필요하므로 공격이 성립한다.

### 시퀀스 번호 추측

공격의 성패는 시퀀스 번호에 매우 민감하다. 위조 패킷에 넣는 번호는 서버가 기다리는 수신 창 안에 들어야 한다. 수신 창은 `RCV.NXT{:math}`부터 `RCV.NXT + RCV.WND - 1{:math}`까지다. 너무 작으면 무시되고, 창을 벗어나게 크면 수신 측이 버린다.

![수신 측 슬라이딩 윈도우: 수신·확인 완료 영역, RCV.NXT부터 RCV.WND만큼의 수신 창, 수신 불가 영역과 창 안에 주입된 데이터의 위치](./images/net-tcp-attacks-window.svg '위조 패킷의 시퀀스 번호는 수신 창 안에 들어야 유효하다')

스니핑이 불가능해도 수신 창 크기로 필요한 시도 횟수를 어림할 수 있다. 전체 시퀀스 공간은 `2^{32}{:math}`이고, 창 하나가 그 공간을 덮는 비율이 성공 확률이므로 필요한 추측 수는 대략 `2^{32} / \text{RCV.WND}{:math}`다. 리눅스의 수신 버퍼 기본값은 `cat /proc/sys/net/ipv4/tcp_rmem{:bash}`으로 확인한다(최소·기본·최대). 최대 창 3,493,888바이트라면 다음과 같다.

```math
\frac{2^{32}}{3493888} = \frac{4294967296}{3493888} \approx 1229
```

기본 창 87,380바이트라면 약 49,153번이다. 두 경우 모두 각각 1,500번, 50,000번 안에 든다. 즉 큰 수신 창을 쓰는 시스템일수록 적은 수의 위조 패킷으로 창 안에 드는 번호를 맞힐 수 있다.

<details>
<summary>49,153을 직접 계산</summary>

`2^{32} = 4{,}294{,}967{,}296{:math}`을 기본 창 87,380으로 나눈다.

```math
\frac{4294967296}{87380} \approx 49152.7
```

올림하면 49,153번이고, 이는 50,000보다 작다. 창이 넓을수록(최대 창) 1,229번으로 줄어든다.[^watson]

</details>

## TCP 세션 하이재킹

리셋이 연결을 끊는다면 세션 하이재킹은 established 연결에 데이터를 주입한다. 공격자는 리셋과 같은 네 튜플에 더해 수신 창 안의 시퀀스 번호를 맞춘 위조 패킷을 보낸다. 수신 측이 시퀀스 번호 `x{:math}`까지 받았다면 다음 기대 번호는 `x+1{:math}`이다. 위조 패킷이 `x+\delta{:math}`를 쓰면 순서가 어긋나 수신 버퍼의 `x+\delta{:math}` 위치에 저장되고, `\delta{:math}`가 너무 크면 창을 벗어나 버려진다.

![세션 하이재킹: 공격자가 클라이언트와 같은 출발지·목적지 IP와 포트로 위조 TCP 패킷을 보내, 서버 수신 버퍼의 x+δ 위치에 데이터를 주입하는 구조](./images/net-tcp-attacks-hijack.svg '같은 네 튜플과 창 안의 시퀀스 번호로 데이터를 주입한다')

텔넷 연결을 하이재킹하면 공격자가 서버에서 실행될 명령을 주입할 수 있다. 단순히 파일 내용을 출력하는 명령은 결과가 서버 화면에만 나오므로, 공격자는 출력을 자신이 대기하는 원격 포트로 돌리는 명령을 주입해 비밀 파일을 빼내거나, 서버의 셸 입출력을 자신이 통제하는 연결에 묶는 역방향 셸(reverse shell)을 띄운다.

> [!CAUTION] 역방향 셸이 위험한 이유
> 역방향 셸은 서버의 표준 입력·출력·오류를 공격자 쪽 TCP 연결에 묶어, 공격자가 방화벽 너머의 피해 호스트를 원격에서 조종하게 한다. 피해 호스트가 바깥으로 연결을 여는 형태라 인바운드만 막는 방화벽을 우회한다. 해킹에서 널리 쓰이는 기법이므로 아웃바운드 연결 제어와 셸 실행 감시가 중요하다.

세션 하이재킹 방어는 공격자가 패킷을 위조하기 어렵게 만드는 것이다. 출발지 포트와 초기 시퀀스 번호를 무작위로 만들면 추측이 어려워지지만, 같은 네트워크에서 스니핑하는 지역 공격에는 효과가 없다. 근본 방어는 페이로드 암호화다. IPsec으로 네트워크 계층에서 암호화하면 공격자가 시퀀스 번호와 데이터를 모두 볼 수 없다.

## FIN-WAIT2 플러딩

연결 종료 과정에도 약점이 있다. TCP는 FIN_WAIT2 상태에 머무는 시간에 제한을 두지 않는다. 공격자가 서버와 다수의 연결을 맺고 서버가 연결을 닫게 한 뒤 그대로 방치하면, 응용은 이미 연결을 끝냈어도 커널의 TCP 스택에 상태가 남아 메모리 소진 공격이 된다.

![정상 TCP 종료와 LAST_ACK를 건너뛰어 FIN_WAIT2에 머무는 비정상 종료의 상태 전이](./images/net-tcp-attacks-finwait2.svg '마지막 FIN을 보내지 않으면 상태가 커널에 남는다')

방어는 상태에 제한을 두는 것이다. FIN_WAIT2 상태의 지속 시간을 제한해 FIN이 오지 않으면 연결을 중단하고, 제어 프로세스 없는 연결 수나 동시 연결 수의 상한을 둔다.

## TCP 증폭 공격

증폭(amplification) DDoS는 보통 UDP 기반으로 논의되지만 TCP도 취약하다. 공격자가 피해자의 주소로 출발지를 위조해 증폭기(amplifier)에 SYN을 보내면, 증폭기는 피해자에게 SYN+ACK로 답한다. 피해자는 그 연결을 모르므로 ACK를 보내지 않고, 증폭기는 ACK가 올 때까지 SYN+ACK를 반복 재전송한다. 작은 SYN 하나가 여러 SYN+ACK로 증폭돼 피해자에게 쏟아진다.

![TCP 반사 공격: 증폭기가 피해자에게 SYN/ACK를 반복 전송하는 두 가지 동작과, 위조 SYN이 여러 증폭기를 거쳐 피해자 네트워크의 할당·미할당 IP로 반사되는 구성](./images/net-tcp-attacks-amplifier.svg 'ACK가 오지 않으면 증폭기가 SYN+ACK를 거듭 재전송한다')

증폭 계수는 프로토콜마다 다르다. 재전송이 많은 서비스일수록 계수가 크다. 다음 표는 SYN 하나에 대해 경과 시간별로 돌아오는 SYN/ACK 수다.

| 프로토콜 | 10초 이내 | 30초 이내 | 60초 이내 |
| -------- | --------: | --------: | --------: |
| FTP      |         2 |         5 |        10 |
| HTTP     |         2 |         6 |        11 |
| NetBIOS  |         8 |        17 |        22 |
| SIP      |         2 |         6 |        12 |
| SSH      |         3 |         6 |        11 |
| Telnet   |         2 |         5 |        10 |

방어의 핵심은 출발지 주소 위조를 막는 진입 필터링(ingress filtering)과 반사에 악용될 수 있는 서비스의 재전송 정책 조정이다.

## TCP 낙관적 ACK 공격

낙관적 ACK(optimistic ACK) 공격은 혼잡 제어를 역이용한다. TCP 혼잡 제어는 전송이 성공할수록 한 번에 보내는 양을 늘린다. 수신자가 아직 받지 않은 데이터까지 미리 "낙관적으로" ACK하면, 송신자는 손실이 없다고 착각해 전송 속도를 계속 높인다.

![받지 않은 데이터를 미리 ACK하는 수신자와, 뉴 리노(New Reno) 혼잡 제어 상태 기계: 슬로 스타트, 혼잡 회피, 지수 백오프, 빠른 회복 사이의 전이](./images/net-tcp-attacks-newreno.svg '받지 않은 데이터를 ACK하면 송신자가 전송률을 계속 올린다')

이 공격의 증폭 계수는 최대 윈도우 크기와 MSS(maximum segment size)로 정해진다. 피해자가 ACK 하나당 보내는 최대 바이트 수는 `(\text{최대 윈도우} / \text{MSS}){:math}`개의 패킷에 패킷당 `(14 + 40 + \text{MSS}){:math}`바이트를 곱한 값이다. 여기서 14는 이더넷, 40은 IP·TCP 헤더 바이트다. 공격자가 보내는 ACK 하나는 `14 + 40 = 54{:math}`바이트다. 따라서 증폭 계수는 다음과 같이 정리된다.

```math
\frac{\text{최대 윈도우}}{\text{MSS}} \cdot \frac{14 + 40 + \text{MSS}}{54}
= \text{최대 윈도우} \cdot \left(\frac{1}{\text{MSS}} + \frac{1}{54}\right)
```

기본 최대 윈도우 65,536, 기본 MSS 536을 넣으면 다음과 같다.

```math
65536 \cdot \left(\frac{1}{536} + \frac{1}{54}\right) \approx 1336
```

윈도우 스케일링(window scaling)은 창을 최대 `2^{14}{:math}`배까지 키운다. 이를 반영하면 증폭 계수는 약 `1336 \cdot 2^{14} \approx 2.19 \times 10^{7}{:math}`, 즉 2200만 배에 이른다. MSS를 최소 88로 낮추면 약 3200만 배까지 커진다.

<details>
<summary>증폭 계수를 직접 계산</summary>

`1/536 \approx 0.0018657{:math}`, `1/54 \approx 0.0185185{:math}`이므로 합은 약 `0.0203842{:math}`다.

```math
65536 \times 0.0203842 \approx 1336.1
```

여기에 `2^{14} = 16384{:math}`를 곱하면 `1336 \times 16384 = 21{,}889{,}024{:math}`, 약 2190만이다.[^savage]

</details>

## 정리

TCP 공격은 모두 프로토콜이 보관하는 상태와 신뢰하는 필드를 노린다. SYN 플러딩은 half-open 큐를, RST·하이재킹은 시퀀스 번호와 네 튜플을, FIN-WAIT2 플러딩은 종료 상태를, 증폭·낙관적 ACK는 재전송과 혼잡 제어를 악용한다.

| 공격             | 악용 대상           | 핵심 방어                      |
| ---------------- | ------------------- | ------------------------------ |
| SYN 플러딩       | half-open 연결 큐   | SYN 쿠키                       |
| RST 리셋         | 시퀀스 번호·네 튜플 | 계층 암호화(IPsec)             |
| 세션 하이재킹    | 수신 창·시퀀스 번호 | 페이로드 암호화, 번호 무작위화 |
| FIN-WAIT2 플러딩 | 종료 상태 지속 시간 | 상태·연결 수 제한              |
| 증폭/낙관적 ACK  | 재전송·혼잡 제어    | 진입 필터링                    |

공통된 방어의 뿌리는 두 가지다. 출발지 주소 위조를 어렵게 만드는 진입 필터링과, 공격자가 헤더·데이터를 보거나 조작하지 못하게 하는 암호화다. 네트워크 경계에서 트래픽을 걸러 내는 방법은 [방화벽의 종류와 iptables 규칙](/memo/net-firewall)에서, 터널 전체를 암호화하는 방법은 [VPN과 터널링: IPsec과 TLS VPN](/memo/net-vpn)에서 이어서 다룬다.
