편집기가 동작하기 시작하자, 글을 작성하면서 불편한 기능이 하나씩 드러났다. macOS 메모와 나란히 비교하며 하나씩 맞췄다.

## 배경

9월 말에 메모 앱에서 블로그 글을 직접 작성하기 시작했다. 글을 몇 편 작성하자 다음 문제가 드러났다.

| 영역      | 문제                                                                                                           |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| 표        | 표를 삽입한 뒤 열을 추가하거나 이동하려면 Markdown 원문을 수정해야 했다. 글 맨 앞 표의 앞에는 입력할 수 없었다 |
| 찾기      | 긴 글에서 단어 하나를 바꾸려면 직접 찾아야 했다. 브라우저의 ⌘F는 편집기 내부 대치를 지원하지 않는다            |
| 검색 칸   | 관리자로 로그인하면 도구가 늘어 검색 칸이 도구 막대 밖으로 22px 넘쳐 잘렸다                                    |
| 이미지    | 삽입 후에는 캡션을 수정하기 어려웠고, 내려받기가 다른 출처의 이미지에서 동작하지 않았다                        |
| Safari 탭 | 좁은 창에서 탭이 가로로 넘쳐 스크롤해야 표시됐다                                                               |

9월 30일과 10월 1일 이틀에 걸쳐 기능마다 커밋을 나눠 수정했고, 일부는 [#55](https://github.com/hyeoniverse/MacFolio/pull/55)로 병합됐다.

## 표 핸들

커서가 표 안에 있으면 현재 열 위와 현재 행 왼쪽에 작은 둥근 핸들이 표시된다.

| 동작                                 | 결과                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------- |
| 핸들 클릭                            | 그 **열·행 전체 선택**. 핸들은 열 폭만큼 확장된 막대(⌄)가 되어 선택 테두리 위에 배치된다 |
| 막대 메뉴                            | '앞에 열 추가', '뒤에 열 추가', 'N개의 열 삭제' 등 macOS 메모와 같은 문구                |
| 선택 상태에서 **Backspace**          | 셀 내용 비우기                                                                           |
| 선택 범위의 **대각선 꼭짓점** 드래그 | 반대쪽 꼭짓점을 기준으로 범위 확장·축소                                                  |
| 선택한 행·열의 핸들 **드래그**       | 행·열 이동. 드롭 위치에 선이 표시되고, 선택 범위가 포인터를 따라온다                     |

![표 핸들로 열을 선택한 화면](./images/notes-table-handles.jpg '열 핸들을 누르면 열 전체를 선택하고, 핸들이 열 폭만큼 확장된 막대가 된다. 메뉴는 표를 가리지 않는 위치에 표시된다')

[GFM 표](https://github.github.com/gfm/#tables-extension-)는 첫 행이 항상 머리글이다. 그래서 행을 맨 위로 이동하면 표를 재구성해, 새로 첫 행이 된 행을 머리글 셀로, 밀려난 머리글을 일반 셀로 변환한다.

### 선택한 셀이 표시되지 않았다

10월 1일 저녁, 표에서 셀을 선택해도 아무 표시가 없다는 것을 발견했다. 같은 표를 macOS 메모에서 만들어 셀을 선택하니 선택 범위에 노란 테두리가 표시되고 대각선 꼭짓점에 둥근 점이 붙었다. 이 화면을 기준으로 선택 범위의 테두리와 꼭짓점을 다시 구현했다.

![macOS 메모에서 표의 첫 행을 선택한 화면](./images/notes-polish-table-selection-request.jpg '참고한 macOS 메모 화면. 선택 범위에 노란 테두리, 대각선 꼭짓점에 둥근 점이 표시된다')

수정 후 다시 사용해 보니 문제가 두 가지 더 있었다. 표 앞뒤를 눌러도 커서가 이동하지 않거나 표시되지 않았고, 표 뒤에서 Backspace로 표를 삭제할 수 없었다. 아래 두 절에서 각각의 원인과 수정을 정리한다.

### 핸들이 잘못된 위치에 표시됐다

첫 구현의 핸들은 열 위가 아니라 머리글 셀을 덮고 있었다. 계산한 위치와 렌더링된 위치가 약 13px 어긋났다. 처음에는 위치를 측정한 뒤에 레이아웃이 바뀐 것으로 추정하고 다음 프레임에 한 번 더 측정하게 했지만, 결과가 같았다.

원인은 **본문의 문단 간격 규칙**이었다. 읽기 화면과 스타일을 맞추려고 `.memo-markdown > * + * { margin-top: 0.9em }`를 지정했는데, 핸들을 편집기의 직계 자식으로 렌더링하다 보니 핸들도 '본문의 두 번째 이후 요소'에 해당해 0.9em(약 13px)의 위 여백이 적용됐다. 핸들과 테두리에 `margin: 0`을 지정해 해결했다.

### 표 앞에 커서를 놓을 수 없었다

본문 맨 앞에 삽입한 표는 앞에 문단이 없어서 표 앞에 입력할 방법이 없었다. 표 뒤에서 Backspace로 표를 삭제할 수도 없었다. 편집기의 기본 Backspace는 표 뒤의 빈 문단을 삭제하는데, 글 끝에 항상 빈 문단을 유지하는 플러그인이 그 문단을 즉시 다시 생성했다. 삭제와 재생성이 반복될 뿐이었다.

- 표·이미지 앞뒤처럼 텍스트를 입력할 수 없는 위치에도 커서([갭 커서](https://github.com/ProseMirror/prosemirror-gapcursor))를 놓는다. 첫 행에서 ↑, 마지막 행에서 ↓로 이동한다
- 표 바로 뒤 문단의 맨 앞에서 Backspace를 누르면 먼저 **표를 선택하고**, 한 번 더 누르면 삭제한다

## 글 내부 찾기·대치

⌘F를 누르면 글 위에 찾기 막대가 열린다. ‹ ›나 Enter로 검색 결과 사이를 이동하고, 편집 중에는 '대치'를 켜서 하나씩 또는 모두 바꾼다. ⌄ 메뉴에는 영문 대/소문자 무시, 순환 검색, 다음을 포함·다음으로 시작·전체 단어, 최근 검색이 있다.

![글 안에서 찾기](./images/notes-find-bar.jpg '검색 결과는 옅게, 현재 결과는 진하게 강조한다. ⌄ 메뉴에서 옵션과 최근 검색을 선택한다')

![찾기 규칙 하나, 강조 구현 두 가지](./images/notes-polish-find.svg '편집기와 읽기 화면이 같은 findInBlocks 결과를 각자 방식으로 강조한다')

찾기 규칙은 순수 함수 하나로 구현하고, 강조 표시만 두 가지로 구현했다. 이 함수는 현재 `packages/desktop-core/src/memo/find.ts`에 있다.

```ts
export function findMatches(text: string, query: string, options: FindOptions): [number, number][] {
	if (!query) return [];
	const haystack = options.ignoreCase ? text.toLowerCase() : text;
	const needle = options.ignoreCase ? query.toLowerCase() : query;
	const matches: [number, number][] = [];
	let from = 0;
	while (from <= haystack.length - needle.length) {
		const at = haystack.indexOf(needle, from);
		if (at === -1) break;
		const end = at + needle.length;
		const startsWord = !isWordChar(text[at - 1]);
		const endsWord = !isWordChar(text[end]);
		const ok = options.mode === 'contains' || (startsWord && (options.mode === 'startsWith' || endsWord));
		if (ok) {
			matches.push([at, end]);
			from = end;
		} else from = at + 1;
	}
	return matches;
}
```

단어 문자는 `[\p{L}\p{N}_]`라 한글에서도 단어 경계를 판별한다. 블록(문단, 표의 셀, 제목) 경계를 넘는 문자열은 찾지 않는다.

- **편집기**: ProseMirror 데코레이션으로 강조하고, 대치는 트랜잭션으로 실행한다. 문서 끝부터 바꿔야 앞쪽 위치 값이 밀리지 않는다
- **읽기 화면**: DOM을 변경하지 않고 [CSS Custom Highlight API](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Custom_Highlight_API)(`::highlight()`)로 강조한다. 텍스트를 문단·셀 단위로 수집해 검색하고, 검색 결과 위치를 DOM `Range`로 변환한다

읽기 화면의 강조 방법은 두 가지를 비교했다.

| 방법                                | 단점                                                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 검색 결과를 `<mark>`로 감싼다       | React가 렌더링한 DOM을 외부에서 변경하게 된다. 다음 렌더링에서 React가 모르는 노드가 생기거나 사라진다 |
| **CSS Custom Highlight API (선택)** | 지원하지 않는 브라우저에서는 강조가 표시되지 않는다. 그 경우에도 개수 표시와 결과 이동은 동작한다      |

```ts
registry.set('memo-find', new Highlight(...ranges.filter((_, i) => i !== current)));
registry.set('memo-find-current', new Highlight(...(current >= 0 ? [ranges[current]] : [])));
```

⌘F 리스너는 처음에 메모 창 요소에 등록했는데, 본문 텍스트를 눌러도 포커스가 창 내부로 이동하지 않아 동작하지 않았다. 메모가 맨 앞 창일 때 `window`에서 수신하도록 바꿨다.

## 확장되는 검색 칸

관리자 도구가 늘면서 검색 칸이 점점 좁아졌다. 측정해 보니 이미 도구 막대 밖으로 22px 넘쳐 잘리고 있었다(검색 칸의 최소 폭 때문).

검색 칸은 공간이 부족하면 돋보기만 남을 때까지 축소되고, 포커스를 받으면 다른 도구가 **•••**로 접히면서 오른쪽 끝을 고정한 채 왼쪽으로 확장된다. 도구 그룹은 `grid-template-columns: 1fr → 0fr`로, 검색 칸은 `flex-basis`로 애니메이션한다. •••를 누르는 순간 검색 칸의 포커스가 해제되어 도구가 다시 펼쳐지면 안 되므로, 이 버튼은 누를 때 포커스를 가져가지 않게 했다.

![넓어진 검색 칸과 ••• 메뉴](./images/notes-search-expanded.jpg '검색 칸에 포커스가 가면 도구가 •••로 접힌다. 접힌 도구는 ••• 메뉴에 모여 있다')

⌄ 메뉴에서는 체크리스트·표·이미지·코드·첨부 파일이 있는 메모만 필터링할 수 있다. 선택한 조건은 검색 칸 안에 작은 토큰으로 표시된다.

10월 27일부터는 검색어를 제목·본문뿐 아니라 글 주소(slug)와도 비교한다. 공유받은 링크의 주소만 기억할 때도 글을 찾을 수 있게 하려는 것이다.

| 검색어                                                       | 찾는 글 주소       | 규칙                                                   |
| ------------------------------------------------------------ | ------------------ | ------------------------------------------------------ |
| `merge-strategies`, `merge_strat`                            | `merge-strategies` | 하이픈·밑줄로 이은 낱말은 이어진 한 덩어리로 부분 일치 |
| `merge strategies`                                           | `merge-strategies` | 공백으로 나눈 낱말은 각각 어디에든 있으면 된다         |
| `https://macfolio.hyeoniverse.com/memo/merge-strategies?x=1` | `merge-strategies` | `/memo/` 앞과 `?`·`#` 뒤를 떼고 비교                   |

글 주소는 목록에 표시되지 않으므로, 주소로만 걸린 글은 제목·요약에 강조 표시가 없다. ⌄ 메뉴의 조건(표·코드 등)과는 함께 적용된다.

### 검색 순서와 결과가 없을 때 (10월 27일)

같은 날 검색 로직을 `desktop-core`의 `search.ts`로 모았다. 바뀐 점은 세 가지다.

![메모 검색의 단계](./images/notes-polish-search-flow.svg '도식. 검색어를 낱말로 나누고, 글마다 한 번 만든 검색용 글자에서 낱말을 찾아 칸 무게로 점수를 매기고, 결과가 없으면 비슷한 글과 고친 검색어를 보인다')

**1. 입력할 때마다 하던 일을 줄였다.** 예전에는 글자를 하나 칠 때마다 모든 글의 제목·본문을 소문자로 바꿔 비교했다. 글 238편의 본문은 약 205만 자다. 이제 글마다 검색용 글자(제목·주소·태그·초성·요약·본문, NFKC로 전각 글자를 반각으로, 소문자, 공백 하나)를 처음 검색할 때 한 번 만들어 `WeakMap`에 보관한다. 글 내용이 바뀌면 새 글 객체가 되므로 그때만 다시 만든다. 목록은 React의 [`useDeferredValue`](https://react.dev/reference/react/useDeferredValue)로 검색어를 한 박자 늦게 따라가, 입력 칸이 목록을 다시 그리는 동안 멈추지 않는다.

| 측정 (저장소 글 238편, Node 단위 시험) | 고치기 전 | 고친 뒤                     |
| -------------------------------------- | --------- | --------------------------- |
| 글자 하나 칠 때 거르기                 | 4.5~5.1ms | 0.5ms                       |
| 검색용 글자 만들기                     | -         | 31ms (처음 검색할 때 한 번) |
| 결과가 없을 때 추천 계산               | -         | 약 11ms (결과가 0개일 때만) |

**2. 여러 낱말과 순서.** 공백으로 나눈 낱말은 모두 들어 있어야 한다(AND). 낱말마다 어느 칸에서 찾았는지로 점수를 매겨, 제목에서 찾은 글이 본문에서만 찾은 글보다 앞에 온다. 점수가 같으면 보기 설정(날짜순 등)의 순서를 따른다.

| 칸   | 무게 | 비고                                            |
| ---- | ---- | ----------------------------------------------- |
| 제목 | 10   | 검색어 전체와 같으면 +30, 검색어로 시작하면 +10 |
| 주소 | 8    | 제목과 같은 가산                                |
| 태그 | 6    | 본문의 `#태그`                                  |
| 초성 | 5    | 초성만 두 글자 이상 쓴 낱말 (`ㅁㅊ` → 목차)     |
| 요약 | 4    |                                                 |
| 본문 | 1    |                                                 |

한글 입력기는 '엔'을 'ㅇ' → '에' → '엔' 순서로 보내므로, 낱말의 마지막 글자는 입력 중으로 보고 넓게 받는다. 받침 없는 음절은 같은 초성·중성의 모든 음절('프론트에'로 '프론트엔드'), 홑자음은 그 초성의 모든 음절, 받침이 있으면 그 받침이 다음 음절의 초성이 되는 경우('틍'으로 '트엔')까지 받는다. 제목·주소·태그·요약은 띄어쓰기를 무시하고도 비교해 '병합방식'으로 '병합 방식'을 찾는다.

글은 기술 용어를 영문(React, GitHub, TypeScript)으로 쓰는데, 검색은 한글 음차(리액트, 깃허브, 타입스크립트)로 하는 일이 많다. 그래서 저장소 글의 제목·태그에 나오는 용어 40여 개로 표기 묶음 사전을 두고(`react`·`리액트`, `github`·`깃허브`·`깃헙`, `vs code`·`브이에스코드` 등), 검색어 낱말을 같은 묶음의 다른 표기로도 찾는다. 다른 표기로 찾은 칸은 무게의 0.9배만 주어, 원래 표기로 찾은 글이 앞에 온다. 입력 중인 표기(타입스크립)는 세 글자 이상이면 그 표기의 앞부분으로 보고 받는다.

**3. 결과가 없을 때.** "검색 결과가 없습니다." 아래에 고친 검색어와 비슷한 글을 보인다.

<details>
<summary>비슷한 글과 고친 검색어를 고르는 기준</summary>

- 한글은 자모로 풀어 비교한다(프런트엔드 → ㅍㅡㄹㅓㄴㅌㅡㅇㅔㄴㄷㅡ). 한 음절 오타가 자모 1~2개 차이로 잡힌다.
- **비슷한 글:** 낱말마다 제목·주소·태그의 어느 부분과 편집 비용이 자모 길이의 25% 이하(적어도 1)인 글을, 비용이 적은 순서로 5편까지. 본문은 보지 않는다. 긴 본문에는 아무 검색어나 비슷한 부분이 있어 추천이 의미 없어진다.
- **고친 검색어:** 제목·주소·태그 어디에도 없는 낱말을, 제목·주소·태그에 나오는 낱말 중 가장 가까운 것으로 바꾼다. 바꾼 검색어로 찾은 글이 있을 때만 보인다(dispacher → dispatcher, 프런트엔드 셩능 → 프론트엔드 성능).
- 바꾸기 비용은 0.9, 넣기·빼기는 1로 두어, 같은 횟수면 길이가 같은 낱말을 고른다(flix → fix가 아니라 flux).
- 이웃한 두 글자를 맞바꾼 오타는 비용 1로 본다(Damerau–Levenshtein의 인접 전치. dokcer → docker, fulx → flux). 맞바꾸기를 따로 두지 않으면 바꾸기 두 번(1.8)이 되어 6글자 낱말의 허용치(1)를 넘는다.
- 고친 검색어 후보에는 표기 사전의 표기와, 제목의 이웃한 낱말 2~3개를 띄어쓰기 없이 이은 것도 넣는다. 음차의 오타는 사전의 표기로(플럭쓰 → 플럭스), 붙여 쓴 검색어의 오타는 이은 낱말로(프론트엔드셩능 → 프론트엔드 성능) 고친다. 비슷한 글은 음차의 오타를 사전의 표기로 고친 뒤 그 영문 표기로도 찾는다.
- 후보 목록은 같은 글 목록에 한 번만 만들어 `WeakMap`에 보관한다.
- 자모 3개보다 짧은 낱말은 추천하지 않는다. 한두 글자는 무엇과도 비슷하다.

</details>

![결과가 없을 때의 메모 목록](./images/notes-polish-search-similar.jpg '데스크톱 메모에서 리액트를 한 글자 틀리게 적어 찾은 화면. 목록 맨 위에 "검색 결과가 없습니다."와 "혹시 리액트를 찾으셨나요?", "비슷한 글" 머리 밑에 제목에 React가 있는 글 두 편이 먼저 보인다. 본문 칸 가운데에는 검색어에 맞는 메모가 없다는 안내와 고친 검색어, "비슷한 글 5편이 목록에 있습니다. 첫 글 열기"')

목록은 보통 목록과 같은 부품으로 그린다. 안내 두 줄은 목록 왼쪽 끝에 맞추고, 고친 검색어는 메모 강조색 글자 링크로, 비슷한 글은 날짜 묶음 머리와 같은 모양의 '비슷한 글' 머리 아래 보통 메모 줄(`NoteItem`)로 보인다. 고친 검색어가 있으면 비슷한 글은 그 검색어로 찾은 순서의 앞 5편이다. 없으면 철자가 비슷한 글을 비용 순서로, 비용이 같으면 제목 > 주소 > 태그 순서로 보인다.

본문 칸 가운데에도 '‘검색어’에 맞는 메모가 없습니다.', 고친 검색어, '비슷한 글 N편이 목록에 있습니다.'와 첫 글 열기를 보인다. 처음에는 본문 칸에 '선택한 메모 없음'만 두었는데, 목록 칸의 추천을 보지 못하고 검색이 동작하지 않는다고 읽혔다. 휴대폰처럼 한 칸씩 볼 때는 목록 칸에 이미 보이므로 두지 않는다.

결과가 있어도 낱말이 제목·주소·태그에는 없고 본문에서만 걸리면 목록 맨 위에 고친 검색어를 보인다. 이 글처럼 오타를 예로 적은 본문이 있으면 그 오타로 찾은 결과가 0편이 아니어서, 결과가 0편일 때만 추천하면 고친 검색어가 보이지 않는다. 고친 검색어를 누르면 그 검색어로 다시 찾고, 비슷한 글을 누르면 검색어를 지우고 그 글을 연다.

## 이미지: 캡션 수정, 내려받기, 드롭 위치 표시

- **캡션은 클릭한 위치에서 바로 수정한다.** 이전에는 삽입할 때만 캡션을 입력할 수 있고, 이후에는 이미지를 선택해 메뉴를 열어야 했다. 이제 편집기에서 캡션을 누르면 입력칸이 되고 Enter로 저장, Esc로 취소한다. 캡션이 없으면 이미지를 선택했을 때 '캡션 추가'가 표시된다
- **내려받기 버튼.** 이미지에 마우스를 올리면 오른쪽 위에 표시된다. 업로드한 파일은 API 출처, 검색한 사진은 Unsplash·Pexels 출처라 [`<a download>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/a#download)가 동작하지 않는다(다른 출처면 브라우저가 `download` 속성을 무시하고 링크를 연다). 이미지를 `fetch`로 내려받아 파일로 저장하고, 실패하면 새 탭에서 연다
- **드롭 위치 표시.** 편집기에 드롭 위치 표시가 있었지만 색이 지정되지 않아 보이지 않았다. 강조 색을 지정하고, `position: fixed` 요소는 컨테이너 쿼리를 사용하는 메모 창 안에서 창 기준으로 배치되므로[^fixed-container] `body`로 옮겼다

## Safari 탭

좁은 창에서 탭이 가로로 넘쳐 스크롤해야 표시됐다. macOS Safari처럼 **현재 탭은 넓게, 나머지는 좁게** 폭을 배분했다. 모든 탭이 같은 비율(`flex-grow: 1`)에서 시작하고 현재 탭만 더 큰 비율을 가진다. 탭을 바꾸면 `flex-grow` 값이 이동하면서 폭이 애니메이션으로 바뀌고, 다른 탭 제목은 말줄임표로 앞부분만 표시된다.

![좁은 창의 Safari 탭](./images/safari-tabs.jpg '현재 탭은 제목 전체가 표시되고, 다른 탭은 좁게 축소된다. 창이 좁아도 주소창은 유지된다')

처음에는 좁은 창에서만 이 스타일을 적용하고 주소창을 숨겼는데, 두 스타일이 일관되지 않았고 좁은 창에서 주소를 확인할 수 없었다. 이제 모든 폭에서 같은 탭 스타일(둥근 막대 안의 알약)을 사용하고, 주소창도 항상 표시한다. 닫기 버튼은 탭 왼쪽에 고정 공간을 갖고 오른쪽에도 같은 폭의 여백을 두어, 제목과 겹치지 않으면서 가운데 정렬이 유지된다. 이 공간은 현재 탭과 마우스를 올린 탭에서만 확보해, 좁은 창에서 다른 탭은 그만큼 제목을 더 표시한다.

## 남은 것·정리

- 핸들이 13px 어긋난 것처럼, "본문의 모든 형제 요소에 간격" 같은 넓은 선택자는 나중에 추가하는 요소에도 적용된다. 편집기 위에 렌더링하는 UI 요소는 본문 흐름 밖(포털이나 절대 위치)에 배치하는 편이 안전하다.
- `position: fixed`는 `container-type`을 가진 조상 안에서 그 조상을 기준으로 배치된다. 드롭 위치 표시를 `body`로 옮긴 것도 이 때문이었다. 컨테이너 쿼리를 사용하는 앱 안에 고정 위치 요소를 둘 때는 항상 확인해야 한다.
- ⌘F는 이후 [메뉴 막대의 메뉴](/memo/menubar-menus)에서 메뉴의 '찾기…' 단축키로 옮겼고, 메모 내부에서 별도로 처리하던 코드는 삭제했다.
