MacFolio의 서버는 기능을 붙일 때마다 조금씩 자랐다. 관리자 로그인, 글쓰기, 댓글, 메시지, 업로드, 배경화면, GitHub 연동까지 모듈이 11개가 됐고, 글도 기능마다 따로 남겼다. 그러다 보니 전체 모양은 어디에도 없었다. 이 글은 그 전체 모양이다. 저장소에도 같은 내용을 [docs/backend-design.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/backend-design.md)로 두었다.

## 조건

설계를 정한 건 기술보다 조건이었다.

- **관리자는 한 명이다.** 회원가입도, 권한 단계도 필요 없다. 대신 그 한 명이 아닌 사람은 아무것도 바꾸지 못해야 한다.
- **방문자는 가입하지 않는다.** 댓글 한 줄 남기려고 계정을 만들 사람은 없다.
- **돈을 쓰지 않는다.** 서버는 Oracle Cloud Always Free VM 한 대다. 메모리도 넉넉하지 않다.
- **혼자 운영한다.** 새벽에 장애가 나도 볼 사람이 없으니, 고장 나도 화면이 비지 않아야 한다.

## 구성도

![MacFolio 백엔드 구성도](./images/backend-design-architecture.jpg '브라우저는 Workers에서 화면을, Tunnel을 거쳐 API를 받는다. 서버는 바깥에 포트를 열지 않는다')

요청은 두 갈래다. 화면(HTML·JS)은 Cloudflare Workers에서 정적 파일로 받고, API 요청은 Cloudflare Tunnel을 지나 VM 안의 NestJS로 간다. 그림에서 눈여겨볼 곳은 세 군데다.

- **서버에 들어오는 문이 없다.** VM 안의 `cloudflared`가 Cloudflare로 먼저 연결을 열고, 요청은 그 연결로만 들어온다. 방화벽에 80·443을 열지 않고, 인증서 갱신도 신경 쓰지 않는다. compose 파일에는 `ports`가 한 줄도 없어서 DB는 컨테이너 네트워크 밖에서 보이지 않는다.
- **프론트엔드와 API가 같은 사이트다.** `macfolio.`와 `macfolio-api.`가 모두 `hyeoniverse.com` 아래에 있어서, `SameSite=Lax` 세션 쿠키가 API 요청에 함께 간다. API를 `workers.dev`나 IP 주소로 두었다면 로그인부터 되지 않았을 것이다.
- **외부 서비스 앞에는 캐시가 있다.** GitHub는 토큰 없이 시간당 60번까지만 답한다. 방문자마다 GitHub에 물으면 금방 막힌다.

## 요청이 지나가는 층

API에 들어온 요청은 모두 같은 층을 차례로 지난다.

| 층               | 하는 일                                                      |
| ---------------- | ------------------------------------------------------------ |
| `trust proxy`    | 터널 뒤에서 실제 방문자 IP를 읽는다                          |
| helmet, CORS     | 보안 헤더, 사이트 주소에서 온 요청만 쿠키와 함께 받는다      |
| `ValidationPipe` | DTO로 입력을 검사하고, 정해 두지 않은 필드가 있으면 거절한다 |
| `AdminGuard`     | 관리자 전용 경로에서 요청마다 세션을 DB에서 확인한다         |
| `ThrottlerGuard` | 로그인, 댓글·메시지 쓰기에 IP마다 1분 단위 제한              |
| 전역 예외 필터   | 에러 모양을 하나로 맞추고, 예상 못 한 에러는 내용을 감춘다   |

화면에서 편집 단추를 숨기는 것과 서버가 막는 것은 별개다. 버튼이 안 보여도 요청은 보낼 수 있으니, 막는 일은 늘 서버가 한다.

## 설계 결정

무엇을 골랐는지보다 무엇을 막으려고 골랐는지를 적었다.

| 주제          | 고른 방식                                                  | 막는 위험                                                      |
| ------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 관리자 로그인 | GitHub OAuth를 직접 구현, `state` 쿠키를 상수 시간 비교    | 비밀번호 저장, 남이 시작한 로그인(CSRF), 타이밍 공격           |
| 세션          | 쿠키에는 무작위 토큰, DB에는 SHA-256 해시만                | DB가 새도 세션을 가로챌 수 없다. 로그아웃하면 바로 끊긴다      |
| 관리자 확인   | 계정 이름이 아닌 GitHub 숫자 ID                            | 이름이 바뀌거나 남이 그 이름을 가져가도 권한이 넘어가지 않는다 |
| 방문자        | 쿠키 토큰의 HMAC만 저장, 화면에는 내 글인지만              | 가입 없이 내 글만 지운다. 토큰 원문은 서버에 없다              |
| IP            | 앞 두 자리와 HMAC만                                        | 개인정보를 최소로 두면서 같은 사람의 글은 묶어 본다            |
| 필수 항목     | 화면·API 검증에 더해 DB `CHECK` 제약                       | API를 거치지 않은 쓰기(스크립트, 버그)                         |
| 글 편집       | 게시본·임시 저장 분리, 게시마다 버전(50개), 30일 되살리기  | 고치는 중인 글 노출, 잘못 게시, 실수로 지우기                  |
| 업로드        | DB에 저장, 10MB 제한, 파일 앞부분으로 형식 확인, 무작위 ID | 백업 누락, 확장자만 바꾼 파일, 주소 추측                       |
| GitHub        | 서버 캐시, 동시 요청 하나로, 실패하면 마지막 값            | 요청 제한, GitHub 장애 때 빈 화면                              |
| 서버 노출     | Cloudflare Tunnel, 바깥 포트 없음                          | 열린 포트로 들어오는 공격, 인증서 만료                         |
| 배포          | `check`를 통과한 커밋만 Workers에                          | 시험을 건너뛴 배포                                             |

이 중 몇 가지는 처음부터 이렇게 하지 않았다. 댓글은 처음에 이름과 비밀번호를 받았고, 그 비밀번호는 Scrypt 해시로 저장했다. 방문자 쿠키로 바꾸면서 이미 쌓인 댓글은 그대로 두고 새 댓글부터 새 방식을 쓰게 했다. 데이터를 옮기지 않고 방식을 바꾸는 쪽이 혼자 운영하는 서버에는 더 안전했다.

## 파일을 DB에 둔 이유

가장 많이 고민한 결정은 업로드한 이미지를 어디 둘지였다. 보통은 디스크나 오브젝트 스토리지에 두고 DB에는 주소만 적는다. 그런데 서버가 한 대뿐이고, 배포 환경을 옮길 때마다 디스크가 바뀔 수 있다. 글은 DB에 있는데 그 글의 이미지는 디스크에 있으면, 백업도 두 군데를 챙겨야 한다.

그래서 파일도 DB(`bytea`)에 넣었다. 한 파일은 10MB까지로 막고, 배경화면은 브라우저에서 줄여서 올린다. 이렇게 하니 `pg_dump` 한 번에 글과 이미지가 함께 남는다. 사진이 수천 장이 되면 다시 생각해야 하는 결정이지만, 포트폴리오 블로그의 규모에서는 운영이 단순한 쪽이 이겼다.

## 시험

- **단위 시험**: 입력 규칙, 세션·해시, 방문자 이름 같은 순수 함수. 규칙은 `rules.ts`에 모아 두고 컨트롤러는 그 결과만 쓴다.
- **API e2e**: CI에서 PostgreSQL을 띄워 실제 DB로 돈다. 관리자가 아니면 401, 규칙을 어기면 400, 너무 자주 쓰면 429가 나오는지, DB에 해시만 들어가는지까지 확인한다. GitHub와 사진 서비스는 가짜 클래스로 바꿔 끼운다.
- **브라우저 E2E**: 프론트엔드는 가짜 API로 시험해서, API 모양이 바뀌면 두 쪽을 함께 고친다.

두 종류를 합쳐 API 쪽 시험만 120개가 넘는다. 이 시험이 main에 들어오는 모든 커밋에서 돌고, 통과해야 배포된다.
