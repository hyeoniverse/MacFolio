휴대폰 홈 화면의 위젯 편집 모드(길게 누르기)는 위젯 삭제(−)와 추가(+)만 지원했다. 순서를 바꾸려면 위젯을 삭제하고 원하는 페이지에서 다시 추가해야 했고, 같은 페이지 안의 순서는 추가한 순서로 고정됐다. iOS 홈 화면처럼 위젯을 끌어 순서를 바꾸도록 구현했다([#365](https://github.com/hyeoniverse/MacFolio/pull/365)). 처음 구성도 바꿨다. 음악 위젯을 1쪽, GitHub 잔디를 2쪽에 배치해 첫 화면에서 바로 재생할 수 있다.

![처음 구성 변경 전후](./images/mobile-widget-reorder-default.jpg '왼쪽 둘은 변경 전 1쪽(소개·GitHub 잔디)과 2쪽(날씨·캘린더·음악), 오른쪽 둘은 변경 후 1쪽(소개·음악)과 2쪽(날씨·캘린더·GitHub 잔디). iPhone 13 크기, 잔디는 E2E의 가짜 API 자료')

![편집 모드에서 위젯 끌기](./images/mobile-widget-reorder-drag.jpg '왼쪽부터 변경 전 편집 모드(삭제·추가만 가능), 음악 위젯을 소개 위젯 위로 끄는 중(소개 위젯이 아래로 이동), 놓은 뒤, 2쪽에서 날씨 위젯을 캘린더 자리로 끄는 중')

## 동작

| 조작                                   | 결과                                                                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------- |
| 편집 중 위젯을 누르고 움직이기         | 위젯이 1.06배로 커지며 포인터를 따라오고, 놓을 순서가 바뀌면 다른 위젯이 새 자리로 이동 |
| 편집 전 위젯을 0.55초 누른 뒤 움직이기 | 편집 모드가 켜지고, 손을 떼지 않은 채 바로 끌기 시작 (iOS와 같다)                       |
| 놓기                                   | 위젯이 칸에 붙고 순서를 `macfolio:mobile:widgets`에 저장                                |
| 화면 왼쪽·오른쪽 끝에 0.6초 머물기     | 옆 페이지로 넘어가 그 페이지 끝에 배치. 자리가 없는 페이지는 건너뛰지 않고 멈춘다       |
| 편집 중 위젯 밖에서 옆으로 쓸기        | 기존처럼 페이지 넘기기                                                                  |
| 키보드: '위젯 옮기기' 버튼에 초점      | ← ↑는 앞으로, → ↓는 뒤로 한 칸. 페이지 끝이면 옆 페이지로. 결과를 `aria-live`로 안내    |

시스템의 움직임 줄이기([`prefers-reduced-motion`](https://developer.mozilla.org/ko/docs/Web/CSS/@media/prefers-reduced-motion))가 켜져 있으면 흔들림, 확대, 비켜 주는 애니메이션을 모두 생략한다. 끄는 위젯은 그대로 포인터를 따라온다.

## 2열 격자의 배치 규칙

위젯 영역은 2열 CSS 격자다. 작은 위젯은 한 칸, 중간 위젯은 한 줄 전체를 차지한다. 저장 형식은 페이지마다 위젯 배열이고 좌표는 없다. 순서만으로 자리가 정해진다.

끌기를 구현하기 전에 확인해 보니 순서와 화면의 자리가 항상 일치하지는 않았다. CSS 격자의 기본 자동 배치(`grid-auto-flow: row`)는 커서를 앞으로만 옮긴다. `[작게, 중간, 작게]`는 첫 줄 오른쪽 칸을 비운 채 세 줄을 차지한다. 반면 페이지에 위젯을 더 놓을 수 있는지 계산하는 `widgetRows`는 "작은 위젯 둘이 한 줄"로 계산해 두 줄로 판단했다. 위젯 추가 순서에 따라 화면과 계산이 어긋날 수 있었다.

![sparse와 dense 배치](./images/mobile-widget-reorder-grid.svg '같은 순서를 sparse와 dense로 배치한 결과. dense는 뒤의 작은 위젯이 앞의 빈 칸을 채운다')

[`grid-auto-flow: row dense`](https://developer.mozilla.org/ko/docs/Web/CSS/grid-auto-flow)로 바꾸면 뒤의 작은 위젯이 앞의 빈 칸을 채워 `widgetRows`와 일치한다. 다만 dense 배치는 DOM 순서와 화면 순서가 달라진다. 화면 읽기 프로그램과 키보드 초점은 DOM 순서를 따르므로, 저장할 때마다 순서를 화면 순서로 정규화한다(`normalizeOrder`). 정규화한 순서는 sparse와 dense 어느 쪽으로 배치해도 같은 자리에 놓인다.

배치 규칙은 React와 DOM에 의존하지 않는 순수 함수로 분리했다(`desktop/mobile/widgetOrder.ts`).

| 함수             | 역할                                                                     |
| ---------------- | ------------------------------------------------------------------------ |
| `packWidgets`    | 순서대로 위 줄부터 빈 칸을 찾는다. dense 배치와 같은 결과                |
| `normalizeOrder` | 배치 결과를 위 줄, 왼쪽 칸 순으로 정렬                                   |
| `orderForDrop`   | 끄는 위젯을 놓을 순서 계산                                               |
| `moveByKey`      | 키보드로 한 칸 이동. 화면의 자리가 실제로 바뀌는 가장 가까운 순서를 선택 |
| `canMoveTo`      | 다른 페이지에 세 줄 제한 안에서 놓을 수 있는지                           |

## 놓을 자리 계산

`orderForDrop`은 끄는 위젯을 나머지 위젯 사이의 모든 위치(0번째부터 n번째)에 넣어 본다. 후보마다 배치를 계산하고, 그 배치에서 끄는 위젯의 가운데가 실제로 끌고 있는 위젯의 가운데와 가장 가까운 순서를 선택한다. 좌표는 픽셀이 아니라 칸 단위(작은 위젯 한 칸이 1)로 변환해 화면 크기와 무관하게 계산한다.

이 방식에서는 격자 규칙이 자동으로 지켜진다. `[작게 A, 작게 B, 중간 C]`에서 A를 중간 위젯 아래로 끌어도, A를 C 뒤에 넣은 후보는 dense 배치로 첫 줄 빈 칸에 다시 올라간다. 작은 위젯이 혼자 아래 줄로 내려가 위에 빈 칸을 남기는 순서는 후보에 존재하지 않는다.

두 후보의 거리가 비슷한 경계에서는 포인터가 1px만 움직여도 순서가 오가며 다른 위젯이 흔들린다. 지금 순서보다 0.15칸 이상 가까운 후보가 있을 때만 순서를 바꾸는 히스테리시스를 적용했다.

## 포인터 이벤트와 다른 제스처

홈 화면은 이미 [Pointer Events](https://developer.mozilla.org/ko/docs/Web/API/Pointer_events)로 페이지 넘기기와 길게 누르기를 처리한다(`MobileHome`의 `.mobile-pages`). 위젯 끌기도 같은 핸들러에서 제스처를 판정한다.

1. `pointerdown`: 위젯 칸 위인지 기록한다. 편집 중이면 바로 끌 수 있는 상태가 된다.
2. 길게 누르기 타이머(0.55초)가 끝나면 편집 모드를 켜고, 누른 곳이 위젯이면 끌 수 있는 상태로 바꾼다.
3. `pointermove`에서 8px 이상 움직이면 판정한다. 끌 수 있는 위젯이면 방향과 관계없이 위젯 끌기, 아니면 기존처럼 가로는 페이지 넘기기, 세로는 제어 센터에 넘긴다. 위젯 끌기로 판정하면 [`setPointerCapture`](https://developer.mozilla.org/ko/docs/Web/API/Element/setPointerCapture)로 이후 이벤트를 받는다.
4. `pointerup`이면 저장하고, `pointercancel`이면 원래 순서로 되돌린다.

손가락 입력에서는 세 가지 충돌을 처리했다.

- **브라우저 스크롤:** `.mobile-pages`는 세로 쓸기를 브라우저에 넘기려고 [`touch-action: pan-y`](https://developer.mozilla.org/ko/docs/Web/CSS/touch-action)다. 브라우저가 세로 이동을 가져가면 `pointercancel`이 발생한다. 편집 중의 위젯 칸은 `touch-action: none`으로 바꿨다. 다만 `touch-action`은 손가락을 댄 시각의 값이 적용되므로, 길게 눌러 편집이 켜진 손가락에는 효과가 없다. 이 경우는 `touchmove`를 `passive: false`로 등록하고 `preventDefault()`로 막는다.
- **제어 센터:** 화면 어디서든 세로로 쓸면 제어 센터가 열린다(`useVerticalSwipe`). 시작 시각에 `[data-swipe-ignore]` 안이면 무시하는데, 길게 눌러 편집이 켜진 손가락은 시작 시각에 이 속성이 없었다. 쓸기로 판정하는 시각에 대상을 한 번 더 확인하도록 고쳤다.
- **위젯 안의 조작 요소:** 음악 위젯의 재생 위치 막대는 스스로 끄는 요소라 홈 화면 제스처에서 제외되어 있다. 편집 중에는 막대에 `pointer-events: none`을 적용해 그 자리를 눌러도 위젯을 끌 수 있게 했다. 재생 버튼 같은 버튼은 움직이지 않고 누르면 그대로 동작한다.

## 끄는 위젯과 비켜 주는 위젯

편집 중의 위젯은 `transform: rotate()` 키프레임으로 흔들린다. 같은 `transform`에 이동을 인라인으로 지정하면 CSS 애니메이션이 덮어쓴다[^cascade]. 그래서 이동은 개별 변형 속성인 [`translate`](https://developer.mozilla.org/ko/docs/Web/CSS/translate)와 [`scale`](https://developer.mozilla.org/ko/docs/Web/CSS/scale)로 처리했다. 두 속성은 `transform`과 따로 합성되므로 흔들림과 충돌하지 않는다.

- **끄는 위젯:** 흔들림을 멈추고 `scale: 1.06`과 그림자를 적용한다. 매 프레임(`requestAnimationFrame`) 위젯의 레이아웃 위치(`offsetLeft`·`offsetTop`, 변형의 영향을 받지 않는다)를 다시 측정하고, 포인터와의 차이를 `translate`로 지정한다. 순서가 바뀌어 위젯의 칸이 달라지거나 옆 페이지로 넘어가 트랙이 움직이는 중에도 위젯이 포인터 아래에 남는다.
- **비켜 주는 위젯:** [FLIP](https://aerotwist.com/blog/flip-your-animations/) 기법을 쓴다. 렌더링 후(`useLayoutEffect`) 위젯마다 이전 위치와 새 위치의 차이를 계산하고, [Web Animations API](https://developer.mozilla.org/ko/docs/Web/API/Web_Animations_API)로 `translate`를 차이만큼에서 0까지 0.24초 동안 줄인다. 레이아웃은 한 번에 새 자리로 바뀌고, 화면에는 이전 자리에서 미끄러져 오는 것처럼 보인다.
- **놓을 때:** 인라인 `translate`를 지우고, 직전 값에서 0까지 같은 애니메이션을 재생해 칸에 붙는다.

## 다른 페이지로 옮기면 위젯이 작아지던 문제

위젯을 옆 페이지로 옮겨 그 페이지가 세 줄이 되면 모든 페이지의 위젯이 작아졌다. 페이지를 넘길 때마다 크기가 바뀌는 것처럼 보였다.

![위젯 크기 변경 전후](./images/mobile-widget-reorder-size.jpg 'iPhone 13 크기. 2쪽이 세 줄(날씨·캘린더, GitHub 잔디, 음악)인 구성. 수정 전에는 위젯 줄 높이가 117px에서 112px로 줄고 2쪽 아이콘 줄이 잘렸다. 수정 후에는 117px 그대로이고 2쪽에 들어가지 않는 앱은 다음 페이지로 간다')

원인은 위젯 줄 높이 계산(`homePages.ts`의 `widgetRowHeight`)이다. 위젯 아래에 아이콘 두 줄이 들어가도록 줄 높이를 줄이는데, 기준이 "위젯 줄 수가 가장 많은 페이지"였다. 2쪽이 세 줄이 되면 1·3쪽까지 세 줄 기준으로 줄었다. 끌기 이전에도 갤러리에서 위젯을 추가해 세 줄을 만들면 같은 현상이 있었고, 끌기로 페이지를 옮길 수 있게 되면서 쉽게 재현됐다.

| 상황 (Playwright 측정)       | iPhone 13 줄 높이   | Pixel 7 줄 높이     | 아이콘 |
| ---------------------------- | ------------------- | ------------------- | ------ |
| 처음 구성 (모든 페이지 2줄)  | 117px               | 161.5px             | 60px   |
| 수정 전: 2쪽을 3줄로 만든 뒤 | 112px (모든 페이지) | 131px (모든 페이지) | 60px   |
| 수정 후: 2쪽을 3줄로 만든 뒤 | 117px               | 161.5px             | 60px   |

iOS처럼 위젯 크기를 위젯 구성과 무관하게 화면 크기로만 정하도록 바꿨다. 정사각형을 기본으로, "위젯 두 줄 아래 아이콘 두 줄"과 "위젯 세 줄이 페이지에 들어감" 두 조건 중 작은 값으로 줄인다. 세 줄인 페이지는 위젯 아래 남는 높이만큼만 아이콘을 두고, 한 줄도 들어가지 않으면 그 페이지에는 앱을 두지 않는다(`iconRowsBelow`, `pageApps`의 0칸 허용). 이전에는 최소 한 줄을 강제해 아이콘 이름이 잘렸다. 앱 아이콘은 원래 60px 고정이라 측정값은 변하지 않았다.

## 데스크톱 위젯과 코드를 공유하지 않은 이유

바탕화면 위젯도 끌어 옮길 수 있다([180px 칸 격자와 공유 날씨 요청으로 만든 바탕화면·홈 화면 위젯](/memo/desktop-widgets)). 하지만 두 화면은 배치 모델이 다르다.

| 항목                | 바탕화면 (`desktop/widgets/layout.ts`)     | 휴대폰 (`desktop/mobile/widgetOrder.ts`) |
| ------------------- | ------------------------------------------ | ---------------------------------------- |
| 저장                | 위젯마다 칸 좌표 `col`·`row`               | 페이지마다 순서 배열                     |
| 빈 칸               | 허용 (아무 칸에나 배치)                    | 허용하지 않음 (앞에서부터 채운다)        |
| 다른 위젯 위에 놓기 | 원래 자리로 복귀 (macOS처럼 밀어내지 않음) | 다른 위젯이 비켜 준다 (iOS)              |

macOS와 iOS의 동작 차이를 그대로 따랐기 때문에 자리 계산 함수는 따로 두었다. 움직임 줄이기 판단(`prefersReducedMotion`), 위젯 카탈로그와 줄 수 계산(`widgetRows`·`fitsOnPage`)은 같이 쓴다.

## 처음 구성 변경과 저장된 구성

처음 구성은 `DEFAULT_MOBILE_WIDGETS`이고, 방문자의 구성은 브라우저에 저장한다. 그런데 위젯을 옮기거나 빼지 않은 방문자도 구성이 저장되어 있을 수 있다. 사진 위젯의 앨범이나 메모 위젯의 글 보기를 바꾸면 처음 구성 전체가 저장되기 때문이다. 이 방문자에게는 처음 구성을 바꿔도 반영되지 않는다.

| 예전 처음 구성 두 가지 중 하나와 id·종류·크기·순서가 모두 같음 | 새 처음 구성. 앨범·글 보기는 같은 id의 위젯에 옮긴다 | 방문자가 고른 배치가 아니라 고른 값 저장의 부산물이다 |
| 그 밖 (빼거나 더하거나 크기를 바꿈)                            | 그대로 사용                                          | 방문자가 직접 바꾼 구성이다                           |

비교 대상은 이전 처음 구성(`92e281ccc`)과 편집 기능을 처음 만든 시각의 구성(`f11e3058d`) 두 가지다. 저장 형식은 바꾸지 않았으므로, 배포를 되돌려도 이전 코드가 같은 값을 그대로 읽는다. 방문자가 끌기로 예전 처음 구성과 정확히 같은 배치를 직접 만들면 다음 방문에 새 처음 구성으로 바뀐다. 위젯 8개의 순서가 모두 일치해야 하므로 이 경우는 무시했다.

</details>

## 시험

- **단위 시험:** `widgetOrder.test.ts`에서 dense 배치, `widgetRows`와의 일치, 정규화, 놓을 순서와 히스테리시스, 다른 페이지 이동 가능 여부, 키보드 이동을 확인한다. `catalog.test.ts`에서 처음 구성과 예전 구성 변환을 확인한다.
