블로그 폴더는 글 파일 머리말의 `category`로 정해진다. 10월 9일 [폴더 재분류](/memo/memo-folders-reorg)에서 `개발기/MacFolio` 아래를 백엔드·인프라·프론트엔드·회고 네 폴더로 나눴다. 이후 코드 구조를 다루는 글이 늘면서 같은 성격의 글이 세 폴더에 흩어졌다.

| 글                                                                | 있던 폴더  | 다루는 것             |
| ----------------------------------------------------------------- | ---------- | --------------------- |
| [창 관리를 React 밖으로](/memo/desktop-core-windows)              | 프론트엔드 | 패키지 경계           |
| [응답 타입을 두 번 적지 않기](/memo/contracts-comments)           | 인프라     | 화면·서버 공유 스키마 |
| [화면과 서버가 같은 규칙을 쓰기](/memo/desktop-core-shared-rules) | 백엔드     | 화면·서버 공유 규칙   |

세 글 모두 "어떤 코드를 어느 패키지·파일에 두고, 무엇을 공유하는가"를 다룬다. 그런데 독자가 이 주제를 찾으려면 세 폴더를 모두 열어야 했다. 10월 26일 MacFolio의 store 설계 글([#379](https://github.com/hyeoniverse/MacFolio/pull/379))을 쓰면서 프론트엔드 폴더에 맞지 않는다는 지적을 받았고, 이 계기로 `개발기/MacFolio/설계` 폴더를 만들었다.

![설계 폴더를 추가하기 전과 후의 메모 사이드바](./images/blog-design-folder-sidebar.jpg '가짜 API로 촬영한 메모 사이드바. 옮긴 뒤 백엔드 29→26, 인프라 55→42, 프론트엔드 109→103이 되고 설계 22가 생겼다')

## 기준

**설계 폴더에 두는 글:** 코드의 경계와 공유를 다루는 글이다.

- 패키지·모듈 경계: 로직을 어느 패키지에 둘지(desktop-core), 파일을 어떻게 나눌지
- 화면과 서버가 함께 쓰는 타입·스키마·규칙(`@macfolio/contracts`, desktop-core의 메모 규칙)
- 의존 방향과 그것을 지키는 장치(순환 의존 검사, 브랜드 타입, 공통 클라이언트)

**옮기지 않은 글:** 같은 단어(리팩터링, 스키마, 구조)가 들어가도 주제가 화면·서버·운영 중 한쪽이면 그대로 두었다.

| 글                                                       | 남긴 폴더  | 이유                                      |
| -------------------------------------------------------- | ---------- | ----------------------------------------- |
| 리팩터링 4단계 — 공통 컴포넌트 설계                      | 프론트엔드 | 버튼 컴포넌트의 모양·접근성 이름이 주제   |
| 리팩터링 5단계 — 스타일                                  | 프론트엔드 | CSS                                       |
| 리팩터링 6단계 — 서버                                    | 백엔드     | 서버 코드                                 |
| 리팩터링 7단계 — 보안                                    | 인프라     | 보안 점검                                 |
| [MacFolio 백엔드 한 장으로 보기](/memo/backend-design)   | 백엔드     | 서버 한쪽의 구성도. 백엔드 글의 입구 역할 |
| CSS 층(`@layer`) 글                                      | 프론트엔드 | 스타일 우선순위                           |
| [TypeScript 7로 올리기](/memo/typescript-7-side-by-side) | 인프라     | 도구 버전                                 |

리팩터링 연재(1~7단계)는 1~3단계만 설계로 옮겼다. 1단계(타입과 데이터 구조), 2단계(폴더 구조와 의존), 3단계(공통 기반 코드)는 코드 경계가 주제이고, 4~7단계는 각 영역의 작업이다. 연재를 한 폴더에 모으는 것보다 글마다 주제로 나누는 쪽을 택했다. 각 글은 앞뒤 단계로 연결되어 있어 연재를 따라 읽는 데는 지장이 없다.

## 서버 정리 내용과의 관계

관리자가 화면에서 폴더를 옮기거나 이름을 바꾸면 그 내용은 서버의 정리 내용(`GET /memo/organization`)에 저장되고, 저장소의 `category`보다 우선한다([글은 Markdown에 두고 정리만 서버에](/memo/memo-organization-api)). 옮기기 전에 배포 서버의 정리 내용을 확인했다.

| 항목                     | 값                                 | 이번 이동과의 관계                                                         |
| ------------------------ | ---------------------------------- | -------------------------------------------------------------------------- |
| `posts` (글별 폴더 지정) | 2편. 둘 다 이번에 옮긴 글이 아니다 | 영향 없음                                                                  |
| `moves` (폴더 이름 변경) | `개발기` → `개발 기록` 등          | 상위 폴더 이름 변경이라 `설계`도 함께 `개발 기록/MacFolio/설계`로 표시된다 |
| `order` (폴더 순서)      | 비어 있음                          | 기본 정렬(가나다)로 백엔드 다음에 설계가 놓인다                            |

그래서 저장소의 `category`만 바꿔도 배포 화면에 반영된다. 폴더 순서를 바꾸고 싶으면 관리자 화면의 폴더 편집에서 정하면 된다.

## 시험

휴대폰의 폴더 순서 바꾸기 시험은 `개발기/MacFolio` 아래 폴더 이름을 순서대로 확인한다. 네 폴더를 기대하던 값을 다섯 폴더(백엔드·설계·인프라·프론트엔드·회고)로 고쳤다. 다른 메모 시험은 폴더를 경로로 찾거나 글 수를 직접 기록하지 않아 바꿀 필요가 없었다.

## 같은 날 이어진 재구성

이 글을 쓴 뒤 같은 날 블로그 전체 폴더를 다시 나눴다. `개발기`는 `개발 기록`이 되었고, 설계 폴더에는 파일 분할·공통 모듈 글 4편이 더해져 27편이 되었다. 자세한 내용은 [블로그 폴더를 분야별로](/memo/blog-categories)에 있다.
