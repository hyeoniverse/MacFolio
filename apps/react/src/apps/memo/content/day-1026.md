## 글꼴: OS와 관계없이 같은 글꼴로

### 배경: 브라우저가 글꼴을 고르는 방법

CSS의 `font-family`는 글꼴 이름의 목록이다. 브라우저는 앞에서부터 차례로 확인해 기기에 있거나 내려받을 수 있는 첫 글꼴로 글자를 그린다. 예를 들어 `font-family: -apple-system, 'Apple SD Gothic Neo', sans-serif`라면 `-apple-system`을 먼저 찾고, 없으면 `Apple SD Gothic Neo`, 그것도 없으면 일반 글꼴 키워드 `sans-serif`가 가리키는 기기 기본 고딕체를 쓴다. `-apple-system`은 Apple 기기의 브라우저만 알아듣는 이름으로, macOS·iOS의 시스템 글꼴(영문 SF Pro, 한글 Apple SD Gothic Neo)을 가리킨다.

기기에 없는 글꼴은 `@font-face` 규칙으로 서버에서 내려받는다. 이 규칙에는 글꼴 이름, 파일 주소, 그 파일이 담은 굵기 범위를 적는다. 요청한 굵기(예: `font-weight: 700`)의 글꼴 파일이 없으면 브라우저는 가장 가까운 굵기로 그린 뒤 획을 덧칠해 굵게 보이게 만든다. 이를 합성 굵기(synthetic bold)라고 하며, 글꼴 디자이너가 만든 Bold보다 획이 뭉개지고 글자 폭이 달라진다.

글꼴 파일은 저작물이라 웹 서버에서 배포하려면 라이선스가 허락해야 한다. SIL Open Font License(OFL) 1.1은 글꼴을 문서·웹 페이지에 넣어 재배포하는 것을 허락하는 대표적인 오픈 라이선스다. 반면 macOS에 들어 있는 Apple 글꼴은 Apple 기기에서 쓰도록 허락된 것이라 웹 글꼴로 배포할 수 없다.

![기기마다 font-family를 해석한 결과](./images/day-1026-font-fallback.svg '도식. 바꾸기 전에는 Apple 기기만 시스템 글꼴과 실제 Bold를 쓰고, 그 밖의 기기는 Regular 한 굵기에서 합성한 굵은 글씨를 그렸다. 바꾼 뒤에는 모든 OS가 같은 가변 글꼴을 받는다')

### 교체 ([#384](https://github.com/hyeoniverse/MacFolio/pull/384))

같은 화면이 macOS·iOS와 Windows·Android·Linux에서 다른 글꼴로 그려졌다. 글꼴 지정이 `-apple-system`으로 시작해 Apple 기기는 시스템 글꼴(SF Pro, Apple SD Gothic Neo)을, 그 밖의 기기는 `public/fonts/`에서 배포하던 Apple SD Gothic Neo **Regular 한 굵기**를 받았다. 사이트의 굵은 글씨 약 500곳은 Apple 기기가 아니면 브라우저가 합성한 굵기였다. 그리고 ==Apple 글꼴은 웹 배포 허락이 없다==.

![고치기 전: macOS와 Linux](./images/open-fonts-before-os.jpg '고치기 전. 같은 빌드를 macOS Chromium과 Linux Chromium에서 열었다. 영문·숫자·고정폭·굵은 글씨가 다르다')

![고친 뒤: macOS와 Linux](./images/open-fonts-after-os.jpg '고친 뒤. 두 OS가 같은 글꼴을 받는다')

용도마다 SIL OFL 1.1 글꼴을 하나씩 골랐다. 본문의 Pretendard는 가변 글꼴(variable font)이다. 가변 글꼴은 굵기 같은 축을 한 파일에 담아, Regular·Bold 파일을 따로 받지 않아도 45부터 920까지 어떤 굵기든 실제 획 두께로 그린다.

| 용도       | 고치기 전 (Apple 기기 / 그 밖)                 | 고친 뒤 (모두 SIL OFL 1.1)                                 |
| ---------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 본문       | SF Pro + Apple SD Gothic Neo / Regular 웹 글꼴 | Pretendard Variable (굵기 45~920)                          |
| 고정폭     | SF Mono / Consolas·DejaVu Sans Mono 등         | JetBrains Mono Variable                                    |
| 명조       | AppleMyungjo / 기기마다 다름                   | Noto Serif KR Variable                                     |
| PDF 이력서 | Apple SD Gothic Neo                            | Pretendard OTF (react-pdf가 woff를 풀려면 `Buffer`가 필요) |
| 공유 카드  | Apple SD Gothic Neo                            | Pretendard woff (satori는 woff2를 읽지 못함)               |

CSS 파일의 글꼴 지정을 `src/styles/fonts.css`의 변수 셋(`--font-sans`·`--font-mono`·`--font-serif`)으로 바꾸고, Apple 글꼴 파일을 저장소에서 삭제했다. 입력 칸·버튼은 상위 요소의 글꼴을 물려받지 않고 브라우저 기본값인 시스템 글꼴로 그려지므로, `reset` 층에 `font-family: inherit`를 넣었다.

<details>
<summary>Pretendard 동적 서브셋(92조각)을 쓰지 않은 이유</summary>

처음에는 Pretendard가 제공하는 동적 서브셋을 시도했다. 메모 앱 첫 화면은 글 234편의 제목·요약을 한 화면에 그려 92조각 거의 전부(약 1.7MB)를 받았고, `@font-face` CSS 14.6KB 때문에 첫 방문 번들이 271.4KB로 상한 265KB를 넘었다. `scripts/subset-font.py`로 core(영문·문장 부호·자모·KS X 1001 2,350자) 하나와 나머지 한글 ext 8조각으로 직접 나눴다. 저장소 전체에서 KS X 1001 밖 한글은 '긂·똠·햏' 세 글자뿐이었다.

### 전송량 줄이기와 예산 ([#385](https://github.com/hyeoniverse/MacFolio/pull/385))

한글 글꼴은 완성형 글자 11,172자를 모두 담으면 파일이 수 MB가 된다. 그래서 하나의 글꼴을 글자 범위별 파일 여러 개로 나누고, `@font-face`마다 `unicode-range`로 그 파일이 담은 글자 범위를 적는다. 브라우저는 화면에 실제로 그린 글자가 든 범위의 파일만 요청한다. 예를 들어 화면에 '메모', '회고'만 있으면 이 글자가 든 조각 하나만 받는다. KS X 1001은 자주 쓰는 한글 2,350자를 고른 한국 산업 표준 문자 집합으로, 조각을 나누는 기준으로 썼다.

같은 글꼴을 그리는 대가로 데스크톱 첫 화면의 글꼴 전송량이 397KB(Chromium)에서 1,187KB로 늘었다. 교체 PR 본문에 이 수치를 기록하고, 같은 날 후속 PR로 줄였다.

| 화면 (`vite preview`, 글꼴 응답 합계) |          교체 전 | #384 직후 | #385 적용 |
| ------------------------------------- | ---------------: | --------: | --------: |
| 데스크톱 첫 화면                      | 397KB (Chromium) |   1,187KB | **568KB** |
| 휴대폰 홈 (iPhone 15, WebKit)         |   136KB (WebKit) |     591KB | **382KB** |

1. **한글 명조는 Safari 창에 사용자 입력이 있는 시각에 받는다.** 바탕화면은 Safari 창이 처음부터 열려 있어 `ProjectPage.css`의 정적 `@import`로 첫 방문자 모두가 명조 한글 약 440KB를 받았다. 창 안을 누르거나 스크롤하는 등 사용자 입력이 있으면 `import()`로 불러온다. 그 전에는 같은 Pretendard 파일에 `size-adjust`를 준 대체 글꼴로 그린다(아래 설명).
2. **Pretendard core를 이 사이트가 쓰는 글자로 줄였다.** 저장소의 글·화면 문구에 나오는 KS X 1001 1,093자만 core(456KB → 246KB)에 남기고, 나머지 1,257자는 `ksx` 조각(253KB)으로 분리했다.
3. **첫 화면 글꼴 예산.** ==글꼴은 그린 글자에 따라 받아 빌드 결과만으로 크기를 알 수 없다==. 그래서 빌드 결과물 크기를 검사하는 `budget.mjs`가 아니라 E2E에 실제 브라우저 시험 3개를 넣었다: 데스크톱 첫 화면 600KB, 휴대폰 홈 410KB 상한, 데스크톱 첫 화면에 명조 한글 조각이 없는지.

![unicode-range 조각과 받는 조각](./images/day-1026-unicode-range.svg '도식. 같은 이름의 Pretendard를 core·ksx·ext 조각으로 나눴다. 화면에 그린 글자에 따라 core만 받거나, ksx나 ext 조각 하나를 더 받는다')

명조를 늦게 받으면 그 전까지 다른 글꼴로 그렸다가 명조로 바뀌는 순간 글자 폭이 달라져 제목의 줄바꿈과 상자 높이가 흔들린다. `@font-face`의 `size-adjust`는 대체 글꼴의 글자 크기를 비율로 늘이거나 줄여 이 차이를 맞추는 설명자다. 한글 한 글자의 폭은 Noto Serif KR이 0.966em, Pretendard가 0.864em이라 비율을 다음처럼 정했다.

```math
\text{size-adjust} = \frac{0.966\,\text{em}}{0.864\,\text{em}} \approx 111.8\%
```

이 값을 준 대체 글꼴로 그리면 명조로 바뀌는 시각에도 제목 상자가 571×87px로 같다.

![명조를 받기 전과 후](./images/open-fonts-serif-swap.jpg '첫 화면의 Safari 창. 왼쪽은 명조를 받기 전(폭을 맞춘 Pretendard), 오른쪽은 창을 누른 뒤의 Noto Serif KR. 제목의 줄바꿈과 높이가 같다')

> [!WARNING] 따옴표가 사라지면 일반 글꼴 키워드가 되는 글꼴 이름
> 대체 글꼴의 처음 이름 `'Serif Fallback'`은 동작하지 않았다. CSS 압축이 `font-family` 값의 따옴표를 제거하자 첫 낱말이 일반 글꼴 키워드 `serif`로 해석되어 규칙 전체가 무효가 되었다. 이름을 `'Pretendard Serif Fallback'`으로 바꿨다.

과정 전체는 [오픈 라이선스 글꼴로 바꾸고 첫 화면 글꼴을 1,187KB에서 568KB로 줄이기](/memo/open-fonts)에 적었다.

## 저장소 글의 폴더 변경과 서버의 정리 내용 ([#389](https://github.com/hyeoniverse/MacFolio/pull/389))

메모 앱의 글은 두 곳에서 온다. 저장소의 Markdown 파일은 머리말 `category`로 폴더를 정하고, 관리자가 메모 앱에서 폴더 이름을 바꾸거나 글을 다른 폴더로 옮긴 내용은 서버에 따로 저장된다(`GET /memo/organization`). 화면은 저장소 `category`에 서버의 정리 내용을 차례로 덧씌운다. 그래서 저장소 글의 `category`를 고칠 때는 서버의 정리 내용이 그 결과를 다시 바꾸지 않는지 확인해야 한다. 배포 API를 조회만 해서 영향을 확인했다.

![폴더를 정하는 순서](./images/day-1026-folder-overlay.svg '도식. 저장소 category에 moves(폴더 이름 변경), posts(글별 폴더 지정)를 차례로 적용한다. 글별 지정이 남아 있으면 저장소에서 없앤 폴더가 다시 생긴다')

| 항목                     | 값                                     | 영향                                                                               |
| ------------------------ | -------------------------------------- | ---------------------------------------------------------------------------------- |
| `moves` (폴더 이름 변경) | `개발기` → `개발 기록`                 | 저장소 이름을 `개발 기록`으로 바꿔도 표시는 같다                                   |
| `posts` (글별 폴더 지정) | `notes-polish`가 `…/프론트엔드`로 지정 | 그대로 두면 없어진 `프론트엔드` 폴더가 글 하나로 다시 생긴다. 관리자 화면에서 이동 |
| `order` (폴더 순서)      | 비어 있음                              | 가나다순                                                                           |

글 주소(slug)는 파일 이름이라 `category`를 바꿔도 링크는 깨지지 않는다. 폴더 이름에는 경로 구분자 `/`를 쓸 수 없다. 예를 들어 `CI/CD`라는 폴더를 `개발 기록/MacFolio` 아래에 두면 `개발 기록/MacFolio/CI/CD`의 4단이 되어 `MAX_FOLDER_DEPTH` 3을 넘는다. 그래서 `CI·CD`처럼 가운뎃점을 썼다.

> [!WARNING] 머지 뒤에 push한 커밋은 main에 들어가지 않는다
> GitHub PR은 머지 버튼을 누른 시각의 커밋까지만 main에 합친다. #389는 마지막 삭제 커밋을 머지 뒤에 push해 main에 반영되지 않았다. 다음 날 #392로 같은 변경을 다시 반영했다.

## 의존성: 편집기를 막은 패치 버전 ([#382](https://github.com/hyeoniverse/MacFolio/pull/382), [#383](https://github.com/hyeoniverse/MacFolio/pull/383))

### 배경: 패치 버전과 Dependabot

npm 패키지 버전은 대개 유의적 버전(Semantic Versioning) `주.부.패치` 형식을 따른다. 규칙상 패치 번호만 오른 버전(예: 2.3.2 → 2.3.3)은 기존 사용법을 바꾸지 않는 버그 수정이어야 한다. Dependabot은 GitHub가 제공하는 봇으로, 의존성의 새 버전을 찾아 `package.json`과 잠금 파일을 올리는 PR을 자동으로 연다. 패치 버전 PR은 시험만 통과하면 그대로 머지하기 쉽다.

관리자 편집기(Milkdown)는 화면에서 고친 문서를 저장할 때 Markdown 문자열로 직렬화한다. 직렬화는 remark 생태계의 `mdast-util-to-markdown`이 맡고, `remark-cjk-friendly`는 한글처럼 띄어쓰기 규칙이 다른 문자 옆의 `**강조**`를 올바르게 처리하도록 이 단계에 규칙을 더하는 플러그인이다.

### 원인과 수정

Dependabot PR 가운데 #382(`docker/login-action` 4.6.0 → 4.7.0)는 그대로 머지했고, #383(15개 패키지 업데이트)은 메모 편집기 E2E에서 실패했다.

| 항목        | 내용                                                                                                                                                                                     |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 원인 버전   | `remark-cjk-friendly` 2.3.2 → 2.3.3 (함께 올라온 `mdast-util-to-markdown-cjk-friendly` 1.0.1)                                                                                            |
| 증상        | Milkdown 편집기가 글을 Markdown으로 직렬화하는 `containerPhrasing`에서 강조 처리기가 `TypeError: Cannot read properties of undefined (reading 'length')`. 관리자 편집 화면이 열리지 않음 |
| 영향 범위   | 방문자 읽기 화면은 Markdown을 직렬화하지 않아 영향 없음                                                                                                                                  |
| 배제한 원인 | `mdast-util-to-markdown`이 2.1.3·2.2.0 두 사본으로 나뉜 것. 2.2.0 하나로 맞춰도 같은 오류                                                                                                |
| 수정        | `package.json`에서 2.3.2로 고정, `dependabot.yml`에서 2.3.3 제외. 나머지 14개 업데이트는 반영                                                                                            |

읽기 화면은 Markdown 문자열을 화면으로 바꾸는 방향(파싱)만 쓰고, 편집기는 반대 방향(직렬화)도 쓴다. 이번 오류는 직렬화 쪽에만 있어 읽기 화면 시험으로는 드러나지 않는다.

> [!TIP] 고정한 버전에는 해제 조건을 남긴다
> `dependabot.yml`의 제외 항목에는 해제 조건을 주석으로 남겼다: 다음 버전이 나오면 편집기 E2E로 확인한 뒤 이 줄을 삭제한다.

## 돌아보며

글꼴을 통일한 대가를 #384 본문에 화면별 전송량(397KB → 1,187KB)으로 기록해, 후속 PR의 결과(568KB)를 같은 측정 방법으로 비교할 수 있었다. 번들 예산(`budget.mjs`)은 빌드 결과만 검사해 글꼴 전송량이 늘어난 것을 잡지 못했다. ==그린 글자에 따라 달라지는 자원은 실제 브라우저 시험으로 예산을 걸어야 한다==.

#389의 삭제 커밋은 머지 뒤에 push해 main에서 빠졌다. PR에 커밋을 더하기 전에 `gh pr view --json state`로 머지 여부부터 확인한다.

패치 버전 하나가 관리자 편집 화면을 막았다. 읽기 화면만 시험했다면 배포 뒤에야 알았을 오류를 편집기 E2E가 잡았다. 고정한 버전은 `dependabot.yml`에 해제 조건과 함께 기록해, 다음 버전이 나오면 다시 확인하게 했다.
