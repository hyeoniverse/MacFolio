관리자가 더한 배경화면은 지금까지 사진만 됐다. 사진을 고르면 브라우저가 긴 변 2,560px로 줄여 JPEG로 바꾼 뒤 올렸다. 그래서 움직이는 GIF를 골라도 첫 장면 한 장만 남았다. macOS의 움직이는 배경화면처럼 바다가 출렁이는 화면을 깔고 싶어서, MP4 동영상과 움직이는 GIF를 배경화면으로 쓸 수 있게 했다.

## 무엇이 바뀌었나

- 관리자 칸의 이름이 '사진 추가…'에서 '사진·동영상 추가…'로 바뀌었다. 파일 고르기 창에서 MP4도 고를 수 있다.
- GIF는 줄이지 않고 원본 그대로 올린다. 줄이면 캔버스에 한 장면만 그려지기 때문이다. 썸네일만 첫 장면으로 만든다.
- MP4도 원본 그대로 올린다. 썸네일(포스터)은 브라우저가 동영상의 0.5초쯤 장면을 캔버스에 그려 JPEG로 만든다.
- 고르기 칸의 동영상 썸네일 가운데에는 재생 표시(▶)가 있다. 스크린 리더는 이름 뒤에 '(동영상)'을 읽는다.
- 방문자는 다른 배경화면처럼 고른다. 데스크톱과 휴대폰 홈 화면 모두 된다.

## 화면에 까는 방법

배경화면은 원래 CSS 변수(`--wallpaper`) 하나로 그린다. 동영상은 CSS 배경으로 틀 수 없어서, 고른 배경화면이 동영상이면 `<video>`를 하나 더 깐다.

- 배경 변수에는 포스터 이미지를 넣는다. 동영상을 불러오는 동안이나 틀지 못할 때는 이 멈춘 장면이 보인다.
- `<video>`는 `muted`, `loop`, `autoplay`, `playsinline`이고 `object-fit: cover`로 화면을 꽉 채운다. 브라우저는 소리 없는 동영상만 저절로 틀어 주기 때문에 소리는 늘 끈다.
- 데스크톱에서는 화면에 고정하고 창과 아이콘 아래(z-index -1)에 둔다. 휴대폰에서는 홈 화면 안에 두어서, 앱을 열면 홈 화면과 함께 살짝 뒤로 물러난다.
- 시스템의 '동작 줄이기'(prefers-reduced-motion)를 켜면 `<video>`를 그리지 않는다. 포스터만 남는다.
- 탭이 가려지면(`visibilitychange`) 멈추고, 다시 보이면 이어서 튼다. 보이지 않는 동영상을 계속 풀면 배터리만 쓴다.

설정에는 `wallpaperVideo`(휴대폰은 `mobileWallpaperVideo`) 값이 새로 생겼다. 다음에 사이트를 열 때 서버에 목록을 묻기 전에도 바로 동영상을 깔 수 있다. 서버에서 그 배경화면이 지워졌으면 지금처럼 기본 배경화면으로 돌아간다.

## 포스터를 브라우저에서 만드는 이유

서버(NestJS)에는 동영상을 푸는 도구(ffmpeg 같은 것)가 없다. 이것 하나 때문에 서버 이미지에 ffmpeg을 넣기보다, 이미 동영상을 풀 줄 아는 브라우저에서 만들기로 했다.

1. 고른 파일을 `URL.createObjectURL`로 `<video>`에 넣는다.
2. 첫 데이터가 오면(`loadeddata`) 0.5초 지점으로 옮긴다. 처음이 검은 화면인 영상이 많아서다.
3. 옮기기가 끝나면(`seeked`) 그 장면을 캔버스에 그려 긴 변 1,280px JPEG로 만든다.

움직임 줄이기를 켠 사람에게는 이 포스터가 배경 전체이기 때문에 사진 썸네일(640px)보다 크게 만든다. 브라우저가 그 코덱을 풀지 못하면 어두운 그라데이션 그림을 대신 쓰고, 재생 표시로 동영상인 것을 알린다.

## 서버에서 확인하는 것

파일 형식은 이름이나 브라우저가 보낸 형식을 믿지 않고 파일 앞부분으로 본다. 이미지는 원래 이렇게 했고(PNG·JPEG·GIF·WebP), MP4를 더했다.

- MP4는 4~8바이트가 `ftyp`이고, 그 뒤 4글자(주 브랜드)가 `isom`·`mp42`·`avc1` 같은 MP4 값이어야 한다.
- QuickTime(`qt  `)은 받지 않는다. 브라우저마다 틀기도 하고 못 틀기도 해서다.
- 썸네일은 늘 이미지여야 한다.

크기 한도는 사진 10MB, 동영상 30MB다. 올린 파일 표의 DB 제약(CHECK)이 10MB였기 때문에, 새 마이그레이션을 만들어 30MB로 늘렸다. 이미 배포한 마이그레이션은 고치지 않는다. 10MB 한도는 API가 그대로 지키고, 30MB까지는 배경화면 동영상만 받는다.

파일을 내려 주는 `/files/:id`는 이제 `Range` 요청을 받는다. `<video>`는 파일을 앞부분부터 나눠 받는데, Safari는 서버가 `206 Partial Content`로 답하지 않으면 동영상을 틀지 않는다. 동영상도 이미지처럼 `inline`으로 내려 준다.

사이트의 보안 정책(CSP)에는 이미 `media-src`에 API 주소가 들어 있어서 따로 고칠 것이 없었다.

## 확인

- 서버 단위 시험: MP4 판별(브랜드, 상자 크기, QuickTime 거절), Range 머리말 읽기
- 서버 e2e 시험(실제 PostgreSQL): MP4 올리기, `video: true`, 206 응답, 416, 크기 한도(이미지 10MB·동영상 30MB)
- 화면 단위 시험: 설정에서 동영상 주소를 읽고, 안전하지 않은 주소는 버리기
- Playwright: 관리자가 MP4를 올리면 원본 그대로 가고 포스터가 JPEG로 만들어지는지, 방문자가 고르면 배경에서 재생되는지, 탭을 가리면 멈추는지, 움직임 줄이기에서 포스터만 보이는지, 휴대폰 홈 화면에서도 깔리는지

시험용 Chromium은 H.264를 풀지 못한다. 그래서 시험에서는 브라우저의 `MediaRecorder`로 색이 바뀌는 캔버스를 1초 녹화해 VP9을 담은 MP4를 만들어 썼다.
