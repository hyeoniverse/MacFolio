## 들어가기 전에

## 운영체제의 목적과 역할

### 정의

운영체제는 하드웨어와 사용자 사이에서 인터페이스를 제공하고, ==한정된 시스템 자원을 효율적으로 관리해 컴퓨터의 성능을 높이는 시스템 소프트웨어==다. 여기서 인터페이스는 두 가지 뜻을 가진다. 사용자에게는 마우스로 창을 끌고 아이콘을 누르는 GUI(Graphical User Interface)나 명령을 입력하는 셸(shell)을 제공하고, 프로그램에게는 "파일을 열어라", "메모리를 더 달라" 같은 요청을 받는 시스템 호출을 제공한다.

운영체제가 없는 컴퓨터를 생각하면 역할이 분명해진다. 메모 앱이 파일을 저장하려면 SSD 컨트롤러의 레지스터에 명령을 직접 써야 하고, SSD 제조사가 바뀌면 프로그램을 다시 작성해야 한다. 음악 앱과 메모 앱을 동시에 실행하면 두 프로그램이 같은 메모리 주소를 쓰지 않도록 서로 조율할 방법도 없다. 운영체제는 이런 하드웨어 제어와 자원 배분을 한곳에 모아, 응용 프로그램이 `open`, `write` 같은 공통 기능만 호출하게 한다.

| 소프트웨어 구분   | 뜻                                                   | 예                                |
| ----------------- | ---------------------------------------------------- | --------------------------------- |
| 시스템 소프트웨어 | 하드웨어를 제어하고 다른 프로그램의 실행 환경을 제공 | 운영체제, 장치 드라이버, 컴파일러 |
| 응용 소프트웨어   | 사용자가 원하는 특정 작업을 수행                     | 브라우저, 워드프로세서, 게임      |

### 목적

운영체제의 목적은 한정된 하드웨어 자원을 효율적이고 안전하게 사용하게 하는 것이다. 성능 측면에서는 다음 지표를 개선하는 것이 목표다.

| 목표             | 뜻                                                                      |
| ---------------- | ----------------------------------------------------------------------- |
| 처리량 향상      | 단위 시간당 완료하는 작업 수를 늘린다                                   |
| 응답 시간 단축   | 사용자가 명령을 입력한 뒤 첫 반응이 나오기까지의 시간을 줄인다          |
| 신뢰도 향상      | 오류 없이 동작하고, 한 프로그램의 오류가 시스템 전체로 번지지 않게 한다 |
| 사용 가능도 향상 | 필요한 시각에 시스템을 사용할 수 있는 비율을 높인다                     |

네 목표는 서로 부딪히기도 한다. 처리량만 보면 CPU를 한 작업에 오래 맡기는 편이 문맥 교환이 적어 유리하지만, 그러면 다른 사용자가 입력한 명령의 응답 시간이 길어진다. 응답 시간은 =="극대화"가 아니라 "단축"이 목표==라는 점도 구분해 둔다. 운영체제의 설계는 사용 목적(서버, 데스크톱, 스마트폰, 자동차 제어기)에 따라 이 목표 사이의 균형점을 고르는 일이다.

### 관리하는 자원

| 영역          | 하는 일                                                                      |
| ------------- | ---------------------------------------------------------------------------- |
| 프로세스 관리 | 프로그램 실행 생성·종료, CPU 시간 배분(스케줄링), 프로세스 간 통신과 동기화  |
| 메모리 관리   | 프로세스마다 메모리 영역 할당·회수, 다른 프로세스의 메모리 접근 차단         |
| 입출력 관리   | 장치 드라이버로 디스크·키보드·네트워크 카드를 제어하고, 공통 인터페이스 제공 |
| 파일 관리     | 디스크의 블록을 파일과 디렉터리로 구성하고, 접근 권한 검사                   |
| 보호와 보안   | 사용자 인증, 권한 분리, 프로세스 격리                                        |

각 영역을 조금 더 풀면 다음과 같다.

- **프로세스 관리**: 실행 중인 프로그램(프로세스)을 만들고 종료하며, 준비된 프로세스 중 누구에게 CPU를 줄지 결정한다. 프로세스끼리 데이터를 주고받는 통신(파이프, 소켓, 공유 메모리)과, 같은 데이터를 동시에 고치지 않게 하는 동기화도 포함한다.
- **기억장치 관리**: 주기억장치(RAM)의 어느 영역을 어느 프로세스에 줄지 결정하고, 프로세스가 끝나면 회수한다. 가상 메모리로 RAM보다 큰 주소 공간을 제공하고, 한 프로세스가 다른 프로세스의 메모리를 읽지 못하게 막는다.
- **입출력장치 관리**: 키보드, 디스크, 프린터, 네트워크 카드는 제조사마다 제어 방식이 다르다. 운영체제는 장치마다 장치 드라이버(device driver)를 두고, 응용 프로그램에는 "읽기", "쓰기"라는 같은 인터페이스를 제공한다. 장치가 작업을 마치면 CPU에 인터럽트(interrupt) 신호를 보내고, 운영체제가 그 신호를 처리한다.
- **정보 관리**: 디스크의 데이터를 파일과 디렉터리 단위로 구성하고, 파일의 생성·삭제·읽기·쓰기와 접근 권한을 관리한다. 이 영역을 파일 관리라고도 한다.

![사용자 모드의 브라우저, 편집기, 셸, 라이브러리가 시스템 호출 인터페이스를 거쳐 커널 모드의 프로세스 관리, 기억장치 관리, 입출력 관리, 정보 관리에 요청하고, 커널이 하드웨어를 제어한다](./images/csintro-operating-systems-structure.svg '운영체제가 관리하는 네 영역은 모두 커널 안에 있다')

### 커널과 시스템 호출

운영체제의 핵심부를 커널(kernel)이라고 한다. CPU는 두 가지 실행 모드를 하드웨어로 구분한다. 커널은 모든 명령어와 모든 메모리에 접근할 수 있는 커널 모드(kernel mode)에서 실행되고, 일반 응용 프로그램은 일부 명령어와 자기 메모리만 쓸 수 있는 사용자 모드(user mode)에서 실행된다.

응용 프로그램이 파일을 읽거나 네트워크로 데이터를 보내려면 커널에 요청해야 한다. 이 요청을 ==시스템 호출(system call)==이라고 한다. 예를 들어 C의 `printf("hello\n")`는 내부에서 `write(1, "hello\n", 6)` 시스템 호출을 실행하고, CPU는 커널 모드로 전환되어 커널의 코드가 화면(표준 출력)에 글자를 쓴 뒤 사용자 모드로 돌아온다.

==이 구분이 보안의 기반==이다. 응용 프로그램이 디스크 장치를 직접 제어할 수 없으므로, 커널은 모든 파일 접근 요청에서 권한을 검사할 수 있다. 악성코드가 시스템 전체를 장악하려면 커널 모드 권한을 얻어야 하므로, 권한 상승(privilege escalation) 취약점이 공격의 주요 목표가 된다.

### 부팅

운영체제도 디스크에 저장된 프로그램이므로, 실행하려면 누군가 메모리에 적재해야 한다. 그러나 전원을 막 켠 시각의 RAM은 비어 있다. 이 문제는 메인보드의 플래시 메모리(ROM)에 저장된 펌웨어가 해결한다. 전원이 들어오면 CPU는 정해진 주소에서 펌웨어를 실행하고, 펌웨어가 다음 단계 프로그램을 적재하는 식으로 운영체제까지 단계적으로 올라간다. 이 과정을 부팅(booting)이라고 한다.

![전원 공급, 펌웨어 실행, 자체 진단 POST, 부트 로더 적재, 부트 로더가 커널 적재, 커널이 첫 프로세스 실행 순서로 진행하고, POST에서 오류가 나면 오류 메시지를 출력하고 멈춘다. 보안 부팅은 각 단계의 서명을 검증한다](./images/csintro-operating-systems-boot.svg '부팅은 작은 프로그램이 더 큰 프로그램을 차례로 적재하는 과정이다')

1. **전원 공급**: 전원 장치가 안정된 전압을 공급하면 CPU가 초기화된다.
2. **펌웨어 실행**: CPU가 ROM의 펌웨어를 실행한다. 오랫동안 바이오스(BIOS, Basic Input/Output System)가 이 역할을 했고, 2010년대 이후의 PC는 대부분 UEFI(Unified Extensible Firmware Interface)를 쓴다.
3. **자체 진단(POST, Power-On Self-Test)**: 메모리, 키보드, 저장 장치 같은 필수 하드웨어가 응답하는지 점검한다. 이상이 있으면 오류 메시지나 경고음(beep code)을 내고 멈춘다.
4. **부트 로더 적재**: 부팅 순서에 지정된 저장 장치에서 부트 로더(boot loader)를 주기억장치로 읽어 온다. Linux의 GRUB, Windows의 Windows Boot Manager가 예다.
5. **커널 적재**: 부트 로더가 운영체제 커널 파일을 메모리에 적재하고 실행을 넘긴다.
6. **운영체제 구동**: 커널은 장치를 초기화하고 첫 사용자 프로세스(Linux의 `systemd`, macOS의 `launchd`)를 실행한다. 이 프로세스가 로그인 화면 등 나머지 프로그램을 차례로 실행한다.

| 비교        | BIOS                     | UEFI                                          |
| ----------- | ------------------------ | --------------------------------------------- |
| 등장        | 1981년 IBM PC의 BIOS     | 2006년 UEFI 2.0 규격 공개, 2010년대 PC의 표준 |
| 부팅 디스크 | MBR, 2TiB 이하 디스크    | GPT, 2TiB를 넘는 디스크                       |
| 보안        | 부트 로더 검증 기능 없음 | 보안 부팅(Secure Boot)으로 서명 검증          |
| 실행 환경   | 16비트 실모드            | 32·64비트 모드, 드라이버와 네트워크 기능 포함 |

보안 부팅은 각 단계가 다음 단계 프로그램의 ==전자 서명을 검증한 뒤에만 실행을 넘기는== 방식이다. 부트킷(bootkit)처럼 운영체제보다 먼저 실행되어 백신을 무력화하는 악성코드는 부트 로더나 커널을 변조해야 하는데, 서명이 맞지 않으면 실행 자체가 거부된다. Apple 실리콘 Mac과 iPhone은 칩 안의 읽기 전용 Boot ROM에서 시작해 같은 방식의 서명 검증을 거친다.

## 처리 방식에 따른 분류

운영체제는 하드웨어 가격과 사용 형태에 맞춰 발전했다. 아래 분류는 시대 순서이기도 하고, 오늘날의 운영체제는 여러 방식을 함께 지원한다.

| 방식            | 동작                                                                                                    | 예                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 일괄 처리       | 작업을 모아 두었다가 한 번에 순서대로 처리. 실행 중 사용자와 상호작용 없음                              | 월말 급여 계산, 야간 백업                            |
| 다중 프로그래밍 | 여러 프로그램을 메모리에 적재하고, 실행 중인 프로그램이 입출력을 기다리는 동안 다른 프로그램에 CPU 할당 | 1960년대 메인프레임 OS                               |
| 시분할          | CPU 시간을 짧은 조각(타임 슬라이스)으로 나눠 여러 사용자·프로그램에 번갈아 할당해 대화형 사용 가능      | 유닉스, 오늘날의 모든 데스크톱 OS                    |
| 다중 처리       | CPU(코어)가 둘 이상이라 실제로 여러 명령 흐름을 동시에 실행                                             | 멀티코어 PC와 스마트폰                               |
| 실시간          | 정해진 마감 시간 안에 처리를 끝내는 것을 보장. 경성(hard)은 마감을 넘기면 실패, 연성(soft)은 품질 저하  | 자동차 에어백 제어, 산업용 로봇, 영상 스트리밍(연성) |
| 분산            | 네트워크로 연결된 여러 컴퓨터가 작업과 자원을 나눠 처리                                                 | 클라우드 클러스터                                    |

다중 프로그래밍의 효과는 숫자로 보면 분명하다. 프로그램 하나가 실행 시간의 80%를 디스크 입출력을 기다리는 데 쓴다면, 그 프로그램만 메모리에 있으면 CPU 사용률은 20%다. 같은 성질의 프로그램 네 개를 메모리에 두면 네 개가 모두 동시에 입출력을 기다릴 확률이 `0.8^4 \approx 0.41{:math}`이므로, CPU 사용률은 약 59%로 올라간다.

![단일 프로그래밍에서는 A가 디스크를 읽는 동안 CPU가 유휴 상태이고, 다중 프로그래밍에서는 그 시간에 B가 CPU를 사용해 CPU 사용률이 40%에서 약 80%로 오른다](./images/csintro-operating-systems-multiprogramming.svg '입출력 대기 시간을 다른 프로그램의 연산으로 채우는 것이 다중 프로그래밍이다')

각 방식을 조금 더 자세히 보면 다음과 같다.

**일괄 처리 시스템**(batch processing system)은 자료가 발생할 때마다 처리하지 않고, 일정 기간 또는 일정량이 모일 때까지 보관했다가 한꺼번에 처리한다. 전기·수도·가스 요금 계산은 한 달 치 검침 값을 모아 월말에 한 번에 계산하고, 급여 계산과 대규모 시험 채점도 같은 방식이다. 사용자가 중간에 개입할 수 없으므로 응답 시간은 길지만, 준비 작업을 한 번만 하면 되므로 대량 처리에 효율적이다. 오늘날 은행의 야간 정산 작업과 `cron`으로 예약한 백업 스크립트가 일괄 처리의 후손이다.

![사용자 1~4가 보낸 작업 1~4를 관리자가 모아 작업 1과 3은 Batch 1로, 작업 2와 4는 Batch 2로 묶어 컴퓨터에 한꺼번에 넘긴다](./images/csintro-operating-systems-batch.jpg '일괄 처리 시스템은 작업을 묶음(batch) 단위로 모아 처리한다. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-4')

**다중 프로그래밍 시스템**(multiprogramming system)은 여러 프로그램을 주기억장치에 함께 적재하고 CPU를 번갈아 사용하게 한다. 핵심은 ==입출력 대기 시간의 활용==이다. 디스크 읽기 한 번은 CPU 명령 수백만 개를 실행할 시간이 걸리므로, 그동안 CPU를 다른 프로그램에 넘기면 CPU가 유휴 상태로 남지 않는다. 위 그림에서 A만 있을 때는 CPU 사용률이 40%였고, B를 함께 두자 약 80%로 올랐다.

**다중 처리 시스템**(multiprocessing system)은 CPU를 두 개 이상 탑재해 실제로 여러 작업을 같은 순간에 처리한다. 목적은 처리 능력 증대와 신뢰성 향상이다. CPU 하나가 고장 나도 나머지가 작업을 이어받을 수 있기 때문이다. 오늘날에는 칩 하나에 코어 여러 개를 넣은 멀티코어 프로세서가 일반적이다. 다중 프로그래밍은 ==CPU 하나를 번갈아 쓰는 병행(concurrency)==, 다중 처리는 ==여러 CPU가 동시에 실행하는 병렬(parallelism)==이라는 점이 다르다.

**시분할 시스템**(time-sharing system)은 각 사용자(프로그램)에게 수~수십 밀리초 단위의 CPU 시간을 번갈아 할당한다. 전환이 매우 빠르므로 각 사용자는 컴퓨터를 혼자 쓰는 것처럼 느끼고, 명령을 입력하면 곧바로 결과를 보는 대화형(interactive) 사용이 가능해진다. 1961년 MIT의 CTSS가 초기 사례이고, 유닉스는 처음부터 시분할 운영체제로 설계되었다.

![작업 1, 2, 3이 time slice 길이만큼 (1), (2), (3), (4), (5), (6) 순서로 번갈아 CPU를 사용하는 시간축 그림](./images/csintro-operating-systems-timesharing.jpg '시분할 시스템은 작업 1, 2, 3에 같은 길이의 타임 슬라이스를 돌아가며 할당한다. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-7')

그림에서 작업 1은 (1)에서 타임 슬라이스를 다 쓰면 작업이 끝나지 않았어도 CPU를 작업 2에 넘기고, 작업 3까지 한 바퀴 돈 뒤 (4)에서 이어서 실행한다. 타임 슬라이스가 10밀리초이고 작업이 3개라면 각 작업은 30밀리초마다 한 번씩 CPU를 받으므로, 사람이 느끼기에는 세 작업이 동시에 진행된다.

**실시간 시스템**(real-time system)은 입력된 데이터를 즉시 처리해 정해진 시간 안에 결과를 내는 것을 보장한다. 평균 속도보다 ==최악의 경우에도 마감을 지키는지==가 중요하다.

| 구분       | 마감을 넘기면                      | 예                                         |
| ---------- | ---------------------------------- | ------------------------------------------ |
| 경성(hard) | 시스템 실패. 인명·재산 피해 가능   | 에어백 전개, 항공기 비행 제어, 심박 조율기 |
| 연성(soft) | 결과의 가치가 떨어지지만 계속 동작 | 영상 통화, 동영상 재생, 온라인 게임        |

에어백은 충돌 감지 후 수십 밀리초 안에 펴져야 하므로, 이런 제어기에는 실시간 운영체제(RTOS)를 쓴다. 자동차용으로는 기능 안전 표준 ISO 26262 인증을 받은 VxWorks 같은 RTOS가 있다. 동영상은 프레임 하나가 늦게 표시되면 화면이 잠깐 끊길 뿐이므로 일반 운영체제로도 충분하다.

**분산 처리 시스템**(distributed processing system)은 네트워크로 연결된 여러 컴퓨터에 작업과 자원을 나눠 처리한다. 설계 목적은 자원 공유, 연산 속도와 신뢰성 향상, 통신 기능 활용이다. 검색 엔진이 수천 대 서버에 색인을 나눠 저장하고 검색 요청을 동시에 처리하는 구조, 클라우드의 데이터베이스가 데이터를 세 지역에 복제해 한 지역이 정전되어도 서비스를 유지하는 구조가 예다.

![인터넷 IP 네트워크를 중심으로 데이터베이스 서버, 미디어 서버, 프린트 서버, 영상 정보기기, 웹 서버, 데스크톱이 연결되어 있다](./images/csintro-operating-systems-distributed.jpg '분산 처리 시스템은 역할이 다른 여러 컴퓨터가 네트워크로 자원을 나눠 쓴다. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-9')

## 대표적인 운영체제

범용 운영체제(general-purpose OS)는 특정 장치나 용도에 한정하지 않고 여러 종류의 응용 프로그램을 실행하는 운영체제다. PC와 서버의 범용 운영체제는 유닉스, 리눅스, Windows, macOS 네 계열로 나눌 수 있다. Android와 iOS는 각각 리눅스 커널과 macOS의 XNU 커널을 바탕으로 만든 모바일 운영체제다.

| 운영체제 | 시작                                      | 특징                                                                                                                     |
| -------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 유닉스   | 1969년 벨 연구소, 켄 톰프슨과 데니스 리치 | 1973년 C로 다시 작성되어 다른 하드웨어로 이식이 쉬워짐. 다중 사용자·시분할. 이후 BSD 등으로 분화                         |
| 리눅스   | 1991년 리누스 토르발스                    | 유닉스와 호환되는 커널을 새로 작성. GPL 라이선스로 소스 코드를 공개하고 수정·재배포 허용. Android와 대부분의 서버가 사용 |
| Windows  | 1985년 Microsoft, MS-DOS 위의 GUI         | 현재 버전은 1993년 Windows NT 커널 계열. 개인용 PC 점유율이 가장 높다                                                    |
| macOS    | 2001년 Mac OS X, NeXTSTEP 기반            | 커널 XNU는 Mach 마이크로커널과 BSD 코드를 결합. 유닉스 인증(UNIX 03)을 받은 운영체제                                     |

### 유닉스

유닉스는 1969년 벨 연구소의 켄 톰프슨(Ken Thompson)이 DEC의 PDP-7 컴퓨터에서 작은 프로그램 모음으로 시작했다. 1973년 데니스 리치(Dennis Ritchie)와 함께 커널을 C 언어로 다시 작성하면서, 어셈블리어로 작성된 다른 운영체제와 달리 ==C 컴파일러만 있으면 새 하드웨어로 옮길 수 있게== 되었다. 이후 캘리포니아 대학교 버클리의 BSD와 AT&T의 System V로 갈라졌고, 여러 회사가 각자의 유닉스(Solaris, AIX, HP-UX)를 만들었다.

![캐비닛 여러 개로 이루어진 DEC PDP-7 미니컴퓨터 본체와 테이프 장치](./images/csintro-operating-systems-unix.jpg '유닉스가 처음 개발된 DEC PDP-7. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-10')

유닉스가 남긴 설계 원칙은 지금의 운영체제에도 그대로 남아 있다.

- **모든 것은 파일**: 디스크의 파일뿐 아니라 터미널, 장치(`/dev/disk0`)도 파일처럼 `open`, `read`, `write`로 다룬다.
- **작은 프로그램의 조합**: `ls`, `grep`, `sort`처럼 한 가지 일만 하는 프로그램을 파이프(`|`)로 연결해 복잡한 작업을 만든다.
- **다중 사용자와 권한**: 사용자마다 계정과 UID가 있고, 파일마다 소유자·그룹·기타 사용자의 읽기·쓰기·실행 권한이 있다.

현재 유닉스는 내장 컨트롤러부터 메인프레임까지 실행되는 개방형 표준으로 자리 잡았고, POSIX 표준과 The Open Group의 UNIX 인증이 "유닉스다움"의 기준이 된다.

### 리눅스

리눅스는 1991년 핀란드 헬싱키 대학교 학생 리누스 토르발스(Linus Torvalds)가 개인용 컴퓨터(인텔 80386)에서 실행되는 유닉스 호환 커널로 작성해 공개했다. ==유닉스 코드를 가져오지 않고 처음부터 새로 작성==했으며, GNU 프로젝트의 셸·컴파일러·유틸리티와 결합해 완전한 운영체제가 되었다.

![왼쪽은 무대에서 발표하는 리누스 토르발스, 오른쪽은 Ubuntu 리눅스의 데스크톱과 소프트웨어 센터 창](./images/csintro-operating-systems-linux.jpg '리누스 토르발스와 Ubuntu 리눅스의 실행 화면. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-11')

리눅스 커널에 패키지 관리자와 기본 프로그램을 묶어 배포하는 단위를 배포판(distribution)이라고 한다.

| 배포판      | 계열    | 주 용도                            |
| ----------- | ------- | ---------------------------------- |
| Ubuntu      | Debian  | 데스크톱, 클라우드 서버            |
| Debian      | Debian  | 서버, 안정성 중시                  |
| Fedora      | Red Hat | 최신 기술을 먼저 적용하는 데스크톱 |
| RHEL, Rocky | Red Hat | 기업 서버                          |
| Alpine      | 독자    | 컨테이너 이미지(작은 크기)         |

전 세계 상위 500대 슈퍼컴퓨터가 모두 리눅스를 쓰고, Android 스마트폰도 리눅스 커널 위에서 동작한다.

> [!NOTE] 리눅스와 오픈 소스 라이선스
> 리눅스 커널은 GPL 버전 2로 배포된다. 누구나 소스 코드를 받아 수정하고 재배포할 수 있으며, 수정한 커널을 배포하는 경우 그 소스 코드도 같은 조건으로 공개해야 한다. 이 조건 덕분에 Ubuntu, Debian, Fedora 같은 여러 배포판(distribution)이 같은 커널을 공유한다.

### Windows

Microsoft는 1981년 IBM PC용 명령줄 운영체제 MS-DOS를 공급했고, 1983년 11월 Windows를 발표한 뒤 MS-DOS 위에서 실행되는 그래픽 환경인 Windows 1.0을 1985년 11월에 출시했다. 이후 Windows는 두 계열로 나뉘어 발전하다가 2001년 Windows XP에서 하나로 합쳐졌다.

| 계열    | 버전               | 특징                                                                           |
| ------- | ------------------ | ------------------------------------------------------------------------------ |
| 9x 계열 | Windows 95, 98, Me | MS-DOS 기반. 32비트 응용 프로그램을 실행하지만 16비트 코드가 남아 있음. 가정용 |
| NT 계열 | Windows NT, 2000   | 처음부터 새로 설계한 32비트 커널. NTFS, 사용자 권한, 네트워킹. 업무용          |
| 통합    | XP 이후 모든 버전  | NT 커널 위에 9x의 편의 기능을 결합                                             |

표 이후로는 Windows 10(2015)이 "마지막 Windows"를 표방하며 기능을 꾸준히 업데이트하는 방식으로 바뀌었고, Windows 11(2021)은 TPM 2.0 보안 칩과 보안 부팅을 지원하는 UEFI 펌웨어를 설치 요구 사항으로 정했다. 보안 측면에서 보면 Windows의 역사는 ==사용자 권한 분리를 강화한 과정==이다. 9x 계열에는 사용자 권한 개념이 사실상 없어 어떤 프로그램이든 시스템 파일을 고칠 수 있었고, Vista의 사용자 계정 컨트롤(UAC)부터 관리자 계정도 평소에는 일반 권한으로 실행하고 필요한 경우에만 확인 창을 띄워 권한을 높인다.

Apple은 1984년 매킨토시와 함께 GUI 운영체제를 내놓았다. 이 운영체제는 두 시기로 나뉜다.

클래식 Mac OS는 프로그램이 스스로 CPU를 양보해야 다른 프로그램이 실행되는 협력형(cooperative) 멀티태스킹이었고 메모리 보호가 없어, 프로그램 하나가 멈추면 컴퓨터 전체가 멈췄다. Mac OS X는 운영체제가 CPU를 강제로 회수하는 선점형 멀티태스킹과 프로세스별 메모리 보호를 도입했다. 이 차이는 뒤에서 다룰 선점·비선점 스케줄링, 가상 메모리와 직접 이어진다. iPhone의 iOS, Apple Watch의 watchOS도 같은 XNU 커널을 쓴다.

## 프로세스

### 프로그램과 프로세스

프로그램(program)은 디스크에 저장된 실행 파일이다. 프로세스(process)는 그 프로그램이 ==메모리에 적재되어 실행 중인 상태==다. 같은 프로그램으로 여러 프로세스를 만들 수 있다. 터미널 창을 세 개 열면 `zsh` 프로그램 하나에서 프로세스 세 개가 생기고, 각 프로세스는 별도의 메모리와 프로세스 번호(PID)를 가진다.

운영체제는 프로세스마다 프로세스 제어 블록(PCB, Process Control Block)이라는 자료 구조를 만들어 관리한다. 프로세스가 생성되는 시각에 만들어지고 종료되면 삭제된다.

| PCB 항목                   | 내용                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| 프로세스 식별자            | PID, 부모 프로세스의 PID                                                |
| 상태                       | 준비, 실행, 대기 등                                                     |
| 프로그램 카운터와 레지스터 | CPU를 다른 프로세스에 넘길 시각의 레지스터 값 (다시 실행할 시각에 복원) |
| 스케줄링 정보              | 우선순위, 사용한 CPU 시간                                               |
| 메모리 정보                | 페이지 테이블 위치                                                      |
| 입출력·파일 정보           | 열린 파일 목록, 작업 디렉터리                                           |
| 보안 정보                  | 사용자 ID(UID), 그룹 ID                                                 |

![PCB를 위에서부터 포인터와 프로세스 상태, 프로세스 식별자, 프로그램 카운터, 레지스터, 기억장치 관리 정보, 개방된 파일 리스트, 기타 정보 칸으로 나눈 그림](./images/csintro-operating-systems-pcb.jpg 'PCB의 구성. 맨 위 포인터는 같은 큐에 있는 다음 PCB를 가리켜 준비 큐를 연결 리스트로 만든다. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-15')

CPU를 한 프로세스에서 다른 프로세스로 넘기려면 현재 레지스터 값을 PCB에 저장하고 다음 프로세스의 값을 복원해야 한다. 이를 ==문맥 교환(context switch)==이라고 한다. 문맥 교환 중에는 어떤 프로세스의 작업도 진행되지 않으므로, 너무 자주 일어나면 성능이 떨어진다.

![P1이 실행 중 인터럽트가 발생하면 커널이 P1의 레지스터와 PC를 PCB1에 저장하고 PCB2에서 복원해 P2를 실행한다. P2가 시스템 호출로 대기하면 반대로 PCB2에 저장하고 PCB1에서 복원한다](./images/csintro-operating-systems-context-switch.svg 'PCB는 프로세스를 중단했다가 같은 지점에서 다시 실행하기 위한 기록이다')

문맥 교환은 두 가지 계기로 일어난다. 하나는 타이머 인터럽트다. 운영체제는 하드웨어 타이머를 설정해 일정 시간마다 CPU를 되돌려 받는다. 다른 하나는 프로세스가 시스템 호출로 디스크 읽기처럼 오래 걸리는 작업을 요청해 스스로 대기 상태로 가는 경우다. 문맥 교환 한 번의 비용은 수 마이크로초 수준이지만, 새 프로세스의 데이터가 CPU 캐시에 없어서 생기는 간접 비용이 더 크다.

### 프로세스 상태

프로세스는 실행되는 동안 다음 다섯 상태를 오간다.

![프로세스 상태 전이도. 생성에서 승인되면 준비, 디스패치되면 실행, 타임 슬라이스가 만료되면 다시 준비, 입출력을 요청하면 대기, 입출력이 완료되면 준비, 실행을 마치면 종료로 이동한다](./images/csintro-operating-systems-states.svg '단일 코어에서 실행 상태의 프로세스는 언제나 하나뿐이다')

| 상태 | 뜻                                                                                             |
| ---- | ---------------------------------------------------------------------------------------------- |
| 생성 | 프로세스를 만들고 PCB와 메모리를 할당하는 중                                                   |
| 준비 | 실행할 준비가 끝났고 CPU 할당을 기다리며 준비 큐(ready queue)에 있음                           |
| 실행 | CPU를 할당받아 명령어를 실행 중                                                                |
| 대기 | 디스크 읽기, 키보드 입력, 네트워크 응답 같은 사건을 기다리는 중. CPU를 할당해도 진행할 수 없음 |
| 종료 | 실행을 마쳤고 운영체제가 자원을 회수하는 중                                                    |

예를 들어 텍스트 편집기에서 파일을 열면, 편집기 프로세스는 디스크 읽기를 요청하고 대기 상태로 바뀐다. 그동안 CPU는 준비 큐의 다른 프로세스를 실행한다. 디스크가 읽기를 마치고 인터럽트를 보내면 편집기는 준비 상태로 돌아가고, 스케줄러가 다시 CPU를 할당하면 실행 상태가 되어 화면에 내용을 표시한다.

### 스레드

스레드(thread)는 프로세스 안의 실행 흐름 단위다. 프로세스 하나에 스레드가 여러 개 있으면, 스레드들은 코드·전역 변수·열린 파일 같은 프로세스의 자원을 공유하고, ==각자의 프로그램 카운터·레지스터·스택만 별도로== 가진다.

| 비교           | 프로세스                                       | 스레드                                                         |
| -------------- | ---------------------------------------------- | -------------------------------------------------------------- |
| 메모리         | 프로세스마다 독립된 주소 공간                  | 같은 프로세스의 스레드끼리 주소 공간 공유                      |
| 생성·전환 비용 | 큼(주소 공간 생성, 페이지 테이블 교체)         | 작음                                                           |
| 격리           | 한 프로세스의 오류가 다른 프로세스에 영향 없음 | 한 스레드가 메모리를 망가뜨리면 프로세스 전체가 종료될 수 있음 |
| 예             | Chrome이 탭마다 별도 프로세스 사용             | 웹 서버가 요청마다 스레드 하나로 처리                          |

Chrome과 Safari가 탭이나 사이트마다 별도 프로세스를 쓰는 이유가 격리다. 악성 웹 페이지가 렌더러의 취약점을 이용해도 그 탭의 프로세스 메모리에만 접근할 수 있고, 다른 탭의 로그인 정보는 운영체제의 프로세스 격리로 보호된다.

### 병행 프로세스와 동기화

두 개 이상의 연관된 프로세스(또는 스레드)가 동시에 실행되는 것을 병행 프로세스(concurrent process)라고 한다. 단일 CPU에서는 번갈아 실행되고, 멀티코어에서는 실제로 같은 순간에 실행된다. 어느 쪽이든 언제 문맥 교환이 일어날지 프로그램이 정할 수 없으므로, 공유 데이터를 다루면 실행할 때마다 결과가 달라지는 오류가 생길 수 있다.

여러 프로세스나 스레드가 같은 데이터를 동시에 변경하면 실행 순서에 따라 결과가 달라질 수 있다. 이를 ==경쟁 상태(race condition)==라고 한다. 예를 들어 두 스레드가 잔액 1000원인 계좌에서 동시에 100원을 출금하면, 두 스레드가 모두 1000을 읽고 900을 기록해 최종 잔액이 800이 아니라 900이 될 수 있다.

공유 데이터를 변경하는 코드 구간을 임계 구역(critical section)이라고 하고, 한 시각에 하나의 실행 흐름만 임계 구역에 들어가게 하는 것을 상호 배제(mutual exclusion)라고 한다. 운영체제와 언어는 이를 위해 뮤텍스(mutex) 락과 세마포어(semaphore)를 제공한다. 동기화(synchronization)는 이런 도구로 실행 순서를 맞추는 일 전체를 가리킨다.

출금 예를 코드로 쓰면 다음과 같다. `balance = balance - 100`은 한 줄이지만 CPU에서는 "읽기, 빼기, 쓰기" 세 명령으로 나뉘고, 그 사이에 다른 스레드가 끼어들 수 있다.

```c
#include <pthread.h>

int balance = 1000;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *withdraw(void *arg) {
	pthread_mutex_lock(&lock);   // 임계 구역 진입: 다른 스레드는 여기서 대기
	int b = balance;             // 1) 읽기
	b = b - 100;                 // 2) 빼기
	balance = b;                 // 3) 쓰기
	pthread_mutex_unlock(&lock); // 임계 구역 퇴장
	return NULL;
}
```

락이 없으면 두 스레드가 모두 1)에서 1000을 읽은 뒤 3)에서 900을 쓸 수 있다. 락이 있으면 두 번째 스레드는 첫 번째가 `unlock`할 때까지 `lock`에서 대기하므로 최종 잔액은 항상 800이다.

| 용어      | 뜻                                                                   |
| --------- | -------------------------------------------------------------------- |
| 임계 구역 | 공유 자원을 읽고 쓰는 코드 구간                                      |
| 상호 배제 | 한 시각에 하나의 실행 흐름만 임계 구역에 들어가게 하는 성질          |
| 뮤텍스    | 상호 배제를 위한 락. 잠근 스레드만 풀 수 있다                        |
| 세마포어  | 정수 카운터. 동시에 N개까지 들어가게 하거나 실행 순서를 맞출 때 사용 |

경쟁 상태는 보안 취약점이 되기도 한다. 프로그램이 파일 권한을 검사한(check) 시각과 실제로 여는(use) 시각 사이에 공격자가 파일을 다른 파일의 심볼릭 링크로 바꾸면, 검사를 통과한 뒤 엉뚱한 파일을 열게 된다. 이를 TOCTOU(Time Of Check to Time Of Use) 취약점이라고 한다.

### 교착 상태

락을 쓰면 새로운 문제가 생긴다. 프로세스 P1이 자원 A를 잡은 채 자원 B를 기다리고, P2가 B를 잡은 채 A를 기다리면 둘 다 영원히 진행하지 못한다. 이를 교착 상태(deadlock)라고 한다. 다중 프로그래밍 시스템에서 하나 이상의 프로세스가 ==절대 일어나지 않을 사건을 기다리는 상태==다.

![프로세스 P1은 자원 1을 할당받고 자원 2를 요구하며, 프로세스 P2는 자원 2를 할당받고 자원 1을 요구해 순환이 생긴다](./images/csintro-operating-systems-deadlock-slide.jpg '두 프로세스가 서로의 자원을 기다리는 교착 상태. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-18')

일상의 예로는 좁은 일방 교차로의 네 방향에서 차가 동시에 진입해 서로 앞 차가 빠지기를 기다리는 상황이 있다. 교착 상태는 다음 네 조건이 **모두** 성립하는 경우에만 발생한다(Coffman 조건).

| 조건        | 뜻                                                                               |
| ----------- | -------------------------------------------------------------------------------- |
| 상호 배제   | 자원을 한 번에 한 프로세스만 사용할 수 있다                                      |
| 보유와 대기 | 자원을 가진 채로 다른 자원을 기다린다(점유와 대기라고도 한다)                    |
| 비선점      | 다른 프로세스가 가진 자원을 강제로 빼앗을 수 없다                                |
| 환형 대기   | P1은 P2의 자원을, P2는 P3의 자원을, …, Pn은 P1의 자원을 기다리는 순환이 존재한다 |

대응 방법은 네 가지다.

- **예방(prevention)**: 네 조건 중 하나가 성립하지 않게 설계한다. 예를 들어 모든 프로세스가 자원을 정해진 번호 순서로만 요청하게 하면 환형 대기가 생기지 않는다.
- **회피(avoidance)**: 자원을 할당하기 전에 교착 상태로 이어질 수 있는 상태인지 계산해 위험하면 할당을 미룬다. 은행원 알고리즘(banker's algorithm)이 대표적이다.
- **탐지(detection)와 회복(recovery)**: 교착 상태를 허용하되 주기적으로 자원 할당 그래프에서 순환을 찾고, 발견하면 프로세스를 종료하거나 자원을 회수한다. 데이터베이스가 교착 상태의 트랜잭션 하나를 취소하는 것이 예다. 회복 방법으로는 순환에 포함된 프로세스를 하나씩 종료하거나, 한 프로세스의 자원을 빼앗아(선점) 다른 프로세스에 주고 빼앗긴 프로세스를 처음부터 다시 실행하는 방법이 있다.

예방은 확실하지만 자원 사용률을 낮추고, 회피는 각 프로세스가 앞으로 필요한 자원의 최대량을 미리 알려야 해서 범용 운영체제에서는 쓰기 어렵다. 그래서 Linux, Windows, macOS 같은 범용 운영체제는 커널 내부에서는 락 순서 규칙으로 예방하고, 응용 프로그램끼리의 교착 상태는 대부분 그대로 두어 사용자가 응답 없는 프로그램을 강제 종료하게 한다.

## CPU 스케줄링

준비 큐에 여러 프로세스가 있을 때 다음에 어느 프로세스에 CPU를 할당할지 정하는 것이 CPU 스케줄링이다. 실행 중인 프로세스에서 운영체제가 CPU를 강제로 회수할 수 있으면 선점형(preemptive), 프로세스가 스스로 종료하거나 대기 상태로 갈 때까지 기다리면 비선점형(non-preemptive)이다.

### 스케줄링의 목적

스케줄링 기법을 고를 때 고려하는 목적은 다음과 같다. 모두를 동시에 최대로 만족시킬 수는 없으므로, 시스템의 용도에 따라 우선순위를 정한다.

| 목적                           | 뜻                                                              |
| ------------------------------ | --------------------------------------------------------------- |
| 공정성                         | 모든 프로세스를 정해진 규칙에 따라 공평하게 대우                |
| 처리량 최대화                  | 단위 시간당 완료하는 프로세스 수를 늘림                         |
| 응답 시간 최소화               | 대화형 사용자의 명령에 빨리 반응                                |
| 반환 시간 예측 가능            | 시스템 부하와 관계없이 작업이 끝나는 시각을 비슷하게 유지       |
| 자원의 균형적인 사용           | CPU, 메모리, 입출력장치가 놀지 않게 작업을 섞음                 |
| 응답 시간과 자원 활용도의 조화 | 빠른 응답을 위해 자원 활용도를 지나치게 희생하지 않음           |
| 무한 연기 배제                 | 어떤 프로세스도 끝없이 실행이 미뤄지지(기아) 않게 함            |
| 우선순위에 따른 실행 보장      | 중요한 프로세스를 먼저 실행                                     |
| 과도한 부하 방지               | 부하가 클 때 새 작업 수용을 늦춰 시스템 전체가 느려지지 않게 함 |

### 성능 지표

| 지표       | 정의                                         | 바람직한 방향 |
| ---------- | -------------------------------------------- | ------------- |
| CPU 사용률 | 전체 시간 중 CPU가 작업을 수행한 시간의 비율 | 높게          |
| 처리량     | 단위 시간당 완료한 프로세스 수               | 높게          |
| 반환 시간  | 도착부터 완료까지 걸린 시간                  | 짧게          |
| 대기 시간  | 준비 큐에서 기다린 시간의 합                 | 짧게          |
| 응답 시간  | 도착부터 처음 CPU를 할당받기까지의 시간      | 짧게          |

### 기법별 동작 비교

세 프로세스가 시각 0에 P1, P2, P3 순서로 도착하고, 각각 CPU를 5, 3, 1만큼 사용해야 한다고 하자.

![FCFS는 P1, P2, P3 순서로 0~5, 5~8, 8~9에 실행하고, SJF는 P3, P2, P1 순서로 0~1, 1~4, 4~9에 실행하고, 시간 할당량 2의 라운드 로빈은 P1, P2, P3, P1, P2, P1 순서로 번갈아 실행한다](./images/csintro-operating-systems-scheduling.svg '같은 작업이라도 순서에 따라 평균 대기 시간이 2.6배 차이 난다')

1. **FCFS(First-Come, First-Served)**: 도착 순서대로 실행하는 비선점형 기법이다. 구현이 단순하지만, 실행 시간이 긴 P1이 앞에 있으면 짧은 P2, P3가 오래 기다린다. 이를 호위 효과(convoy effect)라고 한다.
2. **SJF(Shortest Job First)**: 실행 시간이 가장 짧은 프로세스부터 실행하는 비선점형 기법이다. ==평균 대기 시간이 가능한 모든 순서 중 최소==임이 증명되어 있다. 다만 실제로는 실행 시간을 미리 알 수 없어 과거 실행 기록으로 추정하고, 짧은 작업이 계속 도착하면 긴 작업이 끝없이 밀리는 기아(starvation)가 생긴다.
3. **SRT(Shortest Remaining Time)**: SJF의 선점형 버전이다. 새 프로세스가 도착하면 실행 중인 프로세스의 남은 시간과 비교해 더 짧은 쪽을 실행한다.
4. **라운드 로빈(Round Robin, RR)**: 도착 순서대로 실행하되, 각 프로세스는 시간 할당량(time quantum) 동안만 실행하고 준비 큐 끝으로 이동하는 선점형 기법이다. 위 그림에서 할당량이 2이므로 P1이 2만큼 실행한 뒤 P2로 넘어간다. 평균 대기 시간은 FCFS와 같지만 응답 시간이 0, 2, 4로 고르게 짧아 대화형 시스템에 적합하다. 할당량이 너무 크면 FCFS와 같아지고, 너무 작으면 문맥 교환 비용이 커진다.
5. **HRN(Highest Response-ratio Next)**: SJF의 기아 문제를 줄인 비선점형 기법이다. 다음 응답률이 가장 높은 프로세스를 실행한다. ==오래 기다릴수록 응답률이 커지므로== 긴 작업도 결국 실행된다.

```math
\text{응답률} = \frac{\text{대기 시간} + \text{실행 시간}}{\text{실행 시간}}
```

6. **우선순위(Priority)**: 프로세스마다 우선순위를 부여하고 가장 높은 것부터 실행한다. 선점형과 비선점형 모두로 구현할 수 있다. 기아를 막기 위해 ==오래 기다린 프로세스의 우선순위를 점점 높이는 에이징(aging)==을 함께 쓴다.
7. **다단계 큐(MLQ, Multi-Level Queue)**: 프로세스를 성격(대화형, 일괄 처리 등)에 따라 여러 큐로 나누고, 큐마다 다른 기법을 적용한다. 프로세스는 처음 배정된 큐에서 다른 큐로 이동하지 않는다.
8. **다단계 피드백 큐(MLFQ, Multi-Level Feedback Queue)**: 큐 사이 이동을 허용한다. 새 프로세스는 가장 높은 우선순위 큐에서 짧은 할당량으로 시작하고, 할당량을 다 쓰면(CPU를 오래 쓰는 프로세스이면) 한 단계 낮은 큐로 내려간다. 상위 큐들은 라운드 로빈, 최하위 큐는 FCFS로 처리하는 구성이 일반적이다. 입출력을 자주 하는 대화형 프로세스는 상위 큐에 남아 빠르게 응답하고, 계산 위주 프로세스는 하위 큐에서 긴 할당량으로 실행된다.

위 예의 계산을 표로 정리하면 다음과 같다.

| 기법     | P1 대기 | P2 대기 | P3 대기 | 평균 대기 시간 | 평균 반환 시간 |
| -------- | ------- | ------- | ------- | -------------- | -------------- |
| FCFS     | 0       | 5       | 8       | 4.33           | 7.33           |
| SJF      | 4       | 1       | 0       | 1.67           | 4.67           |
| RR (q=2) | 4       | 5       | 4       | 4.33           | 7.33           |

반환 시간은 대기 시간에 실행 시간을 더한 값이다. 예를 들어 SJF에서 P1, P2, P3는 각각 시각 9, 4, 1에 완료되므로 평균 반환 시간은 `(9 + 4 + 1) / 3 \approx 4.67{:math}`이다. 세 프로세스가 모두 시각 0에 도착했으므로 완료 시각이 곧 반환 시간이다.

### 도착 시각이 다른 경우: SJF, SRT, HRN 계산

앞의 예는 모든 프로세스가 시각 0에 도착해 선점이 의미가 없었다. 도착 시각이 다르면 선점형과 비선점형의 차이가 드러난다. 다음 네 프로세스를 보자.

| 프로세스 | 도착 시각 | 실행 시간 |
| -------- | --------- | --------- |
| P1       | 0         | 7         |
| P2       | 1         | 4         |
| P3       | 2         | 1         |
| P4       | 3         | 3         |

![SJF는 P1, P3, P4, P2 순서, SRT는 P1, P2, P3, P2, P4, P1 순서, HRN은 P1, P3, P2, P4 순서로 실행하며 평균 대기 시간은 각각 5.00, 3.00, 5.25이다](./images/csintro-operating-systems-srt-hrn.svg '선점형 SRT가 평균 대기 시간이 가장 짧다')

**SJF(비선점)**

1. 시각 0에는 P1만 도착했으므로 P1을 실행한다. 비선점이므로 P1은 시각 7까지 실행한다.
2. 시각 7에 준비 큐에는 P2(4), P3(1), P4(3)가 있다. 가장 짧은 P3를 7~8에 실행한다.
3. 다음으로 짧은 P4를 8~11에, P2를 11~15에 실행한다.

**SRT(선점)**

1. 시각 0에 P1을 실행한다.
2. 시각 1에 P2가 도착한다. P2의 실행 시간 4가 P1의 남은 시간 6보다 짧으므로 P1을 중단하고 P2를 실행한다.
3. 시각 2에 P3가 도착한다. P3의 1이 P2의 남은 시간 3보다 짧으므로 P3를 2~3에 실행한다.
4. 시각 3에 P4가 도착한다. 남은 시간은 P1 6, P2 3, P4 3이다. P2와 P4가 같으면 먼저 도착한 P2를 3~6에 실행한다.
5. 이어서 P4를 6~9에, P1을 9~15에 실행한다.

**HRN(비선점)**

1. 시각 0~7에 P1을 실행한다.
2. 시각 7에 각 프로세스의 응답률을 계산한다. 대기 시간은 7에서 도착 시각을 뺀 값이다.

```math
\text{P2} = \frac{6 + 4}{4} = 2.5,\quad \text{P3} = \frac{5 + 1}{1} = 6,\quad \text{P4} = \frac{4 + 3}{3} \approx 2.33
```

3. 응답률이 가장 높은 P3를 7~8에 실행한다.
4. 시각 8에 다시 계산한다. P2는 `(7 + 4) / 4 = 2.75{:math}`, P4는 `(5 + 3) / 3 \approx 2.67{:math}`이므로 P2를 8~12에, 마지막으로 P4를 12~15에 실행한다.

| 기법 | P1 대기 | P2 대기 | P3 대기 | P4 대기 | 평균 대기 시간 | 평균 반환 시간 |
| ---- | ------- | ------- | ------- | ------- | -------------- | -------------- |
| SJF  | 0       | 10      | 5       | 5       | 5.00           | 8.75           |
| SRT  | 8       | 1       | 0       | 3       | 3.00           | 6.75           |
| HRN  | 0       | 7       | 5       | 9       | 5.25           | 9.00           |

대기 시간은 "완료 시각 − 도착 시각 − 실행 시간"이다. SRT는 평균 대기 시간이 가장 짧지만, 긴 P1은 8만큼 기다렸고 짧은 작업이 계속 도착하면 더 밀린다. HRN은 시각 8에서 SJF라면 P4(3)를 골랐을 자리에 더 오래 기다린 P2를 골랐다. 대기 시간이 응답률의 분자에 들어가 있기 때문이다. SRT는 남은 실행 시간을 계속 추적하고 비교해야 하므로 SJF보다 운영체제의 관리 부담이 크다.

### 우선순위와 다단계 큐

우선순위 스케줄링은 프로세스마다 숫자로 된 우선순위를 주고 가장 높은 것부터 실행한다. 유닉스 계열에서는 nice 값(-20~19, 작을수록 높은 우선순위)으로 사용자가 우선순위를 조정할 수 있다.

```bash
nice -n 10 ./backup.sh     # 우선순위를 낮춰 실행
renice -n 5 -p 12345       # 실행 중인 PID 12345의 nice 값 변경
```

![다단계 큐는 시스템, 대화형, 일괄 처리 큐가 고정되어 있고, 다단계 피드백 큐는 새 작업이 큐 0에서 시작해 할당량을 다 쓰면 아래 큐로 강등되고 오래 기다리면 승격된다](./images/csintro-operating-systems-mlfq.svg 'MLFQ는 실행 기록을 보고 프로세스의 성격을 스스로 판단한다')

다단계 큐(MLQ)는 작업의 성격에 따라 준비 큐를 여러 개 두고 큐마다 다른 기법을 적용한다. 큐 사이에는 고정된 우선순위가 있어서, 위 큐가 비어 있을 때만 아래 큐의 프로세스가 실행된다. 프로세스가 큐를 옮겨 다니지 않으므로 ==아래 큐의 프로세스는 기아에 빠질 수 있다==.

![최상위 우선순위부터 시스템 프로세스, 대화형 프로세스, 편집 프로세스, 일괄 처리형 프로세스, 응용 프로세스 큐가 있고, 도착한 프로세스는 한 큐에 배정되어 CPU를 선점 방식으로 할당받는다](./images/csintro-operating-systems-mlq.jpg '다단계 큐의 5단계 구성 예. 출처: 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미, 그림 5-25')

그림의 예에서는 시스템 프로세스 큐가 가장 높고 응용 프로세스 큐가 가장 낮다. 운영체제 자체의 작업과 사용자가 화면 앞에서 기다리는 대화형 작업을 먼저 처리하고, 결과를 나중에 받아도 되는 일괄 처리 작업은 위 큐가 비었을 때 실행한다. 아래 큐의 프로세스가 실행 중이더라도 위 큐에 새 프로세스가 도착하면 CPU를 빼앗기는 선점 방식이다.

다단계 피드백 큐(MLFQ)는 큐 사이 이동을 허용해 이 문제를 줄인다. 프로세스의 실행 시간을 미리 알 수 없다는 SJF의 한계를, 실행하면서 관찰한 결과로 보완하는 방식이다. 편집기처럼 키 입력을 기다리는 입출력 위주 프로세스는 할당량을 다 쓰기 전에 CPU를 내놓으므로 상위 큐에 남고, 동영상 인코딩처럼 계산만 하는 연산 위주 프로세스는 할당량을 계속 소진해 하위 큐로 내려간다. 하위 큐는 우선순위가 낮은 대신 할당량이 커서, 한 번 실행되면 오래 실행되므로 문맥 교환이 줄어든다. 하위 큐에서 오래 기다린 프로세스를 다시 위 큐로 올리는 에이징을 함께 써서 기아를 막는다.

### 기법 비교

| 기법     | 선점 여부  | 기준                     | 장점                    | 단점                      |

## 메모리 관리와 가상 메모리

### 왜 가상 메모리가 필요한가

여러 프로세스가 물리 메모리(RAM)를 직접 주소로 사용하면 두 가지 문제가 생긴다. 첫째, 프로세스 A가 실수나 악의로 프로세스 B의 메모리 주소에 쓰면 B의 데이터가 망가진다. 둘째, 컴파일러는 프로그램이 메모리의 어느 위치에 적재될지 미리 알 수 없다.

가상 메모리(virtual memory)는 프로세스마다 0번지부터 시작하는 독립된 가상 주소 공간을 주고, CPU가 메모리에 접근할 때마다 ==가상 주소를 물리 주소로 변환==하는 방식이다. 변환은 CPU 안의 MMU(Memory Management Unit) 하드웨어가 수행하고, 변환 규칙은 운영체제가 관리한다.

### 페이징

가장 널리 쓰는 방식은 페이징(paging)이다. 가상 주소 공간을 같은 크기의 페이지(page)로, 물리 메모리를 같은 크기의 프레임(frame)으로 나누고, 페이지 테이블(page table)에 "가상 페이지 몇 번이 물리 프레임 몇 번에 있는지"를 기록한다. 페이지 크기는 x86-64 Linux와 Windows에서 4KiB, Apple 실리콘의 macOS에서 16KiB가 기본이다.

![프로세스 A의 페이지 0은 프레임 5에, 페이지 1은 프레임 2에 매핑되고 페이지 2는 디스크에 있다. 프로세스 B의 페이지 0은 프레임 1에, 페이지 1은 A와 같은 프레임 2에 매핑되어 공유된다](./images/csintro-operating-systems-paging.svg '프로세스는 자기 가상 주소만 알고, 실제 프레임 위치는 페이지 테이블이 결정한다')

주소 변환은 다음 순서로 일어난다. 페이지 크기가 4KiB(4096바이트)이고 프로세스 A가 가상 주소 `0x1A3C`(10진수 6716)를 읽는다고 하자.

1. 가상 주소를 페이지 번호와 페이지 안의 위치(오프셋)로 나눈다. `6716 = 1 \times 4096 + 2620{:math}`이므로 페이지 1, 오프셋 2620(`0xA3C`)이다.
2. 페이지 테이블에서 페이지 1을 찾으면 프레임 2다.
3. 물리 주소는 `2 \times 4096 + 2620 = 10812{:math}`(`0x2A3C`)다.

이 구조가 주는 이점은 다음과 같다.

- **격리**: 프로세스 B의 페이지 테이블에는 A의 프레임이 없으므로, B는 어떤 가상 주소를 써도 A의 메모리에 접근할 수 없다. 접근하려 하면 MMU가 예외를 발생시키고 운영체제가 B를 종료한다(Segmentation fault).
- **공유**: 두 프로세스의 페이지를 같은 프레임에 매핑하면 메모리를 공유한다. 같은 공유 라이브러리(`libc`)를 수십 개 프로세스가 쓰더라도 물리 메모리에는 한 벌만 적재된다.
- **권한**: 페이지 테이블 항목에 읽기·쓰기·실행 권한 비트가 있다. 데이터 영역을 실행 불가(NX 비트)로 표시하면, 공격자가 버퍼 오버플로로 스택에 넣은 기계어를 실행할 수 없다.
- **물리 메모리보다 큰 주소 공간**: 당장 쓰지 않는 페이지는 디스크의 스왑(swap) 영역에 내려 둘 수 있다.

### 페이지 폴트와 스와핑

페이지 테이블에 "현재 메모리에 없음"으로 표시된 페이지에 접근하면 MMU가 페이지 폴트(page fault) 예외를 발생시킨다. 운영체제는 해당 프로세스를 대기 상태로 바꾸고, 디스크에서 그 페이지를 빈 프레임으로 읽어 온 뒤 페이지 테이블을 갱신하고 명령을 다시 실행한다. 빈 프레임이 없으면 가장 오래 사용하지 않은 페이지(LRU 근사) 등을 골라 디스크로 내보낸다.

디스크 접근은 RAM보다 수만 배 이상 느리므로, 실행 중인 프로그램들이 필요로 하는 메모리가 RAM보다 크게 많아지면 페이지 폴트 처리에 대부분의 시간을 쓰고 실제 작업은 거의 진행되지 않는다. 이를 ==스래싱(thrashing)==이라고 한다. 메모리가 부족한 컴퓨터에서 앱 전환이 몇 초씩 걸리는 현상이 이것이다.

## 파일 시스템

디스크(SSD, HDD)는 일정 크기 블록의 배열일 뿐이다. 파일 시스템(file system)은 이 블록들 위에 파일과 디렉터리라는 구조를 만들고, 어느 블록이 어느 파일에 속하는지 기록한다.

유닉스 계열 파일 시스템은 파일마다 아이노드(inode)라는 메타데이터 구조를 둔다. 아이노드에는 파일 크기, 소유자, 권한, 수정 시각, 그리고 데이터 블록의 위치가 기록되고, 파일 이름은 들어 있지 않다. 파일 이름은 디렉터리에 "이름 → 아이노드 번호" 항목으로 저장된다. 그래서 같은 아이노드를 가리키는 이름을 여러 개 만들 수 있고(하드 링크), 파일 이름을 바꾸는 `mv`는 데이터 블록을 복사하지 않고 디렉터리 항목만 수정하므로 파일 크기와 관계없이 즉시 끝난다.

| 파일 시스템 | 사용처                | 특징                                                            |
| ----------- | --------------------- | --------------------------------------------------------------- |
| APFS        | macOS, iOS            | 스냅숏, 파일 복제 시 블록 공유(copy-on-write), 기본 암호화 지원 |
| ext4        | 대부분의 Linux 배포판 | 저널링으로 전원 차단 후 빠른 복구                               |
| NTFS        | Windows               | 저널링, ACL 기반 권한                                           |
| FAT32·exFAT | USB 메모리, SD 카드   | 단순해 여러 OS가 지원. 파일 권한 개념이 없음                    |

파일 시스템은 접근 제어의 기반이기도 하다. 유닉스 계열에서는 파일마다 소유자·그룹·기타 사용자에 대해 읽기(r)·쓰기(w)·실행(x) 권한을 지정하고, 커널은 `open` 시스템 호출마다 요청한 프로세스의 UID와 이 권한을 비교한다. FAT32에는 이 권한 정보가 없으므로, USB 메모리의 파일은 그것을 연결한 컴퓨터의 누구나 읽을 수 있다.

## 직접 해 보기: 터미널에서 프로세스와 메모리, 파일 정보 조회

macOS나 Linux 터미널에서 아래 명령으로 지금까지 다룬 개념을 실제 값으로 확인할 수 있다.

**프로세스 목록과 상태**

```bash
ps -eo pid,ppid,stat,comm | head
```

```text
  PID  PPID STAT COMM
    1     0 Ss   /sbin/launchd
```

`PPID`는 부모 프로세스 번호다. PID 1(`launchd` 또는 `systemd`)이 모든 프로세스의 조상이고, `ps`는 그것을 실행한 `zsh`의 자식이다. `STAT`의 첫 글자 `R`은 실행 또는 준비 상태(Running/Runnable), `S`는 대기 상태(Sleeping)다. 대부분의 프로세스가 `S`인 것은 사용자 입력이나 네트워크 응답을 기다리는 시간이 대부분이기 때문이다.

```bash
top -o cpu        # macOS. Linux는 top 실행 후 P 키
```

`#TH` 열(macOS)에 프로세스별 스레드 수가 표시된다. 브라우저는 수십 개의 스레드를 사용한다.

```bash
getconf PAGESIZE       # x86-64 Linux: 4096, Apple 실리콘 macOS: 16384

```

`vm_stat`의 `Pageins`/`Pageouts`는 디스크에서 읽어 오거나 내보낸 페이지 수다. 무거운 앱을 여러 개 실행하기 전후로 값을 비교하면 스와핑이 일어났는지 확인할 수 있다.

**아이노드와 하드 링크**

```bash
cd /Users/me/practice
echo "hello" > a.txt
ln a.txt b.txt          # 하드 링크
```

## 직접 해 보기: C 프로그램으로 파일 50개를 만들며 시스템 호출 관찰

파일을 만드는 짧은 C 프로그램 하나에도 운영체제의 프로세스 관리, 정보(파일) 관리, 입출력 관리가 모두 관여한다. 아래 프로그램은 `week1.txt`부터 `week50.txt`까지 파일 50개를 만들고 각 파일에 `Hello`를 기록한다.

**1단계: 소스 코드 작성**

```c
// create_files.c
#include <stdio.h>

int main(void) {
	char fName[256];

	for (int cnt = 1; cnt <= 50; cnt++) {
		// "week" + 번호 + ".txt" 형태의 파일 이름을 만든다
		snprintf(fName, sizeof fName, "/Users/me/practice/week%d.txt", cnt);

		FILE *file = fopen(fName, "w"); // 없으면 만들고, 있으면 내용을 비운다
		if (file == NULL) {
			perror(fName); // 디렉터리가 없거나 권한이 없으면 원인을 출력
			return 1;
		}
		fputs("Hello", file);
		fclose(file);
	}
	return 0;
}
```

파일 이름은 `snprintf`로 만든다. `strcpy`와 `strcat`을 이어 붙여 만들 수도 있지만, 버퍼 크기를 검사하지 않아 경로가 길면 배열 밖에 기록하는 버퍼 오버플로가 생긴다. `snprintf`는 두 번째 인자로 받은 크기를 넘겨 쓰지 않는다. `fopen`이 실패하면 `NULL`을 돌려주므로 반드시 검사한다.

**2단계: 컴파일과 실행**

```bash
mkdir -p /Users/me/practice
cc -Wall -o create_files create_files.c
./create_files
ls /Users/me/practice | head -3
ls /Users/me/practice | wc -l
cat /Users/me/practice/week1.txt
```

```text
week1.txt
week10.txt
week11.txt
      50
Hello
```

`ls`는 이름을 사전 순으로 정렬하므로 `week10.txt`가 `week2.txt`보다 앞에 온다. 파일 수는 50개이고, 각 파일의 크기는 5바이트다.

**3단계: 프로세스로서의 실행 확인**

`./create_files`를 입력하면 셸은 `fork` 시스템 호출로 자기 자신을 복제한 자식 프로세스를 만들고, 자식은 `exec`로 `create_files` 프로그램을 적재한다. 이 순간 프로그램이 프로세스가 되고 PCB가 생긴다. 실행이 끝나면 `return 0`의 값 0이 종료 상태로 부모(셸)에 전달된다.

```bash
./create_files; echo "종료 상태: $?"
```

```text
종료 상태: 0
```

**4단계: 시스템 호출 관찰**

![fopen은 open 시스템 호출로 바뀌어 커널이 권한 검사 후 아이노드를 만들고 파일 디스크립터 3을 반환한다. fputs는 libc 버퍼에만 기록하고, fclose가 write와 close 시스템 호출을 실행한다](./images/csintro-operating-systems-syscalls.svg 'C 표준 라이브러리는 버퍼링으로 시스템 호출 횟수를 줄인다')

Linux에서는 `strace`로 프로세스가 실행한 시스템 호출을 볼 수 있다(macOS에서는 `sudo dtruss`가 같은 역할을 하지만 시스템 무결성 보호(SIP)를 끄지 않으면 제한된다).

```bash
strace -e trace=openat,write,close ./create_files 2>&1 | grep week | head -3
strace -c ./create_files
```

```text
openat(AT_FDCWD, "/home/me/practice/week1.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
openat(AT_FDCWD, "/home/me/practice/week2.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
openat(AT_FDCWD, "/home/me/practice/week3.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
```

결과에서 확인할 점은 세 가지다.

1. `fopen(name, "w")`은 `openat` 시스템 호출로 바뀌고, `"w"` 모드는 `O_WRONLY|O_CREAT|O_TRUNC`(쓰기 전용, 없으면 생성, 있으면 비우기) 플래그가 된다.
2. 반환값 3은 파일 디스크립터(file descriptor)다. 0, 1, 2는 표준 입력·출력·오류가 이미 사용하므로 새 파일은 3을 받고, `close`로 반납하면 다음 파일이 다시 3을 받는다. `fclose`를 빠뜨리면 디스크립터가 계속 쌓여, 프로세스당 한도(`ulimit -n`, macOS 기본값 256)에 도달하는 순간 `fopen`이 실패한다.
3. 반복문 안에서는 `openat`, `write`, `close`가 각각 50번 실행된다. `-c` 요약의 `openat`·`close` 횟수는 동적 링커가 공유 라이브러리를 여는 몇 번이 더해져 50보다 조금 크다. `fputs`는 libc의 버퍼에만 기록하고, `fclose`가 버퍼를 비우면서 `write`를 한 번 실행한다.

**5단계: 권한과 보안**

```bash
ls -l /Users/me/practice/week1.txt
umask
```

```text
-rw-r--r--  1 me  staff  5 Jun  5 10:00 /Users/me/practice/week1.txt
022
```

프로그램은 권한 `0666`(모두 읽기·쓰기)을 요청했지만 실제 파일은 `0644`(`rw-r--r--`)다. 커널이 프로세스의 `umask` 값 `022`에 해당하는 비트(그룹과 기타 사용자의 쓰기)를 지우기 때문이다. 같은 프로그램을 쓰기 권한이 없는 디렉터리(예: `/System`)에 대해 실행하면 커널이 `open`을 거부하고 `perror`가 `Permission denied`를 출력한다. 응용 프로그램은 디스크에 직접 쓸 수 없고 커널을 거쳐야 하므로, 권한 검사를 피할 방법이 없다는 것이 이 실험의 요점이다.

> [!WARNING] 반복으로 파일을 만드는 코드
> 반복 횟수나 경로를 잘못 지정하면 디스크를 파일로 가득 채우거나 기존 파일을 덮어쓸 수 있다(`"w"` 모드는 내용을 비운다). 빈 연습용 디렉터리에서 실행하고, 실습 뒤에는 `rm /Users/me/practice/week*.txt`로 정리한다. 일부 악성코드는 같은 원리로 파일을 대량 생성해 저장 공간을 고갈시킨다.

## 확인 문제

<details>
<summary>1. 운영체제의 목표가 아닌 것은? ① 처리량 향상 ② 응답 시간 극대화 ③ 신뢰성 향상 ④ 유용성 증대</summary>

②. 응답 시간은 짧게 만드는(단축) 것이 목표다.

</details>

<details>
<summary>2. 한 프로그램이 입출력장치를 사용하는 동안 다른 프로그램이 CPU를 사용해 CPU 효율을 높이는 시스템은?</summary>

다중 프로그래밍 시스템. 시분할 시스템은 입출력 여부와 관계없이 CPU 시간을 일정하게 나눠 준다는 점이 다르다.

</details>

<details>
<summary>3. 리눅스에 대한 설명으로 틀린 것은? ① 다양한 배포판이 있다 ② 소스 코드가 공개되어 있으나 수정과 배포에 제약이 있다 ③ 유닉스 호환 운영체제다 ④ 오픈 소스 정책을 따른다</summary>

②. GPL에 따라 누구나 수정·재배포할 수 있다. 수정한 커널을 배포하면 소스 코드도 공개해야 한다는 조건이 있을 뿐이다.

</details>

<details>
<summary>4. 참/거짓: 프로그램은 수동적 개체이고 프로세스는 능동적 개체다. PCB는 프로세스 실행이 끝난 뒤에도 정보를 유지한다.</summary>

첫 문장은 참이다. 둘째 문장은 거짓이다. PCB는 프로세스가 종료되면 삭제된다. 유닉스 계열에서는 부모가 종료 상태를 회수(`wait`)할 때까지 최소한의 정보만 남은 좀비(zombie) 상태가 잠시 존재한다.

</details>

<details>
<summary>5. 교착 상태의 해결 방안이 아닌 것은? ① 예방 ② 회피 ③ 탐지 ④ 삭제</summary>

④. 해결 방안은 예방, 회피, 탐지, 회복이다.

</details>

<details>
<summary>6. SRT 기법에 대한 설명으로 틀린 것은? ① 예상 실행 시간이 가장 짧은 작업을 먼저 처리한다 ② 시분할 시스템에 적합한 선점 기법이다 ③ 잔여 실행 시간이 가장 짧은 프로세스를 먼저 처리한다 ④ 잔여 실행 시간을 계속 추적해야 한다</summary>

①. 이것은 비선점 SJF의 설명이다. SRT는 처음 예상 시간이 아니라 남은 시간을 비교하고, 새 프로세스가 도착하면 실행 중인 프로세스를 선점할 수 있다.

</details>
