팀 프로젝트에서 프론트의 로그인·인증과 구독·AI 체험 API 연동은 내가 맡았다. 로그인은 Google OAuth이고, 백엔드가 토큰을 쿠키로 내려준다. 이 글은 마감 주(2월 1일~6일)에 로그인 코드가 어떻게 바뀌었는지를 커밋 기록으로 다시 따라간다. 당시에는 "되게 만들기"에 바빠 왜 그렇게 바꿨는지 거의 남기지 않았다. 1년 8개월 뒤 같은 코드를 다시 읽은 이야기는 [한 번도 동작하지 않던 토큰 갱신](/memo/newpick-api-client)에 있다.

![마감 주의 로그인 코드](./images/newpick-v1-auth-timeline.svg '빨간 점은 v2에서 문제의 원인으로 다시 만난 것')

## 1월: 팝업 로그인과 1분마다의 만료 확인

처음 만든 로그인은 팝업이었다. 로그인 버튼을 누르면 백엔드의 Google 로그인 주소를 작은 창으로 열고, 로그인이 끝나면 백엔드가 `postMessage`로 사용자 정보를 부모 창에 보낸다. 부모 창은 출처(`origin`)가 백엔드인지 확인하고 사용자 정보를 저장한다.

토큰 만료는 1월 26일에 넣었다. 1분마다 토큰 쿠키를 확인해 없으면 사용자 상태를 지우고 "로그인 세션이 만료되었습니다" 알림을 띄웠다. 만료되면 갱신하는 것이 아니라 **로그아웃시키는** 방식이었다.

1월 29일 프론트엔드 코드 리뷰 회의록에는 이런 항목이 있다.

- 토큰 만료 처리? → 공부해 보세요
- 보안상 refreshToken은 백엔드에서 다루고, 프론트는 accessToken만 갖고 있는 게 맞다

다음 날 자료실에 "인증 인가 정보는 어디에 담아야 할까? (cookie? authentication header?)"라는 문서를 만들고 참고 글을 모았다. 마감까지 일주일이었다.

## 백엔드: HTTPS가 없으면 Google 로그인이 안 된다

같은 주에 백엔드는 배포 문제를 풀고 있었다. 노션 트러블슈팅에 남은 기록을 요약하면 이렇다.

| 문제                                                 | 해결                                                               |
| ---------------------------------------------------- | ------------------------------------------------------------------ |
| `api.newpick.site`가 EC2에 연결되지 않음             | 가비아 DNS의 A 레코드를 EC2 공인 IP로                              |
| Google OAuth는 HTTPS가 필수                          | Nginx 리버스 프록시 + certbot 무료 인증서, 자동 갱신               |
| `redirect_uri_mismatch`                              | Google 콘솔에 `https://api.newpick.site/auth/google/callback` 등록 |
| "앱이 Google의 OAuth 2.0 정책을 준수하지 않음"       | OAuth 앱을 프로덕션 상태로 게시                                    |
| 만료된 access token을 받으면 가드가 401만 반환 (2/2) | 가드를 고쳐 refresh 흐름이 가능하게                                |

처음 계획은 프론트 `newpick.net`(Vercel), 백엔드 `api.newpick.site`였다. 서로 다른 사이트면 백엔드가 내려준 쿠키를 프론트에서 쓰기 어렵다. 결국 프론트도 `www.newpick.site`로 옮기고, 2월 3일 백엔드가 쿠키 domain을 `.newpick.site`로 지정해 두 서브도메인이 쿠키를 함께 쓰게 했다.

## 2월 1일 새벽: 만들고 바로 주석 처리한 프록시

2월 1일 02시 58분 커밋("초기 데이터는 SSR로 불러오기")은 61개 파일을 바꿨다. 로그인 사용자와 구독 정보를 서버에서 미리 불러오도록 바꾸면서, 두 가지를 같이 넣었다.

```ts
// next.config: 프론트의 /api/* 요청을 백엔드로 넘긴다
async rewrites() {
	return [{ source: '/api/:path*', destination: 'http://localhost:3001/:path*' }];
}

// constants/api.ts
export const getApiUrl = () => (typeof window === 'undefined' ? BACK_URL : '/api');
// export const API_URL = getApiUrl();
export const API_URL = BACK_URL;
```

브라우저는 같은 도메인의 `/api`로 요청하고 Next가 백엔드로 넘기게 하면, 쿠키가 프론트 도메인에 저장되어 사이트가 달라서 생기는 문제가 사라진다. 그 방법을 만들어 놓고, **같은 커밋에서** 주석 처리하고 `API_URL = BACK_URL`로 돌려놓았다. 이유는 남아 있지 않다. 이후 프록시 대상은 배포 환경에서 `https://api.newpick.site`를 가리키도록 고쳐졌지만, `API_URL`은 마지막까지 `BACK_URL`이었다. 팀은 프록시 대신 위의 서브도메인 쿠키 방식을 택했고, 프록시 설정은 쓰이지 않은 채 남았다.

> **v2에서**: 이 주석 한 줄이 v2 4단계의 출발점이었다. `getApiUrl`을 그대로 살려 [요청 경로를 /api 하나로](/memo/newpick-api-client) 모았다. 1년 8개월 전의 내가 이미 답을 써 두고 꺼 둔 셈이다.

## 2월 3일: 하루에 다섯 번 바뀐 인증 코드

| 시각  | 커밋                                   | 내용                                                                              |
| ----- | -------------------------------------- | --------------------------------------------------------------------------------- |
| 07:48 | 루트 layout 동적 렌더링으로 전환       | `force-dynamic`. 모든 페이지가 요청마다 렌더링 ([앞 글](/memo/newpick-v1-nextjs)) |
| 09:44 | `fetchWithAuth` 제거                   | 토큰 갱신 래퍼의 이름을 `fetch`로 바꾸고, 호출하는 곳도 모두 `fetch`로            |
| 09:58 | 핫픽스 병합: `fetch` → `fetchWithAuth` | 전역 `fetch`를 가리는 이름이라 되돌림. **호출하는 곳은 `fetch` 그대로**           |
| 10:24 | 로그인 팝업 무한 루프 개선             | 팝업 차단 확인, 타임아웃, 리스너 정리                                             |
| 19:15 | 서버 쪽 refresh 재시도 개선            | 새 토큰을 인자로 넘겨 한 번 다시 요청                                             |

09:44와 09:58 사이에 무슨 일이 있었는지는 기록이 없다. 결과만 보면, 래퍼 이름은 원래대로 돌아왔지만 호출하는 곳은 전부 import 없이 쓰는 **브라우저 기본 `fetch`**가 됐다. 오류가 나지 않으므로 아무도 알아채지 못했고, 브라우저에서 토큰이 만료되면 갱신 없이 요청이 실패하는 상태로 마감을 맞았다.

19:15의 재시도는 refresh 응답에서 새 토큰을 `data?.access_token`으로 읽었다. 백엔드가 보내는 필드 이름은 `accessToken`이었다. 이 재시도도 한 번도 동작하지 않았다.

## 2월 6일 02:11: 팝업에서 리다이렉트로

발표 당일 새벽 2시 11분, 팝업 로그인을 통째로 지우고 리다이렉트 방식으로 바꿨다(`hotfix: 로그인 팝업에서 리다이렉트 방식으로 변경`, −64줄). 로그인 버튼은 현재 창을 백엔드 로그인 주소로 보내고, 로그인이 끝나면 백엔드가 `?oauthSuccess=true`를 붙여 프론트로 돌려보낸다. 프론트는 이 값을 보고 사용자 정보를 다시 조회한다.

이유는 커밋에 남아 있지 않다. 사흘 전 무한 루프와 팝업 차단을 고쳤던 코드를 발표 몇 시간 전에 버린 것이니, 배포 환경에서 팝업과 `postMessage` 흐름이 끝내 안정되지 않았던 것으로 보인다. 리다이렉트 방식은 v2에서도 그대로 쓰고 있다.

## 발표 다음 날 적은 것

2월 7일 향후 계획 회의에서 내 몫으로 적은 일은 이랬다.

- 노션을 팀 노션으로 옮기기, README 작성
- styled-components → CSS
- 마이페이지의 "내 뉴스레터"에 받은 뉴스레터 내역 보기
- **access token 받는 것 수정**

마지막 줄은 마감 주에 끝내지 못한 것을 나도 알고 있었다는 기록이다. 이 일은 1년 8개월 뒤 v2 4단계에서 했다.

| v1에 남은 것                                | v2에서                                                         |
| ------------------------------------------- | -------------------------------------------------------------- |
| `fetchWithAuth` 호출하는 곳 0개             | 모든 요청을 `apiFetch` 하나로, 401이면 refresh 한 번 후 재시도 |
| 서버 재시도가 `access_token`을 읽음         | 렌더링 전 middleware에서 갱신                                  |
| `getApiUrl` 주석 처리, `API_URL = BACK_URL` | `/api` 프록시로 통일                                           |
| refresh 응답 본문에 토큰                    | 쿠키로만 전달                                                  |
| 루트 layout `force-dynamic`                 | 제거, 로그인 표시 쿠키로 정적 빌드                             |

## 남은 것·배운 것

- 마감 주의 커밋 메시지는 "fix", "개선", "hotfix"뿐이고 이유가 없다. 1년 8개월 뒤 나는 diff만 보고 당시 의도를 추측해야 했다. 급할수록 한 줄이라도 "왜"를 남겨야 한다.
- 오류가 나지 않는 잘못(이름이 같은 전역 함수, 다른 필드 이름)이 가장 오래 남았다. 둘 다 타입이나 테스트가 있었다면 바로 드러났을 것이다.
- 같은 문제(다른 도메인의 쿠키)에 두 해결책(프록시, 서브도메인 쿠키)이 동시에 만들어졌고, 하나는 쓰이지 않은 채 남았다. 무엇을 택했는지 한 줄로 남겼다면, v2에서 "설정만 있고 쓰이지 않는 프록시"를 보고 이유를 추측할 필요가 없었다. v2는 프록시 쪽을 택해 서브도메인과 쿠키 domain 설정이 필요 없어졌다.
