MacFolio의 **활동 상태 보기**는 macOS의 활동 상태 보기 모양을 한 방문 분석 화면이다. 관리자는 그중 **검색어** 탭에서 방문자가 무엇을 검색하다 이 사이트에 들어왔는지 확인한다([리퍼러 검색어와 Search Console API로 유입 검색어 수집하기](/memo/search-keywords)). 그런데 이 탭은 검색어마다 방문 수만 보여 주었다. "cors 쿠키"로 12명이 들어왔다는 사실은 알 수 있어도, 그 12명이 CORS 글을 읽었는지 첫 화면만 보고 나갔는지는 알 수 없었다.

검색어와 본 글을 함께 보면 판단할 수 있는 것이 늘어난다. 예를 들어 "cors 쿠키"로 들어온 방문이 대부분 [PR 미리보기 CORS 글](/memo/preview-cors-read-only)을 읽었다면 그 글이 검색 의도에 맞는 것이고, 첫 화면에서 나갔다면 검색 결과에 보이는 제목·요약이 실제 글과 어긋났다는 뜻이다. 그래서 검색어를 누르면 그 검색어로 들어와 본 페이지·글이 옆에 보이게 했다.

## 배경: 검색어 자료는 두 종류다

검색어 탭에는 출처가 다른 표가 둘 있다. 표마다 가진 자료가 달라서 고치는 방법도 달랐다.

| 표                           | 자료를 만드는 곳                                                                                    | 한 줄의 단위                        | 이번에 필요한 일                    |
| ---------------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------- | ----------------------------------- |
| **검색어 / 페이지**          | Google Search Console. 구글이 집계한 날짜·검색어·페이지별 클릭·노출 수를 서버가 6시간마다 받아 둔다 | (날짜, 검색어, 페이지)              | 화면에서 검색어로 페이지를 거른다   |
| **검색엔진이 넘겨준 검색어** | 이 사이트의 방문 수집. 네이버처럼 들어온 주소에 검색어를 실어 보내는 검색엔진으로 온 방문만 남는다  | 방문 하나의 이벤트(들어옴, 글 열기) | 서버가 검색어별로 본 글을 새로 센다 |

Search Console은 구글이 검색 결과에서 집계한 숫자다. **노출**은 이 사이트가 검색 결과에 보인 횟수, **클릭**은 그 결과를 눌러 들어온 횟수다. 구글은 개별 방문자의 검색어를 사이트에 넘기지 않으므로, 구글 검색어는 이 집계로만 볼 수 있다.

반면 네이버 같은 검색엔진은 사용자가 검색 결과를 누를 때 브라우저가 보내는 **리퍼러**(이전 페이지 주소)에 검색어를 남긴다. MacFolio는 이 검색어를 방문의 첫 이벤트에 함께 저장한다. 방문 하나는 여러 이벤트로 기록된다. 들어올 때의 `visit`, 앱을 열 때의 `app`, 글이나 프로젝트를 열 때의 `item`, 탭을 숨길 때의 `leave`다([sendBeacon으로 5초마다 묶어 보내는 방문 이벤트](/memo/analytics-collect)).

## Search Console 표: 이미 받은 행을 반대로 거른다

Search Console에서 받는 행은 처음부터 (검색어, 페이지) 짝이다. 화면은 이 행을 검색어로 묶어 왼쪽 표를, 페이지로 묶어 오른쪽 표를 그린다. 원래는 페이지를 누르면 왼쪽 표가 그 페이지로 들어온 검색어만 보이는 한 방향 거르기만 있었다. 같은 행을 검색어로 거르면 반대 방향이 된다.

```ts
// apps/react/src/apps/activity/model.ts
// only를 주면 다른 쪽이 그 값인 줄만 묶는다
export function groupSearchRows(rows: SearchQueryRow[], by: 'query' | 'page', only?: string | null) {
	const other = by === 'query' ? 'page' : 'query';
	for (const row of rows) {
		if (only && row[other] !== only) continue;
		// … by 쪽 값으로 클릭·노출을 더한다
	}
}
```

예를 들어 받아 둔 행이 다음과 같으면, "macfolio"를 누른 오른쪽 표에는 첫 화면(클릭 18)과 CRA→Vite 글(클릭 2) 두 줄이 남는다.

| 검색어                  | 페이지      | 클릭 | 노출 |
| ----------------------- | ----------- | ---: | ---: |
| ==macfolio==            | 첫 화면     |   18 |  240 |
| macos 포트폴리오 사이트 | 첫 화면     |    6 |  180 |
| cra vite 마이그레이션   | CRA→Vite 글 |    9 |  150 |
| ==macfolio==            | CRA→Vite 글 |    2 |   60 |

![검색어 macfolio를 고른 Search Console 표](./images/search-term-pages-console.jpg '왼쪽에서 macfolio를 누르면 오른쪽 페이지 표가 그 검색어로 나온 페이지와 클릭 수만 보인다')

두 표에서 동시에 하나씩 고르면 양쪽 표가 서로를 걸러 한 줄씩만 남는다. 그래서 한쪽을 고르면 다른 쪽에서 고른 것은 풀리게 했다. 서버와 주고받는 자료는 그대로이고 화면 코드만 바뀌었다.

## 넘겨준 검색어 표: 서버가 검색어별 본 글을 센다

넘겨준 검색어 표의 숫자는 서버가 날마다 이벤트를 모아 저장한 **일별 집계**(`DailyStat`)에서 온다. 원본 이벤트는 90일만 보관하고, 집계는 (날짜, 지표, 키, 값) 행으로 계속 남는다. 예를 들어 `searchTerm` 지표의 `cors 쿠키` 키 값이 3이면 그날 그 검색어로 들어온 방문이 3번이라는 뜻이다. 이 집계에는 검색어와 글을 이어 주는 정보가 없었다. 그래서 같은 방식으로 지표 하나를 더했다.

![하루치 이벤트에서 searchTermItem 행을 만드는 과정](./images/search-term-pages-aggregate.svg '같은 방문의 visit 이벤트에서 검색어를 읽고, 그 방문의 item 이벤트마다 검색어와 글을 묶은 키를 한 번씩 센다')

1. **키:** `검색어⇥앱/항목`이다(⇥는 탭 문자). 예를 들어 "cors 쿠키"로 들어와 `memo/cors` 글을 연 방문은 `cors 쿠키⇥memo/cors` 키를 1 올린다. 검색어는 저장할 때 공백을 한 칸으로 줄이므로 탭이 들어 있지 않아, 탭에서 나누면 검색어와 글이 정확히 갈린다. PostgreSQL 글자 열은 널 문자(`\u0000`)를 받지 않아 그것으로는 묶지 않았다.
2. **방문마다 한 번:** 한 방문에서 같은 글을 여러 번 열어도 1로 센다. 글 조회수(`item` 지표)와 같은 규칙이다.
3. **검색어 없는 방문은 제외:** github.com에서 들어온 방문이 같은 글을 읽어도 이 지표에는 넣지 않는다.

> [!NOTE] 이벤트 순서에 기대지 않는다
> 집계 함수는 하루치 이벤트를 DB에서 읽어 받는데, 이 목록은 순서가 보장되지 않는다. 글 열기(`item`)가 들어옴(`visit`)보다 먼저 올 수 있어서, 먼저 `visit` 이벤트만 훑어 방문별 검색어를 모은 뒤 글 열기를 센다. 시험에도 글 열기를 방문보다 앞에 둔 경우를 넣었다.

화면은 고른 검색어로 시작하는 키만 골라 뒷부분(`memo/cors`)을 글 제목으로 바꾼다. 글 조회수 표와 같은 이름 붙이기를 쓰므로 "메모 › 글 제목"으로 보인다.

![넘겨준 검색어 macfolio를 고른 화면](./images/search-term-pages-visits.jpg '검색어를 누르면 그 검색어로 들어온 방문이 본 글이 오른쪽에 열린다. 다시 누르면 닫힌다')

### 이미 모은 날 채우기

새 지표는 이 기능을 배포한 뒤에 모은 날에만 생긴다. 그대로 두면 배포 전 날짜를 고른 표는 비어 있다. 다행히 원본 이벤트는 90일 동안 남아 있으므로, 집계를 돌 때마다 다음 조건의 날만 다시 모은다.

| 조건                                          | 처리                                                |
| --------------------------------------------- | --------------------------------------------------- |
| 원본 이벤트가 남아 있고 이미 모은 날          | 확인 대상                                           |
| 그날 `searchTerm` 행이 있다(검색어 방문 있음) | 확인 대상                                           |
| 그날 `searchTermItem` 행이 없다               | 이벤트를 다시 모아 ==`searchTermItem` 행만== 넣는다 |

다른 지표는 이미 저장되어 있으므로 다시 넣지 않는다. 90일보다 오래된 날은 원본이 지워져 채울 수 없다. DB 구조는 바꾸지 않았다. `DailyStat`은 지표 이름을 글자로 저장하는 표라 새 지표에 마이그레이션이 필요 없다.

## 누가 볼 수 있나

검색어와 검색어별 본 글은 관리자에게만 응답한다. 방문자용 요약에서는 이 표를 빈 목록으로 보낸다. 검색어는 드물수록 특정인을 짐작하게 할 수 있어서, 원래 검색어 표를 관리자 전용으로 둔 규칙을 새 표에도 그대로 적용했다.

## 시험

| 종류       | 확인한 것                                                                                                                     |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 단위(서버) | 검색어별 본 글 집계: 방문마다 한 번, 글 열기가 방문보다 먼저 와도 같은 결과, 검색어 없는 방문 제외                            |
| 단위(화면) | 검색어로 페이지 거르기(클릭 수 포함), 검색어별 본 글 고르기에서 앞부분만 같은 다른 검색어("cors"와 "cors 쿠키")가 섞이지 않음 |
| API E2E    | 관리자에게만 응답, 방문자 요약은 빈 목록, 새 지표를 모르던 때 모은 날을 채우되 다른 지표는 다시 넣지 않음                     |
| 화면 E2E   | 검색어를 고르면 고른 페이지가 풀리고 페이지 표가 바뀜, 넘겨준 검색어를 누르면 본 글 표가 열리고 다시 누르면 닫힘              |

## 남은 과제

- **네이버 유입이 적다:** 넘겨준 검색어 표는 검색어를 리퍼러에 남기는 검색엔진에서 온 방문만 보인다. 지금 유입은 대부분 구글이라 이 표의 줄 수가 적다.
- **구글 검색어로 들어와 본 다음 글:** Search Console은 검색 결과에서 처음 연 페이지까지만 알려 준다. 들어온 뒤 읽은 다른 글은 구글 검색어와 이을 방법이 없다.
