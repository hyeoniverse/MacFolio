글 안의 링크를 따라 다른 글로 넘어간 뒤 원래 글로 돌아가려면, 메모 목록에서 제목을 다시 찾아 눌러야 했다. macOS의 Finder와 Safari는 도구 막대의 ‹ › 버튼으로 돌아가고, 버튼을 길게 누르면 지난 위치 목록이 열린다. 메모 앱에 같은 버튼을 더했다.

![고치기 전 목록 도구 막대](./images/memo-history-nav-toolbar-before.jpg '고치기 전. 목록 도구 막대에는 폴더 이름과 글 수만 있었다')

![고친 뒤 목록 도구 막대](./images/memo-history-nav-toolbar-after.jpg '고친 뒤. 폴더 이름 앞에 ‹ › 버튼이 있다. 막 연 메모처럼 지난 칸이 없으면 흐리게 보인다')

## 동작

| 조작                                                    | 결과                                                              |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| ‹ · › 누르기                                            | 한 칸 뒤·앞으로 간다                                              |
| 길게 누르기(약 0.5초), 누른 채 아래로 끌기, 오른쪽 클릭 | 그 방향의 지난 칸 목록을 연다. 손을 떼도 한 칸 이동은 하지 않는다 |
| ⌘[ · ⌘] (Windows·Linux는 Ctrl)                          | 한 칸 뒤·앞으로. 메뉴 막대의 **이동 › 뒤로·앞으로**와 같다        |

![길게 눌러 연 뒤로 기록](./images/memo-history-nav-menu.jpg '‹를 길게 누른 화면. 가까운 칸부터 글 제목과 그 글이 들어 있는 폴더(사이드바와 같은 개발 기록 › MacFolio › 회고 표기)가 보이고, 고르면 그때 연 폴더와 글을 다시 연다. 마우스를 올린 둘째 줄은 강조 바탕 위에서 흰 글자다')

목록의 둘째 줄은 그 글이 실제로 들어 있는 폴더다. 처음에는 그 글을 볼 때 열려 있던 목록(예: '모든 글')을 적었는데, 어느 글인지 알아보는 데 도움이 되지 않아 글의 폴더로 바꿨다. 관리자가 메모 정리로 글을 옮겼다면 옮긴 폴더를 적는다. 글 없이 폴더만 연 칸은 그 폴더 경로를 적는다.

둘째 줄은 원래 흐린 회색(`--color-secondary-label`)인데, 마우스를 올려 파란 강조 바탕이 되면 회색이 바탕에 묻혔다. 공용 메뉴(`shared/ui/menu/Menu.css`)에서 강조된 항목의 둘째 줄도 첫 줄과 같은 강조 글자색(흰색)을 쓰게 했다. 흰 글자와 강조 바탕의 대비는 라이트 4.02:1(#007AFF), 다크 3.65:1(#0A84FF)로 첫 줄과 같다. macOS 메뉴와 같은 조합이지만 WCAG AA의 작은 글자 기준(4.5:1)에는 못 미친다. 휴대폰(touch) 메뉴는 누름 바탕이 옅은 회색이라 둘째 줄을 흐린 색 그대로 둔다.

누른 채 아래로 끌어도 목록이 열리는 것은 macOS 버튼의 동작을 따른 것이다. 마우스를 누른 위치보다 8px 아래로 움직이면 0.5초를 기다리지 않고 연다.

## 기록 규칙

기록 한 칸은 **연 폴더(또는 '모든 글'·태그 같은 보기)와 그때 본 글**이다. 규칙은 순수 함수 파일 `navHistory.ts`에 두고 단위 시험으로 고정했다.

![이동 기록의 세 단계](./images/memo-history-nav-stack.svg '도식. ① 글 셋을 연 뒤 ② ‹ 두 번 ③ 그 자리에서 새 글을 열면 앞쪽 칸을 버린다')

- **새 칸:** 지금 칸 뒤에 쌓고, 앞으로 갈 칸이 있었다면 버린다(Safari와 같다). 지금 칸과 같으면 쌓지 않는다.
- **빈 칸 채우기:** 글을 불러오기 전이나 폴더를 연 직후처럼 글이 없는 칸은, 같은 폴더에서 글이 열리면 그 칸을 바꾼다. 그렇지 않으면 처음 연 순간의 '모든 글(글 없음)' 칸이 기록 맨 앞에 남는다.
- **상한:** 50칸. 넘으면 오래된 칸부터 버린다.
- **지운 글:** 지금 없는 글의 칸은 ‹ ›와 길게 누르기 목록에서 건너뛴다. 칸 자체는 남겨 두어, 글이 되살아나면 다시 갈 수 있다.
- **돌아갈 때:** 검색어와 ⌄ 메뉴의 조건을 비운다. 조건이 남아 있으면 그 글이 목록에서 걸러져 다른 글이 열린다.

## 브라우저 기록에 쌓지 않은 이유

메모는 글을 열 때마다 주소를 `/memo/<글>`로 바꾸지만, `history.replaceState`로 바꾸기만 하고 브라우저 기록은 늘리지 않는다(`shared/lib/appLink.ts`, [앱 안의 화면에 주소 붙이기](/memo/app-links)). 한 탭 안에 메모·Safari·Finder 창이 함께 떠 있어서, 브라우저의 뒤로 가기가 어느 창의 기록을 되돌릴지 정할 수 없기 때문이다. 그래서 이 기록은 브라우저 기록과 따로 메모 창 안에 둔다.

## 새로 고쳐도 남게: sessionStorage

처음에는 기록을 메모리에만 두어 새로 고치면 사라졌다. 새로 고친 뒤에도 브라우저의 뒤로 가기는 동작하는데 ‹만 비어 있으면 어색하므로, 기록을 `sessionStorage`에 저장한다(키 `macfolio:memo:history`, `shared/lib/storage.ts`).

| 저장소                  | 새로 고침 | 다른 탭     | 탭을 닫으면 | 판단                                                            |
| ----------------------- | --------- | ----------- | ----------- | --------------------------------------------------------------- |
| 메모리 (처음)           | 사라짐    | 따로        | 사라짐      | 새로 고치면 ‹가 비어 어색하다                                   |
| `localStorage`          | 남음      | **같이 씀** | 남음        | 두 탭이 한 기록을 덮어쓰고, 며칠 전 기록이 다음 방문에 나타난다 |
| `sessionStorage` (선택) | 남음      | 따로        | 사라짐      | 브라우저 기록과 같은 범위                                       |

- **형식:** `{ v: 1, index, entries }`. 다시 읽을 때 버전이 다르거나 모양이 틀리면 버리고 빈 기록으로 시작한다. 길이는 50칸까지, 지금 칸은 범위 안으로 맞춘다(`parseNavHistory`).
- **복원 시 거르기:** 글을 다 불러온 시각에 한 번, 지운 글·비밀 글로 바뀌어 볼 수 없는 글·없어진 폴더의 칸을 빼고 지금 칸을 맞춘다(`pruneNavHistory`). 지금 칸이 빠지면 앞의 가장 가까운 칸이 지금 칸이 되고, 빼서 이웃하게 된 같은 칸은 하나로 합친다.
- **불러오기 전에는 쌓지 않는다:** 글을 불러오기 전 첫 화면(글 없는 '모든 글')을 쌓으면 저장해 둔 앞쪽 칸이 지워진다. 그래서 글을 다 불러온 뒤부터 쌓는다.
- 휴지통 앱의 '내 브라우저 데이터'에 이 기록이 보이고, 지울 수 있다(`apps/bin/siteStorage.ts`).

## 단축키와 편집기

메뉴 막대의 단축키는 지금까지 ⌘가 붙은 키라면 글자를 쓰는 칸에서도 들었다(⌘F가 편집기 안에서도 찾기를 연다). 그런데 메모 편집기(Milkdown)는 ⌘[를 목록 내어쓰기에 쓴다. 그래서 단축키 정의(`shared/ui/menu/shortcut.ts`)에 `whileTyping`을 더하고, 뒤로·앞으로는 `whileTyping: false`로 두었다. 편집기에 커서가 있을 때 ⌘[는 편집기가 받는다.

## 휴대폰

휴대폰 메모는 iOS 메모처럼 화면마다 왼쪽 위에 떠 있는 뒤로 가기(목록 → 폴더)를 쓴다. 같은 자리에 ‹ ›를 두면 두 가지 '뒤로'가 생겨 헷갈리므로, ‹ ›는 데스크톱 창에만 둔다.

## 돌아온 글의 스크롤 위치

10월 30일 추가: 처음 구현에서는 ‹로 돌아온 글이 항상 맨 위부터 열렸다. 긴 글을 중간까지 읽다가 관련 글을 보고 돌아오면, 읽던 자리를 다시 찾아 스크롤해야 했다. 브라우저의 뒤로 가기처럼 떠날 때의 위치에서 다시 시작하게 했다.

**기록에 위치를 적는다.** 기록의 칸(`NavEntry`)에 본문 스크롤 위치 `scroll`(px)을 더했다. 다른 칸으로 가기 직전에 `rememberScroll`이 지금 칸에 위치를 적고, 같은 칸인지 가르는 `sameEntry`에는 쓰지 않는다. sessionStorage에 저장하는 기록에 함께 들어가므로 새로 고쳐도 남는다.

```ts
export function rememberScroll(history: NavHistory, scroll: number): NavHistory {
	const current = history.entries[history.index];
	const top = Math.round(Math.min(Math.max(scroll, 0), MAX_SCROLL));
	if (!current || !Number.isFinite(top) || current.scroll === top) return history;
	const entries = history.entries.slice();
	entries[history.index] = { ...current, scroll: top };
	return { ...history, entries };
}
```

**떠나는 위치는 따로 기억한다.** 다른 글을 열면 본문을 맨 위로 옮기는 effect가 먼저 돈다. 그 뒤에 `scrollTop`을 읽으면 0이므로, 문서의 `scroll` 이벤트에서 본문 영역의 마지막 위치를 ref에 담아 두고 그 값을 떠나는 칸에 적는다. 본문 영역은 글을 고를 때 생기고 바뀔 수 있어, 요소에 직접 리스너를 달지 않고 `document`에서 캡처 단계로 받아 `event.target`이 본문 영역일 때만 쓴다.

**돌아올 때는 자리 잡을 때까지 맞춘다.** 위치를 한 번만 맞추면 편집 화면에서 어긋났다. 900px로 맞춘 직후 목차와 편집기 내용이 늦게 그려져 본문 높이가 바뀌고, 브라우저의 스크롤 앵커링(scroll anchoring)이 화면에 보이던 내용을 유지하려고 위치를 950px로 옮겼다. 그래서 약 0.6초(40프레임) 동안 매 프레임 위치를 다시 맞추고, 그동안 사용자가 휠이나 터치로 스크롤하면 바로 멈춘다.
