공통 컴포넌트로 옮기는 마지막 단계다. 처음 계획에는 글자 버튼(`Button`) 말고도 목록의 줄(`ListRow`), 나눔 버튼(`SegmentedControl`), 검색 칸(`SearchField`), 켜고 끄는 버튼(`Switch`), 빈 화면 안내(`EmptyState`)가 있었다. 결과부터 말하면 `Button`만 만들었다.

## 글자 버튼: 여섯 군데, 같은 모양

'취소'와 '보내기'처럼 글자가 있는 버튼이 여섯 군데에서 따로 정의되어 있었다.

| 어디               | 클래스                            | 모양      | 강조 버튼 | 지우기 버튼   |
| ------------------ | --------------------------------- | --------- | --------- | ------------- |
| 메일 쓰기          | `.mail-button`                    | 둥근 네모 | `primary` |               |
| 메시지 삭제 확인   | `.messages-delete-actions button` | 둥근 네모 |           | `destructive` |
| 메모 댓글          | `.memo-comment-button`            | 알약      | `primary` | `danger`      |
| 설정의 관리자 계정 | `.admin-account-button`           | 둥근 네모 | `primary` |               |
| 로그인 결과        | `.login-flow-button`              | 둥근 네모 | (늘 강조) |               |
| 메모 이미지 창     | `.memo-image-submit`              | 알약      | (늘 강조) |               |

모양은 거의 같았다. 여백 `5px 14px` 안팎, 모서리 8px 아니면 알약, 강조 버튼은 앱의 강조 색 바탕, 지우는 버튼은 빨간 바탕, 못 누를 때는 흐리게. 다른 것은 색과 이름뿐이었다. 같은 뜻을 `danger`와 `destructive` 두 이름으로 쓰고 있기도 했다.

![여러 앱의 글자 버튼](./images/shared-text-button.jpg '모두 Button 하나다. 색과 모양은 앱이 정한 변수를 따른다')

```tsx
<Button onClick={onCancel}>취소</Button>
<Button tone="primary" type="submit" disabled={sending}>보내기</Button>
<Button tone="danger" type="submit">삭제</Button>
```

3단계의 `IconButton`과 같은 방식이다. 버튼 CSS는 `components` 층에 두고, 색과 모양은 변수로 받는다.

```css
/* 메모: 알약 모양, 노란 강조 */
[data-app='memo'] {
	--ui-button-radius: 999px;
	--ui-button-bg: var(--memo-search-bg);
	--ui-accent: var(--memo-accent);
	--ui-on-accent: #2b2100;
}

/* 메시지 삭제 확인: 여백만 조금 좁게 */
.messages-delete-actions {
	--ui-button-padding: 4px 14px;
}
```

메일 버튼의 그림자나 관리자 계정 버튼의 테두리처럼 그 앱에만 있는 것은 앱의 CSS에 덧붙였다. 앱의 CSS는 층 밖이라 점수와 상관없이 이긴다.

### body에 그린 창에는 변수가 닿지 않는다

메모의 서식·이미지 창은 2단계에서 만든 떠 있는 창이라 `body`에 그린다. 그래서 메모 창(`[data-app='memo']`)에 정한 변수가 닿지 않는다. 변수 없이 그리면 '넣기' 버튼이 기본 강조 색인 파란색이 된다.

예전 CSS는 이 문제를 노란색(`#edbb4d`)을 직접 적어서 풀고 있었다. 같은 방식으로, 이미지 창의 바깥 요소에 변수를 다시 정했다.

```css
.memo-format-panel {
	--ui-button-radius: 999px;
	--ui-accent: #edbb4d;
	--ui-on-accent: #2b2100;
}
```

### 또 하나의 기본값

이미지 창 안에는 이런 규칙도 있었다.

```css
.memo-format-panel button {
	border: none;
	background: none;
	color: inherit;
}
```

창 안의 버튼들이 공통으로 쓰는 기본값이다. 1단계에서 `reset` 층으로 옮긴 `.memo button`과 같은 종류인데, 그때는 놓쳤다. 층 밖에 그대로 두면 `background: none`이 `components` 층의 강조 색을 이긴다. 이 규칙도 `reset` 층으로 옮겼다.

### 확인

3단계와 같은 두 가지로 확인했다.

- **계산된 스타일**: 메일 쓰기, 메시지 삭제 확인, 댓글 쓰기·지우기, 관리자 계정, 이미지 창을 열고 버튼마다 `getComputedStyle`을 적어 `main`과 비교했다. 마우스를 올린 상태도 적었다. 다른 것은 `display`가 `block`에서 `flex`로 바뀐 것(버튼이 `inline-flex`가 되었다)과 0.016px의 소수점 차이 하나뿐이었다. 폭, 높이, 색, 여백은 모두 같았다
- **화면**: 58장 모두 0.001% 이하

## 만들지 않은 것

계획에 있던 나머지 다섯 가지도 지금 코드를 살펴봤다. 공통 컴포넌트는 쓰는 곳이 여럿이고 그 모양과 동작이 같을 때 이득이 있다. 쓰는 곳이 한두 군데뿐이거나 서로 다르면, 오히려 그 차이를 다 받는 옵션이 생긴다.

| 후보               | 쓰는 곳                                   | 정한 것                                                                                                  |
| ------------------ | ----------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `Switch`           | 설정의 클릭 소리 하나                     | 만들지 않음. 쓰는 곳이 하나다                                                                            |
| `EmptyState`       | 메모·메일·메시지의 "메모 없음" 같은 한 줄 | 만들지 않음. 글 한 줄(`<p>`, `<li>`)이라 컴포넌트로 감쌀 것이 없다                                       |
| `SearchField`      | 메모, 메시지                              | 만들지 않음. 메모는 검색 조건 칩, 조건 메뉴, 넓어지는 움직임이 있고, 메시지는 칸 하나다                  |
| `SegmentedControl` | 메모 보기 방식, 이미지 창의 가져올 곳     | 만들지 않음. 하나는 눌린 상태(`aria-pressed`) 버튼 둘, 하나는 탭(`role="tab"`)과 탭 내용이라 뜻이 다르다 |
| `ListRow`          | 메모 글, 메일, 메시지 대화, 음악 곡       | 만들지 않음. 줄마다 들어가는 내용(날짜·폴더, 보낸 사람, 곡 번호·앨범)과 배치가 모두 다르다               |

`SegmentedControl`은 겉모양(회색 바탕 위의 흰 알약)이 같아서 고민했다. 하지만 스크린 리더에게 하나는 "켜고 끄는 버튼 둘"이고, 하나는 "탭 목록"이다. 모양을 합치려고 뜻까지 하나로 맞추면 접근성이 나빠진다. 세 번째로 쓸 곳이 생기면 그때 다시 본다.

## 네 단계를 마치며

| 단계 | 한 일                                              | 줄어든 것                                      |
| ---- | -------------------------------------------------- | ---------------------------------------------- |
| 1    | 앱 루트의 기본값을 `reset` 층으로                  | `!important`가 필요한 원인                     |
| 2    | 메뉴·떠 있는 창: `Menu`, `useDismiss`, `placement` | 닫기·자리 잡기 5벌 → 공통 부품                 |
| 3    | `!important` 정리, `IconButton`, `components` 층   | `!important` 66개 → 0개, 아이콘 버튼 4벌 → 1벌 |
| 4    | `Button`                                           | 글자 버튼 6벌 → 1벌                            |

이 PR은 16파일(258줄 추가, 133줄 삭제)을 바꿨다. 단계마다 화면 58장을 전후로 비교했다. 3단계부터는 계산된 스타일도 비교했다. 화면이 바뀐 것은 1·2단계뿐이다. 1단계는 앱 기본값에 덮여 있던 값이 살아난 곳들이고, 2단계는 Apple 메뉴와 메모 메뉴의 모양이 하나로 맞은 것이다. 3·4단계는 화면이 그대로였다.

## 그 뒤

열흘 뒤 리팩터링 4단계를 시작하며 같은 후보를 다시 쟀다(/memo/ui-inventory). 그사이 Finder, 사진·음악의 휴대폰 화면, 메일 휴대폰 시트가 생겨 수가 바뀌었다. 기준은 같았지만 결과 하나가 달라졌다.

![10월 1일과 10월 11일의 판단 비교](./images/shared-text-button-revisit.svg '같은 기준, 다른 수')

`SearchField`는 `type="search"`가 여섯 곳으로 늘었고, 메모를 뺀 다섯이 같은 모양이라 뽑았다. 나머지는 여전히 보류다. 이 글에서 만든 `Button`은 지금 앱 쪽에서 25개 파일이 쓴다. 손으로 쓴 글자 버튼 30곳도 나중에 이것으로 옮겼다(/memo/text-button-migrate).

## 남은 것·배운 것

- 공통 컴포넌트는 "같은 모양, 같은 뜻, 여러 곳" 세 가지가 맞을 때 만든다. 하나라도 빠지면 옵션만 늘어난다.
- "만들지 않음"은 영원한 결정이 아니다. 그날의 코드 수로 정한 것이라, 화면이 늘면 다시 잰다. 결정과 함께 이유를 적어 두면 다시 잴 때 빠르다.
- 같은 뜻을 두 이름(`danger`, `destructive`)으로 쓰고 있던 것처럼, 합치는 일은 이름을 하나로 맞추는 일이기도 하다.
- `body`에 그리는 창(포털)은 앱 루트의 CSS 변수를 물려받지 못한다. 변수로 테마를 주는 구조에서는 포털의 바깥 요소에 변수를 다시 정해야 한다.
