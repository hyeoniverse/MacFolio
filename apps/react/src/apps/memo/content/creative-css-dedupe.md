Safari 앱의 프로젝트 페이지는 CSS가 2만 8천 줄이 넘는다. 이슈에 "공통 부분을 묶기"를 적어 두었는데, 무엇을 묶을지 감으로 정하기보다 파일끼리 실제로 무엇이 겹치는지부터 세어 보았다. PR은 [#241](https://github.com/hyeoniverse/MacFolio/pull/241)이다.

## 배경

Safari 앱은 프로젝트마다 소개 페이지를 보여 준다. 기존 일곱 프로젝트는 각자 손으로 만든 전용 페이지(`safari/project/custom/`)가 있고, 새 프로젝트용으로는 신문·칸반·터미널 같은 템플릿 열두 개가 있다. 그 사이에 여러 페이지가 함께 쓰는 부품 모음 `CreativeParts.tsx`가 있다. 라이트·다크 비교 밀대(`Compare`), 스크롤 장면(`ScrollFrames`), 막대(`Bars`), 큰 그림(`FeatureMedia`) 같은 것이다.

이 사이트에서 가장 큰 CSS가 이쪽에 몰려 있어서, 스타일을 정리하는 작업의 첫 대상이 됐다. 겉으로 보이는 문제는 없었다. 다만 같은 부품의 스타일을 고칠 때 어느 파일을 고쳐야 하는지 헷갈렸다. 두 파일에 같은 선택자가 있으니 한쪽만 고치면 다른 쪽이 덮어쓰는지 아닌지를 매번 따져야 했다.

## 세어 보기

모든 CSS 파일에서 규칙(선택자와 속성 묶음)을 뽑아, 두 파일에 **선택자와 내용이 모두 같은** 규칙이 몇 개인지 짝마다 셌다.

| 짝                                          | 같은 규칙 |
| ------------------------------------------- | --------- |
| `CreativeParts.css` ↔ `HyeoniversePage.css` | 106       |
| 그 밖의 모든 짝                             | 5개 이하  |

템플릿 열두 개(신문, 칸반, 터미널 등)는 일부러 서로 다르게 그린 페이지라 겹치는 규칙이 거의 없었다. 겹침은 한 곳에 몰려 있었다.

## 왜 겹쳤나

전후 비교 밀대, 스크롤 장면, 레이아웃 도식 같은 부품은 처음에 HYEONIVERSE 페이지 안에서 만들었다. 다른 페이지에서도 쓰려고 `CreativeParts.tsx`로 옮기면서 CSS도 `CreativeParts.css`로 복사했는데, 원래 자리의 규칙을 지우지 않았다. HYEONIVERSE 페이지는 이제 그 부품을 `CreativeParts`에서 불러 쓰므로, 부품의 CSS도 함께 로드된다.

```tsx
// apps/react/src/apps/safari/project/custom/HyeoniversePage.tsx
import '@/apps/safari/project/custom/HyeoniversePage.css';
import { Bars, Compare, FeatureMedia, ScrollFrames } from '@/apps/safari/project/CreativeParts';
// CreativeParts.tsx 안에서 import '@/apps/safari/project/CreativeParts.css';
```

같은 규칙이 두 번 실려도 값이 같으니 화면은 똑같다. 그래서 오래 아무도 몰랐다. 비용은 두 가지였다. 같은 내용이 페이지 CSS에 한 번 더 실린다. 그리고 부품의 스타일을 고칠 때 두 곳을 같이 고치지 않으면, 어느 쪽이 나중에 오느냐에 따라 고친 것이 먹거나 먹지 않는다.

![HyeoniversePage.css가 먼저, CreativeParts.css가 나중에 실린다. 같은 규칙이 두 번 있으면 나중 것이 이긴다](./images/creative-css-dedupe-order.svg '같은 선택자·같은 값이면 어느 쪽을 지워도 결과는 같다. 지우는 쪽은 페이지 전용 파일')

## 고른 방법

| 방법                                         | 좋은 점                                   | 나쁜 점                                                         |
| -------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------- |
| `CreativeParts.css` 쪽을 지운다              | 페이지 파일은 그대로                      | 부품을 쓰는 다른 페이지(템플릿)가 스타일을 잃는다               |
| 공통 부분을 새 파일로 빼고 둘 다 그걸 부른다 | 구조가 깔끔해 보인다                      | 이미 `CreativeParts.css`가 그 역할이다. 파일만 하나 는다        |
| `HyeoniversePage.css`의 복사본만 지운다      | 부품의 주인(`CreativeParts`)이 분명해진다 | 페이지 전용으로 덮어쓰던 자리가 섞여 있으면 결과가 바뀔 수 있다 |

셋째를 골랐다. 마지막 칸의 위험은 아래 "같은지 확인하기"로 막았다.

## 지우기

같은 규칙인지는 글자 비교가 아니라 CSS 파서(postcss)로 판단했다. `@media` 안의 규칙은 같은 `@media` 안의 규칙과만 같다고 본다. 이렇게 고른 103개를 `HyeoniversePage.css`에서 지웠고, 파일은 1,444줄에서 735줄이 되었다. 지운 규칙은 `.cr-feature-media > img`, `.cr-compare`, `.cr-compare-dark`, `.cr-compare-handle`처럼 모두 `cr-` 접두사가 붙은 부품 쪽 선택자였다. `@keyframes`도 여섯 개 지웠는데, 역시 부품이 쓰는 움직임이었다.

| 항목                        | 전       | 후                   |
| --------------------------- | -------- | -------------------- |
| `HyeoniversePage.css` 줄 수 | 1,444    | 735                  |
| 파일 크기                   | 29,590 B | 16,192 B             |
| gzip -9                     | 8,053 B  | 5,144 B              |
| 커밋 변경                   |          | +41 / −710 (글 포함) |

![HyeoniversePage.css의 줄 수와 크기가 절반 가까이 줄었다](./images/creative-css-dedupe-size.svg '지운 뒤 줄 수는 51%, gzip 크기는 64%가 남았다')

## 같은지 확인하기

같은 규칙이 다른 파일에 남아 있어도, 지운 규칙이 다른 규칙을 다시 덮어쓰던 자리였다면 결과가 바뀔 수 있다. 그래서 화면을 눈으로 보는 대신 **브라우저가 계산한 스타일**을 비교했다.

1. 지우기 전 빌드로 HYEONIVERSE 페이지를 열고, 페이지 안의 모든 요소(1,860개)마다 `getComputedStyle`의 모든 속성을 기록한다.
2. 라이트·다크 두 번, 데스크톱과 휴대폰 두 기종(iPhone·Pixel)에서 한다.
3. 지운 뒤 빌드로 같은 일을 하고 비교한다.

모든 경우에서 3,720개 요소의 계산된 스타일이 같았다.

스크린숏을 겹쳐 보는 비교와 견주면, 계산된 스타일 비교는 화면 밖에 있는 요소와 지금 안 보이는 상태의 값까지 숫자로 맞춰 본다. 글꼴 렌더링 잡음 같은 것에 흔들리지도 않는다.

![지운 전후의 계산된 스타일 비교 흐름](./images/creative-css-dedupe-compare.svg '전후 빌드를 같은 조건에서 열고 요소마다 계산된 스타일을 기록해 맞춰 보았다')

## 남은 것과 배운 것

- 다른 짝에서 겹친 규칙 5개 이하는 그대로 두었다. 템플릿마다 우연히 같은 값(`display: flex` 같은 것)을 쓴 것이라, 묶으면 오히려 템플릿끼리 엮인다.
- `CreativeParts.css`(879줄)는 여전히 크다. 부품마다 파일을 나누는 것은 부품이 더 늘면 한다.
- 이 작업 뒤에 간격·그림자 값을 `--space-*`·`--shadow-*` 토큰으로 바꾸는 정리가 이어졌다. 복사본이 남아 있었다면 같은 값을 두 번 바꿔야 했다.

배운 것: "공통 부분을 묶자"는 막연한 할 일은 세어 보면 구체적인 한 곳이 된다. 이번에는 짝 하나에 겹침의 대부분이 몰려 있었다. 그리고 CSS를 지울 때 "화면이 같아 보인다"는 확인으로는 부족하다. 계산된 스타일을 기록해 맞춰 보면 지운 규칙이 아무 일도 하지 않았다는 것을 숫자로 말할 수 있다.
