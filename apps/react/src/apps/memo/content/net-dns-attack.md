## 들어가기 전에

DNS(Domain Name System)는 사람이 기억하는 이름 `www.example.com`을 라우터가 처리하는 IP 주소로 바꾸는 분산 데이터베이스다. 인터넷 초기에는 모든 호스트의 이름과 주소를 `HOSTS.TXT` 파일 하나에 모아 두고 각 호스트가 주기적으로 내려받았다. 호스트가 수천 대를 넘어서자 파일 크기와 갱신 트래픽이 감당할 수 없을 만큼 커졌고, 이름 충돌을 한 기관이 조정해야 하는 문제도 생겼다. 1987년 RFC 1034·1035는 이름 공간을 계층으로 나누고 각 계층의 관리를 위임하는 방식으로 이 문제를 풀었다.

이 설계는 확장성을 얻은 대신 보안을 거의 고려하지 않았다. 질의와 응답은 대부분 인증 없는 UDP 데이터그램 한 쌍이고, 리졸버는 16비트 트랜잭션 ID와 포트 번호가 맞으면 응답을 믿는다. 은행 사이트 이름에 대한 응답 하나를 공격자의 주소로 바꿔치기하면, 사용자는 주소창에 올바른 이름을 입력하고도 공격자의 서버와 통신한다. 게다가 리졸버는 응답을 캐시하므로 잘못된 기록 하나가 TTL 동안 그 리졸버를 쓰는 모든 사용자에게 퍼진다.

이 글이 답하려는 질문은 다음과 같다. 이름 하나가 주소로 바뀌기까지 어떤 서버들이 어떤 메시지를 주고받는가. 그 과정의 어느 지점에서 공격자가 거짓 정보를 끼워 넣을 수 있고, 그 공격은 왜 성공하는가. 무작위화, 서명, 암호화 채널은 각각 무엇을 막고 무엇을 막지 못하는가.

| ---- | -------------------------------------------------------------- |

DNS는 UDP 53번 포트를 주로 쓰므로 UDP 헤더와 체크섬은 [UDP와 TCP의 헤더, 연결 설정과 종료, 상태 전이](/memo/net-udp-tcp)를 참고한다. 같은 LAN에서 패킷을 엿보고 출발지 주소를 위조하는 원리는 [패킷 스니핑과 스푸핑, pcap과 원시 소켓의 이해](/memo/net-sniffing-spoofing)에서 다룬다. IP 주소의 옥텟 표기와 사설 주소 대역은 [IP 헤더와 서브넷, ARP 주소 변환](/memo/net-ip-arp)을 기준으로 한다.

> [!WARNING] 공격 설명의 범위
> 이 글은 방어하는 사람의 관점에서 공격의 원리와 성공 조건, 탐지와 방어를 개념 수준으로 설명한다. 패킷을 위조하는 코드나 도구 사용 절차는 싣지 않는다. 동작을 직접 관찰하려면 외부와 분리된 가상 머신 안에서 자신이 관리하는 리졸버와 존만 대상으로 삼는다.

## DNS 도메인 계층

### 트리 구조의 이름 공간

도메인 이름 공간은 트리 구조다. 트리의 각 노드를 도메인(domain)이라 하고, 부모 노드를 기준으로 부를 때는 서브도메인(subdomain)이라 한다. 트리의 뿌리는 루트(ROOT)이고 점 하나(`.`)로 표기한다. 루트 바로 아래가 최상위 도메인(TLD, Top-Level Domain)이고, `www.example.com`에서 TLD는 `com`이다. 그 아래 2단계 도메인(second-level domain)은 보통 회사나 학교 같은 특정 기관에 할당된다.

![루트 아래 .com, .net, .edu, .gov, .fr 최상위 도메인(TLD)이 있고 .com 아래 google, example 2단계 도메인이 있는 트리](./images/net-dns-attack-tree.svg '이름을 오른쪽에서 왼쪽으로 읽으면 트리를 위에서 아래로 내려간다')

전체 도메인 이름(FQDN, Fully Qualified Domain Name)은 노드에서 루트까지 올라가며 레이블을 점으로 이은 문자열이다. `www.example.com.`의 마지막 점이 루트를 뜻하고, 일상에서는 생략한다. 레이블 하나는 최대 63바이트, 이름 전체는 와이어 형식으로 최대 255바이트다(RFC 1035).

### 루트 서버

루트 존(root zone)의 권한 네임서버를 루트 서버라 한다. 루트 서버는 모든 TLD의 네임서버 정보를 제공하고, 캐시가 비어 있는 리졸버가 질의를 시작하는 지점이다. 루트 존 파일 전체는 약 2MB이고 `https://www.internic.net/domain/root.zone`에서 내려받을 수 있다.

루트 서버는 `a.root-servers.net`부터 `m.root-servers.net`까지 이름이 13개다. 이름이 13개로 묶인 이유는 초기 DNS 응답이 UDP 512바이트에 들어가야 했고, 루트 NS 레코드와 그 주소를 그 안에 담을 수 있는 수가 13개였기 때문이다. 이름은 13개지만 각 이름 뒤에는 애니캐스트(anycast)로 같은 주소를 광고하는 서버가 전 세계에 수백 곳씩 있어, 실제 인스턴스는 1,000개를 넘는다.

13개 이름을 12개 기관이 운영하고, VeriSign이 `a`와 `j` 두 개를 맡는다.

| 이름 | 운영 기관                   | 이름 | 운영 기관           |
| ---- | --------------------------- | ---- | ------------------- |
| a    | VeriSign                    | h    | 미 육군 연구소(ARL) |
| b    | 남캘리포니아대학교 ISI      | i    | Netnod              |
| c    | Cogent Communications       | j    | VeriSign            |
| d    | 메릴랜드대학교              | k    | RIPE NCC            |
| e    | NASA 에임스 연구센터        | l    | ICANN               |
| f    | Internet Systems Consortium | m    | WIDE Project        |
| g    | 미 국방부(NIC)              |      |                     |

> [!NOTE] 루트 서버 주소를 아는 방법
> 리졸버는 루트 서버 주소를 DNS로 알아낼 수 없다. 그래서 BIND의 `named.root` 같은 루트 힌트(root hints) 파일에 13개 이름과 주소를 미리 넣어 두고, 시작할 때 이 중 하나에 루트 NS 목록을 질의해 최신 정보로 갱신한다(priming).

### 최상위 도메인

TLD 전체 목록은 IANA(Internet Assigned Numbers Authority)가 관리하고, 새 TLD의 승인 절차도 감독한다. TLD는 성격에 따라 다음처럼 나뉜다.

| 분류                 | 예                                            | 설명                                       |
| -------------------- | --------------------------------------------- | ------------------------------------------ |
| 기반 구조 TLD        | `.arpa`                                       | 역방향 조회 등 인터넷 기반 구조용          |
| 일반 TLD(gTLD)       | `.com`, `.net`, `.org`, `.info`               | 용도 제한이 없거나 느슨함                  |
| 후원 TLD(sTLD)       | `.edu`, `.gov`, `.mil`, `.travel`, `.jobs`    | 특정 공동체를 대표하는 기관이 제안·후원    |
| 국가 코드 TLD(ccTLD) | `.kr`, `.au`, `.cn`, `.fr`                    | ISO 3166 두 글자 국가 코드                 |
| 예약 TLD             | `.example`, `.test`, `.localhost`, `.invalid` | 문서·시험용으로 예약, 실제로 위임하지 않음 |

IANA는 각 TLD를 지정 관리자(designated manager)인 레지스트리(registry)에 위임한다. 초기 TLD와 그 뒤에 추가된 대표 TLD의 도입 시기와 용도는 다음과 같다.

| TLD     | 도입 | 운영 기관(레지스트리)    | 용도                 |
| ------- | ---- | ------------------------ | -------------------- |
| `.com`  | 1985 | VeriSign                 | 제한 없음            |
| `.net`  | 1985 | VeriSign                 | 원래 네트워크 사업자 |
| `.org`  | 1985 | Public Interest Registry | 제한 없음            |
| `.edu`  | 1985 | EDUCAUSE                 | 미국 고등 교육 기관  |
| `.gov`  | 1985 | 미국 연방 총무청(GSA)    | 미국 정부            |
| `.mil`  | 1985 | 미국 국방부              | 미군                 |
| `.biz`  | 2001 | NeuLevel                 | 사업                 |
| `.info` | 2001 | Afilias                  | 제한 없음            |
| `.asia` | 2007 | DotAsia Organisation     | 아시아 지역          |
| `.xxx`  | 2011 | ICM Registry             | 성인 콘텐츠          |

`.kr`은 국가 코드 TLD이고 지정 관리자는 한국인터넷진흥원(KISA)이다. IANA 루트 존 데이터베이스의 `.kr` 항목에는 관리 기관, 행정·기술 연락처, 네임서버 목록, 등록 서비스 URL과 WHOIS 서버(`whois.kr`)가 실려 있고, 최초 등록일은 1986년 9월 29일이다. 한국에서는 IP 주소, AS 번호, 도메인 이름을 「인터넷주소자원에 관한 법률」(약칭 인터넷주소법)로 관리하고, 그 아래 「도메인이름 관리준칙」이 세부 사항을 정한다.

레지스트리는 다시 등록대행자(registrar)와 계약해 일반 사용자의 등록을 받는다. 해외의 GoDaddy, Tucows, 국내의 가비아, 후이즈 같은 업체가 등록대행자다. KISA는 `.kr` 등록 업무에 경쟁 체계를 도입해, 인터넷주소법에 따라 KISA와 등록대행 계약을 맺은 업체가 가격과 부가 서비스를 다르게 제공한다. 레지스트리는 존 데이터를 운영하고, 등록대행자는 사용자 계정과 결제를 맡는 분업 구조다.

## DNS 존과 권한 네임서버

### 존과 도메인의 차이

도메인 트리는 이름 공간이 어떻게 생겼는지를 보여 줄 뿐, 누가 어느 부분을 관리하는지는 나타내지 않는다. DNS의 관리 단위는 존(zone)이다. 존은 트리에서 이어진 도메인과 서브도메인을 하나로 묶고 그 묶음의 관리 권한을 한 주체에 맡긴다. 도메인은 이름의 범위이고 존은 권한의 범위다. 도메인 하나가 여러 존으로 나뉘어 각기 다른 주체가 관리할 수도 있다.

![example.com 존 아래 usa, uk, france 서브도메인이 각각 별도 존이고, usa 존 아래 nyc가 다시 별도 존인 구조](./images/net-dns-attack-zones.svg 'chicago와 boston은 usa 존 안에 남고 nyc는 따로 위임됐다')

위 그림의 회사는 국가별 지사가 자기 DNS 정보를 직접 관리하도록 `usa`, `uk`, `france` 서브도메인의 관리 권한을 위임(delegation)했다. 회사 전체를 존 하나로 관리할 수도 있지만, 그러면 지사의 변경 하나하나가 본사를 거쳐야 하는 의존성이 생긴다. 위임하면 `example.com` 존에는 위임하지 않은 이름(`mail.example.com` 등)의 레코드와, 각 서브도메인의 권한 서버를 가리키는 NS 레코드만 남는다.

존과 도메인이 같아지는 경우도 있다. 도메인을 서브도메인으로 나누지 않았거나, 나눴더라도 서브도메인 데이터를 같은 존에 넣었다면 그 존이 도메인의 DNS 데이터 전부를 담으므로 둘은 일치한다. 서브도메인을 별도 존으로 위임하는 순간 부모 존은 도메인 데이터의 일부만 갖는다.

![kr 존, co.kr 존, user-domain.co.kr 존, lab.user-domain.co.kr 존 사이의 존 컷과 존 정점을 표시한 그림](./images/net-dns-attack-zonecut.svg '존 컷(zone cut)마다 권한이 아래 존으로 넘어간다')

부모 존과 자식 존의 경계를 존 컷(zone cut)이라 하고, 자식 존의 맨 위 노드를 존 정점(zone apex)이라 한다. 위 그림에서 `kr` 도메인은 `kr` 존, `co.kr` 존, `user-domain.co.kr` 존, `lab.user-domain.co.kr` 존으로 나뉘고, `www`와 `ftp`는 `user-domain.co.kr` 존 안에 남는다. `lab.user-domain.co.kr`은 도메인이면서 동시에 하나의 존이다.

### 권한 네임서버와 존 전송

각 존에는 그 존의 정보를 공개하는 권한 네임서버(authoritative name server)가 최소 하나 있다. 권한 네임서버는 DNS 질의에 원본이자 확정적인 답을 준다. 권한 네임서버는 주 서버(primary, master)와 보조 서버(secondary, slave)로 나뉜다. 주 서버는 존 레코드의 원본을 보관하고, 보조 서버는 자동 갱신 방식으로 같은 사본을 유지한다.

![주 네임서버가 마스터 존 파일을 읽고 보조 네임서버로 존 전송을 하며, 재귀 네임서버가 두 서버에 반복 질의를 보내고, 사용자 호스트의 스텁 리졸버가 재귀 네임서버에 재귀 질의를 보내는 구조](./images/net-dns-attack-servers.svg '권한 서버 쪽은 존 전송, 사용자 쪽은 재귀 질의, 그 사이는 반복 질의')

보조 서버는 주 서버의 SOA 레코드 일련 번호(serial)를 주기적으로 조회하고, 번호가 커졌으면 존 전송(zone transfer, AXFR·IXFR)으로 내용을 받아 온다. 존 전송은 TCP 53번 포트를 쓴다. 존 전송을 아무 호스트에나 허용하면 존 안의 모든 이름이 노출되므로, 실제 운영에서는 보조 서버의 주소로만 허용하고 TSIG(RFC 8945) 같은 공유 키 인증을 더한다.

### 존 파일

BIND 9에서 존은 `named.conf`에 선언하고 실제 레코드는 존 파일에 적는다. 정방향 조회(이름에서 주소)와 역방향 조회(주소에서 이름)를 위한 존을 하나씩 선언하면 다음과 같다.

```bash
// /etc/bind/named.conf.local
zone "example.net" {
    type master;
    file "/etc/bind/example.net.db";
};

zone "0.168.192.in-addr.arpa" {
    type master;
    file "/etc/bind/192.168.0.db";
};
```

정방향 존 파일은 SOA, NS, MX, A 레코드로 이루어진다.

```bash
; /etc/bind/example.net.db
$TTL 3D        ; 자체 TTL이 없는 레코드의 기본 만료 시간
@       IN      SOA     ns.example.net. admin.example.net. (
                1       ; Serial
                8H      ; Refresh
                2H      ; Retry
                4W      ; Expire
                1D )    ; Minimum (부정 응답 캐시 TTL)

@       IN      NS      ns.example.net.
@       IN      MX      10 mail.example.net.

www     IN      A       192.168.0.101
mail    IN      A       192.168.0.102
ns      IN      A       192.168.0.10
*.example.net.  IN  A   192.168.0.100   ; 나머지 모든 이름
```

`@`는 존 이름 자체(`example.net.`)를 뜻한다. SOA의 두 번째 이름 `admin.example.net.`은 관리자 메일 주소 `admin@example.net`을 점으로 표기한 값이다. Refresh는 보조 서버가 주 서버의 일련 번호를 확인하는 주기, Retry는 그 확인이 실패했을 때 다시 시도하는 간격, Expire는 주 서버와 연락이 끊긴 보조 서버가 존 데이터를 더 이상 권한 있는 답으로 쓰지 않게 되는 시한이다. RFC 2308 이후 Minimum 값은 존재하지 않는 이름에 대한 부정 응답(NXDOMAIN)을 캐시하는 시간으로 쓰인다. 마지막 줄의 와일드카드는 따로 정의하지 않은 모든 이름에 `192.168.0.100`을 돌려준다.

역방향 존 파일은 같은 SOA·NS 뒤에 PTR 레코드를 둔다. 레코드 이름 `101`은 존 이름 `0.168.192.in-addr.arpa.`와 이어져 `101.0.168.192.in-addr.arpa.`, 즉 주소 `192.168.0.101`을 가리킨다.

```bash
; /etc/bind/192.168.0.db
$TTL 3D
@       IN      SOA     ns.example.net. admin.example.net. (
                1 8H 2H 4W 1D )
@       IN      NS      ns.example.net.

101     IN      PTR     www.example.net.
102     IN      PTR     mail.example.net.
10      IN      PTR     ns.example.net.
```

설정을 바꾼 뒤에는 `named-checkconf{:bash}`와 `named-checkzone example.net /etc/bind/example.net.db{:bash}`로 문법을 검사하고 `sudo rndc reload{:bash}`로 서버가 설정을 다시 읽게 한다. 사용자 호스트가 이 서버를 쓰도록 `/etc/resolv.conf`의 `nameserver` 줄을 바꾸고 `dig www.example.net{:bash}`으로 결과를 확인한다.

## DNS 질의 과정

### 스텁 리졸버와 재귀 리졸버

응용 프로그램은 IP 주소가 필요하면 로컬 호스트의 DNS 리졸버에 묻는다. 이 리졸버는 직접 DNS 트리를 탐색하지 않고, 자기 캐시에서 답을 찾지 못하면 미리 지정한 DNS 서버 하나에 질의를 통째로 맡긴다. 이런 단순한 리졸버를 스텁 리졸버(stub resolver)라 한다. 질의를 받아 트리를 따라 끝까지 답을 찾아 주는 서버는 재귀 리졸버(recursive resolver)이고, 흔히 로컬 DNS 서버, 캐시 DNS 서버라 부른다. ISP가 DHCP로 알려 주는 서버나 Cloudflare `1.1.1.1`, Google `8.8.8.8` 같은 공개 리졸버가 여기에 해당한다. 사용자의 망 바깥에 있을 수도 있으므로 "로컬"보다 "기본(default) DNS 서버"가 더 정확한 이름이다.

![로컬 컴퓨터 안에서 웹 브라우저와 메일 클라이언트가 스텁 리졸버에 묻고, 스텁 리졸버가 ISP의 재귀 리졸버에 물으며, 각 단계에 캐시가 있는 구조](./images/net-dns-attack-stub.svg '브라우저, 운영체제, 재귀 리졸버가 각자 캐시를 가진다')

캐시는 여러 층에 있다. 브라우저가 자체 캐시를 갖고, 운영체제의 스텁 리졸버가 캐시를 갖고, 재귀 리졸버가 가장 큰 공유 캐시를 갖는다. 공격자 입장에서는 재귀 리졸버의 캐시가 가장 가치가 크다. 한 번 오염시키면 그 리졸버를 쓰는 사용자 전체가 영향을 받기 때문이다.

### 로컬 DNS 파일

DNS 서버에 묻기 전에 호스트가 조회하는 파일이 두 개 있다.

| 파일               | 역할                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| `/etc/hosts`       | 일부 호스트 이름의 IP 주소를 직접 보관한다. 대부분의 시스템에서 DNS보다 먼저 조회한다.  |
| `/etc/resolv.conf` | 스텁 리졸버가 질의를 보낼 DNS 서버 주소를 보관한다. DHCP가 받은 주소도 여기에 기록된다. |

조회 순서는 `/etc/nsswitch.conf`의 `hosts:` 줄(예: `files dns`)이 정한다. DHCP 클라이언트가 임대를 갱신할 때 `/etc/resolv.conf`를 덮어쓰므로, DNS 서버를 고정하려면 DHCP 클라이언트 설정이나 `systemd-resolved` 설정에서 지정해야 한다.

### 반복 질의와 재귀 질의

재귀 리졸버는 루트부터 차례로 내려간다. 루트 서버는 `www.example.net`의 주소를 모르지만 `.net`을 관리하는 서버 목록은 안다. 그래서 답 대신 ".net 서버에 물어보라"는 위임 응답(referral)을 돌려준다. `.net` 서버도 같은 방식으로 `example.net` 서버 목록을 알려 주고, 마지막으로 `example.net`의 권한 서버가 실제 주소를 준다.

![로컬 DNS 서버가 루트, .net, example.net 서버에 차례로 www.example.net의 주소를 묻고, 앞의 두 서버는 다음 서버를 알려 주는 위임 응답을, 마지막 서버는 답을 주는 과정](./images/net-dns-attack-referral.svg '루트와 TLD 서버는 답을 모르면 다음 단계 서버를 알려 준다')

질의 방식은 두 가지다. 재귀 질의(recursive query)는 "최종 답을 찾아서 달라"는 요청이고, 받은 서버가 대신 탐색을 끝까지 수행한다. 반복 질의(iterative query)는 "아는 만큼만 달라"는 요청이고, 받은 서버는 답이나 다음 단계 서버의 목록을 돌려준다. 메시지 헤더의 RD(Recursion Desired) 비트가 요청 종류를, RA(Recursion Available) 비트가 서버의 재귀 지원 여부를 나타낸다.

![위쪽은 로컬 컴퓨터가 재귀 리졸버에 재귀 질의를 보내고 그 서버가 루트·TLD·2단계 서버를 반복 질의하는 구조, 아래쪽은 로컬 리졸버가 직접 각 서버를 반복 질의하는 구조](./images/net-dns-attack-recursive.svg '재귀 리졸버를 쓰면 탐색은 서버가, 반복 리졸버를 쓰면 클라이언트가 한다')

일반적인 구성에서는 사용자 호스트와 재귀 리졸버 사이만 재귀 질의이고, 재귀 리졸버와 권한 서버 사이는 반복 질의다. 루트 서버나 TLD 서버는 부하 때문에 재귀 질의를 받아 주지 않는다. 이론상 모든 서버가 재귀 질의를 허용하면 요청이 사슬처럼 이어져 마지막 서버의 답이 거꾸로 전달되지만, 상위 서버에 부하가 몰리므로 실제로는 쓰지 않는다.

`dig`의 옵션으로 두 방식을 비교할 수 있다.

| 명령                                      | 동작                                                    |
| ----------------------------------------- | ------------------------------------------------------- |
| `dig www.example.com`                     | RD=1로 기본 리졸버에 재귀 질의(`+recurse`가 기본값)     |
| `dig +norecurse www.example.com`          | RD=0으로 보내 서버가 아는 것만 받는다                   |
| `dig +trace www.example.com`              | dig가 직접 루트부터 반복 질의하며 각 단계의 응답을 출력 |
| `dig @a.root-servers.net www.example.net` | 지정한 서버 하나에 직접 질의                            |

### 반복 질의를 손으로 따라가기

재귀 리졸버가 하는 일을 `dig @서버`로 한 단계씩 재현하면 위임 응답의 구조가 보인다. 먼저 루트 서버에 묻는다.

```text
$ dig @a.root-servers.net www.example.net
;; QUESTION SECTION:
;www.example.net.            IN  A

;; AUTHORITY SECTION:
net.                  172800  IN  NS  m.gtld-servers.net.
net.                  172800  IN  NS  l.gtld-servers.net.
net.                  172800  IN  NS  k.gtld-servers.net.

;; ADDITIONAL SECTION:
m.gtld-servers.net.   172800  IN  A   192.55.83.30
l.gtld-servers.net.   172800  IN  A   192.41.162.30
k.gtld-servers.net.   172800  IN  A   192.52.178.30
```

Answer 섹션이 비어 있고, Authority 섹션에 `.net`의 NS 레코드가, Additional 섹션에 그 네임서버들의 A 레코드가 들어 있다. Additional 섹션의 주소를 글루 레코드(glue record)라 한다. `.net`의 네임서버 이름 `m.gtld-servers.net`이 `.net` 안에 있으므로, 주소를 함께 주지 않으면 그 이름을 찾기 위해 다시 `.net` 서버에 물어야 하는 순환이 생기기 때문이다. TTL 172800초는 48시간이다.

`.net` 서버와 `example.net` 서버에 차례로 같은 질문을 한다.

```text
$ dig @m.gtld-servers.net www.example.net
;; AUTHORITY SECTION:
example.net.          172800  IN  NS  a.iana-servers.net.
example.net.          172800  IN  NS  b.iana-servers.net.

;; ADDITIONAL SECTION:
a.iana-servers.net.   172800  IN  A   199.43.132.53
b.iana-servers.net.   172800  IN  A   199.43.133.53

$ dig @a.iana-servers.net www.example.net
;; ANSWER SECTION:
www.example.net.      86400   IN  A   93.184.216.34
```

`.net` 서버는 `example.net`의 권한 서버를 알려 주고, 그 서버에 물으면 Answer 섹션에 최종 A 레코드가 온다. 재귀 리졸버는 이 과정에서 받은 NS·A 레코드를 모두 캐시해, 다음에 `ftp.example.net`을 물으면 루트와 `.net`을 건너뛰고 곧바로 `example.net` 서버에 묻는다.

### DNS 캐시

로컬 DNS 서버는 다른 서버에서 받은 정보를 캐시한다. 캐시의 각 항목은 TTL(time-to-live) 값을 가지고, TTL이 지나면 캐시에서 삭제된다. TTL은 레코드를 공개하는 권한 서버가 정한다. 캐시가 성능을 크게 높이는 반면, 잘못된 레코드가 들어가면 TTL 동안 계속 잘못된 답을 내준다는 점이 캐시 오염 공격의 근거가 된다.

BIND에서는 캐시를 파일로 내보내 내용을 조회할 수 있다. `sudo rndc dumpdb -cache{:bash}`는 `named.conf.options`의 `dump-file`에 지정한 경로(기본 `/var/cache/bind/named_dump.db`, 설정에 따라 `dump.db`)에 캐시를 기록하고, `sudo rndc flush{:bash}`는 캐시 전체를 삭제한다. 오염이 의심되면 덤프에서 해당 도메인의 NS·A 레코드를 확인하고, 이상한 항목이 있으면 `rndc flushname example.net{:bash}`로 그 이름만 삭제한다.

## DNS 메시지 형식

### 헤더와 네 섹션

DNS 질의와 응답은 같은 형식을 쓴다. 12바이트 고정 헤더 뒤에 Question, Answer, Authority, Additional 네 섹션이 온다.

![16비트 폭으로 그린 DNS 헤더: ID, 플래그(QR, Opcode, AA, TC, RD, RA, Z, AD, CD, RCODE), 네 개의 개수 필드와 그 뒤의 가변 길이 섹션 네 개](./images/net-dns-attack-header.svg '헤더 12바이트 중 공격과 방어의 초점은 ID 16비트다')

| 필드    | 비트 | 의미                                                                |
| ------- | ---- | ------------------------------------------------------------------- |
| ID      | 16   | 트랜잭션 ID. 질의자가 정하고 응답이 그대로 복사해 짝을 맞춘다       |
| QR      | 1    | 0이면 질의, 1이면 응답                                              |
| Opcode  | 4    | 0 표준 질의(QUERY), 2 상태(STATUS), 4 NOTIFY, 5 UPDATE              |
| AA      | 1    | Authoritative Answer. 권한 서버가 준 답이면 1                       |
| TC      | 1    | TrunCation. UDP 크기 제한으로 잘렸으면 1, 클라이언트는 TCP로 재질의 |
| RD      | 1    | Recursion Desired. 재귀 질의 요청                                   |
| RA      | 1    | Recursion Available. 서버가 재귀를 지원하면 1                       |
| Z       | 1    | 예약, 0                                                             |
| AD      | 1    | Authentic Data. 리졸버가 DNSSEC 검증에 성공했으면 1(RFC 4035)       |
| CD      | 1    | Checking Disabled. 질의자가 DNSSEC 검증을 직접 하겠다는 표시        |
| RCODE   | 4    | 0 NOERROR, 1 FORMERR, 2 SERVFAIL, 3 NXDOMAIN, 4 NOTIMP, 5 REFUSED   |
| QDCOUNT | 16   | Question 섹션의 항목 수                                             |
| ANCOUNT | 16   | Answer 섹션의 자원 레코드 수                                        |
| NSCOUNT | 16   | Authority 섹션의 자원 레코드 수                                     |
| ARCOUNT | 16   | Additional 섹션의 자원 레코드 수                                    |

네 섹션의 역할은 다음과 같다. Question 섹션은 질의 내용(이름, 타입, 클래스)을, Answer 섹션은 질문에 대한 답 레코드를, Authority 섹션은 권한 네임서버를 가리키는 레코드를, Additional 섹션은 질의와 관련된 추가 레코드를 담는다. 앞의 루트 서버 응답에서 Answer가 비고 Authority와 Additional만 채워진 모습이 위임 응답의 전형이다.

플래그 필드를 16진수로 읽는 연습을 한 번 해 둔다. 권한 서버의 응답에서 흔히 보이는 `0x8400`을 이진수로 풀면 다음과 같다.

```math
\texttt{0x8400} = \underbrace{1}_{\text{QR}}\,\underbrace{0000}_{\text{Opcode}}\,\underbrace{1}_{\text{AA}}\,\underbrace{0}_{\text{TC}}\,\underbrace{0}_{\text{RD}}\;\underbrace{0}_{\text{RA}}\,\underbrace{0}_{\text{Z}}\,\underbrace{0}_{\text{AD}}\,\underbrace{0}_{\text{CD}}\,\underbrace{0000}_{\text{RCODE}}
```

QR=1(응답), Opcode=0(표준 질의), AA=1(권한 있는 응답)이고 나머지는 모두 0이다. 재귀 리졸버가 클라이언트에 주는 응답은 보통 RD·RA가 켜진 `0x8180`이다.

### 자원 레코드

Answer, Authority, Additional 섹션의 항목은 모두 자원 레코드(RR, Resource Record) 형식이다. 이름(NAME), 타입(TYPE, 16비트), 클래스(CLASS, 16비트, 인터넷은 IN=1), TTL(32비트, 초), 데이터 길이(RDLENGTH, 16비트), 데이터(RDATA)로 이루어진다. Question 섹션 항목은 이 중 이름, 타입, 클래스만 가진다.

| 타입   | 번호 | 데이터                        | 정의     |
| ------ | ---- | ----------------------------- | -------- |
| A      | 1    | IPv4 주소 4바이트             | RFC 1035 |
| NS     | 2    | 권한 네임서버의 이름          | RFC 1035 |
| CNAME  | 5    | 별칭이 가리키는 정식 이름     | RFC 1035 |
| SOA    | 6    | 존의 시작, 일련 번호와 타이머 | RFC 1035 |
| PTR    | 12   | 역방향 조회 결과 이름         | RFC 1035 |
| MX     | 15   | 우선순위와 메일 서버 이름     | RFC 1035 |
| TXT    | 16   | 임의 문자열(SPF, 도메인 검증) | RFC 1035 |
| AAAA   | 28   | IPv6 주소 16바이트            | RFC 3596 |
| DS     | 43   | 자식 존 키의 해시             | RFC 4034 |
| RRSIG  | 46   | 레코드 집합의 서명            | RFC 4034 |
| NSEC   | 47   | 다음 이름(부재 증명)          | RFC 4034 |
| DNSKEY | 48   | 존의 공개 키                  | RFC 4034 |

메시지 안에서 이름은 점 대신 레이블마다 길이 바이트를 앞에 붙이고 길이 0 바이트로 끝낸다. `www.example.com`은 `3 www 7 example 3 com 0`으로 표기하고 길이는 다음과 같다.

```math
(1+3) + (1+7) + (1+3) + 1 = 17 \text{ 바이트}
```

같은 이름이 메시지 안에서 반복되면 앞서 나온 위치를 가리키는 2바이트 포인터(상위 2비트가 `11`)로 압축한다.

### 응답을 믿는 조건

리졸버가 UDP로 받은 응답을 자기 질의의 답으로 받아들이려면 다음 조건이 모두 맞아야 한다. 이 목록은 공격자가 위조 응답을 만들 때 맞춰야 하는 값이기도 하므로, 방어는 결국 이 중 추측하기 어려운 값을 늘리는 방향으로 간다.

1. 응답의 출발지 IP 주소가 질의를 보낸 DNS 서버의 주소와 같다.
2. 응답의 목적지 IP 주소가 질의한 호스트의 주소와 같다.
3. 응답의 출발지 UDP 포트가 질의의 목적지 포트(보통 53)와 같다.
4. 응답의 목적지 UDP 포트가 질의의 출발지 포트와 같다.
5. UDP 체크섬이 올바르다.
6. 트랜잭션 ID가 질의의 ID와 같다.
7. 응답 Question 섹션의 이름이 질의의 Question 섹션과 같다.
8. Answer 섹션의 이름이 질의한 이름과 같다.
9. 진짜 응답보다 먼저 도착한다.

![IP 헤더의 출발지·목적지 주소, UDP 헤더의 출발지 포트 53과 목적지 포트, DNS 헤더의 트랜잭션 ID와 플래그 0x8400, 레코드 개수를 표시한 응답 패킷 구조](./images/net-dns-attack-reply.svg '파랗게 칠한 필드가 리졸버가 질의와 대조하는 값이다')

1~5번과 7~8번은 질의를 볼 수 없는 원격 공격자도 대부분 알거나 계산할 수 있다. 서버 주소와 포트 53은 공개돼 있고, 질의 이름은 공격자가 직접 질의를 유도하면 정할 수 있으며, 체크섬은 패킷을 만들면서 계산하면 된다. 남는 비밀은 6번 트랜잭션 ID와 4번 질의의 출발지 포트 두 가지다. 이 두 값의 무작위성이 원격 공격에 대한 DNS의 거의 유일한 방어선이다.

### 역방향 조회

역방향 조회(reverse lookup)는 IP 주소로 호스트 이름을 찾는다. IP 주소는 왼쪽이 상위 단위이고 도메인 이름은 오른쪽이 상위 단위이므로, 리졸버는 옥텟 순서를 뒤집은 이름을 만들어 `in-addr.arpa` 밑에 붙인다. `128.230.171.184`의 역방향 질의 이름은 `184.171.230.128.in-addr.arpa`이고, 이 이름의 PTR 레코드를 묻는다. IPv6는 니블(4비트) 단위로 뒤집어 `ip6.arpa` 밑에 붙인다.

![IP 주소 128.230.171.184를 184.171.230.128.in-addr.arpa로 바꾸고, 루트, in-addr.arpa, 128.in-addr.arpa, 230.128.in-addr.arpa 순으로 위임을 따라가는 그림](./images/net-dns-attack-reverse.svg '역방향 트리도 정방향과 같은 위임 구조를 따른다')

반복 과정은 정방향과 같다.

| 단계 | 질의 대상                         | 받은 응답                                                          |
| ---- | --------------------------------- | ------------------------------------------------------------------ |
| 1    | 루트 서버                         | `in-addr.arpa` 존의 네임서버                                       |
| 2    | `in-addr.arpa` 네임서버           | `128.in-addr.arpa` 존의 네임서버                                   |
| 3    | `128.in-addr.arpa` 네임서버(ARIN) | `230.128.in-addr.arpa` 존의 네임서버(`ns1.syr.edu`, `ns2.syr.edu`) |
| 4    | `230.128.in-addr.arpa` 네임서버   | PTR 레코드 `syr.edu`                                               |

3·4단계를 `dig`로 재현하면 다음과 같다.

```text
$ dig @r.arin.net -x 128.230.171.184
;; AUTHORITY SECTION:
230.128.in-addr.arpa.   86400  IN  NS  ns2.syr.edu.
230.128.in-addr.arpa.   86400  IN  NS  ns1.syr.edu.

$ dig @ns2.syr.edu -x 128.230.171.184
;; ANSWER SECTION:
184.171.230.128.in-addr.arpa.  3600  IN  PTR  syr.edu.
```

`dig -x 128.230.171.184{:bash}`는 이 질의 이름을 자동으로 만들어 PTR을 묻는다. 3단계에서 ARIN 서버가 등장하는 이유는 `128.0.0.0/8` 블록을 북미 지역 인터넷 레지스트리인 ARIN이 관리하기 때문이다. 4단계의 서버는 주소 블록 `128.230.0.0/16`을 받은 기관이 운영한다. 이 사실이 뒤의 역방향 조회 위조 공격의 핵심이다.

## DNS 공격 개관

### 두 가지 목표

DNS 공격은 크게 두 갈래다. 서비스 거부(DoS) 공격은 로컬 DNS 서버나 권한 네임서버가 질의에 응답하지 못하게 만든다. 이름을 주소로 바꾸지 못하면 호스트는 사실상 통신할 수 없다. DNS 스푸핑(spoofing) 공격은 피해자에게 거짓 IP 주소를 주어, 의도한 곳과 다른 기계와 통신하게 만든다. 사용자가 은행 사이트에 접속하려는데 DNS가 공격자의 주소를 돌려주면, 사용자 컴퓨터는 공격자의 웹 서버와 통신한다.

### 공격 표면

![사용자 기계의 로컬 DNS 파일(1), 사용자 기계와 로컬 DNS 서버 사이(2), 로컬 DNS 서버와 인터넷의 DNS 서버들 사이(3), 악성 도메인의 권한 서버(4) 네 지점을 번호로 표시한 그림](./images/net-dns-attack-attack-points.svg '번호마다 공격자에게 필요한 위치와 권한이 다르다')

| 위치                             | 공격자의 조건               | 대표 공격                             |
| -------------------------------- | --------------------------- | ------------------------------------- |
| ① 사용자 호스트의 로컬 DNS 파일  | 호스트의 관리자 권한 탈취   | `/etc/hosts`, `/etc/resolv.conf` 변조 |
| ② 사용자와 로컬 DNS 서버 사이    | 같은 LAN에서 패킷 관찰      | 사용자에게 응답 위조                  |
| ③ 로컬 DNS 서버와 상위 서버 사이 | 같은 LAN(로컬) 또는 원격    | 로컬·원격 캐시 오염, Kaminsky         |
| ④ 악성 도메인의 권한 서버        | 자기 도메인의 네임서버 운영 | 응답 위조, 역방향 조회 위조, 리바인딩 |

### 침해된 호스트에서의 공격

공격자가 이미 호스트의 루트 권한을 얻었다면 DNS 프로토콜을 건드릴 필요도 없다. `/etc/resolv.conf`를 바꿔 악성 DNS 서버를 로컬 DNS 서버로 지정하면 그 호스트의 DNS 과정 전체를 통제한다. `/etc/hosts`에 `www.bank32.com`의 항목을 더하면 DNS보다 먼저 조회되므로 그 이름만 골라 공격자 주소로 보낸다. 이 공격은 DNS 문제가 아니라 호스트 침해의 결과이므로, 방어는 두 파일의 무결성 감시(파일 무결성 검사 도구, 설정 관리 도구의 주기적 대조)와 권한 관리에 있다. 악성코드가 `hosts` 파일을 바꾸는 사례가 많아 백신 제품도 이 파일을 감시한다.

## 로컬 DNS 캐시 오염

### 같은 LAN에서의 응답 위조

공격자가 사용자나 로컬 DNS 서버와 같은 LAN에 있으면 질의 패킷을 직접 볼 수 있다. 질의를 보면 앞의 9가지 조건에 필요한 값, 특히 트랜잭션 ID와 출발지 포트를 그대로 알 수 있으므로 추측이 필요 없다. 공격자가 할 일은 진짜 응답보다 먼저 위조 응답을 도착시키는 것뿐이다.

![사용자 기계 10.0.2.18, 공격자 10.0.2.17, 로컬 DNS 서버 10.0.2.16이 한 LAN에 연결된 구성](./images/net-dns-attack-lan.svg '세 기계가 같은 브로드캐스트 도메인에 있으면 공격자가 질의를 관찰할 수 있다')

![LAN 안에서 공격자가 사용자의 DNS 질의를 가로채 사용자에게, 또는 로컬 DNS 서버의 상위 질의를 가로채 로컬 DNS 서버에 위조 응답을 보내는 두 경로](./images/net-dns-attack-spoof-paths.svg '왼쪽 공격자는 캐시를, 오른쪽 공격자는 사용자 한 명을 노린다')

공격 지점은 두 곳이다. 사용자 호스트의 질의를 보고 사용자에게 위조 응답을 보내면 그 사용자 한 명만 속는다. 로컬 DNS 서버가 상위 서버로 보내는 질의를 보고 로컬 DNS 서버에 위조 응답을 보내면 서버가 그 응답을 캐시하므로, TTL 동안 그 서버를 쓰는 모든 사용자가 속는다. 후자가 로컬 DNS 캐시 오염(local DNS cache poisoning)이다. 실습 도구는 스니핑 필터로 특정 이름의 질의를 잡아 ID·포트를 복사한 응답을 만들어 보낸다.

### 오염된 캐시의 모습

```text
$ dig www.example.net
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 61991
;; flags: qr aa ra; QUERY: 1, ANSWER: 1, AUTHORITY: 1, ADDITIONAL: 0

;; ANSWER SECTION:
www.example.net.   259200  IN  A   1.2.3.4              ①

;; AUTHORITY SECTION:
example.net.       259200  IN  NS  ns.attacker32.com.   ②
```

오염이 성공한 리졸버에 질의하면 위와 같은 결과가 나온다. ①의 A 레코드는 `www.example.net` 하나만 바꾸지만, ②의 NS 레코드는 `example.net` 아래 모든 이름의 권한 서버를 공격자의 서버로 바꾼다. 리졸버는 이후 `mail.example.net` 등 어떤 이름을 물어도 `ns.attacker32.com`에 묻는다. 공격자가 권한 섹션을 노리는 이유가 이 증폭 효과다. TTL 259200초는 3일이다.

> [!TIP] 로컬 공격의 탐지와 방어
> 같은 질의에 대해 서로 다른 응답 두 개가 짧은 간격으로 도착하는 현상은 응답 경쟁의 흔적이다. 일부 IDS는 이를 탐지 규칙으로 쓴다. 근본 방어는 공격자가 질의를 볼 수 없게 만드는 것이다. 스위치의 포트 보안과 ARP 스푸핑 방지(Dynamic ARP Inspection), 리졸버와 상위 서버 사이의 DNSSEC 검증, 클라이언트와 리졸버 사이의 DoT·DoH가 여기에 해당한다. 같은 LAN의 관찰자에게는 ID 무작위화가 아무 효과가 없다.

## 원격 DNS 캐시 오염

### 두 개의 16비트 비밀

질의를 볼 수 없는 원격 공격자는 트랜잭션 ID와 출발지 포트를 추측해야 한다. 둘 다 16비트이므로 조합은 `2^{32}{:math}`가지다.

```math
2^{16} \times 2^{16} = 2^{32} = 4{,}294{,}967{,}296
```

초당 1,000개의 위조 응답을 보낸다면 공간 전체를 시도하는 데 걸리는 시간은 다음과 같다.

```math
\frac{4{,}294{,}967{,}296}{1{,}000 \text{ /s}} \approx 4{,}294{,}967 \text{ s} \approx 49.7 \text{ 일}
```

호스트 1,000대로 이루어진 봇넷이 각각 초당 1,000개를 보내면 초당 `10^6{:math}`개이므로 약 4,295초, 즉 1.2시간이다. 출발지 포트를 고정한 리졸버라면 ID 16비트만 남아 `65536 / 1000 \approx 65.5{:math}`초에 공간 전체를 덮는다. 출발지 포트 무작위화가 공격 공간을 65,536배 넓힌다는 뜻이다.

### 캐시 효과

계산만 보면 봇넷 앞에서는 32비트도 충분하지 않아 보인다. 그런데 실제 공격에는 시간 창이라는 제약이 있다. 위조 응답은 리졸버가 질의를 보낸 뒤 진짜 응답이 오기 전, 보통 수십~수백 밀리초 안에 도착해야 한다. 그 사이에 맞히지 못하면 진짜 응답이 도착하고, 리졸버는 그 답을 캐시한다. 그러면 TTL이 끝날 때까지 같은 이름으로는 다시 질의가 나가지 않으므로 공격자는 기다려야 한다. 이것이 캐시 효과(cache effect)이고, TTL이 하루라면 하루에 한 번밖에 시도할 수 없다.

## Kaminsky 공격

### 질문을 매번 바꾼다

2008년 Dan Kaminsky는 캐시 효과를 우회하는 방법을 발표했다. 아이디어는 두 가지다. 첫째, 매번 다른 질문을 한다. `www.example.com` 대신 존재하지 않는 무작위 이름 `twysw.example.com`, `qkfzr.example.com` 등을 차례로 묻게 하면, 이름이 매번 캐시에 없으므로 리졸버가 매번 새 질의를 보낸다. 실패해도 기다릴 필요가 없다. 둘째, 위조 응답의 Answer 섹션이 아니라 Authority 섹션에 원하는 정보를 담는다. 공격자가 노리는 것은 무작위 이름의 주소가 아니라 `example.com` 존 전체의 네임서버 정보다.

![Kaminsky 공격 한 회차를 공격자, 로컬 DNS 서버, example.com 권한 서버의 세 생명선으로 그린 시퀀스 도식](./images/net-dns-attack-kaminsky.svg '실패해도 이름만 바꿔 곧바로 다음 회차를 시작한다')

한 회차는 다음 순서로 진행된다.

1. 공격자가 피해 리졸버에 `twysw.example.com`의 주소를 묻는다. 공개 리졸버이거나 공격자가 피해 망 안의 클라이언트로 질의를 유도할 수 있으면 가능하다.
2. 리졸버는 캐시에 없으므로 `example.com` 권한 서버에 질의한다.
3. 공격자는 권한 서버를 사칭한 위조 응답을 여러 개 보낸다. 각 응답은 서로 다른 트랜잭션 ID를 추측한다.
4. 권한 서버의 진짜 응답(NXDOMAIN)보다 ID가 맞는 위조 응답이 먼저 도착하면 오염에 성공하고, 아니면 다른 이름으로 1번부터 다시 한다.

위조 응답은 다음과 같은 모양이다.

```text
;; QUESTION SECTION:
;twysw.example.com.          IN  A

;; ANSWER SECTION:
twysw.example.com.  259200   IN  A   1.2.3.4

;; AUTHORITY SECTION:
example.com.        259200   IN  NS  ns.attacker32.com.
```

위조 응답의 Question과 Answer는 무작위 이름이라 성공해도 쓸모가 없다. 핵심은 Authority 섹션의 `example.com NS ns.attacker32.com`이다. 이 레코드는 `example.com`의 하위 이름에 대한 응답에 실린 `example.com`의 NS이므로, 리졸버의 관점에서는 질의 대상 존에 속한 정상적인 위임 정보로 보인다. 리졸버가 이를 캐시하면 이후 `example.com`의 모든 이름에 대한 질의가 공격자의 네임서버로 간다.

### 성공 확률 계산

Kaminsky 공격이 왜 실용적이었는지 계산으로 확인한다. 출발지 포트가 고정된 리졸버에서 공격자가 한 회차에 위조 응답 `n = 100{:math}`개를 진짜 응답보다 먼저 넣을 수 있다고 하자. 한 회차의 성공 확률은 다음과 같다.

```math
p = \frac{n}{2^{16}} = \frac{100}{65536} \approx 0.00153
```

`k{:math}`회차 안에 한 번이라도 성공할 확률이 50%가 되는 `k{:math}`를 구한다.

```math
1 - (1-p)^k = 0.5 \;\Rightarrow\; k = \frac{\ln 0.5}{\ln(1-p)} \approx \frac{0.693}{0.00153} \approx 454
```

이름만 바꿔 454회차를 반복하는 데는 몇 초에서 몇 분이면 충분하다. 캐시 효과가 있었다면 454회차는 TTL의 454배였다. 이 계산 때문에 2008년 7월 주요 DNS 구현이 동시에 패치를 배포했다(CERT VU#800113).

같은 조건에서 출발지 포트까지 무작위로 바뀌면 다음과 같다.

```math
p = \frac{100}{2^{32}} \approx 2.33 \times 10^{-8}, \qquad k \approx \frac{0.693}{2.33 \times 10^{-8}} \approx 2.98 \times 10^{7}
```

약 3,000만 회차가 필요하다. 각 회차마다 리졸버에 질의 하나와 위조 응답 100개를 보내야 하므로 총 30억 개 가까운 패킷이고, 그 전에 리졸버의 이상 탐지나 응답 속도 제한에 걸린다.

<details>
<summary>실제 포트 공간이 16비트보다 작은 이유</summary>

계산은 포트 16비트를 모두 쓴다고 가정했다. 실제로는 0~1023번 잘 알려진 포트를 빼고, 운영체제나 리졸버 설정에 따라 쓰는 범위가 더 좁다. BIND의 기본 범위가 1024~65535(64,512개)라면 포트에서 얻는 엔트로피는 다음과 같다.

```math
\log_2 64512 \approx 15.98 \text{ 비트}
```

리눅스의 임시 포트 기본 범위 32768~60999(28,232개)를 쓰면 약 14.8비트다. 방화벽이나 NAT 장비가 출발지 포트를 순차 값으로 다시 쓰면 리졸버의 무작위화가 사라진다. 그래서 RFC 5452는 리졸버가 가능한 넓은 포트 범위를 무작위로 쓰고, 중간 장비가 이를 보존하도록 요구한다.

</details>

> [!IMPORTANT] Kaminsky 공격이 드러낸 것
> 이 공격은 구현 버그가 아니라 프로토콜 설계의 한계를 이용했다. 32비트 미만의 비밀로 인증하는 UDP 질의응답 구조는 시도 횟수 제한이 사라지면 버틸 수 없다. 포트 무작위화는 공격 비용을 높였을 뿐 원리적으로 막지는 못하므로, 근본 해법은 응답 자체를 서명하는 DNSSEC다.

### 탐지 지표

Kaminsky 공격은 흔적을 많이 남긴다. 같은 존 아래 존재하지 않는 무작위 이름에 대한 질의가 짧은 시간에 급증하고, 권한 서버를 사칭한 응답 중 트랜잭션 ID가 맞지 않아 버려지는 응답 수가 늘어난다. BIND와 Unbound는 이런 불일치 응답 수를 통계로 집계하고, Unbound의 `unwanted-reply-threshold`는 불일치 응답이 기준을 넘으면 경고를 남기고 캐시를 보호하는 조치를 한다. 리졸버 모니터링에서 NXDOMAIN 비율과 불일치 응답 수를 함께 조회하면 공격 시도를 조기에 발견한다.

## 악성 DNS 서버의 응답 위조

### 자기 도메인의 권한 서버를 이용한 공격

공격자가 패킷을 위조하지 않아도 되는 경로도 있다. 공격자는 자기 도메인(`attacker32.com`)을 등록하고 그 권한 네임서버를 직접 운영할 수 있다. 사용자가 `attacker32.com`에 접속하면 질의가 결국 공격자의 서버로 오고, 공격자는 정당한 권한 서버로서 응답한다. 이때 Answer 섹션뿐 아니라 Authority와 Additional 섹션에도 아무 정보나 넣을 수 있다.

리졸버의 방어 원칙은 베일리윅(bailiwick) 검사다. 질의한 존의 권한 서버는 그 존 안의 이름에 대해서만 믿을 수 있다. 존 바깥 이름에 대한 레코드(out-of-zone, out-of-bailiwick)는 버린다. RFC 2181 5.4.1절은 자료의 출처에 따라 신뢰 순위를 정하고, Additional 섹션의 자료를 가장 낮은 순위로 둔다.

### Authority 섹션의 위조

```text
;; QUESTION SECTION:
;www.example.net.            IN  A

;; ANSWER SECTION:
www.example.net.    259200   IN  A   192.168.0.101

;; AUTHORITY SECTION:
example.net.        259200   IN  NS  ns.example.net.    허용
facebook.com.       259200   IN  NS  ns.example.net.    존 밖이므로 버림
```

`www.example.net`을 물었는데 `example.net`의 권한 서버가 Authority 섹션에 `facebook.com NS ns.example.net`을 넣었다. 이 서버는 `facebook.com`에 대해 아무 권한이 없으므로 리졸버는 이 레코드를 버린다. 받아들인다면 `facebook.com` 전체의 네임서버가 공격자 서버로 바뀐다.

### Additional 섹션의 위조

```text
;; ANSWER SECTION:
www.example.net.    259200   IN  A   192.168.0.101

;; AUTHORITY SECTION:
example.net.        259200   IN  NS  www.facebook.com.  허용

;; ADDITIONAL SECTION:
www.facebook.com.   259200   IN  A   192.168.0.201      존 밖이므로 쓰지 않음
```

이번에는 `example.net`의 네임서버를 `www.facebook.com`이라고 알리고, Additional 섹션에 `www.facebook.com`의 주소를 공격자 주소로 넣었다. NS 레코드 자체는 `example.net`에 대한 정보이므로 허용된다. 그러나 `www.facebook.com`의 A 레코드는 `example.net` 존 바깥이므로 믿지 않고, 리졸버가 `facebook.com`의 권한 서버에 직접 물어 주소를 얻는다. 글루 레코드가 필요한 경우는 네임서버 이름이 위임받은 존 안에 있을 때뿐이므로, 존 밖 글루를 버려도 정상 동작에는 지장이 없다.

BIND로 확인하면 Additional 섹션의 존 밖 자료가 캐시 덤프에 남기는 하지만, 응답을 만들 때는 그 자료를 쓰지 않는다. 다른 사람에게 들은 2차 정보는 답의 근거로 쓰지 않는다는 원칙이다.

> [!NOTE] 베일리윅 검사와 Kaminsky 공격
> Kaminsky 공격의 위조 응답은 `twysw.example.com`을 물었을 때 `example.com`의 NS를 주므로 베일리윅 검사를 통과한다. 베일리윅 검사는 악성 권한 서버가 남의 존을 사칭하는 것은 막지만, 정당한 권한 서버를 사칭하는 위조 패킷은 막지 못한다. 후자는 무작위화와 서명의 몫이다.

### 역방향 조회를 이용한 위조

역방향 조회 결과를 접근 제어에 쓸 수 있을까. 예를 들어 "`syr.edu`에서 온 패킷만 이 서비스를 쓸 수 있다"는 규칙을, 패킷의 출발지 주소를 역방향 조회해 이름이 `syr.edu`로 끝나는지로 판정한다고 하자.

앞의 역방향 조회 4단계를 다시 보면, 마지막 PTR 응답은 그 주소 블록을 받은 기관의 서버가 준다. 공격자가 보낸 패킷의 출발지 주소는 공격자의 주소 블록에 속하므로, 그 역방향 조회는 공격자가 운영하는 네임서버로 간다. 공격자는 PTR에 어떤 이름이든 적을 수 있다. `192.168.0.101`이 `www.example.net` 대신 `www.facebook.com`이라고 답해도 막는 장치가 없다.

> [!CAUTION] 역방향 조회 결과로 접근을 허용하지 않는다
> PTR 레코드는 주소 소유자가 스스로 주장하는 이름일 뿐이다. 이름 기반 접근 제어가 꼭 필요하면 FCrDNS(Forward-Confirmed reverse DNS)를 쓴다. PTR로 얻은 이름을 다시 정방향으로 조회해 그 결과에 원래 주소가 들어 있는지 대조한다. 공격자는 자기 역방향 존은 조작할 수 있지만 `syr.edu`의 정방향 존은 조작할 수 없다. 그래도 가장 안전한 방법은 이름이 아닌 암호학적 인증이다.

## 캐시 오염에 대한 방어

### DNSSEC

DNSSEC(DNS Security Extensions)는 DNS 자료에 출처 인증과 무결성 검증을 더하는 확장이다(RFC 4033·4034·4035). DNSSEC으로 보호되는 존의 모든 응답에는 디지털 서명이 붙는다. 리졸버는 서명을 검증해 정보가 진짜인지 판단하고, 위조 자료는 서명 검증에 실패하므로 캐시 오염이 막힌다. 공격자가 트랜잭션 ID와 포트를 모두 맞혀도, 존의 개인 키 없이는 올바른 서명을 만들 수 없다.

DNSSEC이 더한 레코드는 네 가지다.

| 레코드       | 내용                                                          |
| ------------ | ------------------------------------------------------------- |
| DNSKEY       | 존의 공개 키. 보통 키 서명 키(KSK)와 존 서명 키(ZSK)로 나뉜다 |
| RRSIG        | 같은 이름·타입의 레코드 집합(RRset)에 대한 서명               |
| DS           | 자식 존 KSK의 해시. 부모 존에 두고 부모가 서명한다            |
| NSEC / NSEC3 | 정렬 순서상 다음 이름. 이름이 없다는 사실을 서명으로 증명한다 |

![루트 서버 응답의 DNSKEY, RRSIG, .net 서버 공개 키의 해시인 DS가 .net 서버 응답의 DNSKEY를 검증하고, .net 응답의 DS가 example.net 서버 응답의 DNSKEY를 검증하는 신뢰 사슬](./images/net-dns-attack-dnssec-chain.svg '루트 키 하나만 별도 경로로 믿으면 나머지는 서명으로 이어진다')

신뢰 사슬(chain of trust)은 다음처럼 이어진다.

1. 리졸버는 루트 존의 KSK를 신뢰 앵커(trust anchor)로 미리 설정해 둔다. 이 키는 DNS가 아닌 다른 경로로 얻은 정보다.
2. 루트 응답의 DNSKEY를 신뢰 앵커와 대조하고, 그 키로 RRSIG를 검증한다. 루트 응답에 실린 `.net`의 DS 레코드도 루트 키로 서명돼 있다.
3. `.net` 서버의 DNSKEY를 해시해 루트가 준 DS와 같은지 확인한다. 같으면 `.net`의 키를 믿고, 그 키로 `.net` 응답의 RRSIG와 `example.net`의 DS를 검증한다.
4. 같은 방식으로 `example.net`의 DNSKEY를 믿고, 최종 A 레코드의 RRSIG를 검증한다.

DS는 부모가 자식의 키를 보증하는 수단이다. 자식 존의 키를 바꾸면 부모의 DS도 바꿔야 하므로, KSK와 ZSK를 나눠 자주 바꾸는 ZSK는 부모와 협의 없이 교체하고 KSK만 DS로 연결한다. 루트 존은 2010년 7월에 서명됐다.

DNSSEC 검증은 재귀 리졸버가 하고, 검증에 성공하면 클라이언트에 주는 응답의 AD 비트를 켠다. 검증에 실패하면 SERVFAIL을 돌려준다. `dig +dnssec example.com{:bash}`으로 RRSIG가 함께 오는지, 응답 플래그에 `ad`가 있는지 조회할 수 있다.

> [!WARNING] DNSSEC이 하지 않는 일
> DNSSEC은 무결성과 출처 인증만 제공하고 기밀성은 제공하지 않는다. 질의 내용은 여전히 평문으로 오간다. 서명하지 않은 존은 보호받지 못하고, 스텁 리졸버가 AD 비트를 그대로 믿으면 스텁과 리졸버 사이의 위조는 막지 못한다. NSEC은 존의 이름 목록을 순서대로 따라가 수집(zone walking)할 수 있게 만들어, NSEC3가 해시로 이를 어렵게 했다. 서명이 붙어 응답이 커지므로 증폭 공격의 재료가 되기도 한다.

### TLS/SSL

TLS(Transport Layer Security)도 캐시 오염에 대한 해법이 된다. DNS로 `www.example.net`의 IP 주소를 얻은 뒤, 클라이언트는 그 주소의 서버에 자신이 정말 `www.example.net`인지 증명하라고 요구한다. 서버는 신뢰할 수 있는 기관이 서명한 공개 키 인증서를 제시하고, 그 인증서에 대응하는 개인 키를 가지고 있음을 보여야 한다. DNS가 오염돼 공격자 서버로 연결되더라도 공격자는 `www.example.net`의 인증서와 개인 키가 없으므로 인증에 실패한다. HTTPS는 TLS 위에 만들어지므로 DNS 캐시 오염을 무력화한다. 다만 사용자가 인증서 경고를 무시하고 진행하면 이 방어는 사라진다.

DNSSEC과 TLS는 모두 공개 키 기술에 기반하지만 신뢰 사슬이 다르다.

| 비교 항목    | DNSSEC                                  | TLS/SSL                                  |
| ------------ | --------------------------------------- | ---------------------------------------- |
| 신뢰 사슬    | DNS 존 계층. 부모 존이 자식 존을 보증   | PKI. 인증 기관(CA)이 다른 컴퓨터를 보증  |
| 신뢰 앵커    | 루트 존 KSK 하나                        | 운영체제·브라우저의 루트 CA 수십~수백 개 |
| 보호 대상    | DNS 응답 자체(이름과 주소의 대응)       | 연결 상대의 신원과 이후 통신 내용        |
| 기밀성       | 없음                                    | 있음(통신 암호화)                        |
| 오염 시 결과 | 위조 응답을 리졸버가 버린다             | 오염은 일어나지만 연결 단계에서 실패한다 |
| 적용 범위    | 존 운영자와 리졸버가 모두 지원해야 한다 | 서버가 인증서를 쓰는 응용 프로토콜만     |

### DNS 전송 암호화

DoT(DNS over TLS, RFC 7858)와 DoH(DNS over HTTPS, RFC 8484)는 스텁 리졸버와 재귀 리졸버 사이의 DNS 메시지를 TLS로 감싼다. DoT는 TCP 853번 포트를 쓰고, DoH는 HTTPS 443번 포트로 일반 웹 트래픽과 섞인다. 두 방식 모두 리졸버의 인증서를 검증하므로 같은 LAN의 공격자가 사용자에게 응답을 위조하는 경로(공격 표면 ②)를 막고, 질의 내용을 엿보는 것도 막는다. 그러나 재귀 리졸버와 권한 서버 사이(③)는 여전히 평문 UDP이고, 리졸버 자체가 오염되면 암호화된 채널로 오염된 답이 전달된다. 전송 암호화는 DNSSEC을 대체하지 않고 보완한다.

### 무작위화와 0x20 인코딩

DNSSEC 배포에는 시간이 걸리므로, 리졸버 쪽에서 위조를 어렵게 만드는 기법이 함께 쓰인다. RFC 5452는 트랜잭션 ID와 출발지 포트를 모두 예측 불가능한 난수로 만들고, 응답의 Question 섹션이 질의와 정확히 같은지 확인하도록 요구한다.

0x20 인코딩(Dagon 등, 2008)은 질의 이름의 대소문자를 무작위로 섞는다. DNS 이름 비교는 대소문자를 구분하지 않지만, 권한 서버는 응답의 Question 섹션에 질의한 이름을 그대로 복사한다. 리졸버가 `wWw.ExAmpLe.cOm`처럼 보내고 응답의 대소문자가 정확히 같은지 확인하면, 위조자는 알파벳 글자마다 1비트를 더 맞혀야 한다. 이름이 0x20인 이유는 ASCII에서 대문자와 소문자의 차이가 `0x20` 비트 하나이기 때문이다. `www.example.com`에는 알파벳이 13글자 있으므로 다음과 같다.

```math
2^{16}_{\text{ID}} \times 2^{16}_{\text{포트}} \times 2^{13}_{\text{0x20}} = 2^{45} \approx 3.5 \times 10^{13}
```

==0x20 인코딩은 프로토콜 변경 없이 리졸버만 고쳐 적용할 수 있다==는 장점이 있다. 반면 알파벳이 적은 이름(`1.example`)에서는 효과가 작고, Question을 소문자로 바꿔 돌려주는 일부 권한 서버와 충돌하므로 실패 시 일반 질의로 되돌리는 처리가 필요하다.

### 리졸버 설정 강화

위 기법들은 대부분 리졸버 설정으로 켠다. BIND 9 기준으로 방어에 해당하는 설정을 모으면 다음과 같다.

```bash
// /etc/bind/named.conf.options
options {
    directory "/var/cache/bind";

    // DNSSEC 검증: 루트 신뢰 앵커를 자동 관리한다
    dnssec-validation auto;

    // 재귀 질의와 캐시 응답은 내부 망에만 허용한다 (개방형 리졸버 방지)
    recursion yes;
    allow-recursion { 127.0.0.1; 192.168.0.0/24; };
    allow-query-cache { 127.0.0.1; 192.168.0.0/24; };

    // 존 전송은 허용하지 않는다 (보조 서버가 있으면 그 주소만)
    allow-transfer { none; };

    // 버전 문자열을 숨긴다
    version "not disclosed";

    // query-source port 를 고정하지 않는다: 출발지 포트 무작위화를 유지한다
};
```

`query-source port 33333;`처럼 출발지 포트를 고정하는 설정은 공격 공간을 `2^{16}{:math}`로 줄이므로 운영 환경에서 쓰면 안 된다. 같은 이유로 `dnssec-validation no;`도 실험 환경 밖에서는 쓰지 않는다. Unbound에서는 `harden-glue: yes`(존 밖 글루 거부), `use-caps-for-id: yes`(0x20 인코딩), `harden-dnssec-stripped: yes`(서명이 있어야 할 응답에서 서명이 빠지면 거부) 같은 옵션이 같은 역할을 한다.

### 방어 기법 비교

| 방어                 | 막는 공격                                   | 막지 못하는 것                       | 적용 위치           |
| -------------------- | ------------------------------------------- | ------------------------------------ | ------------------- |
| 출발지 포트 무작위화 | 원격 응답 위조(공간 `2^{16}{:math}`배 확대) | LAN 관찰자, 악성 권한 서버           | 리졸버, NAT 장비    |
| 0x20 인코딩          | 원격 응답 위조(알파벳 수만큼 비트 추가)     | LAN 관찰자, 짧은 이름                | 리졸버              |
| 베일리윅 검사        | 악성 권한 서버의 존 밖 레코드               | 정당한 서버를 사칭한 위조            | 리졸버              |
| DNSSEC               | 모든 응답 위조, 캐시 오염                   | 서명 안 된 존, 스텁 구간, 기밀성     | 존 운영자와 리졸버  |
| DoT·DoH              | 스텁 구간의 위조와 도청                     | 리졸버 오염, 리졸버와 권한 서버 사이 | 클라이언트와 리졸버 |
| TLS/HTTPS            | 오염된 주소로의 연결 성립                   | 인증서 경고 무시, TLS를 안 쓰는 응용 | 응용 계층           |
| 응답 속도 제한(RRL)  | 반사·증폭 DoS                               | 분산된 정상 형태 질의                | 권한 서버           |
| 재귀 허용 범위 제한  | 개방형 리졸버 악용, 외부의 질의 유도        | 내부 호스트를 통한 유도              | 리졸버              |

## DNS 리바인딩 공격

### 동일 출처 정책

웹 브라우저는 동일 출처 정책(SOP, Same Origin Policy)으로 스크립트를 격리한다. 페이지 안의 JavaScript(Ajax) 코드는 그 페이지를 내려준 서버와만 상호 작용할 수 있다. 출처(origin)는 스킴, 호스트 이름, 포트의 조합이다.

![같은 출처의 두 스크립트는 서로의 데이터와 메서드에 접근하지만, 다른 출처의 스크립트와는 동일 출처 정책 때문에 응답을 주고받지 못하고, 서버 사이의 API 호출은 이 정책과 무관한 구조](./images/net-dns-attack-sop.svg '출처가 다르면 스크립트가 서로의 데이터를 읽지 못한다')

브라우저는 출처를 IP 주소가 아니라 호스트 이름으로 판단한다. 이 점이 리바인딩 공격의 출발점이다.

### 공격 구조

![방화벽 안의 사용자 브라우저에서 공격자 스크립트가 동작하지만, 내부 서버로의 요청은 동일 출처 정책이, 공격자의 직접 접속은 방화벽이 막는 구조](./images/net-dns-attack-firewall.svg '공격자는 방화벽 안 서버에 바깥에서 접근하려 한다')

공격 목표는 방화벽 안쪽의 취약한 서버, 예를 들어 인증 없이 관리 페이지를 여는 공유기나 사물인터넷 기기다. 공격자는 방화벽 때문에 직접 접근하지 못하고, 사용자 브라우저에서 실행되는 공격자 스크립트도 동일 출처 정책 때문에 그 서버에 요청을 보내 응답을 읽지 못한다.

![사용자 기계가 www.attacker32.com의 IP 주소를 묻고 진짜 답을 받아 페이지를 내려받은 뒤, 다시 같은 이름을 물었을 때 악성 네임서버가 내부 서버의 IP 주소를 가짜 답으로 돌려주고 Ajax 코드가 방화벽 안의 내부 서버를 공격하는 과정](./images/net-dns-attack-rebinding.svg '같은 이름이 처음에는 공격자 서버를, 다음에는 내부 서버를 가리킨다')

1. 사용자가 `www.attacker32.com`에 접속한다. 공격자의 네임서버는 진짜 웹 서버 주소를 돌려주되, TTL을 2초처럼 아주 짧게 준다.
2. 브라우저가 공격자 서버에서 페이지와 JavaScript를 받는다.
3. 스크립트가 잠시 기다렸다가 같은 출처 `www.attacker32.com`에 요청을 보낸다. 캐시가 만료됐으므로 브라우저가 다시 주소를 묻고, 이번에는 공격자의 네임서버가 내부 서버의 사설 주소를 돌려준다.
4. 브라우저는 출처가 같다고 판단하므로 스크립트가 내부 서버에 요청을 보내고 응답을 읽어 공격자에게 전달한다.

이름과 주소의 대응을 중간에 바꾼다(rebind)는 데서 이름이 붙었다. 공격자는 자기 도메인의 정당한 권한 서버이므로 패킷 위조나 캐시 오염이 전혀 필요 없다.

### 리바인딩 방어

| 위치     | 방어                                                                                                               | 한계                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| 브라우저 | DNS 피닝(pinning): 세션 중간에 IP 주소가 바뀌는 것을 거부                                                          | 프록시, VPN, CDN과 충돌하고 브라우저마다 구현이 일관되지 않다 |
| 리졸버   | 외부 도메인의 응답에 사설·루프백 주소가 들어 있으면 버린다(dnsmasq `--stop-dns-rebind`, Unbound `private-address`) | 내부 도메인 예외 목록을 따로 관리해야 한다                    |
| 서버     | HTTP `Host` 헤더가 알려진 이름이 아니면 거부                                                                       | 서버마다 설정해야 한다                                        |
| 서버     | IP 주소 외의 수단(비밀번호, 토큰)으로 사용자 인증                                                                  | 인증 없는 임베디드 기기가 많다                                |

리바인딩된 요청의 `Host` 헤더에는 `www.attacker32.com`이 그대로 들어 있으므로, 내부 서버가 자기 이름이 아닌 `Host`를 거부하면 공격이 실패한다. 내부 서비스라도 "방화벽 안이니 안전하다"는 가정을 버리고 인증을 요구하는 것이 근본 방어다.

## DNS 서비스 거부 공격

### 루트 서버 공격

루트 네임서버를 무너뜨리면 인터넷 전체를 멈출 수 있을 것처럼 보이지만, 실제로는 어렵다. 첫째, 루트 서버는 13개 이름 뒤에 애니캐스트로 분산된 수많은 중복 서버가 있다. 둘째, TLD 네임서버 정보는 로컬 DNS 서버에 캐시되고 그 TTL이 48시간(172800초)이다. 루트가 응답하지 않아도 캐시가 남아 있는 동안은 대부분의 이름 해석이 계속된다. 공격이 눈에 띄는 효과를 내려면 이틀 가까이 지속돼야 한다.

### TLD 서버 공격

TLD 네임서버는 루트보다 공격하기 쉽다. `.com`, `.net`, `.gov` 같은 대형 TLD는 DoS에 강한 기반 구조를 갖췄지만, 일부 국가 코드 TLD는 기반 구조가 충분하지 않다. 그런 TLD를 무너뜨리면 특정 국가의 인터넷 이름 해석 전체가 마비될 수 있다.

### 특정 도메인의 네임서버 공격

실제로 큰 피해를 낸 사례는 많은 도메인을 대신 운영하는 DNS 제공자를 겨냥한 공격이다.

| 시기        | 대상                    | 경과와 영향                                                                                                                                                                                       |
| ----------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2009년 5월  | DNSPod(중국 DNS 제공자) | 동영상 서비스 Baofeng을 노린 DDoS로 DNSPod 서버가 중단됐다. 다음 날 캐시가 만료되자 Baofeng 플레이어가 버그로 DNS 질의를 빠르게 반복해 China Telecom 망을 포화시켰고, 20개 성의 인터넷이 마비됐다 |
| 2009년 12월 | UltraDNS                | Amazon, Walmart, Expedia 등 대형 전자상거래 기업의 DNS 제공자를 겨냥한 DDoS로 약 1시간 동안 접속 장애가 생겼다                                                                                    |
| 2016년 10월 | Dyn                     | IP 카메라, 베이비 모니터 같은 IoT 기기로 이루어진 Mirai 봇넷이 여러 차례 DDoS를 일으켜 CNN, BBC, HBO, PayPal 등의 서비스가 중단됐다                                                               |

DNSPod 사례는 클라이언트 소프트웨어의 재시도 정책이 DNS 장애를 망 전체의 장애로 키운다는 점을, Dyn 사례는 DNS 제공자 한 곳에 의존하면 그 제공자가 단일 장애점이 된다는 점을 보여 준다.

### 반사·증폭 공격

DNS는 DoS의 대상이면서 도구로도 쓰인다. 출발지 주소를 피해자로 위조한 작은 질의를 개방형 리졸버나 권한 서버에 보내면, 그 서버가 훨씬 큰 응답을 피해자에게 보낸다. 60바이트 질의로 3,000바이트 응답을 얻으면 증폭률은 다음과 같다.

```math
\frac{3000}{60} = 50
```

DNSSEC 서명이 붙은 응답이나 큰 TXT 레코드가 증폭률을 키운다. 이 밖에 존재하지 않는 무작위 하위 이름을 대량으로 질의해 리졸버의 캐시를 우회하고 권한 서버에 부하를 몰아주는 무작위 하위 도메인 공격(random subdomain attack)도 있다. Kaminsky 공격과 같은 무작위 이름 기법을 DoS에 쓴 형태다.

### DoS 방어

| 방어                     | 내용                                                                                    |
| ------------------------ | --------------------------------------------------------------------------------------- |
| 애니캐스트와 중복 배치   | 같은 주소를 여러 지역에서 광고해 공격 트래픽을 분산한다                                 |
| 복수 DNS 제공자          | 서로 다른 제공자의 네임서버를 NS로 함께 등록해 단일 장애점을 없앤다                     |
| 응답 속도 제한(RRL)      | 권한 서버가 같은 대상에 같은 응답을 보내는 비율을 제한해 반사 공격의 재료가 되지 않는다 |
| 개방형 리졸버 차단       | 재귀 질의를 내부 망에만 허용한다                                                        |
| 출발지 주소 검증(BCP 38) | ISP가 자기 망에서 나가는 패킷 중 출발지가 위조된 것을 버려 반사 공격 자체를 어렵게 한다 |
| 적절한 TTL               | 너무 짧은 TTL은 장애 시 캐시 완충 시간을 없앤다                                         |
| Serve-stale(RFC 8767)    | 권한 서버에 닿지 못하면 만료된 캐시 응답을 임시로 내준다                                |

BIND에서 응답 속도 제한은 다음처럼 켠다.

```bash
options {
    rate-limit {
        responses-per-second 10;
        window 5;
    };
};
```

같은 응답이 같은 대상 주소 블록에 초당 10개를 넘으면 초과분을 버리거나, 일부는 TC 비트를 켠 잘린 응답으로 보내 정상 클라이언트가 TCP로 재질의하게 한다. 위조 출발지의 피해자는 TCP 연결을 맺지 않으므로 증폭이 일어나지 않는다.

## 정리

| 영역      | 핵심                                                                                                |
| --------- | --------------------------------------------------------------------------------------------------- |
| 구조      | 루트, TLD, 2단계 도메인의 트리. 관리 단위는 존이고 존 컷마다 NS로 위임한다                          |
| 질의      | 스텁 리졸버는 재귀 질의, 재귀 리졸버는 루트부터 반복 질의. 결과는 TTL 동안 캐시                     |
| 약점      | UDP 위에서 16비트 ID와 16비트 포트만으로 응답을 인증한다                                            |
| 스푸핑    | 로컬 오염은 질의를 보고 응답, 원격 오염은 ID·포트를 추측, Kaminsky는 무작위 이름으로 캐시 효과 우회 |
| 악성 서버 | 존 밖 레코드는 베일리윅 검사로 버리고, PTR은 접근 제어 근거로 쓰지 않는다                           |
| 방어      | 무작위화와 0x20은 비용을 높이고, DNSSEC은 서명으로 위조를 막고, TLS는 오염된 연결을 끊는다          |
| 리바인딩  | 짧은 TTL로 같은 이름을 내부 주소에 다시 묶는다. Host 헤더 검사와 인증으로 막는다                    |
| DoS       | 루트는 분산과 캐시로 강하고, 약한 TLD와 DNS 제공자가 표적이다. 애니캐스트, 복수 제공자, RRL         |

DNS 공격의 공통점은 응답의 출처를 확인할 수단이 약하다는 데 있다. 무작위화는 공격을 비싸게 만들 뿐이고, 서명(DNSSEC)과 종단 인증(TLS)이 출처 확인 문제를 직접 해결한다. 다음 순서의 [BSD 소켓 API로 만드는 TCP 서버와 클라이언트](/memo/net-socket-programming)에서는 이런 프로토콜을 실제 프로그램으로 다루는 소켓 인터페이스를 다루고, [TCP 프로토콜을 겨냥한 공격과 방어](/memo/net-tcp-attacks)에서는 TCP의 시퀀스 번호를 추측하는 공격이 DNS의 트랜잭션 ID 추측과 어떻게 닮았는지 이어서 본다.
