[코드를 고치지 않고 프로젝트와 앱 관리하기](/memo/site-projects-editing)에서 관리자가 시스템 설정에서 프로젝트를 고치게 했다. 그 편집 화면의 소개 탭에는 **페이지 모양**을 고르는 칸이 있다. 이 글은 그 모양(템플릿)들이 어떻게 바뀌어 왔는지 적는다. 같은 PR([#187](https://github.com/hyeoniverse/MacFolio/pull/187)) 안에서 여러 번 갈아엎었기 때문에, 무엇을 버렸고 왜 버렸는지를 함께 남긴다.

![템플릿 수가 7, 8, 12, 13개로 늘었다가 공통 내용 모델 위에서 4개, 다시 9개가 된 흐름](./images/site-projects-editing-templates-history.svg '템플릿 수의 변화. 마지막 세 단계가 지금 구조다')

## 지금 모습

먼저 결과부터 적는다. `packages/desktop-core/src/site/projects.ts`의 `PROJECT_LOOKS`는 열 가지다.

| 모양       | 이름           | 성격                                                             |
| ---------- | -------------- | ---------------------------------------------------------------- |
| `product`  | 제품           | 큰 화면과 짧고 큰 문장 (Apple 제품 페이지)                       |
| `friendly` | 카드           | 밝은 카드와 아이콘, 단계 흐름 (Stripe). **새 프로젝트의 기본값** |
| `paper`    | 문서           | 따뜻한 흰 문서, 토글과 알림 상자 (Notion)                        |
| `bento`    | 벤토           | 크기가 다른 타일, 가는 선, 고정폭 글자 (Framer·Raycast 템플릿)   |
| `keynote`  | 키노트         | 어두운 무대의 발표 장면                                          |
| `magazine` | 매거진         | 명조와 큰 사진의 케이스 스터디                                   |
| `devtool`  | 개발자 도구    | 복사되는 clone 명령, 커밋 목록, 기여 그래프                      |
| `repo`     | 저장소         | GitHub 저장소 화면 그대로                                        |
| `playful`  | 놀이           | 색 면과 둥근 도형, 스티커                                        |
| `custom`   | 직접 짠 페이지 | 프로젝트 id로 등록한 코드 페이지                                 |

![시스템 설정의 프로젝트 편집 화면에 페이지 모양 카드 열 개(제품부터 직접 짠 페이지까지)가 보인다](./images/site-projects-editing-templates-picker.jpg '편집 화면 소개 탭의 페이지 모양 카드. 코드의 프로젝트는 직접 짠 페이지가 기본이다')

코드에 있는 일곱 프로젝트는 처음부터 그 프로젝트를 위해 짠 페이지가 있다(이 사이트의 제품 페이지, NewPick의 신문 1면, WTD의 칸반, QRU의 명함, SproutFarm의 타이틀 화면과 크레딧, DevCourse의 터미널, 포트폴리오의 장과 몽이). 그것은 바꾸지 않는다. 그래서 `custom` 모양을 두었다. `apps/safari/project/custom/`에 프로젝트 id로 컴포넌트를 등록하면 그 프로젝트가 `custom`을 골랐을 때 그 코드로 그린다. 기존 일곱 프로젝트는 모두 여기에 등록돼 `custom`이 기본값이고, 등록이 없는 프로젝트가 `custom`을 고르면 기본 모양으로 그리며 편집 화면이 그 사실을 알려 준다. 템플릿은 새 프로젝트를 더할 때 고르는 것이다.

## 1단계: 어디에나 맞는 기본 모양

처음 페이지 모양 7가지는 저마다 한 프로젝트에 맞춰 짠 것이었다(신문 1면, 칸반 보드, 게임 크레딧, 터미널 일지…). 새 프로젝트에 그중 하나를 고르면 원래 프로젝트 이야기에 맞춘 빈자리가 어색하게 남았다. 그래서 어떤 내용에나 맞는 **기본(카드)** 모양(`showcase`)을 더하고 새 프로젝트의 기본값으로 삼았다. 큰 제목과 링크, 숫자, 대표 화면, 주요 기능·만든 방식·쓰는 법 카드, 화면 모음, 진행 과정, 기술 사양 순서이고, 없는 묶음은 통째로 빠져서 내용이 적어도 빈자리가 없다. 로고가 있으면 이름 대신 로고를, 프로젝트 아이콘이 있으면 이름 옆에 작게 둔다.

## 2단계: 읽는 방식이 다른 열두 가지

기본 모양을 새로 짜고 나니 나머지 일곱이 옆에서 밋밋해 보였다. 틀만 새로 써 봤지만 결국 "제목 → 섹션 → 섹션" 세로 스크롤에 색만 다른 꼴이었다. 색·타이포가 밋밋하고, 다 비슷한 세로 스크롤이고, 움직임이 없었다. 그래서 **읽는 방식 자체가 다른 모양 열두 가지**를 짰다. 마음에 안 드는 것은 나중에 빼기로 하고 네 갈래를 섞었다.

| 갈래        | 모양         | 읽는 방식                                                                                            |
| ----------- | ------------ | ---------------------------------------------------------------------------------------------------- |
| 스크롤 연출 | `cinema`     | 한 화면씩 고정되는 장면. 스크롤 진행도를 CSS 변수로 넘겨 대표 화면이 솟고, 기능 그림이 밀고 들어온다 |
|             | `phone`      | 가운데 고정된 폰 틀. 왼쪽 이야기가 가운데 선을 지나면 폰 안 화면이 그 단계 그림으로 바뀐다           |
|             | `horizontal` | 세로 스크롤이 가로 트랙을 민다. 패널마다 바탕색이 바뀐다                                             |
| 강한 비주얼 | `brutal`     | 흰·검·형광 세 색, 4px 선, 12열 격자 블록, 흐르는 띠, 마우스를 따라오는 반전 원                       |
|             | `arcade`     | 네온 간판 점등, 주사선·CRT, HIGH SCORE, 캐릭터 선택 카드(3D 기울기), 흐르는 크레딧                   |
| 차분한      | `atelier`    | 아이보리·세리프·큰 여백. 줄 마스크로 글이 올라오고, 그림은 커튼처럼 열린다                           |
| 앱 UI 흉내  | `inbox`      | 메일 클라이언트 3단. 항목이 메일 한 통이고 열면 읽음 처리, 뱃지가 줄고, 검색이 거른다                |
|             | `checklist`  | 할 일 앱. 항목을 체크하면 설명이 펼쳐지고 진행 고리가 찬다                                           |
|             | `repo`       | GitHub 저장소 화면. 파일 트리, 커밋 그래프와 타입 거르기, 아래 터미널 서랍                           |
|             | `dialogue`   | RPG 대화창. 타자 치듯 찍히는 대사와 선택지로 주제를 골라 읽는다                                      |
|             | `deck`       | 발표 슬라이드. ←→·점·소터로 넘긴다                                                                   |
|             | `assistant`  | macOS 설정 도우미. 단계 목록과 '계속'으로 한 화면씩                                                  |

규칙은 같았다. 어떤 프로젝트든 어떤 모양이나 고를 수 있으니 없는 필드는 그 부분이 통째로 빠지고, 한 프로젝트 전용 장식(게임 스프라이트, 몽이, 이 사이트의 화면 크기 시뮬레이터)은 그 프로젝트에서만 그린다. 움직임은 `prefers-reduced-motion`에서 즉시 상태로 떨어지고, E2E는 그 상태로 돈다. 데모 조각(포트폴리오의 번역·요약·파형·테마 데모, 터미널 셸, 화면 크기 시뮬레이터, 요청 경로 그림)은 어느 모양에서든 꽂을 수 있게 색 변수(`--cr-*`, `--pd-*`)만 읽도록 떼어 두었다.

### 칸을 다 채우면 꽉 차게

템플릿은 어떤 프로젝트에나 쓰이니, 편집 화면의 칸을 다 채웠을 때 빈 곳이 없어야 한다. 템플릿 열세 개가 실제로 읽는 필드를 표로 정리해 보니 장, 조작법, 폴더 구조, 출처, 항목의 자세히·여러 장·영상 같은 것이 JSON으로만 들어갔다. 그 칸들을 편집 화면에 더하고, 모양마다 가상의 예시 프로젝트(북클럽, 픽셀팜, 스테이션 같은 것)를 만들어 '예시로 채우기'로 새 프로젝트를 시작하게 했다(`apps/settings/lookSamples.ts`). 그 예시로 템플릿을 하나씩 열어 빈칸(항목 수와 맞지 않는 격자, 그림 없는 항목의 빈 그림 자리, 한쪽만 찬 열)을 메우고, 입력했는데 화면 어디에도 안 나오던 필드(주 언어, 자세히, 쓰는 법, 진행 과정 등)를 그 모양의 화풍으로 넣었다.

예시를 채우며 확인 창을 띄우다 보니 공통 경고창의 여백이 0이었다. 빌드한 CSS에서 `@layer reset, components;` 선언이 빠지고 components 층이 reset 층보다 먼저 나와, 초기화 규칙(`* { padding: 0 }`)이 공통 컴포넌트를 이기고 있었다. 층 순서는 처음 나온 곳에서 정해지므로 `index.html`의 인라인 `<style>` 맨 앞에서 선언해 모든 CSS보다 먼저 정한다.

## 3단계: 랜딩 키트, 그리고 효과 걷어 내기

열두 가지는 여전히 정보 나열처럼 보였다. 브랜드 제품 랜딩 페이지와 견주어 보니 부족한 점은 넷이었다. 첫 화면이 약하고, 구역이 제목과 목록의 반복이고, 시각 디테일이 엉성하고, 그림이 없으면 빈약했다.

그래서 템플릿들이 함께 쓸 랜딩 키트(`project/landing/`)를 만들었다. 기기 틀(브라우저·노트북·휴대폰), 히어로 뒤 빛 번짐, 큰 숫자 띠, 기술 로고 줄, 빈칸 없는 벤토, 마무리 CTA가 들어 있다. 핵심은 **그림이 없을 때 쓰는 가짜 제품 화면**이다. 프로젝트의 이름·아이콘 색·주요 기능·숫자로 대시보드·목록·채팅·편집기·모바일·게임 화면을 그린다. 화면 속 글은 모두 프로젝트 데이터에서 오고, 시험이 그것을 확인한다. 템플릿은 세 갈래 톤으로 나눠 이 키트로 손봤다. Apple 쪽(시네마·폰·아틀리에·설정 도우미), Linear·Vercel 쪽(가로·저장소·발표·아케이드), Stripe·Notion 쪽(기본·메일함·할 일·브루탈)이다.

결과를 띄워 보니 번들번들했다. 빛 번짐, 그라데이션 글자, 기기 반사, 기울기, 유리 효과, 색 그림자가 한꺼번에 들어가 있었다. 진짜 브랜드 페이지는 오히려 절제되어 있어서, 효과를 모두 걷어 내고 단색 바탕·큰 타이포·강조색 하나·얕은 그림자 한 벌만 남겼다. 아케이드의 네온은 간판 한 곳에만 둔다.

그랬더니 이번에는 무겁고 칙칙해졌다. 원인은 셋이었다.

| 원인                                                    | 고친 것                                                                            |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 여러 템플릿이 사이트 테마와 상관없이 어두운 바탕을 강제 | 라이트 테마에서는 흰 바탕, 사이트 테마를 따름(시네마·발표는 어두운 장면 한두 곳만) |
| 강조색 채도를 너무 낮춰 회색빛                          | 아이콘 색의 채도를 되살리되 흰 바탕과의 대비 3 이상이 되게 밝기를 맞춤             |
| 제목이 700~800으로 너무 굵음                            | 큰 제목 600, 본문 #424245와 17px, 구역 여백을 넉넉하게                             |

회색 바탕 위 회색 카드 대신 흰 페이지와 아주 옅은 면의 대비를 쓴다.

### 넣은 그림이 안 보이던 주요 기능

이미 있는 주요 기능에 그림을 넣어도 페이지가 그대로인 경우가 있었다. 편집 화면은 값을 잘 저장했는데, 그리는 쪽이 다른 것을 먼저 골랐다. 그림보다 갈래 도식(variants)을 먼저 그렸고, 다크 테마 그림(`imageDark`)은 옛 그림의 짝이라 그림을 바꿔도 밀대 반쪽에 옛 화면이 남았다. 칸반(WTD)과 터미널(DevCourse) 페이지는 아예 항목의 그림을 그리지 않았다. 그래서 그림을 갈래 도식보다 먼저 그리고, 그림을 바꾸면 다크 그림을 함께 지우고, 두 페이지도 그림을 그리게 했다. 영상은 편집 화면에 보이는 칸이라 그대로 그림보다 먼저 보이되, 영상이 있는 항목의 그림 칸에 그 사실을 알린다.

## 4단계: 내용은 하나로, 템플릿은 넷으로

템플릿이 열세 개로 늘어나면서 문제가 둘 쌓였다. 하나는 템플릿마다 읽는 칸이 달랐다는 점이다. 어떤 모양은 폴더 구조를 그리고 어떤 모양은 그리지 않았고, 커밋 규칙이나 조작법처럼 한 모양만 쓰는 칸도 있었다. 칸을 채워도 모양을 바꾸면 그 내용이 사라졌다. 다른 하나는 디자인이었다. 열세 개를 고루 다듬을 수 없어서 어느 것도 완성도가 높지 않았다.

그래서 먼저 **공통 내용 모델**을 만들었다. `landingOf(project)`는 어떤 프로젝트든 첫 화면, 차례가 정해진 구역들, 마무리로 바꾸는 순수 함수다. 값이 없는 구역은 아예 생기지 않는다. 항목의 그림은 영상, 그림, 화면 여러 장 차례로 한 목록에 모으고, 대표 화면이 비면 화면 모음의 첫 그림을 쓴다. 단위 시험은 편집 화면이 고치는 칸이 하나도 버려지지 않는지까지 확인한다.

![Project를 landingOf가 첫 화면, 14개 구역, 마무리로 바꾸고, 아홉 템플릿이 그것만 읽는다](./images/site-projects-editing-templates-landing.svg '공통 내용 모델. 구역 차례는 포트폴리오를 읽는 순서다')

템플릿은 이 내용만 읽는다. 구역마다 그리는 함수를 모은 묶음은 구역 종류를 하나도 빠뜨릴 수 없게 타입으로 막았다. 그래서 어떤 템플릿을 골라도 채운 칸이 모두 보이고, 조작법과 폴더 구조와 출처도 모든 템플릿이 그린다. 조작법 칸은 이때 모양 전용 칸에서 내용 탭의 공통 칸이 되었다.

그다음 템플릿을 **넷으로 줄였다**. 제품(Apple), 카드(Stripe), 문서(Notion), 벤토(Framer·Raycast)로 레퍼런스를 하나씩 정했다. 템플릿마다 폴더 하나로 나눠 서로를 가져오지 않게 했고, 지켜야 할 계약(모든 구역, 빈 구역 없음, 구역 이름, 라이트·다크, 좁은 창, 움직임 줄이기, 효과 절제)은 `templates/README.md`에 적었다.

새 프로젝트의 기본 모양은 카드로 정했다. 제품 모양은 큰 화면이 있어야 살아나는데, 막 더한 프로젝트에는 그림이 없는 경우가 많다. 카드 모양은 그림이 없어도 아이콘 카드로 꽉 차 보인다.

네 템플릿은 같은 기준으로 다듬었다. 예시를 다 채운 프로젝트, 그림을 모두 뺀 프로젝트, 이름과 소개와 기능 두 개만 있는 프로젝트를 라이트·다크와 좁은 창에서 모두 찍어 보고, 어느 경우에도 빈자리가 보이지 않게 했다. 그림이 없을 때 제품은 큰 아이콘 타일로, 카드는 프로젝트 내용으로 그린 앱 화면 모형으로, 문서는 태그 색을 깐 표지로, 벤토는 아이콘 타일과 명령 팔레트로 그 자리를 채운다. 예시 그림도 배경화면 대신 실제 앱 화면 캡처로 바꿨다. 배경화면을 넣으면 제품 페이지가 아니라 사진첩처럼 보였기 때문이다. 마무리 문장은 첫 화면 제목을 되풀이하지 않도록, 써 볼 곳이 있는지에 따라 권하는 문장을 따로 둔다. 예시 프로젝트도 열세 개에서 하나(북클럽)로 줄여 모든 템플릿이 함께 쓴다.

### 예전 이름은 표로 옮긴다

예전 모양 이름으로 서버에 저장해 둔 프로젝트도 그대로 보여야 했다. 그래서 검사 규칙(`parseProjects`)에 옛 이름을 지금 이름으로 바꾸는 표(`LEGACY_LOOKS`)를 두었다. 서버와 화면이 같은 규칙을 쓰므로 저장할 때도 읽을 때도 옛 이름이 지금 이름으로 바뀐다. 아래는 마지막에 정한 표다.

| cinema, deck                  | 키노트 |
| phone                         | 제품   |

## 5단계: 다시 아홉으로

네 템플릿은 정돈되어 보였지만 고를 것이 적었고, 카드와 RPG 대화창은 아직 약했다. 그래서 키노트(어두운 무대의 발표 장면), 매거진(명조와 큰 사진의 케이스 스터디), 개발자 도구(복사되는 clone 명령, 커밋 목록, 기여 그래프), 놀이(색 면과 둥근 도형, 스티커)를 더했다. 같은 내용 모델 위에 있으니 새 템플릿은 폴더 하나와 E2E 한 파일이면 된다. 예전 이름도 더 가까운 새 템플릿으로 다시 맞췄다(위 표).

- **카드**는 Stripe 실제 페이지와 견주어 약한 곳(탁한 겨자색, 싸 보이는 베이지 띠, 창 하나뿐인 첫 화면)을 짚고, 비스듬한 띠와 줄무늬, 창 위에 겹친 숫자·기능 카드로 다시 그렸다.
- **매거진**은 명조 웹 글꼴을 쓰고 싶었지만 사이트의 CSP가 바깥 글꼴을 막는다. 그래서 기기에 있는 명조(맥에서는 애플명조)를 쓴다.

### 저장소 모양을 되살리다

저장소 모양은 개발자 도구로 옮겼다가 다시 살렸다. GitHub 저장소를 흉내 낸 그 모양은 다른 것과 겹치지 않는 장점이 있었다. 다만 예전 코드는 프로젝트 칸을 직접 읽고 탭마다 다른 내용을 보여 줬으므로 공통 내용 모델 위에서 다시 짰고, 예전 이름 표에서 repo를 빼서 저장소 모양으로 저장해 둔 프로젝트는 다시 이 모양으로 보인다.

- 페이지는 처음부터 저장소 화면으로 열린다. 처음에는 위에 랜딩식 첫 화면(가운데 배지, 큰 제목, clone 명령, 창 속 화면)이 있었는데 개발자 도구 템플릿과 너무 닮아 걷어 냈다. 큰 제목은 README의 h1이 되고, 링크 버튼은 About 칸으로, clone 주소는 가지 줄의 초록 Code 버튼 안으로 들어갔다.
- 처음에는 README 하나에 모든 구역이 길게 이어져, 긴 랜딩 페이지를 상자에 넣은 것처럼 보였다. 그래서 GitHub가 README 상자 위에 README, Contributing, License 탭을 두는 것처럼 구역을 문서로 나눴다. README.md에는 큰 제목과 소개, 대표 화면, 숫자, 목차가 남고, 나머지 구역은 docs/FEATURES.md, docs/USAGE.md, docs/CHANGELOG.md처럼 제 문서가 된다. 문서 탭이나 파일 트리의 docs/ 폴더에서 파일을 누르면 그 문서가 열리고, 경로 줄에 blob/main/docs/FEATURES.md가 보인다.
- 진행 과정은 v0.1.0부터 v1.0.0까지의 릴리스 목록, 기술 사양은 Built with 주제와 표와 폴더 구조 코드 블록, 맡은 일은 할 일 목록이 된다. 파일 상자는 폴더 구조로 만든 트리라 폴더를 눌러 펼치고, DevCourse는 예전처럼 실제 저장소를 탐색한다.
- Commits 탭은 진행 과정을 커밋 그래프로 그리고 타입으로 거르며, 커밋 규칙이 있으면 Conventions 탭이 생긴다. 터미널 서랍의 셸도 폴더 구조를 `ls`와 `cd`로 돌아보고, `ls docs`와 `cat docs/USAGE.md`가 된다.
- 저장소 탭은 Safari 창의 탭과 섞이지 않게 탭 역할 대신 내비게이션과 현재 표시 버튼으로 두었다.
- 공통 시험은 모든 구역이 한꺼번에 보이기를 기대하므로, 저장소 모양의 시험만 문서 탭을 차례로 열며 구역의 차례와 내용을 확인한다.

옆 칸의 **Languages**도 손봤다. 처음에는 프로젝트에 적어 둔 주 언어 하나를 100%로 그렸다. GitHub 링크가 있으니 실제 언어 비율을 보여 주는 편이 맞다. 다만 브라우저가 GitHub API를 직접 부르면 방문자마다 요청 제한을 나눠 쓰게 되므로, 사이트의 API에 `GET /github/languages/{owner}/{이름}`을 두고 서버가 대신 묻는다.

- 누구나 부를 수 있는 경로가 아무 저장소나 대신 묻는 통로가 되면 안 된다. 그래서 코드의 프로젝트가 가리키는 저장소와 관리자가 저장한 프로젝트 주소의 저장소만 받고, 그 밖은 GitHub에 묻지 않고 404로 답한다.
- 코드의 프로젝트 목록은 화면 코드에 있어 서버가 읽을 수 없으므로, 공용 패키지(`desktop-core/src/site/github.ts`)에 저장소 이름만 따로 두고 화면의 시험이 두 목록이 같은지 확인한다.
- 받은 비율은 저장소마다 6시간(없는 저장소라는 답은 30분) 들고 있고, GitHub에 닿지 못하면 마지막 값을 준다.
- 비율은 소수 첫째 자리까지 반올림하되 합이 꼭 100이 되게 맞추고, 0.5%보다 작거나 일곱째부터인 언어는 Other로 묶는다. 화면은 GitHub처럼 언어마다 한 토막인 막대와 색 점 목록을 그리고, 받는 동안이나 받지 못하면 예전처럼 주 언어 하나로 그린다.

## 6단계: 포트폴리오가 늘 묻는 것들을 칸으로

프로젝트를 소개하는 글에는 거의 정해진 항목이 있다. 기능, 기술 스택, 트러블슈팅, 구현 방법, 팀원, 배포 결과물, 내 역할, 진행 과정이다. 지금까지의 칸은 기능, 기술, 구현, 역할, 진행 과정까지는 갖췄지만 트러블슈팅, 팀원, 배포 결과물은 적을 곳이 없어서 장(chapters)에 억지로 넣거나 빼야 했다. 세 가지를 프로젝트 데이터의 필드로 더했다.

| 필드        | 칸                                         |
| ----------- | ------------------------------------------ |
| 트러블슈팅  | 제목, 문제, 원인, 해결, 결과, 그림, 아이콘 |
| 팀원        | 이름, 역할, GitHub 주소, 사진, 나 표시     |
| 배포 결과물 | 이름, 주소, 플랫폼, 설명, 그림             |

서버와 화면이 같은 검사(`parseProjects`)를 쓰므로 주소는 https만 받고, 개수와 글자 수에도 이웃 칸과 같은 한도를 둔다.

공통 내용 모델에는 구역 세 개를 더하고, 차례를 포트폴리오를 읽는 순서로 다시 정했다. 무엇인지(숫자, 주요 기능, 화면 모음, 쓰는 법), 어떻게 만들었는지(구현 방법, 트러블슈팅, 더 들려줄 이야기, 조작법, 기술 사양), 누가 만들었는지(팀원, 내 역할), 언제 만들었는지(진행 과정), 어디서 볼 수 있는지(배포 결과물)를 지나 출처로 끝난다. 구역 이름도 만든 방식은 구현 방법으로, 맡은 일은 내 역할로 바꿨다.

목표는 이미지가 하나도 없어도 비어 보이지 않는 것이었다. 트러블슈팅은 아이콘과 번호 아래에 문제, 원인, 해결, 결과를 한 줄로 잇는 단계 띠를 그리고 해결부터는 강조색으로 칠한다. 팀원은 사진이 없으면 이름 첫 글자를 담은 동그라미를 그리고, 나는 강조색 테두리와 작은 표시로 구분한다. 배포 결과물은 올린 곳(Vercel, App Store, npm, Docker 등)에 맞는 아이콘과 공개 상태, 호스트 이름을 보여 주는 링크 카드다. 짜임은 랜딩 키트의 공통 조각 하나로 두고, 템플릿은 변수와 접두사 클래스로 자기 색과 모양을 입힌다. 저장소 모양만은 GitHub답게 그렸다. 트러블슈팅은 docs/TROUBLESHOOTING.md에서 GitHub의 알림 상자(WARNING, NOTE, TIP, IMPORTANT)로, 팀원은 docs/TEAM.md의 사진 달린 표와 옆 칸의 Contributors로, 배포 결과물은 docs/DEPLOYMENT.md와 옆 칸의 Deployments로 보인다. 편집 화면의 내용 탭에는 세 목록을 다른 목록처럼 시트로 고치게 더했고, 북클럽 예시도 트러블슈팅 세 건(그림이 있는 것과 없는 것), 팀원 네 명, 배포 결과물 세 곳으로 채웠다.

## 7단계: 서로 비슷한 템플릿 좁게 손보기

아홉을 나란히 놓고 보니 서로 너무 비슷했다. 처음에는 읽는 방식 자체(사이드바, 슬라이드 덱, 대시보드, 스크랩북)를 바꿔 봤는데, 2단계처럼 오히려 산만해져서 전부 되돌렸다. 그다음엔 좁게 손봤다. 디자인의 인상과 스크롤로 읽는 방식은 그대로 두고, 겹치던 세 가지만 바꿨다.

1. 첫 화면 구도: 가운데 제목, 왼쪽 제목과 오른쪽 창, 화면 가득한 그림 위 제목, 처음부터 타일 격자, 왼쪽 정렬 큰 제호, 터미널 창, 가운데 포스터.
2. 구역 머리의 모양과 제목 말투: 공용 문장 대신 템플릿마다 자기 문장.
3. 템플릿마다 대표 구역 한두 개.

저장소와 문서는 원래 구조가 달라서 두었다.

## 빠진 템플릿: RPG 대화창의 기록

RPG 대화창(`dialogue`)은 이 PR에서 뺐다. 마을과 대화, 그림판까지 손이 많이 가는 모양이라 템플릿 작업과 따로 다듬기로 하고, 작업은 `feat/rpg-dialogue` 브랜치에 남겨 두었다. 예전에 dialogue로 저장해 둔 프로젝트는 예전 이름 표가 카드로 바꿔 읽는다. 다시 꺼낼 때를 위해 거쳐 온 길을 적어 둔다.

| 차례 | 바꾼 것                                                                                                            | 까닭                                                                                        |
| ---- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 1    | 고전 RPG 상자로: 라이트는 포켓몬처럼 흰 상자와 두 열 선택지, 다크는 언더테일처럼 검은 상자와 빨간 하트 커서        | 처음의 아늑한 픽셀 농장 풍이 다른 템플릿보다 약해 보였다                                    |
| 2    | 풍경을 걷어 내고 새까만 무대에 흰 테두리(6px) 대화 상자 하나. 갈무리11은 11px·22px만                               | CSS 나무·구름, 땅 타일, 14가지 배경 테마, 픽셀로 뭉갠 대표 화면이 서로 다른 화풍으로 겹쳤다 |
| 3    | 주제마다 고전 RPG 화면을 데이터로 그림(퀘스트 목록, 스킬 트리, 버그 몬스터 전투, 파티 카드, 월드 맵, 보물 상자 등) | 그림이 없으면 무대에 아이콘 하나만 있어 심심했다                                            |
| 4    | 480×270 게임 화면 하나로 묶고 정수 배로 키움(ResizeObserver + CSS zoom)                                            | 11px 옆 22px 글자, 웹 크기 버튼처럼 크기가 제각각이었다                                     |
| 5    | 포켓몬 GBA 전투 화면처럼 주제마다 색 띠와 타원 발판, 한 칸 외곽선, 크림색 상자                                     | 새까만 바탕에 흰 그림과 노랑만 있어 밤새 켜 둔 터미널 같았다                                |
| 6    | 16×16 타일 장면 열 가지와 12×12 픽셀 아이콘, 기술 로고                                                             | 색 띠만으로는 예쁘지 않았고 Font Awesome 아이콘이 화풍과 맞지 않았다                        |
| 7    | 해상도를 360×208로, 길잡이 줄·두 줄 대화 상자·NEXT 표가 있는 여정 메뉴                                             | 1440 화면에서 글자가 22px로 작았고, 선택지 14개를 세 열로 깔아 다음이 보이지 않았다         |
| 8    | 페이지 전체를 게임 화면으로, 78% 불투명 남색 창(Celeste·Sea of Stars 풍)                                           | 하늘색 여백과 틀 때문에 게임 화면이 상자 속 그림처럼 보였다                                 |
| 9    | 걸어 다니는 40×24칸 마을. 장소마다 주제를 둔다                                                                     | 메뉴에서 줄을 하나씩 누르는 것과 다를 바 없었다                                             |
| 10   | Ninja Adventure Asset Pack(CC0) 타일과 사람으로 바꿈                                                               | 코드로 한 칸씩 찍은 건물과 배경이 투박했고 간격이 들쭉날쭉했다                              |
| 11   | 풀숲을 다시 그리고, 그림을 게임 화면 밖으로 꺼내고, 주제 장면을 지움                                               | 덤불 바둑판이 초록 벽돌처럼 보였고, 게임 화면 안의 사진이 두세 배로 커져 흐렸다             |

몇 가지는 다른 곳에도 쓸 만해서 자세히 남긴다.

- **정수 배율**: 고전 게임이 보기 좋은 것은 화면 전체를 낮은 해상도 하나로 그린 뒤 정수 배로 키워, 글자와 테두리와 그림이 한 픽셀 격자를 나눠 쓰기 때문이다. 처음 480×270에서는 1440 창이 두 배, 780 창이 한 배였다. Safari 전체 화면의 실제 페이지 칸은 1440과 1100 창 모두 높이가 641px이라 384×216은 세 배가 들어가지 않아, 세 배(1080×624)가 두 폭 모두에 들어가는 360×208을 골랐다. 그 뒤 페이지 전체를 쓰게 바꾸면서는 게임 칸이 세로 200칸(가로 340칸) 이상 남는 가장 큰 정수 배율을 고르고, 1440×641 페이지는 세 배에 480×214칸이 된다.
- **대비**: 크림 바탕 위 흐린 글을 #7a7a70에서 #5a5a52로 짙게 해 6.5:1, 이름표 5.8:1, 커서 줄 4.9:1로 모든 글이 4.5:1을 넘게 했다. 남색 창 시기에는 장면의 가장 밝은 흰 칸 위에서도 흰 글 9.6:1, 흐린 글(#b8c0d8) 5.3:1, 금색(#ffd166) 6.7:1이었다.
- **두 줄 대화 상자**: 갈무리11의 글자 폭(한글 11, 빈칸 4.6)을 넉넉하게 잡아 줄을 미리 나눈 뒤 두 줄씩 넘긴다. 어림이 실제보다 좁지 않으면 브라우저는 같은 자리나 더 뒤에서 줄을 바꾸므로 세 줄로 넘치지 않는다.
- **픽셀 그림 만들기**: 프로젝트 아이콘과 팀원 사진은 네 배 크기로 줄여 그린 뒤 색을 16개로 줄이고 4×4칸마다 가장 많은 색 하나를 골라(섞인 색을 만들지 않는다) 24×24 픽셀 그림으로 바꾼다. 장면은 칸마다 색 대신 팔레트 글자를 두어 다크는 밤 팔레트로 바꿔 칠하고, 해시로만 흩뿌려 늘 같은 모습이다.
- **마을**: 방향 키나 WASD로 한 칸(16px)을 180ms 동안 걷고, `requestAnimationFrame`은 걷는 동안에만 돈다. 화면을 누르면 너비 우선 탐색으로 길을 찾는다. 데이터에 없는 주제의 자리는 빈집이나 꽃밭으로 남겨 어느 프로젝트에서나 지도의 짜임새가 같다. 모든 주제를 읽으면 북쪽 문이 열려 엔딩이 나온다. 걷기 싫은 사람과 화면 읽기 프로그램을 쓰는 사람을 위해 X나 바로 가기 버튼이 주제 메뉴를 그대로 열고, 지도는 읽기 프로그램에서 숨기며 알림 줄이 앞에 무엇이 있는지 문장으로 알린다.
- **에셋**: Ninja Adventure Asset Pack은 CC0라 출처를 밝히지 않아도 되지만, 받은 주소와 사용 허락 전문을 `public/imgs/rpg/ninja/LICENSE.txt`에 남겼다. 쓰는 타일 묶음 아홉 장과 사람 열두 명, 몬스터 여섯 마리, 상자, 그림자, 말풍선만 옮겨 모두 360KB쯤이다. 흙길·물·돌바닥은 이웃 여덟 칸의 모양으로 47가지 모서리 조각 중 하나를 고르는 자동 타일로 깐다.
- **그림은 게임 화면 밖에**: 게임 화면은 정수 배로 키운 픽셀 판이라 그 안의 사진도 두세 배로 커져 흐려졌다. 무대에는 그림 자리만 두고 그 자리의 실제 픽셀 사각형을 재서 바깥 판에 그림을 띄운다. 원래 크기의 1.5배를 넘기지 않아, 1440 전체 화면에서 1440×900 그림은 499×312, 1124×1422 그림은 246×312로 선다.
- **키 받기**: Safari에서 탭을 누르면 포커스가 탭 버튼에 남는데, 키를 페이지 안이나 문서 바탕에서 눌렀을 때만 받고 있어서 X가 듣지 않았다. 지금은 이 페이지가 든 Safari 창 안이면 어디서 눌러도 Z, X, 방향 키, Esc를 받되, 글 상자와 다른 앱 창의 키는 그대로 두고, 탭이나 도구 막대 버튼에서 누른 Enter·Space는 그 버튼이 처리한다.

데이터에서는 이때 `backdrop` 필드와 열네 테마 목록을 지웠다. 예전에 저장해 둔 값에 backdrop이 있어도 검사 규칙이 모르는 필드를 버리므로 오류 없이 읽힌다. 장면 그림(`art`)은 SproutFarm의 직접 짠 페이지가 쓰므로 데이터에 남기고 편집 화면에서만 뺐다.

## 확인

- 단위(랜딩 내용): 빈 구역은 빠지고, 구역 차례가 정해져 있고, 첫 화면 그림은 대표 화면이나 화면 모음의 첫 그림이고, 편집 화면이 고치는 칸을 하나도 버리지 않는다. 예전 모양 이름은 지금 모양으로 바뀐다.
- 단위(`lookSamples.test.ts`): 직접 짠 페이지를 뺀 모양마다 예시가 하나씩 있고 모든 모양이 같은 예시를 모양만 바꿔 쓴다, '예시로 채우기'는 id·저장소·데모·앱을 그대로 둔다.
- E2E: 템플릿마다 한 파일(`e2e/looks/`)로 예시의 모든 구역이 차례대로 보이고, 빈 프로젝트도 빈 구역 없이 그려지고, 링크가 열리고, 사이트 테마를 따르는지 본다. 저장소 모양은 문서 탭을 차례로 연다.
- 화면: 예시를 다 채운 것, 그림을 모두 뺀 것, 이름·소개·기능 두 개만 있는 것을 라이트·다크와 좁은 창에서 찍어 빈자리를 찾았다.

## 남은 것과 배운 것

- 템플릿 수를 늘리기 전에 **내용 모델**부터 정했어야 했다. 열세 개가 저마다 프로젝트 칸을 직접 읽을 때는 칸이 사라지는 문제와 다듬기 부담이 함께 커졌다. `landingOf` 하나를 두고 구역 묶음을 타입으로 막은 뒤에는 새 템플릿이 폴더 하나와 E2E 한 파일로 끝났다.
- 효과를 더하는 것보다 걷어 내는 쪽이 대개 나았다. 빛 번짐·그라데이션·유리 효과를 다 넣은 결과보다 단색 바탕과 강조색 하나가 더 단정했다.
- 이름을 바꿀 때는 옛 이름을 지우지 말고 바꾸는 표(`LEGACY_LOOKS`)를 검사 규칙에 두면, 서버에 남은 값도 고칠 필요가 없다.
- RPG 대화창은 브랜치에 있다. 다시 꺼내려면 지금의 공통 내용 모델과 아홉 템플릿 위에서 맞춰야 한다.
