[코드를 고치지 않고 프로젝트와 앱 관리하기](/memo/site-projects-editing)에서 관리자가 시스템 설정에서 프로젝트를 수정하도록 했다. 그 편집 화면의 소개 탭에는 **페이지 모양**을 고르는 칸이 있다. 이 글은 그 모양(템플릿)의 변경 과정을 정리한다. 같은 PR([#187](https://github.com/hyeoniverse/MacFolio/pull/187)) 안에서 구조를 여러 번 다시 설계했기 때문에, 무엇을 폐기했고 왜 폐기했는지를 함께 기록한다.

![템플릿 수가 7, 8, 12, 13개로 늘었다가 공통 내용 모델 위에서 4개, 다시 9개가 된 흐름](./images/site-projects-editing-templates-history.svg '템플릿 수의 변화. 마지막 세 단계가 지금 구조다')

## 지금 모습

결과부터 정리한다. `packages/desktop-core/src/site/projects.ts`의 `PROJECT_LOOKS`는 열 가지다.

| 모양       | 이름           | 성격                                                             |
| ---------- | -------------- | ---------------------------------------------------------------- |
| `product`  | 제품           | 큰 화면과 짧고 큰 문장 (Apple 제품 페이지)                       |
| `friendly` | 카드           | 밝은 카드와 아이콘, 단계 흐름 (Stripe). **새 프로젝트의 기본값** |
| `paper`    | 문서           | 따뜻한 흰 문서, 토글과 알림 상자 (Notion)                        |
| `bento`    | 벤토           | 크기가 다른 타일, 가는 선, 고정폭 글자 (Framer·Raycast 템플릿)   |
| `keynote`  | 키노트         | 어두운 무대의 발표 장면                                          |
| `magazine` | 매거진         | 명조와 큰 사진의 케이스 스터디                                   |
| `devtool`  | 개발자 도구    | 복사되는 clone 명령, 커밋 목록, 기여 그래프                      |
| `repo`     | 저장소         | GitHub 저장소 화면 그대로                                        |
| `playful`  | 놀이           | 색 면과 둥근 도형, 스티커                                        |
| `custom`   | 직접 짠 페이지 | 프로젝트 id로 등록한 코드 페이지                                 |

![시스템 설정의 프로젝트 편집 화면에 페이지 모양 카드 열 개(제품부터 직접 짠 페이지까지)가 보인다](./images/site-projects-editing-templates-picker.jpg '편집 화면 소개 탭의 페이지 모양 카드. 코드의 프로젝트는 직접 짠 페이지가 기본이다')

코드에 있는 일곱 프로젝트는 처음부터 그 프로젝트 전용으로 작성한 페이지가 있다(이 사이트의 제품 페이지, NewPick의 신문 1면, WTD의 칸반, QRU의 명함, SproutFarm의 타이틀 화면과 크레딧, DevCourse의 터미널, 포트폴리오의 장과 몽이). 이 페이지는 유지한다. 그래서 `custom` 모양을 추가했다. `apps/safari/project/custom/`에 프로젝트 id로 컴포넌트를 등록하면, 그 프로젝트가 `custom`을 골랐을 때 그 코드로 렌더링한다. 기존 일곱 프로젝트는 모두 여기에 등록되어 `custom`이 기본값이다. 등록이 없는 프로젝트가 `custom`을 고르면 기본 모양으로 렌더링하고 편집 화면에 그 사실을 표시한다. 템플릿은 새 프로젝트를 추가할 때 고르는 선택지다.

## 1단계: 어디에나 맞는 기본 모양

처음 페이지 모양 7가지는 각각 한 프로젝트에 맞춰 작성한 것이었다(신문 1면, 칸반 보드, 게임 크레딧, 터미널 일지 등). 새 프로젝트에 그중 하나를 고르면, 원래 프로젝트의 내용에 맞춘 자리가 비어 남았다. 그래서 어떤 내용에나 맞는 **기본(카드)** 모양(`showcase`)을 추가하고 새 프로젝트의 기본값으로 정했다.

- 구역 순서: 큰 제목과 링크 → 숫자 → 대표 화면 → 주요 기능·만든 방식·쓰는 법 카드 → 화면 모음 → 진행 과정 → 기술 사양
- 값이 없는 구역은 통째로 렌더링하지 않아, 내용이 적어도 빈자리가 생기지 않는다
- 로고가 있으면 이름 대신 로고를, 프로젝트 아이콘이 있으면 이름 옆에 작게 표시한다

## 2단계: 읽는 방식이 다른 열두 가지

기본 모양을 추가한 뒤 나머지 일곱 모양을 나란히 비교하니, 모두 "제목 → 섹션 → 섹션" 세로 스크롤 구조에 색만 다른 형태였다. 색과 타이포그래피의 대비가 약하고, 스크롤 구조가 같고, 애니메이션이 없었다. 그래서 **읽는 방식 자체가 다른 모양 열두 가지**를 작성했다. 채택하지 않을 모양은 나중에 제거하기로 하고 네 갈래로 나눴다.

| 갈래        | 모양         | 읽는 방식                                                                                            |
| ----------- | ------------ | ---------------------------------------------------------------------------------------------------- |
| 스크롤 연출 | `cinema`     | 한 화면씩 고정되는 장면. 스크롤 진행도를 CSS 변수로 넘겨 대표 화면이 솟고, 기능 그림이 밀고 들어온다 |
|             | `phone`      | 가운데 고정된 폰 틀. 왼쪽 이야기가 가운데 선을 지나면 폰 안 화면이 그 단계 그림으로 바뀐다           |
|             | `horizontal` | 세로 스크롤이 가로 트랙을 민다. 패널마다 바탕색이 바뀐다                                             |
| 강한 비주얼 | `brutal`     | 흰·검·형광 세 색, 4px 선, 12열 격자 블록, 흐르는 띠, 마우스를 따라오는 반전 원                       |
|             | `arcade`     | 네온 간판 점등, 주사선·CRT, HIGH SCORE, 캐릭터 선택 카드(3D 기울기), 흐르는 크레딧                   |
| 차분한      | `atelier`    | 아이보리·세리프·큰 여백. 줄 마스크로 글이 올라오고, 그림은 커튼처럼 열린다                           |
| 앱 UI 흉내  | `inbox`      | 메일 클라이언트 3단. 항목이 메일 한 통이고 열면 읽음 처리, 배지 수가 줄고, 검색으로 필터링한다       |
|             | `checklist`  | 할 일 앱. 항목을 체크하면 설명이 펼쳐지고 진행 고리가 찬다                                           |
|             | `repo`       | GitHub 저장소 화면. 파일 트리, 커밋 그래프와 타입 필터, 아래 터미널 서랍                             |
|             | `dialogue`   | RPG 대화창. 타자 치듯 찍히는 대사와 선택지로 주제를 골라 읽는다                                      |
|             | `deck`       | 발표 슬라이드. ←→·점·소터로 넘긴다                                                                   |
|             | `assistant`  | macOS 설정 도우미. 단계 목록과 '계속'으로 한 화면씩                                                  |

열두 가지 모두 같은 규칙을 따른다.

- 어떤 프로젝트든 어떤 모양이나 고를 수 있으므로, 값이 없는 필드의 구역은 통째로 렌더링하지 않는다.
- 한 프로젝트 전용 장식(게임 스프라이트, 몽이, 이 사이트의 화면 크기 시뮬레이터)은 그 프로젝트에서만 렌더링한다.
- 애니메이션은 [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)이 켜져 있으면 최종 상태로 바로 표시하고, E2E 시험은 이 설정으로 실행한다.
- 데모 컴포넌트(포트폴리오의 번역·요약·파형·테마 데모, 터미널 셸, 화면 크기 시뮬레이터, 요청 경로 그림)는 어느 모양에서든 배치할 수 있게 색 변수(`--cr-*`, `--pd-*`)만 읽도록 분리했다.

### 칸을 다 채우면 꽉 차게

템플릿은 어떤 프로젝트에나 쓰이므로, 편집 화면의 칸을 모두 채웠을 때 빈 곳이 없어야 한다. 템플릿 열세 개가 실제로 읽는 필드를 표로 정리하니 장, 조작법, 폴더 구조, 출처, 항목의 자세히·여러 장·영상 같은 필드는 JSON으로만 입력할 수 있었다. 그 칸들을 편집 화면에 추가하고, 모양마다 가상의 예시 프로젝트(북클럽, 픽셀팜, 스테이션 같은 것)를 만들어 '예시로 채우기'로 새 프로젝트를 시작하게 했다(`apps/settings/lookSamples.ts`). 그 예시로 템플릿을 하나씩 열어 빈칸(항목 수와 맞지 않는 격자, 그림 없는 항목의 빈 그림 자리, 한쪽만 찬 열)을 채우고, 입력해도 화면에 표시되지 않던 필드(주 언어, 자세히, 쓰는 법, 진행 과정 등)를 그 모양의 스타일로 추가했다.

예시를 채우는 과정에서 확인 창을 열었는데, 공통 경고창의 여백이 0이었다. 빌드한 CSS에서 `@layer reset, components;` 선언이 빠지고 components 레이어가 reset 레이어보다 먼저 나와, 초기화 규칙(`* { padding: 0 }`)이 공통 컴포넌트의 스타일보다 우선했다. [캐스케이드 레이어](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer)의 순서는 처음 등장한 위치에서 정해진다. 그래서 `index.html`의 인라인 `<style>` 맨 앞에서 선언해 모든 CSS보다 먼저 순서를 정한다.

| 상태         | 레이어 등장 순서   | 결과                                        |
| ------------ | ------------------ | ------------------------------------------- |
| 수정 전 빌드 | components → reset | 나중에 선언된 reset이 우선해 여백이 0       |
| 수정 후      | reset → components | 나중에 선언된 components가 우선해 여백 유지 |

## 3단계: 랜딩 키트, 그리고 효과 정리

열두 가지는 여전히 정보를 나열한 페이지처럼 보였다. 브랜드 제품 랜딩 페이지와 비교해 부족한 점 네 가지를 정리했다.

1. 첫 화면에 대표 이미지나 큰 문장처럼 시선을 끄는 요소가 없다.
2. 모든 구역이 제목과 목록의 반복이다.
3. 간격, 그림자, 테두리 같은 세부 스타일이 정돈되지 않았다.
4. 그림이 없는 프로젝트는 빈 공간이 많다.

그래서 템플릿들이 함께 쓸 랜딩 키트(`project/landing/`)를 만들었다. 기기 틀(브라우저·노트북·휴대폰), 히어로 뒤 빛 번짐, 큰 숫자 띠, 기술 로고 줄, 빈칸 없는 벤토, 마무리 CTA가 들어 있다. 핵심은 **그림이 없을 때 쓰는 가상 제품 화면(목업)**이다. 프로젝트의 이름·아이콘 색·주요 기능·숫자로 대시보드·목록·채팅·편집기·모바일·게임 화면을 렌더링한다. 화면 속 글은 모두 프로젝트 데이터에서 가져오고, 시험이 이를 확인한다. 템플릿은 세 갈래 톤으로 나눠 이 키트로 수정했다. Apple 쪽(시네마·폰·아틀리에·설정 도우미), Linear·Vercel 쪽(가로·저장소·발표·아케이드), Stripe·Notion 쪽(기본·메일함·할 일·브루탈)이다.

결과 화면에는 빛 번짐, 그라데이션 글자, 기기 반사, 기울기, 유리 효과, 색 그림자가 한 페이지에 모두 적용되어 있었다. 실제 브랜드 페이지는 효과를 절제해 사용하므로, 효과를 모두 제거하고 단색 바탕·큰 타이포그래피·강조색 하나·얕은 그림자 한 종류만 남겼다. 아케이드의 네온은 간판 한 곳에만 적용한다.

효과를 제거하자 이번에는 화면이 어둡고 채도가 낮아졌다. 원인은 세 가지였다.

| 원인                                                    | 수정한 것                                                                          |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 여러 템플릿이 사이트 테마와 상관없이 어두운 바탕을 강제 | 라이트 테마에서는 흰 바탕, 사이트 테마를 따름(시네마·발표는 어두운 장면 한두 곳만) |
| 강조색 채도를 너무 낮춰 회색빛                          | 아이콘 색의 채도를 되살리되 흰 바탕과의 대비 3 이상이 되게 밝기를 맞춤             |
| 제목이 700~800으로 너무 굵음                            | 큰 제목 600, 본문 #424245와 17px, 구역 여백을 넉넉하게                             |

회색 바탕 위 회색 카드 대신 흰 페이지와 아주 옅은 면의 대비를 사용한다.

### 추가한 그림이 표시되지 않던 주요 기능

이미 있는 주요 기능에 그림을 추가해도 페이지가 바뀌지 않는 경우가 있었다. 편집 화면은 값을 정상적으로 저장했지만, 렌더링하는 쪽이 다른 값을 먼저 선택했다.

| 증상                                                | 원인                                                  | 수정                                    |
| --------------------------------------------------- | ----------------------------------------------------- | --------------------------------------- |
| 그림을 넣어도 갈래 도식이 표시된다                  | 그림보다 갈래 도식(variants)을 먼저 렌더링했다        | 그림을 갈래 도식보다 먼저 렌더링한다    |
| 그림을 바꿔도 비교 슬라이더 반쪽에 옛 화면이 남는다 | 다크 테마 그림(`imageDark`)이 옛 그림의 짝으로 남았다 | 그림을 바꾸면 다크 그림을 함께 삭제한다 |
| 칸반(WTD)·터미널(DevCourse) 페이지에 그림이 없다    | 두 페이지가 항목의 그림을 렌더링하지 않았다           | 두 페이지도 그림을 렌더링한다           |

영상은 편집 화면에 보이는 칸이므로 그대로 그림보다 먼저 표시하되, 영상이 있는 항목의 그림 칸에 그 사실을 안내한다.

## 4단계: 내용은 하나로, 템플릿은 넷으로

템플릿이 열세 개로 늘어나면서 문제가 두 가지 생겼다. 하나는 템플릿마다 읽는 칸이 달랐다는 점이다. 어떤 모양은 폴더 구조를 렌더링하고 어떤 모양은 렌더링하지 않았고, 커밋 규칙이나 조작법처럼 한 모양만 쓰는 칸도 있었다. 칸을 채워도 모양을 바꾸면 그 내용이 화면에서 사라졌다. 다른 하나는 유지 비용이었다. 열세 개를 같은 수준으로 다듬을 수 없어, 어느 템플릿도 완성도를 높이지 못했다.

그래서 먼저 **공통 내용 모델**을 만들었다. `landingOf(project)`는 어떤 프로젝트든 첫 화면, 차례가 정해진 구역들, 마무리로 바꾸는 순수 함수다. 값이 없는 구역은 결과에 포함하지 않는다. 항목의 그림은 영상, 그림, 화면 여러 장 순서로 한 목록에 수집하고, 대표 화면이 비면 화면 모음의 첫 그림을 쓴다. 단위 시험은 편집 화면이 수정하는 칸이 하나도 누락되지 않는지까지 확인한다.

![Project를 landingOf가 첫 화면, 14개 구역, 마무리로 바꾸고, 아홉 템플릿이 그것만 읽는다](./images/site-projects-editing-templates-landing.svg '공통 내용 모델. 구역 차례는 포트폴리오를 읽는 순서다')

템플릿은 이 내용만 읽는다. 구역마다 렌더링 함수를 모은 객체는 구역 종류를 하나라도 빠뜨리면 타입 오류가 나도록 정의했다. 그래서 어떤 템플릿을 골라도 채운 칸이 모두 표시되고, 조작법과 폴더 구조와 출처도 모든 템플릿이 렌더링한다. 조작법 칸은 이때 모양 전용 칸에서 내용 탭의 공통 칸이 되었다.

그다음 템플릿을 **넷으로 줄였다**. 제품(Apple), 카드(Stripe), 문서(Notion), 벤토(Framer·Raycast)로 레퍼런스를 하나씩 정했다. 템플릿마다 폴더 하나로 분리해 서로 import하지 않게 했고, 지켜야 할 계약(모든 구역, 빈 구역 없음, 구역 이름, 라이트·다크, 좁은 창, 움직임 줄이기, 효과 절제)은 `templates/README.md`에 기록했다.

새 프로젝트의 기본 모양은 카드로 정했다. 제품 모양은 큰 대표 화면이 있어야 구성이 완성되는데, 새로 추가한 프로젝트에는 그림이 없는 경우가 많다. 카드 모양은 그림이 없어도 아이콘 카드로 구역을 채운다.

네 템플릿은 같은 기준으로 다듬었다. 아래 세 프로젝트를 라이트·다크 테마와 좁은 창에서 모두 캡처해, 어느 경우에도 빈자리가 보이지 않게 했다.

1. 예시를 모두 채운 프로젝트
2. 그림을 모두 뺀 프로젝트
3. 이름, 소개, 기능 두 개만 있는 프로젝트

그림이 없을 때 각 템플릿이 대신 렌더링하는 요소는 다음과 같다.

| 템플릿 | 그림 자리에 렌더링하는 것           |
| ------ | ----------------------------------- |
| 제품   | 큰 아이콘 타일                      |
| 카드   | 프로젝트 내용으로 만든 앱 화면 목업 |
| 문서   | 태그 색을 배경으로 한 표지          |
| 벤토   | 아이콘 타일과 명령 팔레트           |

예시 그림도 배경화면 대신 실제 앱 화면 캡처로 바꿨다. 배경화면을 넣으면 제품 페이지가 아니라 사진첩처럼 보였기 때문이다. 마무리 문장은 첫 화면 제목을 반복하지 않도록, 써 볼 수 있는 주소가 있는지에 따라 다른 문장을 사용한다. 예시 프로젝트도 열세 개에서 하나(북클럽)로 줄여 모든 템플릿이 공유한다.

### 예전 이름은 표로 옮긴다

예전 모양 이름으로 서버에 저장한 프로젝트도 그대로 표시되어야 했다. 그래서 검사 규칙(`parseProjects`)에 옛 이름을 지금 이름으로 바꾸는 표(`LEGACY_LOOKS`)를 추가했다. 서버와 화면이 같은 규칙을 쓰므로 저장할 때도 읽을 때도 옛 이름이 지금 이름으로 바뀐다. 아래는 최종 표다.

| 예전 이름                     | 지금   |
| ----------------------------- | ------ |
| showcase, assistant, dialogue | 카드   |
| cinema, deck                  | 키노트 |
| phone                         | 제품   |
| atelier                       | 매거진 |
| inbox, checklist              | 문서   |
| horizontal, brutal            | 벤토   |
| arcade                        | 놀이   |

## 5단계: 다시 아홉으로

네 템플릿은 스타일이 정돈되었지만 선택지가 적었고, 카드와 RPG 대화창은 완성도가 낮았다. 그래서 키노트(어두운 무대의 발표 장면), 매거진(명조와 큰 사진의 케이스 스터디), 개발자 도구(복사되는 clone 명령, 커밋 목록, 기여 그래프), 놀이(색 면과 둥근 도형, 스티커)를 추가했다. 같은 내용 모델을 쓰므로 새 템플릿은 폴더 하나와 E2E 한 파일로 추가된다. 예전 이름도 더 가까운 새 템플릿으로 다시 연결했다(위 표).

- **카드**는 Stripe 실제 페이지와 비교해 부족한 부분(채도가 낮은 겨자색, 대비가 약한 베이지 띠, 창 하나뿐인 첫 화면)을 정리하고, 비스듬한 띠와 줄무늬, 창 위에 겹친 숫자·기능 카드로 다시 디자인했다.
- **매거진**은 명조 웹 글꼴이 필요했지만 사이트의 [CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)가 외부 글꼴 요청을 차단한다. 그래서 기기에 설치된 명조(Mac에서는 애플명조)를 사용한다.

### 저장소 모양을 복원했다

저장소 모양은 개발자 도구로 통합했다가 다시 복원했다. GitHub 저장소 화면을 재현한 이 모양은 다른 템플릿과 구성이 겹치지 않는다. 다만 예전 코드는 프로젝트 칸을 직접 읽고 탭마다 다른 내용을 표시했으므로 공통 내용 모델 위에서 다시 작성했고, 예전 이름 표에서 repo를 빼서 저장소 모양으로 저장해 둔 프로젝트는 다시 이 모양으로 보인다.

- 페이지는 처음부터 저장소 화면으로 열린다. 처음에는 위에 랜딩식 첫 화면(가운데 배지, 큰 제목, clone 명령, 창 속 화면)이 있었는데 개발자 도구 템플릿과 구성이 같아 제거했다. 큰 제목은 README의 h1이 되고, 링크 버튼은 About 칸으로, clone 주소는 가지 줄의 초록 Code 버튼 안으로 들어갔다.
- 처음에는 README 하나에 모든 구역이 길게 이어져, 긴 랜딩 페이지를 상자에 넣은 것처럼 보였다. 그래서 GitHub가 README 상자 위에 README, Contributing, License 탭을 배치하는 것처럼 구역을 문서로 나눴다. README.md에는 큰 제목과 소개, 대표 화면, 숫자, 목차가 남고, 나머지 구역은 docs/FEATURES.md, docs/USAGE.md, docs/CHANGELOG.md처럼 별도 문서가 된다. 문서 탭이나 파일 트리의 docs/ 폴더에서 파일을 누르면 그 문서가 열리고, 경로 줄에 blob/main/docs/FEATURES.md가 보인다.
- 진행 과정은 v0.1.0부터 v1.0.0까지의 릴리스 목록, 기술 사양은 Built with 주제와 표와 폴더 구조 코드 블록, 맡은 일은 할 일 목록이 된다. 파일 상자는 폴더 구조로 만든 트리라 폴더를 눌러 펼치고, DevCourse는 예전처럼 실제 저장소를 탐색한다.
- Commits 탭은 진행 과정을 커밋 그래프로 렌더링하고 타입으로 필터링하며, 커밋 규칙이 있으면 Conventions 탭이 생긴다. 터미널 서랍의 셸에서도 폴더 구조를 `ls`와 `cd`로 탐색하고, `ls docs`와 `cat docs/USAGE.md`를 실행할 수 있다.
- 저장소 탭은 Safari 창의 탭과 구분되도록, 접근성 역할을 탭(`tab`) 대신 내비게이션과 현재 위치를 표시하는 버튼으로 지정했다.
- 공통 시험은 모든 구역이 한꺼번에 보이기를 기대하므로, 저장소 모양의 시험만 문서 탭을 차례로 열며 구역의 차례와 내용을 확인한다.

옆 칸의 **Languages**도 수정했다. 처음에는 프로젝트에 입력한 주 언어 하나를 100%로 렌더링했다. GitHub 링크가 있으므로 실제 언어 비율을 표시하도록 바꿨다. 다만 브라우저가 [GitHub REST API](https://docs.github.com/en/rest/repos/repos#list-repository-languages)를 직접 호출하면 인증 없는 요청의 [요청 제한](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)을 방문자마다 소모한다. 그래서 사이트의 API에 `GET /github/languages/{owner}/{이름}`을 추가하고 서버가 대신 조회한다.

![브라우저가 사이트 API에 언어 비율을 요청하면, 허용 목록과 캐시를 확인한 뒤 GitHub REST API를 호출하는 흐름](./images/site-projects-editing-templates-languages.svg 'Languages 막대의 조회 경로. 허용 목록에 없는 저장소는 GitHub에 요청하지 않는다')

- 누구나 호출할 수 있는 경로가 임의 저장소를 대신 조회하는 프록시가 되면 안 된다. 그래서 코드의 프로젝트가 가리키는 저장소와 관리자가 저장한 프로젝트 주소의 저장소만 허용하고, 그 밖의 저장소는 GitHub에 요청하지 않고 404로 응답한다.
- 코드의 프로젝트 목록은 화면 코드에 있어 서버가 읽을 수 없으므로, 공용 패키지(`desktop-core/src/site/github.ts`)에 저장소 이름만 별도로 저장하고 화면의 시험이 두 목록이 같은지 확인한다.
- 조회한 비율은 저장소마다 6시간(없는 저장소라는 응답은 30분) 캐시하고, GitHub에 연결하지 못하면 마지막 값을 응답한다(`apps/api/src/github/languages.service.ts`).
- 비율은 소수 첫째 자리까지 반올림하되 합이 꼭 100이 되게 맞추고, 0.5%보다 작거나 일곱째부터인 언어는 Other로 묶는다. 화면은 GitHub처럼 언어마다 한 구간인 막대와 색 점 목록을 렌더링하고, 응답을 기다리는 동안이나 요청이 실패하면 예전처럼 주 언어 하나로 렌더링한다.

## 6단계: 포트폴리오의 공통 항목을 칸으로

포트폴리오의 프로젝트 소개에는 대부분 같은 항목이 들어간다. 기능, 기술 스택, 트러블슈팅, 구현 방법, 팀원, 배포 결과물, 내 역할, 진행 과정이다. 기존 칸은 기능, 기술, 구현, 역할, 진행 과정까지는 갖췄지만 트러블슈팅, 팀원, 배포 결과물은 입력할 칸이 없어 장(chapters)에 함께 넣거나 생략해야 했다. 이 세 가지를 프로젝트 데이터의 필드로 추가했다.

| 필드        | 칸                                         |
| ----------- | ------------------------------------------ |
| 트러블슈팅  | 제목, 문제, 원인, 해결, 결과, 그림, 아이콘 |
| 팀원        | 이름, 역할, GitHub 주소, 사진, 나 표시     |
| 배포 결과물 | 이름, 주소, 플랫폼, 설명, 그림             |

서버와 화면이 같은 검사(`parseProjects`)를 쓰므로 주소는 https만 허용하고, 개수와 글자 수에도 다른 칸과 같은 상한을 적용한다.

공통 내용 모델에는 구역 세 개를 추가하고, 순서를 포트폴리오를 읽는 순서로 다시 정했다. 무엇인지(숫자, 주요 기능, 화면 모음, 쓰는 법), 어떻게 만들었는지(구현 방법, 트러블슈팅, 더 들려줄 이야기, 조작법, 기술 사양), 누가 만들었는지(팀원, 내 역할), 언제 만들었는지(진행 과정), 어디서 볼 수 있는지(배포 결과물)를 지나 출처로 끝난다. 구역 이름도 만든 방식은 구현 방법으로, 맡은 일은 내 역할로 바꿨다.

목표는 이미지가 하나도 없어도 빈 화면으로 보이지 않는 것이었다.

| 구역        | 이미지 없이 렌더링하는 방식                                                               | 저장소 모양에서                                                           |
| ----------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 트러블슈팅  | 아이콘과 번호 아래 문제 → 원인 → 해결 → 결과 단계 띠, 해결부터 강조색                     | docs/TROUBLESHOOTING.md의 GitHub 알림 상자(WARNING, NOTE, TIP, IMPORTANT) |
| 팀원        | 사진이 없으면 이름 첫 글자를 넣은 원, 본인은 강조색 테두리와 작은 표시                    | docs/TEAM.md의 사진 표와 옆 칸 Contributors                               |
| 배포 결과물 | 배포 플랫폼(Vercel, App Store, npm, Docker 등) 아이콘, 공개 상태, 호스트 이름의 링크 카드 | docs/DEPLOYMENT.md와 옆 칸 Deployments                                    |

레이아웃은 랜딩 키트의 공통 컴포넌트 하나로 작성하고, 템플릿은 CSS 변수와 접두사 클래스로 고유한 색과 모양을 적용한다. 편집 화면의 내용 탭에는 세 목록을 다른 목록과 같은 시트 방식으로 수정하는 칸을 추가했고, 북클럽 예시도 트러블슈팅 세 건(그림이 있는 것과 없는 것), 팀원 네 명, 배포 결과물 세 곳으로 채웠다.

## 7단계: 서로 비슷한 템플릿의 차이 만들기

아홉 개를 나란히 비교하니 구성이 서로 비슷했다. 처음에는 읽는 방식 자체(사이드바, 슬라이드 덱, 대시보드, 스크랩북)를 바꿨는데, 2단계처럼 템플릿마다 상호작용이 달라 일관성이 떨어져 모두 되돌렸다. 그다음에는 범위를 좁혔다. 디자인의 인상과 스크롤로 읽는 방식은 유지하고, 겹치던 세 가지만 바꿨다.

1. 첫 화면 구도: 가운데 제목, 왼쪽 제목과 오른쪽 창, 화면 가득한 그림 위 제목, 처음부터 타일 격자, 왼쪽 정렬 큰 제호, 터미널 창, 가운데 포스터.
2. 구역 머리의 모양과 제목 말투: 공용 문장 대신 템플릿마다 자기 문장.
3. 템플릿마다 대표 구역 한두 개.

저장소와 문서 템플릿은 원래 구조가 달라 변경하지 않았다.

## 빠진 템플릿: RPG 대화창의 기록

RPG 대화창(`dialogue`)은 이 PR에서 제외했다. 마을, 대화, 픽셀 그림까지 작업량이 많아 템플릿 작업과 별도로 진행하기로 하고, 작업은 `feat/rpg-dialogue` 브랜치에 보관했다. 예전에 dialogue로 저장한 프로젝트는 예전 이름 표가 카드로 바꿔 읽는다. 다시 작업할 시각을 위해 변경 과정을 기록한다.

아래 구현 세부는 다른 기능에도 적용할 수 있어 기록한다.

<details>
<summary>정수 배율, 대비, 대화 상자, 픽셀 그림, 마을, 에셋, 키 입력</summary>

- **정수 배율**: 고전 게임 화면이 선명한 것은 화면 전체를 낮은 해상도 하나로 렌더링한 뒤 정수 배로 확대해, 글자와 테두리와 그림이 같은 픽셀 격자를 공유하기 때문이다. 처음 480×270에서는 1440 창이 두 배, 780 창이 한 배였다. Safari 전체 화면의 실제 페이지 칸은 1440과 1100 창 모두 높이가 641px이라 384×216은 세 배가 들어가지 않아, 세 배(1080×624)가 두 폭 모두에 들어가는 360×208을 골랐다. 그 뒤 페이지 전체를 쓰게 바꾸면서는 게임 칸이 세로 200칸(가로 340칸) 이상 남는 가장 큰 정수 배율을 고르고, 1440×641 페이지는 세 배에 480×214칸이 된다.
- **대비**: 크림 바탕 위 보조 글자색을 #7a7a70에서 #5a5a52로 어둡게 해 6.5:1, 이름표 5.8:1, 커서 줄 4.9:1로 모든 글자가 [WCAG 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) 4.5:1을 넘게 했다. 남색 창 시기에는 장면의 가장 밝은 흰 칸 위에서도 흰 글 9.6:1, 보조 글자(#b8c0d8) 5.3:1, 금색(#ffd166) 6.7:1이었다.
- **두 줄 대화 상자**: 갈무리11의 글자 폭(한글 11, 빈칸 4.6)을 넉넉하게 추정해 줄을 미리 나눈 뒤 두 줄씩 넘긴다. 추정 폭이 실제보다 좁지 않으면 브라우저는 같은 위치나 더 뒤에서 줄을 바꾸므로 세 줄로 넘치지 않는다.
- **픽셀 그림 생성**: 프로젝트 아이콘과 팀원 사진은 네 배 크기로 축소해 렌더링한 뒤 색을 16개로 줄이고 4×4칸마다 가장 많은 색 하나를 골라(섞인 색을 만들지 않는다) 24×24 픽셀 그림으로 바꾼다. 장면은 칸마다 색 대신 팔레트 문자를 저장해 다크 테마에서는 밤 팔레트로 바꿔 칠하고, 장식 배치는 난수 대신 해시로 정해 항상 같은 모습이다.
- **마을**: 방향 키나 WASD로 한 칸(16px)을 180ms 동안 이동하고, [`requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)은 이동하는 동안에만 실행한다. 화면을 누르면 너비 우선 탐색으로 길을 찾는다. 데이터에 없는 주제의 자리는 빈집이나 꽃밭으로 남겨 어느 프로젝트에서나 지도의 짜임새가 같다. 모든 주제를 읽으면 북쪽 문이 열려 엔딩이 나온다. 이동하지 않고 읽으려는 사용자와 스크린 리더 사용자를 위해 X 키나 바로 가기 버튼이 주제 메뉴를 바로 열고, 지도는 스크린 리더에서 숨기며 알림 영역(live region)이 앞에 무엇이 있는지 문장으로 안내한다.
- **에셋**: Ninja Adventure Asset Pack은 CC0라 출처를 밝히지 않아도 되지만, 내려받은 주소와 라이선스 전문을 `public/imgs/rpg/ninja/LICENSE.txt`에 보관했다. 사용하는 타일셋 아홉 장과 캐릭터 열두 명, 몬스터 여섯 마리, 상자, 그림자, 말풍선만 복사해 합계 약 360KB다. 흙길·물·돌바닥은 이웃 여덟 칸의 모양으로 47가지 모서리 조각 중 하나를 고르는 자동 타일(autotile)로 배치한다.
- **그림은 게임 화면 밖에**: 게임 화면은 정수 배로 확대한 픽셀 캔버스라 그 안의 사진도 두세 배로 확대되어 흐려졌다. 무대에는 그림 자리만 배치하고, 그 자리의 실제 픽셀 사각형을 측정해 바깥 레이어에 그림을 표시한다. 원래 크기의 1.5배를 넘기지 않아, 1440 전체 화면에서 1440×900 그림은 499×312, 1124×1422 그림은 246×312로 표시된다.
- **키 입력**: Safari에서 탭을 누르면 포커스가 탭 버튼에 남는데, 키 이벤트를 페이지 안이나 문서 바탕에서 발생한 경우에만 처리해 X 키가 동작하지 않았다. 지금은 이 페이지가 열린 Safari 창 안이면 어디서 눌러도 Z, X, 방향 키, Esc를 처리하되, 글 상자와 다른 앱 창의 키 입력은 그대로 전달하고, 탭이나 도구 막대 버튼에서 누른 Enter·Space는 그 버튼이 처리한다.

</details>

데이터에서는 이 과정에서 `backdrop` 필드와 열네 테마 목록을 삭제했다. 예전에 저장한 값에 backdrop이 있어도 검사 규칙이 알 수 없는 필드를 제거하므로 오류 없이 읽힌다. 장면 그림(`art`)은 SproutFarm의 직접 짠 페이지가 쓰므로 데이터에 유지하고 편집 화면에서만 제거했다.

## 확인

- 단위(랜딩 내용): 빈 구역은 빠지고, 구역 차례가 정해져 있고, 첫 화면 그림은 대표 화면이나 화면 모음의 첫 그림이고, 편집 화면이 고치는 칸을 하나도 버리지 않는다. 예전 모양 이름은 지금 모양으로 바뀐다.
- 단위(`lookSamples.test.ts`): 직접 짠 페이지를 뺀 모양마다 예시가 하나씩 있고 모든 모양이 같은 예시를 모양만 바꿔 쓴다. '예시로 채우기'는 id·저장소·데모·앱을 변경하지 않는다.
- E2E: 템플릿마다 한 파일(`e2e/looks/`)로 예시의 모든 구역이 순서대로 표시되는지, 빈 프로젝트도 빈 구역 없이 렌더링되는지, 링크가 열리는지, 사이트 테마를 따르는지 확인한다. 저장소 모양은 문서 탭을 차례로 연다.
- 화면: 예시를 모두 채운 것, 그림을 모두 뺀 것, 이름·소개·기능 두 개만 있는 것을 라이트·다크와 좁은 창에서 캡처해 빈자리를 확인했다.

## 남은 과제와 정리

- 템플릿 수를 늘리기 전에 **내용 모델**부터 정했어야 했다. 열세 개가 각자 프로젝트 칸을 직접 읽을 때는 칸이 사라지는 문제와 유지 비용이 함께 커졌다. `landingOf` 하나를 만들고 구역 렌더링 함수를 타입으로 강제한 뒤에는 새 템플릿이 폴더 하나와 E2E 한 파일로 추가되었다.
- 3단계에서는 빛 번짐·그라데이션·유리 효과를 모두 넣은 결과보다, 효과를 제거하고 단색 바탕과 강조색 하나만 남긴 결과를 채택했다.
- 이름을 바꿀 때 옛 이름을 새 이름으로 바꾸는 표(`LEGACY_LOOKS`)를 검사 규칙에 추가하면, 서버에 저장된 값을 마이그레이션하지 않아도 된다.
- RPG 대화창은 `feat/rpg-dialogue` 브랜치에 있다. 다시 병합하려면 지금의 공통 내용 모델과 아홉 템플릿 구조에 맞춰 수정해야 한다.
