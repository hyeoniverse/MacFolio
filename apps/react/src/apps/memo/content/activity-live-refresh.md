'활동 상태 보기'를 열어 둔 채 방문을 기다리면 숫자가 바뀌지 않았다. 개요·유입 경로·앱·글 탭은 앱을 연 시각에 `GET /analytics/summary`를 한 번 호출하고, 그 뒤에는 기간을 바꾸거나 보기 메뉴의 '새로 고침'을 골라야만 다시 호출했다. 메뉴 안의 항목이라 이 기능이 있는지 알기 어려웠고, 결국 페이지 전체를 새로 고쳤다. 메모의 조회수·댓글 수·좋아요 수도 메모 앱을 처음 연 시각의 값에 머물렀다.

이번 변경으로 두 화면 모두 **브라우저 탭이 보이고 앱 창이 열려 있는 동안 1분마다** 값을 다시 조회한다. 도구 막대에는 마지막 갱신 시각과 새로 고침 버튼이 생겼다.

![활동 상태 보기의 도구 막대 오른쪽에 '14:03:24 갱신', 새로 고침 버튼, 기간 선택이 있다](./images/activity-live-refresh-window.jpg '도구 막대 오른쪽의 갱신 시각과 새로 고침 버튼 (가짜 데이터)')

## 조회하는 조건

조회는 세 조건이 모두 참일 때만 진행한다.

| 조건                 | 확인 방법                                                                                         | 거짓이 되는 경우                         |
| -------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 브라우저 탭이 보임   | [`document.visibilityState`](https://developer.mozilla.org/docs/Web/API/Document/visibilityState) | 다른 탭으로 전환, 브라우저 창 최소화     |
| 앱 창이 화면에 있음  | 창 store의 `isRunning && !isMinimized`                                                            | 빨간 버튼으로 닫기, 노란 버튼으로 최소화 |
| 그 값을 쓰는 탭을 봄 | `tab === 'live'` 등                                                                               | 실시간 탭에서 개요 탭으로 전환           |

두 번째 조건이 필요한 이유가 있다. MacFolio의 앱 컴포넌트는 창을 닫아도 언마운트되지 않는다. 처음 연 뒤로 계속 렌더링해 두어야 다시 열 때 입력 중인 글이나 스크롤 위치가 남기 때문이다(`hasOpened`). 그래서 이전 코드에서는 실시간 탭을 고른 채 창을 닫으면 `setInterval`이 그대로 남아 10초마다 `GET /analytics/live`를 호출했다. 이번에 만든 `useAppWindowShown('activity')`가 이 상태를 조회 조건에 넣는다.

## 시간표

![브라우저 탭이 숨은 동안과 창을 최소화한 뒤에는 요청이 없고, 다시 보이면 바로 요청하며, 실패하면 다음 요청까지 2분을 기다리는 시간표](./images/activity-live-refresh-timeline.svg '0~10분 동안의 요청 (도식)')

- **간격은 응답이 끝난 시각부터 측정한다.** `setInterval`은 응답이 늦어도 다음 요청을 보내 요청이 겹칠 수 있다. `setTimeout`을 응답마다 다시 예약하면 한 번에 요청 하나만 진행한다.
- **조건이 거짓이 되면 예약을 취소하고, 다시 참이 되면 바로 조회한다.** 탭을 오래 숨겨 두었다가 돌아왔을 때 최대 1분 지난 값을 보지 않게 한다. 후속 변경에서 탭만 다시 보일 때는 간격이 지났을 때만 바로 조회하도록 바꿨다([후속 글](/memo/live-refresh-more)).
- **실패하면 간격을 2배씩 늘린다.** 60초 → 120초 → 240초 → … 최대 10분([지수 백오프](https://en.wikipedia.org/wiki/Exponential_backoff)). 성공하면 60초로 돌아온다. 서버가 재시작 중일 때 열린 화면들이 1분마다 요청을 보내지 않게 한다.
- **수동 새로 고침은 진행 중인 요청과 합친다.** 버튼을 여러 번 눌러도 요청은 하나다.

## 공통 훅: 일정과 React를 분리

일정 관리(간격·중복 방지·백오프)는 React 없이 `shared/lib/poller.ts`의 `createPoller`에 두고, `shared/hooks/usePolling.ts`가 visibility와 `active` 값을 연결한다. 이 저장소의 단위 시험은 DOM 없이 Node에서 실행하므로, 일정 로직을 순수 모듈로 분리해야 [Vitest의 가짜 타이머](https://vitest.dev/guide/mocking/timers)로 시간을 앞당겨 확인할 수 있다.

```ts
const summaryPolling = usePolling(
	(isCurrent) =>
		fetchSummary(from, to).then((next) => {
			if (isCurrent()) setSummary(next);
		}),
	{ intervalMs: 60_000, active: shown && SUMMARY_TABS.has(tab), resetKey: `${admin}-${period}` }
);
// summaryPolling: { loading, updatedAt, failures, refresh }
```

`resetKey`(기간, 로그인 여부)가 바뀌면 진행 중인 요청의 응답을 버리고 바로 다시 조회한다. 7일을 보다가 30일로 바꾼 직후 7일 응답이 늦게 도착해도 `isCurrent()`가 `false`라 화면에 반영하지 않는다.

<summary>poller의 상태 전이</summary>

| 호출               | 진행 중이 아닐 때                                                           | 진행 중일 때                      |
| ------------------ | --------------------------------------------------------------------------- | --------------------------------- |
| `setActive(true)`  | 간격이 지났으면 바로 조회, 아니면 남은 시간 뒤 (창·탭을 다시 열었으면 바로) | 아무것도 하지 않음                |
| `setActive(false)` | 예약 취소                                                                   | 예약 취소 (응답은 반영)           |
| `refresh()`        | 바로 조회 (`active`일 때만)                                                 | 아무것도 하지 않음                |
| `reset()`          | 바로 조회                                                                   | 진행 중인 응답을 버리고 바로 조회 |
| `dispose()`        | 예약 취소                                                                   | 진행 중인 응답을 버림 (언마운트)  |

React 컴파일러 규칙(`react-hooks/refs`)은 렌더링 중에 ref를 함수로 넘기는 것을 금지한다. 그래서 poller는 `useState` 초기화 함수가 아니라 `useEffect` 안에서 만들고, 최신 `run` 함수는 ref로 넘긴다.

## 갱신해도 화면 상태는 유지

값만 바꾸고 화면 상태는 유지한다.

- **표 정렬**: 정렬 상태는 `StatTable` 안의 `useState`에 있다. 갱신은 `rows`만 바꾸고 표를 다시 마운트하지 않으므로, '조회' 오름차순으로 정렬한 표는 새 값으로 다시 정렬된다. 본문을 다시 마운트하는 `key`는 탭·기간이 바뀔 때만 바뀐다([앞 탭의 정렬을 물려받던 버그](/memo/analytics-public)를 고친 그 `key`다).
- **실시간의 펼친 방문**: 펼침 상태는 `visitId`로 보관하므로 목록이 갱신돼도 같은 방문이 펼친 채로 남는다.
- **스크롤**: 갱신 중에 '불러오는 중…'으로 바꾸지 않는다. 처음 불러올 때만 빈 상태를 보이고, 그 뒤에는 이전 값을 둔 채 응답을 기다린다.
- **실패**: 이미 값이 있으면 본문을 오류 문구로 바꾸지 않고, 도구 막대에만 '갱신 실패 · 14:03:25 기준'을 표시한다.

![도구 막대 오른쪽에 주황색 글자로 '갱신 실패 · 14:03:25 기준'이 보인다](./images/activity-live-refresh-failed.jpg '요약 요청이 503으로 실패한 뒤의 도구 막대 (가짜 데이터)')

새로 고침 단축키는 ⌥R이다. ⌘R은 브라우저가 먼저 처리해 페이지가 막을 수 없으므로, 다른 앱의 단축키처럼 ⌥ 조합을 쓴다(프로젝트 앱 창의 새로 고침도 ⌥R이다). 갱신 시각 글자에는 `aria-live`를 달지 않았다. 실시간 탭은 10초마다 시각이 바뀌어 스크린 리더가 계속 읽게 된다. 실패 문구만 `role="status"`로 알린다.

## 비용

서버는 Oracle Cloud VM 한 대의 Docker Compose이고, Cloudflare Tunnel 뒤에 있다. 요청 수는 화면 하나가 1시간 동안 계속 보일 때의 값이다.

| 화면                     | 경로                                   | 간격            | 요청/시간 | 요청 하나의 DB 조회                                                      |
| ------------------------ | -------------------------------------- | --------------- | --------- | ------------------------------------------------------------------------ |
| 개요·유입 경로·지역·기기 | `GET /analytics/summary`               | 60초            | 60        | 방문자: 서버의 1분 캐시[^1]. 관리자: 7번 (집계 유지 4번 + 기간 조회 3번) |
| 앱·글 (조회수 추가)      | `GET /analytics/views`                 | 60초            | +60       | 1분 캐시. 계산할 때 `groupBy` 1번 + 오늘 이벤트 1번                      |
| 실시간 (관리자)          | `GET /analytics/live`                  | 10초 · 60초[^2] | 360 · 60  | 1번 (`createdAt` 인덱스, 최대 2만 행)                                    |
| 서버 (관리자)            | `GET /resources`                       | 60초            | 60        | 2번 (7일 표본 최대 10,080행 + 알림 1행)                                  |
| 메모                     | `GET /analytics/views`, `/posts/stats` | 60초            | 120       | 조회수는 1분 캐시, 댓글·좋아요 수는 `groupBy` 2번                        |

[^1]: 방문자가 몇 명이든 같은 기간의 요약은 1분에 한 번만 계산한다. 그래서 방문자 화면을 60초보다 자주 조회해도 값이 바뀌지 않는다. 60초라는 간격은 이 캐시에서 정했다.

[^2]: 실시간 기간이 30분 이하면 10초, 그보다 길면 60초. 이전 코드와 같은 간격이다.

조회 경로(`GET`)에는 요청 제한(`@RateLimit`)이 없고, 쓰기 경로만 IP마다 1분에 횟수를 제한한다. Cloudflare는 요청 수로 과금하지 않는다. 늘어나는 부하는 방문자 한 명이 메모를 띄워 둘 때 1분에 `/posts/stats`의 `groupBy` 2번이다. 댓글·좋아요 표는 글 수만큼의 행으로 묶이므로 무시할 수 있는 수준이다.

반대로 줄어든 요청도 있다. 실시간 탭을 고른 채 창을 닫거나 브라우저 탭을 숨기면 이전에는 1시간에 360번을 계속 보냈고, 이제는 0번이다.

## 폴링, SSE, WebSocket

| 항목                 | 폴링 (이번 방법)            | SSE                                                     | WebSocket                               |
| -------------------- | --------------------------- | ------------------------------------------------------- | --------------------------------------- |
| 서버 변경            | 없음                        | NestJS `@Sse()` 경로와 값이 바뀐 시각을 알리는 장치     | 게이트웨이(`@nestjs/websockets`)와 인증 |
| 연결                 | 요청마다 짧게               | 열린 창마다 1개 유지                                    | 같음                                    |
| Cloudflare Tunnel    | 영향 없음                   | 프록시 읽기 제한(100초)[^3] 안에 하트비트를 보내야 한다 | 같음                                    |
| 값이 화면에 오기까지 | 최대 60초                   | 서버가 값을 다시 계산하는 시각까지                      | 같음                                    |
| VM(1 OCPU, 1GB) 부하 | 요청마다 짧게 처리하고 끝남 | 연결마다 소켓·메모리, 배포할 때 모든 연결이 끊긴다      | 같음                                    |

[^3]: [Cloudflare 오류 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/): 원본 서버가 100초 동안 응답하지 않으면 연결을 끊는다.

SSE로 바꿔도 값이 더 빨리 바뀌지 않는다. 방문 이벤트는 브라우저가 5초마다 묶어 보내고, 방문자 요약은 서버가 1분 동안 같은 값을 준다. 서버가 "값이 바뀌었다"고 알리려면 결국 서버 안에서 주기적으로 다시 계산해야 한다. 폴링 주기를 서버 캐시와 같게 두면 받는 값의 지연은 같고, 서버에는 연결을 유지하는 코드가 생기지 않는다.
