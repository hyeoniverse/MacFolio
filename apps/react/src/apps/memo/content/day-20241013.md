## 앱 상태를 AppContext 하나로

첫 커밋 "Fix: music player"는 이름과 달리 이날의 기반을 만든 커밋이다. 15개 파일에서 743줄을 더했다.

- `AppContext`: 앱 13개마다 `{ isRunning, isMinimized, zIndex }`를 보관하고, 열기·닫기·최소화·최대화 함수를 제공한다
- `Container`: 창 틀(제목 표시줄, 신호등, 끌기)을 한 컴포넌트가 렌더링한다. 앱마다 따로 있던 `MacOSTitlebar`를 삭제했다
- `types/AppTyes.ts`: 앱 이름과 상태 타입 (파일 이름의 오타는 그대로 남았다)

이전까지는 [이틀 전 옮긴 컴포넌트](/memo/day-20241011)가 각자 자기 창을 다뤘다. 이 커밋부터 창의 상태를 한곳에서 관리했다.

## 창: 크기 조절, 애니메이션, 맨 앞으로

`Container`가 생기자 창 동작을 여기에 차례로 추가했다.

| 커밋                           | 내용                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| feat: safari                   | Safari를 `Container`로 감싸고, 창 네 변을 끌어 크기를 바꾸게 했다(최소 200×150px). 최소화되면 렌더링하지 않는다 |
| feat: add animation            | 최소화하면 `scale(1)` → `scale(0)`, 0.5초 동안 줄어드는 `minimize` 키프레임                                     |
| feat: bring using app to front | 누른 창을 맨 앞으로 (`bringAppToFront`)                                                                         |
| feat: bring app to top         | Dock에서 앱을 열 때도 맨 앞으로                                                                                 |
| feat: content style            | 창 내용 영역의 스타일                                                                                           |

맨 앞으로 올리는 방식은 이랬다. 모든 앱을 `zIndex` 순으로 정렬해 0부터 다시 번호를 매기고, 누른 앱에 가장 큰 번호를 준다.

```ts
const bringAppToFront = useCallback(
	(appName: AppName) => {
		const sortedApps = Object.entries(apps).sort(([, a], [, b]) => a.zIndex - b.zIndex);
		setApps((prevState) => {
			const updatedApps = { ...prevState };
			sortedApps.forEach(([name], index) => {
				updatedApps[name as AppName].zIndex = index;
			});
			updatedApps[appName].zIndex = sortedApps.length;
			return updatedApps;
		});
	},
	[apps]
);
```

지금 보면 두 가지 문제가 있다. 정렬은 `setApps` 밖의 `apps`로 하고, 바깥 객체만 복사한 채 안쪽 객체의 `zIndex`를 직접 변경한다. 같은 렌더에서 두 번 호출하면 앞의 결과를 반영하지 못한다.

## Dock, 상태 막대, 공유 버튼

- **상태 막대 아이콘**: 메뉴 막대 오른쪽에 이전 곡·일시 정지·다음 곡·음량 아이콘 넷을 추가했다. 이 시점에는 누를 수 없는 장식이었고, 오후 늦게 음악 상태와 연결했다(아래 「음악 재생 상태를 창 밖으로」)
- **공유 버튼**: Dock의 공유 칸을 누르면 `navigator.clipboard.writeText(window.location.href)`로 주소를 복사하고, react-toastify로 "링크가 복사되었습니다!" 알림을 표시한다. 알림이 떠 있는 동안 공유 칸 아래 실행 표시를 켠다
- **Dock 정리**: GitHub·Notion 칸이 각 서비스의 첫 화면 대신 본인 프로필로 이동하게 했고, Launchpad 칸의 동작을 한 줄 수정했다

## 블로그 앱: iframe이 클릭을 가져가다

블로그 앱은 따로 운영하던 블로그(`codingkirby.github.io`)를 창 안에 iframe으로 표시하는 앱이다(60줄).

그런데 블로그 창이 뒤에 있을 때 그 안을 눌러도 맨 앞으로 올라오지 않았다. iframe 안의 클릭은 다른 문서의 이벤트라 바깥 창의 `onClick`까지 전달되지 않기 때문이다. 오후의 "fix: bring app to front" 커밋에서, 블로그 창이 맨 앞이 아닐 때만 iframe 위에 투명한 `div`를 덮어 클릭을 받게 했다.

```tsx
// 현재 blog 앱이 가장 높은 zIndex인지 확인
const isTopApp = Object.values(apps).every((app) => app.zIndex <= apps.blog.zIndex);

{
	!isTopApp && <div style={{ position: 'absolute', inset: 0, zIndex: 1 }} onClick={() => bringAppToFront('blog')} />;
}
```

맨 앞에 올라오면 덮개가 사라져 블로그를 그대로 조작할 수 있다. iframe을 창 안에 넣는 앱마다 필요한 처리인데, 이날은 블로그 앱에만 넣었다.

## 저장소를 client와 server로

React 앱 전체(77개 파일)를 `client/`로 옮기고(내용 변경 없이 경로만), 다음 커밋에서 Express 생성기로 `server/`를 만들었다. 생성기가 만든 jade 템플릿(`views/*.jade`)과 `routes/users.js`가 수정 없이 커밋되었다. 루트에는 `concurrently`로 두 폴더를 함께 실행하는 `package.json`(`npm run dev`)을 추가했다.

## 메일 앱과 사용하지 않은 메일 경로

메일 앱은 받은편지함 모양으로 시작했다(107줄). 메일 세 통은 코드에 적은 더미 데이터였다. 다음 커밋에서 더미 메일을 환영 메일 한 통으로 줄이고, 쓰기 버튼을 `mailto:` 링크로 변경했다. 같은 커밋에 빈 `server/.env` 파일도 들어갔다.

마지막 커밋에서 서버에 nodemailer로 Gmail SMTP를 쓰는 `POST /sendMail` 경로(39줄)를 추가했지만, 앱은 이 경로를 호출하지 않았다. 이 경로는 이틀 뒤 삭제된다([2024년 10월 15일 회고](/memo/day-20241015)).

## 음악 재생 상태를 창 밖으로

음악 플레이어는 이날 네 번 수정했다. 아침 첫 커밋과 그 7분 뒤 커밋에서 재생 로직을 정리하고, 최소화 애니메이션을 추가할 때 함께 다듬었다. 마지막 커밋에서는 재생 상태를 `MusicContext`(97줄)로 분리하고, 아침에 장식으로 추가한 상태 막대 아이콘에 `prevTrack`·`play`/`pause`·`nextTrack`을 연결했다. 재생 중이면 일시 정지 아이콘, 멈춰 있으면 재생 아이콘을 표시한다. 창을 닫아도 음악은 계속 재생되어야 해서, 재생 상태를 창 컴포넌트 밖에 보관해야 했다. 이 분리는 이튿날 [음악을 창 밖으로](/memo/day-20241014) 옮기는 작업으로 이어진다.

## 돌아보며

하루에 앱 둘과 서버 하나를 더했지만, 서버와 앱은 이날 한 번도 연결되지 않았다. 서버를 먼저 만들고 사용할 곳을 나중에 찾은 셈이다. 메일 앱이 결국 `mailto:`로 간 것을 보면, 그날 필요했던 것은 서버가 아니라 메일 앱의 화면이었다. 2026년에 메일을 서버로 보내게 한 것은 스팸 차단과 일일 상한까지 정한 뒤였다.

창 관리는 반대였다. 아침에 `AppContext`와 `Container`라는 기반을 먼저 만들었기 때문에, 크기 조절·애니메이션·맨 앞으로 올리기를 같은 날 하나씩 추가할 수 있었다. 블로그 iframe처럼 기반이 예상하지 못한 경우는 앱 안에서 따로 처리했다.
