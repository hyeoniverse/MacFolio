### 보안 점검 ([#252](https://github.com/hyeoniverse/MacFolio/pull/252))

보안 점검 도구는 검사 대상에 따라 두 종류로 나뉜다.

| 종류                               | 검사 대상                  | 방식                                                        | 사용한 도구             |
| ---------------------------------- | -------------------------- | ----------------------------------------------------------- | ----------------------- |
| SAST (정적 애플리케이션 보안 시험) | 직접 작성한 소스 코드      | 코드를 실행하지 않고, 위험한 코드 형태를 기술한 규칙과 비교 | Semgrep                 |
| SCA (소프트웨어 구성 분석)         | 설치한 외부 패키지(의존성) | 패키지 이름과 버전을 공개 취약점 데이터베이스와 대조        | pnpm audit, osv-scanner |

Semgrep이 보고한 7건 중 4건은 오탐(규칙의 형태와 일치하지만 실제로는 위험하지 않은 코드), 3건은 실제 영향이 없는 코드였다. 영향이 없는 3건 중 2건은 `__proto__` 같은 이름을 폴더 이름으로 그대로 따라가던 코드였다.

JavaScript 객체에서 `obj['__proto__']`는 객체 자신의 키가 아니라 모든 일반 객체가 공유하는 원형 객체(`Object.prototype`)를 가리킨다. 예를 들어 폴더 구조 텍스트를 트리로 만드는 반복문에 `__proto__/` 줄이 들어오면, 새 폴더 객체에 값을 쓰려던 코드가 원형 객체에 값을 쓰게 된다. 이를 프로토타입 오염(prototype pollution)이라 한다. 이 텍스트는 코드에 작성한 프로젝트 소개뿐이라 방문자가 바꿀 수 없어 영향은 없었지만, 수정 비용이 작아 해당 이름을 제외하도록 고쳤다.

ERROR 등급만 차단하는 Semgrep CI 작업을 추가했다([Semgrep과 SCA 도구로 점검하기](/memo/security-scan)). WARNING 이하까지 차단하면 오탐 때문에 PR이 자주 멈추므로, 확실한 위험만 머지를 막는다.

osv-scanner와 함께 쓰려던 NVD API 키는 발급받지 못했다. NVD는 미국 국립표준기술연구소(NIST)가 운영하는 공개 취약점 데이터베이스다. 신청 양식을 제출해도 확인 메일이 오지 않고 화면이 멈췄으며, 알려진 해결 방법을 모두 시도해도 결과가 같았다. 그래서 NVD 키 발급은 접고 해당 항목을 닫았다.

### UTM 집계 ([#253](https://github.com/hyeoniverse/MacFolio/pull/253))

UTM 매개변수는 링크 주소 뒤에 붙여 방문이 어디서 왔는지 기록하는 값이다. 예를 들어 이력서 PDF에 넣은 링크를 `https://사이트주소/?utm_source=resume&utm_medium=pdf&utm_campaign=resume-2026`처럼 만들면, 그 링크로 들어온 방문은 출처 `resume`, 매체 `pdf`, 캠페인 `resume-2026`으로 집계된다.

| 매개변수       | 뜻                      | 값의 예                     |
| -------------- | ----------------------- | --------------------------- |
| `utm_source`   | 출처 (어느 사이트·문서) | `linkedin`, `resume`        |
| `utm_medium`   | 매체 (어떤 형태의 링크) | `profile`, `post`, `social` |
| `utm_campaign` | 캠페인 (어떤 배포 묶음) | `resume-2026`               |

활동 상태 보기에 매체 표, 출처·매체·캠페인 조합 표와 조합별 일별 추이, 관리자용 UTM 링크 생성기를 추가했다. 출처 표와 캠페인 표를 따로 보면 "LinkedIn 글에 게시한 2026년 링크"로 들어온 방문이 몇 회인지 알 수 없어서, 세 값을 함께 묶은 조합 표가 필요했다.

방문 시 읽은 `utm_*` 값은 `history.replaceState`로 주소창에서 삭제한다. `history.replaceState`는 페이지를 다시 불러오지 않고 주소창의 주소만 바꾸는 브라우저 API다. 방문자가 UTM이 붙은 주소를 복사해 공유하면 같은 캠페인 방문이 중복 집계되고 링크를 배포한 곳도 함께 전달되기 때문이다([UTM 조합 표와 링크 생성기](/memo/utm-analytics)).

### 롤백 훈련 ([#254](https://github.com/hyeoniverse/MacFolio/pull/254))

롤백은 새 버전을 배포한 뒤 문제가 생겼을 때 이전 버전으로 되돌리는 작업이다. API 서버는 Docker 컨테이너로 실행되고, 배포 스크립트(`ops/deploy.sh`)는 새 이미지로 컨테이너를 교체한 뒤 헬스 체크를 확인한다. 헬스 체크는 Docker가 컨테이너 안에서 정해진 명령(여기서는 `/health` 요청)을 주기적으로 실행해 컨테이너 상태를 `healthy`·`unhealthy`로 표시하는 기능이다. 새 컨테이너가 `healthy`가 되지 못하면 스크립트는 이전 태그로 되돌리게 작성해 두었다.

그런데 이 경로가 실제로 동작하는지 확인한 적은 없었다. 그래서 헬스 체크에 항상 실패하는 훈련용 이미지를 운영 서버에 배포해 확인했다([롤백 훈련](/memo/rollback-drill)).

![롤백 훈련에서 확인한 순서와 41초](./images/day-1018-rollback-drill.svg '훈련 전 태그를 기록하고, 항상 실패하는 sha-dead000을 배포해, 이전 태그로 되돌아오는 과정을 서버 로그로 확인했다')

훈련은 서버에서 수동으로 했고, 순서는 다음과 같다.

1. **훈련 전 상태 기록:** 현재 태그는 `sha-7e7eac0`, 컨테이너는 healthy, `/health`도 같은 버전을 응답했다. 이미 서버에 접속한 상태에서 `ssh <서버 접속 명령>` 줄까지 함께 붙여 넣어 문법 오류가 한 줄 출력됐지만, 나머지 명령은 정상 실행됐다

![훈련 전 서버 상태](./images/rollback-drill-server-before.jpg '훈련 전. API_TAG와 컨테이너 상태, /health 응답을 먼저 기록했다. 접속 주소는 마스킹했다')

2. **훈련용 이미지 배포:** 헬스 체크에 항상 실패하는 `sha-dead000` 이미지를 빌드해 올리고, GitHub Actions의 "API 배포" 워크플로를 그 태그로 수동 실행했다
3. **롤백 확인:** 워크플로는 3분 만에 실패로 종료됐고, 서버 로그에는 `이전 버전으로 되돌린다: sha-7e7eac0` 다음에 `배포 실패, 되돌림: sha-7e7eac0가 다시 떠 있다`가 기록됐다. 두 줄의 로그 시각 차이로 계산한 ==롤백에 걸린 시간은 41초다==

![서버 로그의 되돌림](./images/rollback-drill-server-log.jpg '훈련 중 서버 로그. 새 이미지가 헬스 체크를 통과하지 못하자 41초 만에 이전 태그로 복구됐다')

4. **최종 상태 확인:** `watch docker compose ps`로 `sha-7e7eac0` 컨테이너가 healthy 상태로 유지되는 것을 확인하고 종료했다

```bash
cd ~/deploy
grep '^API_TAG=' .env                 # 훈련 전 태그 기록
docker compose ps api                 # (healthy) 확인
curl -s https://<API 주소>/health; echo
# 훈련용 이미지를 배포한 뒤
watch docker compose ps               # 이전 태그가 healthy로 유지되는지 확인
```

자세한 절차와 복구 방법은 [docs/rollback-drill.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/rollback-drill.md)와 [ops/deploy.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/deploy.sh)에 있고, 헬스 체크는 [Docker의 HEALTHCHECK 문서](https://docs.docker.com/reference/dockerfile/#healthcheck)를 따랐다.

## Finder의 문서 폴더와 미리보기 앱

리팩터링과 점검을 마친 뒤 Finder 작업을 시작했다. 이슈 [#8](https://github.com/hyeoniverse/MacFolio/issues/8)을 정리하며 설계부터 정했다.

| 결정 사항      | 내용                                                                             |
| -------------- | -------------------------------------------------------------------------------- |
| 파일 저장 위치 | 저장소가 아니라 Cloudflare R2. 사이트 Worker가 같은 출처의 `/files/` 경로로 제공 |
| 폴더 구조      | 기존 저장소 Markdown 문서와 별도로 이력서·포트폴리오·자격증 폴더                 |
| 파일 열기      | PDF와 그림은 Finder 안이 아니라 별도의 미리보기 앱에서 연다                      |

R2는 Cloudflare의 객체 저장소(파일을 키 이름으로 저장하고 꺼내는 저장소)이고, Amazon S3와 같은 API를 제공한다. PDF 같은 큰 파일을 git 저장소에 넣으면 저장소 용량이 계속 커지므로 R2에 보관한다. 사이트 Worker가 `/files/<키>` 요청을 R2로 연결해, 파일이 사이트와 같은 주소(같은 출처)에서 제공된다.

그때까지 Finder의 문서 폴더에는 저장소의 Markdown 문서만 있었다. 이날 그 아래에 이력서·포트폴리오·자격증 폴더를 추가했다.

![Finder의 문서 폴더](./images/day-1018-finder-docs.jpg#float-right 'Finder의 문서 폴더. 이력서·포트폴리오·자격증 폴더를 이날 추가했다. 사이드바의 데스크탑·블로그는 다음 날 화면')

처음에는 PDF와 그림을 Finder 창 안에서 표시했다. 그런데 macOS에서는 PDF를 Finder 안에서 읽지 않고, 더블클릭하면 미리보기(Preview) 앱이 열린다. 결과 화면을 보고 PDF와 그림을 별도 창의 미리보기 앱으로 열기로 바꿨고, 실제 미리보기 앱 수준으로 구현하는 데 필요한 범위를 검토한 뒤 착수했다.

미리보기 앱의 페이지는 브라우저 내장 PDF 뷰어 대신 pdf.js로 직접 렌더링한다. pdf.js는 Mozilla가 만든 JavaScript PDF 렌더러로, PDF 페이지를 `<canvas>`에 그린다. 내장 뷰어는 iframe 안에서 브라우저가 그리는 화면이라 페이지 썸네일, 검색, 텍스트 선택, 배율을 앱에서 제어할 수 없기 때문이다.

관리자의 파일 업로드 경로도 구현했다. ==파일이 API 서버를 거치지 않고 R2로 직접 전송된다==([Cloudflare R2 파일을 Worker가 같은 출처 /files/로 제공하기](/memo/finder-files)).

이 방식은 서명 URL(presigned URL)을 쓴다. 서명 URL은 "이 키에, 이 시각까지, 이 방식(PUT)으로 올려도 된다"는 허가를 주소 안에 서명으로 담은 일회성 주소다. API 서버는 R2 접근 키로 서명만 만들어 주고, 브라우저는 그 주소로 파일을 R2에 직접 올린다. 메모리 1GB짜리 VM이 20MB 파일을 받아 다시 R2로 보내는 중계를 하지 않아도 된다.

```text
브라우저 ── 폴더·이름·크기 ──▶ API: 관리자 세션, 파일 종류, 20MB 이하 확인
브라우저 ◀── 5분 유효한 서명 URL ── API
브라우저 ── 파일 본문 ──▶ R2 (API 서버를 거치지 않음)
```

![서명 URL로 R2에 직접 올리는 요청 순서](./images/day-1018-presigned-upload.svg 'API 서버는 ①②에서 권한과 크기만 확인하고 서명 URL을 반환한다. 파일 본문은 ③에서 브라우저가 R2로 직접 보낸다')

이 작업은 [#255](https://github.com/hyeoniverse/MacFolio/pull/255)로 올렸고, 다음 날 미리보기 앱을 보완한 뒤 머지했다.

## 음악 앱 버그 세 가지

마지막으로 음악 앱 버그 세 가지를 [#257](https://github.com/hyeoniverse/MacFolio/pull/257)로 고쳤다([isRunning 정의와 React key·ref 함수 동일성이 일으킨 음악 앱 버그](/memo/music-player-fixes)).

| 증상                                                          |
| ------------------------------------------------------------- |
| 배경 음악이 재생 중인데 Dock의 음악 아이콘에 실행 표시가 없음 |
| 셔플을 누르면 재생 막대의 앨범 표지가 겹쳐 쌓임               |
| '지금 재생 중' 시트를 끝없이 아래로 스크롤할 수 있음          |

macOS의 Dock은 실행 중인 앱 아이콘 아래에 점을 표시한다. 창을 모두 닫아도 앱이 종료되지 않았다면 점은 남는다. 첫째 버그는 이 구분이 없는 오래된 구조에서 비롯됐다. ==창이 열려 있는지와 앱이 실행 중인지를 하나의 값으로 관리하는 구조==가 2024년 10월의 첫 React 코드부터 있었다([2024년 10월 14일 회고](/memo/history-2024#10월-14일---최소화-애니메이션-위치-저장-최대화)).

음악은 창이 없어도 배경 음악으로 재생될 수 있으므로 두 상태가 달라질 수 있는데, 값(`isRunning`)이 하나뿐이라 구분하지 못했다. 창을 닫으면 `isRunning`이 `false`가 되어, 음악이 재생 중인데도 Dock의 점이 사라졌다. 그래서 두 상태를 별도의 값으로 나눴다.

![창이 열린 상태와 실행 중인 상태를 나누기 전후](./images/day-1018-is-running.svg '수정 전에는 창을 닫으면 실행 표시도 사라졌다. 수정 후에는 창 여부와 실행 여부를 따로 관리해, 창 없이 재생 중이어도 Dock에 점이 표시된다')

## 돌아보며

이날은 진행 중이던 작업을 마무리했다. 열흘 동안 이어 온 계획을 끝내고, 그동안 미뤄 둔 점검과 훈련을 했다. 리팩터링 PR은 화면을 바꾸지 않아 검토할 항목이 적었고, 그래서 올린 뒤 바로 머지할 수 있었다.

롤백 훈련은 코드로만 존재하던 복구 경로를 실제 서버에서 한 번 실행해 본 작업이다. 되돌림이 동작한다는 사실과 함께 41초라는 수치를 얻었고, 장애가 났을 때 사이트가 얼마나 오래 영향을 받는지 추정할 근거가 생겼다.

Finder 작업은 반대로 새 작업의 시작이었다. 첫 커밋은 Finder 창 안에서 PDF를 표시하는 방식이었는데, 37분 만에 미리보기 앱으로 옮겼다. 이 사이트의 기준은 "macOS처럼"이다. macOS에서는 PDF를 Finder 안에서 읽지 않는다는 점을 먼저 확인했다면 첫 커밋부터 미리보기 앱으로 구현했을 것이다.
