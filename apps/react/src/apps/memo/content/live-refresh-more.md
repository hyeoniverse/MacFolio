[앞 글](/memo/activity-live-refresh)에서 만든 `usePolling`은 '활동 상태 보기'와 메모의 조회수에만 적용했다. 다른 화면은 여전히 앱을 연 시각의 값에 머물렀다. 메시지 앱에서 답글을 기다리면 앱을 닫았다 열어야 했고, 바탕화면의 GitHub 기여 위젯은 페이지를 새로 고칠 때까지 같은 값을 보였다. 반대로 메뉴 막대와 날씨는 `setInterval`로 탭이 숨은 동안에도 요청을 보냈다.

이번 변경으로 아래 화면이 모두 **보이는 동안만** 같은 규칙으로 갱신한다.

![메시지 창에 새 답글 '답글 기능은 언제 생겼나요?'가 나타나 있고, 입력 칸에는 쓰던 '감사합니다! 어떤 부분이'가 그대로 남아 있다](./images/live-refresh-more-messages.jpg '15초 안에 새 답글이 보이고 입력 중인 글은 남는다 (가짜 데이터)')

## 적용 범위와 1시간당 요청 수

화면 하나를 1시간 동안 계속 띄워 둘 때의 요청 수다. '숨김'은 다른 브라우저 탭을 보고 있거나, 앱 창을 닫거나 최소화했거나, 휴대폰에서 앱이 홈 화면을 덮은 상태다.

| 화면                         | 경로                                   | 간격 | 이전                        | 이후 (보임)           | 이후 (숨김) |
| ---------------------------- | -------------------------------------- | ---- | --------------------------- | --------------------- | ----------- |
| 메시지: 보고 있는 대화       | `GET /messages/threads/:id`            | 15초 | 열 때 1번                   | 240                   | 0           |
| 메시지: 피드백 목록          | `GET /messages/threads`                | 60초 | 열 때 1번                   | 60                    | 0           |
| 메모 댓글                    | `GET /posts/:slug/comments`            | 60초 | 글을 열 때 1번              | 60                    | 0           |
| 메일 받은 편지함 (관리자)    | `GET /contact/inbox`                   | 2분  | 열 때 1번                   | 30                    | 0           |
| 메모 글 목록                 | `GET /posts`                           | 10분 | 열 때 1번                   | 6                     | 0           |
| 최근 글 위젯                 | `GET /posts`                           | 10분 | 페이지마다 1번              | 6 (위젯 수와 무관)    | 0           |
| 인기글 위젯                  | `GET /analytics/views`, `/posts/stats` | 10분 | 페이지마다 1번씩            | 12                    | 0           |
| GitHub 기여 위젯·GitHub 앱   | `GET /github/activity`                 | 10분 | 앱을 열 때마다 1번          | 6 (위젯·앱이 나눠 씀) | 0           |
| 메뉴 막대 서버 자원 (관리자) | `GET /resources`                       | 5분  | 12 (숨겨도)                 | 12                    | 0           |

| 날씨 앱·날씨 위젯            | Open-Meteo (외부)                      | 15분 | 도시마다 4 (숨겨도, 닫아도) | 도시마다 4            | 0           |

간격은 값이 바뀌는 빈도로 정했다. 메시지는 답글이 오가는 동안 기다리는 시간이 짧아야 하므로 15초, 댓글·피드백 목록은 1분, 연락 메일은 하루 몇 통 수준이라 2분, 글과 GitHub 기여는 하루 단위로 바뀌므로 10분이다.

## 다시 보일 때의 규칙 변경

앞 글의 `poller`는 조건이 다시 참이 되면 **언제나** 바로 조회했다. 탭을 잠깐 옮겼다 돌아올 때마다 요청이 하나씩 늘었다. 이번에 원인에 따라 나눴다.

![탭을 5초 숨겼다 보이면 35초에 묻지 않고 60초에 묻는다. 70초 숨겼다 100초에 보이면 바로 묻는다. 창을 닫고 10초 뒤 다시 열면 40초에 바로 묻는다](./images/live-refresh-more-resume.svg '간격 60초인 화면의 0~120초 (도식)')

| 원인                                         | 동작                                                                  |
| -------------------------------------------- | --------------------------------------------------------------------- |
| 브라우저 탭만 다시 보임 (`visibilitychange`) | 마지막 조회가 끝난 시각부터 간격이 지났으면 바로, 아니면 남은 시간 뒤 |
| `active`가 다시 참 (창·탭을 다시 엶)         | 바로 (사용자가 직접 연 화면이라 최신 값을 기대한다)                   |
| 조회 조건 변경 (`resetKey`: 대화, 글, 기간)  | 진행 중인 응답을 버리고 바로                                          |

`createPoller`의 `setActive(active, immediate)`가 두 경우를 받고, `usePolling`은 `active`가 거짓에서 참으로 바뀐 경우에만 `immediate`를 넘긴다. 실패가 이어지는 중이면 어느 경우든 늘린 간격을 지킨다.

## 위젯 여러 개, 요청 하나

바탕화면에는 같은 종류의 위젯을 여러 개 둘 수 있고, GitHub 기여 위젯과 GitHub 앱 창은 같은 `GET /github/activity`를 쓴다. 위젯마다 `usePolling`을 두면 위젯 수만큼 요청이 생긴다. 그래서 일정을 모듈에 하나 두고, 화면은 보이는 동안 그 일정을 '빌린다'.

![GitHub 기여 위젯 두 개와 GitHub 앱 창이 activityPolling 하나에 등록하고, 요청은 10분마다 한 번이다](./images/live-refresh-more-shared.svg 'createSharedPoller (도식)')

```ts
// githubActivityApi.ts: 일정은 모듈에 하나
export const activityPolling = createSharedPoller({ intervalMs: 10 * 60_000, run: () => loadActivity() });

// GithubWidget.tsx: 바탕화면·홈 화면이 보이는 동안 등록한다
const polling = useSharedPolling(activityPolling, useHomeScreenShown() && Boolean(env.apiUrl));
```

`createSharedPoller`는 `acquire()`가 돌려준 반납 함수의 수를 집계한다. 하나 이상이면 켜고 0이면 끈다. 응답은 이미 있던 store(`activityStore`, `serverPostsStore`, `postIndexStore`)에 보관하므로 위젯은 `useSyncExternalStore`로 같은 값을 읽는다.

위젯이 보이는지는 `useHomeScreenShown()`으로 확인한다. 바탕화면은 늘 보이는 것으로 본다(창이 위젯을 덮었는지는 알 수 없다). 휴대폰은 앞에 앱이 없을 때(`foregroundApp(apps) === null`)만 홈 화면이 보인다. 앱을 쓰는 동안 홈 화면 위젯은 요청하지 않고, 홈으로 돌아왔을 때 10분이 지났으면 바로 조회한다.

## 메시지: 스크롤과 입력 유지

메시지 앱은 15초마다 말풍선을 다시 받으므로 화면 상태를 건드리지 않는 것이 중요하다.

- **입력 중인 글**: 입력 상태는 `Composer` 안의 `useState`에 있고, 주기 조회는 `messages` 배열만 바꾼다. `Composer`를 다시 마운트하는 `key`(쓰기 버튼을 누른 횟수)는 바뀌지 않는다.
- **스크롤**: 이전에는 말풍선 수가 바뀔 때마다 맨 아래로 이동했다. 위로 올려 지난 말풍선을 읽는 중에 답글이 오면 읽던 위치를 잃는다. 이제 대화 칸(`role="log"`)의 `scroll` 이벤트에서 맨 아래 48px 안에 있는지 기록하고, 새 말풍선이 오면 맨 아래에 있었거나 내가 보낸 말풍선일 때만 따라 내려간다.
- **같은 응답**: 15초마다 받은 목록이 이전과 같으면 `keepIfSame`이 이전 배열을 그대로 돌려줘 다시 렌더링하지 않는다.
- **응답 순서**: 답글을 보낸 직후, 보내기 전에 출발한 조회의 응답이 늦게 도착하면 방금 보낸 말풍선이 잠깐 사라진다. 화면에서 말풍선을 더하거나 지운 시각을 기록해 두고, 그보다 먼저 출발한 조회의 응답은 반영하지 않는다. 댓글, 메일 답장도 같은 방법을 쓴다.

로컬 저장소 모드(`VITE_MESSAGES_STORE=local`)는 이 브라우저만 쓰므로 값이 바뀌지 않는다. `usePolling`의 `repeat: false`로 처음 열 때와 대화를 바꿀 때만 읽는다.

## 바뀌지 않은 응답의 전송량

메시지 API는 이미 응답에 [약한 ETag](https://developer.mozilla.org/docs/Web/HTTP/Reference/Headers/ETag)를 붙인다. NestJS가 쓰는 Express의 기본 설정(`etag: 'weak'`)이 JSON 응답 몸통의 해시로 만든다. 응답에 `Cache-Control`이 없으므로 브라우저 HTTP 캐시는 다음 `fetch`에 `If-None-Match`를 자동으로 붙이고, 값이 같으면 서버는 몸통 없이 `304 Not Modified`를 보낸다. 브라우저는 캐시한 몸통으로 `fetch`의 응답을 채우므로 화면 코드는 바꿀 것이 없다. 그래서 API는 바꾸지 않았고, API e2e 시험(`messages.e2e.test.ts`)에 304 응답을 확인하는 항목만 더했다.

<details>
<summary>ETag가 줄이지 못하는 것</summary>

ETag는 전송량만 줄인다. 서버는 304를 보낼 때도 DB를 조회하고 JSON을 만든 뒤 해시를 비교한다. 말풍선 조회는 `guestMessage`의 `(threadId, createdAt)` 인덱스를 쓰는 조회 1번이라 부담이 작다. 피드백 목록(`GET /messages/threads`)은 모든 피드백과 말풍선을 함께 읽으므로, 피드백이 수천 개로 늘면 `since` 파라미터로 바뀐 것만 받는 API가 필요하다. 지금은 피드백이 수십 개라 60초 간격이면 충분하다.

</details>

## 비용

방문자 한 명이 메시지 앱을 1시간 띄워 두면 요청은 300번(말풍선 240 + 목록 60)이다. 조회 경로에는 요청 제한이 없고 Cloudflare는 요청 수로 과금하지 않는다. 서버는 요청마다 인덱스 조회 1~2번을 실행하고, 대부분 304라 응답은 몇백 바이트다.

줄어든 요청도 있다. 사이트를 다른 탭에 띄워 두기만 해도 이전에는 1시간에 방문자 6번(방문 추이), 관리자 18번(서버 자원 12 + 방문 추이 6)을 보냈다. 날씨 앱을 한 번 연 뒤에는 창을 닫아도 도시마다 1시간에 4번씩 Open-Meteo를 호출했다. 이제 모두 0번이다.
