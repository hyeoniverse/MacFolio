MacFolio는 휴대폰에서 열면 macOS 바탕화면 대신 iOS 홈 화면을 표시한다. 화면 맨 위의 상태 표시줄(시계·배터리), 맨 아래의 홈 인디케이터(가로 막대), 앱마다 iOS 방식의 레이아웃이 따로 있어서, 넓은 창에서는 드러나지 않는 문제가 휴대폰에서만 나타난다.

### 날씨 앱: 판정 기준이 달랐던 휴대폰 화면

사이트는 폭 767px 이하(가로로 눕힌 휴대폰은 그 이상도)를 휴대폰 화면으로 판정하고, 이 판정은 `useIsMobile` 훅 한 곳에서 한다. 그런데 ==날씨 앱은 자체 기준으로 640px 이하일 때만 iOS 레이아웃으로 전환했다==. 판정 기준이 두 개였던 셈이다.

예를 들어 744px 폭의 세로 화면(iPad mini 세로 폭)에서는 사이트 전체가 휴대폰 셸(iOS 홈 화면)을 표시하지만, 날씨 앱은 넓은 창 레이아웃을 렌더링했다. 그 결과 위쪽이 흐려지고 사이드바 버튼이 상태 표시줄에 가려졌다. 메모 앱처럼 휴대폰 화면이면 폭과 관계없이 iOS 레이아웃을 쓰도록 고쳤다([useIsMobile과 ResizeObserver로 정하는 data-compact 레이아웃 기준](/memo/weather-layout-fixes)).

![날씨 앱 744px](./images/day-1016-weather.jpg '744px 세로 화면. 왼쪽은 넓은 창 레이아웃의 사이드바가 남아 있는 수정 전')

같은 PR에서 두 가지를 더 고쳤다.

- 넓은 창에서 사이드바 버튼을 누를 수 있게 사이드바 전체의 z-index를 올려 두었는데, 그 사이드바가 창의 신호등 버튼(닫기·최소화·최대화)을 덮었다
- 휴대폰의 목록 버튼이 장소가 하나뿐이면 왼쪽으로 밀려 배치됐다

### 상태 표시줄과 홈 인디케이터: 배경 밝기에 따라 색 선택

홈 화면의 상태 표시줄은 배경화면과 관계없이 항상 흰색이었다. 밝은 배경화면에서는 흰 바탕에 흰 글자가 되어 읽을 수 없었다. 실제 iOS는 배경이 밝으면 시계와 아이콘을 검은색으로, 어두우면 흰색으로 그린다.

이제 상태 표시줄과 홈 인디케이터 바로 아래에 렌더링된 화면(배경화면, 사진 등)의 색을 몇 지점에서 읽고, 흰색과 검은색(`#1c1c1e`) 중 그 색들과의 대비가 더 큰 쪽을 선택한다. 시계 영역과 아이콘 영역은 각각 따로 판정한다([배경 이미지 픽셀 샘플링과 대비 계산으로 상태 표시줄 글자색 정하기](/memo/mobile-bars-contrast)).

대비는 웹 접근성 지침(WCAG)의 정의를 따른다. 먼저 색마다 상대 휘도(relative luminance) `L`을 구한다. 상대 휘도는 사람 눈이 느끼는 밝기를 0(검정)~1(흰색)로 나타낸 값이고, 녹색 성분의 비중이 가장 크다. 두 색의 대비는 밝은 쪽 휘도를 `L₁`, 어두운 쪽을 `L₂`라 할 때 다음과 같고, 1(같은 색)에서 21(흰색과 검정) 사이의 값이 된다.

```math
\text{대비} = \frac{L_1 + 0.05}{L_2 + 0.05}
```

| 바탕색 (예시)         | 상대 휘도 | 흰색과의 대비 | 검은색과의 대비 | 선택   |
| --------------------- | --------: | ------------: | --------------: | ------ |
| 밝은 베이지 `#e8dcc8` |     0.725 |          1.35 |           12.56 | 검은색 |
| 남색 `#2b4a8b`        |     0.073 |          8.55 |            1.99 | 흰색   |

코드는 흰색 쪽 평균 대비에 1.3을 곱해 비교한다. 대비만 비교하면 iOS의 파란색처럼 중간 밝기 바탕에서 검은색이 근소하게 앞서는데, iOS는 그런 파란 바탕 위에 흰 글자를 쓰기 때문이다.

![상태 표시줄](./images/day-1016-bars.jpg 'iOS 18 라이트 배경화면. 수정 후에는 시계와 아이콘이 검은색이다')

시행착오가 둘 있었다.

- **글자 주변의 글로(glow) 효과:** 처음에는 밝기가 섞인 배경에 대비하려고 글자 둘레에 반대 색의 옅은 글로를 넣었다. 결과 화면에서 글자 윤곽이 번져 보여서 삭제했다. 실제 iOS도 단색만 쓰고 글로를 쓰지 않는다. 글로가 필요한 곳은 배경화면 하나의 아이콘 영역뿐이었다
- **홈 인디케이터의 판정 범위:** 글로를 삭제한 뒤 Kaleidoscope 배경화면에서 홈 인디케이터가 검은색으로 표시되는 버그를 찾았다. 인디케이터의 터치 영역은 화면 폭 전체인데, 색도 그 영역의 15·50·85% 지점에서 읽고 있었다. 가운데 막대 아래는 남색이지만 양 끝의 밝은 청록색이 평균을 끌어올려 검은색이 선택됐다. 실제로 보이는 막대(134px) 바로 아래만 읽도록 고쳤다

![홈 인디케이터 색을 읽는 지점의 범위 전후](./images/day-1016-indicator-samples.svg '수정 전에는 화면 폭 전체의 세 지점 중 두 곳이 밝은 청록이라 검은색이 선택됐다. 수정 후에는 보이는 막대 아래만 읽어 흰색이 선택된다. 색과 대비 값은 설명을 위한 예시다')

### 활동 상태 보기: `<` 버튼 삭제

휴대폰의 활동 상태 보기 첫 화면에는 홈으로 돌아가는 `<` 버튼이 있었고, 그 자리를 비우려고 탭 줄 전체가 왼쪽에서 64px 들여 배치되어 있었다. iOS에서 탭으로 구성된 앱의 첫 화면에는 뒤로 가기 버튼이 없고, 홈으로는 화면 아래에서 위로 쓸어 올려 돌아간다. 이 사이트의 날씨·사진 앱도 같은 규칙을 따른다.

버튼을 삭제하고 탭 줄과 기간 줄을 카드와 같은 정렬선에 맞췄다. 기간 선택은 넓은 창과 같은 오른쪽 끝으로 옮겼다.

## 메모 편집기

### 구분선과 "한 줄에 서식 하나" 규칙 ([#227](https://github.com/hyeoniverse/MacFolio/pull/227))

Markdown에서 `---` 한 줄은 구분선(`<hr>`)이 된다. 이 요소에 스타일이 지정되지 않아 브라우저 기본값(회색 2px 입체선, 위쪽 여백만 있음)이 그대로 표시됐다. 테두리 색 1px 선에 위아래 여백을 같게 지정했다. 편집기가 `---`를 `***`로 변환해 저장하던 문제도 고쳤다. 두 표기 모두 구분선이지만, 저장소 글은 `---`로 통일되어 있어 편집할 때마다 다른 줄로 바뀌면 변경 내역이 불필요하게 늘어난다.

![구분선](./images/day-1016-hr.jpg '다크 모드 읽기 화면. 수정 전에는 밝고 굵은 선이 두드러졌다')

목록 항목 안의 제목, 토글 제목 안의 머리말을 Notion처럼 허용할지, iOS 메모처럼 허용하지 않을지 결정해야 했다. 예를 들어 `- ## 설치` 같은 줄을 허용하면 목록 기호 옆에 큰 제목이 붙는다. iOS·macOS 메모 방식으로 정했고, 근거는 두 가지다.

- 서식 메뉴가 이미 macOS 메모의 서식 목록(한 줄에 하나만 선택)을 따르고 있었다
- Notion 방식으로 저장하면 읽기 화면에서 목록 기호 옆에 큰 제목이 붙어 레이아웃이 어색했다

이제 목록 항목에서 머리말 서식을 선택하면 그 줄은 목록에서 빠져 머리말이 된다([한 줄에 모양은 하나](/memo/memo-one-style-per-line)).

### 키보드 위 서식 막대와 문단 도구 ([#230](https://github.com/hyeoniverse/MacFolio/pull/230))

휴대폰에서 메모를 편집하다 화면 키보드가 올라오면 화면 아래의 서식 막대가 키보드에 가려졌다.

브라우저에는 뷰포트(viewport, 페이지가 보이는 영역)가 두 가지 있다. 레이아웃 뷰포트는 CSS의 `position: fixed; bottom: 0`이 기준으로 삼는 영역이고, 비주얼 뷰포트(`window.visualViewport`)는 지금 실제로 화면에 보이는 영역이다. iOS Safari는 키보드가 올라와도 레이아웃 뷰포트(`innerHeight`)는 그대로 두고 비주얼 뷰포트만 줄인다. 그래서 `bottom: 0`에 고정한 막대는 키보드 뒤에 남는다.

| 값                      | 키보드가 올라온 뒤   |
| ----------------------- | -------------------- |
| `window.innerHeight`    | 변하지 않음          |
| `visualViewport.height` | 키보드 높이만큼 감소 |

두 값의 차이로 키보드가 가린 높이를 계산해, 서식 막대를 그만큼 올려 키보드 바로 위에 화면 폭 전체로 표시했다. 주소창이 접히고 펴질 때도 비주얼 뷰포트 높이가 조금 바뀌므로, 차이가 120px 미만이면 키보드로 판정하지 않는다.

![키보드가 올라온 뒤의 innerHeight와 visualViewport.height](./images/day-1016-visual-viewport.svg 'innerHeight는 그대로이고 visualViewport.height만 줄어든다. 두 값의 차이가 키보드 높이이고, 서식 막대를 그만큼 올린다')

![키보드 위 서식 막대](./images/day-1016-keyboard.jpg '시험 브라우저에는 화면 키보드가 없어서 visualViewport만 줄이고 그 영역을 회색으로 칠했다')

같은 PR에 iOS 메모의 문단 도구도 추가했다. 서식 막대 끝의 문단 버튼을 누르면 막대가 내어쓰기·들여쓰기, 위·아래로 이동, 인용, 목록 버튼으로 전환된다.

시험 브라우저(Playwright)에는 화면 키보드가 없어서, 시험에서는 비주얼 뷰포트 높이만 줄여 키보드가 올라온 상태를 재현했다. 이 PR은 실제 아이폰에서 확인하지 못해 이날은 머지하지 않았다.

## 공통 정리: 대기 중이던 PR과 z-index 층 이름

10월 13일에 올린 활동 상태 보기 여백 정리([#222](https://github.com/hyeoniverse/MacFolio/pull/222))와 SearchField 컴포넌트 추출([#223](https://github.com/hyeoniverse/MacFolio/pull/223))을 사흘 만에 머지했다. #223은 CI 실패를 고친 뒤, 머지 전에 휴대폰 검색 문제 넷을 더 고쳐 넣었다. 예를 들면 다음과 같다.

- 사진 앱의 검색 칸이 줄어들지 않아 닫기(×) 버튼이 화면 밖으로 잘렸다
- 메시지 앱은 검색 중에도 오른쪽 버튼이 '새 피드백'이었다. 이제 검색 중에는 그 버튼이 검색 닫기(×)가 된다

공통 정리 계획(#150)의 다음 항목인 z-index도 정리했다([#231](https://github.com/hyeoniverse/MacFolio/pull/231), [z-index를 층 이름으로](/memo/design-tokens#z-index-층-흩어진-숫자를---z--변수로-모으기-231)). `z-index`는 겹친 요소 중 어느 것이 위에 그려지는지 정하는 CSS 속성이고, 값이 클수록 위에 그려진다. 13개 파일 20곳에 `1000`, `9999`, `15000` 같은 숫자로 흩어져 있던 값을 `theme.css`의 층 이름 변수 15개(`--z-dock`, `--z-menubar`, `--z-login` 등)로 통합했다.

```css
/* 전: 숫자만으로는 어느 층이 위인지 알 수 없다 */
z-index: 1000;

/* 후: 이름으로 층을 표현하고, 순서는 theme.css 한 곳에서 관리한다 */
z-index: var(--z-dock);
```

숫자만 흩어져 있으면 새 요소를 Dock 위, 메뉴 막대 아래에 두려 할 때 13개 파일을 모두 열어 값을 비교해야 한다. 층 이름 목록이 한 곳에 있으면 그 목록에서 위아래 값을 확인하고 사이 값을 고르면 된다.

## #187: RPG 대화창 네 차례 재설계

#187은 프로젝트마다 템플릿을 골라 Safari 페이지로 보여 주는 PR이고, RPG 대화창은 프로젝트 내용을 게임 화면처럼 보여 주는 템플릿이다. 이틀 전 잃은 2단계를 처음부터 다시 했다. 먼저 아홉 템플릿의 새 구역을 다듬었다.

- 팀원 카드의 GitHub 주소가 카드 밖으로 넘쳐서, 짧은 주소(`github.com/아이디`)로 표시했다
- 그림이 없는 트러블슈팅 항목은 문제·원인·해결·결과를 2×2 격자로 배치했다

이어서 RPG 대화창을 네 차례 다시 설계했다. 매번 실행한 화면을 보고 가장 눈에 띄는 문제 하나를 골라 그 축만 바꿨다.

| 차례 | 화면을 보고 판단한 문제                        | 바꾼 것                                                                                                                                   |
| ---: | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
|    1 | (2단계 재시작)                                 | 주제마다 데이터로 렌더링하는 게임 화면: 퀘스트 목록, 버그 몬스터 전투(문제→원인→해결→결과에 따라 HP가 100→67→33→0), 파티, 장비, 보물 상자 |
|    2 | 구성은 개선됐지만 표현이 거칠다                | 480×270 고정 해상도로 렌더링하고 정수배로 확대. 중첩된 상자를 없애고 색을 4가지로 제한                                                    |
|    3 | 색감이 어둡고 단조롭다                         | 라이트 모드는 포켓몬 GBA 같은 낮 장면, 다크 모드는 남색 밤 장면. 주제마다 단색 띠                                                         |
|    4 | 배경만으로는 부족하고 아이콘도 픽셀이어야 한다 | 16×16 픽셀 타일로 구성한 장면 10종, 12×12 픽셀 아이콘 35종과 기술 로고 24종                                                               |

두 번째 차례의 "정수배 확대"는 픽셀 그림을 선명하게 유지하는 방법이다. 480×270 화면을 1440×810으로 키우면 원래 픽셀 하나가 정확히 3×3 픽셀이 된다. 1.5배처럼 정수가 아닌 배율로 키우면 원래 픽셀 하나가 1픽셀과 2픽셀로 번갈아 그려져 같은 크기의 점이 서로 다른 굵기로 보인다.

![RPG 네 번](./images/day-1016-rpg.jpg '같은 트러블슈팅 장면을 네 차례 다시 설계했다')

네 번째 화면을 다시 확인하니 글이 잘 읽히지 않고, 메뉴 간 이동 흐름도 파악하기 어려웠다. 결론은 다음 날로 미뤘고, 다음 날 RPG 대화창을 #187에서 떼어 `feat/rpg-dialogue` 브랜치에 보관했다.

## CI: ECR Public 전송량 한도, 다섯 번째

이날 CI 실패는 모두 같은 원인이었다. API 시험은 실제 PostgreSQL이 필요해서, CI가 시험 전에 Postgres 컨테이너 이미지를 `public.ecr.aws`(Amazon ECR Public)에서 내려받는다. 이 요청이 `toomanyrequests: Data limit exceeded`로 거부되어 형식 검사와 시험을 시작하지 못했다.

| 날짜      | 위치              |
| --------- | ----------------- |
| 10월 13일 | #220 머지 후 main |
| 10월 15일 | #225              |
| 10월 16일 | #225 머지 후 main |
| 10월 16일 | #223              |
| 10월 16일 | #229              |

10월 10일에 Docker Hub의 내려받기 횟수 한도를 피하려고 ECR Public으로 옮겼는데, ==이번에는 ECR Public의 한도에 걸렸다==. ECR Public은 로그인하지 않은 요청의 전송량에 한도를 두고, GitHub Actions 실행기는 여러 사용자가 같은 IP 대역을 공유한다. 매번 실패한 작업만 재실행해 통과시켰고, 이미지 저장소는 이날까지 변경하지 않았다.

## 돌아보며

휴대폰 화면 PR은 모두 같은 절차로 진행했다. main에서 브랜치를 새로 만들고, 같은 시나리오로 수정 전후 화면을 캡처해 비교했다. PR끼리 겹치는 파일이 없어 어떤 순서로 머지해도 충돌하지 않았고, 대부분 올린 뒤 27~70분 안에 머지했다. ==변경을 작게 나누면 검토도 빨라진다.==

RPG 대화창은 반대였다. 네 차례 재설계하는 동안 판단 기준은 "거칠다", "어둡다", "부족하다" 같은 인상이었고, 매번 해상도 → 색 → 타일 순으로 한 축씩만 바꿨다. 10월 13일 회고에 "템플릿마다 참고할 실제 제품을 먼저 정한 뒤에야 방향이 잡혔다"고 적었는데, RPG에는 그런 기준이 없었다. 참고할 게임 화면 하나를 먼저 정했다면 재설계 횟수를 줄일 수 있었다.

> [!WARNING] 반복되는 이미지 한도 초과
> ECR 한도는 이제 일시적인 문제가 아니다. 나흘 동안 다섯 번 걸렸고, 매번 수동으로 재실행했다. 재실행하면 통과해서 미뤄 왔지만, 이미지를 캐시하거나 저장소를 바꿔야 한다.
