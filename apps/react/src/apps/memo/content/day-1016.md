### 날씨 앱: 판정 기준이 달랐던 휴대폰 화면

사이트는 폭 767px 이하(가로로 눕힌 휴대폰은 그 이상도)를 휴대폰 화면으로 판정한다. 그런데 날씨 앱은 자체 기준으로 640px 이하일 때만 iOS 레이아웃으로 전환했다. 그래서 641~767px 구간에서는 휴대폰 셸 안에 넓은 창 레이아웃이 표시되어, 위쪽이 흐려지고 사이드바 버튼이 상태 표시줄에 가려졌다. 메모 앱처럼 휴대폰 화면이면 폭과 관계없이 iOS 레이아웃을 쓰도록 수정했다([useIsMobile과 ResizeObserver로 정하는 data-compact 레이아웃 기준](/memo/weather-layout-fixes)).

![날씨 앱 744px](./images/day-1016-weather.jpg '744px 세로 화면. 왼쪽은 넓은 창 레이아웃의 사이드바가 남아 있는 수정 전')

같은 PR에서 두 가지를 더 수정했다.

- 넓은 창에서 사이드바 버튼을 누를 수 있게 사이드바 전체의 z-index를 올려 두었는데, 그 사이드바가 창의 신호등 버튼을 덮었다
- 휴대폰의 목록 버튼이 장소가 하나뿐이면 왼쪽으로 밀려 배치됐다

### 상태 표시줄과 홈 인디케이터: 배경 밝기에 따라 색 선택

홈 화면의 상태 표시줄은 배경화면과 관계없이 항상 흰색이었다. 밝은 배경화면에서는 흰 바탕에 흰 글자가 되어 읽을 수 없었다. 이제 상태 표시줄과 홈 인디케이터 바로 아래에 렌더링된 화면(배경화면, 사진 등)의 밝기를 읽어, 흰색과 검은색 중 대비가 더 큰 색을 선택한다. 시계 영역과 아이콘 영역은 각각 따로 판정한다([배경 이미지 픽셀 샘플링과 대비 계산으로 상태 표시줄 글자색 정하기](/memo/mobile-bars-contrast)).

![상태 표시줄](./images/day-1016-bars.jpg 'iOS 18 라이트 배경화면. 수정 후에는 시계와 아이콘이 검은색이다')

시행착오가 둘 있었다.

- **글자 주변의 글로(glow) 효과:** 처음에는 밝기가 섞인 배경에 대비하려고 글자 둘레에 반대 색의 옅은 글로를 넣었다. 결과 화면에서 글자 윤곽이 번져 보여서 삭제했다. 실제 iOS도 단색만 쓰고 글로를 쓰지 않는다. 글로가 필요한 곳은 배경화면 하나의 아이콘 영역뿐이었다
- **홈 인디케이터의 판정 범위:** 글로를 삭제한 뒤 Kaleidoscope 배경화면에서 홈 인디케이터가 검은색으로 표시되는 버그를 발견했다. 인디케이터의 터치 영역은 화면 폭 전체인데, 밝기도 그 전체(양 끝의 밝은 청록색 포함)를 기준으로 판정하고 있었다. 실제로 보이는 막대(134px) 바로 아래만 판정하도록 수정했다

### 활동 상태 보기: `<` 버튼 삭제

휴대폰의 활동 상태 보기 첫 화면에는 홈으로 돌아가는 `<` 버튼이 있었고, 그 자리를 비우려고 탭 줄 전체가 왼쪽에서 64px 들여 배치되어 있었다. iOS에서 탭으로 구성된 앱의 첫 화면에는 뒤로 가기 버튼이 없고, 이 사이트의 날씨·사진 앱도 같은 규칙을 따른다. 버튼을 삭제하고 탭 줄과 기간 줄을 카드와 같은 정렬선에 맞췄다. 기간 선택은 넓은 창과 같은 오른쪽 끝으로 옮겼다.

## 메모 편집기

### 구분선과 "한 줄에 서식 하나" 규칙 ([#227](https://github.com/hyeoniverse/MacFolio/pull/227))

구분선(`<hr>`)에 스타일이 지정되지 않아 브라우저 기본값(회색 2px 입체선, 위쪽 여백만 있음)이 그대로 표시됐다. 테두리 색 1px 선에 위아래 여백을 같게 지정했다. 편집기가 `---`를 `***`로 변환해 저장하던 문제도 수정했다.

![구분선](./images/day-1016-hr.jpg '다크 모드 읽기 화면. 수정 전에는 밝고 굵은 선이 두드러졌다')

목록 항목 안의 제목, 토글 제목 안의 머리말을 Notion처럼 허용할지, iOS 메모처럼 허용하지 않을지 결정해야 했다. iOS·macOS 메모 방식으로 정했다. 근거는 두 가지다.

- 서식 메뉴가 이미 macOS 메모의 서식 목록(한 줄에 하나만 선택)을 따르고 있었다
- Notion 방식으로 저장하면 읽기 화면에서 목록 기호 옆에 큰 제목이 붙어 레이아웃이 어색했다

이제 목록 항목에서 머리말 서식을 선택하면 그 줄은 목록에서 빠져 머리말이 된다([한 줄에 모양은 하나](/memo/memo-one-style-per-line)).

### 키보드 위 서식 막대와 문단 도구 ([#230](https://github.com/hyeoniverse/MacFolio/pull/230))

휴대폰에서 메모를 편집하다 화면 키보드가 올라오면 화면 아래의 서식 막대가 키보드에 가려졌다. iOS Safari는 키보드가 올라와도 레이아웃 뷰포트(`innerHeight`)는 그대로 두고, 보이는 영역(`visualViewport`)만 줄이기 때문이다.

| 값                      | 키보드가 올라온 뒤   |
| ----------------------- | -------------------- |
| `window.innerHeight`    | 변하지 않음          |
| `visualViewport.height` | 키보드 높이만큼 감소 |

두 값의 차이로 키보드가 가린 높이를 계산해, 서식 막대를 키보드 바로 위에 화면 폭 전체로 표시했다. 주소창이 접힐 때처럼 차이가 120px 미만이면 키보드로 판정하지 않는다.

![키보드 위 서식 막대](./images/day-1016-keyboard.jpg '시험 브라우저에는 화면 키보드가 없어서 visualViewport만 줄이고 그 영역을 회색으로 칠했다')

같은 PR에 iOS 메모의 문단 도구도 추가했다. 서식 막대 끝의 문단 버튼을 누르면 막대가 내어쓰기·들여쓰기, 위·아래로 이동, 인용, 목록 버튼으로 전환된다. 이 PR은 실제 아이폰에서 확인하지 못해 이날은 머지하지 않았다.

## 공통 정리: 대기 중이던 PR과 z-index 층 이름

10월 13일에 올린 활동 상태 보기 여백 정리([#222](https://github.com/hyeoniverse/MacFolio/pull/222))와 SearchField 컴포넌트 추출([#223](https://github.com/hyeoniverse/MacFolio/pull/223))을 사흘 만에 머지했다. 15시 40분에 #223의 CI 실패를 확인해 수정했고, 머지 전에 휴대폰 검색 문제 넷을 #223에 추가로 수정했다. 예를 들면 다음과 같다.

- 사진 앱의 검색 칸이 줄어들지 않아 닫기(×) 버튼이 화면 밖으로 잘렸다
- 메시지 앱은 검색 중에도 오른쪽 버튼이 '새 피드백'이었다. 이제 검색 중에는 그 버튼이 검색 닫기(×)가 된다

공통 정리 계획(#150)의 다음 항목인 z-index도 정리했다([#231](https://github.com/hyeoniverse/MacFolio/pull/231), [z-index를 층 이름으로](/memo/z-index-layers)). 13개 파일 20곳에 `1000`, `9999`, `15000` 같은 숫자로 흩어져 있던 값을 `theme.css`의 층 이름 변수 15개(`--z-dock`, `--z-menubar`, `--z-login` 등)로 통합했다.

```css
/* 전: 숫자만으로는 어느 층이 위인지 알 수 없다 */
z-index: 1000;

/* 후: 이름으로 층을 표현하고, 순서는 theme.css 한 곳에서 관리한다 */
z-index: var(--z-dock);
```

값 자체는 하나도 변경하지 않아 화면은 그대로다. 이 PR은 다음 날 0시에 머지했다.

## 돌아보며

휴대폰 화면 PR 다섯 개는 같은 절차로 진행했다. main에서 브랜치를 새로 만들고, 같은 시나리오로 수정 전후 화면을 캡처해 비교했다. PR끼리 겹치는 파일이 없어 어떤 순서로 머지해도 충돌하지 않았고, 다섯 개 중 넷이 올린 지 27~70분 사이에 머지됐다. 변경을 작게 나누면 검토도 빨라진다.

RPG 대화창은 반대였다. 네 차례 재설계하는 동안 판단 기준은 "거칠다", "어둡다", "부족하다" 같은 인상이었고, 매번 해상도 → 색 → 타일 순으로 한 축씩만 변경했다. 10월 13일 회고에 "템플릿마다 참고할 실제 제품을 먼저 정한 뒤에야 방향이 잡혔다"고 적었는데, RPG에는 그런 기준이 없었다. 참고할 게임 화면 하나를 먼저 정했다면 재설계 횟수를 줄일 수 있었다.

ECR 한도는 이제 일시적인 문제가 아니다. 나흘 동안 다섯 번 발생했고, 매번 수동으로 재실행했다. 재실행하면 통과해서 미뤄 왔지만, 이미지를 캐시하거나 저장소를 변경해야 할 시점이다.
