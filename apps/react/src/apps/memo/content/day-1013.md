## 템플릿 13개 → 4개 → 10개

[#187](https://github.com/hyeoniverse/MacFolio/pull/187)은 시스템 설정에서 프로젝트를 편집하는 PR이다. 새 프로젝트의 Safari 페이지는 선택한 템플릿으로 렌더링한다. 템플릿은 같은 프로젝트 데이터를 서로 다른 화면 구성으로 보여 주는 틀이다. 예를 들어 같은 "북클럽 앱" 데이터를 제품 템플릿은 Apple 제품 페이지처럼 큰 제목과 화면 하나로, 문서 템플릿은 Notion 문서처럼 제목과 본문 위주로 보여 준다. 템플릿은 네 단계를 거쳐 바꿨다.

| 단계              | 템플릿 수 | 내용                                                                                                                                                                                                               |
| ----------------- | --------: | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. 장식 제거      |        13 | 전날 넣은 빛 번짐, 그라데이션 글자, 반사, 기울기, 글래스 효과, 컬러 그림자, 떠 있는 카드를 모두 제거. 단색 배경, 큰 글자, 강조색 하나, 옅은 그림자 하나만 유지. 라이트 테마에서도 어두운 배경이던 것은 흰 배경으로 |
| 2. 공통 데이터    |         4 | 모든 템플릿이 같은 랜딩 데이터(`landingOf`)만 읽게 하고, 제품·카드·문서·벤토 4개로 통합                                                                                                                            |
| 3. 참고 제품 지정 |         4 | 템플릿마다 참고할 실제 제품을 지정: 제품은 Apple 제품 페이지, 카드는 Stripe, 문서는 Notion, 벤토는 Framer·Raycast                                                                                                  |
| 4. 템플릿 추가    |        10 | 키노트·매거진·개발자 도구·놀이를 추가하고, GitHub 저장소 화면 형식의 저장소 템플릿을 복원. RPG 대화창 포함                                                                                                         |

벤토(bento)는 크기가 다른 상자를 격자에 채워 넣는 레이아웃으로, 칸을 나눈 도시락처럼 기능 하나를 상자 하나에 담는다.

### 왜 13개를 4개로 줄였나

템플릿마다 읽는 데이터 필드가 달라서, 편집 화면에서 입력한 필드가 어떤 템플릿에서는 표시되고 어떤 템플릿에서는 표시되지 않았다. 예를 들어 "사용법"을 입력해도 cinema 템플릿은 그 필드를 읽지 않아 화면에 나오지 않았다. 그래서 모든 템플릿이 같은 랜딩 데이터를 읽게 바꿨다.

![모든 템플릿이 같은 landingOf 데이터를 읽고, 이전 템플릿 이름은 LEGACY_LOOKS로 변환하는 구조](./images/day-1013-landing-data.svg 'landingOf가 만든 섹션 목록을 모든 템플릿이 읽는다. 서버에 저장된 이전 템플릿 이름은 읽는 시점에 가장 가까운 새 템플릿으로 바꾼다')

```text
landingOf(project): 모든 템플릿이 읽는 랜딩 데이터
 ├ 히어로
 ├ 수치
 ├ 주요 기능
 ├ 화면 모음
 ├ 사용법
 └ 구현 방식 등
 ※ 비어 있는 섹션은 렌더링하지 않는다
```

히어로(hero)는 페이지 맨 위에서 제목·한 줄 소개·대표 이미지를 크게 보여 주는 첫 영역이다.

이전 템플릿 이름은 폐기하지 않았다. 서버에 저장된 값이 `cinema`면 키노트로, `brutal`이면 벤토로, 가장 가까운 새 템플릿으로 변환해 읽는다(`LEGACY_LOOKS`). ==서버 데이터를 마이그레이션하지 않고도 기존 프로젝트 페이지가 깨지지 않게 하려는 판단이다.== 마이그레이션은 DB에 저장된 값을 새 형식으로 일괄 변경하는 작업인데, 이 방식은 DB의 `cinema`를 그대로 두고 화면이 읽을 때만 `keynote`로 바꾼다.

![제품 템플릿](./images/day-1013-product.jpg '템플릿 4개 중 제품. Apple 제품 페이지처럼 큰 제목과 가운데 정렬, 그 아래 창 프레임 안의 큰 화면. 전날의 랜딩 페이지와 같은 프로젝트다')

### 저장소 템플릿의 언어 비율 API

저장소 템플릿의 Languages 막대는 실제 GitHub 언어 비율을 표시한다. GitHub 저장소 화면 오른쪽에 "TypeScript 90.0% · CSS 8.0%"처럼 표시되는 그 막대다. GitHub API는 언어별 코드 바이트 수만 돌려주므로, 공개 경로 `GET /github/languages/:owner/:name`이 그 바이트 수를 비율로 변환한다.

![저장소 언어 비율 API가 요청을 처리하는 순서](./images/day-1013-languages-api.svg '등록된 저장소인지 확인하고, 6시간 캐시가 있으면 바로 응답하고, 없으면 GitHub에 조회해 비율로 바꾼다. 오른쪽의 바이트 수는 예시 값이다')

| 고려 사항        | 조치                                                                    |
| ---------------- | ----------------------------------------------------------------------- |
| 오픈 프록시 악용 | 사이트 프로젝트에 등록된 저장소만 허용한다. 임의 저장소 조회는 거부한다 |
| GitHub API 한도  | 저장소별로 6시간 캐시한다                                               |
| GitHub 장애      | 응답이 없으면 이전에 캐시한 값을 사용한다                               |

오픈 프록시는 누구의 요청이든 대신 전달해 주는 서버다. 임의 저장소를 허용하면, 다른 사람이 이 경로로 GitHub API를 대량 호출해 MacFolio 서버의 GitHub API 한도를 소진시킬 수 있다. 등록된 저장소만 허용하면 조회 대상이 프로젝트 수만큼으로 제한된다.

## Sheet: 두 번째 공통 컴포넌트

시트(sheet)는 화면 아래에서 올라와 현재 화면 위에 겹치는 패널이다. iOS에서 메일 쓰기 창이나 공유 메뉴가 아래에서 올라오는 것이 시트다. main에서는 전날 Modal에 이어 Sheet를 추출했다. 휴대폰 음악 앱의 시트 동작이 어색해서 손을 댔다.

메일 쓰기, 메일 동작, 음악 지금 재생 중 3곳이 시트를 각자 구현하고 있었다. 오버레이, 열림·닫힘 애니메이션, 닫기 동작을 `Sheet` 하나로 통합하고, 형태 차이는 `variant` 3개로 구분했다([#220](https://github.com/hyeoniverse/MacFolio/pull/220), [오버레이·닫기·role을 공통 Sheet 컴포넌트로 추출하고 모양은 variant로 나누기](/memo/ui-sheet)).

| variant | 형태                                                                 |
| ------- | -------------------------------------------------------------------- |
| `page`  | 메일 쓰기·답장. 상태 표시줄 아래부터 바닥까지 덮고, 위에 손잡이 막대 |
| `card`  | 메일 동작. 홈 막대 위에 떠 있는 카드, 네 모서리가 둥글다             |
| `cover` | 음악 지금 재생 중. 오버레이 없이 앱 화면 전체를 덮는다               |

PR을 올린 뒤 두 가지를 추가로 수정했다.

| 증상                                     | 원인                                                           | 수정                             |
| ---------------------------------------- | -------------------------------------------------------------- | -------------------------------- |
| 시트가 열릴 때 뒤의 앱 화면이 스크롤된다 | 시트에 초점을 옮기면 브라우저가 초점 요소를 화면 안으로 스크롤 | `focus({ preventScroll: true })` |
| 음악 화면의 왼쪽 여백이 사라진다         | 시트가 가로로 넘쳐 화면 전체가 옆으로 밀렸다                   | `overflow-x: hidden`             |

첫 번째는 브라우저의 기본 동작이다. `element.focus()`를 호출하면 브라우저는 그 요소가 화면에 보이도록 스크롤한다. 시트는 열리는 순간 아직 `translateY(100%)`(화면 아래 바깥)에서 올라오는 중이었으므로, 초점을 옮기자 브라우저가 음악 앱 화면을 343px 스크롤했다가 애니메이션이 끝나며 0으로 되돌렸다. 화면이 위아래로 흔들린 이유다. `preventScroll: true` 옵션은 이 스크롤을 생략한다.

수정 후 전후 화면을 픽셀 단위로 비교해 동일한 것을 확인했다. 같은 방식으로 SearchField 추출([#223](https://github.com/hyeoniverse/MacFolio/pull/223))과 분석 앱의 여백 정리([#222](https://github.com/hyeoniverse/MacFolio/pull/222))도 PR을 열고 전후 화면을 픽셀 단위로 비교했다. 두 PR은 이날 머지하지 않았다.

## 두 번 발견한 CSS 레이어 순서 버그

### 증상

휴대폰으로 메일 앱을 열자 "서버에서 문제가 생겼습니다" 문구가 매우 작게, 여백 없이 보낸 편지함 바로 아래에 붙어 있었다. 이 문제와 비슷한 gap·padding 문제를 함께 고쳤다.

![휴대폰 메일의 오류 문구](./images/day-1013-mail-error-small.jpg '수정 전 휴대폰 메일상자. 빨간 오류 문구가 작고, 목록 상자에 여백 없이 붙어 있다')

여백을 점검하다가 답장 버튼의 padding이 0인 것을 찾았다.

### 배경: cascade layer

CSS는 같은 요소에 여러 규칙이 겹치면 우선순위(cascade)로 하나를 고른다. cascade layer는 규칙을 이름 붙인 묶음(`@layer`)으로 나누고, 묶음 사이의 우선순위를 선언 순서로 정하는 기능이다. 먼저 선언한 레이어가 가장 낮고, 나중에 선언한 레이어가 가장 높다.

이 사이트는 두 레이어를 쓴다.

- `reset`: 브라우저 기본 스타일을 지운다. 예: `* { padding: 0 }`
- `components`: 공통 컴포넌트의 스타일. 예: 공통 버튼의 `padding: var(--ui-button-padding)`

`@layer reset, components;` 순서면 components가 우선해 버튼에 여백이 생긴다. 순서가 반대가 되면 reset의 `padding: 0`이 이긴다.

### 원인

```css
/* 기대한 순서: 뒤에 선언한 레이어가 우선 */
@layer reset, components;

/* 실제 빌드 결과: 공통 컴포넌트 CSS 파일이 먼저 로드되어 순서가 뒤집힘 */
@layer components, reset;
/* → reset의 * { padding: 0 }이 버튼의 padding보다 우선 */
```

`@layer`의 순서는 ==처음 등장한 순서로 정해진다==. 순서를 선언한 문장이 따로 있어도, 그보다 먼저 `@layer components { ... }` 블록이 나오면 그 시점에 components가 첫 번째로 정해진다. 빌드한 HTML에서 공통 컴포넌트 CSS가 들어 있는 파일이 main CSS보다 먼저 연결되어 `components`가 먼저 선언됐다.

![빌드한 HTML에서 CSS 파일 순서에 따라 뒤집힌 @layer 순서와 수정](./images/day-1013-layer-order.svg '공통 컴포넌트 CSS 파일이 먼저 붙으면 components가 먼저 등장해 낮은 우선순위가 된다. index.html의 인라인 style 맨 앞에서 순서를 먼저 선언하면 파일 순서와 무관해진다')

### 해결

레이어 순서 선언을 `index.html`의 인라인 스타일 맨 앞으로 옮겨, 어떤 CSS 파일보다 먼저 선언되게 했다([#221](https://github.com/hyeoniverse/MacFolio/pull/221), [CSS 파일 로드 순서와 무관하게 @layer 순서를 index.html에서 먼저 선언하기](/memo/css-layer-order-fix)).

```html
<!-- index.html의 <head> -->
<style>
	@layer reset, components;
</style>
```

> [!WARNING] 머지하지 않은 브랜치의 수정
> 이 버그는 전날 #187에서 이미 수정했다. 그 수정이 아직 머지하지 않은 브랜치에 있어서, main에서는 처음부터 다시 찾아야 했다.

## 메일 입력 칸 오류 표시: 여섯 번의 시도

같은 PR에서 메일 쓰기 창의 입력 칸 오류 표시도 바꿨다. 빈 칸으로 보내기를 누르면 칸마다 오류 문구가 한 줄씩 추가되어 레이아웃이 밀렸다. 예를 들어 받는 사람·제목·본문을 모두 비우고 보내면 문구 세 줄이 생기면서 본문 칸이 그만큼 아래로 내려갔다.

![빨간 배경 오류와 칸 오류](./images/day-1013-mail-red-errors.jpg '수정 중의 데스크톱 메일. 목록 위 빨간 배경 경고와, 칸마다 표시된 빨간 테두리·문구. 받는 사람 주소는 마스킹했다')

| 시도 | 방식                                              |
| ---: | ------------------------------------------------- |
|    1 | 오류를 빨간 배경 상자에 표시                      |
|    2 | 필수 배지                                         |
|    3 | 칸 아래 줄의 안내 문구                            |
|    4 | 칸 밖 별도 줄의 흐린 문구                         |
|    5 | 칸 안의 placeholder 안내, 이름표만 빨간색         |
|    6 | macOS 메일 방식: 칸 사이에 아무것도 표시하지 않음 |

첫 시도는 시각적으로 과하고 화면과 어울리지 않았다. 2~5번째 시도는 차례로 적용하고 매번 화면을 열어 확인했다. 안내 문구로는 강조가 과하거나 글자 크기가 주변과 달랐고, 어느 방식이든 칸 사이에 요소가 늘어나 화면이 복잡해졌다. ==여섯 번째에야 macOS 메일의 방식을 따랐다.==

![macOS 메일의 경고창](./images/day-1013-macos-mail-alert.jpg '참고한 macOS 화면. 제목 없이 보내면 칸에 표시하지 않고 경고창으로 확인한다. 보낸 사람 주소는 마스킹했다')

- 네 칸이 모두 채워져야 보내기 버튼이 활성화된다
- 형식이 잘못되면 공통 경고창에 문구 하나를 표시한다

예를 들어 받는 사람 칸에 `abc`처럼 메일 주소 형식이 아닌 값을 넣고 보내면, 칸 아래에 문구가 생기지 않고 경고창 하나가 열린다. 칸 배치는 오류가 있든 없든 같다.

## CI: ECR Public의 요청 한도

Sheet를 머지한 뒤 main CI가 시험을 시작하지 못했다. API e2e용 PostgreSQL 이미지를 내려받다가 `toomanyrequests: Data limit exceeded` 오류가 났다. 10월 10일에 Docker Hub의 요청 한도를 피해 ECR Public(`public.ecr.aws`)으로 옮겼는데, 이번에는 ECR Public의 한도에 걸렸다.

| 레지스트리 | 로그인하지 않은 사용자의 한도(공식 문서) |
| ---------- | ---------------------------------------- |
| Docker Hub | IPv4 주소마다 6시간에 100회 내려받기     |
| ECR Public | 초당 1회 내려받기, 월 500GB 데이터 전송  |

오류 문구의 "Data limit"은 데이터 전송량 한도를 뜻한다. GitHub 러너는 IP 대역을 여러 사용자와 공유하므로, 어느 레지스트리든 로그인 없이 쓰면 다른 사용자의 사용량에 영향을 받는다. 다음 머지(#221)의 CI는 통과했다. 같은 한도는 15일과 16일에도 반복된다.

## 돌아보며

템플릿 구조가 안정된 것은 두 가지를 정한 뒤였다. 하나는 모든 템플릿이 같은 데이터를 읽는다는 것(`landingOf`), 다른 하나는 템플릿마다 참고할 실제 제품이다. 그 전 사흘 동안은 템플릿마다 읽는 데이터도, 디자인 기준도 달랐다. 그래서 13개를 만들 때마다 빈 영역을 채우는 작업이 생겼고, 장식을 추가했다가 제거했다. 무엇을 보여 줄지를 먼저 정하고 디자인했다면, 전날 넣고 이날 바로 걷어 낸 장식은 처음부터 없었을 것이다.

메일 입력 칸 오류도 같았다. 여섯 번 바꾼 끝에 정한 방식은 macOS 메일이 이미 쓰고 있는 방식이었다. macOS를 재현하는 사이트이니, 처음부터 macOS 메일을 확인했다면 한 번에 끝났을 것이다.

반대로 Sheet와 Modal은 전날 집계한 목록대로 재작업 없이 끝났다. ==무엇을 만들지 먼저 정하면 재작업 횟수가 줄어든다.==

10월 4일에 PR 하나에 여러 기능을 몰아넣은 것을 반성하고, 10월 7일에는 트래픽 분석을 여러 PR로 나눴다. 그런데 이번에도 #187 하나를 사흘 동안 키웠다. 그 사이 main의 버그 수정 하나를 그 안에 묻어, main에서 같은 버그를 다시 찾아야 했다. 편집 화면, 템플릿, 저장소 언어 API는 각각 따로 머지할 수 있는 단위였다.
