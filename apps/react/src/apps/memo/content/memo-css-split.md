메모 앱은 이 사이트에서 가장 큰 앱이다. 스타일도 `Memo.css` 한 파일에 4,600줄이 모여 있어서, 휴대폰 목록 화면의 여백 하나를 고치려 해도 긴 파일을 검색해 내려가야 했다. [리팩터링 계획](/memo/refactor-step2-structure)의 "큰 파일 나누기"에서 이 파일이 가장 컸다.

## 왜 그냥 옮기면 안 되는가

CSS는 같은 우선순위의 선택자가 둘이면 **뒤에 적힌 것이 이긴다**. 휴대폰 규칙이 데스크톱 규칙보다 뒤에 있어야 덮어쓸 수 있고, 나중에 더한 규칙이 앞의 것을 고치는 곳도 있다. 그래서 "사이드바 규칙은 모두 sidebar.css로"처럼 흩어진 규칙을 모으면 차례가 바뀌어 화면이 달라질 수 있다.

![모으기와 자르기](./images/memo-css-split-order-risk.svg '주제별로 모으면 차례가 바뀌어 화면이 달라질 수 있다. 자르기만 하면 차례는 그대로다')

| 방법                                          | 좋은 점                           | 걸리는 점                                                                                     |
| --------------------------------------------- | --------------------------------- | --------------------------------------------------------------------------------------------- |
| 컴포넌트마다 CSS를 붙인다 (`Sidebar.css` 등)  | 컴포넌트와 스타일이 함께 산다     | 규칙이 여러 컴포넌트에 걸친 곳이 많고, 불러오는 차례가 import 차례에 따라 바뀐다              |
| CSS Modules로 바꾼다                          | 이름이 겹치지 않는다              | 클래스 이름이 바뀌어 E2E 선택자와 다른 앱의 규칙이 깨진다. 4,600줄을 한 번에 옮길 일이 아니다 |
| **구역 경계에서 자르고 `@import`로 차례대로** | 결과가 바이트까지 같게 할 수 있다 | 파일 안에 "나중에 더한 규칙"이 그대로 남는다                                                  |

## 차례 그대로 자르기

규칙을 옮기지 않고, 파일을 **구역 경계에서 잘랐다**. 원래 파일에는 `/* ─── 폴더 사이드바 ─── */` 같은 구역 제목이 있었고, 자르는 자리가 `@media`·`@layer` 블록 안이 아닌지(중괄호 깊이가 0인지) 확인했다.

| 차례  | 파일                                                  | 줄    | 무엇                                        |
| ----- | ----------------------------------------------------- | ----- | ------------------------------------------- |
| 1     | `theme.css`                                           | 149   | 색 변수, 떠 있는 칸 배치, 칸 너비 손잡이    |
| 2–4   | `toolbar`·`sidebar`·`list`                            | 924   | 도구 막대, 폴더 사이드바, 글 목록           |
| 5–9   | `note`·`format`·`editor-blocks`·`comments`·`markdown` | 2,099 | 본문, 서식 도구, 편집기 블록, 댓글, 본문 글 |
| 10    | `gallery.css`                                         | 130   | 갤러리                                      |
| 11–13 | `compact`·`phone-note`·`phone-lists`                  | 981   | 좁은 창, 휴대폰 본문, 휴대폰 목록           |
| 14–15 | `highlight`·`late`                                    | 333   | 코드 강조, 나중에 더한 규칙                 |

![열다섯 파일의 줄 수 막대](./images/memo-css-split-order.svg '차례를 바꾸지 않고 구역 경계에서만 잘랐다')

`Memo.css`는 열다섯 줄의 `@import` 목록이 되었다. 빌드 도구가 이 목록을 차례대로 한 파일로 합친다.

```css
/* 메모 앱의 스타일. 파일 차례가 곧 적용 차례라(뒤에 온 같은 선택자가 이긴다) 원래 한 파일이던 차례 그대로 불러온다 */
@import './styles/theme.css';
@import './styles/toolbar.css';
@import './styles/sidebar.css';
/* … */
@import './styles/highlight.css';
@import './styles/late.css';
```

맨 위 주석이 이 파일의 유일한 규칙이다. 차례를 바꾸지 말 것. 새 규칙은 알맞은 구역 파일에 더하되, 같은 선택자를 덮는 규칙이 뒤 파일에 있는지 먼저 본다.

자르는 자리를 고를 때 중괄호 깊이를 센 것은 `@media (max-width: …) { … }` 안에서 자르면 앞 파일은 `{`가 열린 채 끝나고 뒤 파일은 `}`로 시작해 둘 다 깨진 CSS가 되기 때문이다.

## 같은지 확인하기

눈으로 화면을 비교하는 대신, 나누기 전과 후에 빌드한 CSS 파일의 해시(md5)를 비교했다. 둘이 같았다. 주석은 빌드에서 빠지므로, 규칙과 차례가 하나도 바뀌지 않았다는 뜻이다. 빌드한 파일 이름(내용 해시가 들어간다)도 그대로였다. 화면 스크린샷 비교보다 이쪽이 빠르고 엄격하다. 스크린샷은 시험이 지나가는 화면만 보지만, 빌드 결과 비교는 모든 규칙을 본다.

PR([#238](https://github.com/hyeoniverse/MacFolio/pull/238))은 27개 파일, 4,689줄 더하기, 4,619줄 지우기다. 더한 줄이 70줄 많은 것은 파일마다 붙인 구역 주석과 `@import` 줄이다. 코드 주석 여덟 곳에서 "`Memo.css`의 … 규칙"이라고 적어 둔 것을 나눈 파일 이름(`styles/compact.css`, `styles/theme.css` 등)으로 고쳤다. `CONTRIBUTING.md`의 파일 이름 규칙 표에는 "스타일이 길면(2,000줄 넘게) `styles/`에 나누고 원래 `.css`는 `@import` 목록"이라는 줄을 더했다.

## 남겨 둔 것

맨 뒤의 `late.css`는 새 메모·검색 칸 움직임, 이미지 틀, 캡션처럼 나중에 더한 규칙이 섞여 있다. 각자 자리(목록, 본문)로 옮기면 깔끔하지만 차례가 바뀐다. 옮길 때는 하나씩, 덮어쓰는 규칙이 없는지 확인하면서 한다.

지금(10월 19일) 열다섯 파일은 모두 4,644줄이다. 가장 큰 것은 `note.css`(612줄)와 `phone-lists.css`(580줄)다.

## 배운 것

- 큰 파일을 나눌 때 "어디로 옮길까"보다 "무엇이 바뀌면 안 되나"를 먼저 정한다. CSS에서는 차례였다.
- 결과물이 같다는 것을 해시로 확인할 수 있는 리팩터링은 화면을 하나하나 볼 필요가 없다. 같지 않으면 어디서 달라졌는지 빌드 결과를 `diff`로 본다.
- 나중에 정리할 것(`late.css`)을 이름으로 드러내 두면, 다음에 손댈 사람이 찾기 쉽다.
