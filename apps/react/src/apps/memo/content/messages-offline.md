메시지 앱(감상·의견·피드백)은 [방문자 쿠키로 이름을 정하는 작업](/memo/visitor-identity)에서 서버에 저장하게 됐다. 그런데 서버에 닿지 못할 때의 화면은 따로 만들지 않았다. 목록을 못 불러오면 "아직 남겨진 피드백이 없어요."가 떴고, 글을 보내면 입력창 아래에 브라우저의 영어 문구 "Failed to fetch"가 붉게 떴다.

![데스크톱 전후](./images/messages-offline-desktop.jpg '전: 빈 목록, 보내면 Failed to fetch / 후: 열 때와 보낼 때 모두 경고창')

## 배경

재현은 API 서버를 띄우지 않고 프론트엔드만 `pnpm dev`로 띄우면 됐다. 배포에서도 API 서버는 Oracle Cloud의 1GB 서버 한 대라, 배포 중이거나 서버가 멈추면 같은 화면이 나올 수 있었다.

빈 목록은 거짓말이다. 피드백이 없는 게 아니라 못 불러온 것이다. 서버가 없으면 읽지도 쓰지도 못하니 앱을 쓸 수 있는 척하는 것보다 열지 않는 편이 맞다. 메모가 코드를 못 불러오면 경고창을 띄우는 것과 같은 방식이다.

서버에 닿지 못할 때 할 수 있는 일을 세 가지로 놓고 비교했다.

| 방법                                           | 좋은 점                                                          | 문제                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------ |
| 빈 목록을 그대로 둔다 (원래)                   | 할 일이 없다                                                     | "피드백이 없다"는 틀린 정보를 준다. 보내면 영어 오류         |
| 앱 안에 "연결할 수 없음" 화면과 다시 시도 버튼 | 앱을 닫지 않는다                                                 | 앱마다 오류 화면을 따로 만들어야 하고, 빈 껍데기 창이 남는다 |
| 경고창을 띄우고 앱을 끈다 (고름)               | 메모의 코드 불러오기 실패와 같은 방식. 공통 경고창을 그대로 쓴다 | 다시 열어야 다시 시도한다                                    |

## 열 때 서버에 묻기

앱을 열면 피드백 목록(`GET /messages/threads`)부터 불러온다. 이 첫 요청이 실패하면 앱 내용을 그리지 않고 경고창을 띄운다.

> **메시지를 열 수 없습니다**
> 지금 서버에 연결할 수 없습니다. 잠시 뒤 다시 시도해 주세요. [확인]

알리기만 하는 창이라 버튼은 [확인] 하나다. 공통 경고창(AlertDialog)에 `cancelLabel={null}`을 주면 취소 버튼을 빼고, 남은 버튼이 가로를 다 쓴다. [확인]을 누르면 앱을 완전히 끈다. 데스크톱에서는 창이 닫히고, 휴대폰에서는 홈 화면으로 돌아간다. 다음에 열면 처음부터 다시 서버에 묻는다.

![휴대폰 전후](./images/messages-offline-mobile.jpg '휴대폰도 같다. 확인을 누르면 홈 화면으로')

## 열어 둔 뒤에 끊기면

![목록 상태](./images/messages-offline-status.svg '처음 불러오기 실패만 error가 되고, 쓰는 도중의 실패는 상태를 바꾸지 않는다')

앱을 쓰는 도중에 서버가 끊기면 앱을 닫지 않는다. 쓰던 글이 사라지기 때문이다. 그래서 처음 불러오기와 그 뒤의 목록 새로고침을 나눴다. `useConversations.ts`의 목록 상태는 `loading`에서만 `error`로 넘어간다.

```ts
const [status, setStatus] = useState<'loading' | 'ready' | 'error'>('loading');
// ...
.catch(() => setStatus((prev) => (prev === 'loading' ? 'error' : prev)))
```

보내기만 실패하고, 같은 경고창으로 "메시지를 보내지 못했습니다 / 서버에 연결할 수 없습니다. 잠시 뒤 다시 시도해 주세요. [확인]"을 띄운다. [확인]을 누르면 쓴 글이 입력창에 그대로 있고 커서도 돌아온다.

처음에는 입력창 아래에 붉은 글 한 줄로 띄웠다. 그런데 에러가 생기면 그 줄만큼 입력창이 위로 밀렸다가, 글을 고치면 다시 내려왔다. 경고창은 화면 위에 뜨므로 아무것도 밀지 않는다. E2E 시험에서 보내기 전과 실패한 뒤의 입력창 위치가 같은지 본다.

경고창 두 가지도 다듬었다. 문구가 "시도해 주/세요"처럼 낱말 중간에서 꺾여서 `word-break: keep-all`을 줬다. 열 때 [확인]에 초점을 두는데, 브라우저 기본 초점 테두리가 굵게(휴대폰 에뮬레이션에서는 주황) 그려져서 버튼 색을 옅게 섞은 바깥 고리로 바꿨다. 공통 경고창이라 메모를 지울 때 묻는 창에도 같이 적용된다.

`fetch`가 네트워크 문제로 실패하면 브라우저마다 다른 영어 문구(`Failed to fetch`, `Load failed`)를 던진다. 저장소에서 이것을 받아 위의 한국어 문구로 바꾼다. 말풍선을 불러오다 실패한 것은 처리하지 않은 Promise 에러로 남아 있었다. 이것도 받아서 보던 말풍선을 그대로 둔다.

## 개발할 때는 .env로

서버가 없으면 앱이 열리지 않으니, API를 띄우지 않고 화면만 고칠 때 곤란하다. 저장소를 `.env`로 고르게 했다.

| `VITE_MESSAGES_STORE` | 저장하는 곳                | 쓰는 때                       |
| --------------------- | -------------------------- | ----------------------------- |
| `local`               | 이 브라우저 (localStorage) | 서버 없이 화면을 확인할 때    |
| 비움 또는 `server`    | 서버 (`VITE_API_URL`)      | 배포. 서버가 없으면 열지 않음 |

```bash
echo 'VITE_MESSAGES_STORE=local' >> apps/react/.env.local
```

값을 읽는 곳은 `shared/config/env.ts` 한 곳이다. `local`이 아니면 모두 서버로 본다.

```ts
messagesStore: ((globalThis.__MACFOLIO_MESSAGES_STORE__ ?? import.meta.env.VITE_MESSAGES_STORE) === 'local'
	? 'local'
	: 'server') as 'local' | 'server',
```

저장소를 고르는 곳도 하나다. `repository/index.ts`의 `getConversationRepository`가 이 값을 보고 `localStorage` 저장소나 API 저장소 가운데 하나를 만든다. 두 저장소는 같은 `ConversationRepository` 모양을 따르므로 화면 코드는 어느 쪽인지 모른다.

배포 기본값은 서버다. 값을 비워 두면 서버에 저장하므로, 배포 설정에 따로 넣을 것이 없다. 예전에는 "서버 주소가 있으면 서버, 없으면 브라우저"였다. 그래서 배포에서 주소가 빠지면 방문자마다 자기 브라우저에만 글이 남는데, 화면으로는 그것을 알아채기 어려웠다.

E2E 시험은 API 주소를 바꾸던 자리(`__MACFOLIO_API_URL__`) 옆에 `__MACFOLIO_MESSAGES_STORE__`를 두었다. 시험은 기본으로 `local`을 쓰고, 가짜 API를 켜면 `server`가 된다. 서버 쪽 시험은 세 가지다.

- 서버 주소가 없을 때
- 서버가 응답하지 않을 때
- 열어 둔 뒤에 끊길 때

## 확인

- `e2e/messages.spec.ts`: "서버 주소가 없으면 앱을 열지 않고 알린다. 확인하면 앱을 끈다", "서버가 응답하지 않으면 앱을 열지 않는다", "열어 둔 뒤에 서버가 끊기면 보내기 실패만 경고창으로 알리고, 쓴 글은 남는다". 마지막 시험은 보내기 전과 실패한 뒤의 입력창 위치가 같은지도 본다.
- `e2e/mobile.spec.ts`에도 휴대폰에서 [확인]을 누르면 홈 화면으로 돌아가는지 더했다.
- 첫 커밋(`4f616edf6`)은 19개 파일을 고쳤다. 그중 화면 코드는 `Messages.tsx`·`useConversations.ts`·`apiConversationRepository.ts`이고, 나머지는 시험·`.env.example`·`README.md`·`docs/deployment.md` 같은 설정과 문서다. 두 번째 커밋(`31f2a0e31`)은 보내기 실패를 입력창 아래 붉은 글에서 경고창으로 옮기며 `Messages.css`의 오류 줄 스타일 10줄을 지웠다([PR #73](https://github.com/hyeoniverse/MacFolio/pull/73)).

## 남은 것·배운 것

- 앱을 끈 뒤 다시 시도하려면 앱을 다시 열어야 한다. 서버가 돌아왔는지 알아서 다시 묻지는 않는다.
- 저장소 기본값을 "주소가 있으면 서버"에서 "늘 서버, `local`일 때만 브라우저"로 바꾼 것이 가장 중요한 변경이었다. 배포 설정이 빠졌을 때 조용히 다른 곳에 저장하는 것보다, 앱이 열리지 않아 바로 알아채는 쪽이 낫다.
- 이 저장소 두 개는 뒤에 `packages/contracts`의 같은 `Thread`·`Message` 모양을 쓰게 정리했다([서버 저장소와 로컬 저장소가 같은 모양을 쓰게](/memo/contracts-messages)).
