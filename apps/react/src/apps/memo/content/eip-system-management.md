## 5과목은 무엇을 묻는가

정보처리기사 필기의 마지막 과목인 **정보시스템 구축 관리**는 소프트웨어를 만드는 조직이 프로젝트를 어떻게 계획하고, 어떤 기반(네트워크·서버·저장장치) 위에서 시스템을 운영하며, 그 시스템을 공격에서 어떻게 지키는지를 다룬다. 앞의 네 과목이 설계·구현·데이터베이스·프로그래밍처럼 "만드는 기술"이라면, 5과목은 "만드는 일을 관리하고 운영하는 기술"에 해당한다.

지금 적용되는 한국산업인력공단 출제기준(2023년 1월부터 2025년 12월까지)에서 5과목은 필기 100문항 가운데 20문항을 차지한다. 시험 전체 구조와 합격 기준은 [연재 첫 글](/memo/eip-overview)에 정리했다. 5과목은 용어 수가 가장 많은 과목이어서, 처음 보는 신기술 용어 한두 개 때문에 과락 기준선 근처까지 떨어지는 경우가 흔하다.

출제기준의 세부 항목은 네 덩어리다.

| 주요 항목                        | 세부 항목                                           | 이 글의 절                                       |
| -------------------------------- | --------------------------------------------------- | ------------------------------------------------ |
| 소프트웨어 개발 방법론 활용      | 방법론 선정, 비용 산정, 일정 관리, 프로세스 표준    | 개발 방법론, 비용 산정, 일정 관리, 프로세스 표준 |
| IT 프로젝트 정보시스템 구축 관리 | 네트워크 구축, 신기술 동향, 하드웨어·DB 관련 신기술 | 네트워크 구축, 신기술 용어                       |
| 소프트웨어 개발 보안 구축        | Secure SDLC, 시큐어 코딩, 암호 알고리즘             | 개발 보안                                        |
| 시스템 보안 구축                 | 서비스 공격 유형, 접근 통제, 인증, 보안 솔루션      | 시스템 보안                                      |

문항 비중은 회차마다 다르지만 대체로 앞의 두 덩어리(방법론·비용 산정·신기술)에서 10문항 안팎, 뒤의 두 덩어리(보안)에서 10문항 안팎이 나온다. 계산 문제는 LOC·COCOMO·임계 경로 정도이고, 나머지는 "다음 설명에 해당하는 용어는?" 형태가 대부분이다.

> [!TIP] 공부 순서
> 비용 산정과 일정 관리는 공식 몇 개로 확실히 점수를 얻는 영역이므로 먼저 끝낸다. 신기술 용어는 양이 많고 회차마다 새 용어가 섞여 나오므로 표로 묶어 반복해서 조회하는 방식이 효율적이다. 보안 용어는 실기에서도 그대로 다시 나오기 때문에 필기 단계에서 정확한 이름과 영문 약어까지 익혀 두면 실기 준비 시간이 줄어든다.

## 소프트웨어 개발 방법론

### 방법론이 필요한 이유

**소프트웨어 개발 방법론**은 소프트웨어를 개발하면서 어떤 순서로 무엇을 만들고, 어떤 문서와 그림(산출물)을 남기며, 누가 어떤 역할을 맡는지를 정해 둔 체계다. 생명 주기 모형(폭포수, 나선형 등)이 "단계의 순서"를 말한다면, 방법론은 각 단계에서 쓰는 기법과 산출물까지 포함한다.

방법론은 시대별로 "시스템을 무엇 단위로 나누어 바라보는가"가 달라지면서 바뀌어 왔다.

![구조적, 정보공학, 객체지향, CBD, 애자일 방법론의 중심 단위와 산출물](./images/eip-system-management-methodologies.svg '방법론마다 시스템을 쪼개는 기준이 기능, 데이터, 객체, 컴포넌트, 반복 주기로 바뀐다')

### 구조적 방법론

**구조적 방법론**(Structured Development)은 1970년대에 정립된 방법으로, 시스템을 "입력을 받아 처리하고 출력하는 기능의 흐름"으로 보고 큰 기능을 작은 기능으로 하향식으로 나눈다. 분석 단계에서는 **DFD**(Data Flow Diagram, 자료 흐름도)로 데이터가 어떤 처리를 거쳐 어디로 가는지 그리고, **자료 사전**(DD)으로 데이터 항목을 정의하며, **소단위 명세서**(Mini-Spec)로 가장 작은 처리의 논리를 적는다. 설계 단계에서는 모듈을 계층으로 배치한 구조도를 만든다.

> [!NOTE] 분할과 정복
> 구조적 방법론의 핵심 원리는 **분할과 정복**(Divide and Conquer)이다. 복잡한 문제를 사람이 한 번에 이해할 수 있는 크기까지 쪼갠 뒤 하나씩 해결한다. 다만 기능 중심으로 쪼개면 같은 데이터를 여러 기능이 따로 다루게 되어, 데이터 구조가 바뀌면 여러 모듈을 함께 고쳐야 하는 문제가 생긴다.

### 정보공학 방법론

**정보공학 방법론**(Information Engineering)은 1980년대에 등장했다. 기업의 업무 시스템에서는 기능보다 데이터가 더 오래 유지된다는 점에 착안해, ==데이터를 중심으로 전사(기업 전체) 정보 시스템을 계획==한다. 정보 전략 계획 → 업무 영역 분석 → 업무 시스템 설계 → 구축 순서로 진행하며, 데이터 모델링 도구로 **ERD**(Entity-Relationship Diagram, 개체 관계도)를 쓴다. 대규모 조직의 정보 시스템을 통합하는 데 적합하지만, 계획 단계가 길고 작은 프로젝트에는 무겁다.

### 객체지향 방법론

**객체지향 방법론**(Object-Oriented)은 데이터와 그 데이터를 다루는 연산(메서드)을 하나로 묶은 **객체**를 기본 단위로 한다. 1990년대에 럼바우(OMT), 부치, 야콥슨(유스케이스)의 방법이 경쟁하다가 표기법이 **UML**(Unified Modeling Language)로 통일되었다. 캡슐화, 상속, 다형성 덕분에 변경의 영향이 객체 안에 머물고, 이미 만든 클래스를 재사용하기 쉽다. 분석·설계 기법 자체는 [1과목 소프트웨어 설계 글](/memo/eip-software-design)에서 자세히 다룬다.

### CBD 방법론

**CBD**(Component Based Development, 컴포넌트 기반 개발)는 독립적으로 배포할 수 있는 실행 단위인 **컴포넌트**를 조립해 시스템을 만드는 방법이다. 컴포넌트는 내부 구현을 숨기고 **인터페이스**(외부에서 호출할 수 있는 기능 목록)만 공개하므로, 같은 인터페이스를 지키는 다른 컴포넌트로 교체할 수 있다. 예를 들어 쇼핑몰의 결제 기능을 결제 컴포넌트 하나로 만들어 두면, 다른 쇼핑몰을 만드는 경우 이 컴포넌트를 그대로 가져다 쓸 수 있다.

CBD의 개발 절차는 **개발 준비 → 분석 → 설계 → 구현 → 테스트 → 전개 → 인도** 순서다. 재사용으로 개발 기간과 비용을 줄이고, 표준화된 인터페이스로 유지보수가 쉬워지는 것이 장점이다.

### 애자일 방법론

**애자일**(Agile)은 2001년 17명의 개발자가 발표한 「애자일 소프트웨어 개발 선언」에서 시작된 개발 철학이다. 선언문은 네 가지 가치를 비교 형태로 제시한다.

| 더 가치 있게 여기는 것 | 그보다 덜 중시하는 것 |
| ---------------------- | --------------------- |
| 개인과 상호작용        | 프로세스와 도구       |
| 작동하는 소프트웨어    | 포괄적인 문서         |
| 고객과의 협력          | 계약 협상             |
| 변화에 대응하기        | 계획을 따르기         |

선언문은 오른쪽 항목도 가치가 있지만 왼쪽 항목을 더 중시한다고 밝힌다. 시험에서는 "애자일 선언의 가치가 아닌 것"을 고르는 문제가 나오는데, 오른쪽 항목(예: "계획을 따르기")을 왼쪽에 놓은 보기가 정답이 된다.

애자일 철학을 구체적인 절차로 만든 방법이 여럿 있다.

| 방법          | 핵심 특징                                                     | 시험에 자주 나오는 용어                |
| ------------- | ------------------------------------------------------------- | -------------------------------------- |
| 스크럼(Scrum) | 1~4주 단위 스프린트를 반복, 역할과 회의를 정해 둠             | PO, 스크럼 마스터, 백로그, 번다운 차트 |
| XP            | 짧은 주기로 자주 출시하고 고객이 개발에 참여                  | 짝 프로그래밍, TDD, 리팩토링           |
| 칸반(Kanban)  | 작업을 카드로 보드에 붙여 흐름을 시각화, 진행 중 작업 수 제한 | WIP 제한                               |
| 린(Lean)      | 도요타 생산 방식에서 온 낭비 제거 원칙                        | 낭비 제거, 빠른 인도                   |
| FDD           | 기능(Feature) 단위로 짧게 반복                                | 기능 목록                              |

![제품 백로그에서 스프린트 계획, 스프린트, 리뷰와 회고, 증분 출시로 이어지는 스크럼 흐름](./images/eip-system-management-scrum.svg '스프린트 하나가 끝나면 리뷰와 회고를 거쳐 다음 스프린트 계획으로 돌아간다')

스크럼의 산출물 가운데 **번다운 차트**(Burn-down Chart)는 가로축을 시간, 세로축을 남은 작업량으로 두고 그린 그래프다. 스프린트가 진행될수록 선이 0을 향해 내려가야 하며, 선이 이상적인 기울기보다 위에 있으면 일정이 밀리고 있다는 뜻이다.

XP는 다섯 가지 핵심 가치(**용기, 단순성, 의사소통, 피드백, 존중**)와 12가지 실천 방법으로 구성된다. 실천 방법 가운데 시험에 나오는 것은 짝 프로그래밍(두 사람이 한 컴퓨터에서 한 명은 작성하고 한 명은 검토), 공동 코드 소유, 테스트 주도 개발(테스트 코드를 먼저 작성), 지속적인 통합, 리팩토링(동작을 바꾸지 않고 구조를 개선), 작은 릴리즈 정도다.

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> "XP의 핵심 가치가 아닌 것은?" 보기: ① 용기 ② 피드백 ③ 정형 분석 ④ 단순성. 정답은 ③이다. 다섯 가치(용기, 단순성, 의사소통, 피드백, 존중)를 이름 그대로 외워 두면 바로 고를 수 있다.

| 헷갈리는 짝       | 구분 기준                                                                      |
| ----------------- | ------------------------------------------------------------------------------ |
| 구조적 ↔ 정보공학 | 구조적은 기능(DFD), 정보공학은 데이터(ERD) 중심                                |
| 객체지향 ↔ CBD    | 객체지향은 클래스 단위 설계, CBD는 배포 가능한 컴포넌트를 조립                 |
| 스크럼 ↔ XP       | 스크럼은 관리 방식(역할·회의·스프린트), XP는 개발 기술 실천(짝 프로그래밍·TDD) |

## 소프트웨어 비용 산정

### 비용 산정의 분류

**비용 산정**은 소프트웨어를 개발하는 데 필요한 인원, 기간, 돈을 미리 예측하는 작업이다. 너무 적게 잡으면 프로젝트가 적자가 나거나 품질이 떨어지고, 너무 많이 잡으면 수주 경쟁에서 진다. 산정 기법은 크게 두 갈래로 나뉜다.

| 분류   | 방식                                                       | 기법                                                |
| ------ | ---------------------------------------------------------- | --------------------------------------------------- |
| 하향식 | 경험 많은 전문가의 판단으로 전체 비용을 먼저 정하고 나눈다 | 전문가 감정 기법, 델파이 기법                       |
| 상향식 | 세부 작업 단위의 비용을 계산해 합한다                      | LOC 기법, 개발 단계별 인월수 기법, 수학적 산정 기법 |

**델파이 기법**은 전문가 감정 기법의 약점(한 사람의 편견)을 보완하려고, 여러 전문가가 서로 얼굴을 보지 않고 조정자를 통해 의견을 주고받으며 추정치를 좁혀 가는 방법이다. **수학적 산정 기법**(경험적·실험적 추정 모형)은 과거 프로젝트 자료로 만든 공식에 값을 넣어 계산하며, COCOMO, Putnam, FP가 여기에 속한다.

### 비용 산정에 쓰는 기본 단위

계산 문제를 풀기 전에 단위를 정리한다.

| 기호·단위 | 뜻                                                           | 예                  |
| --------- | ------------------------------------------------------------ | ------------------- |
| LOC       | Lines Of Code, 원시 코드 줄 수                               | 36,000줄            |
| KDSI      | Kilo Delivered Source Instructions, 인도된 코드 1,000줄 단위 | 36,000줄 = 36KDSI   |
| MM(인월)  | Man-Month, 한 사람이 한 달 동안 하는 일의 양                 | 10명이 3개월 = 30MM |
| 생산성    | 한 사람이 한 달에 작성하는 코드 줄 수                        | 300줄/MM            |

### LOC 기법

**LOC 기법**은 각 기능의 코드 줄 수를 낙관치(가장 적게 나올 경우), 기대치(가장 그럴듯한 경우), 비관치(가장 많이 나올 경우)로 추정한 뒤, 가중 평균으로 예측치를 구하고 이를 바탕으로 노력과 비용을 계산한다.

**예제**: 어떤 시스템의 코드 줄 수를 낙관치 30,000줄, 기대치 36,000줄, 비관치 42,000줄로 추정했다. 개발자 1인의 월평균 생산성은 300줄, 1인당 월 인건비는 600만 원이고 10명을 투입한다.

| 기호 | 뜻                      | 값       |
| ---- | ----------------------- | -------- |
| $a$  | 낙관치                  | 30,000줄 |
| $m$  | 기대치                  | 36,000줄 |
| $b$  | 비관치                  | 42,000줄 |
| $p$  | 1인당 월평균 생산 줄 수 | 300줄    |
| $c$  | 1인당 월 인건비         | 600만 원 |
| $n$  | 투입 인원               | 10명     |

1. 세 추정치에 가중치 1:4:1을 주어 예측 LOC를 구한다.

```math
\text{LOC} = \frac{a + 4m + b}{6} = \frac{30{,}000 + 4 \times 36{,}000 + 42{,}000}{6} = 36{,}000
```

2. 예측 LOC를 1인당 생산성으로 나누어 노력(인월)을 구한다.

```math
\text{노력} = \frac{\text{LOC}}{p} = \frac{36{,}000}{300} = 120\ \text{MM}
```

3. 노력에 단위 비용을 곱해 개발 비용을, 투입 인원으로 나누어 개발 기간을 구한다.

```math
\begin{aligned}
\text{개발 비용} &= 120 \times 600\text{만 원} = 72{,}000\text{만 원} \\
\text{개발 기간} &= \frac{120}{10} = 12\ \text{개월}
\end{aligned}
```

| 결과               | 값           |
| ------------------ | ------------ |
| 예측 LOC           | 36,000줄     |
| 노력               | 120MM        |
| 개발 비용          | 7억 2천만 원 |
| 개발 기간          | 12개월       |
| 생산성(LOC ÷ 노력) | 300줄/MM     |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> "LOC 36,000, 개발자 10명, 1인당 월 300줄이면 개발 기간은?" 같은 문제가 거의 같은 형태로 반복된다. 노력 = LOC ÷ 생산성, 기간 = 노력 ÷ 인원 두 줄만 기억하면 된다.

### COCOMO 모형

**COCOMO**(COnstructive COst MOdel)는 1981년 배리 보엠(Barry Boehm)이 TRW사의 프로젝트 자료를 분석해 발표한 비용 산정 모형이다. 예측한 코드 규모(KDSI)를 소프트웨어 유형별 공식에 넣어 노력(MM)과 기간을 계산한다.

COCOMO는 소프트웨어를 세 가지 개발 유형으로 나눈다.

| 유형                    | 성격                                       | 시험에서 쓰는 규모 기준 | 예                                     |
| ----------------------- | ------------------------------------------ | ----------------------- | -------------------------------------- |
| 조직형(Organic)         | 경험 많은 소규모 팀이 익숙한 환경에서 개발 | 5만 줄(50KDSI) 이하     | 사무 처리, 업무용, 과학 계산 응용      |
| 반분리형(Semi-detached) | 조직형과 내장형의 중간                     | 30만 줄(300KDSI) 이하   | 운영체제, DBMS, 컴파일러 같은 유틸리티 |
| 내장형(Embedded)        | 하드웨어·규정 같은 엄격한 제약 아래 개발   | 30만 줄 초과            | 신호기 제어, 미사일 유도, 실시간 처리  |

보엠의 원래 정의는 규모보다 팀 경험, 요구사항의 엄격함, 하드웨어 제약 같은 개발 환경으로 유형을 나눈다. 시험에서는 위 표의 규모 기준과 예시로 유형을 고르는 문제가 대부분이다.

COCOMO에는 정밀도에 따라 세 가지 단계가 있다.

| 단계                 | 계산 방식                                                        |
| -------------------- | ---------------------------------------------------------------- |
| 기본형(Basic)        | 규모(KDSI)와 유형만으로 계산                                     |
| 중간형(Intermediate) | 기본형에 15가지 비용 승수(제품·컴퓨터·인력·프로젝트 특성)를 곱함 |
| 발전형(Detailed)     | 중간형의 승수를 개발 단계별로 따로 적용                          |

1995년 이후에는 객체 점수·기능 점수를 입력으로 받는 COCOMO II가 나왔지만, 필기에서는 기본형의 세 유형과 중간형·발전형의 이름 정도를 묻는다.

**예제**: 규모 30KDSI인 소프트웨어를 기본형 COCOMO의 세 유형으로 각각 계산해 비교한다.

| 기호   | 뜻                      | 조직형    | 반분리형  | 내장형    |
| ------ | ----------------------- | --------- | --------- | --------- |
| $E$    | 노력(MM)                |           |           |           |
| $D$    | 개발 기간(개월)         |           |           |           |
| $a, b$ | 노력 공식의 계수와 지수 | 2.4, 1.05 | 3.0, 1.12 | 3.6, 1.20 |
| $d$    | 기간 공식의 지수        | 0.38      | 0.35      | 0.32      |

1. 노력은 규모의 거듭제곱에 계수를 곱해 구한다. 조직형이면 다음과 같다.

```math
E = a \times (\text{KDSI})^{b} = 2.4 \times 30^{1.05} \approx 85.3\ \text{MM}
```

2. 기간은 노력의 거듭제곱에 2.5를 곱해 구한다.

```math
D = 2.5 \times E^{d} = 2.5 \times 85.3^{0.38} \approx 13.5\ \text{개월}
```

3. 평균 투입 인원은 노력을 기간으로 나눈다.

```math
N = \frac{E}{D} = \frac{85.3}{13.5} \approx 6.3\ \text{명}
```

같은 방법으로 세 유형을 계산하면 다음과 같다(파이썬으로 계산한 값을 소수 첫째 자리에서 반올림).

| 유형     | 노력 $E$ | 기간 $D$ | 평균 인원 $N$ |
| -------- | -------- | -------- | ------------- |
| 조직형   | 85.3MM   | 13.5개월 | 6.3명         |
| 반분리형 | 135.4MM  | 13.9개월 | 9.7명         |
| 내장형   | 213.2MM  | 13.9개월 | 15.3명        |

![30KDSI를 세 유형으로 계산하면 노력은 85.3, 135.4, 213.2인월로 커지고 기간은 13~14개월로 비슷하다](./images/eip-system-management-cocomo-modes.svg '제약이 엄격한 유형일수록 같은 규모에도 노력(인월)이 크게 늘어난다')

==같은 30,000줄이라도 내장형은 조직형의 2.5배에 가까운 노력이 든다==. 하드웨어 제약과 엄격한 요구사항 때문에 설계·검증에 드는 시간이 늘어나기 때문이다.

### Putnam 모형

**Putnam 모형**은 1978년 로렌스 퍼트넘(Lawrence Putnam)이 제안한 모형으로, 소프트웨어 생명 주기 전체에 걸쳐 노력이 시간에 따라 어떻게 분포하는지를 예측한다. 그래서 **생명 주기 예측 모형**이라고도 부른다. 노력 분포는 **Rayleigh-Norden 곡선**을 따른다고 가정한다. 프로젝트 초반에는 인원이 적다가 구현·시험 단계에서 정점에 이르고, 이후 유지보수 단계까지 서서히 줄어드는 모양이다.

![투입 인원이 서서히 늘어 납기 무렵 정점에 이르고 이후 길게 줄어드는 Rayleigh-Norden 곡선](./images/eip-system-management-putnam.svg 'Putnam 모형은 노력의 총량뿐 아니라 시간에 따른 분포를 예측한다')

Putnam 모형은 대형 프로젝트의 노력 분포 예측에 쓰이고, 이 모형을 자동화한 도구가 **SLIM**이다.

### 기능 점수(FP) 모형

**기능 점수**(Function Point, FP) 모형은 1979년 IBM의 앨런 앨브레히트(Allan Albrecht)가 제안했다. 코드 줄 수는 프로그래밍 언어에 따라 크게 달라지고 개발이 끝나야 정확히 알 수 있다는 문제가 있다. 기능 점수는 대신 ==사용자 입장에서 시스템이 제공하는 기능의 양==을 측정하므로, 요구사항만 정해지면 언어와 관계없이 규모를 추정할 수 있다. 현재는 IFPUG(국제 기능 점수 사용자 그룹)가 측정 규칙을 관리하며 ISO/IEC 20926으로 표준화되어 있다.

기능은 다섯 유형으로 나눈다.

| 유형 | 이름                                    | 뜻                                                    | 예(도서관 시스템)            |
| ---- | --------------------------------------- | ----------------------------------------------------- | ---------------------------- |
| EI   | 외부 입력(External Input)               | 경계 밖에서 들어와 내부 파일을 바꾸는 처리            | 회원 등록, 도서 대출 처리    |
| EO   | 외부 출력(External Output)              | 계산·가공을 거쳐 밖으로 내보내는 처리                 | 월별 연체료 통계 보고서      |
| EQ   | 외부 조회(External inQuiry)             | 가공 없이 조회 결과를 내보내는 처리                   | 도서 검색                    |
| ILF  | 내부 논리 파일(Internal Logical File)   | 이 시스템이 관리하는 데이터 묶음                      | 회원, 도서, 대출 기록        |
| EIF  | 외부 연계 파일(External Interface File) | 다른 시스템이 관리하고 이 시스템은 참조만 하는 데이터 | 본인 인증 기관의 사용자 정보 |

![애플리케이션 경계를 기준으로 EI는 들어오고 EO와 EQ는 나가며, ILF는 안에, EIF는 밖에 있다](./images/eip-system-management-fp-components.svg '기능 점수는 경계를 넘나드는 거래 기능과 경계 안팎의 데이터 기능으로 나누어 집계한다')

각 기능은 복잡도(관련 데이터 항목 수 등)에 따라 단순·보통·복잡으로 나뉘고, 유형과 복잡도별 가중치가 정해져 있다.

| 유형 | 단순 | 보통 | 복잡 |
| ---- | ---- | ---- | ---- |
| EI   | 3    | 4    | 6    |
| EO   | 4    | 5    | 7    |
| EQ   | 3    | 4    | 6    |
| ILF  | 7    | 10   | 15   |
| EIF  | 5    | 7    | 10   |

**예제**: 도서관 시스템의 기능을 집계했더니 아래 표의 개수가 나왔다. 14가지 일반 시스템 특성(데이터 통신, 성능, 온라인 갱신 등)을 각각 0~5점으로 평가한 합계(총 영향도)는 42점이다.

| 기호 | 뜻                                                              |
| ---- | --------------------------------------------------------------- |
| UFP  | 조정 전 기능 점수(Unadjusted FP), 가중치 × 개수의 합            |
| TDI  | 총 영향도(Total Degree of Influence), 14개 특성 점수의 합(0~70) |
| VAF  | 가치 조정 인자(Value Adjustment Factor)                         |
| AFP  | 조정된 기능 점수                                                |

1. 유형별로 개수에 가중치를 곱해 더한다.

| 유형 | 단순 | 보통 | 복잡 | 계산            | 소계 |
| ---- | ---- | ---- | ---- | --------------- | ---- |
| EI   | 2개  | 3개  | 1개  | 2×3 + 3×4 + 1×6 | 24   |
| EO   | 1개  | 2개  | 1개  | 1×4 + 2×5 + 1×7 | 21   |
| EQ   | 3개  | 1개  | 0개  | 3×3 + 1×4       | 13   |
| ILF  | 1개  | 2개  | 0개  | 1×7 + 2×10      | 27   |
| EIF  | 1개  | 0개  | 0개  | 1×5             | 5    |

```math
\text{UFP} = 24 + 21 + 13 + 27 + 5 = 90
```

2. 총 영향도로 가치 조정 인자를 구한다. TDI가 0이면 0.65, 70이면 1.35이므로 조정 범위는 ±35%다.

```math
\text{VAF} = 0.65 + 0.01 \times \text{TDI} = 0.65 + 0.01 \times 42 = 1.07
```

3. 조정 전 점수에 조정 인자를 곱한다.

```math
\text{AFP} = \text{UFP} \times \text{VAF} = 90 \times 1.07 = 96.3
```

| 결과              | 값     |
| ----------------- | ------ |
| 조정 전 기능 점수 | 90     |
| 가치 조정 인자    | 1.07   |
| 조정된 기능 점수  | 96.3FP |

이렇게 얻은 FP에 조직의 과거 자료(예: 1FP당 0.5MM)를 곱하면 노력을 추정할 수 있다. 필기에서는 계산보다는 "기능 점수 산정에 쓰는 요소가 아닌 것"(보기에 코드 줄 수, 프로그래머 경력 같은 항목이 섞여 나온다)이나 FP 기반 자동화 도구인 **ESTIMACS**를 묻는 경우가 많다.

| 헷갈리는 짝     | 구분                                                                      |
| --------------- | ------------------------------------------------------------------------- |
| SLIM ↔ ESTIMACS | SLIM은 Putnam 모형 기반, ESTIMACS는 FP 모형 기반 자동화 도구              |
| EO ↔ EQ         | 출력에 계산·가공(합계, 통계)이 있으면 EO, 저장된 값을 그대로 보여 주면 EQ |
| ILF ↔ EIF       | 이 시스템이 데이터를 추가·수정하면 ILF, 참조만 하면 EIF                   |

## 일정 관리

### 작업 분할과 네트워크 도표

비용을 정한 뒤에는 일정을 세운다. 먼저 **WBS**(Work Breakdown Structure, 작업 분할 구조도)로 프로젝트 전체를 관리할 수 있는 크기의 작업으로 쪼갠다. 그다음 작업 사이의 선후 관계(어떤 작업이 끝나야 다음 작업을 시작할 수 있는지)를 화살표로 이어 **네트워크 도표**를 그린다. 네트워크 도표로 일정을 계산하는 대표 기법이 PERT와 CPM이다.

| 기법                   | 작업 기간                  | 주 용도                                   |
| ---------------------- | -------------------------- | ----------------------------------------- |
| PERT                   | 낙관치·기대치·비관치 세 값 | 처음 해 보는 연구 개발형 프로젝트         |
| CPM                    | 하나의 확정된 값           | 반복 경험이 있는 프로젝트, 임계 경로 계산 |
| 간트 차트(Gantt Chart) | 막대 길이로 표시           | 일정 진행 현황을 한눈에 공유              |

### PERT의 기대 시간

PERT는 1950년대 미 해군의 폴라리스 미사일 개발에서 쓰인 기법이다. 처음 하는 작업은 기간을 확신할 수 없으므로 세 값을 추정한다.

| 기호 | 뜻                             | 예   |
| ---- | ------------------------------ | ---- |
| $o$  | 낙관치(모든 일이 잘 풀릴 경우) | 4일  |
| $m$  | 기대치(가장 가능성 높은 값)    | 6일  |
| $p$  | 비관치(문제가 겹칠 경우)       | 14일 |

1. 기대 시간은 기대치에 4배 가중치를 준 평균이다.

```math
t_e = \frac{o + 4m + p}{6} = \frac{4 + 24 + 14}{6} = 7\ \text{일}
```

2. 불확실성의 크기는 표준편차와 분산으로 나타낸다.

```math
\sigma = \frac{p - o}{6} = \frac{14 - 4}{6} \approx 1.67,\quad \sigma^2 \approx 2.78
```

| 결과      | 값        |
| --------- | --------- |
| 기대 시간 | 7일       |
| 표준편차  | 약 1.67일 |
| 분산      | 약 2.78   |

기대치가 6일인데 기대 시간이 7일로 늘어난 이유는 비관치(14일)가 기대치에서 멀리 떨어져 있기 때문이다. LOC 기법의 예측치 공식과 PERT의 기대 시간 공식은 같은 모양(1:4:1 가중 평균)이다.

### CPM과 임계 경로

**임계 경로**(Critical Path)는 시작부터 끝까지 이어지는 경로 가운데 ==소요 기간의 합이 가장 긴 경로==다. 프로젝트는 가장 긴 경로가 끝나야 완료되므로, 임계 경로 위의 작업이 하루 늦어지면 프로젝트 전체가 하루 늦어진다. 임계 경로에 없는 작업은 그만큼 늦어져도 되는 **여유 시간**(Slack, Float)이 있다.

**예제**: 다음 여섯 작업으로 이루어진 프로젝트의 임계 경로와 전체 기간을 구한다.

| 작업 | 기간 | 선행 작업 |
| ---- | ---- | --------- |
| A    | 4일  | 없음      |
| B    | 3일  | 없음      |
| C    | 5일  | A         |
| D    | 6일  | A, B      |
| E    | 4일  | C         |
| F    | 3일  | D, E      |

| 기호 | 뜻                                               |
| ---- | ------------------------------------------------ |
| ES   | 가장 빠른 시작 시각(Earliest Start)              |
| EF   | 가장 빠른 종료 시각(Earliest Finish) = ES + 기간 |
| LS   | 가장 늦은 시작 시각(Latest Start) = LF − 기간    |
| LF   | 가장 늦은 종료 시각(Latest Finish)               |
| 여유 | LS − ES                                          |

1. **전진 계산**: 앞에서부터 ES와 EF를 구한다. 선행 작업이 여럿이면 그중 가장 늦은 EF가 ES가 된다.

```math
\begin{aligned}
\text{A}&: 0 \to 4,\quad \text{B}: 0 \to 3,\quad \text{C}: 4 \to 9 \\
\text{D}&: \max(4, 3) = 4 \to 10,\quad \text{E}: 9 \to 13 \\
\text{F}&: \max(10, 13) = 13 \to 16
\end{aligned}
```

2. **후진 계산**: 마지막 작업의 LF를 전체 기간(16일)으로 두고 뒤에서부터 LS와 LF를 구한다. 후행 작업이 여럿이면 그중 가장 이른 LS가 LF가 된다.

```math
\begin{aligned}
\text{F}&: 13 \leftarrow 16,\quad \text{E}: 9 \leftarrow 13,\quad \text{D}: 7 \leftarrow 13 \\
\text{C}&: 4 \leftarrow 9,\quad \text{B}: 4 \leftarrow 7,\quad \text{A}: \min(4, 7) = 0 \leftarrow 4
\end{aligned}
```

3. 여유가 0인 작업을 이으면 임계 경로다.

| 작업 | ES  | EF  | LS  | LF  | 여유 | 임계 |
| ---- | --- | --- | --- | --- | ---- | ---- |
| A    | 0   | 4   | 0   | 4   | 0    | ○    |
| B    | 0   | 3   | 4   | 7   | 4    |      |
| C    | 4   | 9   | 4   | 9   | 0    | ○    |
| D    | 4   | 10  | 7   | 13  | 3    |      |
| E    | 9   | 13  | 9   | 13  | 0    | ○    |
| F    | 13  | 16  | 13  | 16  | 0    | ○    |

이 표는 파이썬으로 전진·후진 계산을 실행해 확인한 값이다. 임계 경로는 **A → C → E → F**, 전체 기간은 **16일**이다.

![A, C, E, F가 빨간 선으로 이어진 임계 경로이고 B와 D에는 여유가 있다](./images/eip-system-management-cpm.svg '노드마다 ES·EF·LS·LF를 적으면 여유가 0인 작업이 임계 경로가 된다')

> [!TIP] 빠르게 푸는 방법
> 시험에 나오는 네트워크는 경로가 3~5개 정도다. 시작에서 끝까지 가능한 경로를 모두 적고 기간을 더하면 가장 큰 값이 임계 경로다. 이 예제의 경로는 A-C-E-F(16일), A-D-F(13일), B-D-F(12일) 세 개이므로 답은 16일이다.

### 간트 차트

**간트 차트**는 1910년대 헨리 간트(Henry Gantt)가 고안한 막대 그래프로, 가로축을 시간으로 두고 작업마다 시작 시각부터 종료 시각까지 막대를 그린다. 누가 언제 무엇을 하는지, 지금 어느 작업이 진행 중인지 한눈에 보여 주어 진행 상황 보고에 많이 쓴다. 반면 작업 사이의 선후 관계는 잘 드러나지 않으므로, 선후 관계 분석은 네트워크 도표로 하고 결과를 간트 차트로 공유하는 경우가 많다.

![같은 여섯 작업을 0일부터 16일까지 막대로 그린 간트 차트](./images/eip-system-management-gantt.svg 'CPM으로 구한 ES를 막대의 시작으로 두고, 여유 시간을 점선으로 덧붙였다')

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> "간트 차트에 대한 설명으로 틀린 것은?" 같은 문제에서 "작업 간의 상호 관련성을 명확히 보여 준다"가 틀린 보기로 나온다. 간트 차트는 이정표, 기간, 작업 진행 상황을 보여 주지만 선후 관계 표현은 약하다.

## 프로세스 표준

### ISO/IEC 12207

**ISO/IEC 12207**은 소프트웨어의 획득부터 공급, 개발, 운영, 유지보수까지 생명 주기 전체에서 수행할 프로세스를 정의한 국제 표준이다. 1995년판의 분류가 시험에 나온다.

| 분류                    | 프로세스                                                             |
| ----------------------- | -------------------------------------------------------------------- |
| 기본 생명 주기 프로세스 | 획득, 공급, 개발, 운영, 유지보수                                     |
| 지원 생명 주기 프로세스 | 문서화, 형상 관리, 품질 보증, 검증, 확인, 합동 검토, 감사, 문제 해결 |
| 조직 생명 주기 프로세스 | 관리, 기반 구조, 개선, 교육 훈련                                     |

### CMMI

**CMMI**(Capability Maturity Model Integration)는 미국 카네기멜런 대학교 소프트웨어 공학 연구소(SEI)가 만든 모델로, 소프트웨어 개발 조직의 프로세스가 얼마나 성숙했는지를 다섯 단계로 평가한다. 공공 사업 입찰에서 CMMI 3단계 이상을 요구하는 경우가 있어, 기업이 인증을 받는 목표로 쓰인다.

![1 초기, 2 관리, 3 정의, 4 정량적 관리, 5 최적화로 올라가는 계단](./images/eip-system-management-cmmi.svg '단계가 올라갈수록 개인의 역량보다 조직의 표준과 수치 관리에 의존한다')

| 단계 | 이름                                | 상태                                                       |
| ---- | ----------------------------------- | ---------------------------------------------------------- |
| 1    | 초기(Initial)                       | 정해진 프로세스가 없어 성공 여부가 개인 역량에 달림        |
| 2    | 관리(Managed)                       | 프로젝트마다 계획을 세우고 진행을 추적함                   |
| 3    | 정의(Defined)                       | 조직 공통의 표준 프로세스를 정하고 프로젝트가 이를 맞춰 씀 |
| 4    | 정량적 관리(Quantitatively Managed) | 품질과 성과를 수치로 측정해 통제함                         |
| 5    | 최적화(Optimizing)                  | 측정 결과로 프로세스를 지속적으로 개선함                   |

### SPICE

**SPICE**(Software Process Improvement and Capability dEtermination)는 소프트웨어 프로세스를 평가하고 개선하기 위한 국제 표준으로, 공식 명칭은 **ISO/IEC 15504**다. 2015년부터 ISO/IEC 330xx 시리즈로 이어졌지만 시험에서는 15504라는 번호와 SPICE라는 이름을 짝지어 묻는다.

SPICE는 프로세스를 다섯 범주(고객-공급자, 공학, 지원, 관리, 조직)로 나누고, 각 프로세스의 능력을 여섯 단계로 평가한다.

| 수준 | 이름               | 뜻                                                |
| ---- | ------------------ | ------------------------------------------------- |
| 0    | 불완전(Incomplete) | 프로세스가 구현되지 않았거나 목적을 달성하지 못함 |
| 1    | 수행(Performed)    | 프로세스를 수행해 목적을 달성함                   |
| 2    | 관리(Managed)      | 정해진 자원 안에서 작업 산출물을 관리함           |
| 3    | 확립(Established)  | 표준 프로세스를 정의하고 사용함                   |
| 4    | 예측(Predictable)  | 정해진 한계 안에서 일관되게 수행됨                |
| 5    | 최적화(Optimizing) | 사업 목표에 맞게 지속적으로 개선함                |

| 헷갈리는 짝              | 구분                                                        |
| ------------------------ | ----------------------------------------------------------- |
| CMMI ↔ SPICE             | CMMI는 1~5단계(초기부터), SPICE는 0~5단계(불완전부터)       |
| CMMI 3단계 ↔ SPICE 3수준 | CMMI는 정의(Defined), SPICE는 확립(Established)             |
| CMMI 4단계 ↔ SPICE 4수준 | CMMI는 정량적 관리, SPICE는 예측                            |
| ISO/IEC 12207 ↔ 15504    | 12207은 생명 주기 프로세스 정의, 15504는 프로세스 능력 평가 |

> [!NOTE] 소프트웨어 개발 프레임워크
> 같은 영역에서 **소프트웨어 개발 프레임워크**의 특성(모듈화, 재사용성, 확장성, 제어의 역흐름)도 자주 나온다. **제어의 역흐름**(IoC, Inversion of Control)은 개발자가 작성한 코드가 프레임워크를 호출하는 대신, 프레임워크가 필요한 시각에 개발자의 코드를 호출하는 구조를 말한다. 국내 공공 사업에서 쓰는 **전자정부 프레임워크**는 스프링(Spring) 기반이다.

## 네트워크 구축

### 토폴로지

**토폴로지**(Topology, 망 구성 형태)는 컴퓨터와 통신 장비를 회선으로 연결하는 모양이다. 형태에 따라 장애가 생긴 경우의 영향 범위, 필요한 회선 수, 확장 방법이 달라진다.

![성형, 링형, 버스형, 계층형, 망형 다섯 가지 연결 모양](./images/eip-system-management-topology.svg '주황색 점은 중앙 장비, 망형은 모든 노드가 서로 직접 연결된다')

| 형태         | 연결 방식                        | 장점                                    | 단점                                             |
| ------------ | -------------------------------- | --------------------------------------- | ------------------------------------------------ |
| 성형(Star)   | 중앙 장비에 모든 단말을 연결     | 단말 추가·장애 위치 파악이 쉬움         | 중앙 장비 고장 시 전체 중단                      |
| 링형(Ring)   | 이웃한 노드끼리 원형으로 연결    | 데이터 충돌이 없음                      | 노드 하나의 고장이 전체에 영향(이중 링으로 보완) |
| 버스형(Bus)  | 회선 하나에 여러 노드를 연결     | 설치가 간단하고 저렴                    | 트래픽이 많으면 충돌로 성능 저하                 |
| 계층형(Tree) | 중앙에서 가지가 뻗어 나가는 형태 | 분산 처리에 유리                        | 상위 노드 장애가 하위 전체에 영향                |
| 망형(Mesh)   | 모든 노드를 서로 직접 연결       | 한 경로가 끊겨도 우회 가능, 신뢰성 높음 | 회선이 많이 필요해 비용이 큼                     |

망형은 노드가 $n$개이면 회선 $n(n-1)/2$개, 노드당 포트 $n-1$개가 필요하다. 노드 5개면 회선 $5 \times 4 / 2 = 10$개, 포트는 노드당 4개다. 이 계산은 필기에서 숫자만 바꿔 자주 나온다.

### 네트워크 장비와 계층

| 장비          | OSI 계층      | 하는 일                                                |
| ------------- | ------------- | ------------------------------------------------------ |
| 리피터        | 1 물리        | 약해진 신호를 재생해 전송 거리를 늘림                  |
| 허브          | 1 물리        | 여러 회선을 묶음, 받은 신호를 모든 포트로 보냄         |
| 브리지·스위치 | 2 데이터 링크 | MAC 주소를 보고 해당 포트로만 프레임을 보냄            |
| 라우터        | 3 네트워크    | IP 주소를 보고 최적 경로를 선택해 다른 네트워크로 전달 |
| 게이트웨이    | 4~7 상위      | 프로토콜 구조가 다른 네트워크를 연결                   |

OSI 7계층, 프로토콜, 라우팅의 자세한 내용은 [실기 대비 보안·네트워크·신기술 용어 글](/memo/eip-practical-security-network)에서 이어서 다룬다.

### 무선 LAN과 근거리 통신

| 규격·기술   | 특징                                                                   |
| ----------- | ---------------------------------------------------------------------- |
| IEEE 802.3  | 유선 이더넷, CSMA/CD(충돌 감지)                                        |
| IEEE 802.11 | 무선 LAN, CSMA/CA(충돌 회피)                                           |
| IEEE 802.15 | 무선 개인 영역 네트워크(WPAN). 블루투스, 지그비(ZigBee, 저전력 센서망) |
| NFC         | 약 10cm 이내 근거리 무선 통신, 교통카드·모바일 결제                    |
| UWB         | 초광대역 무선, 짧은 거리에서 위치를 정밀하게 측정                      |

무선 LAN 규격은 버전에 따라 주파수와 최고 속도가 다르다. 802.11b는 2.4GHz·11Mbps, 802.11a는 5GHz·54Mbps, 802.11g는 2.4GHz·54Mbps, 802.11n은 2.4GHz와 5GHz를 함께 쓰고 최고 600Mbps다. 802.11e는 속도가 아니라 QoS(서비스 품질) 기능을 더한 부가 규격이다.

## 신기술 용어

5과목에서 가장 넓은 영역이다. 회차마다 새로운 용어가 한두 개씩 나오지만, 반복해서 나오는 용어가 더 많다. 분야별로 묶어 정리한다.

### 클라우드와 가상화

미국 국립표준기술연구소(NIST)는 2011년 SP 800-145에서 **클라우드 컴퓨팅**을 "구성 가능한 컴퓨팅 자원의 공유 풀에 네트워크로 언제든 편리하게 접근하고, 최소한의 관리로 빠르게 할당·반납할 수 있게 하는 모델"로 정의했다. 정의에는 다섯 가지 필수 특성(주문형 셀프서비스, 광범위한 네트워크 접근, 자원 풀링, 신속한 탄력성, 측정되는 서비스), 세 가지 서비스 모델, 네 가지 배치 모델(사설, 커뮤니티, 공용, 하이브리드)이 들어 있다.

![온프레미스, IaaS, PaaS, SaaS로 갈수록 사용자가 관리하는 층이 줄어든다](./images/eip-system-management-cloud.svg '파란 칸이 사용자가 직접 관리하는 범위다')

| 서비스 모델                       | 사업자가 제공하는 것           | 사용자가 관리하는 것          | 예                        |
| --------------------------------- | ------------------------------ | ----------------------------- | ------------------------- |
| IaaS(Infrastructure as a Service) | 서버·스토리지·네트워크, 가상화 | 운영체제부터 애플리케이션까지 | AWS EC2                   |
| PaaS(Platform as a Service)       | IaaS + 운영체제, 런타임        | 애플리케이션과 데이터         | Heroku, Google App Engine |
| SaaS(Software as a Service)       | 완성된 소프트웨어              | 설정과 사용                   | Gmail, Microsoft 365      |

| 용어                     | 뜻                                             |
| ------------------------ | ---------------------------------------------- |
| 하이퍼바이저(Hypervisor) | 물리 서버에서 여러 가상 머신을 실행            |
| 도커(Docker)             | 커널을 공유하는 컨테이너로 애플리케이션 배포   |
| 쿠버네티스(Kubernetes)   | 컨테이너 배포·확장·복구 자동화(오케스트레이션) |
| 서버리스(Serverless)     | 서버 관리 없이 함수 단위로 실행·과금           |
| 멀티 클라우드            | 여러 클라우드 사업자의 서비스를 함께 사용      |

### 네트워크 신기술

| 용어                                  | 뜻                                                    |
| ------------------------------------- | ----------------------------------------------------- |
| SDN(Software Defined Networking)      | 제어 기능을 분리해 중앙 소프트웨어로 네트워크를 제어  |
| NFV(Network Functions Virtualization) | 네트워크 기능을 범용 서버의 소프트웨어로 실행         |
| SDDC(Software Defined Data Center)    | 모든 자원을 가상화해 소프트웨어로 관리하는 데이터센터 |
| 메시 네트워크(Mesh Network)           | 노드가 그물처럼 연결되어 경로를 스스로 찾는 망        |
| 애드 혹 네트워크(Ad-hoc Network)      | 고정 기반 없이 이동 단말끼리 임시로 구성하는 망       |
| 피코넷(Piconet)                       | 블루투스·UWB로 여러 장치를 묶은 소규모 무선망         |
| IoT(Internet of Things)               | 사물에 센서와 통신 기능을 넣어 인터넷으로 연결        |

## 소프트웨어 개발 보안 구축

### 보안의 3대 요소

정보 보안의 목표는 세 가지로 요약하며, 영문 앞 글자를 따서 **CIA**라고 부른다.

| 요소                    | 뜻                                              | 침해 예             |
| ----------------------- | ----------------------------------------------- | ------------------- |
| 기밀성(Confidentiality) | 인가된 사용자만 정보를 볼 수 있음               | 도청, 개인정보 유출 |
| 무결성(Integrity)       | 인가된 사용자만 정보를 수정할 수 있음           | 데이터 변조         |
| 가용성(Availability)    | 인가된 사용자가 필요한 시각에 정보를 쓸 수 있음 | 서비스 거부 공격    |

여기에 사용자가 본인임을 확인하는 **인증**(Authentication)과, 보내거나 받은 사실을 나중에 부인하지 못하게 하는 **부인 방지**(Non-repudiation)를 더하기도 한다.

### Secure SDLC

**Secure SDLC**는 소프트웨어 개발 생명 주기(요구사항 분석, 설계, 구현, 테스트, 유지보수)의 각 단계에 보안 활동을 넣어, 출시 후에 취약점을 고치는 대신 처음부터 안전하게 만드는 방법이다. 결함을 발견하는 단계가 늦을수록 고치는 비용이 커지기 때문에, 요구사항 단계에서 보안 요구사항을 정의하고 설계 단계에서 위협 모델링을 하는 편이 경제적이다.

| 방법론                                 | 만든 곳              | 특징                                                                    |
| -------------------------------------- | -------------------- | ----------------------------------------------------------------------- |
| MS SDL(Security Development Lifecycle) | 마이크로소프트       | 교육부터 대응까지 단계별 보안 활동, 위협 모델링                         |
| Seven Touchpoints                      | 게리 맥그로(Cigital) | 코드 검토, 위험 분석, 침투 테스트 등 7가지 보안 실천을 생명 주기에 대응 |
| CLASP                                  | OWASP                | 활동 중심·역할 기반, 이미 운영 중인 조직에 적용하기 쉬움                |

### 시큐어 코딩 7대 항목

**시큐어 코딩**(Secure Coding)은 구현 단계에서 보안 약점(취약점이 될 수 있는 코드 결함)을 만들지 않도록 하는 코딩 기법이다. 행정안전부와 한국인터넷진흥원(KISA)의 「소프트웨어 개발보안 가이드」는 구현 단계 보안 약점을 7가지 유형으로 나눈다.

| 유형                     | 내용                                             | 대표 약점                                 |
| ------------------------ | ------------------------------------------------ | ----------------------------------------- |
| 입력 데이터 검증 및 표현 | 입력값 미검증                                    | SQL 삽입, XSS, 경로 조작                  |
| 보안 기능                | 인증·접근 제어·암호화를 부적절하게 구현          | 취약한 암호 알고리즘, 하드코드된 비밀번호 |
| 시간 및 상태             | 여러 프로세스가 동시에 실행되면서 생기는 약점    | 경쟁 조건(TOCTOU), 종료되지 않는 반복문   |
| 에러 처리                | 오류를 처리하지 않거나 오류 메시지에 정보가 노출 | 오류 메시지 정보 노출, 부적절한 예외 처리 |
| 코드 오류                | 개발자의 코딩 실수                               | 널 포인터 역참조, 자원 미해제             |
| 캡슐화                   | 데이터와 기능을 불충분하게 숨겨 노출             | 디버그 코드 잔류, 시스템 데이터 정보 노출 |
| API 오용                 | 보안에 취약한 API를 사용하거나 잘못 사용         | DNS 조회 결과에 의존한 보안 결정          |

**SQL 삽입**(SQL Injection)은 입력값을 문자열로 이어 붙여 SQL 문을 만드는 코드에서 공격자가 입력에 SQL 문법을 섞어 쿼리의 의미를 바꾸는 공격이다. 다음은 파이썬과 sqlite3로 실제 실행한 예다.

```python
import sqlite3
db = sqlite3.connect(':memory:')
db.execute("CREATE TABLE users (id TEXT, pw TEXT, name TEXT)")
db.executemany("INSERT INTO users VALUES (?, ?, ?)", [('admin', 's3cret', '관리자'), ('kim', 'pw1234', '김철수')])

user_id = "admin' --"
user_pw = "아무거나"

# 취약한 방식: 입력값을 문자열로 이어 붙인다
query = "SELECT name FROM users WHERE id = '" + user_id + "' AND pw = '" + user_pw + "'"
print(query)
print(db.execute(query).fetchall())

# 안전한 방식: 입력값을 매개변수로 넘긴다
print(db.execute("SELECT name FROM users WHERE id = ? AND pw = ?", (user_id, user_pw)).fetchall())
```

```text
SELECT name FROM users WHERE id = 'admin' --' AND pw = '아무거나'
[('관리자',)]
[]
```

아이디 칸에 넣은 `'`가 문자열을 닫고, 뒤의 `--`가 SQL 주석을 시작해 비밀번호 조건 전체를 무효로 만든다. 그 결과 비밀번호를 몰라도 관리자로 로그인된다. 매개변수(`?`)로 넘기면 데이터베이스가 입력 전체를 하나의 문자열 값으로 취급하므로 일치하는 행이 없다. 이렇게 SQL 구조와 값을 분리하는 방식을 **준비된 문**(Prepared Statement) 또는 매개변수화 쿼리라고 한다.

### 암호 알고리즘

암호 알고리즘은 키를 쓰는 방식에 따라 나뉜다.

![대칭 키 암호는 같은 키 K로 암호화와 복호화를 하고, 공개 키 암호는 받는 사람의 공개 키로 암호화하고 개인 키로 복호화한다](./images/eip-system-management-crypto.svg '대칭 키는 빠르지만 키 분배가 문제이고, 공개 키는 느리지만 키를 공개해도 된다')

**대칭 키 암호**(비밀 키, 개인 키, 단일 키 암호)는 암호화와 복호화에 같은 키를 쓴다. 계산이 빨라 대량의 데이터를 암호화하는 데 쓰지만, 통신 상대와 키를 미리 안전하게 나눠 가져야 하고, $n$명이 서로 통신하려면 $n(n-1)/2$개의 키가 필요하다. 처리 단위에 따라 블록 암호와 스트림 암호로 나뉜다.

| 알고리즘 | 개발                   | 블록 크기 | 키 길이         | 비고                                      |
| -------- | ---------------------- | --------- | --------------- | ----------------------------------------- |
| DES      | 1975 미국 NBS(현 NIST) | 64비트    | 56비트          | 16라운드, 키가 짧아 현재 안전하지 않음    |
| 3DES     | DES 개선               | 64비트    | 112·168비트     | DES를 세 번 적용                          |
| AES      | 2001 미국 NIST         | 128비트   | 128·192·256비트 | 라운드 10·12·14, 현재 국제 표준           |
| SEED     | 1998 한국인터넷진흥원  | 128비트   | 128비트         | 16라운드, 국내 금융권에서 널리 사용       |
| ARIA     | 2004 한국              | 128비트   | 128·192·256비트 | 국가 표준, 라운드 12·14·16                |
| IDEA     | 1990 라이·메시         | 64비트    | 128비트         | PES를 개선                                |
| Skipjack | 미국 NSA               | 64비트    | 80비트          | 클리퍼 칩에 내장, 음성 통신 암호화        |
| RC4·LFSR |                        | 스트림    |                 | 비트·바이트 단위로 암호화하는 스트림 암호 |

**공개 키 암호**(비대칭 암호)는 서로 다른 두 키를 쓴다. 누구에게나 알려 주는 **공개 키**로 암호화하면, 짝이 되는 **개인 키**를 가진 사람만 복호화할 수 있다. 키를 미리 나눌 필요가 없고 $n$명이면 키가 $2n$개면 되지만, 계산이 느려서 실제로는 공개 키 암호로 대칭 키를 안전하게 전달한 뒤 데이터는 대칭 키로 암호화한다.

| 알고리즘            | 근거가 되는 수학 문제         | 비고                                       |
| ------------------- | ----------------------------- | ------------------------------------------ |
| RSA                 | 큰 수의 소인수분해가 어려움   | 1977년 리베스트·샤미르·애들먼(MIT)         |
| ECC(타원 곡선 암호) | 타원 곡선 위의 이산 로그 문제 | RSA보다 짧은 키로 같은 강도, 모바일에 유리 |
| ElGamal             | 이산 로그 문제                | 암호화와 전자서명                          |
| Diffie-Hellman      | 이산 로그 문제                | 키 교환 알고리즘                           |

**해시**(Hash)는 임의 길이의 입력을 고정 길이의 값으로 바꾸는 단방향 함수다. 결과값에서 원래 입력을 계산해 낼 수 없고, 입력이 1비트만 달라도 결과가 완전히 달라진다. 비밀번호 저장, 파일 무결성 검사, 전자서명에 쓴다.

| 알고리즘       | 출력 길이   | 비고                                                   |
| -------------- | ----------- | ------------------------------------------------------ |
| MD5            | 128비트     | 1991년 리베스트, 충돌이 발견되어 보안 용도로 쓰지 않음 |
| SHA-1          | 160비트     | 충돌 공격이 실증되어 사용 중단 권고                    |
| SHA-256(SHA-2) | 256비트     | 현재 널리 쓰임                                         |
| SHA-3          | 224~512비트 | 2015년 NIST 표준(Keccak)                               |
| HAS-160        | 160비트     | 국내 전자서명용 해시                                   |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> "다음 중 대칭 키 암호 알고리즘이 아닌 것은? ① AES ② SEED ③ RSA ④ ARIA" 정답은 ③이다. 공개 키 쪽은 RSA, ECC, ElGamal, Diffie-Hellman 네 개만 기억하면 나머지 블록 암호 이름은 대칭 키로 분류할 수 있다.

## 시스템 보안 구축

### 서비스 거부 공격

**서비스 거부**(DoS, Denial of Service) 공격은 대상 시스템의 자원(대역폭, 메모리, 연결 슬롯)을 고갈시켜 정상 사용자가 서비스를 쓰지 못하게 하는 공격이다. 보안 3대 요소 가운데 가용성을 침해한다.

| 공격                   | 방법                                                                         |
| ---------------------- | ---------------------------------------------------------------------------- |
| Ping of Death          | 65,535바이트를 넘는 ICMP 패킷으로 재조립 중 시스템 중단                      |
| 스머핑(Smurfing)       | 출발지를 대상 IP로 위조한 ICMP 요청을 브로드캐스트로 보내 응답을 대상에 집중 |
| SYN 플러딩             | SYN만 대량으로 보내고 ACK를 보내지 않아 연결 대기 공간을 채움                |
| 티어드롭(TearDrop)     | IP 조각의 오프셋 값을 겹치게 조작해 재조립할 수 없게 만듦                    |
| 랜드 어택(LAND Attack) | 출발지·목적지 IP를 모두 대상으로 설정해 자기 자신에게 응답하게 함            |
| UDP 플러딩             | 대량의 UDP 패킷을 보내 대역폭과 처리 자원을 소모                             |

**분산 서비스 거부**(DDoS, Distributed DoS) 공격은 악성 코드에 감염된 다수의 컴퓨터(좀비 PC)를 동원해 동시에 공격한다. 공격자는 마스터(핸들러)에 명령을 내리고, 마스터는 다시 여러 에이전트에 명령을 전달한다.

![공격자가 두 마스터에 명령하고, 각 마스터가 세 에이전트를 조종해 공격 대상으로 트래픽을 보낸다](./images/eip-system-management-ddos.svg '한 명의 공격자가 수많은 에이전트를 통해 공격하므로 출발지를 하나씩 차단하기 어렵다')

| 도구                     | 특징                                                    |
| ------------------------ | ------------------------------------------------------- |
| Trinoo                   | 가장 초기의 DDoS 도구, 주로 UDP 플러딩                  |
| TFN(Tribe Flood Network) | UDP 플러딩에 SYN 플러딩, ICMP 플러딩, 스머핑까지 수행   |
| TFN2K                    | TFN의 확장판                                            |
| Stacheldraht             | 공격자·마스터·에이전트 사이 통신을 암호화해 노출을 피함 |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> "패킷의 출발지 주소와 목적지 주소를 모두 공격 대상의 주소로 만들어 보내는 공격은?" 정답은 랜드 어택이다. 출발지를 위조한다는 점은 스머핑과 같지만, 스머핑은 브로드캐스트를 이용한 증폭, 랜드 어택은 자기 자신에게 응답하게 만드는 구조라는 점이 다르다.

### 그 밖의 공격 기법

| 공격                  | 방법                                                                   |
| --------------------- | ---------------------------------------------------------------------- |
| 스니핑(Sniffing)      | 네트워크를 지나는 패킷을 엿봄(수동적 공격)                             |
| 스푸핑(Spoofing)      | IP·MAC·DNS 정보를 위조해 다른 대상으로 위장                            |
| ARP 스푸핑            | 가짜 ARP 응답으로 트래픽을 가로챔                                      |
| 세션 하이재킹         | 인증을 마친 세션의 정보를 가로채 정상 사용자처럼 행동                  |
| 버퍼 오버플로         | 정해진 크기보다 큰 데이터를 써 넣어 인접 메모리(복귀 주소 등)를 덮어씀 |
| 백도어(Back Door)     | 정상 인증을 거치지 않고 시스템에 접근하는 비밀 통로                    |
| 랜섬웨어              | 파일을 암호화하고 복호화 대가로 돈을 요구                              |
| APT(지능형 지속 위협) | 특정 조직을 목표로 장기간 잠입해 정보를 수집하고 빼돌림                |
| 제로 데이 공격        | 취약점이 공개되거나 패치가 나오기 전에 그 취약점을 이용                |

버퍼 오버플로를 막는 기술로는 복귀 주소 앞에 특정 값(카나리)을 넣어 두고 함수가 끝나는 시각에 값이 바뀌었는지 검사하는 **스택 가드**, 스택에 복귀 주소의 복사본을 따로 보관하는 **스택 실드**, 메모리 배치를 실행할 때마다 무작위로 바꾸는 **ASLR**이 있다.

### 접근 통제

**접근 통제**(Access Control)는 사용자(주체)가 파일·데이터(객체)에 접근하려 하면 허용할지 결정하는 기능이다. 누가 권한을 정하는지에 따라 세 가지 정책으로 나뉜다.

![DAC는 소유자가 권한을 주고, MAC는 보안 등급으로 판단하며, RBAC는 역할에 권한을 묶는다](./images/eip-system-management-access-control.svg '세 정책은 권한을 결정하는 주체와 기준이 다르다')

| 정책                      | 권한 결정           | 기준                    | 예                           |
| ------------------------- | ------------------- | ----------------------- | ---------------------------- |
| DAC(임의적 접근 통제)     | 데이터 소유자       | 사용자의 신원           | 유닉스 파일 권한(chmod), ACL |
| MAC(강제적 접근 통제)     | 시스템(보안 관리자) | 주체와 객체의 보안 등급 | 군사 기밀 등급 시스템        |
| RBAC(역할 기반 접근 통제) | 중앙 관리자         | 사용자의 역할(직무)     | 회사의 부서·직급별 권한      |

MAC를 구현하는 대표 모델이 **벨-라파듈라**(Bell-LaPadula) 모델과 **비바**(Biba) 모델이다.

| 모델        | 목적   | 읽기 규칙                                  | 쓰기 규칙                                     |
| ----------- | ------ | ------------------------------------------ | --------------------------------------------- |
| 벨-라파듈라 | 기밀성 | No Read Up(자기보다 높은 등급을 읽지 못함) | No Write Down(자기보다 낮은 등급에 쓰지 못함) |
| 비바        | 무결성 | No Read Down(낮은 등급을 읽지 못함)        | No Write Up(높은 등급에 쓰지 못함)            |

벨-라파듈라는 기밀 정보가 아래로 새지 않게 막고, 비바는 신뢰도가 낮은 정보가 위로 섞여 들어가지 않게 막는다. 두 모델의 규칙은 정확히 반대 방향이다.

### 인증

**인증**은 시스템에 접근하려는 사용자가 주장하는 그 사람이 맞는지 확인하는 절차다. 확인 근거에 따라 유형을 나눈다.

| 유형                          | 근거           | 예                             |
| ----------------------------- | -------------- | ------------------------------ |
| 지식 기반(Something You Know) | 알고 있는 것   | 비밀번호, PIN                  |
| 소유 기반(Something You Have) | 가지고 있는 것 | OTP 생성기, 스마트카드, 휴대폰 |
| 생체 기반(Something You Are)  | 신체 특징      | 지문, 홍채, 얼굴               |
| 행위 기반(Something You Do)   | 행동 특징      | 서명, 키 입력 패턴             |
| 위치 기반(Somewhere You Are)  | 접속 위치      | GPS, IP 주소                   |

서로 다른 유형을 두 가지 이상 함께 쓰면 **다중 요소 인증**(MFA)이다. 비밀번호와 PIN은 둘 다 지식 기반이므로 둘을 함께 써도 다중 요소가 아니다.

### 보안 솔루션

| 솔루션                  | 하는 일                                                   |
| ----------------------- | --------------------------------------------------------- |
| 방화벽(Firewall)        | 내부·외부망 사이에서 IP·포트 규칙으로 허용·차단           |
| 침입 탐지 시스템(IDS)   | 비정상 행위를 실시간으로 탐지해 알림(오용 탐지·이상 탐지) |
| 침입 방지 시스템(IPS)   | 탐지에 그치지 않고 공격 트래픽을 직접 차단                |
| 웹 방화벽(WAF)          | SQL 삽입·XSS 같은 웹 공격 차단                            |
| VPN(가상 사설망)        | 공중망 위 암호화 터널(IPSec VPN, SSL VPN)                 |
| NAC(네트워크 접근 제어) | 단말의 백신·패치 상태를 확인한 뒤 접속 허용               |
| DLP(데이터 유출 방지)   | 메일·USB 등을 통한 내부 정보 유출 차단                    |
| SIEM                    | 여러 보안 장비의 로그와 이벤트를 수집해 통합 분석         |
| ESM(통합 보안 관리)     | 여러 보안 솔루션을 하나의 콘솔에서 관리                   |
| Secure OS               | 커널에 접근 통제·감사 기능을 넣은 운영체제                |

각 솔루션이 네트워크의 어디에 놓이는지, 실기에서 어떻게 묻는지는 [실기 대비 보안·네트워크·신기술 용어 글](/memo/eip-practical-security-network)에서 그림과 함께 다룬다.
