## 2과목은 무엇을 묻는가

## 자료구조

자료구조(Data Structure)는 데이터를 메모리에 어떤 모양으로 저장하고 어떤 방법으로 꺼낼지 정한 구조다. 같은 데이터라도 구조에 따라 검색·삽입·삭제에 걸리는 시간이 크게 달라진다.

| 분류                     | 구조                                         | 특징                                            |
| ------------------------ | -------------------------------------------- | ----------------------------------------------- |
| 선형 구조 (Linear)       | 배열, 선형 리스트(연속·연결), 스택, 큐, 데크 | 데이터가 한 줄로 앞뒤 관계를 가진다             |
| 비선형 구조 (Non-Linear) | 트리, 그래프                                 | 한 데이터가 여러 데이터와 계층·망 관계를 가진다 |

### 배열과 연결 리스트

배열(Array)은 같은 자료형의 데이터를 메모리의 연속된 공간에 저장한다. 첨자(index)로 위치를 계산할 수 있어 `a[5]` 같은 접근이 한 번에 끝나지만, 중간에 데이터를 삽입하거나 삭제하려면 뒤의 데이터를 모두 한 칸씩 옮겨야 한다. 연속 리스트(Contiguous List)도 같은 방식이다.

연결 리스트(Linked List)는 각 노드가 데이터와 다음 노드의 주소(포인터)를 함께 저장한다. 삽입과 삭제는 포인터만 바꾸면 되지만, 특정 위치의 데이터를 찾으려면 첫 노드부터 포인터를 따라가야 하고 포인터를 저장하는 공간이 추가로 필요하다.

| 비교 항목       | 배열 (연속 리스트)  | 연결 리스트                 |
| --------------- | ------------------- | --------------------------- |
| 메모리 배치     | 연속된 공간         | 흩어진 노드를 포인터로 연결 |
| k번째 원소 접근 | 바로 계산 (빠름)    | 처음부터 따라감 (느림)      |
| 중간 삽입·삭제  | 뒤 원소 이동 (느림) | 포인터 변경 (빠름)          |
| 추가 저장 공간  | 없음                | 노드마다 포인터 공간        |

### 스택

스택(Stack)은 한쪽 끝(Top)에서만 삽입과 삭제가 일어나는 구조다. ==가장 나중에 넣은 데이터가 가장 먼저 나오므로== 후입선출(LIFO, Last In First Out)이라고 한다. 삽입을 푸시(Push), 삭제를 팝(Pop)이라 부른다.

![스택과 큐의 삽입·삭제 위치](./images/eip-software-development-stack-queue.svg '스택은 Top 한 곳에서, 큐는 Rear로 넣고 Front로 꺼낸다')

스택이 가득 찼는데 푸시하면 오버플로(Overflow), 비었는데 팝하면 언더플로(Underflow)가 발생한다. 스택은 다음 기능의 기반이 된다.

| 응용 분야              | 스택에 쌓는 것                     |
| ---------------------- | ---------------------------------- |
| 함수 호출과 복귀       | 호출한 위치(복귀 주소)와 지역 변수 |
| 인터럽트 처리          | 처리 중이던 작업의 상태            |
| 수식 계산, 후위식 변환 | 연산자와 피연산자                  |
| 깊이 우선 탐색(DFS)    | 아직 방문하지 않은 갈림길          |
| 실행 취소 (Undo)       | 직전 작업들                        |

<details>
<summary>예제: 스택 연산 결과</summary>

빈 스택에 `Push A, Push B, Pop, Push C, Push D, Pop, Pop`을 차례로 실행하면 꺼낸 순서와 남은 데이터는 다음과 같다.

### 큐와 데크

큐(Queue)는 한쪽 끝(Rear)에서 삽입하고 반대쪽 끝(Front)에서 삭제하는 구조다. 먼저 넣은 데이터가 먼저 나오므로 선입선출(FIFO, First In First Out)이라고 한다. 운영체제의 작업 스케줄링, 프린터 출력 대기열, 너비 우선 탐색(BFS)에 쓰인다.

데크(Deque, Double Ended Queue)는 양쪽 끝 모두에서 삽입과 삭제가 가능한 구조다. 입력을 한쪽으로 제한한 것을 Scroll, 출력을 한쪽으로 제한한 것을 Shelf라고 부른다.

### 그래프

그래프(Graph)는 정점(Vertex, 노드)과 정점을 잇는 간선(Edge)의 집합이다. 지하철 노선도, 도로망, SNS의 친구 관계처럼 데이터가 망 형태로 연결될 때 쓴다. 간선에 방향이 없으면 무방향 그래프, 있으면 방향 그래프라고 한다.

정점 n개로 만들 수 있는 최대 간선 수는 시험에 자주 나오는 계산이다.

| 기호 | 뜻        |
| ---- | --------- |
| n    | 정점의 수 |

1. 무방향 그래프에서는 정점 두 개를 고르는 조합마다 간선이 하나다.

```math
\text{무방향 최대 간선 수} = \frac{n(n-1)}{2}
```

2. 방향 그래프에서는 A→B와 B→A가 다른 간선이므로 두 배가 된다.

```math
\text{방향 최대 간선 수} = n(n-1)
```

| 정점 수 n | 무방향 최대 간선 | 방향 최대 간선 |
| --------- | ---------------- | -------------- |
| 4         | 6                | 12             |
| 5         | 10               | 20             |
| 10        | 45               | 90             |

모든 정점 쌍이 간선으로 연결된 그래프를 완전 그래프(Complete Graph)라고 한다. 그래프의 모든 정점을 포함하면서 사이클이 없는 부분 트리는 신장 트리(Spanning Tree)이고, 그중 간선 가중치의 합이 가장 작은 것이 최소 비용 신장 트리다.

### 트리

트리(Tree)는 사이클이 없는 그래프로, 하나의 근 노드에서 시작해 가지가 아래로 뻗어 나가는 계층 구조다. 폴더 구조, 조직도, 데이터베이스 인덱스(B-트리)가 트리 구조다.

![트리 용어](./images/eip-software-development-tree-terms.svg '근 노드, 차수, 단말 노드, 레벨을 한 트리에서 확인')

| 용어                       | 뜻                                                     |
| -------------------------- | ------------------------------------------------------ |
| 노드 (Node)                | 트리의 기본 요소. 데이터와 다른 노드로의 가지를 가진다 |
| 근 노드 (Root Node)        | 부모가 없는 맨 위 노드                                 |
| 차수 (Degree)              | 한 노드에 연결된 자식(가지)의 수                       |
| 트리의 차수                | 노드 차수 가운데 가장 큰 값                            |
| 단말 노드 (Leaf, Terminal) | 자식이 없는 노드 (차수 0)                              |
| 비단말 노드                | 자식이 하나 이상인 노드                                |
| 레벨 (Level)               | 근 노드를 1로 하여 아래로 1씩 늘어나는 층 번호         |
| 깊이 (Depth)               | 트리의 가장 큰 레벨                                    |
| 형제 노드 (Sibling)        | 같은 부모를 가진 노드                                  |

모든 노드의 차수가 2 이하인 트리를 이진 트리(Binary Tree)라고 한다. 깊이가 k인 이진 트리의 노드 수는 최대 2^k − 1개이며, 이렇게 모든 레벨이 꽉 찬 이진 트리를 포화 이진 트리(Full Binary Tree), 마지막 레벨만 왼쪽부터 차례로 채운 트리를 완전 이진 트리(Complete Binary Tree)라고 한다. 깊이 4의 포화 이진 트리는 2^4 − 1 = 15개의 노드를 가진다.

### 트리 순회

이진 트리 순회(Traversal)는 모든 노드를 한 번씩 방문하는 방법이다. 근 노드(Root)를 언제 방문하느냐에 따라 이름이 붙는다.

| 순회             | 방문 순서            | 기억할 점                |
| ---------------- | -------------------- | ------------------------ |
| 전위 (Preorder)  | 루트 → 왼쪽 → 오른쪽 | 루트를 ==맨 앞==에 방문  |
| 중위 (Inorder)   | 왼쪽 → 루트 → 오른쪽 | 루트를 ==가운데==에 방문 |
| 후위 (Postorder) | 왼쪽 → 오른쪽 → 루트 | 루트를 ==맨 뒤==에 방문  |

![같은 이진 트리의 전위·중위·후위 순회](./images/eip-software-development-tree-traversal.svg '노드 옆 숫자가 방문 순서')

손으로 풀 때는 서브트리를 하나의 덩어리로 묶고 재귀적으로 펼친다. 위 트리의 중위 순회를 예로 들면 다음과 같다.

1. 근 노드 A 기준으로 "왼쪽 서브트리(B, D) → A → 오른쪽 서브트리(C, E, F, G, H)" 순서다.
2. 왼쪽 서브트리 B는 왼쪽 자식 D만 있으므로 "D → B"다.
3. 오른쪽 서브트리 C는 "E 서브트리 → C → F"이고, E 서브트리는 "G → E → H"다.
4. 이어 붙이면 D, B, A, G, E, H, C, F가 된다.

손 계산을 Python으로 확인한다.

```python
T = {'A': ('B', 'C'), 'B': ('D', None), 'C': ('E', 'F'), 'D': (None, None),
     'E': ('G', 'H'), 'F': (None, None), 'G': (None, None), 'H': (None, None)}

def pre(n):
    if not n: return []
    l, r = T[n]; return [n] + pre(l) + pre(r)

def ino(n):
    if not n: return []
    l, r = T[n]; return ino(l) + [n] + ino(r)

def post(n):
    if not n: return []
    l, r = T[n]; return post(l) + post(r) + [n]

print("전위", ''.join(pre('A')))
print("중위", ''.join(ino('A')))
print("후위", ''.join(post('A')))
```

```text
전위 ABDCEGHF
중위 DBAGEHCF
후위 DBGHEFCA
```

> [!TIP] 시험에서는 이렇게 묻는다
> 트리 그림을 주고 전위·중위·후위 순회 결과를 고르게 한다. 보기 네 개가 대부분 같은 글자로 시작하므로, ==후위 순회의 마지막 글자는 항상 근 노드, 전위 순회의 첫 글자도 항상 근 노드==라는 점으로 보기를 먼저 줄이면 빠르다.

### 수식 표기법 변환

수식은 연산자의 위치에 따라 세 가지로 쓸 수 있다. 사람이 쓰는 `A+B`는 중위 표기(Infix), 연산자가 앞에 오는 `+AB`는 전위 표기(Prefix), 뒤에 오는 `AB+`는 후위 표기(Postfix)다. 후위 표기는 괄호 없이도 계산 순서가 정해지므로 컴파일러가 수식을 스택으로 계산할 때 쓴다. 수식을 트리로 그리면 중위식은 중위 순회, 후위식은 후위 순회 결과와 같다.

시험에서는 손으로 바꾸는 방법을 쓴다.

1. 연산 순서대로 괄호를 모두 친다: `(((A+B)*C)-(D/E))`
2. 후위식이면 각 연산자를 자기를 감싼 괄호의 닫는 괄호 자리로, 전위식이면 여는 괄호 자리로 옮긴다.
3. 괄호를 제거한다. 후위식은 `AB+C*DE/-`, 전위식은 `-*+ABC/DE`다.

컴퓨터는 같은 변환을 스택으로 처리한다. 피연산자는 바로 출력하고, 연산자는 스택 위의 연산자와 우선순위를 비교해 넣거나 꺼낸다.

![중위식을 후위식으로 바꾸는 스택 동작](./images/eip-software-development-postfix.svg '연산자 스택과 출력이 기호 하나를 읽을 때마다 바뀌는 과정')

후위식을 계산할 때도 스택을 쓴다. 숫자는 푸시하고, 연산자를 만나면 두 개를 팝해 계산한 결과를 다시 푸시한다. `(3+4)*5-8/2`를 후위식 `3 4 + 5 * 8 2 / -`로 바꿔 계산한 과정을 Python으로 출력하면 다음과 같다.

```text
   3 -> [3]
   4 -> [3, 4]
   + -> [7]
   5 -> [7, 5]
   * -> [35]
   8 -> [35, 8]
   2 -> [35, 8, 2]
   / -> [35, 4]
   - -> [31]
31
```

## 정렬

정렬(Sort)은 데이터를 키 값의 오름차순이나 내림차순으로 재배열하는 작업이다. 시험에는 "다음 자료를 ○○ 정렬로 오름차순 정렬할 때 2회전 후의 결과는?" 같은 문제가 나온다. 아래 예제는 모두 같은 자료 `[8, 3, 5, 1, 9, 2]`를 오름차순으로 정렬하며, 회전마다의 결과는 Python으로 실행해 출력한 값이다.

### 선택 정렬

선택 정렬(Selection Sort)은 남은 구간에서 ==최솟값을 찾아 구간의 맨 앞 자리와 교환==하는 과정을 반복한다. 1회전에 첫째 자리, 2회전에 둘째 자리가 확정된다.

![선택 정렬의 회전별 결과](./images/eip-software-development-sort-selection.svg '회전마다 남은 구간의 최솟값이 앞쪽 자리로 이동')

```python
def selection(a):
    a = a[:]; n = len(a)
    for i in range(n - 1):
        m = i
        for j in range(i + 1, n):
            if a[j] < a[m]: m = j
        a[i], a[m] = a[m], a[i]
        print(f"선택 {i+1}회전: {a}")
    return a

selection([8, 3, 5, 1, 9, 2])
```

```text
선택 1회전: [1, 3, 5, 8, 9, 2]
선택 2회전: [1, 2, 5, 8, 9, 3]
선택 3회전: [1, 2, 3, 8, 9, 5]
선택 4회전: [1, 2, 3, 5, 9, 8]
선택 5회전: [1, 2, 3, 5, 8, 9]
```

### 버블 정렬

버블 정렬(Bubble Sort)은 이웃한 두 값을 비교해 앞의 값이 크면 교환하는 과정을 처음부터 끝까지 반복한다. 한 회전이 끝나면 남은 값 중 ==가장 큰 값이 맨 뒤로 이동==해 자리가 확정된다. 물속 거품이 위로 떠오르는 모습에서 이름이 붙었다.

![버블 정렬의 회전별 결과](./images/eip-software-development-sort-bubble.svg '회전마다 가장 큰 값이 뒤쪽에 확정')

```text
버블 1회전: [3, 5, 1, 8, 2, 9]
버블 2회전: [3, 1, 5, 2, 8, 9]
버블 3회전: [1, 3, 2, 5, 8, 9]
버블 4회전: [1, 2, 3, 5, 8, 9]
버블 5회전: [1, 2, 3, 5, 8, 9]
```

1회전을 자세히 풀면 (8, 3) 교환 → (8, 5) 교환 → (8, 1) 교환 → (8, 9) 그대로 → (9, 2) 교환이다. 5회전에서는 교환이 한 번도 일어나지 않았으므로, 교환 여부를 검사하는 구현은 여기서 정렬을 끝낸다.

### 삽입 정렬

삽입 정렬(Insertion Sort)은 둘째 값부터 시작해, 현재 값을 ==앞쪽의 이미 정렬된 구간에서 알맞은 위치에 끼워 넣는다==. 카드 게임에서 손에 든 카드를 한 장씩 정리하는 방식과 같다.

![삽입 정렬의 회전별 결과](./images/eip-software-development-sort-insertion.svg '정렬된 앞 구간이 회전마다 한 칸씩 늘어난다')

```text
삽입 1회전: [3, 8, 5, 1, 9, 2]
삽입 2회전: [3, 5, 8, 1, 9, 2]
삽입 3회전: [1, 3, 5, 8, 9, 2]
삽입 4회전: [1, 3, 5, 8, 9, 2]
삽입 5회전: [1, 2, 3, 5, 8, 9]
```

4회전의 9는 앞 구간의 최댓값 8보다 크므로 제자리에 남는다. 이미 거의 정렬된 자료라면 대부분의 회전이 이렇게 비교 한 번으로 끝나서, 삽입 정렬의 최선 시간 복잡도는 O(n)이다.

### 퀵 정렬

퀵 정렬(Quick Sort)은 피벗(Pivot, 기준값)을 하나 고르고, 피벗보다 작은 값은 왼쪽, 큰 값은 오른쪽으로 분할한 뒤, 양쪽 구간을 같은 방법으로 다시 정렬한다. 문제를 작은 문제로 나눠 푸는 분할 정복(Divide and Conquer) 방식이다.

![퀵 정렬의 분할 과정](./images/eip-software-development-sort-quick.svg '분할마다 피벗이 최종 위치에 확정')

```text
퀵 피벗 2: [1, 2, 5, 8, 9, 3] (구간 0~5)
퀵 피벗 3: [1, 2, 3, 8, 9, 5] (구간 2~5)
퀵 피벗 5: [1, 2, 3, 5, 9, 8] (구간 3~5)
퀵 피벗 8: [1, 2, 3, 5, 8, 9] (구간 4~5)
퀵 결과 [1, 2, 3, 5, 8, 9]
```

위 예제는 구간의 마지막 값을 피벗으로 쓰는 로무토(Lomuto) 분할이다. 피벗이 매번 구간의 최솟값이나 최댓값이 되면 분할이 한쪽으로만 일어나 최악 시간 복잡도 O(n²)이 된다. 실제 구현은 중앙값에 가까운 피벗을 고르거나 무작위로 골라 이 경우를 피한다.

### 정렬 알고리즘 비교

| 정렬                  | 평균                          | 최악       | 핵심 동작                                            |
| --------------------- | ----------------------------- | ---------- | ---------------------------------------------------- |
| 선택 정렬 (Selection) | O(n²)                         | O(n²)      | 남은 구간의 최솟값을 앞으로                          |
| 버블 정렬 (Bubble)    | O(n²)                         | O(n²)      | 이웃한 두 값 비교·교환, 최댓값이 뒤로                |
| 삽입 정렬 (Insertion) | O(n²)                         | O(n²)      | 정렬된 구간에 끼워 넣기 (최선 O(n))                  |
| 셸 정렬 (Shell)       | 간격에 따라 다름, 약 O(n^1.5) | O(n²)      | 일정 간격으로 떨어진 값끼리 삽입 정렬 후 간격을 줄임 |
| 퀵 정렬 (Quick)       | O(n log n)                    | O(n²)      | 피벗 기준 분할 후 재귀                               |
| 힙 정렬 (Heap)        | O(n log n)                    | O(n log n) | 완전 이진 트리로 힙을 만들고 루트를 꺼냄             |
| 합병 정렬 (Merge)     | O(n log n)                    | O(n log n) | 반으로 나눠 정렬한 뒤 두 구간을 합침                 |
| 기수 정렬 (Radix)     | O(dn)                         | O(dn)      | 자릿수(d)별로 버킷에 분배 (비교하지 않음)            |

> [!TIP] 시험에서는 이렇게 묻는다
> "다음 자료를 버블 정렬로 오름차순 정렬할 때 1회전 후의 결과는?"처럼 회전 결과를 고르게 한다. 정렬마다 ==한 회전 뒤에 어느 자리가 확정되는지==만 알면 보기를 빠르게 지울 수 있다. 선택 정렬은 맨 앞, 버블 정렬은 맨 뒤가 확정되고, 삽입 정렬은 앞쪽 구간이 정렬된 상태가 된다. 최악 시간 복잡도가 O(n log n)인 정렬을 고르는 문제도 나오는데, 답은 힙 정렬과 합병 정렬이다.

## 검색과 시간 복잡도

### 시간 복잡도와 빅오 표기법

시간 복잡도(Time Complexity)는 입력 크기 n이 커질 때 알고리즘의 실행 단계 수가 얼마나 늘어나는지 나타낸다. 빅오(Big-O) 표기법은 그중 최악의 경우에 대한 상한을 가장 큰 차수 항만 남겨 표기한다. 예를 들어 3n² + 5n + 2단계가 걸리는 알고리즘은 O(n²)이다.

| 표기       | 이름        | n이 1,000일 때 대략의 단계 수 | 예                    |
| ---------- | ----------- | ----------------------------- | --------------------- |
| O(1)       | 상수형      | 1                             | 배열 첨자 접근, 해싱  |
| O(log₂n)   | 로그형      | 10                            | 이진 검색             |
| O(n)       | 선형        | 1,000                         | 순차 검색             |
| O(n log₂n) | 선형 로그형 | 약 10,000                     | 퀵(평균)·힙·합병 정렬 |
| O(n²)      | 제곱형      | 1,000,000                     | 선택·버블·삽입 정렬   |
| O(2ⁿ)      | 지수형      | 약 10^301                     | 배낭 문제의 완전 탐색 |

### 순차 검색과 이진 검색

순차 검색(Sequential Search)은 처음부터 끝까지 하나씩 비교하므로 정렬되지 않은 자료에도 쓸 수 있지만 O(n)이 걸린다. 이진 검색(Binary Search)은 ==정렬된 자료==에서 가운데 값과 찾는 값을 비교해 후보 구간을 절반씩 줄인다.

![정렬된 배열에서 23을 찾는 이진 검색](./images/eip-software-development-binary-search.svg '비교할 때마다 lo와 hi가 좁혀진다')

```python
a = [2, 5, 8, 12, 16, 23, 38, 56, 72, 91]

def bs(a, k):
    lo, hi = 0, len(a) - 1; step = 0
    while lo <= hi:
        mid = (lo + hi) // 2; step += 1
        print(f"  {step}회: lo={lo} hi={hi} mid={mid} a[mid]={a[mid]}")
        if a[mid] == k: return mid
        if a[mid] < k: lo = mid + 1
        else: hi = mid - 1
    return -1

print("찾은 위치", bs(a, 23))
```

```text
  1회: lo=0 hi=9 mid=4 a[mid]=16
  2회: lo=5 hi=9 mid=7 a[mid]=56
  3회: lo=5 hi=6 mid=5 a[mid]=23
찾은 위치 5
```

### 해싱

해싱(Hashing)은 해시 함수로 키 값을 저장 위치(홈 주소)로 바로 계산해 접근하는 방법이다. 비교 없이 위치를 계산하므로 평균 O(1)에 검색한다. 서로 다른 키가 같은 홈 주소로 계산되는 현상을 충돌(Collision)이라 하고, 같은 홈 주소를 갖는 키들을 동의어(Synonym)라고 한다.

| 해시 함수                    | 방법                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| 제산법 (Division)            | 키를 테이블 크기보다 작은 소수로 나눈 나머지를 주소로 사용 |
| 제곱법 (Mid-Square)          | 키를 제곱한 값의 중간 자리 숫자를 주소로 사용              |
| 폴딩법 (Folding)             | 키를 여러 부분으로 나눠 더하거나 XOR한 값을 주소로 사용    |
| 기수 변환법 (Radix)          | 키를 다른 진법으로 변환한 뒤 주소 범위에 맞게 자름         |
| 숫자 분석법 (Digit Analysis) | 키의 자리 중 고르게 분포된 자리들을 골라 주소로 사용       |

제산법으로 키 23, 37, 51을 7로 나눈 나머지를 구하면 2, 2, 2로 모두 충돌한다. 테이블 크기를 소수로 정하고 키 분포를 고려하는 이유다.

## 통합 구현

통합 구현은 따로 개발한 모듈과 외부 시스템을 연결해 하나의 서비스로 동작하게 만드는 작업이다. 예를 들어 쇼핑몰의 주문 모듈이 택배사 시스템에 배송 요청을 보내고 송장 번호를 받아 오려면, 두 시스템이 어떤 경로로, 어떤 형식의 데이터를 주고받을지 정해야 한다.

연계 시스템은 데이터를 보내는 송신 시스템, 받는 수신 시스템, 그리고 둘 사이에서 형식을 변환하고 전송을 관리하는 연계 서버로 구성된다. 연계 방식은 중간 솔루션을 거치는지에 따라 나뉜다.

| 구분      | 방식                                                 | 특징                                                                         |
| --------- | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| 직접 연계 | DB 링크, DB 커넥션 풀, API/Open API, JDBC, 화면 링크 | 구현이 단순하고 빠르지만 두 시스템의 결합도가 높다                           |
| 간접 연계 | EAI, ESB, 웹 서비스(SOAP), 소켓(Socket)              | 연계 솔루션이 중개해 다양한 환경을 통합하지만 성능 저하와 구축 비용이 따른다 |

연계 데이터는 전송 전에 송신 쪽에서 코드값 변환과 암호화를 거치고, 수신 쪽에서 복호화와 형식 검증을 거친다. 전송에 실패한 데이터는 오류 테이블에 기록해 재전송하고, 전송 결과를 로그로 남겨 연계 장애를 추적한다.

> [!TIP] 시험에서는 이렇게 묻는다
> "다음 중 간접 연계 방식이 아닌 것은?"처럼 연계 방식을 분류하게 한다. DB 링크와 JDBC는 직접 연계, EAI와 ESB는 간접 연계다.

## 인터페이스 구현

### 데이터 포맷: JSON과 XML

시스템 사이에 데이터를 주고받으려면 양쪽이 같은 형식으로 해석해야 한다. 웹 서비스에서는 JSON과 XML이 가장 많이 쓰인다. 같은 주문 정보를 두 형식으로 표현하면 다음과 같다.

```json
{
	"orderNo": 1024,
	"customer": "kim",
	"items": [
		{ "isbn": "9788966262472", "qty": 1 },
		{ "isbn": "9791162241967", "qty": 2 }
	]
}
```

```xml
<order>
	<orderNo>1024</orderNo>
	<customer>kim</customer>
	<items>
		<item isbn="9788966262472" qty="1"/>
		<item isbn="9791162241967" qty="2"/>
	</items>
</order>
```

| 비교 항목 | JSON (JavaScript Object Notation)          | XML (eXtensible Markup Language)      |
| --------- | ------------------------------------------ | ------------------------------------- |
| 표현 방식 | 속성-값 쌍(키: 값)과 배열                  | 사용자가 정의한 태그로 감싼 계층 구조 |
| 크기      | 태그가 없어 짧다                           | 여는 태그와 닫는 태그로 길어진다      |
| 표준      | RFC 8259, ECMA-404                         | W3C 권고안                            |
| 스키마    | JSON Schema (선택)                         | DTD, XML Schema로 구조 검증           |
| 주 용도   | REST API, 웹 브라우저와 서버의 데이터 교환 | SOAP 웹 서비스, 문서 교환, 설정 파일  |

### AJAX와 웹 서비스

AJAX(Asynchronous JavaScript and XML)는 웹 페이지 전체를 새로 고치지 않고, 자바스크립트가 서버와 비동기로 데이터를 주고받아 페이지의 일부만 갱신하는 기술이다. 검색창에 글자를 입력할 때마다 추천 검색어가 바뀌는 기능이 대표적이다. 이름에 XML이 들어 있지만 요즘은 주로 JSON을 주고받는다.

웹 서비스(Web Service)는 네트워크로 연결된 서로 다른 시스템이 표준 프로토콜로 기능을 호출하는 방식이다.

| 기술 | 이름                                             | 역할                                                                               |
| ---- | ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| SOAP | Simple Object Access Protocol                    | HTTP 위에서 XML 형식의 메시지로 기능을 호출하는 프로토콜                           |
| WSDL | Web Services Description Language                | 웹 서비스의 이름, 제공 위치, 호출 방법을 XML로 기술                                |
| UDDI | Universal Description, Discovery and Integration | WSDL을 등록하고 검색하는 저장소                                                    |
| REST | REpresentational State Transfer                  | 자원을 URI로 식별하고 HTTP 메서드(GET, POST, PUT, DELETE)로 다루는 아키텍처 스타일 |

### 인터페이스 보안

연계 구간은 외부와 데이터를 주고받으므로 스니핑(도청), 위·변조, 재전송 공격의 대상이 된다. 보안 기능은 계층별로 적용한다.

| 영역              | 적용 기술                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------- |
| 네트워크 영역     | IPsec (IP 계층에서 패킷 암호화·인증), SSL/TLS (전송 계층 암호화, HTTPS의 기반), S-HTTP (웹 메시지 단위 암호화) |
| 애플리케이션 영역 | 시큐어 코딩 가이드에 따른 입력값 검증, 인증·권한 확인                                                          |
| 데이터베이스 영역 | 민감 데이터 암호화, 접근 권한 관리, 스토어드 프로시저·트리거로 접근 통제                                       |

인터페이스 데이터가 변조되지 않았는지는 데이터 무결성 검사 도구로 확인한다. 무결성 검사 도구는 파일의 해시값을 미리 계산해 보관하고, 주기적으로 다시 계산해 비교함으로써 변경된 파일을 찾는다. 대표 도구로 Tripwire, AIDE, Samhain, Claymore, Slipwire, Fcheck가 있다.

### 인터페이스 구현 검증 도구

| 도구     | 특징                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| xUnit    | 단위 테스트 프레임워크 묶음 (Java의 JUnit, C++의 CppUnit, .NET의 NUnit)                                                       |
| STAF     | 서비스 호출, 컴포넌트 재사용 등 다양한 환경을 지원하는 테스트 프레임워크. 각 테스트 대상에 데몬을 설치해 분산 환경에서 테스트 |
| FitNesse | 웹 기반 테스트 케이스 설계·실행·결과 확인을 지원                                                                              |
| NTAF     | FitNesse의 협업 기능과 STAF의 재사용·확장성을 통합한 NHN의 자동화 프레임워크                                                  |
| Selenium | 다양한 브라우저와 개발 언어를 지원하는 웹 애플리케이션 테스트 프레임워크                                                      |
| watir    | Ruby로 작성하는 웹 애플리케이션 테스트 프레임워크                                                                             |

구현한 인터페이스가 운영 중에 정상 동작하는지는 APM(Application Performance Management) 같은 감시 도구로 조회한다. APM은 트랜잭션 처리 시간, 변숫값, 호출 함수, 로그를 수집해 성능 저하와 장애 원인을 분석하며, Scouter와 Jennifer가 대표적이다.

> [!TIP] 시험에서는 이렇게 묻는다
> "속성-값 쌍으로 이뤄진 데이터 객체를 전달하는 개방형 표준 포맷은?"(JSON), "다양한 브라우저와 언어를 지원하는 웹 테스트 도구는?"(Selenium), "데이터 무결성 검사 도구가 아닌 것은?"(보기에 xUnit 같은 테스트 도구를 섞는다) 형태가 자주 나온다.

## 제품 소프트웨어 패키징

제품 소프트웨어 패키징은 개발이 끝난 소프트웨어를 고객이 설치해 쓸 수 있도록 실행 파일, 설치 프로그램, 매뉴얼을 묶어 배포 형태로 만드는 작업이다. 개발자가 아니라 ==사용자 중심==으로 진행하고, 사용자의 실행 환경(운영체제, CPU, 메모리)을 고려해 모듈 단위로 패키징한다. 신규 배포와 변경 배포를 구분하고, 버전 관리와 릴리즈 노트를 함께 관리한다.

### 릴리즈 노트

릴리즈 노트(Release Note)는 배포하는 버전의 변경 내용을 정리한 문서다. 개발 팀이 직접 현재 시제로 작성하고, 신규 소스와 빌드 등의 이력을 정확하게 기록한다.

| 작성 항목      | 내용                                                               |
| -------------- | ------------------------------------------------------------------ |
| 헤더 (Header)  | 문서 이름, 제품 이름, 버전 번호, 릴리즈 날짜, 참고 날짜, 노트 버전 |
| 개요           | 제품과 변경 사항의 간략한 개요                                     |
| 목적           | 새로운 기능, 수정된 기능의 목록과 릴리즈 노트의 목적               |
| 문제 요약      | 수정된 버그의 간단한 설명, 릴리즈 추가 항목 요약                   |
| 재현 항목      | 버그 발견 과정과 재현 절차                                         |
| 수정·개선 내용 | 버그를 수정·개선한 내용                                            |
| 사용자 영향도  | 버전 변경으로 사용자가 다시 확인해야 할 기능과 영향                |
| SW 지원 영향도 | 다른 응용 프로그램이나 지원 프로세스에 주는 영향                   |
| 노트           | 설치, 업그레이드, 제품 문서화에 관한 참고 사항                     |
| 면책 조항      | 회사·표준 제품과 관련된 메시지, 프리웨어·불법 복제 금지 문구       |
| 연락처         | 사용자 지원과 문의 연락처                                          |

### DRM

디지털 저작권 관리(DRM, Digital Rights Management)는 디지털 콘텐츠가 허가된 사용자에게만, 허가된 범위 안에서 쓰이도록 암호화와 사용 권한을 관리하는 기술이다. 음원 스트리밍 서비스에서 내려받은 곡이 구독을 해지하면 재생되지 않는 기능이 DRM으로 구현된다.

| 구성 요소                            | 역할                                                             |
| ------------------------------------ | ---------------------------------------------------------------- |
| 콘텐츠 제공자 (Contents Provider)    | 콘텐츠를 제공하는 저작권자                                       |
| 콘텐츠 분배자 (Contents Distributor) | 암호화된 콘텐츠를 유통하는 곳 (쇼핑몰 등)                        |
| 패키저 (Packager)                    | 콘텐츠를 메타 데이터와 함께 배포 가능한 단위로 묶어 암호화       |
| 보안 컨테이너                        | 콘텐츠 원본을 안전하게 유통하기 위한 전자적 보안 장치            |
| DRM 컨트롤러                         | 배포된 콘텐츠의 이용 권한을 통제 (사용자 PC에 설치되는 프로그램) |
| 클리어링 하우스 (Clearing House)     | 저작권 사용 권한, 라이선스 발급, 사용량에 따른 결제를 관리       |
| 콘텐츠 소비자                        | 콘텐츠를 구매해 사용하는 주체                                    |

| 기술 요소           | 내용                                           |
| ------------------- | ---------------------------------------------- |
| 암호화 (Encryption) | 콘텐츠와 라이선스를 암호화하고 전자 서명       |
| 키 관리             | 콘텐츠를 암호화한 키의 저장과 분배             |
| 암호화 파일 생성    | 콘텐츠를 암호화된 콘텐츠로 생성 (Packager)     |
| 식별 기술           | 콘텐츠에 대한 식별 체계 표현 (DOI 등)          |
| 저작권 표현         | 라이선스의 내용 표현 (XrML, MPEG-21 REL)       |
| 정책 관리           | 라이선스 발급과 사용에 대한 정책 표현·관리     |
| 크랙 방지           | 크랙에 의한 콘텐츠 사용 방지                   |
| 인증                | 라이선스 발급과 사용의 기준이 되는 사용자 인증 |

### 설치·사용 매뉴얼

설치 매뉴얼은 사용자가 처음 설치할 때 참고하는 문서로, 설치 전 확인 사항(지원 운영체제, 필요한 공간), 설치 과정의 화면 캡처와 설명, 설치 후 확인 방법, 삭제 방법, 문의처를 담는다. 사용자 매뉴얼은 설치한 소프트웨어의 기능과 사용 방법을 설명하며, 컴포넌트별 사용법과 예외 상황 처리 방법을 포함한다.

### 형상 관리

형상 관리(SCM, Software Configuration Management)는 소프트웨어 개발 과정에서 만들어지는 산출물(소스 코드, 문서, 설정 파일)의 변경을 식별하고 통제·기록하는 활동이다. 여러 사람이 같은 코드를 동시에 수정해도 누가, 언제, 무엇을, 왜 바꿨는지 추적할 수 있게 한다. 형상 관리는 유지보수 단계뿐 아니라 ==개발 전 과정==에서 수행한다.

| 기능                  | 내용                                                   |
| --------------------- | ------------------------------------------------------ |
| 형상 식별             | 관리할 항목을 정하고 이름과 관리 번호를 부여한다       |
| 버전 제어 (형상 통제) | 변경 요청을 검토·승인하고 기준선(Baseline)에 반영한다  |
| 형상 감사             | 기준선이 무결한지, 변경이 올바르게 반영됐는지 검토한다 |
| 형상 기록 (상태 보고) | 형상 식별, 통제, 감사 결과를 기록하고 보고한다         |

기준선(Baseline)은 정식으로 검토·승인되어 이후 변경은 공식 절차를 거쳐야만 가능한 산출물의 기준 시점이다. 변경을 검토하고 승인하는 조직을 형상 통제 위원회(CCB, Configuration Control Board)라고 한다.

### 버전 관리 도구

버전 관리 도구는 형상 관리를 실제로 수행하는 소프트웨어다. 기본 용어와 동작은 다음과 같다.

![버전 관리 도구의 기본 동작](./images/eip-software-development-version-control.svg '체크아웃, 커밋, 충돌과 업데이트')

| 용어                 | 동작                                                          |
| -------------------- | ------------------------------------------------------------- |
| 저장소 (Repository)  | 최신 버전과 변경 이력이 저장된 곳                             |
| 가져오기 (Import)    | 아무것도 없는 저장소에 처음으로 파일을 복사                   |
| 체크아웃 (Check-Out) | 저장소에서 파일을 받아 작업 공간에 복사                       |
| 체크인 (Check-In)    | 수정한 파일을 저장소에 반영                                   |
| 커밋 (Commit)        | 체크인할 때 이전 버전과 비교해 충돌이 없으면 새 버전으로 갱신 |
| 동기화 (Update)      | 저장소의 최신 버전으로 작업 공간을 갱신                       |
| 디프 (Diff)          | 두 버전의 차이를 줄 단위로 비교                               |

| 방식             | 구조                                                  | 도구                                       |
| ---------------- | ----------------------------------------------------- | ------------------------------------------ |
| 공유 폴더 방식   | 매일 개발한 파일을 약속된 공유 폴더에 복사            | RCS, SCCS                                  |
| 클라이언트/서버  | 중앙 서버 저장소 하나에서 버전을 관리                 | CVS, SVN(Subversion), Clear Case, Perforce |
| 분산 저장소 방식 | 개발자마다 로컬 저장소를 가지고, 원격 저장소와 동기화 | Git, Mercurial, Bazaar, Bitkeeper          |

Git은 2005년 Linus Torvalds가 리눅스 커널 개발을 위해 만들었다. 커밋은 로컬 저장소에 먼저 기록되고, `push`로 원격 저장소에 반영한다. 네트워크 연결 없이도 커밋과 이력 조회가 가능하다는 점이 클라이언트/서버 방식과 다르다.

빌드 자동화 도구는 소스 코드 컴파일, 테스트, 패키징을 자동으로 수행한다. Ant, Make, Maven, Jenkins, Gradle이 대표적이다. Jenkins는 Java 기반의 지속적 통합(CI) 서버로 Git 같은 버전 관리 도구와 연동하고, Gradle은 Groovy나 Kotlin 기반 DSL로 빌드 스크립트를 작성하며 안드로이드 앱 개발 환경의 기본 빌드 도구다.

> [!TIP] 시험에서는 이렇게 묻는다
> "형상 관리의 기능이 아닌 것은?"(보기에 "형상 분석"이나 "형상 개발"을 섞는다), "DRM 구성 요소 중 라이선스 발급과 결제를 관리하는 것은?"(클리어링 하우스), "분산 저장소 방식의 버전 관리 도구는?"(Git), "Groovy 기반 DSL을 쓰는 빌드 도구는?"(Gradle)처럼 나온다.

## 애플리케이션 테스트

### 테스트의 기본 원리

애플리케이션 테스트는 소프트웨어의 결함을 찾아 품질을 확인하는 활동이다. 국제 소프트웨어 테스팅 자격 위원회(ISTQB)의 기초 과정 실러버스는 테스트의 일반 원리를 일곱 가지로 정리하며, 시험에 거의 그대로 나온다.

| 원리                   | 뜻                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| 결함 존재 증명         | 테스트는 결함이 ==있음==을 보여 줄 수 있지만, 결함이 없음을 증명할 수는 없다               |
| 완벽한 테스트는 불가능 | 입력과 경로의 모든 조합을 테스트할 수 없으므로 위험과 우선순위로 범위를 정한다             |
| 초기 집중              | 개발 초기(요구사항·설계 단계)에 테스트를 시작해야 결함 수정 비용이 줄어든다                |
| 결함 집중              | 결함의 대부분은 소수의 모듈에 몰려 있다 (파레토 법칙: 20%의 모듈에서 80%의 결함)           |
| 살충제 패러독스        | 같은 테스트 케이스를 반복하면 더 이상 새 결함을 찾지 못하므로 케이스를 주기적으로 개선한다 |
| 정황 의존              | 소프트웨어의 성격(은행 시스템, 게임)에 따라 테스트 방법이 달라야 한다                      |
| 오류-부재의 궤변       | 결함을 모두 고쳐도 사용자 요구를 만족하지 못하면 품질이 높다고 할 수 없다                  |

### 검증과 확인

| 구분                | 질문                                       | 관점        |
| ------------------- | ------------------------------------------ | ----------- |
| 검증 (Verification) | 명세서대로 ==올바르게 만들었는가==         | 개발자 관점 |
| 확인 (Validation)   | 사용자가 원한 ==올바른 제품을 만들었는가== | 사용자 관점 |

### V 모델과 테스트 레벨

V 모델은 폭포수 모형에 테스트 단계를 짝지은 모델이다. 왼쪽으로 내려가며 개발 단계를 진행하고, 구현이 끝나면 오른쪽으로 올라가며 각 개발 단계에 대응하는 테스트를 수행한다.

![V 모델](./images/eip-software-development-v-model.svg '개발 단계와 테스트 레벨의 짝')

| 테스트 레벨   | 대응하는 개발 단계 | 확인하는 것                                                    |
| ------------- | ------------------ | -------------------------------------------------------------- |
| 단위 테스트   | 상세 설계·구현     | 모듈(함수, 클래스) 하나가 명세대로 동작하는가. 주로 화이트박스 |
| 통합 테스트   | 아키텍처 설계      | 모듈을 결합했을 때 인터페이스와 상호작용에 결함이 없는가       |
| 시스템 테스트 | 시스템(기능) 설계  | 실제 환경과 같은 조건에서 기능·비기능 요구사항을 만족하는가    |
| 인수 테스트   | 요구사항 분석      | 사용자가 요구한 대로 동작해 인수할 수 있는가                   |

인수 테스트에는 알파 테스트와 베타 테스트가 있다.

| 구분        | 장소              | 진행 방식                                                        |
| ----------- | ----------------- | ---------------------------------------------------------------- |
| 알파 테스트 | ==개발자의 장소== | 사용자가 개발자 앞에서 테스트하고 개발자는 결함과 문제를 기록    |
| 베타 테스트 | ==사용자의 장소== | 개발자 없이 실제 업무에서 사용하며 발견한 문제를 개발자에게 보고 |

이 밖에 인수 테스트 종류로 사용자 인수 테스트, 운영상 인수 테스트, 계약 인수 테스트, 규정 인수 테스트가 있다.

### 정적 테스트와 동적 테스트

프로그램을 실행하는지에 따라 테스트를 나눈다.

| 구분        | 방법                                                   | 예                                       |
| ----------- | ------------------------------------------------------ | ---------------------------------------- |
| 정적 테스트 | 프로그램을 ==실행하지 않고== 명세서나 소스 코드를 분석 | 동료 검토, 워크스루, 인스펙션, 코드 검사 |
| 동적 테스트 | 프로그램을 ==실행하면서== 결함을 찾는다                | 화이트박스 테스트, 블랙박스 테스트       |

### 화이트박스 테스트

화이트박스 테스트(White Box Test)는 모듈의 ==내부 소스 코드를 보면서== 논리 흐름의 모든 경로를 테스트한다. 구조 기반 테스트라고도 한다. 대표 기법은 기초 경로 검사와 제어 구조 검사다.

기초 경로 검사(Basis Path Testing)는 Tom McCabe가 제안한 기법으로, 코드의 제어 흐름 그래프에서 순환 복잡도를 구하고 그 수만큼 독립 경로를 테스트한다. 제어 흐름 그래프(Control Flow Graph)는 문장이나 분기점을 노드로, 실행 흐름을 간선으로 그린 그래프다.

![코드의 제어 흐름 그래프와 순환 복잡도](./images/eip-software-development-cfg.svg '노드 9개, 간선 11개, 분기 노드 3개')

순환 복잡도(Cyclomatic Complexity)는 다음 두 가지 방법으로 구하며 결과가 같다.

| 기호 | 뜻                                           |
| ---- | -------------------------------------------- |
| V(G) | 그래프 G의 순환 복잡도                       |
| E    | 간선(화살표) 수                              |
| N    | 노드 수                                      |
| D    | 조건 분기 노드 수 (if, for, while 같은 판단) |

1. 간선과 노드 수로 구한다.

```math
V(G) = E - N + 2 = 11 - 9 + 2 = 4
```

2. 분기 노드 수로 구한다. 노드 ②(for), ③(if), ⑥(if)가 분기다.

```math
V(G) = D + 1 = 3 + 1 = 4
```

3. 그래프를 평면에 그렸을 때 간선으로 둘러싸인 영역 수에 바깥 영역 1을 더해도 같은 값이 나온다.

| 계산 방법        | 결과 |
| ---------------- | ---- |
| E − N + 2        | 4    |
| 분기 노드 수 + 1 | 4    |
| 영역 수 + 1      | 4    |

V(G) = 4이므로 독립 경로 4개를 지나는 입력을 만들면 기초 경로 검사가 끝난다. 각 경로를 지나는 입력을 실제로 실행한 결과는 다음과 같다.

```python
def grade(scores):
    total = 0
    for s in scores:
        if s < 0:
            continue
        total += s
    if total >= 60:
        return "합격"
    return "불합격"

for case in ([], [70], [-10], [30]):
    print(case, grade(case))
```

```text
[] 불합격
[70] 합격
[-10] 불합격
[30] 불합격
```

| 입력    | 지나는 경로                   | 새로 지나는 간선                  |
| ------- | ----------------------------- | --------------------------------- |
| `[]`    | ① → ② → ⑥ → ⑧ → ⑨             | 반복을 한 번도 안 도는 경로       |
| `[70]`  | ① → ② → ③ → ⑤ → ② → ⑥ → ⑦ → ⑨ | ③→⑤, ⑤→②, ⑥→⑦                     |
| `[-10]` | ① → ② → ③ → ④ → ② → ⑥ → ⑧ → ⑨ | ③→④, ④→②                          |
| `[30]`  | ① → ② → ③ → ⑤ → ② → ⑥ → ⑧ → ⑨ | 반복을 돈 뒤 불합격으로 가는 조합 |

제어 구조 검사에는 조건문의 논리식을 테스트하는 조건 검사(Condition Testing), 반복문을 중점적으로 테스트하는 루프 검사(Loop Testing), 변수의 정의와 사용 위치를 따라가는 데이터 흐름 검사(Data Flow Testing)가 있다.

### 화이트박스 테스트의 검증 기준

테스트 케이스가 코드를 얼마나 실행했는지는 커버리지(Coverage) 기준으로 측정한다. `if (a > 0 && b > 0)` 한 줄을 예로 비교한다.

| 기준                                  | 만족 조건                                                         | 필요한 케이스 예 (a, b)            |
| ------------------------------------- | ----------------------------------------------------------------- | ---------------------------------- |
| 문장 검증 (Statement Coverage)        | 모든 문장을 한 번 이상 실행                                       | (1, 1)                             |
| 분기 검증 (Branch, Decision Coverage) | 판단문 전체가 참·거짓을 한 번씩                                   | (1, 1) 참, (−1, 1) 거짓            |
| 조건 검증 (Condition Coverage)        | 판단문 안의 ==개별 조건==(a>0, b>0)이 각각 참·거짓을 한 번씩      | (1, −1), (−1, 1)                   |
| 조건/분기 검증 (Condition/Decision)   | 전체 판단과 개별 조건이 모두 참·거짓을 한 번씩                    | (1, 1), (−1, −1)                   |
| 변경 조건/분기 검증 (MC/DC)           | 각 개별 조건이 ==다른 조건과 상관없이== 전체 결과를 바꾸는지 확인 | (1, 1), (−1, 1), (1, −1)           |
| 다중 조건 검증 (Multiple Condition)   | 개별 조건의 ==모든 조합==을 테스트                                | (1, 1), (1, −1), (−1, 1), (−1, −1) |

조건 검증의 예 (1, −1), (−1, 1)은 a>0과 b>0이 각각 참과 거짓을 한 번씩 가졌지만, 두 경우 모두 전체 판단은 거짓이라 if 블록 안의 문장을 한 번도 실행하지 못한다. 조건 검증이 분기 검증을 보장하지 않는다는 점이 시험에 나온다.

### 블랙박스 테스트

블랙박스 테스트(Black Box Test)는 내부 코드를 보지 않고 ==요구사항 명세만 보고== 입력과 출력이 맞는지 테스트한다. 명세 기반 테스트라고도 한다.

| 기법                                       | 방법                                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------ |
| 동치 분할 검사 (Equivalence Partitioning)  | 입력을 같은 결과가 나오는 범위(동치 클래스)로 나누고 각 범위의 대표값으로 테스트     |
| 경계값 분석 (Boundary Value Analysis)      | 오류가 경계 근처에서 많이 발생한다는 점을 이용해 경계값과 그 바로 앞뒤 값으로 테스트 |
| 원인-효과 그래프 검사 (Cause-Effect Graph) | 입력 조건(원인)과 출력(효과)의 관계를 그래프로 분석해 효용성 높은 케이스를 선정      |
| 오류 예측 검사 (Error Guessing)            | 테스터의 경험과 감각으로 오류가 날 만한 입력을 골라 테스트                           |
| 비교 검사 (Comparison Testing)             | 같은 요구로 만든 여러 버전의 프로그램에 같은 입력을 넣고 결과를 비교                 |
| 결정 테이블 검사 (Decision Table)          | 조건 조합과 그에 따른 동작을 표로 만들어 조합마다 테스트                             |
| 상태 전이 검사 (State Transition)          | 이벤트에 따른 상태 변화를 상태 전이도로 그리고 각 전이를 테스트                      |

점수(0~100점)를 입력받아 60점 이상이면 합격을 출력하는 프로그램으로 동치 분할과 경계값 분석을 비교하면 다음과 같다.

![점수 입력의 동치 분할과 경계값](./images/eip-software-development-blackbox.svg '동치 분할은 범위마다 대표값 하나, 경계값 분석은 경계와 그 바로 바깥')

| 기법        | 테스트 입력             | 기대 결과                              |
| ----------- | ----------------------- | -------------------------------------- |
| 동치 분할   | −5, 30, 80, 110         | 오류, 불합격, 합격, 오류               |
| 경계값 분석 | −1, 0, 59, 60, 100, 101 | 오류, 불합격, 불합격, 합격, 합격, 오류 |

> [!IMPORTANT] 블랙박스와 화이트박스 기법 구분
> 기법 이름만 주고 어느 쪽인지 묻는 문제가 매우 자주 나온다.
>
> | 화이트박스 (내부 구조)                                 | 블랙박스 (명세)                                                |
> | ------------------------------------------------------ | -------------------------------------------------------------- |
> | 기초 경로 검사, 조건 검사, 루프 검사, 데이터 흐름 검사 | 동치 분할, 경계값 분석, 원인-효과 그래프, 오류 예측, 비교 검사 |
> | 문장·분기·조건 커버리지                                | 결정 테이블, 상태 전이                                         |
>
> 블랙박스 기법은 "동경원오비"로 외운다.

### 통합 테스트의 방식

통합 테스트는 모듈을 어떤 순서로 결합하느냐에 따라 나뉜다. 아직 만들지 않은 모듈은 테스트용 임시 모듈로 대신한다.

![하향식·상향식 통합 테스트](./images/eip-software-development-integration.svg '하향식은 스텁, 상향식은 드라이버로 빈 모듈을 대신한다')

| 방식               | 결합 순서                                                       | 임시 모듈                                                                      |
| ------------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 하향식 (Top Down)  | 상위 모듈에서 하위 모듈 방향으로 통합. 깊이 우선 또는 너비 우선 | ==스텁(Stub)==: 하위 모듈을 대신해 정해진 값만 돌려주는 모듈                   |
| 상향식 (Bottom Up) | 하위 모듈들을 클러스터로 묶어 위로 통합                         | ==드라이버(Driver)==: 상위 모듈을 대신해 하위 모듈을 호출하고 결과를 받는 모듈 |
| 빅뱅 (Big Bang)    | 모든 모듈을 한꺼번에 결합                                       | 없음. 결함 위치를 찾기 어렵다                                                  |
| 샌드위치           | 상위는 하향식, 하위는 상향식으로 동시에                         | 스텁과 드라이버 모두                                                           |

모듈을 통합하거나 결함을 수정한 뒤에는 회귀 테스트(Regression Test)를 수행한다. 변경으로 인해 기존에 잘 동작하던 기능에 새 결함이 생기지 않았는지 이전 테스트 케이스를 다시 실행해 확인하는 테스트다.

### 테스트 케이스, 오라클, 하네스

테스트 케이스(Test Case)는 특정 요구사항을 확인하기 위해 설계한 입력값, 실행 조건, 기대 결과의 묶음이다. IEEE 829 표준은 식별자, 테스트 항목, 입력 명세, 출력 명세, 환경 설정, 특수 절차 요구, 의존성 기술을 구성 요소로 정한다.

테스트 오라클(Test Oracle)은 테스트 결과가 참인지 거짓인지 판단하기 위해 미리 정해 둔 참값을 계산하거나 확인하는 기법이다.

| 오라클 종류             | 방법                                                          |
| ----------------------- | ------------------------------------------------------------- |
| 참 오라클 (True)        | 모든 입력값에 대해 기대 결과를 제공해 발생한 모든 오류를 검출 |
| 샘플링 오라클           | 특정 몇몇 입력값에 대해서만 기대 결과를 제공                  |
| 추정 오라클 (Heuristic) | 특정 입력값에는 기대 결과를 제공하고 나머지는 추정으로 처리   |
| 일관성 검사 오라클      | 변경이 있을 때 수행 전과 후의 결과가 같은지 확인              |

테스트 하네스(Test Harness)는 테스트를 지원하기 위해 만든 코드와 데이터의 묶음이다. 앞에서 본 테스트 드라이버와 스텁 외에 테스트 슈트(테스트 케이스의 집합), 테스트 스크립트(자동화된 실행 절차), 목 오브젝트(Mock Object, 사용자의 행위를 조건부로 미리 입력해 두고 그 상황에 맞는 예정된 행위를 수행하는 객체)가 있다.

### 결함 관리

결함(Defect)은 소프트웨어가 개발자가 설계한 것과 다르게 동작하거나 다른 결과가 발생하는 상태다. 테스트에서 발견한 결함은 결함 관리 도구에 등록해 상태를 추적한다.

| 결함 상태             | 뜻                                                           |
| --------------------- | ------------------------------------------------------------ |
| 결함 등록 (Open)      | 결함이 보고되었지만 아직 분석되지 않음                       |
| 결함 검토 (Reviewed)  | 등록된 결함을 담당 모듈 개발자, 테스터, 프로그램 리더가 검토 |
| 결함 할당 (Assigned)  | 결함을 수정할 개발자에게 할당                                |
| 결함 수정 (Resolved)  | 개발자가 결함 수정을 완료                                    |
| 조치 보류 (Deferred)  | 수정이 불가능해 연기 (우선순위나 일정상 다음 버전으로)       |
| 결함 종료 (Closed)    | 결함이 해결되어 테스터와 품질 관리 담당자가 종료를 승인      |
| 결함 해제 (Clarified) | 검토 결과 결함이 아니라고 판명                               |

결함 관리 도구로는 Mantis, Trac, Redmine, Bugzilla가 있다. 결함은 심각도(시스템 중단, 기능 오류, 화면 표시 오류)와 우선순위(즉시 수정, 다음 릴리즈)로 분류해 수정 순서를 정한다.

애플리케이션 성능은 처리량(Throughput, 일정 시간 안에 처리하는 일의 양), 응답 시간(Response Time, 요청한 뒤 응답이 올 때까지 걸린 시간), 경과 시간(Turnaround Time, 요청부터 처리를 완료할 때까지 걸린 시간), 자원 사용률(CPU·메모리·네트워크 사용량) 네 가지 지표로 측정한다.

> [!TIP] 시험에서는 이렇게 묻는다
> "하향식 통합 테스트에서 하위 모듈을 대신하는 것은?"(스텁), "개발자의 장소에서 사용자가 테스트하는 것은?"(알파 테스트), "같은 테스트를 반복하면 새 결함을 찾지 못한다는 원리는?"(살충제 패러독스), "블랙박스 테스트 기법이 아닌 것은?"(기초 경로 검사)처럼 나온다.

## 소스 코드 품질 분석

### 클린 코드

클린 코드(Clean Code)는 다른 개발자가 읽고 이해하고 고치기 쉽도록 작성한 코드다. 코드를 작성하는 시간보다 읽는 시간이 훨씬 길기 때문에, 가독성이 유지보수 비용을 좌우한다. 클린 코드 작성 원칙은 다음과 같다.

| 원칙          | 내용                                                                            |
| ------------- | ------------------------------------------------------------------------------- |
| 가독성        | 누구든지 코드를 쉽게 읽을 수 있도록 작성한다. 이해하기 쉬운 이름, 들여쓰기 사용 |
| 단순성        | 한 번에 한 가지 일만 처리하도록 작성한다. 클래스·메서드·함수를 최소 단위로 분리 |
| 의존성 배제   | 코드가 다른 모듈에 미치는 영향을 최소화한다                                     |
| 중복성 최소화 | 중복된 코드는 삭제하고 공통된 코드를 사용한다                                   |
| 추상화        | 상위 클래스·메서드·함수에서 간략하게 특성을 나타내고 상세 내용은 하위에서 구현  |

외계인 코드(Alien Code)는 아주 오래되었거나 참고 문서·개발자가 없어 유지보수가 매우 어려운 코드를 말한다. 스파게티 코드는 실행 흐름이 `goto` 등으로 얽혀 따라가기 어려운 코드다.

### 리팩토링

리팩토링(Refactoring)은 Martin Fowler가 정의한 개념으로, ==외부에서 보이는 동작은 바꾸지 않고== 내부 구조를 개선해 이해하기 쉽고 수정하기 쉽게 만드는 작업이다. 리팩토링이 필요한 신호를 코드 스멜(Code Smell)이라고 한다.

| 코드 스멜        | 예                                         | 리팩토링 기법                |
| ---------------- | ------------------------------------------ | ---------------------------- |
| 중복 코드        | 같은 할인 계산식이 세 파일에 복사되어 있음 | 메서드 추출 (Extract Method) |
| 긴 메서드        | 주문 처리 함수 하나가 300줄                | 메서드 추출, 조건문 분해     |
| 큰 클래스        | 한 클래스가 회원·주문·결제를 모두 처리     | 클래스 추출 (Extract Class)  |
| 긴 매개변수 목록 | `createUser(a, b, c, d, e, f, g)`          | 매개변수 객체 도입           |
| 의미 없는 이름   | `int d;` `void proc()`                     | 이름 변경 (Rename)           |

리팩토링은 동작을 바꾸지 않아야 하므로, 시작하기 전에 테스트 코드를 갖춰 두고 작은 단계마다 테스트를 실행해 동작이 같은지 확인한다.

### 코드 복잡도

앞의 화이트박스 테스트에서 구한 순환 복잡도는 코드 품질 지표로도 쓰인다. 값이 클수록 경로가 많아 이해와 테스트가 어렵다. McCabe는 모듈의 순환 복잡도를 10 이하로 유지하라고 권장했다. 순환 복잡도가 20인 함수는 기초 경로 검사에만 테스트 케이스 20개가 필요하므로, 함수를 나누는 리팩토링 대상이 된다.

### 소스 코드 품질 분석 도구

| 구분           | 방법                                                              | 도구                                                 |
| -------------- | ----------------------------------------------------------------- | ---------------------------------------------------- |
| 정적 분석 도구 | 코드를 ==실행하지 않고== 코딩 표준 위반, 복잡도, 잠재 결함을 분석 | pmd, cppcheck, SonarQube, checkstyle, ccm, cobertura |
| 동적 분석 도구 | 코드를 ==실행해== 메모리 누수, 스레드 결함을 분석                 | Avalanche, Valgrind                                  |

| 도구       | 특징                                                                |
| ---------- | ------------------------------------------------------------------- |
| pmd        | Java 등의 소스에서 미사용 변수, 최적화되지 않은 코드 등 결함을 찾음 |
| cppcheck   | C/C++ 코드의 메모리 누수, 오버플로 등 분석                          |
| SonarQube  | 중복 코드, 복잡도, 코딩 설계 등을 분석하는 소스 분석 통합 플랫폼    |
| checkstyle | Java 코드가 코딩 표준을 따르는지 검사                               |
| ccm        | 다양한 언어의 코드 복잡도를 분석                                    |
| cobertura  | Java 테스트 커버리지 측정                                           |
| Valgrind   | 메모리 누수와 스레드 결함을 실행 중에 분석                          |

> [!TIP] 시험에서는 이렇게 묻는다
> 제어 흐름 그래프를 주고 순환 복잡도를 구하게 하거나(E − N + 2), "정적 분석 도구가 아닌 것은?"(Valgrind나 Avalanche를 섞는다), "클린 코드 작성 원칙이 아닌 것은?"(보기에 "다형성"이나 "중복성 강화"를 섞는다) 형태로 나온다.

## 확인 문제

<details>
<summary>1. 빈 큐에 A, B, C를 차례로 넣고 두 번 꺼낸 뒤 D를 넣었다. 큐의 Front에 있는 값은?</summary>

C. A와 B가 먼저 나가고 남은 순서는 C, D다.

</details>

<details>
<summary>2. 정점이 6개인 무방향 그래프의 최대 간선 수는?</summary>

6 × 5 ÷ 2 = 15개.

</details>

<details>
<summary>3. [5, 2, 4, 1]을 선택 정렬로 오름차순 정렬할 때 1회전 후의 결과는?</summary>

[1, 2, 4, 5]. 최솟값 1과 첫째 자리 5를 교환한다.

</details>

<details>
<summary>4. 중위식 A*(B+C)를 후위식으로 바꾸면?</summary>

ABC+*. 괄호 안의 B+C를 먼저 BC+로 바꾸고, A와 곱하므로 A BC+ *가 된다.

</details>

<details>
<summary>5. 분기 노드가 4개인 제어 흐름 그래프의 순환 복잡도는?</summary>

4 + 1 = 5.

</details>

<details>
<summary>6. 상향식 통합 테스트에서 하위 모듈을 호출하기 위해 임시로 만드는 모듈은?</summary>

테스트 드라이버(Driver).

</details>

<details>
<summary>7. 입력 범위가 1~10일 때 경계값 분석으로 고르는 값은?</summary>

0, 1, 10, 11 (책에 따라 2와 9를 더하기도 한다).

</details>
