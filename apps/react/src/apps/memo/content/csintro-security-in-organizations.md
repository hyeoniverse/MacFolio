## 들어가기 전에

방화벽과 백신을 설치했다고 기업이 안전해지지는 않는다. 퇴사자의 계정이 그대로 남아 있거나, 패치 담당자가 정해져 있지 않거나, 사고가 났을 때 누구에게 보고해야 하는지 모르면 장비가 탐지한 경보도 쓸모가 없다. 기업의 정보보호는 기술 대책과 함께 정책, 조직, 절차를 갖추고 이를 주기적으로 점검·개선하는 **관리체계**로 운영한다.

| 순서 | 내용                                             |
| ---- | ------------------------------------------------ |
| 1    | 정보보호 관리체계와 ISMS·ISMS-P 인증             |
| 2    | 위험 관리: 자산, 위협, 취약점, 위험 처리         |
| 3    | 보안 정책 체계와 조직(CISO·CPO)                  |
| 4    | 기술 대책: 시스템·네트워크·웹 보안의 다계층 방어 |

필요한 배경은 정보보호의 목표인 기밀성·무결성·가용성과, [네트워크 위협의 분류와 방화벽·IDS·IPS·VPN](/memo/csintro-network-security)에서 다룬 경계 보안 장비다. 법령 내용은 2025년 기준이며, 개정이 잦으므로 실무에서는 국가법령정보센터와 KISA의 최신 고시를 확인한다.

## 정보보호 관리체계

정보보호 관리체계(ISMS, Information Security Management System)는 조직이 보호할 자산을 정하고, 위험을 평가해 대책을 고르고, 그 대책이 제대로 운영되는지 점검해 개선하는 과정을 문서와 절차로 정한 것이다. 국제 표준은 ISO/IEC 27001이며, 계획(Plan) → 실행(Do) → 점검(Check) → 개선(Act)을 반복하는 구조를 따른다.

### ISMS-P 인증

국내에서는 과학기술정보통신부와 개인정보보호위원회가 공동으로 고시한 「정보보호 및 개인정보보호 관리체계 인증 등에 관한 고시」에 따라 한국인터넷진흥원(KISA)이 인증을 운영한다. 2018년 11월 기존의 정보보호 관리체계(ISMS) 인증과 개인정보보호 관리체계(PIMS) 인증을 통합해 ISMS-P가 만들어졌다.

| 구분      | ISMS                          | ISMS-P                                         |
| --------- | ----------------------------- | ---------------------------------------------- |
| 범위      | 정보보호 관리체계             | 정보보호 + 개인정보 처리 전 과정               |
| 인증기준  | 80개                          | 101개                                          |
| 법적 근거 | 정보통신망법 제47조           | 정보통신망법 제47조, 개인정보 보호법 제32조의2 |
| 의무 여부 | 기준에 해당하는 사업자는 의무 | 자율 신청                                      |

![ISMS-P 인증기준은 관리체계 수립 및 운영 16개, 보호대책 요구사항 64개, 개인정보 처리 단계별 요구사항 21개로 구성된다](./images/csintro-security-in-organizations-ismsp.svg 'ISMS는 1·2 영역 80개, ISMS-P는 세 영역 101개를 심사한다')

**ISMS 인증 의무 대상**은 정보통신망법 시행령이 정한다. 주요 기준은 다음과 같다.

- 전기통신사업법에 따라 등록한 기간통신사업자로서 서울과 모든 광역시에서 정보통신망 서비스를 제공하는 자(ISP)
- 집적정보통신시설(IDC) 사업자
- 연간 매출액 또는 세입이 1,500억 원 이상인 상급종합병원, 재학생 1만 명 이상인 고등교육기관
- 전년도 정보통신서비스 부문 매출액 100억 원 이상이거나, 직전 3개월 일평균 이용자 수 100만 명 이상인 정보통신서비스 제공자

인증의 유효 기간은 3년이며, 그동안 매년 사후 심사를 받고 3년마다 갱신 심사를 받는다. 금융 분야는 금융보안원도 인증 기관으로 지정되어 있다.

인증은 특정 시점에 기준을 충족했음을 보여 줄 뿐 사고가 나지 않는다는 보증은 아니다. 인증을 받은 기업에서도 대규모 유출 사고가 일어나, 인증 이후 실제 운영 수준을 점검하는 사후 관리 강화가 꾸준히 논의된다.

## 위험 관리

위험 관리는 관리체계의 중심이다. 모든 자산을 같은 수준으로 보호할 수는 없으므로, 어떤 자산이 어떤 위협에 얼마나 노출되어 있는지 평가해 한정된 예산을 우선순위에 따라 배분한다.

| 용어   | 뜻                                                    | 예시                              |
| ------ | ----------------------------------------------------- | --------------------------------- |
| 자산   | 조직이 가치를 두는 정보, 시스템, 인력, 시설           | 고객 DB 서버                      |
| 위협   | 자산에 손실을 줄 수 있는 원인                         | 외부 해커의 SQL 삽입 공격         |
| 취약점 | 위협이 이용할 수 있는 약점                            | 입력값 검증이 없는 로그인 페이지  |
| 위험   | 위협이 취약점을 이용해 손실을 일으킬 가능성과 그 영향 | DB 유출로 인한 과징금과 신뢰 하락 |

![자산 식별, 위협 식별, 취약점 진단, 위험 평가, 위험 처리 순서로 진행하고, 위험 처리 방법은 감소·회피·전가·수용 네 가지다](./images/csintro-security-in-organizations-risk.svg '위험 관리 절차와 위험 처리 방법')

위험 평가에서는 흔히 다음과 같이 위험도를 산정한다.

```math
\text{위험도} = \text{자산 가치} \times \text{위협 발생 가능성} \times \text{취약성 정도}
```

예를 들어 각 항목을 1~3점으로 매기면, 고객 DB(자산 가치 3)가 인터넷에 노출된 상태(위협 3)에서 패치가 밀린 경우(취약성 3)는 27점, 내부망에만 있는 테스트 서버(1 × 1 × 2)는 2점이다. 조직은 허용할 수 있는 위험 수준(DoA, Degree of Assurance)을 예를 들어 9점으로 정하고, 이를 넘는 위험부터 대책을 세운다.

| 처리 방법 | 뜻                                    | 예시                                         |
| --------- | ------------------------------------- | -------------------------------------------- |
| 감소      | 보호대책을 도입해 위험을 낮춤         | 웹 방화벽 도입, 시큐어 코딩, 패치            |
| 회피      | 위험의 원인이 되는 업무를 하지 않음   | 필요 없는 주민등록번호 수집 중단             |
| 전가      | 손실을 제3자에게 넘김                 | 사이버 보험 가입, 전문 업체에 운영 위탁      |
| 수용      | 대책 비용이 손실보다 크면 그대로 감수 | 허용 수준 이하의 위험, 경영진 승인 후 문서화 |

대책을 적용한 뒤에도 남는 위험(잔여 위험)은 경영진이 승인하고, 위험 평가는 연 1회 이상 또는 시스템이 크게 바뀔 때마다 다시 수행한다.

## 보안 정책과 조직

### 정책 체계

보안 정책은 상위 문서에서 하위 문서로 갈수록 구체적이다.

| 문서            | 내용                                   | 예시                                                            |
| --------------- | -------------------------------------- | --------------------------------------------------------------- |
| 정책(policy)    | 경영진이 승인한 정보보호의 목표와 원칙 | "모든 개인정보는 암호화해 저장한다"                             |
| 지침(standard)  | 정책을 지키기 위한 구체적 기준         | "비밀번호는 영문·숫자·특수문자 조합 8자 이상"                   |
| 절차(procedure) | 담당자가 따라 하는 단계별 방법         | "퇴사자 발생 시 인사팀 통보 후 24시간 이내 전 시스템 계정 삭제" |

정책은 경영진의 승인을 받아 전 직원에게 알리고, 법령이나 조직이 바뀌면 개정한다. 정책이 있어도 절차가 없으면 실무자가 무엇을 해야 하는지 알 수 없어 운영되지 않는다.

### 조직과 인력

| 직책                      | 근거                     | 역할                                                |
| ------------------------- | ------------------------ | --------------------------------------------------- |
| 정보보호 최고책임자(CISO) | 정보통신망법 제45조의3   | 정보보호 계획 수립, 취약점 분석, 침해사고 대응 총괄 |
| 개인정보 보호책임자(CPO)  | 개인정보 보호법 제31조   | 개인정보 처리 업무 총괄, 정보주체 고충 처리         |
| 정보보호 실무 조직        | ISMS-P 인증기준 1.1.3 등 | 보안관제, 취약점 점검, 교육, 감사                   |

정보통신서비스 제공자는 CISO를 지정해 과학기술정보통신부에 신고해야 하며, 자산 총액이나 매출이 일정 규모 이상이면 CISO가 정보보호 외의 업무를 겸할 수 없다. 인적 보안으로는 입사 시 보안 서약, 정기 보안 교육, 직무 분리, 퇴사 시 계정 회수와 자산 반납을 관리한다.

## 기술 대책: 다계층 방어

기업의 기술 대책은 하나의 장비가 뚫려도 다음 계층에서 막도록 여러 겹으로 배치한다. 이를 다계층 방어(defense in depth)라 한다.

| 계층         | 대책                                                                                    |
| ------------ | --------------------------------------------------------------------------------------- |
| 네트워크     | 라우터 ACL, 외부·내부 2단 방화벽, DMZ, IDS·IPS, DDoS 차단, VPN, 망 분리                 |
| 시스템       | 계정 관리(다중 인증), 세션 시간 제한, 접근 통제, 최소 권한, 로그 관리, 취약점·패치 관리 |
| 애플리케이션 | 웹 방화벽(WAF), 시큐어 코딩, 웹셸 탐지, 정기 모의 해킹                                  |
| 데이터       | 개인정보 암호화, DB 접근 통제, 백업                                                     |
| 단말         | 백신·EDR, 네트워크 접근 제어(NAC), 매체 제어                                            |

시스템 보안의 6개 항목인 계정, 세션, 접근 통제, 권한, 로그, 취약점 관리는 ISMS-P 보호대책 요구사항의 2.5(인증 및 권한관리), 2.6(접근통제), 2.9(시스템 및 서비스 운영관리), 2.11(사고 예방 및 대응)에 대응한다. 예를 들어 "로그 관리"는 접속 기록을 생성하는 데 그치지 않고 위·변조되지 않게 별도 서버에 보관하고 정기적으로 검토해야 충족된다.

웹 서버는 누구나 접근할 수 있는 DMZ에 있어 가장 먼저 공격받는다. 웹 애플리케이션 취약점 점검에는 OWASP(Open Worldwide Application Security Project)가 몇 년마다 발표하는 OWASP Top 10을 기준으로 삼는다. 판마다 순위와 항목이 바뀌므로 최신판을 [owasp.org/Top10](https://owasp.org/Top10/)에서 확인한다. 2021년판에서는 접근 통제 실패(Broken Access Control)가 1위였고, 인젝션과 XSS는 한 항목(Injection)으로 합쳐졌다.

## 보안관제와 침해사고 대응

### 보안관제

방화벽, IPS, 웹 방화벽, 서버, 단말이 남기는 로그를 따로 보면 하나의 공격이 여러 장비에 남긴 흔적을 연결하기 어렵다. 보안관제는 이 로그를 한곳에 수집해 시간순으로 연관 분석하는데, 이 시스템을 SIEM(Security Information and Event Management)이라 한다. 예를 들어 "웹 방화벽이 SQL 삽입을 탐지한 IP가 몇 분 뒤 DB 서버에 대량 조회를 일으켰다"는 사실은 두 장비의 로그를 합쳐야 보인다. 최근에는 정상 행위의 기준선을 학습해 벗어난 행위를 찾는 기계학습 기반 분석도 함께 쓴다.

악성코드 감염은 보통 피싱 메일이나 감염된 웹 사이트 방문 → 악성코드 다운로드·실행 → C&C 서버 접속과 추가 모듈 설치 → 내부 확산 → 데이터 탈취 순서로 진행된다. 관제의 목표는 마지막 단계에 이르기 전, C&C 접속 같은 앞 단계에서 징후를 찾는 것이다.

### 침해사고 대응 절차

NIST SP 800-61은 침해사고 대응을 다음 단계로 나눈다[^sp80061].

| 단계           | 내용                                                                 |
| -------------- | -------------------------------------------------------------------- |
| 준비           | 대응 조직(CERT)과 연락망, 절차서, 분석 도구, 백업 마련, 모의 훈련    |
| 탐지·분석      | 경보와 로그로 사고 여부를 판단하고 범위·심각도 분류                  |
| 봉쇄·근절·복구 | 감염 시스템 격리, 악성코드·백도어 제거, 패치 후 백업으로 서비스 복구 |
| 사후 활동      | 원인 분석 보고서 작성, 재발 방지 대책 반영, 절차 개선                |

봉쇄 단계에서는 증거 보존이 중요하다. 감염 서버를 바로 포맷하면 공격 경로와 유출 범위를 확인할 수 없으므로, 메모리와 디스크 이미지를 먼저 확보하는 디지털 포렌식 절차를 따른다.

### 신고 의무

| 사고                    | 근거                                  | 신고 기한                               | 신고처                                      |
| ----------------------- | ------------------------------------- | --------------------------------------- | ------------------------------------------- |
| 침해사고(해킹, DDoS 등) | 정보통신망법 제48조의3                | 침해사고를 알게 된 시각부터 24시간 이내 | 과학기술정보통신부 또는 KISA                |
| 개인정보 유출           | 개인정보 보호법 제34조, 시행령 제40조 | 유출을 알게 된 시각부터 72시간 이내     | 개인정보보호위원회 또는 KISA, 정보주체 통지 |

개인정보 유출 신고는 1천 명 이상 유출, 민감정보·고유식별정보 유출, 외부 불법 접근에 의한 유출 가운데 하나에 해당하면 의무다. 이 밖에 일정 규모 이상의 기업은 「정보보호산업법」 제13조에 따라 정보보호 투자액과 인력 현황을 매년 공시한다.
