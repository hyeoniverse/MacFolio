리팩터링 계획([#150](https://github.com/hyeoniverse/MacFolio/issues/150))의 목적은 두 가지였다. 다음 기능을 추가할 때 수정할 곳이 한 군데가 되게 하는 것, 그리고 기능마다 따로 적용한 보안 설정을 하나의 기준으로 통일하는 것이다.

## 왜 계획이 필요했나

9월 말부터 열흘 남짓 기능 추가 속도가 빨랐다. 메모 편집기, 관리자 API, 트래픽 분석, 휴대폰 화면, 프로젝트 앱이 차례로 추가되면서 같은 역할의 코드가 앱마다 중복으로 생겼다. 증상은 다음과 같았다.

- 서버가 응답에 필드를 추가해도 화면의 타입은 그대로라 컴파일러가 검출하지 못했다.
- 관리자 세션이 만료되어 요청이 401로 실패해도, 그 요청을 보낸 화면 외에는 만료 사실을 알 수 없었다.
- 새 팝업의 `z-index`를 정하려면 CSS 파일 네 개를 열어 값을 비교해야 했다.
- 프로젝트 iframe 안의 링크 하나로 MacFolio 창 전체가 다른 주소로 바뀔 수 있었다.

각각은 작은 문제지만, 다음 기능을 추가할 때마다 수정할 곳이 여러 군데라는 공통점이 있었다. 그래서 10월 10일 새벽에 이슈 #150을 열고 영역별 작업 목록을 작성했다.

## 계획을 나눈 방법

계획은 주제별로 일곱 단계로 나누고, 모든 단계에 적용할 규칙을 정했다.

| 규칙                                  | 이유                                                               |
| ------------------------------------- | ------------------------------------------------------------------ |
| 1~6단계는 동작을 변경하지 않는다      | "동작이 같다"를 자동으로 검증할 수 있어야 PR을 빨리 머지할 수 있다 |
| 동작이 변경되는 보안 작업은 별도 PR로 | 거부되는 요청이 생기면 원인 PR을 바로 특정해야 한다                |
| PR 하나에 주제 하나                   | 검토할 diff가 작고, 되돌릴 때 PR 하나만 되돌리면 된다              |

다른 방식도 검토했다.

| 방식                               | 장점                                    | 선택하지 않은 이유                                               |
| ---------------------------------- | --------------------------------------- | ---------------------------------------------------------------- |
| 앱 단위로 전체 정리                | 앱 하나를 마치면 그 앱은 정리가 끝난다  | 같은 문제(요청, 저장소, 버튼)를 앱마다 반복해서 해결해야 한다    |
| 큰 브랜치 하나에 모아 한 번에 머지 | 중간 상태가 main에 남지 않는다          | 다른 기능 PR과 충돌이 누적되고, 문제를 일으킨 변경을 찾기 어렵다 |
| 주제별 단계 + 작은 PR (선택)       | 같은 문제를 한 번에 해결하고, 매번 머지 | 단계 사이에 이전 방식과 새 방식이 일시적으로 공존한다            |

## 실제 진행 순서

단계 번호는 주제 순서이고, 실제 진행 순서는 달랐다. 보안 점검이 먼저 시작되어 10월 9일부터 11일까지 이어졌고, 1~3단계는 11일 하루에 집중됐다. 공통 컴포넌트는 12일부터 18일까지로 가장 길었고, 스타일과 서버는 17~18일에 진행했다.

![일곱 단계의 머지 날짜](./images/refactor-retrospective-timeline.svg '보안이 먼저 시작됐고, 1~3단계는 하루, 4단계가 가장 길었다')

1~3단계가 하루에 끝난 것은 PR을 작게 나눈 효과가 컸다. 1단계 PR 열 개는 오전 네 시간 사이에 머지했고, 도메인 PR 하나의 diff는 수백 줄 이내였다. 4단계가 길었던 것은 PR마다 컴포넌트를 만들고, 사용처 수십 곳을 교체하고, 화면이 같은지 E2E로 비교하는 작업이 필요했기 때문이다.

## 일곱 단계

1. [타입과 데이터 구조](/memo/refactor-step1-types) — 응답 타입을 `@macfolio/contracts`로, `profile.ts` 분리, 브랜드 타입
2. [폴더 구조와 의존](/memo/refactor-step2-structure) — 이름 규칙, 순환 의존 해소, 큰 파일 분리
3. [공통 기반 코드](/memo/refactor-step3-foundation) — API 클라이언트, 브라우저 저장소, 뷰포트 판정
4. [공통 컴포넌트 설계](/memo/refactor-step4-components) — Modal·Sheet·SearchField, 접근성 이름, 버튼 교체, Menu variant
5. [스타일](/memo/refactor-step5-styles) — 디자인 토큰, `Memo.css` 분리, 중복·미사용 CSS
6. [서버](/memo/refactor-step6-server) — 분석 서비스 분리, 입력 검증을 공유 스키마로
7. [보안](/memo/refactor-step7-security) — 헤더, sandbox, 요청 제한, 의존성과 CI

마무리 단계에서 ESLint 경고 185개를 정리하고 네 패키지 모두 `--max-warnings 0`을 적용했다(#144).

## 돌아보며

- **먼저 측정했다.** 공통 컴포넌트 후보 아홉 개는 실제 사용처를 조사해 보니 세 개였고, 사용하지 않는 CSS 클래스는 처음 추정한 150개에서 9개로 줄었다. 계획에 적은 수치를 그대로 믿지 않고 다시 측정한 것이 작업량을 줄였다.
- **동일성을 검증했다.** 1~6단계는 동작을 변경하지 않는 것이 규칙이었다. 빌드한 CSS를 바이트 단위로, 화면을 계산된 스타일로 비교해 "변경 없음"을 증명했다.
- **보안은 별도 PR로 진행했다.** 동작이 변경되는 PR은 리팩터링과 섞지 않아서, 거부되는 요청이 생겨도 원인을 바로 특정할 수 있었다.

## 아쉬웠던 것

- **수치가 시점마다 달랐다.** 계획 수립 시 측정한 줄 수(예: `FolderSidebar.tsx` 675줄)와 PR 직전 줄 수(697줄)가 달랐다. 계획 문서의 수치는 측정 날짜와 함께 기록해야 했다.
- **CI가 외부 요인으로 중단됐다.** 이 기간에 Docker Hub의 내려받기 한도에 걸려 Postgres 이미지를 받지 못하고 CI가 시작되지 못한 날이 있었다. 이미지 저장소를 ECR Public으로 변경했지만, 리팩터링과 무관한 문제로 머지가 지연됐다.
- **4단계가 길어졌다.** 사용처를 교체하는 PR(#245·#246·#247)이 마지막 날에 집중됐다. 컴포넌트를 만든 PR과 사용처를 교체하는 PR 사이에 다른 기능 작업(#187 등)이 들어가면서 간격이 벌어졌다.

## 의도적으로 남긴 것

- 공통 컴포넌트 후보 여섯 개(`ListRow`, `SegmentedControl`, `Switch`, `EmptyState`, `Toolbar`, `Sidebar`)은 보류했다.
- 앱 CSS의 hex 색 225곳과 프로젝트 페이지의 브랜드 색은 토큰으로 바꾸지 않았다.
- 같은 의미의 `z-index` 값 통합, `Memo.tsx` 분리는 진행하지 않았다.

## 다음 작업

- 리팩터링 이후 생긴 큰 파일을 같은 기준으로 분리한다. 현재 가장 큰 파일은 프로젝트 관리 화면 `settings/ProjectsPane.tsx` 3,307줄이고, `Memo.tsx`는 917줄로 늘었다.
- 토큰을 사용하지 않은 새 CSS 값을 차단하는 린트 규칙을 추가한다. 의도적으로 남긴 값이 많아 예외 목록부터 정해야 한다.
- 비슷한 값의 통합(간격 18px·28px, 같은 의미의 `z-index` 값)은 화면을 확인하며 하나씩 진행한다.
