리팩터링 계획([#150](https://github.com/hyeoniverse/MacFolio/issues/150))의 목적은 두 가지였다. 다음 기능을 붙일 때 고칠 곳이 한 군데가 되게 하는 것, 그리고 기능마다 따로 챙긴 보안 설정을 한 기준으로 맞추는 것이다.

## 왜 계획이 필요했나

9월 말부터 열흘 남짓 기능을 붙이는 속도가 빨랐다. 메모 편집기, 관리자 API, 트래픽 분석, 휴대폰 화면, 프로젝트 앱이 차례로 들어오면서 같은 일을 하는 코드가 앱마다 생겼다. 증상은 이런 식이었다.

- 서버가 응답에 칸을 더해도 화면의 타입은 그대로라 컴파일러가 알아채지 못했다.
- 관리자 세션이 끝나 요청이 401로 실패해도, 그 요청을 보낸 화면 말고는 몰랐다.
- 새 팝업의 `z-index`를 정하려면 CSS 파일 네 개를 열어 숫자를 비교해야 했다.
- 프로젝트 iframe 안의 링크 하나로 MacFolio 창 전체가 다른 주소로 바뀔 수 있었다.

하나씩은 작은 일이지만 다음 기능을 붙일 때마다 고칠 곳이 여러 군데라는 점이 같았다. 그래서 10월 10일 새벽에 이슈 #150을 열고 영역별로 할 일을 적었다.

## 계획을 나눈 방법

계획은 주제별로 일곱 단계로 나누고, 단계마다 지킬 규칙을 하나씩 정했다.

| 규칙                           | 까닭                                                        |
| ------------------------------ | ----------------------------------------------------------- |
| 1~6단계는 동작을 바꾸지 않는다 | "그대로"를 기계로 확인할 수 있어야 PR을 빨리 머지할 수 있다 |
| 동작이 바뀌는 보안은 따로 낸다 | 거절되는 요청이 생기면 원인이 어느 PR인지 바로 알아야 한다  |
| PR 하나에 주제 하나            | 리뷰할 diff가 작고, 되돌릴 때 한 PR만 되돌리면 된다         |
| PR마다 글 한 편                | 왜 그렇게 했는지가 커밋 메시지보다 길게 남는다              |

계획을 다른 방식으로 짤 수도 있었다.

| 방식                               | 좋은 점                             | 이번에 고르지 않은 까닭                                     |
| ---------------------------------- | ----------------------------------- | ----------------------------------------------------------- |
| 앱 하나씩 통째로 정리              | 앱 하나가 끝나면 그 앱은 깨끗하다   | 같은 문제(요청, 저장소, 버튼)를 앱마다 다시 풀어야 한다     |
| 큰 브랜치 하나에 모아 한 번에 머지 | 중간 상태가 main에 남지 않는다      | 다른 기능 PR과 충돌이 쌓이고, 무엇이 깨뜨렸는지 찾기 어렵다 |
| 주제별 단계 + 작은 PR (고름)       | 같은 문제를 한 번에 풀고, 매번 머지 | 단계 사이에 옛 방식과 새 방식이 잠깐 섞인다                 |

## 실제로 한 순서

단계 번호는 주제 순서이고, 실제로 한 순서는 달랐다. 보안 점검이 먼저 시작되어 10월 9일부터 11일까지 이어졌고, 1~3단계는 11일 하루에 몰렸다. 공통 컴포넌트는 12일부터 18일까지 가장 길었고, 스타일과 서버는 17~18일에 했다.

![일곱 단계의 머지 날짜](./images/refactor-retrospective-timeline.svg '보안이 먼저, 1~3단계는 하루, 4단계가 가장 길었다')

1~3단계가 하루에 끝난 것은 작게 나눈 덕이 크다. 1단계 PR 열 개는 오전 네 시간 사이에 머지되었고, 도메인 PR 하나가 글까지 합쳐 300줄 안팎이었다. 4단계가 길었던 것은 부품을 만들고, 사용처 수십 곳을 옮기고, 모양이 같은지 E2E로 비교하는 일이 PR마다 따랐기 때문이다.

## 일곱 단계

1. [타입과 데이터 구조](/memo/refactor-step1-types) — 응답 타입을 `@macfolio/contracts`로, `profile.ts` 나누기, 브랜드 타입
2. [폴더 구조와 의존](/memo/refactor-step2-structure) — 이름 규칙, 순환 의존 풀기, 큰 파일 나누기
3. [공통 기반 코드](/memo/refactor-step3-foundation) — API 클라이언트, 저장소, 화면 질문
4. [공통 컴포넌트 설계](/memo/refactor-step4-components) — Modal·Sheet·SearchField, 접근성 이름, 버튼 옮기기, Menu variant
5. [스타일](/memo/refactor-step5-styles) — 디자인 토큰, `Memo.css` 나누기, 중복·미사용 CSS
6. [서버](/memo/refactor-step6-server) — 분석 서비스 나누기, 검사를 공유 스키마로
7. [보안](/memo/refactor-step7-security) — 헤더, sandbox, 요청 제한, 의존성과 CI

마무리 단계에서 ESLint 경고 185개를 정리하고 네 패키지 모두 `--max-warnings 0`을 걸었다(#144).

## 어떻게 확인했나

| 단계        | 확인 방법                                                                       |
| ----------- | ------------------------------------------------------------------------------- |
| 1 타입      | 기존 단위 시험이 거절 문구와 순서를 그대로 비교. 고치지 않고 통과해야 함        |
| 2 구조      | `pnpm cycles`(madge) 순환 0, 나누기 PR은 E2E 파일을 고치지 않음                 |
| 3 기반 코드 | `client.test.ts` 10개 등 새 모듈 시험, 사용처는 기존 E2E                        |
| 4 컴포넌트  | 공통 클래스를 뗀 계산된 스타일과 붙인 계산된 스타일 비교, 접근성 이름 시험      |
| 5 스타일    | 계산된 스타일 전후 비교, 빌드 CSS의 md5 비교                                    |
| 6 서버      | API e2e 124개, 단위 157개, contracts 시험                                       |
| 7 보안      | 바뀌는 동작마다 실패하는 시험 먼저: CSP 위반 fixture, sandbox E2E, 경로 64개 표 |

## 돌아보며

- **먼저 세었다.** 공통 부품 후보 아홉은 세어 보니 셋이었고, 쓰지 않는 CSS 클래스는 처음 150개에서 9개가 되었다. 계획에 적은 숫자를 그대로 믿지 않은 것이 일을 줄였다.
- **같은지 확인했다.** 1~6단계는 동작을 바꾸지 않는 것이 규칙이었다. 빌드한 CSS를 바이트로, 화면을 계산된 스타일로 비교해 "그대로"를 증명했다.
- **보안은 따로 냈다.** 동작이 바뀌는 PR은 리팩터링과 섞지 않아서, 거절되는 요청이 생겨도 원인을 바로 알 수 있었다.

- **글이 설계 문서가 됐다.** PR마다 글을 쓰려면 "왜"를 한 문단으로 적어야 했다. 일곱 단계 글과 PR별 글이 지금은 이 저장소의 설계 기록이다.

## 아쉬웠던 것

- **숫자가 시점마다 달랐다.** 계획을 세울 때 잰 줄 수(예: `FolderSidebar.tsx` 675줄)와 PR 직전 줄 수(697줄)가 달랐다. 계획 문서의 숫자는 날짜와 함께 적어야 했다.
- **CI가 바깥 사정으로 멈췄다.** 이 기간에 Docker Hub의 받기 한도에 걸려 Postgres 이미지를 받지 못하고 CI가 시작도 못 한 날이 있었다. 이미지를 ECR Public에서 받게 바꿨지만, 리팩터링과 상관없는 일로 머지가 밀렸다.
- **4단계가 길어졌다.** 사용처를 옮기는 PR(#245·#246·#247)이 마지막 날에 몰렸다. 부품을 만든 PR과 사용처를 옮기는 PR 사이에 다른 기능 작업(#187 등)이 끼면서 간격이 벌어졌다.

## 일부러 남긴 것

- 공통 부품 후보 여섯(`ListRow`, `SegmentedControl`, `Switch`, `EmptyState`, `Toolbar`, `Sidebar`)은 보류했다.
- 앱 CSS의 hex 색 225곳과 프로젝트 페이지의 브랜드 색은 이름을 붙이지 않았다.
- 같은 뜻의 `z-index` 값 합치기, `Memo.tsx` 나누기는 하지 않았다.

## 다음에 할 일

- 리팩터링이 끝난 뒤에 생긴 큰 파일을 같은 기준으로 나눈다. 지금 가장 큰 것은 프로젝트 관리 화면 `settings/ProjectsPane.tsx` 3,307줄이고, `Memo.tsx`는 917줄로 늘었다.
- 토큰을 쓰지 않은 새 CSS 값을 막는 장치를 둔다. 일부러 남긴 값이 많아 예외 목록부터 정해야 한다.
- 비슷한 값끼리 합치는 일(간격 18px·28px, `z-index` 같은 뜻의 값)은 화면을 보며 하나씩 한다.
