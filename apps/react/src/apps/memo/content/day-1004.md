## 프로젝트마다 다른 페이지

### 무엇을 바꿨나

MacFolio의 Safari 앱은 프로젝트마다 탭을 하나씩 열어 소개 페이지를 보여 준다. 그전에는 프로젝트 페이지가 색만 다르고 구성은 같았다. 프로젝트마다 내용을 전달하는 방식을 따로 만들었다. 게임은 캐릭터를 움직이며 보고, 터미널 과정은 명령어를 입력하며 보고, 뉴스 서비스는 신문 지면 형태로 본다.

| 프로젝트    | 페이지 구성                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------- |
| 새싹 농장   | 게임 에셋으로 만든 페이지, 흙길 지도 위를 걷는 주인공, 아침에서 밤으로 바뀌는 하늘, 엔딩 크레딧 |
| DevCourse   | 터미널 화면만 배치하고, 명령(`ls`·`cd`·`tree`·`cat`)을 입력해야 내용이 표시된다                 |
| 큐알유      | 실제 앱의 분위기, 스크롤에 맞춰 펼쳐지는 질의응답, 데이터베이스 구조                            |
| 뉴픽        | 신문 지면처럼 헤드라인 사진 기사·사진 기사·단신                                                 |
| MacFolio    | 확대되는 노트북, 화면 크기 시뮬레이터, 벤토 그리드                                              |
| HYEONIVERSE | 마스코트 몽이, 라이트·다크 전환 슬라이더, 레이아웃 전환                                         |

예를 들어 DevCourse 페이지에서 `ls`를 입력하면 `Week02` 같은 폴더 목록이 표시되고, `cd Week02`로 폴더에 들어가 `cat Readme.md`로 파일을 열어야 내용이 나온다. 터미널 명령을 다루는 프로젝트라는 성격을 페이지를 사용하는 방법으로 보여 준다.

### 애니메이션 수정

움직이는 요소는 여러 번 고쳤다.

| 대상                      | 수정 과정                                                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 새싹 농장의 소            | 걸음과 발끝 위치를 세 번 수정. 이미지 두 장이 번갈아 바뀌는 것처럼 보였고, 걸을 때 옆모습이 어색했다                                              |
| 개발 일지의 주인공        | 일정한 걸음 → 진행 방향에 따른 앞·뒤·옆 모습 → 멀어지면 뛰어서 따라오기                                                                           |
| 첫 화면의 소와 닭         | 나무 위를 밟고 지나갔다. 요소의 앞뒤 순서(z-index)를 발끝(요소의 가장 아래) 높이로 정하도록 수정했고, 한 번 수정한 뒤에도 남아 있어 다시 확인했다 |
| 노을에서 밤으로 가는 하늘 | 경계가 너무 뚜렷해 인벤토리 위 여백을 늘리고, 맨 아래 풀밭에만 밝게 남아 있던 영역에 밤 조명을 적용했다                                           |

### 발끝 높이로 정하는 앞뒤 순서

화면을 위에서 비스듬히 내려다보는 2D 게임 장면에서는, 화면 아래쪽에 있는 물체일수록 보는 사람에게 가깝다. 그래서 아래쪽 물체가 위쪽 물체를 가려야 자연스럽다. CSS에서 겹친 요소의 앞뒤 순서는 `z-index`로 정하고, 값이 큰 요소가 앞에 그려진다.

처음에는 소와 닭이 나무 뒤쪽(화면 위쪽)을 지나가는 경우에도 나무 위에 그려져, 나무를 밟고 지나가는 것처럼 보였다. 각 요소의 발끝 높이(요소 상자의 아래 끝에서 그림 아래의 투명 여백 `data-foot`을 뺀 y 좌표)를 `z-index`로 쓰도록 바꿨다.

![소 A의 발끝 y=170, 나무 발끝 y=194, 소 B의 발끝 y=256이라 z-index 순서가 소 B, 나무, 소 A가 되어 소 A는 나무 뒤로, 소 B는 나무 앞으로 지나간다](./images/day-1004-foot-zindex.svg '발끝이 아래에 있는 요소가 앞에 그려진다. 상자의 아래 끝이 아니라 그림의 실제 발끝을 기준으로 한다')

상자의 아래 끝 대신 발끝을 기준으로 한 이유는 그림의 여백 때문이다. 예를 들어 그림 아래에 투명한 여백이 20px 있는 나무는, 상자 아래 끝을 기준으로 하면 실제 뿌리보다 20px 아래에 있는 것으로 계산되어 그 사이를 지나는 소를 가린다. 동물은 옆으로만 걸으므로 걷는 동안 발끝 높이는 바뀌지 않는다.

### 그 밖의 페이지 수정

- **큐알유:** "어떻게 만들었나요?"는 눌러야 내용이 보이는 방식이었다. 스크롤에 맞춰 차례로 펼쳐지고, 위로 스크롤하면 다시 접히게 했다. 처음에는 펼쳐지는 순간이 잘 보이지 않았는데, 펼치는 시점(trigger)이 너무 일렀기 때문이다. 요소가 화면 아래 끝에 들어오자마자 펼쳐지면, 사용자가 그 부분을 보기 전에 이미 펼쳐져 있다
- **수치 검증:** HYEONIVERSE·뉴픽·WTD·큐알유 페이지의 수치를 각 저장소를 근거로 바로잡았다. 9월 29일에 NewPick 팀 구성을 잘못 기재한 것과 같은 유형의 오류다

## 실제로 동작하는 AI 데모와 사용 제한

### 배경: 외부 AI 공급자와 비용

HYEONIVERSE 페이지의 CMS 장은 설명 대신 직접 사용해 보는 데모(발표 갤러리, 음성 생성, 파형 편집, 문서 변환, 번역, 요약)로 바꿨다. 데모가 실제로 동작하도록 API도 만들었다. 음성 생성이나 번역은 직접 구현하지 않고 외부 공급자(Fish Audio, Google Cloud Text-to-Speech 같은 서비스)의 API를 호출한다. 이런 API는 호출 횟수나 글자 수에 따라 요금이 붙거나 무료 한도가 있으므로, 누구나 쓸 수 있는 공개 페이지에서 제한 없이 호출하면 한 사람이 반복 요청만으로 한도를 모두 소진할 수 있다.

그래서 처음부터 두 가지를 함께 구현했다.

| 장치           | 내용                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| 공급자 대체    | 첫 공급자가 실패하면 다음 공급자로 넘어간다. 공급자 한 곳의 장애나 키 만료에도 데모가 계속 동작한다     |
| 호출 횟수 제한 | IP마다, 그리고 사이트 전체로 하루 호출 수에 상한을 둔다. 상한에 도달하면 HTTP 429(요청 과다)로 거절한다 |

| 데모      | 공급자 (실패하면 다음 공급자) | 제한                           |
| --------- | ----------------------------- | ------------------------------ |
| 음성 생성 | Fish → Google → Edge          | 80자, IP당 하루 3회, 전체 50회 |
| 번역·요약 | 실제 공급자                   | IP당 하루 3회, 전체 50회       |
| AI 커버   | 실제 공급자                   | IP당 하루 3회, 전체 10회       |

### 요청 하나가 처리되는 순서

음성 생성 요청을 예로 들면, 서버(`SpeechService`)는 먼저 하루 사용량(`DailyQuota`)에서 1회를 차감한다. IP 주소는 원본 대신 HMAC 해시로 집계한다. 남은 횟수가 없으면 공급자를 호출하지 않고 429로 응답한다. 차감에 성공하면 Fish, Google, Edge 순서로 시도해 처음 성공한 공급자의 음성을 돌려준다. 세 곳이 모두 실패하면 502(상위 서버 오류)로 응답하고, 차감한 1회를 되돌려 사용자가 실패한 요청 때문에 횟수를 잃지 않게 했다.

![요청은 DailyQuota.take에서 IP당 3회·전체 50회를 확인해 없으면 429, 통과하면 Fish·Google·Edge를 차례로 시도해 성공하면 음성을, 셋 다 실패하면 502와 함께 1회를 되돌린다](./images/day-1004-quota-fallback.svg '음성 생성 요청 하나의 처리 순서. 응답에 각 공급자의 시도 결과가 함께 담겨 화면이 차례로 표시한다')

예를 들어 Fish 키가 만료된 날에 요청하면 응답의 시도 기록은 `fish 실패 → google 성공`이 되고, 화면은 이 순서를 그대로 표시해 대체 동작을 보여 준다. 하루 사용량은 날짜(UTC 기준)가 바뀌면 0부터 다시 집계한다.

### 음성 데모의 시행착오

- 처음에는 브라우저 내장 음성 합성(Web Speech API의 `speechSynthesis`)으로 만들었다. 서버 호출 없이 동작하지만, 목소리 종류를 보여 줄 수 없고 Fish보다 부자연스러워서 Fish를 우선 사용하게 바꿨다
- 직접 사용해 보니 소리가 나지 않았고, 클립 끌기도 동작하지 않았다. 클립 순서는 핸들 없이 길게 눌러 끌도록 변경했다
- 데모 API 키는 서버의 `api.env`에 `FISH_AUDIO_API_KEY`, `GOOGLE_TTS_API_KEY`를 추가하고 API를 다시 배포해 활성화했다. 배포한 뒤 "서버에 닿지 못했습니다"가 표시되어 설정을 다시 확인했다

마스코트 몽이는 화면에 보이는 데모 옆으로 이동해 사용을 권하고, 결과에 반응한다.

![현재의 HYEONIVERSE 페이지](./images/day-1004-hyeoniverse.jpg 'Safari의 HYEONIVERSE 페이지 현재 화면. 페이지 구성은 다음 날까지 더 변경되었다')

## Safari에서만 발생한 문제

### 배경: position sticky와 overflow clip

`position: sticky; top: 0`인 요소는 평소에는 일반 요소처럼 문서 흐름을 따라 스크롤되다가, 위 끝이 스크롤 영역의 위 끝에 닿으면 그 자리에 고정된다. 부모 요소의 아래 끝이 올라오면 다시 함께 밀려 올라간다. 프로젝트 페이지의 "스크롤하면 화면이 따라 움직입니다" 장면은 이 동작을 이용한다. 화면 높이보다 긴 트랙 안에 장면을 두고, 트랙을 지나는 동안 장면을 창에 고정한 채 스크롤 진행도에 따라 그림을 바꾼다.

`overflow: clip`은 요소 밖으로 넘친 내용을 잘라 내 보이지 않게 하는 값이다. `overflow-x: clip`은 가로 방향만 자른다. 몽이가 페이지 가장자리 밖으로 나오는 경우 가로 스크롤 막대가 생기지 않도록 페이지 전체에 `overflow-x: clip`을 적용해 두었다.

![sticky 무대와 진행도](./images/projects-one-list-sticky-progress.svg '트랙을 지나는 동안 무대는 창에 고정되고, 스크롤한 비율이 진행도로 들어간다')

### 증상과 원인

**Safari에서 멈춘 스크롤 장면**과 **Safari에서 사라지던 몽이**는 하루 작업의 맨 끝에야 고쳤다. ==Chrome에서만 개발하고 Safari 확인을 작업 마지막으로 미뤘기 때문이다.==

| 증상                                                                      | 원인                                                                                   |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| "스크롤하면 화면이 따라 움직입니다" 장면이 멈춤 (한 번 고친 뒤 다시 발생) | 페이지에 `overflow: clip`을 적용하면 Safari에서 `position: sticky`가 동작하지 않았다   |
| 몽이가 화면에서 사라지고, 마우스를 올리면 깜빡임                          | 높이가 0인 몽이 레이어에 `overflow: clip`을 적용하면 Safari에서 몽이가 표시되지 않았다 |

![같은 CSS에서 Chromium은 장면이 창 위쪽에 고정되고, Safari는 장면이 일반 요소처럼 위로 밀려 나가 고정되지 않는다](./images/day-1004-sticky-clip.svg '페이지 전체에 overflow-x: clip을 적용한 상태의 브라우저별 결과')

첫 번째 수정은 클리핑을 페이지 전체가 아니라 몽이 레이어에만 적용하는 방법이었다. 그러자 sticky는 다시 동작했지만 Safari에서 몽이가 사라졌다. 몽이 레이어는 높이가 0인 상자인데, Safari가 가로만 자르라는 설정을 세로까지 적용해, 높이 0 바깥에 그려진 몽이가 모두 잘렸다.

최종 수정에서는 어떤 레이어에도 클리핑을 적용하지 않았다. 몽이는 항상 화면 안에 배치하고, 가로 스크롤은 스크롤 컨테이너(Safari 창의 페이지 영역) 자체에서 막았다. 스크롤 컨테이너 자체의 `overflow`는 그 안의 sticky를 깨지 않는다. 자세한 과정은 [PROJECTS 단일 원본으로 GitHub 스냅샷과 프로젝트 목록 합치기](/memo/projects-one-list)에 있다.

> [!TIP] Safari 확인 시점
> sticky, overflow, 스크롤 연동 애니메이션처럼 브라우저마다 구현 차이가 있는 CSS를 바꾼 경우, 그 변경을 커밋하기 전에 Safari에서 한 번 열어 확인한다.

## 돌아보며

- 실제 공급자를 호출하는 API는 공개되는 순간부터 비용이 발생한다. 그래서 데모에는 사용 제한부터 적용했다.
