macOS의 날씨 앱과 같은 모양의 **날씨** 앱을 추가했다. Launchpad와 휴대폰 홈 화면에서 열 수 있고, Dock에는 고정하지 않는다. 2026년 10월 10일 첫 커밋(`1acec758b`) 이후 같은 날 화면 다듬기(`eb038a30b`)와 iOS Safari 밀어서 삭제 수정(`d5f9f6741`), 이튿날 검색 속도 개선(`2536320be`)이 이어졌다.

## 데이터: Open-Meteo

[Open-Meteo](https://open-meteo.com/)는 API 키 없이 쓰는 공개 날씨 API다(데이터 라이선스 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)). 그래서 사이트의 API 서버를 거치지 않고 브라우저가 직접 호출한다.

- [일기예보](https://open-meteo.com/en/docs) `api.open-meteo.com/v1/forecast`: 현재 날씨, 시간별(이틀), 일별(10일)을 요청 한 번으로 조회한다. `timezone=auto`면 시각이 그 장소의 시간대로 오고, `wind_speed_unit=ms`면 풍속이 m/s 단위로 온다
- [지오코딩](https://open-meteo.com/en/docs/geocoding-api)[^geocoding] `geocoding-api.open-meteo.com/v1/search`

다른 데이터 출처와 비교한 결과는 다음과 같다.

| 데이터                       | 키        | 브라우저에서 바로 | 버린 이유 / 고른 이유                                            |
| ---------------------------- | --------- | ----------------- | ---------------------------------------------------------------- |
| 기상청 공공데이터 API        | 필요      | 불가              | 키를 숨기려면 서버를 거쳐야 한다. 해외 도시가 없다               |
| OpenWeatherMap 같은 상용 API | 필요      | 불가              | 키를 숨기려면 서버를 거쳐야 하고, 무료 호출 한도를 관리해야 한다 |
| Open-Meteo                   | 필요 없음 | 가능              | 서버 코드가 필요 없다. 출처(CC BY 4.0)만 표시한다                |

공개된 날씨 정보를 표시하기 위해 API 서버에 중계 코드를 추가하지 않는 것이 목표였다. API 서버 없이 정적 사이트만 실행한 경우(`pnpm dev`)에도 날씨 앱은 동작해야 한다. 키가 필요 없는 Open-Meteo는 이 조건을 만족한다.

사이트의 CSP는 [`connect-src`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/connect-src)에 등록된 주소로만 요청을 허용한다. 그래서 두 주소를 `worker/securityHeaders.ts`에 추가하고, 보안 헤더 시험에도 추가했다. 화면 맨 아래에는 데이터 출처를 표시한다.

## 한국어 이름 검색

먼저 지오코딩 API를 직접 호출해 결과를 확인했다.

| 검색어  | 결과                                            |
| ------- | ----------------------------------------------- |
| `서울`  | 없음                                            |
| `부산`  | 경상북도 의성군의 마을 'Pusan'이 먼저           |
| `Busan` | 부산광역시 (행정 중심지, 인구 3,285,147)가 먼저 |
| `Tokyo` | 도쿄 (수도)가 먼저, 그다음 파푸아뉴기니의 Tokyo |

한국어로 검색하면 결과가 없거나 엉뚱한 장소가 먼저 나온다. 그래서 자주 검색할 도시 39곳(국내 17, 해외 22)을 한국어 이름과 영어 별칭과 함께 코드에 내장했다(`places.ts`의 `CITIES`). 검색 순서는 다음과 같다.

1. 내장 도시: 한국어·영어 이름에 검색어가 포함되면 즉시 표시한다 (`주` → 광주, 청주, 전주, 제주)
2. Open-Meteo: 입력이 0.3초 멈춘 뒤 호출하고(디바운스), 결과를 수도(`PPLC`) → 행정 중심지(`PPLA`) → 인구 순으로 재정렬한다[^pplc]
3. 같은 장소(약 1km 이내)는 한 번만, 최대 8개까지 표시한다

## 검색이 느린 문제

실제로 사용해 보니 장소 검색 응답이 느렸다. 측정해 보니 Open-Meteo 지오코딩 응답 시간이 요청당 **1~10초**였다(같은 검색어도 요청마다 달랐고, 일기예보 API는 1초 남짓). 옵션(`language`, `count`)을 바꿔도 같았다. 여기에 입력이 멈출 때마다 0.3초 뒤 다시 요청했고, 한글은 조합 중인 글자('ㄴ', '노', '놘'…)마다 요청을 보냈다. 외부 서버의 응답 시간은 개선할 수 없으므로 **대기가 필요한 경우를 줄였다**(`2536320be`).

- **내장 도시를 39곳에서 211곳으로 확장.** 국내 시·군과 서울의 구 25개, 해외 주요 도시를 넣었다. 지오코딩은 '노원구'·'강남구' 같은 구 이름을 찾지 못하고 '성남'은 같은 이름의 마을을 먼저 반환해서, 국내 좌표는 직접 입력했다(도시는 중심, 구는 구청 근처. 날씨 격자 간격이 수 km라 이 정도 오차는 결과에 영향이 없다). 대부분의 검색은 이제 입력 즉시 결과가 나온다
- **정렬 순서:** 이름이 검색어로 시작하는 장소 → 이름에 검색어가 포함된 장소 → 지역 이름에 포함된 장소. '서울'을 입력하면 서울 다음에 서울특별시의 구 25개가 나온다
- **Open-Meteo는 후순위로 호출:** 두 글자 이상 입력 후 0.25초(`SEARCH_DELAY_MS = 250`) 멈추면 요청하고, 응답을 기다리는 동안 목록 아래에 '더 찾는 중…'을 표시한다. 내장 결과는 그동안에도 그대로 보인다
- **한글 조합 중에는 요청하지 않는다.** 조합이 끝나면 요청한다. 조합 종료 이벤트(`compositionend`)를 보내지 않는 키보드도 있어서 입력 이벤트마다 [`isComposing`](https://developer.mozilla.org/en-US/docs/Web/API/InputEvent/isComposing)으로 조합 상태를 다시 확인한다
- **같은 검색어는 다시 요청하지 않는다.** 응답을 메모리에 캐시해, 다른 검색어를 입력했다가 돌아와도 즉시 표시한다
- **8초(`SEARCH_TIMEOUT_MS = 8000`)가 지나면 요청을 중단한다.** 결과가 하나도 없으면 '결과 없음'을 표시한다

내장 도시 검색 코드는 짧다. 이름이 검색어로 시작하면 0, 포함하면 1, 지역 이름에 포함하면 2로 순위를 매기고, 같은 순위는 목록 순서(큰 도시 먼저)를 따른다.

```ts
// apps/react/src/apps/weather/places.ts
const rank = (city: (typeof CITIES)[number]) => {
	const names = [city.name.toLowerCase(), ...city.aliases];
	if (names.some((name) => name.startsWith(q))) return 0;
	if (names.some((name) => name.includes(q))) return 1;
	if (city.region.includes(q)) return 2;
	return null;
};
```

![글자를 치면 내장 도시를 바로 보여 주고, 조건이 맞을 때만 Open-Meteo에 묻는 흐름](./images/weather-app-search-flow.svg '장소 찾기 흐름')

목록을 확장한 뒤 '서울'을 검색하니 종로구가 결과에서 빠져 있었다. 중복 표시를 막기 위해 약 1km 이내를 같은 장소로 판정했는데, 서울(시청)과 종로구(구청)가 1km 이내에 있었다. 기준을 약 500m(위도·경도 차 0.005도)로 좁히고 이 경우를 시험에 추가했다.

```ts
/** 두 장소가 같은 곳인지 (약 500m 안). 1km로 두었더니 서울(시청)과 종로구(구청)가 같은 곳이 되어 종로구가 찾기에서 빠졌다 */
export const samePlace = (a: Place, b: Place) =>
	Math.abs(a.latitude - b.latitude) < 0.005 && Math.abs(a.longitude - b.longitude) < 0.005;
```

## 화면

- **왼쪽:** 장소 카드. 카드마다 그 장소의 하늘 색, 이름, 현지 시각, 날씨, 기온, 최고·최저 기온을 표시한다. 마우스를 올리면 나타나는 ×로 삭제한다(마지막 하나는 삭제할 수 없다)
- **오른쪽:** 선택한 장소의 하늘 색 배경 위에 이름, 큰 기온, 날씨, 최고·최저 기온
  - 시간별 일기예보: 현재부터 24칸, 강수 확률은 30% 이상인 칸에만 표시
  - 10일간의 일기예보: 10일 동안의 최저·최고 기온을 눈금 범위로 삼아 날마다 기온 범위 막대를 렌더링하고, 오늘 막대에는 현재 기온 점을 표시
  - 상세 칸: 체감 온도, 습도, 바람(방향), 자외선 지수(기상청 단계), 일출·일몰, 강수량

하늘 색은 WMO 날씨 코드[^wmo]를 맑음·구름 조금·흐림·안개·이슬비·비·눈·뇌우 여덟 가지로 분류하고, 낮·밤으로 나눠 정한다. macOS 날씨 앱도 화면 모드와 상관없이 하늘 색을 쓰므로 다크 모드에서도 색이 같다.

추가한 장소 목록은 브라우저의 localStorage에 저장한다. 기본값은 서울 하나다. 휴지통의 '내 브라우저 데이터'에도 '날씨 장소'로 표시되어 삭제할 수 있다(휴지통 시험이 코드가 사용하는 저장 키를 모두 등록했는지 검사하므로, 누락하면 시험이 실패한다).

현재 위치 기능은 구현하지 않았다. 사이트의 [`Permissions-Policy`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Permissions-Policy)가 위치 권한을 차단하고 있고, 위치 권한을 요청하기보다 방문자가 도시를 검색해 추가하는 방식이 개인정보 수집을 줄인다.

## 실제 앱과 비교해 다시 조정하기

첫 화면을 실제 macOS·iOS 날씨 앱 스크린샷과 나란히 비교해, 다른 부분을 다음과 같이 수정했다(`eb038a30b`, `d5f9f6741`).

**맥 (넓은 창)**

- 하늘 색 배경이 창 전체를 채우고, 사이드바는 그 위에 떠 있는 둥근 반투명 패널이다. 사이드바 오른쪽 위의 버튼으로 접고, 접으면 신호등 옆에 버튼이 나타난다
- 장소는 카드를 오른쪽 클릭해 '삭제'로 삭제한다 (마우스를 올리면 보이던 ×는 제거했다)
- 장소 이름 위에 지역 이름(대한민국)을 작은 글자로 추가하고 글자 크기를 줄였다
- 시간별 일기예보 아래는 2단 배치: 왼쪽 10일 일기예보, 오른쪽 상세 칸
- 밤에는 남색 하늘에 별을 배치하고, 칸 배경을 어둡고 투명하게 한다

사이드바에 블러([`backdrop-filter`](https://developer.mozilla.org/en-US/docs/Web/CSS/backdrop-filter))를 적용하자 그 안의 사이드바 버튼이 클릭되지 않았다. `backdrop-filter`가 새 [쌓임 맥락(stacking context)](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_positioned_layout/Stacking_context)을 만들어서, 버튼의 z-index를 올려도 창 상단의 끌기 영역(z-index 3) 아래에 놓였다. 사이드바 전체의 z-index를 올리면 이번에는 사이드바가 신호등 버튼을 덮는다. 그래서 사이드바 상자는 클릭을 통과시키고([`pointer-events: none`](https://developer.mozilla.org/en-US/docs/Web/CSS/pointer-events)) 내부 요소만 클릭을 받게 했다. 신호등 클릭 시험을 추가해 이 문제를 검출했다. 같은 원리의 문제는 [sticky 도구 막대가 버튼을 가린 이유](/memo/sticky-stacking-context)에 자세히 정리했다.

**아이폰 (좁은 창)**

- 홈으로 가는 버튼을 제거했다 (iOS 날씨처럼 홈 바 제스처로 나간다)
- 하단에 떠 있는 막대: 가운데 장소 점, 오른쪽 목록 버튼. 화면을 가로로 밀면 이전·다음 장소로 이동한다 (가로 스크롤하는 시간별 칸은 제외). 장소가 하나면 이동할 대상이 없으므로 점 막대를 렌더링하지 않는다 (수정 전에는 점 하나만 있는 막대가 표시되어, 눌러도 동작이 없는 요소가 되었다)
- 시간별 일기예보 위에 요약 문장: 날씨가 처음 바뀌는 시각과 오늘 돌풍의 최대 풍속 (예: '오전 12시쯤 구름 조금 상태가 예상됩니다. 돌풍의 풍속은 최대 3m/s입니다.'). 돌풍은 Open-Meteo의 `wind_gusts_10m_max` 값을 쓴다
- 목록 화면: 큰 '날씨' 제목, ••• 메뉴(목록 편집, °C 섭씨, °F 화씨), 카드의 '시각 • 지역' 표기, 하단에 떠 있는 알약 모양 검색 칸, 맨 아래 데이터 출처
- 카드를 왼쪽으로 밀면 빨간 휴지통 버튼이 나타난다. 목록 편집 상태에서는 모든 카드에 항상 표시된다. 마우스로 밀면 버튼을 놓는 순간 `click` 이벤트가 이어져 방금 연 카드를 다시 닫았기 때문에, 밀기 직후의 `click`은 무시하게 했다. 그래도 실제 iPhone에서는 카드가 열리지 않았다. iOS Safari는 미는 손가락이 세로로 조금만 흔들려도 스크롤로 판단해 [`pointercancel`](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)을 보내는데, 코드가 이 이벤트를 '닫기'(`setOffset(0)`)로 처리하고 있었다. 수정 후에는 `pointercancel`에서도 민 거리로 열기·닫기를 결정하고, 가로로 밀기 시작하면 카드가 포인터를 점유하며([`setPointerCapture`](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture)), 목록에는 세로 스크롤만 브라우저가 처리하도록 [`touch-action: pan-y`](https://developer.mozilla.org/en-US/docs/Web/CSS/touch-action)를 지정한다. 시험도 마우스가 아니라 세로로 흔들리는 실제 터치 이벤트로 카드를 민다

- 아이콘에 색을 적용했다: 해는 노랑, 비는 하늘색

## 좁은 창과 휴대폰

창 폭이 640px보다 좁으면([컨테이너 쿼리](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_queries)) 위의 아이폰 모양으로 바뀐다. 기준이 화면 폭이 아니라 창 폭이므로 맥에서 창을 좁혀도 같은 모양이 된다. '오후 12시'가 잘리던 시간별 칸은 글자 너비만큼 넓어지게 했다.

## 남은 과제와 정리

- 현재 위치 기능은 구현하지 않았다. 사이트의 `Permissions-Policy`가 `geolocation=()`으로 위치 권한을 차단하고 있고, 날씨 앱 하나를 위해 이 정책을 완화하지 않았다.
- 내장 도시 좌표는 수동으로 입력한 값이다. 국내 시·군은 모두 넣었지만 해외는 주요 도시뿐이라, 그 밖의 장소는 응답이 느린 Open-Meteo 검색에 의존한다.
- 외부 API의 응답 시간은 개선할 수 없다. 대신 내장 데이터로 즉시 결과를 표시하고 외부 응답은 도착하는 대로 추가하면, 대부분의 검색에서 대기 시간이 사라진다.
- 실제 기기(iOS Safari)의 터치 입력은 시험 브라우저의 마우스 입력과 다르다. 손가락이 세로로 조금만 흔들려도 `pointercancel`이 발생한다. 시험도 이 터치 동작을 재현해야 한다.
- 창 폭 641~767px에서 레이아웃이 어긋난 문제는 이후 별도로 수정했다([날씨 앱의 세 가지 어긋남 — 가려진 신호등, 휴대폰 안의 넓은 창, 밀려난 목록 버튼](/memo/weather-layout-fixes)).
