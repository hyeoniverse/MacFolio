## 머지 뒤 배포를 막은 검색 성능 시험 ([#414](https://github.com/hyeoniverse/MacFolio/pull/414))

### 배경: CI 작업의 의존 관계

이 저장소는 `main`에 커밋이 들어오면 GitHub Actions가 `.github/workflows/ci.yml`의 작업(job)을 실행한다. 작업은 GitHub가 제공하는 가상 머신인 러너(GitHub-hosted runner)에서 돌고, 러너는 여러 사용자가 나눠 쓰는 공유 자원이라 같은 코드라도 실행할 때마다 속도가 조금씩 다르다. 작업 사이의 순서는 `needs`로 지정한다. 사이트를 올리는 `deploy` 작업은 형식·린트·타입·단위 시험·빌드를 묶은 `check`가 성공해야 실행된다.

```yaml
# .github/workflows/ci.yml
deploy:
  needs: [check, e2e-reuse, e2e, api-image, api-deploy]
  if: >-
    always() && github.event_name == 'push' && github.ref == 'refs/heads/main' &&
    needs.check.result == 'success' && ...
```

![check 실패가 deploy를 막는 구조](./images/day-1106-deploy-gate.svg 'deploy는 check, e2e, API 이미지·배포의 결과를 모두 확인한다. check 안의 시험 한 건이 실패하면 deploy는 실행되지 않는다')

### 증상

전날 [#412](https://github.com/hyeoniverse/MacFolio/pull/412)를 머지한 뒤 CI의 `check` 작업이 desktop-core 검색 성능 시험 한 건에서 실패했다. `deploy`가 `check`에 걸려 있어 사이트에 배포되지 않았다. 같은 커밋을 다시 실행하면 통과했다.

```
FAIL src/memo/search.test.ts > 성능 > 글 240편(본문 8,600자씩)에서 검색어를 한 글자씩 칠 때 한 번에 평균 5ms 안
AssertionError: expected 5.458333333333333 to be less than 5
```

[#412](https://github.com/hyeoniverse/MacFolio/pull/412)는 검색 코드를 바꾸지 않았다. 실패한 시험은 [10월 27일](/memo/day-1027)에 검색 순위를 만들며 더한 것이다. 코드 변경 없이 실행할 때마다 결과가 달라지는 시험을 흔들리는 시험(flaky test)이라고 부른다.

### 원인

메모 앱의 검색은 글마다 제목·본문을 검색하기 쉬운 형태로 바꾼 "검색용 글자"를 만들어 두고, 검색어를 칠 때마다 그 글자에서 찾는다. 검색용 글자는 글마다 처음 한 번만 만들어 `searchIndexOf`의 `WeakMap`에 보관한다. `WeakMap`은 객체를 키로 쓰는 JavaScript 맵이고, 키 객체(여기서는 글 객체)가 더 이상 쓰이지 않으면 값도 함께 메모리에서 정리된다. 글 객체가 같으면 다시 만들지 않고 보관한 값을 돌려준다.

| 호출                              | 동작                                   |
| --------------------------------- | -------------------------------------- |
| `searchIndexOf(post)` 첫 호출     | 검색용 글자를 만들어 `WeakMap`에 보관  |
| `searchIndexOf(post)` 두 번째부터 | 보관한 같은 객체를 반환                |
| `searchIndexOf({ ...post })`      | 새 객체라 키가 달라 처음부터 다시 생성 |

시험은 이 보관이 동작하는지를 절대 시간(검색 한 번 평균 5ms 미만)으로 확인했다. 같은 코드가 Mac에서는 0.2ms, GitHub 공유 러너에서는 5ms 안팎이고, 러너가 느린 순간에는 기준을 넘는다. 위 로그의 5.46ms가 그 경우다.

> [!IMPORTANT] 시험이 지키려던 것은 속도가 아니라 캐시
> 검색용 글자는 글마다 처음 한 번만 만들고, 글자를 칠 때마다 다시 만들지 않는다. 절대 시간으로 이 성질을 확인하면 ==러너 속도까지 함께 시험한다==.

### 고친 방법

시험 하나를 둘로 나눴다.

| 시험               | 확인하는 것                                                                                                                                   | 러너 속도의 영향              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| 검색용 글자 재사용 | 검색어를 10번 반복해 친 뒤에도 글 240편의 `searchIndexOf(post)`가 처음 만든 객체와 같다(`===`)                                                | 없음 (시간을 재지 않는다)     |
| 상대 비교          | 새 글 객체 240개의 검색용 글자를 처음부터 만드는 시간(`build`)과 검색 한 번의 평균 시간(`perQuery`)을 같은 실행에서 재 `perQuery < build / 5` | 두 값에 같이 걸려 비율은 유지 |

첫 시험은 객체 동일성을 직접 비교한다. JavaScript의 `===`는 두 객체가 메모리에서 같은 객체일 때만 `true`이므로, 캐시가 동작하면 열 번 검색한 뒤에도 같은 객체가 나오고, 검색마다 새로 만들면 내용이 같아도 `false`가 된다.

```ts
// packages/desktop-core/src/memo/search.test.ts (#414)
it('검색용 글자는 글마다 처음 한 번만 만들고, 검색어를 칠 때마다 같은 것을 그대로 쓴다', () => {
	typeAll();
	const built = many.map(searchIndexOf);
	for (let round = 0; round < 10; round++) typeAll();
	expect(many.every((item, i) => searchIndexOf(item) === built[i])).toBe(true);
});
```

둘째 시험은 시간을 재되, 기준을 고정된 숫자 대신 같은 실행 안에서 잰 다른 값으로 잡는다. `{ ...item }`으로 복사한 새 글 객체 240개는 `WeakMap`에 키가 없어 검색용 글자를 처음부터 만든다. 이 시간(`build`)과, 보관한 검색용 글자로 검색 한 번에 걸리는 평균 시간(`perQuery`)을 비교한다.

```ts
const fresh = many.map((item) => ({ ...item }));
const buildStart = Date.now();
for (const item of fresh) searchIndexOf(item);
const build = Date.now() - buildStart;
// … 검색어를 10번 반복해 치며 perQuery를 잰다
expect(perQuery).toBeLessThan(build / 5);
```

![절대 시간 기준과 상대 비교](./images/day-1106-relative-check.svg '절대 기준은 러너 속도에 따라 넘나든다. 상대 비교는 두 값이 함께 느려져 비율이 유지되고, 캐시가 깨질 때만 비율이 무너진다')

Mac에서 잰 값은 아래와 같다.

| 값                 | Mac 측정    |
| ------------------ | ----------- |
| `build`            | 10~14ms     |
| `perQuery`         | 0.21~0.23ms |
| `build / perQuery` | 48~62배     |
| 시험 기준          | 5배 초과    |

==캐시가 깨져 검색마다 검색용 글자를 다시 만들면 `perQuery`가 `build`와 비슷해져== 비율이 1배 근처로 떨어지고 두 번째 시험이 실패한다. 러너가 느리면 `build`와 `perQuery`가 함께 느려지므로 48~62배라는 비율은 5배 기준과 거리가 크다.

시간 측정 함수는 `Date.now()`를 그대로 썼다. 브라우저의 `performance.now()`는 밀리초 아래까지 재지만, desktop-core는 브라우저 밖에서도 쓰는 패키지라 tsconfig에 DOM 타입 정의(`lib: ["DOM"]`)를 넣지 않았다. 고친 뒤 `search.test.ts` 24건을 5회 반복 실행해 모두 통과했다.

## 돌아보며

1. 캐시를 지키려던 시험이 절대 시간을 재서 러너 속도까지 시험했다. 확인하려는 성질은 객체 동일성(`===`)처럼 직접 검사하고, 시간이 꼭 필요하면 같은 실행 안의 두 값을 비교한다.
2. `deploy`가 `check`에 걸려 있어, 코드와 무관한 시험 한 건의 실패가 그날 머지한 기능 전체의 배포를 막았다.
3. 10월 30일·31일의 임베드 편집 시험과 스크롤 복원 시험에 이어, 시간과 순서에 기대는 시험을 또 고쳤다.
