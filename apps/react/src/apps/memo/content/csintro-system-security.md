## 들어가기 전에

시스템(system)은 예전에는 하드웨어 한 대에 설치된 운영체제와 프로그램을 뜻했다. 지금은 웹 서버, 데이터베이스, 네트워크 장비가 서로 연결되어 하나의 서비스를 이루므로, 시스템의 경계가 흐려져 네트워크 전체를 하나의 시스템으로 보기도 한다. 시스템 보안은 이 시스템을 허가받은 사람만, 허가받은 범위 안에서 쓰도록 만들고, 그 사용 기록을 남겨 문제가 생겼을 때 추적할 수 있게 하는 일이다.

시스템 보안은 보통 여섯 가지 관리 항목으로 나누어 다룬다.

| 항목        | 질문                                            | 예                                   |
| ----------- | ----------------------------------------------- | ------------------------------------ |
| 계정 관리   | 접속한 사람이 누구인가                          | 아이디와 비밀번호, 지문              |
| 세션 관리   | 로그인한 뒤의 연결을 그 사람이 계속 쓰고 있는가 | 일정 시간 후 자동 로그아웃           |
| 접근 제어   | 어디에서 접속할 수 있는가                       | 특정 IP에서만 데이터베이스 접속 허용 |
| 권한 관리   | 접속한 사람이 무엇을 할 수 있는가               | 파일 읽기만 허용, 쓰기 금지          |
| 로그 관리   | 누가 언제 무엇을 했는가                         | 로그인 실패 기록                     |
| 취약점 관리 | 시스템 자체에 결함은 없는가                     | 보안 업데이트 적용                   |

![사용자가 접근 제어, 계정 관리, 세션 관리, 권한 관리를 차례로 거쳐 시스템을 쓰고, 로그 관리가 모든 단계를 기록하며, 취약점 관리가 이 통제를 우회하지 못하게 받친다](./images/csintro-system-security-six-areas.svg '여섯 항목은 사용자가 시스템에 들어와 작업하는 순서와 대응한다')

여섯 항목은 따로 떨어진 것이 아니라 서로를 보완한다. 예를 들어 비밀번호가 유출되어 계정 관리가 뚫려도, 접근 제어가 사내 IP에서만 접속을 허용하면 공격자는 밖에서 로그인하지 못한다. 공격자가 그 장벽마저 넘었더라도 권한 관리가 일반 계정에 최소 권한만 주었다면 피해 범위가 좁아지고, 로그 관리가 남긴 기록으로 침입 경로를 찾을 수 있다. 이처럼 ==여러 겹의 통제를 쌓아 한 겹이 뚫려도 다음 겹이 막도록 설계하는 것을 심층 방어(defense in depth)라고 한다==.

이 글은 이 순서로 설명하고, 마지막에 가장 오래되고 대표적인 취약점인 버퍼 오버플로를 다룬다. 필요한 배경은 리눅스나 macOS 터미널에서 명령을 입력해 본 경험 정도다. 네트워크 수준의 접근 제어는 [방화벽의 종류와 iptables 규칙](/memo/net-firewall)에서 자세히 다룬다.

## 계정 관리

### 인증의 네 가지 요소

시스템에 접속하려는 사람이 주장하는 신원이 맞는지 확인하는 과정을 인증(authentication)이라고 한다. 인증에 쓰는 정보는 네 종류로 나뉜다.

| 요소                       | 설명                            | 예                                       |
| -------------------------- | ------------------------------- | ---------------------------------------- |
| 알고 있는 것(knowledge)    | 머릿속에 기억하는 정보          | 비밀번호, PIN                            |
| 가지고 있는 것(possession) | 본인만 소지한 물건              | 출입 카드, OTP 생성기, 스마트폰 인증 앱  |
| 본인의 특징(inherence)     | 신체적·행동적 특징              | 지문, 얼굴, 홍채                         |
| 위치하는 곳(location)      | 접속을 시도하는 장소가 적절한지 | 사내망 IP, 등록된 전화번호로 되거는 콜백 |

네 번째 요소인 '위치하는 곳'은 접속을 시도하는 위치가 적절한지 확인하는 방식이다. 전통적인 예가 콜백(call back)으로, 사용자가 전화 접속으로 시스템에 연결하면 시스템이 일단 연결을 끊고 미리 등록된 전화번호로 다시 걸어 등록된 장소에서 접속한 것이 맞는지 확인했다. 지금은 해외 IP에서 로그인하면 추가 인증을 요구하거나, 회사 네트워크 안에서만 업무 시스템 로그인을 허용하는 형태로 쓰인다.

| 요소           | 장점                          | 약점                                                      |
| -------------- | ----------------------------- | --------------------------------------------------------- |
| 알고 있는 것   | 비용이 없고 바꾸기 쉽다       | 잊어버리거나, 추측·피싱·유출로 남에게 알려질 수 있다      |
| 가지고 있는 것 | 원격 공격자가 복제하기 어렵다 | 분실·도난, 장치를 사고 관리하는 비용                      |
| 본인의 특징    | 잊어버리거나 빌려줄 수 없다   | 유출되면 바꿀 수 없다. 오인식률(FAR)과 거부율(FRR)이 있다 |
| 위치하는 곳    | 사용자가 할 일이 없다         | VPN 등으로 위치를 속일 수 있어 단독으로 쓰기 어렵다       |

서로 다른 종류의 요소를 두 가지 이상 함께 쓰는 방식을 다중 요소 인증(MFA)이라고 한다. 은행 앱에서 비밀번호(알고 있는 것)를 입력한 뒤 스마트폰으로 받은 일회용 번호(가지고 있는 것)를 입력하는 것이 예다. ==비밀번호를 두 번 묻는 것은 같은 종류의 요소이므로 다중 요소 인증이 아니다==. 생체 인식 방식별 원리는 [모바일 플랫폼과 유비쿼터스 컴퓨팅, 사물인터넷·클라우드·빅데이터의 구조](/memo/csintro-mobile-future-computing)에서 다룬다.

### OTP는 어떻게 매번 다른 번호를 만드는가

'가지고 있는 것'의 대표인 OTP(one-time password) 앱은 인터넷에 연결되지 않아도 서버와 같은 번호를 만들어 낸다. 가장 널리 쓰는 TOTP(time-based OTP, RFC 6238)는 다음 원리로 동작한다.

![인증 앱과 서버가 등록 시 공유한 비밀 키 K와 현재 시각의 30초 단위 번호 T로 각각 HMAC을 계산해 같은 6자리 번호를 얻고, 사용자가 앱의 번호를 입력하면 서버가 자신이 계산한 값과 비교한다](./images/csintro-system-security-totp.svg '서버와 앱이 같은 재료로 같은 계산을 하므로 통신이 필요 없다')

1. 처음 등록할 때 서버가 계정마다 무작위 비밀 키 `K`를 만들어 QR 코드로 보여 주고, 앱이 이를 저장한다.
2. 로그인할 때 앱과 서버는 각자 현재 유닉스 시각(1970년 1월 1일부터 지난 초)을 30으로 나눈 몫 `T`를 계산한다.

```math
T = \left\lfloor \frac{\text{현재 유닉스 시각}}{30} \right\rfloor
```

3. `K`와 `T`를 해시 기반 메시지 인증 코드 HMAC-SHA1에 넣어 20바이트 값을 얻고, 그중 4바이트를 골라 정수로 바꾼 뒤 `10^6{:math}`으로 나눈 나머지를 6자리 번호로 쓴다.

예를 들어 현재 시각이 1,750,000,000초이면 `T = \lfloor 1{,}750{,}000{,}000 / 30 \rfloor = 58{,}333{,}333{:math}`이다. 30초가 지나 1,750,000,030초가 되면 `T{:math}`가 58,333,334로 바뀌어 전혀 다른 번호가 나온다. ==번호를 엿보더라도 30초 뒤에는 쓸모가 없고==, 번호에서 거꾸로 `K`를 계산할 수도 없다. 다만 사용자를 속여 가짜 사이트에 번호를 입력하게 하는 실시간 피싱은 막지 못하므로, 접속한 사이트의 주소까지 확인하는 패스키(passkey) 같은 방식이 함께 쓰인다.

### 윈도우의 계정과 그룹

윈도우는 사용자를 그룹으로 묶고 그룹에 권한을 준다. 명령 프롬프트에서 다음 명령으로 그룹 목록과 구성원을 확인한다.

```bat
net localgroup
net localgroup Administrators
```

| 그룹             | 권한                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Administrators   | 시스템의 모든 설정을 바꿀 수 있는 관리자 그룹                                                                                                                                                              |
| Users            | 일반 사용자. 프로그램 실행은 되지만 시스템 설정 변경 불가                                                                                                                                                  |
| Guests           | 임시 사용자. Users보다 더 제한됨. 기본 비활성화                                                                                                                                                            |
| Backup Operators | 권한과 관계없이 파일을 백업·복원할 수 있음. 로컬 로그인과 시스템 종료 가능                                                                                                                                 |
| Power Users      | Administrators 권한 대부분을 가지지만 로컬 컴퓨터에서만 관리 가능. 그 컴퓨터 밖의 네트워크에서는 일반 사용자. Windows 7 이후에는 XP에서 업그레이드한 컴퓨터와의 호환성을 위해 남아 있고 관리 권한은 제한적 |

도메인 컨트롤러의 기본 정책에서는 Users와 Guests 그룹의 구성원이 네트워크를 통해 서버에 접근할 수 있지만, 서버 앞에 앉아 직접 로그인하는 로컬 로그인은 허용되지 않는다. 관리자 그룹 구성원을 확인하면 다음과 같이 나온다.

```text
C:\Users\Administrator>net localgroup administrators
별칭     administrators
설명     컴퓨터 도메인에 모든 액세스 권한을 가진 관리자입니다.

구성원
-------------------------------------------------------------------------------
Administrator
명령을 잘 실행했습니다.
```

구성원 목록에 모르는 계정이 있다면 공격자가 관리자 계정을 만들어 둔 것일 수 있다.

![명령 프롬프트에서 net localgroup administrators를 실행해 별칭 administrators, 설명, 구성원 Administrator가 출력된 화면](./images/csintro-system-security-net-localgroup.jpg 'Windows에서 관리자 그룹 구성원을 확인한 결과. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

Administrators 그룹의 구성원 수는 최소한으로 유지한다. 관리자도 평소에는 일반 계정으로 작업하고, 설정을 바꿀 때만 사용자 계정 컨트롤(UAC) 확인 창을 거쳐 관리자 권한을 쓴다.

### 유닉스의 계정: /etc/passwd와 /etc/shadow

유닉스 계열 운영체제(리눅스 포함)는 계정 정보를 `/etc/passwd` 파일에 한 줄에 한 계정씩 저장한다.

![/etc/passwd의 root 계정 줄을 콜론으로 나눈 일곱 필드: 사용자 이름, 비밀번호 자리 x, UID 0, GID 0, 설명, 홈 디렉터리 /root, 로그인 셸 /bin/bash](./images/csintro-system-security-passwd.svg '세 번째 필드인 UID가 0이면 이름과 관계없이 관리자다')

![리눅스 터미널에서 cat /etc/passwd를 실행해 root, bin, daemon, adm, lp, sync, shutdown, halt, mail, ftp, nobody 등 계정이 콜론으로 구분된 일곱 필드로 출력된 화면. 대부분 셸이 /sbin/nologin이다](./images/csintro-system-security-etc-passwd.jpg '리눅스의 /etc/passwd. 두 번째 필드가 모두 x이고, 시스템 계정은 /sbin/nologin으로 로그인을 막는다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

UID(user ID)는 운영체제가 사용자를 구별하는 번호다. ==커널은 이름이 아니라 UID로 권한을 판단하므로==, 이름이 `root`가 아니어도 UID가 0이면 관리자 권한을 갖는다. 공격자가 침입한 뒤 UID가 0인 계정을 몰래 추가하는 경우가 있으므로, 다음 명령으로 UID 0 계정이 root 하나뿐인지 확인한다.

```bash
awk -F: '$3 == 0 { print $1 }' /etc/passwd
```

초기 유닉스는 두 번째 필드에 비밀번호 해시를 그대로 적었다. 그런데 `/etc/passwd`는 사용자 이름과 UID를 조회하려고 모든 사용자가 읽을 수 있어야 하므로, 누구나 해시를 가져가 오프라인에서 비밀번호를 추측해 볼 수 있었다. 그래서 ==해시를 root만 읽을 수 있는 `/etc/shadow`로 옮기고== 원래 자리에는 `x`만 남겼다. 해시는 원래 값으로 되돌릴 수 없는 일방향 함수로 계산한 값이며, 로그인할 때 입력한 비밀번호를 같은 방식으로 해시해 저장된 값과 비교한다.

![입력한 비밀번호와 shadow에 저장된 솔트를 해시 함수에 넣어 계산한 해시가 shadow의 저장된 해시와 같으면 로그인에 성공한다](./images/csintro-system-security-hash-login.svg '시스템은 비밀번호 원문을 몰라도 맞는지 확인할 수 있다')

`/etc/shadow`의 한 줄은 다음과 같다.

```text
alice:$6$Qw8z1kLp$9fT2Vx...a1:20100:0:99999:7:::
```

| 필드 | 값                  | 뜻                                                                            |
| ---- | ------------------- | ----------------------------------------------------------------------------- |
| 1    | `alice`             | 사용자 이름                                                                   |
| 2    | `$6$Qw8z1kLp$9fT2…` | `$알고리즘$솔트$해시`. `6`은 SHA-512, `y`는 yescrypt, `!`나 `*`는 로그인 불가 |
| 3    | `20100`             | 마지막으로 비밀번호를 바꾼 날(1970년 1월 1일부터 지난 일수)                   |
| 4, 5 | `0`, `99999`        | 비밀번호를 다시 바꿀 수 있기까지 최소 일수, 반드시 바꿔야 하는 최대 일수      |
| 6    | `7`                 | 만료 며칠 전부터 경고할지                                                     |

솔트(salt)는 계정마다 다르게 정하는 무작위 문자열로, 비밀번호와 함께 해시한다. 솔트가 없으면 같은 비밀번호는 항상 같은 해시가 되므로, 공격자는 흔한 비밀번호 수억 개의 해시를 미리 계산한 표(레인보 테이블)를 만들어 두고 찾아보기만 하면 된다. 솔트가 붙으면 ==계정마다 표를 새로 만들어야 하므로 이 방법이 소용없어진다==.

그룹은 `/etc/group`에 저장된다.

```text
root:x:0:
wheel:x:10:alice,bob
```

필드는 차례로 그룹 이름, 그룹 비밀번호(거의 쓰지 않음), GID, 그 그룹에 추가로 속한 계정 목록이다. 위 예에서 alice와 bob은 wheel 그룹에 속해 `sudo`로 관리자 명령을 실행할 수 있다. GID 0은 root 그룹이다.

macOS의 `/etc/group`에서 몇 줄을 골라 보면 다음과 같다.

```text
wheel:*:0:root
staff:*:20:root
admin:*:80:root
certusers:*:29:root,_jabber,_postfix,_cyrus,_calendar,_dovecot
_postgres:*:216:_devicemgr,_calendar,_teamsserver,_xserverdocs
com.apple.access_ssh:*:399:
```

마지막 필드에 계정 이름이 여러 개면 그 계정들이 모두 그 그룹에 속한다. `certusers` 그룹에는 인증서 파일을 읽어야 하는 메일·메신저 서비스 계정들이 묶여 있다. 파일 하나를 여러 서비스가 읽어야 할 때 파일을 모두에게 공개하지 않고 그룹 권한으로 필요한 서비스만 읽게 만드는 방식이다. `com.apple.access_ssh`는 원격 로그인(SSH)을 허용할 사용자를 담는 그룹으로, 시스템 설정의 공유 → 원격 로그인에서 "다음 사용자만"을 고르면 이 그룹이 채워진다.

macOS에서 `cat /etc/passwd`를 실행하면 다음과 같은 줄이 이어진다.

```text
nobody:*:-2:-2:Unprivileged User:/var/empty:/usr/bin/false
root:*:0:0:System Administrator:/var/root:/bin/sh
daemon:*:1:1:System Services:/var/root:/usr/bin/false
_uucp:*:4:4:Unix to Unix Copy Protocol:/var/spool/uucp:/usr/sbin/uucico
_www:*:70:70:World Wide Web Server:/Library/WebServer:/usr/bin/false
_mysql:*:74:74:MySQL Server:/var/empty:/usr/bin/false
_sshd:*:75:75:sshd Privilege separation:/var/empty:/usr/bin/false
_spotlight:*:89:89:Spotlight:/var/empty:/usr/bin/false
_softwareupdate:*:200:200:Software Update Service:/var/db/softwareupdate:/usr/bin/false
```

이 출력에서 읽을 수 있는 점은 다음과 같다.

1. 두 번째 필드가 모두 `*`다. macOS는 비밀번호 해시를 이 파일에도 shadow 파일에도 두지 않고 디렉터리 서비스 데이터베이스에 저장한다.
2. 밑줄(`_`)로 시작하는 계정이 수십 개 있다. 웹 서버, 데이터베이스, Spotlight 같은 서비스마다 전용 계정을 두어, 한 서비스가 공격당해도 그 서비스의 권한만큼만 피해가 나게 한 것이다. 최소 권한의 원칙을 계정 수준에서 적용한 예다.
3. 이 계정들의 셸은 `/usr/bin/false`다. 이 프로그램은 아무것도 하지 않고 실패 코드를 돌려주므로, 누군가 이 계정으로 로그인하더라도 명령을 입력할 셸이 열리지 않는다. 리눅스에서는 `/sbin/nologin`이 같은 역할을 한다.
4. `nobody`의 UID는 -2로, 아무 파일도 소유하지 않은 가장 낮은 권한의 사용자다. 네트워크 파일 시스템에서 원격 root 요청을 이 사용자로 바꿔 처리한다.

리눅스의 `/etc/passwd`도 구조는 같다. root(UID 0) 다음에 `bin`, `daemon`, `adm`, `lp`, `mail`, `ftp` 같은 시스템 계정이 낮은 UID로 이어지고, 대부분 셸이 `/sbin/nologin`이다. 일반 사용자는 배포판에 따라 UID 1000(예전에는 500)부터 시작하고 홈 디렉터리는 `/home` 아래에 만들어진다.

> [!NOTE] macOS의 계정 정보
> macOS의 `/etc/passwd`에는 단일 사용자 모드에서 쓰는 시스템 계정만 들어 있다. 실제 사용자 계정은 디렉터리 서비스(Open Directory)가 관리하므로 `dscl . -list /Users UniqueID`나 `id` 명령으로 확인한다. 일반 사용자의 UID는 501부터 시작하고, 관리자 그룹 이름은 `admin`이다.

### 데이터베이스, 응용 프로그램, 네트워크 장비의 계정

운영체제 밖에도 관리자 계정이 있다. MS-SQL Server의 기본 관리자 계정은 `sa`(system administrator)이고, 오라클에는 `SYS`와 `SYSTEM`이 있다. `SYS`는 데이터 사전(데이터베이스 자체의 정보를 담은 테이블)을 소유하고 데이터베이스 생성·종료 같은 SYSDBA 권한 작업을 할 수 있는 반면, `SYSTEM`은 일반 관리 작업만 할 수 있다. 이런 기본 관리자 계정은 이름이 널리 알려져 있어 공격 대상이 되므로, 설치 직후 비밀번호를 바꾸고 쓰지 않으면 잠근다.

응용 프로그램의 계정도 관리 대상이다. 웹 응용 프로그램의 관리자 페이지가 기본 비밀번호로 열려 있으면, 공격자는 그곳에서 서버의 파일을 올리거나 설정 정보를 얻어 운영체제까지 공격할 수 있다. 라우터·스위치 같은 네트워크 장비는 장비 자체에 사용자 개념이 약하지만, 계정별로 실행할 수 있는 명령을 제한할 수 있다. 장비가 많은 대규모 네트워크에서는 TACACS+나 RADIUS 같은 인증 서버로 계정을 한곳에서 관리한다.

### 비밀번호 관리

추측하기 쉬운 비밀번호는 다음과 같다.

- 길이가 짧거나 비어 있는 비밀번호
- 사전에 나오는 단어나 그 조합(`password`, `sunshine`)
- 키보드 배열 순서(`qwerty`, `1q2w3e4r`)
- 아이디, 생일, 전화번호처럼 사용자 정보에서 유추할 수 있는 값

공격자는 유출된 비밀번호 목록과 사전 단어를 조합해 초당 수십억 개의 후보를 시험하는 도구를 쓴다. ==비밀번호의 안전성을 결정하는 가장 큰 요소는 길이다==. 예를 들어 소문자 26개만 쓰는 8자리 비밀번호의 경우의 수는 `26^{8} \approx 2.1 \times 10^{11}{:math}`이지만, 16자리면 `26^{16} \approx 4.4 \times 10^{22}{:math}`로 약 2천억 배가 된다.

해시를 빼낸 공격자가 그래픽 카드로 초당 `10^{10}{:math}`(100억)개의 후보를 시험한다고 하면, 모든 경우를 다 시험하는 데 걸리는 최대 시간은 다음과 같다. 문자 종류가 `c{:math}`개, 길이가 `n{:math}`이면 경우의 수는 `c^{n}{:math}`이다.

| 문자 종류                    | 길이 | 경우의 수                   | 최대 소요 시간 |
| ---------------------------- | ---- | --------------------------- | -------------- |
| 숫자 10개                    | 6    | `10^6{:math}`               | 0.0001초       |
| 소문자 26개                  | 8    | `2.1 \times 10^{11}{:math}` | 21초           |
| 대소문자·숫자·특수 문자 94개 | 8    | `6.1 \times 10^{15}{:math}` | 약 7일         |
| 소문자 26개                  | 12   | `9.5 \times 10^{16}{:math}` | 약 110일       |
| 소문자 26개                  | 16   | `4.4 \times 10^{22}{:math}` | 약 14만 년     |

8자리에 온갖 문자를 섞는 것보다 ==소문자만으로 16자리를 만드는 편이 훨씬 안전하다==는 것을 알 수 있다. 이 계산은 무작위로 고른 비밀번호를 가정한 것이고, `Summer2025!`처럼 사람이 만든 패턴은 사전 공격으로 몇 초 만에 풀린다. 그래서 시스템 쪽에서는 bcrypt, scrypt, yescrypt처럼 일부러 계산을 느리게 만든 해시 함수를 써서 초당 시험 횟수 자체를 줄인다.

미국 NIST의 디지털 신원 지침 SP 800-63B는 비밀번호 정책을 다음과 같이 권고한다.

| 항목           | 권고                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------ |
| 길이           | 비밀번호만으로 인증하면 15자 이상, 다중 요소 인증의 한 요소로 쓰면 8자 이상. 최대 64자 이상 허용 |
| 차단 목록      | 유출된 비밀번호, 사전 단어, 반복·연속 문자열은 등록 거부                                         |
| 조합 규칙      | "대문자·숫자·특수 문자를 섞어라" 같은 규칙을 강제하지 않는다                                     |
| 주기적 변경    | 정해진 주기마다 바꾸라고 강제하지 않는다. 유출 정황이 있을 때만 바꾸게 한다                      |
| 반복 실패 제한 | 연속 실패 횟수를 제한해 온라인 추측 공격을 막는다                                                |

조합 규칙과 주기적 변경을 강제하면 사용자는 `Password1!`을 `Password2!`로 바꾸는 식으로 예측 가능한 패턴을 만들기 때문에, 오히려 안전성이 떨어진다는 연구 결과가 반영된 것이다. 기억하기 쉬우면서 추측하기 어려운 비밀번호로는 서로 관련 없는 단어 여러 개를 이은 긴 문장이 적합하고, 서비스마다 다른 비밀번호를 쓰려면 비밀번호 관리자를 쓴다.

계정 잠금은 일정 횟수 이상 틀리면 계정을 일정 시간 쓰지 못하게 해 무차별 대입(brute force) 공격을 막는다. 다만 잠금 시간이 너무 길면 공격자가 일부러 틀려 정상 사용자를 접속하지 못하게 할 수 있으므로, 영구 잠금보다는 점점 늘어나는 대기 시간이나 CAPTCHA를 함께 쓴다.

## 세션 관리

세션(session)은 사용자와 시스템, 또는 두 시스템 사이에 인증을 거쳐 맺어진 연결이 유지되는 상태다. 웹에서는 로그인에 성공하면 서버가 세션 식별자를 발급해 쿠키로 보내고, 브라우저는 이후 요청마다 이 쿠키를 함께 보내 로그인 상태를 유지한다.

![브라우저가 아이디와 비밀번호로 로그인하면 서버가 Set-Cookie로 세션 식별자를 보내고, 이후 요청마다 쿠키가 함께 가는데, 이를 스니핑한 공격자가 같은 식별자로 서버에 요청해 사용자로 행세한다](./images/csintro-system-security-session.svg '세션 식별자는 로그인 이후 비밀번호와 같은 역할을 한다')

HTTP는 요청 하나하나가 독립적인 프로토콜이라, 서버는 방금 로그인한 사람과 다음 요청을 보낸 사람이 같은지 스스로 알 수 없다. 그래서 로그인에 성공하면 추측할 수 없는 긴 무작위 값을 세션 식별자로 만들어 브라우저에 맡기고, 이후 요청에 그 값이 붙어 오면 같은 사용자로 간주한다.

==세션 식별자를 가로채면 비밀번호를 몰라도 그 사용자로 행세할 수 있다==. 이를 세션 하이재킹(session hijacking)이라고 한다. 같은 네트워크에서 암호화되지 않은 트래픽을 엿보는 패킷 스니핑이 대표적인 수단이다. 대책은 다음과 같다.

- **전 구간 암호화**: HTTPS로 통신해 세션 쿠키가 평문으로 네트워크에 흐르지 않게 한다. 패킷 스니핑의 원리는 [패킷 스니핑과 스푸핑, pcap과 원시 소켓의 이해](/memo/net-sniffing-spoofing)에서 다룬다.
- **세션 만료**: 일정 시간 동안 아무 입력이 없으면 세션을 끊는다. 은행 사이트가 10분 동안 조작이 없으면 자동으로 로그아웃하는 것이 예다.
- **쿠키 속성**: 세션 쿠키에 `Secure`(HTTPS에서만 전송), `HttpOnly`(자바스크립트에서 읽지 못함), `SameSite`(다른 사이트에서 보낸 요청에는 붙이지 않음) 속성을 붙인다. 웹 페이지에 끼워 넣은 악성 스크립트가 `document.cookie`로 세션 값을 훔쳐 가는 공격을 `HttpOnly`가 막는다.
- **로그인 시 식별자 재발급**: 로그인 전에 쓰던 식별자를 로그인 후에도 그대로 쓰면, 공격자가 미리 정해 둔 식별자를 피해자에게 심어 두는 세션 고정(session fixation) 공격이 가능하다. 로그인에 성공하면 식별자를 새로 만든다.
- **재인증**: 중요한 작업 직전에 다시 인증을 요구해, 세션을 가로챈 사람이 처음 인증한 사용자와 같은지 확인한다. 이체할 때 인증서 비밀번호나 OTP를 다시 묻는 것, 비밀번호를 바꿀 때 현재 비밀번호를 묻는 것, 비밀번호 만료 후 재설정을 요구하는 것이 모두 여기에 속한다.

## 접근 제어

접근 제어(access control)는 적절한 권한을 가진 주체만 특정 시스템이나 정보에 접근하도록 통제하는 것이다. ==네트워크 관점에서 가장 기본적인 수단은 IP 주소와 서비스 포트다==. "데이터베이스 서버의 1521번 포트에는 웹 서버 두 대의 IP만 접속할 수 있다"는 규칙이 예다.

### 운영체제의 접근 제어

서버를 원격으로 관리하는 통로는 공격자가 가장 먼저 노리는 곳이다. 운영체제별로 흔히 쓰는 관리 인터페이스는 다음과 같다.

| 운영체제      | 서비스                       | 기본 포트          | 특징                                                     |
| ------------- | ---------------------------- | ------------------ | -------------------------------------------------------- |
| 유닉스·리눅스 | 텔넷(Telnet)                 | TCP 23             | 비밀번호까지 평문으로 전송. 쓰지 않는다                  |
|               | SSH                          | TCP 22             | 전 구간 암호화. 파일 전송(SFTP, scp)도 같은 연결로 가능  |
|               | XDMCP / X11                  | UDP 177 / TCP 6000 | 원격 그래픽 로그인. 암호화되지 않아 SSH 터널 안에서 쓴다 |
|               | FTP                          | TCP 21             | 파일 전송. 평문이므로 SFTP로 대체                        |
| 윈도우        | 원격 데스크톱(RDP)           | TCP 3389           | 터미널 서비스. 포트 변경 가능                            |
|               | VNC, Radmin 등 GUI 관리 도구 | TCP 5900 등        | 제3자 원격 제어 프로그램                                 |

텔넷과 FTP처럼 암호화하지 않는 프로토콜은 쓰지 않는다. SSH와 RDP는 인터넷 전체에 열어 두면 하루에도 수천 번의 비밀번호 대입 시도가 들어오므로, 관리자 PC의 IP나 VPN 대역에서만 접속을 허용하도록 방화벽 규칙을 둔다. 리눅스에서는 `/etc/hosts.allow`와 `/etc/hosts.deny`(TCP Wrapper)나 `sshd_config`의 `AllowUsers`로도 접속을 제한할 수 있다.

```text
# /etc/ssh/sshd_config
# root로 직접 로그인 금지
PermitRootLogin no
# 비밀번호 대신 공개 키 인증만 허용
PasswordAuthentication no
# alice가 192.0.2.0/24 대역에서 접속할 때만 허용
AllowUsers alice@192.0.2.*
```

### 데이터베이스의 접근 제어

오라클은 `$ORACLE_HOME/network/admin/sqlnet.ora` 파일에서 접속을 허용할 IP를 지정한다. 다음 설정은 `192.0.2.10`과 `192.0.2.20`에서만 접속을 허용한다.

```text
tcp.validnode_checking = yes
tcp.invited_nodes = (192.0.2.10, 192.0.2.20)
```

![터미널에서 cat sqlnet.ora를 실행해 파일 경로 /opt/oracle/11g/network/admin/sqlnet.ora와 NAMES.DIRECTORY_PATH=(TNSNAMES, EZCONNECT) 설정이 보이는 화면](./images/csintro-system-security-sqlnet.jpg '접근 제어 설정을 넣기 전의 sqlnet.ora. 여기에 tcp.invited_nodes 줄을 추가한다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

MS-SQL Server는 IP 기반 접근 제어 기능을 기본으로 제공하지 않으므로, 운영체제 방화벽이나 네트워크 방화벽으로 접근을 제한한다.

### 응용 프로그램과 네트워크 장비의 접근 제어

웹 서버인 IIS와 Apache, nginx도 IP 기반 접근 제어를 제공한다. 예를 들어 nginx는 관리자 페이지 경로에 `allow 192.0.2.0/24; deny all;`처럼 설정해 사내 대역에서만 열 수 있다.

네트워크 장비의 접근 제어는 두 가지다. 하나는 장비 관리 화면 자체에 접속할 수 있는 IP를 제한하는 것이고, 다른 하나는 장비를 지나가는 트래픽을 ACL(access control list)로 걸러 내는 것이다. ACL은 "출발지 IP, 목적지 IP, 포트가 이러면 허용 또는 거부"라는 규칙을 위에서부터 차례로 대조하는 목록이며, 방화벽의 패킷 필터링과 원리가 같다. 시스코 라우터의 확장 ACL 예는 다음과 같다.

```text
access-list 110 permit tcp 192.0.2.0 0.0.0.255 host 198.51.100.5 eq 22
access-list 110 deny   tcp any host 198.51.100.5 eq 22
access-list 110 permit ip any any
```

1. 192.0.2.0/24 대역에서 서버 198.51.100.5의 SSH(22번)로 가는 TCP 패킷은 허용한다.
2. 그 밖의 출발지에서 같은 서버의 22번으로 가는 패킷은 거부한다.
3. 나머지 트래픽은 모두 허용한다.

==규칙은 위에서부터 처음 일치하는 줄 하나만 적용되므로 순서가 중요하다==. 1번과 2번의 순서를 바꾸면 관리자 대역도 2번에 먼저 걸려 거부된다. 또 시스코 ACL은 목록 끝에 보이지 않는 "나머지 모두 거부"가 붙어 있어, 3번 줄이 없으면 다른 트래픽이 모두 막힌다.

### 접근 제어 모델

누가 접근 규칙을 정하는가에 따라 접근 제어는 세 가지 모델로 나뉜다.

| 모델                      | 규칙을 정하는 주체        | 예                                                                |
| ------------------------- | ------------------------- | ----------------------------------------------------------------- |
| 임의 접근 제어(DAC)       | 파일의 소유자             | 유닉스 rwx, NTFS 권한. 소유자가 `chmod`로 다른 사람에게 권한을 줌 |
| 강제 접근 제어(MAC)       | 시스템 관리자의 보안 정책 | 군사 시스템의 비밀 등급, SELinux. 소유자도 정책을 바꿀 수 없음    |
| 역할 기반 접근 제어(RBAC) | 역할(직무)에 권한을 붙임  | "회계 담당" 역할에 회계 시스템 권한을 주고 사람을 역할에 배정     |

일반 운영체제는 DAC를 기본으로 쓰고, 기업 업무 시스템은 사람이 부서를 옮길 때마다 권한을 일일이 고치지 않아도 되는 RBAC를 주로 쓴다.

## 권한 관리

접근 제어가 "어디에서 들어올 수 있는가"라면 권한 관리는 "들어온 뒤 무엇을 할 수 있는가"를 정한다. ==각 사용자에게 업무에 꼭 필요한 최소한의 권한만 주는 것을 최소 권한의 원칙(principle of least privilege)이라고 한다==.

### 윈도우 NTFS 권한

윈도우의 파일 시스템인 NTFS는 파일과 폴더마다 사용자·그룹별 권한을 지정한다. 파일 탐색기에서 폴더의 속성 → 보안 탭에서 확인할 수 있다.

| 권한           | 허용되는 작업                                                    |
| -------------- | ---------------------------------------------------------------- |
| 모든 권한      | 아래 전부 + 권한 설정 변경, 소유권 가져오기, 하위 폴더·파일 삭제 |
| 수정           | 읽기·쓰기·실행 + 폴더와 파일 삭제                                |
| 읽기 및 실행   | 내용 읽기 + 프로그램 실행                                        |
| 폴더 내용 보기 | 폴더 안의 파일과 하위 폴더 이름 보기(폴더에만 적용)              |
| 읽기           | 파일 내용, 속성, 권한 설정 보기                                  |
| 쓰기           | 새 파일·하위 폴더 만들기, 파일 내용 바꾸기                       |

![폴더 속성 창의 보안 탭에서 Authenticated Users, SYSTEM, Administrators, Users 그룹을 고르고, Users의 권한 목록에서 읽기 및 실행, 폴더 내용 보기, 읽기에 허용이 체크된 화면](./images/csintro-system-security-ntfs-dialog.jpg '임의의 폴더에 NTFS 권한을 설정하는 보안 탭. 권한마다 허용과 거부 열이 따로 있다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

여러 권한이 겹칠 때는 다음 규칙으로 최종 권한을 계산한다.

1. **권한은 누적된다.** 사용자 A가 "읽기" 권한을 가진 그룹 1과 "쓰기" 권한을 가진 그룹 2에 동시에 속하면, A는 읽기와 쓰기를 모두 할 수 있다.
2. **명시적으로 지정한 권한이 상위 폴더에서 상속된 권한보다 우선한다.** 폴더에서는 읽기만 허용해도, 그 안의 특정 파일에 쓰기를 직접 허용하면 그 파일은 쓸 수 있다.
3. **같은 수준에서는 거부가 허용보다 우선한다.** A가 속한 그룹 하나에 "쓰기 거부"가 있으면, 다른 그룹에서 쓰기를 허용해도 A는 쓸 수 없다.

![사용자 A가 읽기 허용 그룹과 쓰기 허용 그룹에 속하면 읽기와 쓰기가 모두 되고, 폴더에서 읽기만 허용해도 파일에 쓰기를 직접 허용하면 그 파일은 쓸 수 있으며, 한 그룹이 쓰기를 거부하면 다른 그룹의 허용과 관계없이 쓸 수 없다](./images/csintro-system-security-ntfs-rules.svg '여러 그룹에 속한 사용자의 최종 권한을 정하는 세 규칙')

거부 우선 규칙은 특정 사람만 콕 집어 막을 때 쓴다. 예를 들어 "영업부 공유 폴더는 영업부 그룹 전체에 수정 권한을 주되, 퇴사 예정자 그룹에는 쓰기 거부"를 걸면, 퇴사 예정자가 영업부 그룹에 남아 있어도 파일을 고치거나 지울 수 없다.

### 유닉스의 권한

유닉스는 파일마다 소유자(user), 소유 그룹(group), 그 외 사용자(others) 세 부류에 대해 읽기(r), 쓰기(w), 실행(x) 권한을 지정한다. `ls -l` 명령으로 확인한다.

```text
$ ls -l /etc
drwxr-xr-x  2 root root  4096 Nov 10 17:26 alternatives
-rw-r--r--  1 root root  2981 Mar  3 09:12 passwd
-rw-r-----  1 root shadow 1203 Mar  3 09:12 shadow
```

| 열  | 예             | 뜻                           |
| --- | -------------- | ---------------------------- |
| 1   | `drwxr-xr-x`   | 파일 종류 1글자 + 권한 9글자 |
| 2   | `2`            | 하드 링크 수                 |
| 3   | `root`         | 소유자                       |
| 4   | `root`         | 소유 그룹                    |
| 5   | `4096`         | 크기(바이트)                 |
| 6   | `Nov 10 17:26` | 마지막 수정 시각             |
| 7   | `alternatives` | 파일 이름                    |

첫 글자는 파일 종류를 나타낸다.

| 문자 | 파일 종류                                                  | 예                        |
| ---- | ---------------------------------------------------------- | ------------------------- |
| `-`  | 일반 파일(regular file)                                    | 문서, 프로그램, 설정 파일 |
| `d`  | 디렉터리(directory)                                        | `/etc`, `/home/alice`     |
| `l`  | 심볼릭 링크(symbolic link). 다른 파일을 가리키는 바로 가기 | `/bin` → `/usr/bin`       |
| `c`  | 문자 장치(character device). 버퍼 없이 한 글자씩 입출력    | 터미널 `/dev/tty`         |
| `b`  | 블록 장치(block device). 버퍼를 거쳐 블록 단위로 입출력    | 디스크 `/dev/sda`         |
| `s`  | 소켓(socket). 프로세스끼리 통신하는 통로                   | `/var/run/mDNSResponder`  |
| `p`  | 파이프(pipe). 한쪽이 쓴 데이터를 다른 쪽이 읽는 통로       | `mkfifo`로 만든 파일      |

두 번째 열인 링크 수는 그 파일에 연결된 이름(하드 링크)의 개수다. 디렉터리는 자기 자신을 가리키는 `.`과 하위 디렉터리마다 있는 `..`이 링크로 세어지므로, 하위 디렉터리가 없는 디렉터리의 링크 수는 2다. 세 번째 열의 소유자는 보통 파일을 만든 계정이고 파일 생성자나 관리자가 바꿀 수 있으며, 네 번째 열의 소유 그룹은 만든 계정이 속한 그룹이다.

나머지 아홉 글자는 세 글자씩 끊어 읽고, 각 권한을 2진수 한 자리로 보아 8진수로 바꿀 수 있다.

![drwxr-xr-x에서 파일 종류 d를 빼고 rwx, r-x, r-x를 각각 2진수 111, 101, 101로 보고 자릿값 4, 2, 1을 더해 7, 5, 5를 얻는 과정](./images/csintro-system-security-permission.svg '세 글자마다 r=4, w=2, x=1을 더한다')

1. `rwx`는 2진수 `111`이므로 `4 + 2 + 1 = 7{:math}`
2. `r-x`는 2진수 `101`이므로 `4 + 0 + 1 = 5{:math}`
3. 따라서 `rwxr-xr-x`는 `755`다.

| 8진수 | 문자열      | 흔한 용도                                           |
| ----- | ----------- | --------------------------------------------------- |
| 755   | `rwxr-xr-x` | 프로그램, 디렉터리: 누구나 실행·조회, 소유자만 수정 |
| 644   | `rw-r--r--` | 일반 파일: 누구나 읽기, 소유자만 수정               |
| 600   | `rw-------` | SSH 개인 키 같은 비밀 파일: 소유자만 읽기·쓰기      |
| 777   | `rwxrwxrwx` | 누구나 수정 가능. 보안상 쓰지 않는다                |

권한은 `chmod`로 바꾸고, 소유자는 `chown`으로 바꾼다.

```bash
chmod 600 ~/.ssh/id_ed25519   # 개인 키는 소유자만 읽기·쓰기
chmod o-w report.txt          # others의 쓰기 권한만 제거
```

위 `ls -l` 예시에서 `/etc/passwd`는 644로 누구나 읽을 수 있지만, `/etc/shadow`는 640이고 소유 그룹이 `shadow`라서 root와 shadow 그룹만 읽을 수 있다.

디렉터리에서 r, w, x의 뜻은 파일과 조금 다르다.

| 권한 | 파일에서          | 디렉터리에서                                         |
| ---- | ----------------- | ---------------------------------------------------- |
| r    | 내용 읽기         | 안에 있는 파일 이름 목록 보기(`ls`)                  |
| w    | 내용 고치기       | 안에 파일 만들기, 지우기, 이름 바꾸기                |
| x    | 프로그램으로 실행 | 안으로 들어가기(`cd`), 안의 파일에 이름으로 접근하기 |

==파일을 지울 수 있는지는 그 파일의 권한이 아니라 파일이 들어 있는 디렉터리의 w 권한이 결정한다==. 그래서 누구나 쓸 수 있는 `/tmp` 같은 디렉터리에서는 남의 파일을 지울 수 있는 문제가 생기는데, 이를 막는 것이 아래의 sticky 비트다.

### setuid, setgid, sticky 비트

rwx 아홉 글자 외에 특수 권한 비트 세 개가 더 있다.

![passwd 프로그램의 소유자 실행 자리에 s가 있으면 setuid, wall의 그룹 실행 자리에 s가 있으면 setgid, /tmp의 others 실행 자리에 t가 있으면 sticky 비트다](./images/csintro-system-security-special-bits.svg '특수 비트는 실행 권한 x 자리에 겹쳐 표시된다')

사용자가 자기 비밀번호를 바꾸는 `passwd` 명령은 root만 쓸 수 있는 `/etc/shadow`를 고쳐야 한다. 일반 사용자가 이 일을 할 수 있는 것은 `passwd` 프로그램에 setuid 비트가 있어 ==실행하는 동안 소유자인 root의 권한으로 동작하기 때문이다==. 편리한 대신 setuid 프로그램에 버퍼 오버플로 같은 결함이 있으면 일반 사용자가 root 권한을 얻을 수 있으므로, 공격자가 가장 먼저 찾는 대상이다. 다음 명령으로 시스템의 setuid 파일 목록을 확인하고, 목록에 없던 파일이 새로 생겼는지 점검한다.

```bash
find / -perm -4000 -type f 2>/dev/null
```

8진수로 쓸 때는 특수 비트를 맨 앞 자리에 붙인다. `chmod 4755 file`은 setuid + `rwxr-xr-x`, `chmod 1777 dir`은 sticky + `rwxrwxrwx`다.

### 새 파일의 기본 권한: umask

새로 만든 파일의 권한은 프로그램이 요청한 권한(파일은 보통 666, 디렉터리는 777)에서 umask에 있는 비트를 지운 값이다. umask가 022이면 다음과 같다.

| 구분     | 요청 | umask 022로 지우는 비트 | 결과              |
| -------- | ---- | ----------------------- | ----------------- |
| 파일     | 666  | 그룹·others의 w         | 644 (`rw-r--r--`) |
| 디렉터리 | 777  | 그룹·others의 w         | 755 (`rwxr-xr-x`) |

umask를 077로 두면 새 파일이 600, 새 디렉터리가 700이 되어 다른 사용자는 아무것도 볼 수 없다. 여러 사람이 함께 쓰는 서버에서 개인 파일을 보호할 때 쓴다.

## 로그 관리

### AAA

접근 통제를 설명하는 틀로 AAA를 쓴다.

| 단계                 | 질문                | 예                                                  |
| -------------------- | ------------------- | --------------------------------------------------- |
| 인증(Authentication) | 너는 누구인가       | 아이디와 비밀번호로 신원 확인                       |
| 인가(Authorization)  | 무엇을 할 수 있는가 | 인증된 사용자 alice에게 `/home/alice` 쓰기만 허용   |
| 기록(Accounting)     | 무엇을 했는가       | 로그인 시각, 실행한 명령, 접근한 파일을 로그로 남김 |

기록 단계에서 남긴 로그는 악의적인 행위를 한 사용자를 찾아내는 근거가 된다. ==어떤 행위를 한 주체를 로그로 추적할 수 있는 정도를 책임 추적성(accountability)이라고 하고==, 보안과 관련된 이벤트를 시간순으로 기록한 로그를 감사 추적(audit trail)이라고 한다. 모든 관리자가 `root` 계정 하나를 함께 쓰면 로그에 `root`만 남아 누가 한 일인지 알 수 없으므로, 관리자마다 개인 계정으로 로그인한 뒤 `sudo`를 쓰게 하는 것이 책임 추적성을 높이는 방법이다.

### 윈도우의 로그

윈도우는 로그를 이벤트(event)라고 부르며, 여러 구성 요소의 로그를 한곳에 모아 저장하는 중앙 집중 방식을 쓴다. 제어판 → 관리 도구 → 이벤트 뷰어(`eventvwr.msc`)에서 확인한다. 로그온 성공·실패 같은 보안 이벤트를 남기려면 로컬 보안 정책의 감사 정책(audit policy)을 켜야 한다.

![이벤트 뷰어의 Windows 로그 아래 보안 로그를 선택해 감사 성공 이벤트 4616, 4672, 4624, 4648 등이 날짜, 원본, 이벤트 ID, 작업 범주와 함께 나열되고 아래에 선택한 이벤트의 세부 내용이 보이는 화면](./images/csintro-system-security-eventviewer.jpg '이벤트 뷰어의 보안 로그. 4624는 로그온 성공, 4672는 관리자 권한 로그온, 4616은 시스템 시간 변경이다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

이벤트 뷰어의 각 이벤트에는 다음 항목이 표시된다.

| 항목       | 설명                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------- |
| 종류(수준) | 보안 로그는 감사 성공과 감사 실패로 나뉜다. 어떤 시도가 성공했을 때와 실패했을 때 남는다 |
| 날짜, 시간 | 로그를 남긴 날짜와 시각                                                                  |
| 원본       | 로그를 남긴 구성 요소. 보안 감사는 `Microsoft Windows security auditing`                 |
| 이벤트 ID  | 로그 종류별 고유 번호. 이 번호를 알면 필요한 로그만 골라 빠르게 분석할 수 있다           |
| 사용자     | 로그를 발생시킨 사용자                                                                   |
| 컴퓨터     | 로그를 발생시킨 시스템                                                                   |

감사 정책에서 켤 수 있는 항목은 다음과 같다.

| 감사 정책                   | 기록하는 내용                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------ |
| 개체 액세스 감사            | 파일, 디렉터리, 레지스트리 키, 프린터 같은 개체에 대한 접근 시도와 속성 변경         |
| 계정 관리 감사              | 사용자·그룹 추가·변경·삭제, 계정 활성화·비활성화, 비밀번호 변경                      |
| 계정 로그온 이벤트 감사     | 도메인 컨트롤러가 처리한 도메인 계정의 인증                                          |
| 로그온 이벤트 감사          | 이 컴퓨터에서 일어난 로컬 로그온·로그오프. 계정 로그온 감사보다 다양한 이벤트를 남김 |
| 권한 사용 감사              | 관리자 권한이 필요한 작업 수행, 권한 설정 변경                                       |
| 디렉터리 서비스 액세스 감사 | 시스템 접근 제어 목록(SACL)이 지정된 액티브 디렉터리 개체에 대한 접근                |
| 정책 변경 감사              | 사용자 권한 할당, 감사 정책, 신뢰 정책의 변경                                        |
| 프로세스 추적 감사          | 사용자나 프로그램이 프로세스를 시작하거나 중지할 때                                  |
| 시스템 이벤트 감사          | 시스템 시작과 종료, 보안 로그 삭제 같은 주요 사건                                    |

보안 로그 삭제는 이벤트 ID 1102로 따로 남는다. 공격자가 흔적을 지우려고 로그를 지우면 "로그를 지웠다"는 기록이 새로 생기는 셈이므로, ==이 이벤트 자체가 침입의 증거가 된다==.

| 로그          | 내용                                                              |
| ------------- | ----------------------------------------------------------------- |
| 응용 프로그램 | 응용 프로그램이 남긴 오류·경고                                    |
| 보안          | 로그온 성공(이벤트 ID 4624)·실패(4625), 권한 사용, 감사 정책 변경 |
| 시스템        | 드라이버, 서비스 시작·중지 같은 운영체제 구성 요소의 이벤트       |

### 유닉스의 로그

리눅스는 대부분의 로그를 `/var/log` 디렉터리에 저장한다(솔라리스 같은 일부 유닉스는 `/var/adm`).

| 로그                                       | 내용                                      | 확인 명령           |
| ------------------------------------------ | ----------------------------------------- | ------------------- |
| utmp(`/var/run/utmp`)                      | 현재 로그인한 사용자, 터미널, 로그인 시각 | `who`, `w`, `users` |
| wtmp(`/var/log/wtmp`)                      | 로그인·로그아웃·재부팅 이력               | `last`              |
| btmp(`/var/log/btmp`)                      | 실패한 로그인 시도                        | `lastb`             |
| `/var/log/messages` 또는 `/var/log/syslog` | 시스템 전반의 메시지(syslog)              | `less`, `tail -f`   |
| `/var/log/secure` 또는 `/var/log/auth.log` | SSH 로그인, `sudo` 사용 같은 인증 기록    | `grep sshd`         |
| 셸 히스토리(`~/.bash_history`)             | 사용자가 입력한 명령                      | `history`           |

로그를 저장하는 디렉터리는 유닉스 종류마다 조금씩 다르다. 초기 유닉스는 `/usr/adm`, 솔라리스·HP-UX 10.x 이후·IBM AIX는 `/var/adm`, FreeBSD와 리눅스는 `/var/log`를 쓰고, 솔라리스는 `/var/adm`과 `/var/log`에 나누어 저장한다. 일부 리눅스는 현재 상태를 담은 utmp를 `/var/run`에 둔다.

utmp는 유닉스의 가장 기본적인 로그로, 로그인한 계정 이름, 로그인 장치(콘솔, tty 등), 로그인 셸의 프로세스 ID, 로그인 시각과 로그아웃 여부를 담는다. utmp·wtmp·btmp는 텍스트가 아니라 구조체를 이어 붙인 바이너리 파일이라 `w`, `who`, `users`, `last`, `finger` 같은 전용 명령으로 읽는다.

```text
$ w
 14:21  up 3 days,  2:10, 2 users, load averages: 1.52 1.43 1.38
USER     TTY      FROM              LOGIN@  IDLE WHAT
me       console  -                월09    3days -
me       s000     -                14:02       - w
```

`console`은 컴퓨터 앞에서 직접 로그인한 세션, `s000`은 터미널 창 하나에 해당한다. SSH로 원격 접속한 세션이면 FROM 열에 접속한 IP가 나오므로, 모르는 IP가 보이면 즉시 확인한다.

syslog는 시스템 운영 전반의 로그로, 커널과 서비스가 남긴 메시지를 날짜·호스트 이름·프로그램 이름과 함께 한 줄씩 기록한다.

```text
Jun  6 23:09:10 server kernel: [    0.243039] PCI: MMCONFIG for domain 0000 [bus 00-ff]
Jun  6 23:09:10 server kernel: [    0.247483] bio: create slab <bio-0> at 0
Jun  6 23:12:44 server sshd[2231]: Failed password for root from 203.0.113.7 port 51122 ssh2
```

| 부분                   | 뜻                                                         |
| ---------------------- | ---------------------------------------------------------- |
| `Jun  6 23:09:10`      | 기록 시각                                                  |
| `server`               | 로그를 남긴 호스트 이름                                    |
| `kernel`, `sshd[2231]` | 로그를 남긴 프로그램과 PID                                 |
| 나머지                 | 메시지. 위는 부팅 중 하드웨어 인식, 아래는 SSH 로그인 실패 |

셋째 줄처럼 `Failed password for root`가 같은 IP에서 수백 번 반복되면 비밀번호 대입 공격이다. `grep "Failed password" /var/log/auth.log | awk '{print $11}' | sort | uniq -c | sort -rn`으로 시도한 IP별 횟수를 집계할 수 있다. systemd를 쓰는 최근 리눅스는 저널(journald)에도 로그를 모으며 `journalctl`로 조회한다. macOS는 통합 로깅 시스템을 쓰고 `log show` 명령으로 조회한다.

### 원격 로그 서버

침입한 공격자는 흔적을 지우려고 로그를 삭제하거나 고친다. 로그를 별도의 로그 서버로 실시간 전송해 두면, ==공격자가 한 시스템을 장악해도 이미 전송된 기록은 지울 수 없다==. 저장 공간이 거의 없는 라우터·스위치 같은 네트워크 장비는 원래부터 syslog 프로토콜로 로그 서버에 로그를 보내 저장한다.

![서로 다른 네트워크에 있는 네트워크 장비 세 대가 모두 한 대의 로그 서버로 로그를 보내는 구성도](./images/csintro-system-security-logserver-slide.jpg '저장 공간이 없는 네트워크 장비는 로그를 별도 로그 서버로 보낸다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

![라우터·스위치, 방화벽, 웹 서버가 syslog로 로그 서버에 로그를 보내고, 침입당한 웹 서버가 로컬 로그를 지워도 로그 서버에 이미 받은 기록은 남는다](./images/csintro-system-security-logserver.svg '로그 서버는 침입한 공격자가 흔적을 지우기 어렵게 만든다')

여러 시스템의 로그를 한곳에 모으면 시각을 기준으로 사건을 이어 볼 수 있다는 장점도 있다. 방화벽 로그에서 23:12에 외부 IP의 접속을 확인하고, 같은 시각 웹 서버 로그에서 그 IP의 요청을, 이어서 데이터베이스 로그에서 대량 조회를 찾는 식이다. 이렇게 하려면 모든 시스템의 시계가 맞아야 하므로 NTP로 시각을 동기화한다. 기업에서는 로그를 모아 상관관계를 분석하고 경보를 띄우는 SIEM(security information and event management) 시스템을 쓴다.

## 취약점 관리

취약점(vulnerability)은 공격자가 보안 정책을 우회하는 데 쓸 수 있는 시스템의 결함이다. 공개된 취약점에는 CVE(Common Vulnerabilities and Exposures) 번호가 붙는다. 예를 들어 WannaCry 랜섬웨어가 이용한 Windows SMB 취약점은 CVE-2017-0144다.

취약점 관리의 기본은 제조사가 배포하는 보안 패치를 빨리 적용하는 것이다. 윈도우는 Windows 업데이트가 자동으로 패치를 확인하고 설치하며, 설정 → Windows 업데이트 → 업데이트 기록에서 설치된 패치 목록을 확인할 수 있다. macOS는 시스템 설정 → 일반 → 소프트웨어 업데이트, 데비안·우분투는 `sudo apt update && sudo apt upgrade`로 적용한다.

![Windows 10 설정의 업데이트 및 복구 화면에서 업데이트 상태가 최신이고, 업데이트 확인 버튼과 업데이트 기록, 업데이트 설정 항목이 보이는 화면](./images/csintro-system-security-windows-update.jpg 'Windows 업데이트에서 보안 패치를 확인하고 적용한다. 출처: 양대일, 『정보 보안 개론』, 한빛아카데미')

![macOS 소프트웨어 업데이트 창에 사용자의 Mac은 최신 상태입니다, macOS Catalina 10.15.5라는 문구와 자동으로 Mac 최신으로 유지하기 체크 상자가 켜져 있다](./images/csintro-system-security-softwareupdate.jpg 'macOS Catalina의 소프트웨어 업데이트 화면. 자동 업데이트를 켜 두는 것이 기본 대응이다')

취약점의 심각도는 CVSS(Common Vulnerability Scoring System) 점수로 0.0부터 10.0까지 매긴다. 네트워크로 원격 공격이 가능한지, 인증이 필요한지, 사용자의 조작이 필요한지, 성공하면 기밀성·무결성·가용성이 얼마나 침해되는지를 따져 계산한다. 9.0 이상은 '긴급'으로, 인증 없이 원격에서 시스템을 장악할 수 있는 취약점이 여기에 속한다. 패치가 많아 한꺼번에 적용하기 어려우면 CVSS 점수가 높고 인터넷에 노출된 시스템부터 적용한다.

![취약점 발견부터 패치 공개까지는 패치가 없는 제로데이 구간이고, 패치 공개 후 공격자가 패치를 비교해 공격 코드를 만들어 내 시스템에 패치를 적용하기 전까지가 가장 위험한 구간이다](./images/csintro-system-security-patch-window.svg '패치 공개부터 적용까지의 시간을 줄이는 것이 취약점 관리의 목표다')

패치는 공개되는 순간 공격자에게도 취약점의 위치를 알려 준다. 공격자는 패치 전후의 코드를 비교해 공격 코드를 만들기 때문에, ==패치가 나온 뒤 적용하지 않은 기간이 가장 위험하다==. [악성코드의 분류와 감염 경로, 탐지와 대응](/memo/csintro-malware)에서 다룬 Code Red, Slammer, WannaCry 모두 패치가 이미 나와 있던 취약점을 이용했다.

## 버퍼 오버플로

### 원리

버퍼(buffer)는 데이터를 임시로 담아 두는 고정 크기의 메모리 영역이다. 버퍼 오버플로(buffer overflow)는 프로그램이 버퍼 크기보다 긴 데이터를 복사해, 버퍼 바로 뒤에 있는 메모리까지 덮어쓰는 결함이다. ==C와 C++은 배열 경계를 자동으로 검사하지 않기 때문에==, 개발자가 길이를 확인하지 않으면 이 결함이 생긴다.

```c
#include <string.h>

void greet(const char *name)
{
	char buf[8];
	strcpy(buf, name);   /* name의 길이를 확인하지 않고 복사한다 */
}
```

`strcpy`는 원본 문자열의 끝(`\0`)이 나올 때까지 복사하므로, `name`이 8바이트를 넘으면 `buf` 밖의 메모리를 덮어쓴다. 함수의 지역 변수는 스택(stack)이라는 메모리 영역에 저장되는데, ==스택에는 지역 변수 바로 위에 함수가 끝난 뒤 돌아갈 위치인 반환 주소(return address)도 함께 저장되어 있다==.

![스택 프레임에서 8바이트 버퍼에 Hi를 복사하면 버퍼 안에 머물지만, A를 24개 복사하면 낮은 주소에서 높은 주소 방향으로 저장된 프레임 포인터와 반환 주소까지 덮어쓴다](./images/csintro-system-security-overflow.svg '버퍼를 넘친 데이터가 반환 주소를 덮어쓴다')

1. 정상 입력 `"Hi"`는 3바이트(`H`, `i`, `\0`)라 버퍼 안에 들어간다.
2. 64비트 시스템에서 `A` 24개를 넣으면 버퍼 8바이트, 저장된 프레임 포인터 8바이트, 반환 주소 8바이트를 차례로 덮어쓴다.
3. 함수가 끝나면 CPU는 반환 주소 자리에 있는 값 `0x4141414141414141`(`A`의 ASCII 코드 0x41의 반복)로 이동하려 하고, 그런 주소에는 코드가 없으므로 프로그램이 세그멘테이션 오류로 종료된다.
4. 공격자가 `A` 대신 의도한 주소 값을 넣으면 프로그램의 실행 흐름을 바꿀 수 있다. 1988년 Morris 웜과 2001년 Code Red 웜이 이런 방식으로 원격 시스템의 제어권을 얻었다.

### 방어

| 방어                      | 방법                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 길이 검사                 | `strcpy`, `strcat`, `gets` 대신 크기를 받는 `snprintf`, `strlcpy`, `fgets`를 쓴다                              |
| 메모리 안전 언어          | Rust, Go, Java처럼 배열 경계를 자동으로 검사하는 언어를 쓴다                                                   |
| 스택 카나리(stack canary) | 컴파일러가 버퍼와 반환 주소 사이에 임의의 값을 넣고, 함수가 끝날 때 값이 바뀌었으면 프로그램을 중단한다        |
| ASLR                      | 프로그램을 실행할 때마다 스택과 라이브러리의 주소를 무작위로 바꿔, 공격자가 이동할 주소를 예측하지 못하게 한다 |
| 실행 금지 메모리(NX, DEP) | 스택처럼 데이터를 담는 영역에서는 코드를 실행하지 못하게 한다                                                  |

앞의 함수는 다음과 같이 고친다.

```c
#include <stdio.h>

void greet(const char *name)
{
	char buf[8];
	snprintf(buf, sizeof buf, "%s", name);   /* 최대 7글자 + \0만 복사 */
}
```

`snprintf`는 버퍼 크기를 받아 그 이상은 잘라 내므로, 입력이 아무리 길어도 버퍼 밖을 덮어쓰지 않는다.

## 직접 해 보기

macOS나 리눅스 터미널에서 앞에서 설명한 관리 항목을 직접 확인해 본다.

### 계정과 그룹

```bash
cat /etc/passwd                     # 계정 목록 (macOS는 서비스 계정 위주)
cat /etc/group                      # 그룹 목록과 구성원
id                                  # 내 UID, GID, 소속 그룹
grep -v '^#' /etc/passwd | head -5  # 시스템 계정 목록
grep '^admin' /etc/group            # macOS 관리자 그룹 구성원
```

```text
$ id
uid=501(me) gid=20(staff) groups=20(staff),12(everyone),80(admin),...
```

UID 501은 macOS에서 처음 만든 사용자의 번호이고, `admin`(GID 80) 그룹에 속해 있으므로 `sudo`로 관리자 명령을 실행할 수 있다.

### 권한

```bash
ls -l /etc/passwd /etc/sudoers
touch test.txt && ls -l test.txt   # 기본 권한 확인(-rw-r--r--)
chmod 600 test.txt && ls -l test.txt
```

`/etc/sudoers`는 `-r--r-----`(440)로 root와 wheel 그룹만 읽을 수 있다. 새로 만든 파일이 644가 되는 이유는 앞에서 본 것처럼 요청 권한 666에서 umask 022의 비트를 지운 결과이기 때문이다.

홈 디렉터리에서 `ls -al`을 실행하면 macOS에서만 보이는 기호가 있다.

```text
$ ls -al ~
drwxr-xr-x+ 43 me    staff   1376  5 28 14:33 .
drwxr-xr-x   6 root  admin    192  4  7 04:45 ..
-rw-------   1 me    staff   2187  5 28 14:21 .bash_history
drwx------   3 me    staff     96  4 15 21:43 .ssh
drwx------@ 15 me    staff    480  5 28 14:29 Desktop
drwx------+  8 me    staff    256  5 28 09:56 Downloads
drwxr-xr-x+  5 me    staff    160  5 28 14:33 Public
```

| 관찰                             | 의미                                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| 권한 뒤의 `@`                    | 확장 속성(extended attribute)이 있다. `xattr -l`로 확인. 인터넷에서 받은 파일의 격리 표시 등 |
| 권한 뒤의 `+`                    | 기본 rwx 외에 ACL이 붙어 있다. `ls -le`로 확인. Downloads 등에 "모두 삭제 거부" 규칙이 있다  |
| `.bash_history`가 600            | 입력한 명령 기록은 본인만 읽을 수 있다                                                       |
| `Desktop`, `Downloads`가 700     | 다른 사용자는 들어갈 수도 없다                                                               |
| `Public`이 755                   | 다른 사용자와 공유하는 폴더라 누구나 읽을 수 있다                                            |
| `..`의 소유자가 root, 그룹 admin | `/Users`는 관리자만 고칠 수 있다                                                             |

### 로그

```bash
w                                    # 현재 로그인한 사용자와 하는 일
last | head -5                       # 최근 로그인·재부팅 이력
log show --last 1h --predicate 'process == "sudo"'   # macOS: 최근 1시간 sudo 사용 기록
history | tail -5                    # 최근에 입력한 명령
```

macOS는 Sierra(10.12)부터 통합 로깅을 쓰지만, 한동안 `/var/log/system.log`에도 일부 시스템 로그가 텍스트로 남아 `less`나 `vi`로 읽을 수 있었다.

```text
Jun  4 00:00:09 MacBook-Pro com.apple.xpc.launchd[1] (com.apple.mdworker.shared.0C000000-0200-0000-0000-000000000000[2391]): Service exited due to SIGKILL | sent by mds[126]
Jun  4 00:01:08 MacBook-Pro syslogd[99]: ASL Sender Statistics
```

첫 줄은 프로세스 관리자인 launchd(PID 1)가 남긴 기록으로, Spotlight 색인 작업 프로세스(mdworker)가 mds의 SIGKILL 신호로 종료되었다는 뜻이다. 정상적인 동작이지만, 이처럼 어떤 프로세스가 누구에 의해 언제 시작·종료되었는지가 남으므로 악성 프로세스의 실행 흔적을 찾는 데 쓸 수 있다. 최근 macOS에서는 대부분의 기록이 통합 로깅에만 남으므로 `log show`나 콘솔(Console) 앱으로 본다.

### 취약점(패치)

```bash
softwareupdate --list                # macOS: 설치할 수 있는 업데이트 목록
sw_vers                              # 현재 macOS 버전
softwareupdate --history | head      # 설치된 업데이트 이력
```

GUI에서는 시스템 설정 → 일반 → 소프트웨어 업데이트(Catalina 이전은 시스템 환경설정 → 소프트웨어 업데이트)에서 확인한다. "자동으로 Mac 최신으로 유지하기"를 켜 두면 보안 업데이트가 나오는 즉시 설치된다. `sw_vers`로 확인한 버전을 Apple 보안 업데이트 페이지에서 찾으면 그 버전 이후에 고쳐진 CVE 목록을 볼 수 있다.

## 정리

| 항목          | 핵심                                           | 도구·파일                                      |
| ------------- | ---------------------------------------------- | ---------------------------------------------- |
| 계정 관리     | 인증 요소, UID 0 계정 점검, 긴 비밀번호와 MFA  | `/etc/passwd`, `/etc/shadow`, `net localgroup` |
| 세션 관리     | 암호화, 세션 만료, 중요 작업 전 재인증         | HTTPS, 세션 쿠키                               |
| 접근 제어     | IP와 포트로 접속 출발지 제한                   | `sqlnet.ora`, ACL, 방화벽                      |
| 권한 관리     | 최소 권한, 누적·상속·거부 우선 규칙, rwx 8진수 | NTFS 보안 탭, `chmod`, `chown`                 |
| 로그 관리     | AAA, 책임 추적성, 원격 로그 서버               | 이벤트 뷰어, `/var/log`, `last`                |
| 취약점 관리   | CVE, 빠른 패치 적용                            | Windows 업데이트, `softwareupdate`             |
| 버퍼 오버플로 | 길이 검사 없는 복사가 반환 주소를 덮어씀       | `snprintf`, 스택 카나리, ASLR, NX              |
