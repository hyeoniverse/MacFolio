v1에서 프론트의 로그인과 인증은 내가 맡은 부분이었다. 1년 8개월 만에 다시 읽어 보니, 토큰이 만료되면 어떻게 되는지 한 번에 설명할 수 없었다. 리팩토링 4단계의 첫 PR(PR #26)은 프론트의 모든 API 호출을 한 경로로 모으고, 토큰 갱신과 보호 경로 확인을 정리했다.

## 무엇이 동작하지 않았나

| 코드                                           | 문제                                                               | 결과                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------- |
| 토큰 갱신 래퍼 `fetchWithAuth`                 | 호출하는 곳 0개                                                    | 브라우저에서 토큰이 만료되면 요청이 그냥 실패        |
| 서버 렌더링 중 재시도                          | 응답의 `access_token`을 읽음. 백엔드가 보내는 필드는 `accessToken` | 서버 쪽 갱신이 한 번도 동작하지 않음                 |
| `API_URL = BACK_URL`                           | Next rewrites 프록시 설정만 있고 쓰이지 않음                       | 쿠키를 api 도메인에 두려고 www/api 서브도메인이 필요 |
| 루트 layout `force-dynamic` + 트렌드 매번 조회 | 모든 페이지가 요청마다 렌더링                                      | 페이지마다 백엔드 추가 호출                          |
| `/auth/refresh` 응답 본문의 토큰               | HttpOnly 쿠키와 별개로 본문에도 토큰                               | 스크립트로 토큰을 읽을 수 있음                       |

access token은 3시간, refresh token은 12시간 유효하다. 그런데 갱신 경로가 모두 끊겨 있었으므로, 로그인하고 3시간이 지나면 refresh token이 남아 있어도 요청이 실패하고 다시 로그인해야 했다.

## 요청 경로: 브라우저는 /api, 서버는 API_URL

![요청 경로](./images/newpick-api-client-paths.svg '브라우저는 같은 도메인의 /api 프록시로, 서버는 백엔드로 직접')

브라우저가 api 도메인으로 직접 요청하면, 로그인 쿠키는 api 도메인에 저장된다. 프론트와 api가 다른 사이트면 SameSite 설정과 서브도메인 구성이 필요하다. 프론트의 `/api/*`를 Next rewrites로 백엔드에 넘기면 브라우저 입장에서는 같은 도메인 요청이 되고, 쿠키도 프론트 도메인에 저장된다.

이 방식은 팀 시절에도 `getApiUrl`이라는 이름으로 만들어 두고 주석 처리되어 있었다. 기록을 남겨 레포를 합친 덕분에 찾을 수 있었다. 서버 렌더링 중에는 프록시를 거칠 이유가 없으므로 `API_URL`로 백엔드를 직접 호출한다.

```ts
// 브라우저는 같은 도메인 프록시, 서버는 백엔드 직접
export const API_URL = typeof window === 'undefined' ? BACK_URL : '/api';
```

## apiFetch: 401이면 한 번 갱신하고 다시

모든 요청은 `apiFetch` 하나를 거친다. JSON 직렬화, 에러 타입(`ApiError`, `status`로 분기), 401 처리를 한곳에서 한다.

```ts
let refreshing: Promise<boolean> | null = null;

/** 동시에 여러 요청이 401을 받아도 refresh는 한 번만 보냅니다. */
function refreshSession(): Promise<boolean> {
	refreshing ??= fetch(API_ENDPOINTS.AUTH.REFRESH(), { credentials: 'include' })
		.then((response) => response.ok)
		.catch(() => false)
		.finally(() => {
			refreshing = null;
		});
	return refreshing;
}
```

페이지 하나가 API를 서너 개 동시에 부르는 경우, 토큰이 만료되면 모두 401을 받는다. 각자 refresh를 보내면 같은 요청이 여러 번 나가고, 순서에 따라 실패할 수도 있다. 진행 중인 refresh가 있으면 그 Promise를 같이 기다리게 해서 refresh는 한 번만 보낸다.

## middleware: 페이지를 그리기 전에

서버 컴포넌트는 쿠키를 읽을 수만 있고 쓸 수 없다. 서버 렌더링 중에 토큰을 갱신해도 새 쿠키를 브라우저에 내려줄 방법이 없다. 그래서 갱신은 렌더링보다 먼저 실행되는 middleware에서 한다.

1. access 쿠키가 없고 refresh 쿠키가 있으면 백엔드에서 새 토큰을 받는다.
2. 새 쿠키를 응답에 실어 브라우저에 내려주고, **이번 요청의 쿠키도 바꿔** 같은 요청을 처리하는 서버 컴포넌트가 새 토큰을 보게 한다.
3. `/mypage`는 토큰이 없으면 렌더링하지 않고 `/?login=required`로 보낸다. 이전에는 컴포넌트마다 `!user`를 직접 확인했다.

백엔드는 `/auth/refresh` 응답 본문에서 토큰을 빼고 쿠키로만 보내게 바꿨다. 쿠키 SameSite 기본값은 `lax`다. 프록시를 거치므로 같은 사이트 쿠키이기 때문이다.

## 타입을 붙이다 찾은 버그

`apiFetch<T>`로 응답 타입을 지정하자, 그동안 조용히 틀려 있던 곳이 컴파일 오류로 드러났다.

| 코드                  | 문제                                         |
| --------------------- | -------------------------------------------- |
| `getTrendList`        | 항상 `undefined`를 반환                      |
| 무료 체험 `newslinks` | 기본값의 타입이 실제 응답과 다름             |
| `api/ai.ts`           | `dateEnd` 인자를 받고도 `dateStart`로 덮어씀 |

## 확인

프로덕션 빌드(`next start`)와 docker compose api로 실제 요청을 보내, 같은 방식으로 띄운 main 빌드와 비교했다.

| 홈 요청 한 번당 백엔드 호출 | main                                        | 변경 후             |
| --------------------------- | ------------------------------------------- | ------------------- |
| 비로그인                    | 2회 (`/newsletters`, `/newsletters/trends`) | 1회 (트렌드는 캐시) |
| 로그인                      | 4회 (+ 프로필, 구독 상태)                   | 3회                 |

| 상황                                 | main                                  | 변경 후                                        |
| ------------------------------------ | ------------------------------------- | ---------------------------------------------- |
| refresh 쿠키만 있는 상태로 `/mypage` | 200, 갱신 없이 로그아웃 상태로 렌더링 | 갱신 → 새 쿠키 발급 → 같은 요청에서 프로필 200 |
| 쿠키 없이 `/mypage`                  | 200                                   | 307 → `/?login=required`                       |
| `/api/auth/logout` (프록시)          |                                       | 쿠키 삭제 `Set-Cookie`가 브라우저까지 전달     |

## 남은 것·배운 것

- 브라우저의 "401 → refresh → 재시도"는 curl로 확인할 수 없어, 5단계 테스트(#11)에서 다룬다.
- 이 PR 이후에도 모든 페이지는 동적 렌더링이었다. 루트 layout이 서버에서 로그인 사용자를 읽기 때문이다. 이 문제는 [깜빡임 없이 정적 페이지로 바꾼 글](/memo/newpick-static-auth-hint)에서 풀었다.
- 같은 날 이어서 올린 데이터 패칭 정리 PR(#27)은 "병합됨"으로 표시됐지만 main에 들어가지 않았다. 그 이야기는 [별도 글](/memo/newpick-stacked-pr)에 있다.
- 로그인 직후에는 모든 것이 동작하므로, 만료와 실패 경로는 일부러 만들어 보지 않으면 확인되지 않는다. 이번에는 refresh 쿠키만 남긴 요청을 직접 만들어 확인했다.
