## 메모 목록을 원문 묶음보다 먼저 ([#407](https://github.com/hyeoniverse/MacFolio/pull/407))

### 배경: 청크와 전송량

Vite 같은 번들러는 앱의 코드를 청크(chunk)라는 JavaScript 파일 여러 개로 나눠 내보낸다. 코드에서 `import()`로 불러오는 모듈은 별도 청크가 되어, 그 코드가 필요한 시각에만 내려받는다. 이 사이트의 저장소 글은 Markdown 원문을 문자열로 import해 번들에 넣으므로, 글 원문도 청크의 일부로 내려받는다. 청크는 서버가 brotli로 압축해 보내고, 브라우저가 받아서 푼다.

네트워크가 느린 기기에서는 받을 바이트 수(전송량)가, CPU가 느린 기기에서는 받은 코드를 해석하고 실행하는 시간(처리량)이 화면 표시를 늦춘다. 두 조건을 따로 걸어 재면 어느 쪽이 병목인지 가를 수 있다. Chrome 개발자 도구의 CPU 제한(throttling)은 CPU를 N배 느리게, 네트워크 제한은 대역폭과 지연 시간을 정해 흉내 낸다.

### 원인

배포 사이트에서 메모 앱을 열면 창은 바로 뜨지만 목록이 비어 있는 시간이 길었다. 목록 하나를 그리려고 글 247편의 원문 전체(`contentFiles` 청크, 압축 전 3.76MB, brotli 805KB)를 받았다.

| 배포 사이트, Dock에서 열기               |    창 |  목록 |
| ---------------------------------------- | ----: | ----: |
| 제한 없음                                | 0.3초 | 0.5초 |
| CPU만 4배 느리게                         | 1.3초 | 1.3초 |
| 네트워크만 10Mbps, 지연 100ms            | 0.8초 | 3.1초 |
| CPU 6배, 5Mbps, 지연 150ms (중급 휴대폰) | 2.9초 | 8.3초 |

CPU만 제한하면 창과 목록이 같은 시각에 표시된다. ==병목은 처리량이 아니라 전송량==이다. 목록이 본문에서 읽는 것은 첫 그림, `#태그`, 검색 조건(체크리스트·표·코드 등이 있는지)뿐이고, 원문 전체가 필요한 곳은 본문 검색 하나다.

![목록용 색인 전후 요청 순서](./images/memo-post-list-index-waterfall.svg '전에는 메모 앱 청크 다음에 원문 묶음을 받아야 목록을 그렸다. 후에는 색인으로 목록을 먼저 그리고 연 글의 청크만 받는다')

### 수정

1. **목록용 색인** `virtual:post-list`: 빌드 시각에 모든 글의 `Post`를 JSON으로 내보낸다. `body`에는 목록이 읽는 줄만 남기고(`listBody`) `bodyPending: true`를 붙인다. `listing.test.ts`가 원문과 색인 본문에서 `firstImage`·`tagsOf`·`POST_FILTERS`의 답이 같은지 검사한다.
2. **글별 청크**: `import.meta.glob('../content/*.md', { query: '?raw&single' })`. `contentFiles.ts`가 같은 파일을 `?raw`로 import해, 모듈 ID가 같으면 Rollup이 동적 `import()`를 큰 청크로 보낸다. 쿼리를 달리해 다른 모듈로 만들었다. Flux 글 청크는 brotli 10KB다.
3. **전체 원문은 뒤에서**: 마운트 직후 `contentFiles`를 동적 `import()`로 받아 본문 검색과 관리자 편집에 쓴다.

> [!WARNING] 색인 본문을 편집기에 열면 그대로 서버에 저장된다
> `bodyPending`인 글은 관리자 편집기에 열지 않고 원문이 온 뒤에 연다. 처음에는 관리자 화면 전체를 원문이 올 때까지 읽기 화면으로 고정했는데, 그사이 누른 "새 메모"의 편집기 초점이 사라져 E2E 3건이 실패했다.

`loadPostBody`를 처음에 글 저장소 모듈에 넣자, Finder도 쓰는 그 모듈에 247편의 `import()` 목록이 들어가 첫 방문 번들이 267.8KB로 예산(265KB)을 넘었다. 메모 앱만 import하는 `postBody.ts`로 옮겨 263.2KB가 되었다. 빌드 결과 JS 파일은 325개에서 572개가 되었다.

| ----------------------------- | -------: | -------: |
| 네트워크만 10Mbps, 지연 100ms |   3.09초 |   1.31초 |
| CPU 6배, 5Mbps, 지연 150ms    |   8.27초 |   2.53초 |
| 같은 조건, 글 주소로 들어옴   |   2.43초 |   1.10초 |

![목록 표시 시간 전후](./images/day-1031-list-timing.svg '그래프. 세 조건 모두 목록이 그려지기까지 걸린 시간이 절반 이하로 줄었다. 가장 느린 중급 휴대폰 조건은 8.27초에서 2.53초가 되었다')

같은 PR에서 `memo-history.spec.ts`의 스크롤 복원 시험을 고쳤다. 본문이 다 그려지기 전에 한 번만 스크롤해 main에서도 12회 중 2회 실패했다. 본문 높이가 생길 때까지 스크롤을 다시 시도한다. 자세한 과정은 [목록용 색인 글](/memo/memo-post-list-index)에 적었다.

## 휴대폰 편집 화면의 알약 ([#408](https://github.com/hyeoniverse/MacFolio/pull/408))

메모 편집 화면은 글자 크기를 CSS `zoom`으로 바꾼다. `zoom`은 요소와 그 자손 전체를 배율만큼 확대·축소하는 속성으로, 글자뿐 아니라 너비·여백·위치 값까지 함께 바뀐다. 요소에 `zoom`이 겹쳐 있으면 배율은 곱해진다. 예를 들어 부모가 `zoom: 0.9`, 자식이 `zoom: 0.5`이면 자식은 0.45배로 그려진다.

![휴대폰 편집 화면 알약 전후](./images/week-1026-phone-pills.jpg 'iPhone 15 Pro Max 크기 WebKit에서 글자를 한 단계 줄인 상태. 전에는 게시 알약이 작아져 옆 알약과 겹치고, 글자 크기 알약이 새 메모 버튼에 겹쳤다')

| 요소           | 증상                                                       | 원인                                                                                                          | 수정                                                                          |
| -------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 게시 알약      | 글자를 한 단계 줄이면 y 50 → 43, 높이 44 → 37px, 10px 겹침 | 글자 크기를 `.memo-writer-meta`의 `zoom`으로 바꾸는데, 알약이 그 안에 떠 있어 크기와 `top`·`right`까지 줄었다 | `zoom: calc(1 / var(--memo-text-scale))`. 겹친 zoom은 곱해져 원래 크기가 된다 |

## 첫 화면 성능 ([#409](https://github.com/hyeoniverse/MacFolio/pull/409))

### 배경: FCP·LCP·TTFB와 Lighthouse

- **TTFB**(Time to First Byte): 요청을 보낸 뒤 서버 응답의 첫 바이트가 도착하기까지 걸린 시간이다.
- **FCP**(First Contentful Paint): 페이지를 연 뒤 글자나 그림이 처음 화면에 그려지기까지 걸린 시간이다.
- **LCP**(Largest Contentful Paint): 화면에서 가장 큰 글자 덩어리나 그림이 그려지기까지 걸린 시간이다.

Lighthouse는 Chrome에 들어 있는 페이지 품질 측정 도구로, 성능·접근성·권장사항 등을 100점 만점으로 매긴다. 모바일 성능 측정의 기본값은 simulate 방식이다. 실제로는 빠른 네트워크로 한 번 불러온 뒤, 그 기록을 바탕으로 느린 4G와 느린 CPU였다면 얼마나 걸렸을지 계산한다. 그래서 Lighthouse의 FCP는 관찰한 값이 아니라 계산한 값이다.

### 계산한 FCP와 관찰한 첫 렌더링

배포 사이트의 Lighthouse 모바일 점수는 91(FCP·LCP 2.8초)이었다. 관찰한 첫 렌더링은 0.58초(TTFB 394ms + 렌더링 지연 186ms)인데 simulate는 2.8초를 계산했다.

> [!NOTE] simulate가 FCP 계산에 넣는 요청
> Lighthouse simulate는 관찰한 첫 렌더링 전에 수신을 마친 요청을 모두 첫 렌더링에 필요한 것으로 보고 느린 4G로 다시 계산한다. 렌더링을 막는 `theme-boot.js`(2KB)를 받는 사이 modulepreload 번들 38개가 먼저 도착해, 요청 39개·145KB가 FCP 계산에 들어갔다.

![관찰한 FCP와 계산한 FCP](./images/day-1031-fcp-simulate.svg '도식. 관찰한 첫 렌더링은 0.58초인데, 렌더링을 막는 2KB 스크립트를 받는 사이 도착한 번들 38개까지 simulate가 계산에 넣어 2.8초가 되었다')

### 테마 스크립트 인라인과 CSP 해시

CSP는 페이지가 실행할 수 있는 스크립트를 제한해, 공격자가 주입한 `<script>`가 실행되지 못하게 한다. 그래서 기본적으로 HTML 안에 직접 적은 인라인 스크립트도 막는다. `'unsafe-inline'`을 더하면 인라인 스크립트가 모두 허용되어 이 보호가 사라진다. 대신 `script-src 'sha256-…'`처럼 스크립트 내용의 SHA-256 해시를 적으면, 내용이 정확히 그 해시와 같은 인라인 스크립트만 실행된다. 한 글자라도 다르면 해시가 달라져 막힌다.

`theme-boot.js`는 CSP가 인라인 스크립트를 막아 파일로 분리했던 다크 모드 스크립트다. 빌드 시각에 `index.html`의 `<!--theme-boot-->` 자리를 `<script>`로 바꾸고, ==CSP `script-src`에는 `'unsafe-inline'` 없이 그 SHA-256 해시 하나만 더한다==. 해시는 `_headers`(빌드)와 Worker가 첫 화면에 붙이는 CSP(`siteHtml.ts`)에 같은 함수로 들어간다. `themeBoot.test.ts`가 해시와 스크립트 내용이 같은지 검사해, 스크립트를 고치고 해시를 갱신하지 않으면 시험이 실패한다.

### 첫 화면 HTML의 엣지 캐시

Cloudflare Worker는 Cloudflare의 전 세계 데이터 센터(PoP, Point of Presence)에서 요청을 처리하는 서버리스 코드다. 요청마다 isolate라는 가벼운 실행 환경에서 돌고, isolate는 한동안 요청이 없으면 사라진다. `caches.default`는 Worker가 그 데이터 센터의 HTTP 캐시에 응답을 보관하고 꺼내 쓰는 Cache API다. stale-while-revalidate는 RFC 5861에 정의된 캐시 규칙으로, 유효 기간이 지난 보관본을 먼저 응답하고 뒤에서 새 응답을 받아 보관본을 갱신한다.

TTFB의 원인은 새로 뜬 Worker가 HTML을 만들기 전에 API `/site`·`/posts`와 정적 자산 `seo/posts.json`(압축 전 4MB)을 기다리는 데 있었다. isolate 안의 1분 캐시는 isolate가 새로 뜨거나 PoP가 바뀌면 사라진다. 첫 화면 HTML을 `caches.default`에 보관하고, 1분이 지났으면 보관본을 먼저 준 뒤 `waitUntil`로 새로 만든다(stale-while-revalidate). 이 규칙은 Worker의 `edgeCache.test.ts`가 검사한다.

![엣지 캐시 흐름](./images/week-1026-edge-cache.svg '도식. 1분 안이면 보관본, 1분이 지났으면 보관본을 먼저 주고 뒤에서 새로 만든다. 키에 ETag가 있어 배포하면 새 키가 된다')

| 배포 뒤 (Lighthouse 12.8.2, 5회 중앙값) |       전 |          후 |
| --------------------------------------- | -------: | ----------: |
| 모바일 점수                             |       91 |     **100** |
| 모바일 FCP·LCP                          |    2.8초 |   **1.0초** |
| 데스크톱 점수                           |       97 |     **100** |
| 데스크톱 FCP·LCP                        |   0.98초 |  **0.30초** |
| 첫 화면 서버 처리 시간                  | 약 320ms | **52~82ms** |

로컬에서는 차이가 보이지 않았다. 로컬 정적 서버(HTTP/1.1)는 첫 렌더링 전에 번들을 모두 받아 양쪽 모두 FCP 3.2초 안팎이고, `wrangler dev`는 캐시가 늘 차 있어 TTFB가 3ms 안팎이다. 그래서 배포 뒤 같은 방법으로 다시 잰 값을 PR에 남겼다.

## zod의 eval과 방문자의 401 ([#410](https://github.com/hyeoniverse/MacFolio/pull/410))

zod는 TypeScript에서 데이터의 형태(스키마)를 선언하고 실제 값이 그 형태에 맞는지 검사하는 라이브러리다. 이 사이트는 `packages/contracts`의 zod 스키마로 서버가 요청 본문을, 화면이 응답을 검사한다. `new Function('…')`은 문자열을 JavaScript 코드로 바꿔 실행하는 기능으로 `eval`과 같은 부류이며, CSP는 `'unsafe-eval'`이 없으면 이를 막는다. zod v4는 검사 속도를 높이려고 스키마마다 검사 함수를 코드 문자열로 만들어 `new Function`으로 실행하는 JIT 방식을 쓰고, `jitless` 설정으로 이를 끌 수 있다.

권장사항 점수 92에서 실패한 감사 항목 두 개를 화면 변경 없이 고쳤다.

| 감사 항목           | 기록                      | 원인                                                                                     | 수정                                                               |
| ------------------- | ------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `inspector-issues`  | CSP 위반 `kEvalViolation` | zod v4가 객체 스키마를 처음 검사하는 시각에 `new Function('')`으로 eval 가능 여부를 확인 | 스키마보다 먼저 `z.config({ jitless: true })`                      |
| `errors-in-console` | `GET /auth/me 401`        | 로그인하지 않은 방문자도 시작 시각에 관리자 세션을 묻는다                                | 로그인 표시(`STORAGE_KEYS.adminSignedIn`)가 있는 브라우저만 묻는다 |

> [!NOTE] 서버에서는 eval이 실제로 실행되고 있었다
> 브라우저는 CSP가 막아 시도만 기록되었지만, Node에는 CSP가 없어 zod가 `new Function`으로 검사 함수를 만들고 있었다. 재료는 스키마 정의뿐이라 요청 값이 코드가 되지는 않지만, 서버·브라우저 모두 jitless로 바꿨다.

로그인 표시는 물어볼 이유가 있다는 힌트일 뿐이고, 권한은 서버가 매 요청 세션 쿠키로 확인한다(`AdminGuard`). 배포 직후에는 이미 로그인한 관리자도 표시가 없어 한 번 다시 로그인해야 한다.

같은 PR에서 CI의 `pnpm audit --prod --audit-level=high`가 새로 공개된 follow-redirects 1.16.1 취약점(GHSA-mrwp-f3q8-3g9p, 사용자 지정 인증 헤더가 다른 호스트로 리다이렉트를 따라감. 경로 API > msedge-tts > axios)으로 실패해 overrides로 1.16.2를 지정했다.

## 돌아보며

**알게 된 것**

- 메모 목록이 느린 원인은 CPU 제한과 네트워크 제한을 나눠 재서 갈랐다. CPU만 느린 조건에서는 창과 목록이 같은 시각에 표시되어 전송량 문제로 좁혀졌다.
- Lighthouse FCP 2.8초와 관찰한 첫 렌더링 0.58초는 달랐다. simulate가 계산에 넣는 요청을 확인하고 나서 원인이 렌더링을 막는 2KB 파일과 그사이 도착한 번들 38개라는 것을 찾았다.
- `loadPostBody`를 공용 모듈에 넣자 첫 방문 번들이 4.6KB 늘어 예산을 넘었다. 그대로 배포했으면 메모 앱을 열지 않는 첫 방문자도 247편의 `import()` 목록을 받았다.

**고친 것과 남은 것**

- 로컬은 HTTP/1.1과 늘 찬 캐시 때문에 차이가 보이지 않아, 배포 뒤 측정을 기준으로 삼았다.
- CSP 위반은 브라우저에서만 기록됐지만, 같은 contracts를 쓰는 서버에서는 eval이 막히지 않고 실행되고 있었다. 원인 코드가 실행되는 곳을 모두 찾아 서버 쪽까지 고쳤다.
- 원문 묶음은 성능 최적화 2편에서 첫 화면에서만 뺐고, 그 뒤 글이 199편에서 247편으로 늘며 2.4MB에서 3.76MB가 됐다. 첫 화면 밖의 묶음 크기도 예산에 넣어야 한다.
