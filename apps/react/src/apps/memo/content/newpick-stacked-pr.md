리팩토링 4단계는 두 PR로 나눴다. 요청 경로와 인증을 정리하는 PR #26([요청 경로를 하나로](/memo/newpick-api-client))과, 그 위에서 데이터 패칭을 정리하고 죽은 코드를 지우는 PR #27이다. #27은 #26의 브랜치를 base로 쌓은 **스택 PR**이었다. 둘 다 10월 19일에 "Merged"가 됐다.

엿새 뒤 다음 작업을 고르려고 진행 상황을 보다가 이상한 점을 발견했다. #27이 지웠다는 `@faker-js/faker`가 main의 `package.json`에 그대로 있었고, 서버 렌더링 중에 조회수를 올리는 코드도 그대로였다.

## 무슨 일이 있었나

```bash
$ git merge-base --is-ancestor 55dce0b origin/main && echo "IN MAIN" || echo "NOT IN MAIN"
NOT IN MAIN
```

`55dce0b`는 #27의 병합 커밋이다. 이 커밋은 main의 조상이 아니었다. 병합 시각을 보면 이유가 보인다.

| PR  | base                     | 병합 시각 (UTC)     |
| --- | ------------------------ | ------------------- |
| #26 | `main`                   | 2026-10-19 04:31:13 |
| #27 | `feat/phase4-api-client` | 2026-10-19 04:31:18 |

![스택 PR 병합 순서](./images/newpick-stacked-pr-graph.svg '#27은 이미 main에 들어간 #26 브랜치로 병합됐다')

GitHub는 아래 PR(#26)이 병합되고 그 브랜치가 **삭제되면** 위 PR(#27)의 base를 자동으로 main으로 바꿔 준다. 이번에는 #26의 브랜치가 지워지지 않았고(지금도 남아 있다), 5초 뒤 #27이 병합됐다. #27은 base가 `feat/phase4-api-client`인 채로 병합됐고, 그 브랜치는 이미 main에 들어간 뒤라 아무 데로도 이어지지 않았다. GitHub에는 보라색 "Merged"가 표시되므로, 화면만 봐서는 알 수 없었다.

그 사이 #9 진행 상황 댓글에 "조회수, 죽은 코드가 남았다"고 적었는데, 그것도 이 때문이었다. #27의 본문에는 완료라고 적혀 있고, main에는 없었다.

## 다시 올리기

#27의 커밋 두 개를 현재 main 위에 그대로 cherry-pick했다(PR #32). 그 사이 main에 들어온 [정적 빌드 PR](/memo/newpick-static-auth-hint)과 겹친 `Providers.tsx` 한 곳에서 충돌이 났다. #29는 로그인 표시 쿠키를 읽는 코드를 넣었고, #27은 트렌드를 React Query 캐시에 미리 채우는 코드를 넣었다. 두 쪽을 모두 살려 합쳤다.

#27이 하던 일은 이렇다.

| 변경          | 이전                                                       | 이후                                             |
| ------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| 조회수        | 서버 렌더링 중에 증가. 실패하면 페이지 500                 | 기사를 연 브라우저에서 한 번 (`useViewCount`)    |
| 트렌드        | React Query와 Zustand에 이중 저장, 브라우저가 다시 요청    | React Query 하나, 서버 값으로 캐시를 채움        |
| 카테고리 이름 | 기사 상세가 매번 `GET /category`                           | 고정 상수에서 변환 (id 1~6은 migration으로 보장) |
| 죽은 코드     | import되지 않는 파일 20개, faker·json-server 등 의존성 4개 | 삭제 (+54 / −1,255줄)                            |

## main과 나란히 비교

"다시 올렸다"로 끝내지 않고, main과 이 브랜치를 같은 조건(프로덕션 빌드, docker compose api, 테스트 뉴스레터 3건)으로 띄워 비교했다. main은 별도 worktree에서 빌드했다.

| 상황                                               | main             | 이 PR        |
| -------------------------------------------------- | ---------------- | ------------ |
| 서버로 기사 페이지 3번 요청 (curl, 봇과 같은 조건) | 조회수 0 → **3** | 0 → **0**    |
| 브라우저로 기사 열기                               | —                | 0 → **1**    |
| 홈 첫 방문 시 브라우저의 트렌드 재요청             | 1회              | **0회**      |
| 존재하지 않는 기사 `/articles/detail/9999`         | **500**          | 200, 빈 본문 |

![기사 상세](./images/newpick-stacked-pr-detail.jpg '브라우저에서 기사를 연 뒤 조회수 1')

![홈 트렌드](./images/newpick-stacked-pr-trends.jpg '브라우저 요청 없이 서버에서 받은 트렌드로 표시')

존재하지 않는 기사는 500 오류 페이지에서 빈 화면으로 바뀌었다. 나아지긴 했지만 "기사를 찾을 수 없습니다" 같은 안내가 없다. 빈 상태 화면 이슈(#17)에 이미 적어 둔 항목이다.

![main: 500](./images/newpick-stacked-pr-missing-before.jpg 'main: 조회수 증가 요청이 404면 페이지 전체가 500')

![이 PR: 빈 화면](./images/newpick-stacked-pr-missing-after.jpg '이 PR: 500은 없지만 안내도 없다')

번들 크기는 거의 같았다(홈 19.4 kB → 19.3 kB). 지운 파일은 원래 import되지 않아 번들에 들어가지 않았기 때문이다. 이 PR의 효과는 번들이 아니라 요청 수와 조회수의 정확도다.

한 가지는 표에서 뺐다. #27은 "prefetch에도 조회수가 오른다"를 고친다고 적었는데, 홈에서 기사 링크가 화면에 보여도 main과 이 PR 모두 조회수가 오르지 않았다. 고쳤다고 볼 근거가 없었다.

## 남은 것·배운 것

- 스택 PR은 아래 PR을 병합한 뒤 **위 PR의 base가 main으로 바뀐 것을 확인하고** 병합해야 한다. 브랜치 자동 삭제를 켜 두면 GitHub가 base를 바꿔 준다.
- "Merged" 표시는 "어딘가에 병합됐다"는 뜻이지 "main에 있다"는 뜻이 아니다. 단계 이슈를 닫기 전에 main에서 변경을 직접 확인하는 습관이 필요하다.
- PR 본문의 "완료"를 믿고 진행 상황을 적었다가 틀렸다. 진행 상황은 PR 본문이 아니라 main의 코드로 확인해야 한다.
