이날 작업은 밤 10시 반에 시작했다. 메모 앱으로 글을 쓰다가 발견한 문제를 하나씩 수정해, 자정 전에 [#225](https://github.com/hyeoniverse/MacFolio/pull/225) 하나로 올렸다. #187은 2단계 작업이 중단된 상태로 커밋이 없었다. 주제는 게시 검증, 폴더·취소선 버그, 새 서식(토글·각주), 편집 화면과 읽기 화면의 일치, 개발 환경 문제다.

![10월 15일 작업 흐름](./images/day-1015-timeline.svg '밤 11시대에 #225의 커밋 8개')

## 요약 200자 제한에 막힌 게시

저장소에 포함된 글을 편집기에서 수정해 게시하려 하자 "요약은 200자까지 입력할 수 있습니다." 경고가 표시되고 게시되지 않았다. 편집 화면에는 요약 입력 칸이 없는데, 일부 저장소 글의 머리말 요약이 200자를 넘었다. 수정할 칸이 없으니 경고를 해소할 방법도 없었다.

| 단계                 | 결과                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| 처음 검색            | 요약이 200자를 넘는 글 7편                                                                      |
| 최신 main으로 rebase | 11편 추가 발견                                                                                  |
| 조치                 | 18편의 요약을 200자 이내로 수정                                                                 |
| 재발 방지            | `content.test.ts` 추가: 저장소 글 140편이 편집기와 같은 규칙(`validateDraft`)을 통과하는지 검사 |

이제 요약이 긴 글은 저장소에 머지되기 전에 시험에서 실패한다.

좁은 창에서 경고 문구가 날짜·폴더 줄과 겹치던 문제도 수정했다. 경고가 표시되면 날짜 줄 위에 별도 줄로 배치한다.

## 사라지는 빈 폴더와 ~ 하나로 적용되던 취소선

**빈 폴더:** 폴더 목록은 저장된 폴더와 글에 지정된 폴더를 합쳐 렌더링한다. 그래서 글에서만 생긴 폴더는 마지막 글이 빠지면 함께 사라졌다. 글이 폴더를 떠나는 네 경로에서 원래 폴더를 저장하게 했다(`keepFolder`).

| 경로                    |
| ----------------------- |
| 드래그 앤 드롭으로 이동 |
| 여러 개 선택 후 이동    |
| 삭제                    |
| 편집 화면에서 폴더 변경 |

**취소선:** `220~440px`처럼 범위를 적은 글에서 두 `~` 사이가 취소선으로 렌더링됐다. 읽기 화면(remark-gfm)과 편집기 모두 `~` 하나짜리 취소선을 허용하고 있었다. 두 곳 모두 `~~`만 취소선으로 처리하게 했다. 읽기 화면은 remark-gfm 옵션을 `singleTilde: false`로 지정하고, 편집기는 같은 옵션으로 파싱하면서 `~` 하나를 받던 입력 규칙을 `~~`만 받는 규칙으로 교체했다.

```markdown
사이드바 180~360px, 목록 220~440px ← 전: "360px, 목록 220" 부분이 취소선
~~취소선~~ ← 후: ~~ 두 개만 취소선
```

![~ 하나로 적용된 취소선](./images/day-1015-tilde.jpg '실제로 문제가 된 글 「메모 칸 너비 조절」. 사이드바 180~360px의 가운데가 취소선으로 렌더링됐다')

## 토글 목록과 각주

서식 메뉴(가가)에 "토글 목록"과 "각주 넣기"를 추가했다.

| 서식      | 동작                                                                       | 저장 형식                                           |
| --------- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| 토글 목록 | › 를 눌러 접고 펼친다. 접힌 상태도 저장한다                                | 읽기 화면이 이미 렌더링하던 `<details>`·`<summary>` |
| 각주      | 커서 위치에 번호를 넣고, 글 끝에 내용 칸을 만들어 커서를 그곳으로 이동한다 | `[^1]`                                              |

![토글 목록과 각주](./images/day-1015-toggle.jpg '편집기에서 토글 제목 앞의 ›로 접고, 본문의 [1]은 글 끝의 각주로 링크된다')

화면을 캡처하다가 버그를 하나 더 발견했다. 각주를 넣으면 글 중간의 빈 줄이 `<br />`로 저장됐다. 함께 수정했다.

정정할 내용도 있었다. 처음에는 "기존 편집기가 `<details>` 줄을 버려서 저장하면 사라졌다"고 판단했다. 다시 확인하니 main의 편집기는 그 줄을 원본 HTML 문자열로 표시하고 그대로 저장했다. 사라진 것은 새로 만든 플러그인의 초기 버그였다. 커밋 메시지와 PR에는 정정한 내용으로 기록했다.

## 편집 화면을 읽기 화면과 일치시키기

### 글 안 링크 이동

관리자로 편집할 때는 각주 번호나 글 안 링크(`#이름`)를 눌러도 해당 위치로 이동하지 않았다. 이제 편집기에서도 각주 번호, ↩, 글 안 링크를 누르면 해당 위치로 스크롤하고, 도착한 곳을 잠시 노란색으로 강조한다. 링크 글자를 수정하려면 Option 키를 누른 채 클릭한다. macOS 메모와 같은 방식이다.

### 레이아웃 측정

줄 높이와 여백은 눈으로 맞추지 않고 측정했다. 같은 글을 두 화면에서 열고, 본문 블록마다 위치(`top`)와 높이(`height`)를 비교했다. 차이가 있는 곳은 두 군데였다.

| 차이              | 원인                                                                            | 수정 대상                               |
| ----------------- | ------------------------------------------------------------------------------- | --------------------------------------- |
| 본문 글자 크기    | 편집기 15px, 읽기 화면 14px. 편집 칸이 700px보다 좁으면 글자를 키우던 이전 규칙 | 편집기 (규칙 삭제)                      |
| 긴 코드가 든 목록 | 읽기 화면에서 긴 코드가 칸 밖으로 넘쳤다                                        | 읽기 화면 (편집기처럼 칸 안에서 줄바꿈) |

이제 문단, 제목, 목록, 표, 이미지, 코드, 접기 블록, 각주가 두 화면에서 같은 위치에 렌더링된다. 이 비교는 E2E 시험으로 고정했다.

![편집 화면과 읽기 화면](./images/day-1015-parity.jpg '같은 글. 수정 전 편집 화면은 글자가 커서 줄바꿈이 더 많았다')

### 관리자 배지를 보기 전환 버튼으로

관리자 배지를 버튼으로 바꿨다. 누르면 방문자가 보는 읽기 화면으로 전환되고, 다시 누르면 편집 화면으로 돌아온다. 휴대폰에는 화면 상단에 배지가 없어서 ••• 메뉴에 "읽기 화면으로 보기"를 추가했다.

![관리자 배지](./images/day-1015-chip.jpg '편집 화면의 관리자 배지를 누르면 눈 아이콘의 읽기 화면으로 전환된다')

## 개발 환경 문제: 로그인 400과 패키지 연결

수정 결과를 확인하려고 로그인하자 "로그인 요청이 올바르지 않습니다." 400 오류가 발생했다. 4000번 포트에는 다시 Docker 컨테이너 `macfolio-api-1`이 실행 중이었다. 이번에는 그날 밤 docker compose로 실행된 것이었다.

1. 배포용 이미지라 `NODE_ENV=production`이다
2. 그래서 OAuth state 검증용 쿠키에 `Secure` 속성이 붙는다
3. 브라우저는 http인 `localhost:4000`에 `Secure` 쿠키를 다시 전송하지 않을 수 있다
4. GitHub에서 돌아왔을 때 비교할 state 쿠키가 없어 400을 반환한다

같은 시각에 개발 서버도 오류를 냈다. 새 브랜치를 최신 main에서 만들었는데, 그 사이 main에 새 패키지 `@macfolio/contracts`가 추가되었고 로컬 `node_modules`에는 링크되어 있지 않았다. `pnpm install`을 다시 실행해 해결했다.

## CI: 시험을 시작하지 못한 #225

#225의 CI가 실패했다. 코드 문제가 아니었다. Postgres 이미지를 `public.ecr.aws`에서 내려받다가 `toomanyrequests: Data limit exceeded`로 세 번 연속 거부됐다. 실패한 작업만 재실행했다. 같은 한도 초과는 다음 날에도 네 번 더 발생한다.

## 돌아보며

이날 수정한 것은 모두 메모 앱을 직접 사용하다가 발견했다. 특히 요약 200자 문제는 편집기의 검증 규칙과 저장소 글이 서로 다른 기준을 쓰던 문제다. 편집기는 200자를 넘으면 게시를 막는데, 저장소 글은 그 규칙으로 검사한 적이 없었다. 같은 규칙을 시험에서도 사용하자(`content.test.ts`) 18편이 한꺼번에 드러났다. 검증 규칙은 데이터가 들어오는 모든 경로에서 같아야 한다.

편집 화면을 측정값으로 맞춘 것이 효과적이었다. 눈으로 비교하면 "거의 같다"에서 멈춘다. 블록마다 위치를 측정하니 15px과 14px의 차이, 그리고 읽기 화면 쪽의 결함까지 드러났다.

이전 API 컨테이너는 이틀 연속 다른 증상으로 나타났다. 전날은 `Cannot PUT`, 이날은 로그인 400이다. 같은 원인을 두 번 찾았으므로, 개발 서버를 시작할 때 4000번 포트가 이미 점유되어 있으면 바로 알리도록 하는 것이 맞다.
