## 요약 200자에 막힌 게시

저장소에 든 글을 편집기에서 고쳐 게시하려고 하자 "요약은 200자까지 입력할 수 있습니다."라는 경고가 나오고 게시가 되지 않았다. 편집 화면에는 요약 칸이 없다. 그런데 저장소 글 일부의 머리말 요약이 200자를 넘었다. 고칠 칸이 없으니 경고를 풀 방법도 없었다.

처음에는 요약이 긴 글 일곱 개를 찾았다. 최신 main으로 옮기자 열한 개가 더 걸려서, 모두 열여덟 개의 요약을 200자 안으로 줄였다. 그리고 `content.test.ts`를 새로 만들었다. 저장소 글 140개가 모두 편집기와 같은 규칙(`validateDraft`)을 지키는지 검사한다. 이제 요약이 긴 글은 저장소에 들어오기 전에 시험에서 걸린다.

경고 문구가 좁은 창에서 날짜·폴더 줄과 겹치던 것도 고쳤다. 경고가 떠 있으면 그 줄을 날짜 줄 위의 따로 한 줄로 내린다.

## 사라지는 빈 폴더와 ~ 하나짜리 취소선

폴더 목록은 저장해 둔 폴더와 글에 적힌 폴더를 합쳐 그린다. 그래서 글에서만 생긴 폴더는 마지막 글이 빠지면 함께 사라졌다. 글이 폴더를 떠나는 네 곳(끌어 놓기, 여러 개 옮기기, 지우기, 편집 화면에서 폴더 바꾸기)에서 원래 폴더를 저장해 두게 했다(`keepFolder`).

`220~440px`처럼 범위를 적은 글은 두 `~` 사이가 취소선이 되었다. 읽기 화면과 편집기 모두 `~` 하나짜리 취소선을 받고 있었다. 이제 두 곳 모두 `~~`만 취소선으로 본다.

![~ 하나짜리 취소선](./images/day-1015-tilde.jpg '실제로 걸린 글 「메모 칸 너비 조절」. 사이드바 180~360px의 가운데가 취소선이었다')

## 토글 목록과 각주

서식 메뉴(가가)에 "토글 목록"과 "각주 넣기"를 더했다. 토글은 읽기 화면이 이미 그리던 `<details>`·`<summary>` 표기 그대로 저장하고, 접힌 상태도 저장한다. 각주는 커서 자리에 번호를 넣고 글 끝에 내용 칸을 만들어 커서를 그리로 옮긴다. 저장 형식은 `[^1]`이다.

![토글 목록과 각주](./images/day-1015-toggle.jpg '편집기에서 토글 제목 앞의 ›로 접고, 본문의 [1]은 글 끝의 각주로 이어진다')

캡처를 찍다가 버그를 하나 더 찾았다. 각주를 넣으면 글 가운데의 빈 줄이 `<br />`로 저장되었다. 함께 고쳤다.

정정할 것도 있었다. 처음 보고에서는 "원래 편집기가 `<details>` 줄을 버려서 저장하면 사라졌다"고 했다. 다시 보니 main의 편집기는 그 줄을 날것의 HTML 글자로 보여 주고 그대로 저장했다. 사라진 것은 새로 만든 플러그인의 초기 버그였다. 커밋 메시지와 PR에는 바른 내용으로 적었다.

## 편집 화면을 읽기 화면과 같은 자리에

관리자로 편집할 때는 각주 번호나 글 안 링크(`#이름`)를 눌러도 그 자리로 가지 않았다. 이제 편집기에서도 각주 번호, ↩, 글 안 링크를 누르면 그 자리로 가고, 도착한 곳을 잠깐 노랗게 칠한다. 링크 글자를 고치려면 Option을 누른 채 누른다. macOS 메모와 같은 방식이다.

줄 높이와 여백은 눈으로 맞추지 않고 쟀다. 같은 글을 두 화면에서 열고 본문 블록마다 위치와 높이를 비교했다. 다른 곳은 두 군데였다.

- **본문 글자 크기:** 편집기는 15px, 읽기 화면은 14px이었다. 편집 칸이 700px보다 좁으면 글자를 키우던 옛 규칙 때문이었다.
- **긴 코드가 든 목록:** 여기서는 읽기 화면이 잘못이었다. 긴 코드가 칸 밖으로 나갔다. 편집기처럼 칸 안에서 줄을 바꾸게 했다.

이제 문단, 제목, 목록, 표, 이미지, 코드, 접기, 각주가 두 화면에서 같은 자리에 놓인다. 이 비교는 E2E 시험으로 남겼다.

![편집 화면과 읽기 화면](./images/day-1015-parity.jpg '같은 글. 수정 전 편집 화면은 글자가 커서 줄이 더 많이 바뀌었다')

관리자 배지도 버튼이 되었다. 누르면 방문자가 보는 읽기 화면으로 바뀌고, 한 번 더 누르면 편집 화면으로 돌아온다. 휴대폰에는 화면 위에 배지가 없어서 ••• 메뉴에 "읽기 화면으로 보기"를 넣었다.

![관리자 배지](./images/day-1015-chip.jpg '편집 화면의 관리자 배지를 누르면 눈 아이콘의 읽기 화면이 된다')

## 로그인 400, 다시 그 컨테이너

고친 것을 보려고 로그인하자 "로그인 요청이 올바르지 않습니다." 400이 났다. 4000번 포트에는 또 Docker 컨테이너 `macfolio-api-1`이 떠 있었다. 이번에는 그날 밤 docker compose로 켜진 것이었다.

1. 배포용 이미지라 `NODE_ENV=production`이다.
2. 그래서 로그인 확인용 state 쿠키에 `Secure`가 붙는다.
3. 브라우저는 http인 `localhost:4000`에 이 쿠키를 다시 보내지 않을 수 있다.
4. GitHub에서 돌아왔을 때 비교할 쿠키가 없으니 400이 난다.

같은 시간에 개발 서버도 오류를 냈다. 새 브랜치를 최신 main에서 만들었는데, 그 사이 main에 새 패키지 `@macfolio/contracts`가 생겼다. 로컬 `node_modules`에는 연결되어 있지 않았다. `pnpm install`을 다시 실행해서 풀었다.

## 돌아보며

이날 고친 것은 모두 직접 메모 앱을 쓰다가 찾은 것이다. 특히 요약 200자는 편집기의 검사 규칙과 저장소 글이 따로 놀았던 문제다. 편집기는 200자를 넘으면 막는데, 저장소 글은 아무도 그 규칙으로 검사하지 않았다. 같은 규칙을 시험에서도 쓰게 하자(`content.test.ts`) 열여덟 개가 한꺼번에 드러났다. 규칙은 들어오는 모든 길에서 같아야 한다.

편집 화면 맞추기는 재서 맞춘 것이 좋았다. 눈으로 보면 "거의 같다"에서 멈춘다. 블록마다 위치를 재니 15px과 14px, 그리고 읽기 화면 쪽의 잘못까지 나왔다.

옛 API 컨테이너는 이틀 연속 다른 증상으로 나타났다. 하루는 `Cannot PUT`, 하루는 로그인 400이다. 같은 원인을 두 번 찾았으니, 개발 서버를 켤 때 4000번 포트가 이미 잡혀 있으면 바로 알려 주게 하는 것이 맞다.
