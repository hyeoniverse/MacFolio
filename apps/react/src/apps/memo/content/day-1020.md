## 디자인 토큰을 세 층으로

디자인 토큰은 색·모서리 반경·그림자 같은 디자인 값에 붙인 이름이다. CSS에서는 사용자 정의 속성(custom property)으로 구현한다. `:root`에 `--color-label: rgba(0, 0, 0, 0.85);`처럼 `--`로 시작하는 이름을 정의하고, 각 요소에서 `color: var(--color-label);`처럼 참조한다. 값을 이름으로 참조하면 다크 모드처럼 값이 바뀌어야 하는 상황에서 정의 한 줄만 바꾸면 되고, "이 회색은 기본 글자색"이라는 용도도 코드에 남는다.

전날까지 색·모서리·그림자 값에 이름을 부여해 왔는데, `theme.css` 한 파일 안에서 명명 규칙이 일관되지 않았다.

| 문제                   | 예                                                                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 용도에 여러 이름  | 기본 글자색 하나에 `--color-text`·`text-strong`·`label`·`popover-text`·`menubar-text` 다섯 이름, 값도 `#333`·`#000`·`#1d1d1f`·`#111` 네 가지 |
| 같은 색에 서로 다른 값 | 빨강을 뜻하는 `red`·`danger`·`error`가 각각 다른 값                                                                                          |
| 명명 기준 혼재         | 모서리 반경에 크기 기준 이름(`xs`~`xl`)과 용도 기준 이름(`panel`·`window`)이 함께 쓰임                                                       |

그래서 토큰을 세 층으로 재구성했다([#286](https://github.com/hyeoniverse/MacFolio/pull/286)).

| 층         | 파일             | 정의하는 값                                                                    | 앱 CSS에서 사용                  |
| ---------- | ---------------- | ------------------------------------------------------------------------------ | -------------------------------- |
| 1 원시값   | `primitives.css` | `--palette-*` 색 값, 숫자 이름의 `--radius-4…22`, 높이 단계 `--shadow-1…`      | 색은 사용 금지, 숫자 이름은 사용 |
| 2 의미     | `semantic.css`   | macOS 시스템 색 이름의 `--color-*`, 용도 별칭(`--radius-window` 등), `--z-*`   | 사용                             |
| 3 컴포넌트 | `components.css` | 컴포넌트 하나만 사용하는 값 (Dock·메뉴 막대·사이드바·공통 컴포넌트의 `--ui-*`) | 해당 컴포넌트만 사용             |

참조 방향은 컴포넌트 → 의미 → 원시의 한 방향뿐이다. 빨간색 하나를 예로 들면 다음 세 줄이 이어진다.

```css
/* 1층 primitives.css: 실제 색 값 */
--palette-red-light: #ff3b30;
--palette-red-dark: #ff453a;
/* 2층 semantic.css: macOS 시스템 색 이름 */
--color-system-red: var(--palette-red-light);
/* 3층 components.css: 공통 컴포넌트가 쓰는 이름 */
--ui-danger: var(--color-system-red);
```

![토큰 세 층의 참조 방향](./images/day-1020-token-layers.svg '앱 CSS는 2·3층 이름만 쓰고, 1층 색(--palette-*)을 직접 쓰면 Stylelint가 차단한다. 다크 모드는 2층 이름만 다른 원시값으로 재정의한다')

==앱 CSS가 원시 색(`--palette-*`)을 직접 쓰지 않으므로, 다크 모드에서 색을 바꿀 때는 의미 층의 `--color-*`만 재정의하면 된다.== 위 예에서 `:root[data-theme='dark']`가 `--color-system-red`를 `var(--palette-red-dark)`로 바꾸면, `--ui-danger`를 쓰는 삭제 버튼과 오류 문구가 모두 함께 바뀐다.

같은 방향의 정리 PR을 앞뒤로 이어서 올렸다. 그중 #280은 Stylelint를 도입했다. Stylelint는 CSS 파일을 읽어 규칙에 어긋나는 선언을 찾아내는 정적 검사 도구로, ESLint가 JavaScript에 하는 일을 CSS에 한다.

## 공통 컴포넌트 여섯 개와 큰 파일 분리

리팩터링 계획에서 보류했던 공통 컴포넌트 후보 여섯 개를 다시 조사했다([#276](https://github.com/hyeoniverse/MacFolio/pull/276)). 공통 컴포넌트는 여러 앱이 같은 마크업과 동작을 복사하지 않고 한 구현을 가져다 쓰도록 `shared/ui`에 둔 부품이다. 보류할 당시에는 앱마다 높이·여백이 달라 하나로 합칠 수 없었는데, 그사이 값이 통일된 것이 많았다.

| 컴포넌트     | 재조사 결과                                                            | 판단                       |
| ------------ | ---------------------------------------------------------------------- | -------------------------- |
| `Switch`     | 설정 4곳, 크기 두 가지에 동작은 같음                                   | 생성                       |
| `TabList`    | 탭 4곳의 마크업이 같고, 네 곳 모두 화살표 키 이동이 없었음             | 생성 (화살표 키 이동 추가) |
| `Toolbar`    | 다섯 앱 모두 높이 52px·간격 8px으로 통일됨                             | 생성                       |
| `Sidebar`    | 평평한 형태(Finder·휴지통·설정)와 떠 있는 패널(메모·메일 등) 두 종류   | 생성                       |
| `ListRow`    | 스타일은 앱마다 다르지만 `<li><button aria-current>` 구조는 7곳이 같음 | 마크업 구조만              |
| `EmptyState` | 흐린 글자·가운데 정렬이 10곳에서 같음                                  | 스타일만                   |

`TabList`는 공통 컴포넌트로 합치면서 화살표 키 이동을 넣었다. WAI-ARIA의 탭 패턴은 ←·→ 키로 탭 사이를 이동하도록 정하고 있는데, 네 곳의 탭 모두 Tab 키로만 이동할 수 있었다. 한 곳에 구현하자 네 곳이 모두 키보드로 조작 가능해졌다.

### 스택 PR이 main에 반영되지 않은 문제

스택 PR(stacked pull request)은 큰 변경을 여러 PR로 나눌 때, 각 PR을 main이 아니라 바로 앞 PR의 브랜치 위에 쌓는 방식이다. PR마다 앞 PR 이후의 변경만 diff에 보여 검토하기 쉽다. 대신 각 PR의 base(머지 대상 브랜치)가 main이 아니라 앞 PR의 브랜치라는 점을 머지할 때 고려해야 한다.

#288부터 #292까지가 이 방식이었다. #290을 main에 머지하고, 1분과 3분 뒤 #291과 #292를 머지했다. 그런데 두 PR의 base는 main이 아니라 바로 앞 PR의 브랜치였고, 그 브랜치는 이미 main에 머지한 뒤였다. 그래서 #291과 #292는 GitHub에서 "Merged"로 표시되지만 main에는 반영되지 않았다.

![스택 PR의 base](./images/day-1020-stacked-pr-base.svg '#291은 이미 머지가 끝난 #290 브랜치로, #292는 #291 브랜치로 들어갔다. 세 PR 모두 Merged로 표시되지만 main에는 #290만 반영됐다')

다음 날 [#294](https://github.com/hyeoniverse/MacFolio/pull/294)로 두 변경을 main에 다시 넣었다.

> [!WARNING] 스택 PR의 base
> 스택 PR은 앞 PR이 머지되면 뒤 PR의 base를 main으로 변경한 뒤에 머지해야 한다. GitHub는 PR 화면의 "Edit"에서 base 브랜치를 바꿀 수 있다.

## Finder를 실제 OS 구조로

### 열기 창에서 비어 보이던 포트폴리오 ([#282](https://github.com/hyeoniverse/MacFolio/pull/282))

미리보기의 열기 창에서 **데스크탑 › 포트폴리오**를 열면 "비어 있음"이 표시되는데, **문서 › 포트폴리오**로 이동하면 프로젝트가 모두 있는 것을 확인했다.

| 수정 전                                                                                             | 수정 후                                                                                              |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| ![수정 전](./images/finder-home-tree-openpanel-before.jpg '바탕화면의 포트폴리오를 열면 비어 있음') | ![수정 후](./images/finder-home-tree-openpanel-after.jpg '같은 동작으로 문서 › 포트폴리오가 열린다') |

바탕화면의 포트폴리오는 실제 폴더가 아니라 가상본(alias)이다. macOS의 가상본은 원본 파일이나 폴더를 가리키는 작은 참조 파일로, 열면 원본이 열린다. 이 사이트는 가상본을 "내용이 빈 폴더에 원본 폴더 id를 추가한 것"으로 표현하고 있었다. Finder는 그 id로 원본을 찾아갔지만, 열기 창만 빈 폴더 자체를 열었다.

한 줄로 고칠 수도 있었지만, 같은 유형의 버그가 반복되는 구조인지 먼저 확인했다. 가상본을 처리하는 12곳이 "가상본이면 원본으로 이동한다"는 규칙을 각자 구현하고 있었다. git 기록을 보면 전날 열기 창이 트리를 쓰기 시작한 직후 가상본을 추가하면서 열기 창에서만 처리를 빠뜨렸고, 같은 날 같은 파일을 고칠 때도 다시 빠뜨렸다.

그래서 가상본을 폴더의 변형이 아니라 별도의 노드 종류로 분리했다. 지금의 타입은 다음과 같다. 가상본에는 `children`이 없으므로, 폴더처럼 내용을 읽으려면 반드시 `target`으로 원본을 찾아야 한다.

```ts
interface FolderItem extends ItemBase {
	kind: 'folder';
	children: FinderItem[];
}

interface AliasItem extends ItemBase {
	kind: 'alias';
	/** 원래 폴더의 id (예: docs:포트폴리오) */
	target: string;
}
```

==이제 가상본 처리를 빠뜨린 코드는 타입 검사에서 오류가 난다.== 예전 표현에서는 가상본도 `kind: 'folder'`라 `item.children`을 읽으면 빈 배열이 나왔고, 타입 검사는 이를 정상 코드로 판단했다.

### 루트가 하나인 트리 ([#285](https://github.com/hyeoniverse/MacFolio/pull/285))

이어서 실제 Mac의 Finder 화면과 비교했다. 실제 macOS는 시동 디스크(Macintosh HD) 하나를 루트로 두고 그 아래에 모든 폴더가 있다. 이 사이트의 Finder는 데스크탑·문서·블로그·응용 프로그램이 각각 별도의 최상위 노드였다. Macintosh HD › 사용자 › hyeoniverse 아래에 데스크탑·문서·블로그와 macOS 기본 폴더(공용·그림·다운로드·동영상·음악)를 배치하고, 사이드바의 즐겨찾기를 그 안 폴더로 이동하는 바로가기로 바꿨다.

| 결정 사항         | 선택          |
| ----------------- | ------------- |
| 블로그 폴더 위치  | 홈 폴더 안    |
| 빈 기본 폴더 생성 | 생성          |
| 홈 폴더 이름      | `hyeoniverse` |

서버에 저장된 폴더 id는 그대로 두고 그 위에 노드만 추가해서, 서버 데이터는 변경되지 않는다([가상본을 별도 종류로 분리한 단일 루트 파일 시스템 트리](/memo/finder-filesystem#가상본이-빈-폴더로-열린-원인)).

### 그림과 음악 폴더 ([#287](https://github.com/hyeoniverse/MacFolio/pull/287))

빈 기본 폴더에는 내용을 채웠다. 음악 폴더에는 음악 앱의 곡을, 그림 폴더에는 사진 앱의 사진을 배치했다. 프로젝트 폴더 안에 있던 사진 폴더도 그림 폴더로 옮겼다. 같은 사진이 두 곳에 있으면 원본 위치가 모호해지기 때문이다. 음악은 아티스트 › 앨범 › 곡 구조로 구성하고, 곡을 열면 음악 앱이 그 앨범을 재생 목록으로 삼아 그 곡부터 재생한다.

곡이라는 새 노드 종류를 추가하자, #282에서 Finder의 열기 함수 끝에 넣어 둔 `never` 검사가 컴파일 오류를 냈다. 모든 노드 종류의 처리를 강제하는 TypeScript의 완전성 검사(exhaustiveness check)다. `switch`의 각 `case`가 `kind` 값 하나씩을 처리하면 TypeScript는 남은 가능성을 좁혀 나가고, 모든 종류를 처리했다면 `default`에 도달한 값의 타입은 "어떤 값도 될 수 없음"을 뜻하는 `never`가 된다. 처리하지 않은 종류가 남아 있으면 그 종류가 `never`에 대입되므로 컴파일 오류가 난다. 형태를 요약하면 다음과 같다.

```ts
switch (node.kind) {
	case 'folder':
		/* … */ break;
	case 'alias':
		/* … */ break;
	// 새 종류를 추가하고 case를 작성하지 않으면 아래 줄에서 타입 오류
	default: {
		const unhandled: never = node;
		throw new Error(String(unhandled));
	}
}
```

곡 노드의 타입은 `kind: 'track'`인 `TrackItem`이라, 오류는 `Type 'TrackItem' is not assignable to type 'never'` 형태로 나온다. 누락을 막으려고 넣은 검사가 바로 다음 PR에서 새 노드 종류의 처리 누락을 잡았다.

## 동시에 진행한 두 작업의 충돌

토큰 정리와 Finder 작업은 같은 시간대에 별도 브랜치에서 진행했다. 서로 겹치는 파일이 거의 없어 충돌이 없을 것으로 예상했지만, 한 줄에서 두 번 충돌했다.

![동시에 진행한 두 작업의 충돌](./images/day-1020-collision.svg '#280이 숫자 4px를 차단하자 Finder 쪽 커밋이 CI에서 실패했고, #286이 --radius-xs를 --radius-4로 변경하자 방금 수정한 줄이 정의되지 않은 변수를 참조하게 됐다')

| 순서 | 사건                                                                 | 검출 여부         |
| ---: | -------------------------------------------------------------------- | ----------------- |
|    1 | #280 머지: 토큰 이름이 있는 값을 숫자로 쓰면 차단                    | -                 |
|    2 | Finder 쪽 커밋이 앨범 그림 모서리를 `border-radius: 4px`로 작성      | CI 린트에서 실패  |
|    3 | `var(--radius-xs)`로 수정                                            | -                 |
|    4 | #286 머지: 모서리 토큰을 숫자 기준 이름으로 변경, `--radius-xs` 삭제 | **검출되지 않음** |
|    5 | `var(--radius-4)`로 다시 수정                                        | -                 |

두 번째 충돌은 린트도 CI도 오류를 보고하지 않았다. ==정의되지 않은 CSS 변수는 오류 없이 무시되고==, 모서리 반경만 적용되지 않기 때문이다. CSS 명세에서 `var(--radius-xs)`가 가리키는 속성이 없으면 그 선언은 "계산 시점에 무효(invalid at computed-value time)"가 되고, `border-radius`는 초깃값 0으로 돌아간다. 브라우저 콘솔에도 경고가 나오지 않으므로, 화면에서 모서리가 각진 것을 보고서야 알 수 있다.

숫자를 차단하는 규칙은 첫 번째 충돌을 검출했지만, 이름을 바꾼 두 번째는 직접 찾아야 했다. 다음 날에는 토큰을 대규모로 바꾼 뒤 스타일이 어긋난 곳이 없는지 확인하려고, main과 Finder 브랜치를 같은 장면에서 캡처해 픽셀 단위로 비교했다. 같아야 하는 장면 14장(라이트·다크)이 모두 차이 0이었다. 이어진 정리는 [10월 21일 회고](/memo/day-1021)에 적었다.

## 서버 접속과 개발 환경

시스템 데이터 용량이 너무 커져 급하게 Mac을 초기화하면서 로컬 API의 `.env`와 서버 SSH 키를 함께 잃었다. SSH 키 인증은 로컬에 보관한 개인 키와, 서버의 `~/.ssh/authorized_keys` 파일에 등록한 공개 키가 짝을 이루는지 확인하는 방식이다. 개인 키를 잃으면 서버에 등록된 공개 키와 짝을 맞출 방법이 없다.

서버의 배포 설정값을 가져오려 해도 접속할 키가 없었다. 비밀번호 로그인 계정이 없는 Ubuntu 서버라 시리얼 콘솔로도 접속할 수 없어서, 원래 서버의 부트 디스크를 분리해 임시 VM에 연결하고 새 공개 키를 `authorized_keys`에 추가하기로 했다.

![임시 VM이 원래 서버 디스크로 부팅된 과정](./images/oracle-ssh-key-recovery-boot.svg '두 디스크의 루트 레이블이 같아, 디스크를 연결한 임시 VM이 원래 서버 디스크로 부팅됐다')

그런데 디스크를 연결한 임시 VM이 재부팅되면서 **원래 서버 디스크로** 부팅됐다. 두 디스크의 루트 파일 시스템 레이블이 같았기 때문이다. 부팅할 루트 파일 시스템을 레이블로 찾는 설정에서는, 같은 레이블의 디스크가 둘 연결되면 어느 쪽으로 부팅할지 보장되지 않는다.

cloud-init은 클라우드 VM이 처음 부팅될 때 호스트 이름 설정, 공개 키 등록 같은 초기 설정을 하는 프로그램이다. 인스턴스 id가 바뀐 것을 보고 이 부팅을 새 VM의 첫 부팅으로 판단해, 임시 VM용 공개 키를 원래 서버 디스크의 `authorized_keys`에 추가해 둔 상태였다. 디스크 구성을 원래대로 되돌리고 서버를 시작하자 API가 다시 응답했다. 바뀐 호스트 키로 배포 secret(`DEPLOY_KNOWN_HOSTS`)을 고치고, 분실한 이전 키 줄을 `authorized_keys`에서 삭제했다([부트 볼륨을 임시 VM에 연결해 authorized_keys를 고치는 SSH 키 복구](/memo/oracle-ssh-key-recovery), [#278](https://github.com/hyeoniverse/MacFolio/pull/278)).

그 과정의 시행착오는 다음과 같다.

| 시행착오                                        | 바른 방법                                                                  |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| 키 암호(passphrase)와 공개 키를 혼동            | 암호는 개인 키 파일을 여는 비밀번호, 공개 키는 서버에 등록하는 `.pub` 파일 |
| 디스크 확인용 `lsblk`를 Cloud Shell에서 실행    | 디스크를 연결한 임시 VM 안에서 실행해야 연결한 디스크가 보인다             |
| 로컬에서 실행해야 하는 `scp`를 서버 안에서 실행 | `scp`는 파일을 보내는 쪽(로컬)에서 실행한다                                |

로컬 개발 환경도 복구했다.

- pnpm이 없어 먼저 `npm install`을 실행했다가 루트 패키지만 설치되고 `package-lock.json`이 생성됐다. Node 25부터 corepack이 기본 포함되지 않기 때문이다. corepack은 `package.json`의 `packageManager` 필드에 적힌 pnpm 버전을 자동으로 받아 실행하는 Node 동봉 도구였다([zsh: command not found: pnpm](/memo/pnpm-command-not-found))
- 서버의 배포 설정값으로 로컬 `.env`를 만들 때는 `DATABASE_URL`·`CORS_ORIGINS`처럼 로컬 환경과 다른 키만 수정했다. GitHub OAuth는 로그인 후 돌아올 콜백 주소가 OAuth 앱마다 하나로 고정되므로 개발용 OAuth 앱을 새로 발급받기로 했다
- Docker Desktop은 설치만 하고 실행하지 않아 `docker` 명령이 없는 상태였다

## 돌아보며

[10월 19일](/memo/day-1019)에는 겹치는 작업을 병렬로 진행하지 말자고 적었다. 이날은 겹치지 않는다고 판단한 두 작업이 이름 하나에서 충돌했다. 토큰 작업은 이름을 바꾸고, Finder 작업은 그 이름을 새로 썼다. 파일이 겹치지 않아도 **같은 이름을 사용하면** 겹치는 작업이다. 이름을 바꾸는 작업은 다른 작업을 모두 머지한 뒤에 하거나, 바꾸는 쪽이 이전 이름의 사용처를 모두 찾아 고쳐야 한다. 정의되지 않은 CSS 변수를 검출하는 규칙도 필요하다.

가상본 버그와 CSS 변수 이름은 같은 유형의 문제였다. "가상본이면 원본으로 이동한다", "이 이름은 삭제됐다" 같은 규칙을 ==사람이 기억해야 하면 언젠가 누락된다==. 가상본은 별도의 노드 종류로 분리해 컴파일러가 검출하게 했고, 숫자 값은 Stylelint가 검출하게 했다. 아직 사람이 기억해야 하는 것(삭제된 CSS 변수, 스택 PR의 base)이 남아 있다.

서버 키를 분실한 원인은 급하게 Mac을 초기화하면서 `~/.ssh`를 백업하지 않은 것이다.

> [!CAUTION] 초기화 전 백업
> 새 키와 그 암호는 Mac 외부에도 별도로 보관하고, 초기화하기 전에는 `~/.ssh`와 `.env`처럼 저장소에 없는 파일부터 백업해야 한다.
