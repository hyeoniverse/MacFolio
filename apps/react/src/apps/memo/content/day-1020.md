## 디자인 토큰을 세 층으로

전날까지 색·모서리·그림자 값에 이름(토큰)을 부여해 왔는데, `theme.css` 한 파일 안에서 명명 규칙이 일관되지 않았다.

| 문제                   | 예                                                                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 용도에 여러 이름  | 기본 글자색 하나에 `--color-text`·`text-strong`·`label`·`popover-text`·`menubar-text` 다섯 이름, 값도 `#333`·`#000`·`#1d1d1f`·`#111` 네 가지 |
| 같은 색에 서로 다른 값 | 빨강을 뜻하는 `red`·`danger`·`error`가 각각 다른 값                                                                                          |
| 명명 기준 혼재         | 모서리 반경에 크기 기준 이름(`xs`~`xl`)과 용도 기준 이름(`panel`·`window`)이 함께 쓰임                                                       |

저녁에 토큰을 세 층으로 재구성했다([#286](https://github.com/hyeoniverse/MacFolio/pull/286)).

| 층         | 파일             | 정의하는 값                                                                    | 앱 CSS에서 사용                  |
| ---------- | ---------------- | ------------------------------------------------------------------------------ | -------------------------------- |
| 1 원시값   | `primitives.css` | `--palette-*` 색 값, 숫자 이름의 `--radius-4…22`, 높이 단계 `--shadow-1…`      | 색은 사용 금지, 숫자 이름은 사용 |
| 2 의미     | `semantic.css`   | macOS 시스템 색 이름의 `--color-*`, 용도 별칭(`--radius-window` 등), `--z-*`   | 사용                             |
| 3 컴포넌트 | `components.css` | 컴포넌트 하나만 사용하는 값 (Dock·메뉴 막대·사이드바·공통 컴포넌트의 `--ui-*`) | 해당 컴포넌트만 사용             |

참조 방향은 컴포넌트 → 의미 → 원시의 한 방향뿐이다. 앱 CSS가 원시 색(`--palette-*`)을 직접 쓰지 않으므로, 다크 모드에서 색을 바꿀 때는 의미 층의 `--color-*`만 재정의하면 된다. 같은 방향의 정리 PR이 앞뒤로 이어졌다.

### 스택 PR이 main에 반영되지 않은 문제

#288부터 #292까지는 앞 PR의 브랜치 위에 쌓은 스택 PR이었다. 22시 59분에 #290을 main에 머지하고, 1분과 3분 뒤 #291과 #292를 머지했다. 그런데 두 PR의 대상(base)은 main이 아니라 바로 앞 PR의 브랜치였고, 그 브랜치는 이미 main에 머지된 뒤였다. 그래서 #291과 #292는 GitHub에서 "Merged"로 표시되지만 main에는 반영되지 않았다.

```text
main ◀── #290 머지 (22:59)
#291 ── base: #290의 브랜치 ── 머지 (23:00) → 이미 머지된 브랜치에 병합, main에는 미반영
#292 ── base: #291의 브랜치 ── 머지 (23:02) → 같은 이유로 미반영
```

다음 날 아침 [#294](https://github.com/hyeoniverse/MacFolio/pull/294)로 두 변경을 main에 다시 반영했다. 스택 PR은 앞 PR이 머지되면 뒤 PR의 base를 main으로 변경한 뒤에 머지해야 한다.

## Finder를 실제 OS 구조로

### 열기 창에서 비어 보이던 포트폴리오 ([#282](https://github.com/hyeoniverse/MacFolio/pull/282))

저녁에 미리보기의 열기 창에서 **데스크탑 › 포트폴리오**를 열면 "비어 있음"이 표시되는데, **문서 › 포트폴리오**로 이동하면 프로젝트가 모두 있는 것을 확인했다.

| 수정 전                                                                                             | 수정 후                                                                                              |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| ![수정 전](./images/finder-home-tree-openpanel-before.jpg '바탕화면의 포트폴리오를 열면 비어 있음') | ![수정 후](./images/finder-home-tree-openpanel-after.jpg '같은 동작으로 문서 › 포트폴리오가 열린다') |

바탕화면의 포트폴리오는 실제 폴더가 아니라 가상본(alias)인데, 가상본을 "내용이 빈 폴더에 원본 폴더 id를 추가한 것"으로 표현하고 있었다. Finder는 그 id로 원본을 찾아갔지만, 열기 창만 빈 폴더 자체를 열었다.

한 줄로 수정할 수도 있었지만, 같은 유형의 버그가 반복되는 구조인지 먼저 확인했다. 가상본을 처리하는 12곳이 "가상본이면 원본으로 이동한다"는 규칙을 각자 구현하고 있었다. git 기록을 보면 전날(19일) 새벽 열기 창이 트리를 사용하기 시작한 지 두 시간 뒤에 가상본이 추가되면서 열기 창에서만 처리가 누락됐고, 같은 날 오전 같은 파일을 수정할 때도 다시 누락됐다. 그래서 가상본을 폴더의 변형이 아니라 별도의 노드 종류(`kind: 'alias'`)로 분리했다. 이제 가상본 처리를 빠뜨린 코드는 타입 검사에서 오류가 난다.

### 루트가 하나인 트리 ([#285](https://github.com/hyeoniverse/MacFolio/pull/285))

이어서 실제 Mac의 Finder 화면과 비교했다. 실제 OS는 루트 하나 아래에 모든 폴더가 있는데, 이 사이트의 Finder는 데스크탑·문서·블로그·응용 프로그램이 각각 별도의 최상위 노드였다. Macintosh HD › 사용자 › hyeoniverse 아래에 데스크탑·문서·블로그와 macOS 기본 폴더(공용·그림·다운로드·동영상·음악)를 배치하고, 사이드바의 즐겨찾기를 그 안 폴더로 이동하는 바로가기로 변경했다.

| 결정 사항         | 선택          |
| ----------------- | ------------- |
| 블로그 폴더 위치  | 홈 폴더 안    |
| 빈 기본 폴더 생성 | 생성          |
| 홈 폴더 이름      | `hyeoniverse` |

서버에 저장된 폴더 id는 그대로 두고 그 위에 노드만 추가해서, 서버 데이터는 변경되지 않는다([바탕화면의 포트폴리오만 비어 있었다](/memo/finder-home-tree)).

![홈 폴더](./images/finder-home-tree-home.jpg 'Macintosh HD › 사용자 › hyeoniverse. 기본 폴더 아이콘에 macOS처럼 문양을 넣었다')

### 그림과 음악 폴더 ([#287](https://github.com/hyeoniverse/MacFolio/pull/287))

빈 기본 폴더에는 내용을 채웠다. 음악 폴더에는 음악 앱의 곡을, 그림 폴더에는 사진 앱의 사진을 배치했다. 프로젝트 폴더 안에 있던 사진 폴더도 그림 폴더로 옮겼다. 같은 사진이 두 곳에 있으면 원본 위치가 모호해지기 때문이다. 음악은 아티스트 › 앨범 › 곡 구조로 구성하고, 곡을 열면 음악 앱이 그 앨범을 재생 목록으로 삼아 그 곡부터 재생한다.

곡이라는 새 노드 종류를 추가하자, #282에서 Finder의 열기 함수 끝에 넣어 둔 `never` 검사가 컴파일 오류를 냈다. 모든 노드 종류의 처리를 강제하는 TypeScript의 완전성 검사(exhaustiveness check)다. 형태를 요약하면 다음과 같다.

```ts
switch (node.kind) {
	case 'folder':
		/* … */ break;
	case 'alias':
		/* … */ break;
	// 새 종류를 추가하고 case를 작성하지 않으면 아래 줄에서 타입 오류
	default: {
		const unhandled: never = node;
		throw new Error(String(unhandled));
	}
}
```

누락을 방지하려고 넣은 검사가 바로 다음 PR에서 효과를 발휘했다.

## 같은 저녁 두 작업의 충돌

토큰 정리와 Finder 작업은 같은 저녁에 별도 브랜치에서 진행했다. 서로 겹치는 파일이 거의 없어 충돌이 없을 것으로 예상했지만, 한 줄에서 두 번 충돌했다.

![같은 저녁 두 작업의 충돌](./images/day-1020-collision.svg '#280이 숫자 4px를 차단하자 Finder 쪽 커밋이 CI에서 실패했고, #286이 --radius-xs를 --radius-4로 변경하자 방금 수정한 줄이 정의되지 않은 변수를 참조하게 됐다')

| 시각  | 사건                                                                 | 검출 여부         |
| ----- | -------------------------------------------------------------------- | ----------------- |
| 19:21 | #280 머지: 토큰 이름이 있는 값을 숫자로 쓰면 차단                    | -                 |
| 20:47 | Finder 쪽 커밋이 앨범 그림 모서리를 `border-radius: 4px`로 작성      | CI 린트에서 실패  |
| 20:52 | `var(--radius-xs)`로 수정                                            | -                 |
| 21:13 | #286 머지: 모서리 토큰을 숫자 기준 이름으로 변경, `--radius-xs` 삭제 | **검출되지 않음** |
| 22:46 | `var(--radius-4)`로 다시 수정                                        | -                 |

두 번째 충돌은 린트도 CI도 오류를 보고하지 않았다. 정의되지 않은 CSS 변수는 오류 없이 무시되고, 모서리 반경만 적용되지 않기 때문이다. 숫자를 차단하는 규칙은 첫 번째 충돌을 검출했지만, 이름이 변경된 두 번째는 직접 찾아야 했다.

다음 날 아침에는 토큰을 대규모로 변경한 뒤 스타일이 어긋난 곳이 없는지 확인하려고, main과 Finder 브랜치를 같은 장면에서 캡처해 픽셀 단위로 비교했다. 같아야 하는 장면 14장(라이트·다크)이 모두 차이 0이었다.

## 서버 접속과 개발 환경

낮 시간은 이 작업에 사용했다. 시스템 데이터 용량이 너무 커져 급하게 Mac을 초기화하면서 로컬 API의 `.env`와 서버 SSH 키가 함께 삭제됐다. 서버의 배포 설정값을 가져오려 해도 접속할 키가 없었다. 비밀번호 로그인 계정이 없는 Ubuntu 서버라 시리얼 콘솔로도 접속할 수 없어서, 원래 서버의 부트 디스크를 분리해 임시 VM에 연결하고 새 공개 키를 추가하기로 했다.

![임시 VM이 원래 서버 디스크로 부팅된 과정](./images/oracle-ssh-key-recovery-boot.svg '두 디스크의 루트 레이블이 같아, 디스크를 연결한 임시 VM이 원래 서버 디스크로 부팅됐다')

그런데 디스크를 연결한 임시 VM이 17시 54분에 재부팅되면서 **원래 서버 디스크로** 부팅됐다. 두 디스크의 루트 파일 시스템 레이블이 같았기 때문이다. cloud-init은 이를 새 VM의 첫 부팅으로 판단해, 임시 VM용 공개 키를 원래 서버 디스크의 `authorized_keys`에 추가해 둔 상태였다. 디스크 구성을 원래대로 되돌리고 서버를 시작하자 18시 13분에 API가 복구됐다. 변경된 호스트 키로 배포 secret(`DEPLOY_KNOWN_HOSTS`)을 수정하고, 분실한 이전 키 줄을 `authorized_keys`에서 삭제했다([SSH 키를 잃어버린 Oracle 서버 되살리기](/memo/oracle-ssh-key-recovery), [#278](https://github.com/hyeoniverse/MacFolio/pull/278)).

그 과정의 시행착오는 다음과 같다.

- 키 암호(passphrase)와 공개 키를 혼동했다
- 디스크 확인용 `lsblk`를 서버가 아니라 Cloud Shell에서 실행했다
- 로컬에서 실행해야 하는 `scp`를 서버 안에서 실행했다

로컬 개발 환경도 복구했다.

- pnpm이 없어 먼저 `npm install`을 실행했다가 루트 패키지만 설치되고 `package-lock.json`이 생성됐다. Node 25부터 corepack이 기본 포함되지 않기 때문이다([zsh: command not found: pnpm](/memo/pnpm-command-not-found))
- 서버의 배포 설정값으로 로컬 `.env`를 만들 때는 `DATABASE_URL`·`CORS_ORIGINS`처럼 로컬 환경과 다른 키만 수정했다. GitHub OAuth는 콜백 주소가 다르므로 개발용 OAuth 앱을 새로 발급받기로 했다
- Docker Desktop은 설치만 하고 실행하지 않아 `docker` 명령이 없는 상태였다

## 돌아보며

[10월 19일](/memo/day-1019)에는 겹치는 작업을 병렬로 진행하지 말자고 적었다. 이날은 겹치지 않는다고 판단한 두 작업이 이름 하나에서 충돌했다. 토큰 작업은 이름을 변경하고, Finder 작업은 그 이름을 새로 사용했다. 파일이 겹치지 않아도 **같은 이름을 사용하면** 겹치는 작업이다. 이름을 변경하는 작업은 다른 작업을 모두 머지한 뒤에 하거나, 변경하는 쪽이 이전 이름의 사용처를 모두 찾아 수정해야 한다. 정의되지 않은 CSS 변수를 검출하는 규칙도 필요하다.

가상본 버그와 CSS 변수 이름은 같은 유형의 문제였다. "가상본이면 원본으로 이동한다", "이 이름은 삭제됐다" 같은 규칙을 사람이 기억해야 하면 언젠가 누락된다. 가상본은 별도의 노드 종류로 분리해 컴파일러가 검출하게 했고, 숫자 값은 Stylelint가 검출하게 했다. 아직 사람이 기억해야 하는 것(삭제된 CSS 변수, 스택 PR의 base)이 남아 있다.

서버 키를 분실한 원인은 급하게 Mac을 초기화하면서 `~/.ssh`를 백업하지 않은 것이다. 새 키와 그 암호는 Mac 외부에도 별도로 보관하고, 초기화하기 전에는 `~/.ssh`와 `.env`처럼 저장소에 없는 파일부터 백업해야 한다.
