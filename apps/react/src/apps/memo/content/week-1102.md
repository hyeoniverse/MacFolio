## 메모 글 표기

긴 개념 글에서 핵심 문장이 굵게만으로는 눈에 띄지 않았고, 정의와 주의할 점이 본문과 구분되지 않았으며, 관계 대수식의 아래 첨자는 코드 글자로만 적을 수 있었다. 5일 [#412](https://github.com/hyeoniverse/MacFolio/pull/412)에서 형광펜(`==글자==`), 콜아웃(`> [!NOTE]` 등 다섯 종류), KaTeX 수식(` ```math `, `` `식{:math}` ``), 인라인 코드 문법 강조(`{:sql}`), 제목의 글 안 주소를 더했다. 모두 GitHub·Obsidian·rehype-pretty-code의 표기를 따라, 저장소의 Markdown을 다른 뷰어에서 열어도 의미가 유지되게 했다.

| 표기      | 처리                                                                                                                                   |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 형광펜    | remark 플러그인이 한 문단 안에서 `==`를 짝지어 `<mark>`로 그린다. 기존 글 248편을 렌더링해 `<mark>`가 하나도 생기지 않는 것을 확인했다 |
| 콜아웃    | 인용 블록 첫 줄의 `[!종류]`로 종류를 정한다. 편집 화면은 인용 블록 글자를 그대로 남기고 class만 덧씌운다                               |
| 수식      | rehype 단계에서 수식 자리만 표시하고, `trust` 없이 그려 `\href` 같은 명령을 막는다. 수식 249개를 `strict: 'error'`로 검증했다          |
| 문법 강조 | 코드 블록과 같은 lowlight 규칙. 글에 ` ```sql ` 블록이 80개 있는데도 SQL이 등록되지 않았던 것을 함께 고쳤다                            |
| 제목 주소 | GitHub와 같은 id 규칙에 `user-content-`를 붙인다. 편집 화면에서는 툴팁 버튼이나 ⌘ 누르기로 이동한다                                    |

==KaTeX는 수식이 있는 글을 열 때만 불러와==, 첫 방문 번들은 263.6KB / 265KB로 예산 안에 있다. 편집기가 저장할 때 `> [!NOTE]`를 `> \[!NOTE]`로 이스케이프해 콜아웃이 인용문이 되던 문제는 콜아웃을 더한 직후에 고쳤고, `content.test.ts`가 257편 모든 글의 `#주소` 링크가 실제 제목을 가리키는지 검사한다.

## 위에 붙는 목차 막대

[10월 27일](/memo/day-1027)에 만든 목차는 제목 아래 접기 목록과, 스크롤하면 오른쪽 위에 뜨는 버튼·창이었다. 5일에 이 버튼·창을 스크롤 칸 위에 붙는 한 줄 막대로 바꿨다. 막대는 이전 절, 지금 절과 읽는 자리까지의 하위 제목 경로(`절 › ### › ####`), 다음 절을 보이고, 경로의 제목에 마우스를 올리면 같은 계층의 제목 목록을 펼친다. 처음에는 상위 제목은 하위 제목을, 지금 읽는 제목은 같은 계층을 펼치게 했는데, 마우스를 올린 제목에 따라 목록의 기준이 달라져 모두 같은 계층으로 맞췄다. 막대가 본문을 밀지 않도록 붙기 전에는 아래 여백을 막대 높이만큼 음수로 잡고, 제목이 막대에 가리지 않도록 `scroll-padding-top`을 막대 아래 끝에 맞췄다. Safari가 넘기는 상자 끝에서 튕길 때 바탕까지 밀어 뒤가 비치는 문제는 바탕을 넘기지 않는 바깥 카드로 옮겨 해결했다.

## NestJS 12.3이 감싼 오류

2일 Dependabot이 올린 16개 패키지 업데이트([#411](https://github.com/hyeoniverse/MacFolio/pull/411))에 NestJS 12.2.0 → 12.3.2가 들어 있었다. 12.3부터 Express 어댑터가 body-parser의 http-errors를 `HttpException`으로 감싸 `cause`에 넣어, 너무 큰 요청(413)·깨진 JSON(400)의 설명이 영어 원문으로 나갔다. 전역 예외 필터가 http-errors를 직접 받는 경우만 우리말로 바꾸고 있었기 때문이다. `toErrorBody`가 `HttpException`의 `cause.type`으로 설명을 찾게 하고, 필터 단위 시험에 감싼 413 오류를 더했다. 같은 PR에서 `ai` 7이 요구하는 `@ai-sdk/provider-utils` 5를 4로 고정하던 override도 지웠다.

자세한 내용: [11월 2일~5일](/memo/day-1105)

## 러너 속도와 무관한 성능 시험

#412를 머지한 뒤 CI의 `check`가 desktop-core 검색 성능 시험 한 건(평균 5.46ms, 기준 5ms 미만)에서 실패했고, `deploy`가 `check`에 걸려 있어 배포되지 않았다. 같은 코드가 Mac에서는 0.2ms, GitHub 공유 러너에서는 5ms 안팎이다. ==시험이 지키려던 것은 속도가 아니라 검색용 글자 캐시==였다. 6일 [#414](https://github.com/hyeoniverse/MacFolio/pull/414)에서 시험을 둘로 나눴다. 하나는 검색을 반복한 뒤에도 `searchIndexOf(post)`가 처음 만든 객체와 같은지(`===`) 확인하고, 다른 하나는 같은 실행 안에서 잰 검색용 글자를 처음부터 만드는 시간과 검색 한 번의 시간을 비교해 `perQuery < build / 5`인지 확인한다. 캐시가 깨져 검색마다 검색용 글자를 다시 만들면 `perQuery`가 `build`와 비슷해져 두 번째 시험이 실패한다. 두 값에 러너 속도가 같이 걸려 비율은 유지되고, Mac에서 잰 비율은 48~62배다.

자세한 내용: [11월 6일](/memo/day-1106)

## 돌아보며

- 캐시를 지키려던 시험이 절대 시간을 재서 러너 속도까지 시험했다. 앞으로 시험은 확인하려는 성질을 직접 검사한다. 캐시는 객체 동일성으로 확인하고, 시간이 꼭 필요하면 같은 실행 안의 두 값을 비교한다. 배포가 `check`에 걸린 구조에서는 흔들리는 시험 하나가 그날 머지한 기능 전체를 막는다.
- 마이너 업데이트가 예외의 모양을 바꿀 수 있다는 것을 놓쳤다. 오류 응답의 언어와 모양은 사용자에게 보이는 계약이라, 프레임워크가 감싼 형태를 필터 단위 시험에 함께 넣었다.
- 새 표기는 다른 도구의 문법을 따랐고, 편집기가 그 표기를 이스케이프하지 않는지는 저장 형식 시험으로 확인한다.
- 목차 막대는 구현하면서 구성을 거듭 바꿨다. 상태(맨 위, 붙음, 펼침, 휴대폰)별 화면을 먼저 그린 뒤 구현한다는 원칙을 이번에도 지키지 못했다.
