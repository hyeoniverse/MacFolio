## 메모 글 표기

긴 개념 글에서 핵심 문장이 굵게만으로는 눈에 띄지 않았고, 정의와 주의할 점이 본문과 구분되지 않았으며, 관계 대수식의 아래 첨자는 코드 글자로만 적을 수 있었다. 5일 [#412](https://github.com/hyeoniverse/MacFolio/pull/412)에서 형광펜(`==글자==`), 콜아웃(`> [!NOTE]` 등 다섯 종류), KaTeX 수식(` ```math `, `` `식{:math}` ``), 인라인 코드 문법 강조(`{:sql}`), 제목의 글 안 주소를 더했다. 모두 GitHub·Obsidian·rehype-pretty-code의 표기를 따라, 저장소의 Markdown을 다른 뷰어에서 열어도 의미가 유지되게 했다.

| 표기      | 처리                                                                                                                                   |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 형광펜    | remark 플러그인이 한 문단 안에서 `==`를 짝지어 `<mark>`로 그린다. 기존 글 248편을 렌더링해 `<mark>`가 하나도 생기지 않는 것을 확인했다 |
| 콜아웃    | 인용 블록 첫 줄의 `[!종류]`로 종류를 정한다. 편집 화면은 인용 블록 글자를 그대로 남기고 class만 덧씌운다                               |
| 수식      | rehype 단계에서 수식 자리만 표시하고, `trust` 없이 그려 `\href` 같은 명령을 막는다. 수식 249개를 `strict: 'error'`로 검증했다          |
| 문법 강조 | 코드 블록과 같은 lowlight 규칙. 글에 ` ```sql ` 블록이 80개 있는데도 SQL이 등록되지 않았던 것을 함께 고쳤다                            |
| 제목 주소 | GitHub와 같은 id 규칙에 `user-content-`를 붙인다. 편집 화면에서는 툴팁 버튼이나 ⌘ 누르기로 이동한다                                    |

==KaTeX는 수식이 있는 글을 열 때만 불러와==, 첫 방문 번들은 263.6KB / 265KB로 예산 안에 있다. 편집기가 저장할 때 `> [!NOTE]`를 `> \[!NOTE]`로 이스케이프해 콜아웃이 인용문이 되던 문제는 콜아웃을 더한 직후에 고쳤고, `content.test.ts`가 257편 모든 글의 `#주소` 링크가 실제 제목을 가리키는지 검사한다.

## 위에 붙는 목차 막대

[10월 27일](/memo/day-1027)에 만든 목차는 제목 아래 접기 목록과, 스크롤하면 오른쪽 위에 뜨는 버튼·창이었다. 5일에 이 버튼·창을 스크롤 칸 위에 붙는 한 줄 막대로 바꿨다. 막대는 이전 절, 지금 절과 읽는 자리까지의 하위 제목 경로(`절 › ### › ####`), 다음 절을 보이고, 경로의 제목에 마우스를 올리면 같은 계층의 제목 목록을 펼친다. 처음에는 상위 제목은 하위 제목을, 지금 읽는 제목은 같은 계층을 펼치게 했는데, 마우스를 올린 제목에 따라 목록의 기준이 달라져 모두 같은 계층으로 맞췄다. 막대가 본문을 밀지 않도록 붙기 전에는 아래 여백을 막대 높이만큼 음수로 잡고, 제목이 막대에 가리지 않도록 `scroll-padding-top`을 막대 아래 끝에 맞췄다. Safari가 넘기는 상자 끝에서 튕길 때 바탕까지 밀어 뒤가 비치는 문제는 바탕을 넘기지 않는 바깥 카드로 옮겨 해결했다.

## NestJS 12.3이 감싼 오류

2일 Dependabot(의존성의 새 버전을 감지해 업데이트 PR을 자동으로 올리는 GitHub 기능)이 올린 16개 패키지 업데이트([#411](https://github.com/hyeoniverse/MacFolio/pull/411))에 NestJS 12.2.0 → 12.3.2가 들어 있었다.

API 서버는 요청 몸통을 body-parser로 읽는다. 몸통이 크기 제한을 넘거나 JSON 문법이 깨져 있으면 body-parser는 http-errors 형식의 오류 객체(`status`, `type` 필드를 가진 객체)를 만든다. 전역 예외 필터는 이 `type`으로 우리말 설명을 조회한다. 예를 들어 `type: 'entity.too.large'`는 `"요청이 너무 큽니다."`, `type: 'entity.parse.failed'`는 `"요청 본문을 읽을 수 없습니다."`가 된다.

12.3부터 Express 어댑터가 이 http-errors를 `HttpException`으로 감싸 `cause`에 넣는다. 필터는 http-errors를 직접 받는 경우만 우리말로 바꾸고 있었으므로, 감싼 오류는 `HttpException` 분기로 들어가 너무 큰 요청(413)·깨진 JSON(400)의 설명이 영어 원문으로 나갔다.

![12.2와 12.3에서 413 오류가 필터에 도착하는 모양](./images/week-1102-error-wrap.svg '12.3에서는 http-errors가 HttpException의 cause로 한 겹 감싸져 필터의 type 조회 분기를 지나친다')

`toErrorBody`가 `HttpException`의 `cause.type`으로도 설명을 조회하게 하고, 필터 단위 시험에 감싼 413 오류(`new HttpException('request entity too large', 413, { cause })`)를 더했다. 같은 PR에서 `ai` 7이 요구하는 `@ai-sdk/provider-utils` 5를 4로 고정하던 override도 삭제했다.

자세한 내용: [11월 2일~5일](/memo/day-1105)

## 러너 속도와 무관한 성능 시험

메모 앱의 검색은 글마다 검색용 글자(제목·본문을 검색하기 좋은 형태로 바꾼 문자열)를 처음 한 번만 만들어 `WeakMap`에 보관하고, 글자를 입력할 때마다 다시 만들지 않는다. desktop-core의 검색 성능 시험은 이 캐시를 지키기 위해 검색 한 번의 평균 시간이 5ms 미만인지 확인하고 있었다.

[#412](https://github.com/hyeoniverse/MacFolio/pull/412)를 머지한 뒤 CI의 `check` 작업이 이 시험(평균 5.46ms)에서 실패했고, `deploy` 작업이 `check` 통과를 조건으로 실행되므로 배포되지 않았다. 같은 코드가 Mac에서는 0.2ms, GitHub 공유 러너(CI 작업을 실행하는 GitHub의 공용 가상 머신)에서는 5ms 안팎이다. ==시험이 지키려던 것은 속도가 아니라 검색용 글자 캐시==였다.

6일 [#414](https://github.com/hyeoniverse/MacFolio/pull/414)에서 시험을 둘로 나눴다.

| 시험        | 확인하는 것                                                                                                          | 러너 속도의 영향              |
| ----------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| 객체 동일성 | 검색을 반복한 뒤에도 `searchIndexOf(post)`가 처음 만든 객체와 같은지(`===`)                                          | 없음                          |
| 상대 비교   | 글 240개의 검색용 글자를 처음부터 만드는 시간(`build`)과 검색 한 번의 평균 시간(`perQuery`)이 `perQuery < build / 5` | 두 값에 같이 걸려 비율은 유지 |

![절대 시간 기준과 비율 기준](./images/week-1102-perf-ratio.svg '왼쪽: 같은 코드가 러너에 따라 5ms 선을 넘는다. 오른쪽: build와 perQuery를 같은 실행에서 재 비율로 판정한다')

캐시가 깨져 검색마다 검색용 글자를 다시 만들면 `perQuery`가 `build`와 비슷해져 두 번째 시험이 실패한다. Mac에서 잰 값은 `build` 10~14ms, `perQuery` 0.21~0.23ms로 비율이 48~62배라 5배 기준에 여유가 있다.
