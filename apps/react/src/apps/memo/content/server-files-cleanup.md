메모 편집기에 이미지를 끌어 놓으면 파일은 서버의 `Upload` 테이블에 들어가고, 글 본문에는 `![](https://<API 주소>/files/<id>)` 한 줄이 들어간다. 글과 파일은 이 주소 문자열로만 이어져 있다.

그래서 글에서 그 줄을 지워도 파일은 지워지지 않는다. 글을 영구히 지워도 마찬가지다. 사용자 입장에서는 이미지를 지웠는데, 서버에는 그대로 남아 DB를 차지한다.

## 지울 때 파일도 함께 지우면 안 될까

방법을 견줘 보면 이렇다.

| 방법                                         | 좋은 점                                | 걸린 점                                                                                              |
| -------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 저장할 때 빠진 파일을 바로 지우기            | 쌓이지 않는다                          | 예전 버전과 최근 삭제된 글이 깨진다                                                                  |
| 글과 파일 사이에 참조 테이블을 두고 세기     | 쓰는 곳을 바로 안다                    | 편집기가 넣는 것은 주소 문자열이라, 저장할 때마다 본문을 읽어 표를 맞춰야 한다. 어긋나면 표가 틀린다 |
| 목록을 볼 때 글을 훑어 쓰는 곳을 계산 (고름) | 글 본문이 곧 진실이라 어긋날 일이 없다 | 목록을 열 때마다 모든 글과 버전을 읽는다                                                             |

관리자 한 사람이 가끔 여는 화면이라, 열 때마다 계산하는 쪽이 단순하고 틀릴 일이 없었다.

처음 떠오른 방법은 글을 저장할 때 빠진 이미지를 찾아 바로 지우는 것이다. 하지만 이 사이트에는 그럴 수 없는 이유가 두 가지 있다.

- **예전 버전.** 게시할 때마다 버전이 남고, 예전 버전으로 되돌릴 수 있다. 지금 글에서 뺀 이미지도 예전 버전에는 들어 있다.
- **최근 삭제된 항목.** 지운 글은 30일 동안 되살릴 수 있다.

![저장할 때 빠진 그림을 바로 지우면 생기는 일](./images/server-files-cleanup-why.svg '버전 되돌리기와 최근 삭제 되살리기가 깨진다')

바로 지우면 이 둘이 깨진다. 그래서 자동으로 지우지 않고, 파일마다 **어디에서 쓰는지**를 보여 주고 관리자가 고르게 했다.

## 쓰는 곳 찾기

파일과 글은 문자열로만 이어져 있으니, 글의 문자열에서 파일 주소를 찾는다.

```ts
export function uploadIdsIn(text: string | null | undefined): string[] {
	if (!text) return [];
	return [...new Set([...text.matchAll(/\/files\/([\w-]{16})(?![\w-])/g)].map((match) => match[1]))];
}
```

파일 id는 16자(12바이트를 base64url로)라서, 뒤에 글자가 더 붙으면 다른 주소로 본다. 이 함수는 `packages/contracts/src/files.ts`에 두어 서버와 화면이 같이 쓴다. 서버의 `GET /files`(관리자만)는 모든 글의 게시한 내용, 임시 저장, 예전 버전을 이 함수로 훑고, 파일마다 쓰는 곳을 세 가지로 알려 준다.

| 쓰는 곳         | 뜻                                                | 지울 수 있나                             |
| --------------- | ------------------------------------------------- | ---------------------------------------- |
| 지금 글         | 게시한 내용이나 임시 저장 (최근 삭제된 글도 포함) | 아니요 (409)                             |
| 배경화면        | 관리자가 올린 배경화면의 원본·썸네일              | 아니요 (배경화면 설정에서 지운다)        |
| 예전 버전에서만 | 지금 글에서는 뺐지만 예전 버전에 남아 있다        | 예 (그 버전으로 되돌리면 그 자리가 빈다) |
| 없음            |                                                   | 예                                       |

![글과 배경화면에서 파일 주소를 찾아 쓰는 곳별로 지울 수 있는지 나누는 도식](./images/server-files-cleanup-usage.svg '지금 쓰는 파일은 서버가 409로 막는다')

서버는 게시한 요약·본문, 임시 저장한 요약·본문, 예전 버전의 요약·본문을 모두 훑는다.

```ts
// apps/api/src/files/files.service.ts
for (const post of posts)
	for (const text of [post.summary, post.body, post.draftSummary, post.draftBody])
		for (const id of uploadIdsIn(text)) add(current, id, post.slug);
for (const revision of revisions)
	for (const text of [revision.summary, revision.body])
		for (const id of uploadIdsIn(text)) add(old, id, revision.postSlug);
```

지금 글에서 쓰는 파일은 예전 버전 목록에서 뺀다. "예전 버전에서만"이 정확히 그 뜻이 되게 하려는 것이다.

`DELETE /files/:id`도 같은 규칙으로 막는다. 화면에서 지우기 버튼을 감추는 것만으로는 부족하다. 화면을 거치지 않은 요청도 있고, 화면이 목록을 읽은 뒤에 누가 그 파일을 글에 넣었을 수도 있다.

```ts
if (row.wallpaperImage || row.wallpaperThumb) throw new ConflictException('배경화면에서 쓰는 파일입니다.');
const posts = (await this.references()).current.get(id);
if (posts?.size) throw new ConflictException(`글에서 쓰는 파일입니다: ${[...posts].sort().join(', ')}`);
```

409 문구에 글 주소를 적어, 어느 글에서 빼야 하는지 바로 알 수 있게 했다.

목록을 읽을 때 파일 내용(`data`, 바이트)은 읽지 않는다. 한 파일이 10MB까지라, 목록에서 내용까지 읽으면 그만큼 DB에서 끌어온다.

## 서버가 모르는 글

이 블로그의 글 대부분은 저장소의 Markdown 파일이다. 서버 DB에는 관리자가 고친 글만 있다. 저장소 글이 서버의 이미지를 가리키면 서버는 그것을 모른다.

그래서 화면이 한 번 더 본다. 휴지통은 저장소 글의 본문에서도 같은 주소를 찾아, 하나라도 있으면 "글에서 쓰는 파일"로 보고 지우기 버튼을 감춘다.

## 휴지통에서

관리자로 로그인하면 휴지통 사이드바에 "서버 파일"이 생긴다. 맨 위에 쓰는 곳이 없는 파일의 수와 크기가 나오고, 하나씩 또는 한 번에 지운다. 되돌릴 수 없어서 지우기 전에 묻는다.

처음 열어 보니 목록에 블로그 이미지가 하나도 없어서, 잘못 읽은 것인지부터 헷갈렸다. 이 블로그 글 대부분은 저장소의 Markdown이고 그 이미지도 저장소에 있어서 사이트와 함께 배포된다. 서버에는 메모 편집기로 올린 것과 배경화면만 있다. 그래서 목록 위와 빈 화면에 무엇이 여기 보이는지를 한 줄로 적어 두었다.

[휴지통](/memo/bin-app)은 방문자에게는 "이 사이트가 내 브라우저에 남긴 것"을, 관리자에게는 "글에서 버렸지만 서버에 남은 것"을 보여 준다. 둘 다 실제로 비울 수 있는 것이다.

## 시험

- API 단위 시험: 주소 찾기 (전체 주소·경로, 같은 id는 한 번, 16자보다 긴 주소)
- API e2e(`apps/api/test/files.e2e.test.ts`): "파일마다 지금 글, 예전 버전, 배경화면 중 어디에서 쓰는지 알려 준다", "안 쓰는 파일과 예전 버전에서만 쓰는 파일은 지우고, 지금 글이나 배경화면이 쓰는 파일은 409", "관리자가 아니면 목록을 보거나 지울 수 없다 (401)". 정리하면 지금 글·예전 버전·배경화면을 구별하는지, 안 쓰는 파일과 예전 버전만 쓰는 파일은 지우고 나머지는 409, 관리자가 아니면 401
- 화면 E2E(`apps/react/e2e/bin.spec.ts`): 가짜 서버에 네 가지 파일을 두고, 쓰는 파일에는 지우기 버튼이 없고 나머지를 하나씩·한 번에 지우는지

## 남은 것과 배운 것

- **목록은 모든 글을 읽는다.** 글과 버전이 늘면 목록을 여는 시간이 늘어난다. 지금은 관리자 한 사람이 가끔 여는 화면이라 그대로 두었다. 느려지면 그때 참조 표를 두고, 지금의 훑기를 그 표가 맞는지 확인하는 시험으로 바꾸면 된다.
- **파일 내용은 읽지 않는다.** 파일은 DB에 바이트로 들어 있다. 목록 질의의 `select`에서 `data`를 빼 두어, 파일이 늘어도 목록이 끌어오는 양은 이름·크기 같은 몇 칸뿐이다.
- **서버가 모르는 글도 있다.** 저장소의 Markdown은 화면만 안다. 한쪽만 보고 지우면 안 되는 것은, 데이터가 두 곳에 있는 구조에서 늘 생기는 문제다.
- **"자동"보다 "보여 주고 고르게".** 되돌릴 수 없는 지우기는 기준을 보여 주고 사람이 고르게 했다. 덕분에 예전 버전 규칙처럼 애매한 경우도 화면에 그대로 드러난다.
