## 들어가기 전에

대학이 수강 신청 시스템을 새로 만든다고 하자. 요구사항 문서에는 "학생은 여러 과목을 수강하고, 과목마다 성적을 받는다", "교수는 한 학과에 소속된다" 같은 문장이 적혀 있다. 이 문장을 곧바로 `CREATE TABLE{:sql}` 문으로 옮기면 성적을 학생 테이블에 둘지 과목 테이블에 둘지, 학생 한 명이 과목 여러 개를 듣는 사실을 어떻게 저장할지 같은 결정이 코드 작성 도중에 섞여 버린다. 데이터베이스 설계는 이 결정을 단계로 나눈다. 먼저 특정 DBMS와 무관하게 "무엇이 있고 서로 어떻게 연결되는가"를 그림으로 확정하고, 그다음 그 그림을 DBMS가 이해하는 테이블 구조로 바꾼다.

첫 단계에서 쓰는 도구가 개체-관계 모델(E-R 모델)이다. 학생·과목 같은 개체를 사각형, 수강 같은 관계를 마름모, 이름·성적 같은 속성을 타원으로 그려 요구사항을 한 장의 다이어그램으로 정리한다. 두 번째 단계에서는 이 다이어그램을 관계·네트워크·계층 같은 논리적 데이터 모델로 옮긴다.

이 글이 답하려는 질문은 세 가지다. 현실 세계가 데이터베이스에 저장되기까지 어떤 단계를 거치는가. E-R 다이어그램은 개체, 애트리뷰트, 관계와 그 제약을 어떤 기호로 표현하는가. 관계·네트워크·계층 데이터 모델은 관계를 표현하는 방법이 어떻게 다른가.

| 순서 | 내용                                                 |
| ---- | ---------------------------------------------------- |
| 1    | 데이터의 세 세계와 데이터베이스 설계 단계            |
| 2    | 데이터 모델의 구조·연산·제약조건                     |
| 3    | 개체 타입과 애트리뷰트의 유형                        |
| 4    | 관계 타입의 사상 원소 수, 참여 제약, 존재 종속       |
| 5    | E-R 다이어그램 표기법, 키 애트리뷰트, 약한 개체 타입 |
| 6    | 관계·네트워크·계층 데이터 모델과 데이터 구조도       |
| 7    | 연습문제 풀이 8문항                                  |

[앞 글들](/memo/db-relational-model-keys)이 관계 데이터 모델 안에서 릴레이션을 다뤘다면, 이 글은 현실 세계를 어떤 과정으로 릴레이션까지 옮기는지 정리한다.

## 데이터의 세 세계와 데이터베이스 설계

데이터는 세 세계에 걸쳐 표현된다.

| 세계                        | 표현 대상                   | 표현 단위             | 예                                   |
| --------------------------- | --------------------------- | --------------------- | ------------------------------------ |
| 현실 세계(real world)       | 실제로 존재하는 사물과 사건 | 개체, 특성, 값        | 학생 나수영, 그의 학년, 4            |
| 개념 세계(conceptual world) | 사람이 이해하는 추상적 구조 | 개체 타입, 속성, 값   | 학생 개체 타입의 학년 속성           |
| 컴퓨터 세계(computer world) | 컴퓨터가 처리하는 구조      | 레코드 타입, 필드, 값 | STUDENT 레코드 타입의 Year 필드 값 4 |

현실 세계의 개체를 추상화해 개념 세계로 옮기는 과정이 개념적 모델링(정보 모델링)이고, 개념 세계의 구조를 컴퓨터 세계의 레코드 타입과 필드로 변환하는 과정이 데이터 모델링이다.

![현실 세계(개체·특성·값)↔개념 세계(개체 타입·속성·값)↔컴퓨터 세계(레코드 타입·필드·값)와 개념적 모델링·데이터 모델링 흐름도](./images/db-er-model-note-01.jpg '현실 세계, 개념 세계, 컴퓨터 세계와 그 사이의 개념적 모델링·데이터 모델링')

현실 세계를 구조적으로 표현하는 과정이 데이터베이스 설계(database design)다.

| 단계                                  | 입력 → 결과                                                                             | 설계 이름   |
| ------------------------------------- | --------------------------------------------------------------------------------------- | ----------- |
| 1. 개념적 모델링(conceptual modeling) | 현실 세계 → 개념적 구조. 추상적 개념인 개체 타입(entity type)으로 표현                  | 개념적 설계 |
| 2. 데이터 모델링(logical modeling)    | 개념적 구조 → 논리적 구조(데이터 모델). 논리적 개념인 레코드 타입(record type)으로 표현 | 논리적 설계 |
| 3. 데이터 구조화(data structuring)    | 논리적 구조 → 물리적 구조. 저장 장치에서의 데이터 표현                                  | 물리적 설계 |

![현실 세계의 수강 사실이 E-R 다이어그램, 관계 스키마, 저장 파일과 인덱스로 차례로 바뀌는 단계도](./images/db-er-model-design-stages.svg '수강 사실 하나가 개념적·논리적·물리적 설계를 거쳐 저장 구조가 된다')

위 그림은 "나수영 학생이 데이터베이스 과목을 수강해 A를 받았다"는 사실 하나가 세 단계를 거치는 모습이다. 개념적 설계에서는 학생과 과목을 개체 타입, 수강을 관계 타입, 성적을 관계의 속성으로 판단해 E-R 다이어그램으로 그린다. 논리적 설계에서는 이 다이어그램을 STUDENT, COURSE, ENROL 릴레이션으로 바꾸고 수강 사실은 ENROL의 튜플 `<100, C413, A>`가 된다. 물리적 설계에서는 ENROL 레코드를 디스크 블록에 어떻게 배치하고 어느 열에 인덱스를 만들지 정한다.

> [!IMPORTANT]
> ==설계의 핵심은 개념적 구조와 논리적 구조를 거쳐 실제로 저장할 수 있는 물리적 구조로 변환하는 데 있다.==

|           | 개념적 데이터 모델링                                  | 논리적 데이터 모델링                                       |
| --------- | ----------------------------------------------------- | ---------------------------------------------------------- |
| 표현 단위 | 애트리뷰트로 기술한 개체 타입과 개체 타입 사이의 관계 | 데이터 필드로 기술한 레코드 타입과 레코드 타입 사이의 관계 |
| 표현 대상 | 현실 세계                                             | 개념 세계(개념적 구조)                                     |
| 대표 모델 | 개체-관계 모델(E-R model)                             | 관계, 네트워크, 계층, 객체지향, 객체-관계 데이터 모델      |

![현실 세계 개체→개념적 모델링→개념적 구조→데이터 모델링→논리적 구조→데이터 구조화→저장 DB 순환 구성도](./images/db-er-model-note-02.jpg '개념적 모델링, 데이터 모델링, 데이터 구조화를 거쳐 저장 데이터베이스가 된다')

## 데이터 모델

데이터 모델 D는 세 요소로 정의한다.

```math
D = \langle S, O, C \rangle
```

| 요소                    | 내용                                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| S 구조(structure)       | 데이터의 정적 성질. 개체 타입과 그 사이의 관계를 명세한다                                                                       |
| O 연산(operation)       | 데이터의 동적 성질. 개체 인스턴스를 처리하는 연산(데이터 조작 기법)을 명세한다                                                  |
| C 제약조건(constraints) | 데이터의 논리적 제약. 개체 인스턴스의 존재 조건으로, 구조에서 파생되는 제약과 의미상 제약이 있으며, 데이터 조작의 한계를 정한다 |

관계 데이터 모델에 대입하면 S는 릴레이션, O는 [관계 대수](/memo/db-relational-algebra), C는 키와 [무결성 제약](/memo/db-relational-model-keys)이다. 예를 들어 "학번은 학생마다 달라야 한다"는 구조에서 파생되는 제약(키)이고, "성적은 A~F 가운데 하나다"는 의미상 제약이다.

논리적 데이터 모델 가운데 가장 많이 쓰이는 것은 관계 데이터 모델이다. 그 이전에는 네트워크 모델과 계층 모델이 많이 쓰였고, 최근에는 객체지향 모델과 객체-관계 모델도 쓰인다. ==하나의 DBMS는 하나의 논리적 데이터 모델만 구현하며==, ==모델 사이의 주요 차이는 데이터 요소 사이의 관계(relationship)를 표현하는 방식이다.==

## 개체 타입

**개체(entity)** 는 단독으로 존재할 수 있고 다른 것과 구별되는 객체(object)다. 학생 나수영, 과목 C413이 개체다. **개체 타입(entity type)** 은 이름과 애트리뷰트들로 정의하며, 같은 애트리뷰트로 구성된 개체들의 공통된 논리적 구조를 나타낸다. `학생(학번, 이름, 학년, 학과)`가 개체 타입이다. 한 개체 타입에 속하는 개체 인스턴스(instance)들의 집합을 개체 집합(entity set)이라 한다. 애트리뷰트(attribute)는 개체의 성질을 나타내는 이름으로, 앞 글들의 "속성"과 같은 말이다.

### 애트리뷰트의 유형

| 유형                              | 정의                                                                       | 예                               |
| --------------------------------- | -------------------------------------------------------------------------- | -------------------------------- |
| 단순 애트리뷰트(simple)           | 더 작은 구성 요소로 분해할 수 없다                                         | 학년                             |
| 복합 애트리뷰트(composite)        | 기본적인 단순 애트리뷰트 몇 개로 분해할 수 있다                            | 주소(시, 구, 동), 이름(성, 이름) |
| 단일 값 애트리뷰트(single-valued) | 개체마다 값이 하나다                                                       | 학생의 이름                      |
| 다중 값 애트리뷰트(multivalued)   | 개체마다 값이 여러 개일 수 있다. 실제로는 값의 최대 개수를 제한하기도 한다 | 학생의 취미                      |
| 유도 애트리뷰트(derived)          | 다른 애트리뷰트나 개체의 값에서 계산되어 정해진다                          | 과목-성적 개체의 평균 성적       |
| 저장 애트리뷰트(stored)           | 유도 애트리뷰트를 계산하는 데 쓰인 애트리뷰트                              | 등록 개체의 성적                 |
| 널 애트리뷰트(null)               | 널 값을 가질 수 있다                                                       | 휴대전화가 없는 사원의 전화번호  |

> [!NOTE]
> 널 값은 개체 인스턴스가 어떤 애트리뷰트의 값을 갖지 않는다는 사실을 명시적으로 표시한다. 그 값이 개체에 해당하지 않는 경우(not applicable)와 알 수 없는 경우(unknown)가 있고, 알 수 없는 경우는 다시 값은 있지만 누락된 경우(missing)와 값이 있는지조차 모르는 경우(not known)로 나뉜다.

![주소를 도·시(군,읍)·동(면)번지·우편번호로, 동(면)번지를 다시 동(면)·번지·아파트번호로 나눈 복합 애트리뷰트 트리](./images/db-er-model-note-03.jpg '복합 애트리뷰트 주소는 단순 애트리뷰트로 나뉘고, 그 일부는 다시 나뉜다')

## 관계 타입

**관계 타입(relationship type)** 은 개체 집합 사이의 대응, 즉 사상(mapping)이다. 학생 개체 집합과 과목 개체 집합 사이의 "등록"이 관계 타입이며, 관계는 개체 없이 단독으로 존재할 수 없다. 두 개체 집합 사이에 실제로 나타난 관계 인스턴스들의 집합을 관계 집합이라 한다. "나수영이 C413에 등록했다"가 관계 인스턴스 하나다.

![학생-등록(마름모)-과목으로 그린 등록 relationship type E-R 도식](./images/db-er-model-note-04.jpg '학생과 과목 사이의 등록 관계 타입')

![학생 개체 집합·등록 관계 집합·과목 개체 집합의 원소를 선으로 이은 등록 관계 인스턴스 그림](./images/db-er-model-note-05.jpg '등록 관계 집합의 각 원소가 학생 하나와 과목 하나를 잇는다')

### 사상 원소 수

관계 타입의 원소 수 제약조건(cardinality ratio)은 한쪽 개체 하나가 상대 개체 몇 개와 연결될 수 있는지를 정한다. 사상의 함수성으로 구분하며, 함수적이라는 말은 출발 쪽 원소 하나가 도착 쪽 원소 최대 하나에만 대응한다는 뜻이다.

![관계 타입의 사상 원소 수 네 가지](./images/db-er-model-cardinality.svg '한쪽 개체가 상대 개체 몇 개와 연결되는지로 나눈다')

사상 `f: X \to Y{:math}`와 `g: Y \to X{:math}`에 대해,

| 원소 수      | 함수성              | 예                       |
| ------------ | ------------------- | ------------------------ |
| 1:1 (일대일) | f와 g 모두 함수적   | 결혼: 신랑 ↔ 신부        |
| 1:n (일대다) | g만 함수적          | 모자 관계: 어머니 ← 자녀 |
| n:1 (다대일) | f만 함수적          | 소속: 교수 → 학과        |
| n:m (다대다) | 둘 다 함수적이 아님 | 등록: 학생 ↔ 과목        |

소속을 예로 들면, 교수 한 명은 학과 하나에만 속하므로 교수에서 학과로 가는 사상 f는 함수적이고, 학과 하나에는 교수가 여럿 있으므로 g는 함수적이 아니다.

> [!NOTE]
> 사상 원소 수는 시간과 관계없이 항상 유지되는 정적인 관계다.

![두 집합 원소를 선으로 이어 1:1·1:n·n:1·n:n 사상 원소 수를 비교한 4개 그림](./images/db-er-model-note-06.jpg '두 집합의 원소를 선으로 이어 비교한 네 가지 사상 원소 수')

### 참여 제약과 존재 종속

| 개념                             | 정의                                                                                                             | 예                              |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| 전체 참여(total participation)   | 개체 집합 A의 모든 개체가 A-B 관계에 참여한다                                                                    | 모든 교수는 학과에 소속된다     |
| 부분 참여(partial participation) | A의 일부 개체만 A-B 관계에 참여한다                                                                              | 휴학생은 과목에 등록하지 않는다 |
| 존재 종속(existence dependence)  | 개체 b의 존재가 개체 a의 존재에 종속된다. a를 주 개체(dominant entity), b를 종속 개체(subordinate entity)라 한다 | 대출이 있어야 상환이 존재한다   |

관계도 애트리뷰트를 가질 수 있다. 교수가 과목을 강의하는 시간과 장소는 교수만의 성질도, 과목만의 성질도 아니고 "어느 교수가 어느 과목을 강의한다"는 관계의 성질이다.

![교수-강의-과목 관계에 시간·장소 애트리뷰트가 붙은 attributes를 가진 relationship type 도식](./images/db-er-model-note-07.jpg '강의 관계 타입에 시간·장소 애트리뷰트가 붙는다')

![대출(대출번호·대출금액)-대출상환-상환(상환번호·상환일자·상환금액) 존재 종속 예시(주 개체: 대출, 종속 개체: 상환)](./images/db-er-model-note-08.jpg '상환은 대출이 있어야 존재한다. 대출이 주 개체, 상환이 종속 개체다')

## E-R 모델

개체-관계 모델(Entity-Relationship model)은 개체 타입과 관계 타입을 기본 개념으로 현실 세계를 개념적으로 표현하는 개념적 데이터 모델이다. 1976년 Peter Chen이 학술지 ACM Transactions on Database Systems에 발표한 논문에서 제안했고, 이를 그림으로 표현한 것이 E-R 다이어그램이다. E-R 모델에서 개체 집합은 한 개체 타입에 속하는 모든 개체 인스턴스, 관계 집합은 한 관계 타입에 속하는 모든 관계 인스턴스를 가리킨다.

![교수·학생·과목 개체와 지도(1:n)·강의(1:n, 시간·장소)·등록(n:m, 성적) 관계를 그린 대학 E-R 다이어그램](./images/db-er-model-note-13.jpg '대학 E-R 다이어그램: 지도(1:n), 강의(1:n), 등록(n:m)')

![강의 관계(마름모)에 시간·장소 속성 타원이 달린 작은 도식](./images/db-er-model-note-14.jpg '강의 관계에 시간·장소 애트리뷰트를 단 부분')

### E-R 다이어그램 표기법

| 기호               | 의미                                                      |
| ------------------ | --------------------------------------------------------- |
| 사각형             | 개체 타입                                                 |
| 이중 사각형        | 약한 개체 타입                                            |
| 마름모             | 관계 타입                                                 |
| 이중 마름모        | 식별 관계 타입                                            |
| 타원               | 애트리뷰트                                                |
| 밑줄 그은 타원     | 키 애트리뷰트                                             |
| 점선 밑줄 타원     | 부분 키(구별자)                                           |
| 이중 타원          | 다중 값 애트리뷰트                                        |
| 점선 타원          | 유도 애트리뷰트                                           |
| 타원에 연결된 타원 | 복합 애트리뷰트                                           |
| 선(링크)           | 개체 타입·관계 타입·애트리뷰트의 연결. 이중선은 전체 참여 |
| 레이블             | 사상 원소 수(1:1, 1:n, n:1, n:m)                          |

![개체·약한 개체·관계·식별 관계·전체 참여와 일반·키·부분 키·다중 값·복합·유도 애트리뷰트 기호를 모은 E-R 표기법 기호표](./images/db-er-model-note-16.jpg 'E-R 다이어그램 기호 모음')

E-R 다이어그램의 특징은 다음과 같다.

- 다대다(n:m) 관계를 직접 표현한다.
- 둘 이상의 개체 타입이 하나의 관계에 참여하는 다원 관계(n-ary relationship)를 표현한다.
- 두 개체 타입 사이에 관계가 둘 이상 있는 다중 관계(multiple relationship)를 표현한다.
- 관계 타입도 애트리뷰트를 가질 수 있다. 등록 관계의 성적이 그 예다.

![온라인 게임의 Account·Character·Region·Item·Creep 개체와 Has·Contains·Carrying·IsType·RanInto 관계를 Chen 표기법으로 그린 E-R 다이어그램](./images/db-er-model-chen-mmorpg.jpg 'Chen 표기법으로 그린 온라인 게임 E-R 다이어그램. 위 기호표의 기호가 모두 쓰였다')

위 다이어그램은 온라인 게임의 데이터를 Chen 표기법으로 그린 예다. 기호표와 대조하면 다음과 같이 읽힌다.

| 다이어그램의 부분                                  | 기호               | 의미                                                  |
| -------------------------------------------------- | ------------------ | ----------------------------------------------------- |
| AcctName, RegionName, ItemName                     | 실선 밑줄 타원     | 각 개체 타입의 키 애트리뷰트                          |
| Character, Item Instantiation, Creep Instantiation | 이중 사각형        | 약한 개체 타입. CharName, IDNum이 점선 밑줄의 부분 키 |
| Has, IsType                                        | 이중 마름모        | 약한 개체를 강한 개체에 연결하는 식별 관계 타입       |
| Foliage                                            | 이중 타원          | 다중 값 애트리뷰트                                    |
| PlayersIn                                          | 점선 타원          | 유도 애트리뷰트                                       |
| Has의 LastPlayed, CreatedOn                        | 관계에 연결된 타원 | 관계 타입의 애트리뷰트                                |
| Account 1 : Character n                            | 레이블과 이중선    | 계정 하나가 캐릭터 여러 개를 갖고, 캐릭터는 전체 참여 |
| Character m : Creep n (RanInto)                    | 레이블             | 다대다 관계                                           |

### 키 애트리뷰트

키 애트리뷰트(key attribute)는 한 개체 집합 안에서 개체마다 다른 값을 갖는 애트리뷰트나 애트리뷰트 집합이다. 키는 개체 타입 안의 모든 개체 인스턴스를 유일하게 식별하므로, 같은 키 값을 갖는 개체 인스턴스는 둘일 수 없다. E-R 다이어그램에서는 밑줄로 표시한다. 학생의 학번은 키가 될 수 있지만 이름은 동명이인이 있을 수 있어 키가 될 수 없다.

### 약한 개체 타입

자기 애트리뷰트만으로는 키를 명세할 수 없는 개체 타입을 **약한 개체 타입(weak entity type)** 이라 하고, 그 반대를 강한 개체 타입(strong entity type)이라 한다. 강한 개체 타입이 주 개체, 약한 개체 타입이 종속 개체가 된다.

| 용어                                          | 정의                                                                      |
| --------------------------------------------- | ------------------------------------------------------------------------- |
| 구별자(discriminator), 부분 키(partial key)   | 같은 강한 개체에 연관된 약한 개체들 사이에서만 서로를 구별하는 애트리뷰트 |
| 식별 관계 타입(identifying relationship type) | 약한 개체를 강한 개체에 연결해 유일하게 식별하게 하는 관계                |

![대출 L-11의 상환 1·2·3과 대출 L-23의 상환 1·2를 나열해 상환번호가 대출마다 반복됨을 보인 표](./images/db-er-model-weak-entity.svg '상환번호는 대출 안에서만 유일하다')

대출과 상환에서 상환 번호 1, 2, 3은 대출마다 다시 시작한다. 위 그림처럼 L-11과 L-23 모두 상환번호 1과 2를 가지므로 상환 번호만으로는 상환을 식별할 수 없다. =={대출 번호, 상환 번호}로 식별하며, 상환 번호가 구별자다.==

![대출(1)-대출상환(이중 마름모)-상환(n, 이중 사각형, 상환번호 점선 밑줄) 약한 개체 타입 E-R 다이어그램](./images/db-er-model-note-15.jpg '상환은 이중 사각형, 대출상환은 이중 마름모, 상환번호는 점선 밑줄로 그린다')

## 논리적 데이터 모델

논리적 데이터 모델은 개념적 구조를 데이터베이스로 구현하기 위한 중간 단계로, 레코드(개체) 타입과 관계로 표현한다. 종류는 네트워크, 계층, 관계, 객체지향, 객체, 객체-관계, 확장 관계 데이터 모델이 있다.

![현실세계↔E-R 다이어그램↔(설계자)↔데이터 모델↔저장 데이터베이스 흐름도](./images/db-er-model-note-17.jpg '설계자가 E-R 다이어그램을 데이터 모델로 옮겨 저장 데이터베이스를 만든다')

### 관계 데이터 모델

- 데이터베이스는 릴레이션(테이블)의 집합이다. 개체를 표현하는 개체 릴레이션과 관계를 표현하는 관계 릴레이션이 있다.
- 릴레이션 스키마로 개체와 관계를 모두 릴레이션으로 정의한다. 학생-등록-과목에서 등록 관계도 릴레이션 `등록(학번, 과목번호, 성적)`이 된다.

![학생·교수·과목·지도·등록·강의 6개 릴레이션 스키마를 필드 박스로 나열한 관계 데이터 모델 예](./images/db-er-model-note-18.jpg '대학 E-R 다이어그램을 옮긴 릴레이션 스키마 6개')

### 데이터 구조도

자료 구조도(data structure diagram)는 레코드 타입 사이의 관계를 도형으로 표현한다. 1969년 Bachman이 제안해 Bachman 다이어그램이라고도 한다.

| 구성 요소    | 의미                                |
| ------------ | ----------------------------------- |
| 사각형 노드  | 레코드 타입(개체 타입)              |
| 링크(화살표) | 레코드 타입 사이의 일대다(1:n) 관계 |
| 레이블       | 관계 이름                           |

데이터베이스 스키마를 데이터 구조도로 그린 것을 스키마 다이어그램이라 한다. ==스키마 다이어그램이 트리면 계층 데이터 모델, 그래프면 네트워크 데이터 모델이다.== 트리는 모든 노드가 부모를 하나만 갖고 사이클이 없는 구조이고, 그래프는 한 노드가 여러 노드와 연결될 수 있는 구조다. 스키마 다이어그램은 데이터베이스에 허용되는 레코드 타입과 그 사이의 관계를 명세한다.

|                   | 네트워크 데이터 모델                                                           | 계층 데이터 모델                                                                                     |
| ----------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 스키마 다이어그램 | 그래프(network)                                                                | 트리(tree), 사이클 없음                                                                              |
| 관계              | 오너-멤버(owner-member) 관계: 두 레코드 타입 사이의 1:n                        | 부모-자식(parent-child) 관계: 두 레코드 타입 사이의 1:n                                              |
| 관계 이름         | 두 레코드 타입 사이에 관계를 여럿 정의할 수 있어 관계마다 이름을 붙여 식별한다 | 레코드 타입마다 부모가 하나뿐이라 두 레코드 타입 사이의 관계도 하나다. 이름 없이 간선만으로 식별한다 |
| 구조 용어         | 오너 레코드, 멤버 레코드                                                       | 루트 레코드, 자식 레코드, 레벨                                                                       |
| 대표 DBMS         | IDS                                                                            | IMS                                                                                                  |

> [!WARNING]
> ==두 모델 모두 1:n만 직접 표현하므로 n:m 관계는 중간 레코드 타입을 두어 1:n 두 개로 나눠야 한다.==

학생과 과목의 n:m 수강 관계라면 성적 레코드 타입을 가운데 두고 "학생 → 성적"과 "과목 → 성적" 두 개의 1:n 링크로 표현한다. 관계 데이터 모델은 관계도 릴레이션으로 표현해 이 제약이 없다.

![과목→선수과목(선수)·성적(과목성적)·강의(스케줄), 학생→성적(학생-성적), 강의→학생(등록) Bachman 자료구조도](./images/db-er-model-note-19.jpg 'Bachman 자료구조도: 학생과 과목의 n:m을 성적 레코드 타입과 1:n 링크 두 개로 표현한다')

![교수→학생(지도)·과목(강의), 학생⇄과목(등록·수강) owner-member 관계를 그린 네트워크 데이터 모델 스키마](./images/db-er-model-note-20.jpg '네트워크 데이터 모델 스키마: 오너-멤버 관계마다 이름을 붙인다')

![교수를 루트로 학생·과목, 그 아래 수강 과목·등록 학생을 둔 계층 데이터 모델 트리](./images/db-er-model-note-21.jpg '계층 데이터 모델 트리: 교수를 루트로 학생과 과목을 자식으로 둔다')

> 데이터 모델은 무엇인가? 그 구성요소를 중심으로 설명하라.

> 개념적 데이터 모델과 논리적 데이터 모델, 그리고 물리적 데이터 구조와의 관계를 설명해 보라.

세 가지는 데이터베이스 설계의 연속된 단계에서 만들어지는 표현이다. 개념적 데이터 모델로 현실 세계를 개념적 구조로 표현하고, 이를 논리적 데이터 모델의 논리적 구조로 변환하고, 다시 저장 장치의 물리적 구조로 구현한다.

| 표현               | 구성 요소                                 | 종속 대상                          | 대학 데이터베이스의 예                      |
| ------------------ | ----------------------------------------- | ---------------------------------- | ------------------------------------------- |
| 개념적 데이터 모델 | 애트리뷰트로 기술한 개체 타입과 관계 타입 | DBMS와 독립                        | 학생·과목 개체 타입과 등록 관계 타입(E-R)   |
| 논리적 데이터 모델 | 필드로 기술한 레코드 타입과 그 관계       | DBMS가 구현하는 데이터 모델에 종속 | STUDENT, COURSE, ENROL 릴레이션             |
| 물리적 데이터 구조 | 저장 레코드 형식, 레코드 배치, 접근 경로  | 특정 DBMS와 저장 장치에 종속       | ENROL 파일의 레코드 형식, Sno에 만든 인덱스 |

==앞 단계의 구조는 다음 단계 구조의 명세가 되고, 뒤 단계로 갈수록 구현 세부 사항이 늘어난다.== 논리적 구조를 바꾸지 않고 물리적 구조만 바꿀 수 있는 성질이 [물리적 데이터 독립성](/memo/db-three-level-schema)이다.

</details>

<summary>3. E-R 모델 용어 14개</summary>

> 개체 타입, 개체 인스턴스, 개체 집합, 관계 타입, 관계 집합, 널 애트리뷰트, 개체 관계, 복합 애트리뷰트, 약한 개체 타입, 존재 종속, 전체 참여, 부분 키, 구별자, 식별 관계 타입을 간단히 설명하라.

| 용어            | 설명                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------- |
| 개체 타입       | 이름과 애트리뷰트들로 정의하며, 같은 애트리뷰트로 구성된 개체들의 공통된 논리적 구조                        |
| 개체 인스턴스   | 개체 타입에 속하는 개체 하나. 다른 개체와 구별되고 단독으로 존재할 수 있다                                  |
| 개체 집합       | 한 개체 타입에 속하는 개체 인스턴스들의 집합                                                                |
| 관계 타입       | 개체 집합 사이의 대응, 즉 사상(mapping). 개체 타입 사이에 성립할 수 있는 관계를 총체적으로 정의한다         |
| 관계 집합       | 한 관계 타입에 속하는 관계 인스턴스들의 집합                                                                |
| 널 애트리뷰트   | 널 값을 가질 수 있는 애트리뷰트. 널 값은 개체 인스턴스가 그 애트리뷰트 값을 갖지 않음을 명시적으로 표시한다 |
| 개체 관계       | 개체 인스턴스 사이의 관계 하나, 즉 관계 인스턴스. 학생 나수영이 C413에 등록한 사실이 그 예다                |
| 복합 애트리뷰트 | 단순 애트리뷰트 몇 개로 분해할 수 있는 애트리뷰트. 주소를 도, 시, 동·번지, 우편번호로 나누듯 계층을 이룬다  |
| 약한 개체 타입  | 자기 애트리뷰트만으로는 키를 명세할 수 없는 개체 타입                                                       |
| 존재 종속       | 개체 b의 존재가 개체 a의 존재에 종속되는 성질. a를 주 개체, b를 종속 개체라 한다                            |
| 전체 참여       | A-B 관계에서 개체 집합 A의 모든 개체가 관계에 참여하는 제약. 모든 교수가 학과에 소속되는 경우               |
| 부분 키         | 구별자의 다른 이름. 약한 개체 타입의 키 일부가 된다                                                         |
| 구별자          | 같은 강한 개체에 연관된 약한 개체들 사이에서만 서로를 구별하는 애트리뷰트. 상환의 상환 번호                 |
| 식별 관계 타입  | 약한 개체를 강한 개체에 연결해, 강한 개체의 키와 구별자로 약한 개체를 유일하게 식별하게 하는 관계 타입      |

</details>

<summary>4. E-R 다이어그램과 데이터 구조도, 스키마 다이어그램</summary>

> E-R 다이어그램과 데이터 구조도의 차이점을 기술해 보라. 또 스키마 다이어그램은 무엇인가?

|                   | E-R 다이어그램                                         | 데이터 구조도(Bachman 다이어그램)                    |
| ----------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 표현 수준         | 개념적 구조(개념적 데이터 모델)                        | 논리적 구조(네트워크·계층 데이터 모델)               |
| 노드              | 개체 타입(사각형), 관계 타입(마름모), 애트리뷰트(타원) | 레코드 타입(사각형)                                  |
| 관계 표현         | 관계 타입을 별도 기호인 마름모로 그린다                | 별도 기호 없이 이름을 붙인 화살표(링크)로 그린다     |
| 표현 가능한 관계  | 1:1, 1:n, n:1, n:m, 다원 관계, 다중 관계               | 두 레코드 타입 사이의 1:n만                          |
| 관계의 애트리뷰트 | 관계 타입에 애트리뷰트를 붙인다                        | 애트리뷰트를 가진 관계는 레코드 타입으로 바꿔야 한다 |

==데이터 구조도는 1:n 링크만 그리므로, E-R 다이어그램의 n:m 관계는 중간 레코드 타입 하나와 1:n 링크 두 개로 바꿔 그린다.== 위 데이터 구조도 그림에서 학생과 과목 사이의 n:m 관계를 성적 레코드 타입과 학생-성적, 과목성적 링크로 표현한 것이 그 예다.

스키마 다이어그램은 데이터베이스 스키마, 즉 데이터베이스의 논리적 구조를 데이터 구조도로 그린 다이어그램이다. 모양이 트리면 계층 데이터 모델, 그래프면 네트워크 데이터 모델의 스키마다.

</details>

<summary>5. 관계 데이터 모델에서 개체와 관계를 같은 방법으로 표현한다는 뜻</summary>

> "관계 데이터 모델에서 개체와 관계를 표현하는 방법이 같다."라는 말을 예를 들어 설명해 보라.

E-R 다이어그램은 개체 타입을 사각형, 관계 타입을 마름모로 구분하지만, ==관계 데이터 모델은 개체와 관계를 모두 릴레이션으로 표현한다.== 학생-등록-과목을 릴레이션으로 옮기면 개체 릴레이션 STUDENT와 COURSE, 관계 릴레이션 ENROL이 되며, 세 릴레이션은 모양이 같고 같은 연산(관계 대수, SQL)으로 처리한다. 예제 데이터 일부는 다음과 같다.

| STUDENT.Sno | Sname  | Year | Dept   |
| ----------- | ------ | ---- | ------ |
| 100         | 나수영 | 4    | 컴퓨터 |
| 300         | 정기태 | 1    | 컴퓨터 |

| COURSE.Cno | Cname        | Credit | Dept   |
| ---------- | ------------ | ------ | ------ |
| C312       | 자료 구조    | 3      | 컴퓨터 |
| C413       | 데이터베이스 | 3      | 컴퓨터 |

| ENROL.Sno | Cno  | Grade |
| --------- | ---- | ----- |
| 100       | C413 | A     |
| 300       | C312 | A     |
| 300       | C413 | A     |

ENROL은 두 개체 릴레이션의 키(Sno, Cno)와 관계의 애트리뷰트(Grade)를 튜플로 저장하는 관계 릴레이션이다.

> [!NOTE]
> 모든 관계를 별도 릴레이션으로 만들어야 하는 것은 아니며, 1:1이나 1:n 관계는 외래 키로 표현하기도 한다.

</details>

<summary>6. 사원과 부서의 E-R 다이어그램</summary>

> E-R 모델의 기본 개념을 설명해 보라. 그리고 다음 현실 세계를 E-R 다이어그램으로 표현해 보라. 사원(Emp)은 사원번호(Eno), 이름(Name), 주소(Addr)로, 부서(Dep)는 부서번호(Dno), 부서이름(Dname), 예산(Budget)으로 구성된다. 사원은 한 부서만을 위해 근무(Works-for)하고, 근무는 근무 시간(Hours)으로 표현한다. 사원번호와 부서번호는 유일하다. 각 부서에는 부서를 관리(Manages)하는 사원이 한 명 있고, 부서를 관리하는 사원은 모두 다르다.

E-R 모델은 현실 세계를 개체 타입과 관계 타입으로 표현하는 개념적 데이터 모델이다. 개체 타입은 애트리뷰트로 기술하고, 관계 타입은 사상 원소 수와 참여 제약으로 특징짓는다([E-R 모델](#e-r-모델) 절).

![사원과 부서의 E-R 다이어그램](./images/db-er-model-emp-dep.jpg '사원번호와 부서번호에 밑줄을 그어 키를 표시한 사원·부서 E-R 다이어그램')

요구사항에서 원소 수와 참여 제약을 읽으면 다음과 같다.

| 관계      | 원소 수         | 참여                           | 근거                                                                          |
| --------- | --------------- | ------------------------------ | ----------------------------------------------------------------------------- |
| Works-for | 사원 n : 부서 1 | 사원 전체 참여                 | 사원은 한 부서만을 위해 근무한다                                              |
| Manages   | 사원 1 : 부서 1 | 부서 전체 참여, 사원 부분 참여 | 부서마다 관리자가 한 명 있고, 관리자는 모두 다르다. 관리자가 아닌 사원도 있다 |

근무 시간(Hours)은 사원이나 부서가 아니라 "어떤 사원이 어떤 부서에서 근무하는 관계"의 성질이므로 Works-for 관계 타입의 애트리뷰트로 그린다. 키 애트리뷰트 Eno와 Dno에는 밑줄을 긋는다. 원소 수 레이블과 전체 참여(이중선)까지 표기하면 다이어그램의 링크는 다음과 같다.

```text
            Hours
              |
[Emp] ══n══ <Works-for> ──1── [Dep]
[Emp] ──1── <Manages>   ══1══ [Dep]

══ 전체 참여(이중선)   ── 부분 참여
```

</details>

<summary>7. 부모-자식 관계와 오너-멤버 관계의 함수성</summary>

> 부모-자식 관계와 오너-멤버 관계에서 함수성(functionality)을 정의하라. 레코드 인스턴스에 어떤 영향을 주는가?

부모-자식 관계(계층 모델)와 오너-멤버 관계(네트워크 모델)는 모두 두 레코드 타입 사이의 1:n 관계다. 부모(오너) 레코드 타입을 X, 자식(멤버) 레코드 타입을 Y라 하면 사상의 함수성은 다음과 같다.

| 사상                              | 함수성      | 의미                                                             |
| --------------------------------- | ----------- | ---------------------------------------------------------------- |
| `g: Y \to X{:math}` (자식 → 부모) | 함수적      | 자식(멤버) 인스턴스 하나는 부모(오너) 인스턴스 하나에만 연결된다 |
| `f: X \to Y{:math}` (부모 → 자식) | 함수적 아님 | 부모(오너) 인스턴스 하나는 자식(멤버) 인스턴스를 0개 이상 가진다 |

==자식에서 부모로 가는 사상만 함수적이며, 이 함수성이 레코드 인스턴스의 저장 방식을 제약한다.==

| 모델     | 레코드 인스턴스에 미치는 영향                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 계층     | 루트가 아닌 레코드 인스턴스는 반드시 부모 인스턴스 하나 아래에 저장한다. 부모 인스턴스 없이 자식 인스턴스를 삽입할 수 없고, 부모 인스턴스를 삭제하면 그 아래 자식 인스턴스도 모두 삭제된다. 한 자식이 논리적으로 여러 부모에 속하면(n:m) 자식 인스턴스를 부모마다 중복 저장한다                                                                                                               |
| 네트워크 | 멤버 인스턴스는 한 오너-멤버 관계 안에서 오너 인스턴스 하나에만 속한다. 대신 한 레코드 타입이 여러 관계의 멤버가 될 수 있어, 한 인스턴스가 관계마다 다른 오너 인스턴스에 연결된다. n:m은 중간 레코드 타입을 멤버로 두는 1:n 관계 두 개로 표현하므로 중복 저장이 필요 없다. 오너 없는 멤버 인스턴스의 허용 여부는 멤버십을 필수(mandatory)로 정의했는지 선택(optional)으로 정의했는지에 따른다 |

위 계층 데이터 모델 그림에서 학생 아래의 수강 과목, 과목 아래의 등록 학생이 같은 등록 사실을 두 번 저장하는 것이 계층 모델의 중복 저장 예이고, 위 데이터 구조도 그림의 성적 레코드 타입이 네트워크 모델의 중간 레코드 타입 예다.

</details>

<details>
<summary>8. 관계·계층·네트워크 데이터 모델 비교</summary>

> 관계, 계층, 네트워크 데이터 모델의 차이점과 장단점을 설명하라.

|                    | 관계 데이터 모델                                                     | 계층 데이터 모델                                                              | 네트워크 데이터 모델                                    |
| ------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------- |
| 구조               | 릴레이션(테이블)의 집합                                              | 스키마 다이어그램이 트리, 사이클 없음                                         | 스키마 다이어그램이 그래프                              |
| 관계 표현          | 개체와 관계 모두 릴레이션. 관계는 키 값으로 연결                     | 부모-자식 1:n 링크. 레코드 타입마다 부모 하나                                 | 오너-멤버 1:n 링크. 한 레코드 타입이 여러 오너를 가진다 |
| n:m 관계           | 관계 릴레이션으로 직접 표현                                          | 직접 표현 불가. 자식 레코드를 부모마다 중복 저장                              | 직접 표현 불가. 중간 레코드 타입과 1:n 두 개로 표현     |
| 두 타입 간 관계 수 | 제한 없음                                                            | 하나. 간선에 이름이 없어도 식별된다                                           | 여럿. 관계마다 이름을 붙여 식별한다                     |
| 데이터 접근        | 선언적 질의(SQL), 집합 단위 처리                                     | 루트에서 경로를 따라가는 레코드 단위 탐색                                     | 링크를 따라가는 레코드 단위 탐색                        |
| 장점               | 구조가 단순하고 데이터 독립성이 높다. 임의의 조건으로 질의할 수 있다 | 계층 구조인 데이터를 부모에서 자식 방향으로 빠르게 접근한다                   | 계층 모델보다 표현력이 높고 n:m을 중복 없이 표현한다    |
| 단점               | 조인이 많으면 처리 비용이 크다                                       | n:m 표현 시 중복이 생기고, 삽입·삭제가 부모 존재에 묶인다. 구조 변경이 어렵다 | 구조가 복잡하고 프로그램이 링크 구조에 종속된다         |

==모델 사이의 차이는 [데이터 모델](#데이터-모델) 절에서 정리한 대로 데이터 사이의 관계를 표현하는 방식에서 나온다.== 계층·네트워크 모델은 관계를 레코드 사이의 링크로 저장하므로 링크를 따라가는 접근은 빠르지만 프로그램이 그 구조에 종속되고, 관계 모델은 관계를 값으로 표현하므로 구조와 질의가 독립적이다.

</details>

## 정리

- 데이터베이스 설계는 개념적 설계(E-R 모델) → 논리적 설계(관계 데이터 모델 등) → 물리적 설계 순서로 진행한다.
- 데이터 모델은 구조, 연산, 제약조건으로 구성된다.
- 관계 타입은 사상 원소 수(1:1, 1:n, n:1, n:m)와 참여 제약(전체, 부분)으로 특징짓는다.
- 자기 애트리뷰트만으로 식별할 수 없는 약한 개체 타입은 강한 개체의 키와 구별자를 합쳐 식별한다.
