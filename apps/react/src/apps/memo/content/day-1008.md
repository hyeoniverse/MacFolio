## 사진 앱

Dock에 아이콘만 있고 눌러도 동작하지 않던 사진 앱을 만들었다([#21](https://github.com/hyeoniverse/MacFolio/issues/21)).

- **데이터 출처:** 사진 목록을 별도로 관리하지 않고, 프로젝트 페이지에 사용한 화면을 프로젝트마다 앨범으로 묶는다. 프로젝트 페이지에 그림을 추가하면 사진 앱에도 자동으로 반영된다
- **규모:** 이날 기준 앨범 7개, 사진 65장, 영상 5개
- **휴대폰:** iOS 사진 앱의 구성으로 별도 렌더링

자세한 내용은 [프로젝트 정보에서 앨범을 생성하는 macOS·iOS 방식의 사진 앱](/memo/photos-app)에 정리했다.

## 메일: 본인 메일만 보이는 보낸 편지함

전날 메일 앱에서 실제로 메일을 발송할 수 있게 했고, 이날은 발송한 메일을 앱 안에서 다시 조회할 수 있게 했다.

| 사용자 | 조회 범위                                  | 동작                 |
| ------ | ------------------------------------------ | -------------------- |
| 방문자 | 이 브라우저에서 보낸 메일과 그에 대한 답장 | 조회                 |
| 관리자 | 받은 모든 메일                             | 조회, 앱 안에서 답장 |

"본인 메일만"은 화면에서 숨기는 방식이 아니라 **서버가 필터링**한다. 서버는 방문자 쿠키의 HMAC이 일치하는 메일만 반환하고, 메일 하나를 번호로 조회하는 API 경로는 만들지 않았다. 번호로 조회하는 경로가 있으면 번호만 바꿔 다른 사람의 메일을 요청할 수 있기 때문이다([방문자 쿠키 HMAC으로 필터링하는 보낸 편지함과 관리자 받은 편지함](/memo/mail-mailboxes)).

![휴대폰 Safari](./images/day-1008-mobile-safari.jpg '휴대폰 Safari의 현재 화면. 페이지가 화면 전체를 사용하고 하단에 막대 하나가 떠 있다')

### 메모의 휴대폰 모양 기준 불일치 (#135)

| 기준                           | 값                    |
| ------------------------------ | --------------------- |
| 휴대폰 셸을 사용하는 화면 폭   | 767px 이하            |
| 메모가 휴대폰 모양이 되는 기준 | 메모 칸 폭 700px 이하 |

두 기준이 달라서 701~767px 폭에서는 휴대폰 셸 안에 넓은 창 모양의 메모가 렌더링되고, 도구 막대가 상태 표시줄에 가려졌다. 휴대폰 셸 안이면 폭과 관계없이 휴대폰 모양이 되도록 조건을 추가했다.

## 사라질 때도 애니메이션

### 문제

메뉴·경고 대화상자·팝업은 나타날 때만 애니메이션이 적용되고, 닫힐 때는 즉시 사라졌다. React는 요소를 DOM에서 제거한 뒤에는 애니메이션을 적용할 수 없다.

### 조치: 제거 직전에 복사본을 만들어 애니메이션

React 19의 ref 정리 함수(cleanup)가 호출되는 시점에 요소의 **겉모습만 복사**해 같은 위치에 배치하고, 그 복사본에 사라지는 애니메이션을 적용했다(`useExitMotion`).

| 항목             | 동작                                          |
| ---------------- | --------------------------------------------- |
| 여는 쪽 코드     | 변경 없음 (`{open && <Menu />}` 그대로)       |
| 상태·포커스·시험 | 모두 이미 닫힌 상태를 기준으로 동작           |
| 복사본           | 클릭할 수 없고, 스크린 리더에도 노출되지 않음 |

자세한 내용은 [제거 직전 DOM 복제본으로 구현한 퇴장 애니메이션 hook useExitMotion](/memo/global-motion)에 정리했다.

## 돌아보며

**휴대폰 화면은 시험으로 보호해야 한다.** 이날 늘어난 E2E 46개 중 15개가 휴대폰 시험(`mobile.spec.ts`)이었다. 휴대폰 화면은 스와이프와 겹쳐 렌더링하는 요소가 많아서, 육안 확인만 하면 다른 PR이 알아차리기 어려운 방식으로 깨뜨린다. 스와이프, 상태 표시줄 겹침, 화면 전환 방향을 시험으로 남겼다.

**#129가 너무 컸다.** 커밋 18개에 상태 표시줄, 홈 화면, 메시지, 음악, 설정, Safari, 파일이 함께 포함되었다. 전날 트래픽 분석을 PR 네 개로 나눈 것과 반대였다. 휴대폰 화면을 수정하다 보니 하나의 수정이 다음 수정으로 이어졌는데, 작업이 그렇게 이어지는 시점이 PR을 나눠야 하는 시점이다.

**`useExitMotion`은 "여는 쪽 코드를 변경하지 않는다"는 조건을 먼저 정하고 설계했다.** 메뉴·경고 대화상자·팝업을 여는 코드(`{open && <Menu />}`)는 그대로다. 공통 컴포넌트에 기능을 추가할 때는 사용하는 쪽 코드가 바뀌지 않는 방법부터 찾는 것이 맞다.
