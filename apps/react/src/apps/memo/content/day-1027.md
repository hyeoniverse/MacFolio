## 메모 검색 ([#393](https://github.com/hyeoniverse/MacFolio/pull/393))

### 배경: 필터링 검색과 순위 검색

검색에는 두 방식이 있다. 필터링 검색은 검색어가 들어 있는 글만 남기고 순서는 원래 목록(이 사이트에서는 날짜순)을 유지한다. 순위 검색은 글마다 검색어와 얼마나 잘 맞는지 점수를 계산해 점수가 높은 글을 앞에 놓는다. 제목에 검색어가 있는 글은 본문 한 구석에 검색어가 있는 글보다 찾는 글일 가능성이 높으므로, 순위 검색은 칸(제목·요약·본문 등)마다 무게를 다르게 준다. 고치기 전 메모 검색은 제목·본문만 비교하는 필터링 검색이었다.

### 글 주소로 찾기

검색 칸은 제목과 본문만 비교해, 공유받은 링크의 주소(`/memo/merge-strategies`)만 알면 그 글을 찾을 수 없었다. 검색어를 글 주소(slug)와도 비교한다.

| 검색어                                                           | 규칙                                          |
| ---------------------------------------------------------------- | --------------------------------------------- |
| `merge-strategies`                                               | 부분 일치, 대소문자 무시                      |
| `merge_strat`                                                    | 밑줄을 하이픈으로 바꿔 비교                   |
| `https://macfolio.hyeoniverse.com/memo/merge-strategies?x=1#top` | `/memo/` 앞, `?`·`#` 뒤, 끝의 `/`를 떼고 비교 |

### 순위와 속도

주소 검색을 넣으면서 검색 로직을 `packages/desktop-core/src/memo/search.ts`로 모으고, 결과를 날짜 순서가 아니라 점수 순서로 바꿨다.

| 규칙      | 내용                                                                                  |
| --------- | ------------------------------------------------------------------------------------- |
| 낱말      | 공백으로 나눈 낱말이 모두 있어야 한다(AND). 하이픈·밑줄로 이은 낱말은 한 덩어리       |
| 입력 중   | 마지막 글자는 입력 중으로 보고 넓게 받는다 ('프론트에' → 프론트엔드)                  |
| 초성      | 초성만 두 글자 이상이면 제목의 초성에서 찾는다 (`ㅁㅊ` → 목차)                        |
| 칸 무게   | 제목 10, 주소 8, 태그 6, 초성 5, 요약 4, 본문 1. 제목·주소가 검색어와 같으면 +30      |
| 표기 사전 | `react`·`리액트`, `github`·`깃허브`처럼 기술 용어 40여 개의 표기를 묶고, 무게는 0.9배 |

낱말마다 그 낱말이 걸린 칸 가운데 가장 무거운 칸의 무게를 점수로 정하고, 낱말 점수를 더한다. 한 낱말이라도 어느 칸에도 없으면 그 글은 결과에서 빠진다.

![검색 점수 계산 예](./images/day-1027-search-score.svg '도식. 검색어 리액트 목차의 낱말마다 가장 무거운 칸의 무게를 더한다. 표기 사전으로 찾은 react는 0.9배, 목차가 없는 글 D는 결과에서 빠진다')

| 측정 (저장소 글 238편, 본문 약 205만 자) | 전        | 후                     |
| ---------------------------------------- | --------- | ---------------------- |
| 글자 하나 입력 시 필터링                 | 4.5~5.1ms | 0.5ms                  |
| 검색용 문자열 생성                       | -         | 31ms (첫 검색에 한 번) |
| 결과가 0개일 때 추천 계산                | -         | 약 11ms                |

전에는 글자를 입력할 때마다 모든 글의 제목·본문에 `toLowerCase()`를 실행했다. 이제 글마다 정규화한 검색용 문자열을 한 번만 만들어 보관한다.

- **NFKC 정규화**: 유니코드에서 모양이 같은 글자를 한 형태로 맞추는 규칙이다. 예를 들어 전각 영문 `Ｒｅａｃｔ`는 `React`가 되어, 어느 쪽으로 적어도 같은 글로 찾는다. 그 뒤에 소문자로 바꾼다.
- **`WeakMap` 보관**: 글 객체를 키로 검색용 문자열을 보관한다. `WeakMap`은 키 객체가 더 쓰이지 않으면 값도 함께 메모리에서 해제되므로, 글을 다시 불러와 객체가 바뀌어도 예전 문자열이 남지 않는다.
- **`useDeferredValue`**: React가 입력 칸은 바로 갱신하고, 무거운 목록은 검색어를 한 박자 늦게 따라가 그리게 하는 훅이다. 빠르게 입력하는 동안 글자가 늦게 찍히지 않는다.

결과가 0개이면 '혹시 ○○를 찾으셨나요?'와 비슷한 글 5편을 보인다. 비슷한 정도는 편집 거리로 잰다. 편집 거리는 한 문자열을 다른 문자열로 바꾸는 데 필요한 글자 넣기·빼기·바꾸기의 최소 횟수이고, Damerau–Levenshtein 거리는 여기에 이웃한 두 글자 맞바꾸기를 한 번의 편집으로 더한다. 예를 들어 `dokcer`는 `k`와 `c`를 맞바꾸면 `docker`가 되므로 거리 1이다. 한글은 '리엑트'처럼 모음 하나만 틀리는 경우가 많아 글자를 자모로 풀어(`ㄹㅣㅇㅔㄱㅌㅡ`) 비교하고, 제목·주소·태그의 낱말과 비교한다. 본문은 비교하지 않는다. 긴 본문에는 어떤 검색어와도 비슷한 부분이 있기 때문이다.

### 휴대폰에서 결과가 0개인데 이전 글이 남던 문제

React는 목록을 다시 그리면서 각 항목의 `key`로 이전 화면의 DOM 노드와 새 항목을 짝짓는다. 같은 `key`가 둘 이상이면 어느 노드가 어느 항목인지 정할 수 없어, 사라져야 할 노드가 남거나 엉뚱한 노드가 재사용된다.

휴대폰에서 `리액트`로 찾은 뒤 한 글자 틀린 표기로 바꾸면 결과는 0개인데 목록에 앞 검색의 글이 남았다. 원인은 순위 결과를 기존처럼 날짜 묶음('오늘', '어제', '지난 7일')으로 나눈 데 있었다.

| 단계                                | 결과                                                                  |
| ----------------------------------- | --------------------------------------------------------------------- |
| 점수 순서의 글을 날짜 묶음으로 나눔 | 날짜가 섞여 있어 같은 묶음 제목이 여러 번 생긴다 (오늘 → 어제 → 오늘) |
| 묶음 제목을 React key로 사용        | 같은 key가 둘 이상 생긴다                                             |
| 결과가 0개가 되어 목록을 다시 그림  | React가 중복 key의 DOM 노드를 정리하지 못해 이전 글이 화면에 남는다   |

![중복 key가 생긴 구조](./images/day-1027-duplicate-key.svg '도식. 점수 순서 결과를 날짜 묶음으로 나누면 오늘 묶음이 두 번 생겨 key가 겹친다. 고친 뒤에는 묶음 없이 순위대로 한 줄로 그린다')

인기글처럼 검색 결과도 순위대로 한 줄로 늘어놓도록 바꿨다(`useNoteView.ts`의 `ranked`). 결과가 없으면 빈 목록 칸(휴대폰의 흰 카드)도 그리지 않는다. `mobile-memo-search.spec.ts`가 검색 결과에 묶음 제목이 0개인지, 결과가 없어지면 목록이 0개인지 확인한다.

### 최근 검색과 쌓임 맥락

목록 검색어를 최근 검색으로 5개까지 `localStorage`(`macfolio:memo:recent-searches`)에 저장하고, 빈 검색 칸에 초점이 가면 칸 아래(휴대폰은 위)에 목록을 펼친다. 이 목록이 본문 칸 오른쪽 위의 목차 버튼에 가렸다.

CSS의 `z-index`는 겹친 요소 가운데 어느 것을 위에 그릴지 정하는 값이다. 다만 값의 비교는 같은 쌓임 맥락(stacking context) 안에서만 이루어진다. `position: relative`에 `z-index`를 준 요소처럼 특정 조건을 만족하는 요소는 새 쌓임 맥락을 만들고, 그 자식들은 맥락 안에서만 순서를 다툰다. 예를 들어 부모 z-index가 4이고 자식이 10000이어도, 맥락 밖의 z-index 9인 요소와 비교할 때는 부모의 값 4로 비교된다.

목록의 z-index는 `var(--z-menu)`로 충분히 컸다. 문제는 부모 `.memo-search`의 `position: relative; z-index: 4`다. z-index가 있는 위치 지정 요소는 쌓임 맥락(stacking context)을 만들고, ==그 안의 자식은 맥락 밖의 요소와 직접 비교되지 않는다==. 메모 창 안에서는 검색 칸 4와 목차 버튼이 비교되므로 목록이 아래에 그려졌다.

![쌓임 맥락 전후](./images/day-1027-stacking.svg '도식. 목록이 열린 동안만 :has()로 검색 칸을 10으로 올리고, 목차 버튼 9, 글자 크기 버튼 8로 다시 배정했다')

처음에는 목록이 열린 검색 칸을 `z-index: 20`으로 올렸는데, stylelint 규칙(부품 안의 겹침은 -1~10, 화면 전체의 층은 `--z-*` 토큰)에 걸려 CI가 실패했다. 나란히 진행하던 [#396](https://github.com/hyeoniverse/MacFolio/pull/396)에서는 목차 버튼을 11로 올리고 있어, 두 PR의 순서를 함께 다시 정했다.

| 요소                          | 전 (#396 작업 중) |  후 |

| 최근 검색 목록이 열린 검색 칸 |                 4 |  10 |
| 목차 버튼·창                  |                11 |   9 |

## 목차와 이미지 배치 ([#391](https://github.com/hyeoniverse/MacFolio/pull/391), [#394](https://github.com/hyeoniverse/MacFolio/pull/394), [#396](https://github.com/hyeoniverse/MacFolio/pull/396))

### 글 목차와 이미지 정렬·띄우기 ([#391](https://github.com/hyeoniverse/MacFolio/pull/391))

저장소 글 238편의 `##`·`###` 제목 수는 중앙값 9개, 최대 32개이고, 10개 이상인 글이 99편이다. 읽기 화면에 목차가 없어 원하는 절을 찾으려면 끝까지 스크롤해야 했다. 이미지는 본문 가운데에 한 줄씩만 놓을 수 있어, 세로로 긴 캡처 옆에 설명을 배치할 수 없었다.

| 기능          | 표기·동작                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| 목차          | 본문 맨 위 단계의 `h2`·`h3`로 자동 생성, 제목 3개 이상일 때만. 스크롤해 목차가 지나가면 오른쪽 위에 ≡ 버튼 |
| 이미지 정렬   | `![설명](주소#left)`, `#right`                                                                             |
| 이미지 띄우기 | `#float-left`, `#float-right`: 본문 폭의 40%, 문단이 옆으로 흐른다. 휴대폰·좁은 창에서는 띄우지 않는다     |

배치 표기는 HTML `align` 속성, 속성 문법(`{.float-right}`), 캡션 덧붙이기를 비교해 주소의 `#` 조각으로 정했다. `#` 조각은 요청에 포함되지 않아 GitHub 등 다른 뷰어에서도 이미지는 그대로 보이고 배치만 무시된다. 편집기에서는 이미지를 고르면 배치 버튼 다섯 개가 나타나고, 누르면 `src`의 `#` 조각만 바꾼다.

![왼쪽에 띄운 이미지](./images/memo-toc-image-layout-float.jpg '#float-left로 띄운 이미지 옆으로 문단이 흐른다. 시험용 글로 촬영했다')

처음 구현에서는 목차가 비어 있었다. `useLayoutEffect`는 React가 DOM을 바꾼 직후, 브라우저가 화면을 그리기 전에 실행하는 훅이라 DOM의 크기나 내용을 읽는 데 쓴다. ref는 컴포넌트가 실제 DOM 노드를 가리키게 하는 참조다. `MemoToc` 안의 `useLayoutEffect`에서 본문 ref로 제목을 읽었는데, React는 layout 단계에서 형제를 앞에서부터 처리하며 ref도 그 순서로 연결한다. ==본문보다 앞에 그리는 목차의 layout effect 시각에는 본문 ref가 아직 비어 있었다==. 부모(`ReaderBody`)의 layout effect에서 읽도록 옮겼다.

### 누르면 펼치고 접기, 편집 화면 목차

#391에서 만든 목차는 여는 방식, 모양, 편집 화면 세 가지를 다시 고쳤다.

| 항목      | 전 (#391)                            | 후 (#394)                                                             |
| --------- | ------------------------------------ | --------------------------------------------------------------------- |
| 여는 방식 | 마우스를 올리면 열고, 누르면 고정    | 클릭·탭·Enter·Space로 펼침 ↔ 접힘. 고정 상태 없음                     |
| 모양      | 처음부터 펼친 목록, 작은 보조 글자색 | Apple 문서식 목록: 상자 없이 왼쪽 1px 세로선, 본문보다 약간 옅은 글자 |
| 편집 화면 | 목차·글자 크기 버튼 없음             | 읽기 화면과 같은 자리(제목 아래)에 목차와 글자 크기 버튼              |

CSS 전환(transition)은 숫자로 된 두 값 사이를 일정 시간 동안 이어 그리는 기능이라, 내용에 따라 정해지는 `height: auto`로는 전환하지 못한다. 그래서 펼치는 높이는 `display: grid`의 `grid-template-rows`를 `0fr` ↔ `1fr`로 280ms 동안 바꾼다. 접을 때는 `visibility`를 280ms 뒤에 `hidden`으로 바꿔 접힌 목록이 Tab 초점을 받지 않게 했다. 펼침 상태는 `STORAGE_KEYS.memoTocOpen`에 저장해 다음 글에도 유지한다.

![펼친 목차](./images/memo-toc-image-layout-toc-open.jpg '제목 아래의 목차를 펼친 화면. 상자 없이 왼쪽 세로선과 항목만 있고, ### 항목은 들여쓰기로만 구분한다')

> [!NOTE] 편집 화면의 zoom은 글 영역에만 건다
> 편집 화면은 판 전체에 `zoom`을 걸지 않고 날짜 줄·제목·목차·`.ProseMirror`에만 건다. 표 손잡이·서식 막대처럼 화면 좌표로 위치를 계산하는 편집 도구가 배율만큼 한 번 더 밀리기 때문이다.

글자색을 고르는 기준인 대비는 WCAG(웹 콘텐츠 접근성 지침)가 정의한 글자색과 바탕색의 상대 밝기 비율이다. 흰 바탕의 검정 글자는 21:1이고, 본문 크기 글자는 4.5:1 이상이어야 AA 기준을 만족한다.

목차 글자색은 커밋마다 바꿨다. 대비 수치, 본문과의 진하기 관계, 강조색 가운데 무엇을 기준으로 삼을지가 커밋마다 달라졌다.

### 떠 있는 목차 창이 글자 크기 버튼에 가리던 문제

스크롤하면 뜨는 목차 버튼(≡)으로 연 창의 아래쪽이 글자 크기 버튼(가 가)에 가리고 메모 창 아래에서 잘렸다. 항목이 30개 이상인 [VS Code 확장 글](/memo/vscode-extensions-web)에서는 뒤쪽 항목을 고를 수 없었다.

| 원인                                                            | 수정                                                                                        |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 창 최대 높이가 브라우저 화면 기준(`60vh`, 900px 화면에서 540px) | `ResizeObserver`로 본문 스크롤 칸 높이를 재 `--memo-toc-room`으로 전달, 버튼 자리를 뺀 높이 |
| 겹친 자리에서 z-index가 큰 글자 크기 버튼(10)이 위              | 목차 버튼·창 9, 글자 크기 버튼 8                                                            |

![떠 있는 목차 창 전후](./images/day-1027-toc-panel.jpg '1440×900 화면의 기본 크기 메모 창. 전에는 창 아래쪽이 글자 크기 버튼에 가렸고, 후에는 버튼 위에서 끝나고 창 안에서 스크롤한다')

같은 PR에서 창을 macOS 메뉴와 같은 크기(글자 13px, 모서리 14px, 너비 `min(18rem, 70vw)`)로 맞췄다.

### 브라우저형 도구 막대 ([#399](https://github.com/hyeoniverse/MacFolio/pull/399))

프로젝트 앱 창에는 제목 표시줄만 있어, iframe 안에서 링크를 따라가면 이전 페이지로 돌아갈 수단이 없었다. 게임이 아닌 프로젝트(HYEONIVERSE, NewPick, QRU, WTD)에는 Safari처럼 뒤로·앞으로, 주소창, 새로 고침이 있는 도구 막대를 넣었다. 게임(새싹 농장)은 화면을 넓게 쓰도록 제목 표시줄만 남겼다.

![프로젝트 앱 도구 막대 전후](./images/day-1027-project.jpg '창을 chrome="unified"로 열어 신호등 버튼이 도구 막대 위에 겹친다. 사이트 내용은 Playwright로 대체한 시험용 페이지다')

브라우저의 세션 기록(session history)은 한 탭에서 방문한 페이지의 목록으로, 뒤로·앞으로 버튼이 이 목록을 따라 이동한다. 동일 출처 정책(same-origin policy)은 프로토콜·호스트·포트가 모두 같은 페이지끼리만 서로의 문서와 객체에 접근하게 하는 브라우저 규칙이다. iframe의 페이지는 다른 출처라서 `iframe.contentWindow.history`에 접근할 수 없다. 대신 ==iframe 안의 이동이 바깥 문서의 세션 기록에 함께 쌓이는 성질==을 이용한다. MacFolio는 주소 막대를 `replaceState`로만 바꾸므로, 바깥 `history.length`가 늘어난 수가 iframe이 쌓은 기록 수다.

![바깥 문서의 세션 기록으로 iframe 기록 위치 추정](./images/day-1027-frame-history.svg '도식. base·length·index로 위치를 관리하고, 뒤로·앞으로는 바깥 문서의 history.back()·forward()로 iframe을 이동한다')

<details>
<summary>기록 위치를 갱신하는 신호</summary>

| 신호                                     | 처리                                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `history.length` 증가 (400ms 간격 조회)  | iframe에 초점이 있거나 방금 load가 끝났으면 이 iframe의 기록으로 집계, 아니면 다른 창의 기록으로 보고 `base`를 옮긴다 |
| iframe의 `load`                          | 새 이동으로 처리. 앞쪽 기록이 하나 남은 위치에서 이동하면 `history.length`가 그대로라 load로 판별한다                 |
| 뒤로·앞으로·새로 고침 뒤 3초 안의 `load` | 이동이 아니므로 무시. bfcache로 돌아가면 load가 오지 않아 시간으로 끊는다                                             |

`pushState`는 알려 주는 이벤트가 없어 `history.length`를 주기적으로 조회한다. 순수 계산은 단위 시험을 붙인 `frameHistory.ts`, 브라우저 신호 연결은 `useFrameHistory.ts`에 있다.

</details>

새로 고침은 `iframe.src`를 다시 지정하지 않고 `contentWindow.location.replace(src)`를 호출한다. `src`를 바꾸면 세션 기록이 하나 더 쌓이기 때문이다. 다른 출처의 현재 주소는 읽을 수 없어, 새로 고침은 처음 주소를 다시 불러온다.

> [!NOTE] 세션 기록은 문서 전체에 하나다
> 한계는 세션 기록이 문서 전체에 하나라는 점이다. 프로젝트 앱 두 개를 열고 번갈아 이동하면, 뒤로 가기는 마지막에 기록을 쌓은 iframe을 이동한다.

휴대폰은 페이지가 화면 전체를 쓰는 기존 구성을 유지하고, 도구 막대는 데스크톱에만 넣었다. 프로젝트 앱의 처음 구성은 [PROJECTS 데이터에서 생성하는 iframe 앱과 ProjectAppName 브랜드 타입](/memo/project-apps)에 있다.

## 폴더 4단 시도 ([#398](https://github.com/hyeoniverse/MacFolio/pull/398))

`MAX_FOLDER_DEPTH`는 글의 `category`에 `/`로 나눠 적을 수 있는 폴더 단계 수의 상한이다. 예를 들어 `개발 기록/MacFolio/회고`는 3단이다. 사이드바의 `개발 기록/MacFolio` 아래에 폴더 10개가 한 층에 나열되어 있어, 한 단계 더 나누려고 desktop-core의 `MAX_FOLDER_DEPTH`를 3에서 4로 바꿨다. 화면과 서버가 같은 규칙을 사용하므로 한 곳만 바꾸면 된다.

![메모 사이드바 폴더 전후](./images/day-1027-folders.jpg#float-right '기본 사이드바 너비에서 4단 폴더 디자인 시스템이 디자인 시…로 말줄임된다')

머지한 뒤 사이드바를 기본 너비로 확인하자 4단 폴더 이름이 말줄임되고, 들여쓰기가 네 단계라 폴더 이름에 쓸 수 있는 폭이 줄었다. 4단은 쓰지 않고 3단으로 되돌린 뒤 폴더를 다시 정리하기로 했다.

## 돌아보며

여러 PR을 나란히 진행하면서 같은 CSS 층을 PR마다 다르게 바꿨다. 검색 PR에서는 검색 칸을, 목차 PR에서는 목차 버튼을 올렸다. 쌓임 맥락 안에서는 자식의 z-index를 아무리 올려도 부모의 값으로 비교되고, stylelint의 -1~10 범위 때문에 값을 계속 올리는 방법도 막혔다. 한 화면에 떠 있는 요소(검색 목록, 목차 버튼·창, 글자 크기 버튼)의 순서를 표 하나로 정하고 두 PR을 그 표에 맞춘 뒤에야 끝났다.

목차 글자색을 커밋마다 바꿨다. 10월 23일 회고에 적은 "기준 화면과 수치를 먼저 정한다"는 원칙을 또 지키지 못했다. 다음에는 Apple 문서 화면 캡처와 후보 색 두세 개의 대비 표를 먼저 만들어 고른 뒤 구현한다.

검색 결과가 남던 문제는 표시 구조가 데이터 순서와 맞지 않아서 생겼다. 날짜 묶음은 날짜 순서 목록을 전제로 하는데, 점수 순서 목록에 그대로 적용해 묶음 제목과 React key가 중복됐다. 앞으로 정렬 기준을 바꾸면 그 목록을 그리는 구조(묶음, key)도 함께 확인한다.

폴더 깊이는 사이드바 폭에서 먼저 확인했어야 했다. PR 본문에 '디자인 시…' 말줄임을 적고도 머지했고, 머지한 뒤에 3단으로 되돌리기로 했다. 다음에는 구조를 바꾸는 PR이면 기본 크기 화면 캡처부터 확인하고 결정한다.
