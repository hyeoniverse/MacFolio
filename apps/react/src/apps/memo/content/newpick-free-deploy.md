리팩토링을 마친 뉴픽을 다시 인터넷에 올렸다. 목표는 **비용 0원**이다. AI 요약에 쓰는 Claude API만 쓴 만큼 낸다. 웹은 Vercel, api와 DB는 Oracle Cloud의 무료 VM 한 대에 두고, 서버 포트는 하나도 열지 않은 채 Cloudflare Tunnel로만 연결했다(newpick 이슈 #39, PR #40).

![배포 구성](./images/newpick-free-deploy-arch.svg '서버는 Cloudflare로 나가는 연결만 만든다')

![다시 열린 뉴픽](./images/newpick-free-deploy-home.jpg '2026-10-26, 첫 요약을 돌린 뒤의 홈')

## 어디에 올릴까

처음에는 무료 PaaS를 떠올렸지만 뉴픽 api에는 맞지 않았다. api가 **매일 08:00에 뉴스를 크롤링하고 08:30에 요약하는 cron**을 직접 돌리기 때문이다. 요청이 없으면 잠드는 무료 플랜에서는 아침 cron이 그냥 지나간다.

DB 용량도 따져 봤다. 크롤링 원문은 MongoDB TTL 인덱스로 30일이면 지워지고, 뉴스레터는 카테고리마다 하루 1건이다. 구독 메일 기록까지 더해도 **1년에 200MB 안팎**이라 어디에 두든 용량은 문제가 아니었다. 결정을 가른 것은 "항상 떠 있는가"와 "0원인가"였다.

| 선택지                                | 매일 cron | 한국에서 속도    | 걸리는 점                                      |
| ------------------------------------- | --------- | ---------------- | ---------------------------------------------- |
| Oracle Always Free VM (api + DB 함께) | 돈다      | 서울·춘천 리전   | 백업을 직접 해야 한다                          |
| VM(api) + 관리형 무료 DB              | 돈다      | DB가 해외면 느림 | 서비스 세 곳 관리, MySQL 호환 서비스 확인 필요 |
| 무료 PaaS                             | 잠든다    |                  | 아침 발송이 빠질 수 있다                       |
| GCP e2-micro 무료                     | 돈다      | 미국 리전만      | 1GB에 MySQL까지는 빠듯하다                     |

MacFolio api가 이미 같은 계정의 E2.1.Micro(1GB)에서 돌고 있었다. 로컬에서 재 보니 뉴픽은 api + MySQL + Mongo가 약 620MB라 같은 VM에는 들어가지 않는다. Always Free는 E2.1.Micro를 **두 대까지** 주므로 뉴픽 전용으로 한 대를 더 만들었다.

## 1GB에 맞추기

MySQL과 Mongo는 기본값이 "메모리가 넉넉한 서버"를 가정한다. 두 줄씩 줄였다.

```yaml
mysql:
  command:
    - --innodb-buffer-pool-size=64M # 기본 128M
    - --performance-schema=OFF # 이것만 수백 MB
mongo:
  command: ['--wiredTigerCacheSizeGB', '0.25']
```

여기에 swap 4GB를 둔다. compose에는 `ports`가 하나도 없다. 바깥 요청은 tunnel 컨테이너를 거쳐서만 api에 닿고, DB는 compose 네트워크 밖에서 접근할 수 없다.

첫 크롤링(기사 51건)과 6개 카테고리 요약을 돌리는 동안에도 사용 가능 메모리가 380MB쯤 남았다. 매일 아침 cron도 같은 일이라 버틸 수 있다.

## 막혔던 것들

### 1. Ubuntu 20.04로 만들어졌다

인스턴스 화면의 이미지 기본값이 Ubuntu 20.04였다. 2025년 4월에 일반 지원이 끝났고 Docker도 지원 목록에서 뺀 버전이다. 아직 아무것도 없을 때라 지우고 24.04로 다시 만들었다. 만든 직후 SSH가 `Connection refused`였는데, 막힌 게 아니라 부팅 중이었다. 20초 뒤에 열렸다.

### 2. 승인된 리디렉션 URI 칸이 없다

Google OAuth 클라이언트에 운영 주소를 추가하려는데 칸이 보이지 않았다. 처음 만든 클라이언트가 **데스크톱 앱** 유형이었다. 데스크톱 유형은 localhost로 돌아오는 것을 포트와 관계없이 허용해서, 로컬 로그인은 문제없이 됐다. 그래서 유형이 다르다는 것을 이때까지 몰랐다. 웹 애플리케이션 유형으로 새로 만들었다.

### 3. `.env`와 `api.env`

서버 `~/deploy`에는 비밀 값 파일이 두 개다.

| 파일      | 누가 읽나                  | 내용                                             |
| --------- | -------------------------- | ------------------------------------------------ |
| `.env`    | compose가 `${…}`를 채울 때 | `MYSQL_ROOT_PASSWORD`, `TUNNEL_TOKEN`, `API_TAG` |
| `api.env` | api 컨테이너의 환경 변수   | JWT, Google, Claude, 메일                        |

`.env`에 로컬 api 설정을 붙여 넣는 일이 생겼다. 그러자 `MYSQL_ROOT_PASSWORD`가 빈 값이 되고, api가 비밀번호 없이 DB에 붙으려다 `P1000 Authentication failed`로 뜨지 못했다. 바깥에서는 502였다.

MySQL의 root 비밀번호는 볼륨을 처음 만들 때 정해져 데이터에 남는다. 그래서 `.env`에 처음 값만 되돌리면 됐다. 터널 토큰은 아직 살아 있던 tunnel 컨테이너의 환경 변수에서 옮겼다. 다시 겪지 않도록 compose에서 빈 값이면 바로 멈추게 했다.

```yaml
MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?.env에 MYSQL_ROOT_PASSWORD가 없다}
```

### 4. 웹의 `/api`가 `DNS_HOSTNAME_RESOLVED_PRIVATE`

Vercel 배포는 성공했는데 `/api/category`가 404였고, 본문에는 `DNS_HOSTNAME_RESOLVED_PRIVATE`가 있었다. 웹은 `/api/*`를 `API_URL`로 프록시하고, 값이 없으면 `http://localhost:3001`로 보낸다. Vercel이 사설 주소로 가는 요청을 막은 것이다. `API_URL`을 넣고 다시 배포했다. 이 값은 빌드할 때 rewrites에 들어가므로 바꾸면 꼭 다시 배포해야 한다.

### 5. 빌드 로그의 `ApiError: Not Found`

다시 배포하자 빌드 로그에 `ApiError: Not Found`가 여러 번 찍혔다. 운영 DB가 아직 비어 있어서였다. 트렌드 API는 뉴스레터가 없으면 404를 돌려준다. 홈은 빌드할 때 데이터를 읽지만 실패를 잡아 빈 목록으로 그리므로 빌드는 성공한다. 다음 날 cron을 기다리지 않고 api 컨테이너 안에서 크롤링과 요약을 한 번 돌렸다. 기사 51건 크롤링에 약 4분, 6개 카테고리 요약에 약 10분이 걸렸다.

### 6. IT와 정치만 썸네일이 보였다

요약이 끝난 직후 홈 상단에 IT와 정치 썸네일만 보였다. 이미지 요청은 6개 모두 200이었다. 원인은 시간 순서에 있었다. 요약은 카테고리를 하나씩 만든다(IT 22:35, 정치 22:37, 경제 22:39 …). 홈은 10분마다 다시 만들어지는데(ISR), **IT와 정치만 있던 2분 사이에** 다시 만들어졌고 그 결과가 10분 동안 보였다. 다음 재생성에서 6개가 다 보였다. 버그가 아니라 첫 실행에서만 눈에 띄는 타이밍이었다.

### 7. 되돌리기 시험에서 되돌린 버전이 늦게 떴다

자동 배포 스크립트는 새 버전이 뜨지 않으면 이전 태그로 되돌린다. 일부러 바로 종료하는 이미지를 배포해 이 경로를 시험했다. 시험을 빨리 끝내려고 대기 시간을 40초로 줄였더니, 되돌린 버전이 뜨기 전에 시간이 끝나 "되돌리기도 실패"가 기록됐다. 1GB 서버에서는 `prisma migrate deploy`와 Nest 부팅에 **2분 30초쯤** 걸린다. 기본 대기 시간을 300초로 늘렸다. 실제 서버에서 측정하지 않았다면 운영 중에 처음 알았을 숫자다.

## main에 머지하면 배포된다

서버에서 이미지를 빌드하면 1GB에서는 몇 분씩 걸리고 swap을 크게 쓴다. MacFolio와 같은 방식으로, 이미지는 GitHub Actions가 만들고 서버는 받기만 한다.

1. **바뀌었나**: 서버 `/health`가 알려 주는 버전(`sha-` + 커밋)과 이번 커밋 사이에 `apps/api`가 바뀌었는지 본다. 직전 push가 아니라 **서버에 떠 있는 버전**과 비교한다. 그래야 한 번 실패한 배포가 다음 push에서 빠지지 않는다. 웹만 바꾼 머지는 api를 다시 띄우지 않는다.
2. **이미지**: 빌드해서 ghcr.io에 올린다.
3. **배포**: 배포 전용 SSH 키로 서버에 태그 하나를 보낸다. 이 키는 `authorized_keys`에서 `command=`로 묶여 `ops/deploy.sh`만 돌릴 수 있다. `sha-1234567; rm -rf /`처럼 모양이 다른 입력은 거절한다.
4. **서버**: MySQL 백업 → `.env`의 `API_TAG` 교체 → pull → 교체 → `/health` 버전 확인. 안 뜨면 이전 태그로 되돌리고 실패로 끝난다.

이미지에는 curl도 wget도 없어서, 컨테이너 안의 버전 확인은 node의 `fetch`로 한다. 배포와 별개로 매일 04:00 KST에도 백업한다. 서버 시간대가 UTC라 cron에는 `0 19 * * *`로 적었다.

## 남은 것

| 항목               | 상태                                                   |
| ------------------ | ------------------------------------------------------ |
| 자동 배포          | 서버의 GHCR 로그인과 배포 키·Secrets를 넣으면 동작한다 |
| 백업을 서버 밖으로 | 지금은 VM 디스크에만 있다                              |
| 뉴스레터 품질      | 요약 길이, 제목 짓기, 메일 디자인을 다음 작업으로      |

무료 VM 한 대에 DB까지 모으면 편하지만, 그 VM이 하나뿐이라는 점은 잊지 않으려 한다. 백업을 서버 밖으로 옮기는 것이 다음 순서다.
