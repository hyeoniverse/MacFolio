[요청 경로를 정리한 뒤](/memo/newpick-api-client)에도 뉴픽의 모든 페이지는 요청마다 서버에서 렌더링됐다. 루트 layout이 쿠키를 읽어 로그인 사용자를 조회했기 때문이다. 쿠키를 읽는 순간 Next.js는 그 페이지를 정적으로 만들 수 없다. 이 글은 사용자 조회를 브라우저로 옮기면서, 첫 화면에서 로그인 상태가 깜빡이지 않게 한 방법을 정리한다(PR #29).

## 왜 정적이어야 하나

뉴스레터는 매일 아침 한 번 만들어진다. 홈과 기사 목록은 방문자마다 다시 만들 필요가 없는 페이지다.

| 이유                 | 내용                                                                 |
| -------------------- | -------------------------------------------------------------------- |
| 데이터 변경 주기     | 하루 한 번. `revalidate`를 몇 분으로 잡아도 내용은 사실상 같다       |
| 작은 api 서버        | 동적이면 방문자 수만큼 api를 호출한다. ISR이면 재검증 주기마다 한 번 |
| 무료 플랜 cold start | api가 잠들어 있거나 내려가 있어도, 캐시된 페이지는 계속 뜬다         |
| 첫 화면 속도         | "렌더링 + api 왕복" 대신 CDN이 바로 응답한다                         |

솔직히 지금 트래픽이라면 체감 차이는 작다. 그래도 재배포 목표가 "작은 서버 한 대"(#12)이므로, api 호출이 방문자 수에 비례하지 않게 만드는 것을 4단계의 완료 조건으로 두었다.

## 깜빡임은 어디서 생기나

사용자 조회를 그냥 클라이언트로 옮기면, 정적 HTML에는 로그인 정보가 없다. 브라우저가 조회를 끝낼 때까지 헤더는 로그인 여부를 모르고, 로그인한 사용자에게도 "로그인" 버튼이 잠깐 보였다가 프로필로 바뀐다.

| 방법                                          | 동작                                                | 단점                                                      |
| --------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| 스켈레톤                                      | 조회가 끝날 때까지 헤더 오른쪽을 빈 자리로          | 잘못된 상태는 안 보이지만, 매번 빈 자리가 보인다          |
| PPR (Partial Prerendering)                    | 틀은 정적, 사용자 부분만 같은 응답에서 스트리밍     | Next 15.5 정식 버전에서는 쓸 수 없고 16 업그레이드가 필요 |
| **로그인 표시 쿠키 + 인라인 스크립트** (채택) | 첫 페인트 전에 쿠키를 읽어 헤더 상태를 CSS로 정한다 | 프로필 이미지는 조회 후에 채워진다                        |

세 번째는 다크 모드 깜빡임을 막는 흔한 방법과 같다. 화면을 그리기 전에 `<head>`에서 값을 읽어 `<html>`에 속성을 붙이고, CSS가 그 속성으로 보일 것을 정한다.

## 토큰이 아니라 "로그인했다"는 표시

토큰은 HttpOnly 쿠키라 스크립트로 읽을 수 없고, 읽을 수 있게 바꿔서도 안 된다. 그래서 api가 로그인할 때 **로그인 여부만 담은** 쿠키를 하나 더 내려준다.

```ts
export const SESSION_HINT_COOKIE = 'logged_in';

export function sessionHintCookieOptions(maxAge?: number): CookieOptions {
	return { ...authCookieOptions(maxAge), httpOnly: false };
}
```

값은 `1`뿐이고 만료는 refresh token과 같은 12시간이다. 이 쿠키를 위조해도 얻는 것은 "로그인 버튼 대신 프로필 자리가 보이는 것"뿐이다. 실제 권한은 여전히 HttpOnly 토큰으로 판단한다.

![순서](./images/newpick-static-auth-hint-flow.svg '토큰은 그대로 HttpOnly. 스크립트가 읽는 것은 표시 쿠키뿐')

루트 layout의 `<head>`에는 한 줄짜리 스크립트를 넣었다.

```ts
const sessionHintScript = `document.documentElement.dataset.auth=document.cookie.split('; ').includes('${SESSION_HINT_COOKIE}=1')?'in':'out'`;
```

정적 HTML의 헤더는 로그인 버튼과 프로필 자리를 **둘 다** 담고 있다. CSS가 `data-auth`에 맞는 쪽만 보여 준다.

```css
html[data-auth='in'] .auth-out,
html[data-auth='out'] .auth-in {
	display: none;
}
```

하이드레이션이 끝나면 React 상태가 이어받는다. 상태는 `unknown`(쿠키를 읽기 전) → `in` / `out` 세 가지로 두고, `unknown`인 동안에만 두 쪽을 모두 렌더링한다. 서버와 첫 클라이언트 렌더링 결과가 같으므로 하이드레이션 오류가 없다. `in`이면 그때 프로필을 조회하고, 비로그인 방문자는 백엔드를 호출하지 않는다.

![로그인한 헤더](./images/newpick-static-auth-hint-header-in.jpg '로그인: 프로필 자리 (WebKit)')

![비로그인 헤더](./images/newpick-static-auth-hint-header-out.jpg '비로그인: 테마 전환과 로그인 버튼 (WebKit)')

## 표시 쿠키를 토큰 상태에 맞추기

표시 쿠키가 토큰과 어긋나면, 로그아웃된 사람에게 프로필 자리가 보인다. 어긋날 수 있는 경우를 모두 막았다.

| 경우                           | 처리                                                                |
| ------------------------------ | ------------------------------------------------------------------- |
| 로그인, 토큰 갱신 성공         | api가 발급                                                          |
| 로그아웃, 갱신 실패            | api가 삭제. middleware는 api가 보낸 삭제 `Set-Cookie`를 그대로 전달 |
| 표시 쿠키만 남음 (토큰 만료)   | middleware가 삭제                                                   |
| 토큰은 있는데 표시 쿠키가 없음 | middleware가 채움 (이 기능을 배포하기 전에 로그인한 사용자)         |

마지막 줄은 배포 직후를 위한 것이다. 처음에는 놓쳤다가 구현 중에 발견했다. 이미 로그인해 있던 사용자는 표시 쿠키가 없으므로, 그대로 두면 토큰이 있는데도 로그아웃 상태로 보인다.

갱신 실패 시 표시 쿠키를 middleware에서 직접 지우지 않고 api의 `Set-Cookie`를 전달하는 이유는, 쿠키 domain 옵션을 api만 알기 때문이다(`COOKIE_DOMAIN`). 같은 이름이라도 domain이 다르면 다른 쿠키로 취급되어 지워지지 않는다.

## 빌드 결과

| 페이지                    | 이전 | 이후             |
| ------------------------- | ---- | ---------------- |
| `/`, `/about`, `/mypage`  | ƒ    | **○ (10분 ISR)** |
| `/articles`               | ƒ    | ƒ (아래 참고)    |
| `/articles/detail/[slug]` | ƒ    | ƒ                |

`/articles`는 일부러 동적으로 두었다. 제목과 목록이 `?categoryId=`에 따라 달라지는데, 정적으로 만들면 '전체' 화면이 먼저 보였다가 해당 카테고리로 바뀌는 다른 종류의 깜빡임이 생긴다. 정적으로 만들려면 카테고리를 쿼리 대신 경로(`/articles/[category]`)로 옮겨야 한다. 정적으로 바꾸자 빌드가 `useSearchParams() should be wrapped in a suspense boundary`로 실패해서 알게 된 것이다.

홈에는 `revalidate = 600`을 넣었다. 넣지 않으면 Next 15는 빌드 시각에 받은 데이터로 페이지를 고정한다.

## 확인

쿠키 상황은 curl로, 화면은 Playwright로 WebKit과 Chromium에서 확인했다.

| 상황                          | 결과                                      |
| ----------------------------- | ----------------------------------------- |
| 쿠키 없이 `/`                 | 200, `x-nextjs-cache: HIT`                |
| refresh 쿠키만                | 새 access token + `logged_in=1`           |
| 잘못된 refresh + 표시 쿠키    | api가 보낸 표시 쿠키 삭제가 전달됨        |
| access 쿠키만 (표시 없음)     | `logged_in=1` 채움                        |
| 표시 쿠키만 남은 채 `/mypage` | 307 → `/?login=required` + 표시 쿠키 삭제 |

깜빡임은 두 가지로 확인했다. React 번들 요청을 막아 **하이드레이션 전 화면**만 보면, 로그인·비로그인 모두 맞는 쪽만 보였다. 정상 실행에서는 `MutationObserver`로 로드부터 끝까지 감시했고, 잘못된 쪽이 한 번도 보이지 않았다. 비로그인 방문자의 프로필 요청은 0회였다.

## 남은 것·배운 것

- 로그인한 사용자는 프로필 이미지가 조회 후에 채워진다. 기본 아이콘이 같은 크기로 자리를 잡고 있어 레이아웃은 밀리지 않는다.
- 홈은 api가 실패하면 빈 목록으로 렌더링한다. 재생성 시점에 api가 내려가 있으면 빈 홈이 10분간 캐시된다. 이전에는 그 요청 한 번만 비었으므로, 실패 시 이전 페이지를 유지하는 쪽으로 바꿔야 한다.
- 처음 테스트에서 JS를 끄고 하이드레이션 전 화면을 보려 했는데, 그러면 인라인 스크립트도 실행되지 않아 의미가 없었다. React 번들 요청만 막아야 "스크립트는 돌고 React는 아직"인 순간을 볼 수 있다.
