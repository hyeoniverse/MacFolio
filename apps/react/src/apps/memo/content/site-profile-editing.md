이 사이트는 배포용으로 만들었지만, 안에 든 내용은 내 것이다. 이름, 이메일, GitHub 주소, 다룰 수 있는 기술이 모두 `shared/profile.ts`의 상수였다. 다른 사람이 이 저장소를 가져다 띄우면 코드를 고쳐서 다시 빌드해야 했다.

그래서 프로필을 서버에 두고, 관리자가 **시스템 설정 › 정보**에서 고치게 했다. 저장한 값이 없으면 코드의 상수가 기본값으로 쓰인다.

## 고른 방법과 버린 방법

| 방법                           | 장점                                      | 단점                                                                |
| ------------------------------ | ----------------------------------------- | ------------------------------------------------------------------- |
| 빌드할 때 환경 변수로 넣는다   | 서버가 필요 없다                          | 바꿀 때마다 다시 빌드·배포해야 한다. 기술 목록 같은 배열이 어색하다 |
| 저장소에 JSON 설정 파일을 둔다 | 코드와 내용이 나뉜다                      | 여전히 커밋과 배포가 필요하다                                       |
| 서버 DB에 두고 화면에서 고친다 | 배포 없이 바로 바뀐다, 관리자 화면 재사용 | 서버가 없을 때를 따로 생각해야 한다(기본값)                         |

이 사이트에는 이미 관리자 로그인과 DB가 있다. 그래서 세 번째를 골랐고, 서버가 없거나 저장한 값이 없을 때는 지금처럼 코드의 상수를 기본값으로 쓴다.

## 서버: 한 줄짜리 표

```prisma
model SiteContent {
  id        Int      @id @default(1)
  profile   Json?
  updatedAt DateTime @updatedAt
  updatedBy String?
}
```

사이트에 프로필은 하나뿐이라 `id`가 늘 1인 표다. 다음 단계에서 Safari의 프로젝트 내용도 여기에 담을 생각이라 이름을 `SiteContent`로 지었다.

| 요청                   | 누가   | 하는 일                                  |
| ---------------------- | ------ | ---------------------------------------- |
| `GET /site`            | 누구나 | `{ profile, updatedAt }` (없으면 `null`) |
| `PUT /site/profile`    | 관리자 | 검사해서 저장. 틀리면 400과 이유 전부    |
| `DELETE /site/profile` | 관리자 | 저장한 값을 지운다 (코드의 기본값으로)   |

읽기는 요청마다 DB에 묻지 않도록 서비스가 메모리에 들고 있다가, 저장하거나 지울 때 비운다.

```ts
// apps/api/src/site/site.service.ts
view(): Promise<SiteView> {
	this.cache ??= this.prisma.siteContent.findUnique({ where: { id: ROW_ID } }).then((row) => ({
		profile: readProfile(row?.profile),
		// ...
	}));
	this.cache.catch(() => (this.cache = null)); // 실패한 읽기는 기억하지 않는다
	return this.cache;
}
```

값이 아니라 Promise를 기억해 두는 것이 요점이다. 서버가 막 떠서 여러 요청이 한꺼번에 와도 DB에는 한 번만 묻는다. 읽기가 실패하면 기억을 지워 다음 요청이 다시 묻는다. `readProfile`은 DB에 든 값이 규칙에 맞지 않으면(예: 손으로 고친 행) 기본값을 돌려준다.

## 검사는 한 곳에

검사 규칙은 `desktop-core`의 `parseProfile()`에 두고 서버와 화면이 함께 쓴다.

- 이름·이메일·GitHub 주소는 꼭 있어야 한다. 나머지 한 줄 값은 비워도 된다.
- 이메일은 `a@b.c` 모양, GitHub 주소는 `https://github.com/아이디` 모양이다. 끝의 `/`는 뗀다.
- 한 줄 값은 80자까지이고, 줄바꿈·제어 문자는 받지 않는다. 이 값은 메일 머리와 터미널 출력에 들어간다.
- 기술 목록은 20개, 항목마다 40자까지다. 앞뒤 공백, 빈 항목, 겹친 항목은 뺀다.
- 모르는 필드는 버린다.

틀린 곳이 여럿이면 처음 하나만이 아니라 **모두** 모아서 돌려준다. 화면은 저장하기 전에 같은 함수로 먼저 확인하므로, 틀린 값은 서버에 가지도 않는다. 서버는 그래도 다시 확인한다.

## 서버가 쓰던 이름도

서버에도 `'김정현'`이 박혀 있었다. 관리자가 쓴 댓글의 이름과 메시지 앱 고정 항목의 제목이다. 이 둘은 이제 `SiteService.ownerName()`을 쓴다. 저장한 프로필의 이름이고, 없으면 원래 상수다. API e2e로 저장하기 전에는 김정현, 저장한 뒤에는 새 이름, 되돌리면 다시 김정현인지 확인했다.

![SiteContent 표에서 SiteService, 프로필 저장소를 거쳐 useProfile과 getProfile로 읽는 흐름](./images/site-profile-editing-flow.svg '프로필이 서버에서 화면까지 가는 길')

## 화면: 상수 열다섯 곳

프로필 상수를 읽던 곳은 열다섯 파일이었다. 이 Mac에 관하여, 시스템 설정, 메일(환영 메일, 받는 사람, 주소 복사, 메일 앱으로 넘기기), 메모 댓글(작성자 이름·사진), 터미널(`whoami`, `contact`), 휴대폰 홈 위젯과 제어 센터, 관리자 계정 카드, Safari 프로젝트의 크레딧이다. 메시지 앱은 상수를 읽지 않고 `'김정현'`을 따로 적어 두고 있었다(고정 안내의 제목과 첫인사).

문제는 **모듈을 읽을 때 한 번 계산하는 값**이었다.

```ts
// 전: 앱을 열기 전에 이미 정해진다
export const OWNER_ADDRESS = `${PROFILE.name} <${PROFILE.email}>`;
const ADMIN_LOGIN = PROFILE.github.split('/').at(-1) ?? '';
export const PINNED_MESSAGES = [{ text: '안녕하세요, 김정현입니다 👋', ... }];
```

서버의 프로필은 앱이 뜬 뒤에 도착하므로, 이런 값은 끝까지 옛 이름으로 남는다.

![모듈 상수, getProfile, useProfile이 프로필을 읽는 시점 비교](./images/site-profile-editing-timing.svg '언제 읽느냐가 문제였다')
그래서 프로필을 `createStore`로 만든 저장소에 두고, 읽는 방법을 둘로 나눴다.

- 컴포넌트는 `useProfile()`을 쓴다. 저장하면 새로고침하지 않아도 그 자리에서 다시 그려진다.
- 컴포넌트 밖(메일 보내기, 터미널 명령, 메시지 저장소)은 `getProfile()`을 쓴다. 상수 대신 **쓰는 순간에** 읽는다.

상수는 함수가 되었다. `OWNER_ADDRESS`는 `ownerAddress(profile)`, `PINNED_MESSAGES`는 `pinnedMessages()`, `INBOX`는 `inboxOf(profile)`이다.

메일 목록의 "받는 사람"에는 원래 `김정현 <…>` 문자열을 넣고, 그 값과 같은지를 보고 주소 복사 버튼을 그렸다. 이름이 바뀌면 비교가 깨지므로, 받는 사람 자리에는 `TO_OWNER`라는 표시만 두고 그릴 때 지금 프로필로 바꾼다.

메시지 앱은 목록을 한 번 읽어 두므로, 프로필의 이름이 바뀌면 다시 읽게 했다. 앱을 연 뒤에 서버의 프로필이 도착하는 경우에도 고정 항목의 이름이 맞는다.

## 편집 화면

관리자로 로그인하면 시스템 설정 › 정보의 머리 오른쪽에 **편집**이 생긴다. GitHub 항목의 편집과 같은 파란 글자다.

- 보기와 같은 둥근 칸에서, 값 자리가 입력칸으로 바뀐다. macOS 설정처럼 테두리 없이 오른쪽 정렬이고, 고르는 줄에만 파란 테두리가 생긴다.
- 기술 목록은 쉼표로 나눠 한 줄로 쓴다.
- **완료**를 누르면 확인하고 저장한다. 틀리면 칸 위에 이유가 모두 빨간 상자로 뜬다.
- 저장한 값이 있을 때만 **기본값으로 되돌리기**가 보이고, 한 번 더 묻는다.
- 비운 값(학교, 인터랙션 기술 등)은 이 Mac에 관하여와 정보에서 줄째 빠진다.

## 확인

- 단위: `parseProfile`(다듬기, 모든 이유 모으기, 모양 검사), `readProfile`(DB의 값이 틀렸으면 기본값)
- API e2e: 401·400과 이유 목록, 저장하면 관리자 댓글 이름·메시지 고정 항목 제목·주인 답장 이름이 바뀜, 되돌리기. 경로 표에 세 경로의 권한을 적었다.
- E2E: 서버에 저장한 프로필이 방문자의 이 Mac에 관하여, 정보, 메일, 메시지에 보임. 관리자가 고치면 틀린 값은 보내지 않고 이유를 보여 주고, 저장한 값은 다듬어져 있고, 다른 창이 그 자리에서 바뀜. 되돌리기.

변경은 42파일, 1,467줄 추가와 213줄 삭제였다. 검사 규칙 `packages/desktop-core/src/site/profile.ts`(116줄)와 그 시험(71줄)이 가운데에 있다.

## 남은 것·배운 것

- 화면은 처음에 코드의 기본값으로 그렸다가 서버의 프로필이 오면 바뀐다. 저장한 값이 기본값과 많이 다르면 첫 순간에 옛 이름이 잠깐 보일 수 있다.
- 모듈을 읽을 때 계산하는 상수는 편하지만 "나중에 바뀔 수 있는 값"과 섞이면 찾기 어려운 버그가 된다. 값이 바뀔 수 있다면 상수 대신 함수로 두고 쓰는 순간에 읽는다.
- 검사 규칙을 서버와 화면이 함께 쓰니, 화면은 보내기 전에 같은 이유를 보여 주고 서버는 같은 이유로 막는다. 둘이 어긋날 일이 없다.
- 표 이름을 `SiteContent`로 넓게 지은 것은 바로 다음 일에서 값을 했다. 프로젝트 내용도 같은 표에 들어갔다(/memo/site-projects-editing).

## 따라 하는 방법

이 저장소를 가져다 쓰는 사람이 자기 프로필로 바꾸는 순서다.

1. 서버를 띄우고(`pnpm dev:all` 또는 배포 서버) 자기 GitHub 숫자 ID를 `api.env`의 `ADMIN_GITHUB_ID`에 넣는다(기본값은 저장소 주인의 ID다)
2. 메뉴 막대에서 GitHub로 로그인한다
3. 시스템 설정 › 정보에서 이름·이메일·GitHub 주소를 고치고 저장한다

저장하면 화면의 상수 열다섯 곳이 서버 값으로 바뀐다. 서버를 쓰지 않으면 코드의 기본값([packages/desktop-core/src/site/profile.ts](https://github.com/hyeoniverse/MacFolio/blob/main/packages/desktop-core/src/site/profile.ts))이 그대로 쓰인다. 시험은 `cd apps/react && npx playwright test e2e/site-profile.spec.ts`.

참고 문서: [GitHub 사용자 ID 찾기(REST users API)](https://docs.github.com/en/rest/users/users#get-a-user).
