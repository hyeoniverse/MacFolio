[성능 측정 리포트](/memo/site-performance-report)에서 원인을 찾았다. 3.8MB 글꼴, 첫 묶음에 들어 있던 블로그 원문과 모든 앱의 코드, 큰 그림과 영상, JS가 그리던 로딩 화면이다. 이 글은 그것들을 하나씩 덜어 낸 기록이다. 순서는 효과가 큰 것부터다.

![느린 휴대폰에서 고치기 전·후](./images/site-performance-diet-filmstrip.jpg '느린 4G·4배 느린 CPU의 휴대폰에서 0.5초마다 찍은 화면. 고치기 전에는 7초 동안 검은 화면, 고친 뒤에는 1초에 사과가, 2초에 시작 안내가 뜬다')

Lighthouse 휴대폰 조건(느린 4G, 4배 느린 CPU)으로 첫 화면을 0.5초마다 찍었다. 고치기 전에는 7초 동안 검은 화면이다. 고친 뒤에는 1초에 사과가 뜨고 2초에 "탭하여 로딩을 시작하세요"가 뜬다.

## 1. 글꼴: 1.7MB → 149KB

본문 글꼴은 TTF 한 벌을 그대로 썼다. 원본 3.8MB, 서버가 압축해도 1.7MB다. 한글 완성형 11,172자를 다 담고 있어서다.

화면에 나오는 한글은 대부분 KS X 1001 완성형 2,350자 안이다. 그래서 둘로 나눴다(`scripts/subset-font.py`, fonttools).

- **core (149KB):** 영문·숫자·문장 부호·자모와 완성형 2,350자
- **ext (232KB):** 나머지 한글 8,822자 (똠, 햏 같은 글자)

```css
/* 같은 이름의 글꼴은 나중에 적은 것부터 찾고, 그 글꼴에 글자가 없으면 다음 것을 찾는다 */
@font-face {
	font-family: 'MacSystemFont';
	font-display: swap;
	src: url('/fonts/AppleSDGothicNeoR-ext.woff2') format('woff2');
	unicode-range: U+AC00-D7A3;
}
@font-face {
	font-family: 'MacSystemFont';
	font-display: swap;
	src: url('/fonts/AppleSDGothicNeoR-core.woff2') format('woff2');
	unicode-range: U+0020-00FF, U+2000-206F, U+3000-303F, U+3131-318E, U+AC00-D7A3;
}
```

처음에는 core의 `unicode-range`에 2,350자를 하나씩 적으려 했다. 그런데 CSS Fonts 4에 따르면 브라우저는 범위가 맞는 글꼴에 글자가 없으면 다음 글꼴을 찾는다. 그래서 두 글꼴 모두 한글 전체를 범위로 두고, core를 나중에 적었다. 흔한 글자는 core에서 찾고 끝난다. core에 없는 글자가 화면에 나올 때만 ext를 받는다. 측정에서 ext는 한 번도 받지 않았다.

글자를 나누다 한 번 헛디뎠다. 파이썬의 `euc_kr`은 2,350자 밖의 글자도 8바이트 조합형으로 인코딩한다. 그래서 "인코딩되면 완성형"으로 고르니 11,172자가 다 골라져 core가 373KB가 되었다. 2바이트로 인코딩되는 것만 세도록 고쳤다.

## 2. 첫 묶음에서 글 원문 2.4MB 빼기

블로그 글은 빌드할 때 원문을 묶는다.

```ts
import.meta.glob('../content/*.md', { query: '?raw', import: 'default', eager: true });
```

`eager: true`라 이 파일을 부르는 곳은 원문 2.4MB를 함께 싣는다. 그런데 이 파일을 바탕화면 아이콘도 불렀다. 바탕화면 아이콘은 Finder의 폴더 트리로 그리고, 그 트리에 블로그 폴더가 있기 때문이다.

글 저장소의 `list()`는 원래 비동기라 고치기 쉬웠다. 원문을 `contentFiles.ts`로 떼고, 처음 목록을 물을 때 `import()`로 받는다.

```ts
export function getPostRepository(): PostRepository {
	repository ??= {
		async list() {
			loading ??= import('./contentFiles').then(({ files }) => createStaticPostRepository(files));
			return (await loading).list();
		},
	};
	return repository;
}
```

이것만으로는 데스크톱에서 여전히 받았다. 바탕화면 아이콘이 첫 화면에서 `list()`를 불러서다. 그래서 글 목록을 트리들이 함께 보는 store로 옮기고, 받기는 블로그 폴더가 필요한 곳(Finder, 열기 창, 휴지통)만 시작하게 했다. 바탕화면 아이콘과 Dock 휴지통은 `useLocations({ posts: false })`로 부른다. 누가 이미 받았으면 그것을 같이 쓴다.

Finder 트리에는 저장소 문서(README, docs/\*.md)도 있다. 여기도 같은 일이 있었다. 트리는 문서의 **경로**만 쓰는데 원문(압축 75KB)이 딸려 왔다. `import.meta.glob`을 `eager` 없이 쓰면 키(경로)는 빌드할 때 정해지고 원문은 부를 때만 받는다. 경로만 쓰는 `docPaths.ts`를 따로 뒀다.

## 3. 앱 코드는 처음 열 때

앱 목록(`apps/registry.ts`)에서 메모·Finder·텍스트 편집기만 `lazy`였다. 나머지 열일곱 앱은 첫 묶음에 있었다. Safari 프로젝트 페이지의 템플릿들과 시스템 설정의 프로젝트 편집기까지 들어 있었다. 모두 `lazy`로 바꿨다. 첫 묶음(`boot`)은 압축 250KB에서 47KB가 되었다.

`main.tsx`는 사이트 콘텐츠를 합친 뒤에 `boot.tsx`를 `import()`로 부른다. 그래서 브라우저는 `main`을 받아 실행하기 전까지 `boot`가 있는 줄 모른다. 한 번 더 왕복하는 셈이다. 빌드할 때 `boot`와 그 묶음이 바로 쓰는 묶음들을 `index.html`에 `<link rel="modulepreload">`로 적는 Vite 플러그인을 더했다. 실행 순서는 그대로고 받기만 함께 한다.

## 4. 그림과 영상

- **아이콘:** Dock에서는 64px로 보이는데 원본은 2560px(`photos.png`)까지 있었다. 256px로 줄여 다시 저장했다. 이름과 형식이 그대로라 코드는 바꾸지 않았다. 1,171KB → 428KB
- **배경화면:** 넓은 그라데이션이라 WebP가 JPG보다 훨씬 작다. 휴대폰 기본 배경화면은 308KB → 60KB. 모두 바꿔 7.9MB → 2.3MB다. 주소는 `wallpaperUrl` 한 곳과 기본값 CSS에서 만든다
- **휴대폰의 데스크톱 배경화면:** `body`가 늘 데스크톱 배경화면을 깔고 있어서, 휴대폰도 쓰지 않는 2048px 그림(348KB)을 받았다. 휴대폰 화면 조건(`isMobileViewport`와 같은 미디어 쿼리)에서는 `body`에도 휴대폰 배경화면을 깐다. 같은 그림이라 한 번만 받는다
- **Safari 첫 페이지:** 데스크톱은 Safari가 열린 채로 시작한다. 그 페이지가 화면 밖의 영상(`autoPlay`)과 영상의 첫 화면 그림(`poster`)까지 받았다. 영상은 화면 가까이(위아래 400px) 오면 그때 `src`와 `poster`를 넣는다(`useNearView`)
- **음악:** 목록에 곡 길이를 보이려고 앱이 켜질 때 곡마다 메타데이터를 받았다. 곡 일곱 개의 길이를 재서 코드에 적고, 곡은 누르기 전에 받지 않는다(`preload="none"`)

## 5. 로딩 화면을 HTML로 먼저

로딩 화면은 React가 그렸다. 그래서 JS를 다 받기 전에는 검은 화면이고, 사과는 Font Awesome 글자라 글꼴까지 받아야 떴다.

먼저 사과를 SVG로 바꿨다. 그리고 `index.html`에 같은 자리·크기로 사과와 진행 막대를 그리는 `#boot-splash`를 두었다. 스크립트를 받는 동안 이것이 보이고, React가 처음 그리면 지운다. 로딩 화면이 같은 자리에 이어 그려져서 바뀌는 순간이 보이지 않는다.

여기서 주의할 곳이 하나 있었다. 운영의 Worker는 검색엔진용 본문을 넣으려고 `index.html`의 `<div id="root"></div>`를 글자 그대로 찾아 바꾼다. 그래서 `#root` 안에는 아무것도 넣지 않고, 그 앞에 따로 두었다.

## 6. 깨진 E2E 16개

앱을 `lazy`로 바꾸고 E2E를 돌리자 16개가 깨졌다. 다시 돌려도 같았다. 까닭은 셋이었다.

**셸이 앱의 CSS를 빌려 쓰고 있었다.** 휴대폰 홈 인디케이터가 투명하게 나오고, 홈 화면에서 쓸어 올려도 앱 전환기가 열리지 않았다. 홈 인디케이터의 모양은 `Window.css`에 있다. 이 CSS를 부르는 것은 창 틀(`Window.tsx`)이고, 창 틀은 앱만 부른다. 앱이 첫 묶음에 있을 때는 이 CSS가 우연히 늘 실려 있었다. 이제 셸(`Desktop.tsx`)이 처음부터 싣는다. 코드 분할이 숨어 있던 의존을 드러낸 셈이다.

**상태 표시줄 색이 잠깐 늦다.** 휴대폰 상태 표시줄은 밑에 깔린 화면을 읽어 글자 색을 정한다. 앱을 연 순간에는 앱 화면이 아직 없어 홈 화면을 읽는다. 0.8초마다 다시 읽으니 곧 맞지만, 열자마자 색을 보던 시험이 깨졌다. 시험은 맞을 때까지 기다리게(`expect.poll`) 고쳤다.

**시험이 너무 일찍 읽었다.** 창이 뜨자마자 목록의 수를 세거나 단축키(⌥N)를 누르던 시험들이다. 이제 창이 뜬 뒤 앱 코드가 올 때까지 잠깐 빈 창이다. 시험은 앱이 그려질 때까지 기다리게 했다. 메모만은 고쳤다. 메모를 열면 글 원문 묶음까지 받아야 해서 목록이 비어 보이는 순간이 있었다. 메모 앱이 원문 묶음을 함께 불러오게 해서, 메모가 뜰 때는 목록이 이미 차 있다.

## 7. 2차: 아이콘과 앨범 그림은 WebP, 메뉴 막대의 사과는 SVG

1차를 머지하고 휴대폰을 다시 들여다봤다. Lighthouse가 "더 작은 형식·크기로 바꾸면 300KB를 아낀다"고 짚은 그림은 거의 앱 아이콘이었다.

- **아이콘:** 256px PNG에서 192px WebP로 바꿨다. 휴대폰 홈 화면의 아이콘은 60px이라 3배 화면에도 192px면 된다. 아이콘 열일곱 개가 428KB에서 51KB가 되었다. PNG는 지우지 않았다. 관리자가 서버에 저장한 프로젝트 내용에는 예전 PNG 주소가 들어 있을 수 있어서다
- **앨범 그림:** 음악 위젯·앱의 앨범 그림을 512px WebP로. 742KB → 146KB
- **사과:** 1차에서 로딩 화면의 사과는 SVG로 바꿨는데, 메뉴 막대의 사과는 여전히 Font Awesome brands 글꼴이었다. 이 사과 하나 때문에 데스크톱 첫 화면이 brands 글꼴(113KB)을 받았다. 두 곳이 같은 SVG 부품(`AppleLogo`)을 쓰게 했다

묶음 수도 줄여 보려 했다. 브라우저를 실제로 느리게 하고 보니, 첫 화면이 미리 받는 JS 묶음 33개가 줄을 서느라 마지막 묶음이 5.1초에 끝났다. Rolldown의 `codeSplitting.groups`로 작은 공용 모듈을 한 묶음에 모아 봤다. 그러자 의존 모듈까지 따라 들어와 672KB짜리 묶음이 생겼다. 의존을 빼니 이번에는 블로그 글 하나하나(작은 모듈이다)까지 모여 596KB가 되었다. 그만뒀다. 줄을 선 것은 로컬 측정 서버가 HTTP/1.1이라 한 번에 6개씩 받아서이기도 하다. 운영(Cloudflare)은 HTTP/2라 묶음 수의 손해가 훨씬 작다.

## 8. 3차: 누르기 전에는 홈 화면을 그리지 않는다

2차를 마치고 휴대폰 LCP를 다시 봤다. 5.8초에 잡힌 "가장 큰 그림"은 로딩 화면 뒤에 숨어 있던 홈 화면이었다. 로딩 화면은 누르기 전까지 화면을 덮는데, 그 뒤에서 앱은 바탕화면·Dock·위젯을 다 그리고 아이콘과 배경화면을 받고 있었다. 아무도 못 보는 화면이 첫 방문의 시간과 양을 쓰고 있었다.

- **누른 뒤에 그린다:** `LoadingScreen`에 `onStart`를 두고, 누르는 순간에 바탕화면(휴대폰은 홈 화면)을 그리기 시작한다. 진행 막대가 차는 2.5초 동안 받으면 되니, 다 찬 뒤 걷히는 화면은 그대로다. 로그인하고 돌아온 경우처럼 로딩 화면을 건너뛸 때는 처음부터 그린다
- **시작 안내도 HTML로:** 1차에서 HTML로 먼저 그린 첫 그림에는 사과와 막대만 있었다. 여기에 "탭하여/클릭하여 로딩을 시작하세요"를 넣었다. 탭과 클릭은 앱이 쓰는 휴대폰 기준과 같은 미디어 쿼리로 고른다
- **스크립트보다 먼저 누르면:** 첫 그림에 안내가 보이니, 스크립트를 받는 동안 누르는 사람이 생긴다. 그 누름을 잃지 않게 `theme-boot.js`가 첫 클릭을 `window.__macfolioTapped`에 적어 두고, 로딩 화면이 뜨면 그것을 보고 바로 시작한다
- **진행 막대가 멈추던 것:** `onStart`를 그릴 때마다 새 함수로 넘기니 로딩 화면의 효과가 다시 돌며 타이머를 지웠다. 함수들은 ref에 담아 늘 지금 것을 부르게 했다

3차는 받는 양을 없앤 것이 아니라 누른 뒤로 미뤘다. 누르고 들어간 뒤까지 받는 양은 휴대폰 768KB로 2차와 같고, 누른 뒤 들어가기까지는 0.13초에서 0.17초로 조금 늘었다. 그래도 첫 방문에서 사람이 보는 것은 로딩 화면이니, 그 화면이 빨리 뜨는 쪽이 낫다.

E2E 하나가 깨졌다. 설정을 바꾸고 "지금 새로고침"을 누른 뒤 Safari 탭을 확인하던 시험인데, 전에는 로딩 화면 뒤에 바탕화면이 이미 그려져 있었다. 이제는 로딩 화면을 누르고 기다리게 고쳤다. 누르기 전에는 바탕화면이 없는지, 스크립트를 받는 동안 첫 그림을 눌러도 들어가는지 보는 시험 두 개를 더했다.

3차의 받는 양은 로딩 화면을 누르기 전까지다. 운영 사이트에서도 1차를 배포한 뒤 휴대폰이 53점에서 73점(LCP 31.5초 → 7.1초), 데스크톱이 60점에서 89점(LCP 5.8초 → 2.1초)이 되었다. 휴대폰을 브라우저에서 실제로 느리게 하면 3차는 92점, FCP·LCP 1.2~2.7초였다. 숫자를 어떻게 읽어야 하는지는 [성능 측정 리포트](/memo/site-performance-report)에 적었다.

휴대폰 점수는 5번 중 87이 셋, 78이 둘로 갈렸다. 78일 때는 React가 다시 그린 시작 안내가 LCP로 잡혔는데, 왜 가끔만 그런지는 아직 모른다. 누른 뒤에 받는 것 중 큰 것은 Font Awesome solid 글꼴(117KB)이다. 쓰는 모양만 남기면 줄겠지만, 프로젝트 내용(서버)에서 아이콘 이름을 고를 수 있어 어떤 모양을 쓸지 빌드할 때 다 알 수 없다.
