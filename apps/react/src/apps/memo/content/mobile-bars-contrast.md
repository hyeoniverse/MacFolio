휴대폰 화면의 상태 표시줄(시각, 신호, Wi-Fi, 배터리)과 하단의 홈 인디케이터는 어떤 배경 위에서도 보여야 한다. 어두운 배경에서는 흰색, 밝은 배경에서는 검은색이다.

![밝은 배경화면과 어두운 배경화면의 상태 표시줄](./images/mobile-bars-contrast-home.jpg '수정 후 화면. 밝은 배경화면에서는 시계·아이콘이 검은색, 어두운 배경화면에서는 흰색이다. 홈 인디케이터는 각자 하단 배경을 샘플링해 두 경우 모두 흰색이다')

## 배경

휴대폰 화면(390×844)에서 두 가지 경우를 재현했다.

| 재현 조건                                    | 증상                                                        |
| -------------------------------------------- | ----------------------------------------------------------- |
| 상단이 밝은 배경화면으로 바꾸고 홈 화면 표시 | 시계와 배터리가 흰 바탕 위 흰 글자로 보이지 않음            |
| 라이트 모드에서 날씨 앱을 밤 장소로 열기     | 홈 인디케이터가 짙은 남색 위 짙은 회색으로 거의 보이지 않음 |

홈 인디케이터는 홈으로 돌아가는 조작 위치를 표시하는 요소라, 보이지 않으면 휴대폰 화면을 처음 사용하는 방문자가 앱을 닫는 방법을 찾지 못한다.

## 보이지 않던 경우

앱 위의 상태 표시줄은 이미 뒤에 렌더링된 화면을 조회해 글자색을 결정하고 있었다(`statusBarTone.ts`, [셸 공통 CSS 변수로 휴대폰 앱의 바탕·카드·제목 막대를 iOS 스타일로 맞추기](/memo/mobile-apps-ios-style) 참고). 막대 아래 세 지점의 요소를 찾아 바탕색을 조회하고, 평균 휘도가 0.4보다 낮으면 흰 글자다. 누락된 경우가 세 가지 있었다.

- **홈 화면의 상태 표시줄**은 조회하지 않고 항상 흰색이었다. iOS 14·18 배경화면의 라이트 버전처럼 상단이 밝은 배경화면에서는 흰 바탕에 흰 글자였다.
- **홈 인디케이터**는 앱 위에서는 화면 모드의 글자색(`--color-text`), 홈 화면에서는 반투명 흰색이었다. 라이트 모드에서 날씨 앱의 밤하늘을 열면 짙은 남색 위에 짙은 회색 막대였다.
- **이미지는 조회하지 못했다.** 바탕색과 그라데이션만 조회해서, 배경화면(`background: url(...) center / cover`)이나 사진 위에서는 색을 알 수 없었다.

검토한 방법은 세 가지다.

| 방법                                                                                                                      | 장점                          | 단점                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------- |
| [`mix-blend-mode: difference`](https://developer.mozilla.org/en-US/docs/Web/CSS/mix-blend-mode)로 바탕의 반전 색을 렌더링 | 조회 코드가 없다              | 중간 밝기 바탕에서 회색이 되어 대비가 더 낮아진다. iOS처럼 흰색·검은색 중 하나가 아니다 |
| 글자 주변에 반대 색 그림자(`drop-shadow`) 적용                                                                            | 섞인 바탕에서도 윤곽이 남는다 | 글자 윤곽이 번진다. 한 번 적용했다가 제거했다 (아래)                                    |
| **뒤의 화면을 조회해 흰색·검은색 중 선택 (선택)**                                                                         | iOS와 같은 결과               | 이미지·iframe을 조회하는 코드가 필요하다                                                |

앱 위의 상태 표시줄에 이미 세 번째 방식이 구현되어 있었으므로, 적용 범위를 홈 화면·홈 인디케이터·이미지까지 넓혔다.

## 이미지의 해당 위치 픽셀 샘플링

이미지를 한 번만 폭 64px로 축소해 캔버스에 렌더링하고, 픽셀 데이터를 이미지 URL별로 캐시한다. 막대 아래 한 점이 이미지의 어느 픽셀에 해당하는지는 `background-size`·[`object-fit`](https://developer.mozilla.org/en-US/docs/Web/CSS/object-fit)에 따라 계산한다. 배경화면은 `cover`라서, 넘친 쪽은 가운데를 기준으로 잘린다.

```ts
export function imageRect(box, image, fit) {
	if (fit !== 'cover' && fit !== 'contain') return { x: 0, y: 0, width: box.width, height: box.height };
	const scales = [box.width / image.width, box.height / image.height];
	const scale = fit === 'cover' ? Math.max(...scales) : Math.min(...scales);
	const width = image.width * scale;
	const height = image.height * scale;
	return { x: (box.width - width) / 2, y: (box.height - height) / 2, width, height };
}
```

해당 위치 주변 3×3 픽셀의 평균을 그 점의 색으로 사용한다. 다른 출처의 이미지는 [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/CORS) 헤더가 없으면 캔버스가 오염(tainted)되어 [`getImageData`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getImageData)가 예외를 던지므로[^tainted], 이 경우에는 이전처럼 화면 모드를 따른다. 홈 화면의 유리 위젯처럼 반투명한 바탕은 그 아래 색과 알파 합성해 계산한다.

홈 인디케이터도 같은 함수로 자기 뒤의 색을 조회한다. 다른 앱에 가려진 앱의 인디케이터는 조회하지 않는다.

## 휘도 0.4 대신 대비로 선택

이미지를 조회하자 셀로시아 배경화면 왼쪽 위의 회갈색 위에서 흰 시계의 대비가 낮았다. 휘도가 약 0.3이라 0.4 기준으로는 흰색이 선택된다. 그런데 [WCAG 대비율](https://www.w3.org/TR/WCAG21/#dfn-contrast-ratio)[^contrast]을 계산하면 흰 글자는 약 3이고, 검은 글자(#1c1c1e)는 5가 넘는다. 두 색의 대비가 같아지는 지점은 휘도 약 0.2다.

그래서 흰색과 검은색 중 바탕과의 평균 대비가 더 큰 쪽을 선택한다. 휘도가 아니라 대비를 평균하므로, 샘플 대부분이 어둡고 한 곳만 밝으면 흰색이 선택된다.

대비만 비교하면 iOS 파랑(`#3b82f6`, 휘도 0.235) 위에서도 검은색이 근소하게 높다. iOS는 이런 파랑 위에 흰 글자를 사용하고, 이 사이트의 파란 헤더도 마찬가지다. 흰색 대비에 1.3배 가중치(`WHITE_BIAS`)를 곱해 전환 지점을 휘도 약 0.24로 옮겼다. 결과적으로 파랑은 흰색, 회갈색과 베이지는 검은색이다.

```ts
const WHITE_BIAS = 1.3;

export function toneFor(colors: (string | null)[]): StatusBarTone | null {
	const values = colors.map((color) => (color ? parseColor(color) : null)).filter((rgb) => rgb !== null);
	if (values.length === 0) return null;
	const average = (target: number) =>
		values.reduce((sum, rgb) => sum + contrast(luminance(rgb), target), 0) / values.length;
	return average(WHITE_LUMINANCE) * WHITE_BIAS >= average(DARK_LUMINANCE) ? 'light' : 'dark';
}
```

이 글을 수정하면서 몇 가지 바탕에 대해 WCAG 대비를 다시 계산했다. 검은 글자는 `#1c1c1e`(휘도 0.0117)다.

| 바탕                | 휘도  | 흰 글자 대비 | ×1.3  | 검은 글자 대비 | 선택되는 색                   |
| ------------------- | ----- | ------------ | ----- | -------------- | ----------------------------- |
| iOS 파랑 `#3b82f6`  | 0.235 | 3.68         | 4.78  | 4.63           | 흰색 (가중치가 없으면 검은색) |
| 회색 `#808080`      | 0.216 | 3.95         | 5.13  | 4.31           | 흰색                          |
| 메모 바탕 `#f3f4f6` | 0.904 | 1.10         | 1.43  | 15.46          | 검은색                        |
| 다크 바탕 `#1e1e1e` | 0.013 | 16.67        | 21.67 | 1.02           | 흰색                          |

가중치가 없으면 두 대비가 같아지는 지점이 휘도 0.205, 가중치 1.3배면 0.240이다.

## 시계 쪽과 아이콘 쪽을 분리

Sky 배경화면은 상단 왼쪽이 옅은 청록, 오른쪽이 짙은 남색이다. 막대 전체를 평균하면 한 색만 선택되어, 한쪽은 대비가 부족해진다. 시계 쪽(막대 폭의 8~22%)과 아이콘 쪽(78~92%)을 따로 샘플링해 각각 색을 결정한다.

![시계 쪽과 아이콘 쪽을 따로 샘플링하고, 휘도에 따라 색을 선택하는 기준](./images/mobile-bars-contrast-sampling.svg '흰색과 검은색의 전환 지점을 휘도 0.4에서 약 0.24로 옮겼다')

막대의 글자색은 시계 쪽을 따르고, 아이콘 쪽 결과가 다르면 아이콘 영역에서만 색을 바꾼다. 앱 위의 단색 막대에서는 양쪽 결과가 항상 같으므로 이전과 동작이 같다.

### 적용했다가 제거한 반대 색 그림자

한 영역 안에서도 밝은 곳과 어두운 곳이 섞일 수 있다. 셀로시아의 아이콘 영역은 절반은 짙은 갈색, 절반은 베이지라 어느 색을 선택해도 일부의 대비가 부족하다. 그래서 처음에는 흰 글자 주변에 옅은 어두운 그림자, 검은 글자 주변에 옅은 밝은 그림자를 [`drop-shadow`](https://developer.mozilla.org/en-US/docs/Web/CSS/filter-function/drop-shadow)로 적용했다. 홈 인디케이터에도 같은 `box-shadow`를 적용했다.

같은 날 다시 확인하니 그림자 때문에 글자와 아이콘 윤곽이 번져 보였다. iOS 상태 표시줄도 단색만 사용하고 그림자를 적용하지 않는다. 시계 쪽·아이콘 쪽 분리 샘플링과 대비 기준 선택만으로 섞인 바탕에서도 대부분 판독할 수 있어서, 그림자를 제거했다(`1981a8531`, CSS 27줄 삭제).

## 시험 과정에서 발견한 문제

새 시험을 추가한 뒤 빌드의 타입 검사가 시험 파일의 `findLast`에서 실패했다(`tsconfig`의 `lib`에 포함되지 않은 메서드). 그런데 빌드 출력을 버리는 스크립트로 실행해서, 이후 시험은 이전 빌드 결과물을 대상으로 실행됐다. 상태 표시줄의 글자색이 바뀌지 않는 실패를 조사하다가, 빌드한 CSS에 새 규칙이 없는 것을 확인하고 원인을 찾았다. 이제 시험 전에 빌드 결과를 확인한다.

## 시험

| 종류                                 | 확인 항목                                                                                                                                |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 단위                                 | 대비 기준 선택(파랑은 흰색, 회갈색은 검은색), 이미지 위치 계산(cover·contain·stretch), 반투명 합성                                       |
| 화면 E2E (iPhone·Android 에뮬레이션) | 밝은 배경화면에서 시계·아이콘이 검은색, 어두운 배경화면에서 흰색, 라이트 모드 날씨 밤하늘에서 홈 인디케이터가 흰색, 메모 목록에서 검은색 |

단위 시험은 `apps/react/src/desktop/mobile/statusBarTone.test.ts`에 있다. 예: "대비가 큰 쪽: iOS 파랑 위는 흰색, 베이지·회갈색 배경화면 위는 검은색 (휘도 0.4가 아니라 대비로 가른다)", "cover: 상자를 꽉 채우고 넘친 쪽은 가운데로 자른다", "반투명한 유리 위젯은 밑의 색에 겹쳐 본다". 화면 시험은 `e2e/mobile.spec.ts`에 61줄을 추가했다. 기능 커밋(`ae35f53eb`)에서 `statusBarTone.ts`가 약 180줄 늘어 변경 규모가 가장 컸다([#228](https://github.com/hyeoniverse/MacFolio/pull/228)).

## 남은 것·정리

- 다른 출처의 이미지는 CORS 헤더가 없으면 캔버스에서 조회할 수 없어 화면 모드를 따른다. 사진 앱의 이미지처럼 같은 출처의 이미지만 정확하다.
- 샘플링 지점은 막대 아래 몇 곳이다. 아주 가는 무늬가 있는 배경화면에서는 샘플 위치에 따라 결과가 달라질 수 있다.
- 시험 실패를 조사하다가 빌드가 실패한 상태로 이전 빌드를 대상으로 시험이 실행된 것을 확인했다. 빌드 출력을 버리는 스크립트는 실패를 숨긴다. 시험 결과가 예상과 다르면 먼저 시험 대상이 최신 빌드인지 확인해야 한다.
- 흰색·검은색을 휘도 임계값 하나로 나누는 규칙은 단순하지만 중간 밝기에서 판정이 틀린다. 대비를 직접 비교하고, 디자인 관습(파랑 위의 흰 글자)은 가중치 같은 명시적인 상수로 기록하면 나중에 근거를 추적하기 쉽다.
