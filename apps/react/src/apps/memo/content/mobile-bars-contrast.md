휴대폰 화면의 상태 표시줄(시간, 신호, Wi-Fi, 배터리)과 아래의 홈 인디케이터는 어떤 배경 위에서도 보여야 한다. 어두운 배경에서는 흰색, 밝은 배경에서는 검은색이다.

## 배경

재현은 휴대폰 화면(390×844)에서 두 가지로 했다. 배경화면을 위쪽이 밝은 것으로 바꾸고 홈 화면을 보면 시계와 배터리가 흰 바탕에 흰 글자로 사라졌다. 라이트 모드에서 날씨 앱을 밤 장소로 열면 아래 홈 인디케이터가 짙은 남색 위의 짙은 회색이라 거의 보이지 않았다. 둘 다 "어디로 돌아가는지"를 알려 주는 표시라, 안 보이면 휴대폰 화면을 처음 본 사람이 길을 잃는다.

## 무엇이 안 보였나

앱 위의 상태 표시줄은 이미 밑의 화면을 읽어 글자색을 정하고 있었다(`statusBarTone.ts`). 막대 밑 세 군데의 요소를 찾아 바탕색을 읽고, 평균 휘도가 0.4보다 낮으면 흰 글자다. 빠진 곳이 셋 있었다.

- **홈 화면의 상태 표시줄**은 읽지 않고 늘 흰색이었다. iOS 14·18 배경화면의 라이트 버전처럼 위쪽이 밝은 배경화면에서는 흰 바탕에 흰 글자였다.
- **홈 인디케이터**는 앱 위에서는 화면 모드의 글자색(`--color-text`), 홈 화면에서는 반투명 흰색이었다. 라이트 모드에서 날씨 앱의 밤하늘을 열면 짙은 남색 위에 짙은 회색 막대였다.
- **그림은 읽지 못했다.** 바탕색과 그라데이션만 읽어서, 배경화면(`background: url(...) center / cover`)이나 사진 위에서는 색을 알 수 없었다.

고를 수 있는 방법은 셋이었다.

| 방법                                                   | 좋은 점                       | 문제                                                                                  |
| ------------------------------------------------------ | ----------------------------- | ------------------------------------------------------------------------------------- |
| `mix-blend-mode: difference`로 바탕의 반대 색을 그린다 | 읽는 코드가 없다              | 중간 밝기 바탕에서 회색이 되어 오히려 흐리다. iOS처럼 흰색·검은색 둘 중 하나가 아니다 |
| 글자 둘레에 반대 색 빛(`drop-shadow`)을 둔다           | 섞인 바탕에서도 윤곽이 남는다 | 글자 윤곽이 번진다. 한 번 넣었다가 뺐다 (아래)                                        |
| 밑의 화면을 읽어 흰색·검은색 가운데 고른다 (고름)      | iOS와 같은 결과               | 그림·iframe을 읽는 코드가 필요하다                                                    |

앱 위의 상태 표시줄에 이미 세 번째 방식이 있었으므로, 그것을 홈 화면·홈 인디케이터·그림까지 넓히기로 했다.

## 그림의 그 자리 화소를 읽는다

그림을 한 번만 64px 폭으로 줄여 캔버스에 그려 두고, 화소를 주소별로 기억한다. 막대 밑의 한 점이 그림의 어디에 해당하는지는 `background-size`·`object-fit`에 따라 계산한다. 배경화면은 `cover`라서, 넘친 쪽은 가운데를 기준으로 잘린다.

```ts
export function imageRect(box, image, fit) {
	if (fit !== 'cover' && fit !== 'contain') return { x: 0, y: 0, width: box.width, height: box.height };
	const scales = [box.width / image.width, box.height / image.height];
	const scale = fit === 'cover' ? Math.max(...scales) : Math.min(...scales);
	const width = image.width * scale;
	const height = image.height * scale;
	return { x: (box.width - width) / 2, y: (box.height - height) / 2, width, height };
}
```

그 자리 둘레 3×3 화소의 평균을 그 점의 색으로 본다. 다른 사이트의 그림은 CORS가 없으면 캔버스에서 읽을 수 없어서(`getImageData`가 실패한다), 그때는 전처럼 화면 모드를 따른다. 홈 화면의 유리 위젯처럼 반투명한 바탕은 그 밑의 색에 겹쳐 본다.

홈 인디케이터도 같은 함수로 자기 밑을 읽는다. 가려진 앱의 인디케이터는 읽지 않는다.

## 휘도 0.4 대신 대비로 고른다

그림을 읽자 셀로시아 배경화면 왼쪽 위의 회갈색에서 흰 시계가 흐릿했다. 휘도가 0.3쯤이라 0.4 기준으로는 흰색이다. 그런데 대비를 재 보면 흰 글자는 3 언저리이고, 검은 글자(#1c1c1e)는 5가 넘는다. 두 색의 대비가 같아지는 자리는 휘도 0.2쯤이다.

그래서 흰색과 검은색 가운데 바탕과의 평균 대비가 더 큰 쪽을 고른다. 휘도를 평균하지 않고 대비를 평균해서, 대부분 어둡고 한 군데만 밝으면 흰색이다.

대비만 보면 iOS 파랑(`#3b82f6`, 휘도 0.235) 위에서도 검은색이 근소하게 앞선다. iOS는 그런 파랑 위에 흰 글자를 쓰고, 이 사이트의 파란 머리 막대도 그렇다. 흰색에 1.3배 덤을 줘서 갈리는 자리를 휘도 0.24쯤으로 옮겼다. 파랑은 흰색, 회갈색과 베이지는 검은색이다.

```ts
const WHITE_BIAS = 1.3;

export function toneFor(colors: (string | null)[]): StatusBarTone | null {
	const values = colors.map((color) => (color ? parseColor(color) : null)).filter((rgb) => rgb !== null);
	if (values.length === 0) return null;
	const average = (target: number) =>
		values.reduce((sum, rgb) => sum + contrast(luminance(rgb), target), 0) / values.length;
	return average(WHITE_LUMINANCE) * WHITE_BIAS >= average(DARK_LUMINANCE) ? 'light' : 'dark';
}
```

이 글을 고치며 몇 가지 바탕에 대해 WCAG 대비를 다시 계산해 봤다. 검은 글자는 `#1c1c1e`(휘도 0.0117)다.

| 바탕                | 휘도  | 흰 글자 대비 | ×1.3  | 검은 글자 대비 | 고르는 색                 |
| ------------------- | ----- | ------------ | ----- | -------------- | ------------------------- |
| iOS 파랑 `#3b82f6`  | 0.235 | 3.68         | 4.78  | 4.63           | 흰색 (덤이 없으면 검은색) |
| 회색 `#808080`      | 0.216 | 3.95         | 5.13  | 4.31           | 흰색                      |
| 메모 바탕 `#f3f4f6` | 0.904 | 1.10         | 1.43  | 15.46          | 검은색                    |
| 다크 바탕 `#1e1e1e` | 0.013 | 16.67        | 21.67 | 1.02           | 흰색                      |

덤이 없으면 두 대비가 같아지는 자리가 휘도 0.205, 덤 1.3배면 0.240이다.

## 시계 쪽과 아이콘 쪽을 따로

Sky 배경화면은 위쪽이 왼쪽은 옅은 청록, 오른쪽은 짙은 남색이다. 막대 전체를 평균하면 한 색이 나와서, 어느 한쪽은 묻힌다. 시계 쪽(막대 폭의 8~22%)과 아이콘 쪽(78~92%)을 따로 읽어 각각 색을 정한다.

![시계 쪽과 아이콘 쪽을 따로 읽고, 휘도에 따라 색을 고르는 기준](./images/mobile-bars-contrast-sampling.svg '흰색과 검은색이 갈리는 자리를 휘도 0.4에서 0.24쯤으로 옮겼다')

막대의 글자색은 시계 쪽을 따르고, 아이콘 쪽만 다르면 아이콘에서 바꾼다. 앱 위의 한 가지 색 막대에서는 양쪽이 늘 같으니 전과 똑같다.

### 넣었다가 뺀 반대 색 빛

한 덩어리 안에서도 밝고 어두운 곳이 섞일 수 있다. 셀로시아의 아이콘 자리는 반은 짙은 갈색, 반은 베이지라 어느 색을 골라도 일부가 묻힌다. 그래서 처음에는 흰 글자 둘레에 옅게 어두운, 검은 글자 둘레에 옅게 밝은 `drop-shadow`를 줬다. 홈 인디케이터에도 같은 `box-shadow`를 줬다.

같은 날 다시 보니 빛이 글자와 아이콘 윤곽을 번지게 했다. iOS 상태 표시줄도 한 가지 색만 쓰고 둘레에 빛을 두지 않는다. 시계 쪽·아이콘 쪽을 따로 읽고 대비로 고르는 것만으로 섞인 바탕도 대부분 읽혀서, 빛을 뺐다(`1981a8531`, CSS 27줄 삭제).

## 시험하다 걸린 것

새 시험을 더한 뒤 빌드의 타입 검사가 시험 파일의 `findLast`에서 실패했다(설정한 lib에 없다). 그런데 빌드 출력을 버리고 있어서, 그 뒤의 시험은 앞선 빌드를 대상으로 돌았다. 상태 표시줄의 글자색이 바뀌지 않는다는 실패를 쫓다가, 빌드한 CSS에 새 규칙이 없는 것을 보고 알았다. 이제 시험 전에 빌드 결과를 확인한다.

## 시험

- 단위: 대비로 고르기(파랑은 흰색, 회갈색은 검은색), 그림 자리 계산(cover·contain·늘이기), 반투명 겹치기
- 화면 E2E(iPhone·Android 흉내): 밝은 배경화면에서 시계·아이콘이 검은색, 어두운 배경화면에서 흰색, 라이트 모드의 날씨 밤하늘에서 홈 인디케이터가 흰색, 메모 목록에서 검은색

단위 시험은 `apps/react/src/desktop/mobile/statusBarTone.test.ts`에 있다. 예: "대비가 큰 쪽: iOS 파랑 위는 흰색, 베이지·회갈색 배경화면 위는 검은색 (휘도 0.4가 아니라 대비로 가른다)", "cover: 상자를 꽉 채우고 넘친 쪽은 가운데로 자른다", "반투명한 유리 위젯은 밑의 색에 겹쳐 본다". 화면 시험은 `e2e/mobile.spec.ts`에 61줄을 더했다. 기능 커밋(`ae35f53eb`)에서 `statusBarTone.ts`가 180줄 가까이 늘어 가장 컸다([PR #228](https://github.com/hyeoniverse/MacFolio/pull/228)).

## 남은 것·배운 것

- 다른 사이트의 그림은 CORS 헤더가 없으면 캔버스에서 읽을 수 없어 화면 모드를 따른다. 사진 앱의 그림처럼 같은 사이트에서 오는 그림만 정확하다.
- 읽는 점은 막대 밑 몇 곳이다. 아주 가는 무늬가 있는 배경화면에서는 고른 점에 따라 결과가 달라질 수 있다.
- 시험 실패를 쫓다가 빌드가 실패한 채 이전 빌드로 시험이 돈 것을 알았다. 빌드 출력을 버리는 스크립트는 실패를 숨긴다. 시험 결과가 이상하면 먼저 시험 대상이 새 빌드인지 확인해야 한다.
- 흰색·검은색을 휘도 하나로 가르는 규칙은 단순하지만 중간 밝기에서 틀린다. 대비를 직접 비교하고, 디자인 관습(파랑 위의 흰 글자)은 덤 같은 명시적인 값으로 적어 두면 나중에 이유를 찾기 쉽다.
