## 첫 방문 성능: 세 차례 개선

이날 가장 큰 작업이다. Lighthouse로 측정한 첫 방문 성능은 휴대폰 55점(LCP 25.7초), 데스크톱 62점(LCP 5.8초)이었고, 첫 방문마다 4.9MB·9MB를 내려받았다. 원인을 하나씩 찾아 세 차례에 걸쳐 개선했다.

| 항목 (로컬, 5회 중앙값) | 휴대폰 개선 전 → 1차 → 2차 → 3차      | 데스크톱 개선 전 → 1차 → 2차 → 3차      |
| ----------------------- | ------------------------------------- | --------------------------------------- |
| Lighthouse 성능         | 55 → 68 → 69~72 → **78~87**           | 62 → 90 → 93 → **98**                   |
| FCP                     | 14.3초 → 4.0초 → 4.0초 → **3.2초**    | 2.5초 → 0.8초 → 0.8초 → **0.7초**       |
| LCP                     | 25.7초 → 6.2초 → 5.8초 → **3.2초**    | 5.8초 → 1.9초 → 1.7초 → **1.1초**       |
| 첫 방문 전송량          | 4,893KB → 1,011KB → 725KB → **483KB** | 9,050KB → 2,177KB → 1,848KB → **771KB** |

![느린 휴대폰에서 0.5초 간격으로 캡처한 첫 화면](./images/site-performance-diet-filmstrip.jpg '개선 전에는 7초 동안 검은 화면이었고, 개선 후에는 1초에 사과 로고, 2초에 시작 안내가 보인다')

### 1차 ([#319](https://github.com/hyeoniverse/MacFolio/pull/319)): 큰 것부터

| 원인                                               | 조치                                                                       | 감소량                                     |
| -------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------ |
| 본문 글꼴 TTF 한 벌 (압축 1.7MB)                   | 완성형 2,350자 `core`와 나머지 한글 `ext`의 woff2 두 조각, `unicode-range` | 1.7MB → 149KB                              |
| 블로그 글 199편의 원문이 첫 번들에 포함            | 글 목록을 처음 조회하는 시점에 `import()`                                  | 740KB                                      |
| 메모·Finder 등 일부 앱 외 모든 앱이 첫 번들에 포함 | 모든 앱을 `lazy`로                                                         | 첫 번들 250KB → 47KB (brotli)              |
| 2560px 아이콘, JPG 배경화면                        | 아이콘 256px, 배경화면 WebP                                                | 아이콘 1,171 → 428KB, 배경화면 7.9 → 2.3MB |
| 로딩 화면을 JS가 렌더링                            | `index.html`의 `#boot-splash`가 먼저 표시, 사과 로고는 SVG                 | 휴대폰 FCP 14.3 → 4.0초                    |

앱을 `lazy`로 바꾸자 셸이 앱의 CSS에 의존하던 문제가 발견됐다. 홈 인디케이터와 앱 전환기의 스타일이 `Window.css`에 있었는데, 이 CSS는 앱 창이 불러오고 있었다. 앱이 첫 번들에서 빠지자 셸이 그 스타일을 잃었다. 셸(`Desktop.tsx`)이 직접 불러오도록 수정했다. 창이 열리자마자 내용을 읽던 E2E 시험 여섯 곳도 앱이 렌더링될 때까지 기다리게 했다.

### 2차·3차 ([#323](https://github.com/hyeoniverse/MacFolio/pull/323)): 아이콘 WebP, 누른 뒤에 렌더링하는 바탕화면

- 2차: 앱 아이콘을 192px WebP로(428KB → 51KB), 앨범 그림을 512px WebP로(742KB → 146KB), 메뉴 막대의 사과 로고를 SVG 컴포넌트로 바꿔 Font Awesome brands(113KB)를 첫 화면에서 제외했다
- 3차: 로딩 화면을 누르기 전에는 바탕화면(휴대폰 홈 화면)을 렌더링하지 않는다. 휴대폰 LCP가 5.8초에서 3.2초로, 요청 수가 75개에서 49개로 줄었다. 스크립트를 내려받는 동안 먼저 누른 입력도 `window.__macfolioTapped`에 기록해 두어 손실되지 않게 했다

측정 방법도 보완했다. Lighthouse 기본값(simulate)은 네트워크를 계산으로 흉내 내서, 로컬 서버가 첫 렌더링 전에 미리 받은 JS 33개까지 첫 렌더링에 필요했다고 계산했다. 브라우저를 실제로 느리게 하는 `THROTTLING=devtools` 모드를 측정 스크립트에 추가해 두 값을 함께 기록했다. 운영 사이트도 1차 배포 전후로 측정했다(휴대폰 53 → 73점, LCP 31.5 → 7.1초).

자세한 과정은 [성능 최적화 1 - 휴대폰 LCP를 25.7초에서 3.2초로 줄인 Lighthouse 성능 측정 리포트](/memo/site-performance-report)와 [성능 최적화 2 - 글꼴 subset·lazy import·modulepreload·WebP로 첫 방문 전송량 9MB를 0.8MB로](/memo/site-performance-diet)에 정리했다.

### 시행착오

- **머지한 브랜치에 커밋을 이어서 올렸다.** #319를 머지한 뒤 같은 브랜치에 2차 커밋 셋을 push해서, 커밋이 main에 반영되지 않았다. 새 PR(#323)로 옮겼다. 10월 20일 회고에 적은 스택 PR 사고와 같은 유형이다. 머지된 브랜치에는 더 이상 push하지 않는다
- **메모 관리자 E2E가 6번 중 4번 실패했다.** 글 원문을 메모를 처음 열 때 내려받게 되면서, 목록이 채워지기 전에 폴더를 만들면 중복 이름을 감지하지 못했다. 시험이 목록이 채워진 뒤에 편집하도록 수정했다

## 위젯 기능 확장

전날 만든 위젯 8종의 기능을 확장했다.

### 사진 위젯의 영상, 메모 위젯의 세 가지 보기 ([#317](https://github.com/hyeoniverse/MacFolio/pull/317))

![영상을 재생하는 사진 위젯](./images/day-1022-photo-widget.jpg 'Finder › 그림 › 영상 폴더를 선택한 사진 위젯. 영상은 음소거 상태로 재생되고, 오른쪽 아래에 일시 정지와 소리 버튼이 있다')

- **사진 위젯:** 그림만 표시하던 위젯이 영상도 재생한다. 브라우저 자동 재생 정책상 음소거 상태여야 자동으로 재생되므로 기본은 음소거다. 그림은 10초 후, 영상은 재생이 끝나는 시각에 다음 항목으로 넘어간다. GIF는 `<img>`에서 직접 멈출 수 없어서, 일시 정지하면 현재 프레임을 캔버스에 그려 덮는다
- **메모 위젯:** 최근 글·인기글·랜덤 중 하나를 고른다. 인기글 점수(조회 1, 좋아요 3, 댓글 5점)는 메모 앱 사이드바와 같은 함수(`popularPosts`)로 계산한다. 전체 글 목록은 인기글·랜덤 위젯이 있을 때만 `import()`로 불러와 첫 화면 크기는 그대로다
- **사진 앱:** 사진 위젯은 Finder › 그림의 폴더를 읽는데 사진 앱은 읽지 않아서, 위젯에는 있는 앨범이 앱에는 없었다. 두 곳이 같은 함수(`folderSources`)로 읽게 했다

![최근 글·인기글·랜덤으로 설정한 메모 위젯 세 개](./images/day-1022-memo-widgets.jpg '같은 메모 위젯을 각각 최근 글·인기글·랜덤으로 설정한 바탕화면. 머리띠의 아이콘과 이름으로 구분한다')

### 명언 위젯과 화면 간 설정 공유 ([#330](https://github.com/hyeoniverse/MacFolio/pull/330))

![명언 위젯](./images/day-1022-quote-widget.jpg '원문, 번역, 출처를 표시한다. 빈 곳을 누르면 다른 명언으로 바뀐다')

개발·디자인에 관한 짧은 명언 위젯을 만들었다. 출처가 널리 알려진 말만, 작은 위젯에 들어가도록 120자 이하로 골랐다. 날마다(서울 기준) 다음 명언으로 넘어가고, 누르면 무작위로 다른 명언을 표시한다. 이날 밤 69개, 124개로 늘렸고, 다음 날 아침 365개로 늘려 1년 동안 겹치지 않게 했다.

처음에는 위젯 판 전체를 버튼으로 만들었는데, 그러면 위젯을 끌어서 옮길 수 없었다. 위젯 끌기와 오른쪽 클릭 메뉴는 버튼 위에서 시작하지 않기 때문이다. 다른 위젯처럼 빈 곳을 누르면 동작하게 하고, 키보드용으로 오른쪽 위에 별도 버튼을 배치했다.

같은 PR에서 사진 위젯의 설정 저장 방식도 수정했다. 바탕화면 위젯과 휴대폰 위젯은 배치를 따로 저장하는데, 선택한 앨범도 그 안에 들어 있어서 바탕화면에서 고른 앨범이 휴대폰에는 반영되지 않았다. 같은 id·종류의 위젯은 선택값을 두 화면이 공유하게 했다(`widgets/sharedOptions.ts`).

### 아이폰 Safari에서만 각진 음악 위젯

음악 위젯의 배경은 앨범 표지에 `filter: blur`를 적용한 `::before` 레이어다. 아이폰 Safari는 이 레이어를 별도로 합성해서, 부모의 `overflow: hidden` + `border-radius`로 잘리지 않았다. 같은 둥근 모양을 `clip-path: inset(0 round …)`로 한 번 더 지정했다. 맥 Safari와 Playwright WebKit에서는 재현되지 않았다. 원인과 해결 방법은 [iOS Safari의 filter 합성 레이어에서 빠지는 border-radius 클리핑과 clip-path](/memo/music-widget-ios-corners)에 정리했다.

## 검색어 탭과 분석

### 검색어 탭 ([#327](https://github.com/hyeoniverse/MacFolio/pull/327))

유입 경로에는 `www.google.com`만 남고 무엇을 검색했는지는 알 수 없었다. Google·Bing은 브라우저가 호스트만 전달하기 때문이다. 두 경로를 함께 쓴다.

1. **방문의 검색어:** 검색엔진이 주소에 검색어를 포함할 때만(네이버 `query`, 다음 `q` 등) 그 값 하나를 읽어 방문 이벤트에 `searchTerm`으로 보낸다
2. **Google Search Console:** 서버가 6시간마다 서비스 계정으로 날짜·검색어·페이지별 노출·클릭·평균 순위를 가져와 저장한다. `googleapis` 패키지 없이 JWT(RS256)를 `node:crypto`로 서명한다

![검색어 탭](./images/search-keywords-tab.jpg '활동 상태 보기의 검색어 탭. Search Console의 검색어·페이지 표와 검색엔진이 전달한 검색어를 함께 표시한다')

검색어 수집이 추가되어 개인정보 문서의 "유입 경로의 경로와 검색어는 수집하지 않는다"를 수정했다. 과정은 [리퍼러 검색어와 Search Console API로 유입 검색어 수집하기](/memo/search-keywords)에 정리했다.

### Safari가 분석 이벤트 응답을 취소하던 문제 ([#320](https://github.com/hyeoniverse/MacFolio/pull/320))

Safari 콘솔에 5초마다 같은 오류가 3줄씩 쌓였다. 분석 이벤트 전송 주기와 같았다.

![CORP 헤더 전후 흐름](./images/day-1022-corp.svg 'API는 helmet 기본값으로 모든 응답에 CORP same-origin을 붙인다. 사이트와 API의 출처가 달라 Safari가 sendBeacon 응답을 취소했다')

API는 `helmet()` 기본값을 써서 모든 응답에 `Cross-Origin-Resource-Policy: same-origin`이 붙는다. CORS는 허용 목록으로 통과했지만, CORP는 별개의 검사다. Safari는 sendBeacon(no-cors) 응답에도 CORP를 적용해서 출처가 다르면 응답을 취소한다. `POST /analytics/events` 한 경로에만 `cross-origin`을 지정했다. 응답이 본문 없는 204라 다른 출처에 전달해도 노출되는 정보가 없다.

Chrome에서는 같은 오류가 발생하지 않아 그동안 발견하지 못했다. Safari 방문이 집계에서 빠져 있었는지는 확인하지 못했고, 배포 후 Safari 방문 수의 변화로 확인할 예정이다.

## 앱 수정

### 최소화 후 다시 열면 휴대폰 모양이 되던 메모 ([#324](https://github.com/hyeoniverse/MacFolio/pull/324))

![최소화 후 다시 연 메모](./images/day-1022-memo-compact.jpg '창 폭이 898px인데도 폴더 → 목록 → 본문을 한 칸씩 표시하는 휴대폰 모양으로 열렸다')

메모는 `ResizeObserver`로 칸의 폭을 측정해 700px 이하면 한 칸씩 표시한다. 창을 최소화하면 창 틀(`AppWindow`)만 `null`을 렌더링하고, 폭을 측정하는 훅이 있는 `Memo` 컴포넌트는 그대로 남는다.

```text
열기       칸 A 생성 → useEffect([ref])가 A를 관찰 → 898px
최소화     칸 A만 제거 → 관찰 중인 A의 폭 0 → compact
다시 열기  칸 B 생성 → ref 객체가 같아 effect가 다시 실행되지 않음
           → B를 관찰하지 않음 → 폭 0 유지 → 넓은 창에 휴대폰 모양
```

`useEffect(..., [ref])`는 ref **객체**가 바뀔 때만 다시 실행된다. 객체는 그대로이고 안의 요소만 바뀌어서 새 칸을 관찰하지 못했다. 요소를 붙이는 함수(`attach`)로 받아 요소가 바뀔 때마다 state가 바뀌게 하는 `useElementWidth` 훅을 만들었다. 같은 방식을 쓰던 날씨·사진 앱도 함께 수정했다.

### 바탕화면 보기 ([#326](https://github.com/hyeoniverse/MacFolio/pull/326))

macOS Sonoma의 "배경화면을 클릭하여 데스크탑 보기"를 구현했다. 바탕화면 빈 곳을 누르면 떠 있는 창이 모두 가까운 왼쪽·오른쪽 가장자리로 이동하고 40px만 남는다.

![창이 양쪽 가장자리로 이동한 바탕화면](./images/day-1022-reveal-desktop.jpg '바탕화면을 누르면 창이 가장자리로 이동하고 위젯과 아이콘이 드러난다. 다시 누르거나 남은 창 가장자리를 누르면 돌아온다')

창은 `left`·`top`이 아니라 CSS `translate`로 이동해서, 열기·닫기 애니메이션(`transform`)과 창 끌기에 영향을 주지 않는다. 바탕화면을 끌어 아이콘을 선택하는 동작은 창을 이동시키지 않는다.

### 그 밖의 수정

- [#315](https://github.com/hyeoniverse/MacFolio/pull/315): 음량 창 위에 겹친 투명한 range 입력의 길이(9rem)가 보이는 칸(6rem)보다 길어서, 맨 위를 눌러도 91%에서 멈췄다. 칸 전체가 포인터 입력을 받아 누른 높이 그대로 음량을 정한다

## 같은 날 글의 순서 ([#331](https://github.com/hyeoniverse/MacFolio/pull/331))

같은 날짜의 글을 아침부터 밤까지 차례로 올리면, 메모 목록에서는 올린 순서가 아니라 제목 순으로 정렬됐다. 머리말의 `date`에 날짜만 있고, 정렬 함수가 날짜 다음에 바로 제목을 비교했기 때문이다.

![같은 날 글 순서 전후](./images/day-1022-same-day-order.jpg '왼쪽은 제목 순, 오른쪽은 올린 시각 순. 가장 나중에 올린 글이 맨 위에 온다')

날짜와 제목 사이에 **올린 시각**을 비교 기준으로 추가했다. 저장소 글은 빌드 시점에 git에서 처음 추가된 커밋의 시각을 읽고, 서버 글은 DB의 시각을 쓴다. 이날은 서버 글의 기준을 글을 처음 만든 시각으로 했고, 다음 날 게시 순서와 일치하도록 **처음 게시한 시각**(`firstPublishedAt`)으로 변경해 머지했다.

## Finder의 저장소 문서 목록

README와 `docs/` 문서의 영어판(`README.en.md`, `docs/en/`)을 추가한 [#329](https://github.com/hyeoniverse/MacFolio/pull/329)에서 Finder의 문제를 발견했다. Finder는 저장소 문서를 `README.md`, `docs/*.md`처럼 **파일 이름을 나열해** 번들에 넣고 있어서, 새 파일(`README.en.md`)과 하위 폴더(`docs/en/`)가 빠졌다. glob을 `README*.md`, `docs/**/*.md`로 바꿔 새 문서를 별도로 등록하지 않아도 포함되게 했다.

## 돌아보며

**Safari에서만 생긴 문제가 셋이었다.** 분석 이벤트의 CORP, 아이폰의 음악 위젯 모서리, 그리고 다음 날 발견한 맥 Safari의 표 정렬 문제다. 셋 다 Chromium과 Playwright WebKit의 자동 시험으로는 재현되지 않았다. 자동 시험이 통과해도 실제 Safari에서 콘솔과 화면을 확인하는 단계를 배포 후 점검에 넣어야 한다. 점검할 렌더링 차이는 [macOS Safari와 iOS Safari의 렌더링 차이](/memo/safari-macos-ios-rendering)에 정리했다.

**성능을 개선한 같은 날 밤에 첫 번들이 다시 커졌다.** 명언 위젯이 명언 데이터를 첫 번들에 포함시켜, `boot` 번들이 47KB에서 65KB로 늘었다. 다음 날 재측정에서 발견해 명언 위젯을 `lazy`로 분리했다([성능 재측정](/memo/site-performance-remeasure)). 수동 측정만으로는 회귀를 늦게 발견한다. 첫 번들 크기를 CI에서 검사하는 기준(예: brotli 50KB 상한)이 필요하다.

**ref 객체를 의존성으로 둔 effect**는 메모·날씨·사진 세 곳에 같은 형태로 있었다. 한 곳에서 발견한 패턴은 저장소 전체에서 검색해 함께 수정하는 것이 효과적이었다.
