데이터베이스 기초 연재의 마지막 글로, 개념적 설계와 논리적 설계 실습을 다룬다. [앞 글](/memo/db-er-model)의 E-R 모델로 회사 데이터베이스를 개념적으로 설계하고, 그 결과를 관계 데이터 모델의 릴레이션으로 바꾼 뒤 Oracle DDL로 구현한다.

## 요구사항

1. 회사에는 여러 사원이 재직한다. 사원마다 사원번호(고유), 이름, 직책, 급여, 주소를 저장한다. 주소는 시, 구, 동으로 나눈다.
2. 사원은 0명 이상의 부양가족을 가진다. 한 부양가족은 두 명 이상의 사원에게 속하지 않는다. 부양가족마다 이름과 성별을 저장한다.
3. 회사는 여러 프로젝트를 진행한다. 프로젝트마다 프로젝트번호(고유), 이름, 예산, 진행 위치를 저장한다. 한 프로젝트는 여러 위치에서 진행될 수 있다.
   - 프로젝트마다 여러 사원이 일하고, 사원은 여러 프로젝트에서 일할 수 있다. 사원이 프로젝트에서 맡은 역할과 근무 기간을 저장한다.
   - 프로젝트마다 관리자가 한 명 있고, 한 사원은 두 개 이상의 프로젝트를 관리할 수 없다. 관리자가 임무를 시작한 날짜를 저장한다.
4. 사원은 한 부서에만 속한다. 부서마다 부서번호(고유), 이름, 부서가 위치한 층을 저장한다.
5. 프로젝트에는 부품이 필요하고, 한 부품을 여러 프로젝트에서 쓸 수 있다. 부품마다 부품번호(고유), 이름, 가격을 저장하고, 다른 부품을 포함하는 부품이면 포함된 부품의 정보도 저장한다.
6. 부품을 공급하는 공급자가 있다. 한 공급자는 여러 부품을, 한 부품은 여러 공급자에게서 공급받을 수 있다. 공급자마다 공급자번호(고유), 이름, 신용도를 저장하고, 어떤 공급자가 어떤 부품을 어떤 프로젝트에 얼마나 공급하는지 저장한다.

## 개념적 설계: E-R 다이어그램

데이터는 세 개의 세계를 거쳐 데이터베이스에 들어간다. ==현실 세계를 추상화해 개념적 구조를 만드는 과정이 개념적 모델링이고, 개념적 구조를 DBMS가 지원하는 논리적 구조로 변환하는 과정이 데이터 모델링이다.==

| 세계        | 대상                | 구성 요소             | 다음 세계로 가는 과정 |
| ----------- | ------------------- | --------------------- | --------------------- |
| 현실 세계   | 개체                | 개체, 특성, 값        | 추상화(개념적 모델링) |
| 개념 세계   | 개념(개념적 구조)   | 개체 타입, 속성, 값   | 변환(데이터 모델링)   |
| 컴퓨터 세계 | 데이터(논리적 구조) | 레코드 타입, 필드, 값 |                       |

요구사항에서 개체 타입, 관계 타입, 애트리뷰트를 찾는다.

| 요구사항 | 개체 타입            | 관계 타입                         | 판단 근거                                                                             |
| -------- | -------------------- | --------------------------------- | ------------------------------------------------------------------------------------- |
| 1        | 사원                 |                                   | 사원번호가 키. 주소는 복합 애트리뷰트                                                 |
| 2        | 부양가족 (약한 개체) | 부양 (1:n, 식별 관계)             | 부양가족은 자기 애트리뷰트만으로 식별할 수 없고 사원이 있어야 존재한다. 이름이 구별자 |
| 3        | 프로젝트             |                                   | 위치는 다중 값 애트리뷰트                                                             |
| 3        |                      | 근무 (사원 m : 프로젝트 n)        | 역할, 근무 기간은 관계의 애트리뷰트                                                   |
| 3        |                      | 관리 (사원 1 : 프로젝트 1)        | 프로젝트는 관리자가 반드시 있으므로 전체 참여. 시작 날짜는 관계의 애트리뷰트          |
| 4        | 부서                 | 소속 (부서 1 : 사원 n)            |                                                                                       |
| 5        | 부품                 | 포함 (부품 1 : 부품 n, 순환 관계) | 한 부품이 여러 하위 부품을 포함한다                                                   |
| 5, 6     | 공급자               | 공급 (프로젝트·부품·공급자 3진)   | 공급량은 세 개체가 모두 정해져야 의미가 있다                                          |

![회사 데이터베이스의 E-R 다이어그램](./images/db-er-to-relational-company.svg '개체 타입 6개와 관계 타입 6개. 애트리뷰트는 생략했다')

공급처럼 세 개 이상의 개체 타입이 참여하는 관계를 다중 관계(다원 관계)라 한다. "프로젝트에 부품이 필요하다"를 프로젝트-부품 2진 관계로 따로 두지 않은 이유는, 요구사항 6의 공급이 이미 프로젝트와 부품을 연결하기 때문이다. ==공급량은 (공급자, 부품, 프로젝트) 조합마다 정해지므로 2진 관계 세 개로 나누면 표현할 수 없다.==

## 논리적 설계: 7단계 사상

E-R 스키마에는 개체 타입과 관계 타입이 따로 있지만, ==관계 데이터베이스에는 개체 타입과 관계 타입의 구분 없이 릴레이션만 있다.== 그래서 사상할 대상이 정규 개체 타입인지 약한 개체 타입인지, 2진 관계인지 3진 이상의 관계인지, 애트리뷰트가 단일 값인지 다중 값인지에 따라 사상 방법이 달라진다. 이 규칙을 7단계 알고리즘으로 적용한다. 각 단계의 결과에서 밑줄 대신 `PK`, `FK`로 키를 표시한다.

3\~6단계에서 관계 타입의 애트리뷰트를 릴레이션에 넣을 때, 복합 애트리뷰트이면 1단계와 같이 그것을 구성하는 단순 애트리뷰트만 넣는다.

![사상할 대상(개체 타입·2진 관계·3진 관계·다중값 애트리뷰트)과 알고리즘 단계 1~7 대응표](./images/db-er-to-relational-note-10.jpg '사상할 대상(개체 타입·2진 관계·3진 관계·다중값 애트리뷰트)과 알고리즘 단계 1~7 대응표 (강의 자료)')

### 1단계: 정규 개체 타입

- 정규(강한) 개체 타입 E마다 릴레이션 R을 만든다.
- E의 단순 애트리뷰트를 모두 R에 넣는다.
- 복합 애트리뷰트는 그것을 구성하는 단순 애트리뷰트만 넣는다.
- E의 키가 R의 기본 키가 된다.

```text
사원     (사원번호 PK, 이름, 직책, 급여, 시, 구, 동)
부서     (부서번호 PK, 이름, 층)
프로젝트 (프로젝트번호 PK, 이름, 예산)
부품     (부품번호 PK, 이름, 가격)
공급자   (공급자번호 PK, 이름, 신용도)
```

주소는 복합 애트리뷰트라 시, 구, 동으로 들어간다. 프로젝트의 위치는 다중 값이라 7단계에서 처리한다.

![개체 E1(PK, A)을 릴레이션 E1(PK, A)로 옮기는 사상 도식](./images/db-er-to-relational-note-11.jpg '개체 E1(PK, A)을 릴레이션 E1(PK, A)로 옮기는 사상 도식 (강의 자료)')

### 2단계: 약한 개체 타입

- 주 개체 타입 E를 갖는 약한 개체 타입 W마다 릴레이션 R을 만들고, W의 단순 애트리뷰트를 모두 넣는다.
- 주 개체 릴레이션의 기본 키를 R에 외래 키로 넣는다.
- ==R의 기본 키는 그 외래 키와 W의 부분 키(구별자)의 조합이다.==

```text
부양가족 (사원번호 PK·FK → 사원, 이름 PK, 성별)
```

부양가족 이름은 사원마다 겹치지 않으면 되므로, {사원번호, 이름}이 기본 키다.

![E1(1)-식별 관계 R-약한 개체 E2(N, 부분 키 K)를 E1(PK1,A1)과 E2(FK1,K,A2)로 옮기는 사상 도식](./images/db-er-to-relational-note-12.jpg 'E1(1)-식별 관계 R-약한 개체 E2(N, 부분 키 K)를 E1(PK1,A1)과 E2(FK1,K,A2)로 옮기는 사상 도식 (강의 자료)')

### 3단계: 2진 1:1 관계

1:1 관계 R에 참여하는 두 릴레이션 S, T 가운데 하나(S)를 골라, T의 기본 키를 S에 외래 키로 넣고 R의 애트리뷰트도 S에 넣는다. ==**관계에 전체 참여하는 쪽을 S로 고른다.**== 관리 관계를 사상하는 방법을 비교하면 다음과 같다.

| 방법                  | 결과                                           | 평가                                                                         |
| --------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------- |
| 1. 프로젝트에 외래 키 | `프로젝트(…, 관리자사원번호 FK, 시작날짜)`     | 프로젝트는 모두 관리자가 있어(전체 참여) 널이 생기지 않는다. 채택            |
| 2. 사원에 외래 키     | `사원(…, 관리프로젝트번호 FK, 시작날짜)`       | 관리자가 아닌 사원이 대부분이라 널이 많이 생긴다                             |
| 3. 관계 릴레이션      | `관리(사원번호 FK, 프로젝트번호 FK, 시작날짜)` | 동작하지만 조인이 하나 늘어난다                                              |
| 4. 하나로 병합        | 사원과 프로젝트를 한 릴레이션으로              | 두 개체가 모두 전체 참여할 때만 가능하다. 여기서는 사원이 부분 참여라 부적합 |

```text
프로젝트 (프로젝트번호 PK, 이름, 예산, 관리자사원번호 FK → 사원 UNIQUE, 시작날짜)
```

외래 키만 넣으면 한 사원번호가 여러 프로젝트 튜플에 나타날 수 있어 관계가 1:N이 된다. "한 사원은 두 개 이상의 프로젝트를 관리할 수 없다"를 지키려면 ==관리자사원번호에 UNIQUE 제약을 걸어 1:1을 보장한다.== 그러면 관리자사원번호도 프로젝트 릴레이션의 후보 키가 된다.

![E1-R(1:1)-E2 관계와 방법 1(E2에 FK1)·방법 2(E1에 FK2) 사상 결과](./images/db-er-to-relational-note-13.jpg 'E1-R(1:1)-E2 관계와 방법 1(E2에 FK1)·방법 2(E1에 FK2) 사상 결과 (강의 자료)')

![1:1 관계의 방법 3(관계 릴레이션 R(FK1,FK2) 분리)·방법 4(E1·E2를 한 릴레이션으로 합침) 사상 결과](./images/db-er-to-relational-note-14.jpg '1:1 관계의 방법 3(관계 릴레이션 R(FK1,FK2) 분리)·방법 4(E1·E2를 한 릴레이션으로 합침) 사상 결과 (강의 자료)')

### 4단계: 2진 1:N 관계

- 1:N 관계 R에서 N 쪽 릴레이션 S에, 1 쪽 릴레이션 T의 기본 키를 외래 키로 넣는다.
- R의 애트리뷰트도 S에 넣는다.

==반대로 1 쪽에 N 쪽의 기본 키를 넣으면, 부서 하나에 사원번호 여러 개가 들어가 원자 값 조건을 어기거나 부서 튜플이 사원 수만큼 중복된다.==

```text
사원 (사원번호 PK, 이름, 직책, 급여, 시, 구, 동, 소속부서번호 FK → 부서)
부품 (부품번호 PK, 이름, 가격, 상위부품번호 FK → 부품)
```

포함 관계는 부품이 자기 자신과 맺는 순환 관계다. 외래 키가 같은 릴레이션의 기본 키를 참조하며, 최상위 부품의 상위부품번호는 널이다. 한 부품이 여러 상위 부품에 들어갈 수 있다면 포함은 M:N이 되어 5단계처럼 `부품구성(상위부품번호, 하위부품번호)` 릴레이션으로 분리해야 한다.

![1:N 관계의 사상 방법 1·2와 자기 참조 1:N 관계의 사상](./images/db-er-to-relational-note-15.jpg '1:N 관계의 사상 방법 1·2와 자기 참조 1:N 관계의 사상 (강의 자료)')

### 5단계: 2진 M:N 관계

- M:N 관계 R마다 릴레이션 R을 만든다.
- 참여하는 두 릴레이션의 기본 키를 외래 키로 넣고, 그 조합을 R의 기본 키로 한다.
- R의 애트리뷰트를 넣는다.

```text
근무 (사원번호 PK·FK → 사원, 프로젝트번호 PK·FK → 프로젝트, 역할, 근무기간)
```

==M:N은 어느 한쪽에 외래 키를 넣으면 반드시 다중 값이 되므로 관계 릴레이션이 필요하다.==

![E1-R(M:N)-E2를 E1·E2와 관계 릴레이션 R(FK1,FK2)로 옮기는 사상 도식](./images/db-er-to-relational-note-16.jpg 'E1-R(M:N)-E2를 E1·E2와 관계 릴레이션 R(FK1,FK2)로 옮기는 사상 도식 (강의 자료)')

### 6단계: 3진 이상의 관계

- 3진 이상의 관계 R마다 릴레이션 R을 만든다.
- 참여하는 모든 릴레이션의 기본 키를 외래 키로 넣고, R의 애트리뷰트를 넣는다.
- 보통 외래 키 전체의 조합이 기본 키다. 참여 개체의 원소 수가 1:N:N이면, 1 쪽을 제외한 외래 키의 조합으로 기본 키를 정할 수 있다.

```text
공급 (공급자번호 PK·FK → 공급자, 부품번호 PK·FK → 부품, 프로젝트번호 PK·FK → 프로젝트, 공급량)
```

![E1·E2·E3의 3진 관계 R을 N:N:N이면 FK1·FK2·FK3 전체가 키, 1:N:N이면 FK2·FK3가 키인 R(…, A)로 옮기는 두 사상 도식](./images/db-er-to-relational-note-17.jpg 'E1·E2·E3의 3진 관계 R을 N:N:N이면 FK1·FK2·FK3 전체가 키, 1:N:N이면 FK2·FK3가 키인 R(…, A)로 옮기는 두 사상 도식 (강의 자료)')

### 7단계: 다중 값 애트리뷰트

- 다중 값 애트리뷰트마다 릴레이션 R을 만든다.
- 그 애트리뷰트와, 그 애트리뷰트를 가진 개체(관계) 릴레이션의 기본 키를 외래 키로 넣는다.
- R의 기본 키는 다중 값 애트리뷰트와 외래 키의 조합이다.

```text
프로젝트위치 (프로젝트번호 PK·FK → 프로젝트, 위치 PK)
```

![다중값 애트리뷰트 B를 가진 E1을 E1(PK1,A)과 MVA(FK1,B)로 나누는 사상 도식](./images/db-er-to-relational-note-18.jpg '다중값 애트리뷰트 B를 가진 E1을 E1(PK1,A)과 MVA(FK1,B)로 나누는 사상 도식 (강의 자료)')

## 최종 관계 스키마

| 분류      | 릴레이션                                                     | 기본 키                              | 외래 키                                  |
| --------- | ------------------------------------------------------------ | ------------------------------------ | ---------------------------------------- |
| 개체      | 사원(사원번호, 이름, 직책, 급여, 시, 구, 동, 소속부서번호)   | 사원번호                             | 소속부서번호 → 부서                      |
| 개체      | 부서(부서번호, 이름, 층)                                     | 부서번호                             |                                          |
| 개체      | 프로젝트(프로젝트번호, 이름, 예산, 관리자사원번호, 시작날짜) | 프로젝트번호                         | 관리자사원번호 → 사원 (UNIQUE)           |
| 개체      | 부품(부품번호, 이름, 가격, 상위부품번호)                     | 부품번호                             | 상위부품번호 → 부품                      |
| 개체      | 공급자(공급자번호, 이름, 신용도)                             | 공급자번호                           |                                          |
| 약한 개체 | 부양가족(사원번호, 이름, 성별)                               | {사원번호, 이름}                     | 사원번호 → 사원                          |
| 관계      | 근무(사원번호, 프로젝트번호, 역할, 근무기간)                 | {사원번호, 프로젝트번호}             | 사원번호 → 사원, 프로젝트번호 → 프로젝트 |
| 관계      | 공급(공급자번호, 부품번호, 프로젝트번호, 공급량)             | {공급자번호, 부품번호, 프로젝트번호} | 세 열 모두                               |
| 다중 값   | 프로젝트위치(프로젝트번호, 위치)                             | {프로젝트번호, 위치}                 | 프로젝트번호 → 프로젝트                  |

릴레이션 9개가 나온다. 개체 타입 6개 가운데 5개는 1단계, 약한 개체 1개는 2단계에서 릴레이션이 되었고, 관계 타입 6개 가운데 1:1(관리)과 1:N(소속, 포함)은 외래 키로 흡수되어 별도 릴레이션이 생기지 않았다. 부양은 2단계에서 부양가족 릴레이션의 외래 키가 되었고, M:N(근무)과 3진(공급)만 관계 릴레이션이 되었다.

외래 키 위치를 고르는 기준을 요약하면 다음과 같다.

| 관계          | 외래 키 위치       | 이유                                    |
| ------------- | ------------------ | --------------------------------------- |
| 1:1           | 전체 참여하는 쪽   | 널이 생기지 않는다                      |
| 1:N           | N 쪽               | 1 쪽에 넣으면 다중 값이나 중복이 생긴다 |
| M:N, 3진 이상 | 별도 관계 릴레이션 | 어느 쪽에 넣어도 다중 값이 된다         |

설계를 마친 뒤에는 각 릴레이션의 함수 종속을 확인해 [정규화](/memo/db-normalization)로 검증한다. 이 스키마는 각 릴레이션의 결정자가 모두 후보 키(프로젝트에서는 기본 키인 프로젝트번호와 UNIQUE인 관리자사원번호)라 BCNF를 만족한다.

## 실습 과제 풀이

12주차 실습에서는 회사와 서점 데이터베이스의 E-R 다이어그램을 손으로 그린 뒤 PowerPoint로 다시 그렸고, 이어서 7단계 사상으로 관계 스키마를 만들었다. 기말 과제에서는 회사 데이터베이스를 Oracle DDL로 구현하고 데이터를 넣어 검색·갱신·삭제문을 실행했다.

<summary>실습 1. 회사 데이터베이스 E-R 다이어그램</summary>

> 회사 데이터베이스 요구사항을 고려해 개념적 데이터베이스를 E-R 다이어그램으로 설계하라.

풀이는 [개념적 설계](#개념적-설계-e-r-다이어그램) 절의 표와 도식과 같다. 개체 타입은 사원, 부양가족(약한 개체), 프로젝트, 부서, 부품, 공급자의 6개이고, 관계 타입은 부양(1:N 식별 관계), 근무(M:N), 관리(1:1, 프로젝트 전체 참여), 소속(부서 1 : 사원 N), 포함(부품의 순환 1:N), 공급(공급자·부품·프로젝트 3진)의 6개다. 주소는 복합 애트리뷰트, 프로젝트 위치는 다중 값 애트리뷰트, 역할·근무 기간·시작 날짜·공급량은 관계의 애트리뷰트다.

![실습에서 그린 회사 데이터베이스 E-R 다이어그램](./images/db-er-to-relational-company-er.jpg '실습 결과. 부속 부품과 가족을 약한 개체(이중 사각형)로, 위치를 다중 값 애트리뷰트(이중 타원)로 그렸다')

이 요구사항을 그릴 때 갈리기 쉬운 부분은 다음과 같다.

| 부분      | 잘못 그리기 쉬운 형태                            | 이 글의 설계                  | 이유                                                                                                                             |
| --------- | ------------------------------------------------ | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 공급      | 공급자-부품 2진 관계 + 부품-프로젝트 "사용" 관계 | 공급자·부품·프로젝트 3진 관계 | 공급량은 (공급자, 부품, 프로젝트) 조합마다 정해진다. 2진 관계 둘로는 "어느 공급자가 어느 프로젝트에 공급했는지"를 표현할 수 없다 |
| 부속 부품 | 별도의 약한 개체 "부속 부품"과 m:n 관계          | 부품 자신과의 순환 관계       | 부속 부품도 부품번호로 식별되는 부품이라, 키를 가진 강한 개체다. 같은 개체 타입 안의 관계로 그린다                               |
| 소속      | 1:1, 또는 부서 쪽 n·사원 쪽 1                    | 부서 쪽 1, 사원 쪽 n          | 한 부서에 여러 사원이 속한다. 부양에서 사원 쪽 1, 가족 쪽 n으로 적은 것처럼 "여러" 쪽 개체 옆에 n을 적어야 한다                  |
| 관리      | 프로젝트와 관리 사이를 단일선으로                | 프로젝트 쪽 이중선            | 모든 프로젝트에 관리자가 한 명 있으므로 프로젝트는 관리 관계에 전체 참여한다                                                     |

<details>
<summary>실습 2. 서점 데이터베이스 E-R 다이어그램</summary>

> 서점은 도서를 구매하는 고객의 정보를 관리한다. 고객마다 고객아이디(고유), 이름, 적립금을, 도서마다 ISBN(고유), 제목, 저자명, 가격을 저장한다. 고객은 여러 도서를 구매할 수 있고, 각 도서는 여러 고객이 구매할 수 있으며, 구매일자와 구매방법을 저장한다. 출판사마다 출판사번호(고유), 이름, 위치, 전화번호를 저장하고, 각 출판사는 서점에 여러 종류의 도서를 공급한다.

| 구분      | 이름   | 애트리뷰트                           | 원소 수·참여 제약                                                |
| --------- | ------ | ------------------------------------ | ---------------------------------------------------------------- |
| 개체 타입 | 고객   | 고객아이디(키), 이름, 적립금         |                                                                  |
| 개체 타입 | 도서   | ISBN(키), 제목, 저자명, 가격         |                                                                  |
| 개체 타입 | 출판사 | 출판사번호(키), 이름, 위치, 전화번호 |                                                                  |
| 관계 타입 | 구매   | 구매일자, 구매방법                   | 고객 M : 도서 N                                                  |
| 관계 타입 | 공급   |                                      | 출판사 1 : 도서 N. 도서는 반드시 출판사가 있으므로 전체 참여한다 |

ISBN은 출판사가 발행하는 도서마다 붙는 번호라, 한 도서(ISBN)를 공급하는 출판사는 하나다. 그래서 공급은 출판사 1 : 도서 N 관계이고, ==구매일자와 구매방법은 고객이나 도서 한쪽이 아니라 구매 행위에 속하므로 구매 관계의 애트리뷰트다.==

![서점 데이터베이스 E-R 다이어그램](./images/db-er-to-relational-bookstore-er.jpg '실습 결과. 도서는 반드시 출판사가 있으므로 공급 관계에 전체 참여(이중선)한다')

</details>

<details>
<summary>실습 3. 회사·서점 데이터베이스 논리적 설계</summary>

> 1, 2에서 설계한 E-R 다이어그램을 7단계 사상 알고리즘으로 관계 스키마로 바꿔라.

회사 데이터베이스의 결과는 [최종 관계 스키마](#최종-관계-스키마) 절의 릴레이션 9개다. 사상할 때 틀리기 쉬운 부분은 다음과 같다.

| 부분          | 틀리기 쉬운 사상                          | 바른 사상                                    |
| ------------- | ----------------------------------------- | -------------------------------------------- |
| 소속 사상     | 방법 1로 부서에 사원번호 외래 키를 넣었다 | N 쪽인 사원에 부서번호 외래 키를 넣는다      |
| 근무 릴레이션 | 근무(사원번호, 프로젝트번호)              | 근무(사원번호, 프로젝트번호, 역할, 근무기간) |

서점 데이터베이스는 4단계와 5단계만 적용하면 된다.

```text
고객   (고객아이디 PK, 이름, 적립금)
출판사 (출판사번호 PK, 이름, 위치, 전화번호)
도서   (ISBN PK, 제목, 저자명, 가격, 출판사번호 FK → 출판사 NOT NULL)  -- 4단계: 1:N은 N 쪽에
구매   (고객아이디 PK·FK → 고객, ISBN PK·FK → 도서, 구매일자, 구매방법)  -- 5단계: M:N은 관계 릴레이션
```

도서가 공급 관계에 전체 참여하므로 출판사번호는 널을 허용하지 않는다. ==같은 고객이 같은 책을 여러 번 살 수 있다면 {고객아이디, ISBN}만으로는 구매 튜플을 식별할 수 없으므로, 구매일자를 기본 키에 포함하거나 구매번호를 따로 둔다.==

</details>

<details>
<summary>실습 4. 회사 데이터베이스 Oracle DDL</summary>

> 회사 데이터베이스의 모든 테이블을 Oracle DDL로 생성하고, 한 테이블에 ALTER의 ADD, MODIFY, DROP을 실행하라. 모든 테이블에 데이터를 넣고, 교재의 검색문 종류별로 SELECT문을 하나씩, UPDATE문과 DELETE문 예제를 작성하라.

#### Oracle의 데이터 타입과 제약조건

Oracle은 표준 SQL의 데이터 타입을 다음 이름으로 쓴다.

| 표준 SQL     | Oracle      | 설명                                                                                         |
| ------------ | ----------- | -------------------------------------------------------------------------------------------- |
| CHARACTER(s) | CHAR(s)     | 고정 길이 문자열. 기본 1바이트, 최대 2,000바이트. 값이 s보다 짧으면 나머지를 공백으로 채운다 |
| VARCHAR(s)   | VARCHAR2(s) | 가변 길이 문자열. 최대 4,000바이트. 실제 값의 길이만큼만 저장한다                            |
| NUMERIC      | NUMBER(p,s) | 전체 자릿수 p, 소수 자릿수 s. 정수 6자리·소수 2자리는 `NUMBER(8,2)`                          |
| DATETIME     | DATE        | 날짜와 시각. 1초 단위                                                                        |

==CHAR는 짧은 쪽 끝에 공백을 채워 비교하므로 `'AA'`와 `'AA  '`를 같다고 판단하고, VARCHAR2는 공백도 한 문자로 비교하므로 다르다고 판단한다.== 사원번호처럼 길이가 정해진 코드는 CHAR, 이름처럼 길이가 다양한 값은 VARCHAR2가 알맞다.

| 제약조건    | 의미                                                                                                                 |
| ----------- | -------------------------------------------------------------------------------------------------------------------- |
| PRIMARY KEY | 행을 고유하게 식별한다. 테이블마다 하나만 정의하며, UNIQUE + NOT NULL과 같다. DBMS가 UNIQUE 인덱스를 자동으로 만든다 |
| UNIQUE      | 값의 중복을 금지한다. NULL은 대상이 아니라 NULL인 행이 여러 개여도 위반이 아니다                                     |
| NOT NULL    | NULL 입력을 금지한다. 지정하지 않은 열은 NULL을 허용한다                                                             |
| CHECK       | 참·거짓으로 평가되는 논리식으로 입력 값의 범위를 제한한다                                                            |
| FOREIGN KEY | 다른 테이블의 기본 키를 참조한다. 참조 무결성 옵션을 지정할 수 있다                                                  |

NOT NULL처럼 열 정의 뒤에 쓰는 방식을 열 수준, `CONSTRAINT ... PRIMARY KEY (...)`처럼 열 정의를 마친 뒤 모아 쓰는 방식을 테이블 수준 제약이라 하며, 한 문장에서 섞어 써도 된다. 제약조건에 이름을 붙이면 `ALTER TABLE ... DROP CONSTRAINT 이름`으로 제거할 수 있다. 테이블 이름과 열 이름은 문자로 시작하고 A-Z, a-z, 0-9, \_, $, # 만 쓸 수 있으며 예약어는 쓸 수 없다(`10_PLAYER`, `T-PLAYER`는 잘못된 이름이다).

#### DDL

기말 과제에서 최종 스키마를 Oracle DDL로 만들었다. 테이블 이름은 단수형 영문으로 정하고, 근무 관계는 CONDUCT(수행)로 이름 붙였다.

```sql
CREATE TABLE DEPART (
  Dno    CHAR(3)      NOT NULL,
  Dname  VARCHAR2(20) NOT NULL,
  Floor  NUMBER(3),
  CONSTRAINT DEPART_PK PRIMARY KEY (Dno)
);

-- 1:N 소속: N 쪽(사원)에 부서 외래 키
CREATE TABLE EMPLOYEE (
  Eno    CHAR(7)      NOT NULL,
  Ename  VARCHAR2(20) NOT NULL,
  Duty   VARCHAR2(10),
  Pay    NUMBER(10),
  City   VARCHAR2(20),               -- 복합 애트리뷰트 주소는 단순 애트리뷰트로
  State  VARCHAR2(20),
  Street VARCHAR2(20),
  Dept   CHAR(3)      NOT NULL,
  CONSTRAINT EMPLOYEE_PK  PRIMARY KEY (Eno),
  CONSTRAINT EMPLOYEE_FK1 FOREIGN KEY (Dept) REFERENCES DEPART (Dno)
);

-- 1:1 관리: 전체 참여하는 프로젝트 쪽에 관리자 외래 키와 관계 애트리뷰트
CREATE TABLE PROJECT (
  Pno     CHAR(7)      NOT NULL,
  Pname   VARCHAR2(20) NOT NULL,
  Budget  NUMBER(10),
  Manager CHAR(7)      NOT NULL,
  Sdate   DATE,
  CONSTRAINT PROJECT_PK  PRIMARY KEY (Pno),
  CONSTRAINT PROJECT_FK1 FOREIGN KEY (Manager) REFERENCES EMPLOYEE (Eno)
);

CREATE TABLE SUPPLIER (
  Sno    NUMBER(3)    NOT NULL,
  Sname  VARCHAR2(20) NOT NULL,
  Credit NUMBER(3),
  CONSTRAINT SUPPLIER_PK PRIMARY KEY (Sno)
);

-- 순환 1:N 포함: 같은 테이블의 기본 키를 참조
CREATE TABLE COMPONENT (
  Cno     NUMBER(10)   NOT NULL,
  Cname   VARCHAR2(20) NOT NULL,
  Price   NUMBER(10),
  Contain NUMBER(10),
  CONSTRAINT COMPONENT_PK  PRIMARY KEY (Cno),
  CONSTRAINT COMPONENT_FK1 FOREIGN KEY (Contain) REFERENCES COMPONENT (Cno)
);

-- 약한 개체: 주 개체의 키 + 부분 키
CREATE TABLE FAMILY (
  Eno    CHAR(7)      NOT NULL,
  Fname  VARCHAR2(20) NOT NULL,
  Gender CHAR(1),
  CONSTRAINT FAMILY_PK  PRIMARY KEY (Eno, Fname),
  CONSTRAINT FAMILY_FK1 FOREIGN KEY (Eno) REFERENCES EMPLOYEE (Eno)
);

-- 3진 공급: 세 외래 키의 조합이 기본 키
CREATE TABLE SUPPLY (
  Sno    NUMBER(3)  NOT NULL,
  Pno    CHAR(7)    NOT NULL,
  Cno    NUMBER(10) NOT NULL,
  Amount NUMBER(10),
  CONSTRAINT SUPPLY_PK  PRIMARY KEY (Sno, Pno, Cno),
  CONSTRAINT SUPPLY_FK1 FOREIGN KEY (Sno) REFERENCES SUPPLIER (Sno),
  CONSTRAINT SUPPLY_FK2 FOREIGN KEY (Pno) REFERENCES PROJECT (Pno),
  CONSTRAINT SUPPLY_FK3 FOREIGN KEY (Cno) REFERENCES COMPONENT (Cno)
);

-- 다중 값 애트리뷰트: 소유 개체의 키 + 값
CREATE TABLE LOCATION (
  Pno    CHAR(7)      NOT NULL,
  Locate VARCHAR2(20) NOT NULL,
  CONSTRAINT LOCATION_PK  PRIMARY KEY (Pno, Locate),
  CONSTRAINT LOCATION_FK1 FOREIGN KEY (Pno) REFERENCES PROJECT (Pno)
);
```

<details>
<summary>나머지 테이블(CONDUCT)과 ALTER 실습</summary>

```sql
-- M:N 근무(수행): 두 외래 키의 조합이 기본 키, 관계 애트리뷰트 포함
CREATE TABLE CONDUCT (
  Pno    CHAR(7)      NOT NULL,
  Eno    CHAR(7)      NOT NULL,
  Role   VARCHAR2(20),
  Period NUMBER(4),
  CONSTRAINT CONDUCT_PK  PRIMARY KEY (Pno, Eno),
  CONSTRAINT CONDUCT_FK1 FOREIGN KEY (Pno) REFERENCES PROJECT (Pno),
  CONSTRAINT CONDUCT_FK2 FOREIGN KEY (Eno) REFERENCES EMPLOYEE (Eno)
);

ALTER TABLE EMPLOYEE ADD Hobby VARCHAR2(20);
ALTER TABLE EMPLOYEE MODIFY Hobby VARCHAR2(10);
ALTER TABLE EMPLOYEE DROP COLUMN Hobby;
```

</details>

위 DDL은 Oracle Database 23ai Free에서 그대로 실행된다. 다만 PROJECT에는 [3단계](#3단계-2진-11-관계) 절의 UNIQUE 제약이 빠져 있어, 한 사원이 두 프로젝트의 관리자로 등록되는 것을 막지 못한다. 다음 문장을 더해야 1:1 관리 관계가 보장된다.

```sql
ALTER TABLE PROJECT ADD CONSTRAINT PROJECT_UK1 UNIQUE (Manager);
```

이 제약을 건 뒤 이미 다른 프로젝트를 관리하는 사원번호로 프로젝트를 넣으면 `ORA-00001: unique constraint (<스키마>.PROJECT_UK1) violated` 오류가 난다.

==테이블을 만드는 순서도 외래 키가 정한다.== EMPLOYEE는 DEPART를, PROJECT는 EMPLOYEE를 참조하므로 DEPART → EMPLOYEE → PROJECT 순서로 만들어야 한다. SUPPLY는 SUPPLIER, PROJECT, COMPONENT가 모두 있어야 만들 수 있다. 데이터를 넣을 때도 같은 순서다. 사원 행의 Dept 값은 DEPART에 있는 부서번호여야 하고(참조 무결성), 그렇지 않으면 Oracle이 `ORA-02291: integrity constraint (<스키마>.EMPLOYEE_FK1) violated - parent key not found` 오류를 반환한다. 반대로 테이블을 제거할 때는 참조하는 테이블부터 제거하거나 `DROP TABLE DEPART CASCADE CONSTRAINTS`로 참조하는 외래 키 제약을 함께 제거한다.

#### ALTER TABLE 명령

ALTER 실습에 쓴 ADD, MODIFY, DROP COLUMN 외에 Oracle이 지원하는 테이블 변경 명령은 다음과 같다.

| 명령                                                     | 동작                                                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `ALTER TABLE t ADD (열 타입)`                            | 열을 추가한다. 새 열은 항상 마지막 열이 되며 위치를 지정할 수 없다                                      |
| `ALTER TABLE t DROP COLUMN 열`                           | 열을 제거한다. 한 번에 하나씩, 최소 한 열은 남아야 하며 복구할 수 없다                                  |
| `ALTER TABLE t MODIFY (열 타입 [DEFAULT 식] [NOT NULL])` | 데이터 타입, 기본값, NOT NULL 제약을 변경한다                                                           |
| `ALTER TABLE t RENAME COLUMN 옛이름 TO 새이름`           | 열 이름을 바꾸고 관련 제약조건도 자동으로 고친다. ANSI/ISO 표준이 아니라 Oracle 등 일부 DBMS의 기능이다 |
| `ALTER TABLE t ADD CONSTRAINT 이름 ...`                  | 테이블을 만든 뒤 제약조건을 추가한다                                                                    |
| `ALTER TABLE t DROP CONSTRAINT 이름`                     | 제약조건을 제거한다                                                                                     |
| `RENAME t TO 새이름`                                     | 테이블 이름을 바꾼다                                                                                    |

#### ALTER로 스키마를 만들 때 생기는 오류

테이블을 먼저 만들고 ALTER로 제약을 붙여 가며 스키마를 완성할 때는 다음 오류가 생기기 쉽다.

| 부분         | 잘못된 스크립트                                                                                         | 문제                                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 열 이름 변경 | `CREATE TABLE`에서 이미 Ename으로 만든 뒤 `RENAME COLUMN Name TO Ename` 실행                            | Name 열이 없고 Ename이 이미 있어 `ORA-00957: duplicate column name`이 난다. Name으로 만든 직후에 바꿔야 한다                                    |
| 제약 추가    | CREATE TABLE PROJECT 없이 PROJECT에, CREATE TABLE ASSIGN보다 먼저 ASSIGN에 기본 키 추가                 | 테이블이 아직 없어 `ORA-00942`가 난다                                                                                                           |
| 소속         | DEPART에 Eno 열과 사원 외래 키를 넣었다가 제약만 제거하고, ASSIGN(Eno, Dno) 관계 테이블을 따로 만들었다 | 1:N에서 1 쪽에 외래 키를 넣은 오류다. 제약을 제거해도 Eno 열은 남는다. ASSIGN의 기본 키 {Eno, Dno}는 한 사원이 여러 부서에 속하는 것도 허용한다 |
| 포함         | `FOREIGN KEY(Cno) REFERENCES COMPONENT(Cno)`                                                            | 자기 기본 키를 자기가 참조해 모든 행이 자기 자신을 가리킨다. 상위 부품을 담을 Contain 열을 따로 두고 그 열을 외래 키로 해야 한다                |
| 근무         | WORK(Eno, Pno)                                                                                          | 관계의 애트리뷰트인 역할과 근무 기간이 없다                                                                                                     |

==1:N 관계는 N 쪽 테이블의 외래 키 열 하나로 표현되므로, 소속에 ASSIGN 같은 관계 테이블은 필요하지 않다.== 위 DDL은 EMPLOYEE에 Dept 열을 둔다.

INSERT는 `INSERT INTO 테이블 (열 목록) VALUES (...)`처럼 열을 지정하는 형식과, 위처럼 열 목록 없이 모든 열의 값을 테이블의 열 순서대로 빠짐없이 주는 형식이 있다. 열을 지정하는 형식에서 빠진 열에는 NULL(DEFAULT가 정의되어 있으면 기본값)이 들어가며, 기본 키나 NOT NULL 열은 빠뜨릴 수 없다. 문자 값은 작은따옴표로 감싸고 숫자 값은 감싸지 않는다.

#### 검색문 종류별 SELECT

교재의 데이터 검색 절에 나오는 검색 종류마다 SELECT문을 하나씩 만들었다. 모든 문장과 결과는 위 예제 데이터로 Oracle에서 실행해 확인했다. ORDER BY가 없는 문장은 행 순서가 보장되지 않는다.

| 종류                      | 검색 내용                                  |
| ------------------------- | ------------------------------------------ |
| 일반 검색(DISTINCT)       | 사원 직책의 종류                           |
| 조건 검색                 | 개발부(D02)에서 급여가 3400 이상인 사원    |
| 순서를 명세하는 검색      | 사원을 급여 내림차순으로                   |
| 산술식과 문자 스트링      | 프로젝트 예산을 10% 늘린 값                |
| 복수 테이블로부터의 검색  | 프로젝트와 관리자 이름                     |
| 자기 자신의 테이블에 조인 | 부품과 그 부품을 포함하는 상위 부품        |
| 집계 함수                 | 전체 사원 수, 평균·최고 급여               |
| GROUP BY                  | 부서별 사원 수와 평균 급여                 |
| HAVING                    | 사원이 2명 이상 참여하는 프로젝트          |
| 부속 질의문               | 모바일앱 프로젝트에 참여하는 사원          |
| LIKE                      | 이름이 '메'로 시작하는 부품                |
| NULL                      | 다른 부품에 포함되지 않는 최상위 부품      |
| EXISTS                    | 부양가족이 있는 사원                       |
| UNION                     | 프로젝트 관리자이거나 부양가족이 있는 사원 |

일반 검색은 `DISTINCT`로 중복을 제거한다. `ALL`이 기본값이라 생략하면 중복 행이 모두 나온다.

```sql
SELECT DISTINCT Duty FROM EMPLOYEE;
```

| Duty |
| ---- |
| 부장 |
| 과장 |
| 대리 |
| 사원 |

조건 검색은 WHERE에 비교 연산자와 AND, OR, NOT을 쓴다.

```sql
SELECT Eno, Ename, Pay
FROM   EMPLOYEE
WHERE  Dept = 'D02' AND Pay >= 3400;
```

| Eno     | Ename  | Pay  |
| ------- | ------ | ---- |
| E230002 | 이나래 | 4800 |
| E230005 | 정마루 | 3400 |

최라온(3200)은 D02이지만 급여 조건에서 제외된다.

```sql
SELECT Ename, Pay FROM EMPLOYEE ORDER BY Pay DESC;
```

| Ename  | Pay  |
| ------ | ---- |
| 김가람 | 6000 |
| 이나래 | 4800 |
| 박다솜 | 4000 |
| 정마루 | 3400 |
| 최라온 | 3200 |

SELECT 목록에 산술식과 문자 상수를 쓰고 `AS`로 결과 열 이름을 바꿀 수 있다. 별명에 공백이나 특수 문자가 있거나 대소문자를 구분해야 하면 큰따옴표로 감싼다.

```sql
SELECT Pname, Budget * 1.1 AS "증액 예산", '만원' AS 단위
FROM   PROJECT;
```

| Pname      | 증액 예산 | 단위 |
| ---------- | --------- | ---- |
| 물류시스템 | 55000     | 만원 |
| 모바일앱   | 33000     | 만원 |
| 데이터분석 | 22000     | 만원 |

복수 테이블로부터의 검색은 FROM에 테이블을 나열하고 WHERE에 조인 조건을 쓴다. Oracle에서는 테이블 별명 앞에 `AS`를 쓰지 않는다.

```sql
SELECT P.Pname, E.Ename, P.Sdate
FROM   PROJECT P, EMPLOYEE E
WHERE  P.Manager = E.Eno;
```

| Pname      | Ename  | Sdate      |
| ---------- | ------ | ---------- |
| 물류시스템 | 김가람 | 2023-03-02 |
| 모바일앱   | 이나래 | 2023-04-10 |
| 데이터분석 | 박다솜 | 2023-05-15 |

Sdate는 NLS_DATE_FORMAT을 `YYYY-MM-DD`로 설정했을 때의 표시 형식이다.

순환 관계인 포함은 같은 테이블에 별명을 두 개 붙여 자기 자신과 조인한다.

```sql
SELECT C.Cname AS 하위부품, U.Cname AS 상위부품
FROM   COMPONENT C, COMPONENT U
WHERE  C.Contain = U.Cno;
```

| 하위부품 | 상위부품 |
| -------- | -------- |
| 메인보드 | 서버     |
| 전원장치 | 서버     |
| 메모리   | 메인보드 |

Contain이 NULL인 서버와 모니터는 조인 조건을 만족하는 짝이 없어 하위부품 열에 나오지 않는다.

```sql
SELECT COUNT(*) AS 사원수, AVG(Pay) AS 평균급여, MAX(Pay) AS 최고급여
FROM   EMPLOYEE;
```

| 사원수 | 평균급여 | 최고급여 |
| ------ | -------- | -------- |
| 5      | 4280     | 6000     |

평균급여는 (6000 + 4800 + 4000 + 3200 + 3400) / 5 = 21400 / 5 = 4280이다.

```sql
SELECT   Dept, COUNT(*) AS 사원수, AVG(Pay) AS 평균급여
FROM     EMPLOYEE
GROUP BY Dept
ORDER BY Dept;
```

| Dept | 사원수 | 평균급여 |
| ---- | ------ | -------- |
| D01  | 1      | 6000     |
| D02  | 3      | 3800     |
| D03  | 1      | 4000     |

D02의 평균은 (4800 + 3200 + 3400) / 3 = 3800이다. HAVING은 그룹을 만든 뒤 그룹 단위로 조건을 건다.

```sql
SELECT   Pno, COUNT(*) AS 참여사원수
FROM     CONDUCT
GROUP BY Pno
HAVING   COUNT(*) >= 2;
```

| Pno     | 참여사원수 |
| ------- | ---------- |
| P230001 | 2          |
| P230002 | 3          |

```sql
SELECT Ename
FROM   EMPLOYEE
WHERE  Eno IN (SELECT Eno FROM CONDUCT WHERE Pno = 'P230002');
```

| Ename  |
| ------ |
| 이나래 |
| 최라온 |
| 정마루 |

LIKE의 `%`는 길이 0 이상의 임의 문자열, `_`는 임의의 한 문자와 일치한다.

```sql
SELECT Cname, Price FROM COMPONENT WHERE Cname LIKE '메%';
```

| Cname    | Price |
| -------- | ----- |
| 메인보드 | 500   |
| 메모리   | 100   |

NULL은 `= NULL`로 비교하면 결과가 UNKNOWN이 되어 어떤 행도 선택되지 않으므로 `IS NULL`로 검색한다.

```sql
SELECT Cno, Cname FROM COMPONENT WHERE Contain IS NULL;
```

| Cno | Cname  |
| --- | ------ |
| 1   | 서버   |
| 4   | 모니터 |

```sql
SELECT Ename
FROM   EMPLOYEE E
WHERE  EXISTS (SELECT * FROM FAMILY F WHERE F.Eno = E.Eno);
```

| Ename  |
| ------ |
| 김가람 |
| 이나래 |

EXISTS 안의 부속 질의문은 바깥 행의 E.Eno를 참조하므로 사원 행마다 다시 평가된다. UNION은 두 검색 결과의 합집합을 구하며 중복 행을 제거한다.

```sql
SELECT Manager AS Eno FROM PROJECT
UNION
SELECT Eno FROM FAMILY;
```

| Eno     |
| ------- |
| E230001 |
| E230002 |
| E230003 |

E230001은 관리자이면서 부양가족이 두 명이지만 한 번만 나온다.

#### UPDATE와 DELETE

==UPDATE와 DELETE에 WHERE를 쓰지 않으면 테이블의 모든 행이 갱신되거나 삭제된다.== 개발부 사원의 급여를 5% 올린다.

```sql
UPDATE EMPLOYEE
SET    Pay = Pay * 1.05
WHERE  Dept = 'D02';
```

3개 행이 갱신되어 이나래 5040, 최라온 3360, 정마루 3570이 된다. WHERE에는 부속 질의문도 쓸 수 있다. 서울에서 진행하는 프로젝트의 예산을 5000 늘린다.

```sql
UPDATE PROJECT
SET    Budget = Budget + 5000
WHERE  Pno IN (SELECT Pno FROM LOCATION WHERE Locate = '서울');
```

P230001(55000)과 P230002(35000)의 2개 행이 갱신되고, 대전에서만 진행하는 P230003은 그대로다.

DELETE는 참조 무결성의 영향을 받는다. 부양가족 행은 다른 테이블이 참조하지 않으므로 바로 삭제된다.

```sql
DELETE FROM FAMILY WHERE Eno = 'E230002';
```

1개 행(이솔)이 삭제된다. 반면 CONDUCT가 참조하는 사원을 먼저 삭제하면 오류가 난다.

```sql
DELETE FROM EMPLOYEE WHERE Eno = 'E230005';
-- ORA-02292: integrity constraint (<스키마>.CONDUCT_FK2) violated - child record found

DELETE FROM CONDUCT  WHERE Eno = 'E230005';   -- 1개 행 삭제
DELETE FROM EMPLOYEE WHERE Eno = 'E230005';   -- 1개 행 삭제
```

외래 키에 `ON DELETE CASCADE`를 지정하지 않았으므로, ==자식 테이블의 참조 행을 먼저 삭제한 뒤에야 부모 행을 삭제할 수 있다.== E230005는 프로젝트 관리자도 아니고 부양가족도 없어 CONDUCT 행만 삭제하면 된다.

## 정리

- 개념적 설계에서는 요구사항의 명사를 개체 타입과 애트리뷰트로, 동사를 관계 타입으로 옮기고, 원소 수와 참여 제약을 정한다.
- 논리적 설계에서는 7단계 규칙으로 개체, 약한 개체, 1:1, 1:N, M:N, 3진 관계, 다중 값 애트리뷰트를 차례로 릴레이션과 외래 키로 바꾼다.
- 1:1은 전체 참여하는 쪽, 1:N은 N 쪽에 외래 키를 두고, M:N과 3진 관계는 관계 릴레이션을 만든다. 1:1 쪽 외래 키에는 UNIQUE 제약을 건다.
- Oracle DDL에서는 참조되는 테이블부터 만들고, 데이터도 같은 순서로 넣으며, 삭제는 참조하는 행부터 한다.
