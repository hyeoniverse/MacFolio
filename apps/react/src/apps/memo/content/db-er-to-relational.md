데이터베이스 기초 연재의 마지막 글로, 개념적 설계와 논리적 설계 실습을 다룬다. [앞 글](/memo/db-er-model)의 E-R 모델로 회사 데이터베이스를 개념적으로 설계하고, 그 결과를 관계 데이터 모델의 릴레이션으로 바꾼다.

## 요구사항

1. 회사에는 여러 사원이 재직한다. 사원마다 사원번호(고유), 이름, 직책, 급여, 주소를 저장한다. 주소는 시, 구, 동으로 나눈다.
2. 사원은 0명 이상의 부양가족을 가진다. 한 부양가족은 두 명 이상의 사원에게 속하지 않는다. 부양가족마다 이름과 성별을 저장한다.
3. 회사는 여러 프로젝트를 진행한다. 프로젝트마다 프로젝트번호(고유), 이름, 예산, 진행 위치를 저장한다. 한 프로젝트는 여러 위치에서 진행될 수 있다.
   - 프로젝트마다 여러 사원이 일하고, 사원은 여러 프로젝트에서 일할 수 있다. 사원이 프로젝트에서 맡은 역할과 근무 기간을 저장한다.
   - 프로젝트마다 관리자가 한 명 있고, 한 사원은 두 개 이상의 프로젝트를 관리할 수 없다. 관리자가 임무를 시작한 날짜를 저장한다.
4. 사원은 한 부서에만 속한다. 부서마다 부서번호(고유), 이름, 부서가 위치한 층을 저장한다.
5. 프로젝트에는 부품이 필요하고, 한 부품을 여러 프로젝트에서 쓸 수 있다. 부품마다 부품번호(고유), 이름, 가격을 저장하고, 다른 부품을 포함하는 부품이면 포함된 부품의 정보도 저장한다.
6. 부품을 공급하는 공급자가 있다. 한 공급자는 여러 부품을, 한 부품은 여러 공급자에게서 공급받을 수 있다. 공급자마다 공급자번호(고유), 이름, 신용도를 저장하고, 어떤 공급자가 어떤 부품을 어떤 프로젝트에 얼마나 공급하는지 저장한다.

## 개념적 설계: E-R 다이어그램

요구사항에서 개체 타입, 관계 타입, 애트리뷰트를 찾는다.

| 요구사항 | 개체 타입            | 관계 타입                         | 판단 근거                                                                             |
| -------- | -------------------- | --------------------------------- | ------------------------------------------------------------------------------------- |
| 1        | 사원                 |                                   | 사원번호가 키. 주소는 복합 애트리뷰트                                                 |
| 2        | 부양가족 (약한 개체) | 부양 (1:n, 식별 관계)             | 부양가족은 자기 애트리뷰트만으로 식별할 수 없고 사원이 있어야 존재한다. 이름이 구별자 |
| 3        | 프로젝트             |                                   | 위치는 다중 값 애트리뷰트                                                             |
| 3        |                      | 근무 (사원 m : 프로젝트 n)        | 역할, 근무 기간은 관계의 애트리뷰트                                                   |
| 3        |                      | 관리 (사원 1 : 프로젝트 1)        | 프로젝트는 관리자가 반드시 있으므로 전체 참여. 시작 날짜는 관계의 애트리뷰트          |
| 4        | 부서                 | 소속 (부서 1 : 사원 n)            |                                                                                       |
| 5        | 부품                 | 포함 (부품 1 : 부품 n, 순환 관계) | 한 부품이 여러 하위 부품을 포함한다                                                   |
| 5, 6     | 공급자               | 공급 (프로젝트·부품·공급자 3진)   | 공급량은 세 개체가 모두 정해져야 의미가 있다                                          |

![회사 데이터베이스의 E-R 다이어그램](./images/db-er-to-relational-company.svg '개체 타입 6개와 관계 타입 6개. 애트리뷰트는 생략했다')

"프로젝트에 부품이 필요하다"를 프로젝트-부품 2진 관계로 따로 두지 않은 이유는, 요구사항 6의 공급이 이미 프로젝트와 부품을 연결하기 때문이다. ==공급량은 (공급자, 부품, 프로젝트) 조합마다 정해지므로 2진 관계 세 개로 나누면 표현할 수 없다.==

## 논리적 설계: 7단계 사상

E-R 스키마를 릴레이션으로 바꾸는 규칙은 다음 7단계다. 각 단계의 결과에서 밑줄 대신 `PK`, `FK`로 키를 표시한다.

![사상할 대상(개체 타입·2진 관계·3진 관계·다중값 애트리뷰트)과 알고리즘 단계 1~7 대응표](./images/db-er-to-relational-note-10.jpg '사상할 대상(개체 타입·2진 관계·3진 관계·다중값 애트리뷰트)과 알고리즘 단계 1~7 대응표 (강의 자료)')

### 1단계: 정규 개체 타입

- 정규(강한) 개체 타입 E마다 릴레이션 R을 만든다.
- E의 단순 애트리뷰트를 모두 R에 넣는다.
- 복합 애트리뷰트는 그것을 구성하는 단순 애트리뷰트만 넣는다.
- E의 키가 R의 기본 키가 된다.

```text
사원     (사원번호 PK, 이름, 직책, 급여, 시, 구, 동)
부서     (부서번호 PK, 이름, 층)
프로젝트 (프로젝트번호 PK, 이름, 예산)
부품     (부품번호 PK, 이름, 가격)
공급자   (공급자번호 PK, 이름, 신용도)
```

주소는 복합 애트리뷰트라 시, 구, 동으로 들어간다. 프로젝트의 위치는 다중 값이라 7단계에서 처리한다.

![개체 E1(PK, A)을 릴레이션 E1(PK, A)로 옮기는 사상 도식](./images/db-er-to-relational-note-11.jpg '개체 E1(PK, A)을 릴레이션 E1(PK, A)로 옮기는 사상 도식 (강의 자료)')

### 2단계: 약한 개체 타입

- 주 개체 타입 E를 갖는 약한 개체 타입 W마다 릴레이션 R을 만들고, W의 단순 애트리뷰트를 모두 넣는다.
- 주 개체 릴레이션의 기본 키를 R에 외래 키로 넣는다.
- ==R의 기본 키는 그 외래 키와 W의 부분 키(구별자)의 조합이다.==

```text
부양가족 (사원번호 PK·FK → 사원, 이름 PK, 성별)
```

부양가족 이름은 사원마다 겹치지 않으면 되므로, {사원번호, 이름}이 기본 키다.

![E1(1)-식별 관계 R-약한 개체 E2(N, 부분 키 K)를 E1(PK1,A1)과 E2(FK1,K,A2)로 옮기는 사상 도식](./images/db-er-to-relational-note-12.jpg 'E1(1)-식별 관계 R-약한 개체 E2(N, 부분 키 K)를 E1(PK1,A1)과 E2(FK1,K,A2)로 옮기는 사상 도식 (강의 자료)')

### 3단계: 2진 1:1 관계

1:1 관계 R에 참여하는 두 릴레이션 S, T 가운데 하나(S)를 골라, T의 기본 키를 S에 외래 키로 넣고 R의 애트리뷰트도 S에 넣는다. ==**관계에 전체 참여하는 쪽을 S로 고른다.**== 관리 관계를 사상하는 방법을 비교하면 다음과 같다.

| 방법                  | 결과                                           | 평가                                                                         |
| --------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------- |
| 1. 프로젝트에 외래 키 | `프로젝트(…, 관리자사원번호 FK, 시작날짜)`     | 프로젝트는 모두 관리자가 있어(전체 참여) 널이 생기지 않는다. 채택            |
| 2. 사원에 외래 키     | `사원(…, 관리프로젝트번호 FK, 시작날짜)`       | 관리자가 아닌 사원이 대부분이라 널이 많이 생긴다                             |
| 3. 관계 릴레이션      | `관리(사원번호 FK, 프로젝트번호 FK, 시작날짜)` | 동작하지만 조인이 하나 늘어난다                                              |
| 4. 하나로 병합        | 사원과 프로젝트를 한 릴레이션으로              | 두 개체가 모두 전체 참여할 때만 가능하다. 여기서는 사원이 부분 참여라 부적합 |

```text
프로젝트 (프로젝트번호 PK, 이름, 예산, 관리자사원번호 FK → 사원, 시작날짜)
```

![1:1 관계의 방법 3(관계 릴레이션 R(FK1,FK2) 분리)·방법 4(E1·E2를 한 릴레이션으로 합침) 사상 결과](./images/db-er-to-relational-note-14.jpg '1:1 관계의 방법 3(관계 릴레이션 R(FK1,FK2) 분리)·방법 4(E1·E2를 한 릴레이션으로 합침) 사상 결과 (강의 자료)')

### 4단계: 2진 1:N 관계

- 1:N 관계 R에서 N 쪽 릴레이션 S에, 1 쪽 릴레이션 T의 기본 키를 외래 키로 넣는다.
- R의 애트리뷰트도 S에 넣는다.

==반대로 1 쪽에 N 쪽의 기본 키를 넣으면, 부서 하나에 사원번호 여러 개가 들어가 원자 값 조건을 어기거나 부서 튜플이 사원 수만큼 중복된다.==

```text
사원 (사원번호 PK, 이름, 직책, 급여, 시, 구, 동, 소속부서번호 FK → 부서)
부품 (부품번호 PK, 이름, 가격, 상위부품번호 FK → 부품)
```

포함 관계는 부품이 자기 자신과 맺는 순환 관계다. 외래 키가 같은 릴레이션의 기본 키를 참조하며, 최상위 부품의 상위부품번호는 널이다. 한 부품이 여러 상위 부품에 들어갈 수 있다면 포함은 M:N이 되어 5단계처럼 `부품구성(상위부품번호, 하위부품번호)` 릴레이션으로 분리해야 한다.

![1:N 관계의 사상 방법 1·2와 자기 참조 1:N 관계의 사상](./images/db-er-to-relational-note-15.jpg '1:N 관계의 사상 방법 1·2와 자기 참조 1:N 관계의 사상 (강의 자료)')

### 5단계: 2진 M:N 관계

- M:N 관계 R마다 릴레이션 R을 만든다.
- 참여하는 두 릴레이션의 기본 키를 외래 키로 넣고, 그 조합을 R의 기본 키로 한다.
- R의 애트리뷰트를 넣는다.

```text
근무 (사원번호 PK·FK → 사원, 프로젝트번호 PK·FK → 프로젝트, 역할, 근무기간)
```

==M:N은 어느 한쪽에 외래 키를 넣으면 반드시 다중 값이 되므로 관계 릴레이션이 필요하다.==

![E1-R(M:N)-E2를 E1·E2와 관계 릴레이션 R(FK1,FK2)로 옮기는 사상 도식](./images/db-er-to-relational-note-16.jpg 'E1-R(M:N)-E2를 E1·E2와 관계 릴레이션 R(FK1,FK2)로 옮기는 사상 도식 (강의 자료)')

### 6단계: 3진 이상의 관계

- 3진 이상의 관계 R마다 릴레이션 R을 만든다.
- 참여하는 모든 릴레이션의 기본 키를 외래 키로 넣고, R의 애트리뷰트를 넣는다.
- 보통 외래 키 전체의 조합이 기본 키다. 참여 개체의 원소 수가 1:N:N이면, 1 쪽을 제외한 외래 키의 조합으로 기본 키를 정할 수 있다.

```text
공급 (공급자번호 PK·FK → 공급자, 부품번호 PK·FK → 부품, 프로젝트번호 PK·FK → 프로젝트, 공급량)
```

![E1·E2·E3의 3진 관계 R을 N:N:N이면 FK1·FK2·FK3 전체가 키, 1:N:N이면 FK2·FK3가 키인 R(…, A)로 옮기는 두 사상 도식](./images/db-er-to-relational-note-17.jpg 'E1·E2·E3의 3진 관계 R을 N:N:N이면 FK1·FK2·FK3 전체가 키, 1:N:N이면 FK2·FK3가 키인 R(…, A)로 옮기는 두 사상 도식 (강의 자료)')

### 7단계: 다중 값 애트리뷰트

- 다중 값 애트리뷰트마다 릴레이션 R을 만든다.
- 그 애트리뷰트와, 그 애트리뷰트를 가진 개체(관계) 릴레이션의 기본 키를 외래 키로 넣는다.
- R의 기본 키는 다중 값 애트리뷰트와 외래 키의 조합이다.

```text
프로젝트위치 (프로젝트번호 PK·FK → 프로젝트, 위치 PK)
```

![다중값 애트리뷰트 B를 가진 E1을 E1(PK1,A)과 MVA(FK1,B)로 나누는 사상 도식](./images/db-er-to-relational-note-18.jpg '다중값 애트리뷰트 B를 가진 E1을 E1(PK1,A)과 MVA(FK1,B)로 나누는 사상 도식 (강의 자료)')

## 최종 관계 스키마

| 분류      | 릴레이션                                                     | 기본 키                              | 외래 키                                  |
| --------- | ------------------------------------------------------------ | ------------------------------------ | ---------------------------------------- |
| 개체      | 사원(사원번호, 이름, 직책, 급여, 시, 구, 동, 소속부서번호)   | 사원번호                             | 소속부서번호 → 부서                      |
| 개체      | 부서(부서번호, 이름, 층)                                     | 부서번호                             |                                          |
| 개체      | 프로젝트(프로젝트번호, 이름, 예산, 관리자사원번호, 시작날짜) | 프로젝트번호                         | 관리자사원번호 → 사원                    |
| 개체      | 부품(부품번호, 이름, 가격, 상위부품번호)                     | 부품번호                             | 상위부품번호 → 부품                      |
| 개체      | 공급자(공급자번호, 이름, 신용도)                             | 공급자번호                           |                                          |
| 약한 개체 | 부양가족(사원번호, 이름, 성별)                               | {사원번호, 이름}                     | 사원번호 → 사원                          |
| 관계      | 근무(사원번호, 프로젝트번호, 역할, 근무기간)                 | {사원번호, 프로젝트번호}             | 사원번호 → 사원, 프로젝트번호 → 프로젝트 |
| 관계      | 공급(공급자번호, 부품번호, 프로젝트번호, 공급량)             | {공급자번호, 부품번호, 프로젝트번호} | 세 열 모두                               |
| 다중 값   | 프로젝트위치(프로젝트번호, 위치)                             | {프로젝트번호, 위치}                 | 프로젝트번호 → 프로젝트                  |

릴레이션 9개가 나온다. 개체 타입 6개 가운데 5개는 1단계, 약한 개체 1개는 2단계에서 릴레이션이 되었고, 관계 타입 6개 가운데 1:1(관리)과 1:N(소속, 포함)은 외래 키로 흡수되어 별도 릴레이션이 생기지 않았다. 부양은 2단계에서 부양가족 릴레이션의 외래 키가 되었고, M:N(근무)과 3진(공급)만 관계 릴레이션이 되었다.

외래 키 위치를 고르는 기준을 요약하면 다음과 같다.

| 관계          | 외래 키 위치       | 이유                                    |
| ------------- | ------------------ | --------------------------------------- |
| 1:1           | 전체 참여하는 쪽   | 널이 생기지 않는다                      |
| 1:N           | N 쪽               | 1 쪽에 넣으면 다중 값이나 중복이 생긴다 |
| M:N, 3진 이상 | 별도 관계 릴레이션 | 어느 쪽에 넣어도 다중 값이 된다         |

설계를 마친 뒤에는 각 릴레이션의 함수 종속을 확인해 [정규화](/memo/db-normalization)로 검증한다. 이 스키마는 각 릴레이션의 결정자가 모두 기본 키라 BCNF를 만족한다.

## 실습에서 그린 다이어그램과 비교

12주차 실습에서 같은 요구사항을 손으로 그린 뒤 PowerPoint로 다시 그렸다.

![실습에서 그린 회사 데이터베이스 E-R 다이어그램](./images/db-er-to-relational-company-er.jpg '실습 결과. 부속 부품과 가족을 약한 개체(이중 사각형)로, 위치를 다중 값 애트리뷰트(이중 타원)로 그렸다')

위 도식과 다른 점은 세 가지다.

| 부분      | 실습 결과                                         | 이 글의 설계                  | 이유                                                                                                                             |
| --------- | ------------------------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 공급      | 공급자-부품 2진 관계 + 부품-프로젝트 "사용" 관계  | 공급자·부품·프로젝트 3진 관계 | 공급량은 (공급자, 부품, 프로젝트) 조합마다 정해진다. 2진 관계 둘로는 "어느 공급자가 어느 프로젝트에 공급했는지"를 표현할 수 없다 |
| 부속 부품 | 별도의 약한 개체 "부속 부품"과 m:n 관계           | 부품 자신과의 순환 관계       | 부속 부품도 부품번호로 식별되는 부품이라, 키를 가진 강한 개체다. 같은 개체 타입 안의 관계로 그린다                               |
| 소속      | 처음에 1:1로 그렸다가 부서 쪽 n, 사원 쪽 1로 수정 | 부서 쪽 1, 사원 쪽 n          | 한 부서에 여러 사원이 속한다. 근무·부양처럼 "여러" 쪽 개체 옆에 n을 적어야 다른 관계와 표기가 맞는다                             |

첫 번째는 실습 요구사항 체크리스트에서 마지막 항목("공급자가 어떤 부품을 어떤 프로젝트에 얼마나 공급하는지")을 체크하지 못한 부분이기도 하다.

## Oracle DDL로 구현

14주차 실습에서는 최종 스키마를 Oracle DDL로 만들었다. 주요 테이블만 옮긴다.

```sql
CREATE TABLE DEPART (
  Dno    CHAR(3)      NOT NULL,
  Dname  VARCHAR2(20) NOT NULL,
  Floor  NUMBER(3),
  CONSTRAINT DEPART_PK PRIMARY KEY (Dno)
);

-- 1:N 소속: N 쪽(사원)에 부서 외래 키
CREATE TABLE EMPLOYEE (
  Eno    CHAR(7)      NOT NULL,
  Ename  VARCHAR2(20) NOT NULL,
  Duty   VARCHAR2(10),
  Pay    NUMBER(10),
  City   VARCHAR2(20),               -- 복합 애트리뷰트 주소는 단순 애트리뷰트로
  State  VARCHAR2(20),
  Street VARCHAR2(20),
  Dept   CHAR(3)      NOT NULL,
  CONSTRAINT EMPLOYEE_PK  PRIMARY KEY (Eno),
  CONSTRAINT EMPLOYEE_FK1 FOREIGN KEY (Dept) REFERENCES DEPART (Dno)
);

-- 1:1 관리: 전체 참여하는 프로젝트 쪽에 관리자 외래 키와 관계 애트리뷰트
CREATE TABLE PROJECT (
  Pno     CHAR(7)      NOT NULL,
  Pname   VARCHAR2(20) NOT NULL,
  Budget  NUMBER(10),
  Manager CHAR(7)      NOT NULL,
  Sdate   DATE,
  CONSTRAINT PROJECT_PK  PRIMARY KEY (Pno),
  CONSTRAINT PROJECT_FK1 FOREIGN KEY (Manager) REFERENCES EMPLOYEE (Eno)
);

-- 순환 1:N 포함: 같은 테이블의 기본 키를 참조
CREATE TABLE COMPONENT (
  Cno     NUMBER(10)   NOT NULL,
  Cname   VARCHAR2(20) NOT NULL,
  Price   NUMBER(10),
  Contain NUMBER(10),
  CONSTRAINT COMPONENT_PK  PRIMARY KEY (Cno),
  CONSTRAINT COMPONENT_FK1 FOREIGN KEY (Contain) REFERENCES COMPONENT (Cno)
);

-- 약한 개체: 주 개체의 키 + 부분 키
CREATE TABLE FAMILY (
  Eno    CHAR(7)      NOT NULL,
  Fname  VARCHAR2(20) NOT NULL,
  Gender CHAR(1),
  CONSTRAINT FAMILY_PK  PRIMARY KEY (Eno, Fname),
  CONSTRAINT FAMILY_FK1 FOREIGN KEY (Eno) REFERENCES EMPLOYEE (Eno)
);

-- 3진 공급: 세 외래 키의 조합이 기본 키
CREATE TABLE SUPPLY (
  Sno    NUMBER(3)  NOT NULL,
  Pno    CHAR(7)    NOT NULL,
  Cno    NUMBER(10) NOT NULL,
  Amount NUMBER(10),
  CONSTRAINT SUPPLY_PK  PRIMARY KEY (Sno, Pno, Cno),
  CONSTRAINT SUPPLY_FK1 FOREIGN KEY (Sno) REFERENCES SUPPLIER (Sno),
  CONSTRAINT SUPPLY_FK2 FOREIGN KEY (Pno) REFERENCES PROJECT (Pno),
  CONSTRAINT SUPPLY_FK3 FOREIGN KEY (Cno) REFERENCES COMPONENT (Cno)
);

-- 다중 값 애트리뷰트: 소유 개체의 키 + 값
CREATE TABLE LOCATION (
  Pno    CHAR(7)      NOT NULL,
  Locate VARCHAR2(20) NOT NULL,
  CONSTRAINT LOCATION_PK  PRIMARY KEY (Pno, Locate),
  CONSTRAINT LOCATION_FK1 FOREIGN KEY (Pno) REFERENCES PROJECT (Pno)
);
```

<details>
<summary>나머지 테이블(SUPPLIER, CONDUCT)과 ALTER 실습</summary>

```sql
CREATE TABLE SUPPLIER (
  Sno    NUMBER(3)    NOT NULL,
  Sname  VARCHAR2(20) NOT NULL,
  Credit NUMBER(3),
  CONSTRAINT SUPPLIER_PK PRIMARY KEY (Sno)
);

-- M:N 근무(수행): 두 외래 키의 조합이 기본 키, 관계 애트리뷰트 포함
CREATE TABLE CONDUCT (
  Pno    CHAR(7)      NOT NULL,
  Eno    CHAR(7)      NOT NULL,
  Role   VARCHAR2(20),
  Period NUMBER(4),
  CONSTRAINT CONDUCT_PK  PRIMARY KEY (Pno, Eno),
  CONSTRAINT CONDUCT_FK1 FOREIGN KEY (Pno) REFERENCES PROJECT (Pno),
  CONSTRAINT CONDUCT_FK2 FOREIGN KEY (Eno) REFERENCES EMPLOYEE (Eno)
);

ALTER TABLE EMPLOYEE ADD Hobby VARCHAR2(20);
ALTER TABLE EMPLOYEE MODIFY Hobby VARCHAR2(10);
ALTER TABLE EMPLOYEE DROP COLUMN Hobby;
```

==테이블을 만드는 순서도 외래 키가 정한다.== EMPLOYEE는 DEPART를, PROJECT는 EMPLOYEE를 참조하므로 DEPART → EMPLOYEE → PROJECT 순서로 만들어야 한다. SUPPLY는 SUPPLIER, PROJECT, COMPONENT가 모두 있어야 만들 수 있다. 데이터를 넣을 때도 같은 순서다. 사원 행의 Dept 값은 DEPART에 있는 부서번호여야 하고(참조 무결성), 그렇지 않으면 Oracle이 `ORA-02291: integrity constraint (EMPLOYEE_FK1) violated - parent key not found` 오류를 반환한다.

## 서점 데이터베이스

같은 방법을 서점 데이터베이스에도 적용했다.

- 고객: 아이디(고유), 이름, 적립금
- 도서: ISBN(고유), 제목, 저자명, 가격
- 고객과 도서는 M:N 구매 관계이고, 구매일자와 구매방법을 저장한다.
- 출판사: 번호(고유), 이름, 위치, 전화번호. 출판사는 여러 도서를 공급하고, 도서는 한 출판사에서 공급된다.

![서점 데이터베이스 E-R 다이어그램](./images/db-er-to-relational-bookstore-er.jpg '실습 결과. 도서는 반드시 출판사가 있으므로 공급 관계에 전체 참여(이중선)한다')

```text
고객   (고객아이디 PK, 이름, 적립금)
출판사 (출판사번호 PK, 이름, 위치, 전화번호)
도서   (ISBN PK, 제목, 저자명, 가격, 출판사번호 FK → 출판사)        -- 4단계: 1:N은 N 쪽에
구매   (고객아이디 PK·FK → 고객, ISBN PK·FK → 도서, 구매일자, 구매방법)  -- 5단계: M:N은 관계 릴레이션
```

같은 고객이 같은 책을 여러 번 살 수 있다면 {고객아이디, ISBN}만으로는 구매 튜플을 식별할 수 없으므로, 구매일자를 기본 키에 포함하거나 구매번호를 따로 둔다.

## 정리

- 개념적 설계에서는 요구사항의 명사를 개체 타입과 애트리뷰트로, 동사를 관계 타입으로 옮기고, 원소 수와 참여 제약을 정한다.
- 논리적 설계에서는 7단계 규칙으로 개체, 약한 개체, 1:1, 1:N, M:N, 3진 관계, 다중 값 애트리뷰트를 차례로 릴레이션과 외래 키로 바꾼다.
- 1:1은 전체 참여하는 쪽, 1:N은 N 쪽에 외래 키를 두고, M:N과 3진 관계는 관계 릴레이션을 만든다.
