## 들어가기 전에

CPU는 메모리에서 읽은 바이트를 명령어로 해석해 실행하는 장치다. CPU가 이해하는 것은 `83 C0 01` 같은 바이트 열뿐이고, `count = count + 1;` 같은 문장은 이해하지 못한다. 프로그래밍 언어(programming language)는 사람이 컴퓨터에 시킬 일을 정해진 문법으로 기술하는 언어이고, 그 기술을 CPU가 실행할 수 있는 형식으로 변환하는 규칙까지 포함한다. 사람이 쓰는 표현과 기계가 실행하는 명령 사이를 연결하는 도구라고 할 수 있다.

## 저급 언어와 고급 언어

프로그래밍 언어는 하드웨어에 얼마나 가까운지에 따라 저급 언어(low-level language)와 고급 언어(high-level language)로 나눈다. 여기서 "저급"과 "고급"은 ==품질이 아니라 추상화 수준==을 뜻한다. 저급 언어는 CPU의 명령어 하나하나를 직접 다루고, 고급 언어는 변수·조건문·함수처럼 하드웨어와 무관한 개념으로 프로그램을 기술한다.

| 구분      | 종류       | 표기                              | 번역 도구            | 하드웨어 의존성           |
| --------- | ---------- | --------------------------------- | -------------------- | ------------------------- |
| 저급 언어 | 기계어     | 0과 1의 2진수(보통 16진수로 표기) | 필요 없음            | CPU 종류마다 다름         |
| 저급 언어 | 어셈블리어 | `mov`, `add` 같은 기호            | 어셈블러             | CPU 종류마다 다름         |
| 고급 언어 | C, Java 등 | 영어 단어와 수식에 가까운 문장    | 컴파일러, 인터프리터 | 번역기만 바꾸면 이식 가능 |

아래 그림은 "변수 `count`의 값을 1 늘린다"는 같은 연산을 세 수준으로 표현한 것이다. 기계어는 x86-64 CPU에서 최적화하지 않고 컴파일하면 실제로 생성되는 바이트다.

### 기계어

기계어(machine language)는 CPU가 직접 해석하는 2진수 명령이다. 명령어마다 어떤 동작을 할지 나타내는 연산 코드(opcode)와 그 대상(레지스터, 메모리 주소, 상수)을 정해진 비트 위치에 기록한다. 위 그림의 `83 C0 01`에서 `83`은 "레지스터나 메모리에 8비트 상수를 더하거나 빼는 계열의 명령", `C0`은 "대상은 `eax` 레지스터이고 연산은 덧셈", `01`은 더할 값 1이다. 2진수로 쓰면 `10000011 11000000 00000001`이다. 초기 컴퓨터의 프로그래머는 이런 비트 열을 스위치나 천공 카드로 직접 입력했다.

==기계어는 CPU 종류마다 다르다.== 이 명령어 형식의 규약을 명령어 집합 구조(ISA, Instruction Set Architecture)라고 한다. 인텔·AMD의 x86-64와 Apple 실리콘·스마트폰의 ARM64는 ISA가 달라서, x86-64용 기계어를 ARM64 CPU에서 그대로 실행할 수 없다. Apple 실리콘 Mac이 x86-64용 앱을 실행할 수 있는 것은 Rosetta 2가 x86-64 기계어를 ARM64 기계어로 변환하기 때문이다. 대부분은 앱을 처음 실행할 때 미리 변환해 두고, 실행 중에 생성되는 코드는 그때그때 변환한다.

### 어셈블리어

어셈블리어(assembly language)는 기계어 명령을 사람이 읽을 수 있는 기호(니모닉, mnemonic)로 바꿔 쓴 언어다. `83 C0 01` 대신 `add eax, 1`이라고 쓴다. 기계어 명령과 어셈블리어 명령은 ==대체로 일대일로 대응==하고, 어셈블러(assembler)라는 프로그램이 어셈블리어를 기계어로 변환한다. 메모리 주소에도 `loop_start` 같은 이름(레이블)을 붙일 수 있어서, 명령을 하나 끼워 넣을 때마다 뒤쪽 주소를 손으로 다시 계산하던 작업을 어셈블러가 대신한다.

어셈블리어도 CPU마다 다르다. 같은 덧셈을 ARM64에서는 `add w8, w8, #1`처럼 쓴다. 지금은 운영체제의 부팅 코드, 성능이 매우 중요한 암호화 루틴, 그리고 악성코드 분석·리버스 엔지니어링처럼 실행 파일을 직접 읽어야 하는 보안 분야에서 주로 쓴다. 소스 코드가 없는 악성코드는 디스어셈블러로 기계어를 어셈블리어로 되돌려 분석한다([악성코드](/memo/csintro-malware) 참고).

### 고급 언어

고급 언어는 C, Java, Python처럼 하드웨어 세부 사항을 감춘 언어다. 사람이 일상에서 쓰는 영어 단어(`if`, `while`, `print`)와 수식을 그대로 쓸 수 있다. 고급 언어가 해결한 문제는 세 가지다.

1. **이름으로 데이터를 다룬다.** 메모리 주소 `[rbp-4]`를 직접 기억하지 않고 `count`라는 변수 이름을 쓴다. 변수를 어느 주소에 배치할지는 번역 프로그램이 결정한다.
2. **한 문장이 여러 명령이 된다.** `count = count + 1;` 한 줄이 기계어 명령 세 개로 변환된다. `if`, `for`, 함수 호출 같은 구문도 여러 개의 비교·분기 명령으로 변환된다.
3. **이식성이 생긴다.** 같은 C 소스 코드를 x86-64용 컴파일러로 번역하면 x86-64 기계어가, ARM64용 컴파일러로 번역하면 ARM64 기계어가 만들어진다. 소스 코드는 한 번만 작성하면 된다.

고급 언어로 작성한 프로그램은 다음 순서로 실행된다. 사람이 작성한 원시 코드(source code, 소스 코드)를 번역 프로그램이 기계어로 된 목적 코드(object code)로 바꾸고, 그 목적 코드를 CPU가 실행해 결과를 낸다.

```text
원시 코드(count.c) ──번역──▶ 목적 코드(count.o, 실행 파일) ──실행──▶ 결과물
```

대신 고급 언어는 실제로 어떤 기계어가 실행되는지 프로그래머가 직접 제어하기 어렵다. C처럼 포인터로 메모리 주소를 직접 다룰 수 있는 언어는 고급 언어 중에서도 하드웨어에 가까운 편이라 운영체제와 임베디드 소프트웨어에 많이 쓴다.

## 프로그래밍 언어의 발전

언어는 그 시대의 하드웨어 가격과 해결하려던 문제에 맞춰 만들어졌다. 아래 연표는 10년 단위로 주요 언어의 처음 발표 연도를 정리한 것이다.

![1950년대 어셈블리어·FORTRAN·LISP·COBOL, 1960년대 ALGOL·BASIC·PL/I·Simula, 1970년대 Pascal·C·Smalltalk·Prolog, 1980년대 C++·Objective-C·Perl, 1990년대 Python·Visual Basic·Java·JavaScript, 2000년대 C#·Scratch·Go·App Inventor, 2010년대 Swift·Rust·Kotlin을 배치한 연표](./images/csintro-programming-languages-timeline.svg '연대별 주요 언어. 숫자는 처음 발표한 연도의 끝 두 자리(Rust와 Kotlin은 1.0 출시 연도)')

### 1950년대: 어셈블리어와 첫 고급 언어

1940년대 컴퓨터는 기계어로 프로그래밍했다. 1950년대에 들어 기계어 대신 어셈블리어로 프로그램을 작성하기 시작했고, 1957년 IBM의 존 배커스(John Backus) 팀이 첫 상용 고급 언어인 FORTRAN(FORmula TRANslation)을 IBM 704용으로 발표했다. FORTRAN의 목표는 과학·공학 분야의 복잡한 수식 계산을 수식에 가까운 표기로 쓰게 하면서도, 손으로 짠 어셈블리어에 뒤지지 않는 속도의 기계어를 만드는 것이었다. 당시 프로그래머들은 컴파일러가 만든 코드가 느릴 것이라고 의심했기 때문에, FORTRAN 컴파일러는 최적화에 많은 노력을 들였다. 1958년에는 존 매카시(John McCarthy)가 인공지능 연구용으로 LISP을 만들었다.

### 1960년대: 사무 처리 언어와 범용 언어

FORTRAN을 발전시킨 과학기술용 언어(ALGOL 60 등)가 이어서 나왔고, 기업의 급여·재고·회계 처리를 위한 사무용 언어도 개발되었다. 대표적인 사무용 언어가 1959년 CODASYL 위원회가 설계한 COBOL(COmmon Business-Oriented Language)이다. 1964년 IBM은 System/360과 함께 FORTRAN의 수치 계산 능력과 COBOL의 데이터 처리 능력을 한 언어에 담으려고 PL/I(Programming Language One)을 발표했다. 같은 해 다트머스 대학의 케메니(Kemeny)와 커츠(Kurtz)는 초보자용 언어 BASIC을 만들었고, 1967년 노르웨이에서 나온 Simula는 클래스와 객체 개념을 처음 도입해 이후 객체 지향 언어의 출발점이 되었다.

### 1970년대: 구조적 프로그래밍과 C

하드웨어 가격이 내려가면서 전체 비용에서 소프트웨어 개발·유지 비용이 차지하는 비중이 커졌다. 프로그램 규모가 커지자 복잡성을 관리하는 것이 중요해졌고, 제어 구조를 명확히 표현하는 언어가 등장했다.

- **Pascal(1970)**: 스위스의 니클라우스 비르트(Niklaus Wirth)가 구조적 프로그래밍 교육을 위해 설계했고, 계산기를 만든 수학자 블레즈 파스칼의 이름을 땄다. 엄격한 자료형 검사와 명확한 제어 구조 덕분에 1980년대까지 대학 교육용으로 널리 쓰였다. 표준 Pascal은 입출력과 문자열 처리 기능이 약해서 대화식 프로그램이나 사무 처리에는 적합하지 않았다.
- **C(1972)**: 벨 연구소의 데니스 리치(Dennis Ritchie)가 유닉스 운영체제를 작성하려고 만들었다. 하드웨어를 직접 다룰 수 있으면서도 다른 기종으로 옮기기 쉬워서 지금도 운영체제, 임베디드, 데이터베이스 엔진에 쓴다. 이후 언어에 비해 포인터와 메모리 관리를 직접 해야 해서 배우기 어렵다.
- **Smalltalk(1972)**: 제록스 PARC에서 앨런 케이(Alan Kay) 팀이 만든 순수 객체 지향 언어다. 모든 값이 객체이고, 객체끼리 메시지를 주고받아 계산한다.
- **Prolog(1972)**: 사실과 규칙을 선언하고 질의하는 논리 프로그래밍 언어다.

### 1980년대: 개인용 컴퓨터와 BASIC, 객체 지향의 시작

개인용 컴퓨터가 보급되어, 중앙 컴퓨터 한 대에 의존하던 계산을 사용자 각자의 컴퓨터에서 처리하게 되었다. 학생과 초보자가 바로 쓸 수 있는 언어가 필요해지면서 BASIC이 거의 모든 개인용 컴퓨터에 기본으로 탑재되었다. BASIC은 1964년 다트머스의 시분할 시스템(time-sharing system, 한 대의 컴퓨터를 여러 단말기 사용자가 시간을 잘게 나눠 번갈아 쓰는 방식)에서 쓰도록 만든 언어라 입력하고 바로 실행하기 쉬웠다. 하지만 초기 BASIC은 줄 번호와 `GOTO`로 실행 순서를 옮기는 비구조적 언어여서, 프로그램이 커질수록 실행 흐름을 추적하기 어렵고 유지 보수 비용이 커졌다.

```basic
10 INPUT X
20 IF X < 0 THEN GOTO 50
30 PRINT SQR(X)
40 GOTO 10
50 PRINT "ARGUMENT ERROR"
60 GOTO 10
```

1985년에는 비야네 스트롭스트룹(Bjarne Stroustrup)이 C에 클래스를 더한 C++를 발표했다.

### 1990년대: 객체 지향과 GUI, 웹

객체 지향 언어가 본격적으로 쓰이기 시작했다. Windows 같은 GUI(Graphical User Interface) 환경이 보급되면서 창, 버튼, 메뉴를 클래스로 제공하는 라이브러리가 함께 발전했다. 마이크로소프트의 Visual Basic(1991)은 화면에 버튼을 끌어다 놓고 그 버튼의 클릭 이벤트에 코드를 붙이는 방식으로 GUI 프로그램을 빠르게 만들게 했다. 1995년에는 썬 마이크로시스템즈의 Java와 넷스케이프의 JavaScript가 나와 월드 와이드 웹(WWW)의 확산과 함께 성장했고, 1991년 발표된 Python도 이 시기에 자리를 잡았다.

### 2000년대 이후: 4세대·5세대 언어와 컴포넌트

사용자는 더 쉽게 프로그램을 만들고, 이미 만들어진 기능을 가져다 쓰기를 원했다. 이런 요구에서 나온 것이 4세대 언어(4GL, Fourth-Generation Language)다. 언어의 세대는 보통 다음처럼 나눈다.

| 세대 | 예                                       | 특징                                                                      |
| ---- | ---------------------------------------- | ------------------------------------------------------------------------- |
| 1GL  | 기계어                                   | CPU가 직접 실행하는 2진수                                                 |
| 2GL  | 어셈블리어                               | 기계어의 기호 표기                                                        |
| 3GL  | FORTRAN, COBOL, C, Java                  | 절차를 기술하는 범용 고급 언어                                            |
| 4GL  | SQL, PowerBuilder, Delphi, 리포트 생성기 | 무엇을 원하는지 기술하면 처리 절차는 도구가 만든다. 시각적 개발 환경 제공 |
| 5GL  | Prolog 등 논리·제약 기반 언어            | 문제의 조건을 기술하면 시스템이 해를 찾는다. 인공지능 연구와 함께 발전    |

1982년 시작한 일본의 제5세대 컴퓨터 프로젝트도 Prolog 같은 논리 프로그래밍을 핵심 기술로 삼았다. 최근에는 대규모 언어 모델이 자연어 설명으로 코드를 생성하면서, 자연어로 프로그램을 기술한다는 목표가 다른 방식으로 실현되고 있다.

객체 지향 기법이 발전하면서 소프트웨어 컴포넌트(component) 기술도 발전했다. 컴포넌트는 정해진 인터페이스로만 기능을 제공하는 독립된 소프트웨어 부품이다. 전자 부품을 규격에 맞춰 회로 기판에 꽂듯이, 규격화된 인터페이스를 지키는 컴포넌트를 조립해 프로그램을 만든다. COM, JavaBeans, .NET 어셈블리가 이런 기술이고, 오늘날의 패키지 저장소(npm, PyPI)와 웹 API도 같은 방향의 기술이다. 객체 지향 기술이 웹과 결합하면서 웹 서비스로 다양한 정보를 제공하는 방식도 발전했다.

1990년대 이후의 흐름을 보면 하드웨어 성능이 높아지면서 언어 설계의 우선순위가 =="기계를 효율적으로 쓰는 것"에서 "프로그래머가 실수 없이 빨리 작성하는 것"으로== 옮겨 갔다. 메모리를 자동으로 회수하는 가비지 컬렉션(garbage collection)이 Java, Python, JavaScript에 기본으로 들어간 것이 그 예다. 2015년 1.0이 나온 Rust는 가비지 컬렉션 없이도 컴파일 단계에서 메모리 오류를 검출하는 방식으로 C의 성능과 메모리 안전성을 함께 얻으려는 언어다.

> [!NOTE] 메모리 안전성과 보안
> C와 C++는 배열 범위를 넘어 쓰는 것을 막지 않는다. 이런 버퍼 오버플로가 원격 코드 실행 취약점의 주요 원인이라, 미국 CISA 등은 2023년 12월 공동 지침에서 메모리 안전 언어(C#, Go, Java, Python, Rust, Swift 등)로 전환하는 로드맵을 세우도록 권고했다. ==언어 선택이 곧 보안 설계의 일부==다. 버퍼 오버플로의 동작은 [시스템 보안](/memo/csintro-system-security)에서 다룬다.

## 주요 언어의 특징

### COBOL

COBOL은 사무 처리용으로 설계되어 지금도 은행·보험·공공기관의 메인프레임에서 대량의 거래 데이터를 처리한다.

| 구분 | 내용                                                                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장점 | 컴퓨터 기종과 무관하게 표준 문법으로 작성할 수 있다. 파일의 순차 처리·비순차 처리를 모두 지원해 파일 처리 기능이 강하다. 영어 문장에 가까워 읽기 쉽다 |
| 단점 | 문장이 길어 원시 코드 분량이 많고, 그만큼 컴파일러도 크고 기억 공간을 많이 쓴다. 과학 계산 같은 복잡한 수치 처리에는 부적합하다                       |

COBOL 프로그램은 네 개의 부(DIVISION)로 구성한다.

| 부                      | 역할                     | 기술 내용                           |
| ----------------------- | ------------------------ | ----------------------------------- |
| IDENTIFICATION DIVISION | 프로그램을 식별하는 정보 | 프로그램 이름, 작성자, 작성 일자    |
| ENVIRONMENT DIVISION    | 프로그램이 실행되는 환경 | 컴퓨터 종류, 입출력 파일과 장치     |
| DATA DIVISION           | 처리할 데이터의 구조     | 기억 장소의 형식, 크기, 레코드 구조 |
| PROCEDURE DIVISION      | 실제로 수행할 처리       | 처리 순서에 따른 명령문             |

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PAYROLL.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 HOURS     PIC 99      VALUE 40.
       01 RATE      PIC 9(5)    VALUE 12000.
       01 PAY       PIC 9(7).
       PROCEDURE DIVISION.
           MULTIPLY HOURS BY RATE GIVING PAY.
           DISPLAY "PAY: " PAY.
           STOP RUN.
```

`PIC 9(5)`는 "10진수 5자리"라는 자료 형식이다. 급여 계산처럼 소수점 아래 오차가 허용되지 않는 금액을 ==10진수 자릿수로 정확하게== 다룬다.

### Pascal

Pascal은 복합문 `begin`~`end`, 조건문 `if-then-else`, 반복문 `while-do`와 `repeat-until` 같은 제어 구조가 있어 구조적 프로그래밍에 적합하다. 아래는 0이 입력될 때까지 수를 읽어 제곱근을 출력하고, 음수이면 오류 문구를 출력하는 프로그램이다.

```pascal
program squareroots(input, output);
var
  x : real;
begin
  repeat
    read(x);
    if x >= 0
      then writeln(sqrt(x))
      else writeln('argument error')
  until x = 0
end.
```

`repeat ... until x = 0`은 ==본문을 먼저 한 번 실행하고 조건을 검사하는== 후판단 반복이다. 앞의 BASIC 예제와 같은 일을 하지만 `GOTO` 없이 반복 안에 선택을 넣은 구조라, 읽는 사람이 실행 흐름을 위에서 아래로 따라갈 수 있다.

### Visual Basic

| 구분 | 내용                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 장점 | 쉽고 간편하게 작성할 수 있어 초보자나 교육용으로 좋다. 한글 지원이 우수하다. 마이크로소프트가 제공하는 개발 도구를 편하게 이용할 수 있다 |

Private Sub btnHello_Click()

### C 계열: C, C++, C#

| 구분 | 내용                                                                                                                                                                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 장점 | 어셈블리어 같은 저급 언어의 기능(비트 연산, 메모리 주소 직접 접근)을 포함한다. 구조적 프로그래밍 기능이 있어 읽고 작성하기 쉽다. 이식성이 높아 대부분의 운영체제에서 쓴다. C++는 C 프로그램을 거의 그대로 받아들이므로 기존 자산을 옮겨 오기 쉽다 |

세 언어의 관계는 이름에 드러난다. C++의 `++`는 C의 증가 연산자로 "C에서 한 단계 나아갔다"는 뜻이고, C#은 2000년 6월 마이크로소프트가 Java와 비슷한 설계로 .NET용으로 만든 언어다.

### Java

Java는 1995년 썬 마이크로시스템즈의 제임스 고슬링(James Gosling) 팀이 발표했다. C++의 문법과 객체 지향 기능을 이어받으면서, 메모리를 직접 해제하는 기능과 포인터 연산을 없애 규모를 줄이고 안전성을 높였다. 소스 코드를 특정 CPU가 아닌 JVM용 바이트코드로 번역하므로 "한 번 작성하면 어디서나 실행(Write Once, Run Anywhere)"할 수 있고, 이 성질 덕분에 다양한 기종이 연결된 웹 환경에 적합했다. 초기에는 웹 페이지 안에서 실행되는 애플릿으로 주목받았고, 지금은 서버 프로그램과 안드로이드 앱(Kotlin과 함께)에 주로 쓴다.

## 프로그램을 만드는 과정

프로그램은 대체로 다음 순서로 만든다.

| 단계               | 하는 일                                                        | 결과물               |
| ------------------ | -------------------------------------------------------------- | -------------------- |
| 1. 요구 사항 분석  | 사용자가 필요로 하는 기능과 제약을 파악하고 해결할 문제를 확정 | 요구 사항 명세서     |
| 2. 프로그램 설계   | 코딩 전에 처리 논리를 대략 그린다(알고리즘 설계)               | 순서도, 의사 코드    |
| 3. 코딩            | 프로그래밍 언어로 프로그램을 작성                              | 소스 코드            |
| 4. 번역(컴파일)    | 고급 언어 명령문을 기계어로 변환                               | 목적 코드, 실행 파일 |
| 5. 디버깅과 테스트 | 오류를 찾아 고치고 의도대로 동작하는지 시험                    | 검증된 프로그램      |

### 요구 사항 분석과 설계

요구 사항 분석은 사용자가 무엇을 필요로 하는지, 프로그램으로 해결할 문제가 무엇인지 확인하는 단계다. 기능 요구(예: "학번을 입력하면 수강 과목을 보여 준다") 외에 입력 형식, 처리 시간, 보안 요구(예: "본인만 자기 성적을 조회할 수 있다") 같은 제약도 이 단계에서 정한다. 보안 요구를 나중에 추가하면 설계를 다시 해야 하는 경우가 많아서, 처음부터 분석 대상에 넣는다.

설계는 실제 코딩을 시작하기 전에 프로그램의 처리 논리를 그려 내는 단계로, 알고리즘 설계라고도 한다. 알고리즘(algorithm)은 문제를 푸는 유한한 처리 단계의 순서다. 설계 결과는 순서도(flowchart)나 의사 코드(pseudocode)로 표현한다. 순서도에서 직사각형은 처리, 마름모는 조건 판단, 화살표는 실행 순서를 나타낸다.

### 세 가지 제어 구조

1966년 뵘(Böhm)과 자코피니(Jacopini)는 어떤 알고리즘이든 ==순차, 선택, 반복의 세 가지 제어 구조만 조합해 표현할 수 있음==을 증명했다. 이를 구조적 프로그램 정리라고 한다.

![구조적 프로그래밍의 세 제어 구조. 순차는 문장 A, B, C를 차례로 실행하고, 선택은 조건이 참이면 문장 A, 거짓이면 문장 B를 실행한 뒤 합류하고, 반복은 조건이 참인 동안 본문을 실행하고 거짓이면 빠져나간다](./images/csintro-programming-languages-control.svg '세 구조는 각각 입구와 출구가 하나라서 상자처럼 이어 붙이거나 중첩할 수 있다')

- **순차(sequence)**: 문장을 적힌 순서대로 실행한다.
- **선택(selection)**: 조건에 따라 다음에 실행할 문장을 고르는 분기 구조다. `if`, `switch`.
- **반복(iteration, loop)**: 종료 조건을 만족할 때까지 같은 문장을 되풀이한다. `while`, `for`, `do-while`.

세 구조는 모두 ==입구(entry)와 출구(exit)가 하나씩==이다. 그래서 한 구조의 출구를 다음 구조의 입구에 끝과 끝을 이어 붙이는 연결(스태킹, stacking)과, 한 구조를 다른 구조의 본문 안에 넣는 중첩(nesting)으로 큰 프로그램을 만들 수 있다. 의사 코드에서는 구조가 끝나는 위치를 `endif`(선택 구조의 끝), `endwhile`(반복 구조의 끝) 같은 종료 구문으로 명시해 어디까지가 한 구조인지 분명히 한다.

```text
read x
while x ≠ 0
    if x ≥ 0
        print sqrt(x)
    else
        print "argument error"
    endif
    read x
endwhile
```

아래 그림은 같은 원리를 순서도와 의사 코드로 나란히 나타낸 것이다. 순차 구조(stepA, stepB)의 출구가 선택 구조(conditionC)의 입구로, 선택 구조가 합류한 지점이 다시 반복 구조(conditionF)의 입구로 이어진다. 오른쪽 의사 코드의 `endif`와 `endwhile`이 순서도에서 화살표가 합류하는 지점과 대응한다.

![순서도 왼쪽에 Sequence(stepA, stepB), Selection(conditionC가 Yes면 stepD, No면 stepE), Loop(conditionF가 Yes인 동안 stepG)가 위에서 아래로 이어 붙어 있고, 오른쪽에 같은 내용을 do, if-then-else-endif, while-endwhile로 쓴 의사 코드가 있다](./images/csintro-programming-languages-stacking.jpg '세 구조를 스태킹한 순서도와 의사 코드. 출처: Joyce Farrell, 『Programming Logic and Design』, Cengage, Figure 2-1')

### 반복 구조의 세 가지 형태

반복 구조는 조건을 언제 검사하는지에 따라 세 가지 형태가 있다.

![for 문은 초기식, 조건식, 문장, 증가 연산 순으로 실행하고 조건식이 거짓이면 빠져나간다. while 문은 조건식이 참인 동안 문장을 반복한다](./images/csintro-programming-languages-loops.jpg 'for 문과 while 문의 순서도. 출처: 김종훈·김종진, 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미')

| 형태       | 조건 검사 시점 | 본문 최소 실행 횟수 | 주 용도                        |
| ---------- | -------------- | ------------------- | ------------------------------ |
| `for`      | 본문 실행 전   | 0회                 | 반복 횟수가 정해진 경우        |
| `while`    | 본문 실행 전   | 0회                 | 조건이 바뀔 때까지 반복        |
| `do-while` | 본문 실행 후   | ==1회==             | 입력을 먼저 받고 검사하는 경우 |

```c
for (int i = 1; i <= 3; i++) {   // 초기식; 조건식; 증가 연산
	printf("%d\n", i);
}

int n = 3;
while (n > 0) {                  // 조건이 거짓이면 한 번도 실행하지 않는다
	printf("%d\n", n);
	n--;
}

int x;
do {                             // 일단 한 번 실행한 뒤 조건을 검사한다
	scanf("%d", &x);
} while (x != 0);
```

`for` 문의 실행 순서를 `i`의 값으로 추적하면 다음과 같다.

| 단계 | 실행        | `i` | 조건 `i <= 3` | 출력 |
| ---- | ----------- | --- | ------------- | ---- |
| 1    | 초기식      | 1   | 참            |      |
| 2    | 본문 → 증가 | 2   | 참            | 1    |
| 3    | 본문 → 증가 | 3   | 참            | 2    |
| 4    | 본문 → 증가 | 4   | 거짓 → 종료   | 3    |

예를 들어 Pascal 예제와 같은 프로그램을 C로 쓰면 `do-while` 반복 안에 선택을 중첩한 구조가 된다.

```c
#include <math.h>
#include <stdio.h>

int main(void) {
	double x;
	do {                                  // 반복
		if (scanf("%lf", &x) != 1) break;
		if (x >= 0)                       // 선택
			printf("%f\n", sqrt(x));
		else
			printf("argument error\n");
	} while (x != 0);
	return 0;
}
```

## 번역 방식: 컴파일러, 인터프리터, 하이브리드

고급 언어로 작성한 소스 코드는 어떤 방식으로든 기계어로 변환되어야 실행된다. 번역 시점과 단위에 따라 세 가지 방식으로 나눈다.

![컴파일 방식은 소스 코드를 컴파일러가 실행 파일로 번역한 뒤 CPU가 실행하고, 인터프리터 방식은 인터프리터가 문장을 읽으며 바로 실행하고, 바이트코드 방식은 컴파일러가 만든 바이트코드를 가상 머신이 해석하거나 JIT 컴파일한다](./images/csintro-programming-languages-translate.svg '번역을 언제, 어떤 단위로 하는지가 다르다')

### 컴파일러

컴파일러(compiler)는 실행 전에 프로그램 전체를 한 번에 기계어로 번역해 실행 파일을 만든다. C, C++, COBOL, FORTRAN, Pascal, Rust, Go가 이 방식을 쓴다. C 컴파일 과정은 실제로 네 단계로 나뉜다.

![main.c가 전처리기를 거쳐 main.i, 컴파일러를 거쳐 main.s, 어셈블러를 거쳐 main.o가 되고, 링커가 libc와 연결해 실행 파일 a.out을 만든다](./images/csintro-programming-languages-c-pipeline.svg '각 단계는 cc 명령의 옵션으로 따로 멈춰 결과를 확인할 수 있다')

| 단계   | 입력 → 출력                     | 하는 일                                                         |
| ------ | ------------------------------- | --------------------------------------------------------------- |
| 전처리 | `main.c` → `main.i`             | `#include` 파일 내용을 붙이고 `#define` 매크로를 치환           |
| 컴파일 | `main.i` → `main.s`             | 어휘·구문 분석, 타입 검사, 최적화, 어셈블리어 생성              |
| 어셈블 | `main.s` → `main.o`             | 어셈블리어를 기계어 목적 파일로 변환                            |
| 링크   | `main.o` + 라이브러리 → `a.out` | `printf` 같은 외부 함수의 주소를 연결해 하나의 실행 파일로 만듦 |

컴파일 단계 안에서는 다시 소스 코드를 `int`, `count`, `=` 같은 토큰으로 자르는 어휘 분석, 토큰이 문법에 맞게 배열되었는지 확인해 구문 트리를 만드는 구문 분석, 변수 타입이 맞는지 확인하는 의미 분석, 코드 최적화와 코드 생성이 차례로 일어난다. 구문 오류는 구문 분석에서 발견된다.

번역을 미리 끝내므로 실행 속도가 빠르고, 문법 오류와 많은 타입 오류를 ==실행 전에 발견==한다. 대신 소스 코드를 고칠 때마다 다시 컴파일해야 하고, 실행 파일은 특정 ISA와 운영체제에만 맞는다. 배포하는 쪽은 실행 파일만 주면 되므로 소스 코드를 공개하지 않아도 된다.

### 인터프리터

인터프리터(interpreter)는 실행 파일을 만들지 않고, 프로그램을 ==한 행(문장)씩 읽어 번역과 실행을 동시에== 한다. 초기 BASIC과 셸 스크립트(bash, zsh)가 대표적인 예다. 수정한 뒤 바로 실행해 볼 수 있어 짧은 자동화 작업이나 학습에 편하지만, 실행할 때마다 해석하므로 같은 계산을 컴파일된 프로그램보다 느리게 수행한다. 반복문 안의 문장은 반복할 때마다 다시 해석해야 한다. 또 실행 전에 전체를 검사하지 않으므로, 오타가 있는 줄도 그 줄에 도달하기 전에는 오류가 나지 않는다.

```bash
echo "시작"
ech "오타"   # 이 줄에 도달한 시각에 'command not found' 오류
```

위 스크립트를 실행하면 "시작"이 먼저 출력되고, 그 다음 줄에서 오류가 난다. 컴파일 방식이었다면 실행 전에 오류가 보고되고 아무것도 출력되지 않았을 것이다.

### 하이브리드: 바이트코드와 가상 머신

하이브리드 방식은 컴파일러와 인터프리터를 함께 쓴다. 먼저 소스 코드를 특정 CPU에 묶이지 않는 중간 코드로 컴파일하고, 그 중간 코드를 인터프리터(가상 머신)가 실행한다. Java, C#, Python(CPython)이 이 방식을 쓰는 대표적인 언어다.

Java 컴파일러(`javac`)는 소스 코드를 JVM(Java Virtual Machine)이 해석하는 중간 형식인 바이트코드(`.class` 파일)로 번역한다. JVM은 바이트코드를 해석해 실행하다가, 자주 실행되는 부분을 실행 중에 기계어로 컴파일한다. 이를 ==JIT(Just-In-Time) 컴파일==이라고 한다. 바이트코드는 CPU와 무관하므로 JVM만 있으면 Windows, macOS, Linux 어디서든 같은 `.class` 파일이 실행된다.

```bash
javac Hello.java      # Hello.class(바이트코드) 생성
javap -c Hello        # 바이트코드를 사람이 읽는 형식으로 출력
java Hello            # JVM이 Hello.class를 실행
```

Python(CPython)도 `.py` 파일을 먼저 바이트코드로 컴파일해 `__pycache__/*.pyc`에 저장하고, 가상 머신이 그 바이트코드를 해석한다. 바이트코드는 표준 모듈 `dis`로 확인할 수 있다.

```python
import dis
def inc(count):
    return count + 1
dis.dis(inc)
# LOAD_FAST  count / LOAD_CONST 1 / BINARY_OP + / RETURN_VALUE  (버전마다 명령 이름이 조금 다르다)
```

CPython은 3.13부터 실험적인 JIT 컴파일러를 포함하지만 기본으로는 꺼져 있다. JavaScript 엔진(Chrome의 V8, Safari의 JavaScriptCore)도 해석과 JIT 컴파일을 함께 쓴다.

> [!IMPORTANT] "컴파일 언어"와 "인터프리터 언어"는 언어가 아니라 구현의 성질이다
> ==같은 언어도 구현에 따라 방식이 다르다.== Python에는 바이트코드 인터프리터인 CPython과 JIT 컴파일러인 PyPy가 있고, C에도 인터프리터가 존재한다. 따라서 "Python은 인터프리터 언어"라는 말은 "가장 널리 쓰는 구현인 CPython이 바이트코드를 해석한다"는 뜻으로 이해해야 한다.

| 방식       | 번역 시점         | 실행 속도         | 오류 발견           | 이식성                   | 예                               |
| ---------- | ----------------- | ----------------- | ------------------- | ------------------------ | -------------------------------- |
| 컴파일     | 실행 전 전체      | 빠름              | 실행 전에 대부분    | ISA·OS마다 다시 컴파일   | C, C++, COBOL, FORTRAN, Rust, Go |
| 인터프리트 | 실행 중 문장 단위 | 느림              | 그 줄 실행 시각     | 인터프리터만 있으면 실행 | 초기 BASIC, bash, zsh            |
| 하이브리드 | 실행 전 + 실행 중 | JIT로 빠르게 근접 | 구문 오류는 실행 전 | VM만 있으면 실행         | Java, C#, Python, JavaScript     |

## 디버깅과 테스트

### 오류의 종류

디버깅(debugging)은 프로그램에 들어 있는 오류(버그)를 찾아 제거하는 작업이다. 오류는 발견 시점과 원인에 따라 나눈다.

![컴파일 단계에서 구문 오류, 실행 단계에서 실행 시간 오류, 결과 검증 단계에서 논리 오류가 발견된다](./images/csintro-programming-languages-errors.svg '오류의 종류와 발견되는 단계')

| 종류           | 원인                                         | 발견 시점              | 예                                        |
| -------------- | -------------------------------------------- | ---------------------- | ----------------------------------------- |
| 구문 오류      | 오타나 문법에 맞지 않는 명령문               | 컴파일 시(컴파일 방식) | 세미콜론 누락, 괄호 짝 불일치             |
| 실행 시간 오류 | 실행 중 수행할 수 없는 연산                  | 실행 중                | 0으로 나누기, 널 포인터 역참조            |
| 논리 오류      | 문법은 맞지만 제어 구조나 계산이 의도와 다름 | 결과를 검증해야 발견   | `<=` 대신 `<`를 써서 마지막 원소를 빠뜨림 |

구문 오류는 컴파일러가 위치와 함께 알려 준다.

```text
count.c:3:22: error: expected ';' after expression
    count = count + 1
                     ^
                     ;
```

논리 오류는 ==프로그램이 정상적으로 끝나므로== 찾기 어렵다. 아래 함수는 1부터 `n`까지 더하려 했지만 반복 조건을 `<`로 써서 `n`을 빠뜨린다.

```c
int sum(int n) {
	int s = 0;
	for (int i = 1; i < n; i++)   // i <= n 이어야 한다
		s += i;
	return s;
}
```

`sum(3)`을 손으로 추적하면 `i`가 1, 2일 때만 더해 3을 반환한다. 기대값 6과 다르다는 것은 결과를 검증해야 알 수 있다. 이런 오류를 찾기 위해 입력과 기대 출력을 정해 두고 자동으로 비교하는 단위 테스트(unit test)를 작성한다. 디버거(gdb, lldb, IDE의 디버거)로 중단점(breakpoint)을 걸고 변수 값을 한 줄씩 확인하는 방법도 쓴다.

> [!WARNING] 논리 오류는 보안 취약점이 되기도 한다
> 배열 범위 검사를 `<=`로 잘못 쓰면 배열 끝을 하나 넘어 쓰는 오프 바이 원(off-by-one) 오류가 된다. C에서는 이것이 메모리 손상으로 이어져 공격자가 악용할 수 있다.

### 알파 테스트와 베타 테스트

테스트(시험)는 프로그램이 요구 사항대로 동작하는지 확인하는 작업이다. 출시 전 테스트는 누가, 어디서 하는지에 따라 두 단계로 나눈다.

| 구분        | 수행 주체                     | 환경                      | 목적                                       |
| ----------- | ----------------------------- | ------------------------- | ------------------------------------------ |
| 알파 테스트 | 개발 조직 내부(개발자, QA 팀) | 개발 환경, 통제된 장소    | 주요 기능 결함을 출시 전에 발견            |
| 베타 테스트 | 선정된 실제 고객·사용자       | 사용자가 실제로 쓰는 환경 | 다양한 기기·사용 방식에서 생기는 문제 발견 |

모바일 앱의 TestFlight, Google Play의 비공개 테스트 트랙, 게임의 공개 베타 서비스가 베타 테스트의 예다.

## 절차 지향과 구조적 프로그래밍

패러다임(paradigm)은 프로그램을 어떤 단위로 나누고 어떻게 조합할지에 대한 설계 방식이다. 한 언어가 여러 패러다임을 지원하는 경우가 많다.

### 절차 지향 언어

절차 지향(procedural) 언어는 프로그램을 처리 순서에 따라 명령문을 나열하고, 그 명령문들을 함수(프로시저)로 묶어 순서대로 호출한다. ==코드가 적힌 순서대로 실행==된다는 점이 핵심이다. Pascal, COBOL, FORTRAN, BASIC, C가 대표적이다. 데이터는 구조체 등으로 따로 정의하고, 함수가 그 데이터를 인자로 받아 처리한다.

```c
struct Account { char owner[32]; long balance; };

void deposit(struct Account *a, long amount) {
	a->balance += amount;
}
```

냉장고에 소고기를 넣는 일을 예로 들면, 사람은 "1. 냉장고 문을 연다, 2. 소고기를 넣는다, 3. 냉장고 문을 닫는다"라는 순서로 생각한다. 절차 지향 프로그램은 이 순서를 그대로 `open(냉장고)`, `insert(소고기)`, `close(냉장고)` 세 함수 호출로 옮긴다. 사람이 일을 처리하는 순서와 코드의 순서가 같아 이해하기 쉽다.

데이터(`struct Account`)와 기능(`deposit`)이 분리되어 있으므로, 다른 함수가 `balance`를 직접 음수로 바꾸는 것을 막을 수단이 없다. 프로그램이 커지면 어느 함수가 어떤 데이터를 바꾸는지 추적하기 어려워지고, 데이터 구조를 하나 바꾸면 그 데이터를 쓰는 모든 함수를 찾아 고쳐야 해서 운영·유지 비용이 커진다.

### 구조적 프로그래밍

구조적 프로그래밍(structured programming)은 절차 지향 프로그램이 복잡해지면서 커진 유지 비용을 줄이기 위해 나온 작성 방법이다. 원칙은 네 가지다.

1. 프로그램을 작은 단위로 나눠 조직한다(모듈화). 한 함수는 한 가지 일을 한다.
2. 각 단위는 입구와 출구가 하나인 형태로 작성한다.
3. 가능하면 `goto` 문을 쓰지 않는다.
4. 순차, 선택, 반복 구조만 쓴다.

다익스트라(Dijkstra)가 1968년 "Go To Statement Considered Harmful"에서 `goto`가 실행 순서를 추적하기 어렵게 만든다고 지적한 뒤 이 방식이 널리 퍼졌다. 앞의 BASIC 예제와 Pascal 예제를 비교하면 차이가 보인다. BASIC 예제는 `GOTO 10`, `GOTO 50`을 따라 줄 번호를 오가야 흐름을 알 수 있지만, Pascal 예제는 `repeat` 블록과 `if` 블록의 들여쓰기만 보면 된다.

순서도로 비교하면 차이가 더 분명하다. 아래 왼쪽 순서도는 맨 아래 상자에서 나온 화살표가 위쪽 선택 구조의 한쪽 갈래 안에 있는 상자로 되돌아가, 선택 구조와 반복이 서로 겹친다. 이런 흐름은 `goto` 없이는 코드로 옮길 수 없다. 오른쪽 순서도는 선택 구조가 끝난 뒤 합류하고, 그 다음 반복 구조가 시작되어 ==구조가 서로 겹치지 않는다.==

![왼쪽 나쁜 프로그램은 맨 아래 상자에서 선택 구조 갈래 안의 세 번째 상자로 되돌아가는 화살표가 있어 구조가 겹쳐 있다. 오른쪽 좋은 프로그램은 선택 구조가 합류한 뒤 반복 구조가 이어지고 마지막 상자로 끝난다](./images/csintro-programming-languages-structured.jpg '구조적이지 않은 흐름(a)과 구조적인 흐름(b). 출처: 김종훈·김종진, 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미')

## 객체 지향 프로그래밍

### 절차 지향과의 차이

절차 지향 언어는 데이터와 데이터를 처리하는 기능을 별도로 관리한다. 객체 지향(object-oriented) 언어는 ==데이터와 기능을 객체로 묶어 캡슐화==한 뒤, 객체끼리 메시지를 전달해 일을 처리한다.

![절차 지향 언어는 기능이 계층적으로 호출되며 공유 데이터에 각각 접근해 기능과 데이터가 일치하지 않고, 객체 지향 언어는 기능과 데이터를 한 객체로 묶고 객체끼리 메시지를 전달한다](./images/csintro-programming-languages-proc-vs-oop.jpg '절차 지향(왼쪽)과 객체 지향(오른쪽)의 구조 차이. 출처: 김종훈·김종진, 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미')

왼쪽 구조에서는 여러 기능이 같은 데이터 영역에 직접 접근하므로, 데이터 하나를 바꾸면 영향을 받는 기능을 찾기 어렵다. 오른쪽 구조에서는 데이터가 그 데이터를 다루는 기능과 함께 객체 안에 있고, 다른 객체는 메시지로만 요청할 수 있으므로 변경의 영향 범위가 객체 안으로 제한된다.

### 주요 개념

![Account 클래스에 private 필드 balance와 public 메서드 deposit, balance가 있고, new Account()로 서로 다른 잔액을 가진 객체 a1, a2가 만들어지며, SavingsAccount가 Account를 상속해 deposit을 재정의한다](./images/csintro-programming-languages-class-object.svg '클래스는 설계도, 객체는 그 설계도로 만든 실체다')

| 개념            | 뜻                                                                                            | 예                                                             |
| --------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 클래스(class)   | 공통 속성과 기능을 가진 객체들을 일반화한 범주. 객체를 만드는 설계도                          | `Account`                                                      |
| 객체(object)    | 개별적으로 식별되는 실체. 속성(데이터)과 기능(메서드)을 함께 가진다                           | 잔액 5,000원인 계좌 `a1`                                       |
| 메시지(message) | 객체 간에 전달되는 명령 단위. 실제로는 메서드 호출                                            | `a1.deposit(100)`                                              |
| 상속            | 하위 클래스가 상위 클래스의 속성과 기능을 모두 물려받음                                       | `SavingsAccount extends Account`                               |
| 추상화          | 상대 객체에 대해 꼭 필요한 부분만 알고 나머지 세부 사항은 감춤                                | 사용자는 `deposit`과 `balance()`만 안다                        |
| 캡슐화          | 속성과 기능을 객체에 포함하고, 세부 구현을 사용자로부터 은폐                                  | `balance`가 `private`이라 `deposit`의 검사를 우회할 수 없다    |
| 다형성          | 상위 클래스 타입으로 하위 클래스 객체를 가리킬 때, 같은 호출이 실제 클래스에 따라 다르게 동작 | `Account a = new SavingsAccount(); a.deposit(100);`은 101 입금 |

```java
class Account {
	private long balance;                 // 캡슐화: 외부에서 직접 접근 불가

	void deposit(long amount) {
		if (amount <= 0) throw new IllegalArgumentException("입금액은 양수");
		balance += amount;
	}
	long balance() { return balance; }
}

class SavingsAccount extends Account {    // 상속
	@Override
	void deposit(long amount) {           // 다형성: 같은 호출, 다른 동작
		super.deposit(amount + amount / 100);  // 1% 보너스
	}
}

Account[] accounts = { new Account(), new SavingsAccount() };
for (Account a : accounts) a.deposit(100);   // 각각 100, 101 입금
```

추상화는 조직도로 보면 이해하기 쉽다. 아래 그림에서 고객은 S사 안에 매니저, 회계, 하드웨어·소프트웨어 엔지니어가 있다는 것을 알 필요가 없고, 서비스센터라는 창구만 안다. 고객 입장에서 S사는 "서비스센터에 요청하면 처리해 주는 객체"이고 ==나머지 내부 구조는 감춰져 있다.== 회사가 내부 조직을 바꿔도 고객이 서비스센터에 요청하는 방법은 그대로다.

![S사가 서비스센터와 연결되고 서비스센터가 고객과 연결된다. S사 아래에는 매니저와 회계, 엔지니어와 그 아래 HW엔지니어, SW엔지니어가 있다](./images/csintro-programming-languages-abstraction.jpg '추상화의 예. 고객은 서비스센터만 알고 S사 내부 조직은 모른다. 출처: 김종훈·김종진, 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미')

다형성은 상위 클래스 이름으로 하위 클래스 객체를 가리키는 데서 생긴다. 아래 그림에서 `포유동물` 포인터 `한마리`가 먼저 강아지 `바둑이`를, 다음에 고양이 `나비`를 가리킨다. 두 번 모두 같은 `한마리->짖어라()`를 호출하지만, 실제로 실행되는 메서드는 가리키는 객체의 클래스가 결정하므로 첫 번째는 "멍멍", 두 번째는 "야옹"이 출력된다. C++에서는 `짖어라`를 `virtual` 함수로 선언해야 이렇게 동작한다.

![포유동물 클래스 아래 강아지와 고양이 클래스가 있고 각각 짖어라()가 멍멍, 야옹을 낸다. 오른쪽 코드는 포유동물 포인터 한마리에 바둑이와 나비의 주소를 차례로 넣고 짖어라()를 호출한다](./images/csintro-programming-languages-polymorphism.jpg '다형성의 예. 같은 호출이 객체에 따라 다른 소리를 낸다. 출처: 김종훈·김종진, 『컴퓨터 사이언스: 새내기를 위한 최신 컴퓨터 개론』, 한빛아카데미')

마지막 두 줄이 다형성의 예다. 반복문은 배열 원소가 어떤 클래스인지 모르고 `deposit`만 호출하지만, ==실제로 실행되는 메서드는 각 객체의 클래스가 결정==한다. 새 계좌 종류를 추가해도 이 반복문은 고칠 필요가 없다.

캡슐화는 보안과도 관련이 있다. 잔액 검증 로직이 `deposit` 한 곳에만 있으므로, 검증을 빠뜨린 코드 경로가 생길 여지가 줄어든다.

### 그 밖의 패러다임

- **함수형(functional)**: 값을 바꾸지 않는 함수의 조합으로 계산을 표현한다. 같은 입력에 항상 같은 출력을 내는 순수 함수를 중심으로 한다. Haskell, LISP 계열, 그리고 JavaScript의 `map`/`filter`/`reduce`.
- **선언형(declarative)**: 어떻게 계산할지가 아니라 무엇을 원하는지를 기술한다. SQL의 `SELECT name FROM users WHERE age > 20`은 조회 순서를 지정하지 않고 결과 조건만 적는다. HTML, 정규 표현식도 선언형이다.
- **논리형(logic)**: 사실과 규칙을 선언하고 질의하면 시스템이 답을 추론한다. Prolog.

```javascript
// 같은 계산(짝수만 골라 제곱해 합하기)을 두 방식으로
let total = 0; // 절차적: 상태를 바꾸며 단계 기술
for (const n of [1, 2, 3, 4]) if (n % 2 === 0) total += n * n;

const total2 = [1, 2, 3, 4] // 함수형: 변환의 조합
	.filter((n) => n % 2 === 0)
	.map((n) => n * n)
	.reduce((a, b) => a + b, 0); // 둘 다 20
```

### App Inventor

App Inventor는 안드로이드 앱을 드래그 앤 드롭 방식의 블록으로 만드는 비주얼 프로그래밍 언어다. 웹 브라우저에서 화면 디자이너로 버튼·레이블·센서 같은 컴포넌트를 배치하고, 블록 편집기에서 그 컴포넌트의 이벤트에 동작 블록을 끼운다.

![App Inventor 블록 편집기. 왼쪽 목록에 Control, Logic, Math 같은 기본 블록과 Button1, Sound1, AccelerometerSensor1 컴포넌트가 있고, 작업 영역에 when AccelerometerSensor1.Shaking do call Sound1.Play, when Button1.Click do call Sound1.Play, call Sound1.Vibrate 500 블록이 조립되어 있다](./images/csintro-programming-languages-app-inventor.jpg 'App Inventor의 HelloPurr 예제 블록 편집 화면. 출처: MIT App Inventor')

위 화면의 블록은 두 개의 이벤트 처리기다. 휴대폰을 흔들면(`AccelerometerSensor1.Shaking`) 소리를 내고, 버튼을 누르면(`Button1.Click`) 소리를 내고 500밀리초 진동한다. 같은 동작을 Java로 쓰면 센서 등록, 리스너 클래스, 진동 권한 처리까지 수십 줄이 필요하다.

App Inventor가 초보자에게 유리한 이유는 네 가지다.

1. 명령어를 기억하거나 타이핑할 필요가 없다. 목록에서 블록을 고른다.
2. 블록의 모양이 끼울 수 있는 위치를 제한한다. 값이 들어갈 자리에는 값 블록만 끼워져서 구문 오류가 생기지 않는다.
3. 주어진 선택 사항(드롭다운)에서 컴포넌트와 속성을 고르므로 이름 오타가 없다.
4. 이벤트를 직접 다룬다. `when ... do` 블록이 Visual Basic의 이벤트 처리기와 같은 역할을 해서, 이벤트 구동 방식을 자연스럽게 익힌다.

## 직접 해 보기: C 코드를 단계별로 번역해 보기

C 컴파일러의 네 단계를 옵션으로 하나씩 멈춰 결과를 확인한다. macOS에서는 Xcode Command Line Tools(`xcode-select --install`)를, Linux에서는 `gcc`를 설치한다.

### 1. 소스 코드 작성

```c
// count.c
#include <stdio.h>
#define STEP 1

int increase(int count) {
	count = count + STEP;
	return count;
}

int main(void) {
	printf("%d\n", increase(41));
	return 0;
}
```

### 2. 단계별 번역

```bash
cd /Users/me/practice
cc -E count.c -o count.i      # 전처리: stdio.h 내용이 붙고 STEP이 1로 치환된다
wc -l count.c count.i         # 13줄이 수백 줄로 늘어난 것을 확인
cc -O0 -S count.c -o count.s  # 컴파일: 최적화 없이 어셈블리어 생성
cc -c count.s -o count.o      # 어셈블: 기계어 목적 파일
cc count.o -o count           # 링크: printf가 연결된 실행 파일
./count                       # 42 출력
```

`count.i`를 열어 보면 맨 아래 `increase` 함수에서 `STEP`이 사라지고 `count = count + 1;`로 바뀌어 있다. 매크로 치환은 컴파일 전에 글자 단위로 일어난다는 뜻이다.

### 3. 어셈블리어와 기계어 확인

```bash
grep -A8 '_increase:\|^increase:' count.s   # 함수 부분의 어셈블리어
objdump -d count.o | head -30               # 목적 파일을 다시 어셈블리어로(역어셈블)
cc -O2 -S count.c -o count-o2.s             # 최적화하면 명령 수가 줄어든다
```

x86-64 Linux의 `gcc -O0`에서는 위 그림처럼 `count`를 스택 메모리 `[rbp-4]`에 저장하고 `mov`, `add`, `mov`로 처리하는 코드가, `-O2`에서는 `lea eax, [rdi+1]` 한 줄로 줄어든 코드가 생성된다. Apple 실리콘 Mac에서는 ARM64 어셈블리어가 나오고, `-O0`에서는 `ldr`, `add w8, w8, #1`, `str`가, `-O2`에서는 `add w0, w0, #1` 한 줄이 생성된다. `objdump -d` 결과에는 각 명령 왼쪽에 `83 c0 01` 같은 기계어 바이트가 함께 표시된다. 같은 소스 코드가 ISA와 최적화 수준에 따라 다른 기계어가 된다는 점을 직접 확인할 수 있다.

### 4. 구문 오류와 논리 오류 만들어 보기

`count = count + STEP;`의 세미콜론을 지우고 `cc -c count.c`를 실행하면 줄 번호와 함께 `expected ';'` 오류가 나고 목적 파일이 만들어지지 않는다. 세미콜론을 되돌리고 `+`를 `-`로 바꾸면 컴파일은 성공하지만 `./count`가 40을 출력한다. 컴파일러는 의도를 알지 못하므로 논리 오류는 출력값을 기대값과 비교해야 발견된다.

웹 브라우저에서 바로 시험하려면 [Compiler Explorer](https://godbolt.org/)에 코드를 붙여 넣고 컴파일러와 옵션을 바꿔 가며 결과를 비교하면 된다.
