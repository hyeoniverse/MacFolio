## 들어가기 전에

CPU는 메모리에서 읽은 바이트를 명령어로 해석해 실행하는 장치다. CPU가 이해하는 것은 `83 C0 01` 같은 바이트 열뿐이고, `count = count + 1;` 같은 문장은 이해하지 못한다. 프로그래밍 언어는 사람이 읽고 쓰기 쉬운 형식으로 명령을 기술하고, 그것을 CPU가 실행할 수 있는 형식으로 변환하는 규칙의 체계다.

필요한 배경은 두 가지다. 첫째, 2진수 8자리(8비트)가 1바이트이고, 1바이트는 16진수 두 자리(`00`~`FF`)로 표기한다. 둘째, CPU 안에는 레지스터(register)라는 소수의 고속 저장 공간이 있고, CPU는 메모리의 값을 레지스터로 읽어 와 계산한 뒤 다시 메모리에 쓴다.

## 저급 언어와 고급 언어

프로그래밍 언어는 하드웨어에 얼마나 가까운지에 따라 저급 언어(low-level language)와 고급 언어(high-level language)로 나눈다. 여기서 "저급"과 "고급"은 품질이 아니라 추상화 수준을 뜻한다. 저급 언어는 CPU의 명령어 하나하나를 직접 다루고, 고급 언어는 변수·조건문·함수처럼 하드웨어와 무관한 개념으로 프로그램을 기술한다.

아래 그림은 "변수 `count`의 값을 1 늘린다"는 같은 연산을 세 수준으로 표현한 것이다. 기계어는 x86-64 CPU에서 최적화하지 않고 컴파일하면 실제로 생성되는 바이트다.

![변수 count를 1 늘리는 연산을 C 한 줄, 어셈블리어 세 줄(mov, add, mov), 기계어 바이트 8B 45 FC, 83 C0 01, 89 45 FC로 비교한 도식](./images/csintro-programming-languages-levels.svg '고급 언어 한 줄이 기계어 명령 세 개가 된다')

### 기계어

기계어(machine language)는 CPU가 직접 해석하는 2진수 명령이다. 명령어마다 어떤 동작을 할지 나타내는 연산 코드(opcode)와 그 대상(레지스터, 메모리 주소, 상수)을 정해진 비트 위치에 기록한다. 위 그림의 `83 C0 01`에서 `83`은 "레지스터나 메모리에 8비트 상수를 더하거나 빼는 계열의 명령", `C0`은 "대상은 `eax` 레지스터이고 연산은 덧셈", `01`은 더할 값 1이다.

기계어는 CPU 종류마다 다르다. 이 명령어 형식의 규약을 명령어 집합 구조(ISA, Instruction Set Architecture)라고 한다. 인텔·AMD의 x86-64와 Apple 실리콘·스마트폰의 ARM64는 ISA가 달라서, x86-64용 기계어를 ARM64 CPU에서 그대로 실행할 수 없다. Apple 실리콘 Mac이 x86-64용 앱을 실행할 수 있는 것은 Rosetta 2가 실행 전에 기계어를 ARM64 기계어로 변환하기 때문이다.

### 어셈블리어

어셈블리어(assembly language)는 기계어 명령을 사람이 읽을 수 있는 기호(니모닉, mnemonic)로 바꿔 쓴 언어다. `83 C0 01` 대신 `add eax, 1`이라고 쓴다. 기계어 명령과 어셈블리어 명령은 대체로 일대일로 대응하고, 어셈블러(assembler)라는 프로그램이 어셈블리어를 기계어로 변환한다.

어셈블리어도 CPU마다 다르다. 같은 덧셈을 ARM64에서는 `add w8, w8, #1`처럼 쓴다. 지금은 운영체제의 부팅 코드, 성능이 매우 중요한 암호화 루틴, 그리고 악성코드 분석·리버스 엔지니어링처럼 실행 파일을 직접 읽어야 하는 보안 분야에서 주로 쓴다.

### 고급 언어

고급 언어는 C, Java, Python처럼 하드웨어 세부 사항을 감춘 언어다. 고급 언어가 해결한 문제는 세 가지다.

1. **이름으로 데이터를 다룬다.** 메모리 주소 `[rbp-4]`를 직접 기억하지 않고 `count`라는 변수 이름을 쓴다. 변수를 어느 주소에 배치할지는 번역 프로그램이 결정한다.
2. **한 문장이 여러 명령이 된다.** `count = count + 1;` 한 줄이 기계어 명령 세 개로 변환된다. `if`, `for`, 함수 호출 같은 구문도 여러 개의 비교·분기 명령으로 변환된다.
3. **이식성이 생긴다.** 같은 C 소스 코드를 x86-64용 컴파일러로 번역하면 x86-64 기계어가, ARM64용 컴파일러로 번역하면 ARM64 기계어가 만들어진다. 소스 코드는 한 번만 작성하면 된다.

대신 고급 언어는 실제로 어떤 기계어가 실행되는지 프로그래머가 직접 제어하기 어렵다. C처럼 포인터로 메모리 주소를 직접 다룰 수 있는 언어는 고급 언어 중에서도 하드웨어에 가까운 편이라 운영체제와 임베디드 소프트웨어에 많이 쓴다.

## 주요 언어의 등장과 설계 목적

언어는 그 시대의 하드웨어와 해결하려던 문제에 맞춰 만들어졌다. 아래 표는 이후 언어들에 큰 영향을 준 언어를 등장 순서로 정리한 것이다.

| 언어       | 처음 발표        | 설계 목적과 특징                                                                                        |
| ---------- | ---------------- | ------------------------------------------------------------------------------------------------------- |
| FORTRAN    | 1957             | 과학·공학 계산. 수식을 거의 그대로 코드로 쓸 수 있게 한 최초의 널리 쓰인 고급 언어(FORmula TRANslation) |
| COBOL      | 1959             | 사무 처리. 급여·회계 같은 레코드 처리를 영어 문장에 가까운 문법으로 기술                                |
| LISP       | 1958             | 기호 처리와 인공지능 연구. 리스트 자료 구조와 재귀를 중심으로 한 함수형 언어의 시초                     |
| BASIC      | 1964             | 교육용. 시분할 시스템의 단말기에서 초보자가 바로 입력하고 실행하도록 설계                               |
| Pascal     | 1970             | 구조적 프로그래밍 교육. `begin`/`end`, `if-then-else`, `while-do`로 제어 구조를 명확히 표현             |
| C          | 1972             | 유닉스 운영체제 개발. 하드웨어를 직접 다루면서도 다른 CPU로 옮기기 쉬운 시스템 프로그래밍 언어          |
| Smalltalk  | 1972 (공개 1980) | 순수 객체 지향. 모든 값이 객체이고 객체 간 메시지 전달로 계산                                           |
| C++        | 1985             | C에 클래스와 객체 지향 기능을 추가                                                                      |
| Python     | 1991             | 읽기 쉬운 문법의 범용 스크립트 언어                                                                     |
| Java       | 1995             | "한 번 작성하면 어디서나 실행". 바이트코드와 JVM으로 운영체제·CPU에 독립적인 실행                       |
| JavaScript | 1995             | 웹 브라우저 안에서 웹 페이지를 동적으로 바꾸기 위한 언어                                                |
| C#         | 2000             | Microsoft .NET 플랫폼용 객체 지향 언어                                                                  |

1990년대 이후의 흐름을 보면 하드웨어 성능이 높아지면서 언어 설계의 우선순위가 "기계를 효율적으로 쓰는 것"에서 "프로그래머가 실수 없이 빨리 작성하는 것"으로 옮겨 갔다. 메모리를 자동으로 회수하는 가비지 컬렉션(garbage collection)이 Java, Python, JavaScript에 기본으로 들어간 것이 그 예다. 2010년대에 등장한 Rust는 가비지 컬렉션 없이도 컴파일 단계에서 메모리 오류를 검출하는 방식으로 C의 성능과 메모리 안전성을 함께 얻으려는 언어다.

> [!NOTE] 메모리 안전성과 보안
> C와 C++는 배열 범위를 넘어 쓰는 것을 막지 않는다. 이런 버퍼 오버플로가 원격 코드 실행 취약점의 주요 원인이라, 미국 CISA 등은 2023년 이후 새 소프트웨어에 메모리 안전 언어(Rust, Go, Java, C# 등)를 쓰도록 권고하고 있다. 언어 선택이 곧 보안 설계의 일부다.

## 번역 방식: 컴파일러, 인터프리터, 바이트코드

고급 언어로 작성한 소스 코드는 어떤 방식으로든 기계어로 변환되어야 실행된다. 변환 시점에 따라 세 가지 방식으로 나눈다.

![컴파일 방식은 소스 코드를 컴파일러가 실행 파일로 번역한 뒤 CPU가 실행하고, 인터프리터 방식은 인터프리터가 문장을 읽으며 바로 실행하고, 바이트코드 방식은 컴파일러가 만든 바이트코드를 가상 머신이 해석하거나 JIT 컴파일한다](./images/csintro-programming-languages-translate.svg '번역을 언제, 어떤 단위로 하는지가 다르다')

### 컴파일러

컴파일러(compiler)는 실행 전에 프로그램 전체를 기계어로 번역해 실행 파일을 만든다. C, C++, Rust, Go가 이 방식을 쓴다. C 컴파일 과정은 실제로 네 단계로 나뉜다.

| 단계   | 입력 → 출력                     | 하는 일                                                         |
| ------ | ------------------------------- | --------------------------------------------------------------- |
| 전처리 | `main.c` → `main.i`             | `#include` 파일 내용을 붙이고 `#define` 매크로를 치환           |
| 컴파일 | `main.i` → `main.s`             | 문법 검사, 최적화, 어셈블리어 생성                              |
| 어셈블 | `main.s` → `main.o`             | 어셈블리어를 기계어 목적 파일로 변환                            |
| 링크   | `main.o` + 라이브러리 → `a.out` | `printf` 같은 외부 함수의 주소를 연결해 하나의 실행 파일로 만듦 |

번역을 미리 끝내므로 실행 속도가 빠르고, 문법 오류와 많은 타입 오류를 실행 전에 발견한다. 대신 소스 코드를 고칠 때마다 다시 컴파일해야 하고, 실행 파일은 특정 ISA와 운영체제에만 맞는다.

### 인터프리터

인터프리터(interpreter)는 실행 파일을 만들지 않고, 소스 코드를 읽으면서 바로 실행한다. 셸 스크립트(bash, zsh)가 대표적인 예다. 수정한 뒤 바로 실행해 볼 수 있어 짧은 자동화 작업에 편하지만, 실행할 때마다 해석하므로 같은 계산을 컴파일된 프로그램보다 느리게 수행한다. 또 실행 전에 전체를 검사하지 않으므로, 오타가 있는 줄도 그 줄에 도달하기 전에는 오류가 나지 않는다.

```bash
echo "시작"
ech "오타"   # 이 줄에 도달한 시각에 'command not found' 오류
```

### 바이트코드와 가상 머신

오늘날 많이 쓰는 언어는 두 방식을 섞는다. Java 컴파일러(`javac`)는 소스 코드를 특정 CPU의 기계어가 아니라 JVM(Java Virtual Machine)이 해석하는 중간 형식인 바이트코드(`.class` 파일)로 번역한다. JVM은 바이트코드를 해석해 실행하다가, 자주 실행되는 부분을 실행 중에 기계어로 컴파일한다. 이를 JIT(Just-In-Time) 컴파일이라고 한다. 바이트코드는 CPU와 무관하므로 JVM만 있으면 Windows, macOS, Linux 어디서든 같은 `.class` 파일이 실행된다.

Python(CPython)도 `.py` 파일을 먼저 바이트코드로 컴파일해 `__pycache__/*.pyc`에 저장하고, 가상 머신이 그 바이트코드를 해석한다. CPython은 3.13부터 실험적인 JIT 컴파일러를 포함하지만 기본으로는 꺼져 있다. JavaScript 엔진(Chrome의 V8, Safari의 JavaScriptCore)도 해석과 JIT 컴파일을 함께 쓴다.

> [!IMPORTANT] "컴파일 언어"와 "인터프리터 언어"는 언어가 아니라 구현의 성질이다
> 같은 언어도 구현에 따라 방식이 다르다. Python에는 바이트코드 인터프리터인 CPython과 JIT 컴파일러인 PyPy가 있고, C에도 인터프리터가 존재한다. 따라서 "Python은 인터프리터 언어"라는 말은 "가장 널리 쓰는 구현인 CPython이 바이트코드를 해석한다"는 뜻으로 이해해야 한다.

| 방식            | 번역 시점         | 실행 속도         | 이식성                   | 예                           |
| --------------- | ----------------- | ----------------- | ------------------------ | ---------------------------- |
| 컴파일          | 실행 전 전체      | 빠름              | ISA·OS마다 다시 컴파일   | C, C++, Rust, Go             |
| 인터프리트      | 실행 중 문장 단위 | 느림              | 인터프리터만 있으면 실행 | bash, zsh                    |
| 바이트코드 + VM | 실행 전 + 실행 중 | JIT로 빠르게 근접 | VM만 있으면 실행         | Java, C#, Python, JavaScript |

## 프로그램을 만드는 과정

### 요구 사항 분석과 설계

프로그램 작성은 코드 입력보다 먼저 무엇을 해결할지 정하는 데서 시작한다. 요구 사항 분석은 사용자가 필요로 하는 기능과 제약(입력 형식, 처리 시간, 보안 요구)을 확인하는 단계다. 설계는 그 기능을 어떤 순서의 처리 단계로 구현할지 정하는 단계로, 이 처리 단계를 알고리즘(algorithm)이라고 한다. 설계 결과는 순서도(flowchart)나 의사 코드(pseudocode)로 표현한다.

### 세 가지 제어 구조

1966년 뵘(Böhm)과 자코피니(Jacopini)는 어떤 알고리즘이든 순차, 선택, 반복의 세 가지 제어 구조만 조합해 표현할 수 있음을 증명했다. 이를 구조적 프로그램 정리라고 한다.

![구조적 프로그래밍의 세 제어 구조. 순차는 문장 A, B, C를 차례로 실행하고, 선택은 조건이 참이면 문장 A, 거짓이면 문장 B를 실행한 뒤 합류하고, 반복은 조건이 참인 동안 본문을 실행하고 거짓이면 빠져나간다](./images/csintro-programming-languages-control.svg '세 구조는 각각 입구와 출구가 하나라서 상자처럼 이어 붙이거나 중첩할 수 있다')

- **순차(sequence)**: 문장을 적힌 순서대로 실행한다.
- **선택(selection)**: 조건에 따라 실행할 문장을 고른다. `if`, `switch`.
- **반복(iteration)**: 조건이 참인 동안 같은 문장을 되풀이한다. `while`, `for`.

세 구조는 모두 입구와 출구가 하나씩이다. 그래서 하나의 구조를 다른 구조의 본문 안에 넣거나(중첩), 끝과 끝을 이어 붙여서(연결) 큰 프로그램을 만들 수 있다. 구조적 프로그래밍(structured programming)은 이 세 구조만 쓰고, 임의의 위치로 실행을 옮기는 `goto` 문을 피하는 작성 방법이다. 다익스트라(Dijkstra)가 1968년 "Go To Statement Considered Harmful"에서 `goto`가 프로그램의 실행 순서를 추적하기 어렵게 만든다고 지적한 뒤 널리 퍼졌다.

예를 들어 "0을 입력할 때까지 숫자를 읽어 제곱근을 출력하고, 음수이면 오류를 출력한다"는 프로그램은 반복 안에 선택을 중첩한 구조다.

```c
#include <math.h>
#include <stdio.h>

int main(void) {
	double x;
	do {                                  // 반복
		if (scanf("%lf", &x) != 1) break;
		if (x >= 0)                       // 선택
			printf("%f\n", sqrt(x));
		else
			printf("argument error\n");
	} while (x != 0);
	return 0;
}
```

### 오류의 종류와 테스트

프로그램의 오류(버그)는 발견 시점과 원인에 따라 나눈다.

| 종류           | 원인                           | 발견 시점              | 예                                        |
| -------------- | ------------------------------ | ---------------------- | ----------------------------------------- |
| 구문 오류      | 언어 문법 위반                 | 컴파일 시(컴파일 방식) | 세미콜론 누락, 괄호 짝 불일치             |
| 실행 시간 오류 | 실행 중 수행할 수 없는 연산    | 실행 중                | 0으로 나누기, 널 포인터 역참조            |
| 논리 오류      | 문법은 맞지만 의도와 다른 계산 | 결과를 검증해야 발견   | `<=` 대신 `<`를 써서 마지막 원소를 빠뜨림 |

논리 오류는 컴파일러가 찾아 주지 않으므로 테스트로 찾는다. 소프트웨어를 출시하기 전에는 개발 조직 내부에서 시험하는 알파 테스트(alpha test)와, 실제 사용자가 자기 환경에서 사용해 보는 베타 테스트(beta test)를 거친다. 디버깅(debugging)은 테스트로 드러난 오류의 원인을 찾아 고치는 작업이다.

## 프로그래밍 패러다임

패러다임(paradigm)은 프로그램을 어떤 단위로 나누고 어떻게 조합할지에 대한 설계 방식이다. 한 언어가 여러 패러다임을 지원하는 경우가 많다.

### 절차 지향

절차 지향(procedural) 프로그래밍은 프로그램을 처리 순서에 따라 함수(프로시저)들로 나눈다. 데이터는 구조체 등으로 따로 정의하고, 함수가 그 데이터를 인자로 받아 처리한다. C, Pascal, FORTRAN이 대표적이다.

```c
struct Account { char owner[32]; long balance; };

void deposit(struct Account *a, long amount) {
	a->balance += amount;
}
```

데이터(`struct Account`)와 기능(`deposit`)이 분리되어 있으므로, 다른 함수가 `balance`를 직접 음수로 바꾸는 것을 막을 수단이 없다. 프로그램이 커지면 어느 함수가 어떤 데이터를 바꾸는지 추적하기 어려워진다.

### 객체 지향

객체 지향(object-oriented) 프로그래밍은 데이터와 그 데이터를 다루는 기능을 객체(object)로 묶는다. 객체의 설계도가 클래스(class)이고, 객체에 동작을 요청하는 것을 메서드 호출 또는 메시지 전달이라고 한다.

```java
class Account {
	private long balance;                 // 캡슐화: 외부에서 직접 접근 불가

	void deposit(long amount) {
		if (amount <= 0) throw new IllegalArgumentException("입금액은 양수");
		balance += amount;
	}
	long balance() { return balance; }
}

class SavingsAccount extends Account {    // 상속
	@Override
	void deposit(long amount) {           // 다형성: 같은 호출, 다른 동작
		super.deposit(amount + amount / 100);  // 1% 보너스
	}
}
```

| 개념   | 뜻                                                       | 위 코드의 예                                                   |
| ------ | -------------------------------------------------------- | -------------------------------------------------------------- |
| 캡슐화 | 데이터를 객체 안에 감추고 정해진 메서드로만 접근하게 함  | `balance`가 `private`이라 `deposit`의 검사를 우회할 수 없다    |
| 추상화 | 사용하는 쪽에 필요한 기능만 드러내고 구현 세부는 감춤    | 사용자는 `deposit`과 `balance()`만 안다                        |
| 상속   | 기존 클래스의 속성과 기능을 물려받아 새 클래스를 정의    | `SavingsAccount extends Account`                               |
| 다형성 | 같은 메서드 호출이 실제 객체의 클래스에 따라 다르게 동작 | `Account a = new SavingsAccount(); a.deposit(100);`은 101 입금 |

캡슐화는 보안과도 관련이 있다. 잔액 검증 로직이 `deposit` 한 곳에만 있으므로, 검증을 빠뜨린 코드 경로가 생길 여지가 줄어든다.

### 그 밖의 패러다임

- **함수형(functional)**: 값을 바꾸지 않는 함수의 조합으로 계산을 표현한다. 같은 입력에 항상 같은 출력을 내는 순수 함수를 중심으로 한다. Haskell, LISP 계열, 그리고 JavaScript의 `map`/`filter`/`reduce`.
- **선언형(declarative)**: 어떻게 계산할지가 아니라 무엇을 원하는지를 기술한다. SQL의 `SELECT name FROM users WHERE age > 20`은 조회 순서를 지정하지 않고 결과 조건만 적는다. HTML, 정규 표현식도 선언형이다.
- **블록 기반 시각 언어**: Scratch, 엔트리, MIT App Inventor처럼 명령 블록을 끌어다 맞추는 언어다. 문법 오류가 생길 수 없게 블록의 모양이 결합 가능한 위치를 제한하므로 프로그래밍 교육에 쓴다.

## 직접 해 보기: C 코드를 어셈블리어로 변환해 보기

컴파일러가 만드는 어셈블리어는 `-S` 옵션으로 직접 확인할 수 있다. macOS에서는 Xcode Command Line Tools(`xcode-select --install`)를, Linux에서는 `gcc`를 설치한다.

```c
// count.c
int increase(int count) {
	count = count + 1;
	return count;
}
```

```bash
cd /Users/me/practice
cc -O0 -S count.c -o count.s     # 최적화 없이 어셈블리어 생성
cat count.s
cc -O2 -S count.c -o count-o2.s  # 최적화하면 명령 수가 줄어든다
```

x86-64 Linux의 `gcc -O0`에서는 위 그림처럼 `count`를 스택 메모리 `[rbp-4]`에 저장하고 `mov`, `add`, `mov`로 처리하는 코드가, `-O2`에서는 `lea eax, [rdi+1]` 한 줄로 줄어든 코드가 생성된다. Apple 실리콘 Mac에서는 ARM64 어셈블리어(`add w0, w0, #1`)가 나온다. 같은 소스 코드가 ISA와 최적화 수준에 따라 다른 기계어가 된다는 점을 직접 확인할 수 있다.

웹 브라우저에서 바로 시험하려면 [Compiler Explorer](https://godbolt.org/)에 코드를 붙여 넣고 컴파일러와 옵션을 바꿔 가며 결과를 비교하면 된다.

## 정리

| 주제              | 핵심                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------- |
| 저급 언어         | 기계어는 CPU가 해석하는 바이트, 어셈블리어는 그 기호 표기. 둘 다 ISA마다 다르다          |
| 고급 언어         | 변수·제어문으로 하드웨어를 감추고, 컴파일러를 바꿔 다른 CPU로 이식                       |
| 번역 방식         | 컴파일(실행 전 전체), 인터프리트(실행 중), 바이트코드 + VM(JIT). 언어가 아닌 구현의 성질 |
| 구조적 프로그래밍 | 순차·선택·반복만으로 모든 알고리즘 표현, `goto` 지양                                     |
| 오류              | 구문 오류, 실행 시간 오류, 논리 오류. 논리 오류는 테스트로 찾는다                        |
| 패러다임          | 절차 지향은 데이터와 함수 분리, 객체 지향은 캡슐화·상속·다형성                           |
