데이터베이스 기초 연재의 세 번째 글로, 4장(관계 데이터베이스)을 다룬다. 관계 데이터 모델(relational data model)은 1970년 IBM의 E. F. Codd가 제안했고, 수학의 릴레이션(relation)과 집합(set) 이론에 기초한다.

## 테이블과 릴레이션

일반 사용자는 릴레이션을 테이블로 생각하면 직관적으로 이해할 수 있다. 다만 테이블은 구체적인 표현이고 릴레이션은 추상적인 개념이라 완전히 같지는 않다(아래 릴레이션의 특성 참고).

| 관계 데이터 모델      | 테이블        | 파일 시스템(프로그래밍 시스템)      |
| --------------------- | ------------- | ----------------------------------- |
| 릴레이션(relation)    | 테이블(table) | 파일(file)                          |
| 튜플(tuple)           | 행(row)       | 레코드(record), 레코드 어커런스     |
| 애트리뷰트(attribute) | 열(column)    | 필드(field)·아이템(item), 필드 타입 |

> [!WARNING]
> ==관계 데이터베이스라고 해서 데이터가 물리적으로 테이블 형태로 저장된다는 뜻은 아니다.== 테이블은 논리적 구조이고, 물리적 저장 방식은 내부 스키마가 정한다.

다음 학생 릴레이션을 예로 쓴다. 이 연재의 다른 글도 같은 데이터를 쓴다.

| 학번 | 이름   | 학년 | 학과   |
| ---- | ------ | ---- | ------ |
| 100  | 나수영 | 4    | 컴퓨터 |
| 200  | 이찬수 | 3    | 전기   |
| 300  | 정기태 | 1    | 컴퓨터 |
| 400  | 송병길 | 4    | 컴퓨터 |
| 500  | 박종화 | 2    | 산공   |

이 릴레이션의 차수(degree)는 애트리뷰트 수인 4이고, 카디널리티(cardinality)는 튜플 수인 5다.

## 도메인과 애트리뷰트

==**도메인(domain)** 은 애트리뷰트가 가질 수 있는 값들의 집합이다.== 학번의 도메인이 세 자리 자연수라면 실수나 문자열은 들어갈 수 없다.

**애트리뷰트(attribute)** 는 도메인이 릴레이션 안에서 맡는 역할(role)의 이름이다. 학번과 학년은 넓게 보면 둘 다 자연수 도메인이지만 역할이 달라 이름으로 구별된다. ==그래서 한 릴레이션 안의 애트리뷰트 이름은 모두 달라야 한다.== 역할 이름을 도메인 이름과 같게 지정할 수도 있다.

| 도메인                        | 애트리뷰트      | 값                                                 |
| ----------------------------- | --------------- | -------------------------------------------------- |
| 단순 도메인(simple domain)    | 단순 애트리뷰트 | 원자 값 (예: 학년 4)                               |
| 복합 도메인(composite domain) | 복합 애트리뷰트 | 복합 값 (예: 날짜 <연, 월, 일>, 주소 <시, 구, 동>) |

복합 애트리뷰트의 값도 릴레이션 안에서는 하나의 단위로 취급한다.

## 릴레이션 스키마와 인스턴스

릴레이션은 스키마와 인스턴스로 구성된다.

|           | 릴레이션 스키마(relation schema)                                                | 릴레이션 인스턴스(relation instance)                                     |
| --------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 다른 이름 | 릴레이션 내포(intension), 릴레이션 스킴(scheme), 릴레이션 타입                  | 릴레이션 외연(extension), 릴레이션 값                                    |
| 내용      | 릴레이션 이름 + 애트리뷰트 이름의 집합                                          | 어느 한 시각에 릴레이션이 포함한 튜플의 집합 (스냅숏)                    |
| 표기      | `R(A_1, A_2, \ldots, A_n){:math}`, 각 `A_i{:math}`는 도메인 `D_i{:math}`에 대응 | `\{\langle V_1, V_2, \ldots, V_n \rangle\}{:math}`, `V_i \in D_i{:math}` |
| 성질      | 정적. 시간이 지나도 바뀌지 않는다                                               | 동적. 삽입·삭제·갱신으로 바뀐다                                          |

학생 릴레이션의 스키마는 `학생(학번, 이름, 학년, 학과)`이고, 위 표의 다섯 행이 지금 시각의 인스턴스다. ==스키마를 먼저 정의하고, 스키마에 맞춰 튜플을 넣는다.==

스키마는 애트리뷰트의 집합이라는 점을 드러내 `R(\{A_1, A_2, \ldots, A_n\}){:math}`으로도 표기한다. 인스턴스의 튜플도 위치가 아닌 이름으로 값을 대응시켜 `(\mathit{attr}_1 = V_1, \mathit{attr}_2 = V_2, \ldots, \mathit{attr}_n = V_n){:math}`처럼 표기할 수 있다. 릴레이션 값(인스턴스)은 보통 그냥 릴레이션이라 부르며, 개념적으로 ==릴레이션은 릴레이션 스키마와 릴레이션 인스턴스를 합친 것이다.==

수학적으로 릴레이션 R은 도메인들의 카티션 프로덕트(Cartesian product)의 부분집합이다.

```math
R \subseteq D_1 \times D_2 \times \cdots \times D_n
```

즉 R은 `d_i \in D_i{:math}`인 n-튜플 `\langle d_1, d_2, \ldots, d_n \rangle{:math}`의 집합이다. 여기서 n이 차수, 튜플의 수가 카디널리티다. 차수에 따라 1차(unary), 2차(binary), 3차(ternary), …, n차 릴레이션이라 부른다. ==차수는 스키마가 정하므로 고정이고, 카디널리티는 인스턴스에 따라 바뀐다.==

## 릴레이션의 특성

| 특성                  | 내용                                                                 | 테이블과의 차이                     |
| --------------------- | -------------------------------------------------------------------- | ----------------------------------- |
| 튜플의 유일성         | 릴레이션은 튜플의 집합이므로 똑같은 튜플이 두 개 있을 수 없다        | 테이블에는 같은 행이 중복될 수 있다 |
| 튜플의 무순서성       | 집합의 원소에는 순서가 없다                                          | 테이블의 행에는 위아래 순서가 있다  |
| 애트리뷰트의 무순서성 | 스키마는 애트리뷰트의 집합이고, 튜플은 <애트리뷰트:값> 쌍의 집합이다 | 테이블의 열에는 좌우 순서가 있다    |
| 애트리뷰트의 원자성   | 애트리뷰트 값은 논리적으로 분해할 수 없는 원자 값(atomic value)이다  |                                     |

> [!NOTE]
> ==널 값(null value)도 원자 값으로 취급한다.== 널은 값을 모르는 경우(unknown)와 해당 사항이 없는 경우(inapplicable)를 명시적으로 표현하는 특수한 값이다.

애트리뷰트 값으로 원자 값만 허용하는 릴레이션을 **정규화 릴레이션(normalized relation)** 이라 한다. 한 학생의 수강 과목이 `{C413, E412}`처럼 집합으로 들어간 비정규화 릴레이션은 분해(decomposition)로 정규화하며, 분해 후에도 같은 의미를 유지해야 한다.

| 학번 | 과목번호 (비정규화) |
| ---- | ------------------- |
| 100  | {C413, E412}        |

| 학번 | 과목번호 (정규화) |
| ---- | ----------------- |
| 100  | C413              |
| 100  | E412              |

정규화는 [7장 글](/memo/db-normalization)에서 함수 종속과 함께 자세히 다룬다.

## 관계 데이터베이스와 스키마

관계 데이터베이스(relational database)는 테이블의 집합이며, 시간에 따라 내용(상태)이 바뀌는 테이블로 데이터베이스를 표현한다.

```math
\text{관계 데이터베이스 스키마} = \{\text{릴레이션 스키마}\} + \{\text{무결성 제약조건}\}
```

대학 데이터베이스는 다음 릴레이션들로 구성된다. 기본 키는 학생의 학번, 과목의 과목번호, 등록의 {학번, 과목번호}다.

```text
학생 (학번, 이름, 학년, 학과)
과목 (과목번호, 과목이름, 학점, 학과, 담당교수)
등록 (학번, 과목번호, 성적, 중간성적, 기말성적)
```

## 키

> [!IMPORTANT]
> ==키(key)는 각 튜플을 유일하게 식별할 수 있는 애트리뷰트 집합이다.==

| 키                     | 정의                                                               | 학생 릴레이션 예                        |
| ---------------------- | ------------------------------------------------------------------ | --------------------------------------- |
| 슈퍼 키(super key)     | 유일성은 만족하지만 최소성은 만족하지 않을 수 있는 애트리뷰트 집합 | {학번, 이름}, {학번}                    |
| 후보 키(candidate key) | 유일성과 최소성을 모두 만족하는 애트리뷰트 집합                    | {학번}                                  |
| 기본 키(primary key)   | 후보 키 중에서 설계자가 지정한 하나. 널을 허용하지 않는다          | 학번                                    |
| 대체 키(alternate key) | 기본 키를 제외한 나머지 후보 키                                    | (주민등록번호 애트리뷰트가 있다면 그것) |
| 외래 키(foreign key)   | 다른 (또는 같은) 릴레이션의 기본 키를 참조하는 애트리뷰트 집합     | 등록의 학번                             |

릴레이션 `R(A_1, A_2, \ldots, A_n){:math}`의 애트리뷰트 집합 `K = \{A_i, A_j, \ldots, A_k\}{:math}`가 후보 키가 되려면 다음 두 성질을 만족해야 한다.

| 성질               | 조건                                                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 유일성(uniqueness) | 각 튜플에 대해 K의 값 `\langle v_i, v_j, \ldots, v_k \rangle{:math}`는 유일하다                                                             |
| 최소성(minimality) | K는 튜플을 유일하게 식별하는 데 필요한 애트리뷰트만 포함한다. {학번, 이름}은 학번만으로 식별되므로 이름이 불필요해 최소성을 만족하지 않는다 |

> [!WARNING]
> 강의록은 슈퍼 키를 "유일성은 만족하지만 최소성은 만족하지 않는 애트리뷰트의 집합"으로 설명해 후보 키와 구별한다. 정의상으로는 유일성만 요구하므로 최소성까지 만족하는 후보 키도 슈퍼 키에 속한다. ==후보 키는 최소인 슈퍼 키이고, `\text{기본 키} \subseteq \text{후보 키} \subseteq \text{슈퍼 키}{:math}`의 포함 관계가 성립한다.==

### 외래 키

릴레이션 R의 애트리뷰트 집합 FK가 릴레이션 S의 기본 키일 때, FK를 R의 외래 키라 한다.

- FK의 도메인은 S의 기본 키의 도메인과 같다.
- FK의 값은 S에 있는 기본 키 값이거나 널이다.
- R을 참조 릴레이션(referencing relation), S를 피참조 릴레이션(referenced relation)이라 한다.
- R과 S는 같은 릴레이션일 수도 있다.

```text
-- R ≠ S: 학과장교수번호는 교수의 기본 키를 참조
교수 (교수번호, 교수이름, 학과번호, 직급)
학과 (학과번호, 학과이름, 학과장교수번호, 학생수)
등록 (학번, 과목번호, 성적)         -- 학번은 학생을, 과목번호는 과목을 참조

-- R = S: 학장교수번호가 같은 릴레이션의 교수번호를 참조
교수1 (교수번호, 교수이름, 학과번호, 학장교수번호)
```

==등록 릴레이션처럼 외래 키 두 개가 합쳐져 기본 키가 되는 경우도 많다.==

## 무결성 제약

| 제약                               | 규칙                                                          | 위반 예                                          |
| ---------------------------------- | ------------------------------------------------------------- | ------------------------------------------------ |
| 개체 무결성(entity integrity)      | 기본 키 값은 언제든 널일 수 없다                              | 학번이 널인 학생 튜플 삽입                       |
| 참조 무결성(referential integrity) | 외래 키 값은 피참조 릴레이션의 기본 키 값이거나 널이어야 한다 | 학생 릴레이션에 없는 학번 600으로 등록 튜플 삽입 |

널은 정보가 없음을 명시적으로 표현하는 특수한 데이터 값이며, [릴레이션의 특성](#릴레이션의-특성) 절에서 본 두 경우(unknown, inapplicable)를 표현한다.

==이 제약조건은 데이터베이스 상태가 항상 만족해야 한다.== **데이터베이스 상태(database state)** 는 어느 한 시각에 데이터베이스에 저장된 모든 데이터 값이며, 데이터베이스 인스턴스(스키마에 포함된 모든 릴레이션 인스턴스의 집합)라고도 한다. 상태는 삽입·삭제·변경 연산으로 계속 바뀌므로, DBMS는 상태가 바뀌어도 무결성 제약을 항상 만족시켜야 한다. SQL에서 이를 명세하는 `PRIMARY KEY{:sql}`, `FOREIGN KEY … ON DELETE{:sql}` 구문은 [SQL 데이터 정의문 글](/memo/db-sql-ddl-dml)에서 다룬다.

<details>
<summary>2. 튜플에 순서가 없는 이유</summary>

> 릴레이션에서 튜플은 왜 순서가 없는가?

==릴레이션은 튜플을 원소로 하는 집합이고, 집합의 원소에는 순서가 없다.== 학생 릴레이션의 다섯 튜플을 어떤 순서로 나열해도 같은 릴레이션이다. 테이블로 그리면 위아래 순서가 생기지만, 그 순서는 표현 방식의 산물일 뿐 릴레이션의 정보가 아니다.

</details>

<details>
<summary>3. 튜플이 중복될 수 없는 이유</summary>

> 릴레이션에서 같은 튜플은 왜 중복될 수 없는가?

릴레이션은 집합이고, 집합에는 같은 원소가 두 번 포함되지 않는다. 그래서 릴레이션의 튜플은 모두 서로 다르며, 이 성질이 13번에서 다루는 후보 키 존재의 근거가 된다.

</details>

<details>
<summary>4. 릴레이션의 특성</summary>

> 릴레이션의 특성을 설명해 보라.

[릴레이션의 특성](#릴레이션의-특성) 절의 네 가지다. 튜플의 유일성과 무순서성은 릴레이션이 튜플의 집합이라서, 애트리뷰트의 무순서성은 스키마가 애트리뷰트의 집합이라서 성립한다. 애트리뷰트의 원자성은 값이 논리적으로 분해할 수 없는 원자 값이어야 한다는 조건이며, 널도 원자 값으로 취급한다.

</details>

<details>
<summary>5. 애트리뷰트 무순서성의 뜻과 구현</summary>

> 릴레이션에서 애트리뷰트 사이에 순서가 없다는 것은 어떤 뜻이며 어떻게 구현할 수 있는가?

릴레이션 스키마가 애트리뷰트의 순서 리스트가 아니라 집합으로 정의된다는 뜻이다. `학생(학번, 이름, 학년, 학과)`와 `학생(이름, 학번, 학과, 학년)`은 같은 스키마다.

구현은 튜플을 위치 기반 값의 나열 `<100, 나수영, 4, 컴퓨터>`가 아니라 `<애트리뷰트 이름:값>` 쌍의 집합 `{학번:100, 이름:나수영, 학년:4, 학과:컴퓨터}`로 표현하는 방식이다. 값을 위치가 아닌 애트리뷰트 이름으로 찾으므로, 내부 저장 구조에서 필드를 어떤 순서로 배치해도 결과가 같다. SQL에서 `SELECT 이름, 학번{:sql}`처럼 열을 이름으로 지정하는 것도 같은 원리다.

</details>

<details>
<summary>6. 테이블과 내부 표현의 관계</summary>

> 릴레이션을 보통 테이블로 표현하는데, 이것은 컴퓨터 내부에 저장된 릴레이션을 표현한 것인가? 아니라면 외부 표현과 내부 표현의 관계와, 서로 달라도 되는 이유를 설명하라.

아니다. 릴레이션은 추상적 개념이고 테이블은 그것을 기술하는 구체적 표현 하나일 뿐이다. 하나의 릴레이션은 여러 형태의 테이블로 표현될 수 있고, 내부에 저장되는 구조는 물리적 설계에 따라 독립적으로 정해진다. ==외부의 릴레이션과 내부 표현 사이의 사상(mapping)은 DBMS의 물리적 데이터 독립성이 지원하므로, 둘의 구조가 달라도 된다.== 내부 구조를 바꿔도 사용자가 조회하는 릴레이션은 그대로다.

</details>

<details>
<summary>7. 키의 정의와 널 값</summary>

> 키를 정의하고 그 특성을 설명하라. 널 값과 키의 특성은 어떤 관계가 있는가?

키는 릴레이션의 각 튜플을 유일하게 식별하는 애트리뷰트 집합이며, 후보 키는 유일성과 최소성을 만족한다([키](#키) 절). 최소성은 키를 구성하는 애트리뷰트 중 하나라도 빼면 유일성이 깨지는 성질이다.

널과의 관계는 기본 키에서 드러난다. 기본 키 값이 널이면 그 튜플을 식별할 수 없으므로, ==기본 키에 속한 애트리뷰트는 어느 시각에도 널 값을 가질 수 없다.== 이것이 개체 무결성이다.

</details>

<details>
<summary>8. 키의 종류와 관계</summary>

> 키에는 어떤 종류가 있고 그들 간에는 어떤 관계가 있는가? 슈퍼 키와 후보 키의 차이점을 설명하라.

| 키      | 다른 키와의 관계                                              |
| ------- | ------------------------------------------------------------- |
| 슈퍼 키 | 유일성을 만족하는 모든 애트리뷰트 집합                        |
| 후보 키 | 슈퍼 키 중 최소성까지 만족하는 것                             |
| 기본 키 | 후보 키 중 설계자가 지정한 하나                               |
| 대체 키 | 기본 키를 제외한 나머지 후보 키                               |
| 외래 키 | 다른(또는 같은) 릴레이션의 기본 키를 참조하는 애트리뷰트 집합 |

포함 관계는 `\text{기본 키} \subseteq \text{후보 키} \subseteq \text{슈퍼 키}{:math}`이고, `\text{후보 키} = \text{기본 키} \cup \text{대체 키}{:math}`다. 슈퍼 키와 후보 키의 차이는 최소성이다. 학생 릴레이션에서 {학번, 이름}은 슈퍼 키지만 이름을 빼도 유일하므로 후보 키가 아니고, {학번}은 슈퍼 키이면서 후보 키다.

</details>

<details>
<summary>9. 외래 키의 정의와 중요성</summary>

> 외래 키란 무엇이며 왜 중요한지 설명하라.

릴레이션 R의 애트리뷰트 집합 FK가 릴레이션 S의 기본 키일 때 FK를 R의 외래 키라 하며, FK의 값은 S에 있는 기본 키 값이거나 널이다([외래 키](#외래-키) 절). 외래 키가 중요한 이유는 ==관계 데이터 모델에서 릴레이션 사이, 즉 개체와 개체 사이의 관계를 표현하는 수단==이기 때문이다. 등록 릴레이션은 학번과 과목번호라는 두 외래 키로 학생과 과목을 연결한다. 외래 키가 존재하지 않는 값을 가리키면 이 연결이 깨지므로, 참조 무결성으로 외래 키 값을 제한한다.

</details>

<details>
<summary>10. 납품 데이터베이스의 키와 무결성</summary>

> 다음 S(납품업자), P(제품), SP(발송) 릴레이션 스키마가 있다.

```text
S  (Sno, Sname, Status, City)       -- 납품업자, 기본 키 Sno
P  (Pno, Pname, Colour, Weight)     -- 제품, 기본 키 Pno
SP (Sno, Pno, Qty)                  -- 발송, 기본 키 {Sno, Pno}
```

#### (1) S의 슈퍼 키와 개체 무결성

> 릴레이션 S에서 슈퍼 키의 예를 하나 들고, 개체 무결성 제약을 설명하라.

S의 슈퍼 키 예는 {Sno, Sname}이다. Sno만으로 튜플이 유일하므로 Sno를 포함한 애트리뷰트 집합은 모두 슈퍼 키이고, Sname은 최소성 측면에서 불필요하다. {Sno} 자체도 슈퍼 키이며 동시에 후보 키다.

개체 무결성은 S의 기본 키 Sno가 어느 시각에도 널일 수 없다는 제약이다. SP에서는 기본 키 {Sno, Pno}의 어느 한 애트리뷰트도 널일 수 없다.

#### (2) 참조 무결성

> 위 스키마를 예로 참조 무결성 제약을 설명하라.

SP의 Sno는 S의 기본 키를, SP의 Pno는 P의 기본 키를 참조하는 외래 키다. ==참조 무결성에 따라 SP의 Sno 값은 S에 있는 Sno 값이어야 하고, Pno 값은 P에 있는 Pno 값이어야 한다.== 다만 SP에서는 Sno와 Pno가 기본 키의 구성 애트리뷰트이므로 개체 무결성 때문에 널도 허용되지 않는다.

| 연산                                              | 결과                                           |
| ------------------------------------------------- | ---------------------------------------------- |
| S에 없는 Sno 값 S9로 SP 튜플 `<S9, P1, 100>` 삽입 | 참조 무결성 위반                               |
| SP가 참조하는 S1 튜플을 S에서 삭제                | 참조 무결성 위반 (거부하거나 연쇄 삭제로 처리) |
| SP의 Pno를 P에 없는 값으로 갱신                   | 참조 무결성 위반                               |

</details>

<details>
<summary>11. 데이터베이스 상태와 연산</summary>

> 데이터베이스 상태란 무엇이며 어떤 의미를 갖는가? 데이터베이스 연산과 어떤 관계가 있는가?

데이터베이스 상태는 어느 한 시각에 데이터베이스에 저장된 모든 데이터 값이며, 데이터베이스 스키마에 포함된 모든 릴레이션 인스턴스의 집합인 데이터베이스 인스턴스와 같다. 데이터를 처음 적재한 초기 상태 이후 삽입·삭제·변경 연산이 실행될 때마다 한 상태에서 다른 상태로 바뀐다. ==연산 전 상태와 연산 후 상태가 모두 무결성 제약을 만족해야 하며, 제약을 깨는 연산은 DBMS가 거부해야 한다.==

</details>

<details>
<summary>12. 무결성 제약을 유지하는 방법</summary>

> 무결성 제약은 어떤 면에서 시간에 독립적이다. 데이터베이스 내용이 변하는 과정에서 무결성 제약을 유지하는 기법과 구현 방법을 설명하라.

무결성 제약은 특정 시각에만 만족하면 되는 조건이 아니라 데이터베이스가 항상 만족해야 하는 조건이다. 그래서 스키마에 포함된 무결성 규정을 데이터 사전(카탈로그)에 보관하고, 삽입·삭제·갱신 연산을 실행할 때마다 변경된 데이터에 적용해 검사한다. 이 일은 DBMS의 무결성 부시스템(integrity subsystem)이 담당한다. SQL에서는 `PRIMARY KEY{:sql}`, `FOREIGN KEY{:sql}`, `CHECK{:sql}` 같은 제약조건을 테이블 정의에 명세하면 DBMS가 연산마다 검사한다.

</details>

<details>
<summary>13. 모든 릴레이션이 후보 키를 갖는 이유</summary>

> 모든 릴레이션은 반드시 후보 키를 갖는다고 볼 수 있다. 그 이유를 설명하라.

릴레이션은 튜플의 집합이라 모든 튜플이 서로 다르다. 따라서 애트리뷰트 전체의 집합은 항상 유일성을 만족하는 슈퍼 키이고, 여기서 빼도 유일성이 유지되는 애트리뷰트를 하나씩 제거하면 ==최소성까지 만족하는 후보 키가 반드시 남는다.== 제거할 애트리뷰트가 없으면 애트리뷰트 전체가 후보 키다.

</details>

<details>
<summary>14. 기본 키의 유일성과 개체 무결성</summary>

> 기본 키의 유일성 조건과 개체 무결성 조건을 비교 설명하라.

| 조건        | 내용                                     |
| ----------- | ---------------------------------------- |
| 유일성      | 모든 튜플의 기본 키 값이 서로 다르다     |
| 개체 무결성 | 기본 키에 속한 애트리뷰트는 널일 수 없다 |

기본 키 값의 전부 또는 일부가 널이면 그 튜플을 다른 튜플과 구별할 수 없어 유일성이 깨진다. ==개체 무결성은 기본 키의 유일성을 유지하기 위한 제약이다.==

</details>

## 정리

- 릴레이션은 스키마(정적)와 인스턴스(동적)로 구성되며, 수학적으로는 도메인들의 카티션 프로덕트의 부분집합이다.
- 릴레이션은 튜플이 유일하고 순서가 없으며, 애트리뷰트에도 순서가 없고 값은 원자 값이다.
- 후보 키는 유일성과 최소성을 만족하고, 그중 하나가 기본 키다. 외래 키는 다른 릴레이션의 기본 키를 참조한다.
- 개체 무결성은 기본 키에 널을 금지하고, 참조 무결성은 외래 키가 존재하는 값을 가리키게 한다.
