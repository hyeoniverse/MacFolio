블로그 글에 공유 단추를 달려고 보니, 공유할 주소가 없었다.

MacFolio는 macOS 데스크톱을 흉내 낸 **페이지 하나**짜리 앱이다. 메모 앱에서 어떤 글을 열든, Safari에서 어떤 탭을 보든 주소 막대에는 늘 `macfolio.hyeoniverse.com`만 있다. 이 주소를 보내면 받은 사람은 로딩 화면 → 데스크톱에서 시작해 메모 앱을 열고 그 글을 직접 찾아야 한다.

## 주소를 정했다

```text
/memo/<글 주소>        예: /memo/cra-to-vite
/safari/<프로젝트 id>  예: /safari/sproutfarm
```

글 주소(slug)는 메모 앱이 글을 구분하는 데 원래 쓰던 값이다. 저장소의 글은 파일 이름이 그대로 주소다. 프로젝트 id도 Safari 탭이 원래 쓰던 값이다. 한글처럼 주소에 그대로 쓸 수 없는 글자는 `encodeURIComponent`로 인코딩하고, 읽을 때 되돌린다. 깨진 인코딩(`%E0%A4%A`)은 주소가 없는 것으로 친다.

## 없는 경로를 열면

프론트엔드는 Cloudflare Workers에서 정적 파일로만 서빙한다. `/memo/cra-to-vite`라는 파일은 없다. 그런데 `wrangler.jsonc`에 처음부터 이 한 줄이 있었다.

```jsonc
"assets": {
	"directory": "./apps/react/dist",
	"not_found_handling": "single-page-application",
}
```

없는 경로를 열면 404 대신 `index.html`을 돌려준다. 그래서 서버는 고칠 것이 없고, **앱이 시작할 때 경로를 읽기만** 하면 된다.

![글 주소로 들어와서 그 글이 열리기까지](./images/app-links-flow.svg '서버는 index.html만 주고, 나머지는 앱이 시작할 때 처리한다')

## 처음 값으로 연다

경로는 페이지를 연 순간에 한 번만 읽는다. 앱이 곧 주소 막대를 바꾸기 때문이다.

```ts
const initial = parseAppPath(window.location.pathname); // { app: 'memo', id: 'cra-to-vite' }
export const linkedId = (app: LinkedApp) => (initial?.app === app ? initial.id : null);
```

이 값을 상태의 **처음 값**으로 쓴다. 열고 나서 이펙트로 옮기면 첫 화면이 한 번 그려졌다가 바뀐다.

- 앱 상태: 그 앱을 실행 중, 맨 앞(zIndex 2)으로 시작한다. 휴대폰은 원래 홈 화면에서 시작하지만, 링크로 들어오면 그 앱부터 보인다
- 메모: `useState(() => linkedId('memo'))`로 그 글을 고른 채 시작한다. 좁은 화면(폴더 → 목록 → 본문)은 본문 칸부터 보인다
- Safari: 그 프로젝트 탭을 고른 채 시작한다. 없는 id면 원래대로 첫 탭

서버에만 있는 글(관리자가 쓴 글)은 저장소 글보다 늦게 온다. 그래서 고른 글 주소를 상태에 들고 있다가, 서버 글이 도착하면 그때 그 글이 보인다.

![휴대폰에서 글 주소로 들어왔을 때](./images/app-links-mobile.jpg '홈 화면 대신 메모 앱의 본문부터. 오른쪽 위가 공유 단추')

## 주소 막대는 맨 앞 창을 따른다

링크로 들어오는 것만큼, **보고 있는 화면의 주소가 주소 막대에 있는 것**도 중요하다. 새로 고침해도 그 글이 남고, 주소 막대를 복사해도 된다.

처음에는 메모 앱이 고른 글이 바뀔 때마다 직접 `history.replaceState`를 불렀다. Safari도 같은 일을 하게 되자 둘이 주소를 서로 덮었다. 메모를 보고 있는데 뒤에 있는 Safari의 탭 주소가 남는 식이었다.

그래서 주소를 바꾸는 곳을 하나로 모았다.

1. 앱은 "지금 내가 보여 주는 항목"만 알린다: `setAppAddress('memo', slug)`
2. 앱 상태(창 순서를 아는 곳)가 **맨 앞 창**의 항목으로 주소를 바꾼다

```ts
useEffect(() => {
	const front = () => /* 실행 중이고 최소화하지 않은 앱 중 zIndex가 가장 큰 앱 */;
	syncAddressBar(front());
	return appAddresses.subscribe(() => syncAddressBar(front()));
}, [apps]);
```

창을 앞으로 가져오거나 닫으면 `apps`가 바뀌고, 앱이 항목을 바꾸면 저장소가 알린다. 둘 다 같은 함수로 주소를 정한다.

`pushState`가 아니라 `replaceState`를 썼다. 글을 고를 때마다 방문 기록이 쌓이면, 뒤로 가기를 수십 번 눌러야 사이트를 떠날 수 있다. 이 사이트에서 뒤로 가기는 "사이트 밖으로"가 자연스럽다.

### 처음 보이는 창은 주소를 덮지 않는다

데스크톱에서는 Safari가 처음부터 열려 있다. 처음 만든 대로라면 사이트 주소로 들어오자마자 주소 막대가 `/safari/newpick`(첫 탭)으로 바뀌었다. 사이트를 보러 왔는데 주소가 멋대로 바뀌고, 그 주소를 복사하면 사이트가 아니라 프로젝트 하나를 보내게 된다. Dock의 "공유"(지금 주소를 복사한다) 테스트가 이걸 잡았다.

그래서 앱이 주소를 알리는 건 **링크로 들어왔거나 사람이 직접 고른 뒤부터**로 했다.

- Safari: 링크로 연 탭이거나, 탭·이전/다음·시작 페이지에서 직접 고른 뒤
- 메모: 링크로 연 글이거나, 목록에서 직접 고른 뒤 (처음에 저절로 보이는 맨 위 글은 아니다)

또 맨 앞 앱이 아직 아무것도 알리지 않았으면(글을 불러오는 중) 들어온 주소를 그대로 둔다. 불러오는 사이에 새로 고침해도 링크가 남는다.

## 공유 단추

메모는 글 위 도구 막대에, Safari는 주소창 옆에 공유 단추를 두었다. Safari에서 이 자리는 원래 주소창과 똑같이 데모를 새 탭에서 여는 단추였다. 이제는 이 프로젝트 페이지(MacFolio 안의 주소)를 보낸다. 데모는 주소창을 누르면 열린다.

```ts
if (navigator.share && matchMedia('(pointer: coarse)').matches) {
	await navigator.share({ title, url }); // 휴대폰: 메시지·카카오톡으로 바로
} else {
	await navigator.clipboard.writeText(url);
	notify({ app, title: '링크 복사됨', body: `‘${title}’ 링크를 복사했습니다.` });
}
```

아이콘은 iOS·macOS의 공유 모양(위가 트인 둥근 네모에서 화살표가 올라오는 모양)으로 했다. Font Awesome 무료 아이콘에는 이 모양이 없다. 비슷한 `arrow-up-from-bracket`은 아래가 받침대 모양이라, SVG로 직접 그려 공용 컴포넌트(`ShareIcon`)로 두었다. 글자 크기(`1em`)와 글자색(`currentColor`)을 따라서 도구 막대, ••• 메뉴, Safari 어디에 두어도 옆의 아이콘과 크기·색이 맞는다.

데스크톱 Chrome·Safari에도 `navigator.share`가 있다. 하지만 마우스로 쓰는 화면에서는 운영체제 공유 창보다 "복사됨" 알림이 빠르다. 그래서 손가락으로 쓰는 화면(`pointer: coarse`)에서만 공유 시트를 연다. 공유 시트를 그냥 닫으면(`AbortError`) 아무것도 하지 않는다.

![메모의 공유 단추와 알림](./images/app-links-memo-share.jpg '도구 막대의 공유 단추를 누르면 macOS 알림처럼 "링크 복사됨"')

![Safari의 공유 단추](./images/app-links-safari-share.jpg '주소창은 데모를 열고, 옆의 공유 단추는 이 프로젝트 페이지 주소를 복사한다')

게시하지 않은 글(관리자의 새 메모)에는 공유 단추가 없다. 방문자에게는 없는 글이라 주소를 보내도 열리지 않는다.

### 단추 하나에 도구 막대가 넘쳤다

전체 E2E를 돌리자, 이 기능과 상관없어 보이는 검색 칸 테스트가 실패했다. "검색 칸에 초점이 가면 도구가 접히고, 검색 칸은 **오른쪽 끝을 지킨 채** 왼쪽으로 넓어진다"를 보는 테스트다. 오른쪽 끝이 11.5px 움직였다.

관리자로 글을 고치는 중에는 도구 막대에 서식 도구가 함께 올라온다. 창의 기본 폭(900px)에서는 여기에 공유 단추 하나(30px + 간격)가 더해지자 도구 막대가 넘쳐, 검색 칸이 오른쪽으로 밀려나 있었다. 도구가 접히면 자리가 남아 제자리로 돌아오니, 그 차이가 "움직였다"로 잡힌 것이다.

관리자는 그 자리에서 주로 글을 고친다. 그래서 고치는 중에는 공유를 도구 막대에서 빼고 ••• 메뉴에만 두었다. 방문자의 도구 막대에는 서식 도구가 없어 그대로 둔다.

## 테스트

E2E로 여섯 가지를 본다.

- `/memo/cra-to-vite`로 들어오면 그 글이 열리고, 다른 글을 고르면 주소가 바뀌고, 창을 닫으면 사이트 주소로 돌아간다
- 공유 단추가 글 주소를 클립보드에 넣고 알림을 띄운다
- `/safari/sproutfarm`로 들어오면 그 탭이 열리고, 탭을 바꾸면 주소도 바뀐다
- 주소 막대가 맨 앞 창을 따른다 (Safari를 앞으로 → 사이트 주소, 탭을 고르면 탭 주소, 메모를 앞으로 → 글 주소)
- 사이트 주소로 들어오면 처음 열린 Safari가 주소를 바꾸지 않는다
- 관리자가 고치는 중에는 공유가 ••• 메뉴에 있고, 눌러도 글 주소를 복사한다

휴대폰(iPhone·Pixel 흉내)에서는 글 주소로 들어오면 홈 화면 대신 메모 앱의 본문이 보이는지 본다. 경로를 만들고 읽는 함수는 단위 테스트로 본다: 한글 주소, 깨진 인코딩, 주소가 없는 앱.

## 글 안의 링크도 사이트 안에서

글끼리 서로 링크를 걸기 시작하자(`[백업 스크립트](/memo/db-backup)`) 문제가 보였다. 본문의 링크는 모두 새 탭으로 열리게 되어 있어서, 다른 글로 가는 링크를 누르면 사이트가 새 탭에 처음부터 다시 떴다. 로딩 화면부터 다시 보고, 메모 앱을 다시 열어야 그 글이 보였다.

링크를 그리는 곳(`MarkdownLink`)이 주소를 먼저 본다. 같은 사이트의 앱 항목(`/memo/<글>`, `/safari/<프로젝트>`)이면 Finder가 글을 열 때와 같은 길(`openRequest`)로 그 앱에 열어 달라고 한다. 메모 글은 지금 메모 앱에서 그 글로 바뀌고, 주소 막대도 그 글로 바뀐다. 바깥 링크는 전처럼 새 탭이다. ⌘·Ctrl을 누르거나 가운데 단추로 누르면 브라우저 기본대로 새 탭에서 열 수 있게, 그때는 가로채지 않는다. `href`는 그대로 `/memo/db-backup`이라 링크 주소 복사도 된다.

같은 사이트인지는 주소를 `new URL(href, 사이트 주소)`로 풀어 출처(origin)를 비교한다. `https://evil.example/memo/db-backup`처럼 경로만 같은 바깥 주소는 바깥 링크로 남는다.

## 남은 것

카카오톡이나 슬랙에 링크를 붙이면 보이는 **미리 보기(제목·설명·그림)**는 아직 사이트 전체의 것이다. 미리 보기는 링크를 받은 서버가 HTML의 `<meta property="og:…">`를 읽어 만든다. 그런데 어떤 경로든 같은 `index.html`이 나가고, 글은 JS가 연 뒤에야 정해진다. 글마다 다른 미리 보기를 보이려면, Worker가 `index.html`을 돌려주기 전에 그 글의 제목·요약을 `<meta>`에 넣어야 한다(`HTMLRewriter`). 정적 파일만 서빙하던 구성에 Worker 스크립트가 처음 생기는 일이라 따로 하기로 했다.
