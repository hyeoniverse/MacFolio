macOS 화면 맨 위의 메뉴 막대는 창마다 메뉴가 붙는 Windows와 다르게 화면에 하나뿐이고, 내용은 지금 사용 중인 앱(맨 앞 창의 앱)에 따라 교체된다. 메모를 쓰다가 음악 창을 누르면 굵은 앱 이름이 '음악'으로 바뀌고, 메뉴도 음악 앱의 메뉴로 바뀐다. 전날까지 MacFolio의 메뉴 막대는 파일·보기·윈도우·도움말이 열리기는 했지만 내용이 모든 앱에 공통이었다. 이날은 이 메뉴를 앱마다 다르게 채우고, 메뉴 항목을 키보드로 실행하는 단축키를 넣었다.

![10월 6일 작업 흐름](./images/day-1006-timeline.svg '메뉴 막대 작업과 이어진 정리 작업의 순서')

## 앱별 메뉴 등록

메뉴 막대는 화면 맨 위의 공통 컴포넌트이고, "새로운 메모"나 "새로운 탭" 같은 동작은 각 앱 컴포넌트 안의 상태에 의존한다. 그래서 메뉴 막대가 앱 내부 동작을 직접 호출하지 않고, ==각 앱이 자기 메뉴 항목을 메뉴 막대에 등록==하는 구조로 만들었다. 앱이 맨 앞으로 오면 그 앱이 등록한 항목이 공통 메뉴와 병합되어 표시된다. 병합 구조는 [앱이 등록한 메뉴를 공통 메뉴와 병합하는 메뉴 막대 구조](/memo/menubar-menus)에 있다.

| 단계 | 메뉴를 등록한 앱                                            | PR                                                       |
| ---- | ----------------------------------------------------------- | -------------------------------------------------------- |
| 1    | 메모, Safari, Finder, 음악                                  | [#111](https://github.com/hyeoniverse/MacFolio/pull/111) |
| 2    | 메일, 터미널, 시스템 설정, iframe 앱(프로젝트 앱, API 문서) | [#113](https://github.com/hyeoniverse/MacFolio/pull/113) |

![현재의 메뉴 막대 메뉴](./images/day-1006-menu.jpg '메모가 맨 앞일 때 메뉴 막대의 메뉴를 연 현재 화면')

그 전에 작은 버그 두 개를 고쳤다.

- 메모 글 안의 다른 글 링크(`/memo/글주소`)를 누르면 새 탭이 열렸다. 사이트 안의 주소이면 새 탭 대신 같은 페이지의 메모 창에서 그 글을 열게 했다([#109](https://github.com/hyeoniverse/MacFolio/pull/109), [History API로 SPA 창 상태를 /memo·/safari 주소와 연결하기](/memo/app-links))
- 메뉴 막대를 클릭하면 현재 앱 이름이 Finder로 바뀌었다. 창 밖(바탕화면)을 누르면 Finder가 활성 앱이 되는데, 메뉴 막대 클릭도 창 밖 클릭으로 처리되었기 때문이다. 메뉴 막대와 거기서 연 메뉴는 눌러도 활성 앱을 유지하게 했다([#110](https://github.com/hyeoniverse/MacFolio/pull/110), [창 순서와 분리한 활성 앱 상태로 메뉴 막대 앱 이름 맞추기](/memo/menu-bar-app-name))

## 단축키: ⌘ 대신 ⌥

### 배경: 수식 키와 브라우저가 예약한 단축키

단축키는 ⌘(Command)·⌥(Option)·⇧(Shift)·⌃(Control) 같은 수식 키와 글자 키를 함께 누르는 조합이다. macOS 앱은 ⌘N(새로 만들기), ⌘T(새 탭), ⌘W(닫기)를 공통으로 사용한다.

![Mac 키보드 왼쪽 아래의 수식 키](./images/menubar-menus-modifier-keys.jpg '왼쪽 아래 줄의 fn, ctrl, alt(⌥), cmd(⌘)와 위쪽 두 줄의 ⇧. MacFolio 단축키는 ⌘ 대신 ⌥ 조합을 사용한다')

웹 페이지는 `keydown` 이벤트로 키 입력을 받고, `preventDefault()`를 호출하면 그 키의 기본 동작을 취소할 수 있다. 예를 들어 ⌘F를 받아 브라우저의 찾기 창 대신 페이지 자체의 검색 창을 열 수 있다. 그러나 ⌘N·⌘T·⌘W는 다르다. 이 키는 ==브라우저가 페이지보다 먼저 처리==해 새 창·새 탭·탭 닫기를 실행하고, 페이지에는 이벤트가 전달되지 않는다. 페이지가 이벤트를 받지 못하므로 `preventDefault()`로 막을 수도 없다. W3C의 Keyboard Lock 명세도 일부 키는 기본적으로 브라우저나 운영체제가 가져가 웹 앱이 받을 수 없다고 설명한다.

![⌘W는 브라우저가 처리하고 ⌥W는 페이지의 keydown 처리기까지 전달되는 경로](./images/day-1006-key-routing.svg '같은 W 키라도 수식 키에 따라 처리하는 주체가 다르다. ⌥ 조합은 페이지까지 전달된다')

그래서 macOS 단축키와 같은 글자에 ⌥를 조합했다([#112](https://github.com/hyeoniverse/MacFolio/pull/112)). ⌘N이면 ⌥N, ⌘W이면 ⌥W다. ⌘F처럼 페이지가 받을 수 있는 키는 그대로 사용한다.

| 키               | 동작                                       |
| ---------------- | ------------------------------------------ |
| ⌥N               | 새로운 메모(관리자) · 새로운 Finder 윈도우 |
| ⌥T · ⌥W          | 새로운 탭 · 탭 닫기 (Safari)               |
| ⌥[ · ⌥] · ⌥↑     | 뒤로 · 앞으로 · 상위 폴더 (Finder)         |
| ⌥Space · ⌥← · ⌥→ | 재생/일시정지 · 이전 곡 · 다음 곡 (음악)   |
| ⌥W · ⌥M          | 윈도우 닫기 · 최소화 (공통)                |

### 글자 대신 키 위치로 비교

⌥ 조합에는 함정이 하나 있다. macOS에서 ⌥는 특수 문자를 입력하는 키이기도 하다. ⌥W를 누르면 `KeyboardEvent.key`는 `"w"`가 아니라 `"∑"`가 된다. 그래서 단축키는 입력된 글자(`key`) 대신 눌린 키의 물리적 위치(`code`)로 비교한다. ⌥W의 `code`는 수식 키와 관계없이 `"KeyW"`다.

| 누른 키 | `key` | `code` | `altKey` |
| ------- | ----- | ------ | -------- |
| W       | `w`   | `KeyW` | `false`  |
| ⌥W      | `∑`   | `KeyW` | `true`   |

같은 이유로 입력 칸이나 글 편집기에 커서가 있으면 ⌘ 없는 단축키를 실행하지 않는다. 그렇지 않으면 ⌥로 특수 문자를 입력하려는 시각에 메뉴 동작이 실행된다. Windows·Linux에서는 ⌥ 자리에 Alt를 사용하고, 메뉴에도 `Alt+W`로 표시한다.

### 중복된 ⌥W

도움말에 키보드 단축키 목록을 추가하고 화면에 띄워 보니, Safari에 '탭 닫기 ⌥W'와 '윈도우 닫기 ⌥W'가 함께 있었다. 키를 누르면 메뉴 항목을 등록 순서대로 탐색하다가 처음 일치하는 항목을 실행한다. ==같은 키가 두 항목에 지정되면 앞쪽 항목만 동작==하므로, 윈도우 닫기는 메뉴에 단축키가 표시되지만 실제로는 실행되지 않았다.

![Safari 메뉴에서 탭 닫기와 윈도우 닫기가 같은 ⌥W를 쓰던 상태와, 윈도우 닫기를 ⌥⇧W로 옮긴 상태](./images/day-1006-shortcut-conflict.svg '변경 전에는 첫 번째 일치인 탭 닫기에서 탐색이 끝나 윈도우 닫기가 실행되지 않았다')

| 상황                      | '윈도우 닫기' 단축키 |
| ------------------------- | -------------------- |
| 앱이 ⌥W를 사용하지 않음   | ⌥W                   |
| 앱이 ⌥W를 사용함 (Safari) | ⌥⇧W                  |

앱이 ⌥W를 이미 쓰면 윈도우 닫기를 ⌥⇧W로 옮겼다. macOS Safari도 ⌘W는 탭 닫기, ⌘⇧W는 윈도우 닫기로 같은 규칙을 쓴다. 단축키 목록을 화면에 띄우지 않았다면 놓쳤을 문제다.

![현재의 키보드 단축키 목록](./images/day-1006-shortcuts.jpg '도움말 → 키보드 단축키의 현재 화면')

## 메뉴 구성: 맨 앞 앱의 메뉴만

==macOS에서 메뉴 막대는 맨 앞 앱의 메뉴만 표시한다.== 예를 들어 Safari가 맨 앞이면 윈도우 메뉴에는 Safari 윈도우만 나열되고, 다크 모드 같은 시스템 설정은 앱 메뉴가 아니라 시스템 설정에 있다. 이 원칙에 맞지 않는 항목을 정리했다([#114](https://github.com/hyeoniverse/MacFolio/pull/114)).

| 메뉴         | 변경 전           | 변경 후                           |
| ------------ | ----------------- | --------------------------------- |
| 윈도우       | 다른 앱 목록 포함 | 맨 앞 앱의 윈도우 항목만          |
| 보기         | 다크 모드 포함    | 다크 모드 제외 (앱의 보기 항목만) |
| 굵은 앱 이름 | 메뉴 없음         | 앱 메뉴 (가리기, 종료)            |
| Safari       | -                 | 책갈피 메뉴 추가                  |
| 메일         | -                 | 사서함 메뉴 추가                  |

이 작업으로 이슈 [#96](https://github.com/hyeoniverse/MacFolio/issues/96)(메뉴 막대를 맨 앞 앱에 맞게)의 범위를 마무리했고, 다음 날 [#113](https://github.com/hyeoniverse/MacFolio/pull/113)을 머지하면서 닫았다. 전날 만든 API 자동 배포를 서버에서 한 번에 설정하도록 정리한 문서([#108](https://github.com/hyeoniverse/MacFolio/pull/108))도 이날 머지했다.

## 돌아보며

브라우저가 가로채는 키 대신 ⌥를 쓴 결정으로, 화면에 표시되는 단축키와 실제로 동작하는 단축키가 항상 일치한다. ⌘W를 표시해 두고 실제로는 브라우저 탭이 닫히는 상황이 생기지 않는다. 중복된 ⌥W는 단축키 목록을 화면에 띄워서 찾았다. 표시와 동작을 같은 데이터(메뉴 항목의 단축키 정의)에서 만들었기 때문에, 목록을 띄우는 것만으로 충돌이 드러났다.

메뉴 막대 작업은 사흘에 걸쳐 여섯 번에 나눠 진행했다. "맨 앞 앱의 메뉴만"이라는 원칙을 처음에 정했다면 #114 같은 정리 작업이 따로 필요하지 않았다. 다음 날에는 앱이 메뉴를 등록하는 시각에 메뉴 제목이 이동하면서, main에서만 실패하는 메뉴 시험까지 생겼다([10월 7일](/memo/day-1007)).

> [!TIP] 단축키를 정의할 때
> 표시 문구와 실행 조건을 같은 정의에서 만들고, 정의 전체를 한 화면에 나열해 보면 중복과 충돌을 바로 확인할 수 있다.
