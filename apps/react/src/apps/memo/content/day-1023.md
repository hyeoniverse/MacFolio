## 메모 편집기

### 저장할 때 바뀌던 Markdown ([#332](https://github.com/hyeoniverse/MacFolio/pull/332))

메모 앱의 글은 두 곳에서 온다. 저장소의 Markdown 파일(저장소 글)과, 관리자가 편집기로 게시해 DB에 저장한 글(서버 글)이다. 로컬에서 고친 저장소 글이 화면에 반영되지 않아 원인을 찾다가, 같은 주소의 글을 예전에 편집기로 게시해 DB에 남아 있는 것을 확인했다. ==서버 글은 같은 주소의 저장소 글을 대체한다==(`mergeServerPosts`). 이 과정에서 편집기 문제 셋을 함께 고쳤다.

![편집기로 저장한 태그 줄 전후](./images/day-1023-editor-tags.jpg '고치기 전에는 첫 태그 앞에 역슬래시가 붙어 저장되어 태그로 인식되지 않았다. unescapeTags가 줄 맨 앞과 목록·인용 기호 뒤의 # 가운데 제목이 될 수 없는 것만 되돌린다')

편집기는 화면의 문서를 저장할 때 remark-stringify로 Markdown 문자열을 만든다. remark-stringify는 문서 구조를 Markdown으로 되돌리는 라이브러리로, 다시 읽었을 때 의미가 바뀌지 않도록 특수 문자 앞에 `\`를 붙이는 이스케이프를 한다. 예를 들어 글 끝의 태그 줄 `#MacFolio #회고`는 저장 후 `\#MacFolio #회고`가 되어, 메모 앱이 첫 태그를 태그로 인식하지 못했다.

| 문제                                         | 원인                                                                                                                                | 수정                                                 |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 저장하면 글 끝 첫 태그가 `\#MacFolio`가 된다 | remark-stringify는 줄 맨 앞의 `#`를 무조건 이스케이프한다. CommonMark 제목은 `#` 뒤에 공백이 필요해 `#MacFolio`는 제목이 될 수 없다 | 저장 직전에 `unescapeTags`                           |
| 토글을 펼치기만 해도 '임시 저장됨'           | 펼침 여부가 문서의 `open` 속성이었다                                                                                                | 펼침을 ProseMirror 플러그인 상태(화면 상태)로 옮겼다 |
| 서버에서 고친 저장소 글을 되돌릴 수 없다     | 메뉴가 없었다                                                                                                                       | '저장소 글로 되돌리기'                               |

두 번째 문제의 배경은 ProseMirror의 상태 구분이다. ProseMirror는 문서 내용(노드와 속성)과, 문서 밖에서 화면 표시에만 쓰는 플러그인 상태를 따로 관리한다. 펼침 여부를 노드의 `open` 속성에 두면 토글을 펼치는 동작도 "문서 변경"이 되어 임시 저장이 실행됐다. 플러그인 상태로 옮기자 펼치고 접어도 문서는 바뀌지 않는다.

### 편집 중 링크 이동과 이미지 확대 ([#339](https://github.com/hyeoniverse/MacFolio/pull/339), [#340](https://github.com/hyeoniverse/MacFolio/pull/340))

편집기에서는 링크를 클릭하면 커서가 놓일 뿐 이동하지 않는다. 링크에 마우스를 올리면 링크 위 18px에 '글로 이동'·'새 탭에서 열기' 상자를 띄웠다. 이미지는 노드 뷰가 클릭을 선택·캡션 편집에 쓰므로, 돋보기 버튼과 더블클릭으로 읽기 화면과 같은 라이트박스를 연다. 노드 뷰는 ProseMirror가 특정 노드(링크, 이미지)를 직접 그리도록 맡기는 DOM 코드라 React 컴포넌트 트리 밖에 있다. 두 기능 모두 이 노드 뷰와 React 컴포넌트를 `createStore` 저장소 하나로 연결했다. 노드 뷰가 저장소에 '이 링크 위에 마우스가 있다'를 기록하면, React 쪽 상자 컴포넌트가 그 값을 읽어 표시한다.

### 비밀 글 ([#355](https://github.com/hyeoniverse/MacFolio/pull/355))

서버 글을 관리자에게만 보이게 지정한다. 글 주소를 받는 공개 경로를 `git grep`으로 모두 찾아 서버에서 필터링했다: 글 목록, 공유 카드, 댓글, 좋아요, 인기글, 조회수, 트래픽 요약, 메모 정리 내용, Worker의 첫 화면 본문, sitemap, RSS. 비밀 글 주소로 직접 요청하면 없는 글과 같은 응답을 보낸다. 저장소 글은 공개 저장소에 원문이 있어 지정할 수 없다. 자세한 과정은 [메모 비밀 글](/memo/memo-secret-posts)에 적었다.

## 화면이 보이는 동안만 다시 조회하기

폴링(polling)은 서버에 일정 간격으로 같은 요청을 다시 보내 새 값을 가져오는 방식이다. 서버가 변경을 직접 밀어 주는 SSE·WebSocket보다 단순하지만, 아무도 화면을 보지 않을 때도 요청을 보내지 않도록 멈추는 조건이 필요하다.

'활동 상태 보기'의 값과 메모 조회수는 앱을 연 시각의 값에서 바뀌지 않았다. 반대로 실시간 탭은 `setInterval`로 10초마다 조회했는데, 창을 닫아도 앱 컴포넌트가 언마운트되지 않아 ==1시간에 360번 요청이 계속 나갔다.==

| 단계 | PR                                                       | 내용                                                                                                                                                                                                                       |
| ---- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | [#353](https://github.com/hyeoniverse/MacFolio/pull/353) | `poller.ts`(응답 뒤 간격 재예약, 중복 방지, 실패 시 간격 2배·최대 10분)와 `usePolling`(탭이 보이고 창이 열려 있을 때만). 활동 상태 보기와 메모 조회수에 1분 간격으로 적용                                                  |
| 2    | [#357](https://github.com/hyeoniverse/MacFolio/pull/357) | 메시지, 메모 댓글, 메일, 위젯으로 확대. 숨은 탭에서도 돌던 `setInterval` 세 곳(메뉴 막대 두 곳, 날씨)을 옮겼다. 위젯 여러 개가 같은 값을 보면 일정 하나를 공유하고, 탭만 다시 보일 때는 간격이 지난 경우에만 바로 조회한다 |

![여러 화면이 일정 하나를 공유하는 구조](./images/live-refresh-more-shared.svg '위젯 여러 개와 앱 창이 같은 값을 보면 공유 일정 하나를 빌려 쓰고, 보는 곳이 0이면 멈춘다')

`poller.ts`의 동작을 1분 간격으로 예를 들면 아래 그림과 같다. 다음 요청은 응답이 도착한 뒤에 예약하므로, 응답이 늦어도 요청이 겹치지 않는다. 실패하면 대기 시간을 2배씩 늘리는 지수 백오프(exponential backoff)로 서버가 장애 중일 때 요청이 몰리지 않게 한다. 탭이 보이는지는 `document.visibilityState`로 판단한다. 다른 탭으로 전환하거나 브라우저를 최소화하면 이 값이 `hidden`이 되고 `visibilitychange` 이벤트가 발생한다.

![poller.ts의 요청 시각](./images/day-1023-poll-backoff.svg '정상일 때는 응답 뒤 1분마다, 연속 실패하면 2·4·8분, 상한 10분으로 늘린다. 탭이 숨으면 멈추고, 다시 보일 때 간격이 지났으면 바로 조회한다')

| 연속 실패 횟수 | 다음 요청까지 대기 |
| -------------: | -----------------: |
|              0 |                1분 |
|              1 |                2분 |
|              2 |                4분 |
|              3 |                8분 |
|         4 이상 |        10분 (상한) |

SSE·WebSocket과 비교한 이유와 확대 과정은 [visibilityState와 지수 백오프로 보이는 동안만 폴링하는 usePolling 훅과 같은 요청 묶기](/memo/activity-live-refresh)에 적었다.

## 분석과 검색

### 실시간 7일과 IP별 방문 ([#333](https://github.com/hyeoniverse/MacFolio/pull/333))

실시간 탭은 최근 30분만 보여 줘서, 서버가 마스킹된 IP를 7일 동안 보관하는데도 30분이 지난 방문은 IP로 따라갈 수 없었다. 기간(30분·3시간·24시간·7일)을 고르고, 마스킹된 IP마다 방문을 집계하는 표를 더했다. IP를 누르면 아래 방문 목록이 그 IP로 필터링된다.

![실시간 탭의 IP 표](./images/day-1023-live-ip.jpg '7일 기간의 IP 표와 203.0.113.x로 필터링한 방문 목록. 방문을 누르면 들어옴 → 글 보기 순서가 펼쳐진다. 가짜 API 자료로 촬영했다')

같은 PR에서 맥 Safari에서만 유입 경로 조합 표를 정렬하면 이름 칸 글자가 사라지던 문제도 고쳤다. 자동 시험 브라우저(Chromium, Playwright WebKit)에서는 재현되지 않았다. 이 표만 이름 칸이 버튼이고, 정렬하면 `tbody`를 다시 만들며 페이드를 건다는 차이에서 "다시 만든 버튼 + 페이드" 조합을 원인으로 추정했다. 이름이 버튼인 표는 정렬할 때 `tbody`를 다시 만들지 않는다.

### 관리자 IP 제외 ([#337](https://github.com/hyeoniverse/MacFolio/pull/337))

관리자 세션 쿠키가 붙은 방문만 집계에서 제외하고 있어, 로그인하지 않은 휴대폰으로 사이트를 확인하면 일반 방문으로 집계됐다. HMAC은 비밀 키와 입력을 함께 해시해, 키를 모르는 사람은 같은 결과를 만들 수 없게 하는 방식이다. IPv4 주소는 약 43억 개뿐이라 키 없는 SHA-256 해시는 모든 IP를 해시해 대조하면 원래 IP가 드러나지만, HMAC은 키가 없으면 대조표를 만들 수 없다. 관리자로 인증된 요청의 IP를 `HMAC-SHA256(IP_HASH_SECRET, "admin-ip:" + IP)`로 기록하고, 그 IP의 방문은 세션이 없어도 저장하지 않는다. IP 원문은 저장하지 않고, 마지막 관리자 요청 뒤 30일이 지나면 행을 삭제한다. 같은 공유기 뒤의 다른 방문자도 30일 동안 집계에서 빠지는 한계는 [개인정보 문서](https://github.com/hyeoniverse/MacFolio/blob/main/docs/privacy.md)에 적었다.

### Search Console 연결과 SSH 시간 초과 ([#360](https://github.com/hyeoniverse/MacFolio/pull/360))

검색어 탭에 Google Search Console 자료를 연결했다. Search Console은 사이트를 '속성' 단위로 등록한다. 도메인 속성은 `example.com`의 모든 하위 도메인과 http·https를 한 속성으로 묶고, URL 접두어 속성은 `https://www.example.com/`처럼 지정한 주소로 시작하는 페이지만 묶는다. 사이트를 도메인 속성(`sc-domain:`)으로 등록하면 같은 도메인의 다른 하위 도메인 페이지까지 응답에 섞인다. URL 접두어 속성을 추가로 등록하는 대신, 서버가 `searchAnalytics.query`에 `dimensionFilterGroups`(`page`, `includingRegex`)를 붙여 이 사이트 페이지만 요청하도록 했다. 이미 받아 둔 다른 하위 도메인 행은 동기화하면서 삭제한다.

![Search Console 연결 순서](./images/search-console-setup-flow.svg 'Search Console 속성과 사이트맵, Google Cloud 서비스 계정, 권한 추가, 서버 api.env 설정 순서')

서비스 계정 키를 서버로 옮기는 과정에서 `scp`가 `Operation timed out`으로 실패했다. 보안 목록은 열려 있었고 GitHub Actions 배포는 성공했다. ==원인은 접속 주소였다.== 이전에 SSH 키를 복구하며 만든 임시 VM의 공인 IP를 서버 주소로 기억하고 있었다. `known_hosts`의 기록과 Cloud Shell의 `oci compute instance list-vnics` 결과로 실제 서버 IP를 확인하고, `~/.ssh/config`에 별칭을 등록했다.

![SSH 시간 초과 원인을 좁힌 순서](./images/ssh-timeout-public-ip-diagnosis.svg '로컬 네트워크, 통신사 경로, 서버 방화벽을 차례로 배제한 뒤 접속 주소가 다른 VM의 IP라는 것을 확인했다')

## 휴대폰 화면

### 상태 표시줄 밑에 깔린 사진·팁 ([#335](https://github.com/hyeoniverse/MacFolio/pull/335))

사진 보관함을 맨 위로 올리면 첫 줄 사진이 상태 표시줄과 제목 밑에 깔렸고, 그 자리를 누르면 사진 대신 제어 센터가 열렸다. 홈 화면의 앱 21개를 하나씩 열어 상태 표시줄 영역에 보이는 글자·그림·버튼을 찾자 팁 앱도 걸렸다. 상태 표시줄이 앱 위에 겹치는 iOS 구조는 유지하고, 내용 맨 위에 상태 표시줄과 큰 제목만큼 여백을 넣었다.

![사진 보관함 전후](./images/day-1023-photos-statusbar.jpg '고치기 전에는 맨 위에서도 첫 줄이 상태 표시줄과 제목 밑에 깔렸다. 고친 뒤에는 제목 아래에서 시작하고, 스크롤해 사진이 제목 밑으로 들어가면 제목 뒤가 어두워진다')

이 PR은 방향을 여러 번 바꿨다. 상태 표시줄을 누른 위치의 버튼에 탭을 전달하는 방법과 앱 화면 전체를 상태 표시줄 아래에서 시작하는 방법을 차례로 시도했다가, 후자가 iOS와 달라 되돌리고 보관함에만 여백을 두는 방법으로 정했다. 스크롤 가장자리 흐림도 강도와 층 수를 다섯 번 조정했다.

### 사진 위젯을 누르면 그 사진 ([#354](https://github.com/hyeoniverse/MacFolio/pull/354))

사진 위젯을 누르면 사진 앱이 항상 보관함 격자로 열렸다. 기존 앱 간 요청 경로(`openRequest.ts`)로 위젯에 표시 중인 사진의 앨범과 사진 id를 넘겨, 그 앨범 안의 크게 보기로 연다. 휴대폰 홈 화면 편집 중에 위젯을 누르면 남던 요청도 막았다. [openRequest로 위젯이 표시 중인 사진을 사진 앱 크게 보기로 넘기기](/memo/photo-widget-open-current)에 적었다.

### 메시지 앱 ([#363](https://github.com/hyeoniverse/MacFolio/pull/363))

| 증상                                                       | 어긋난 두 기준                                           | 수정                                                 |
| ---------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- |
| 넓은 휴대폰 화면(641~767px)에서 검색 알약이 입력 칸을 덮음 | 휴대폰 셸 기준(767px)과 목록·대화 분리 기준(앱 폭 640px) | 나란히 보는 화면에서는 검색 알약을 목록 칸 안에 배치 |
| 키보드가 올라오면 대화 머리까지 화면 밖으로 밀림           | 레이아웃 뷰포트와 비주얼 뷰포트                          | 키보드가 있는 동안 앱 화면을 비주얼 뷰포트에 맞춤    |
| 빈 목록의 말풍선 아이콘 윗부분 잘림                        | 줄 상자 40px와 글리프 45px                               | `line-height: 1.25`                                  |

두 번째 줄의 두 뷰포트는 iOS Safari에서 크기가 다르다. 레이아웃 뷰포트는 CSS의 `position: fixed`와 `100vh`가 기준으로 삼는 영역이고, 비주얼 뷰포트는 지금 실제로 화면에 보이는 영역이다. 키보드가 올라오면 비주얼 뷰포트만 키보드 높이만큼 줄고 레이아웃 뷰포트는 그대로라, 레이아웃 뷰포트 기준으로 배치한 화면은 위쪽이 밀려 올라간다. `window.visualViewport`의 `height`·`offsetTop`으로 앱 화면을 보이는 영역에 맞췄다.

고정한 대화 머리는 처음에 불투명 단색이라 말풍선이 머리 아래에서 잘려 보였다. 옅은 그라데이션과 블러로 바꾸고, 블러는 12px에서 시작해 실제 화면을 보며 2px까지 낮췄다.

![키보드가 올라온 메시지 화면](./images/messages-layout-fixes-keyboard.jpg '키보드가 올라와도 대화 머리는 화면 위에 남고 대화와 입력 칸만 비주얼 뷰포트에 맞춰 올라간다')

### 홈 화면 위젯 끌어 옮기기 ([#365](https://github.com/hyeoniverse/MacFolio/pull/365))

편집 모드에서 위젯 순서를 바꾸려면 삭제했다가 다시 추가해야 했다. 2열 격자 배치 규칙을 순수 함수로 정리하고, 끄는 위젯은 `translate`로, 비켜 주는 위젯은 FLIP으로 움직였다. FLIP(First, Last, Invert, Play)은 요소의 처음 위치와 마지막 위치를 측정한 뒤, 마지막 위치에 놓인 요소를 `transform`으로 처음 위치까지 되돌려 놓고 그 `transform`을 0으로 애니메이션하는 기법이다. 배치는 한 번에 바꾸고 움직임은 `transform`만으로 그려 브라우저가 레이아웃을 다시 계산하지 않는다. 처음 구성에서 음악 위젯을 1쪽, GitHub 잔디를 2쪽으로 맞바꿨다.

![위젯을 끄는 중](./images/mobile-widget-reorder-drag.jpg '음악 위젯을 소개 위젯 위로 끄는 중. 소개 위젯이 아래로 비켜 준다')

같은 PR에서 한 페이지가 위젯 세 줄이 되면 모든 페이지의 위젯과 아이콘이 작아지던 문제를 찾았다. ==위젯 줄 높이를 위젯 줄 수가 가장 많은 페이지에 맞춰 계산했기 때문이다.== 줄 높이를 화면 크기로만 정하도록 바꿨다. 자세한 내용은 [Pointer Events와 FLIP으로 2열 격자 위젯 순서 바꾸기](/memo/mobile-widget-reorder)에 적었다.

## 스타일: 인용 색과 prose.css ([#361](https://github.com/hyeoniverse/MacFolio/pull/361), [#364](https://github.com/hyeoniverse/MacFolio/pull/364))

Markdown 본문의 인용(`> …`)이 보조 글자색이라 흐렸다. 인용 규칙이 블로그(`.memo-markdown`)와 문서 보기·텍스트 편집기(`.finder-doc`)에 따로 있어 둘 다 고쳐야 했다. 처음에 두 곳을 다른 PR로 올렸다가([#362](https://github.com/hyeoniverse/MacFolio/pull/362)), 같은 규칙을 두 PR이 나눠 고치면 머지 순서에 따라 결과가 달라질 수 있어 [#362](https://github.com/hyeoniverse/MacFolio/pull/362)를 닫고 [#361](https://github.com/hyeoniverse/MacFolio/pull/361) 하나로 합쳤다.

공통 규칙을 `styles/prose.css`로 옮기자 텍스트 편집기 창에서 연 문서의 코드 블록에 문법 강조 색이 없는 문제가 드러났다. 강조 색 변수(`--hl-*`)를 `[data-app='memo']`·`[data-app='finder']`에만 정의해, `data-app='textedit'` 창에서는 `var()`가 무효가 되었다. 코드 색은 `:root`의 `--color-code-*`를 직접 참조하고, 본문 요소에 공통 클래스 `.prose`를 붙였다. 선택자는 `:where(.prose) …`로 시작해 명시도(specificity)가 0이고, 화면마다 다른 값은 `--prose-*` 변수로 분리했다. 명시도는 같은 요소에 규칙이 여러 개 걸렸을 때 어느 규칙이 이기는지 정하는 점수다. `:where()` 안의 선택자는 점수에 들어가지 않으므로, 각 화면의 CSS가 클래스 하나짜리 선택자로도 공통 규칙을 덮어쓸 수 있다. [Markdown 본문 CSS를 prose.css와 --prose-* 변수로 합치기](/memo/markdown-prose-css)에 적었다.

## 성능: 재측정, 회귀, 예산

| 단계   | PR                                                       | 내용                                                                                                                                                               |
| ------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 재측정 | [#338](https://github.com/hyeoniverse/MacFolio/pull/338) | 3차 배포 후 운영 사이트 재측정: 휴대폰 98점(LCP 1.9초), 데스크톱 97점(LCP 1.0초). 같은 측정에서 명언 위젯 데이터 66KB가 첫 번들에 들어간 회귀를 찾아 `lazy`로 분리 |
| 5차    | [#367](https://github.com/hyeoniverse/MacFolio/pull/367) | 로컬 휴대폰 LCP가 회차마다 3.3초와 4.6초로 갈리던 원인 확인, 휴대폰 로딩 화면이 화면 전체를 덮도록 수정, CI 성능 예산                                              |

==LCP가 갈리던 원인은 글꼴이 아니었다.== 브라우저는 페이지를 그리는 동안 화면에서 가장 큰 요소가 바뀔 때마다 그 요소를 LCP 후보로 기록하고, 마지막 후보의 시각을 LCP로 확정한다. 후보로 기록되기 전에 DOM에서 사라진 요소는 계산에서 빠진다. Lighthouse trace에서 4초대 회차는 HTML의 시작 안내(`#boot-splash`)가 LCP 후보로 기록되기 전에 `App.tsx`가 마운트되며 그 요소를 삭제했다. 그래서 그 뒤에 그려진 다른 요소가 LCP가 되어 값이 늦어졌다.

![#boot-splash 삭제 시점과 LCP](./images/day-1023-boot-splash-lcp.svg '3.3초 회차는 #boot-splash가 LCP 후보로 기록된 뒤에 App이 마운트됐다. 4.6초 회차는 기록 전에 App이 그 요소를 삭제했다. 수정본은 로딩 화면을 누를 때까지 요소를 유지한다')

`#boot-splash`를 로딩 화면을 누를 때까지 남기자 번갈아 측정한 28회씩에서 LCP 4초 이상이 3회에서 0회로 줄었고, 첫 방문 전송량은 487KB에서 278KB로 줄었다.

![회차별 LCP](./images/site-performance-lcp-budget-runs.svg '같은 컴퓨터에서 main과 수정본을 한 회씩 번갈아 28회씩 측정한 LCP')

성능 예산(performance budget)은 번들 크기나 지표에 상한을 정해 두고, 넘으면 빌드나 CI를 실패시키는 방식이다. 4차 회귀(명언 위젯)는 수동 측정이라 늦게 찾았다. 같은 회귀를 PR에서 바로 드러내도록 첫 방문 번들의 brotli 크기에 상한을 걸었다(`boot` 55KB, 첫 방문 합계 265KB). 4차 회귀가 다시 생기면 `boot`가 68KB로 상한을 넘어 `check` 단계가 실패한다. 경과는 [성능 재측정](/memo/site-performance-lcp-budget#운영-사이트-재측정)과 [성능 5차](/memo/site-performance-lcp-budget)에 있다.

- **깨진 링크 ([#359](https://github.com/hyeoniverse/MacFolio/pull/359)):** 글 229편을 스크립트로 검사해 11편을 찾았다. 관련 글을 `- 앞 글: /memo/…`처럼 주소만 적은 글과, 각주 바로 뒤에 괄호를 붙인 글(`사전 요청[^preflight](OPTIONS)`)이다. 뒤의 경우 `[^preflight](OPTIONS)`가 각주가 아니라 주소가 `OPTIONS`인 링크로 해석된다. `content.test.ts`에 글마다 세 가지 검사(링크 대상 글이 있는지, 주소만 적힌 곳이 없는지, `[^x](` 형태가 없는지)를 더했다.
- **물결표 취소선 ([#356](https://github.com/hyeoniverse/MacFolio/pull/356)):** README의 `78~87`, `2.6~3.3초`처럼 한 줄에 범위가 둘 있으면 GitHub가 그 사이를 취소선으로 렌더링했다. 예를 들어 `점수 78~87, 시간 2.6~3.3초`는 `87, 시간 2.6` 부분에 줄이 그어졌다. GitHub Flavored Markdown은 `~` 하나도 취소선 구분자로 인정한다. 메모 앱은 `singleTilde: false`라 해당하지 않는다. 문서 8개의 범위를 `\~`로 이스케이프했다.

## 돌아보며

**아쉬운 것**

- 일괄 수정 PR을 동시에 올리자 저장소 글에 기대는 시험이 연달아 실패했다. 버튼을 부분 일치 이름으로 찾는 시험, 특정 글에 표가 없다는 전제, 특정 글의 토글 위치에 기대는 시험이었다.
- 한 PR 안에서 상태 표시줄, 스크롤 가장자리 흐림, 편집기 링크 상자를 각각 네다섯 번 고쳤다. iOS 화면처럼 기준 화면이 있으면 먼저 캡처하고, 여백·블러 반경·간격 같은 수치를 정한 뒤 구현해야 한다.

**바꾼 것**

- 시험에 필요한 글은 가짜 API의 서버 글로 만들고, 역할 이름은 `exact: true`로 찾는 것을 기본으로 한다. 저장소 글은 시험의 고정 자료가 아니다.
- 인용 색은 블로그와 문서 보기에서 따로 고쳐야 했고, 코드 강조 색은 한쪽 창에서만 빠졌다. 같은 스타일이 두 곳에 있었기 때문이다. `prose.css` 하나로 옮긴 뒤로는 새 Markdown 화면에 `.prose` 클래스만 붙이면 된다.
- 전날 적은 첫 번들 크기 검사는 이날 CI 성능 예산으로 넣었다.
