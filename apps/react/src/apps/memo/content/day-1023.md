## 메모 편집기

### 저장할 때 바뀌던 Markdown ([#332](https://github.com/hyeoniverse/MacFolio/pull/332))

로컬에서 고친 저장소 글이 화면에 반영되지 않아 원인을 찾다가, 같은 주소의 글이 예전에 편집기로 게시되어 DB에 남아 있는 것을 확인했다. 서버 글은 같은 주소의 저장소 글을 대체한다(`mergeServerPosts`). 이 확인 과정에서 편집기 문제 셋을 함께 고쳤다.

![편집기로 저장한 태그 줄 전후](./images/day-1023-editor-tags.jpg '고치기 전에는 첫 태그가 #MacFolio로 저장되어 태그로 인식되지 않았다. unescapeTags가 줄 맨 앞과 목록·인용 기호 뒤의 # 가운데 제목이 될 수 없는 것만 되돌린다')

| 문제                                         | 원인                                                                                                                                | 수정                                                 |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 저장하면 글 끝 첫 태그가 `\#MacFolio`가 된다 | remark-stringify는 줄 맨 앞의 `#`를 무조건 이스케이프한다. CommonMark 제목은 `#` 뒤에 공백이 필요해 `#MacFolio`는 제목이 될 수 없다 | 저장 직전에 `unescapeTags`                           |
| 토글을 펼치기만 해도 '임시 저장됨'           | 펼침 여부가 문서의 `open` 속성이었다                                                                                                | 펼침을 ProseMirror 플러그인 상태(화면 상태)로 옮겼다 |
| 서버에서 고친 저장소 글을 되돌릴 수 없다     | 메뉴가 없었다                                                                                                                       | '저장소 글로 되돌리기'                               |

### 편집 중 링크 이동과 이미지 확대 ([#339](https://github.com/hyeoniverse/MacFolio/pull/339), [#340](https://github.com/hyeoniverse/MacFolio/pull/340))

편집기에서는 링크를 클릭하면 커서가 놓일 뿐 이동하지 않는다. 링크에 마우스를 올리면 링크 위 18px에 '글로 이동'·'새 탭에서 열기' 상자를 띄웠다. 이미지는 노드 뷰가 클릭을 선택·캡션 편집에 쓰므로, 돋보기 버튼과 더블클릭으로 읽기 화면과 같은 라이트박스를 연다. 두 기능 모두 React 트리 밖의 노드 뷰와 React 컴포넌트를 `createStore` 저장소 하나로 연결했다.

### 비밀 글 ([#355](https://github.com/hyeoniverse/MacFolio/pull/355))

서버 글을 관리자에게만 보이게 지정한다. 글 주소를 받는 공개 경로를 `git grep`으로 모두 찾아 서버에서 필터링했다: 글 목록, 공유 카드, 댓글, 좋아요, 인기글, 조회수, 트래픽 요약, 메모 정리 내용, Worker의 첫 화면 본문, sitemap, RSS. 비밀 글 주소로 직접 요청하면 없는 글과 같은 응답을 보낸다. 저장소 글은 공개 저장소에 원문이 있어 지정할 수 없다. 자세한 과정은 [메모 비밀 글](/memo/memo-secret-posts)에 적었다.

![관리자 화면의 비밀 글](./images/memo-secret-posts-admin.jpg '목록 제목 앞의 fa-user-lock 아이콘과 편집기 날짜 줄의 비밀 글 표시. 잠근 메모와 구별하려고 아이콘과 색을 나눴다')

## 화면이 보이는 동안만 다시 조회하기

'활동 상태 보기'의 값과 메모 조회수는 앱을 연 시각의 값에서 바뀌지 않았다. 반대로 실시간 탭은 `setInterval`로 10초마다 조회했는데, 창을 닫아도 앱 컴포넌트가 언마운트되지 않아 1시간에 360번 요청이 계속 나갔다.

## 분석과 검색

### 실시간 7일과 IP별 방문 ([#333](https://github.com/hyeoniverse/MacFolio/pull/333))

실시간 탭은 최근 30분만 보여 줘서, 서버가 마스킹된 IP를 7일 동안 보관하는데도 30분이 지난 방문은 IP로 따라갈 수 없었다. 기간(30분·3시간·24시간·7일)을 고르고, 마스킹된 IP마다 방문을 집계하는 표를 더했다. IP를 누르면 아래 방문 목록이 그 IP로 필터링된다.

![실시간 탭의 IP 표](./images/day-1023-live-ip.jpg '7일 기간의 IP 표와 203.0.113.x로 필터링한 방문 목록. 방문을 누르면 들어옴 → 글 보기 순서가 펼쳐진다. 가짜 API 자료로 촬영했다')

같은 PR에서 맥 Safari에서만 유입 경로 조합 표를 정렬하면 이름 칸 글자가 사라지던 문제도 수정했다. 자동 시험 브라우저(Chromium, Playwright WebKit)에서는 재현되지 않았다. 이 표만 이름 칸이 버튼이고, 정렬하면 `tbody`를 다시 만들며 페이드를 건다는 차이에서 "다시 만든 버튼 + 페이드" 조합을 원인으로 추정했다. 이름이 버튼인 표는 정렬할 때 `tbody`를 다시 만들지 않는다.

### 관리자 IP 제외 ([#337](https://github.com/hyeoniverse/MacFolio/pull/337))

관리자 세션 쿠키가 붙은 방문만 집계에서 제외하고 있어, 로그인하지 않은 휴대폰으로 사이트를 확인하면 일반 방문으로 집계되었다. 관리자로 인증된 요청의 IP를 `HMAC-SHA256(IP_HASH_SECRET, "admin-ip:" + IP)`로 기록하고, 그 IP의 방문은 세션이 없어도 저장하지 않는다. IP 원문은 저장하지 않고, 마지막 관리자 요청 뒤 30일이 지나면 행을 삭제한다. 같은 공유기 뒤의 다른 방문자도 30일 동안 집계에서 빠지는 한계는 [개인정보 문서](https://github.com/hyeoniverse/MacFolio/blob/main/docs/privacy.md)에 적었다.

### Search Console 연결과 SSH 시간 초과 ([#360](https://github.com/hyeoniverse/MacFolio/pull/360))

검색어 탭에 Google Search Console 자료를 연결했다. 사이트를 도메인 속성(`sc-domain:`)으로 등록하면 같은 도메인의 다른 하위 도메인 페이지까지 응답에 섞인다. URL 접두어 속성을 추가로 등록하는 대신, 서버가 `searchAnalytics.query`에 `dimensionFilterGroups`(`page`, `includingRegex`)를 붙여 이 사이트 페이지만 요청하도록 했다. 이미 받아 둔 다른 하위 도메인 행은 동기화하면서 삭제한다.

![Search Console 연결 순서](./images/search-console-setup-flow.svg 'Search Console 속성과 사이트맵, Google Cloud 서비스 계정, 권한 추가, 서버 api.env 설정 순서')

서비스 계정 키를 서버로 옮기는 과정에서 `scp`가 `Operation timed out`으로 실패했다. 보안 목록은 열려 있었고 GitHub Actions 배포는 성공했다. 원인은 접속 주소였다. 이전에 SSH 키를 복구하며 만든 임시 VM의 공인 IP를 서버 주소로 기억하고 있었다. `known_hosts`의 기록과 Cloud Shell의 `oci compute instance list-vnics` 결과로 실제 서버 IP를 확인하고, `~/.ssh/config`에 별칭을 등록했다.

![SSH 시간 초과 원인을 좁힌 순서](./images/ssh-timeout-public-ip-diagnosis.svg '로컬 네트워크, 통신사 경로, 서버 방화벽을 차례로 배제한 뒤 접속 주소가 다른 VM의 IP라는 것을 확인했다')

- [Google Search Console 연결하기](/memo/search-console-setup): 속성 추가부터 서버 설정까지의 순서
- [SSH가 시간 초과되던 이유](/memo/ssh-timeout-public-ip): 원인을 좁힌 순서와 재발 방지 설정

## 휴대폰 화면

### 상태 표시줄 밑에 깔린 사진·팁 ([#335](https://github.com/hyeoniverse/MacFolio/pull/335))

사진 보관함을 맨 위로 올리면 첫 줄 사진이 상태 표시줄과 제목 밑에 깔렸고, 그 자리를 누르면 사진 대신 제어 센터가 열렸다. 홈 화면의 앱 21개를 하나씩 열어 상태 표시줄 영역에 보이는 글자·그림·버튼을 찾자 팁 앱도 걸렸다. 상태 표시줄이 앱 위에 겹치는 iOS 구조는 유지하고, 내용 맨 위에 상태 표시줄과 큰 제목만큼 여백을 뒀다.

![사진 보관함 전후](./images/day-1023-photos-statusbar.jpg '고치기 전에는 맨 위에서도 첫 줄이 상태 표시줄과 제목 밑에 깔렸다. 고친 뒤에는 제목 아래에서 시작하고, 스크롤해 사진이 제목 밑으로 들어가면 제목 뒤가 어두워진다')

이 PR은 방향을 여러 번 바꿨다. 상태 표시줄을 누른 위치의 버튼에 탭을 전달하는 방법과 앱 화면 전체를 상태 표시줄 아래에서 시작하는 방법을 차례로 시도했다가, 후자가 iOS와 달라 되돌리고 보관함에만 여백을 두는 방법으로 정했다. 스크롤 가장자리 흐림도 강도와 층 수를 다섯 번 조정했다.

![한 PR 안에서 여러 번 수정한 곳](./images/day-1023-iterations.svg '상태 표시줄 4회, 스크롤 가장자리 흐림 5회, 편집기 링크 상자 5회. 점 하나가 커밋 하나다')

### 사진 위젯을 누르면 그 사진 ([#354](https://github.com/hyeoniverse/MacFolio/pull/354))

사진 위젯을 누르면 사진 앱이 항상 보관함 격자로 열렸다. 기존 앱 간 요청 경로(`openRequest.ts`)로 위젯에 표시 중인 사진의 앨범과 사진 id를 넘겨, 그 앨범 안의 크게 보기로 연다. 휴대폰 홈 화면 편집 중에 위젯을 누르면 남던 요청도 막았다. [사진 위젯을 누르면 그 사진을 크게 보기로](/memo/photo-widget-open-current)에 적었다.

### 홈 화면 위젯 끌어 옮기기 ([#365](https://github.com/hyeoniverse/MacFolio/pull/365))

편집 모드에서 위젯 순서를 바꾸려면 삭제했다가 다시 추가해야 했다. 2열 격자 배치 규칙을 순수 함수로 정리하고, 끄는 위젯은 `translate`로, 비켜 주는 위젯은 FLIP으로 움직였다. 처음 구성에서 음악 위젯을 1쪽, GitHub 잔디를 2쪽으로 맞바꿨다.

![위젯을 끄는 중](./images/mobile-widget-reorder-drag.jpg '음악 위젯을 소개 위젯 위로 끄는 중. 소개 위젯이 아래로 비켜 준다')

같은 PR에서 한 페이지가 위젯 세 줄이 되면 모든 페이지의 위젯과 아이콘이 작아지던 문제를 찾았다. 위젯 줄 높이를 위젯 줄 수가 가장 많은 페이지에 맞춰 계산했기 때문이다. 줄 높이를 화면 크기로만 정하도록 바꿨다. 자세한 내용은 [휴대폰 홈 화면 위젯 끌어 옮기기](/memo/mobile-widget-reorder)에 적었다.

## 스타일: 인용 색과 prose.css ([#361](https://github.com/hyeoniverse/MacFolio/pull/361), [#364](https://github.com/hyeoniverse/MacFolio/pull/364))

Markdown 본문의 인용(`> …`)이 보조 글자색이라 흐렸다. 인용 규칙이 블로그(`.memo-markdown`)와 문서 보기·텍스트 편집기(`.finder-doc`)에 따로 있어 둘 다 고쳐야 했다. 처음에 두 곳을 다른 PR로 올렸다가(#362), 같은 규칙을 두 PR이 나눠 고치면 머지 순서에 따라 결과가 달라질 수 있어 #362를 닫고 #361 하나로 합쳤다.

공통 규칙을 `styles/prose.css`로 옮기자 텍스트 편집기 창에서 연 문서의 코드 블록에 문법 강조 색이 없는 문제가 드러났다. 강조 색 변수(`--hl-*`)를 `[data-app='memo']`·`[data-app='finder']`에만 정의해, `data-app='textedit'` 창에서는 `var()`가 무효가 되었다. 코드 색은 `:root`의 `--color-code-*`를 직접 참조하고, 본문 요소에 공통 클래스 `.prose`를 붙였다. 선택자는 `:where(.prose) …`로 시작해 명시도가 0이고, 화면마다 다른 값은 `--prose-*` 변수로 분리했다. [Markdown 본문 스타일을 prose.css 하나로](/memo/markdown-prose-css)에 적었다.

## Markdown 검사와 글 내용에 의존하던 시험

저장소 글과 문서를 분야별로 나눠 일괄 수정하는 PR 10개([#343](https://github.com/hyeoniverse/MacFolio/pull/343)~[#352](https://github.com/hyeoniverse/MacFolio/pull/352))를 올리는 과정에서 Markdown 문법 오류 두 종류와 시험 문제를 발견했다.

- **깨진 링크 ([#359](https://github.com/hyeoniverse/MacFolio/pull/359)):** 글 229편을 스크립트로 검사해 11편을 찾았다. 관련 글을 `- 앞 글: /memo/…`처럼 주소만 적은 글과, 각주 바로 뒤에 괄호를 붙인 글(`사전 요청[^preflight](OPTIONS)`)이다. 뒤의 경우 `[^preflight](OPTIONS)`가 각주가 아니라 주소가 `OPTIONS`인 링크로 해석된다. `content.test.ts`에 글마다 세 가지 검사(링크 대상 글이 있는지, 주소만 적힌 곳이 없는지, `[^x](` 형태가 없는지)를 더했다.
- **물결표 취소선 ([#356](https://github.com/hyeoniverse/MacFolio/pull/356)):** README의 `78~87`, `2.6~3.3초`처럼 한 줄에 범위가 둘 있으면 GitHub가 그 사이를 취소선으로 렌더링했다. GitHub Flavored Markdown은 `~` 하나도 취소선 구분자로 인정한다. 메모 앱은 `singleTilde: false`라 해당하지 않는다. 문서 8개의 범위를 `\~`로 이스케이프했다.

## 돌아보며

**PR 10개를 동시에 올리자 저장소 글에 의존하는 시험이 연달아 실패했다.** 버튼을 부분 일치 이름으로 찾는 시험, 특정 글에 표가 없다는 전제, 특정 글의 토글 위치에 기대는 시험이었다. 글은 계속 바뀌는 데이터라 시험의 고정 자료로 쓰면 안 된다. 시험에 필요한 글은 가짜 API의 서버 글로 만들고, 역할 이름은 `exact: true`로 찾는 것을 기본으로 한다.

**한 PR 안에서 같은 화면을 네다섯 번 수정했다.** 상태 표시줄, 스크롤 가장자리 흐림, 편집기 링크 상자가 그렇다. iOS 화면처럼 기준이 되는 화면이 있으면 먼저 그 화면을 캡처해 비교 기준으로 두고, 수치(여백, 블러 반경, 간격)를 정한 뒤에 구현하는 편이 반복을 줄인다.

**같은 스타일이 두 곳에 있으면 같은 문제를 두 번 겪는다.** 인용 색은 블로그와 문서 보기에서 따로 고쳐야 했고, 코드 강조 색은 한쪽 창에서만 빠졌다. `prose.css` 하나로 옮긴 뒤에는 새 Markdown 화면에 `.prose` 클래스만 붙이면 된다.

**회귀를 찾은 날 그 회귀를 막는 검사도 넣었다.** 오후의 재측정으로 첫 번들 회귀를 찾았고, 밤에 CI 성능 예산을 걸었다. 전날 회고에 "첫 번들 크기를 CI에서 검사하는 기준이 필요하다"고 적은 항목을 하루 만에 반영했다.
