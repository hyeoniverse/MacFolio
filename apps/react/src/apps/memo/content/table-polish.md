[ProseMirror gap cursor를 표 양옆의 세로 커서로 보이게 하기](/memo/table-gap-cursor) 작업 이후 표를 편집하면서 발견한 문제를 정리했다.

## 배경

메모 앱은 이 블로그의 글을 작성하는 편집기이기도 하다. 편집기는 [ProseMirror](https://prosemirror.net/) 위에 구현했고, 표는 [`prosemirror-tables`](https://github.com/ProseMirror/prosemirror-tables)로 처리한다. macOS 메모의 표를 기준으로 행·열 손잡이, 칸 끌어 선택하기, 표 양옆 커서를 차례로 구현했다.

10월 1일 저녁, 실제로 글을 작성하며 표를 사용해 보니 칸을 끌어 선택해도 아무 표시가 나타나지 않았다. Mac의 메모 앱에서 같은 조작을 해 보고 그 화면을 기준으로 삼았다. 이어서 표를 더 사용하면서 문제 세 가지를 추가로 발견했다.

| 문제                                  | 원인                                                           |
| ------------------------------------- | -------------------------------------------------------------- |
| 끌어 선택한 범위가 표시되지 않는다    | 손잡이와 함께 테두리·꼭짓점까지 숨겼다                         |
| 표 옆을 클릭해도 커서가 놓이지 않는다 | 표 옆은 편집기 바깥이라 클릭 처리기가 이벤트를 수신하지 못했다 |
| 표를 삭제하려면 Backspace 두 번       | 먼저 선택하고 다음에 삭제하는 2단계였다                        |
| 게시 버튼 위쪽이 잘린다               | 버튼이 스크롤 칸 가장자리에 정확히 붙어 있었다                 |

![표 다듬기](./images/table-polish.jpg '끌어 고른 칸에는 테두리와 꼭짓점, 표 양옆 여백을 누르면 그쪽에 세로 커서')

## 끌어 선택한 칸에도 테두리 표시

![macOS 메모에서 표의 첫 줄 두 칸을 끌어 고른 화면](./images/table-polish-macos-selection.jpg '참고한 macOS 메모 화면. 끌어 고른 범위에 노란 테두리와 대각선 꼭짓점 둘이 그려진다')

이전 작업에서 "칸을 끌어 선택하면 손잡이를 표시하지 않는다"는 규칙을 적용했다. 끄는 도중 한 열 전체가 선택 범위에 들어가면 손잡이 막대가 펼쳐졌기 때문이다. 그런데 이때 손잡이뿐 아니라 **선택 범위의 테두리와 꼭짓점까지** 함께 숨겼다.

```tsx
// 칸을 끌어 골랐으면 손잡이·테두리 없이 고른 칸 표시만
if (!table || !tableBox || !run || table.dragged) return null;
```

macOS 메모는 끌어 선택한 범위에도 노란 테두리와 대각선 꼭짓점 두 개를 렌더링한다. 선택 범위를 바로 확인할 수 있고, 꼭짓점을 끌어 범위를 조정할 수 있다. 숨겨야 했던 것은 행·열 손잡이뿐이었다.

```tsx
if (!table || !tableBox || !run) return null;
// 칸을 끌어 골랐으면 고른 범위의 테두리와 꼭짓점만 (행·열 손잡이는 손잡이로 고를 때만)
const handles = !table.dragged;
```

| 선택 방법   | 수정 전                  | 수정 후                       |
| ----------- | ------------------------ | ----------------------------- |
| 손잡이 클릭 | 손잡이 + 테두리 + 꼭짓점 | 손잡이 + 테두리 + 꼭짓점      |
| 마우스 끌기 | 선택한 칸 배경색만       | 테두리 + 꼭짓점 (손잡이 없음) |

꼭짓점으로 범위를 조정하는 명령은 원래 "손잡이로 선택한 변경"이라는 표시를 붙였다. 그대로 두면 끌어 선택한 범위의 꼭짓점을 조작하는 순간 손잡이가 나타난다. 그래서 명령에 `byHandle`을 전달해 처음 선택한 방법을 유지하도록 했다.

## 표 옆 여백을 클릭하면 그쪽에 커서

←·→ 키로는 표 양옆에 세로 커서를 놓을 수 있었지만, 마우스로는 불가능했다. 표 옆을 클릭하면 커서가 의도하지 않은 칸으로 이동했다.

처음에는 편집기의 `handleClick`에서 클릭 위치가 표의 왼쪽·오른쪽인지 판단해 틈 커서를 놓았다. 그런데 시험해 보니 아무 동작도 일어나지 않았다. 이 편집기의 표는 **편집기 너비 전체를 차지**한다. 표 옆은 편집기 바깥인 본문 칸의 여백(좌우 32px)이라, 클릭 이벤트가 편집기의 처리기까지 전달되지 않았다.

![표 옆 여백이 편집기 바깥이라 본문 칸에서 누름을 받는 구조](./images/table-polish-click-areas.svg '표 옆은 편집기 밖이다')

검토한 방법은 세 가지다.

| 방법                                           | 장점                                  | 단점                                                        |
| ---------------------------------------------- | ------------------------------------- | ----------------------------------------------------------- |
| 편집기에 좌우 안쪽 여백을 지정해 표를 좁힌다   | `handleClick`만으로 처리된다          | 본문 글과 표의 너비가 달라지고, 다른 글의 레이아웃이 바뀐다 |
| 표 양옆에 보이지 않는 클릭 영역을 추가한다     | 클릭 위치가 명확하다                  | 표마다 요소가 늘고, 표가 이동하면 위치를 갱신해야 한다      |
| 본문 칸에 `mousedown`을 등록하고 좌표로 찾는다 | 화면은 그대로, 처리기 하나로 해결한다 | 편집기 밖 이벤트라 플러그인이 직접 등록·해제해야 한다       |

화면을 바꾸지 않는 마지막 방법을 선택했다. 플러그인의 [`view`](https://prosemirror.net/docs/ref/#state.PluginSpec.view)에서 본문 칸(`.memo-scroll`)에 `mousedown` 처리기를 별도로 등록했다.

```ts
view: (view) => {
	const area = view.dom.closest('.memo-scroll');
	const onDown = (event: MouseEvent) => {
		if (view.dom.contains(event.target as Node)) return; // 편집기 안은 handleClick이 맡는다
		const gap = gapBesideTableAt(view, event.clientX, event.clientY);
		if (gap === null) return;
		event.preventDefault(); // 여백을 눌러 편집기의 초점이 빠지지 않게
		placeGap(view, gap);
	};
	area?.addEventListener('mousedown', onDown);
	return { destroy: () => area?.removeEventListener('mousedown', onDown) };
},
```

`gapBesideTableAt`은 글 안의 각 표의 화면 좌표를 측정해, 클릭한 높이가 표 범위 안이고 위치가 표의 오른쪽(또는 왼쪽)이면 표 뒤(또는 앞) 위치를 반환한다. `preventDefault`를 생략하면 여백을 클릭하는 순간 편집기가 포커스를 잃고, 틈 커서는 포커스가 있을 때만 표시되므로 커서가 사라진다.

시험을 작성하면서 문제가 하나 더 있었다. 표 오른쪽 30px 위치를 클릭하도록 했더니 창 가장자리의 크기 조절 손잡이가 클릭됐다. 시험 창이 좁아 본문 여백이 32px뿐이었기 때문이다. 표에서 12px 떨어진 위치를 클릭하도록 수정했다.

## Backspace 한 번에 표를 삭제한다

표 바로 뒤에서 Backspace를 누르면 먼저 표를 선택하고(노란 테두리), 한 번 더 눌러야 삭제됐다. 삭제 대상을 보여 주려는 동작이었지만, 편집할 때마다 두 번 누르는 조작이 번거로웠다. 이제 한 번에 삭제한다.

| 커서 위치                                    | 키        | 수정 전                  | 수정 후   |
| -------------------------------------------- | --------- | ------------------------ | --------- |
| 표 바로 뒤 문단의 맨 앞, 또는 표 오른쪽 커서 | Backspace | 표 선택 → 다시 눌러 삭제 | 바로 삭제 |
| 표 왼쪽 커서                                 | Delete    | 표 선택 → 다시 눌러 삭제 | 바로 삭제 |

코드로는 Backspace 처리기의 한 분기다. 커서 바로 앞이 표이면 바로 삭제하고, 이미지이면 선택만 한다(`apps/react/src/apps/memo/writer/tableCommands.ts`).

```ts
const start = $block.pos - before.nodeSize;
if (before.type.name === 'table') {
	view.dispatch(state.tr.delete(start, $block.pos).scrollIntoView());
	return true;
}
if (before.type.name !== 'image_block') return false;
view.dispatch(state.tr.setSelection(NodeSelection.create(state.doc, start)));
return true;
```

편집기에는 실행 취소([history 플러그인](https://prosemirror.net/docs/ref/#history))가 있어서, 잘못 삭제한 표는 ⌘Z로 복원된다. 따라서 한 번에 삭제해도 데이터가 손실되지 않는다.

이미지는 기존대로 두 번 눌러야 삭제된다. 이미지는 선택했을 때 테두리가 표시되어 삭제 대상을 바로 확인할 수 있고, 실수로 삭제하면 다시 업로드해야 하기 때문이다.

## 게시 버튼 위쪽이 잘렸다

편집기 맨 위 줄 오른쪽의 '게시' 버튼 위쪽이 약간 잘려 표시됐다. 버튼의 좌표와 상위 요소들의 `overflow`를 측정하니 원인이 바로 확인됐다.

```text
button      top 153.0  bottom 171.0
memo-scroll top 153.0  overflow-y: auto
```

버튼의 위쪽 경계가 스크롤 칸의 위쪽 경계와 정확히 일치했다. 스크롤 칸은 넘치는 내용을 클리핑하므로, 고해상도 화면에서 반 픽셀 오차가 생기거나 포커스 테두리가 표시되면 위쪽이 잘린다. 본문 칸에 위쪽 여백 4px을 지정했다.

```css
/* 위쪽 4px: 맨 위의 게시 단추(편집기)가 스크롤 칸 가장자리에 붙어 위쪽이 잘리지 않게 */
.memo-reader .memo-scroll {
	padding: 4px 2rem 3rem; /* 수정 전: 0 2rem 3rem */
}
```

![수정 전에는 게시 버튼 위쪽이 스크롤 칸 경계와 같아 잘리고, 수정 후에는 4px 아래로 내려온 도식](./images/table-polish-publish-clip.svg '스크롤 칸 위쪽에 4px 여백을 지정했다')

읽기 화면도 같은 스크롤 칸을 사용하므로 날짜 줄이 4px 아래로 이동했지만, 읽기 화면과 편집 화면의 글 위치는 계속 일치한다.

## 남은 것·배운 것

- 표 옆을 클릭할 때 표의 위·아래 경계를 벗어난 높이이면 아무 동작도 하지 않는다.
- 숨기는 대상을 정확히 구분해야 한다. 숨겨야 했던 것은 손잡이였는데 테두리까지 함께 숨겼다. 조건 하나(`table.dragged`)가 두 기능을 함께 막고 있었다.
- 편집기 내부의 처리기는 편집기 DOM 밖의 이벤트를 수신하지 않는다. 화면에서 "편집기 옆"으로 보이는 영역이 DOM에서는 편집기 밖일 수 있다.
- 스크롤 칸 가장자리에 정확히 붙은 요소는 반 픽셀 오차에도 잘린다. 버튼 좌표를 측정해 수치로 비교하니 원인이 바로 확인됐다.
