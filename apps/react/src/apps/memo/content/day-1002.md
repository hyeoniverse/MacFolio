## 메시지·댓글: 이름·비밀번호 칸 대신 쿠키

### 문제: 네 번 수정해도 어색한 입력 칸

휴대폰 메시지 화면의 이름·비밀번호 입력 칸을 오후에만 네 번(15:49, 16:06, 18:06, 19:09) 수정했다. 입력창과 높이·간격을 맞췄지만, 두 칸이 본문 입력창보다 더 눈에 띄었다. 같은 화면에서 함께 발견한 문제는 다음과 같다.

- 빈 목록 화면에서 안내 문구와 빈 카드의 간격이 좁았다
- "감상, 의견, 피드백을 남겨 주세요" 문구와 "방문자 (나) ›" 캡슐이 위아래 요소와 간격 없이 붙어 있었다
- "누구나 답글을 달 수 있어요"처럼 정보가 없는 안내 문구가 있었다 (삭제)
- PR 스크린샷을 확인해 보니 수정했다고 판단한 곳이 그대로였다. 전후가 구분되지 않는 PR 설명은 새로 작성했다

19:36에 입력 칸 자체를 제거했다. 여러 번 수정한 결과, 문제는 칸의 모양이 아니라 칸이 존재한다는 것이었다.

### 조치: 서버가 발급하는 쿠키로 작성자 식별

입력 칸이 필요했던 이유는 하나다. 작성자가 나중에 자기 글을 삭제하려면 누가 썼는지 식별해야 한다. 이 목적이라면 사용자 입력이 아니어도 된다.

| 항목           | 변경 전                          | 변경 후                                      |
| -------------- | -------------------------------- | -------------------------------------------- |
| 작성자 식별    | 사용자가 입력한 이름·비밀번호    | 서버가 처음 방문한 브라우저에 발급하는 쿠키  |
| 표시 이름      | 입력한 이름                      | 쿠키 값으로 정하는 이름 (예: "🦊 날쌘 여우") |
| 같은 사람 판별 | 같은 이름·비밀번호를 입력해야 함 | 같은 브라우저면 언제 방문해도 같은 이름      |
| 자기 글 삭제   | 비밀번호 입력                    | 작성한 브라우저에서 삭제                     |

자세한 구조는 [이름·비밀번호 없이 쓰는 메시지와 댓글](/memo/visitor-identity)에 정리했다. 메시지도 이때 처음 서버에 저장하게 했고, 서버에 연결할 수 없으면 메시지 앱을 열지 않는다([서버가 없으면 메시지 앱을 열지 않기](/memo/messages-offline)).

### 시행착오

- **PR 순서:** UI 작업(#69)을 끝내기 전에 쿠키 작업을 새 브랜치로 시작했고, 계획 단계였던 #70을 충분히 확인하지 않고 머지했다. GitHub의 머지 기록은 삭제할 수 없어 이력에 남았다. 이후로는 PR을 머지하기 전에 반드시 내용을 확인하고, 작업이 겹치면 먼저 시작한 작업을 마무리한 뒤 나중 작업을 리베이스한다
- **서버 미배포 상태의 오류:** 머지 후 메모에 댓글을 작성해 보니 "이름을 입력해 주세요", "비밀번호는 4~20자로…" 오류만 표시되고 입력 칸은 없었다. 프론트엔드는 새 코드인데 서버는 아직 이전 코드였기 때문이다. 서버가 응답하지 않으면 메시지는 조회도 작성도 할 수 없으므로, 오류 문구를 수정하는 대신 메모처럼 앱을 여는 단계에서 차단했다. 개발 모드에서는 `.env` 설정으로 이 화면을 확인할 수 있게 하고, "서버에 연결할 수 없습니다" 문구가 표시될 때 레이아웃이 이동하지 않게 했다
- **백업 명령을 로컬에서 실행:** 서버를 새 코드로 갱신하기 전에 DB를 백업하려고 `cd ~/deploy && docker compose exec -T db pg_dump …`를 실행했는데 `no such file or directory`가 발생했다. 이 명령을 서버가 아니라 로컬 Mac에서 실행했기 때문이다. 서버에 SSH로 접속한 뒤 실행해야 한다

```bash
ssh ubuntu@<서버>
cd ~/deploy
docker compose exec -T db pg_dump -U macfolio macfolio > ~/backup-$(date +%F).sql
```

현재는 이 과정을 [ops/backup.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/backup.sh)가 수행한다.

## 휴대폰 앱을 iOS 모양으로

### 휴대폰 메모를 iOS 메모처럼 재구성

오전에는 휴대폰 메모를 iOS 메모의 구성으로 다시 만들었다.

- 큰 제목
- 카드로 묶은 목록
- 스크롤 영역 밖에 떠 있는 플로팅 버튼
- 하단 검색 칸
- 폴더 편집에서 ≡ 핸들로 순서 변경 ([폴더 순서를 손잡이로 바꾸기](/memo/memo-folder-order))

빠진 요소는 실제 iOS 메모 스크린샷과 나란히 비교하며 찾았다. 게시 버튼 안에 글자를 넣으면 버튼이 너무 좁아지는 문제, 목록 화면의 검색 칸과 글쓰기 버튼, 폴더 화면의 새 폴더·편집 버튼이 누락된 것을 이 비교로 발견했다.

![현재의 휴대폰 메모](./images/day-1002-mobile-memo.jpg '이날 만든 휴대폰 메모 목록의 현재 화면. 큰 제목이 뒤로 가기 줄에 표시된다')

### 공통 컴포넌트로 여섯 개 앱에 적용

메모에서 맞춘 배경·카드·플로팅 버튼을 공통 컴포넌트로 분리해 음악·설정·암호·단축어·메일·메시지 여섯 개 앱에 한 번에 적용했다. 앱마다 따로 맞추면 같은 작업을 여섯 번 반복해야 한다. 음악은 iOS 음악처럼 보관함·플레이리스트·앨범·아티스트로 나눴다([휴대폰 앱들을 메모처럼](/memo/mobile-apps-ios-style)).

![현재의 휴대폰 음악](./images/day-1002-mobile-music.jpg '휴대폰 음악의 현재 화면. 보관함에서 플레이리스트·아티스트·앨범·노래로 이동한다')

## 배포 후 메모가 열리지 않던 오류

밤에 메모를 열면 간헐적으로 "문제가 발생했습니다"가 표시되었고, 다시 열어도 같았다.

| 단계 | 상황                                                        |
| ---- | ----------------------------------------------------------- |
| 1    | 사용자가 페이지를 열어 둔 상태에서 새 버전이 배포된다       |
| 2    | 배포로 메모 코드 파일 이름(해시)이 바뀐다                   |
| 3    | 열려 있던 페이지가 메모를 열 때 이전 이름의 파일을 요청한다 |
| 4    | 파일을 불러오지 못해 오류 화면이 표시된다                   |

이날은 새로고침을 권하는 경고 대화상자를 표시하는 것으로 대응했다([배포 직후 메모가 안 열리던 까닭](/memo/app-error-alert)). 근본 원인은 사흘 뒤에 찾았다. 사이트가 존재하지 않는 코드 파일 요청에도 첫 화면(`index.html`)을 상태 코드 200으로 반환하고 있었다([없는 코드 파일에 index.html을 주던 문제](/memo/asset-404)).

## 돌아보며

**"이 요소가 왜 필요한가"를 먼저 확인해야 한다.** 이름·비밀번호 칸을 네 번 수정하기 전에 이 질문을 했다면 처음부터 쿠키 방식을 선택했을 것이다. 휴대폰 앱에서는 이 질문을 제대로 했다. 배경과 카드가 앱마다 달라야 할 이유가 없어서 공통 컴포넌트로 통합했고, 앱마다 반복할 작업 여섯 번을 한 번으로 줄였다.

**오류는 증상만 처리하고 넘어갔다.** 경고 대화상자로 사용자 불편은 줄였지만, 같은 오류가 다시 발생하지 않게 수정한 것은 사흘 뒤였다. 당일 원인 조사용 이슈를 따로 등록해 두었다면 더 빨리 수정했을 것이다.
