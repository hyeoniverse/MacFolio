이날은 메시지·댓글의 작성자 식별 방식을 바꿨고, 휴대폰 앱을 iOS 모양으로 통일했고, 전날 시작한 메모 기능을 마무리했고, 배포 후 메모가 열리지 않던 오류에 대응했다.

![10월 2일 작업 흐름](./images/day-1002-timeline.svg '새벽에는 메모 마무리, 낮에는 휴대폰 앱, 저녁에는 방문자 이름과 오류 안내')

## 메시지·댓글: 이름·비밀번호 칸 대신 쿠키

### 문제: 네 번 수정해도 어색한 입력 칸

휴대폰 메시지 화면의 이름·비밀번호 입력 칸을 세 시간여 동안 네 번 고쳤다. 입력창과 높이·간격을 맞췄지만, 두 칸이 본문 입력창보다 더 눈에 띄었다.

결국 입력 칸 자체를 없앴다. 네 번 고치고 나서야 ==문제는 칸의 모양이 아니라 칸이 존재한다는 것==을 알았다.

### 조치: 서버가 발급하는 쿠키로 작성자 식별

입력 칸이 필요했던 이유는 하나였다. 작성자가 나중에 자기 글을 삭제하려면 누가 썼는지 식별해야 한다. 이 목적이라면 사용자 입력이 없어도 된다.

| 항목           | 변경 전                          | 변경 후                                      |
| -------------- | -------------------------------- | -------------------------------------------- |
| 작성자 식별    | 사용자가 입력한 이름·비밀번호    | 서버가 처음 방문한 브라우저에 발급하는 쿠키  |
| 표시 이름      | 입력한 이름                      | 쿠키 값으로 정하는 이름 (예: "🦊 날쌘 여우") |
| 같은 사람 판별 | 같은 이름·비밀번호를 입력해야 함 | 같은 브라우저면 언제 방문해도 같은 이름      |
| 자기 글 삭제   | 비밀번호 입력                    | 작성한 브라우저에서 삭제                     |

자세한 구조는 [httpOnly 방문자 쿠키의 HMAC 해시로 가입 없이 방문자 식별하기](/memo/visitor-identity)에 있다. 메시지도 이때 처음 서버에 저장하게 했고, 서버에 연결할 수 없으면 메시지 앱을 열지 않는다([첫 요청 실패와 사용 중 연결 끊김을 구분하는 메시지 앱 오류 처리](/memo/messages-offline)).

### 시행착오

- **PR 순서:** UI 작업(#69)을 끝내기 전에 쿠키 작업을 새 브랜치로 시작했고, 계획 단계였던 #70을 충분히 확인하지 않고 머지했다. GitHub의 머지 기록은 삭제할 수 없어 이력에 그대로 남았다. 그 뒤로는 PR을 머지하기 전에 반드시 내용을 확인하고, 작업이 겹치면 먼저 시작한 작업을 마무리한 뒤 나중 작업을 리베이스한다
- **서버 미배포 상태의 오류:** 머지한 뒤 메모에 댓글을 써 보니 "이름을 입력해 주세요", "비밀번호는 4~20자로…" 오류만 표시되고 입력 칸은 없었다. 프론트엔드는 새 코드인데 서버는 아직 이전 코드였기 때문이다. 서버가 응답하지 않으면 메시지는 조회도 작성도 할 수 없으므로, 오류 문구를 수정하는 대신 메모처럼 앱을 여는 단계에서 차단했다. 개발 모드에서는 `.env` 설정으로 이 화면을 확인할 수 있게 하고, "서버에 연결할 수 없습니다" 문구가 표시될 때 레이아웃이 이동하지 않게 했다
- **백업 명령을 로컬에서 실행:** 서버를 새 코드로 갱신하기 전에 DB를 백업하려고 `cd ~/deploy && docker compose exec -T db pg_dump …`를 실행했는데 `no such file or directory`를 받았다. 이 명령을 서버가 아니라 로컬 Mac에서 실행했기 때문이다. 서버에 SSH로 접속한 뒤 실행해야 했다

```bash
ssh ubuntu@<서버>
cd ~/deploy
docker compose exec -T db pg_dump -U macfolio macfolio > ~/backup-$(date +%F).sql
```

현재는 이 과정을 [ops/backup.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/backup.sh)가 수행한다.

## 휴대폰 앱을 iOS 모양으로

### 휴대폰 메모를 iOS 메모처럼 재구성

휴대폰 메모를 iOS 메모의 구성으로 다시 만들었다.

- 큰 제목
- 카드로 묶은 목록
- 스크롤 영역 밖에 떠 있는 플로팅 버튼
- 하단 검색 칸
- 폴더 편집에서 ≡ 핸들로 순서 변경 ([폴더 순서를 손잡이로 바꾸기](/memo/memo-folder-order))

![현재의 휴대폰 메모](./images/day-1002-mobile-memo.jpg#float-right '이날 만든 휴대폰 메모 목록의 현재 화면. 큰 제목이 뒤로 가기 줄에 표시된다')

빠진 요소는 실제 iOS 메모 스크린샷과 나란히 비교하며 찾았다. 게시 버튼 안에 글자를 넣으면 버튼이 너무 좁아지는 문제와, 목록 화면의 검색 칸·글쓰기 버튼, 폴더 화면의 새 폴더·편집 버튼이 빠진 것을 이 비교로 찾았다.

### 공통 컴포넌트로 여섯 개 앱에 적용

![현재의 휴대폰 음악](./images/day-1002-mobile-music.jpg#float-left '휴대폰 음악의 현재 화면. 보관함에서 플레이리스트·아티스트·앨범·노래로 이동한다')

메모에서 맞춘 배경·카드·플로팅 버튼을 공통 컴포넌트로 분리해 음악·설정·암호·단축어·메일·메시지 여섯 개 앱에 한 번에 적용했다. ==앱마다 따로 맞추면 같은 작업을 여섯 번 반복해야 한다.== 음악은 iOS 음악처럼 보관함·플레이리스트·앨범·아티스트로 나눴다([셸 공통 CSS 사용자 정의 속성으로 휴대폰 앱의 바탕·카드 색 통일하기](/memo/mobile-apps-ios-style)).

## 메모 마무리: 최근 삭제된 항목과 태그

전날 시작한 최근 삭제된 항목과 태그를 마무리했다. 화면을 열어 항목을 하나씩 확인하며 고쳤다.

**최근 삭제된 항목**

| 항목      | 수정 내용                                                                                 |
| --------- | ----------------------------------------------------------------------------------------- |
| 안내 상자 | 상자로 되돌리되, 휴지통 아이콘을 상자가 아니라 제목 첫 줄의 세로 가운데에 정렬            |
| ⋯ 메뉴    | "휴지통 비우기" 추가                                                                      |
| 즉시 삭제 | 바로 삭제하지 않고 macOS처럼 확인 대화상자 표시. 화면 전체가 아니라 메모 창 가운데에 표시 |

![즉시 삭제 확인 대화상자](./images/memo-recently-deleted-confirm-request.jpg '즉시 삭제를 누르면 표시할 확인 대화상자의 참고 화면. 메모 창 가운데에 표시한다')

태그 필터에 미선택·포함·제외 세 상태와 "모두 포함·일부 포함" 조건을 추가했다.

## 배포 후 메모가 열리지 않던 오류

배포한 뒤 메모를 열면 간헐적으로 "문제가 발생했습니다"가 표시되었고, 다시 열어도 같았다.

| 단계 | 상황                                                        |
| ---- | ----------------------------------------------------------- |
| 1    | 사용자가 페이지를 열어 둔 상태에서 새 버전이 배포된다       |
| 2    | 배포로 메모 코드 파일 이름(해시)이 바뀐다                   |
| 3    | 열려 있던 페이지가 메모를 열 때 이전 이름의 파일을 요청한다 |
| 4    | 파일을 불러오지 못해 오류 화면이 표시된다                   |

이날은 새로고침을 권하는 경고 대화상자를 표시해 대응했다([삭제된 옛 코드 파일을 요청하는 React.lazy 로드 실패 구분하기](/memo/app-error-alert)).

> [!NOTE] 근본 원인
> 근본 원인은 사흘 뒤에 찾았다. 사이트가 존재하지 않는 코드 파일 요청에도 첫 화면(`index.html`)을 상태 코드 200으로 반환하고 있었다([not_found_handling 뒤 Worker 함수로 SPA 주소와 없는 자산의 404 나누기](/memo/asset-404)).

## 돌아보며

**"이 요소가 왜 필요한가"를 먼저 확인해야 했다.** 이름·비밀번호 칸을 네 번 고치기 전에 이 질문을 했다면 처음부터 쿠키 방식을 골랐을 것이다. 휴대폰 앱에서는 이 질문을 제대로 했다. 배경과 카드가 앱마다 달라야 할 이유가 없어서 공통 컴포넌트로 통합했고, 앱마다 반복할 작업 여섯 번을 한 번으로 줄였다.

**오류는 증상만 처리하고 넘어갔다.** 경고 대화상자로 사용자 불편은 줄였지만, 같은 오류가 다시 발생하지 않게 고친 것은 사흘 뒤였다. 그날 바로 원인 조사용 이슈를 등록했다면 더 빨리 고쳤을 것이다.
