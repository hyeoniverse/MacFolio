휴대폰 메시지 화면의 이름·비밀번호 칸을 오후에만 네 번 다듬었다. 3시 49분, 4시 6분, 6시 6분, 7시 9분. 입력창과 높이를 맞추고 간격을 맞췄는데도 두 칸이 입력창보다 더 눈에 띄었다.

7시 36분에 칸을 아예 없앴다. 여러 번 고쳐 보니 칸의 모양이 아니라 칸이 있는 것 자체가 문제였다.

그 전에 본 문제들은 이랬다. 빈 목록 화면에서 안내 글과 빈 카드가 너무 붙어 있었고, PR 스크린샷을 열어 보니 고쳤다던 곳이 그대로였다. 전후가 구분되지 않는 PR 설명은 새로 쓰게 했다. 이름·비밀번호 칸은 모양이 혼자 튀었고, "감상, 의견, 피드백을 남겨 주세요" 문구와 "방문자 (나) ›" 캡슐이 위아래와 너무 붙어 있었다. "누구나 답글을 달 수 있어요" 같은 쓸모없는 안내도 지웠다. 그러다 "그래도 같은 사람이면 같은 이름을 쓰게 할 수 없을까"를 물은 것이 쿠키 방식의 출발점이다.

![10월 2일 작업 흐름](./images/day-1002-timeline.svg '새벽에는 메모 마무리, 낮에는 휴대폰 앱, 저녁에는 방문자 이름과 오류 안내')

## 이름·비밀번호 칸 대신 쿠키

칸이 필요했던 이유는 하나였다. 자기 글을 나중에 지우려면 누가 썼는지 알아야 한다. 그렇다면 꼭 입력 칸이 아니어도 된다. 서버가 처음 온 브라우저에 쿠키를 주고, 그 값으로 "🦊 날쌘 여우" 같은 이름을 정한다. 같은 브라우저면 언제 와도 같은 이름이고, 자기 글은 그 브라우저에서 지운다([이름·비밀번호 없이 쓰는 메시지와 댓글](/memo/visitor-identity)).

메시지도 이때 처음 서버에 저장했다. 서버에 닿지 못하면 메시지 앱을 열지 않는다([서버가 없으면 메시지 앱을 열지 않기](/memo/messages-offline)).

이 부분은 순서가 꼬였다. UI 작업(#69)이 끝나지 않았는데 쿠키 작업이 새 브랜치로 시작되었고, 계획 단계였던 #70이 내가 확인하기 전에 머지되었다. GitHub의 "머지됨" 기록은 지울 수 없어서 이력에 그대로 남았다. 이 뒤로는 PR을 머지하기 전에 반드시 내가 확인하고, 작업이 겹치면 먼저 것을 마무리한 뒤 나중 것을 리베이스하는 순서를 지키기로 했다.

머지 뒤 실제로 메모에 댓글을 달아 보니 "이름을 입력해 주세요", "비밀번호는 4~20자로…" 오류만 뜨고 입력 칸은 없었다. 서버를 아직 새 코드로 올리지 않아서였다. 여기서 방향을 정했다. 서버가 응답하지 않으면 메시지는 불러올 수도 남길 수도 없으니, 오류를 고칠 게 아니라 메모처럼 앱을 여는 단계에서 막는다. 개발 모드에서는 `.env` 설정으로 이 화면을 확인할 수 있게 하고, "서버에 연결할 수 없습니다" 문구가 나타날 때 레이아웃이 움직이지 않게 했다.

서버를 새 코드로 맞추기 전에 백업부터 하려다 한 번 더 막혔다. `cd ~/deploy && docker compose exec -T db pg_dump …`를 내 Mac에서 쳐서 `no such file or directory`가 났다. 이 명령은 서버에 SSH로 들어가서 쳐야 한다.

```bash
ssh ubuntu@<서버>
cd ~/deploy
docker compose exec -T db pg_dump -U macfolio macfolio > ~/backup-$(date +%F).sql
```

지금은 이 과정이 [ops/backup.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/backup.sh)로 바뀌었다.

## 휴대폰 앱의 공통 모양

오전에는 휴대폰 메모를 iOS 메모처럼 다시 짰다. 큰 제목, 카드로 묶은 목록, 넘기는 칸 밖에 떠 있는 버튼, 아래 검색 칸. 폴더 편집에는 ≡ 손잡이로 순서를 바꾸는 기능을 넣었다([폴더 순서를 손잡이로 바꾸기](/memo/memo-folder-order)).

![지금의 휴대폰 메모](./images/day-1002-mobile-memo.jpg '이날 만든 휴대폰 메모 목록의 지금 모습. 큰 제목이 뒤로 가기 줄에 있다')

그다음 메모에서 맞춘 바탕·카드·떠 있는 버튼을 공통 컴포넌트로 분리해 음악·설정·암호·단축어·메일·메시지에 한 번에 적용했다. 음악은 iOS 음악처럼 보관함·플레이리스트·앨범·아티스트로 나눴다([휴대폰 앱들을 메모처럼](/memo/mobile-apps-ios-style)).

![지금의 휴대폰 음악](./images/day-1002-mobile-music.jpg '휴대폰 음악의 지금 모습. 보관함에서 플레이리스트·아티스트·앨범·노래로 들어간다')

새벽에는 전날 밤의 최근 삭제된 항목과 태그를 마무리했다. 태그에는 미선택·포함·제외 세 상태와 "모두·일부 포함"이 들어갔다.

새벽 작업은 화면을 열어 보며 하나씩 짚었다. 휴지통은 안내 상자로 되돌리되, 휴지통 아이콘을 상자가 아니라 제목 첫 줄의 세로 가운데에 맞추고, 문구를 "30일 뒤에 영구히 삭제됩니다. 원본 항목이 휴지통에 있기 때문에 수정할 수 없습니다…"로 바꾸고, "되살리기"를 "되돌려 놓기"로 고치고, 상자 안 문구 아래에 버튼을 한 줄로 오른쪽 정렬하고, ⋯ 메뉴에 "휴지통 비우기"를, 문구 아래에 구분선을 넣었다. 즉시 삭제는 바로 지우지 않고 macOS처럼 묻게 했다. 이 경고창은 화면 전체가 아니라 메모 창의 가운데에 뜬다.

![즉시 삭제 확인창](./images/memo-recently-deleted-confirm-request.jpg '즉시 삭제를 누르면 이렇게 물어야 한다고 정한 참고 화면. 메모 창 가운데에 띄운다')

태그 설명 예시에 내 개인적인 단어가 들어가 있던 것도 이때 보고 바꿨다. 오전에는 "모두 포함·일부 포함" 고르기의 화살표를 chevron으로 바꾸고, 새 메모의 필요 없는 설명 문구를 지웠다. 휴대폰 메모를 다시 짤 때는 게시 버튼 안에 글자를 넣으면 너무 좁아진다는 것, 목록 화면의 검색 칸과 글쓰기 버튼, 폴더 화면의 새 폴더·편집 버튼이 빠졌다는 것을 실제 iOS 메모 스크린샷과 나란히 놓고 찾았다.

## 배포 뒤에 메모가 열리지 않던 오류

밤에는 메모를 열 때 가끔 "문제가 발생했습니다"가 떴고, 다시 열어도 같았다. 배포로 메모 코드 파일 이름이 바뀌었는데, 열려 있던 페이지가 옛 이름을 찾고 있었다. 이날은 새로고침을 권하는 OS 경고창으로 막았다([배포 직후 메모가 안 열리던 까닭](/memo/app-error-alert)).

근본 원인은 사흘 뒤에 찾았다. 사이트가 없는 코드 파일에도 첫 화면(index.html)을 200으로 주고 있었다([없는 코드 파일에 index.html을 주던 문제](/memo/asset-404)).

그 밖에 계정 사진이 늦게 올 때 자리를 채우고([프로필 사진이 늦게 올 때](/memo/settings-avatar-placeholder)), 관리자가 배경화면을 추가하는 기능을 만들었다([관리자가 배경화면을 더하기](/memo/custom-wallpapers)). 계정 사진은 GitHub에서 늦게 올 때 그 자리가 뻥 뚫려 보이는 걸 보고 고쳤고, 배경화면 추가는 만들다가 "넣지 말까" 고민도 했지만 기본 배경화면은 지울 수 없게 하는 조건으로 넣었다. 블로그와 PR의 이미지 화질이 뭉개져 보이는 것도 이날 봐서 고해상도로 바꿨다(#71).

## 돌아보며

이날 얻은 교훈은 "이 요소가 왜 필요한가"를 먼저 묻는 것이다. 이름·비밀번호 칸을 네 번 고치기 전에 이 질문을 했으면 처음부터 쿠키를 썼을 것이다. 휴대폰 앱에서는 이 질문을 제대로 했다. 바탕과 카드가 앱마다 달라야 할 이유가 없어서 하나로 합쳤고, 앱마다 따로 맞추는 일을 여섯 번 줄였다.

오류는 증상만 막고 넘어갔다. 경고창으로 사용자 불편은 줄였지만, 같은 오류가 다시 생기지 않게 고친 것은 사흘 뒤였다. 그날 원인을 찾는 이슈를 따로 열어 두었으면 더 빨리 고쳤을 것이다.
