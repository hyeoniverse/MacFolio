이날 커밋은 세 개다. 모두 새벽 세 시 전에 올렸다. 다음 단계를 맡긴 담당 둘이 사용량 한도에 걸려 멈췄고, 그 사이 임시 작업 폴더도 지워졌다. 그래서 그 뒤의 작업은 남지 않았다.

![10월 14일 작업 흐름](./images/day-1014-timeline.svg '새벽 0~2시에 회고 글 둘과 #187 커밋 하나. 그 뒤로는 커밋이 없다')

## 회고를 시간에서 주제로

10월 11일부터 13일까지의 회고 글을 쓰면서, 앞서 쓴 10월 7일 회고가 시간대별로 짜여 있는 것을 고쳤다. 9월 30일과 10월 10일 회고도 같은 문제가 있어서 함께 고쳤다([#224](https://github.com/hyeoniverse/MacFolio/pull/224)).

시간대별 회고는 한 번 고친 적이 있다. 그런데 새 글을 쓰면서 다시 시각 표를 뼈대로 삼았다. 그래서 이번에는 짜는 규칙을 적어 두었다. 그날의 PR을 주제(기능, 정리, 사고)로 묶고, 주제마다 원인에서 수정까지 이어서 쓴다. 시각은 흐름 그림과 본문 속에서만 쓴다.

## 포트폴리오가 늘 묻는 세 구역

[#187](https://github.com/hyeoniverse/MacFolio/pull/187)의 공통 랜딩 내용(`landingOf`)에는 기능, 기술, 만든 방식, 맡은 일, 진행 과정이 있었다. 하지만 포트폴리오에서 거의 늘 묻는 세 가지는 적을 칸이 없었다.

| 새 구역     | 칸                                   | 그림이 없을 때                    |
| ----------- | ------------------------------------ | --------------------------------- |
| 트러블슈팅  | 제목·문제·원인·해결·결과·그림·아이콘 | 문제 → 원인 → 해결 → 결과 단계 띠 |
| 팀원        | 이름·역할·GitHub 주소·사진·'나' 표시 | 이름 첫 글자 동그라미             |
| 배포 결과물 | 이름·주소·플랫폼·설명·그림           | 플랫폼 아이콘과 공개 상태         |

세 구역을 데이터 검사, 편집 화면(내용 탭의 목록과 시트), 공통 예시(북클럽: 트러블슈팅 3건, 팀원 4명, 배포 3곳), 랜딩 구역에 모두 더했다. 아홉 템플릿이 모두 새 구역을 그린다. 저장소 템플릿은 `docs/TROUBLESHOOTING.md`, `TEAM.md`, `DEPLOYMENT.md` 문서와 옆 칸의 Contributors·Deployments로 보여 준다.

구역 이름 둘을 포트폴리오에서 쓰는 말로 바꿨다. '만든 방식'은 '구현 방법'이 되었고, '맡은 일'은 '내 역할'이 되었다. 구역 차례도 프로젝트를 소개하는 순서로 다시 정했다.

![랜딩 구역 차례](./images/day-1014-sections.svg '무엇인지 → 어떻게 만들었는지 → 누가 → 언제 → 어디서. 초록은 새 구역, 남색은 이름을 바꾼 구역')

이 커밋 하나에서 41개 파일이 바뀌었고, 2,606줄이 늘고 55줄이 줄었다. 그때 #187 브랜치의 단위 시험 802개와 E2E 481개가 모두 통과했다.

![트러블슈팅 구역](./images/day-1014-trouble.jpg '제품 템플릿의 트러블슈팅 구역. 이날 그린 것을 이틀 뒤 다듬은 모습이다')

## Cannot PUT /site/projects

편집 화면에서 저장을 누르자 `Cannot PUT /site/projects`가 났다. 코드에는 이 경로가 있었다. 그런데 4000번 포트에서 응답한 것은 개발 서버가 아니었다. 예전에 빌드해 둔 API 이미지를 띄운 Docker 컨테이너 `macfolio-api-1`이었다.

1. 컨테이너가 4000번 포트를 먼저 잡았다.
2. `pnpm dev:all`의 API는 포트를 얻지 못하고 꺼졌다(`EADDRINUSE`).
3. 화면의 요청은 옛 API로 갔다. 옛 API에는 `PUT /site/projects` 경로가 없었다.

컨테이너를 멈추고(`docker stop macfolio-api-1`) 개발 서버를 다시 켜서 해결했다. DB 컨테이너는 개발 서버도 쓰므로 그대로 두었다. 누가 이 컨테이너를 켰는지는 찾지 못했다. 같은 컨테이너는 다음 날 밤 로그인을 막으며 다시 나타난다.

## 멈춘 2단계

새 구역을 올린 뒤 2단계를 담당 둘에게 맡겼다. 하나는 RPG 대화창을 주제마다 게임 그래픽(퀘스트, 버그 몬스터 전투, 파티, 보물 상자)으로 그리는 일이고, 다른 하나는 템플릿마다 새 구역을 다듬는 일이다.

두 담당은 사용량 한도에 걸려 중간에 멈췄다. 그 사이 임시 작업 폴더(/tmp)도 통째로 지워졌다. 커밋하지 않은 2단계 작업은 남지 않았고, 이틀 뒤 오후에 처음부터 다시 했다. 올려 둔 1단계 커밋은 브랜치에 있어서 안전했다.

| 브라우저 E2E            |  357 |        0 |
| 단위 시험 (화면 + core) |  477 |        0 |

| API 단위 시험           |  157 |        0 |

숫자는 그날 마지막 main 커밋의 시험 수다(시험 파일의 `test(`·`it(`를 센다). 이날 main은 전날과 같은 커밋이다. 단위 시험은 이번에 같은 방법으로 다시 세어 477개가 나왔다. 10월 13일 글의 471개와 6개가 다르다.

## 돌아보며

이날 잃은 것은 코드가 아니라 시간이다. 2단계 작업은 /tmp 아래의 작업 폴더에만 있었고, 브랜치에 올리지 않았다. 담당이 멈추고 폴더가 지워지자 남은 것이 없었다. 오래 걸리는 작업은 중간 결과를 작업용 브랜치에 커밋해 두면, 담당이 멈춰도 이어서 할 수 있다.

옛 API 컨테이너는 오류 문구가 길을 잘못 알려 줬다. `Cannot PUT`은 경로가 없다는 뜻인데, 실제로는 경로가 아니라 서버가 달랐다. 이런 오류가 나면 코드보다 먼저 그 포트에서 누가 응답하는지(`docker ps`, `lsof -i :4000`)를 보는 것이 빠르다.
