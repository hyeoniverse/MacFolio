이날 커밋은 3개(그중 2개는 회고 글)로, 모두 새벽 3시 전에 올렸다. 이후 단계의 작업은 작업 환경의 사용량 한도로 중단됐고, 그 사이 임시 작업 폴더도 삭제되어 결과가 남지 않았다. 다룬 주제는 #187의 포트폴리오 섹션 추가, 저장 실패의 원인 분석, 중단된 2단계 작업이다.

![10월 14일 작업 흐름](./images/day-1014-timeline.svg '새벽 0~2시에 회고 글 2개와 #187 커밋 1개. 이후로는 커밋이 없다')

## 포트폴리오 필수 섹션 세 가지

[#187](https://github.com/hyeoniverse/MacFolio/pull/187)의 공통 랜딩 데이터(`landingOf`)에는 기능, 기술, 구현 방식, 담당 업무, 진행 과정이 있었다. 그러나 포트폴리오 검토에서 거의 항상 확인하는 세 가지를 입력할 필드가 없었다.

| 새 섹션     | 필드                                   | 이미지가 없을 때의 대체 표시        |
| ----------- | -------------------------------------- | ----------------------------------- |
| 트러블슈팅  | 제목·문제·원인·해결·결과·이미지·아이콘 | 문제 → 원인 → 해결 → 결과 단계 표시 |
| 팀원        | 이름·역할·GitHub 주소·사진·'나' 표시   | 이름 첫 글자 원형 아바타            |
| 배포 결과물 | 이름·주소·플랫폼·설명·이미지           | 플랫폼 아이콘과 공개 상태           |

세 섹션을 다음 네 곳에 모두 추가했다.

| 위치             | 내용                                            |
| ---------------- | ----------------------------------------------- |
| 데이터 검증      | 새 필드의 스키마와 검증 규칙                    |
| 편집 화면        | 내용 탭의 목록과 편집 시트                      |
| 공통 예시 데이터 | 북클럽 예시: 트러블슈팅 3건, 팀원 4명, 배포 3곳 |
| 랜딩 섹션        | 템플릿 9개 모두 새 섹션을 렌더링                |

저장소 템플릿은 GitHub 저장소 화면 형식에 맞춰 `docs/TROUBLESHOOTING.md`, `TEAM.md`, `DEPLOYMENT.md` 문서와 사이드바의 Contributors·Deployments로 표시한다.

섹션 이름 두 개를 포트폴리오에서 일반적으로 쓰는 용어로 변경했다. '만든 방식'은 '구현 방법'으로, '맡은 일'은 '내 역할'로 바꿨다. 섹션 순서도 프로젝트를 소개하는 순서로 다시 정했다.

![랜딩 섹션 순서](./images/day-1014-sections.svg '무엇인지 → 어떻게 만들었는지 → 누가 → 언제 → 어디서. 초록은 새 섹션, 남색은 이름을 변경한 섹션')

이 커밋 하나에서 파일 41개가 변경되고, 2,606줄이 추가되고 55줄이 삭제됐다. 당시 #187 브랜치의 단위 시험 802개와 E2E 481개가 모두 통과했다.

![트러블슈팅 섹션](./images/day-1014-trouble.jpg '제품 템플릿의 트러블슈팅 섹션. 이날 만든 것을 이틀 뒤 다듬은 화면이다')

## Cannot PUT /site/projects: 4000번 포트의 이전 API

편집 화면에서 저장하자 `Cannot PUT /site/projects` 오류가 발생했다. 코드에는 이 경로가 있었다. 4000번 포트에서 응답한 것은 개발 서버가 아니라, 예전에 빌드한 API 이미지로 실행된 Docker 컨테이너 `macfolio-api-1`이었다.

![4000번 포트를 점유한 이전 API 컨테이너](./images/day-1014-port.svg '요청은 4000번 포트를 먼저 점유한 이전 API 컨테이너로 갔다. 개발 서버의 API는 포트를 얻지 못해 종료된 상태였다')

1. 컨테이너가 4000번 포트를 먼저 점유했다
2. `pnpm dev:all`의 API는 포트를 얻지 못해 `EADDRINUSE`로 종료됐다
3. 화면의 요청은 이전 API로 전달됐고, 이전 API에는 `PUT /site/projects` 경로가 없었다

컨테이너를 중지하고(`docker stop macfolio-api-1`) 개발 서버를 다시 실행해 해결했다. DB 컨테이너는 개발 서버도 사용하므로 그대로 유지했다. 이 컨테이너를 누가 실행했는지는 확인하지 못했다. 같은 컨테이너는 다음 날 밤 로그인 실패의 원인으로 다시 나타난다.

## 중단된 2단계 작업

새 섹션을 올린 뒤 2단계를 두 작업으로 나눠 시작했다.

- RPG 대화창을 주제별 게임 그래픽(퀘스트, 버그 몬스터 전투, 파티, 보물 상자)으로 만드는 작업
- 템플릿마다 새 섹션의 디자인을 다듬는 작업

두 작업은 작업 환경의 사용량 한도로 중간에 중단됐다. 그 사이 임시 작업 폴더(`/tmp`)가 통째로 삭제됐다. 커밋하지 않은 2단계 작업은 남지 않았고, 이틀 뒤 오후에 처음부터 다시 진행했다. 이미 push한 1단계 커밋은 브랜치에 남아 있었다.

## 돌아보며

이날 손실된 것은 코드가 아니라 시간이다. 2단계 작업은 `/tmp` 아래 작업 폴더에만 있었고, 브랜치에 커밋하지 않았다. 작업이 중단되고 폴더가 삭제되자 남은 것이 없었다. 오래 걸리는 작업은 중간 결과를 작업 브랜치에 커밋해 두어야, 중간에 중단되어도 이어서 진행할 수 있다.

이전 API 컨테이너의 경우 오류 메시지가 원인을 잘못 가리켰다. `Cannot PUT`은 경로가 없다는 의미인데, 실제 원인은 경로가 아니라 요청을 받은 서버였다. 이런 오류가 나면 코드보다 먼저 해당 포트에서 어떤 프로세스가 응답하는지(`docker ps`, `lsof -i :4000`)를 확인하는 것이 빠르다.
