---

바탕화면 위젯을 추가한 뒤, 휴대폰으로 사이트에 처음 접속하면 로딩 화면이 표시되기 전까지 검은 화면이 오래 유지되었다. 이 지연을 수치로 확인하려고 [Lighthouse](https://developer.chrome.com/docs/lighthouse/overview)로 첫 방문 성능을 측정했다.

결론부터 적는다. 휴대폰은 Lighthouse 55점에 LCP(최대 콘텐츠가 렌더링되기까지)가 25.7초, 데스크톱은 62점에 5.8초였다. 첫 방문마다 휴대폰은 4.9MB, 데스크톱은 9MB를 전송했다. 원인을 세 차례에 걸쳐 개선한 뒤([#319](https://github.com/hyeoniverse/MacFolio/pull/319) 1차, [#323](https://github.com/hyeoniverse/MacFolio/pull/323) 2·3차) 같은 조건으로 다시 측정했다. 개선 과정은 [성능 최적화 2: 글꼴 subset·lazy import·modulepreload·WebP로 첫 방문 전송량 9MB를 0.8MB로](/memo/site-performance-diet)에, 3차까지 배포된 운영 사이트의 재측정은 [성능 재측정](/memo/site-performance-remeasure)에 따로 정리했다.

<details>
<summary>용어 정리: FCP, LCP, TBT, CLS</summary>

| 지표 | 이름                     | 뜻                                                                                        |
| ---- | ------------------------ | ----------------------------------------------------------------------------------------- |
| FCP  | First Contentful Paint   | 글자나 이미지가 처음 렌더링된 시각 ([web.dev](https://web.dev/articles/fcp))              |
| LCP  | Largest Contentful Paint | 화면에 보이는 가장 큰 요소가 렌더링된 시각 ([web.dev](https://web.dev/articles/lcp))      |
| TBT  | Total Blocking Time      | FCP 이후 메인 스레드가 50ms 넘게 막힌 시간의 합 ([web.dev](https://web.dev/articles/tbt)) |
| CLS  | Cumulative Layout Shift  | 불러오는 동안 화면 요소가 밀려난 정도 ([web.dev](https://web.dev/articles/cls))           |

Lighthouse 성능 점수는 이 지표들을 가중 평균한 0~100점 값이다.

</details>

## 결과

**휴대폰**

| 항목                     | 개선 전 | 1차     | 2차   | 3차       |
| ------------------------ | ------- | ------- | ----- | --------- |
| Lighthouse 성능 점수     | 55      | 68      | 69~72 | **78~87** |
| FCP (첫 콘텐츠 렌더링)   | 14.3초  | 4.0초   | 4.0초 | **3.2초** |
| LCP (최대 콘텐츠 렌더링) | 25.7초  | 6.2초   | 5.8초 | **3.2초** |
| TBT (메인 스레드 차단)   | 115ms   | 0ms     | 0ms   | **0ms**   |
| 첫 방문 전송량           | 4,893KB | 1,011KB | 725KB | **483KB** |
| 요청 수                  | 61      | 74      | 75    | **49**    |

**데스크톱**

| 항목                     | 개선 전 | 1차     | 2차     | 3차       |
| ------------------------ | ------- | ------- | ------- | --------- |
| Lighthouse 성능 점수     | 62      | 90      | 93      | **98**    |
| FCP (첫 콘텐츠 렌더링)   | 2.5초   | 0.8초   | 0.8초   | **0.7초** |
| LCP (최대 콘텐츠 렌더링) | 5.8초   | 1.9초   | 1.7초   | **1.1초** |
| TBT (메인 스레드 차단)   | 9ms     | 0ms     | 0ms     | **0ms**   |
| 첫 방문 전송량           | 9,050KB | 2,177KB | 1,848KB | **771KB** |
| 요청 수                  | 111     | 101     | 102     | **49**    |

CLS(레이아웃 이동)는 개선 전부터 0이었다. 1차는 글꼴·글 원문·앱 코드·이미지·로딩 화면을, 2차는 아이콘·앨범 이미지의 WebP 변환과 메뉴 막대의 사과를, 3차는 로딩 화면 뒤에서 미리 렌더링하던 바탕화면을 개선했다.

3차의 "첫 방문 전송량"은 로딩 화면을 누르기 전까지다. 3차는 전송량을 없앤 것이 아니라 누른 뒤로 미뤘다. 누르고 진입한 뒤까지의 전송량은 휴대폰 768KB, 데스크톱 1,895KB로 2차와 같다.

![개선 전·후의 LCP, FCP, 전송량](./images/site-performance-report-chart.svg '휴대폰과 데스크톱의 LCP, FCP, 첫 방문 전송량. 회색이 개선 전, 초록이 3차까지 개선한 뒤')

누르기 전까지의 전송량은 휴대폰이 1/10, 데스크톱이 1/12로 줄었다. 무엇이 줄었는지는 리소스 유형별로 보면 분명하다.

![첫 방문 전송량, 리소스 유형별](./images/site-performance-report-weight.svg '리소스 유형별 전송량. 글꼴(주황)과 이미지(초록)가 가장 많이 줄었다')

- **글꼴:** 1,736KB → 149KB. 본문 글꼴 TTF 한 벌(압축해도 1.7MB)을 자주 쓰는 글자만 담은 woff2(149KB)로 교체했다. 아이콘 글꼴은 누른 뒤에 수신한다
- **JS:** 1,132KB → 220KB. 블로그 글 199편의 원문과 모든 앱의 코드가 첫 번들에 포함되어 있었다
- **이미지:** 휴대폰 1,878KB → 60KB(배경화면 한 장), 데스크톱 5,010KB → 348KB. 2560px PNG 아이콘, JPG 배경화면, 처음 열린 Safari 페이지의 이미지 수십 장이었다
- **영상:** 데스크톱 1,026KB → 0. 처음 열린 Safari 페이지가 화면 밖의 영상까지 수신했다

TBT는 원래 낮았다. 이 사이트는 렌더링이 아니라 **네트워크 전송**에 오래 걸렸다.

## 측정 방법

- **도구:** Lighthouse 12.8.2(성능 항목만), Playwright 1.64(Chromium 156)
- **휴대폰:** Lighthouse 기본값. 느린 4G(왕복 150ms, 1.6Mbps)와 4배 느린 CPU를 시뮬레이션한다
- **데스크톱:** `--preset=desktop` (왕복 40ms, 10Mbps)
- **서버:** 빌드 결과를 로컬 정적 서버로 제공했다. 운영처럼 텍스트 파일은 brotli로 압축하고, 화면 경로는 `index.html`로 응답한다(`apps/react/scripts/perf/serve.mjs`)
- **횟수:** 개선 전·후를 5회씩, 한 번에 하나만 실행하고 중앙값을 썼다. 빌드와 측정이 겹치면 CPU를 함께 사용해 측정값의 편차가 커진다. 그래서 빌드와 겹친 첫 측정값은 폐기하고 다시 측정했다

## 운영 사이트

로컬 수치만으로는 실제 사이트가 빨라졌는지 알 수 없다. 1차 배포 전·후와 3차까지 배포한 뒤에 운영 주소를 같은 방법으로 5회씩 측정했다.

| 항목            | 휴대폰 개선 전 | 1차 배포 후 | 3차 배포 후    | 데스크톱 개선 전 | 1차 배포 후 | 3차 배포 후     |
| --------------- | -------------- | ----------- | -------------- | ---------------- | ----------- | --------------- |
| Lighthouse 성능 | 53             | 73          | **98** (86~98) | 60               | 89          | **97** (96~100) |
| FCP             | 15.0초         | 2.4초       | **1.9초**      | 2.9초            | 0.9초       | **1.0초**       |
| LCP             | 31.5초         | 7.1초       | **1.9초**      | 5.8초            | 2.1초       | **1.0초**       |
| 첫 방문 전송량  | 6,342KB        | 1,239KB     | **602KB**      | 7,134KB          | 3,229KB     | **889KB**       |

운영도 로컬과 같은 방향으로 개선되었다. 데스크톱은 운영이 이미지를 더 많이 전송한다. 관리자가 수정한 프로젝트 내용이 처음 열리는 Safari 페이지에 들어가기 때문이다. 3차 배포 후의 측정 과정은 [성능 재측정](/memo/site-performance-remeasure)에 정리했다.

## 측정값 해석

휴대폰 FCP는 로컬 simulate에서 4.0초인데 운영(1차 배포 후)에서는 2.4초다. 둘 다 같은 느린 4G를 가정했는데 왜 다를까.

Lighthouse의 기본값(simulate)은 빠른 네트워크에서 한 번 수신한 기록으로 느린 네트워크에서 걸릴 시간을 **계산**한다. 이때 "첫 렌더링 전에 수신한 리소스"는 첫 렌더링에 필요했던 리소스로 간주한다. 로컬에서는 첫 렌더링이 47ms에 일어나는데, 그때까지 [`modulepreload`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/modulepreload)로 지정한 JS 번들 33개(약 400KB)도 모두 수신을 마친다. 그래서 이 33개가 FCP 계산에 포함되어 FCP가 4.0초가 된다.

브라우저를 실제로 느리게 해서(`--throttling-method=devtools`) 측정하면 다음과 같다.

| 휴대폰 (실제 스로틀링) | 개선 전 | 2차   | 3차           |
| ---------------------- | ------- | ----- | ------------- |
| Lighthouse 성능        | 65      | 78    | **92**        |
| FCP                    | 9.2초   | 1.2초 | **1.2~2.7초** |
| LCP                    | 12.1초  | 6.0초 | **1.2~2.7초** |
| 첫 방문 전송량         | 5,932KB | 782KB | **483KB**     |

표의 값을 정리하면 다음과 같다.

- **3차:** HTML이 먼저 렌더링하는 첫 화면이 1.2초에 표시된다(일부 회차는 2.7초). 3차에서는 누르기 전에 홈 화면을 렌더링하지 않으므로 LCP가 HTML의 첫 렌더링과 같다.
- **2차의 LCP 6.0초:** 로딩 화면 뒤의 홈 화면이 원인이다. 로컬 서버는 HTTP/1.1이라 동시 연결 6개로만 수신해 번들 33개가 대기열에 쌓였고, 마지막 번들이 5.1초에 끝난 뒤에야 홈 화면을 렌더링했다.
- **운영:** Cloudflare는 [HTTP/2](https://developer.mozilla.org/en-US/docs/Glossary/HTTP_2)로 응답해, 요청 33개를 한 연결에서 동시에 주고받는다.

![HTTP/1.1과 HTTP/2에서 번들 33개를 내려받는 순서](./images/site-performance-report-http-queue.svg 'HTTP/1.1은 연결 6개로 번들을 차례로 수신하고, HTTP/2는 한 연결에서 동시에 수신한다 (도식)')

그래서 휴대폰 FCP는 simulate와 실제 스로틀링 값을 함께 확인하고, 최종 판단은 운영 측정값으로 한다.

Lighthouse만으로는 "진입한 뒤"를 측정할 수 없다. 이 사이트는 로딩 화면을 눌러야 바탕화면이 표시된다. 그래서 [Playwright](https://playwright.dev/)로 별도 측정 스크립트(`apps/react/scripts/perf/measure.mjs`)를 작성했다. 측정 항목은 다음과 같다.

1. 로딩 화면이 표시되기까지의 시간
2. 누른 뒤 바탕화면이 표시되기까지의 시간(진입 시간)
3. 그 시각까지의 전송량
4. JS 힙 크기

진입 시간은 개선 전·후 모두 0.2초 이내였다. 앱 코드를 처음 실행하는 시각에 로드하도록 바꾸고 바탕화면을 누른 뒤에 렌더링하면서 0.05초에서 0.17초로 늘었지만, 이 시간은 로딩 화면이 표시된 동안에 지나간다.

## 병목 분석

개선 전 Lighthouse의 요청 목록을 전송량 순으로 정렬했다. 상위 6개 파일의 합이 3,754KB다.

| 순위 | 파일                                 | 전송량  | 내용                                                      |
| ---- | ------------------------------------ | ------- | --------------------------------------------------------- |
| 1    | `/fonts/AppleSDGothicNeoR.ttf`       | 1,688KB | 본문 글꼴 TTF 한 벌 (원본 3.8MB)                          |
| 2    | `/assets/EmptyState-….js`            | 739KB   | 이름은 빈 상태 컴포넌트인데 안에는 블로그 글 199편의 원문 |
| 3    | `/imgs/wallpapers/highsierra.jpg`    | 565KB   | 기본 배경화면 (휴대폰도 수신했다)                         |
| 4    | `/imgs/wallpapers/ios-sky-light.jpg` | 310KB   | 휴대폰 기본 배경화면                                      |
| 5    | `/assets/boot-….js`                  | 250KB   | 모든 앱의 코드                                            |
| 6    | `/imgs/messages.png`                 | 202KB   | 메시지 앱 아이콘 (360px)                                  |

두 번째 줄은 파일 이름과 내용이 달랐다. 번들러([Vite](https://vite.dev/guide/build))는 여러 곳이 함께 쓰는 모듈을 하나의 청크로 합치고, 그 청크에 포함된 모듈 이름 하나를 파일 이름으로 붙인다. 그래서 `EmptyState`라는 이름의 청크 안에 2.4MB짜리 글 원문이 들어 있었다. 파일 이름으로는 알 수 없었고, sourcemap으로 청크마다 모듈별 크기를 집계해 확인했다.

LCP가 늦은 원인도 둘로 나뉘었다.

- **데스크톱:** LCP 요소는 로딩 화면의 사과 아이콘이었다. 그런데 이 사과는 Font Awesome 글꼴(114KB)의 글리프였고, 로딩 화면은 JS가 렌더링한다. 그래서 LCP의 91%가 "렌더링 지연"이었다. JS와 글꼴을 모두 수신해야 사과가 표시된다
- **휴대폰:** LCP 요소는 음악 위젯의 앨범 이미지였다. 이미지 자체는 작은데, 다른 이미지 수십 장과 글꼴의 수신을 기다리느라 수신을 시작하기까지 21초가 걸렸다

## 남은 과제

- **휴대폰 점수가 78과 87로 갈린다:** 일부 회차에서 React가 다시 렌더링한 시작 안내가 LCP(4.5초)로 다시 집계된다. 원인은 아직 확인하지 못했다
- **진입 후:** 전송량 768KB(휴대폰)는 그대로다. 첫 번들 33개와 Font Awesome solid 글꼴(117KB)이 남았다. 아이콘 글꼴은 프로젝트 내용에서 아이콘 이름을 고를 수 있어 사용하는 아이콘만 남기기 어렵다
- **2·3차의 운영 측정값:** [성능 재측정](/memo/site-performance-remeasure)에 정리했다
- **CI 성능 예산:** 지금은 수동으로 측정한다. 첫 방문 전송량 같은 상한을 CI에서 검사하면 전송량이 다시 늘어나는 회귀를 PR 단계에서 발견할 수 있다. 재측정에서 실제로 첫 번들이 22KB 늘어난 회귀를 발견했다([성능 재측정](/memo/site-performance-remeasure))

측정 조건과 재측정 명령은 저장소의 [`docs/performance.md`](https://github.com/hyeoniverse/MacFolio/blob/main/docs/performance.md)에 정리했다.
