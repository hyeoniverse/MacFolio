## 1과목은 무엇을 묻는가

1과목 소프트웨어 설계는 필기 100문항 가운데 20문항을 차지한다. 시험 전체 구조와 합격 기준은 [연재 첫 글](/memo/eip-overview)에 정리했다.

1과목은 "무엇을 만들지 정하고, 어떤 구조로 만들지 그리는 단계"를 다룬다. 프로그램을 작성하기 전에 고객의 요구를 문서로 옮기고(요구사항 확인), 화면을 그리고(화면 설계), 프로그램의 뼈대와 부품을 나누고(애플리케이션 설계), 다른 시스템과 데이터를 주고받는 방법을 정한다(인터페이스 설계). 지금 적용되는 한국산업인력공단 출제기준(2023년 1월부터 2025년 12월까지)의 주요 항목도 이 네 가지다.

![1과목의 주요 항목 네 개와 세부 주제](./images/eip-software-design-scope.svg '네 주요 항목 아래 이 글에서 다루는 세부 주제')

| 주요 항목         | 세부 주제                                                  | 이 글의 절                                      |
| ----------------- | ---------------------------------------------------------- | ----------------------------------------------- |
| 요구사항 확인     | 생명주기 모델, 애자일, 요구사항 분석·명세, 분석 도구, UML  | 생명주기 모델, 애자일, 요구사항, 분석 기법, UML |
| 화면 설계         | UI 유형, 기본 원칙, 설계 도구, 품질 요구사항               | 화면 설계                                       |
| 애플리케이션 설계 | 아키텍처 패턴, 객체지향, SOLID, 결합도·응집도, 디자인 패턴 | 아키텍처, 객체지향 설계 원칙, 모듈, 디자인 패턴 |
| 인터페이스 설계   | 인터페이스 요구사항, 대상 식별, 미들웨어, EAI              | 인터페이스 설계                                 |

1과목은 계산 문제가 거의 없고, 용어의 정의를 보기에서 고르거나 "옳지 않은 것"을 찾는 문제가 대부분이다. 대신 비슷한 이름이 많아서(집합과 포함, 결합도와 응집도, include와 extend, 생성 패턴과 구조 패턴) 짝을 지어 구분해 두는 공부가 점수를 좌우한다. 이 글은 절마다 그런 짝을 비교 표로 묶고, 시험에서 어떤 형태로 묻는지 예제로 보여 준다.

> [!NOTE] 필기와 실기의 관계
> 필기 1과목의 내용 대부분이 실기의 "요구사항 확인", "화면 설계", "통합 구현" 단원에 다시 나온다. 필기에서는 보기를 고르지만 실기에서는 용어를 직접 써야 하므로, 영문 이름(예: Coupling, Cohesion, Singleton)까지 함께 외워 두면 실기 준비 시간이 줄어든다.

## 소프트웨어 생명주기 모델

소프트웨어 생명주기(SDLC, Software Development Life Cycle)는 소프트웨어를 구상하는 시점부터 폐기하는 시점까지 거치는 단계를 정의한 모델이다. 보통 요구 분석, 설계, 구현, 시험, 유지보수 단계로 나누며, 단계를 어떤 순서로, 몇 번 반복하느냐에 따라 모델이 갈린다. 생명주기 모델을 정하면 각 단계의 산출물(요구사항 명세서, 설계서, 테스트 계획서)과 일정이 정해지므로 프로젝트 관리의 기준이 된다.

### 폭포수 모형

폭포수 모형(Waterfall Model)은 1970년 Winston Royce의 논문에서 단계별 개발 과정이 그림으로 소개된 뒤 널리 퍼진 모델이다. 물이 위에서 아래로만 떨어지듯 ==이전 단계로 돌아가지 않는다는 전제==로, 한 단계를 끝내고 산출물을 검토·승인한 뒤에 다음 단계로 넘어간다. 가장 오래되고 가장 널리 쓰인 모델이라 "고전적 생명주기 모형"이라고도 부른다.

![폭포수 모형과 나선형 모형](./images/eip-software-design-lifecycle.svg '폭포수는 한 방향으로, 나선형은 네 활동을 여러 바퀴 반복')

장점은 단계와 산출물이 명확해 관리가 쉽다는 점이다. 단점은 요구사항이 처음에 완벽히 정해져 있어야 한다는 점이다. 예를 들어 은행 창구 시스템을 폭포수로 개발하면서 시험 단계에서 "모바일 앱에서도 같은 기능이 필요하다"는 요구가 새로 나오면, 요구 분석 단계로 돌아가 설계서와 구현을 모두 다시 고쳐야 한다.

### 프로토타입 모형

프로토타입 모형(Prototype Model)은 실제 시스템을 만들기 전에 화면이나 핵심 기능만 갖춘 견본(시제품)을 먼저 만들어 고객에게 보여 주고, 피드백을 받아 요구사항을 확정하는 방식이다. 고객이 "주문 화면에 배송 예정일이 보였으면 좋겠다"처럼 말로 설명하기 어려운 요구를 견본을 보고 구체적으로 말할 수 있다는 점이 장점이다. 견본은 요구사항을 확인하는 용도라 버리는 경우가 많고, 견본을 그대로 제품으로 쓰려 하면 품질 문제가 생긴다.

### 나선형 모형

나선형 모형(Spiral Model)은 Barry Boehm이 1986년에 제안했다. 폭포수의 체계적인 단계와 프로토타입의 반복을 합치고, 매 반복마다 ==위험 분석(Risk Analysis)==을 넣은 점이 특징이다. 한 바퀴는 네 가지 활동으로 이뤄진다.

| 순서 | 활동         | 하는 일                                                    |
| ---- | ------------ | ---------------------------------------------------------- |
| 1    | 계획 수립    | 이번 반복의 목표, 제약 조건, 대안을 정한다                 |
| 2    | 위험 분석    | 기술·일정·비용 위험을 찾고 줄일 방법(프로토타입 등)을 정함 |
| 3    | 개발 및 검증 | 이번 반복의 결과물을 만들고 시험한다                       |
| 4    | 고객 평가    | 고객이 결과물을 평가하고 다음 반복을 계획한다              |

바퀴를 돌 때마다 나선이 바깥으로 커지듯 결과물이 점점 완성된다. 위험을 일찍 발견할 수 있어 규모가 크고 복잡한 프로젝트에 맞지만, 위험 분석 역량이 없으면 효과가 떨어진다.

### 반복적·점증적 모형과 비교

반복적 모형(Iterative Model)은 전체 시스템을 여러 번 반복해 다듬고, 점증적 모형(Incremental Model)은 시스템을 기능 단위로 나눠 하나씩 완성해 붙인다. 예를 들어 쇼핑몰을 점증적으로 만들면 1차에 회원·상품 조회, 2차에 장바구니·주문, 3차에 결제·배송 조회를 완성해 차례로 출시한다.

| 모형        | 진행 방식                        | 맞는 상황                       | 시험 키워드                    |
| ----------- | -------------------------------- | ------------------------------- | ------------------------------ |
| 폭포수      | 단계를 한 번씩, 되돌아가지 않음  | 요구사항이 확정된 소규모 사업   | 고전적, 선형 순차, 단계별 승인 |
| 프로토타입  | 견본을 보여 주고 요구사항 확정   | 고객 요구가 불명확할 때         | 시제품, 견본, 사용자 피드백    |
| 나선형      | 네 활동을 여러 바퀴 반복         | 대규모·고위험 사업              | Boehm, 위험 분석, 점진적       |
| 반복·점증적 | 기능 단위로 나눠 차례로 완성     | 일부 기능을 먼저 출시해야 할 때 | 증분, 반복                     |
| 애자일      | 짧은 주기로 동작하는 결과물 제공 | 요구사항이 자주 바뀔 때         | 고객 협업, 변화 대응           |

> [!TIP] 시험에서는 이렇게 묻는다
> "위험 분석 단계가 포함된 생명주기 모형은?"처럼 설명을 주고 모형 이름을 고르게 한다. ==Boehm과 위험 분석은 나선형==, "이전 단계로 돌아갈 수 없다"는 폭포수, "견본"은 프로토타입이라는 연결을 외워 둔다. 나선형의 네 활동 순서(계획 수립 → 위험 분석 → 개발 및 검증 → 고객 평가)를 빈칸으로 묻기도 한다.

## 애자일과 XP, 스크럼

### 애자일 선언

애자일(Agile)은 "민첩한"이라는 뜻으로, 특정 방법론 하나가 아니라 짧은 주기를 반복하며 고객 요구 변화에 빠르게 대응하는 방법론들을 묶어 부르는 이름이다. 2001년 미국 유타주에 모인 개발자 17명이 발표한 「애자일 소프트웨어 개발 선언」이 출발점이며, 선언문은 네 가지 가치를 내세운다.

| 더 가치를 두는 것   | 덜 가치를 두는 것 |
| ------------------- | ----------------- |
| 개인과 상호작용     | 공정과 도구       |
| 작동하는 소프트웨어 | 포괄적인 문서     |
| 고객과의 협력       | 계약 협상         |
| 변화에 대응하기     | 계획을 따르기     |

선언문은 오른쪽 항목도 가치가 있지만 왼쪽 항목에 더 높은 가치를 둔다고 명시한다. 문서와 계획을 버리라는 뜻이 아니라는 점이 시험에서 오답 보기로 자주 쓰인다. 대표적인 애자일 방법론으로는 XP, 스크럼, 칸반(Kanban), 린(Lean), 기능 중심 개발(FDD, Feature Driven Development)이 있다.

### XP

XP(eXtreme Programming)는 Kent Beck이 1990년대 후반에 정리한 방법론으로, 1~3주 정도의 짧은 반복과 잦은 릴리즈로 고객 요구에 대응한다. 다섯 가지 핵심 가치를 내세운다.

| 핵심 가치                | 뜻                                                      |
| ------------------------ | ------------------------------------------------------- |
| 의사소통 (Communication) | 개발자, 고객, 관리자가 직접 자주 대화한다               |
| 단순성 (Simplicity)      | 지금 필요한 기능만 가장 단순하게 구현한다               |
| 피드백 (Feedback)        | 테스트와 고객 평가로 결과를 빠르게 확인한다             |
| 용기 (Courage)           | 고객 요구 변화에 맞춰 설계를 과감히 바꾸고 리팩토링한다 |
| 존중 (Respect)           | 팀원 서로의 역할과 의견을 존중한다                      |

XP는 가치를 실천하는 구체적인 규칙(실천 사항)도 정한다. 시험에 자주 나오는 실천 사항은 다음과 같다.

| 실천 사항                             | 내용                                                                |
| ------------------------------------- | ------------------------------------------------------------------- |
| 짝 프로그래밍 (Pair Programming)      | 두 사람이 컴퓨터 한 대로 함께 코딩한다. 한 명이 작성, 한 명이 검토  |
| 테스트 주도 개발 (TDD)                | 실패하는 테스트를 먼저 작성하고, 통과하는 코드를 그다음에 작성한다  |
| 전체 팀 (Whole Team)                  | 고객도 팀의 일원으로 개발 현장에 참여한다                           |
| 공동 코드 소유 (Collective Ownership) | 누구나 어느 코드든 수정할 수 있다                                   |
| 지속적인 통합 (CI)                    | 작은 단위로 자주 저장소에 통합하고 자동으로 빌드·테스트한다         |
| 리팩토링 (Refactoring)                | 동작은 그대로 두고 코드 구조를 계속 개선한다                        |
| 소규모 릴리즈 (Small Releases)        | 동작하는 결과물을 짧은 주기로 자주 배포한다                         |
| 계획 게임 (Planning Game)             | 고객이 사용자 스토리의 우선순위를 정하고 개발자가 작업량을 추정한다 |

### 스크럼

스크럼(Scrum)은 럭비에서 선수들이 어깨를 맞대고 공을 다투는 대형에서 이름을 따온 방법론으로, 팀이 스스로 일을 나눠 맡는 자기 조직화를 강조한다. Ken Schwaber와 Jeff Sutherland가 작성한 「스크럼 가이드」가 공식 정의이며, 2020년판 기준으로 역할은 제품 책임자, 스크럼 마스터, 개발자 세 가지다.

![스크럼의 한 스프린트](./images/eip-software-design-scrum.svg '제품 백로그에서 고른 항목을 스프린트 동안 증분으로 만들고 리뷰와 회고로 마무리')

| 구분      | 이름                            | 내용                                                               |
| --------- | ------------------------------- | ------------------------------------------------------------------ |
| 역할      | 제품 책임자 (PO, Product Owner) | 제품 백로그를 작성하고 항목의 우선순위를 정한다                    |
| 역할      | 스크럼 마스터 (SM)              | 팀이 스크럼 규칙을 지키도록 돕고, 진행을 막는 장애 요소를 제거한다 |
| 역할      | 개발자 (Developers)             | 스프린트마다 동작하는 증분을 만든다                                |
| 산출물    | 제품 백로그 (Product Backlog)   | 제품에 필요한 기능(사용자 스토리)을 우선순위 순으로 나열한 목록    |
| 산출물    | 스프린트 백로그                 | 이번 스프린트에 할 항목과 그것을 나눈 작업 목록                    |
| 이벤트    | 스프린트 (Sprint)               | 1개월 이하(보통 2~4주)의 고정된 개발 주기                          |
| 이벤트    | 스프린트 계획 회의              | 이번 스프린트의 목표와 할 항목을 정한다                            |
| 이벤트    | 일일 스크럼 (Daily Scrum)       | 매일 같은 시각 15분 동안 진행 상황과 장애 요소를 공유한다          |
| 이벤트    | 스프린트 리뷰                   | 완성된 증분을 이해관계자에게 시연하고 피드백을 받는다              |
| 이벤트    | 스프린트 회고 (Retrospective)   | 팀이 일하는 방식을 돌아보고 다음 스프린트에서 개선할 점을 정한다   |
| 진척 조회 | 번다운 차트 (Burndown Chart)    | 남은 작업량을 날짜별로 그린 그래프. 0을 향해 내려가야 정상이다     |

리뷰와 회고는 이름이 비슷해 자주 헷갈린다. ==리뷰는 "무엇을 만들었는가"(제품)==를, ==회고는 "어떻게 일했는가"(프로세스)==를 점검한다.

> [!TIP] 시험에서는 이렇게 묻는다
> "스크럼에서 백로그의 우선순위를 정하는 역할은?"(제품 책임자), "XP의 핵심 가치가 아닌 것은?"(보기에 "문서화"나 "정확성"을 섞는다), "애자일 선언의 가치로 옳지 않은 것은?"(문서보다 계약 협상을 중시한다는 식으로 뒤집은 보기) 같은 형태가 많다. XP의 5가지 가치는 앞 글자를 따서 "의단피용존"처럼 묶어 외우는 수험생이 많다.

## 요구사항 확인

### 현행 시스템 파악

새 시스템을 만들기 전에 지금 쓰고 있는 시스템이 무엇을 어떻게 하는지 조사하는 것을 현행 시스템 파악이라고 한다. 시스템 구성(업무 단위), 기능, 다른 시스템과의 인터페이스, 아키텍처, 사용 중인 소프트웨어와 하드웨어, 네트워크 구성을 차례로 조사한다. 개발 기술 환경을 파악할 때는 운영체제, DBMS, 미들웨어, 오픈 소스 라이선스 같은 항목을 확인한다. 예를 들어 오픈 소스 라이브러리를 쓰려면 라이선스가 GPL인지 MIT인지에 따라 소스 공개 의무가 달라지므로 이 단계에서 확인해 둔다.

### 기능 요구사항과 비기능 요구사항

요구사항(Requirements)은 고객이 시스템에 원하는 기능과 그 기능이 갖춰야 할 조건이다. 크게 두 종류로 나눈다.

| 구분            | 뜻                                             | 온라인 서점의 예                                |
| --------------- | ---------------------------------------------- | ----------------------------------------------- |
| 기능 요구사항   | 시스템이 ==무엇을 하는가== (입력, 처리, 출력)  | 회원은 ISBN이나 제목으로 도서를 검색할 수 있다  |
| 비기능 요구사항 | 기능을 ==얼마나 잘, 어떤 조건에서== 수행하는가 | 검색 결과는 2초 안에 표시한다, 동시 접속 1만 명 |

비기능 요구사항에는 성능, 보안, 가용성, 신뢰성, 사용성, 유지보수성, 이식성, 법·규정 준수 같은 품질 조건과 제약 사항이 들어간다. "개인정보는 암호화해 저장한다"는 기능처럼 보이지만 보안 품질을 정한 조건이므로 비기능 요구사항이다.

### 요구사항 개발 프로세스

요구사항은 도출, 분석, 명세, 확인 네 단계로 다듬는다.

![요구사항 개발 프로세스](./images/eip-software-design-requirements.svg '도출에서 확인까지 네 단계와 그 전체를 감싸는 요구사항 관리')

| 단계 | 영문          | 하는 일                                         | 대표 기법·산출물                                 |
| ---- | ------------- | ----------------------------------------------- | ------------------------------------------------ |
| 도출 | Elicitation   | 이해관계자에게서 요구를 수집한다                | 인터뷰, 설문, 브레인스토밍, 워크숍, 프로토타이핑 |
| 분석 | Analysis      | 누락·모순·중복을 찾고 범위를 정한다             | DFD, 자료 사전, UML                              |
| 명세 | Specification | 분석한 요구를 문서로 작성한다                   | 요구사항 명세서(SRS)                             |
| 확인 | Validation    | 명세서가 고객 요구를 정확히 반영했는지 검증한다 | 동료 검토, 워크스루, 인스펙션                    |

명세 방법은 정형 명세와 비정형 명세로 나뉜다. 정형 명세는 수학 기호와 논리식으로 요구사항을 적는 방법이라 모호함이 없지만 작성과 이해가 어렵다(Z, VDM, Petri-net이 대표적). 비정형 명세는 자연어, 그림, 표로 적는 방법이라 이해하기 쉽지만 같은 문장을 사람마다 다르게 해석할 수 있다.

요구사항 확인 단계의 검토 방법 세 가지도 구분해 둔다.

| 검토 방법               | 진행 방식                                                               |
| ----------------------- | ----------------------------------------------------------------------- |
| 동료 검토 (Peer Review) | 작성자가 명세서를 설명하고 동료들이 결함을 찾는다                       |
| 워크스루 (Walk Through) | 검토 자료를 회의 전에 배포하고, 짧은 회의로 결함을 찾는다               |
| 인스펙션 (Inspection)   | 작성자를 ==제외한== 전문가들이 정해진 절차에 따라 결함을 찾는 공식 검토 |

> [!TIP] 시험에서는 이렇게 묻는다
> 요구사항 문장을 여러 개 주고 비기능 요구사항을 고르게 하거나, 요구사항 개발 단계의 순서(도출 → 분석 → 명세 → 확인)를 묻는다. "작성자를 제외한 전문가"가 나오면 인스펙션이다.

## 구조적 분석과 객체지향 분석

요구사항을 분석할 때 쓰는 도구는 시스템을 "데이터가 흘러가며 처리되는 과정"으로 보느냐, "객체들이 메시지를 주고받는 구조"로 보느냐에 따라 나뉜다.

### 자료 흐름도

자료 흐름도(DFD, Data Flow Diagram)는 시스템 안에서 자료가 어디서 들어와 어떤 처리를 거쳐 어디에 저장되는지 그린 그림이다. 구성 요소는 네 가지뿐이라 비전공자인 고객도 읽을 수 있다.

![수강 신청 시스템의 자료 흐름도](./images/eip-software-design-dfd.svg '단말, 프로세스, 자료 흐름, 자료 저장소 네 기호')

| 구성 요소                | 기호                 | 예시                         |
| ------------------------ | -------------------- | ---------------------------- |
| 프로세스 (Process)       | 원                   | 1.0 수강 신청, 2.0 정원 확인 |
| 자료 흐름 (Data Flow)    | 화살표               | 신청 과목, 가능 여부         |
| 자료 저장소 (Data Store) | 평행선(위아래 두 줄) | 수강 내역, 강의 정보         |
| 단말 (Terminator)        | 사각형               | 학생                         |

DFD는 단계적으로 상세화한다. 시스템 전체를 프로세스 하나로 그린 것을 배경도(Context Diagram, 0레벨)라 하고, 그 프로세스를 1.0, 2.0으로 나눈 것이 1레벨, 1.0을 다시 1.1, 1.2로 나눈 것이 2레벨이다. 위 그림은 1레벨에 해당한다.

### 자료 사전

자료 사전(DD, Data Dictionary)은 DFD에 나온 자료 흐름과 자료 저장소의 내용을 기호로 정의한 문서다. "메타데이터(데이터에 대한 데이터)"라고 설명하는 문제가 자주 나온다.

| 기호     | 뜻                | 예                                        |
| -------- | ----------------- | ----------------------------------------- |
| `=`      | 자료의 정의       | `수강신청 = 학번 + 과목코드 + 신청일`     |
| `+`      | 자료의 연결 (AND) | `학번 + 이름`                             |
| `[ \| ]` | 자료의 선택 (OR)  | `결제수단 = [카드 \| 계좌이체 \| 포인트]` |
| `{ }`    | 자료의 반복       | `장바구니 = {도서코드 + 수량}`            |
| `( )`    | 생략 가능한 자료  | `주소 = 도로명 + (상세주소)`              |
| `** **`  | 주석              | `** 학번은 8자리 숫자 **`                 |

### 구조적 분석의 다른 도구

| 도구                                       | 용도                                                                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 소단위 명세서 (Mini-Spec)                  | DFD의 최하위 프로세스가 하는 일을 의사 코드, 결정표 등으로 적는다                                                          |
| 개체 관계도 (ERD)                          | 데이터와 데이터 사이의 관계를 그린다                                                                                       |
| 상태 전이도 (STD)                          | 시스템이 어떤 사건(이벤트)으로 어떤 상태에서 어떤 상태로 바뀌는지 그린다                                                   |
| HIPO (Hierarchy Input Process Output)      | 시스템을 계층으로 나누고 각 기능의 입력·처리·출력을 도표로 그린다. 가시적 도표, 총체적 도표, 세부적 도표로 구성            |
| CASE (Computer Aided Software Engineering) | 요구 분석부터 설계·구현·테스트까지 작업을 자동화하는 도구. 대표 요구사항 분석 CASE 도구로 SADT, SREM, PSL/PSA, TAGS가 있다 |

### 객체지향 분석 방법론

객체지향 분석(OOA, Object Oriented Analysis)은 현실 세계의 대상을 속성(데이터)과 연산(동작)을 함께 가진 객체로 보고, 객체 사이의 관계를 찾아 시스템을 모델링한다. 방법론마다 제안자와 특징이 달라 짝을 지어 묻는다.

| 방법론       | 제안자              | 특징                                                                    |
| ------------ | ------------------- | ----------------------------------------------------------------------- |
| OMT          | Rumbaugh (럼바우)   | 객체 모델링 → 동적 모델링 → 기능 모델링 순서로 분석. 그래픽 표기 중심   |
| Booch        | Booch (부치)        | 미시적·거시적 개발 프로세스를 모두 사용                                 |
| OOSE         | Jacobson (제이콥슨) | 유스케이스를 중심으로 분석                                              |
| Coad-Yourdon | Coad, Yourdon       | E-R 다이어그램으로 객체의 행위를 모델링                                 |
| Wirfs-Brock  | Wirfs-Brock         | 분석과 설계를 구분하지 않고 고객 명세서를 평가해 설계까지 연속으로 진행 |

럼바우의 OMT는 세 단계와 각 단계에서 쓰는 다이어그램을 함께 묻는다.

| 단계        | 무엇을 모델링하는가                 | 쓰는 다이어그램  |
| ----------- | ----------------------------------- | ---------------- |
| 객체 모델링 | 객체와 객체 사이의 관계, 속성, 연산 | 객체 다이어그램  |
| 동적 모델링 | 시간 흐름에 따른 객체의 상태 변화   | 상태 다이어그램  |
| 기능 모델링 | 자료가 어떻게 처리되는가            | 자료 흐름도(DFD) |

> [!TIP] 시험에서는 이렇게 묻는다
> "럼바우 분석 기법에서 자료 흐름도를 사용하는 단계는?"(기능 모델링), "유스케이스를 강조한 방법론은?"(Jacobson), "DFD의 구성 요소가 아닌 것은?"(보기에 "제어 흐름"이나 "클래스"를 섞는다) 형태가 자주 나온다. 럼바우 단계 순서는 "객동기"로 외운다.

## UML

UML(Unified Modeling Language)은 객체지향 시스템을 그리는 표준 그래픽 언어다. 1990년대 중반 Booch, Rumbaugh, Jacobson 세 사람이 각자의 표기법을 합쳐 만들었고, 1997년 OMG(Object Management Group)가 표준으로 채택했다. 현재 판은 2017년에 발표된 UML 2.5.1이고, 2.4.1판은 ISO/IEC 19505로 국제 표준이 되었다.

UML의 구성 요소는 사물(Things), 관계(Relationships), 다이어그램(Diagram) 세 가지다. 사물은 다이어그램 안에 그리는 대상으로 구조 사물(클래스, 유스케이스, 컴포넌트, 노드), 행동 사물(상호작용, 상태), 그룹 사물(패키지), 주해 사물(노트)로 나뉜다.

### 다이어그램의 종류

다이어그램은 시스템의 정적인 구조를 그리는 구조 다이어그램과, 시간에 따른 동작을 그리는 행위 다이어그램으로 나뉜다.

![UML 다이어그램의 분류](./images/eip-software-design-uml-diagrams.svg '구조 다이어그램 6개와 행위 다이어그램 7개')

구분이 헷갈리면 "시간이 흐르는가"를 기준으로 삼는다. 클래스 다이어그램은 프로그램이 실행되지 않아도 존재하는 구조이고, 시퀀스 다이어그램은 메시지가 오가는 순서라 시간이 흐른다. 활동 다이어그램은 순서도처럼 처리 흐름을 그리므로 행위 다이어그램이다.

### 관계의 종류

관계는 사물과 사물이 어떻게 연결되는지 나타낸다. 시험에서 가장 자주 나오는 부분이며, 선 모양과 화살표 방향까지 묻는다.

![UML 관계의 표기법](./images/eip-software-design-uml-relations.svg '여섯 가지 관계의 선 모양과 마름모·삼각형의 위치')

| 관계                    | 뜻                                                         | 코드로 보면                                      |
| ----------------------- | ---------------------------------------------------------- | ------------------------------------------------ |
| 연관 (Association)      | 두 사물이 서로 연결되어 있다                               | 학생 객체가 수강 중인 강의 목록을 참조           |
| 집합 (Aggregation)      | 전체와 부분 관계, 부분이 ==독립적으로 존재 가능==          | 컴퓨터를 버려도 프린터는 다른 컴퓨터에 연결 가능 |
| 포함 (Composition)      | 전체와 부분 관계, 전체가 사라지면 ==부분도 함께 사라짐==   | 주문을 삭제하면 주문 항목도 삭제                 |
| 일반화 (Generalization) | 상위(일반)와 하위(구체) 관계, 상속                         | `class Car extends Vehicle`                      |
| 의존 (Dependency)       | 한 사물이 다른 사물을 잠시 사용. 사용하는 쪽이 영향을 받음 | 메서드 매개변수나 지역 변수로만 사용             |
| 실체화 (Realization)    | 인터페이스가 정한 기능을 클래스가 구현                     | `class Bird implements Flyable`                  |

집합과 포함은 둘 다 마름모를 전체 쪽에 붙인다. 빈 마름모가 집합, 채운 마름모가 포함이다. 일반화의 빈 삼각형은 부모(상위) 쪽을 가리킨다.

### 클래스 다이어그램

클래스 다이어그램은 클래스의 이름, 속성, 연산과 클래스 사이의 관계를 그린다. 클래스 상자는 세 칸으로 나눠 위에서부터 이름, 속성, 연산을 적고, 이름 앞의 기호로 접근 범위(가시성)를 나타낸다.

![주문 도메인의 클래스 다이어그램](./images/eip-software-design-class.svg '가시성 기호, 다중성, 포함과 일반화 관계')

| 기호 | 가시성    | 접근 범위                 |
| ---- | --------- | ------------------------- |
| `+`  | public    | 어디서나 접근             |
| `-`  | private   | 해당 클래스 안에서만      |
| `#`  | protected | 같은 패키지와 하위 클래스 |
| `~`  | package   | 같은 패키지 안에서만      |

선 양 끝의 숫자는 다중성(Multiplicity)으로, 상대 객체가 몇 개 연결될 수 있는지 나타낸다. `1`은 정확히 하나, `0..1`은 없거나 하나, `0..*` 또는 `*`는 0개 이상, `1..*`는 1개 이상이다. 위 그림에서 회원 쪽 `1`과 주문 쪽 `0..*`는 "회원 한 명은 주문을 0개 이상 가진다"는 뜻이다.

### 유스케이스 다이어그램

유스케이스 다이어그램은 사용자 관점에서 시스템이 제공하는 기능을 그린다. 시스템 범위를 사각형(시스템 경계)으로 그리고, 그 밖에 사람 모양의 액터를, 안에 타원 모양의 유스케이스를 배치한다. 액터는 시스템과 상호작용하는 외부 존재로, 사람인 주액터(회원)와 외부 시스템인 부액터(결제 대행사)로 나뉜다.

![온라인 서점의 유스케이스 다이어그램](./images/eip-software-design-usecase.svg 'include는 기본에서 포함으로, extend는 확장에서 기본으로 화살표가 향한다')

유스케이스 사이의 관계 중 include와 extend는 화살표 방향이 반대라서 시험에 단골로 나온다.

| 관계               | 뜻                                                         | 화살표 방향             | 예                 |
| ------------------ | ---------------------------------------------------------- | ----------------------- | ------------------ |
| 포함 (`«include»`) | 기본 유스케이스를 실행하면 ==항상== 포함 유스케이스도 실행 | 기본 → 포함             | 도서 주문 → 로그인 |
| 확장 (`«extend»`)  | 특정 조건을 만족할 ==때만== 확장 유스케이스가 실행         | 확장 → 기본             | 쿠폰 적용 → 결제   |
| 일반화             | 유사한 유스케이스·액터를 묶은 상위 개념                    | 하위 → 상위 (빈 삼각형) | 카드 결제 → 결제   |

### 시퀀스 다이어그램

시퀀스(순차) 다이어그램은 객체들이 시간 순서에 따라 주고받는 메시지를 그린다. 가로축에 객체를, 세로축에 시간을 배치한다.

![로그인 요청의 시퀀스 다이어그램](./images/eip-software-design-sequence.svg '생명선, 활성 박스, 요청과 응답 메시지')

| 구성 요소                    | 표기                          | 뜻                                  |
| ---------------------------- | ----------------------------- | ----------------------------------- |
| 객체 (Object)                | 상자 안의 `:이름`             | 메시지를 주고받는 참여자            |
| 생명선 (Lifeline)            | 객체 아래로 내려가는 점선     | 객체가 존재하는 기간                |
| 실행 (Activation, 활성 박스) | 생명선 위의 좁은 직사각형     | 객체가 메시지를 받아 처리 중인 구간 |
| 메시지 (Message)             | 실선 화살표                   | 객체가 다른 객체에 보내는 요청      |
| 응답 메시지 (Reply)          | 점선 화살표                   | 요청에 대한 결과                    |
| 자체 메시지 (Self Message)   | 자기 자신으로 돌아오는 화살표 | 객체가 자기 메서드를 호출           |

비슷한 행위 다이어그램인 커뮤니케이션 다이어그램은 같은 메시지를 시간축 없이 객체 사이의 링크 위에 번호로 표시한다. 상태 다이어그램은 객체 하나가 이벤트를 받아 어떤 상태로 바뀌는지(예: 주문의 결제 대기 → 결제 완료 → 배송 중 → 배송 완료) 그리고, 활동 다이어그램은 처리 흐름을 분기·병렬 처리와 함께 그린다.

> [!TIP] 시험에서는 이렇게 묻는다
> "UML 다이어그램 중 성격이 다른 하나는?"(구조 다이어그램 사이에 시퀀스를 끼워 넣는다), "전체가 사라지면 부분도 사라지는 관계는?"(포함, Composition), "시퀀스 다이어그램의 구성 요소가 아닌 것은?"(보기에 "노드"나 "패키지"를 섞는다) 형태다. 실기에서는 클래스 다이어그램 그림을 주고 관계 이름을 쓰게 한다.

<details>
<summary>예제: UML 관계 고르기</summary>

다음 설명에 맞는 관계를 고른다.

| 번호 | 설명                                                                           | 답     |
| ---- | ------------------------------------------------------------------------------ | ------ |
| 1    | 대학교와 학과. 대학교가 폐교되면 학과도 함께 없어진다                          | 포함   |

| 3    | `Dog`가 `Animal`을 상속한다                                                    | 일반화 |

| 5    | `ArrayList`가 `List` 인터페이스를 구현한다                                     | 실체화 |

## 화면 설계

### UI의 유형

사용자 인터페이스(UI, User Interface)는 사용자와 시스템이 정보를 주고받는 접점이다. 상호작용 수단에 따라 다음과 같이 나눈다.

| 유형 | 이름                     | 상호작용 방식                                   | 예                                 |
| ---- | ------------------------ | ----------------------------------------------- | ---------------------------------- |
| CLI  | Command Line Interface   | 명령어를 텍스트로 입력하고 결과도 텍스트로 받음 | 터미널, 명령 프롬프트              |
| GUI  | Graphical User Interface | 아이콘·메뉴를 마우스로 선택                     | Windows, macOS 데스크톱            |
| NUI  | Natural User Interface   | 말이나 몸짓 같은 자연스러운 행동으로 조작       | 스마트폰 터치·핀치, 동작 인식 게임 |
| VUI  | Voice User Interface     | 음성으로 조작                                   | 음성 비서, AI 스피커               |
| OUI  | Organic User Interface   | 모든 사물이 입출력 장치가 되는 인터페이스       | 사물 인터넷, 휘어지는 디스플레이   |

### UI의 기본 원칙

UI 설계의 기본 원칙은 네 가지다. 각 원칙의 뜻을 바꿔 오답 보기를 만드는 문제가 자주 나온다.

| 원칙   | 뜻                                                   | 지키지 못한 예                                |
| ------ | ---------------------------------------------------- | --------------------------------------------- |
| 직관성 | 누구나 쉽게 이해하고 사용할 수 있어야 한다           | 저장 버튼에 아무 설명 없는 기호만 표시        |
| 유효성 | 사용자의 목적을 정확하고 완벽하게 달성해야 한다      | 검색 버튼을 눌러도 일부 결과가 누락           |
| 학습성 | 누구나 쉽게 배우고 익힐 수 있어야 한다               | 메뉴 위치가 화면마다 달라 매번 다시 찾아야 함 |
| 유연성 | 사용자 요구를 최대한 수용하고 실수를 최소화해야 한다 | 실수로 삭제한 항목을 되돌릴 방법이 없음       |

설계 지침으로는 사용자 중심, 일관성, 단순성, 결과 예측 가능, 가시성, 표준화, 접근성, 명확성, 오류 발생 해결이 있다. 이 가운데 사용성(얼마나 빠르고 쉽게 이해하고 효율적으로 쓸 수 있는가)을 가장 먼저 고려한다.

### UI 설계 도구

화면을 실제로 구현하기 전에 모양과 흐름을 확인하는 도구는 완성도에 따라 다음과 같이 구분한다.

| 도구                     | 완성도와 용도                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| 와이어프레임 (Wireframe) | 화면에 들어갈 요소의 배치만 선으로 그린 뼈대. 색과 이미지는 넣지 않는다                              |
| 스토리보드 (Storyboard)  | 와이어프레임에 화면 설명, 동작 흐름, 데이터 처리 내용까지 적은 문서. 설계자와 개발자가 최종으로 참고 |
| 프로토타입 (Prototype)   | 와이어프레임·스토리보드에 동적 효과를 넣어 실제처럼 눌러 볼 수 있게 만든 견본                        |
| 목업 (Mockup)            | 실제 화면과 비슷하게 만든 정적인 모형. 시각적으로만 구성하고 동작하지 않는다                         |
| 유스케이스 (Use Case)    | 사용자 요구를 기능 단위로 표현한 모델. UI 요구사항을 정리할 때 쓴다                                  |

### UI 품질 요구사항

소프트웨어 품질 특성의 표준으로 ISO/IEC 9126이 오래 쓰였고, 2011년부터 ISO/IEC 25010(SQuaRE 체계)이 이를 대체했다. 시험에서는 ISO/IEC 9126의 6가지 특성을 주로 묻는다.

| ISO/IEC 9126 특성            | 뜻                                   | 하위 특성 예                        |
| ---------------------------- | ------------------------------------ | ----------------------------------- |
| 기능성 (Functionality)       | 요구한 기능을 정확히 제공하는가      | 적절성, 정밀성, 상호 운용성, 보안성 |
| 신뢰성 (Reliability)         | 정해진 조건에서 오류 없이 동작하는가 | 성숙성, 고장 허용성, 회복성         |
| 사용성 (Usability)           | 쉽게 이해하고 배우고 쓸 수 있는가    | 이해성, 학습성, 운용성, 친밀성      |
| 효율성 (Efficiency)          | 자원을 적게 쓰고 빠르게 응답하는가   | 시간 효율성, 자원 효율성            |
| 유지보수성 (Maintainability) | 수정·개선하기 쉬운가                 | 분석성, 변경성, 안정성, 시험성      |
| 이식성 (Portability)         | 다른 환경으로 옮겨 쓰기 쉬운가       | 적응성, 설치성, 대체성, 공존성      |

ISO/IEC 25010(2011)은 여기에 호환성과 보안성을 독립 특성으로 추가해 8가지로 정리했고, 2023년 개정판은 다시 일부 이름을 바꾸고 안전성(Safety)을 추가했다. 정보처리기사 필기에서는 9126의 6가지 특성과 하위 특성을 묻는 문제가 주로 출제되어 왔다.

> [!TIP] 시험에서는 이렇게 묻는다
> "UI 기본 원칙 중 사용자의 목적을 정확하게 달성하는 것은?"(유효성), "실제 화면처럼 동작하지는 않고 모양만 갖춘 정적 모형은?"(목업), "ISO/IEC 9126의 품질 특성이 아닌 것은?"(보기에 "가시성"이나 "독립성"을 섞는다)처럼 나온다.

## 소프트웨어 아키텍처

소프트웨어 아키텍처(Software Architecture)는 시스템을 이루는 구성 요소, 구성 요소 사이의 관계, 그리고 그 구조를 정한 설계 원칙을 말한다. 건물의 골조처럼 한 번 정하면 바꾸기 어렵기 때문에 성능, 보안, 확장성 같은 품질 속성을 설계 초기에 고려해 결정한다.

### 설계의 기본 원리

| 원리                              | 뜻                                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------------- |
| 모듈화 (Modularity)               | 시스템을 기능 단위의 모듈로 나눈다. 모듈 하나를 고쳐도 다른 모듈에 영향이 적어진다    |
| 추상화 (Abstraction)              | 공통 성질만 뽑아 간단히 표현하고 세부는 나중에 정한다. 과정·데이터·제어 추상화가 있다 |
| 단계적 분해 (Stepwise Refinement) | Niklaus Wirth가 제안. 상위 개념부터 하위 기능으로 점점 구체화한다                     |
| 정보 은닉 (Information Hiding)    | 모듈 내부의 데이터와 구현을 숨기고 정해진 인터페이스로만 접근하게 한다                |

### 아키텍처 패턴

아키텍처 패턴은 자주 마주치는 구조 문제에 대해 검증된 해결 구조다. 시험에는 다음 패턴이 자주 나온다.

![자주 출제되는 아키텍처 패턴 네 가지](./images/eip-software-design-architecture-patterns.svg '계층, 클라이언트-서버, 파이프-필터, MVC의 구조')

| 패턴                      | 구조                                                                              | 대표 사례                                 |
| ------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------- |
| 계층 (Layered)            | 시스템을 계층으로 나누고, 각 계층은 바로 아래 계층의 서비스만 쓰고 바로 위에 제공 | OSI 7계층, 3계층 웹 애플리케이션          |
| 클라이언트-서버           | 서버 하나에 클라이언트 여럿이 요청을 보내고 서버가 응답                           | 웹 브라우저와 웹 서버                     |
| 파이프-필터 (Pipe-Filter) | 데이터가 파이프를 따라 흐르며 필터(처리 단계)를 차례로 거친다                     | UNIX 셸의 `cat log \| grep ERROR \| sort` |
| 모델-뷰-컨트롤러 (MVC)    | 모델(데이터·로직), 뷰(화면), 컨트롤러(입력 처리)를 분리                           | 웹 프레임워크, GUI 애플리케이션           |
| 마스터-슬레이브           | 마스터가 작업을 나눠 슬레이브에 배분하고 결과를 취합해 최종 결과를 만든다         | 데이터베이스 복제, 병렬 연산              |
| 브로커 (Broker)           | 컴포넌트가 브로커에 서비스를 요청하면 브로커가 알맞은 컴포넌트에 연결해 준다      | CORBA, 메시지 브로커                      |
| 피어 투 피어 (P2P)        | 모든 노드가 클라이언트이자 서버                                                   | 파일 공유(BitTorrent)                     |
| 이벤트-버스 (Event-Bus)   | 소스가 채널에 이벤트를 발행하면 그 채널을 구독한 리스너가 처리                    | 알림 서비스                               |
| 블랙보드 (Blackboard)     | 여러 컴포넌트가 공유 데이터 저장소(블랙보드)에 접근해 해결책을 함께 찾는다        | 음성 인식, 신호 해석                      |
| 인터프리터 (Interpreter)  | 특정 언어로 작성된 프로그램을 해석하는 컴포넌트로 구성                            | 질의 언어 해석기                          |

> [!TIP] 시험에서는 이렇게 묻는다
> 패턴의 설명을 주고 이름을 고르게 한다. "데이터 스트림 단계마다 처리를 캡슐화하고 파이프로 전달"은 파이프-필터, "작업을 분할해 배분하고 결과를 취합"은 마스터-슬레이브, "모든 노드가 서버이자 클라이언트"는 P2P다.

## 객체지향 설계 원칙

### 객체지향의 기본 개념

객체지향(Object Oriented)은 프로그램을 데이터와 그 데이터를 다루는 함수를 묶은 객체들의 상호작용으로 구성하는 방식이다. 시험에 나오는 기본 용어는 다음과 같다.

| 용어                   | 뜻                                                                               |
| ---------------------- | -------------------------------------------------------------------------------- |
| 객체 (Object)          | 데이터(속성)와 그 데이터를 처리하는 함수(메서드)를 묶은 실체                     |
| 클래스 (Class)         | 같은 속성과 메서드를 갖는 객체들을 정의한 틀. 클래스로 만든 객체를 인스턴스라 함 |
| 메시지 (Message)       | 객체에 어떤 동작을 하라고 보내는 요청. 메서드 호출로 구현                        |
| 캡슐화 (Encapsulation) | 데이터와 메서드를 하나로 묶고 내부 구현을 숨긴다. 정보 은닉과 함께 쓰인다        |
| 상속 (Inheritance)     | 상위 클래스의 속성과 메서드를 하위 클래스가 물려받는다                           |
| 다형성 (Polymorphism)  | 같은 메시지에 객체마다 다르게 반응한다. 오버라이딩, 오버로딩으로 구현            |
| 추상화 (Abstraction)   | 공통 성질을 뽑아 상위 개념(추상 클래스, 인터페이스)으로 정의한다                 |

### SOLID 원칙

SOLID는 Robert C. Martin이 정리한 객체지향 설계 원칙 다섯 가지의 앞 글자를 딴 이름이다. 원칙을 지키면 기능을 추가하거나 바꿀 때 고쳐야 하는 코드가 줄어든다.

| 원칙 | 이름                                              | 뜻                                                                       |
| ---- | ------------------------------------------------- | ------------------------------------------------------------------------ |
| S    | 단일 책임 원칙 (SRP, Single Responsibility)       | 클래스는 하나의 책임만 가지고, 변경할 이유도 하나여야 한다               |
| O    | 개방-폐쇄 원칙 (OCP, Open-Closed)                 | 기능 확장에는 열려 있고, 기존 코드 변경에는 닫혀 있어야 한다             |
| L    | 리스코프 치환 원칙 (LSP, Liskov Substitution)     | 하위 클래스는 상위 클래스를 대신해도 프로그램이 올바르게 동작해야 한다   |
| I    | 인터페이스 분리 원칙 (ISP, Interface Segregation) | 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나눈다 |
| D    | 의존 역전 원칙 (DIP, Dependency Inversion)        | 구체 클래스가 아니라 추상화(인터페이스)에 의존한다                       |

개방-폐쇄 원칙을 예로 들면, 결제 수단이 카드뿐이던 쇼핑몰에 간편결제를 추가할 때 결제 처리 클래스 안의 `if (type == "card")` 분기를 고치는 대신, `Payment` 인터페이스를 구현한 `EasyPayPayment` 클래스를 새로 추가하는 구조가 OCP를 지킨 설계다. 기존 카드 결제 코드는 한 줄도 바뀌지 않는다.

리스코프 치환 원칙의 고전적인 위반 사례는 `Square extends Rectangle`이다. 직사각형의 너비만 바꾸는 `setWidth(5)`를 정사각형 객체에 호출하면 높이도 함께 바뀌어야 하므로, 직사각형을 기대하고 넓이를 계산한 코드가 틀린 값을 얻는다.

> [!TIP] 시험에서는 이렇게 묻는다
> 원칙의 설명을 주고 이름을 고르는 문제가 대부분이다. "자신이 사용하지 않는 인터페이스와 의존 관계를 맺지 않아야 한다"는 ISP, "확장에는 열려 있고 변경에는 닫혀 있어야 한다"는 OCP다.

## 모듈 설계: 결합도와 응집도

모듈(Module)은 시스템을 기능 단위로 나눈 조각으로, 서브루틴, 함수, 클래스, 패키지 등이 해당한다. 모듈을 얼마나 잘 나눴는지 평가하는 두 기준이 결합도와 응집도다.

- **결합도(Coupling)**: 모듈과 모듈 ==사이==의 의존 정도. 낮을수록 좋다
- **응집도(Cohesion)**: 모듈 ==안==의 구성 요소들이 하나의 목적에 얼마나 관련되어 있는가. 높을수록 좋다

![결합도와 응집도의 순서](./images/eip-software-design-coupling-cohesion.svg '두 줄 모두 왼쪽이 좋은 설계')

### 결합도의 종류

약한(좋은) 것부터 강한(나쁜) 것 순서다.

| 순서 | 결합도                 | 뜻                                                                | 예                                                  |
| ---- | ---------------------- | ----------------------------------------------------------------- | --------------------------------------------------- |
| 1    | 자료 결합도 (Data)     | 필요한 자료(값)만 매개변수로 주고받는다                           | `area(width, height)`                               |
| 2    | 스탬프 결합도 (Stamp)  | 배열·레코드 같은 자료 구조를 통째로 넘기고, 받는 쪽은 일부만 쓴다 | `printName(student)`에서 이름 필드만 사용           |
| 3    | 제어 결합도 (Control)  | 다른 모듈의 처리 흐름을 정하는 제어 신호(플래그)를 넘긴다         | `print(data, mode)`에서 `mode`에 따라 동작이 바뀜   |
| 4    | 외부 결합도 (External) | 한 모듈에서 선언한 변수를 외부의 다른 모듈이 참조한다             | 다른 모듈의 외부 선언 변수를 직접 읽음              |
| 5    | 공통 결합도 (Common)   | 여러 모듈이 공유하는 공통 데이터 영역(전역 변수)을 사용한다       | 전역 변수 `total`을 여러 함수가 수정                |
| 6    | 내용 결합도 (Content)  | 한 모듈이 다른 모듈의 내부 기능이나 데이터를 직접 참조·수정한다   | 다른 모듈 안으로 `goto`, 내부 지역 데이터 직접 변경 |

제어 결합도에는 하위 모듈이 상위 모듈에 처리 방법을 지시하는 권리 전도 현상이 생길 수 있다는 설명이 따라 나온다.

### 응집도의 종류

강한(좋은) 것부터 약한(나쁜) 것 순서다.

| 순서 | 응집도                        | 뜻                                                              | 예                                                            |
| ---- | ----------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| 1    | 기능적 응집도 (Functional)    | 모든 요소가 하나의 기능을 위해 수행된다                         | `calculateTax()` 안의 모든 문장이 세금 계산에만 쓰임          |
| 2    | 순차적 응집도 (Sequential)    | 한 활동의 출력을 다음 활동의 입력으로 쓴다                      | 파일 읽기 → 읽은 값 파싱 → 파싱 결과 검증                     |
| 3    | 교환적 응집도 (Communication) | 같은 입력·출력을 사용하지만 서로 다른 기능을 수행한다           | 같은 주문 레코드로 영수증 출력과 재고 차감을 함께 수행        |
| 4    | 절차적 응집도 (Procedural)    | 여러 기능을 정해진 순서대로 수행하지만 데이터는 주고받지 않는다 | 로그 초기화 → 설정 로드 → 화면 표시                           |
| 5    | 시간적 응집도 (Temporal)      | 특정 시각에 처리되어야 하는 기능들을 묶었다                     | 프로그램 시작 시 실행하는 초기화 모음                         |
| 6    | 논리적 응집도 (Logical)       | 비슷한 성격의 처리를 묶고 매개변수로 하나를 골라 실행한다       | `handle(type)`이 type에 따라 입력·출력·오류 처리 중 하나 실행 |
| 7    | 우연적 응집도 (Coincidental)  | 서로 관련 없는 요소들이 한 모듈에 모여 있다                     | `Utils` 클래스에 날짜 변환, 이메일 발송, 정렬이 섞여 있음     |

> [!IMPORTANT] 순서 외우기
> 결합도는 "자스제외공내"(자료, 스탬프, 제어, 외부, 공통, 내용), 응집도는 "기순교절시논우"(기능, 순차, 교환, 절차, 시간, 논리, 우연)로 외운다. ==두 목록 모두 앞쪽이 좋은 설계==라서, 결합도는 약한 것부터, 응집도는 강한 것부터 적은 순서다.

### 팬인과 팬아웃

모듈 구조도에서 팬인(Fan-In)은 어떤 모듈을 ==호출하는== 상위 모듈의 수, 팬아웃(Fan-Out)은 어떤 모듈이 ==호출하는== 하위 모듈의 수다. 팬인이 높으면 재사용이 잘 되는 모듈이지만 그 모듈에 결함이 생기면 영향이 크므로 집중 테스트가 필요하다. 팬아웃이 높으면 그 모듈이 너무 많은 일을 맡고 있을 수 있으므로 분해를 검토한다.

<details>
<summary>예제: 팬인과 팬아웃 구하기</summary>

모듈 A가 B, C, D를 호출하고, B와 C가 모두 E를 호출하며, D가 E와 F를 호출한다.

| 모듈 | 팬인 (나를 호출하는 모듈 수) | 팬아웃 (내가 호출하는 모듈 수) |
| ---- | ---------------------------- | ------------------------------ |
| A    | 0                            | 3 (B, C, D)                    |
| B    | 1 (A)                        | 1 (E)                          |
| C    | 1 (A)                        | 1 (E)                          |
| D    | 1 (A)                        | 2 (E, F)                       |
| E    | 3 (B, C, D)                  | 0                              |
| F    | 1 (D)                        | 0                              |

E는 팬인이 3이라 세 모듈이 공유하는 공통 모듈이고, E의 결함은 B, C, D 모두에 영향을 준다.

</details>

### 공통 모듈과 코드 설계

공통 모듈은 여러 프로그램에서 공통으로 쓰는 기능(날짜 계산, 로그인 확인, 금액 서식)을 하나로 만든 모듈이다. 공통 모듈의 명세 기법으로는 정확성, 명확성, 완전성, 일관성, 추적성이 있다. 재사용 범위에 따라 함수와 객체, 컴포넌트, 애플리케이션 재사용으로 나눈다.

같은 1과목 범위의 코드(Code) 설계는 자료를 분류·조합·집계하기 쉽게 기호를 붙이는 방법이다. 코드의 주요 기능은 식별, 분류, 배열이며, 종류는 다음과 같다.

| 코드 종류                             | 방법                                                  | 예                                 |
| ------------------------------------- | ----------------------------------------------------- | ---------------------------------- |
| 순차 코드 (Sequence)                  | 발생 순서대로 일련번호 부여                           | 1, 2, 3, 4                         |
| 블록 코드 (Block)                     | 공통성 있는 것끼리 블록으로 묶고 블록 안에서 일련번호 | 1001~1100 총무부, 1101~1200 영업부 |
| 10진 코드 (Decimal)                   | 0~9로 10진 분할을 반복                                | 도서 분류 000 총류, 100 철학       |
| 그룹 분류 코드 (Group Classification) | 대·중·소 분류마다 자릿수를 정해 이어 붙임             | 1-01-001 (본사-총무부-1번)         |
| 연상 코드 (Mnemonic)                  | 명칭이나 약호를 써서 코드만 보고 대상을 떠올림        | TV-40 (40인치 TV)                  |
| 표의 숫자 코드 (Significant Digit)    | 길이·무게 같은 물리적 수치를 그대로 코드에 넣음       | 120-720-1500 (두께-폭-길이)        |
| 합성 코드 (Combined)                  | 두 가지 이상의 코드를 조합                            | 연상 + 순차: KE-711                |

## 디자인 패턴

디자인 패턴(Design Pattern)은 객체지향 설계에서 반복해서 나타나는 문제와 그 해법에 이름을 붙여 정리한 목록이다. 1994년 Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides 네 사람이 쓴 『Design Patterns: Elements of Reusable Object-Oriented Software』가 23가지 패턴을 정리했고, 네 저자를 GoF(Gang of Four)라고 부른다.

![GoF 디자인 패턴 23가지](./images/eip-software-design-gof.svg '생성 5개, 구조 7개, 행위 11개')

### 생성 패턴

생성 패턴은 객체를 만드는 과정을 캡슐화해, 어떤 클래스의 객체를 언제 어떻게 만들지 유연하게 정한다.

| 패턴               | 하는 일                                                                             |
| ------------------ | ----------------------------------------------------------------------------------- |
| 추상 팩토리        | 서로 관련된 객체들의 묶음(예: Windows용 버튼·체크박스)을 구체 클래스 지정 없이 생성 |
| 빌더 (Builder)     | 복잡한 객체를 단계별로 조립하고, 같은 조립 과정으로 다른 표현을 만든다              |
| 팩토리 메서드      | 객체 생성을 하위 클래스에 맡긴다. 상위 클래스는 인터페이스만 정의                   |
| 프로토타입         | 기존 객체를 복제(clone)해 새 객체를 만든다                                          |
| 싱글톤 (Singleton) | 클래스의 인스턴스를 ==하나만== 만들고 어디서든 그 인스턴스에 접근하게 한다          |

싱글톤은 생성자를 `private`으로 막고 정적 메서드로 하나뿐인 인스턴스를 돌려준다.

```java
class Config {
	private static final Config INSTANCE = new Config();
	private int loadCount = 0;
	private Config() { loadCount++; }
	static Config getInstance() { return INSTANCE; }
	int loadCount() { return loadCount; }
}

// main 안에서
Config a = Config.getInstance();
Config b = Config.getInstance();
System.out.println(a == b);
System.out.println(a.loadCount());
```

openjdk 25로 실행한 결과는 다음과 같다. `getInstance()`를 두 번 불러도 같은 객체(`a == b`가 `true`)이고, 생성자는 한 번만 실행되었다.

```text
true
1
```

### 구조 패턴

구조 패턴은 클래스나 객체를 조합해 더 큰 구조를 만든다.

| 패턴                     | 하는 일                                                                          |
| ------------------------ | -------------------------------------------------------------------------------- |
| 어댑터 (Adapter)         | 호환되지 않는 인터페이스를 변환해 함께 동작하게 한다 (220V 기기를 110V 콘센트에) |
| 브리지 (Bridge)          | 기능 계층과 구현 계층을 분리해 각각 독립적으로 확장한다                          |
| 컴포지트 (Composite)     | 개별 객체와 객체 묶음을 트리 구조로 만들어 같은 방법으로 다룬다 (파일과 폴더)    |
| 데코레이터 (Decorator)   | 객체에 기능을 동적으로 덧붙인다 (Java의 `BufferedReader(new FileReader(...))`)   |
| 퍼사드 (Facade)          | 복잡한 하위 시스템 앞에 단순한 통합 인터페이스를 제공한다                        |
| 플라이웨이트 (Flyweight) | 공유 가능한 부분을 한 번만 만들어 공유해 메모리를 아낀다                         |
| 프록시 (Proxy)           | 실제 객체 대신 대리 객체가 접근을 제어한다 (지연 로딩, 접근 권한 검사)           |

### 행위 패턴

행위 패턴은 객체들이 어떻게 책임을 나누고 서로 통신하는지 정한다.

| 패턴              | 하는 일                                                                   |
| ----------------- | ------------------------------------------------------------------------- |
| 책임 연쇄         | 요청을 처리할 수 있는 객체가 나올 때까지 객체 사슬을 따라 요청을 넘긴다   |
| 커맨드 (Command)  | 요청을 객체로 캡슐화해 실행 취소, 대기열, 로그 기록이 가능하게 한다       |
| 인터프리터        | 언어의 문법을 클래스로 표현하고 문장을 해석한다                           |
| 반복자 (Iterator) | 내부 구조를 노출하지 않고 컬렉션의 요소에 차례로 접근한다                 |
| 중재자 (Mediator) | 객체들이 직접 통신하지 않고 중재자를 거쳐 통신한다 (항공 관제탑)          |
| 메멘토 (Memento)  | 객체의 상태를 저장해 두었다가 이전 상태로 복원한다 (Ctrl+Z)               |
| 옵서버 (Observer) | 한 객체의 상태가 바뀌면 그 객체를 구독한 객체들에 자동으로 통지한다       |
| 상태 (State)      | 객체의 상태에 따라 동작을 바꾸고, 상태마다 별도 클래스로 구현한다         |
| 전략 (Strategy)   | 같은 문제를 푸는 알고리즘들을 캡슐화해 실행 중에 바꿔 끼운다              |
| 템플릿 메서드     | 상위 클래스가 알고리즘의 뼈대를 정하고 일부 단계를 하위 클래스가 구현한다 |
| 방문자 (Visitor)  | 자료 구조와 처리 기능을 분리해, 구조를 바꾸지 않고 새 처리를 추가한다     |

옵서버 패턴은 뉴스 채널을 구독한 객체들에게 새 소식을 한꺼번에 알리는 식으로 구현한다.

```java
interface Subscriber { void update(String news); }

class NewsChannel {
	private final List<Subscriber> subscribers = new ArrayList<>();
	void subscribe(Subscriber s) { subscribers.add(s); }
	void publish(String news) {
		for (Subscriber s : subscribers) s.update(news);
	}
}

// main 안에서
NewsChannel channel = new NewsChannel();
channel.subscribe(news -> System.out.println("메일: " + news));
channel.subscribe(news -> System.out.println("앱 알림: " + news));
channel.publish("필기 접수 시작");
```

```text
메일: 필기 접수 시작
앱 알림: 필기 접수 시작
```

`NewsChannel`은 구독자가 메일인지 앱 알림인지 모르고 `update()`만 호출한다. 문자 알림을 추가해도 `NewsChannel` 코드는 바뀌지 않으므로 앞에서 본 개방-폐쇄 원칙도 함께 지킨다.

> [!TIP] 시험에서는 이렇게 묻는다
> 패턴 이름을 주고 생성·구조·행위 중 어디에 속하는지 묻거나(예: "구조 패턴이 아닌 것은?"), 설명을 주고 이름을 쓰게 한다. 실기에서는 "한 객체의 상태가 바뀌면 의존하는 객체들에 알리는 패턴"(Observer)처럼 영문 이름을 직접 쓰게 하는 문제가 자주 나온다.

<summary>헷갈리기 쉬운 패턴 짝</summary>

| 짝                          | 구분하는 기준                                                                                               |
| --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 어댑터와 퍼사드             | 어댑터는 인터페이스 하나를 다른 인터페이스로 ==변환==, 퍼사드는 여러 하위 시스템을 하나의 창구로 ==단순화== |
| 데코레이터와 프록시         | 데코레이터는 기능을 ==추가==, 프록시는 접근을 ==제어==                                                      |
| 전략과 상태                 | 전략은 클라이언트가 알고리즘을 골라 끼우고, 상태는 객체가 자기 상태에 따라 스스로 바뀜                      |
| 팩토리 메서드와 추상 팩토리 | 팩토리 메서드는 객체 ==하나==의 생성을 하위 클래스에, 추상 팩토리는 관련 객체 ==묶음==을 생성               |
| 템플릿 메서드와 전략        | 템플릿 메서드는 상속으로 일부 단계를 바꾸고, 전략은 위임(구성)으로 알고리즘 전체를 바꿈                     |

</details>

## 인터페이스 설계

인터페이스 설계는 우리 시스템과 외부 시스템(다른 회사의 결제 시스템, 기관의 행정 시스템, 사내의 다른 업무 시스템)이 데이터를 주고받는 방법을 정하는 일이다.

### 인터페이스 요구사항 확인과 검증

인터페이스 요구사항 명세서에는 송신·수신 시스템, 주고받는 데이터 항목과 형식, 전송 주기, 오류 처리 방법, 보안 요구가 들어간다. 이 명세서가 맞는지 검증하는 방법은 앞의 요구사항 확인과 같다.

| 검증 방법      | 내용                                                          |
| -------------- | ------------------------------------------------------------- |
| 요구사항 검토  | 동료 검토, 워크스루, 인스펙션으로 명세서의 결함을 찾는다      |
| 프로토타이핑   | 견본을 만들어 요구사항을 확인한다                             |
| 테스트 설계    | 요구사항을 기반으로 테스트 케이스를 만들어 검증 가능성을 확인 |
| CASE 도구 활용 | 일관성 분석으로 요구사항 변경의 영향을 추적한다               |

### 인터페이스 대상 식별과 상세 설계

인터페이스 대상을 식별할 때는 데이터를 보내는 송신 시스템, 받는 수신 시스템, 둘 사이에서 데이터를 변환·전달하는 연계 서버를 정한다. 상세 설계에서는 송신 시스템이 보낼 데이터를 뽑아 연계 테이블이나 파일로 만들고, 연계 서버가 형식을 변환해 수신 시스템에 전송하며, 수신 시스템이 받은 데이터를 자기 데이터베이스에 반영하는 흐름과 각 단계의 오류 처리를 정한다.

### 미들웨어

미들웨어(Middleware)는 운영체제와 응용 프로그램 사이, 또는 서로 다른 시스템 사이에서 통신과 데이터 교환을 중개하는 소프트웨어다. 응용 프로그램은 상대 시스템의 운영체제나 네트워크 방식을 몰라도 미들웨어가 제공하는 기능만 호출하면 된다.

| 종류                              | 하는 일                                                                               |
| --------------------------------- | ------------------------------------------------------------------------------------- |
| DB 미들웨어                       | 응용 프로그램과 서로 다른 DBMS를 연결한다 (ODBC, IDAPI)                               |
| RPC (Remote Procedure Call)       | 원격 프로시저를 로컬 함수처럼 호출한다                                                |
| MOM (Message Oriented Middleware) | 메시지 큐로 ==비동기== 메시지를 전달한다. 즉시 응답이 필요 없는 작업에 맞다           |
| TP-Monitor (트랜잭션 처리 모니터) | 항공기 예약·은행 업무처럼 사용자가 많고 빠른 응답이 필요한 온라인 트랜잭션을 관리한다 |
| ORB (Object Request Broker)       | 분산 객체 사이의 요청을 중개한다. CORBA 표준을 구현                                   |
| WAS (Web Application Server)      | 동적인 웹 콘텐츠를 처리한다 (Tomcat, WebLogic, JEUS)                                  |

### EAI와 ESB

EAI(Enterprise Application Integration)는 기업 안의 서로 다른 애플리케이션(인사, 회계, 영업 시스템)을 연결해 데이터와 프로세스를 통합하는 솔루션이다. 연결 방식에 따라 네 가지 유형으로 나눈다.

![EAI의 네 가지 구축 유형](./images/eip-software-design-eai.svg '포인트 투 포인트, 허브 앤 스포크, 메시지 버스, 하이브리드')

| 유형                              | 구조                                                        | 장단점                                                                                 |
| --------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 포인트 투 포인트 (Point-to-Point) | 애플리케이션끼리 1:1로 직접 연결                            | 구축이 간단하지만, n개 시스템이면 연결이 최대 n(n-1)/2개로 늘어 변경과 재사용이 어렵다 |
| 허브 앤 스포크 (Hub & Spoke)      | 중앙 허브를 거쳐 연결하는 중앙 집중형                       | 확장과 유지보수가 쉽지만 허브에 장애가 나면 전체가 멈춘다                              |
| 메시지 버스 (Message Bus)         | 애플리케이션 사이에 미들웨어(버스)를 배치하고 어댑터로 연결 | 확장성이 높아 대용량 처리에 유리                                                       |
| 하이브리드 (Hybrid)               | 그룹 안은 허브 앤 스포크, 그룹 사이는 메시지 버스           | 필요한 경우에 맞게 골라 쓰지만 구성이 복잡                                             |

ESB(Enterprise Service Bus)는 애플리케이션 사이를 표준 기반의 버스로 연결하는 방식으로, EAI와 비슷하지만 애플리케이션보다 ==서비스== 중심으로 통합하고 웹 서비스(SOAP, REST) 같은 표준을 써서 결합도를 더 낮춘다. 서비스 지향 아키텍처(SOA)를 구현하는 기반으로 쓰인다.

> [!TIP] 시험에서는 이렇게 묻는다
> "EAI 구축 유형 중 중앙 허브에 장애가 발생하면 전체 시스템에 영향을 주는 것은?"(허브 앤 스포크), "비동기 메시지를 전달하는 미들웨어는?"(MOM), "온라인 트랜잭션을 처리·감시하는 미들웨어는?"(TP-Monitor)처럼 나온다.

## 확인 문제

<details>
<summary>1. 위험 분석을 반복하며 점진적으로 개발하는 모형과 제안자는?</summary>

나선형 모형, Barry Boehm. 네 활동은 계획 수립, 위험 분석, 개발 및 검증, 고객 평가 순서다.

</details>

<details>
<summary>2. "검색 결과는 3초 안에 표시되어야 한다"는 어떤 요구사항인가?</summary>

비기능 요구사항(성능). 시스템이 무엇을 하는지가 아니라 얼마나 빨리 하는지를 정한다.

</details>

<details>
<summary>3. 결합도를 약한 것부터 강한 것 순서로 나열하면?</summary>

자료 → 스탬프 → 제어 → 외부 → 공통 → 내용.

</details>

<details>
<summary>4. 모듈 안의 한 활동에서 나온 출력이 다음 활동의 입력으로 쓰이는 응집도는?</summary>

순차적 응집도(Sequential Cohesion). 같은 입력을 쓰지만 서로 다른 일을 하는 교환적 응집도와 구분한다.

</details>

<details>
<summary>5. 다음 중 GoF의 구조 패턴이 아닌 것은? (Adapter, Facade, Observer, Proxy)</summary>

Observer. 행위 패턴이다.

</details>

<details>
<summary>6. 유스케이스 "결제"를 실행할 때 할인 쿠폰이 있을 때만 "쿠폰 적용"이 실행된다. 두 유스케이스의 관계와 화살표 방향은?</summary>

확장(extend) 관계. 화살표는 확장 유스케이스(쿠폰 적용)에서 기본 유스케이스(결제)로 향한다.

</details>

<details>
<summary>7. 하위 클래스가 상위 클래스를 대체해도 프로그램이 정상 동작해야 한다는 원칙은?</summary>

리스코프 치환 원칙(LSP, Liskov Substitution Principle).

</details>
