## 10월 20일: 토큰 세 층과 Finder 단일 트리

## Finder, 미리보기, 파일

### 미리보기 앱을 macOS에 맞추기 (19일)

18일 저녁에 만든 미리보기 앱([#255](https://github.com/hyeoniverse/MacFolio/pull/255))을 macOS 미리보기와 나란히 놓고 차이를 발견할 때마다 수정했다.

새벽 2시 26분부터 4시 19분까지 도구 막대(정보·공유·회전, 버튼 그룹), macOS 26처럼 떠 있는 사이드바와 유리 버튼 그룹, 파일 없이 실행하면 iCloud의 미리보기 폴더에서 시작하는 열기 창, 열기 창의 전체 파일 트리 탐색을 차례로 맞췄다. 휴대폰은 iOS 훑어보기처럼 pdf.js로 렌더링하고, 사진 앱의 앨범을 Finder의 사진 폴더로 옮겨 그림 파일도 미리보기 앱에서 연다.

![macOS 미리보기](./images/project-slides-macos-preview-reference.jpg '참고한 macOS 화면. 왼쪽 썸네일 사이드바를 참고했다')

### 바탕화면 아이콘과 파일 시스템 (19일)

5시 1분에 바탕화면에 폴더 아이콘을 추가했다([#259](https://github.com/hyeoniverse/MacFolio/pull/259), [칸 단위 좌표와 포인터 캡처로 구현한 바탕화면 아이콘 선택과 끌기](/memo/desktop-icons)). 오른쪽 위에서 아래로 배치하고, 클릭·사각형 영역 선택, 격자에 맞춘 이동과 위치 저장, 더블클릭으로 열기, 오른쪽 클릭 메뉴를 macOS와 같게 구현했다.

![바탕화면 아이콘 고르기](./images/day-1019-desktop-icons.jpg '바탕화면을 드래그해 사각형으로 선택하는 중. 사각형 안의 폴더 세 개가 선택됐다')

5시부터 9시까지는 Finder가 실제 파일 시스템처럼 동작하도록 구현했다([#263](https://github.com/hyeoniverse/MacFolio/pull/263), [표시 위치 JSON과 가상본 종류로 구성한 Finder 단일 루트 파일 시스템](/memo/finder-filesystem)).

- **폴더 구조를 서버에 저장:** 관리자가 만들고 옮긴 구조를 `/finder/layout` API에 저장해 방문자도 같은 구조를 본다. 블로그 폴더는 메모 앱의 분류와 연결된다
- **어디에 놓아도 업로드:** 폴더, 바탕화면, 파일 아이콘 위 어디에 놓아도 업로드되고, 허용 형식에 문서·영상·ZIP을 추가했다. 방문자가 놓은 파일은 서버에 올리지 않고 그 방문자 화면에만 표시하며, 그 PDF를 pdf.js가 읽도록 CSP `connect-src`에 `blob:`을 추가했다
- **휴지통:** 복원과 영구 삭제. 바탕화면 파일은 Dock의 휴지통으로 드래그해도 삭제된다

확인 중에는 허용 형식이 적어 `chill.gif`가 거부되고, 새 형식 마이그레이션을 저장소 루트가 아닌 서버의 `~/deploy`에서 실행해 `No such file or directory`로 실패했다. 휴지통 확인 창의 z-index, 휴지통 목록, 바탕화면 파일이 `portfolio/` 키로 저장되던 경로도 수정했다.

같은 시간대에 HYEONIVERSE 구조도의 아이콘이 사각형으로 깨진 문제도 수정했다. Font Awesome 7로 올린 뒤에도 SVG 텍스트로 렌더링하는 아이콘의 CSS에 6 버전의 글꼴 이름이 남아 있었다([#262](https://github.com/hyeoniverse/MacFolio/pull/262), [Font Awesome 7에서 제거된 6의 글꼴 이름과 SVG 텍스트 아이콘](/memo/font-awesome-7-icons)).

### 발표 자료: 필드 대신 프로젝트 폴더 (19일)

4시 45분에 미리보기 앱에 보기 › 슬라이드쇼(⇧⌘F)를 추가하고, 프로젝트 정보에 `slides` 필드를 두어 발표 자료 PDF를 고르게 했다. 그런데 프로젝트마다 Finder 폴더를 만드는 작업([#261](https://github.com/hyeoniverse/MacFolio/pull/261))이 동시에 진행 중이었고, 실제 OS처럼 폴더에 두는 방식이 더 자연스러웠다. 41분 뒤 `slides` 필드를 삭제하고 프로젝트 폴더의 이름순 첫 PDF를 발표 자료로 쓴다. 같은 정보를 두 곳에 기록하지 않기 위한 결정이다([#258](https://github.com/hyeoniverse/MacFolio/pull/258), [pdf.js와 Fullscreen API로 구현한 PDF 슬라이드쇼](/memo/project-slides)).

### 동영상 배경화면, QuickTime, R2 키 오류 (19일)

7시 55분에 MP4와 GIF 배경화면을 추가했다. 음소거로 반복 재생하고, 동작 줄이기 설정이나 백그라운드 탭에서는 정지한다([#264](https://github.com/hyeoniverse/MacFolio/pull/264), [video 요소와 canvas로 만든 포스터로 동영상 배경화면 적용하기](/memo/video-wallpaper)). MP4가 Finder에서 회색 문서 아이콘으로 표시되고 열면 내려받기만 실행되어, 8시 55분에 QuickTime Player 앱을 추가했다. `/files` 경로가 HTTP Range 요청에 응답해 긴 영상도 원하는 위치부터 재생한다.

![QuickTime의 열기 창](./images/day-1019-quicktime.jpg '파일 없이 실행하면 미리보기와 같은 열기 창이 표시된다')

R2 버킷은 Cloudflare에서 직접 설정했다(접근 키는 R2 API 토큰 화면에서 발급). 배포 후 운영 사이트의 업로드가 실패해 요청을 단계별로 직접 보내 확인했다([#268](https://github.com/hyeoniverse/MacFolio/pull/268)).

| 단계 | 확인한 것                         | 결과                                                             |
| ---- | --------------------------------- | ---------------------------------------------------------------- |
| 1    | 업로드 시도                       | "서버에 파일 저장소(R2)가 설정되지 않았습니다"                   |
| 2    | 서버에 R2 설정값 입력 후 재시도   | "저장소에 연결하지 못했습니다. 버킷의 CORS 설정을 확인해 주세요" |
| 3    | CORS 사전 요청(OPTIONS) 직접 전송 | `204`와 `Access-Control-Allow-Origin` 정상 응답                  |
| 4    | 서버 시각 확인                    | 정상 (서명 만료 문제 아님)                                       |
| 5    | 서명한 PUT 요청 직접 전송         | `SignatureDoesNotMatch`                                          |

==오류 문구는 CORS를 가리켰지만 원인은 서버에 입력한 R2 키 값==이었다. 같은 PR에서 '데스크탑 사진 설정'으로 고른 배경화면이 새로고침하면 기본값으로 돌아가던 문제, MP4를 배경화면으로 설정할 수 없던 문제, 관리자 휴지통에 서버 파일이 표시되지 않던 문제도 수정했다([배경화면이 새로고침하면 사라지던 문제](/memo/finder-wallpaper-persist)).

## Markdown 이력서와 텍스트 편집기 (21일)

터미널의 `resume` 명령이 Finder를 여는 대신 웃는 Mac 아스키 아트와 이력서를 출력하도록 바꾼 데서 시작해, 이력서의 데이터 구조를 변경했다([#309](https://github.com/hyeoniverse/MacFolio/pull/309)).

| 항목        | 변경 전                          | 변경 후                                              |
| ----------- | -------------------------------- | ---------------------------------------------------- |
| 원본        | 시스템 설정의 프로필·프로젝트 값 | **Markdown 문서 하나** (API `/site/resume`에 저장)   |
| 렌더링      | 화면마다 값을 조합해 각각 렌더링 | Finder 문서, PDF, 터미널 `resume`이 같은 문서를 읽음 |
| 설정값 반영 | 자동                             | "불러오기"로 문서에 삽입, 삽입 후에는 문서의 일부    |

원본이 하나라 화면마다 내용이 달라지지 않는다. 영문 이력서(`/site/resume/en`)도 추가했고, 이력서 폴더의 `.pdf`는 요청 시점의 Markdown으로 생성한다.

이 문서를 여는 macOS 텍스트 편집기를 만들었다. 처음에는 서식 막대와 미리보기를 분리했다가, 메모 앱처럼 서식이 적용된 상태에서 편집하는 WYSIWYG 편집기(Milkdown)로 바꿨다. 실행 취소·다시 실행, ⌘S 저장, Markdown 원문 보기도 있다.

![텍스트 편집기에서 이력서를 고치는 화면](./images/day-1021-textedit.jpg '서식이 적용된 상태로 편집한다. 오른쪽 위가 불러오기·변경 취소·저장')

- **확장자가 PDF에만 표시됐다.** 이름마다 붙이는 대신 문서 종류에 따라 확장자를 붙이는 함수(`withExtension`) 하나로 모든 문서 이름을 생성했다
- **불러오기가 이전 내용을 읽었다.** Milkdown은 변경 내용을 비동기로 늦게 전달해, 방금 입력한 글자가 상태에 반영되기 전에 불러오기·저장을 누르면 이전 내용으로 덮어썼다. 버튼을 누를 때 편집기에서 현재 내용을 직접 읽는다

## 위젯

### 위젯 8종 (21일)

바탕화면과 휴대폰 홈 화면에 위젯 8종을 추가했다([#311](https://github.com/hyeoniverse/MacFolio/pull/311), [180px 칸 격자 좌표로 바탕화면 위젯 배치하기](/memo/desktop-widgets)). 바탕화면은 180px 격자에 아이콘을 피해 배치하고 위젯 갤러리에서 고르면 빈 칸으로 이동하는 애니메이션이 있으며, 휴대폰은 홈 화면을 길게 눌러 편집한다. 배경은 불투명한 패널 → 유리 질감 → "보는 위젯은 유리, 읽는 위젯(캘린더·메모)은 불투명한 패널"로 두 번 바꿨다. 글자가 많은 위젯은 배경이 비치면 가독성이 떨어지기 때문이다.

### 사진·메모·명언 위젯 (22일)

음악 위젯의 배경은 앨범 표지에 `filter: blur`를 적용한 `::before` 레이어다. 아이폰 Safari는 이 레이어를 별도로 합성해 부모의 `overflow: hidden` + `border-radius`로 잘리지 않았다. 같은 모양을 `clip-path: inset(0 round …)`로 한 번 더 지정했다. 맥 Safari와 Playwright WebKit에서는 재현되지 않았다([iOS Safari의 filter 합성 레이어에서 빠지는 border-radius 클리핑과 clip-path](/memo/music-widget-ios-corners)).

### 인용 색과 prose.css (23일)

Markdown 인용(`> …`)이 흐렸는데, 규칙이 블로그(`.memo-markdown`)와 문서 보기·텍스트 편집기(`.finder-doc`)에 따로 있었다. 두 PR이 같은 규칙을 나눠 고치면 머지 순서에 따라 결과가 달라질 수 있어 하나로 합쳤다([#361](https://github.com/hyeoniverse/MacFolio/pull/361)).

공통 규칙을 `styles/prose.css`로 옮기자 텍스트 편집기 창의 코드 블록에 문법 강조 색이 없는 문제가 드러났다([#364](https://github.com/hyeoniverse/MacFolio/pull/364)). 강조 색 변수(`--hl-*`)를 `[data-app='memo']`·`[data-app='finder']`에만 정의해 `data-app='textedit'` 창에서는 `var()`가 무효였다. 코드 색은 `:root`의 `--color-code-*`를 직접 참조하고, 공통 선택자는 `:where(.prose) …`로 시작해 명시도가 0이며, 화면마다 다른 값은 `--prose-*` 변수로 분리했다([Markdown 본문 CSS를 prose.css와 --prose-* 변수로 합치기](/memo/markdown-prose-css)).

## 첫 방문 성능

### 1~3차 개선 (22일)

Lighthouse로 측정한 첫 방문 성능은 휴대폰 55점(LCP 25.7초), 데스크톱 62점(LCP 5.8초)이었고 첫 방문마다 4.9MB·9MB를 내려받았다. LCP(Largest Contentful Paint)는 화면에서 가장 큰 요소가 그려진 시각이다.

| 항목 (로컬, 5회 중앙값) | 휴대폰 개선 전 → 1차 → 2차 → 3차      | 데스크톱 개선 전 → 1차 → 2차 → 3차      |
| ----------------------- | ------------------------------------- | --------------------------------------- |
| Lighthouse 성능         | 55 → 68 → 69~72 → **78~87**           | 62 → 90 → 93 → **98**                   |
| FCP                     | 14.3초 → 4.0초 → 4.0초 → **3.2초**    | 2.5초 → 0.8초 → 0.8초 → **0.7초**       |
| LCP                     | 25.7초 → 6.2초 → 5.8초 → **3.2초**    | 5.8초 → 1.9초 → 1.7초 → **1.1초**       |
| 첫 방문 전송량          | 4,893KB → 1,011KB → 725KB → **483KB** | 9,050KB → 2,177KB → 1,848KB → **771KB** |

![느린 휴대폰에서 0.5초 간격으로 캡처한 첫 화면](./images/site-performance-diet-filmstrip.jpg '개선 전에는 7초 동안 검은 화면이었고, 개선 후에는 1초에 사과 로고, 2초에 시작 안내가 보인다')

1차([#319](https://github.com/hyeoniverse/MacFolio/pull/319))는 큰 것부터 줄였다.

| 원인                                               | 조치                                                                       | 감소량                                     |
| -------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------ |
| 본문 글꼴 TTF 한 벌 (압축 1.7MB)                   | 완성형 2,350자 `core`와 나머지 한글 `ext`의 woff2 두 조각, `unicode-range` | 1.7MB → 149KB                              |
| 블로그 글 199편의 원문이 첫 번들에 포함            | 글 목록을 처음 조회하는 시점에 `import()`                                  | 740KB                                      |
| 메모·Finder 등 일부 앱 외 모든 앱이 첫 번들에 포함 | 모든 앱을 `lazy`로                                                         | 첫 번들 250KB → 47KB (brotli)              |
| 2560px 아이콘, JPG 배경화면                        | 아이콘 256px, 배경화면 WebP                                                | 아이콘 1,171 → 428KB, 배경화면 7.9 → 2.3MB |
| 로딩 화면을 JS가 렌더링                            | `index.html`의 `#boot-splash`가 먼저 표시, 사과 로고는 SVG                 | 휴대폰 FCP 14.3 → 4.0초                    |

앱을 `lazy`로 바꾸자, 홈 인디케이터와 앱 전환기의 스타일이 앱 창이 불러오는 `Window.css`에 있어 셸이 그 스타일을 잃었다. 셸(`Desktop.tsx`)이 직접 불러오게 했다.

2·3차([#323](https://github.com/hyeoniverse/MacFolio/pull/323))에서는 앱 아이콘을 192px WebP로(428KB → 51KB), 앨범 그림을 512px WebP로(742KB → 146KB) 바꾸고, 메뉴 막대의 사과 로고를 SVG 컴포넌트로 바꿔 Font Awesome brands(113KB)를 첫 화면에서 뺐다. 로딩 화면을 누르기 전에는 바탕화면을 렌더링하지 않아 휴대폰 LCP가 5.8초에서 3.2초로, 요청 수가 75개에서 49개로 줄었다. 스크립트를 받는 동안 먼저 누른 입력은 `window.__macfolioTapped`에 기록해 손실되지 않게 했다.

Lighthouse 기본값(simulate)은 네트워크를 계산으로 흉내 내 로컬에서 미리 받은 JS 33개까지 필요했다고 계산해, 실제로 느리게 하는 `THROTTLING=devtools` 값도 함께 기록했다. 운영 사이트는 1차 배포 전후 휴대폰 53 → 73점, LCP 31.5 → 7.1초였다. 과정은 [휴대폰 LCP를 25.7초에서 3.2초로 줄인 Lighthouse 성능 측정 리포트](/memo/site-performance-diet#병목-분석)와 [Lighthouse 병목 분석과 글꼴 subset·lazy import·modulepreload·WebP로 첫 방문 전송량 9MB를 0.8MB로](/memo/site-performance-diet)에 정리했다.

글 원문을 늦게 받게 되면서, 목록이 채워지기 전에 폴더를 만드는 메모 관리자 E2E가 6번 중 4번 실패해 목록이 채워진 뒤에 편집하도록 고쳤다.

### 재측정, 회귀, CI 예산 (23일)

3차 배포 후 운영 사이트는 휴대폰 98점(LCP 1.9초), 데스크톱 97점(LCP 1.0초)이었다. 같은 측정에서 22일 밤의 명언 위젯이 데이터 66KB를 첫 번들에 넣어 `boot` 번들이 47KB에서 65KB로 늘어난 회귀를 찾아 `lazy`로 분리했다([#338](https://github.com/hyeoniverse/MacFolio/pull/338), [성능 재측정](/memo/site-performance-lcp-budget#운영-사이트-재측정)).

### CSS를 두 번 받던 preload (24일)

배포 사이트를 Safari로 열면 "preloaded using link preload but not used" 경고가 CSS 5개에 표시됐다. #367에서 추가한 `bootPreloadPlugin`이 CSS `preload`에 `crossorigin`을 붙이지 않아 요청 모드가 no-cors였고, Vite preload helper가 붙이는 stylesheet는 cors였다. 모드가 달라 preload 응답이 쓰이지 않고 같은 CSS를 다시 요청했다([#375](https://github.com/hyeoniverse/MacFolio/pull/375)).

| -------------------------- | ----------: | ----------: | --------: | --------: |

### 최소화 후 휴대폰 모양, 조회수, 같은 날 글 순서 (22일)

메모는 `ResizeObserver`로 칸의 폭을 측정해 700px 이하면 한 칸씩 표시한다. 창을 최소화하면 창 틀(`AppWindow`)만 `null`을 렌더링하고 폭을 측정하는 `Memo` 컴포넌트는 남는다([#324](https://github.com/hyeoniverse/MacFolio/pull/324)).

![최소화 후 다시 연 메모](./images/day-1022-memo-compact.jpg '창 폭이 898px인데도 폴더 → 목록 → 본문을 한 칸씩 표시하는 휴대폰 모양으로 열렸다')

```text
열기       칸 A 생성 → useEffect([ref])가 A를 관찰 → 898px
최소화     칸 A만 제거 → 관찰 중인 A의 폭 0 → compact
다시 열기  칸 B 생성 → ref 객체가 같아 effect가 다시 실행되지 않음
           → B를 관찰하지 않음 → 폭 0 유지 → 넓은 창에 휴대폰 모양
```

> [!WARNING] ref 객체를 의존성으로 둔 effect
> `useEffect(..., [ref])`는 ref **객체**가 바뀔 때만 다시 실행된다. 요소를 붙이는 함수(`attach`)로 받아 요소가 바뀔 때마다 state가 바뀌는 `useElementWidth` 훅을 만들고, 같은 형태였던 날씨·사진 앱도 함께 수정했다. 메모 목록의 조회수는 인기글 보기에서만 보이던 것을 모든 줄의 폴더 옆에 `조회 1,234` 형식으로 표시한다([#321](https://github.com/hyeoniverse/MacFolio/pull/321)).

같은 날짜의 글은 정렬 함수가 날짜 다음에 바로 제목을 비교해 제목 순으로 놓였다. 그 사이에 올린 시각을 비교 기준으로 넣었다. 저장소 글은 빌드 시점에 git에서 처음 추가된 커밋 시각을, 서버 글은 처음 게시한 시각(`firstPublishedAt`)을 쓴다([#331](https://github.com/hyeoniverse/MacFolio/pull/331)).

![같은 날 글 순서 전후](./images/day-1022-same-day-order.jpg '왼쪽은 제목 순, 오른쪽은 올린 시각 순. 가장 나중에 올린 글이 맨 위에 온다')

### 편집기 저장 문제, 링크·이미지, 비밀 글 (23일)

로컬에서 고친 저장소 글이 화면에 반영되지 않은 원인은 같은 주소의 글이 예전에 편집기로 게시되어 DB에 남아 있던 것이었다. ==서버 글은 같은 주소의 저장소 글을 대체한다==(`mergeServerPosts`). 확인 과정에서 편집기 문제 셋을 고쳤다([#332](https://github.com/hyeoniverse/MacFolio/pull/332)).

- **저장하면 첫 태그가 `\#MacFolio`가 된다:** remark-stringify는 줄 맨 앞의 `#`를 무조건 이스케이프한다. CommonMark 제목은 `#` 뒤에 공백이 필요해 `#MacFolio`는 제목이 될 수 없으므로, 저장 직전에 `unescapeTags`로 되돌린다
- **토글을 펼치기만 해도 '임시 저장됨':** 펼침 여부가 문서의 `open` 속성이었다. ProseMirror 플러그인 상태(화면 상태)로 옮겼다
- **서버에서 고친 저장소 글을 되돌릴 수 없다:** '저장소 글로 되돌리기' 메뉴를 추가했다

![편집기로 저장한 태그 줄 전후](./images/day-1023-editor-tags.jpg '고치기 전에는 첫 태그가 #MacFolio로 저장되어 태그로 인식되지 않았다')

편집기에서는 링크에 마우스를 올리면 '글로 이동'·'새 탭에서 열기' 상자를, 이미지는 돋보기 버튼과 더블클릭으로 라이트박스를 연다. 두 기능 모두 React 트리 밖의 노드 뷰와 React 컴포넌트를 `createStore` 저장소 하나로 연결했다([#339](https://github.com/hyeoniverse/MacFolio/pull/339), [#340](https://github.com/hyeoniverse/MacFolio/pull/340)).

비밀 글은 서버 글을 관리자에게만 보이게 지정한다([#355](https://github.com/hyeoniverse/MacFolio/pull/355), [메모 비밀 글](/memo/memo-secret-posts)). 글 주소를 받는 공개 경로(목록, 공유 카드, 댓글, 좋아요, 인기글, 조회수, 트래픽 요약, Worker 첫 화면 본문, sitemap, RSS 등)를 `git grep`으로 모두 찾아 서버에서 필터링했다. 비밀 글 주소로 직접 요청하면 없는 글과 같은 응답을 보낸다. 저장소 글은 공개 저장소에 원문이 있어 지정할 수 없다.

## 화면이 보이는 동안만 다시 조회하기 (23일)

활동 상태 보기와 메모 조회수는 앱을 연 시각의 값에서 바뀌지 않았고, 실시간 탭은 `setInterval`로 10초마다 조회했는데, 창을 닫아도 앱 컴포넌트가 언마운트되지 않아 ==1시간에 360번 요청이 계속 나갔다.==

1단계 [#353](https://github.com/hyeoniverse/MacFolio/pull/353)은 `poller.ts`(응답 뒤 간격 재예약, 중복 방지, 실패 시 간격 2배·최대 10분)와 `usePolling`(탭이 보이고 창이 열려 있을 때만)을 만들어 활동 상태 보기와 메모 조회수에 1분 간격으로 적용했다. 2단계 [#357](https://github.com/hyeoniverse/MacFolio/pull/357)은 메시지, 메모 댓글, 메일, 위젯으로 넓히고, 숨은 탭에서도 돌던 `setInterval` 세 곳(메뉴 막대 두 곳, 날씨)을 옮겼다. 같은 값을 보는 화면들은 일정 하나를 공유하고, 탭만 다시 보일 때는 간격이 지난 경우에만 바로 조회한다.

![여러 화면이 일정 하나를 공유하는 구조](./images/live-refresh-more-shared.svg '위젯 여러 개와 앱 창이 같은 값을 보면 공유 일정 하나를 빌려 쓰고, 보는 곳이 0이면 멈춘다')

SSE·WebSocket과 비교한 이유와 확대 과정은 [visibilityState와 지수 백오프로 보이는 동안만 폴링하는 usePolling 훅과 같은 요청 묶기](/memo/activity-live-refresh)에 적었다.

### 검색 로봇용 본문과 공유 카드 (19일·21일)

이 사이트는 화면 전체를 JavaScript로 렌더링한다(CSR). 검색 로봇이 받는 HTML은 어느 주소든 제목이 같고 본문이 비어 있었다. 19일 [#269](https://github.com/hyeoniverse/MacFolio/pull/269)로 Worker가 응답 HTML에 주소마다 다른 `<title>`·설명, og 태그·JSON-LD, 화면에 보이지 않는 로봇용 본문을 삽입하고, 앱이 실행되면 React가 그 영역을 대체하게 했다. `sitemap.xml`은 빌드 시 생성한 글 목록에 API 글(Worker가 1분 캐시)을 합친다.

21일에는 RSS 피드, 글마다 공유 이미지와 수정일, 없는 글 주소의 404를 추가했다([#303](https://github.com/hyeoniverse/MacFolio/pull/303)). 사진이 없는 글의 공유 카드는 빌드 시 제목으로 생성하는데, 그러면 서버에서 작성한 글은 카드가 없다. 카드 생성 코드를 `packages/og-card`로 옮겨 빌드와 API가 같은 코드로 생성한다([#306](https://github.com/hyeoniverse/MacFolio/pull/306)).

### 검색어 탭과 Safari의 CORP (22일)

유입 경로에는 `www.google.com`만 남았다. Google·Bing은 브라우저가 호스트만 전달하기 때문이다. 두 경로를 함께 쓴다([#327](https://github.com/hyeoniverse/MacFolio/pull/327), [리퍼러 검색어와 Search Console API로 유입 검색어 수집하기](/memo/search-keywords)).

1. **방문의 검색어:** 검색엔진이 주소에 검색어를 넣을 때만(네이버 `query`, 다음 `q` 등) 그 값 하나를 방문 이벤트의 `searchTerm`으로 보낸다
2. **Google Search Console:** 서버가 6시간마다 서비스 계정으로 날짜·검색어·페이지별 노출·클릭·평균 순위를 가져온다. `googleapis` 패키지 없이 JWT(RS256)를 `node:crypto`로 서명한다

![검색어 탭](./images/search-keywords-tab.jpg 'Search Console의 검색어·페이지 표와 검색엔진이 전달한 검색어를 함께 표시한다')

Safari 콘솔에는 5초마다 같은 오류가 3줄씩 쌓였다. 분석 이벤트 전송 주기와 같았다([#320](https://github.com/hyeoniverse/MacFolio/pull/320)).

![CORP 헤더 전후 흐름](./images/day-1022-corp.svg '사이트와 API의 출처가 달라 Safari가 CORP same-origin이 붙은 sendBeacon 응답을 취소했다')

> [!NOTE] CORP는 CORS와 별개의 검사
> API는 `helmet()` 기본값이라 모든 응답에 `Cross-Origin-Resource-Policy: same-origin`이 붙는다. CORP는 CORS와 별개의 검사이고, Safari는 sendBeacon(no-cors) 응답에도 CORP를 적용해 출처가 다르면 응답을 취소한다. `POST /analytics/events` 한 경로에만 `cross-origin`을 지정했다. 응답이 본문 없는 204라 노출되는 정보가 없다.

### 실시간 7일과 관리자 IP 제외 (23일)

서버는 마스킹된 IP를 7일 동안 보관하는데 실시간 탭은 최근 30분만 보여 줬다. 기간(30분·3시간·24시간·7일)과 마스킹된 IP별 방문 집계 표를 더하고, IP를 누르면 방문 목록이 그 IP로 필터링된다([#333](https://github.com/hyeoniverse/MacFolio/pull/333)). 맥 Safari에서만 조합 표를 정렬하면 이름 칸 글자가 사라지던 문제는 "다시 만든 버튼 + 페이드" 조합을 원인으로 추정해, 이름이 버튼인 표는 정렬할 때 `tbody`를 다시 만들지 않는다.

![실시간 탭의 IP 표](./images/day-1023-live-ip.jpg '7일 기간의 IP 표와 203.0.113.x로 필터링한 방문 목록. 가짜 API 자료로 촬영했다')

로그인하지 않은 휴대폰으로 확인한 방문도 집계되어, 관리자로 인증된 요청의 IP를 `HMAC-SHA256(IP_HASH_SECRET, "admin-ip:" + IP)`로 기록하고 그 IP의 방문은 세션이 없어도 저장하지 않는다. IP 원문은 저장하지 않고, 마지막 관리자 요청 뒤 30일이 지나면 행을 삭제한다. 같은 공유기 뒤의 다른 방문자도 30일 동안 빠지는 한계는 [개인정보 문서](https://github.com/hyeoniverse/MacFolio/blob/main/docs/privacy.md)에 적었다([#337](https://github.com/hyeoniverse/MacFolio/pull/337)).

### Search Console 연결과 SSH 시간 초과 (23일)

사이트를 도메인 속성(`sc-domain:`)으로 등록하면 다른 하위 도메인 페이지까지 응답에 섞인다. URL 접두어 속성을 추가하는 대신 `searchAnalytics.query`에 `dimensionFilterGroups`(`page`, `includingRegex`)를 붙여 이 사이트 페이지만 요청하고, 이미 받은 다른 하위 도메인 행은 동기화하면서 삭제한다([#360](https://github.com/hyeoniverse/MacFolio/pull/360)).

![Search Console 연결 순서](./images/search-console-setup-flow.svg 'Search Console 속성과 사이트맵, Google Cloud 서비스 계정, 권한 추가, 서버 api.env 설정 순서')

서비스 계정 키를 옮기는 `scp`는 `Operation timed out`으로 실패했다. 보안 목록은 열려 있었고 Actions 배포는 성공했다. 20일 SSH 키 복구 때 만든 임시 VM의 공인 IP를 서버 주소로 기억한 것이 원인이었다. `known_hosts`의 기록과 Cloud Shell의 `oci compute instance list-vnics` 결과로 실제 IP를 확인하고 `~/.ssh/config`에 별칭을 등록했다([부트 볼륨을 임시 VM에 연결해 authorized_keys를 고치는 Oracle 서버 SSH 키 복구](/memo/oracle-ssh-key-recovery)).

![SSH 시간 초과 원인을 좁힌 순서](./images/ssh-timeout-public-ip-diagnosis.svg '네트워크와 방화벽을 차례로 배제한 뒤 접속 주소가 다른 VM의 IP임을 확인했다')

### 머지 후 배포 15분에서 5분으로 (19일)

측정해 보니 머지부터 사이트 반영까지 약 15분 중 8~9분이 화면 E2E였다. 17일에 세 개로 나눈 E2E를 여섯 개로 늘리고, PR에서 이미 통과한 커밋과 트리가 같은 main 커밋은 E2E를 다시 실행하지 않고 배포한다([#266](https://github.com/hyeoniverse/MacFolio/pull/266), [git 트리 비교로 PR에서 통과한 main 커밋의 E2E 재실행 생략하기](/memo/faster-e2e-ci)).

### 글 내용에 의존하던 시험과 Markdown 검사 (19일·23일·25일)

19일 [#270](https://github.com/hyeoniverse/MacFolio/pull/270)에서 글 내용이 바뀌자 메모 E2E가 실패했고, 23일에는 저장소 글과 문서를 고치는 PR 10개([#343](https://github.com/hyeoniverse/MacFolio/pull/343)~[#352](https://github.com/hyeoniverse/MacFolio/pull/352))를 거의 같은 시각에 올리자 관계없는 E2E가 연달아 실패했다.

- **휴대폰 메모 목록 버튼:** Playwright의 역할 이름은 부분 일치라, 글 요약에 '완료'·'목록'이 들어가자 버튼 대신 글 항목이 잡혔다. `exact: true`
- **표 조건 검색:** 표가 없는 저장소 글을 골라 쓰던 시험이 모든 글에 표가 생기자 대상을 잃었다. 가짜 API의 서버 글로 시험한다([#358](https://github.com/hyeoniverse/MacFolio/pull/358))
- **토글 시험:** 기준 글의 토글 위치가 바뀌어, 용어 토글이 있는 병합 방식 글로 확인한다
- **각주 배치:** 각주 정의가 관련 글 절보다 앞이거나 참조 순서와 달라, 첫 참조 순서로 글 끝(태그 줄 앞)에 모은다

같은 과정에서 Markdown 문법 오류 두 종류를 찾았다.

- **깨진 링크([#359](https://github.com/hyeoniverse/MacFolio/pull/359)):** 글 229편을 스크립트로 검사해 11편을 찾았다. 주소만 적은 관련 글 줄과, 각주 바로 뒤에 괄호를 붙인 `사전 요청[^preflight](OPTIONS)`이다. 뒤의 경우 각주가 아니라 주소가 `OPTIONS`인 링크로 해석된다. `content.test.ts`에 링크 대상 글 존재, 주소만 적힌 곳, `[^x](` 형태를 검사하는 시험을 더했다
- **물결표 취소선([#356](https://github.com/hyeoniverse/MacFolio/pull/356)):** README의 `78~87`, `2.6~3.3초`처럼 한 줄에 범위가 둘 있으면 GitHub가 그 사이를 취소선으로 렌더링했다. GFM은 `~` 하나도 취소선 구분자로 인정한다. 메모 앱은 `singleTilde: false`라 해당하지 않는다. 문서 8개의 범위를 `\~`로 이스케이프했다

25일 [#381](https://github.com/hyeoniverse/MacFolio/pull/381)에서는 다른 프로젝트의 새 `…/회고` 등 폴더 이름이 `개발기/MacFolio`의 하위 폴더와 겹쳐, 폴더를 이름만으로 찾던 E2E 12개가 strict mode로 실패했다. 폴더를 전체 경로로 찾는 `memoFolderRow`를 추가했다.

### 머지 뒤 연달아 실패한 CI (22일~24일)

22일 #329 머지 직후부터 실패한 휴대폰 시트 스크롤 시험은 앞 화면의 애니메이션이 만든 가로 스크롤까지 집계하고 있었다([#334](https://github.com/hyeoniverse/MacFolio/pull/334)). 24일 새벽 #368을 머지한 뒤에는 main과 main을 합친 PR의 CI가 서로 다른 이유로 네 번 실패했다. E2E 세 건은 macOS에서 `--repeat-each 6`으로 반복해도 재현되지 않아, CI가 남긴 Playwright trace와 실패 화면으로 원인을 확인했다([CI 아티팩트로 macOS에서 재현되지 않는 E2E 실패 원인 찾기](/memo/ci-failures-after-merges)).

1. **위젯 크기(`mobile.spec.ts`, 115px → 117px):** 휴대폰 홈 아이콘 이름의 `line-height: normal`이 글꼴마다 달라 Linux에서 웹 글꼴 적용 전후 2px 차이가 났다. `line-height: 1.25`로 고정하고 `ResizeObserver`가 첫 아이콘도 관찰한다([#369](https://github.com/hyeoniverse/MacFolio/pull/369))
2. **메모 목록 재정렬(`markdown-safety.spec.ts`, `memo.spec.ts`):** 저장소 글 청크(약 2MB)가 서버 글보다 늦게 도착해 클릭하는 사이 목록이 재정렬됐다. 저장소 글이 도착하기 전(`status === 'loading'`)에는 목록을 비운다(#369)
3. **의존성 취약점 검사:** body-parser 취약점(GHSA-27r3-jxmh-p828) 공개. `pnpm-workspace.yaml`의 `overrides`로 2.4.0([#371](https://github.com/hyeoniverse/MacFolio/pull/371))
4. **`live-refresh.spec.ts`:** 시험이 `scrollTop`을 바꾼 직후 새 답글을 받아 scroll 이벤트보다 먼저 처리했다. 스크롤 직후 scroll 이벤트를 바로 보내도록 시험을 고쳤다(#370 안의 커밋)

메모 목록 재정렬은 시험 하나에 `toPass()` 재시도를 넣었다가 되돌렸다. 메모 E2E 88곳이 같은 방식으로 `.memo-item`을 누르고, 느린 네트워크의 방문자도 다른 글이 열리는 동작이라 앱을 고쳤다.

![CI 실패 순서](./images/ci-failures-after-merges-timeline.svg '#368 머지(01:17)부터 #366·#370 머지(08:09)까지 실패와 수정 순서. multer는 이 뒤의 일이다')

body-parser를 고친 07:52 뒤에는 multer 취약점(GHSA-q7qp-rjg7-q26m, high)이 공개되어 같은 검사가 다시 실패했다. GitHub 권고 공개는 07:08이었지만 `pnpm audit` 결과에는 08:33 실행까지 반영되지 않았고 08:38 실행부터 실패했다. multer·undici·fast-uri를 [#374](https://github.com/hyeoniverse/MacFolio/pull/374)로 올려 09:09에 머지했다. multer는 `POST /files` 하나에서만 쓰고 `AdminGuard`가 먼저 실행되며 비동기 `fileFilter`도 없어 도달 가능성은 낮았다.

**겹치는 작업은 병렬로 진행하지 않는다.** 19일에는 미리보기, 바탕화면, 프로젝트 폴더, 파일 시스템이 모두 Finder의 같은 트리를 변경해 PR이 서로를 기다렸고, 오전 11시까지의 커밋 69개 중 10개가 병합 커밋이었다. 41분 만에 삭제한 발표 자료 필드도 다른 작업의 폴더와 역할이 겹친 결과다.

**오류 문구보다 요청과 기록을 직접 확인한다.** R2 업로드 오류는 CORS를 가리켰지만 원인은 서명 키였고, SSH 시간 초과는 방화벽이 아니라 접속 주소였다. macOS에서 재현되지 않는 E2E 실패는 CI trace의 측정값과 요청 순서로만 드러났고, 두 원인 모두 방문자 기기에서도 생기는 동작이라 앱을 고쳤다.

**자동 시험이 통과해도 실제 Safari를 확인한다.** CORP, 아이폰 음악 위젯 모서리, 맥 Safari의 표 정렬, CSS preload 경고가 모두 Chromium과 Playwright WebKit에서 재현되지 않았다([macOS Safari와 iOS Safari의 렌더링 차이](/memo/safari-macos-ios-rendering)).

**회귀를 찾으면 막는 검사를 함께 넣는다.** 22일 밤 명언 위젯이 첫 번들을 다시 키웠고, 23일에 찾은 뒤 같은 날 CI 예산을 걸었다. 예산이 잡지 못한 요청 중복은 24일 E2E로 보완했다. 시험도 같다. 글 내용에 기대는 시험은 가짜 API의 서버 글과 `exact: true`로 바꿨다.

**같은 규칙이 두 곳에 있으면 같은 문제를 두 번 겪는다.** 인용 색, ref 객체를 의존성으로 둔 effect(메모·날씨·사진), 정의되지 않은 CSS 변수가 그랬다. 한 곳에서 발견한 패턴은 저장소 전체에서 검색해 함께 고치고, 반복되는 실수는 린트 규칙으로 옮긴다.
