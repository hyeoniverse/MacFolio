## Finder를 실제 파일 시스템으로

19일부터 Finder에서 Cloudflare R2에 저장한 실제 파일을 다뤘다. 관리자가 파일을 올리면 API가 5분 동안 유효한 서명 URL(presigned URL)을 발급한다. 서명 URL은 저장소의 비밀 키로 "이 경로에, 이 크기의 파일을, 이 시각까지 올려도 된다"는 내용을 서명해 주소에 붙인 것이라, 브라우저는 비밀 키 없이 그 주소로만 업로드할 수 있다. 그래서 파일 본문은 API 서버를 거치지 않고 R2로 직접 전송된다.

![API가 발급하는 서명 URL의 구성](./images/finder-files-presigned-url.svg 'R2 호스트와 키 경로 뒤에 알고리즘, 자격 증명 범위, 서명 시각, 유효 시간 300초, 서명이 붙는다')

폴더 구조는 `/finder/layout`에 저장해 방문자도 같은 구조를 보고, PDF는 pdf.js로 렌더링하는 미리보기 앱에서 연다. 영상은 QuickTime 앱에서 열고, 서버는 HTTP Range 요청에 응답한다. Range 요청은 `Range: bytes=1000000-`처럼 파일의 일부 구간만 요청하는 방식이라, 영상 중간으로 이동해도 처음부터 내려받지 않는다.

20일에는 열기 창에서 바탕화면의 포트폴리오 가상본이 빈 폴더로 열리는 버그를 계기로, 12곳이 각자 구현하던 "가상본이면 원본으로 이동" 규칙을 별도 노드 종류(`kind: 'alias'`)로 분리했다. TypeScript는 `kind` 값마다 처리 분기를 모두 작성했는지 검사할 수 있으므로, ==이제 가상본 처리를 빠뜨린 코드는 타입 검사에서 오류가 난다.== 같은 날 Macintosh HD › 사용자 › hyeoniverse 아래 단일 트리로 재구성했고, 서버에 저장된 폴더 id는 그대로 유지했다.

![홈 폴더](./images/finder-home-tree-home.jpg 'Macintosh HD › 사용자 › hyeoniverse. 데스크탑·문서·블로그와 macOS 기본 폴더가 한 트리 아래에 있다')

## 디자인 토큰 세 층과 Stylelint

디자인 토큰은 색·간격 같은 값을 이름 있는 CSS 변수로 정의해 참조하는 방식이다. `theme.css` 한 파일에서 기본 글자색 하나에 이름 다섯 개, 값 네 가지가 쓰이고 있었다. 같은 색을 바꾸려면 다섯 이름을 모두 찾아야 했고, 그중 일부만 바꾸면 화면마다 색이 달라졌다.

20일 [#286](https://github.com/hyeoniverse/MacFolio/pull/286)에서 토큰을 원시값(`primitives.css`), 의미(`semantic.css`), 컴포넌트(`components.css`) 세 층으로 나누고, 참조 방향을 컴포넌트 → 의미 → 원시 한 방향으로 정했다. 예를 들어 다크 모드는 의미 층의 이름이 가리키는 원시값만 바꾸면 되고, 컴포넌트 CSS는 수정하지 않는다.

![토큰 참조 방향](./images/day-1020-token-layers.svg '컴포넌트 층은 의미 층만, 의미 층은 원시 층만 참조한다. 컴포넌트에서 원시값을 직접 쓰면 Stylelint가 차단한다')

앞뒤 PR에서 속성에 직접 쓴 이름 없는 색을 161곳에서 6곳으로 줄였고, CSS 정적 검사 도구인 Stylelint로 토큰 범위의 숫자를 직접 쓰지 못하게 했다. 21일 [#296](https://github.com/hyeoniverse/MacFolio/pull/296)에서는 차단 목록보다 허용 목록이 짧아 규칙을 반대로 바꿨다.

남은 문제는 ==정의되지 않은 CSS 변수는 오류 없이 무시된다==는 점이다. 같은 날 Finder 작업에서 방금 이름을 바꾼 `--radius-xs`를 써서 모서리가 사라졌고, 다음 날 둘러보기 카드와 텍스트 편집기에서도 없는 토큰 이름을 썼다.

![정의되지 않은 CSS 변수를 참조했을 때](./images/week-1019-undefined-var.svg '참조가 실패하면 브라우저는 그 속성의 초기값을 쓴다. border-radius의 초기값은 0이라 모서리가 각지게 그려진다')

## Markdown 이력서, 위젯, 둘러보기

21일에는 큰 기능 세 개를 추가했다. 이력서는 시스템 설정의 값을 화면마다 조합하던 방식에서 Markdown 문서 하나(`/site/resume`)로 바꿔, Finder 문서, PDF, 터미널 `resume`이 같은 원본을 읽는다. 이 문서를 여는 앱으로 Milkdown 기반의 WYSIWYG 텍스트 편집기를 만들었다. WYSIWYG는 편집하는 화면이 결과 화면과 같은 방식이다.

바탕화면과 휴대폰 홈 화면에는 180px 격자에 배치하는 위젯 8종을 추가했고, 첫 방문자에게는 화면의 한 영역씩 강조하며 실제로 누르게 하는 둘러보기와 팁 앱을 보여 준다. 세 기능 모두 처음 구현한 형태에서 여러 번 바꿨다(미리보기 분리형 편집기 → WYSIWYG, 불투명 패널 → 유리 → 혼합).

## 첫 방문 성능과 CI 성능 예산

LCP(Largest Contentful Paint)는 화면에서 가장 큰 글자 덩어리나 이미지가 그려진 시각으로, 방문자가 "페이지가 떴다"고 느끼는 시점을 나타내는 지표다. Google은 2.5초 이하를 좋음으로 본다. Lighthouse는 이 지표를 느린 기기·네트워크 조건에서 측정해 점수로 보여 주는 도구다.

22일 Lighthouse로 측정한 첫 방문은 휴대폰 55점(LCP 25.7초), 데스크톱 62점(LCP 5.8초)이었고, 첫 방문마다 휴대폰 4.9MB, 데스크톱 9MB를 내려받았다. 세 차례 개선으로 휴대폰은 LCP 3.2초·483KB, 데스크톱은 98점·771KB가 됐다.

| 개선        | 내용                                                                             |
| ----------- | -------------------------------------------------------------------------------- |
| 글꼴        | 본문 글꼴 TTF(압축 1.7MB)를 `unicode-range`로 나눈 woff2 두 조각(149KB)으로 교체 |
| 코드 분할   | 모든 앱을 `lazy`로 분리해 첫 번들을 250KB에서 47KB(brotli)로                     |
| 렌더링 시점 | 로딩 화면을 누르기 전에는 바탕화면을 렌더링하지 않음                             |

`unicode-range`는 글꼴 파일을 글자 범위별로 나눠 두고, 페이지에 실제로 나온 글자의 범위만 받게 하는 CSS 설정이다. `React.lazy`는 컴포넌트 코드를 별도 파일로 나눠, 그 컴포넌트를 처음 그리는 시각에 내려받게 한다.

![첫 방문 전송량과 첫 번들 크기의 전후 비교](./images/week-1019-transfer.svg '데스크톱 9MB → 771KB, 휴대폰 4.9MB → 483KB, 첫 번들 250KB → 47KB')

같은 날 명언 위젯이 데이터를 첫 번들에 넣어 `boot`가 65KB로 늘었고, 23일 운영 사이트 재측정에서 이 회귀를 찾았다. 같은 날 [#367](https://github.com/hyeoniverse/MacFolio/pull/367)에서 `boot` 55KB, 첫 방문 합계 265KB의 brotli 상한을 CI에 걸었다. 이제 번들이 상한을 넘는 PR은 CI에서 실패한다.

![느린 휴대폰에서 0.5초 간격으로 캡처한 첫 화면](./images/site-performance-diet-filmstrip.jpg '개선 전에는 7초 동안 검은 화면이었고, 개선 후에는 1초에 사과 로고, 2초에 시작 안내가 보인다')

## 배포 시간과 머지 뒤 CI 실패

19일에는 머지부터 배포까지 약 15분 중 8~9분이 화면 E2E였다. E2E를 여섯 작업으로 나눠 병렬로 실행하고, PR에서 통과한 커밋과 트리가 같은 main 커밋은 E2E를 생략해 5분으로 줄였다. 트리는 커밋 시점의 파일 내용 전체를 가리키는 Git 객체다. 트리가 같으면 파일 내용이 같으므로, PR에서 통과한 시험을 main에서 다시 실행할 필요가 없다.

![커밋 객체와 트리, 블롭의 관계](./images/faster-e2e-ci-commit-and-tree.png '커밋 98ca9는 트리 92ec2를 가리키고, 트리는 파일 세 개의 블롭을 가리킨다. 커밋은 트리에 부모·작성자·시각을 더해 해시하므로, 파일이 같아도 커밋 해시는 달라질 수 있다 (Pro Git)')

24일에는 [#368](https://github.com/hyeoniverse/MacFolio/pull/368)을 머지한 뒤 CI가 서로 다른 원인으로 네 번 실패했다. E2E 세 건은 macOS에서 반복해도 재현되지 않아, CI가 남긴 Playwright trace(시험 중의 화면·DOM·네트워크 기록)로 원인을 확인했다. 홈 아이콘 이름의 `line-height: normal`이 Linux에서 웹 글꼴 적용 전후 2px 달라졌고, 약 2MB의 저장소 글 청크가 늦게 도착하는 사이 메모 목록이 재정렬됐다. 두 원인 모두 방문자 기기에서도 생기는 동작이라 시험이 아니라 앱을 고쳤다. 나머지 E2E 한 건은 시험의 scroll 이벤트 순서 문제였다.

의존성 검사는 코드와 무관하게 새로 공개된 body-parser 보안 권고로 실패했고, 그 수정을 머지한 뒤 multer 권고로 다시 실패했다.

## 돌아보며

- 파일이 겹치지 않아도 같은 이름을 사용하면 겹치는 작업이다. 토큰 이름 변경과 Finder 작업이 한 줄에서 두 번 충돌했다.
- 사람이 기억해야 하는 규칙은 언젠가 누락된다. 가상본은 타입 검사로, 숫자 값은 Stylelint로 옮겼고, 정의되지 않은 CSS 변수 검사가 다음 차례로 남았다.
- 오류 문구보다 요청과 기록을 직접 확인한다. R2 업로드 오류는 CORS를 가리켰지만 원인은 서명 키였고, 재현되지 않는 E2E는 trace로만 원인이 드러났다.
- 회귀를 찾은 날 그 회귀를 막는 검사를 넣었다. 다만 전송 크기 예산은 같은 CSS를 두 번 받는 요청 중복을 잡지 못해, 24일에 요청 횟수를 확인하는 E2E를 보완했다.
- CORP, 아이폰 음악 위젯 모서리, CSS preload 경고는 모두 Chromium과 Playwright WebKit에서 재현되지 않았다. 배포 후 실제 Safari 확인을 점검 항목에 포함한다.
