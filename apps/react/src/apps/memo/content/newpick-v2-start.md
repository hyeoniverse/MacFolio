뉴픽(NewPick)은 관심 분야를 고르면 AI가 요약한 뉴스를 매일 아침 메일로 보내 주는 뉴스레터 서비스다. 2024년 12월 26일부터 2025년 2월 6일까지 프로그래머스 데브코스에서 5명(프론트엔드 2, 백엔드 3)이 6주 동안 만들었고, 나는 기획과 프론트엔드의 로그인·인증, 구독·AI 체험·목록 API 연동을 맡았다.

팀 프로젝트 시기의 이야기는 [첫 2주](/memo/newpick-v1-start), [Next.js](/memo/newpick-v1-nextjs), [로그인](/memo/newpick-v1-auth), [발표 이후](/memo/newpick-v1-retro) 네 편에 따로 정리했다.

배포 도메인(`newpick.site`)이 만료되면서 서비스는 내려갔다. 2026년 10월, 이 프로젝트를 혼자 다시 열어 고치고 저비용으로 재배포하기로 했다. 이 글은 그 시리즈의 첫 글로, 무엇부터 했는지와 어떤 순서로 고치기로 했는지를 정리한다.

## 두 레포를 기록째 하나로

팀 시절 코드는 `Devcourse-NewPick/front`와 `Devcourse-NewPick/back` 두 레포에 나뉘어 있었다. 프론트와 백엔드를 함께 고쳐야 하는 작업이 많을 것이므로(쿠키, 토큰 갱신, 응답 형태 등) 한 레포에서 PR 하나로 다루기로 했다.

| 방법                                | 장점                                 | 단점                                                 |
| ----------------------------------- | ------------------------------------ | ---------------------------------------------------- |
| 두 레포 유지                        | 그대로 쓴다                          | 프론트·백엔드를 함께 고치는 변경이 PR 두 개로 나뉜다 |
| 새 레포에 현재 코드만 복사          | 단순하다                             | 팀원 커밋 기록이 사라진다                            |
| **기록째 모노레포로 합치기** (채택) | 한 PR에서 함께 고치고, 기록도 남는다 | 커밋 메시지의 PR 번호가 원본 레포를 가리킨다         |

빈 시작 커밋을 만든 뒤, 두 레포의 기록을 각각 `apps/web`, `apps/api` 아래로 옮겨 병합했다. 팀 작업이 끝난 지점에는 `v1-team-final` 태그를 달았다. 이 태그 이후의 커밋이 개인 작업이다. README에는 원본 레포 링크와 "커밋 메시지의 PR 번호는 원본 레포의 PR"이라는 안내를 남겼다.

## 고치는 순서

처음 코드를 다시 읽으며 문제를 모았더니, 보안 구멍부터 쓰지 않는 인프라, 데이터 모델, 프론트 구조까지 범위가 넓었다. 한 번에 고치면 무엇이 무엇을 깨뜨렸는지 알 수 없으므로, 리팩토링 이슈(#4)를 단계로 나누고 단계마다 이슈와 PR을 따로 두었다. 기능 개선 제안은 별도 이슈(#13)로 분리했다.

![v2 리팩토링 단계](./images/newpick-v2-start-roadmap.svg '0~3단계는 하루에 병합했고, 4단계는 나눠서 진행 중이다')

| 단계 | 목표                                             | 글                                                                                                        |
| ---- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 0    | 깨끗하게 빌드·검사되는 기준선, CI, 측정값        | 이 글                                                                                                     |
| 1    | 재배포 전에 반드시 막아야 하는 보안 문제         | [인증 없이 열려 있던 API 다섯 개](/memo/newpick-security)                                                 |
| 2    | 쓰지 않는 인프라 제거, `docker compose up` 한 번 | [Redis와 Chromium을 걷어 내고 compose 한 번으로](/memo/newpick-infra-simplify)                            |
| 3    | 데이터 정합성, 날짜, 스케줄러, 메일              | [관심사와 북마크를 FK로](/memo/newpick-data-model), [9시간 밀린 하루](/memo/newpick-kst-scheduler)        |
| 4    | 프론트 요청 경로, 인증, 렌더링                   | [요청 경로를 하나로](/memo/newpick-api-client), [깜빡임 없는 정적 페이지](/memo/newpick-static-auth-hint) |
| 5    | 테스트                                           | 예정                                                                                                      |

순서는 "배포했을 때 피해가 큰 것부터"로 정했다. 인증 없이 누구나 팀 Gmail로 메일을 보낼 수 있는 API가 있는 상태로는 다시 배포할 수 없다. 반대로 스타일링 전환(styled-components → Tailwind)은 사용자가 체감하는 문제가 아니므로 뒤로 미뤘다.

## 0단계: 고치기 전에 재기

고친 뒤 "좋아졌다"고 말하려면 고치기 전 값이 있어야 한다. 그래서 0단계는 기능을 건드리지 않고 두 앱이 깨끗하게 빌드·검사되게 만든 뒤, 그 상태를 숫자로 남겼다(PR #1, 50개 파일, +3,099 / −6,454줄). 측정값은 `docs/baseline.md`에 있다.

| api 항목               | 0단계 전                             | 0단계 후 |
| ---------------------- | ------------------------------------ | -------- |
| 직접 의존성 (dev 포함) | 76                                   | 56       |
| 취약점 합계            | 171                                  | 96       |
| critical               | 6                                    | 0        |
| lint 오류              | 40                                   | 0        |
| 타입 오류              | 5                                    | 0        |
| 테스트                 | 10개 파일, 모두 실패하는 빈 스캐폴드 | 0        |

| web 항목            | 값                                   |
| ------------------- | ------------------------------------ |
| Next.js             | 15.1.3 → 15.5.28                     |
| 취약점              | 35 → 11 (남은 critical 1건은 swiper) |
| `'use client'` 파일 | 90개 중 65개                         |
| Zustand store       | 17                                   |
| `console.*` 호출    | 60                                   |
| 렌더링 방식         | 모든 페이지가 동적 (`force-dynamic`) |
| 테스트              | 0                                    |

api에서 import되지 않는 의존성 20개를 지웠고, 한 번도 통과한 적 없는 스캐폴드 spec 10개는 삭제했다. 통과하지 않는 테스트는 CI를 계속 빨간색으로 만들어, 진짜 실패를 가린다. CI는 web과 api 각각 typecheck → lint → (api) test → build 순서로 돌린다.

## 기준선을 만들다 찾은 것: 테마 타입이 any였다

web의 타입 검사를 통과시키는 과정에서 styled-components 테마에 타입을 연결했다. 그러자 테마에 없는 키를 참조하는 스타일이 13곳 드러났다. 타입이 사실상 `any`였기 때문에 지금까지는 오류 없이 `undefined`가 되어 조용히 무시되고 있었다.

| 위치               | 증상                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| Input·Select·Toast | `borderRadius.default` 등 없는 키를 참조해, 모서리와 그림자가 처음부터 적용되지 않음    |
| `SubscribeInduce`  | styled-components의 `useTheme`에서 없는 `themeName`을 읽어, 라이트 모드에서도 다크 배경 |
| `Spinner`          | `size="2.5rem"`을 fontSize 키로 조회해 크기가 비어 있음                                 |

팀 프로젝트 기간에는 화면이 "대충 맞게" 보였기 때문에 아무도 알아채지 못했다. 타입이 있었다면 처음 작성할 때 컴파일러가 알려 줬을 문제다.

## 남은 것·배운 것

- 레포를 합칠 때 기록을 남긴 덕분에, 이상한 코드를 만나면 `git blame`으로 팀원의 의도를 찾아볼 수 있었다. 이후 글에서 "이 코드는 이런 문제를 피하려던 것으로 보인다"고 쓴 부분은 대부분 이렇게 찾았다.
- 기준선을 먼저 남긴 것이 이후 모든 PR의 비교 기준이 됐다. 예를 들어 "모든 페이지가 동적"이라는 한 줄이 4단계의 정적 빌드 작업으로 이어졌다.
- 단계를 나눠도 0~3단계는 하루(10월 19일)에 모두 병합했다. 단계마다 이슈에 완료 조건을 먼저 적어 두니, PR 범위가 커지는 것을 막을 수 있었다.
