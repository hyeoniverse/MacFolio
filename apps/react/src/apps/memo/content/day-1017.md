### RPG 대화창을 마을 탐험 방식으로

[전날](/memo/day-1016)은 RPG 화면에서 메뉴 간 이동 흐름을 파악하기 어렵다는 문제가 남은 상태였다. 자정 직후부터 이 문제를 다뤘다.

| 시각  | 변경한 것                                                                                                                   |
| ----- | --------------------------------------------------------------------------------------------------------------------------- |
| 00:29 | 게임 화면을 360×208로 낮추고 전체 화면에서 3배(글자 33px)로 확대. 맨 위에 현재 위치 표시줄(메뉴 ▸ 주제 ▸ 단계), 읽음 ✓·NEXT |
| 01:27 | Safari 페이지 전체를 게임 화면으로. 높이에 맞춘 정수배 확대, 반투명 어두운 창, 강조 색은 금색 하나                          |
| 02:16 | 40×24 타일 마을을 방향키·WASD로 이동. 게시판·풀숲의 버그·상점·여관 앞에서 Z를 누르면 해당 주제가 열린다                     |
| 03:18 | 마을과 장면을 Pixel-Boy의 Ninja Adventure 에셋(CC0)으로 교체. 자동 타일 흙길·물, 걷기 프레임이 있는 캐릭터                  |
| 04:09 | 한글 입력 상태에서 Z·X·WASD 입력이 인식되지 않던 문제 수정                                                                  |

마지막 문제의 원인은 키 이벤트의 값이었다. 한글 입력 상태에서 Z를 누르면 `event.key`가 `'z'`가 아니라 `'ㅋ'`로 전달되고, Chrome의 입력기(IME)는 `'Process'`를 전달하기도 한다. `event.key`는 입력된 **문자**이고, `event.code`는 눌린 **물리 키의 위치**다. 게임 키는 입력 언어와 관계없이 같아야 하므로 `event.code`로 판정하도록 수정했다.

| 입력 상태 | Z 키의 `event.key`      | Z 키의 `event.code` |
| --------- | ----------------------- | ------------------- |
| 영문      | `'z'`                   | `'KeyZ'`            |
| 한글      | `'ㅋ'` 또는 `'Process'` | `'KeyZ'`            |

```ts
const CODE_KEYS = { KeyZ: 'z', KeyX: 'x', KeyW: 'w', KeyA: 'a', KeyS: 's', KeyD: 'd' };

export function gameKey(event: KeyboardEvent): string {
	const byCode = CODE_KEYS[event.code];
	if (byCode) return byCode;
	return event.key.length === 1 ? event.key.toLowerCase() : event.key;
}
```

이 중 두 PR은 검토하면서 방향을 정했다.

- **#234 글자 크기:** `--text-caption2`를 `--text-caption`으로 통합할지 검토했지만, 두 값이 달라 화면이 변경되므로 유지했다
- **#244 '단추':** 화면과 문서에 '단추'와 '버튼'이 섞여 있었다. 업계에서 쓰는 용어인 '버튼'으로 기존 글까지 모두 통일하고 PR 본문도 수정했다. 이 과정에서 #230 PR 본문의 이미지가 표시되지 않는 것을 발견해 다시 업로드했다

각 PR의 과정은 개별 글에 정리했다: [모서리 반경](/memo/radius-tokens), [분석 서비스 분리](/memo/analytics-service-split), [글자 크기](/memo/font-size-tokens), [설정 스키마](/memo/settings-schemas), [데모 스키마](/memo/demo-input-schemas), [Memo.css 분리](/memo/memo-css-split), [CSS 중복 제거](/memo/creative-css-dedupe), [사용하지 않는 CSS](/memo/unused-css-selectors), [접근성 이름](/memo/ui-a11y-names).

12시에는 앱마다 직접 구현한 아이콘 버튼 45곳을 IconButton 컴포넌트로 교체한 [#245](https://github.com/hyeoniverse/MacFolio/pull/245)를 올렸다. 이 PR은 다음 날 머지했다([아이콘 버튼 옮기기](/memo/icon-button-migrate)).

리팩터링이 아닌 화면 수정도 하나 있었다. 시스템 설정의 프로젝트 목록은 줄마다 ⓘ 버튼과 눈 모양 버튼이 있었다. 줄을 누르면 편집 화면이 열리고, 공개 여부는 스위치로 전환하도록 변경했다([#239](https://github.com/hyeoniverse/MacFolio/pull/239)).

## CI: Postgres 이미지 저장소와 25분 제한

전날 회고에 "이미지를 캐시하거나 저장소를 변경해야 할 시점"이라고 적은 작업을 이날 아침 [#240](https://github.com/hyeoniverse/MacFolio/pull/240)으로 진행했다.

- Postgres 이미지를 ECR Public에서 내려받지 못하면 mirror.gcr.io, 그다음 Docker Hub 순으로 시도한다
- Postgres를 `services`가 아니라 작업 단계(step)로 실행한다. `services`는 이미지를 내려받지 못하면 작업 전체가 시작되지 않지만, 단계로 실행하면 이미지를 끝내 내려받지 못해도 형식 검사 같은 다른 검사는 실행된다

같은 아침 #187을 머지하기 직전에 화면 E2E도 `check` 작업에서 분리해 세 개 작업으로 나눠 병렬 실행했다. 시험 수가 늘어 한 작업의 25분 제한에 걸렸기 때문이다. API 이미지 빌드와 배포는 E2E까지 통과해야 진행한다. 이틀 뒤 이를 다시 여섯 개로 나눴다([머지하고 배포까지 15분에서 5분으로](/memo/faster-e2e-ci)).

| 하루 끝 main 기준       | 수치 | 전날 대비 |
| ----------------------- | ---: | --------: |
| 브라우저 E2E            |  443 |       +68 |
| 단위 시험 (화면 + core) |  615 |      +131 |
| contracts 단위 시험     |   42 |        +9 |
| API 단위 시험           |  166 |        +9 |
| API e2e                 |  128 |        +4 |
| main에 머지한 PR        |   17 |           |

수치는 그날 마지막 main 커밋(#244 머지)에서 `test(`·`it(` 호출을 집계한 값이고, 전날 값도 같은 방법으로 집계했다. 증가한 시험 대부분은 #187에 포함되어 있었다.

## 돌아보며

#187은 일주일 동안 열려 있었고, 그동안 main이 계속 변경되어 이날 새벽에도 main을 한 번 더 병합해야 했다. 이 PR을 머지할 수 있게 만든 것은 기능 추가가 아니라 **분리**였다. RPG 대화창을 다른 브랜치로 옮기자 바로 머지할 수 있었다. 완성되지 않은 실험이 PR 안에 있으면 PR 전체가 그 실험의 완료를 기다리게 된다.

새벽 5시의 템플릿 구조 변경은 1만 5천 줄 규모였고 22분 만에 되돌렸다. 머지를 앞둔 PR에 그 규모의 변경을 넣은 것 자체가 판단 오류였다. 범위를 첫 화면과 구역 머리로 좁힌 두 번째 시도는 유지했다.

공통 정리 PR 열 개는 서로 다른 방법으로 "화면이 그대로인지"를 확인했다. 값을 그대로 두거나, 빌드한 CSS를 바이트 단위로 비교하거나, 계산된 스타일을 요소마다 비교했다. 리팩터링은 무엇이 동일해야 하는지를 먼저 정하면 검증이 빨리 끝난다.
