## #187 마무리: 프로젝트 페이지 템플릿

[#187](https://github.com/hyeoniverse/MacFolio/pull/187)은 시스템 설정에서 프로젝트를 관리하고, 프로젝트마다 템플릿을 골라 Safari 페이지로 보여 주는 PR이다. 템플릿은 같은 프로젝트 데이터(소개, 팀원, 기술, 트러블슈팅 등)를 서로 다른 화면 구성으로 렌더링하는 틀이고, 제품 소개 페이지·개발자 도구 문서·매거진처럼 실제 웹사이트 양식을 참고했다. 10월 10일에 열어 일주일 만에 머지했다([프로젝트를 시스템 설정에서 관리하기](/memo/site-projects-editing), [프로젝트 앱](/memo/project-apps)). 머지 전에 세 가지를 정리했다.

### RPG 대화창을 마을 탐험 방식으로

[전날](/memo/day-1016) RPG 화면에는 메뉴 간 이동 흐름을 파악하기 어렵다는 문제가 남아 있었다. 이 문제부터 다뤘다.

| 단계      | 바꾼 것                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------------- |
| 위치 표시 | 게임 화면을 360×208로 낮추고 전체 화면에서 3배(글자 33px)로 확대. 맨 위에 현재 위치 표시줄(메뉴 ▸ 주제 ▸ 단계), 읽음 ✓·NEXT |
| 전체 화면 | Safari 페이지 전체를 게임 화면으로. 높이에 맞춘 정수배 확대, 반투명 어두운 창, 강조 색은 금색 하나                          |
| 마을 이동 | 40×24 타일 마을을 방향키·WASD로 이동. 게시판·풀숲의 버그·상점·여관 앞에서 Z를 누르면 해당 주제가 열린다                     |
| 에셋 교체 | 마을과 장면을 Pixel-Boy의 Ninja Adventure 에셋(CC0)으로 교체. 자동 타일 흙길·물, 걷기 프레임이 있는 캐릭터                  |
| 한글 입력 | 한글 입력 상태에서 Z·X·WASD 입력이 인식되지 않던 문제 수정                                                                  |

표의 용어 두 가지를 풀어 쓴다.

- **CC0:** 저작자가 저작권을 포기하고 퍼블릭 도메인으로 공개한다는 Creative Commons 표시다. 출처 표기 없이도 상업적 용도를 포함해 자유롭게 쓸 수 있다
- **자동 타일(autotile):** 흙길이나 물처럼 이어지는 지형을 그릴 때, 주변 칸이 같은 지형인지에 따라 모서리·가장자리 그림을 자동으로 골라 붙이는 방식이다. 예를 들어 물 칸의 위쪽만 땅이면 위쪽에 물가 테두리가 있는 그림을 쓴다

### 한글 입력 상태에서 반응하지 않던 게임 키

마지막 문제의 원인은 키 이벤트의 값이었다. 키보드를 누르면 브라우저는 `keydown` 이벤트를 보내고, 이 이벤트에는 `key`와 `code` 두 값이 있다. `event.key`는 그 키로 입력된 **문자**이고, `event.code`는 눌린 **물리 키의 위치**다.

한국어 두벌식 자판에서 Z 키에는 영문 `Z`와 한글 `ㅋ`이 함께 배치되어 있다. 한글 입력 상태에서 Z를 누르면 `event.key`는 `'z'`가 아니라 `'ㅋ'`이고, Chrome의 입력기(IME, 한글처럼 여러 키를 조합해 글자를 만드는 입력 프로그램)가 조합 중이면 `'Process'`가 전달되기도 한다. 반면 `event.code`는 입력 언어와 관계없이 항상 `'KeyZ'`다.

![한국어 두벌식 자판 배열](./images/day-1017-korean-keyboard.jpg '한국어 두벌식 자판. Z 키에는 ㅋ, X에는 ㅌ, W·A·S·D에는 ㅈ·ㅁ·ㄴ·ㅇ이 함께 배치되어 있어, 한글 입력 상태에서는 event.key가 이 한글 자모가 된다')

| 입력 상태 | Z 키의 `event.key`      | Z 키의 `event.code` |
| --------- | ----------------------- | ------------------- |
| 영문      | `'z'`                   | `'KeyZ'`            |
| 한글      | `'ㅋ'` 또는 `'Process'` | `'KeyZ'`            |

게임의 Z·X·WASD는 글자가 아니라 키보드 위의 위치가 의미를 갖는다. 그래서 `event.code`로 판정하도록 고쳤다. `code`가 표에 없는 키(방향키, Enter 등)는 기존처럼 `event.key`를 쓴다.

```ts
const CODE_KEYS = { KeyZ: 'z', KeyX: 'x', KeyW: 'w', KeyA: 'a', KeyS: 's', KeyD: 'd' };

export function gameKey(event: KeyboardEvent): string {
	const byCode = CODE_KEYS[event.code];
	if (byCode) return byCode;
	return event.key.length === 1 ? event.key.toLowerCase() : event.key;
}
```

![Z 키 하나를 눌렀을 때 event.key와 event.code](./images/day-1017-key-vs-code.svg 'event.key는 입력 상태에 따라 z, ㅋ, Process로 달라지고, event.code는 항상 KeyZ다. gameKey()는 code를 먼저 확인한다')

### 22분 만에 되돌린 템플릿 구조 변경

템플릿마다 페이지 구조 자체를 다르게 만드는 커밋을 올렸다. 제품 템플릿은 스크롤 스토리텔링(스크롤에 따라 화면이 전환되는 구성), 키노트는 16:9 슬라이드 덱, 문서는 페이지 트리 사이드바, 매거진은 표지·목차·펼침면 구조다. 49개 파일에 15,013줄을 추가한 커밋이었고, 22분 만에 그대로 되돌렸다. ==머지를 앞둔 PR에 넣기에는 변경 범위가 지나치게 컸다.==

그래서 범위를 좁혀 다시 했다. 페이지 구조는 공통으로 유지하고, 일곱 템플릿의 첫 화면 구도, 구역 머리, 대표 구역만 다르게 했다.

| 템플릿      | 첫 화면의 특징                  |
| ----------- | ------------------------------- |
| 제품        | 큰 제품 화면과 큰 숫자          |
| 개발자 도구 | 터미널 첫 화면과 `package.json` |
| 매거진      | 왼쪽 정렬 큰 제호와 2단 기사    |

## 공통 정리 PR 머지

공통 정리 계획으로 전날부터 올려 둔 PR을 이날 머지했다. 모두 화면이나 API 동작을 바꾸지 않는 리팩터링(동작은 유지하고 코드 구조만 바꾸는 작업)이다. 리팩터링 PR의 검토에서 가장 중요한 질문은 "정말 아무것도 바뀌지 않았는가"이므로, ==PR마다 "변경 전과 같다"를 확인하는 방법을 정해 두었다==.

## CI: Postgres 이미지 저장소와 25분 제한

### 이미지를 내려받는 곳을 세 곳으로

API 시험(e2e)은 실제 PostgreSQL에 연결해 실행하므로, CI가 시험 전에 Postgres 컨테이너 이미지를 내려받아 실행한다. 이 이미지를 내려받는 단계가 10월 13일부터 `toomanyrequests: Data limit exceeded`로 반복해서 실패했다. 전날 회고에 "이미지를 캐시하거나 저장소를 바꿔야 한다"고 적은 작업을 [#240](https://github.com/hyeoniverse/MacFolio/pull/240)으로 했다.

- Postgres 이미지를 ECR Public에서 내려받지 못하면 mirror.gcr.io, 그다음 Docker Hub 순으로 시도한다. 세 곳 모두 Docker 공식 이미지 `postgres:17-alpine`의 사본을 제공한다. mirror.gcr.io는 Google이 운영하는 Docker Hub 사본 저장소다
- Postgres를 `services`가 아니라 작업 단계(step)로 실행한다

GitHub Actions의 `services`는 작업(job)이 시작되기 전에 보조 컨테이너를 띄우는 설정이다. 이 컨테이너의 이미지를 내려받지 못하면 작업 전체가 시작되지 않아, Postgres와 관계없는 형식 검사나 단위 시험도 실행되지 않는다. 단계로 실행하면 이미지를 끝내 내려받지 못해도 앞의 검사들은 실행되고 결과가 남는다.

![Postgres 이미지를 services로 띄울 때와 작업 단계로 띄울 때](./images/day-1017-image-fallback.svg '수정 전에는 이미지 하나를 받지 못하면 작업 전체가 시작되지 않았다. 수정 후에는 세 곳을 차례로 시도하고, 모두 실패해도 앞 단계의 검사 결과가 남는다')

```bash
for image in \
  public.ecr.aws/docker/library/postgres:17-alpine \
  mirror.gcr.io/library/postgres:17-alpine \
  docker.io/library/postgres:17-alpine; do
  if docker pull -q "$image"; then pulled="$image"; break; fi
  echo "::warning::$image 를 받지 못해 다음 곳에서 받습니다."
done
```

### 화면 E2E를 세 작업으로

[#187](https://github.com/hyeoniverse/MacFolio/pull/187)을 머지하기 직전에는 화면 E2E도 `check` 작업에서 떼어 세 개 작업으로 나눠 병렬 실행했다. 화면 E2E는 Playwright가 실제 브라우저로 사이트를 열어 클릭·입력을 재현하는 시험이고, 시험 수가 늘어 한 작업의 제한 시간(`timeout-minutes: 25`)에 걸렸기 때문이다. 세 작업은 시험 파일을 셋으로 나눠(sharding) 서로 다른 실행기에서 동시에 실행한다. API 이미지 빌드와 배포는 E2E까지 통과해야 진행한다. 이틀 뒤 이를 다시 여섯 개로 나눴다([git 트리 비교로 PR에서 통과한 main 커밋의 E2E 재실행 생략하기](/memo/faster-e2e-ci)).

## 돌아보며

**잘된 것**

- 공통 정리 PR은 "화면이 그대로인지"를 PR마다 맞는 방법으로 확인했다.
  - 값을 그대로 둔다.
  - 빌드한 CSS를 바이트 단위로 비교한다.
  - 계산된 스타일을 요소마다 비교한다.
- 템플릿 구조 변경은 범위를 첫 화면과 구역 머리로 좁힌 두 번째 시도를 유지했다.

**아쉬운 것**

- [#187](https://github.com/hyeoniverse/MacFolio/pull/187)을 일주일 동안 열어 두는 사이 main이 계속 바뀌어, 머지 직전에도 main을 한 번 더 병합했다. 결국 머지할 수 있게 된 것은 미완성인 RPG 대화창을 다른 브랜치로 옮긴 뒤였다.
- 첫 템플릿 구조 변경은 1만 5천 줄 규모였고 22분 만에 되돌렸다. 머지를 앞둔 PR에 넣을 규모가 아니었다.
