뉴픽은 매일 아침 네이버 뉴스를 크롤링하고, 카테고리별로 AI 요약을 만들어 구독자에게 메일로 보낸다. 리팩토링 3단계의 나머지(PR #25, 13개 파일, +455 / −409줄)는 이 흐름의 날짜 계산, 스케줄러, 메일 발송을 고쳤다. 데이터 모델 쪽은 [앞 글](/memo/newpick-data-model)에 있다.

## 트러블슈팅 1: 당일 아침 뉴스가 그날 조회에서 빠졌다

크롤링한 원문을 날짜로 조회하는 코드는 이랬다.

```ts
const startDate = dayjs(dateStart).startOf('day').utc(true).toDate();
const endDate = dayjs(dateEnd).endOf('day').utc(true).toDate();
```

서버가 KST라면 `dayjs('2026-10-19').startOf('day')`는 19일 00:00 KST다. 여기서 `.utc(true)`는 **시각 숫자는 그대로 두고 시간대만 UTC로** 바꾼다. 결과는 19일 00:00 UTC, 즉 19일 09:00 KST다. 범위 전체가 9시간 늦게 밀린다.

![9시간 밀린 하루](./images/newpick-kst-scheduler-range.svg '08:00 크롤링 결과가 19일 범위에 들어가지 않는다')

크롤링은 매일 아침에 돈다. 19일 08:00 KST에 크롤링한 뉴스는 기존 식의 "19일" 범위(09:00부터)에 들어가지 않고 "18일" 범위에 들어갔다. 오늘 뉴스로 요약을 만들려고 하면 어제 뉴스가 나오는 셈이다.

고친 식은 서버의 `TZ`와 관계없이 KST로 계산한다.

```ts
/** KST 기준 하루 단위 범위 [dateStart 00:00, dateEnd 23:59:59.999] */
export function kstDayRange(dateStart: string | Date, dateEnd: string | Date) {
	return {
		start: dayjs.tz(toKstDate(dateStart), KST).startOf('day').toDate(),
		end: dayjs.tz(toKstDate(dateEnd), KST).endOf('day').toDate(),
	};
}
```

단위 테스트는 같은 입력을 `TZ=UTC`, `Asia/Seoul`, `America/Los_Angeles`에서 계산해 결과가 같은지 본다. 배포할 서버의 시간대 설정을 믿지 않기 위해서다. 실제로 19일 11:42 KST에 크롤링한 정치 뉴스를 조회하면 19일 12건, 18일 0건이 나왔다.

## 트러블슈팅 2: 저장한 메일 주기로 재시작하면 서버가 뜨지 않았다

관리자가 메일 발송 주기를 바꾸면 메모리에만 저장되어, 재시작하면 기본값으로 돌아갔다. 비어 있던 `ScheduleConfig` 테이블에 저장하고, 시작할 때 읽어 cron을 바꾸게 했다. 그런데 주기를 바꾼 뒤 재시작하자 API가 응답하지 않았다. 컨테이너 상태는 `Up`이었다.

원인은 두 개가 겹쳐 있었다.

| 원인                                                                                                                                 | 결과                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `onModuleInit`에서 데코레이터로 만든 cron을 레지스트리에서 찾았다. @nestjs/schedule은 데코레이터 cron을 부트스트랩 단계에서 등록한다 | cron을 찾지 못해 예외. `onApplicationBootstrap`으로 옮겨도 순서가 보장되지 않았다   |
| `main.ts`가 시작 중 오류를 잡고 로그만 남겼다                                                                                        | 포트를 열지 않은 프로세스가 계속 살아 있어, `restart: on-failure`도 동작하지 않았다 |

메일 발송 cron은 데코레이터 대신 저장된 주기로 직접 등록하게 바꿨다. 그리고 시작에 실패하면 프로세스를 종료하게 했다. 죽어야 재시작된다. 오류를 삼키는 `catch`가 장애를 "조용한 장애"로 바꾸고 있었다.

## 스케줄러와 메일의 그 밖의 버그

| 문제                             | 영향                                      | 수정                                          |
| -------------------------------- | ----------------------------------------- | --------------------------------------------- |
| AI 요약 루프 전체가 `try` 하나   | 카테고리 하나가 실패하면 나머지 모두 중단 | 카테고리별로 실패를 격리하고 실패 목록만 기록 |
| `Number(hour) \|\| 17`           | 0시를 지정하면 17시 (0이 거짓이라)        | DTO로 0~23 검증                               |
| cron에 시간대 없음               | 서버 시간대에 따라 발송 시각이 달라짐     | 모든 cron에 `timeZone: KST` 명시              |
| 대량 발송이 `Promise.all`        | 구독자 수만큼 동시 SMTP 연결, 재시도 없음 | 동시 2통·초당 5통 제한, 최대 3번 재시도       |
| 발송 오류 시 `details` 없는 결과 | 스케줄러가 결과를 기록하다 다시 오류      | 결과 형태 통일                                |

Gmail SMTP는 동시 연결 수와 발송 속도에 제한이 있다. 구독자가 늘수록 한꺼번에 보내는 `Promise.all`은 실패할 가능성이 커지는데, 재시도가 없으니 실패한 사람은 그날 메일을 받지 못했다. 한 명이 실패해도 나머지는 계속 보낸다는 것을 테스트로 고정했다.

쓰는 곳이 없던 메일 메서드 2개와 `retry_queues` 테이블은 삭제했다. 단위 테스트는 22개에서 31개가 됐다(KST 범위 4, 스케줄러 2, 메일 3).

## 이틀 뒤: '어제'를 요청하던 무료 체험

KST 버그를 고친 뒤 프론트를 보니, 홈의 무료 체험은 항상 **어제** 날짜로 요약을 요청하고 있었다. 9시간 밀린 범위 때문에 오늘 아침 뉴스가 "어제"에 들어가 있었으니, 그것을 피하려던 흔적으로 보인다.

그런데 그 날짜를 만드는 방식에 또 다른 문제가 있었다.

```ts
now.setDate(now.getDate() - 1);
return dateFormatter(now.toLocaleDateString('ko-KR', { year: 'numeric', month: '2-digit', day: '2-digit' }));
```

`toLocaleDateString('ko-KR')`의 결과는 `"2026. 10. 20."`이다. 이 문자열을 dayjs로 다시 파싱하는데, dayjs의 파싱 규칙은 이 형식을 모르므로 `new Date(문자열)`에 넘긴다. ISO가 아닌 문자열의 해석은 엔진마다 다르다.

| 엔진                    | `new Date("2026. 10. 20.")`         |
| ----------------------- | ----------------------------------- |
| V8 (Chrome, Node)       | `Tue Oct 20 2026 00:00:00 GMT+0900` |
| JavaScriptCore (Safari) | `Invalid Date`                      |

Safari에서는 `dateStart: "Invalid Date"`가 전송되고, api의 `@IsDateString()` 검증에서 400이 난다. **Safari 사용자는 무료 체험을 쓸 수 없었다.** macOS에 들어 있는 `jsc`로 엔진만 따로 확인했고, 버그 이슈(#28)로 남겼다. 문자열을 거치지 말고 `dayjs().subtract(1, 'day').format('YYYY-MM-DD')`처럼 날짜 객체에서 바로 포맷하면 되고, 고치면서 오늘 날짜로 바꿀지도 함께 정한다.

## 남은 것·배운 것

- 날짜 버그 하나가 다른 곳에 우회 코드를 만들고, 그 우회 코드가 또 다른 버그(Safari)를 품고 있었다. 원인을 고친 뒤에는 그 원인을 피하려던 코드도 찾아봐야 한다.
- 시작 중 오류를 잡아 로그만 남기는 코드는 컨테이너 재시작 정책을 무력화한다. 시작에 실패하면 죽는 것이 맞다.
- 실제 Gmail 발송과 스케줄러 켜기/끄기 상태 저장은 아직 남았다. 켜기/끄기는 관리자 대시보드(#21)를 만들 때 정한다.
