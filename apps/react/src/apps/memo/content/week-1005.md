## 서버 운영: 백업·자동 배포·감시

주 초반의 서버 작업은 "서버가 중단되면?"에 대한 답이다. 글은 서버 밖(R2)에 백업하고(10월 5일), 배포가 실패하면 이전 컨테이너로 되돌리고(10월 5일), 10분마다 외부에서 가동 여부를 확인하고(10월 7일), 유휴 자원 회수에 대비해 1분마다 사용률을 측정한다(10월 10일).

### DB 백업 (10월 5일)

블로그 글과 이미지가 모두 1GB 무료 서버의 DB에만 저장되어 있었다. 매일 DB를 덤프해 서버 밖(Cloudflare R2)에 보관하고, 복원까지 스크립트로 검증하게 했다([pg_dump와 R2로 하는 DB 백업과 복원 시험](/memo/db-backup), [#94](https://github.com/hyeoniverse/MacFolio/pull/94)). 스크립트는 [ops/backup.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/backup.sh)와 [ops/restore.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/restore.sh)에 있고, R2 설정은 [Cloudflare R2 문서](https://developers.cloudflare.com/r2/)와 [rclone 설치 문서](https://rclone.org/install/)를 따랐다.

```bash
sudo -v ; curl https://rclone.org/install.sh | sudo bash   # apt 버전은 R2를 지원하지 않는다
rclone config                                            # R2 원격 저장소 생성
~/macfolio/ops/backup.sh                                 # 한 번 실행해 확인
rclone ls <원격>:<버킷>                                    # 업로드된 파일 확인
```

적용 중 발생한 문제는 세 가지다.

1. R2 무료 한도를 초과할 수 있어, 무료 한도에 도달하기 전에 백업을 중단하게 했다([#98](https://github.com/hyeoniverse/MacFolio/pull/98))
2. apt의 rclone 1.53은 R2 공급자를 지원하지 않아 공식 설치 스크립트로 최신 버전을 설치했다
3. 버킷 목록 조회(`rclone lsd r2:`)는 계정 전체 요청이라, 버킷 하나에만 권한이 있는 키로는 항상 403이다. 연결 확인을 버킷 크기 조회와 시험 파일 업로드·삭제로 변경했다([#99](https://github.com/hyeoniverse/MacFolio/pull/99))

서버에서 처음 실행한 백업 파일은 1,007KB였고, 복원한 DB의 글 수가 원본과 같았다.

### API 자동 배포 (10월 5일)

main에서 API가 변경되면 GitHub Actions가 이미지를 빌드해 GHCR에 업로드하고, 서버는 다음 순서로 배포한다([command= 제한 SSH 키와 GHCR 이미지로 하는 API 자동 배포와 롤백](/memo/api-auto-deploy), [#104](https://github.com/hyeoniverse/MacFolio/pull/104), 이슈 [#100](https://github.com/hyeoniverse/MacFolio/issues/100)). 1GB 메모리 서버가 직접 이미지를 빌드하던 작업이 사라졌다.

```text
GitHub Actions: 이미지 빌드 → GHCR 업로드
서버:          DB 백업 → 컨테이너 교체 → 헬스 체크 → 실패 시 이전 이미지로 롤백
```

실제 서버에 적용하면서 문제가 다섯 번 발생했다. 그중 하나는 첫 배포에서 바로 발생했다. 서버의 compose 파일은 이미지 태그(`API_TAG`)가 없으면 중단하도록 작성했는데, 첫 배포에는 태그가 아직 없어서 배포 전 백업 단계가 중단되었다([#107](https://github.com/hyeoniverse/MacFolio/pull/107)). 로컬 시험용 compose 파일에는 이 검사가 없어 시험에서 발견하지 못했다. ==시험은 운영과 같은 설정 파일로 진행해야 한다.==

### 서버 하드닝 점검 스크립트 (10월 11일)

서버 하드닝 상태를 문서 대신 `ops/audit.sh`가 직접 읽어 출력하게 했다([#183](https://github.com/hyeoniverse/MacFolio/pull/183), [#186](https://github.com/hyeoniverse/MacFolio/pull/186), [서버 하드닝은 스크립트로](/memo/server-hardening-audit)). #183을 머지한 뒤 새벽 1시 반에 실행한 첫 결과에서 "확인" 항목이 두 개였다. SSH(22) 외에 `0.0.0.0:111`(rpcbind)이 외부 인터페이스에서 수신 대기 중이었고, 호스트 방화벽 규칙을 읽지 못했다.

```bash
cd ~/macfolio && git pull && ops/audit.sh
# [포트] 외부에서 수신 대기 중인 포트
#         tcp 0.0.0.0:111      ← rpcbind
#         tcp 0.0.0.0:22
#   확인  SSH 외에 외부에서 수신 대기 중인 포트가 있다
sudo systemctl disable --now rpcbind.socket rpcbind.service
sudo reboot
```

| 단계               | 확인 방법                          | 결과                                                        |
| ------------------ | ---------------------------------- | ----------------------------------------------------------- |
| 재부팅 후 컨테이너 | `cd ~/deploy && docker compose ps` | api·db·tunnel 실행 중 (api는 `health: starting` 후 healthy) |
| 포트               | `ops/audit.sh` 재실행              | `OK SSH(22) 말고 바깥에서 듣는 포트 없음`                   |
| 방화벽             | `sudo iptables -S INPUT`           | 22번만 허용하는 규칙                                        |

스크립트 자체의 오류도 두 가지 발견했다. cloudflared 이미지에는 `id`·`sh`가 없어서 "root가 아닌 사용자" 검사가 오류 메시지를 OK로 출력했고, 방화벽 규칙은 sudo 없이 읽을 수 없었다. #186에서 수정한 뒤 재실행해 모든 항목이 OK로 나왔다.

## 없는 자산의 404와 1년 캐시

10월 2일에 "배포 직후 메모가 열리지 않던" 문제를 경고 대화상자로 처리하고 넘어갔다. 10월 5일에 근본 원인을 찾았다.

| 조건                                                             | 결과                                                 |
| ---------------------------------------------------------------- | ---------------------------------------------------- |
| 사이트가 존재하지 않는 주소에도 항상 `index.html`을 200으로 반환 | 없는 코드 파일 요청에도 HTML이 200으로 응답됨        |
| `/assets/*`에는 1년 동안 재요청하지 않는 `immutable` 캐시 헤더   | 위 HTML 응답이 그 코드 파일 이름으로 1년 동안 캐시됨 |

배포 중에 삭제된 이전 코드 파일 주소를 요청한 브라우저는 ==그 파일 이름으로 HTML을 1년 동안 캐시==하게 된다. 존재하지 않는 파일 주소는 404를, 앱 주소만 첫 화면을 반환하도록 분리했다([not_found_handling 뒤 Worker 함수로 SPA 주소와 없는 자산의 404 나누기](/memo/asset-404), [#103](https://github.com/hyeoniverse/MacFolio/pull/103)).

## 메뉴 막대: 서버 상태·앱별 메뉴·단축키

### 서버 상태 메뉴와 API 문서 앱 (10월 5일)

장식용이던 메뉴 막대의 Wi-Fi 아이콘 자리에 API 서버 상태를 표시했다. `/health`를 주기적으로 호출해 응답 시간과 DB 상태를 막대 개수로 표시하고, 누르면 상세 정보를 보여 준다([/health 응답 시간을 막대 수로 환산하고 no-cors 요청으로 CORS 차단을 구분하는 서버 상태 표시](/memo/server-status-wifi), [#90](https://github.com/hyeoniverse/MacFolio/pull/90)). 화면 끝에서 잘리는 메뉴와 고정 위치로 표시되던 음량 창도 함께 수정했다.

![현재의 서버 메뉴](./images/day-1005-server-menu.jpg '메뉴 막대 오른쪽 위의 서버 메뉴. 현재 화면이고, 시험용 가짜 API에 연결되어 있다')

서버 메뉴의 'API 문서 열기'는 처음에 서버의 `/docs`를 iframe으로 표시했고, 이를 위해 서버의 보안 헤더(`X-Frame-Options`, `frame-ancestors`)에 `/docs` 경로만 예외를 추가했다. 43분 뒤 방식을 바꿨다. 서버 상태 메뉴에서 여는 문서인데, ==서버에 문제가 있어 문서가 가장 필요한 시점에 iframe은 빈 창이 된다.==

그래서 API 코드에서 생성한 `openapi.json`을 사이트에 포함하고 사이트 안에서 Scalar로 렌더링하는 방식으로 바꿨다.

| 항목         | iframe 방식(서버의 Swagger UI) | 사이트 포함 방식(Scalar)                                |
| ------------ | ------------------------------ | ------------------------------------------------------- |
| 서버 중단 시 | 빈 창                          | 정상 표시                                               |
| 보안 헤더    | `/docs`만 iframe 허용 예외     | 예외 불필요 (원래대로 복원)                             |
| 코드와 일치  | 항상 일치                      | 단위 시험이 비교. 파일을 다시 생성하지 않으면 CI가 실패 |

자세한 내용은 [Vite 두 번째 진입점과 iframe으로 Scalar API 문서 격리하기](/memo/api-docs-app)([#95](https://github.com/hyeoniverse/MacFolio/pull/95))에 정리했다. 앱이 늘어나면서 Dock이 Launchpad와 겹치는 문제도 수정했다([글](/memo/dock-layout)).

![현재의 API 문서 앱](./images/day-1005-apidocs.jpg 'API 문서 앱의 현재 화면. 서버 없이도 열린다')

### 앱 이름과 앱별 메뉴 (10월 5~6일)

메뉴 막대의 앱 이름이 맨 앞 창의 앱을 따르게 하고([#97](https://github.com/hyeoniverse/MacFolio/pull/97), [#101](https://github.com/hyeoniverse/MacFolio/pull/101), [창 순서와 분리한 활성 앱 상태로 메뉴 막대 앱 이름 맞추기](/memo/menu-bar-app-name)), 메뉴 막대를 클릭하면 앱 이름이 Finder로 바뀌던 문제([#110](https://github.com/hyeoniverse/MacFolio/pull/110))와 Dock을 누르는 동안 Finder로 깜빡이던 문제([#133](https://github.com/hyeoniverse/MacFolio/pull/133))를 차례로 수정했다.

파일·보기·윈도우·도움말은 10월 5일에 실제 메뉴로 열리게 했고([#105](https://github.com/hyeoniverse/MacFolio/pull/105), 이슈 [#96](https://github.com/hyeoniverse/MacFolio/issues/96)), 10월 6일에 앱마다 메뉴 항목을 등록하게 했다.

### 단축키: ⌘ 대신 ⌥ (10월 6일)

> [!NOTE] ⌘ 대신 ⌥를 쓰는 이유
> macOS 앱은 ⌘N·⌘T·⌘W를 사용하지만, 브라우저 안의 웹 페이지는 이 키 입력을 받지 못한다. 브라우저가 먼저 새 창·새 탭·탭 닫기를 실행하고, 페이지에서 `preventDefault()`로 막을 수도 없다. 그래서 같은 글자에 ⌥를 조합했다([#112](https://github.com/hyeoniverse/MacFolio/pull/112)).

| 키               | 동작                                       |
| ---------------- | ------------------------------------------ |
| ⌥N               | 새로운 메모(관리자) · 새로운 Finder 윈도우 |
| ⌥T · ⌥W          | 새로운 탭 · 탭 닫기 (Safari)               |
| ⌥[ · ⌥] · ⌥↑     | 뒤로 · 앞으로 · 상위 폴더 (Finder)         |
| ⌥Space · ⌥← · ⌥→ | 재생/일시정지 · 이전 곡 · 다음 곡 (음악)   |
| ⌥W · ⌥M          | 윈도우 닫기 · 최소화 (공통)                |

도움말에 키보드 단축키 목록을 추가하고 화면에 표시해 보니, Safari에 '탭 닫기 ⌥W'와 '윈도우 닫기 ⌥W'가 함께 있었다. 같은 키가 두 항목에 지정되면 앞쪽 항목만 동작하므로, 윈도우 닫기는 메뉴에 단축키가 표시되지만 실제로는 동작하지 않았다. 앱이 ⌥W를 사용하면 윈도우 닫기를 ⌥⇧W로 바꾸는 macOS Safari와 같은 규칙을 적용했다.

![현재의 키보드 단축키 목록](./images/day-1006-shortcuts.jpg '도움말 → 키보드 단축키의 현재 화면')

## main에서만 실패한 시험과 생략된 API 배포

10월 7일, 세 문제가 순서대로 이어졌다.

```text
#115 PR 미리보기의 CORS 수정 (API 변경 포함)
  └→ main에서 메뉴 시험 실패 → 이 실행은 배포 단계까지 가지 못함
       └→ #116 메뉴 시험 수정 (API 변경 없음) → CI 통과, 그러나 API 배포 단계 생략
            └→ #115의 API 변경이 어느 실행에서도 배포되지 않음 → #118 배포 판단 기준 변경
```

**PR 미리보기의 CORS.** PR 미리보기에서는 메뉴 막대의 서버 상태가 항상 "연결할 수 없음"이었다. 서버는 정상 동작 중이었고, API의 CORS 허용 목록에 미리보기 주소가 없었다. 미리보기 주소는 브랜치마다 달라서 하나씩 등록할 수 없으므로, 허용 주소에 와일드카드 `*`를 사용할 수 있게 했다([#115](https://github.com/hyeoniverse/MacFolio/pull/115), [no-cors 요청으로 CORS 차단과 서버 중지 구분하기](/memo/server-status-wifi#no-cors-요청으로-cors-차단과-서버-중지-구분)). 10월 11일에는 미리보기 주소에 CORS로 읽기만 허용하고 관리자 쿠키는 허용하지 않게 좁혔다([#182](https://github.com/hyeoniverse/MacFolio/pull/182), [미리보기 주소에는 읽기만](/memo/preview-cors-read-only)).

**정지한 마우스 아래로 이동한 메뉴 제목.** #115를 머지하자 main에서 메뉴 막대 시험 하나가 실패했다. '윈도우' 메뉴를 열었는데 '편집' 메뉴가 열렸다. 로컬과 PR에서는 통과한 시험이고, #115는 메뉴 코드를 변경하지 않았다.

시험이 마우스를 '윈도우' 위에 올린 뒤 메모 앱이 열리며 편집·보기 메뉴가 등록되고, 메뉴 제목들이 오른쪽으로 이동한다. 정지한 마우스 아래로 '편집' 제목이 이동해 오면 ==브라우저는 이것도 마우스가 요소에 진입한 것으로 보고== 진입 이벤트를 발생시켜, 메뉴가 '편집'으로 전환된다.

마우스가 실제로 움직였을 때만 옆 메뉴로 전환하도록 수정했다([#116](https://github.com/hyeoniverse/MacFolio/pull/116)). "마우스는 정지한 채 제목만 이동하는" 상황을 시험으로 직접 재현해, 수정 전 빌드에서는 실패하는 것까지 확인했다.

**생략된 API 배포.** #116을 머지하자 CI는 통과했지만 서버는 여전히 이전 버전이었다. #116에는 API 변경이 없었고, #115에는 있었지만 그 실행은 메뉴 시험 실패로 배포 단계까지 가지 못했다.

| 항목             | 변경 전                                 | 변경 후                                        |
| ---------------- | --------------------------------------- | ---------------------------------------------- |
| 배포 판단 기준   | 직전 push 대비 API 코드 변경 여부       | **서버에서 실행 중인 버전** 대비 변경 여부     |
| 실패한 실행 이후 | 실패한 실행의 API 변경이 누락될 수 있음 | 다음에 성공한 실행이 서버를 최신 버전으로 맞춤 |

판단 기준을 서버에서 실제로 실행 중인 버전으로 변경했다([#118](https://github.com/hyeoniverse/MacFolio/pull/118), [자동 배포를 실제 서버에 걸기](/memo/api-auto-deploy)). 수동으로 다시 배포하고 끝낼 수도 있었지만, 이 변경으로 실패한 실행이 여러 번 있어도 다음에 성공한 실행이 서버를 최신 버전으로 맞춘다.

### 메일 발송과 사서함 (10월 7~8일)

이전에는 메일 앱이 방문자의 메일 프로그램을 여는 `mailto:` 링크였다. 서버가 Resend로 발송하고, 보낸 사람 주소를 Reply-To 헤더에 넣어 바로 답장할 수 있게 하고, Cloudflare Turnstile과 하루 발송 상한으로 스팸을 막았다. 서버 설정이 없으면 이전처럼 메일 프로그램을 여는 방식으로 대체한다([Resend API와 Turnstile로 서버에서 메일 발송하고 스팸 차단하기](/memo/contact-mail), [#125](https://github.com/hyeoniverse/MacFolio/pull/125)).

다음 날에는 발송한 메일을 앱 안에서 다시 조회할 수 있게 했다([#128](https://github.com/hyeoniverse/MacFolio/pull/128)).

| 사용자 | 조회 범위                                  | 동작                 |
| ------ | ------------------------------------------ | -------------------- |
| 방문자 | 이 브라우저에서 보낸 메일과 그에 대한 답장 | 조회                 |
| 관리자 | 받은 모든 메일                             | 조회, 앱 안에서 답장 |

> [!IMPORTANT]
> "본인 메일만"은 화면에서 숨기는 방식이 아니라 **서버가 필터링**한다. 서버는 방문자 쿠키의 HMAC이 일치하는 메일만 반환하고, 메일 하나를 번호로 조회하는 API 경로는 만들지 않았다. 번호로 조회하는 경로가 있으면 번호만 바꿔 다른 사람의 메일을 요청할 수 있기 때문이다([방문자 쿠키의 HMAC으로 서버가 메일 조회 범위를 필터링하기](/memo/mail-mailboxes)).

> [!WARNING] Tunnel 뒤에서 집계되는 IP
> 요청 제한(#162)을 적용하기 전에 서버 설정을 확인했다. 요청 제한은 IP 단위로 집계하는데, Cloudflare Tunnel 뒤에서는 `TRUST_PROXY=1`이 설정되어 있어야 `X-Forwarded-For`에서 실제 방문자 IP를 읽는다. 값이 없으면 모든 요청이 터널의 IP 하나로 집계되어, 방문자 한 명이 한도를 넘으면 모두가 차단된다. 서버의 값은 이미 `1`이어서 변경하지 않았다.

```bash
cd ~/deploy && grep TRUST_PROXY api.env   # TRUST_PROXY=1
```

![개인정보 보호 및 보안](./images/day-1010-privacy.jpg '시스템 설정의 개인정보 보호 및 보안 화면. 관리자가 메일·댓글·메시지의 봇 검증을 켜고 끈다')

GitHub 화면에서만 바꿀 수 있는 설정은 직접 적용했다. Settings › Code security에서 Dependabot security updates, Secret Protection, Push protection을 활성화하고, main Ruleset의 필수 검사에 `secrets`(gitleaks 작업)를 추가했다. 화면의 메뉴 이름이 문서와 달라 [Secret scanning 문서](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)와 [Push protection 문서](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)로 항목을 대조했고, 절차는 [docs/security-scan.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/security-scan.md)에 기록했다.

점검 항목 대부분은 이미 차단되어 있지만 시험이 없던 것(XSS, 경로 권한)이거나 한 단계만 차단되어 있던 것(iframe, 요청 제한)이었다. 차단 사실을 시험으로 고정해야 이후 설정 변경으로 열리지 않는다.

### 사라질 때도 애니메이션 (10월 8일)

메뉴·경고 대화상자·팝업은 나타날 때만 애니메이션이 적용되고, 닫힐 때는 즉시 사라졌다. React는 요소를 DOM에서 제거한 뒤에는 애니메이션을 적용할 수 없다. React 19의 ref 정리 함수(cleanup)가 호출되는 시점에 요소의 **겉모습만 복사**해 같은 위치에 배치하고, 그 복사본에 사라지는 애니메이션을 적용했다(`useExitMotion`, [#134](https://github.com/hyeoniverse/MacFolio/pull/134)).

| 항목             | 동작                                          |
| ---------------- | --------------------------------------------- |
| 여는 쪽 코드     | 변경 없음 (`{open && <Menu />}` 그대로)       |
| 상태·포커스·시험 | 모두 이미 닫힌 상태를 기준으로 동작           |
| 복사본           | 클릭할 수 없고, 스크린 리더에도 노출되지 않음 |

"여는 쪽 코드를 변경하지 않는다"는 조건을 먼저 정하고 설계했다. 자세한 내용은 [ref 정리 함수에서 제거 직전 DOM을 복제해 만드는 퇴장 애니메이션](/memo/global-motion)에 정리했다.

### 계획 1~3단계를 2 → 3 → 1 순서로 (10월 11일)

2. **3단계 공통 기반:** 서버 요청을 `api()`·`apiFetch()`로 통합하고([#196](https://github.com/hyeoniverse/MacFolio/pull/196)), 브라우저 저장소 접근을 `storage.ts`로([#198](https://github.com/hyeoniverse/MacFolio/pull/198)), `matchMedia`·`innerWidth` 접근을 `media.ts`로 모았다([#199](https://github.com/hyeoniverse/MacFolio/pull/199))
3. **1단계 타입·데이터:** API 형식을 contracts로 8개 도메인 이전하고([#200](https://github.com/hyeoniverse/MacFolio/pull/200)~[#207](https://github.com/hyeoniverse/MacFolio/pull/207)), 1,629줄 `profile.ts`를 폴더로 분할하고([#208](https://github.com/hyeoniverse/MacFolio/pull/208)), 글 주소·폴더 경로를 브랜드 타입으로 바꿨다([#209](https://github.com/hyeoniverse/MacFolio/pull/209))

계획의 번호와 반대로 2단계부터 진행했다. 순환 의존(파일 A가 B를 import하고, B가 다시 A를 import하는 관계)을 먼저 제거하고 큰 파일을 먼저 분할해 두어야, 타입을 옮길 때 수정할 파일의 범위가 작아진다. 타입을 먼저 해야 하지 않나 다시 검토했지만 이 순서가 불가피했다. 2단계 안에서 두 가지 방법 중 하나를 고를 때는 작업량이 아니라 코드 품질을 기준으로 판단했다.

| 대상            | 전              | 후                           | 글                                                                                                                                                     |
| --------------- | --------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 서버 요청 코드  | 346줄           | 179줄                        | [공통 API 클라이언트 api()·apiFetch()로 fetch 호출과 401 처리 통합하기](/memo/shared-modules#서버-호출-apiapifetch)                                    |
| 브라우저 저장소 | 134줄           | 53줄                         | [readJson·writeJson으로 브라우저 저장소 예외 처리를 한 곳에 모으기](/memo/shared-modules#브라우저-저장소-readjsonwritejson)                            |
| `profile.ts`    | 1,629줄 한 파일 | 프로젝트별 파일 + `index.ts` | [index.ts 재내보내기로 import 경로를 유지하며 큰 모듈을 폴더로 나누기](/memo/module-splitting#import-경로를-유지하는-indexts-재내보내기-sharedprofile) |

`profile.ts`는 프로젝트별 파일로 분할했지만 `index.ts`가 모두 다시 export해서, 외부 27곳의 import 경로는 변경하지 않았다. 공통 컴포넌트 후보는 "형태·의미가 다르니 보류"로 넘기지 않고 실제 사용처를 집계했고, 이 집계는 다음 날 Modal 추출로 이어진다.

### contracts: 이전하면서 드러난 불일치

1단계의 중심은 `packages/contracts`다. API 요청·응답 형식을 zod 스키마로 한 번 정의하고, 서버는 요청 검증에, 화면은 타입 추론에 함께 사용한다([zod 스키마 패키지 @macfolio/contracts로 서버 검증과 화면 타입 공유하기](/memo/contracts-package#댓글좋아요-스키마-200)). 댓글부터 시작해 글, 메시지, 연락 메일, 배경화면, 업로드 파일, 분석, 사이트 프로필까지 8개 도메인을 PR 8개로 이전했다.

```text
전: 서버 DTO ─┐                후: packages/contracts (zod 스키마 1개)
             ├ 따로 정의                ├─ 서버: parse(Schema, body)로 검증
   화면 type ─┘                         └─ 화면: z.infer로 타입 추론
```

이전 작업보다 중요한 것은 두 곳에 따로 정의된 값이 이미 서로 달라져 있었다는 발견이다.

| 도메인    | 화면                          | 서버                     | 글                                                                                                                                         |
| --------- | ----------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 메시지    | `mine?: boolean` (선택)       | `mine: boolean` (필수)   | [메시지 도메인 옮기기](/memo/contracts-package#메시지-스키마와-두-저장소-구현-202)                                                         |
| 연락 메일 | "30자까지 입력할 수 있습니다" | "30자까지입니다"         | [zod superRefine으로 첫 실패 문구만 반환하는 화면·서버 공통 검사](/memo/contracts-validation#연락-메일-칸마다-첫-실패-문구-하나-203)       |
| 배경화면  | "API와 같은 한도" 주석과 40   | 서버 규칙 40, DB 제약 40 | [DB CHECK·서버·화면에 흩어진 이름 한도를 contracts 정리 함수로 통합하기](/memo/contracts-validation#배경화면-이름-한도-40과-정리-함수-204) |

마지막은 브랜드 타입이었다. 글 주소와 폴더 경로가 모두 `string`이라, 주소창에서 읽은 문자열을 검증 없이 `movePost`에 넘겨도 컴파일됐다. 이제는 `postSlug()`·`folderPath()`를 거쳐야 해당 타입이 된다. 런타임에는 일반 문자열이라 동작은 바뀌지 않는다([PostSlug·FolderPath 브랜드 타입](/memo/branded-ids)).

### 코드 수정 없이 바꾸는 사이트 정보 (10월 11일)

이 저장소를 내려받아 배포하는 사람은 이름과 메일 주소를 바꾸려면 코드를 수정해야 했다. 프로필을 서버에 저장하고, 관리자가 시스템 설정 › 정보에서 수정하게 했다. 상수를 읽던 15곳은 구독 가능한 store를 읽게 바꿨다([#180](https://github.com/hyeoniverse/MacFolio/pull/180), [코드를 고치지 않고 프로필 바꾸기](/memo/site-profile-editing)).

## PR 하나의 CI로 드러나지 않는 실패

### 스택 PR의 머지 대상 (10월 10일)

10월 9일 밤 블로그 폴더 PR [#143](https://github.com/hyeoniverse/MacFolio/pull/143)을 main에 머지했다. 그 브랜치 위에 휴지통 앱 [#145](https://github.com/hyeoniverse/MacFolio/pull/145)를, 다시 그 위에 서버 파일 관리 [#146](https://github.com/hyeoniverse/MacFolio/pull/146)을 쌓아 두었다(스택 PR). 30여 초 뒤 두 PR을 머지했는데, 둘 다 **main이 아니라 아래 브랜치에** 머지됐다. PR의 머지 대상은 base 브랜치이고, 아래 PR이 이미 머지된 뒤라 변경이 main까지 도달하지 않았다.

![스택 PR의 머지 대상](./images/day-1010-stacked-pr.svg '#145와 #146은 base가 아래 PR의 브랜치라, 머지해도 main에 반영되지 않았다')

같은 변경을 main을 base로 다시 올려 머지했다([#147](https://github.com/hyeoniverse/MacFolio/pull/147)). 전날 음악 PR(#141)은 위 PR을 먼저 머지해서 문제가 없었는데, 머지 순서가 우연히 맞았을 뿐이다. ==이후로는 PR을 쌓지 않고 항상 main을 base로 연다.==

### 각자 통과한 PR의 조합 (10월 10~11일)

경로 표 시험(#160)은 좋아요가 추가되기 전의 API 경로로 표를 만들었다. 그 사이 좋아요(#158)가 먼저 main에 머지되어 경로가 6개 늘었다. 두 PR은 각자 CI를 통과했지만, main에서 합쳐지자 "표에 없는 경로"로 실패했다. 수정 PR([#166](https://github.com/hyeoniverse/MacFolio/pull/166))을 열었는데, 같은 표를 수정하던 요청 제한 PR(#162)이 해당 경로까지 포함해 먼저 머지되어 #166은 닫았다.

10월 11일에도 같은 유형으로 main이 한 번 실패했다. 이전 카테고리를 지정한 글 한 편이 다른 PR과 합쳐지면서 '인프라' 폴더가 둘로 나뉘어, 메모 E2E에서 '인프라' 버튼이 두 개 선택되었다. 글은 메모 앱 E2E의 시험 데이터이기도 해서, 글을 추가하는 PR도 메모 E2E를 실행한 뒤 올려야 한다.

### 대소문자를 구분하지 않는 macOS (10월 11일)

데모 파일을 분할하면서 같은 폴더에 `Slides.tsx`와 `slides.ts`가 생겼다. 파일 이름의 대소문자를 구분하는 Linux CI는 통과했지만, 구분하지 않는 macOS(APFS 기본값)에서는 `./Slides`가 `slides.ts`로 해석되어 타입 검사와 빌드가 실패했다. 목록 파일을 `slideDeck.ts`로 변경하고([#197](https://github.com/hyeoniverse/MacFolio/pull/197)), CONTRIBUTING에 파일 이름의 대소문자 규칙을 추가했다.

### 취소된 main CI 실행 (10월 11일)

PR이 몰려 머지되는 동안 main CI는 대부분 끝까지 실행되지 못했다. 같은 브랜치에 새 push가 오면 이전 실행을 취소하도록(`concurrency.cancel-in-progress`) 설정해 두어서, 이날 main의 CI 실행 28회 중 18회가 취소됐다. 연속으로 머지한 PR들은 마지막 머지 커밋에서만 시험을 거쳤고, 위의 카테고리 문제도 그 마지막 실행이 실패해서 드러났다. 머지를 몰아서 하면 확인할 수 있는 실행 자체가 줄어든다.

### 의존성과 CI 설정 (10월 10일)

- **CI가 시작 단계에서 실패:** API e2e용 PostgreSQL 이미지를 Docker Hub에서 인증 없이 내려받다가 요청 한도를 초과했다. GitHub 러너는 IP를 공유해 재실행해도 같았다. 같은 이미지를 ECR Public에서 내려받게 했다([#154](https://github.com/hyeoniverse/MacFolio/pull/154))
- **`@types/node` 26에서 타입 검사 실패:** 프론트엔드 `lib`는 ES2020인데 코드는 ES2022의 `.at()`을 사용했다. 그동안 `@types/node` 22가 ES2022 타입을 함께 불러와 **우연히** 통과하고 있었다. `lib`를 ES2022로 변경했다([#178](https://github.com/hyeoniverse/MacFolio/pull/178))
- **Dependabot PR에도 미리보기 배포:** 모든 PR에 Workers 미리보기를 배포하던 것을 프론트엔드가 변경된 PR에만 배포하게 했다([#179](https://github.com/hyeoniverse/MacFolio/pull/179))
- **lint 경고 4개:** 경고 수준으로 낮춰 둔 규칙의 경고를 해소하고 규칙을 에러로 올린 뒤, 모든 패키지에 `--max-warnings 0`을 적용했다([#144](https://github.com/hyeoniverse/MacFolio/pull/144))

Dependabot을 활성화하자 PR 6개가 한꺼번에 열렸다(vite 6→8, `@types/node` 26 등, [#171](https://github.com/hyeoniverse/MacFolio/pull/171)~[#176](https://github.com/hyeoniverse/MacFolio/pull/176)). 같은 잠금 파일(`pnpm-lock.yaml`)을 변경하므로 하나를 머지할 때마다 나머지가 충돌했다. #172·#175·#176은 충돌로, #161·#172·#173은 CI 실패로 멈춰 하나씩 해결했다. Dependabot 브랜치에 사람이 커밋하면 커밋 메시지 규칙 검사에 걸리던 문제도 #178에서 수정했다.

### 간헐적으로 실패하는 시험 세 건 (10월 10일)

증상은 모두 "가끔 실패"였지만 원인은 서로 달랐다.

- **메모 편집 (코드의 버그):** 전체 시험을 실행할 때만 가끔 실패했다. 세 시험을 `--repeat-each=14 --workers=10`으로 부하를 높여 실행하니 36회 중 2회 재현됐다. 제목에서 Enter를 누르는 시점에 지연 로딩하는 편집기가 아직 없어, 편집기 모듈을 내려받는 동안 입력한 글자가 제목 칸에 들어가고 있었다. 느린 기기에서는 실제 사용자도 겪는 버그라, Enter 입력을 기억했다가 편집기가 준비되면 초점을 옮기게 했다([#148](https://github.com/hyeoniverse/MacFolio/pull/148), [아직 없는 편집기로 옮긴 초점](/memo/lazy-editor-focus))
- **메시지 (시험 데이터의 우연):** 무작위로 생성한 이름이 우연히 겹치면 실패했다. 첫 브라우저 id를 `visitor-a`로 고정했다([#164](https://github.com/hyeoniverse/MacFolio/pull/164))
- **날씨 (자동화 도구의 특성):** 휴대폰 화면에서 카드를 밀고 삭제 버튼을 누르는 시험이 CI에서만 실패했다. 처음에는 카드가 아직 삭제 버튼을 덮고 있다고 추정하고 수정했는데 다시 실패했다. CI와 같은 Linux 컨테이너에서 이벤트를 기록하니, 입력은 삭제 버튼에 도달해 `pointerdown`·`pointerup`까지 발생했지만 `click`이 발생하지 않았다. CDP로 보낸 터치 직후 몇백 ms 안에 다시 누르면 Linux Chrome이 `click`을 발생시키지 않는다. 사람의 입력에서는 생기지 않는 간격이라 해당 시험만 `click`으로 삭제하게 바꿨다. 첫 추정으로 수정한 것 중 "미는 동안에는 애니메이션 없이 손가락 위치를 바로 따라간다"는 올바른 변경이라 유지했다

## 돌아보며

**"서버가 중단되면?"이라는 질문을 구현한 뒤에 했다.** API 문서, 백업, 자동 배포의 방식이 모두 이 질문으로 정해졌지만, API 문서의 iframe 방식은 서버 헤더에 예외까지 추가하고 43분 만에 되돌렸고, 업타임 감시는 서버를 시작하고 일주일이 지나서야 생겼다. 감시는 서버를 처음 배포하는 시점에 함께 구성해야 한다.

**PR 크기가 문제의 크기를 정했다.** 트래픽 분석은 PR 네 개, 보안 점검과 리팩터링 계획은 항목마다 PR 하나로 진행해 범위를 다시 정할 필요가 없었다. 반대로 #129는 커밋 18개에 휴대폰 화면 일곱 곳이 함께 들어갔다. 하나의 수정이 다음 수정으로 이어지는 시점이 PR을 나눠야 하는 시점이다.

**"PR이 통과했다"와 "main이 통과한다"는 다른 사실이다.** 스택 PR의 base, 각자 통과한 PR의 조합, Docker Hub의 요청 한도, 취소된 CI 실행은 모두 PR 하나의 CI로는 드러나지 않는다. 머지한 뒤 main의 CI 결과까지 확인해야 머지가 끝난다.

**간헐적 실패는 재실행으로 통과시키지 않는다.** 세 건의 원인이 모두 달랐고, 날씨 시험은 첫 추정을 Linux에서 재현하기 전에 올려서 한 번 더 실패했다.
