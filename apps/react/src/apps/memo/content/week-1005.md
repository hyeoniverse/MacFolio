## 서버 운영 자동화: 백업, 자동 배포, 감시

10월 5일까지 블로그 글과 이미지는 메모리 1GB 무료 서버의 DB에만 있었다. 서버 디스크가 손상되면 글을 복구할 방법이 없는 상태였다. 그래서 매일 `pg_dump`로 DB 전체를 파일 하나로 내보내 Cloudflare R2(파일 저장소)에 올리고, 복원 스크립트로 그 파일을 실제로 되살려 검증하게 했다. 처음 실행한 백업은 1,007KB였고, 복원한 DB의 글 수는 원본과 같았다.

같은 날 API 자동 배포를 만들었다. GitHub Actions가 컨테이너 이미지를 빌드해 GHCR(GitHub Container Registry)에 올리면, 서버는 DB 백업, 컨테이너 교체, 헬스 체크 순서로 진행하고 실패하면 이전 이미지로 되돌린다. 헬스 체크는 새 서버의 `/health`가 정상 응답하는지 확인하는 단계다. 7일에는 GitHub Actions가 10분마다 외부에서 `/health`를 호출하는 업타임 감시를 추가했다.

![현재의 서버 메뉴](./images/day-1005-server-menu.jpg '메뉴 막대의 서버 메뉴. /health 응답 시간과 DB 상태를 막대 수로 표시한다 (시험용 가짜 API)')

같은 7일, main에서만 실패한 메뉴 시험 때문에 API 변경 하나가 배포되지 않았다. 배포 여부를 직전 push 대비 API 코드의 변경으로 판단했는데, API를 바꾼 실행은 시험 실패로 배포 단계에 가지 못했고 다음 실행에는 API 변경이 없었다. ==판단 기준을 서버에서 실행 중인 버전으로 바꿔==, 실패한 실행이 있어도 다음에 성공한 실행이 서버를 최신 버전으로 맞춘다([#118](https://github.com/hyeoniverse/MacFolio/pull/118)).

![API 배포 여부를 정하는 기준의 전후 비교](./images/week-1005-deploy-decision.svg '커밋 A의 API 변경은 시험 실패로 배포되지 않았다. 직전 push와 비교하면 커밋 B에서도 생략되고, 서버 실행 버전과 비교하면 B에서 A의 변경까지 배포된다')

## 없는 자산에 200을 주던 Worker

Vite는 빌드할 때 코드 파일 이름에 내용의 해시를 붙인다(예: `Memo-3f9a1c.js`). 내용이 바뀌면 이름도 바뀌므로, 브라우저가 이 파일을 오래 캐시해도 새 배포의 파일과 섞이지 않는다. 그래서 `/assets/*`에는 `Cache-Control: max-age=31536000, immutable`을 붙여 1년 동안 다시 요청하지 않게 했다.

10월 2일부터 배포 직후 메모를 열면 간헐적으로 "문제가 발생했습니다"가 표시되었다. 배포로 메모 코드 파일 이름이 바뀌면, 배포 전부터 열려 있던 페이지가 이전 이름의 파일을 요청하다 실패한다. 그날은 새로고침을 권하는 경고 대화상자로 대응했고, 근본 원인은 5일에 찾았다.

사이트는 존재하지 않는 주소에도 SPA 첫 화면인 `index.html`을 상태 코드 200으로 반환했다. 이 응답에도 `/assets/*`의 1년 캐시 헤더가 붙었다. 그래서 ==삭제된 코드 파일 주소를 요청한 브라우저는 그 이름으로 HTML을 1년 동안 캐시했다.== 없는 자산 주소에는 404를, 앱 주소(`/memo/<slug>` 등)에만 첫 화면을 반환하도록 Worker를 분리했다([#103](https://github.com/hyeoniverse/MacFolio/pull/103)).

![수정 전후에 같은 파일 이름을 세 시점에 요청한 결과](./images/asset-404-cache-timeline.svg '수정 전에는 첫 요청의 잘못된 HTML 응답이 1년 캐시에 고정되고, 수정 후에는 캐시 헤더 없는 404가 반환된다')

## React 밖으로 꺼낸 로직, desktop-core

10월 9일에는 새 기능 없이 구조만 바꿨다. 목표는 창 관리, 음악 재생, 메모 규칙 같은 판단 로직을 React와 브라우저 API에 의존하지 않는 패키지(`packages/desktop-core`)로 옮기는 것이었다. 그러면 같은 규칙을 서버(Node)에서도 쓸 수 있고, 브라우저 없이 단위 시험할 수 있다.

창 관리는 React Context의 `useState`에서 store(상태와 구독 함수를 가진 객체)로 옮기고, React는 `useSyncExternalStore`로 구독만 한다. 이 훅은 React 밖에 있는 상태가 바뀔 때 컴포넌트를 다시 그리게 하는 React 공식 API다. 음악 플레이어 store는 동작마다 `moved`·`stopped`·`restart` 같은 결과를 돌려주고, React는 그 결과에 따라 audio 요소만 제어한다.

폴더 3단계, 제목 100자 같은 메모 규칙은 desktop-core 한 곳에 정의한다. `package.json`의 `exports` 조건으로 Vite에는 TypeScript 소스를, 서버에는 빌드한 JS를 제공한다. 패키지 안에서 `react`나 `window`를 사용하면 타입 검사에서 실패한다. ==동작이 바뀌지 않았다는 것은 기존 E2E 통과와 화면 37장의 픽셀 비교로 확인했고==, desktop-core에 단위 시험 129개를 새로 붙였다.

![exports 조건으로 나눈 입구](./images/desktop-core-shared-rules-exports.svg 'source 조건을 켠 React 앱은 소스를, 서버는 dist를 읽는다')

## 보안 점검 목록을 항목별 PR로

10월 10일, 리팩터링·보안 점검 목록을 이슈 [#150](https://github.com/hyeoniverse/MacFolio/issues/150)으로 먼저 작성하고 항목마다 PR을 하나씩 열었다. 항목별로 나누면 PR마다 무엇을 막는 변경인지가 분명하고, 한 항목에서 문제가 생겨도 그 PR만 되돌리면 된다.

| 항목            | 조치                                                                                 |
| --------------- | ------------------------------------------------------------------------------------ |
| 의존성 취약점   | 6건(high 3건)을 `overrides`로 올리고 CI에 `pnpm audit --prod` 추가                   |
| 응답 헤더       | CSP 적용, 프로젝트 앱 iframe에 `sandbox` 적용                                        |
| API 경로        | 경로 64개의 권한과 본문 검증을 표 하나로 고정하는 e2e, 쓰기 경로 33개에 `@RateLimit` |
| 업로드한 사진   | EXIF·XMP를 방향만 남기고 삭제                                                        |
| 워크플로·저장소 | 액션 9개를 커밋 SHA로 고정, 저장소 전체 기록을 gitleaks로 검사                       |

CSP(Content Security Policy)는 페이지가 어느 출처의 스크립트·iframe·이미지를 불러올 수 있는지 응답 헤더로 제한하는 규칙이다. iframe의 `sandbox` 속성은 iframe 안의 페이지가 부모 페이지를 조작하거나 팝업을 여는 등의 동작을 기본으로 막는다.

EXIF는 카메라가 사진 파일 안에 함께 기록하는 메타데이터다. 촬영 기기, 촬영 시각, GPS 위도·경도가 들어 있을 수 있다. 그때까지 ==휴대폰 사진의 위도·경도가 공개되고 있었다.==

![업로드한 사진의 메타데이터 처리](./images/week-1005-exif-strip.svg '왼쪽은 휴대폰 사진에 기록되는 항목의 예. 저장할 때 방향(Orientation)만 남기고 GPS 좌표를 포함한 나머지를 삭제한다')

## API 형식을 contracts 하나로

10월 11일에는 리팩터링 계획의 1~3단계를 마쳤다. 순환 의존을 먼저 제거하고 큰 파일을 먼저 분할해야 타입을 옮길 때 수정 범위가 작아지므로, 계획 번호와 반대로 2 → 3 → 1 순서로 진행했다.

1단계의 중심은 `packages/contracts`다. zod는 데이터의 형식을 코드로 적은 스키마 객체를 만들고, 그 스키마로 실행 중에 값을 검사하는 라이브러리다. API 요청·응답 형식을 zod 스키마로 한 번 정의해, 서버는 `parse(Schema, body)`로 들어온 요청을 검사하고 화면은 같은 스키마에서 TypeScript 타입만 추론한다. 댓글부터 사이트 프로필까지 8개 도메인을 옮겼다.

![zod 스키마 하나를 서버는 실행 시 검사에, 화면은 컴파일 시 타입에 쓴다](./images/contracts-package-schema-dual.svg '서버는 스키마 객체를 실행하고, 화면은 추론한 타입만 가져간다')

옮기다가 ==두 곳에 따로 정의된 값이 이미 달라져 있던 것==을 찾았다. 메시지의 `mine`은 화면에서 선택 항목, 서버에서 필수 항목이었고, 연락 메일의 같은 한도에 오류 문구가 두 가지였다.

## 돌아보며

- "서버가 중단되면?"은 구현 전에 확인해야 한다. API 문서를 서버의 `/docs` iframe으로 만들었다가, 서버가 중단되면 문서도 볼 수 없다는 것을 알고 사이트 번들에 포함하는 방식으로 되돌렸다.
- PR이 통과한 것과 main이 통과하는 것은 다른 사실이다. 스택 PR 두 개가 main에 반영되지 않았고, 각자 통과한 두 PR이 합쳐지자 main이 실패했으며, 11일에는 main CI 실행 28회 중 18회가 취소되었다. 머지한 뒤 main의 CI 결과까지 확인해야 머지가 끝난다.
- 타이밍에 따라 결과가 달라지는 시험은 재실행으로 통과시키지 않는다. 메뉴 시험은 마우스가 정지한 채 제목만 이동하는 상황을 재현해 고쳤고, 간헐적 실패 세 건은 원인이 코드, 시험 데이터, 자동화 도구로 모두 달랐다.
- 큰 기능은 처음부터 나눈다. 트래픽 분석은 네 단계로 나눠 단계마다 머지했지만, 휴대폰 셸 PR [#129](https://github.com/hyeoniverse/MacFolio/pull/129)는 상태 표시줄·홈 화면과 앱 다섯 개의 변경을 함께 담았다.
