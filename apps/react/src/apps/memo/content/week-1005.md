## 서버 운영 자동화: 백업, 자동 배포, 감시

10월 5일까지 블로그 글과 이미지는 1GB 무료 서버의 DB에만 있었다. 매일 `pg_dump`를 Cloudflare R2에 올리고 복원 스크립트로 검증하게 했다. 처음 실행한 백업은 1,007KB였고, 복원한 DB의 글 수는 원본과 같았다. 같은 날 API 자동 배포를 만들었다. GitHub Actions가 이미지를 빌드해 GHCR에 올리면 서버는 DB 백업, 컨테이너 교체, 헬스 체크 순서로 진행하고 실패하면 이전 이미지로 되돌린다. 7일에는 GitHub Actions가 10분마다 외부에서 `/health`를 호출하는 업타임 감시를 추가했다.

같은 7일, main에서만 실패한 메뉴 시험 때문에 API 변경 하나가 배포되지 않았다. 배포 여부를 직전 push 대비 변경으로 판단했는데, API를 바꾼 실행은 시험 실패로 배포 단계에 가지 못했고 다음 실행에는 API 변경이 없었다. ==판단 기준을 서버에서 실행 중인 버전으로 바꿔==, 실패한 실행이 있어도 다음에 성공한 실행이 서버를 최신 버전으로 맞춘다([#118](https://github.com/hyeoniverse/MacFolio/pull/118)).

## 없는 자산에 200을 주던 Worker

10월 2일부터 배포 직후 메모를 열면 간헐적으로 "문제가 발생했습니다"가 표시되었다. 배포로 메모 코드 파일 이름(해시)이 바뀌면, 열려 있던 페이지가 이전 이름의 파일을 요청하다 실패한다. 그날은 새로고침을 권하는 경고 대화상자로 대응했고, 근본 원인은 5일에 찾았다. 사이트는 존재하지 않는 주소에도 `index.html`을 200으로 반환했고, `/assets/*`에는 1년 동안 재요청하지 않는 `immutable` 캐시 헤더가 붙어 있었다. 그래서 ==삭제된 코드 파일 주소를 요청한 브라우저는 그 이름으로 HTML을 1년 동안 캐시했다.== 없는 자산 주소는 404를, 앱 주소만 첫 화면을 반환하도록 Worker를 분리했다([#103](https://github.com/hyeoniverse/MacFolio/pull/103)).

## React 밖으로 꺼낸 로직, desktop-core

10월 9일에는 새 기능 없이 구조 변경 PR 6개만 머지했다. 창 관리는 React Context의 `useState`에서 store로 옮기고 React는 `useSyncExternalStore`로 구독만 한다. 음악 플레이어 store는 동작마다 `moved`·`stopped`·`restart` 같은 결과를 돌려주고, React는 그 결과에 따라 audio 요소만 제어한다. 폴더 3단계, 제목 100자 같은 메모 규칙은 desktop-core 한 곳에 정의하고, `package.json`의 `exports` 조건으로 Vite에는 TypeScript 소스를, 서버(Node)에는 빌드한 JS를 제공한다. 패키지가 `react`나 `window`를 사용하면 타입 검사에서 실패한다. ==동작이 바뀌지 않았다는 것은 기존 E2E 통과와 화면 37장의 픽셀 비교로 확인했고==, desktop-core에 단위 시험 129개를 새로 붙였다.

## 보안 점검 목록을 항목별 PR로

10월 10일, 점검 목록을 이슈 [#150](https://github.com/hyeoniverse/MacFolio/issues/150)으로 먼저 작성하고 항목마다 PR을 하나씩 열었다. 의존성 취약점 6건(high 3건)은 `overrides`로 올리고 CI에 `pnpm audit --prod`를 추가했고, 응답에 CSP를, 프로젝트 앱 iframe에 `sandbox`를 적용했다. API 경로 64개의 권한과 본문 검증은 표 하나로 고정하는 e2e로, 쓰기 경로 33개는 `@RateLimit`으로 묶었다. 업로드한 사진의 EXIF·XMP는 방향만 남기고 삭제했다. 그때까지 ==휴대폰 사진의 위도·경도가 공개되고 있었다.== 워크플로의 액션 9개는 커밋 SHA로 고정하고, 저장소 전체 기록을 gitleaks로 검사한다.

## API 형식을 contracts 하나로

10월 11일에는 리팩터링 계획의 1~3단계를 PR 18개로 마쳤다. 순환 의존을 먼저 제거하고 큰 파일을 먼저 분할해야 타입을 옮길 때 수정 범위가 작아지므로, 계획 번호와 반대로 2 → 3 → 1 순서로 진행했다. 1단계의 중심은 `packages/contracts`다. API 요청·응답 형식을 zod 스키마로 한 번 정의해 서버는 `parse(Schema, body)`로 검증하고 화면은 타입만 추론하며, 8개 도메인을 PR 8개로 옮겼다. 옮기다가 ==두 곳에 따로 정의된 값이 이미 달라져 있던 것==을 찾았다. 메시지의 `mine`은 화면에서 선택, 서버에서 필수였고, 연락 메일의 같은 한도에 문구가 두 가지였다.

## 돌아보며

- "서버가 중단되면?"은 구현 전에 물어야 한다. API 문서를 서버의 `/docs` iframe으로 만들었다가, 서버가 중단되면 문서도 볼 수 없다는 것을 알고 43분 만에 사이트에 포함하는 방식으로 되돌렸다.
- PR이 통과한 것과 main이 통과하는 것은 다른 사실이다. 스택 PR 두 개가 main에 반영되지 않았고, 각자 통과한 두 PR이 합쳐지자 main이 실패했으며, 11일에는 main CI 실행 28회 중 18회가 취소되었다. 머지한 뒤 main의 CI 결과까지 확인해야 머지가 끝난다.
- 타이밍에 따라 결과가 달라지는 시험은 재실행으로 통과시키지 않는다. 메뉴 시험은 마우스가 정지한 채 제목만 이동하는 상황을 재현해 고쳤고, 간헐적 실패 세 건은 원인이 코드, 시험 데이터, 자동화 도구로 모두 달랐다.
- 큰 기능은 처음부터 나눈다. 트래픽 분석은 PR 네 개로 나눠 단계마다 머지했지만, 휴대폰 셸 PR [#129](https://github.com/hyeoniverse/MacFolio/pull/129)는 커밋 18개에 상태 표시줄·홈 화면과 앱 다섯 개의 변경을 함께 담았다.
