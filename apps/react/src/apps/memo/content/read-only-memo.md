메모 앱(이 블로그)에 폴더 만들기, 이름 바꾸기, 끌어서 옮기기, 글 고정을 차례로 넣었다. 처음에는 누구나 자기 브라우저에서 정리해 볼 수 있게 했는데, 생각해 보니 이상했다. 블로그 글의 폴더와 순서는 글쓴이가 정하는 것이다. 방문자가 바꿀 일이 아니다.

## 고를 수 있는 방법

| 방법                                      | 좋은 점                                       | 문제                                                                                |
| ----------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------- |
| 누구나 자기 브라우저에서 정리한다 (원래)  | 할 일이 없다                                  | 블로그의 폴더를 방문자가 바꾸는 것이 이상하다. 관리자의 정리도 남에게 보이지 않는다 |
| 브라우저에서 비밀번호를 묻는다            | 서버가 없어도 된다                            | 비밀번호나 해시가 번들에 들어간다 (아래)                                            |
| Cloudflare Access 같은 앞단 인증          | 코드가 적다                                   | 정리 결과를 저장할 곳은 여전히 없다                                                 |
| 서버 로그인 + 서버 저장 (고름, 다음 단계) | 관리자를 서버가 가리고 결과가 모두에게 보인다 | 백엔드가 있어야 한다. 그때까지는 잠근다                                             |

## 비밀번호를 넣으면 안 되나

가장 쉬운 방법은 비밀번호를 물어보는 것이다. 하지만 이 사이트는 정적 파일이다. 비밀번호를 확인하는 코드가 브라우저에서 돌면, 비밀번호나 그 해시가 자바스크립트 번들에 그대로 들어간다. 개발자 도구를 열면 누구나 볼 수 있다.

설령 확인을 우회하지 못하게 만들어도, 편집한 결과는 그 사람 브라우저의 `localStorage`에만 남는다. 관리자가 정리한 폴더를 다른 방문자에게 보여 줄 방법이 없다. 결국 두 가지가 필요하다.

1. 누가 관리자인지 **서버가** 판단한다.
2. 정리한 결과를 **서버에** 저장한다.

둘 다 백엔드가 있어야 한다.

## 그래서 지금은 잠가 둔다

편집 기능은 모두 한 hook 뒤에 두었다. 백엔드가 붙기 전까지는 늘 `false`다.

```ts
/**
 * 편집은 관리자만 할 수 있다. 이 사이트는 정적 파일이라 브라우저 코드만으로는 관리자를 가릴 수 없으므로
 * 백엔드의 관리자 로그인이 붙기 전까지는 늘 false다.
 */
export function useCanEditMemo(): boolean {
	return false;
}
```

화면은 이 값 하나로 갈린다. `false`면 새 폴더 버튼과 ••• 메뉴가 없고, 끌어서 옮길 수도 없다. 예전에 방문자가 자기 브라우저에 만들어 둔 폴더와 순서도 더는 읽지 않고 지운다.

만들어 둔 편집 기능을 지우지 않은 이유도 있다. 관리자 로그인이 붙으면 이 hook이 서버의 로그인 상태를 돌려주기만 하면 된다. 편집 E2E 테스트도 지우지 않고 건너뛰기로 표시해 두었다가, 그때 다시 켠다.

![방문자가 보는 메모 앱](./images/memo-window.jpg '방문자가 보는 메모. 새 폴더 버튼과 ••• 메뉴가 없고, 글을 끌어 옮길 수 없다')

## 다음 단계

이 글을 쓴 날(9월 28일)에는 백엔드가 없었다. 백엔드에서 할 일은 이렇다.

- GitHub OAuth로 로그인하고, 정해 둔 계정만 관리자로 인정한다
- 폴더·순서·고정 상태를 서버에 저장하고, 쓰기 요청마다 서버가 권한을 다시 확인한다
- 같은 로그인으로 GitHub 앱에 보여 줄 고정 저장소도 설정에서 고른다

화면에서 버튼을 숨기는 것은 보안이 아니라 안내일 뿐이다. 실제로 막는 일은 서버가 한다.

## 다음 날 다시 열었다

![잠그고 다시 열기까지](./images/read-only-memo-timeline.svg '편집 기능을 hook 하나 뒤에 둔 덕분에, 다시 열 때는 그 한 줄만 바꿨다')

9월 29일에 NestJS·Prisma API 뼈대([PR #37](https://github.com/hyeoniverse/MacFolio/pull/37))와 GitHub 관리자 로그인([PR #38](https://github.com/hyeoniverse/MacFolio/pull/38))이 들어갔다. 같은 날 관리자 메모 편집 커밋(`0150b9be1`)에서 hook의 몸통이 바뀌었다.

```ts
// apps/react/src/apps/memo/useCanEditMemo.ts
export function useCanEditMemo(): boolean {
	return useAdmin().status === 'signed-in';
}
```

정리 내용은 이제 API에 저장되고, 방문자는 관리자가 정리한 대로 본다. 화면 쪽에서 바꾼 것은 이 한 줄과, 정리 내용을 `localStorage` 대신 API에서 읽고 쓰는 부분뿐이었다.

## 확인

- 잠근 커밋(`25d435e5d`)에서 편집 E2E를 `e2e/memo.spec.ts`에서 떼어 `e2e/memo-admin.spec.ts`(162줄)로 옮기고 건너뛰기로 두었다. 다시 열 때 그 파일을 켰다.
- 지금 `memo-admin.spec.ts`에는 "새로운 폴더를 만들고 지운다 (서버에 저장된다)", "글과 폴더를 끌어서 다른 폴더로 옮긴다", "폴더는 3단까지만 만들고 옮길 수 있다", "메모를 고정하면 맨 위 고정됨 묶음에 들어가고, 풀 수 있다", "방문자도 관리자가 정리한 대로 보지만, 편집할 수는 없다" 같은 시험이 있다.

## 남은 것·배운 것

- 만든 기능을 지우지 않고 잠그기만 한 것이 다음 날 그대로 쓰였다. 기능을 끌 때는 판단 지점을 하나(`useCanEditMemo`)로 모아 두면 다시 켜는 비용이 거의 없다.
- 버튼을 숨기는 것과 막는 것은 다르다. 다시 열 때도 hook은 "버튼을 보여 줄지"만 정하고, 저장이 되는지는 서버가 요청마다 세션으로 다시 본다.
