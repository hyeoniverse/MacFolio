CI(지속적 통합)는 코드를 main에 합칠 때마다 시험과 빌드를 자동으로 실행하는 과정이다. MacFolio의 CI는 시험이 모두 통과하면 이어서 API 서버와 사이트를 배포한다. 이날은 PR 미리보기의 작은 CORS 문제를 고친 것이 main에서만 실패하는 시험으로, 다시 API 배포 누락으로 이어졌고, 그 연결을 끝까지 추적했다. 이어서 서버 감시를 추가하고, 트래픽 분석을 만들고, 메일 앱에서 실제로 메일을 보내게 했다.

![10월 7일 작업 흐름](./images/day-1007-timeline.svg '메뉴·서버 수정, 서버 감시, 트래픽 분석과 메일 순으로 진행했다')

## CI와 배포: 하나의 수정에서 이어진 세 문제

문제 세 개가 꼬리를 물고 이어졌다.

```text
#115 PR 미리보기의 CORS 수정 (API 변경 포함)
  └→ main에서 메뉴 시험 실패 → 이 실행은 배포 단계까지 가지 못함
       └→ #116 메뉴 시험 수정 (API 변경 없음) → CI 통과, 그러나 API 배포 단계 생략
            └→ #115의 API 변경이 어느 실행에서도 배포되지 않음 → #118 배포 판단 기준 변경
```

### 1. PR 미리보기에서만 "연결할 수 없음"

PR을 열면 그 브랜치의 사이트가 `feat-app-menus-macfolio.hyeoniverse.workers.dev` 같은 별도 주소(미리보기)에 배포된다. 그런데 미리보기에서는 메뉴 막대의 서버 상태가 항상 "서버에 연결할 수 없음"이었다. 서버는 정상 동작 중이었다.

원인은 CORS였다. CORS(Cross-Origin Resource Sharing)는 브라우저가 다른 출처(도메인·포트·프로토콜 중 하나라도 다른 주소)의 응답을 페이지 코드에 넘겨도 되는지 서버의 허락을 확인하는 규칙이다. 페이지가 다른 출처에 요청하면 브라우저는 `Origin` 헤더에 페이지 주소를 실어 보내고, 서버가 응답에 `Access-Control-Allow-Origin` 헤더로 그 주소를 허락해야 응답 내용을 페이지에 넘긴다. API의 허용 목록(`CORS_ORIGINS`)에는 운영 사이트 주소만 있었으므로, 미리보기 페이지의 요청은 서버까지 도달하고도 브라우저에서 차단되었다.

![미리보기 페이지의 /health 요청이 서버에는 도달하지만 허용 헤더가 없어 브라우저가 응답을 넘기지 않는 과정](./images/day-1007-preview-cors.svg '서버는 정상 응답했지만 브라우저가 차단해 fetch가 실패했고, 화면은 이를 서버 중단으로 표시했다')

미리보기 주소는 브랜치마다 달라서 하나씩 등록할 수 없다. 그래서 허용 주소에 와일드카드 `*`를 쓸 수 있게 했다([#115](https://github.com/hyeoniverse/MacFolio/pull/115)). `*`는 점이 없는 이름 한 칸에만 일치한다. `https://*-macfolio.hyeoniverse.workers.dev`는 `https://feat-app-menus-macfolio.hyeoniverse.workers.dev`를 허용하지만, 다른 사람이 만든 `https://x.evil-macfolio.hyeoniverse.workers.dev`는 허용하지 않는다. 허용하지 않은 주소에서는 CORS 차단과 서버 중지를 구분해 "이 주소에서는 쓸 수 없음"으로 표시한다([no-cors 요청으로 CORS 차단과 서버 중지 구분하기](/memo/server-status-wifi#no-cors-요청으로-cors-차단과-서버-중지-구분)).

### 2. main에서만 실패한 메뉴 시험

#115를 머지하자 main에서 메뉴 막대 시험 하나가 실패했다. 시험은 '윈도우' 메뉴를 열었는데, 실제로는 '편집' 메뉴가 열렸다. 로컬과 PR에서는 통과한 시험이고, #115는 메뉴 코드를 건드리지 않았다.

원인은 메뉴 제목이 이동하는 타이밍이었다. 메뉴 막대는 메뉴 하나가 열려 있는 상태에서 마우스를 옆 제목으로 옮기면 그 메뉴로 전환한다. 이 전환을 마우스가 제목에 "진입"하는 이벤트로 처리하고 있었다. 그런데 Pointer Events 명세는 마우스가 움직이지 않아도 ==레이아웃이 바뀌어 마우스 아래의 요소가 달라지면 진입 이벤트를 발생시키라==고 정한다.

![마우스는 정지해 있고 메뉴 제목들이 오른쪽으로 밀리면서 마우스 아래 요소가 윈도우에서 편집으로 바뀌는 과정](./images/day-1007-layout-shift-hover.svg '마우스 좌표는 그대로다. 메모 앱이 편집·보기 메뉴를 등록하면서 제목들이 밀려, 그 자리에 편집이 온다')

| 순서 | 상황                                                                          |
| ---- | ----------------------------------------------------------------------------- |
| 1    | 시험이 마우스를 '윈도우' 위에 올린다                                          |
| 2    | 메모 앱이 열리며 편집·보기 메뉴가 등록되고, 메뉴 제목들이 오른쪽으로 이동한다 |
| 3    | 정지한 마우스 아래로 '편집' 제목이 이동해 온다                                |
| 4    | 브라우저는 이것도 마우스가 요소에 진입한 것으로 보고 진입 이벤트를 발생시킨다 |
| 5    | 메뉴가 '편집'으로 전환된다                                                    |

마우스를 올리는 시각과 메모 앱이 메뉴를 등록하는 시각 중 어느 쪽이 먼저인지는 실행 환경에 따라 달라진다. 로컬과 PR 실행에서는 이 순서가 나타나지 않았다. ==마우스가 실제로 움직인 경우에만 옆 메뉴로 전환하도록== 고쳤다([#116](https://github.com/hyeoniverse/MacFolio/pull/116)). 포인터 이동 이벤트의 이동 거리(`movementX`, `movementY`)가 0이 아닌 경우에만 전환한다. "마우스는 정지한 채 제목만 이동하는" 상황을 시험으로 직접 재현해, 고치기 전 빌드에서는 이 시험이 실패하는 것까지 확인했다. 자세한 내용은 [앱이 등록한 메뉴를 공통 메뉴와 병합하는 메뉴 막대 구조](/memo/menubar-menus)에 있다.

### 3. 생략된 API 배포

#116을 머지하자 CI는 통과했지만 서버는 여전히 이전 버전이었다. API 배포 단계가 생략되었다.

CI는 매번 API 이미지를 빌드하지 않는다. API 코드(`apps/api`, 공유 패키지 등)가 바뀐 커밋에서만 이미지를 빌드하고 배포한다. 문제는 "바뀌었다"를 판단하는 기준이었다.

![main의 세 커밋에서 직전 push와 비교하면 배포가 생략되고, 서버 실행 버전과 비교하면 #115의 변경까지 포함해 배포되는 비교](./images/day-1007-deploy-decision.svg '비교 기준을 직전 push에서 서버가 실제로 실행 중인 버전으로 바꾸자, 실패한 실행의 변경도 다음 성공한 실행에 포함되었다')

#116에는 API 변경이 없었다. #115에는 있었지만, 그 실행은 메뉴 시험 실패로 배포 단계까지 가지 못했다. 직전 push와 비교하면 #116 시점의 차이는 0이므로, ==#115의 API 변경은 어느 실행에서도 배포되지 않았다.==

| 항목             | 변경 전                                 | 변경 후                                        |
| ---------------- | --------------------------------------- | ---------------------------------------------- |
| 배포 판단 기준   | 직전 push 대비 API 코드 변경 여부       | **서버에서 실행 중인 버전** 대비 변경 여부     |
| 실패한 실행 이후 | 실패한 실행의 API 변경이 누락될 수 있음 | 다음에 성공한 실행이 서버를 최신 버전으로 맞춤 |

서버가 실행 중인 버전은 `/health` 응답의 `version`(`sha-1a2b3c4`처럼 커밋 해시로 만든 이미지 태그)으로 확인한다. CI는 이 커밋과 현재 커밋 사이에 API 경로의 차이가 있는지 확인하고, 있으면 배포한다([#118](https://github.com/hyeoniverse/MacFolio/pull/118)).

```bash
deployed=$(curl -fsS "$VITE_API_URL/health" | jq -r '.version // empty')
commit=${deployed#sha-}
git diff --quiet "$commit" "$GITHUB_SHA" -- apps/api packages/desktop-core packages/contracts ...
# 차이가 없으면(종료 코드 0) 배포 생략, 있으면 이미지 빌드와 배포
```

자세한 구조는 [자동 배포를 실제 서버에 걸기](/memo/api-auto-deploy)에 있다.

이 과정에서 로컬 API의 환경 변수도 정리했다. 개발용 값은 `.env`, 배포용 값은 `.env.production`에 보관한다. 로컬 프론트엔드 주소(`http://localhost:5173`)가 허용 목록에 없으면 서버 시작 시 경고를 출력한다. 미리보기에서 겪은 CORS 차단을 로컬에서는 시작 시점에 알 수 있다([#117](https://github.com/hyeoniverse/MacFolio/pull/117)).

## 서버 감시

9월 30일에 서버를 띄웠지만, ==서버가 중단되어도 사이트에 직접 접속하기 전에는 알 방법이 없었다.== 서버 안에서 서버를 감시하는 프로그램은 서버가 멈추면 함께 멈춘다. 그래서 감시는 서버 밖에서 해야 한다.

GitHub Actions는 `schedule` 이벤트로 cron 형식(`*/10 * * * *`은 10분마다)에 맞춰 작업을 실행할 수 있다. 이 예약 실행이 10분마다 API의 `/health`와 사이트를 호출해, `status`가 `ok`이고 `database`가 `up`인지 확인한다. 실패하면 그 실행이 실패로 기록되고 GitHub이 메일로 알린다. 배포 중의 짧은 중단으로 알림이 오지 않도록 30초 간격으로 세 번 더 시도한다.

| 항목          | 조치                                                                |
| ------------- | ------------------------------------------------------------------- |
| 가동 감시     | GitHub Actions가 10분마다 외부에서 `/health`와 사이트를 호출해 확인 |
| 컨테이너 로그 | 삭제되지 않고 계속 누적되던 로그를 컨테이너마다 30MB까지만 보관     |

컨테이너 로그는 Docker의 `json-file` 로그 드라이버에 `max-size: 10m`, `max-file: 3`을 지정했다. 파일 하나가 10MB가 되면 새 파일로 바꿔 기록하고, 세 개를 넘으면 가장 오래된 파일을 삭제하므로 컨테이너당 30MB를 넘지 않는다. 디스크가 작은 무료 VM에서 로그가 디스크를 채워 서버가 멈추는 일을 막는다. 자세한 구성은 [GitHub Actions 예약 실행으로 외부에서 API 서버 업타임 감시하기](/memo/server-uptime-and-logs)([#119](https://github.com/hyeoniverse/MacFolio/pull/119))에 있다.

## 트래픽 분석: PR 네 개로 분할

트래픽 분석은 방문자가 어떤 앱을 열고 어떤 글을 읽는지 집계하는 기능이다(이슈 [#102](https://github.com/hyeoniverse/MacFolio/issues/102)). 외부 분석 도구 대신 직접 만들었다. 규모가 큰 기능이라 처음부터 네 단계로 나누고, 단계마다 PR을 하나씩 열었다. 10월 4일에 프로젝트 페이지 작업 전체를 PR 하나에 담았던 것과 반대로 했다.

| 단계           | 내용                                                                                                     | PR · 글                                                                                                                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. API         | 쿠키 없이 일별 해시로 순방문자를 집계한다. IP 원문은 저장하지 않고, 90일이 지나면 일별 집계값만 보관한다 | [#120](https://github.com/hyeoniverse/MacFolio/pull/120) · [쿠키 없이 하루 해시로 순방문자를 집계하는 분석 API](/memo/analytics-api)                                                                   |
| 2. 수집        | 앱 열기·글 조회·외부 링크·체류 시간을 5초마다 sendBeacon으로 전송                                        | [#121](https://github.com/hyeoniverse/MacFolio/pull/121) · [sendBeacon으로 5초마다 묶어 보내는 방문 이벤트](/memo/analytics-collect)                                                                   |
| 3. 관리자 화면 | '활동 상태 보기' 앱, 표와 SVG 그래프                                                                     | [#122](https://github.com/hyeoniverse/MacFolio/pull/122) · [차트 라이브러리 없이 SVG 하나로 그리는 지표 그래프](/memo/analytics-activity-monitor)                                                      |
| 4. 공개        | 누구나 열 수 있되 공개 수치만, 상세·실시간은 관리자 전용. 글 조회수 추가                                 | [#123](https://github.com/hyeoniverse/MacFolio/pull/123) · [같은 경로에서 세션에 따라 응답 범위를 나누는 분석 요약 API](/memo/analytics-api#요약을-방문자에게-공개한다-세션에-따라-응답-범위를-나눈다) |

두 가지 용어를 풀어 둔다.

- **일별 해시**: 순방문자를 집계하려면 같은 사람을 식별해야 한다. 쿠키를 발급하는 대신 `HMAC(날짜 + IP + User-Agent, 비밀 키)`를 식별값으로 쓴다. HMAC은 비밀 키와 입력을 함께 해시해 고정 길이 값을 만드는 방법으로, 키 없이는 값에서 IP를 되돌릴 수 없다. 날짜가 입력에 들어가므로 같은 사람이 월요일에 두 번, 화요일에 한 번 방문하면 월요일 1명, 화요일 1명으로 집계되고, 날짜가 다른 기록끼리는 같은 사람인지 연결할 수 없다
- **sendBeacon**: 페이지를 닫는 중에도 브라우저가 전송을 끝까지 책임지는 요청 방법이다. 일반 `fetch`는 탭이 닫히면 취소될 수 있어, 체류 시간처럼 떠나는 시각에 보내야 하는 데이터는 이 방법으로 보낸다. 이벤트를 큐에 모아 5초마다, 그리고 탭이 숨겨지는 시각(`visibilitychange`가 `hidden`)에 전송한다

![현재의 활동 상태 보기](./images/day-1007-activity.jpg '활동 상태 보기의 현재 화면. 수치는 시험용 가짜 데이터다')

## 메일 앱에서 실제로 메일 발송

그전에는 메일 앱의 보내기 버튼이 `mailto:` 링크였다. `mailto:` 링크는 방문자 컴퓨터에 설치된 메일 프로그램을 여는 방식이라, 메일 프로그램을 설정하지 않은 방문자는 보낼 수 없었다. 서버가 메일 발송 서비스 Resend의 API로 직접 보내게 바꿨다(이슈 [#25](https://github.com/hyeoniverse/MacFolio/issues/25), [#125](https://github.com/hyeoniverse/MacFolio/pull/125)).

| 항목           | 변경 후                                              |
| -------------- | ---------------------------------------------------- |
| 발송           | 서버가 Resend로 발송                                 |
| 답장           | 보낸 사람 주소를 Reply-To 헤더에 넣어 바로 답장 가능 |
| 스팸 방지      | Cloudflare Turnstile과 하루 발송 상한                |
| 서버 설정 없음 | 이전처럼 메일 프로그램을 여는 방식으로 대체          |

메일의 `From`은 사이트 주소(`contact@hyeoniverse.com`)로 고정하고, 방문자가 입력한 주소(예: `visitor@example.com`)는 `Reply-To`에 넣는다. 받은 메일에서 답장을 누르면 `Reply-To` 주소로 보내지므로 답장은 방문자에게 간다. `From`에 방문자 주소를 넣으면 그 도메인의 발송 인증(SPF·DKIM)을 통과하지 못해, 받는 서버의 DMARC 검사에서 실패한다.

Turnstile은 Cloudflare의 사람 확인 도구로, 페이지가 받은 토큰을 서버가 Cloudflare에 다시 검증한다. 검증을 통과한 요청만 하루 상한(IP별 5통, 사이트 전체 50통)을 차감하므로, 봇의 요청이 실제 방문자의 한도를 소진하지 않는다. 자세한 구조는 [Resend API와 Turnstile로 서버에서 메일 발송하고 스팸 차단하기](/memo/contact-mail)에 있다.

`#115의`처럼 조사가 붙은 이슈 번호를 메모 태그로 인식하던 문제도 고쳤다([#124](https://github.com/hyeoniverse/MacFolio/pull/124)). 메모는 `#단어`를 태그로 인식하는데, `#115의`가 "115의"라는 태그가 되었다.

메뉴 막대 이슈 [#96](https://github.com/hyeoniverse/MacFolio/issues/96)은 [#113](https://github.com/hyeoniverse/MacFolio/pull/113)·[#114](https://github.com/hyeoniverse/MacFolio/pull/114)로 마무리해 닫았다. API 자동 배포 [#100](https://github.com/hyeoniverse/MacFolio/issues/100)은 배포 누락 문제를 고친 뒤에도 아직 열어 두었다.

## 첫 열흘을 돌아보며

첫 열흘의 마지막 날이라 열흘 전체를 함께 돌아봤다.

실패한 시험에서 배포 누락까지 추적했다. 수동으로 다시 배포하고 끝낼 수도 있었다. 대신 배포 여부를 서버의 실제 버전으로 판단하게 바꿔서, 실패한 실행이 여러 번 있어도 다음에 성공한 실행이 서버를 최신 버전으로 맞춘다.

> [!IMPORTANT] 타이밍에 따라 달라지는 시험
> 타이밍에 따라 결과가 달라지는 시험은 재실행으로 통과시키지 않고, 그 타이밍을 재현하는 시험을 만든다.

트래픽 분석은 10월 4일의 반성대로 PR 네 개로 나눴다. 단계마다 리뷰하고 머지해서, 한 단계에 문제가 생겨도 앞 단계에는 영향이 없었다.

서버 감시는 가장 늦게 추가했다. 서버를 띄우고 일주일이 지나서야 서버 중단을 감지할 수단을 갖췄다. 그 사이 서버가 중단되었다면 운영자보다 방문자가 먼저 장애를 겪었다.

> [!TIP] 서버를 처음 배포할 때
> 외부 감시(헬스 체크 예약 실행)와 로그 크기 제한을 첫 배포와 함께 구성한다.
