Dock 맨 왼쪽의 Finder는 아이콘만 있었다. 눌러도 아무 창도 열리지 않았다. macOS에서 가장 먼저 손이 가는 앱이 비어 있으니, 데스크톱을 흉내 낸 사이트로서는 아쉬웠다. 바탕화면에 폴더를 놓으려면 그 폴더를 열 창도 있어야 해서, Finder부터 만들었다. PR은 [#86](https://github.com/hyeoniverse/MacFolio/pull/86)이다.

![Finder 아이콘 보기와 목록 보기](./images/finder-app.jpg '왼쪽: 문서 폴더(아이콘 보기) / 오른쪽: 블로그 폴더(목록 보기)')

## 무엇을 파일로 보여 줄까

이 사이트에 진짜 파일 시스템은 없다. 대신 사이트에 이미 있는 것들을 폴더로 묶었다. 왼쪽 즐겨찾기가 그 네 묶음이다.

| 위치          | 안에 든 것                                | 열면                    |
| ------------- | ----------------------------------------- | ----------------------- |
| 문서          | 저장소의 README, CONTRIBUTING, docs/ 문서 | Finder 안에서 읽는다    |
| 프로젝트      | 포트폴리오 프로젝트 5개                   | Safari의 그 프로젝트 탭 |
| 블로그        | 블로그 글 (카테고리가 폴더)               | 메모에서 그 글          |
| 응용 프로그램 | 창이 있는 앱                              | 그 앱                   |

블로그 폴더는 글의 카테고리(`개발기/MacFolio/백엔드`)를 그대로 폴더 경로로 쓴다. 폴더의 수정일은 안에 든 가장 최근 글의 날짜다. 문서 폴더에는 빈 `이력서` 폴더도 하나 두었다. 저장소가 공개라 넣은 파일은 누구나 받을 수 있어서, 공개용 이력서를 정리하면 그때 넣는다.

트리를 만드는 일은 React와 떨어진 순수 함수(`files.ts`)로 두고 단위 시험을 붙였다. 화면은 이 트리를 그리기만 한다.

| 방법                                        | 좋은 점                           | 나쁜 점                                                      |
| ------------------------------------------- | --------------------------------- | ------------------------------------------------------------ |
| 실제 파일 목록(JSON)을 따로 만들어 둔다     | 진짜 파일 시스템처럼 자유롭다     | 글·프로젝트가 늘 때마다 목록을 손으로 고쳐야 한다            |
| GitHub API로 저장소 트리를 실행 중에 읽는다 | 늘 최신                           | 요청 한도·지연. 블로그 글·앱 같은 "파일 아닌 것"은 못 담는다 |
| **이미 있는 데이터에서 트리를 계산한다**    | 글·프로젝트·앱이 늘면 저절로 반영 | "파일"의 뜻이 위치마다 다르다(열면 하는 일이 다르다)         |

셋째를 골랐다. 위치마다 "열면 무엇을 하는가"만 다르게 두면, 트리 모양은 하나의 함수로 만들 수 있다.

## Finder처럼 동작하기

- **고르기와 열기**: 한 번 누르면 파랗게 고르고, 두 번 누르거나 Enter를 누르면 연다. 빈 곳을 누르면 고른 것이 풀린다.
- **키보드**: 방향키로 고른다. 아이콘 보기에서는 위아래가 한 줄씩 움직이는데, 한 줄에 몇 개가 들어가는지는 창 폭에 따라 다르다. 그래서 그리드의 실제 열 개수를 `grid-template-columns`의 계산값에서 읽는다. ⌘↑는 위 폴더, ⌘↓는 열기.
- **뒤로·앞으로**: 지나온 폴더와 문서를 기록해 두고 오간다. 브라우저 방문 기록처럼, 뒤로 간 다음 다른 곳으로 가면 앞쪽 기록은 버린다.
- **경로 막대**: 아래쪽에 지금 위치까지의 폴더가 보이고, 누르면 그 폴더로 간다.
- **이름으로 찾기**: 지금 폴더가 아니라 모든 위치에서 이름에 검색어가 들어간 항목을 모아 보여 준다.

## 저장소 문서를 Finder에서 읽기

![Finder에서 읽는 저장소 문서](./images/finder-doc.jpg '백엔드 설계 문서의 Mermaid 구성도도 그림으로 그린다')

문서는 빌드할 때 Vite의 `import.meta.glob`으로 묶는다. 저장소의 Markdown을 그대로 읽으니, 문서를 고치면 다음 배포에서 Finder의 문서도 함께 바뀐다.

GitHub에서 보던 문서를 그대로 보여 주려고 몇 가지를 맞췄다.

- **HTML**: README에는 가운데 정렬과 표를 위한 HTML이 섞여 있다. GitHub 앱의 README처럼 `rehype-raw`로 그리고 `rehype-sanitize`(GitHub와 같은 규칙)로 스크립트를 걸렀다.
- **링크**: 다른 문서를 가리키는 상대 링크(`docs/deployment.md`)는 Finder 안에서 그 문서를 연다. 묶지 않은 파일이나 `#제목` 링크는 GitHub의 그 파일을 새 탭에서 연다.
- **그림**: `docs/images`의 그림은 함께 묶고, 그 밖의 그림은 GitHub의 원본 주소에서 불러온다.
- **Mermaid**: 백엔드 설계 문서의 구성도와 ERD는 Mermaid 코드 블록이다. Mermaid 라이브러리는 커서, 그림이 있는 문서를 처음 열 때만 불러온다(`import('mermaid')`). 첫 화면 번들은 그대로다.

## 다른 앱에 "이걸 열어 줘" 하기

글을 열면 메모가, 프로젝트를 열면 Safari가 그 항목을 보여 줘야 한다. 그런데 메모는 처음 열 때 코드를 불러오는 앱이라, Finder가 요청하는 순간에는 아직 화면에 없을 수 있다.

그래서 작은 저장소(`openRequest.ts`)에 요청을 남겨 두고, 받는 앱이 마운트되면서 남은 요청을 꺼내 처리하게 했다. 이미 열려 있으면 구독으로 바로 받는다. Safari는 닫아 둔 탭이면 다시 열어 준다.

```ts
// apps/react/src/shared/lib/openRequest.ts
export const requestOpen = (app: LinkedApp, id: string) => openRequestStore.setState({ request: { app, id } });

export function useOpenRequest(app: LinkedApp, onOpen: (id: string) => void) {
	// …
	useEffect(() => {
		const take = () => {
			const { request } = openRequestStore.getState();
			if (request?.app !== app) return;
			openRequestStore.setState({ request: null });
			handler.current(request.id);
		};
		take(); // 마운트될 때 남아 있던 요청
		return openRequestStore.subscribe(take); // 이미 열려 있으면 바로
	}, [app]);
}
```

![Finder가 requestOpen으로 요청을 남기고 openApp으로 창을 연다. 메모가 마운트되며 useOpenRequest로 꺼낸다](./images/finder-app-open-request.svg '요청은 남아 있다가 받는 앱이 꺼내 가면 지운다')

`window.dispatchEvent` 같은 이벤트로 보내는 방법도 있었지만, 이벤트는 그 순간 듣는 쪽이 없으면 사라진다. 메모가 아직 코드를 불러오는 중이면 요청을 잃는다. 값으로 남겨 두는 저장소가 이 경우에 맞았다. 주소(`/memo/<글>`)를 바꾸는 방법은 메모에는 맞지만, Safari의 탭이나 다른 앱에는 주소 규칙이 없어 일반적이지 않았다.

## 클릭이 사라지던 링크

만들다가 문서 안 링크를 눌러도 아무 일이 일어나지 않는 문제가 있었다. 원인은 react-markdown에 넘기는 컴포넌트였다. 렌더링마다 새 함수를 만들어 넘기니, react-markdown이 링크 요소를 매번 새로 만들었다.

창을 누르면 그 창이 맨 앞으로 오면서 다시 그려진다. 그래서 마우스를 누른 링크와 뗀 링크가 서로 다른 요소가 되고, 클릭 이벤트가 생기지 않았다. 컴포넌트를 `useMemo`로 문서와 화면 모드가 바뀔 때만 새로 만들게 하니 해결됐다.

````tsx
// apps/react/src/apps/finder/DocView.tsx
// 렌더링마다 새 컴포넌트를 넘기면 react-markdown이 요소를 다시 마운트해서,
// 창을 누를 때(맨 앞으로 오며 다시 그린다) 링크가 바뀌어 클릭이 사라진다. 문서·화면 모드가 바뀔 때만 새로 만든다
const components = useMemo<Components>(
	() => ({
		a: ({ node: _node, href = '', children, ...props }) => {
			const target = resolveLink(path, href, DOC_SET);
			// 묶은 문서면 Finder 안에서, 아니면 GitHub를 새 탭으로
		},
		img: /* docs/images면 묶은 그림, 아니면 GitHub 원본 주소 */,
	}),
	[path, dark]
);
``` 메모 앱에도 같은 이유로 컴포넌트를 바깥 상수로 둔 주석이 있었는데, 그걸 다시 밟은 셈이다.

## 휴대폰에서는 '파일'

휴대폰에서는 iOS처럼 '파일'이라는 이름으로 홈 화면에 둔다. 창이 좁으면(컨테이너 쿼리 600px 이하) 왼쪽 사이드바를 접고, 위치를 위쪽에 한 줄로 늘어놓는다.

## 확인

- 단위 시험 `files.test.ts`: "즐겨찾기 위치: 문서, 프로젝트, 블로그, 응용 프로그램", "문서: 폴더(이력서 자리)가 위에, 문서는 이름순", "블로그: 카테고리를 폴더로, 폴더가 위에, 글은 최신순, 폴더 수정일은 가장 최근 글", "프로젝트와 앱", "위치에서 항목까지의 폴더들", "위치 전체에서 이름으로 (대소문자 무시)". `repoDocs.test.ts`는 문서 안 링크를 Finder 안에서 열지 GitHub로 보낼지 가르는 규칙을 본다.

## 남은 것과 배운 것

다음 차례는 바탕화면이다. Finder의 트리에 '데스크톱' 폴더를 더하고, 그 안의 항목을 바탕화면에 아이콘으로 놓을 생각이다. (뒤에 [바탕화면 아이콘](/memo/desktop-icons)으로 했다. 빈 이력서 폴더도 [Finder에서 PDF와 그림 열기](/memo/finder-files)에서 채웠다.)

배운 것: 앱끼리 "이걸 열어 줘"를 주고받을 때, 받는 쪽이 아직 없을 수 있다는 것을 먼저 생각해야 한다. 이벤트는 사라지고 값은 남는다. 그리고 react-markdown의 `components`는 참조가 바뀌면 요소를 새로 만든다. 같은 실수를 두 번 밟고 나서, 이런 객체는 바깥 상수나 `useMemo`로 두는 것을 규칙으로 삼았다.
````
