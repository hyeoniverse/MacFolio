[앞 글](/memo/newpick-v1-start)에서 정리했듯 뉴픽의 프론트는 시작 열이틀 만에 Vite에서 Next.js(App Router)로 바뀌었다. 프론트 팀 모두 Next.js로 서비스를 만드는 것은 처음이었다. 이 글은 6주 동안 노션 트러블슈팅 DB에 남긴 프론트 문제 12건 중, 서버 렌더링과 관련된 것들을 정리한다. 각 절 끝에는 v2에서 같은 코드를 다시 만났을 때의 이야기를 붙였다.

| 문제                              | 날짜   | 원인                                               |
| --------------------------------- | ------ | -------------------------------------------------- |
| 새로고침마다 스타일이 빠진 화면   | 1/7    | styled-components가 서버 HTML에 스타일을 넣지 않음 |
| 헤더 Hydration 오류               | 1/26   | 서버와 브라우저가 로그인 상태를 다르게 그림        |
| `<Link>` 안의 버튼                | 1월 말 | `<a>` 중첩                                         |
| 배포 빌드의 `PageProps` 타입 오류 | 2/2    | Next 15에서 `params`가 Promise로 바뀜              |
| AI가 만든 HTML 렌더링             | 2/1    | `dangerouslySetInnerHTML`의 XSS                    |

## 새로고침마다 스타일이 빠진 화면

Next.js로 옮긴 날, 새로고침할 때마다 아래 화면이 잠깐 보였다. 스타일이 하나도 적용되지 않은 HTML이다.

![스타일 없는 화면](./images/newpick-v1-nextjs-flicker.jpg '2025년 1월 7일 캡처. 새로고침하면 잠깐 이 화면이 보이고 스타일이 적용됐다')

styled-components는 컴포넌트가 실행될 때 스타일을 만들어 `<style>`에 넣는다. 서버 렌더링 결과 HTML에는 그 스타일이 없으므로, 브라우저는 스타일 없는 HTML을 먼저 그리고 JavaScript가 실행된 뒤에야 스타일을 입힌다.

해결은 Next.js 공식 문서의 방법이었다. 서버 렌더링 중 만들어진 스타일을 모아 HTML에 함께 넣는 레지스트리(`lib/registry.tsx`, `ServerStyleSheet` + `useServerInsertedHTML`)를 루트 layout에서 감싼다. 레지스트리 파일은 Next.js로 옮긴 커밋(1월 7일 02시)에 이미 있었는데 같은 날 낮에 이 화면을 캡처했으니, 처음에는 제대로 연결되지 않았던 것으로 보인다. 최종 발표에서는 이 부분을 `_document.tsx`로 설명했는데, 그것은 Pages Router의 방식이고 실제 코드는 App Router용 레지스트리였다.

styled-components는 App Router에서 클라이언트 컴포넌트에서만 쓸 수 있다. 그래서 스타일을 가진 컴포넌트는 모두 `'use client'`가 되어야 했다. 0단계 기준선을 잴 때 `.tsx` 90개 중 65개가 `'use client'`였고, 그중 20개는 스타일 때문에만 붙어 있었다.

## 헤더 Hydration 오류

1월 26일 새벽, 헤더에서 Hydration 오류가 났다.

![Hydration 오류](./images/newpick-v1-nextjs-hydration.jpg '− 줄이 서버 HTML, + 줄이 브라우저. 서버는 로그인 버튼을, 브라우저는 로딩 스피너를 그렸다')

Next.js의 오류 화면에서 `−` 줄은 서버 HTML, `+` 줄은 브라우저의 첫 렌더링이다. 서버는 로그인 버튼을, 브라우저는 로딩 스피너를 그렸다. 헤더는 로그인 상태에 따라 세 가지(스피너, 로그인 버튼, 프로필)를 그리는데, 서버와 브라우저에서 로그인 상태의 초기값이 달랐기 때문이다.

같은 날 두 번 고쳤다.

| 시각  | 방법                                                             | 결과                                            |
| ----- | ---------------------------------------------------------------- | ----------------------------------------------- |
| 05:44 | `next/dynamic`의 `ssr: false`로 헤더를 서버에서 그리지 않음      | 오류는 사라지지만 헤더 전체가 늦게 나타남       |
| 11:53 | `useMount`로 마운트 전에는 상태에 따라 갈리는 부분을 그리지 않음 | 헤더 틀은 서버에서 그리고, 로그인 영역만 나중에 |

두 방법 모두 "서버와 브라우저가 다르게 그릴 부분을 서버에서 그리지 않는다"는 같은 생각이다. 오류는 사라지지만, 첫 화면의 로그인 영역은 매번 비어 있다가 채워진다.

> **v2에서**: 이 문제는 [로그인 상태가 깜빡이지 않는 정적 페이지](/memo/newpick-static-auth-hint)에서 다른 방향으로 풀었다. 서버가 그리지 않는 대신, 로그인 버튼과 프로필 자리를 둘 다 그리고, `<head>`의 한 줄 스크립트가 로그인 표시 쿠키를 읽어 CSS로 하나만 보여 준다. v1의 캡처처럼 서버와 브라우저가 서로 다른 버튼을 그리는 상황이 아예 생기지 않는다.

## `<Link>` 안의 버튼

공통 `Button`(styled-components)을 링크로 쓰려고 `<Button as="a">`를 `<Link>` 안에 넣었더니 `<a>` 안에 `<a>`가 생겨 Hydration 오류가 났다. 버튼 안에 `<Link>`를 넣으면 `<button>` 안에 `<a>`가 되어 HTML 표준에 어긋난다. 노션에 세 가지를 비교해 정리했다.

| 구조                                      | 판단                                             |
| ----------------------------------------- | ------------------------------------------------ |
| `<Link>` 안에 `<Button>` (버튼 태그 유지) | 채택. 클라이언트 이동과 prefetch가 그대로 동작   |
| `<Button>` 안에 `<Link>`                  | 지양. `<button>` 안의 `<a>`, 새 탭 열기가 불안정 |
| `onClick` + `router.push()`               | 가능하지만 ⌘+클릭, 우클릭 새 탭 열기가 안 됨     |

## 배포 빌드에서만 나는 타입 오류

2월 2일, Vercel 배포를 앞두고 `npm run build`가 실패했다.

```text
Type error: Type 'PageParams' does not satisfy the constraint 'PageProps'.
  Types of property 'params' are incompatible.
    Type '{ slug: string; }' is missing the following properties from type 'Promise<any>'
```

Next.js 15부터 동적 경로의 `params`가 Promise다. 개발 서버(`next dev`)는 이 타입을 검사하지 않아 그동안 몰랐고, 프로덕션 빌드에서 처음 드러났다. `params: Promise<{ slug: string }>`로 바꾸고 `await params`로 읽어 그날 밤 고쳤다.

CI가 없었던 것이 원인이다. 빌드를 PR마다 돌렸다면 처음 그 페이지를 만든 날 알았을 것이다. v2는 [0단계](/memo/newpick-v2-start)에서 CI부터 붙였다.

## AI가 만든 HTML 렌더링

뉴스레터 본문은 AI가 만든 HTML이다. 무료 체험 모달을 만들면서(2월 1일) `dangerouslySetInnerHTML`이 XSS에 위험하다는 것을 알고, DOMPurify로 정리한 뒤 `html-react-parser`로 변환하는 방법을 노션에 정리하고 적용했다.

> **v2에서**: 같은 HTML을 보여 주는 **기사 상세 페이지에는 적용되지 않았다**. 체험 모달만 고치고, 같은 데이터를 쓰는 다른 화면을 찾아보지 않았다. v2 1단계에서 공통 `sanitizeHtml`로 두 화면을 모두 막았다([인증 없이 열려 있던 API 다섯 개](/memo/newpick-security)의 XSS 절).

## 마감 주: 서버 컴포넌트로 나누기

1월 29일 프론트엔드 코드 리뷰 회의록에는 "page 컴포넌트는 가급적 SSR을 하되, `use client`는 써야 할 때 쓴다"는 항목이 있다. 그때까지는 모든 화면이 클라이언트 컴포넌트였고 데이터도 브라우저에서 React Query로 가져왔다.

2월 1일 새벽, 초기 데이터를 서버에서 불러오도록 바꿨다. page를 서버 컴포넌트로 두고 데이터가 필요한 UI만 클라이언트 컴포넌트로 나눴다. 그리고 2월 3일 아침, 루트 layout에 이 두 줄을 넣었다. 커밋 메시지는 "루트 레이아웃 컴포넌트 동적 렌더링으로 전환"뿐이고 이유는 남아 있지 않다. 루트 layout이 쿠키로 로그인 사용자를 읽게 된 직후였다.

```ts
export const dynamic = 'force-dynamic';
export const revalidate = 0;
```

> **v2에서**: 이 두 줄이 모든 페이지를 요청마다 렌더링하게 만들었다. 0단계 기준선의 "모든 페이지가 동적(ƒ)"이 이것이다. v2에서 [요청 경로를 정리하며](/memo/newpick-api-client) 지웠고, [표시 쿠키로 정적 빌드](/memo/newpick-static-auth-hint)를 하면서 홈·소개·마이페이지를 정적으로 만들었다. 내가 넣은 코드를 내가 지운 셈이다.

## 남은 것·배운 것

- 당시의 해결은 대부분 "서버에서 그리지 않기"였다. 오류는 사라졌지만 Next.js를 고른 이유였던 서버 렌더링을 조금씩 포기한 것이기도 했다.
- 노션 트러블슈팅 DB에 링크만 남긴 항목이 많다. 무엇을 바꿨는지는 커밋에만 있었고, 이 글도 커밋을 다시 찾아 확인했다. 해결 방법은 링크가 아니라 바꾼 코드로 남겨야 했다.
- styled-components는 마감 직후 회의에서 "CSS로 옮기기"를 개인 과제로 적었다. 그 일은 v2의 4단계(#10, Tailwind 전환)로 남아 있다.
