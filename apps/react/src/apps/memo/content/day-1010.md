## main에 반영되지 않은 스택 PR

### 배경: PR의 base 브랜치

GitHub의 PR(Pull Request)은 "이 브랜치의 변경을 저 브랜치에 합쳐 달라"는 요청이다. 합칠 대상 브랜치를 base, 변경을 담은 브랜치를 head라고 한다. 머지 버튼을 누르면 변경은 base 브랜치에만 들어간다. base가 main이 아니면 main은 바뀌지 않는다.

스택 PR(stacked PR)은 PR을 계단처럼 쌓는 방식이다. 예를 들어 기능 A의 브랜치 위에서 기능 B를 개발하면, B의 PR은 base를 A의 브랜치로 지정한다. 그래야 PR 화면에 B의 변경만 표시된다. 리뷰하기는 쉽지만 머지 순서를 지켜야 한다. 위의 PR부터 아래 브랜치로 머지하고 마지막에 맨 아래 PR을 main에 머지해야 모든 변경이 main에 도달한다.

### 무슨 일이 있었나

전날 밤 블로그 폴더 PR [#143](https://github.com/hyeoniverse/MacFolio/pull/143)을 main에 머지했다. 그 브랜치 위에 휴지통 앱 [#145](https://github.com/hyeoniverse/MacFolio/pull/145)를, 다시 그 위에 서버 파일 관리 [#146](https://github.com/hyeoniverse/MacFolio/pull/146)을 쌓아 두었다. 30여 초 뒤 두 PR을 머지했는데, 둘 다 **main이 아니라 아래 브랜치에** 들어갔다.

| PR   | base 브랜치   | 머지 결과                                     |
| ---- | ------------- | --------------------------------------------- |
| #143 | main          | main에 반영                                   |
| #145 | #143의 브랜치 | #143 브랜치에 들어감. 이 브랜치는 이미 머지됨 |
| #146 | #145의 브랜치 | #145 브랜치에 들어감                          |

맨 아래 PR(#143)을 먼저 머지했으므로 #143의 브랜치는 이미 역할이 끝난 상태였다. 그 위에 머지한 변경은 main으로 이어지는 PR이 없어 main까지 도달하지 않았다.

![스택 PR의 머지 대상](./images/day-1010-stacked-pr.svg '#145와 #146은 base가 아래 PR의 브랜치라, 머지해도 main에 반영되지 않았다')

같은 변경을 main을 base로 한 PR로 다시 올리고, 리뷰에서 나온 수정을 더해 머지했다([#147](https://github.com/hyeoniverse/MacFolio/pull/147)). 전날 음악 PR도 스택 구조였지만 위의 PR을 먼저 머지해서 변경이 모두 main에 도달했다.

> [!IMPORTANT] 이후의 규칙
> 이후로는 PR을 쌓지 않고 항상 main을 base로 연다.

### 휴지통의 용도 변경

처음에는 이 사이트를 만들며 **폐기한 기능**을 모아 보여 주는 곳으로 만들었다. #147에서 **실제로 비울 수 있는 데이터**만 표시하는 곳으로 바꿨다. 폐기한 기능 목록은 방문자에게 쓸모가 없고, 휴지통이라는 이름과도 맞지 않았다. 지금은 다음 두 가지를 표시한다.

- 방문자: 이 사이트가 브라우저의 localStorage에 저장한 값. 예를 들어 바꾼 배경화면 설정이나 최근 검색어를 항목별로 확인하고 삭제한다
- 관리자: 서버에 업로드했지만 어느 글의 본문에도 `/files/<id>` 주소가 없는 파일. 글을 고치며 이미지를 교체하면 이전 이미지가 이 목록에 남는다

자세한 내용은 [휴지통 앱](/memo/bin-app)과 [참조되지 않는 파일 찾기](/memo/server-files-cleanup)에 있다.

### 서버 자원을 모니터링하는 이유

MacFolio의 API는 Oracle Cloud의 Always Free(무료) 가상 머신에서 동작한다. Oracle은 무료 인스턴스가 ==7일 동안 CPU·네트워크·메모리 사용률이 낮으면 유휴 자원으로 판단해 회수할 수 있다.== 공식 문서의 기준은 다음과 같다.

| 항목            | 유휴로 판단하는 기준(7일 동안)    |
| --------------- | --------------------------------- |
| CPU             | 95번째 백분위수 사용률이 20% 미만 |
| 네트워크        | 사용률 20% 미만                   |
| 메모리(A1 계열) | 사용률 20% 미만                   |

95번째 백분위수는 측정값을 작은 것부터 늘어놓았을 때 95% 지점의 값이다. 1분마다 측정하면 7일 동안 10,080개의 값이 생기고, 그중 큰 쪽 504개를 제외한 최댓값이 이 수치가 된다. 잠깐 사용률이 치솟아도 기준을 넘지 못하는 이유다. 사용률이 기준 아래로 떨어지는 것을 미리 알기 위해 측정값을 DB에 저장하고, 임계값을 넘거나 내려가면 메일을 보낸다.

요금 조회(#153)는 Oracle Cloud API를 호출할 때 필요한 요청 서명을 직접 만든다. OCI의 요청 서명은 요청 시각·대상 경로 같은 헤더 값을 API 키(개인 키)로 서명해 `Authorization` 헤더에 넣는 방식이고, OCI SDK를 의존성에 추가하지 않고 이 과정을 구현했다. 배터리 메뉴(#155)는 이 측정값을 메뉴 막대에 표시한다.

![배터리 메뉴](./images/day-1010-battery.jpg '방문자가 메뉴 막대의 배터리를 누른 화면. 최근 7일 방문이 이전 7일보다 증가한 비율만큼 채워진다 (시험용 데이터)')

좋아요와 인기글 점수 계산은 [좋아요와 인기글](/memo/memo-likes-popular)에 정리했다.

### 먼저 알아 둘 용어

<details>
<summary>표에 나오는 보안 용어</summary>

- **XSS(교차 사이트 스크립팅)**: 공격자가 만든 스크립트가 이 사이트의 페이지 안에서 실행되는 공격이다. 예를 들어 댓글에 `<script>`를 넣었는데 그대로 렌더링되면, 그 스크립트가 방문자의 쿠키나 화면을 조작할 수 있다.
- **CSP(Content Security Policy)**: 페이지가 어느 출처의 스크립트·이미지·iframe을 불러올 수 있는지 서버가 응답 헤더로 지정하는 규칙이다. 예를 들어 `script-src 'self'`면 같은 사이트의 스크립트 파일만 실행하고, 본문에 끼워 넣은 스크립트는 브라우저가 거부한다.
- **iframe `sandbox` 속성**: iframe 안의 페이지에서 스크립트 실행, 상위 창 이동 같은 권한을 기본으로 모두 막고, 값으로 적은 권한만 다시 허용한다. MacFolio의 프로젝트 앱은 `allow-scripts`, `allow-forms`, `allow-popups` 등은 허용하고 `allow-top-navigation`은 허용하지 않는다. 그래서 안의 사이트가 `window.top.location`을 바꿔도 MacFolio 전체가 다른 주소로 넘어가지 않는다.
- **요청 제한(rate limit)**: 같은 IP가 정해진 시간 안에 보낼 수 있는 요청 수를 제한한다. MacFolio는 1분 단위로, 예를 들어 댓글·메시지·메일은 IP마다 1분에 5회까지 받고 넘으면 `429 Too Many Requests`로 응답한다.
- **EXIF·XMP**: 사진 파일 안에 함께 저장되는 메타데이터다. 촬영 기기, 촬영 시각, GPS 위도·경도가 들어 있을 수 있다.
- **Turnstile**: Cloudflare의 봇 검증 위젯이다. 사람이 보낸 요청인지 확인한 토큰을 서버가 Cloudflare에 다시 조회해 검증한다.
- **커밋 SHA 고정**: GitHub Actions 워크플로에서 `actions/checkout@v4`처럼 태그로 지정한 액션은 태그가 다른 커밋으로 옮겨지면 다른 코드가 실행된다. `@<40자리 커밋 해시>`로 지정하면 그 코드만 실행한다.
- **gitleaks**: 저장소의 커밋 기록에서 API 키·비밀번호 형태의 문자열을 찾는 도구다.

</details>

### Tunnel 뒤의 요청 제한과 TRUST_PROXY

요청 제한(#162)을 적용하기 전에 서버 설정을 확인했다. 요청 제한은 IP 단위로 집계한다. 그런데 MacFolio의 API는 Cloudflare Tunnel 뒤에 있어서, API 입장에서 모든 요청은 터널 프로그램(cloudflared)이 보낸 것으로 보인다. 실제 방문자의 IP는 `X-Forwarded-For` 헤더에 담겨 온다. 이 헤더는 프록시가 "원래 요청을 보낸 클라이언트의 IP"를 다음 서버에 전달하려고 붙이는 표준 관례다.

다만 헤더는 누구나 위조할 수 있으므로, 서버는 설정으로 허락한 경우에만 이 헤더를 읽는다. MacFolio에서는 `TRUST_PROXY=1`이 "바로 앞 프록시 1단계가 붙인 값을 믿는다"는 설정이다.

![TRUST_PROXY 설정에 따라 요청 제한이 집계하는 IP](./images/day-1010-trust-proxy.svg '값이 없으면 모든 방문자가 터널 IP 하나로 집계되어 한 사람의 요청이 모두의 한도를 소진한다. 값이 1이면 X-Forwarded-For의 방문자 IP로 따로 집계한다. IP 주소는 예시 값이다')

> [!WARNING] 값이 없으면 모두가 차단된다
> `TRUST_PROXY`가 없으면 모든 요청이 터널의 IP 하나로 집계되어, 방문자 한 명이 한도를 넘으면 모두가 차단된다. 서버의 값은 이미 `1`이어서 바꾸지 않았다.

```bash
cd ~/deploy && grep TRUST_PROXY api.env   # TRUST_PROXY=1
```

### 각자 통과한 두 PR이 합쳐지자 main이 실패했다

경로 표 시험(#160)은 API의 모든 경로를 표 한 장에 나열하고, 경로마다 "관리자만 허용하는가", "본문을 검증하는가"를 적어 둔다. 코드에 경로가 새로 생겼는데 표에 없으면 시험이 실패한다. 새 경로를 만들면서 권한 확인을 빠뜨리는 실수를 막기 위한 장치다.

이 표는 좋아요를 추가하기 전의 API 경로로 만들었다. 그 사이 좋아요(#158)를 먼저 main에 머지해서 경로가 6개 늘었다. ==두 PR은 각자 CI를 통과했지만, main에서 합쳐지자 "표에 없는 경로"로 실패했다.== CI는 PR 브랜치의 코드만 검사하므로, 다른 PR이 먼저 머지되어 생긴 조합은 검사하지 않는다.

![각자 통과한 두 PR이 main에서 합쳐져 실패하는 과정](./images/day-1010-merge-skew.svg '#158은 경로를 추가했고, #160은 그 경로가 없던 시점의 코드로 표를 만들었다. 두 변경은 main의 머지 커밋에서 처음 만났다')

수정 PR([#166](https://github.com/hyeoniverse/MacFolio/pull/166))을 열었는데, 같은 표를 고치던 요청 제한 PR(#162)이 해당 경로까지 포함해 먼저 머지되어 #166은 닫았다.

## 간헐적으로 실패하는 시험 세 건

같은 코드로 다시 실행하면 통과하기도 하고 실패하기도 하는 시험을 간헐적 실패(flaky test)라고 한다. 이날 세 건이 있었고, 증상은 모두 "가끔 실패"였지만 ==원인은 서로 달랐다.==

| 시험      | 원인 분류          | 원인                                                                                         | 조치                                                                                                           |
| --------- | ------------------ | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 메모 편집 | 코드의 버그        | 제목에서 Enter를 누르는 시점에 지연 로딩하는 편집기가 아직 없어, 이후 입력이 제목에 들어갔다 | Enter 입력을 기억했다가 편집기가 준비되면 초점 이동 ([#148](https://github.com/hyeoniverse/MacFolio/pull/148)) |
| 메시지    | 시험 데이터의 우연 | 무작위로 생성한 이름이 우연히 겹치면 실패                                                    | 첫 브라우저 id를 `visitor-a`로 고정 ([#164](https://github.com/hyeoniverse/MacFolio/pull/164))                 |
| 날씨      | 자동화 도구의 특성 | CDP로 보낸 터치 직후 몇백 ms 안에 다시 누르면 Linux Chrome이 `click`을 발생시키지 않는다     | 해당 시험은 `click`으로 삭제                                                                                   |

### 메모 편집: 지연 로딩 편집기

메모의 편집기(Milkdown)는 용량이 커서 첫 화면 코드에 넣지 않고, 편집을 시작할 때 따로 내려받는다(지연 로딩). 제목 칸에서 Enter를 누르면 본문 편집기로 초점이 넘어가야 하는데, 편집기 모듈을 내려받는 동안에는 넘겨받을 편집기가 아직 없다. 그 사이 입력한 글자가 제목 칸에 계속 들어갔다.

전체 시험을 실행할 때만 가끔 실패했으므로, 부하를 올려 재현했다. 세 시험을 `--repeat-each=14 --workers=10`(각 시험을 14번씩, 브라우저 10개로 동시에)으로 실행하니 36회 중 2회 실패했다. 동시 실행으로 모듈 내려받기가 느려지면 실패 확률이 올라간다. 느린 기기에서는 실제 사용자도 겪는 버그였다([아직 없는 편집기로 옮긴 초점](/memo/lazy-editor-focus)).

### 날씨: CI에서만 빠진 click

휴대폰 화면에서 카드를 밀고 삭제 버튼을 누르는 시험이 CI에서만 실패했다. 처음에는 카드가 아직 삭제 버튼을 덮고 있다고 추정하고 고쳤는데 다시 실패했다. CI와 같은 Linux 컨테이너에서 이벤트를 기록하니, 입력은 삭제 버튼에 도달해 `pointerdown`·`pointerup`까지 발생했지만 `click`이 발생하지 않았다.

![터치 입력에서 발생하는 이벤트 순서와 CI에서 빠진 click](./images/day-1010-click-events.svg '사람의 터치는 pointerdown, pointerup, click 순서로 이어진다. CI의 CDP 터치를 짧은 간격으로 보내면 Linux Chrome에서 마지막 click이 발생하지 않았다')

CDP(Chrome DevTools Protocol)는 Playwright가 Chrome을 조작할 때 사용하는 통신 규약이다. 사람의 입력에서는 생기지 않는 짧은 간격이라 시험만 `click`으로 바꿨다. 첫 추정으로 고친 것 중 "미는 동안에는 애니메이션 없이 손가락 위치를 바로 따라간다"는 맞는 변경이라 남겼다.

## 의존성과 CI

| 문제                                | 원인                                                                                                                                         | 조치                                                                                                                       |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| CI가 시작 단계에서 실패             | API e2e용 PostgreSQL 이미지를 Docker Hub에서 인증 없이 내려받다가 요청 한도 초과. GitHub 러너는 IP를 공유해 재실행해도 같았다                | 같은 이미지를 ECR Public에서 내려받음 ([#154](https://github.com/hyeoniverse/MacFolio/pull/154))                           |
| `@types/node` 26에서 타입 검사 실패 | 프론트엔드 `lib`는 ES2020인데 코드는 ES2022의 `.at()`을 사용. 그동안 `@types/node` 22가 ES2022 타입을 함께 불러와 **우연히** 통과하고 있었다 | `lib`를 ES2022로 변경 ([#178](https://github.com/hyeoniverse/MacFolio/pull/178))                                           |
| Dependabot PR에도 미리보기 배포     | 모든 PR에 Workers 미리보기를 배포                                                                                                            | 프론트엔드가 변경된 PR에만 배포 ([#179](https://github.com/hyeoniverse/MacFolio/pull/179))                                 |
| lint 경고 4개                       | 경고 수준으로 낮춰 둔 규칙                                                                                                                   | 경고를 해소하고 규칙을 에러로, 모든 패키지에 `--max-warnings 0` ([#144](https://github.com/hyeoniverse/MacFolio/pull/144)) |

두 항목은 배경을 덧붙인다.

- **Docker Hub 요청 한도**: Docker Hub는 로그인하지 않은 사용자의 이미지 내려받기를 IPv4 주소마다 6시간에 100회로 제한한다. GitHub이 제공하는 CI 러너는 여러 저장소의 작업이 같은 IP 대역을 공유하므로, 다른 사람의 작업이 한도를 이미 소진했을 수 있다. 같은 공식 이미지를 Amazon의 공개 저장소(ECR Public, `public.ecr.aws/docker/library/postgres`)에서 받도록 바꿨다
- **TypeScript의 `lib`**: `lib`는 "코드가 어떤 JavaScript 기본 기능을 쓸 수 있는가"를 TypeScript에 알려 주는 설정이다. `[1, 2, 3].at(-1)`(배열의 마지막 값, 결과 `3`)는 ES2022에 추가된 메서드라 `lib`가 ES2020이면 "`at` 속성이 없다"는 오류가 나야 한다. 그런데 Node 타입 패키지 22가 ES2022 타입을 함께 불러와서 오류가 가려져 있었고, 26으로 올리자 그 연결이 사라져 오류가 드러났다

Dependabot을 활성화하자 업데이트 PR이 한꺼번에 열렸다(vite 6→8, mermaid 12, lucide-react 1.x, `@types/node` 26 등, [#171](https://github.com/hyeoniverse/MacFolio/pull/171)~[#176](https://github.com/hyeoniverse/MacFolio/pull/176)). 모두 같은 잠금 파일(`pnpm-lock.yaml`)을 변경하므로 하나를 머지할 때마다 나머지가 충돌하거나 CI가 실패해, 하나씩 해결하며 머지했다. Dependabot 브랜치에 사람이 커밋하면 커밋 메시지 규칙 검사에 걸리던 문제도 #178에서 고쳤다.

같은 날 리팩터링 이슈 [#15](https://github.com/hyeoniverse/MacFolio/issues/15), desktop-core 이슈 [#16](https://github.com/hyeoniverse/MacFolio/issues/16), 백엔드 API 이슈 [#9](https://github.com/hyeoniverse/MacFolio/issues/9)를 닫았다.

### 코드로 관리할 수 없는 저장소 설정

GitHub 화면에서만 바꿀 수 있는 설정은 직접 적용했다.

1. Settings › Code security(Advanced Security)에서 Dependabot security updates, Secret Protection, Push protection 활성화
2. main Ruleset의 필수 검사에 `secrets`(gitleaks 작업) 추가

Push protection은 비밀 값(예: `ghp_`로 시작하는 GitHub 토큰)이 들어 있는 커밋을 push하는 순간 GitHub이 거부하는 기능이다. gitleaks CI가 이미 저장소에 들어온 값을 찾는다면, Push protection은 들어오기 전에 막는다. 화면의 메뉴 이름이 문서와 달라서, "Secret Protection"이 secret scanning 항목이 맞는지 [Secret scanning 문서](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)와 [Push protection 문서](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)로 확인했다. 설정 절차는 [docs/security-scan.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/security-scan.md)에 기록했다.

## 돌아보며

main을 실패시킨 원인은 스택 PR, 각자 통과한 두 PR의 조합, 외부 서비스(Docker Hub)의 요청 한도 세 가지였다. 셋 다 PR 하나의 CI로는 드러나지 않는다. 여러 PR을 나란히 열어 연달아 머지하면 =="PR이 통과했다"와 "main이 통과한다"는 다른 사실==이 된다. 머지한 뒤 main의 CI 결과까지 확인해야 머지가 끝난다.

간헐적 실패 세 건은 원인이 코드, 시험 데이터, 자동화 도구로 모두 달랐다. 증상이 같아도 수정할 위치가 다르므로, 재실행으로 통과시키지 않고 원인을 찾았다. 날씨 시험에서는 첫 추정을 Linux 환경에서 재현하기 전에 올려서 한 번 더 실패했다. 재현한 뒤에 고쳤어야 했다.

보안 점검 항목은 대부분 "이미 차단되어 있지만 시험이 없던 것"(XSS, 경로 권한)이거나 "한 단계만 차단되어 있던 것"(iframe, 요청 제한)이었다. 차단되어 있다는 사실을 시험으로 고정해야, 나중에 설정을 바꿀 때 의도치 않게 열리는 것을 막을 수 있다.
