이날 main에 머지한 PR은 32개로, 지금까지 가장 많다. 작업은 다섯 주제로 나뉜다. 전날 자정에 머지한 PR 두 개가 main에 반영되지 않은 문제, 서버 기능(휴지통·자원 모니터링·좋아요), 보안 점검 목록, 의존성과 CI, 날씨 앱이다. 그 사이에 간헐적으로 실패하는 시험 세 건의 원인을 찾았다.

![10월 10일 작업 흐름](./images/day-1010-timeline.svg '새벽부터 아침까지 휴지통·서버 모니터링·보안, 저녁에는 보안 설정과 의존성, 밤에는 날씨. 커밋 시각 기준')

## main에 반영되지 않은 스택 PR

전날 밤 블로그 폴더 PR [#143](https://github.com/hyeoniverse/MacFolio/pull/143)을 main에 머지했다. 그 브랜치 위에 휴지통 앱 [#145](https://github.com/hyeoniverse/MacFolio/pull/145)를, 다시 그 위에 서버 파일 관리 [#146](https://github.com/hyeoniverse/MacFolio/pull/146)을 쌓아 두었다(스택 PR). 30여 초 뒤 두 PR을 머지했는데, 둘 다 **main이 아니라 아래 브랜치에** 머지됐다. PR의 머지 대상은 base 브랜치이고, 두 PR의 base는 각각 아래 PR의 브랜치였다. 아래 PR이 먼저 머지되어 그 브랜치는 이미 역할이 끝난 상태였으므로, 변경이 main까지 도달하지 않았다.

![스택 PR의 머지 대상](./images/day-1010-stacked-pr.svg '#145와 #146은 base가 아래 PR의 브랜치라, 머지해도 main에 반영되지 않았다')

같은 변경을 main을 base로 한 PR로 다시 올리고, 리뷰에서 나온 수정을 더해 머지했다([#147](https://github.com/hyeoniverse/MacFolio/pull/147)). 전날 음악 PR은 위 PR을 먼저 머지해서 문제가 없었다. 이후로는 PR을 쌓지 않고 항상 main을 base로 연다.

요청 제한(#162)을 적용하기 전에 서버 설정을 확인했다. 요청 제한은 IP 단위로 집계하는데, Cloudflare Tunnel 뒤에서는 `TRUST_PROXY=1`이 설정되어 있어야 `X-Forwarded-For`에서 실제 방문자 IP를 읽는다. 값이 없으면 모든 요청이 터널의 IP 하나로 집계되어, 방문자 한 명이 한도를 넘으면 모두가 차단된다. 서버의 값은 이미 `1`이어서 변경하지 않았다.

```bash
cd ~/deploy && grep TRUST_PROXY api.env   # TRUST_PROXY=1
```

## 간헐적으로 실패하는 시험 세 건

증상은 모두 "가끔 실패"였지만 원인은 서로 달랐다.

| 시험      | 원인 분류          | 원인                                                                                         | 조치                                                                                                           |
| --------- | ------------------ | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 메모 편집 | 코드의 버그        | 제목에서 Enter를 누르는 시점에 지연 로딩하는 편집기가 아직 없어, 이후 입력이 제목에 들어갔다 | Enter 입력을 기억했다가 편집기가 준비되면 초점 이동 ([#148](https://github.com/hyeoniverse/MacFolio/pull/148)) |
| 메시지    | 시험 데이터의 우연 | 무작위로 생성한 이름이 우연히 겹치면 실패                                                    | 첫 브라우저 id를 `visitor-a`로 고정 ([#164](https://github.com/hyeoniverse/MacFolio/pull/164))                 |
| 날씨      | 자동화 도구의 특성 | CDP로 보낸 터치 직후 몇백 ms 안에 다시 누르면 Linux Chrome이 `click`을 발생시키지 않는다     | 해당 시험은 `click`으로 삭제                                                                                   |

- **메모 편집:** 전체 시험을 실행할 때만 가끔 실패했다. 세 시험을 `--repeat-each=14 --workers=10`으로 부하를 높여 실행하니 36회 중 2회 재현됐다. 편집기 모듈을 내려받는 동안 입력한 글자가 제목 칸에 들어가고 있었다. 느린 기기에서는 실제 사용자도 겪는 버그였다([아직 없는 편집기로 옮긴 초점](/memo/lazy-editor-focus))
- **날씨:** 휴대폰 화면에서 카드를 밀고 삭제 버튼을 누르는 시험이 CI에서만 실패했다. 처음에는 카드가 아직 삭제 버튼을 덮고 있다고 추정하고 수정했는데 다시 실패했다. CI와 같은 Linux 컨테이너에서 이벤트를 기록하니, 입력은 삭제 버튼에 도달해 `pointerdown`·`pointerup`까지 발생했지만 `click`이 발생하지 않았다. 사람의 입력에서는 생기지 않는 간격이라 시험만 `click`으로 바꿨다. 첫 추정으로 수정한 것 중 "미는 동안에는 애니메이션 없이 손가락 위치를 바로 따라간다"는 올바른 변경이라 유지했다

Dependabot 브랜치에 사람이 커밋하면 커밋 메시지 규칙 검사에 걸리던 문제도 #178에서 수정했다.

### 코드로 관리할 수 없는 저장소 설정

GitHub 화면에서만 바꿀 수 있는 설정은 직접 적용했다.

1. Settings › Code security(Advanced Security)에서 Dependabot security updates, Secret Protection, Push protection 활성화
2. main Ruleset의 필수 검사에 `secrets`(gitleaks 작업) 추가

화면의 메뉴 이름이 문서와 달라서, "Secret Protection"이 secret scanning 항목이 맞는지 [Secret scanning 문서](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)와 [Push protection 문서](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)로 확인했다. 설정 절차는 [docs/security-scan.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/security-scan.md)에 기록했다.

## 날씨 앱

macOS 날씨 앱을 추가했다([#177](https://github.com/hyeoniverse/MacFolio/pull/177), [macOS 날씨 앱 만들기](/memo/weather-app)). 데이터는 API 키 없이 사용하는 Open-Meteo에서 조회한다. Open-Meteo의 장소 검색은 한국어 도시 이름의 검색 결과가 부정확하고 응답이 느려서, 자주 검색하는 도시 211곳과 서울의 구는 사이트에 내장했다.

![날씨 앱](./images/day-1010-weather.jpg '날씨 앱 화면 (시험용 날씨 데이터)')

그 밖에 Apple 메뉴의 '이 Mac에 관하여'와 시스템 설정의 '정보'에 제작자 프로필을 표시하고([#161](https://github.com/hyeoniverse/MacFolio/pull/161)), 메일 앱에서 운영자 주소를 누르면 클립보드에 복사되게 했다([#165](https://github.com/hyeoniverse/MacFolio/pull/165)).

## 돌아보며

이날 main을 실패시킨 원인은 셋이었다. 스택 PR, 각자 통과한 두 PR의 조합, 외부 서비스(Docker Hub)의 요청 한도. 셋 다 PR 하나의 CI로는 드러나지 않는다. 하루에 PR을 30개 넘게 머지하면 "PR이 통과했다"와 "main이 통과한다"는 다른 사실이 된다. 머지한 뒤 main의 CI 결과까지 확인해야 머지가 끝난다.

간헐적 실패 세 건은 원인이 코드, 시험 데이터, 자동화 도구로 모두 달랐다. 증상이 같아도 수정할 위치가 다르므로, 재실행으로 통과시키지 않고 원인을 찾아야 한다. 날씨 시험에서는 첫 추정을 Linux 환경에서 재현하기 전에 올려서 한 번 더 실패했다. 재현한 뒤에 수정했어야 했다.

보안 점검은 목록을 먼저 작성하고 항목별로 PR을 열었다. 대부분 "이미 차단되어 있지만 시험이 없던 것"(XSS, 경로 권한)이거나 "한 단계만 차단되어 있던 것"(iframe, 요청 제한)이었다. 차단되어 있다는 사실을 시험으로 고정해 두어야, 이후 설정을 변경할 때 의도치 않게 열리는 것을 막을 수 있다.
