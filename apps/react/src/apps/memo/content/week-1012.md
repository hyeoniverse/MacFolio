## 공통 컴포넌트와 디자인 토큰: 리팩터링 계획 완료

공통 컴포넌트는 여러 화면에서 같은 동작을 하는 UI를 한 번만 구현해 함께 쓰는 부품이다. 예를 들어 화면 위에 떠서 닫기 전까지 뒤의 화면을 조작할 수 없게 하는 Modal은, 경고창·배경화면 이름 변경·키보드 단축키 등 5곳이 Esc 키 처리와 포커스 이동을 각자 구현하고 있었다.

4단계는 코드 변경이 아니라 사용처 집계로 시작했다. `shared/ui` 컴포넌트 15개와 직접 작성한 `<button>` 295곳을 분류하고, 계획에 적힌 후보 9개가 실제로 몇 번 반복되는지 다시 측정했다. ==통합할 대상은 Modal·Sheet·SearchField 3개였다.== 나머지 6개는 형태와 역할이 서로 달라, 하나로 묶으면 `compact`·`danger` 같은 옵션만 늘어나므로 보류했다.

디자인 토큰은 색·간격·모서리 반경 같은 값을 `--radius-md: 8px`처럼 이름 있는 CSS 변수로 한 곳에 정의하고, 사용처에서는 `var(--radius-md)`로 참조하는 방식이다. 값을 바꿀 때 정의 한 줄만 고치면 된다. 모서리 반경 239곳, 글자 크기 645곳, 간격 1,543곳, 색 288곳, z-index 20곳을 `--radius-*`·`--text-*`·`--space-*`·`--color-*`·`--z-*` 토큰으로 옮기고, 18일에 남은 PR을 머지해 계획을 마쳤다.

리팩터링은 화면을 바꾸지 않아야 하므로, PR마다 무엇이 같아야 하는지를 먼저 정했다.

![화면이 바뀌지 않았음을 확인하는 세 가지 방법](./images/week-1012-equivalence-checks.svg '토큰 교체는 값이 같은지, 파일 분할은 빌드한 CSS가 바이트 단위로 같은지, 규칙 삭제는 요소마다 계산된 스타일이 같은지 확인했다')

## #187 프로젝트 페이지 템플릿: 공통 데이터와 분리로 머지

PR [#187](https://github.com/hyeoniverse/MacFolio/pull/187)은 시스템 설정에서 프로젝트를 편집하고, 프로젝트마다 고른 템플릿으로 Safari 페이지를 렌더링하는 PR이다. 13일에는 템플릿마다 읽는 데이터 필드가 달라, 입력한 값이 어떤 템플릿에서는 보이지 않았다. 예를 들어 템플릿 A가 읽는 필드에 값을 입력한 뒤 템플릿 B로 바꾸면, B는 다른 필드를 읽으므로 그 값이 화면에 나타나지 않았다.

이를 해결하려고 모든 템플릿이 공통 랜딩 데이터(`landingOf`)만 읽게 하고 13개를 4개로 줄였다. 이전 템플릿 이름은 가장 가까운 새 템플릿으로 변환해 읽어(`LEGACY_LOOKS`), 서버에 저장된 데이터를 마이그레이션하지 않았다.

![모든 템플릿이 같은 landingOf 데이터를 읽고, 이전 템플릿 이름은 LEGACY_LOOKS로 변환하는 구조](./images/day-1013-landing-data.svg '템플릿은 공통 데이터 하나만 읽는다. 서버에 남은 이전 템플릿 이름은 읽는 시각에 새 이름으로 바뀐다')

템플릿마다 참고할 실제 제품(Apple 제품 페이지, Stripe, Notion 등)을 정한 뒤에야 구조가 안정됐다. 머지를 막던 것은 미완성인 RPG 대화창이었고, 17일 `feat/rpg-dialogue` 브랜치로 떼어 내자 바로 머지할 수 있었다.

![제품 템플릿](./images/day-1013-product.jpg '공통 데이터로 묶은 뒤의 제품 템플릿. Apple 제품 페이지처럼 큰 제목과 창 프레임 안의 큰 화면')

## 메모 편집 화면을 읽기 화면과 일치시키기

메모 앱은 저장소의 Markdown 파일(저장소 글)과 관리자가 편집기에서 쓴 글을 함께 보여 준다. 15일에 저장소 글을 편집기에서 게시하려 하자 "요약은 200자까지" 경고로 막혔다. 편집 화면에는 요약 칸이 없는데, 일부 저장소 글의 요약이 200자를 넘었기 때문이다. 저장소 글은 편집기의 검증을 거치지 않고 빌드에 포함되어 그때까지 드러나지 않았다.

편집기와 같은 규칙(`validateDraft`)으로 저장소 글 140편을 검사하는 `content.test.ts`를 추가하자 18편이 한꺼번에 드러났다. 이제 규칙을 어긴 저장소 글은 CI에서 실패한다.

편집 화면의 줄 높이와 여백은 같은 글을 두 화면에서 열고, 본문 블록마다 화면상의 위치(`top`)와 높이(`height`)를 비교해 맞췄다. 그 결과 편집기 15px, 읽기 화면 14px의 글자 크기 차이와, 읽기 화면에서 긴 코드가 칸 밖으로 넘치는 결함이 드러났다. 이 비교를 E2E로 고정했다.

## CI: ECR Public 한도와 E2E 분할

API e2e 시험은 실제 PostgreSQL이 필요해서, CI가 컨테이너 이미지 저장소(registry)에서 Postgres 이미지를 내려받아 실행한다. 저장소마다 일정 시간 안에 내려받을 수 있는 양에 한도가 있다. 10월 10일에 Docker Hub의 한도를 피해 이미지를 ECR Public(AWS의 공개 저장소)으로 옮겼는데, 13일부터 16일까지 `toomanyrequests: Data limit exceeded`에 다섯 번 걸려 형식 검사와 시험을 시작하지 못했다.

매번 재실행하면 통과해서 미루다가, 17일 [#240](https://github.com/hyeoniverse/MacFolio/pull/240)으로 ECR Public, mirror.gcr.io, Docker Hub 순으로 내려받게 했다. 또 Postgres를 `services`가 아니라 작업 단계로 실행해, 이미지를 끝내 받지 못해도 다른 검사는 실행된다.

![Postgres 이미지 내려받기 순서와 실패 범위](./images/week-1012-image-fallback.svg '세 저장소를 차례로 시도하고, 모두 실패해도 DB가 필요한 단계만 실패한다')

같은 날 시험 수가 늘어 한 작업의 25분 제한에 걸린 화면 E2E를 세 작업으로 나눠 병렬 실행했다.

## 롤백 훈련과 보안 점검

롤백은 새 버전에 문제가 있을 때 이전 버전으로 되돌리는 절차다. 배포 스크립트는 새 이미지가 헬스 체크를 통과하지 못하면 이전 이미지로 되돌리게 작성해 두었지만, 운영 서버에서 동작하는지 확인한 적이 없었다. 18일에 헬스 체크에 항상 실패하는 `sha-dead000` 이미지를 운영 서버에 배포하자, 되돌리기를 시작한 지 ==41초 만에 `sha-7e7eac0`이 다시 healthy==가 됐다.

![서버 로그의 되돌림](./images/rollback-drill-server-log.jpg '훈련 중 서버 로그. 새 이미지가 헬스 체크를 통과하지 못하자 41초 만에 이전 태그로 복구됐다')

같은 날 Semgrep으로 정적 분석을 실행했다. Semgrep은 코드를 실행하지 않고 위험한 패턴(검증 없이 사용자 입력을 쓰는 코드 등)을 찾는 도구다. 보고된 7건을 분류해 오탐 4건과 영향 없는 3건을 확인했다. 그중 `__proto__` 같은 이름을 폴더 이름으로 따라가던 2건은 객체의 프로토타입을 오염시킬 수 있는 패턴이라 고쳤고, ERROR 등급만 차단하는 CI 작업을 추가했다.

## 돌아보며

- **공통 컴포넌트**: 사용처를 먼저 집계한 공통 컴포넌트는 재작업 없이 끝났다. 화면 인상으로 시작한 템플릿·RPG 대화창·메일 오류 표시는 여러 번 다시 만들었다.
- **요약 규칙**: 편집기의 요약 규칙을 시험에도 쓰자 규칙에 맞지 않는 글 18편이 드러났다. 검증 규칙은 데이터가 들어오는 모든 경로에 같게 건다.
- **반복된 CI 실패**: ECR 한도는 나흘 동안 다섯 번, 4000번 포트의 이전 API 컨테이너는 이틀 연속 다른 증상으로 나타났다. 재실행으로 넘어가는 실패도 반복되면 구조로 고친다.
- **main에도 있는 버그**: CSS 레이어 순서 버그를 [#187](https://github.com/hyeoniverse/MacFolio/pull/187) 브랜치 안에서만 고쳐, main에서 같은 버그를 다시 찾아야 했다. 큰 브랜치에서 찾은 main의 버그는 찾은 자리에서 별도 PR로 보낸다.
