## 공통 컴포넌트와 디자인 토큰: 리팩터링 계획 완료

4단계는 코드 변경이 아니라 사용처 집계로 시작했다. `shared/ui` 컴포넌트 15개와 직접 작성한 `<button>` 295곳을 분류하고, 계획에 적힌 후보 9개가 실제로 몇 번 반복되는지 다시 측정했다. ==통합할 대상은 Modal·Sheet·SearchField 3개였다.== 나머지 6개는 형태와 역할이 서로 달라 하나로 묶으면 옵션만 늘어나므로 보류했다. 이어서 모서리 반경 239곳, 글자 크기 645곳, 간격 1,543곳, 색 288곳, z-index 20곳을 `--radius-*`·`--text-*`·`--space-*`·`--color-*`·`--z-*` 토큰으로 옮기고, 18일에 남은 PR을 머지해 계획을 마쳤다. 화면을 바꾸지 않는 PR마다 동일성을 확인하는 방법을 먼저 정했다. 값을 그대로 옮기거나, 4,600줄 Memo.css를 15개 파일로 나눈 뒤 빌드한 CSS를 바이트 단위로 비교하거나, 중복 규칙 103개를 지운 페이지에서 요소 3,720개의 계산된 스타일을 비교했다.

## #187 프로젝트 페이지 템플릿: 공통 데이터와 분리로 머지

프로젝트 페이지 PR인 #187은 시스템 설정에서 프로젝트를 편집하고, 프로젝트마다 고른 템플릿으로 Safari 페이지를 렌더링하는 PR이다. 13일에는 템플릿마다 읽는 데이터 필드가 달라 입력한 값이 어떤 템플릿에서는 보이지 않는 문제를 해결하려고, 모든 템플릿이 공통 랜딩 데이터(`landingOf`)만 읽게 하고 13개를 4개로 줄였다. 이전 템플릿 이름은 가장 가까운 새 템플릿으로 변환해 읽어(`LEGACY_LOOKS`) 서버 데이터를 마이그레이션하지 않았다. 템플릿마다 참고할 실제 제품(Apple 제품 페이지, Stripe, Notion 등)을 정한 뒤에야 구조가 안정됐다. 머지를 막던 것은 미완성인 RPG 대화창이었고, 17일 `feat/rpg-dialogue` 브랜치로 떼어 내자 바로 머지할 수 있었다.

## 메모 편집 화면을 읽기 화면과 일치시키기

15일에 저장소 글을 편집기에서 게시하려 하자 "요약은 200자까지" 경고로 막혔다. 편집 화면에는 요약 칸이 없는데 일부 저장소 글의 요약이 200자를 넘었기 때문이다. 편집기와 같은 규칙(`validateDraft`)으로 저장소 글 140편을 검사하는 `content.test.ts`를 추가하자 18편이 한꺼번에 드러났다. 편집 화면의 줄 높이와 여백은 같은 글을 두 화면에서 열고 본문 블록마다 `top`·`height`를 비교해 맞췄다. 그 결과 편집기 15px, 읽기 화면 14px의 글자 크기 차이와 읽기 화면에서 긴 코드가 칸 밖으로 넘치는 결함이 드러났고, 이 비교를 E2E로 고정했다.

## CI: ECR Public 한도와 E2E 분할

10월 10일에 Docker Hub의 내려받기 한도를 피해 Postgres 이미지를 ECR Public으로 옮겼는데, 13일부터 16일까지 `toomanyrequests: Data limit exceeded`에 다섯 번 걸려 형식 검사와 시험을 시작하지 못했다. 매번 재실행하면 통과해서 미루다가 17일 [#240](https://github.com/hyeoniverse/MacFolio/pull/240)으로 ECR Public, mirror.gcr.io, Docker Hub 순으로 내려받게 했다. Postgres를 `services`가 아니라 작업 단계로 실행해, 이미지를 끝내 받지 못해도 다른 검사는 실행된다. 같은 날 시험 수가 늘어 한 작업의 25분 제한에 걸린 화면 E2E를 세 작업으로 나눠 병렬 실행했다.

자세한 내용: [10월 16일](/memo/day-1016), [10월 17일](/memo/day-1017), [E2E 재실행 생략하기](/memo/faster-e2e-ci)

## 롤백 훈련과 보안 점검

배포 스크립트는 새 이미지가 헬스 체크를 통과하지 못하면 이전 버전으로 되돌리게 작성해 두었지만, 실제로 동작하는지 확인한 적이 없었다. 18일에 헬스 체크에 항상 실패하는 `sha-dead000` 이미지를 운영 서버에 배포하자, 되돌리기를 시작한 지 41초 만에 `sha-7e7eac0`이 다시 healthy가 됐다. 같은 날 Semgrep이 보고한 7건을 분류해 오탐 4건과 영향 없는 3건을 확인했고, `__proto__` 같은 이름을 폴더 이름으로 따라가던 2건은 고친 뒤 ERROR 등급만 차단하는 CI 작업을 추가했다.

## 돌아보며

- 사용처를 먼저 집계한 공통 컴포넌트는 재작업 없이 끝났고, 기준 없이 화면 인상으로 시작한 템플릿·RPG 대화창·메일 오류 표시는 여러 번 다시 만들었다. 참고할 실제 화면을 먼저 정해야 반복이 줄어든다.
- 미완성 실험이 PR 안에 있으면 PR 전체가 그 실험을 기다린다. #187 안에서 고친 main의 CSS 레이어 순서 버그는 main에서 다시 찾아야 했으므로, 큰 브랜치에서 찾은 main의 버그는 그 시점에 별도 PR로 보낸다.
- 리팩터링은 무엇이 같아야 하는지(값, 빌드한 CSS 바이트, 계산된 스타일)를 먼저 정하면 검증이 빨리 끝난다.
- 검증 규칙은 데이터가 들어오는 모든 경로에서 같아야 한다. 편집기의 요약 규칙을 시험에도 쓰자 18편이 드러났다.
- 재실행으로 넘어가는 실패도 반복되면 구조로 고친다. ECR 한도는 나흘 동안 다섯 번, 4000번 포트의 이전 API 컨테이너는 이틀 연속 다른 증상으로 나타났다.
