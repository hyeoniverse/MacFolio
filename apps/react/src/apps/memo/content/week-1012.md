## 공통 컴포넌트와 리팩터링 계획 완료

### 사용처 집계 뒤 Modal 추출 (12일)

4단계의 첫 항목은 코드 변경이 아니라 사용처 집계였다([#210](https://github.com/hyeoniverse/MacFolio/pull/210), [공통 부품 목록을 먼저 적고](/memo/ui-modal#공통-부품-집계)).

1. `shared/ui`의 컴포넌트 15개의 props와 사용처를 `docs/ui.md`에 기록
2. 직접 작성한 `<button>` 295곳을 분류. 그중 공통 Button으로 옮길 수 있는 곳은 93곳
3. 계획에 적힌 후보 9개가 현재 코드에서 몇 번 반복되는지 다시 측정

결과는 Sheet·Modal·SearchField 3개였다. 나머지 6개는 사용처는 많아도 형태와 역할이 서로 달라, ==하나로 통합하면 옵션만 늘어난다==고 판단해 보류했다.

먼저 Modal을 추출했다. 경고창, 배경화면 이름 변경, 키보드 단축키, 로그인 결과, Launchpad 5곳이 오버레이(배경 덮개), 포커스 트랩, Esc로 닫기, 바깥 클릭으로 닫기, 닫힘 애니메이션을 각자 구현하고 있었다. 이 다섯 동작을 `Modal` 하나로 옮기고, 내용과 패널 스타일은 각 다이얼로그에 그대로 두었다. '이 Mac에 관하여'는 오버레이 없이 끌어서 옮기는 창이라 대상에서 제외했다([#212](https://github.com/hyeoniverse/MacFolio/pull/212), [오버레이·포커스·Esc 처리를 공통 Modal 컴포넌트로 추출하기](/memo/ui-modal)).

### Sheet와 SearchField (13일·16일)

13일에는 휴대폰 음악 앱의 시트 동작이 어색한 것을 계기로 Sheet를 추출했다. 메일 쓰기, 메일 동작, 음악 지금 재생 중 3곳이 아래에서 올라오는 시트를 각자 구현하고 있었다. 오버레이, 열림·닫힘 애니메이션, 닫기 동작을 `Sheet` 하나로 통합하고, 형태 차이는 `variant` 3개(page·card·cover)로 구분했다([#220](https://github.com/hyeoniverse/MacFolio/pull/220), [오버레이·닫기·role을 공통 Sheet 컴포넌트로 추출하고 모양은 variant로 나누기](/memo/ui-sheet)).

| 증상                                     | 원인                                                           | 수정                             |
| ---------------------------------------- | -------------------------------------------------------------- | -------------------------------- |
| 시트가 열릴 때 뒤의 앱 화면이 스크롤된다 | 시트에 초점을 옮기면 브라우저가 초점 요소를 화면 안으로 스크롤 | `focus({ preventScroll: true })` |
| 음악 화면의 왼쪽 여백이 사라진다         | 시트가 가로로 넘쳐 화면 전체가 옆으로 밀렸다                   | `overflow-x: hidden`             |

수정 후 전후 화면을 픽셀 단위로 비교해 동일한 것을 확인했다. 같은 방식으로 검증한 SearchField 추출([#223](https://github.com/hyeoniverse/MacFolio/pull/223))과 활동 상태 보기의 여백 정리([#222](https://github.com/hyeoniverse/MacFolio/pull/222))는 16일에 머지했다. 머지 전에는 사진 앱 검색 칸의 닫기(×) 버튼이 화면 밖으로 잘리던 문제 등 휴대폰 검색 문제 넷을 #223에 추가로 수정했다.

### z-index 층 이름 (16일)

13개 파일 20곳에 `1000`, `9999`, `15000` 같은 숫자로 흩어져 있던 z-index를 `theme.css`의 층 이름 변수 15개(`--z-dock`, `--z-menubar`, `--z-login` 등)로 통합했다([#231](https://github.com/hyeoniverse/MacFolio/pull/231), [z-index를 층 이름으로](/memo/design-tokens#z-index-층-흩어진-숫자를---z--변수로-모으기-231)). 값은 하나도 변경하지 않아 화면은 그대로다.

```css
/* 전: 숫자만으로는 어느 층이 위인지 알 수 없다 */
z-index: 1000;

/* 후: 이름으로 층을 표현하고, 순서는 theme.css 한 곳에서 관리한다 */
z-index: var(--z-dock);
```

## CSS 레이어 순서와 메일 입력 칸

### 두 번 발견한 레이어 순서 버그 (12일·13일)

12일, #187에서 설정 창 확인 다이얼로그의 여백이 0인 것을 발견해 수정했지만, 이 수정은 다른 커밋에 한 줄로 묻혀 main에는 반영되지 않았다.

13일 새벽 3시, 휴대폰 메일 앱의 "서버에서 문제가 생겼습니다" 문구가 매우 작게, 여백 없이 보낸 편지함 바로 아래에 표시됐다. 비슷한 gap·padding 문제를 함께 수정하다가 답장 버튼의 padding이 0인 것을 발견했다.

![휴대폰 메일의 오류 문구](./images/day-1013-mail-error-small.jpg '수정 전 휴대폰 메일상자. 빨간 오류 문구가 작고, 목록 상자에 여백 없이 붙어 있다')

```css
/* 기대한 순서: 뒤에 선언한 레이어가 우선 */
@layer reset, components;

/* 실제 빌드 결과: 공통 컴포넌트 CSS 파일이 먼저 로드되어 순서가 뒤집힘 */
@layer components, reset;
/* → reset의 * { padding: 0 }이 버튼의 padding보다 우선 */
```

`@layer`의 ==우선순위는 처음 등장한 순서로 정해진다.== 빌드한 HTML에서 공통 컴포넌트 CSS가 든 파일이 먼저 연결되어 `components`가 먼저 선언됐다. 레이어 순서 선언을 `index.html`의 인라인 스타일 맨 앞으로 옮겨 어떤 CSS 파일보다 먼저 선언되게 했다([#221](https://github.com/hyeoniverse/MacFolio/pull/221), [CSS 파일 로드 순서와 무관하게 @layer 순서를 index.html에서 먼저 선언하기](/memo/css-layer-order-fix)). 전날 #187에서 고친 버그를 main에서 처음부터 다시 찾은 셈이다.

> [!WARNING] `event.key`와 `event.code`
> 마지막 문제의 원인은 키 이벤트의 값이었다. `event.key`는 입력된 **문자**이고, `event.code`는 눌린 **물리 키의 위치**다. 한글 입력 상태에서 Z를 누르면 `event.key`가 `'ㅋ'`로 전달되고, Chrome의 입력기(IME)는 `'Process'`를 전달하기도 한다. 게임 키는 입력 언어와 관계없이 같아야 하므로 `event.code`로 판정한다.

| 입력 상태 | Z 키의 `event.key`      | Z 키의 `event.code` |
| --------- | ----------------------- | ------------------- |
| 영문      | `'z'`                   | `'KeyZ'`            |
| 한글      | `'ㅋ'` 또는 `'Process'` | `'KeyZ'`            |

```ts
const CODE_KEYS = { KeyZ: 'z', KeyX: 'x', KeyW: 'w', KeyA: 'a', KeyS: 's', KeyD: 'd' };

export function gameKey(event: KeyboardEvent): string {
	const byCode = CODE_KEYS[event.code];
	if (byCode) return byCode;
	return event.key.length === 1 ? event.key.toLowerCase() : event.key;
}
```

### 사라지는 빈 폴더와 `~` 하나로 적용되던 취소선 (15일)

폴더 목록은 저장된 폴더와 글에 지정된 폴더를 합쳐 렌더링한다. 그래서 글에서만 생긴 폴더는 마지막 글이 빠지면 함께 사라졌다. 글이 폴더를 떠나는 네 경로(드래그 앤 드롭, 여러 개 선택 후 이동, 삭제, 편집 화면에서 폴더 변경)에서 원래 폴더를 저장하게 했다(`keepFolder`).

`220~440px`처럼 범위를 적은 글에서는 두 `~` 사이가 취소선으로 렌더링됐다. 읽기 화면(remark-gfm)과 편집기 모두 `~` 하나짜리 취소선을 허용했기 때문이다. 읽기 화면은 remark-gfm 옵션을 `singleTilde: false`로 지정하고, 편집기는 같은 옵션으로 파싱하면서 `~` 하나를 받던 입력 규칙을 `~~`만 받는 규칙으로 교체했다.

```markdown
사이드바 180~360px, 목록 220~440px ← 전: "360px, 목록 220" 부분이 취소선
~~취소선~~ ← 후: ~~ 두 개만 취소선
```

![~ 하나로 적용된 취소선](./images/day-1015-tilde.jpg '실제로 문제가 된 글 「메모 칸 너비 조절」. 사이드바 180~360px의 가운데가 취소선으로 렌더링됐다')

### 편집기의 토글 목록과 각주 (15일)

서식 메뉴(가가)에 "토글 목록"과 "각주 넣기"를 추가했다. 토글 목록은 › 를 눌러 접고 펼치며 접힌 상태도 저장하고, 읽기 화면이 이미 렌더링하던 `<details>`·`<summary>`로 저장한다. 각주는 커서 위치에 번호를 넣고 글 끝에 내용 칸을 만들어 커서를 그곳으로 이동하며, `[^1]`로 저장한다. 각주를 넣으면 글 중간의 빈 줄이 `<br />`로 저장되던 버그도 함께 수정했다. 처음에는 기존 편집기가 `<details>` 줄을 버린다고 판단했지만, main의 편집기는 그 줄을 원본 HTML 문자열로 표시하고 그대로 저장했다. 사라진 것은 새 플러그인의 초기 버그였다. 자세한 과정은 [Milkdown 편집기에 <details> 토글 목록과 GFM 각주 노드 추가하기](/memo/memo-editor-toggle-footnote)에 적었다.

![토글 목록과 각주](./images/day-1015-toggle.jpg '편집기에서 토글 제목 앞의 ›로 접고, 본문의 [1]은 글 끝의 각주로 링크된다')

### 편집 화면을 읽기 화면과 일치시키기 (15일)

편집기에서도 각주 번호, ↩, 글 안 링크(`#이름`)를 누르면 해당 위치로 스크롤하고 도착한 곳을 잠시 노란색으로 강조한다. 링크 글자를 수정하려면 macOS 메모처럼 Option 키를 누른 채 클릭한다.

줄 높이와 여백은 측정으로 맞췄다. 같은 글을 두 화면에서 열고 본문 블록마다 `top`과 `height`를 비교하자 차이가 두 군데 나왔다.

| 차이              | 원인                                                                            | 수정 대상                               |
| ----------------- | ------------------------------------------------------------------------------- | --------------------------------------- |
| 본문 글자 크기    | 편집기 15px, 읽기 화면 14px. 편집 칸이 700px보다 좁으면 글자를 키우던 이전 규칙 | 편집기 (규칙 삭제)                      |
| 긴 코드가 든 목록 | 읽기 화면에서 긴 코드가 칸 밖으로 넘쳤다                                        | 읽기 화면 (편집기처럼 칸 안에서 줄바꿈) |

이제 문단, 제목, 목록, 표, 이미지, 코드, 접기 블록, 각주가 두 화면에서 같은 위치에 렌더링되고, 이 비교를 E2E로 고정했다. 관리자 배지는 누르면 방문자가 보는 읽기 화면으로 전환되는 버튼으로 바꾸고, 휴대폰은 ••• 메뉴에 "읽기 화면으로 보기"를 추가했다.

![편집 화면과 읽기 화면](./images/day-1015-parity.jpg '같은 글. 수정 전 편집 화면은 글자가 커서 줄바꿈이 더 많았다')

![관리자 배지](./images/day-1015-chip.jpg '편집 화면의 관리자 배지를 누르면 눈 아이콘의 읽기 화면으로 전환된다')

### 구분선, 한 줄에 서식 하나, 키보드 위 서식 막대 (16일)

구분선(`<hr>`)에 스타일이 없어 브라우저 기본값(회색 2px 입체선, 위쪽 여백만 있음)이 표시됐다. 테두리 색 1px 선에 위아래 여백을 같게 지정하고, 편집기가 `---`를 `***`로 변환해 저장하던 문제도 수정했다([#227](https://github.com/hyeoniverse/MacFolio/pull/227)).

![구분선](./images/day-1016-hr.jpg '다크 모드 읽기 화면. 수정 전에는 밝고 굵은 선이 두드러졌다')

목록 항목 안의 제목, 토글 제목 안의 머리말은 Notion처럼 허용하지 않고 iOS·macOS 메모 방식으로 정했다. 서식 메뉴가 이미 macOS 메모의 서식 목록(한 줄에 하나만 선택)을 따르고 있었고, Notion 방식으로 저장하면 읽기 화면에서 목록 기호 옆에 큰 제목이 붙어 레이아웃이 어색했기 때문이다. 목록 항목에서 머리말 서식을 고르면 그 줄은 목록에서 빠져 머리말이 된다([한 줄에 모양은 하나](/memo/memo-one-style-per-line)).

휴대폰에서 화면 키보드가 올라오면 서식 막대가 키보드에 가려졌다. iOS Safari는 키보드가 올라와도 레이아웃 뷰포트(`innerHeight`)는 그대로 두고 보이는 영역(`visualViewport.height`)만 키보드 높이만큼 줄인다. 두 값의 차이로 가려진 높이를 계산해 서식 막대를 키보드 바로 위에 화면 폭 전체로 표시했고, 주소창이 접힐 때처럼 차이가 120px 미만이면 키보드로 판정하지 않는다. 같은 PR에 iOS 메모의 문단 도구(내어쓰기·들여쓰기, 위·아래로 이동, 인용, 목록)도 추가했다([#230](https://github.com/hyeoniverse/MacFolio/pull/230)). 실제 아이폰에서 확인하지 못해 16일에는 머지하지 않았다.

![키보드 위 서식 막대](./images/day-1016-keyboard.jpg '시험 브라우저에는 화면 키보드가 없어서 visualViewport만 줄이고 그 영역을 회색으로 칠했다')

**날씨 앱.** 사이트는 폭 767px 이하(가로로 눕힌 휴대폰은 그 이상도)를 휴대폰 화면으로 판정하는데, 날씨 앱은 자체 기준으로 640px 이하일 때만 iOS 레이아웃으로 전환했다. 641~767px에서는 휴대폰 셸 안에 넓은 창 레이아웃이 표시되어 사이드바 버튼이 상태 표시줄에 가려졌다([useIsMobile과 ResizeObserver로 정하는 data-compact 레이아웃 기준](/memo/weather-layout-fixes)).

![날씨 앱 744px](./images/day-1016-weather.jpg '744px 세로 화면. 왼쪽은 넓은 창 레이아웃의 사이드바가 남아 있는 수정 전')

**상태 표시줄과 홈 인디케이터.** 바로 아래에 렌더링된 화면(배경화면, 사진 등)의 밝기를 읽어 흰색과 검은색 중 대비가 더 큰 색을 고르고, 시계 영역과 아이콘 영역은 따로 판정한다([배경 이미지 픽셀 샘플링과 대비 계산으로 상태 표시줄 글자색 정하기](/memo/mobile-bars-contrast)). 처음 넣은 글자 둘레의 글로(glow)는 윤곽이 번져 보여 삭제했다. 실제 iOS도 단색만 쓴다. 그 뒤 Kaleidoscope 배경화면에서 홈 인디케이터가 검은색으로 표시됐는데, 터치 영역(화면 폭 전체, 양 끝의 밝은 청록색 포함)을 기준으로 밝기를 판정했기 때문이다. 실제로 보이는 막대(134px) 바로 아래만 판정하도록 수정했다.

![상태 표시줄](./images/day-1016-bars.jpg 'iOS 18 라이트 배경화면. 수정 후에는 시계와 아이콘이 검은색이다')

**활동 상태 보기.** iOS에서 탭으로 구성된 앱의 첫 화면에는 뒤로 가기 버튼이 없고, 이 사이트의 날씨·사진 앱도 같은 규칙을 따른다. `<` 버튼을 삭제하고 탭 줄과 기간 줄을 카드 정렬선에 맞췄으며, 기간 선택은 넓은 창과 같은 오른쪽 끝으로 옮겼다.

### TypeScript 7 (12일)

전날 활성화한 Dependabot의 PR 중 작은 업데이트 묶음([#214](https://github.com/hyeoniverse/MacFolio/pull/214)), vitest 5([#216](https://github.com/hyeoniverse/MacFolio/pull/216)), Font Awesome 7([#217](https://github.com/hyeoniverse/MacFolio/pull/217))은 그대로 머지했다. TypeScript 5.9 → 7.0([#215](https://github.com/hyeoniverse/MacFolio/pull/215))은 린트 단계에서 실패했다. TypeScript 7은 Go로 다시 작성한 컴파일러라 아직 JavaScript API가 없고, typescript-eslint는 그 API를 호출한다. 공식 안내에 따라 두 버전을 함께 설치했다.

| 패키지 이름          | 실제 버전        | 사용처                   |
| -------------------- | ---------------- | ------------------------ |
| `typescript`         | TS 6 호환 패키지 | typescript-eslint (린트) |
| `@typescript/native` | TS 7             | 타입 검사, 빌드          |

TS 7에서 제거된 `baseUrl` 옵션도 tsconfig에서 삭제했다([npm 별칭으로 TypeScript 7 tsc와 TypeScript 6 typescript-eslint 함께 쓰기](/memo/typescript-7-side-by-side)).

### Semgrep과 SCA 점검 (18일)

Semgrep(SAST, 코드 정적 분석), pnpm audit과 osv-scanner(SCA, 의존성 취약점 분석)를 실행했다([#252](https://github.com/hyeoniverse/MacFolio/pull/252), [Semgrep과 SCA 도구로 점검하기](/memo/security-scan)). Semgrep이 보고한 7건 중 4건은 오탐, 3건은 실제 영향이 없는 코드였다. 그중 2건은 `__proto__` 같은 이름을 폴더 이름으로 그대로 따라가던 코드여서 해당 이름을 제외하도록 수정했다. ERROR 등급만 차단하는 Semgrep CI 작업을 추가했다.

### UTM 집계 (12일·18일)

12일에는 지원서에 첨부할 링크로 어느 지원처에서 방문했는지 확인하려고 UTM 매개변수를 검토했다. 트래픽 분석이 이미 `utm_source` 등을 읽고 있어, `/?utm_source=<지원처>&utm_medium=resume&utm_campaign=<공고>`처럼 매개변수만 붙이면 집계되는 것을 실제 방문으로 확인했다. 매개변수 정의는 [Google 애널리틱스 도움말](https://support.google.com/analytics/answer/10917952)을 참고했다.

| 매개변수       | 의미      | 예          |
| -------------- | --------- | ----------- |
| `utm_source`   | 유입 출처 | 지원 회사명 |
| `utm_medium`   | 매체      | `resume`    |
| `utm_campaign` | 캠페인    | 공고 이름   |

18일에 활동 상태 보기에 매체 표, 출처·매체·캠페인 조합 표와 조합별 일별 추이, 관리자용 UTM 링크 생성기를 추가했다([#253](https://github.com/hyeoniverse/MacFolio/pull/253), [UTM 조합 표와 링크 생성기](/memo/utm-analytics)). 방문 시 읽은 `utm_*` 값은 `history.replaceState`로 주소창에서 삭제한다. 방문자가 UTM이 붙은 주소를 복사해 공유하면 같은 캠페인 방문이 중복 집계되고, 링크를 배포한 곳도 함께 전달되기 때문이다.

매번 실패한 작업만 재실행해 통과시키다가, 17일 아침 [#240](https://github.com/hyeoniverse/MacFolio/pull/240)으로 구조를 바꿨다.

- Postgres 이미지를 ECR Public에서 내려받지 못하면 mirror.gcr.io, 그다음 Docker Hub 순으로 시도한다
- Postgres를 `services`가 아니라 작업 단계(step)로 실행한다. `services`는 이미지를 내려받지 못하면 작업 전체가 시작되지 않지만, 단계로 실행하면 형식 검사 같은 다른 검사는 실행된다

같은 아침 화면 E2E를 `check` 작업에서 분리해 세 개 작업으로 나눠 병렬 실행했다. 시험 수가 늘어 한 작업의 25분 제한에 걸렸기 때문이다. API 이미지 빌드와 배포는 E2E까지 통과해야 진행한다. 이틀 뒤 이를 여섯 개로 다시 나눴다([git 트리 비교로 PR에서 통과한 main 커밋의 E2E 재실행 생략하기](/memo/faster-e2e-ci)).

12일에는 글 요약의 '이동'이라는 단어가 휴대폰 메모 E2E의 '이동' 버튼 탐색(부분 일치)에 함께 잡혀 시험이 실패했다.

### 롤백 훈련 (18일)

배포 스크립트는 새 이미지가 헬스 체크를 통과하지 못하면 이전 버전으로 되돌리도록 작성되어 있었지만 실제로 확인한 적은 없었다. 헬스 체크에 항상 실패하는 훈련용 이미지를 운영 서버에 배포해 확인했다([#254](https://github.com/hyeoniverse/MacFolio/pull/254), [롤백 훈련](/memo/rollback-drill)).

1. **훈련 전 상태 기록:** 현재 태그 `sha-7e7eac0`, 컨테이너 healthy, `/health`도 같은 버전을 응답

![훈련 전 서버 상태](./images/rollback-drill-server-before.jpg '훈련 전. API_TAG와 컨테이너 상태, /health 응답을 먼저 기록했다. 접속 주소는 마스킹했다')

2. **훈련용 이미지 배포:** 헬스 체크에 항상 실패하는 `sha-dead000` 이미지를 빌드해 올리고, GitHub Actions의 "API 배포" 워크플로를 그 태그로 수동 실행
3. **롤백 확인:** 워크플로는 3분 만에 실패로 종료됐고, 서버 로그에는 `09:04:53 이전 버전으로 되돌린다: sha-7e7eac0` 다음에 `09:05:34 배포 실패, 되돌림: sha-7e7eac0가 다시 떠 있다`가 기록됐다. 롤백에 걸린 시간은 41초다

![서버 로그의 되돌림](./images/rollback-drill-server-log.jpg '훈련 중 서버 로그. 새 이미지가 헬스 체크를 통과하지 못하자 41초 만에 이전 태그로 복구됐다')

4. **최종 상태 확인:** `watch docker compose ps`로 `sha-7e7eac0` 컨테이너가 healthy로 유지되는 것을 확인

```bash
cd ~/deploy
grep '^API_TAG=' .env                 # 훈련 전 태그 기록
docker compose ps api                 # (healthy) 확인
curl -s https://<API 주소>/health; echo
# 훈련용 이미지를 배포한 뒤
watch docker compose ps               # 이전 태그가 healthy로 유지되는지 확인
```

절차와 복구 방법은 [docs/rollback-drill.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/rollback-drill.md)와 [ops/deploy.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/deploy.sh)에 있고, 헬스 체크는 [Docker의 HEALTHCHECK 문서](https://docs.docker.com/reference/dockerfile/#healthcheck)를 따랐다.

### 4000번 포트를 점유한 이전 API 컨테이너 (14일·15일)

14일, 편집 화면에서 저장하자 `Cannot PUT /site/projects` 오류가 발생했다. 코드에는 이 경로가 있었다. 4000번 포트에서 응답한 것은 개발 서버가 아니라 예전에 빌드한 API 이미지로 실행된 Docker 컨테이너 `macfolio-api-1`이었다.

![4000번 포트를 점유한 이전 API 컨테이너](./images/day-1014-port.svg '요청은 4000번 포트를 먼저 점유한 이전 API 컨테이너로 갔다. 개발 서버의 API는 포트를 얻지 못해 종료된 상태였다')

1. 컨테이너가 4000번 포트를 먼저 점유했다
2. `pnpm dev:all`의 API는 포트를 얻지 못해 `EADDRINUSE`로 종료됐다
3. 화면의 요청은 이전 API로 전달됐고, 이전 API에는 `PUT /site/projects` 경로가 없었다

`docker stop macfolio-api-1` 후 개발 서버를 다시 실행해 해결했고, 개발 서버도 쓰는 DB 컨테이너는 유지했다. 15일 밤에는 docker compose로 다시 실행된 같은 컨테이너가 로그인 400("로그인 요청이 올바르지 않습니다.")의 원인이 됐다.

1. 배포용 이미지라 `NODE_ENV=production`이다
2. 그래서 OAuth state 검증용 쿠키에 `Secure` 속성이 붙는다
3. 브라우저는 http인 `localhost:4000`에 `Secure` 쿠키를 다시 전송하지 않을 수 있다
4. GitHub에서 돌아왔을 때 비교할 state 쿠키가 없어 400을 반환한다

같은 시각 개발 서버 오류는 main에 새로 추가된 `@macfolio/contracts`가 로컬 `node_modules`에 링크되지 않은 것이 원인이라 `pnpm install`로 해결했다.

> [!CAUTION]
> 14일에는 #187의 2단계 작업이 중단된 사이 임시 작업 폴더(`/tmp`)가 삭제되어, 커밋하지 않은 결과가 남지 않았다. 2단계는 16일에 처음부터 다시 진행했다.

## Finder 문서 폴더와 미리보기 앱 (18일)

18시부터 이슈 [#8](https://github.com/hyeoniverse/MacFolio/issues/8)을 정리하며 Finder 작업을 시작했다.

| 결정 사항      | 내용                                                                             |
| -------------- | -------------------------------------------------------------------------------- |
| 파일 저장 위치 | 저장소가 아니라 Cloudflare R2. 사이트 Worker가 같은 출처의 `/files/` 경로로 제공 |
| 폴더 구조      | 기존 저장소 Markdown 문서와 별도로 이력서·포트폴리오·자격증 폴더                 |
| 파일 열기      | PDF와 그림은 Finder 안이 아니라 별도의 미리보기 앱에서 연다                      |

![Finder의 문서 폴더](./images/day-1018-finder-docs.jpg#float-right 'Finder의 문서 폴더. 이력서·포트폴리오·자격증 폴더를 18일에 추가했다. 사이드바의 데스크탑·블로그는 다음 날 화면')

처음에는 PDF와 그림을 Finder 창 안에서 표시했다가, 18시 37분에 macOS처럼 별도 창으로 실행되는 미리보기 앱으로 옮겼다. 18시 53분에는 브라우저 내장 PDF 뷰어 대신 pdf.js로 페이지를 직접 렌더링했다. 페이지 썸네일, 검색, 텍스트 선택, 배율을 앱에서 직접 제어하기 위해서다. 관리자 파일 업로드는 API 서버를 거치지 않고 R2로 직접 전송한다([Cloudflare R2 파일을 Worker가 같은 출처 /files/로 제공하기](/memo/finder-files)).

```text
브라우저 ── 폴더·이름·크기 ──▶ API: 관리자 세션, 파일 종류, 20MB 이하 확인
브라우저 ◀── 5분 유효한 서명 URL ── API
브라우저 ── 파일 본문 ──▶ R2 (API 서버를 거치지 않음)
```

이 작업은 [#255](https://github.com/hyeoniverse/MacFolio/pull/255)로 올려 다음 날 새벽에 머지했다.

같은 저녁 음악 앱 버그 세 가지를 [#257](https://github.com/hyeoniverse/MacFolio/pull/257)로 수정했다([isRunning 정의와 React key·ref 함수 동일성이 일으킨 음악 앱 버그](/memo/music-player-fixes)). 배경 음악이 재생 중인데 Dock의 음악 아이콘에 실행 표시가 없음, 셔플을 누르면 재생 막대의 앨범 표지가 겹쳐 쌓임, '지금 재생 중' 시트를 끝없이 아래로 스크롤할 수 있음이다. 첫째는 창이 열려 있는지와 앱이 실행 중인지를 하나의 값(`isRunning`)으로 관리하는 구조가 2024년 10월의 첫 React 코드부터 있었기 때문이다([2024년 10월 14일 회고](/memo/history-2024-2025#최소화-애니메이션-위치-저장-최대화-2024년-10월-14일)). 음악은 창이 없어도 배경 음악으로 재생될 수 있으므로 두 상태를 별도의 값으로 분리했다.

## 돌아보며

**무엇을 만들지 먼저 정한 작업은 한 번에 끝났다.** Modal·Sheet·SearchField는 사용처 집계로 대상을 3개로 줄인 뒤 PR 하나씩으로 끝났다. 후보 9개를 모두 만들었다면 형태가 다른 것을 묶느라 옵션이 늘어난 컴포넌트가 6개 더 생겼을 것이다. 리팩터링 PR도 "무엇이 동일해야 하는가"(값, 빌드한 CSS 바이트, 계산된 스타일)를 먼저 정해 검증이 빨랐다.

**기준 없이 시작한 작업은 반복됐다.** #187의 템플릿은 "빈 곳 없이", "제품 랜딩 페이지처럼" 같은 화면 인상을 기준으로 만들었다가 장식을 넣고 다음 날 제거했다. 구조가 안정된 것은 모든 템플릿이 같은 데이터(`landingOf`)를 읽고 템플릿마다 참고할 실제 제품을 정한 뒤였다. RPG 대화창도 "거칠다", "어둡다" 같은 인상으로 한 축씩 바꿨다. 메일 입력 칸 오류는 여섯 번째에 macOS 메일 방식을 따랐다. macOS를 재현하는 사이트이므로 처음부터 macOS 화면을 확인해야 했다.

**큰 PR은 분리로 머지했다.** #187은 일주일 동안 커밋 61개, 4만 줄을 넘겼고, 그 안에 main의 CSS 레이어 버그 수정이 묻혀 main에서 같은 버그를 다시 찾았다. 머지를 가능하게 한 것은 RPG 대화창을 다른 브랜치로 옮긴 분리였고, 머지 직전에 넣은 1만 5천 줄 구조 변경은 22분 만에 되돌렸다. 편집 화면, 템플릿, 저장소 언어 API는 각각 따로 머지할 수 있는 단위였다.

**검증 규칙은 데이터가 들어오는 모든 경로에서 같아야 한다.** 편집기는 요약 200자 초과를 막았지만 저장소 글은 그 규칙으로 검사한 적이 없어, `validateDraft`를 시험에 쓰자 18편이 한꺼번에 드러났다.

**오류 문구보다 응답한 프로세스를 먼저 확인한다.** `Cannot PUT`과 로그인 400은 같은 이전 컨테이너가 원인이었다. 이런 오류는 코드보다 먼저 `docker ps`, `lsof -i :4000`으로 ==포트에서 응답하는 프로세스를 확인하는 편이 빠르다.== 오래 걸리는 작업의 중간 결과는 `/tmp`가 아니라 작업 브랜치에 커밋해 둔다. ECR 한도처럼 재실행으로 넘어가던 실패는 나흘 동안 다섯 번 반복된 뒤에야 구조로 해결했다.
