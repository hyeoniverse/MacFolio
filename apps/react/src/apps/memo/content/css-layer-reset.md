[게시 버튼 글자가 흐렸던 이유](/memo/memo-button-specificity) 글을 쓰고 나서 남은 숙제가 있었다. 게시 버튼 하나만 고쳤을 뿐, 원인은 그대로였다. 이 글은 그 원인을 걷어 낸 기록이고, 공통 컴포넌트 작업([#57](https://github.com/hyeoniverse/MacFolio/pull/57))의 첫 커밋이다.

10월 1일 새벽, 게시 버튼 글을 읽으면서도 `:where(.memo) button`이 왜 문제인지 한 번에 들어오지 않았다. 공통 버튼 컴포넌트가 따로 없는지, 클래스와 스타일이 어떤 구조로 얽혀 있는지 그림으로 정리해 보니, 앱마다 루트에 기본값을 깔고 그 위에 `!important`로 덮는 구조가 보였다. 컴포넌트 정리가 덜 됐다는 것이 분명해서, 이 글의 층 정리를 시작으로 공통 컴포넌트를 만드는 리팩터링으로 이어 가기로 했다.

## 원인은 앱 루트의 기본값

메모 앱의 CSS 맨 위에는 이런 규칙이 있다.

```css
.memo button {
	font: inherit;
	color: inherit;
	cursor: pointer;
}
```

버튼이 브라우저 기본 글꼴(Arial 등) 대신 앱의 글꼴·글자색을 따르게 하려는 규칙이다. 메일(`.mail button`), 메시지, 음악, 터미널 단축어에도 같은 규칙이 있고, Safari에는 링크용(`.safari a`)이 있다.

문제는 점수다. `.memo button`은 클래스 하나 + 태그 하나라 **(0, 1, 1)**이다. 버튼마다 붙인 클래스(`.memo-tool`, `.memo-writer-publish`)는 **(0, 1, 0)**이다. 기본값이 버튼 규칙을 이긴다. 그래서 버튼마다 적은 색과 글꼴이 무시되었고, 그때마다 `!important`로 덮거나 선택자를 길게 써서 점수를 맞췄다.

앱 전체를 세어 보니 `!important`가 72개였다. 메모 27, 메시지 13, 음악 11, GitHub 7, 메일 6, 터미널 4, Safari 4개다. 대부분이 버튼·링크의 색과 글꼴이었다.

## 점수 대신 층

CSS 층(`@layer`)을 쓰면 규칙끼리 비교하는 순서가 바뀐다. 브라우저는 **층을 먼저 비교하고**, 같은 층일 때만 점수를 본다. 층 밖에 둔 평소의 규칙은 어느 층의 규칙도 이긴다.

![층 밖의 규칙이 층 안의 규칙을 이긴다](./images/css-layer-cascade.svg '기본값만 reset 층에 넣으면 점수가 높아도 진다')

기본값 여섯 개를 `reset` 층으로 옮겼다.

```css
/* styles/layers.css: 다른 CSS보다 먼저 불러와 층 순서를 정한다 */
@layer reset;

/* apps/memo/Memo.css */
@layer reset {
	.memo button {
		font: inherit;
		color: inherit;
		cursor: pointer;
	}
}
```

고를 수 있는 길은 셋이었다.

| 방법                                    | 좋은 점                                  | 나쁜 점                                                              |
| --------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------- |
| 버튼마다 `!important`를 계속 붙인다     | 지금처럼 하면 된다                       | 72개가 계속 는다. 상태(올렸을 때·눌렸을 때)마다 또 겨룬다            |
| `:where(.memo) button`으로 점수를 0으로 | 층 없이 된다. 브라우저 지원이 넓다       | "기본값"이라는 뜻이 코드에 드러나지 않는다. 층을 더 둘 때 쓸 수 없다 |
| `@layer reset`                          | 뜻이 이름으로 드러난다. 층을 늘리기 쉽다 | 층 순서를 정하는 파일을 가장 먼저 불러와야 한다                      |

`:where(.memo) button`으로 점수를 0으로 낮춰도 같은 결과가 나온다. 하지만 층은 "이건 기본값"이라는 뜻이 이름(`reset`)으로 드러난다. 또 다음 단계에서 공통 컴포넌트 층을 하나 더 둘 때도 한 줄(`@layer reset, components;`)로 순서를 정할 수 있어서 층을 골랐다.

옮긴 곳은 여섯 파일이다. `Memo.css`(`.memo button`), `Mail.css`, `Messages.css`, `Music.css`, `Shortcuts.css`(`.shortcuts button`), `Safari.css`(`.safari a`). 층 순서를 정하는 `styles/layers.css`는 `main.tsx`가 다른 CSS보다 먼저 불러오게 첫 줄에 넣었다.

```ts
// main.tsx (이때)
import './styles/layers.css';
import './styles/theme.css';
import './styles/motion.css';
import './index.css';
```

이 "가장 먼저"가 빌드 결과에서는 지켜지지 않을 수 있다는 것은 열하루 뒤에 알았다([CSS 층 순서는 처음 나온 파일이 정한다](/memo/css-layer-order-fix)).

## 무엇이 바뀌는지 미리 알 수 없다

이 변경은 코드 몇 줄이지만, 효과는 앱 전체에 흩어져 있다. 지금까지 기본값에 덮여 있던 값이 **한꺼번에 살아나기** 때문이다. 어디서 무엇이 살아날지는 CSS만 읽어서는 알기 어렵다.

그래서 화면을 찍어 비교했다. E2E의 가짜 API로 장면 20개를 만들고, 밝은 화면·어두운 화면으로 각각 찍었다(40장).

- 데스크톱, Apple 메뉴, 음량 조절, 음악, 메시지, 메일, 터미널, 설정, GitHub, Safari
- 메모: 읽기, 우클릭 메뉴, 정렬 메뉴, ••• 메뉴, 갤러리
- 메모 편집기: 서식 메뉴, 날짜 고르기, 폴더 고르기, 표 손잡이 메뉴

휴대폰(iPhone 크기)에서도 홈 화면, 단축어, 메모, 메일, 메시지, 음악, 설정, Safari, 제어 센터를 같은 방법으로 찍었다(18장).

두 폴더의 같은 장면을 Chromium의 canvas로 읽어, 색이 일정 이상 다른 픽셀을 빨갛게 칠하고 비율을 셌다.

```ts
for (let i = 0; i < a.length; i += 4) {
	const d = Math.abs(a[i] - b[i]) + Math.abs(a[i + 1] - b[i + 1]) + Math.abs(a[i + 2] - b[i + 2]);
	if (d > 30) diff++; // 그리고 그 픽셀을 빨갛게
}
```

먼저 **아무것도 바꾸지 않고** 두 번 찍어 비교했다. 거의 모든 장면이 0.03% 다르게 나왔다. 메뉴 막대의 시계였다. 찍을 때마다 분이 바뀌거나 1초 단위로 다시 그려진다. Playwright의 `page.clock.setFixedTime()`으로 시각을 고정하자 0.001%만 남았다. 이 정도면 남은 차이는 모두 진짜 변화다.

![같은 장면을 전후로 찍고, 시각을 고정하고, 픽셀 차이를 세는 순서](./images/css-layer-reset-compare-steps.svg '먼저 같은 코드로 두 번 찍어 잡음을 없앤 뒤 전후를 비교했다')

## 바뀐 것은 넷

바꾼 뒤 58장을 다시 찍었다. 데스크톱의 메일·메시지·음악·터미널·Safari·설정과 휴대폰의 홈·단축어·메모·메일·메시지·설정·Safari·제어 센터는 **0%**였다. 바뀐 곳은 넷이다. 셋은 CSS에 적어 둔 값이 이제야 먹은 것이고, 하나(음량 조절)는 같이 지운 남은 CSS 때문이다.

**메모 편집기 (1~1.7%)**: 화면 대부분이 빨갛게 나왔지만 실제로는 하나였다. 게시 버튼에 적어 둔 `font-size: 11px; font-weight: 600`이 살아나 버튼 높이가 조금 줄었고, 그 아래 날짜·제목·본문이 2px 위로 올라온 것이다.

![차이 그림](./images/css-layer-diff.jpg '빨간 픽셀이 다른 곳. 게시 버튼이 줄어 그 아래가 통째로 2px 올라왔다')

![게시 버튼](./images/css-layer-publish.jpg '전: 부모 글꼴을 따른 12px. 후: 적어 둔 대로 11px, 굵게')

**폴더 펼치기 화살표 (0.006%)**: `font-size: 8px`로 적어 둔 화살표가 부모 크기로 그려지고 있었다. 작아지니 macOS의 사이드바 화살표에 더 가깝다.

![폴더 화살표](./images/css-layer-disclosure.jpg '전: 부모 글꼴 크기. 후: 적어 둔 8px')

**휴대폰 음악의 재생 목록 (0.7%)**: 휴대폰에서는 iOS 음악 앱처럼 목록 글자를 `17px`로 키우는 규칙이 있었다. 이것도 `.music button`의 `font: inherit`에 덮여 데스크톱 크기 그대로였다.

![휴대폰 음악 재생 목록](./images/css-layer-music.jpg '전: 부모 글꼴 크기. 후: 적어 둔 17px (iOS 음악 앱의 목록 크기)')

**음량 조절 (93%)**: 이건 층이 아니라 같이 지운 **남은 CSS** 때문이다. 상태 막대의 CSS에 예전 음량 창의 규칙이 남아 있었다. 실제 음량 창의 CSS보다 늦게 불러와져 그 값을 덮고 있었다.

- 화면 전체를 어둡게 덮는 배경
- 세로로 돌린 슬라이더의 폭을 `9rem`에서 `100%`(2rem)로 줄이는 규칙

이 둘이 남아 있어서, 음량 창을 열면 화면이 어두워지고 슬라이더를 끌 수 있는 자리도 좁았다. 남은 규칙을 지우자 원래 의도대로 화면을 덮지 않는 작은 조절기가 되었다.

![음량 조절](./images/css-layer-volume.jpg '전: 화면 전체가 어두워진다. 후: 조절기만 뜬다')

## 같이 정리한 것

- 정의되지 않은 `--duration-normal`을 쓰던 곳(표 고르기 테두리 움직임 다섯 줄)을 있는 토큰 `--duration`으로 바꿨다
- 두 파일(알림, 휴대폰 화면)에 똑같이 있던 `.visually-hidden`을 전역 CSS 하나로 옮겼다
- 쓰는 곳이 없는 규칙을 지웠다: 상태 막대의 `.close-button`·`.volume-modal`, 터미널 단축어의 `.shortcut-back`

커밋은 파일 8개, +61/−43이다. CSS 여섯 파일에서 기본값 규칙을 `@layer reset { … }`으로 감싼 것이 대부분이고, `layers.css`(10줄)와 `main.tsx`(1줄)가 더해졌다.

| 장면 묶음              | 장 수 | 바뀐 장면                                                        |
| ---------------------- | ----- | ---------------------------------------------------------------- |
| 데스크톱 (라이트·다크) | 40    | 메모 편집기 1~1.7%, 폴더 화살표 0.006%, 음량 조절 93%. 나머지 0% |
| 휴대폰 (라이트·다크)   | 18    | 음악 재생 목록 0.7%. 나머지 0%                                   |

## !important는 아직 그대로

이제 `!important` 대부분은 필요 없다. 하지만 한꺼번에 지우지 않았다. `!important`는 기본값만이 아니라 **같은 버튼의 다른 상태**(올렸을 때, 눌렸을 때)와도 겨루고 있을 수 있다. 하나씩 지우면서 그 버튼의 모든 상태를 확인해야 한다.

다음 단계에서 공통 컴포넌트(`IconButton`, `Button`, `Menu`)를 만들어 버튼을 옮긴다. 그때 그 버튼의 CSS를 새로 쓰면서 `!important`를 걷어 낸다. 전후 비교도 같은 방법으로 한다.

## 그 뒤: !important는 얼마나 줄었나

이 글을 다듬으며 저장소의 CSS에서 `!important`가 든 줄을 다시 셌다(`git grep -c`). 글을 쓸 때 센 72개는 앱 CSS만 센 것이고, 전역 CSS까지 줄 단위로 세면 74줄이다.

![!important가 든 줄: 이 커밋 전 74, 공통 IconButton PR 뒤 4, 지금 23](./images/css-layer-reset-important-count.svg '줄 단위로 센 !important. 지금 남은 것은 대부분 Safari 프로젝트 페이지와 움직임 줄이기 규칙')

다음 PR([#60](https://github.com/hyeoniverse/MacFolio/pull/60), [아이콘 버튼 옮기기](/memo/icon-button-migrate))에서 4줄까지 줄었다. 지금은 23줄이다. 주석 2줄(`layers.css`), 움직임 줄이기 설정에서 애니메이션을 끄는 5줄(`motion.css`), 그리고 나중에 만든 Safari 프로젝트 페이지들의 16줄이다. 프로젝트 페이지 쪽은 앱 기본값과 싸우는 것이 아니라 페이지 안에서 부품 모양을 덮는 용도라, 다음에 따로 본다.

## 배운 것

- `!important`가 많다는 것은 증상이지 원인이 아니다. 72개를 하나씩 지우기 전에 "왜 필요했나"를 찾으니 원인은 기본값 규칙 여섯 개였다.
- 효과가 앱 전체에 흩어지는 CSS 변경은 화면을 찍어 비교하는 것이 가장 빠른 확인이다. 다만 비교하기 전에 같은 코드로 두 번 찍어 잡음(시계)을 먼저 없애야 한다. 그래야 남은 차이를 모두 진짜 변화로 읽을 수 있다.
- 기본값에 덮여 있던 값이 살아나는 것은 "고장"이 아니라 "원래 의도가 이제야 먹은 것"일 수 있다. 바뀐 넷 가운데 셋이 그랬다.
