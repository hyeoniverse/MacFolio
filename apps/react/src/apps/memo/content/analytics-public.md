[트래픽 분석 3](/memo/analytics-activity-monitor)까지는 '활동 상태 보기'가 관리자 전용이었다. 방문자가 열면 잠긴 화면만 보였다. 써 보니 아까웠다. 포트폴리오를 보러 온 사람에게 "직접 만든 분석이 이렇게 돈다"를 보여 줄 수 있는 앱인데, 정작 그 사람은 볼 수 없었다. Launchpad에도 없으니 이런 앱이 있는지조차 알 수 없었다.

관리자 전용 버전을 커밋하고 세 시간이 안 되어 같은 PR [#162](https://github.com/hyeoniverse/MacFolio/pull/162)에서 방향을 바꿨다. 서버 쪽 커밋은 7개 파일 220줄, 화면 쪽 커밋은 13개 파일 211줄을 더했다.

## 무엇을 공개하나

전부 공개할 수는 없었다. 걸린 것은 둘이었다.

- **캠페인(`utm_campaign`):** 이력서나 지원서에 붙이는 링크에 보통 회사 이름을 넣는다. 그대로 공개하면 어디에 지원했는지가 드러난다. 들어온 곳의 주소(호스트)도 비슷하다
- **실시간:** 방문 하나하나의 흐름과 가린 IP가 있다. 합계가 아니라 사람 단위다

그래서 이렇게 나눴다.

| 누구나                                                                                                                                                  | 관리자만                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 개요(방문·순방문자·앱 열기·머문 시간, 그래프), 앱·글·바깥 링크, 나라·기기·브라우저·OS·언어, 들어온 곳의 **묶음**(검색·소셜·직접·링크), 블로그 글 조회수 | 들어온 곳의 주소, `utm_source`·`utm_campaign`, 실시간 |

## 어디서 나눌까

| 방법                                           | 좋은 점                              | 문제                                                     |
| ---------------------------------------------- | ------------------------------------ | -------------------------------------------------------- |
| 화면에서만 감추기                              | 서버를 안 고친다                     | 숫자는 이미 브라우저에 와 있다. 개발자 도구로 다 보인다  |
| 방문자용 경로를 따로 (`/summary/public`)       | 경로마다 권한이 분명하다             | 계산 코드가 둘로 갈리거나, 같은 함수를 두 번 감싸야 한다 |
| 같은 경로, 서버가 세션을 보고 나눔 (고른 방법) | 계산은 하나, 응답에 `scope`가 붙는다 | 경로에 Guard를 붙일 수 없어 서비스 안에서 나눠야 한다    |

## 서버가 나눈다

화면에서 감추는 것으로는 부족하다. 숫자는 이미 브라우저에 와 있으니 개발자 도구로 볼 수 있다. 그래서 요약 경로(`GET /analytics/summary`)를 누구나 부르게 열되, **서버가** 관리자 세션을 보고 줄 표를 정한다. 관리자가 아니면 들어온 곳의 주소와 utm 표를 빈 목록으로 주고, 응답에 `scope: 'public'`을 적는다. 실시간(`/analytics/live`)은 그대로 관리자만 부른다.

![요약 응답을 서버가 나눈다](./images/analytics-public-scope.svg '같은 경로에 관리자 세션 여부로 줄 표를 정한다')

```ts
const hidden = new Set<string>(scope === 'admin' ? [] : ADMIN_ONLY_BREAKDOWNS);
```

어느 표가 관리자 전용인지는 목록(`ADMIN_ONLY_BREAKDOWNS`) 하나로 정한다. 지금은 `packages/contracts`에 있어서, 화면도 같은 목록을 보고 안내를 띄운다. 표를 하나 더할 때 이 목록에 넣을지만 정하면 된다.

들어온 곳의 묶음(검색·소셜·직접·링크)은 화면에서 나누던 것을 서버로 옮겼다. 방문자에게 주소를 주지 않으니 묶는 일도 서버가 해야 한다. 규칙이 한 곳에만 있게 되었다. 지난 날의 집계는 주소별로 저장돼 있어서, 요약을 낼 때 주소를 묶음으로 바꿔 더한다. 저장된 집계를 다시 만들 필요가 없다.

![방문자와 관리자의 길](./images/analytics-public-paths.svg '방문자 요청은 1분 캐시와 5분에 한 번 모으기를 거친다')

누구나 부르는 경로가 되니 부하도 생각했다. 1년치를 계속 요청해도 DB를 매번 읽지 않게, 방문자용 요약은 같은 기간이면 1분 동안 같은 값을 준다. 요약을 열 때 지난 날을 모으는 일도 방문자 요청에서는 5분에 한 번만 한다(날이 바뀌었으면 바로). 관리자는 드물게 여니 열 때마다 모은다.

```ts
private async cached<T>(key: string, now: Date, compute: () => Promise<T>): Promise<T> {
	const hit = this.publicCache.get(key);
	if (hit && now.getTime() - hit.at < PUBLIC_CACHE_MS) return hit.value as T;
	const value = await compute();
	if (this.publicCache.size > 500) this.publicCache.clear();
	this.publicCache.set(key, { at: now.getTime(), value });
	return value;
}
```

캐시는 서버 메모리의 `Map` 하나다. 키는 `summary:<from>:<to>`라 기간 조합마다 하나씩 생긴다. 누군가 기간을 바꿔 가며 계속 부르면 키가 끝없이 늘 수 있어서, 500개를 넘으면 통째로 비운다. Redis를 두기에는 서버가 작고, 1분짜리 캐시를 잃어도 다시 계산하면 그만이다.

화면은 서버가 준 `scope`를 보고 그린다. 방문자에게는 개요의 '가장 많이 들어온 곳' 대신 묶음 표를, 유입 경로 탭에는 묶음 표와 "관리자만 볼 수 있습니다" 안내를, 실시간 탭에는 안내와 로그인 버튼만 보여 준다. 실시간은 서버에 묻지도 않는다. 앱 정보의 `adminOnly`와 Launchpad·홈 화면·Finder에서 감추던 코드는 걷어 냈다.

## 블로그 글 조회수

글을 볼 때마다 `item` 이벤트(`memo/<글 주소>`)가 이미 가고 있었다. 숫자를 세는 규칙 하나와 경로 하나를 더했다.

- **한 방문에서 같은 글은 한 번.** 메모에서 글 사이를 오가면 같은 글을 여러 번 고르게 된다. 하루치를 모을 때 (방문, 글) 쌍마다 한 번만 센다
- **`GET /analytics/views?app=memo`:** 글마다 전체 기간 조회수. 지난 날은 날마다 모은 숫자의 합, 오늘은 이벤트에서 바로 센다. 누구나 부르고 1분 동안 같은 값을 준다

메모는 앱을 열 때 이 값을 한 번 받아, 글 머리의 날짜 옆에 "조회 42"를 붙인다. 서버가 없으면 붙이지 않는다. '활동 상태 보기'의 앱·글 탭에는 "블로그 글 조회수 (전체 기간)" 표를 더하고, 글 주소 대신 제목을 보여 준다. 기간별 "글·프로젝트" 표도 메모 글은 제목으로 바꿨다.

## 탭을 바꾸면 정렬이 따라왔다

화면 테스트를 고치다가 버그를 하나 찾았다. 유입 경로 탭에서 표를 이름순으로 바꾼 뒤 앱·글 탭으로 가면, 블로그 글 조회수 표가 많은 순이 아니라 이름 역순으로 나왔다.

탭마다 표가 다르지만, React가 보기에는 **같은 자리의 같은 컴포넌트**였다. 그래서 표 안의 정렬 상태를 그대로 두고 내용만 바꿨다. 탭 본문에 `key={tab}`을 주어 탭이 바뀌면 새로 그리게 했다. 시험은 원래 있던 것이 그대로 잡는다: 이름순으로 바꾼 뒤 앱·글 탭에서 많은 순인지 본다.

![key={tab}으로 고친 버그](./images/analytics-public-tab-key.svg '정렬 상태가 표 안에 있어서, 자리가 같으면 탭을 넘어 따라왔다')

정렬 상태를 탭마다 위로 끌어올리는 방법도 있었다. 하지만 탭을 오갈 때 정렬을 기억할 이유가 없었고, `key` 한 줄이 더 작았다.

## 시험

- API 단위(`apps/api/src/analytics/rules.test.ts`): 한 방문에서 같은 글은 한 번, 들어온 곳 묶음
- API e2e(`apps/api/test/analytics.e2e.test.ts`): **요약은 누구나 보지만 방문자에게는 들어온 곳의 호스트·utm이 없다. 실시간은 관리자만**. 응답 JSON 전체를 글자로 바꿔 `kakao-2026` 같은 캠페인 값이 어디에도 없는지 본다. 표 하나만 보면 다른 필드로 새는 것을 놓친다. **글 조회수: 전체 기간, 한 방문에서 같은 글은 한 번. 누구나 본다**는 지난 날의 합과 오늘을 더하는지까지 본다.
- 화면(`apps/react/e2e/activity.spec.ts`): **방문자도 Launchpad에서 열어 공개 숫자를 본다. 들어온 곳의 주소·캠페인과 실시간은 관리자만**, **블로그 글 머리에 조회수 (전체 기간). 서버가 없으면 감춘다**, **서버가 없으면 블로그 글에 조회수가 없다**

## 남은 것, 배운 것

- 나라·언어 표는 방문자에게도 보인다. 방문이 아주 적은 날에는 "어제 일본에서 1명"처럼 사람을 짐작할 수도 있다. 지금 방문 규모에서는 받아들였지만, 적은 값을 묶어 "기타"로 보이는 방법을 생각할 만하다.
- 캐시는 서버 메모리라 서버를 다시 띄우면 비고, 서버가 여러 대면 서로 다른 값을 줄 수 있다. 한 대라 문제는 없다.
- 공개할지 말지는 "합계인가, 사람 단위인가"와 "적은 값이 무엇을 드러내는가"로 나누면 쉬웠다. 캠페인 이름은 합계여도 어디에 지원했는지를 드러낸다.

## 직접 확인하기

같은 요약 경로를 방문자와 관리자로 불러 응답을 비교한다. 방문자 응답에는 `scope`가 관리자가 아니고, 들어온 곳은 묶음 이름만 있다.

```bash
curl -s "https://macfolio-api.hyeoniverse.com/analytics/summary" | head -c 400; echo
curl -s "https://macfolio-api.hyeoniverse.com/analytics/views?app=memo" | head -c 200; echo   # 글 조회수
```

관리자 쪽은 브라우저에서 로그인한 채 활동 상태 보기를 열어 호스트·UTM 표가 보이는지 본다. 나누는 규칙은 서버 시험이 확인한다.

```bash
pnpm --filter @macfolio/api test -- src/analytics/rules.test.ts
pnpm --filter @macfolio/api test:e2e test/analytics.e2e.test.ts
```

경로 설명은 [Swagger](https://macfolio-api.hyeoniverse.com/docs), 공개하는 숫자의 범위는 [docs/privacy.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/privacy.md)에 있다.
