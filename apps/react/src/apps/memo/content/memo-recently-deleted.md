메모를 지울 때마다 "지울까요?"라고 물었다. 묻는 이유는 되돌릴 수 없어서였다. macOS 메모는 묻지 않는다. 지운 메모는 '최근 삭제된 항목'으로 가서 30일 동안 남고, 그 안에서 되살리거나 영구히 지운다. 같은 방식으로 바꿨다([PR #64](https://github.com/hyeoniverse/MacFolio/pull/64)).

## 배경

블로그를 메모 앱 안에서 직접 쓰다 보니 글을 정리하면서 지우는 일이 잦았다. 확인 창은 한 번 더 누르게 할 뿐, 잘못 누른 뒤에는 도움이 되지 않았다. 한 번 지운 글은 게시한 내용·임시 저장·버전 기록이 모두 서버에서 사라져서 되살릴 방법이 없었다. 확인 창을 더 무섭게 만드는 것보다, 지우기는 가볍게 하고 되돌릴 길을 두는 편이 낫다고 판단했다.

고를 수 있는 방법은 세 가지였다.

| 방법                                        | 좋은 점                                       | 문제                                                                                                   |
| ------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 확인 창을 그대로 둔다                       | 할 일이 없다                                  | 습관적으로 누르면 막지 못한다. 되살릴 길이 없다                                                        |
| 지운 글을 별도 휴지통 표로 옮긴다           | 보통 글 질의가 단순하다                       | 글·임시 저장·버전을 표 두 개 사이에서 옮겨야 하고, 저장소 글을 가리는 표시는 여전히 Post에 있어야 한다 |
| Post에 지운 때(`deletedAt`)를 더한다 (고름) | 칸 하나, 마이그레이션 6줄. 옮길 데이터가 없다 | 지운 글을 빼는 조건을 질의마다 챙겨야 한다                                                             |

이미 `deleted` 표시로 저장소 글을 가리고 있었으므로, 같은 행에 지운 때만 더하는 세 번째가 가장 작은 변경이었다.

![최근 삭제된 항목](./images/memo-trash.jpg '폴더 목록 맨 아래의 최근 삭제된 항목. 본문 위 안내 상자에 되돌려 놓기·즉시 삭제')

## 지운 때

예전에도 글을 지우면 행을 없애지 않고 `deleted` 표시만 남겼다. 블로그 글의 상당수는 저장소의 Markdown 파일이라 파일을 지울 수 없어서, "이 주소의 글은 가린다"는 표시가 필요했기 때문이다. 다만 지우면서 임시 저장을 비웠고, 언제 지웠는지는 몰랐다.

그래서 `deletedAt`을 더했다. 표시의 뜻이 이렇게 나뉜다.

| deleted | deletedAt | 뜻                                                       |
| ------- | --------- | -------------------------------------------------------- |
| false   | 없음      | 보통 글                                                  |
| true    | 있음      | 최근 삭제된 항목 (30일 동안 되살릴 수 있다)              |
| true    | 없음      | 영구히 지운 글 (저장소의 같은 주소 파일을 가리기만 한다) |

![세 상태와 옮겨 가는 길](./images/memo-recently-deleted-states.svg '보통 글 → 최근 삭제된 항목 → 영구히 지운 글. 되살리기는 가운데에서만 된다')

마이그레이션(`20261001100000_post_deleted_at/migration.sql`)은 칸을 더하기만 했다. 이미 지운 글은 `deletedAt`이 비어 있으니 영구히 지운 글로 본다. 지운 때가 있는데 지운 글이 아닌 상태는 있을 수 없으므로 DB 제약으로 막았다.

```sql
ALTER TABLE "Post" ADD COLUMN "deletedAt" TIMESTAMP(3);
ALTER TABLE "Post" ADD CONSTRAINT "Post_deleted_at" CHECK ("deletedAt" IS NULL OR "deleted");
```

제약을 적고 나서 보니 놓친 곳이 있었다. 지운 글을 다시 게시하거나 임시 저장하면 `deleted`를 `false`로 되돌리는데, `deletedAt`은 그대로 두고 있었다. 그대로였다면 제약에 걸려 저장이 실패했을 것이다. 두 곳 모두 `deletedAt: null`을 같이 넣었다.

## 되살리기와 영구 삭제

| 하는 일   | 서버                                                                         |
| --------- | ---------------------------------------------------------------------------- |
| 지우기    | `deleted`, `deletedAt`만 바꾼다. 게시한 내용·임시 저장·버전은 그대로         |
| 되살리기  | `deleted`·`deletedAt`을 지운다. 서버에 내용이 없던 저장소 글이면 행을 지운다 |
| 영구 삭제 | 내용·임시 저장·버전을 지우고 가리는 표시만 남긴다                            |
| 30일 뒤   | 관리자 목록을 읽을 때 지운 지 30일이 지난 글을 영구 삭제한다                 |

API는 두 개를 더했다. `POST /posts/:slug/restore`가 되살리고, `DELETE /posts/:slug/permanent`가 영구히 지운다. 기존 `DELETE /posts/:slug`는 이제 최근 삭제된 항목으로 옮기기만 한다. 되살리기는 이렇게 생겼다(`apps/api/src/posts/posts.service.ts`).

```ts
async restore(slug: string): Promise<AdminPost | null> {
	const row = await this.prisma.post.findUnique({ where: { slug } });
	if (!row?.deleted || !row.deletedAt) throw new NotFoundException('최근 삭제된 항목에 없는 글입니다.');
	if (row.title === null && row.draftTitle === null) {
		await this.prisma.post.delete({ where: { slug } });
		return null;
	}
	// ...deleted: false, deletedAt: null
}
```

되살리기의 두 번째 경우가 저장소 글이다. 저장소 글을 서버에서 고친 적 없이 지우면, 서버에는 "가린다"는 표시만 있고 내용은 파일에 있다. 이때 되살린다는 것은 표시를 없애는 것이다. 행이 사라지면 파일이 다시 보인다.

영구 삭제에서 행을 지우지 않는 이유도 같다. 저장소에 같은 주소의 파일이 있다면, 행이 사라지는 순간 그 글이 다시 나타난다. 서버는 저장소에 어떤 파일이 있는지 모르므로, 늘 가리는 표시를 남긴다.

30일이 지난 글은 따로 예약 작업을 두지 않고, 관리자 목록을 읽을 때 정리한다. 지운 글을 보는 것도 관리자뿐이라 그때 정리하면 충분하다.

```ts
private async purgeExpired(now = new Date()) {
	const before = new Date(now.getTime() - RECENTLY_DELETED_DAYS * 24 * 60 * 60 * 1000);
	const expired = await this.prisma.post.findMany({
		where: { deleted: true, deletedAt: { lt: before } },
		select: { slug: true, updatedBy: true },
	});
	for (const { slug, updatedBy } of expired) await this.purge(slug, updatedBy);
}
```

예약 작업을 두지 않은 것은 API 서버가 한 대뿐이고, 정리가 몇 시간 늦어도 보이는 차이가 없기 때문이다. 영구 삭제는 버전 지우기와 행 고치기를 한 트랜잭션으로 묶었다.

## 화면

- 지우기는 묻지 않는다. 즉시 삭제만 되돌릴 수 없어서 묻는다. 브라우저의 확인 창 대신 macOS 경고창처럼 메모 창 한가운데에 "1개의 메모를 영구적으로 삭제하겠습니까?"를 띄운다
- 최근 삭제된 항목은 지운 글이 있을 때만 폴더 목록 맨 아래에 보인다. 날짜로 묶지 않고 최근에 지운 순서로 늘어놓으니 정렬 버튼은 없다. 목록 위에 "30일 동안 여기에 있다가 영구히 지워진다, 폴더로 끌어 놓으면 되살아난다"는 안내를 한 번 적고 구분선을 긋는다. 줄마다 "N일 남음"을 단다
- 지운 글은 관리자에게도 읽기 화면으로 보인다. 본문 위 안내 상자에 남은 날과 고칠 수 없는 까닭, 쓰는 방법을 적고, 그 아래 한 줄 오른쪽에 [되돌려 놓기]·[즉시 삭제]를 둔다. 도구 막대에도 같은 두 가지가 아이콘(↺, 휴지통)으로 있다. 우클릭·••• 메뉴에도 같은 두 가지가 있다
- 최근 삭제된 항목의 ••• 메뉴(우클릭도 같다)에 '휴지통 비우기'가 있다. 남은 메모를 모두 즉시 삭제한다
- 되돌려 놓으면 '모든 글'로 돌아가 그 글을 연다. 마지막 하나를 즉시 삭제하면 최근 삭제된 항목이 사라지므로 역시 '모든 글'로 간다

화면은 한 번에 정해지지 않았다. 10월 1일 오후에 기능을 붙인 뒤 직접 써 보면서 여러 번 되돌렸다.

1. 처음에는 안내 상자를 없애고 날짜 줄과 도구 막대로만 알렸다. 써 보니 "30일 동안 여기에 있다가 지워진다"는 목록 위 안내까지 사라져 있어서 다시 넣었다.
2. 안내 상자로 되돌리면서 여섯 가지를 고쳤다. 휴지통 아이콘을 상자가 아니라 제목 줄 가운데에 맞추기, Finder 문구로 바꾸고 둘째 문장은 작게, '되살리기'를 '되돌려 놓기'로, 상자 안에 [즉시 삭제] 더하기, 버튼을 문구 아래 한 줄로(다시 보니 오른쪽 정렬이 맞아 고쳤다), 목록 ••• 메뉴에 '휴지통 비우기', 안내 아래 구분선.
3. 마지막으로 즉시 삭제에 확인 창을 붙였다. macOS 메모의 경고창을 기준으로 삼았고, 메모 앱 안의 경고이므로 화면 한가운데가 아니라 메모 창 한가운데에 띄웠다.

![macOS 메모의 영구 삭제 확인 창](./images/memo-recently-deleted-confirm-request.jpg '참고한 macOS 메모 화면. 즉시 삭제를 누르면 이 확인 창을 메모 창 가운데에 띄운다')

안내 상자의 문구는 Finder의 휴지통에서 파일을 열 때 나오는 안내를 따랐다.

> 30일 뒤에 영구히 삭제됩니다. 원본 항목이 휴지통에 있기 때문에 수정할 수 없습니다.
> 이 항목을 사용하려면 휴지통 밖으로 드래그하거나 복구하십시오.

한때는 상자를 없애고 날짜 줄과 도구 막대로만 알렸다. 조용하긴 했지만 왜 고칠 수 없는지, 어떻게 꺼내는지가 보이지 않았다. 그래서 상자를 되살리고, 휴지통 아이콘은 상자 한가운데가 아니라 첫 줄(제목)의 가운데에 맞췄다. 줄 높이를 변수 하나로 두고 아이콘과 제목에 같이 쓴다.

```css
.memo-trash-note {
	--title-line: 20px;
	display: flex;
	align-items: flex-start;
}

.memo-trash-note > i,
.memo-trash-note strong {
	line-height: var(--title-line);
}
```

내용은 지우기 직전 관리자가 보던 그대로 보여 준다(임시 저장 → 게시한 내용 → 저장소 파일 순). 그래서 지우기가 이제 임시 저장을 비우지 않는다. 고치던 글을 실수로 지웠다가 되살려도 고치던 내용이 남는다.

화면에서 이 '폴더'는 실제 폴더가 아니다. 경로 자리에 `'\u0000recently-deleted'`를 쓴다. 폴더 이름에 쓸 수 없는 글자로 시작해서 사용자가 만든 폴더와 겹칠 일이 없다.

## 끌어 놓아 되살리기

macOS 메모처럼 끌어 놓기로도 지우고 되살린다.

- 글을 '최근 삭제된 항목'에 놓으면 지운다. 지운 글이 없으면 이 항목이 숨어 있으므로, 글을 끄는 동안에는 놓을 자리로 보이게 했다
- 최근 삭제된 항목의 글을 폴더에 놓으면 되살리면서 그 폴더로 옮긴다. '모든 글'에 놓으면 원래 폴더로 돌아간다

끄는 것의 종류에 지운 글(`deleted`)을 더하고, 놓을 수 있는지 판단하는 곳 하나에서 경우를 나눴다.

```ts
const canDrop = (target: string) => {
	if (!dragging) return false;
	if (dragging.type === 'deleted') return target !== RECENTLY_DELETED;
	if (target === RECENTLY_DELETED) {
		return dragging.type === 'post' && !organized.find((post) => post.slug === dragging.id)?.locked;
	}
	// 글은 다른 폴더로, 폴더는 다른 폴더 안으로 (원래 규칙)
};
```

잠긴 메모는 지울 수 없으니 최근 삭제된 항목에 놓을 수도 없다. 폴더는 지우는 방법이 따로 있어서(글이 없는 폴더만) 놓지 못하게 했다.

E2E에서는 Playwright의 `dragTo`를 쓸 수 없었다. 놓을 자리(최근 삭제된 항목)가 끄기 시작한 뒤에야 생기는데, `dragTo`는 끌기 전에 놓을 곳부터 찾는다. 마우스를 직접 누르고 옮겨서 끌었다.

## 확인

- API 통합 시험 `apps/api/test/posts.e2e.test.ts`에 네 개를 두었다. "지우면 지운 표시로 남고 (저장소 글도 가린다), 다시 게시하면 되살아난다", "최근 삭제된 항목에서 되살리면 지우기 전 그대로, 영구히 지우면 내용과 버전이 사라진다", "서버에 내용이 없는 저장소 글은 되살리면 표시가 지워진다 (파일이 다시 보인다)", "지운 지 30일이 지나면 영구히 지운다".
- 화면 E2E `e2e/memo-editor.spec.ts`: "지우면 묻지 않고 최근 삭제된 항목으로 가고, 거기서 되살리거나 영구히 지운다", "최근 삭제된 항목의 ••• 메뉴로 휴지통을 비운다", "글을 최근 삭제된 항목에 끌어 놓으면 지우고, 지운 글을 폴더에 끌어 놓으면 그 폴더로 되살린다". 서버 대신 `e2e/fakeApi.ts`가 restore·permanent 요청을 흉내 낸다.
- 첫 커밋만 해도 13개 파일, 497줄을 더하고 79줄을 지웠다. 그중 `Memo.tsx`가 194줄로 가장 컸고, 이 덩어리는 뒤에 `useTrash` 훅으로 떼어 냈다.

## 남은 것·배운 것

- 화면 설명은 여러 번 바뀌었다. 안내 상자를 없애고 도구 막대로만 알렸다가(`a3fd486a1`) 다시 상자를 되살렸다(`7710ba20b`). 조용한 화면보다 "왜 고칠 수 없는지"를 알려 주는 쪽이 덜 헷갈렸다.
- 30일 정리는 관리자가 목록을 열어야 돈다. 관리자가 오래 들어오지 않으면 지운 글이 30일보다 오래 남지만, 남은 글은 관리자에게만 보이므로 문제가 되지 않는다.
- 지운 표시 하나에 "가리기"와 "휴지통" 두 뜻을 겹쳐 쓰면 질의가 헷갈린다. 칸을 둘로 나누고 있을 수 없는 조합을 CHECK 제약으로 막아 두니, 제약을 적는 순간 다시 게시·임시 저장 경로의 빈틈이 드러났다. 상태를 표로 먼저 적어 보는 것이 쓸모 있었다.
- 같은 휴지통 개념은 뒤에 휴지통 앱으로 이어졌다. 거기서는 관리자에게 지운 메모를 되살리는 화면을 하나 더 두었다.
