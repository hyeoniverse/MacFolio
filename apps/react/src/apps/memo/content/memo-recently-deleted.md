메모를 삭제할 때마다 "지울까요?" 확인 창을 표시했다. 삭제를 되돌릴 수 없었기 때문이다. macOS 메모는 확인하지 않는다. 삭제한 메모는 '최근 삭제된 항목'으로 이동해 30일 동안 보관되고, 그 기간 안에 복구하거나 영구 삭제한다. 같은 방식으로 변경했다([#64](https://github.com/hyeoniverse/MacFolio/pull/64)).

## 배경

블로그를 메모 앱 안에서 직접 작성하다 보니 글을 정리하면서 삭제하는 일이 잦았다. 확인 창은 클릭을 한 번 늘릴 뿐, 습관적으로 확인을 누른 뒤에는 효과가 없었다. 한 번 삭제한 글은 게시한 내용·임시 저장·버전 기록이 모두 서버에서 삭제되어 복구할 방법이 없었다. 확인 창의 경고를 강화하는 것보다, 삭제는 한 번에 실행하고 복구 경로를 제공하는 편이 낫다고 판단했다.

검토한 방법은 세 가지다.

| 방법                                          | 장점                                            | 단점                                                                                                      |
| --------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 확인 창 유지                                  | 추가 작업이 없다                                | 습관적으로 확인을 누르면 막지 못한다. 복구 방법이 없다                                                    |
| 삭제한 글을 별도 휴지통 테이블로 이동         | 일반 글 쿼리가 단순하다                         | 글·임시 저장·버전을 테이블 두 개 사이에서 이동해야 하고, 저장소 글을 숨기는 표시는 여전히 Post에 필요하다 |
| **Post에 삭제 시각(`deletedAt`) 추가 (선택)** | 열 하나, 마이그레이션 6줄. 이동할 데이터가 없다 | 삭제한 글을 제외하는 조건을 쿼리마다 넣어야 한다                                                          |

이미 `deleted` 표시로 저장소 글을 숨기고 있었으므로, 같은 행에 삭제 시각만 추가하는 세 번째 방법이 변경 범위가 가장 작았다.

![최근 삭제된 항목](./images/memo-trash.jpg '폴더 목록 맨 아래의 최근 삭제된 항목. 본문 위 안내 상자에 되돌려 놓기·즉시 삭제 버튼')

## 삭제 시각

이전에도 글을 삭제하면 행을 제거하지 않고 `deleted` 표시만 남겼다(소프트 삭제[^soft-delete]). 블로그 글의 상당수는 저장소의 Markdown 파일이라 서버가 파일을 삭제할 수 없어서, "이 주소의 글은 숨긴다"는 표시가 필요했기 때문이다. 다만 삭제하면서 임시 저장을 비웠고, 삭제 시각은 기록하지 않았다.

그래서 `deletedAt`을 추가했다. 두 값의 조합에 따라 상태가 다음과 같이 나뉜다.

| deleted | deletedAt | 상태                                                     |
| ------- | --------- | -------------------------------------------------------- |
| false   | 없음      | 일반 글                                                  |
| true    | 있음      | 최근 삭제된 항목 (30일 동안 복구 가능)                   |
| true    | 없음      | 영구 삭제한 글 (저장소의 같은 주소 파일을 숨기기만 한다) |
| false   | 있음      | 존재할 수 없는 조합 (CHECK 제약으로 차단)                |

![세 상태와 상태 전이](./images/memo-recently-deleted-states.svg '일반 글 → 최근 삭제된 항목 → 영구 삭제한 글. 복구는 가운데 상태에서만 가능하다')

마이그레이션(`20261001100000_post_deleted_at/migration.sql`)은 열을 추가하기만 했다. 이미 삭제한 글은 `deletedAt`이 비어 있으므로 영구 삭제한 글로 취급한다. 삭제 시각이 있는데 삭제 상태가 아닌 조합은 존재할 수 없으므로 DB의 [CHECK 제약](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS)으로 차단했다. Prisma 스키마로는 CHECK 제약을 표현할 수 없어서 마이그레이션 SQL에 직접 작성했다.

```sql
ALTER TABLE "Post" ADD COLUMN "deletedAt" TIMESTAMP(3);
ALTER TABLE "Post" ADD CONSTRAINT "Post_deleted_at" CHECK ("deletedAt" IS NULL OR "deleted");
```

제약을 작성하면서 누락된 코드 경로를 발견했다. 삭제한 글을 다시 게시하거나 임시 저장하면 `deleted`를 `false`로 되돌리는데, `deletedAt`은 그대로 유지하고 있었다. 수정하지 않았다면 제약 위반으로 저장이 실패했을 것이다. 두 경로 모두 `deletedAt: null`을 함께 설정했다.

## 복구와 영구 삭제

| 동작      | 서버 처리                                                                          |
| --------- | ---------------------------------------------------------------------------------- |
| 삭제      | `deleted`, `deletedAt`만 변경한다. 게시한 내용·임시 저장·버전은 유지               |
| 복구      | `deleted`·`deletedAt`을 초기화한다. 서버에 내용이 없던 저장소 글이면 행을 삭제한다 |
| 영구 삭제 | 내용·임시 저장·버전을 삭제하고 숨김 표시만 남긴다                                  |
| 30일 경과 | 관리자 목록을 조회할 때 삭제 후 30일이 지난 글을 영구 삭제한다                     |

API는 두 개를 추가했다. `POST /posts/:slug/restore`가 복구하고, `DELETE /posts/:slug/permanent`가 영구 삭제한다. 기존 `DELETE /posts/:slug`는 이제 최근 삭제된 항목으로 이동만 한다. 복구 코드는 다음과 같다(`apps/api/src/posts/posts.service.ts`).

```ts
async restore(slug: string): Promise<AdminPost | null> {
	const row = await this.prisma.post.findUnique({ where: { slug } });
	if (!row?.deleted || !row.deletedAt) throw new NotFoundException('최근 삭제된 항목에 없는 글입니다.');
	if (row.title === null && row.draftTitle === null) {
		await this.prisma.post.delete({ where: { slug } });
		return null;
	}
	// ...deleted: false, deletedAt: null
}
```

복구의 두 번째 분기가 저장소 글이다. 서버에서 수정한 적 없는 저장소 글을 삭제하면, 서버에는 "숨긴다"는 표시만 있고 내용은 파일에 있다. 이때 복구는 표시를 제거하는 것이다. 행이 삭제되면 파일의 글이 다시 표시된다.

영구 삭제에서 행을 삭제하지 않는 이유도 같다. 저장소에 같은 주소의 파일이 있다면, 행이 삭제되는 순간 그 글이 다시 표시된다. 서버는 저장소에 어떤 파일이 있는지 알 수 없으므로, 항상 숨김 표시를 남긴다.

30일이 지난 글은 별도 예약 작업 없이, 관리자 목록을 조회할 때 정리한다. 삭제한 글을 조회하는 사용자도 관리자뿐이라 그 시점에 정리하면 충분하다.

```ts
private async purgeExpired(now = new Date()) {
	const before = new Date(now.getTime() - RECENTLY_DELETED_DAYS * 24 * 60 * 60 * 1000);
	const expired = await this.prisma.post.findMany({
		where: { deleted: true, deletedAt: { lt: before } },
		select: { slug: true, updatedBy: true },
	});
	for (const { slug, updatedBy } of expired) await this.purge(slug, updatedBy);
}
```

예약 작업을 두지 않은 이유는 API 서버가 한 대뿐이고, 정리가 몇 시간 늦어져도 사용자에게 드러나는 차이가 없기 때문이다. 영구 삭제는 버전 삭제와 행 수정을 [트랜잭션](https://www.prisma.io/docs/orm/prisma-client/queries/transactions) 하나로 묶었다.

## 화면

- 삭제는 확인하지 않는다. 되돌릴 수 없는 즉시 삭제만 확인한다. 브라우저 기본 확인 창 대신 macOS 경고창처럼 메모 창 가운데에 "1개의 메모를 영구적으로 삭제하겠습니까?"를 표시한다
- 최근 삭제된 항목은 삭제한 글이 있을 때만 폴더 목록 맨 아래에 표시된다. 날짜 그룹 없이 최근 삭제 순서로 나열하므로 정렬 버튼은 없다. 목록 상단에 "30일 동안 여기에 있다가 영구히 지워진다, 폴더로 끌어 놓으면 되살아난다"는 안내를 한 번 표시하고 구분선을 넣는다. 행마다 "N일 남음"을 표시한다
- 삭제한 글은 관리자에게도 읽기 화면으로 표시된다. 본문 위 안내 상자에 남은 일수와 수정할 수 없는 이유, 복구 방법을 표시하고, 그 아래 한 줄 오른쪽에 [되돌려 놓기]·[즉시 삭제]를 배치한다. 도구 막대에도 같은 두 동작이 아이콘(↺, 휴지통)으로 있고, 우클릭·••• 메뉴에도 같은 두 항목이 있다
- 최근 삭제된 항목의 ••• 메뉴(우클릭 메뉴도 같다)에 '휴지통 비우기'가 있다. 남은 메모를 모두 즉시 삭제한다
- 되돌려 놓으면 '모든 글'로 이동해 그 글을 연다. 마지막 하나를 즉시 삭제하면 최근 삭제된 항목이 사라지므로 역시 '모든 글'로 이동한다

화면 구성은 한 번에 확정되지 않았다. 10월 1일 오후에 기능을 추가한 뒤 직접 사용하면서 여러 번 수정했다.

1. 처음에는 안내 상자를 제거하고 날짜 줄과 도구 막대로만 안내했다. 사용해 보니 "30일 동안 여기에 있다가 지워진다"는 목록 상단 안내까지 함께 사라져 있어서 다시 추가했다.
2. 안내 상자를 복원하면서 여섯 가지를 수정했다.

   | 항목           | 수정 내용                                       |
   | -------------- | ----------------------------------------------- |
   | 휴지통 아이콘  | 상자가 아니라 제목 줄의 세로 중앙에 정렬        |
   | 문구           | Finder 문구로 변경, 둘째 문장은 작은 글자       |
   | 버튼 이름      | '되살리기' → '되돌려 놓기'                      |
   | 상자 안 버튼   | [즉시 삭제] 추가, 문구 아래 한 줄에 오른쪽 정렬 |
   | 목록 ••• 메뉴  | '휴지통 비우기' 추가                            |
   | 목록 상단 안내 | 아래에 구분선 추가                              |

3. 마지막으로 즉시 삭제에 확인 창을 추가했다. macOS 메모의 경고창을 기준으로 삼았고, 메모 앱 안의 경고이므로 화면 가운데가 아니라 메모 창 가운데에 표시했다.

![macOS 메모의 영구 삭제 확인 창](./images/memo-recently-deleted-confirm-request.jpg '참고한 macOS 메모 화면. 즉시 삭제를 누르면 이 확인 창을 메모 창 가운데에 표시한다')

안내 상자의 문구는 Finder의 휴지통에서 파일을 열 때 표시되는 안내를 따랐다.

> 30일 뒤에 영구히 삭제됩니다. 원본 항목이 휴지통에 있기 때문에 수정할 수 없습니다.
> 이 항목을 사용하려면 휴지통 밖으로 드래그하거나 복구하십시오.

안내 상자를 제거했던 버전은 화면 요소가 적었지만, 수정할 수 없는 이유와 복구 방법이 드러나지 않았다. 그래서 상자를 복원하고, 휴지통 아이콘은 상자의 세로 중앙이 아니라 첫 줄(제목)의 세로 중앙에 정렬했다. 줄 높이를 CSS 변수 하나로 정의하고 아이콘과 제목에 함께 적용한다.

```css
.memo-trash-note {
	--title-line: 20px;
	display: flex;
	align-items: flex-start;
}

.memo-trash-note > i,
.memo-trash-note strong {
	line-height: var(--title-line);
}
```

본문은 삭제 직전 관리자가 보던 내용을 그대로 표시한다(우선순위: 임시 저장 → 게시한 내용 → 저장소 파일). 그래서 삭제 시 임시 저장을 더 이상 비우지 않는다. 수정 중이던 글을 실수로 삭제했다가 복구해도 수정 중이던 내용이 유지된다.

화면에서 이 '폴더'는 실제 폴더가 아니다. 경로 값으로 `'\u0000recently-deleted'`를 사용한다. 폴더 이름에 쓸 수 없는 문자로 시작하므로 사용자가 만든 폴더와 충돌하지 않는다.

## 드래그 앤 드롭으로 복구

macOS 메모처럼 드래그 앤 드롭으로도 삭제하고 복구한다.

| 드래그 대상   | 놓는 위치        | 결과                      |
| ------------- | ---------------- | ------------------------- |
| 일반 글       | 최근 삭제된 항목 | 삭제                      |
| 삭제한 글     | 폴더             | 복구하면서 그 폴더로 이동 |
| 삭제한 글     | 모든 글          | 원래 폴더로 복구          |
| 잠긴 글, 폴더 | 최근 삭제된 항목 | 놓을 수 없음              |

삭제한 글이 없으면 최근 삭제된 항목이 숨겨져 있으므로, 글을 드래그하는 동안에는 드롭 대상으로 표시되게 했다.

드래그 대상의 종류에 삭제한 글(`deleted`)을 추가하고, 드롭 가능 여부를 판단하는 함수 하나에서 분기했다.

```ts
const canDrop = (target: string) => {
	if (!dragging) return false;
	if (dragging.type === 'deleted') return target !== RECENTLY_DELETED;
	if (target === RECENTLY_DELETED) {
		return dragging.type === 'post' && !organized.find((post) => post.slug === dragging.id)?.locked;
	}
	// 글은 다른 폴더로, 폴더는 다른 폴더 안으로 (원래 규칙)
};
```

[잠긴 메모](/memo/memo-lock)는 삭제할 수 없으므로 최근 삭제된 항목에 놓을 수도 없다. 폴더는 별도의 삭제 방법(글이 없는 폴더만)이 있어서 놓을 수 없게 했다.

E2E에서는 Playwright의 [`locator.dragTo`](https://playwright.dev/docs/api/class-locator#locator-drag-to)를 사용할 수 없었다. 드롭 대상(최근 삭제된 항목)은 드래그를 시작한 뒤에야 렌더링되는데, `dragTo`는 드래그 전에 드롭 대상부터 찾는다. 그래서 [`page.mouse`](https://playwright.dev/docs/api/class-mouse)로 누르기·이동·놓기를 직접 실행했다.

## 남은 것·정리

- 화면의 안내 방식은 여러 번 바뀌었다. 안내 상자를 제거하고 도구 막대로만 안내했다가(`a3fd486a1`) 다시 상자를 복원했다(`7710ba20b`). 화면 요소를 줄이는 것보다 "수정할 수 없는 이유"를 표시하는 쪽이 사용자의 혼란이 적었다.
- 30일 정리는 관리자가 목록을 조회해야 실행된다. 관리자가 오래 접속하지 않으면 삭제한 글이 30일보다 오래 보관되지만, 남은 글은 관리자에게만 표시되므로 문제가 되지 않는다.
- 삭제 표시 하나에 "숨김"과 "휴지통" 두 의미를 겹쳐 쓰면 쿼리 조건이 모호해진다. 열을 둘로 나누고 존재할 수 없는 조합을 CHECK 제약으로 차단하자, 제약을 작성하는 시점에 다시 게시·임시 저장 경로의 누락이 드러났다. 상태 조합을 표로 먼저 정리하는 방법이 유효했다.
- 같은 휴지통 개념은 이후 [휴지통 앱](/memo/bin-app)으로 이어졌다. 휴지통 앱에는 관리자가 삭제한 메모를 복구하는 화면을 하나 더 추가했다.
