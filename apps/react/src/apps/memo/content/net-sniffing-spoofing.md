## 들어가기 전에

네트워크 문제를 진단하려면 실제로 오가는 패킷을 봐야 한다. 웹 페이지가 느리게 열린다는 신고를 받았을 시각, 서버 로그만으로는 DNS 응답이 늦은 것인지, TCP 재전송이 반복되는 것인지, 서버가 늦게 응답하는 것인지 구별할 수 없다. 회선 위의 패킷을 그대로 수집해 시각과 함께 해석하면 원인이 드러난다. 이 작업이 패킷 스니핑(packet sniffing)이다.

같은 수집 기술은 보안 위협의 관점에서도 중요하다. 암호화하지 않은 로그인 정보는 평문으로 회선에 흐르고, 출발지 주소를 위조한 패킷을 만들어 보내는 스푸핑(spoofing)은 여러 네트워크 공격의 토대가 된다. 운영체제의 일반 소켓은 출발지 IP 주소를 자동으로 채우므로 이런 위조를 기본적으로 막지만, 원시 소켓(raw socket)을 쓰면 헤더 필드를 직접 구성할 수 있다. 이 글은 그 원리를 이해해 탐지와 방어의 근거로 삼는 데 목적이 있다.

이 글이 답하려는 질문은 두 가지다. 스위치로 구성된 현대 네트워크에서 패킷을 어디서, 어떻게 수집하는가. 그리고 운영체제는 패킷을 어떤 경로로 응용에 넘기며, 그 경로를 다루는 도구(libpcap, Scapy)는 어떻게 동작하는가.

| 순서 | 내용                                                                   |
| ---- | ---------------------------------------------------------------------- |
| 1    | 네트워크 장비(허브, 스위치, 라우터)와 트래픽 종류, 브로드캐스트 도메인 |
| 2    | 패킷 분석과 무차별 모드, 스니퍼 배치                                   |
| 3    | 스위치 환경의 수집 방법: 포트 미러링, 허빙 아웃, 탭, ARP 캐시 포이즈닝 |
| 4    | Wireshark와 pcap 라이브러리                                            |
| 5    | BPF와 패킷 수집의 커널 경로                                            |
| 6    | 원시 소켓과 스푸핑의 원리, 방어                                        |
| 7    | Scapy로 패킷 다루기, 전체 방어 정리                                    |

Ethernet 프레임과 MAC 주소, IP 헤더 필드, ARP의 요청과 응답은 [IP 헤더와 서브넷, ARP 주소 변환](/memo/net-ip-arp)에서, ICMP echo 메시지는 [ICMP와 traceroute, IP 라우팅 테이블](/memo/net-traceroute-routing)에서, UDP·TCP 헤더와 체크섬은 [UDP와 TCP의 헤더, 연결 설정과 종료, 상태 전이](/memo/net-udp-tcp)에서 다룬다.

> [!CAUTION] 실습 환경
> 이 글의 수집·구성 예제는 자신이 소유하고 관리하는 격리된 가상 머신 네트워크(예: 같은 NAT 네트워크에 연결한 VM 두세 대)에서만 실행한다. 허가받지 않은 네트워크에서 패킷을 수집하거나 위조한 패킷을 보내는 행위는 관련 법률 위반이 될 수 있다. 예시의 `10.0.2.x` 주소는 가상 머신 NAT 네트워크의 기본 대역이고, 위조 출발지 주소에는 문서용 주소(`192.0.2.0/24`, `198.51.100.0/24`)를 사용했다.

## 네트워크 장비 다시 보기

스니퍼가 무엇을 볼 수 있는지는 스니퍼가 연결된 장비가 프레임을 어떻게 전달하는지에 달려 있다.

### 허브

허브(hub)는 RJ-45 포트 여러 개가 달린 상자이며, 물리 계층에서 신호를 반복하는 장치에 불과하다. 그래서 멀티포트 리피터(multi-port repeater)라고도 한다. 4포트 허브의 1번 포트에 연결된 컴퓨터가 2번 포트의 컴퓨터로 데이터를 보내면, 허브는 그 신호를 2, 3, 4번 포트 모두에 내보낸다. ==허브는 모든 포트로 브로드캐스트하고, 목적지가 아닌 컴퓨터가 프레임을 스스로 폐기한다.==

![컴퓨터 A가 보낸 프레임을 허브가 B, C, D 모두에 전달하고, 목적지가 아닌 C, D가 폐기하는 구조](./images/net-sniffing-spoofing-hub.svg '허브는 목적지와 관계없이 모든 포트로 신호를 반복한다')

### L2 스위치

L2 스위치도 허브처럼 패킷을 반복하지만, 모든 포트로 브로드캐스트하지 않고 목적지 컴퓨터가 연결된 포트로만 보낸다. 트래픽을 줄이기 위해서다. MAC 브리지(bridge), 스위칭 허브라고도 부른다. 스위치는 연결된 장치의 L2 주소(MAC 주소)를 CAM(Content-Addressable Memory) 테이블에 저장하고, 프레임이 들어오면 이 테이블을 조회해 내보낼 포트를 결정한다.

![컴퓨터 A가 보낸 프레임을 스위치가 목적지 B에만 전달하는 구조](./images/net-sniffing-spoofing-switch.svg '스위치는 CAM 테이블로 목적지 포트를 찾아 그 포트로만 보낸다')

CAM 테이블은 MAC(포워딩) 테이블이라고도 하며, 가끔 ARP 테이블이라고 잘못 부르기도 한다. 둘은 다른 테이블이다.

| 구분      | MAC(CAM) 테이블                          | ARP 테이블                                                 |
| --------- | ---------------------------------------- | ---------------------------------------------------------- |
| 계층      | L2                                       | L3                                                         |
| 대응 관계 | MAC 주소 → 스위치 포트                   | IP 주소 → MAC 주소                                         |
| 갱신      | 들어오는 프레임의 출발지 MAC 주소를 학습 | ARP 요청을 브로드캐스트하고 응답으로 갱신                  |
| 만료      | 보통 5분 내외                            | 구현마다 다름(라우터 기본 수 시간, 호스트는 수십 초~수 분) |
| 보유 주체 | 스위치                                   | 모든 호스트와 라우터                                       |

관리형 L2 스위치에도 ARP 테이블이 있지만, 이는 스위치를 설정하는 PC와 통신하기 위한 관리 인터페이스용이다. 관리형 L3 스위치는 서브넷 사이의 포워딩, 즉 라우터 기능을 수행하므로 포워딩 테이블과 함께 ARP 테이블을 실제로 사용한다.

> [!WARNING] CAM 테이블 넘침
> CAM 테이블의 크기는 유한하다. 출발지 MAC 주소를 무작위로 바꾼 프레임이 대량으로 들어와 테이블이 가득 차면, 많은 스위치는 목적지를 찾지 못한 프레임을 모든 포트로 내보내는(flooding) 허브처럼 동작한다. 이 상태가 MAC 플러딩(MAC flooding)이다. 스위치의 포트 보안(port security) 기능으로 포트당 학습할 MAC 주소 수를 제한해 막는다.

### L3 라우터

라우터(router)는 스위치나 허브보다 높은 수준의 기능을 가진 장비로, 두 개 이상의 네트워크 사이에서 패킷을 전달한다. 한 네트워크의 Computer A가 다른 네트워크의 Computer X로 데이터를 보내면, 프레임은 A의 스위치를 거쳐 라우터에 도착하고, 라우터가 다음 네트워크의 스위치로 새 프레임을 만들어 보낸다.

![네트워크 A의 컴퓨터 A가 스위치와 라우터를 거쳐 네트워크 B의 컴퓨터 X에 데이터를 보내는 흐름](./images/net-sniffing-spoofing-router.svg '라우터를 지날 때마다 L2 프레임은 새로 만들어진다')

### 트래픽 종류와 브로드캐스트 도메인

| 종류         | 의미                                           | 주소 예                                               |
| ------------ | ---------------------------------------------- | ----------------------------------------------------- |
| 브로드캐스트 | 네트워크 세그먼트의 모든 포트로 보내는 패킷    | L2 `ff:ff:ff:ff:ff:ff`, L3 서브넷의 브로드캐스트 주소 |
| 멀티캐스트   | 한 출발지에서 여러 목적지로 동시에 보내는 패킷 | IPv4 `224.0.0.0/4`, 대역폭을 가능한 한 적게 쓰기 위함 |
| 유니캐스트   | 한 컴퓨터에서 다른 컴퓨터로 직접 보내는 패킷   | 일반적인 호스트 주소                                  |

L3 브로드캐스트 주소는 네트워크 주소 범위에 따라 달라진다. 호스트 주소의 비트를 모두 1로 채운 값이다.

<details>
<summary>브로드캐스트 주소 계산 두 가지</summary>

`192.168.0.20`, 서브넷 마스크 `255.255.255.0`(/24)이면 호스트 부분은 마지막 8비트다. 이를 모두 1로 채우면 `192.168.0.255`다.

`192.168.0.70/26`이면 호스트 부분은 마지막 6비트다. 마지막 옥텟 70은 이진수로 `01000110`이고, 상위 2비트 `01`이 네트워크 부분이다.

```math
\begin{aligned}
\text{네트워크 주소} &= 01\,000000_2 = 64 \;\Rightarrow\; 192.168.0.64 \\
\text{브로드캐스트 주소} &= 01\,111111_2 = 127 \;\Rightarrow\; 192.168.0.127
\end{aligned}
```

</details>

브로드캐스트 패킷이 퍼질 수 있는 범위를 브로드캐스트 도메인(broadcast domain)이라 한다. 라우터를 거치지 않고 서로 직접 전송할 수 있는 네트워크 세그먼트다. 라우터는 브로드캐스트를 전달하지 않으므로 브로드캐스트 도메인의 경계가 된다.

![라우터를 사이에 둔 두 스위치 네트워크가 각각 별도의 브로드캐스트 도메인을 이루는 구조](./images/net-sniffing-spoofing-broadcast-domain.svg '라우터가 브로드캐스트 도메인을 나눈다')

## 패킷 분석과 스니퍼

### 패킷 분석이란

패킷 분석(packet analysis)은 패킷 스니핑, 프로토콜 분석(protocol analysis)이라고도 하며, 네트워크에서 무슨 일이 일어나는지 이해하기 위해 회선을 지나는 데이터를 실시간으로 수집하고 해석하는 과정이다. 회선을 지나는 원시 데이터를 수집하는 하드웨어 장치나 소프트웨어 도구를 패킷 스니퍼(packet sniffer)라 한다. 쓰임새는 다음과 같다.

- 네트워크 특성 파악
- 네트워크에 누가 있는지 확인
- 누가, 무엇이 대역폭을 사용하는지 판별
- 사용량이 최고인 시간대 확인
- 악성 활동 식별
- 보안에 취약하거나 불필요하게 무거운 응용 발견

### 스니퍼를 어디에 둘 것인가

효과적인 패킷 분석의 핵심은 스니퍼를 물리적으로 어디에 연결하는지에 있다. 스위치와 라우터는 트래픽을 각자 다르게 처리하므로, 분석할 네트워크의 물리 구성을 먼저 파악해야 한다.

![스위치 두 대와 라우터로 이루어진 네트워크 가운데에 스니퍼를 놓고 어디에 연결할지 묻는 그림](./images/net-sniffing-spoofing-placement.svg '같은 스니퍼도 연결 위치에 따라 보이는 트래픽이 달라진다')

### 무차별 모드

노트북으로 네트워크의 패킷을 수집하려면 무차별 모드(promiscuous mode) 드라이버를 지원하는 NIC(Network Interface Card)가 필요하다. 보통 NIC는 목적지 MAC 주소가 자신이거나 브로드캐스트·구독한 멀티캐스트인 프레임만 운영체제로 올리고 나머지는 하드웨어에서 버린다. 무차별 모드에서는 주소와 관계없이 회선에서 받은 모든 프레임을 호스트의 프로세서로 넘긴다. Wi-Fi(IEEE 802.11)에는 비슷한 기능으로 모니터 모드(monitor mode)가 있다. 모니터 모드는 AP에 연결하지 않은 상태로 해당 채널의 모든 802.11 프레임을 수집한다.

![Broadcom BCM5751, Intel X520-DA2, USB 3.0 기가비트 어댑터 NIC 사진](./images/net-sniffing-spoofing-06.jpg '대부분의 현대 NIC는 무차별 모드를 지원한다')

대부분의 현대 NIC는 무차별 모드를 지원하며, Wireshark는 libpcap(Windows에서는 Npcap) 드라이버를 통해 GUI에서 NIC를 바로 무차별 모드로 바꿀 수 있다. NIC 데이터시트에는 하드웨어 수준의 L2 필터링 규칙이 정의되어 있다. Intel 82574 GbE 컨트롤러 데이터시트의 L2 필터링 절은 패킷이 L2 필터를 통과하는 조건 다섯 가지를 정의한다.

다섯 조건 중 하나라도 맞으면 패킷이 L2 필터를 통과한다. 무차별 유니캐스트 필터링이 켜져 있거나, 유니캐스트 MAC 필터와 일치하거나, 무차별 멀티캐스트 필터링이 켜져 있거나, 멀티캐스트 필터와 일치하거나, 브로드캐스트 패킷인 경우다. 무차별 모드는 결국 NIC의 이 필터 비트를 드라이버가 켜는 동작이다.

> [!NOTE] 무차별 모드는 탐지될 수 있다
> 무차별 모드로 바꾸면 관리자가 이를 알아챌 수 있고, 보안상 문제로 간주될 수 있다. 무차별 모드의 호스트는 평소라면 응답하지 않을 주소로 온 프레임도 상위 스택으로 올리므로, 일부러 틀린 MAC 주소로 보낸 ARP 요청이나 ICMP에 응답하는지 확인해 수집 호스트를 탐지하는 기법(예: ARP 기반 탐지)이 있다.

### 허브 환경

허브로만 이루어진 네트워크는 패킷 분석가에게 이상적인 환경이다. 허브에 연결된 스니퍼는 자신이 연결된 컴퓨터의 통신뿐 아니라 그 허브에 연결된 다른 모든 장치 사이의 통신을 볼 수 있다. 스니퍼로 트래픽을 볼 수 있는 장치의 범위를 가시 범위(visibility window)라 한다. 다만 허브 기반 네트워크는 처리량이 낮고 충돌 확률이 높아 거의 남아 있지 않다.

![허브 두 대로 이루어진 네트워크에 연결된 스니퍼의 가시 범위가 컴퓨터 A부터 F까지 모두를 포함하는 구조](./images/net-sniffing-spoofing-visibility-hub.svg '허브 환경의 가시 범위는 허브에 연결된 장치 전체다')

### 스위치 환경

현대 네트워크에서 가장 흔한 연결 장비는 스위치다. 스위치 포트에 스니퍼를 연결하면 브로드캐스트 트래픽과 스니퍼가 설치된 장치 자신이 주고받는 트래픽만 보인다.

![스위치에 연결된 스니퍼의 가시 범위가 스니퍼 자신으로 좁아진 구조](./images/net-sniffing-spoofing-visibility-switch.svg '스위치 환경에서는 무차별 모드를 켜도 다른 호스트의 유니캐스트가 보이지 않는다')

스위치 환경에서 특정 포트의 트래픽을 수집하는 주요 방법은 네 가지다. 앞의 세 가지는 정당한 관리 수단이고, 마지막 하나는 공격 기법이므로 탐지와 방어를 함께 다룬다.

#### 포트 미러링

포트 미러링(port mirroring)은 포트 스패닝(SPAN은 Switched Port Analyzer)이라고도 하며, 대상 포트의 트래픽을 스니퍼가 연결된 포트로 복사하도록 스위치를 설정하는 방법이다. 대상 컴퓨터가 연결된 관리형 스위치의 관리 인터페이스에 접근할 수 있어야 하고, 스위치가 포트 미러링을 지원하며 스니퍼를 꽂을 빈 포트가 있어야 한다.

![컴퓨터 B의 포트를 스니퍼 포트로 미러링해 가시 범위에 B가 포함되는 구조](./images/net-sniffing-spoofing-visibility-mirror.svg '미러링한 포트의 트래픽이 스니퍼 포트로 복사된다')

포트 미러링을 할 시각에는 미러링하는 포트들의 처리량을 고려해야 한다. 여러 포트를 한 포트로 미러링할 수 있는 스위치도 있는데, 이 경우 계산은 다음과 같다.

```math
23\ \text{포트} \times 100\ \text{Mbps} \times 2\ (\text{full-duplex 송수신}) = 4600\ \text{Mbps} = 4.6\ \text{Gbps}
```

24포트 스위치에서 full-duplex 100Mbps 포트 23개를 한 포트로 미러링하면 최대 4.6Gbps가 100Mbps 포트 하나로 몰린다. 단일 포트의 물리적 한계를 한참 넘으므로 패킷 손실이나 네트워크 지연이 생길 수 있다. 이를 초과 구독(oversubscription)이라 한다. 그래서 포트 미러링은 처리량이 높을수록 결과가 일정하지 않을 수 있다.

#### 허빙 아웃

허빙 아웃(hubbing out)은 대상 장치와 분석 시스템을 허브 하나에 함께 연결해 같은 네트워크 세그먼트에 두는 방법이다. 포트 미러링을 쓸 수 없지만 대상 장치가 연결된 스위치에 물리적으로 접근할 수 있을 시각에 쓰는 유효한 해결책이다.

![대상 컴퓨터 B와 스니퍼를 허브로 묶어 스위치에 연결한 구조](./images/net-sniffing-spoofing-visibility-hubout.svg '허브가 대상 장치의 트래픽을 스니퍼에게도 반복한다')

허빙 아웃은 대부분 대상 장치의 통신을 full-duplex에서 half-duplex로 떨어뜨린다. 또 진짜 허브를 구하기 어렵다. 허브로 표시되어 있지만 실제로는 스위치인 제품도 있으므로, 허브로 보이는 장비는 반드시 시험해 확인해야 한다.

#### 탭

네트워크 탭(network tap)은 케이블의 두 지점 사이에 끼워 넣어 그 사이를 지나는 패킷을 수집하는 네트워크 분석 전용 하드웨어다. 두 종류가 있다.

| 종류                     | 포트 수 | 특징                                                                                       |
| ------------------------ | ------- | ------------------------------------------------------------------------------------------ |
| 비집적(nonaggregated) 탭 | 4       | 양방향 트래픽을 모니터 포트 두 개로 나누어 내보내므로 스니퍼에 인터페이스 두 개가 필요하다 |
| 집적(aggregated) 탭      | 3       | 양방향 트래픽을 모니터 포트 하나로 합쳐 내보내므로 인터페이스 하나로 충분하다              |

![집적 탭은 모니터 포트 하나로, 비집적 탭은 모니터 A와 모니터 B 두 포트로 스니퍼에 연결하는 구조](./images/net-sniffing-spoofing-taps.svg '비집적 탭은 방향별로 모니터 포트가 따로 있다')

집적 탭은 양방향 트래픽을 한 포트로 합치므로, 양방향 합계가 모니터 포트의 속도를 넘으면 포트 미러링과 같은 초과 구독 문제가 생길 수 있다. 비집적 탭은 방향별로 포트를 분리해 이 문제를 피하지만 스니퍼에 인터페이스가 둘 필요하다. 탭은 광섬유 구간을 수집할 유일한 선택지이고, 신뢰성이 높아 기업 환경의 상시 모니터링에 적합하지만 비쌀 수 있다.

#### ARP 캐시 포이즈닝

ARP 캐시 포이즈닝(ARP cache poisoning)은 ARP 스푸핑(ARP spoofing)이라고도 하며, 스위치 네트워크에서 트래픽을 가로채는 고급 기법이다. ARP에는 요청 없이 받은 응답도 캐시에 반영하는(gratuitous ARP를 수용하는) 구현이 많고, 응답에 대한 인증이 없다는 약점이 있다. 공격자는 대상 호스트에게 "게이트웨이의 IP 주소는 공격자의 MAC 주소"라고 알리는 위조 ARP 응답을 보내 대상의 ARP 캐시를 오염시킨다. 그러면 대상이 게이트웨이로 보내려던 트래픽이 공격자를 거쳐 가게 되어, 공격자가 중간에서 트래픽을 가로채는 중간자(man-in-the-middle) 위치를 차지한다.

![정상 트래픽 경로와 ARP 캐시가 오염되어 트래픽이 공격자를 경유하는 경로의 비교](./images/net-sniffing-spoofing-arp-poison.svg 'ARP 응답이 인증되지 않는다는 점이 캐시 오염의 근거다')

이 기법은 대상 시스템에 거짓 주소의 패킷을 보내 특정 트래픽을 가로채거나 서비스 거부(DoS)를 일으키는 데 쓰인다. 대상의 네트워크 사용량이 매우 높을 시각에는 공격자를 경유하면서 성능이 떨어져 TLS 기반 통신 시도가 실패할 수 있으므로 바람직하지 않다.

> [!IMPORTANT] ARP 스푸핑 방어
> ARP는 설계상 응답을 인증하지 않으므로 방어는 상위 계층과 장비 기능에 의존한다. 정적 ARP 항목(중요한 게이트웨이 주소 고정), 스위치의 Dynamic ARP Inspection(DHCP 스누핑 바인딩과 대조해 위조 ARP를 폐기), 비정상적인 ARP 응답을 탐지하는 arpwatch 같은 도구가 대표적이다. 근본적으로는 TLS처럼 종단 간 인증과 암호화를 적용한 프로토콜을 쓰면 중간자가 트래픽을 가로채도 내용을 해독하거나 변조할 수 없다. ARP 스푸핑 자체는 [ARP](/memo/net-ip-arp)와 [DNS 공격](/memo/net-dns-attack)에서 이어 다룬다.

### 라우팅 환경과 배치 지침

스위치 네트워크의 모든 수집 기법은 라우팅 네트워크에서도 쓸 수 있다. 다만 여러 네트워크 세그먼트에 걸친 문제를 진단할 시각에는 스니퍼를 어느 세그먼트에 두는지가 중요하다. 문제가 의심되는 경로의 양쪽에서 각각 수집해 비교해야 어느 구간에서 지연이나 손실이 생기는지 판별할 수 있다.

![네트워크 A부터 D까지 라우터로 이어진 환경에서 네트워크 D의 트래픽이 네트워크 B 라우터 구간을 지날 때 문제가 생기는지 묻는 그림](./images/net-sniffing-spoofing-routing.svg '세그먼트를 넘는 문제는 양쪽에서 수집해 비교한다')

| 기법              | 특징                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 포트 미러링       | 네트워크 발자국이 없고 추가 패킷을 만들지 않지만, 높은 처리량에서 결과가 일정하지 않을 수 있다                                                   |
| 허빙 아웃         | 호스트를 잠시 끊어도 될 시각에 유효하나, 여러 호스트 트래픽 수집에는 부적합하다                                                                  |
| 탭                | 호스트를 끊지 않고 신뢰성 있게 수집하며 광섬유에도 쓰이나 비쌀 수 있다                                                                           |
| ARP 캐시 포이즈닝 | 패킷을 주입하므로 신중해야 하고, 다른 방법이 없을 시각의 대안이며 네트워크에 영향을 줄 수 있다                                                   |
| 직접 설치         | 대상 호스트에 수집 도구를 설치하므로 무차별 모드가 필요 없지만, 호스트 문제로 패킷이 누락·변조될 수 있어 시험 환경이나 성능 기준선 측정에 알맞다 |

## Wireshark

Wireshark는 pcap 기반의 자유·오픈소스 패킷 분석기로, 네트워크 문제 해결, 분석, 프로토콜 개발, 교육에 쓰인다. tcpdump와 매우 비슷하지만 그래픽 프런트엔드와 정렬·필터 기능을 통합했다. 명령줄 도구 tshark도 함께 제공하며, 셸 스크립트와 결합하면 수집을 자동화할 수 있다.

Wireshark는 서로 다른 네트워킹 프로토콜의 구조를 이해하는 소프트웨어다. GUI로 캡슐화와 각 필드의 의미를 함께 보여 준다. 라이브 연결에서 수집하거나 이미 저장된 pcap 파일을 읽을 수 있고, Ethernet·IEEE 802.11·PPP·loopback 등 여러 종류의 네트워크에서 데이터를 읽는다. 표시 필터로 화면을 추려 보고, editcap으로 수집 파일을 변환하며, 플러그인으로 새 프로토콜을 해석할 수 있다. 심지어 USB 트래픽도 수집한다.

> [!NOTE] Ethereal에서 Wireshark로
> 1990년대 후반 Gerald Combs가 작은 ISP에서 일하며 Ethereal을 만들어 1998년 무렵 첫 버전을 공개했다. 2006년 그가 CACE Technologies로 옮길 시각, 소스 코드 저작권은 대부분 그에게 있었으나 Ethereal 상표권은 없었으므로 이름을 Wireshark로 바꾸었다. 2010년 Riverbed Technology가 CACE를 인수해 주요 후원자가 되었다.

### 화면 구성

Wireshark 창은 명령 메뉴, 표시 필터 입력줄, 수집된 패킷 목록, 선택한 패킷의 헤더 상세, 16진수·ASCII로 본 패킷 내용으로 이루어진다. `[Capture] – [Start]`로 라이브 패킷을 보거나 pcap 파일을 연다.

> [!WARNING] pcap 파일에는 개인 정보가 있다
> pcap 파일에는 실제 IP 주소와 평문 페이로드가 그대로 담긴다. 공개 데이터셋은 페이로드를 비우고 IP 주소를 해시로 익명화한 뒤에야 배포된다. 수집 파일을 공유하거나 글에 실을 시각에는 실제 주소와 페이로드를 익명화하거나 제거해야 한다. 이 글의 수집 예시 표도 실제 주소를 문서용 주소로 바꾸어 재구성한 것이다.

### 두 종류의 필터

Wireshark에는 성격이 다른 두 필터가 있다. 수집 필터(capture filter)는 수집 도중 조건에 맞지 않는 패킷을 아예 버리고, 표시 필터(display filter)는 수집한 패킷을 모두 보관하면서 화면에만 조건을 적용한다.

| 구분          | 수집 필터                                | 표시 필터                                |
| ------------- | ---------------------------------------- | ---------------------------------------- |
| 적용 시점     | 수집 도중                                | 수집 후(post-filter)                     |
| 버려지는 패킷 | 조건에 맞지 않으면 저장 자체를 안 함     | 모두 보관하고 화면에서만 숨김            |
| 문법          | pcap 라이브러리(BPF) 문법                | Wireshark 고유 문법                      |
| 예            | `tcp port 80 and not host 192.168.0.100` | `ip.addr==192.168.1.10 && tcp.port==445` |

수집 필터는 BPF 문법을 따른다. `tcp port 80 and host 192.168.0.100`, `ether src 00:08:15:00:08:15` 같은 식이다. 표시 필터는 비교 연산자와 논리 연산자를 영어식과 C식으로 모두 지원한다.

| 종류 | 영어식 | C식    | 예                                      |
| ---- | ------ | ------ | --------------------------------------- |
| 비교 | eq     | `==`   | `ip.src==10.0.0.5`                      |
|      | ne     | `!=`   | `ip.src!=10.0.0.5`                      |
|      | gt     | `>`    | `frame.len > 10`                        |
|      | lt     | `<`    | `frame.len < 128`                       |
|      | ge     | `>=`   | `frame.len ge 0x100`                    |
|      | le     | `<=`   | `frame.len <= 0x20`                     |
| 논리 | and    | `&&`   | `ip.src==10.0.0.5 and tcp.flags.fin`    |
|      | or     | `\|\|` | `ip.src==10.0.0.5 or ip.src==192.0.2.1` |
|      | not    | `!`    | `not llc`                               |

표시 필터는 바이트 슬라이스까지 지정할 수 있다. `udp[8:3]==81:60:03`은 UDP 헤더 8바이트를 건너뛴 페이로드 첫 3바이트가 `0x81 0x60 0x03`인 패킷을, `eth.addr[0:3]==00:06:5b`은 특정 제조사의 OUI(Ethernet 주소 상위 3바이트)로 시작하는 프레임을 고른다. 아래는 세 종류의 TCP 핸드셰이크 분석에 쓸 만한 예다.

```text
tcp.flags.syn==1 && tcp.flags.ack==0    # 연결 시도(SYN만 설정)
tcp.flags==0x012                        # SYN+ACK (연결 수락)
tcp.flags==0x002 && ip.dst==10.0.0.0/16 # 특정 서브넷으로의 연결 시도 집계
http.response.code==404 || dns.flags.rcode!=0  # HTTP 404와 DNS 오류
frame contains "sombrero"               # 페이로드에 특정 문자열 포함
frame matches "(?i)sombrero|football"   # 대소문자 무시 정규식 매칭
```

### 패킷 해석과 통계

선택한 패킷은 Ethernet 프레임, IP 패킷, TCP 세그먼트 순으로 계층별 필드가 펼쳐진다. `[Analyze] – [Follow TCP Stream]`은 하나의 TCP 흐름을 응용 데이터 수준에서 재조립해 보여 준다. 보낸 내용은 빨간색, 받은 내용은 파란색으로 표시한다.

![Wireshark의 패킷 분석기와 패킷 수집(pcap)이 OS 스택의 링크 계층에서 송수신한 모든 Ethernet 프레임의 사본을 받는 구조](./images/net-sniffing-spoofing-pcap.svg 'pcap은 OS 스택과 별도로 모든 프레임의 사본을 받는다')

`[Statistics]` 메뉴에는 분석에 바로 쓰는 요약이 많다.

| 메뉴               | 용도                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| Summary            | 수집 패킷 수, 수집 시간, 평균 패킷/초, 평균 크기 등 전체 요약         |
| Protocol Hierarchy | 프로토콜별 패킷 수와 바이트 비율을 계층 구조로 집계                   |
| Conversations      | 종단 쌍별 흐름 목록(예: TCP 흐름 여러 개를 나열하고 하나를 추려 보기) |
| Flow Graph         | 세그먼트 교환을 시퀀스 도식으로 표시(예: TLSv1.2 수집 흐름)           |
| IO Graphs          | 시간에 따른 트래픽 양을 그래프로 비교                                 |
| TCP StreamGraph    | 시간-시퀀스 그래프(Stevens), RTT, 처리량                              |

Conversations로 가장 활발한 TCP 대화를 고르고, IO Graph에 서브넷 기준 표시 필터를 걸어 특정 서브넷의 트래픽을 전체와 비교하는 식으로 분석한다. 보안 관점에서는 `tcp.flags==0x002 && ip.dst==10.0.0.0/16`으로 특정 대역에 대한 연결 시도를 집계하거나, `frame matches`로 추적 파일에서 키워드 집합을 찾는다.

> [!TIP] HTTP와 TCP 핸드셰이크 분석 흐름
> HTTP 요청 하나를 분석하면 전송 계층의 동작이 한눈에 보인다. (1) 표시 필터 `tcp.flags.syn==1`로 연결 시도(SYN), SYN+ACK, ACK 세 패킷을 찾아 3-way handshake를 확인하고, (2) `http.request`로 GET 요청과 서버의 응답 코드를 보며, (3) Follow TCP Stream으로 요청·응답 본문을 재조립하고, (4) Flow Graph로 세그먼트 순서와 지연을, Statistics로 전체 패킷 수와 프로토콜 비율을 집계한다. 핸드셰이크의 순서 번호가 어떻게 매겨지는지는 [UDP와 TCP의 헤더, 연결 설정과 종료, 상태 전이](/memo/net-udp-tcp)의 계산 예와 함께 보면 이해가 깊어진다.

## pcap과 BPF

### pcap 라이브러리

pcap(packet capture)은 네트워크 트래픽을 수집하는 API다. UNIX 계열에서는 libpcap, Windows에서는 Npcap(과거 WinPcap)으로 구현된다. libpcap은 Lawrence Berkeley Laboratory의 tcpdump 개발자들이 만들었다. 모니터링 소프트웨어는 pcap을 이용해 회선을 지나는 패킷을 수집하고, 링크 계층에서 패킷을 보내며, 사용할 수 있는 네트워크 인터페이스 목록을 얻는다.

tcpdump, WinDump, ngrep, Wireshark, Snort(침입 탐지 시스템), Kismet(802.11 탐지·수집) 등 많은 도구가 pcap을 쓴다. libpcap은 이식성 있는 C/C++ 라이브러리로, 패킷 수집 시스템에 대한 고수준 인터페이스를 제공한다. 다른 호스트로 가는 패킷을 포함해 네트워크의 모든 패킷에 이 메커니즘으로 접근한다.

주요 함수는 다음과 같다.

| 함수             | 역할                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| `pcap_lookupdev` | 기본 네트워크 인터페이스 이름을 반환(최신 코드는 `pcap_findalldevs` 권장) |
| `pcap_open_live` | 패킷 수집 디스크립터를 열어 회선의 패킷을 본다                            |
| `pcap_compile`   | 필터 문자열을 BPF 필터 프로그램으로 컴파일                                |
| `pcap_setfilter` | 컴파일된 필터 프로그램을 적용                                             |
| `pcap_next`      | 다음 패킷 하나를 읽는다                                                   |
| `pcap_loop`      | 콜백 핸들러로 패킷을 계속 수집·처리                                       |

libpcap 자체가 OS별 차이(원시 소켓, BPF 장치 등)를 안으로 숨기고 플랫폼마다 같은 API를 제공한다는 점이 핵심이다. 아래는 공개된 libpcap 튜토리얼에 실린 최소 수집 예로, 인터페이스를 열어 `port 23` 필터를 적용하고 패킷 하나의 길이만 출력한다. 수집 자체는 pcap API 수준에서 몇 줄로 끝난다.

```c
#include <pcap.h>
#include <stdio.h>

int main(void) {
	char errbuf[PCAP_ERRBUF_SIZE];
	char *dev = pcap_lookupdev(errbuf); /* 기본 인터페이스 */
	bpf_u_int32 net, mask;
	pcap_lookupnet(dev, &net, &mask, errbuf);

	/* 무차별 모드로 세션을 연다 */
	pcap_t *handle = pcap_open_live(dev, BUFSIZ, 1, 1000, errbuf);

	struct bpf_program fp;
	pcap_compile(handle, &fp, "port 23", 0, net); /* 필터 컴파일 */
	pcap_setfilter(handle, &fp);                  /* 필터 적용 */

	struct pcap_pkthdr header;
	const u_char *packet = pcap_next(handle, &header);
	printf("captured length %d\n", header.len);
	pcap_close(handle);
	return 0;
}
```

`pcap_open_live()`의 세 번째 인자 `1{:c}`이 무차별 모드를, 네 번째 인자가 읽기 타임아웃(ms)을 뜻한다. 연속 수집에는 `pcap_next` 대신 콜백을 등록하는 `pcap_loop()`를 쓴다. 바이트 순서 변환(`ntohs`/`htons`)과 헤더 구조체(`netinet/ip.h`, `netinet/tcp.h`)로 각 계층 필드를 해석한다.

### BPF: 커널에서 거르기

libpcap의 필터는 BPF(BSD Packet Filter)로 구현된다. BPF는 사용자 프로그램이 의사 기계어로 작성한 필터를 소켓에 붙여, 원하지 않는 패킷을 커널 단계에서 버리게 하는 구조다[^bpf]. 필터가 없으면 커널은 모든 패킷을 사용자 공간으로 복사한 뒤 응용이 버려야 하지만, BPF를 붙이면 커널이 먼저 거르므로 복사 비용이 크게 준다.

![BPF 없는 패킷 흐름과 BPF 필터·버퍼가 링크 계층 드라이버와 프로토콜 스택 사이에서 거르는 흐름의 비교](./images/net-sniffing-spoofing-bpf.svg 'BPF는 커널 안에서 원치 않는 패킷을 먼저 버린다')

Wireshark나 tcpdump가 `port 22` 같은 문자열을 넣으면, pcap이 이를 BPF 의사 코드로 컴파일해 소켓에 붙인다. 컴파일된 BPF 프로그램은 `setsockopt(sock, SOL_SOCKET, SO_ATTACH_FILTER, &bpf, sizeof(bpf)){:c}`로 부착된다. 커널이 패킷을 받으면 BPF가 실행되고, 통과한 패킷만 위로 올라간다.

```c
/* port 22 필터를 컴파일한 BPF 프로그램 (tcpdump -dd 'port 22' 형식) */
struct sock_filter code[] = {
	{ 0x28, 0, 0, 0x0000000c }, { 0x15, 0, 8, 0x000086dd },
	{ 0x30, 0, 0, 0x00000014 }, { 0x15, 2, 0, 0x00000084 },
	{ 0x15, 1, 0, 0x00000006 }, { 0x15, 0, 17, 0x00000011 },
	{ 0x28, 0, 0, 0x00000036 }, { 0x15, 14, 0, 0x00000016 },
	{ 0x28, 0, 0, 0x00000038 }, { 0x15, 12, 13, 0x00000016 },
	{ 0x15, 0, 12, 0x00000800 }, { 0x30, 0, 0, 0x00000017 },
	{ 0x15, 2, 0, 0x00000084 }, { 0x15, 1, 0, 0x00000006 },
	{ 0x15, 0, 8, 0x00000011 }, { 0x28, 0, 0, 0x00000014 },
	{ 0x45, 6, 0, 0x00001fff }, { 0xb1, 0, 0, 0x0000000e },
	{ 0x48, 0, 0, 0x0000000e }, { 0x15, 2, 0, 0x00000016 },
	{ 0x48, 0, 0, 0x00000010 }, { 0x15, 0, 1, 0x00000016 },
	{ 0x06, 0, 0, 0x0000ffff }, { 0x06, 0, 0, 0x00000000 },
};

struct sock_fprog bpf = {
	.len = ARRAY_SIZE(code),
	.filter = code,
};
```

tcpdump의 `-d` 옵션으로 사람이 읽을 수 있는 BPF 의사 어셈블리를, `-dd`로 C 배열 형태를 볼 수 있다. 각 명령은 `{opcode, jt, jf, k}` 네 값으로 이루어지며, EtherType이 IP(0x0800)인지, 프로토콜이 TCP(6)인지, 포트가 22인지를 차례로 분기 검사한다.

## 원시 소켓과 스푸핑의 원리

### 수집 경로: 일반 소켓에서 원시 소켓으로

일반 소켓(`SOCK_DGRAM`, `SOCK_STREAM`)은 특정 프로토콜과 포트의 데이터만 받고, 운영체제가 헤더를 벗겨 페이로드만 응용에 준다. 모든 종류의 패킷을 헤더까지 받으려면 원시 소켓(`SOCK_RAW`)으로 열고 무차별 모드를 켜야 한다. Linux에서 링크 계층까지 받는 수집 소켓은 다음처럼 연다.

```c
/* 모든 프로토콜의 프레임을 링크 계층부터 받는다 */
int sock = socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL));

/* 인터페이스를 무차별 모드로 설정 */
struct packet_mreq mr = {0};
mr.mr_type = PACKET_MR_PROMISC;
setsockopt(sock, SOL_PACKET, PACKET_ADD_MEMBERSHIP, &mr, sizeof(mr));
```

받은 버퍼의 앞부분을 Ethernet 헤더 구조체로 캐스팅하면 목적지·출발지 MAC과 EtherType을 읽을 수 있고, EtherType이 IP면 그 뒤를 IP 헤더 구조체로 캐스팅해 각 필드를 읽는다. 이것이 pcap이 내부에서 하는 일이고, 직접 원시 소켓을 다루는 방식은 OS마다 이식성이 없고 필터 설정이 번거로우며 최적화가 없다는 한계가 있다. 그래서 pcap 라이브러리가 만들어졌다. 내부적으로는 여전히 원시 소켓을 쓰지만 API가 플랫폼 공통이고, 사람이 읽는 불리언 식으로 필터를 지정할 수 있다.

### 스푸핑의 원리와 방어

패킷의 중요한 정보가 위조되면 이를 패킷 스푸핑이라 한다. 많은 네트워크 공격이 스푸핑에 기댄다. 일반 소켓으로 UDP 데이터그램을 보내면 운영체제가 출발지 IP 주소를 자기 주소로 채우므로 출발지를 위조할 수 없다. 반면 원시 소켓에 `IP_HDRINCL` 옵션을 켜면 IP 헤더를 응용이 직접 구성하고, 커널은 그 헤더를 그대로 내보낸다. 출발지 주소 필드에 자신이 아닌 주소를 넣으면 그 주소에서 온 것처럼 보이는 패킷이 만들어진다. 이것이 IP 스푸핑의 핵심이다.

스푸핑으로 만든 패킷은 다음 성질을 노린다. 공격자는 응답을 받을 필요가 없거나(DoS처럼 한 방향 공격), 응답을 추측할 수 있는 상황(순서 번호 예측)에서 위조 출발지를 활용한다. 수집 후 위조(sniff-and-spoof)는 먼저 pcap으로 관심 패킷을 수집하고, 출발지와 목적지를 뒤바꾼 응답을 만들어 진짜 서버보다 먼저 보내 상대를 속이는 방식이다. DNS 캐시 오염이 대표적이며 [DNS 공격](/memo/net-dns-attack)에서 다룬다.

> [!IMPORTANT] 스푸핑 방어
> IP 스푸핑은 네트워크 경계와 프로토콜 설계 양쪽에서 막는다. (1) 경계 라우터에서 출발지 주소 검증(ingress/egress filtering, BCP 38): 내부에서 나가는 패킷의 출발지가 실제 내부 대역인지 확인해 위조 출발지를 차단한다. (2) 예측 불가능한 초기 순서 번호(RFC 6528): TCP 세션에 끼어드는 공격을 어렵게 한다. (3) 종단 간 인증·암호화(TLS, IPsec): 출발지를 위조해도 인증을 통과하지 못하므로 세션을 가로채거나 변조할 수 없다. 수집 후 위조는 경합을 이용하므로, DNSSEC처럼 응답에 서명을 붙여 진위를 검증하는 방식이 근본 대책이다.

## Scapy로 패킷 다루기

Scapy는 Python으로 패킷을 구성하고 수집·해석하는 라이브러리로, Linux와 libpcap이 있는 대부분의 UNIX에서 동작하며 Python 2·3을 모두 지원한다. C로 원시 소켓을 다루는 것보다 패킷 구성이 훨씬 간단하지만 속도는 느리다. 그래서 Scapy로 패킷을 구성하고 C로 약간 수정해 보내는 혼합 방식도 쓴다.

수집은 `sniff()`에 BPF 필터와 패킷마다 호출할 콜백을 준다. 아래는 공개된 Scapy 문서의 예로, ICMP 패킷의 출발지·목적지·프로토콜만 출력한다.

```python
from scapy.all import sniff


def show(pkt):
	print('Source IP:', pkt['IP'].src)
	print('Destination IP:', pkt['IP'].dst)
	print('Protocol:', pkt['IP'].proto)


sniff(filter='icmp', prn=show)  # ICMP만 거르고 각 패킷에 show 적용
```

Scapy는 패킷을 계층 객체로 다루므로, 수집한 패킷의 각 계층 필드를 `pkt['IP'].src`처럼 이름으로 읽고 `pkt.show()`로 전체 구조를 확인할 수 있다. 바로 이 계층 모델 때문에 IP 계층의 출발지 필드에 자기 주소가 아닌 값을 넣는 일도 원리상 가능한데, 이것이 곧 IP 스푸핑의 핵심이자 경계 라우터의 출발지 검증(BCP 38)이 필요한 이유다. 이 글에서는 위조 패킷을 구성해 전송하는 코드는 싣지 않는다. 운영체제가 출발지를 자동으로 채우는 일반 소켓과 달리 원시 소켓은 헤더를 직접 구성할 수 있다는 개념만 이해하면, 방어가 왜 네트워크 경계(출발지 검증)와 프로토콜(TLS·DNSSEC의 인증·서명) 양쪽에 필요한지 설명된다. Scapy의 가치는 공격 도구라기보다, 프로토콜의 각 필드가 어떻게 조립되고 검증되는지를 눈으로 확인하며 방어 규칙(필터, 서명 검증)을 설계·시험하는 데 있다.

| 방식                     | 장점                       | 단점                       |
| ------------------------ | -------------------------- | -------------------------- |
| Python + Scapy           | 패킷 구성이 매우 간단하다  | C보다 훨씬 느리다          |
| C + 원시 소켓            | 훨씬 빠르다                | 패킷 구성이 복잡하다       |
| 혼합(Scapy 구성, C 전송) | 구성은 간단, 전송은 빠르다 | 두 언어를 함께 다뤄야 한다 |

## 정리

| 주제             | 핵심                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------- |
| 장비와 가시 범위 | 허브는 전부 보이고, 스위치는 자기 트래픽만 보인다                                     |
| 스위치 수집      | 포트 미러링, 허빙 아웃, 탭(정당한 수단), ARP 캐시 포이즈닝(공격, DAI·정적 ARP로 방어) |
| 무차별 모드      | NIC의 L2 필터를 열어 모든 프레임을 받는다. 탐지될 수 있다                             |
| pcap과 BPF       | pcap은 플랫폼 공통 API, BPF는 커널에서 먼저 거르는 필터                               |
| 원시 소켓        | 헤더를 직접 구성, `IP_HDRINCL`로 출발지 위조 가능 → BCP 38로 차단                     |
| 스푸핑 방어      | 출발지 검증, 예측 불가 순서 번호, TLS·IPsec·DNSSEC 같은 인증·서명                     |

패킷이 커널에서 응용까지 어떤 경로로 오르는지, 어느 필드가 검증되지 않는지를 알면 공격의 원리와 방어의 위치가 함께 보인다. 수집한 세그먼트로 TCP를 직접 노리는 공격은 [TCP 공격](/memo/net-tcp-attacks)에서, 소켓 API로 서버와 클라이언트를 만드는 과정은 [소켓 프로그래밍](/memo/net-socket-programming)에서 이어진다.
