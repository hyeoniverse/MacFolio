환경 변수 11개 중 8개가 Firebase 설정이고, 나머지 셋은 그림·음악·효과음 주소다. 접두사가 바뀌면 배포 환경에 등록한 변수 이름도 함께 변경해야 한다. 이 커밋에서는 코드만 변경했다.

```ts
// 전 (CRA): src/components/common/Dock.tsx
const imgUrl = process.env.REACT_APP_IMAGE_URL;
// 후 (Vite): VITE_ 접두사가 있는 변수만 브라우저 코드에 노출된다
const imgUrl = import.meta.env.VITE_APP_IMAGE_URL;
```

한 곳은 접두사 변경이 빠졌다. `Github.tsx`는 `import.meta.env.REACT_APP_IMAGE_URL`로 바뀌어, `import.meta.env`로 읽는 방식은 바뀌었지만 이름은 `REACT_APP_`로 남았다. Vite는 `VITE_` 접두사가 없는 변수를 브라우저 코드에 노출하지 않으므로 이 값은 `undefined`이고, GitHub 앱의 프로필 사진 주소가 `undefined/me.png`가 된다. 이튿날 Prettier 커밋 뒤에도 그대로였다. ==변경 결과를 확인할 시험이 없어서 발견되지 않은 사례다==. `App.test.tsx` 파일은 남아 있었지만 `package.json`에 `test` 스크립트가 없었다.

같은 커밋에서 컴포넌트와 CSS 대부분도 함께 변경되었다. 변경 줄 수는 창(`Container.tsx`) 572줄, 음악(`MusicPlayer.tsx`) 431줄, `MusicContext` 387줄 등이다.

### 누른 창을 맨 앞으로

맨 앞으로 올리는 방식은 이랬다. 모든 앱을 `zIndex` 순으로 정렬해 0부터 다시 번호를 매기고, 누른 앱에 가장 큰 번호를 부여한다.

```ts
const bringAppToFront = useCallback(
	(appName: AppName) => {
		const sortedApps = Object.entries(apps).sort(([, a], [, b]) => a.zIndex - b.zIndex);
		setApps((prevState) => {
			const updatedApps = { ...prevState };
			sortedApps.forEach(([name], index) => {
				updatedApps[name as AppName].zIndex = index;
			});
			updatedApps[appName].zIndex = sortedApps.length;
			return updatedApps;
		});
	},
	[apps]
);
```

이 코드에는 두 가지 문제가 있다. 정렬은 `setApps` 밖의 `apps`로 하고, 바깥 객체만 복사한 채 안쪽 객체의 `zIndex`를 직접 변경한다. ==같은 렌더에서 두 번 호출하면 앞의 결과를 반영하지 못한다==.

### 블로그 iframe이 클릭을 가져가는 문제

블로그 앱은 따로 운영하던 블로그(`codingkirby.github.io`)를 창 안에 iframe으로 표시하는 앱이다(60줄). 그런데 블로그 창이 뒤에 있을 때 그 안을 눌러도 맨 앞으로 올라오지 않았다. iframe 안의 클릭은 다른 문서의 이벤트라 바깥 창의 `onClick`까지 전달되지 않기 때문이다. 오후의 "fix: bring app to front" 커밋에서, 블로그 창이 맨 앞이 아닐 때만 iframe 위에 투명한 `div`를 덮어 클릭을 받게 했다.

```tsx
// 현재 blog 앱이 가장 높은 zIndex인지 확인
const isTopApp = Object.values(apps).every((app) => app.zIndex <= apps.blog.zIndex);

{
	!isTopApp && <div style={{ position: 'absolute', inset: 0, zIndex: 1 }} onClick={() => bringAppToFront('blog')} />;
}
```

맨 앞에 올라오면 덮개가 사라져 블로그를 그대로 조작할 수 있다. iframe을 창 안에 넣는 앱마다 필요한 처리인데, 이날은 블로그 앱에만 적용했다. 10월 15일에는 Blog 앱에 남아 있던 `bringAppToFront` 호출 하나를 삭제했다. 창을 맨 앞으로 올리는 처리를 `Container`가 담당하게 되었기 때문이다.

### 최소화 애니메이션, 위치 저장, 최대화 (2024년 10월 14일)

10월 14일 새벽 2시 11분부터 6시 42분 사이 커밋 8개는 음악 재생 상태(2개)와 창 동작(6개) 두 주제로 나뉜다.

![2024년 10월 14일 작업 흐름](./images/day-20241014-timeline.svg '새벽 2시와 4~6시에 커밋이 있다')

5시 48분에 최소화 애니메이션을 만들었다. 창의 중심을 기준으로 `translate`와 `scale(0)`을 0.5초 동안 적용하고, `setTimeout` 0.5초 뒤에 최소화 상태로 전환한다. 창 위치는 `containerPosition_<앱>` 키로 localStorage에 저장해, 다시 열면 같은 위치에 표시한다.

```ts
setIsMinimizing(true); // 애니메이션을 트리거
setTimeout(() => {
	minimizeApp(appName);
	setIsMinimizing(false);
	savePositionToStorage(position.x, position.y);
}, 500); // 애니메이션 시간과 맞춰서
```

CSS 전환 0.5초와 `setTimeout` 500ms를 각각 하드코딩해 일치시킨 구조다. 6시 15분과 42분에는 최대화를 구현했다. 최대화하면 창을 상태 막대(25px) 아래부터 화면 끝까지 확장하고, 이전 크기를 `containerSize_<앱>` 키로 저장해 복원할 때 사용한다. 화면 끝까지 확장했기 때문에 최대화한 창이 Dock을 가렸다. 10월 15일에는 제목 표시줄의 더블클릭 최대화(`onDoubleClick={handleMaximize}`) 줄을 정리했다.

| localStorage 키          | 저장 값        | 사용 시점            |
| ------------------------ | -------------- | -------------------- |
| `containerPosition_<앱>` | 창의 x, y      | 최소화 후 다시 열 때 |
| `containerSize_<앱>`     | 최대화 전 크기 | 최대화를 해제할 때   |

### isRunning 하나에 묶인 창과 실행

`AppContext`의 `isRunning`은 창 표시 여부와 앱 실행 여부를 함께 나타냈다. 창을 닫으면 앱도 종료된 것으로 처리했다. 그래서 배경 음악이 재생되는 중에도 음악 창을 닫으면 음악 앱이 "종료" 상태였다. 음악은 창과 무관하게 재생되도록 Context로 옮겼는데([음악과 효과음](#음악과-효과음)), 앱 상태는 여전히 "창이 열려 있다 = 실행 중"이었다. ==이 불일치는 2년 동안 남아 있다가 버그 세 개로 드러났고==, 2026년 10월 18일에 창 표시와 앱 실행 상태로 분리했다.

### Express와 MySQL, 메모 단위 비밀번호 (2024년 10월 21~22일)

21일의 커밋은 밤 11시 26분부터 43분까지 셋이고, 22일 새벽으로 그대로 이어진다. 이틀 커밋은 17개다.

![2024년 10월 21~22일 작업 흐름](./images/day-20241021-timeline.svg '21일 밤 11시부터 22일 새벽 4시까지, 그리고 22일 오전 10시 전후')

21일 밤 11시 26분 커밋 "FEAT: Memo app"은 서버를 Express 생성기의 JavaScript에서 TypeScript로 다시 썼다. `routes → controllers → models` 3계층으로 나누고, `mysql2`의 연결 풀로 MySQL에 연결했다. 테이블은 `folders`와 `memos` 두 개다.

| 계층        | 역할                                                                           |
| ----------- | ------------------------------------------------------------------------------ |
| routes      | 주소와 HTTP 메서드를 컨트롤러에 연결한다 (`PUT /:id` → `updateMemoController`) |
| controllers | 요청 값을 모델에 전달하고 응답을 반환한다                                      |
| models      | `mysql2` 연결 풀로 SQL을 실행한다                                              |

화면에서는 10월 15일 코드에 작성한 폴더·메모를 삭제하고, `MemoContext`가 axios로 서버를 호출하게 했다. 메모를 수정하면 목록의 제목도 즉시 갱신된다.

![메모 저장 흐름](./images/day-20241021-structure.svg '편집 권한이 사용자가 아니라 메모 단위로 정해졌다')

로그인 기능이 없어서, 수정·삭제 권한을 구분하는 방법으로 메모마다 비밀번호를 지정했다. `memos.password` 열에 bcrypt 해시를 저장하고, 수정·삭제 경로 앞에 검증 미들웨어를 배치했다.

```ts
// 메모 수정 (비밀번호 검증 필요)
router.put('/:id', validatePassword, updateMemoController);
// 메모 삭제 (비밀번호 검증 필요)
router.delete('/:id', validatePassword, deleteMemoController);
```

`validatePassword`는 요청 본문의 `password`를 `bcrypt.compare`로 해당 메모의 해시와 비교한다.

| 경우                   | 응답                 |
| ---------------------- | -------------------- |
| 요청에 비밀번호가 없음 | 400                  |
| 메모가 없음            | 404                  |
| 비밀번호 불일치        | 403                  |
| 일치                   | 다음 컨트롤러로 진행 |

22일 오전 9시 49분에 화면에 삭제 기능을 추가하면서, 비밀번호를 입력받는 창을 표시하게 했다. 메모마다 비밀번호를 지정한 것은 "누가 수정할 수 있는가"를 "무엇을 알고 있는가"로 바꾼 것이다. 로그인 없이 구현할 수 있는 가장 가까운 방법이었지만, 비밀번호를 아는 사람은 누구든 관리자 권한을 갖는다.

메모 화면도 함께 바뀌었다. 22일 0시 9분에 `Memo.tsx`에서 `FolderList`, `MemoItem`, `MemoTools`를 분리했고, 새 메모에는 기본 제목과 내용을 지정했다. 2시 58분 커밋의 "고정"은 다음과 같은 정렬 규칙이었다.

```ts
.sort((a, b) => {
	// 1번 폴더에서 id가 1인 메모를 상단 고정
	if (selectedFolder === 1) {
		if (a.id === 1) return -1;
		if (b.id === 1) return 1;
	}
	return b.id - a.id;
});
```

고정할 메모를 선택하는 기능이 아니라, id가 1인 메모를 "모든 메모" 폴더 맨 위에 배치하는 규칙이었다. 고정 기능 대신 고정된 결과를 코드에 작성한 것이다. 4시 13분에는 작성 중인 새 메모를 저장 전까지 임시 메모로 목록에 표시했다.

시간대 처리도 변경했다. 화면의 `toLocaleString`에 지정하던 `timeZone: 'Asia/Seoul'`을 삭제하고, DB 연결에 `timezone: '+09:00'`을 지정했다. 시간대 변환을 화면마다 처리하지 않고 DB 연결 한 곳에서 처리한다.

### Cloud SQL로 이전 (2024년 10월 26일)

26일 아침 8시부터 8분 동안 커밋이 넷이다.

![2024년 10월 26~27일 작업 흐름](./images/day-20241026-timeline.svg '26일 아침 8시에 넷, 27일은 하루 종일 npm install')

8시 정각 커밋은 DB 연결 대상을 Google Cloud SQL로 변경했다. 코드 변경은 적다. 연결 설정에 포트(`DB_PORT`, 기본값 3306)를 추가하고 주석을 작성했을 뿐, 주소·사용자·비밀번호는 이전과 같이 환경 변수에서 읽는다. 변경된 것은 환경 변수가 가리키는 DB 서버다. 마지막 커밋에서 `macbook.sql`(83줄)에 테이블 정의를 기록했다.

```sql
CREATE TABLE `memos` (
  `id` int NOT NULL AUTO_INCREMENT,
  `folder_id` int DEFAULT NULL,
  `title` varchar(300) DEFAULT NULL,
  `content` text,
  `password` varchar(60) NOT NULL DEFAULT '0000',
  ...
```

> [!WARNING] 해시가 아닌 기본값
> `password`의 기본값 `'0000'`은 bcrypt 해시가 아니다. `bcrypt.compare`는 해시 형식이 아닌 값과 비교하면 항상 불일치를 반환하므로, 비밀번호 없이 생성된 메모는 아무도 수정하거나 삭제할 수 없었을 것이다.

### 서버 삭제와 Firebase 이전 (2024년 12월 23일)

12월 22일 밤과 23일 새벽에 커밋이 하나씩이다. 22일 커밋은 [코드 형식 정리](#코드-형식-정리-2024년-12월-22일-2025년-3월-24일)이고, 23일 새벽 2시 36분 커밋은 59,588개 파일을 변경했다.

![2024년 12월 22~23일 작업 흐름](./images/day-20241222-timeline.svg '22일 밤 9시 39분과 23일 새벽 2시 36분')

1. `server/`를 삭제했다. Express, TypeScript 컨트롤러, MySQL 연결이 모두 제거되었다.
2. `client/` 안의 앱을 저장소 루트로 옮겼다. `client/src`가 `src`가 되었고, React를 18.3에서 19.0으로 업그레이드했다.
3. Firebase를 연동했다. 호스팅은 `build` 폴더를 배포하고 모든 경로를 `index.html`로 재작성(rewrite)한다. 메모는 Realtime Database의 `memos/<폴더>/<id>` 경로에 저장한다.

![Firebase 전후 구조](./images/day-20241222-structure.svg '서버를 제거하고 브라우저가 데이터베이스를 직접 읽고 쓴다')

서버를 삭제한 이유는 커밋에 기록되어 있지 않다. 코드로 보면 Express 서버와 Cloud SQL을 별도로 운영하는 대신, 정적 호스팅과 관리형 데이터베이스로 전환하는 선택이었다. 그 과정에서 서버가 담당하던 권한 확인도 함께 사라졌다. 이 커밋의 데이터베이스 보안 규칙은 다음과 같았다.

```json
{
	"rules": {
		".read": true,
		".write": true
	}
}
```

> [!CAUTION] 평문 비밀번호와 누구나 읽는 데이터베이스
> 이 규칙에서는 누구나 모든 메모를 읽고 쓸 수 있다. 메모 비밀번호는 10월 21일부터 서버가 bcrypt 해시로 비교했는데, 이 커밋부터는 브라우저가 메모의 `password` 값을 그대로 읽어 `memo.password === password`로 비교한다. 비밀번호가 평문으로 데이터베이스에 저장되고, 그 데이터베이스는 누구나 읽을 수 있었다.

| 항목             | 서버 시절 (10월 21일~) | Firebase 이전 후 (12월 23일~) |
| ---------------- | ---------------------- | ----------------------------- |
| 비밀번호 저장    | bcrypt 해시            | 평문                          |
| 비교 위치        | 서버 미들웨어          | 브라우저                      |
| 데이터 읽기·쓰기 | 서버 경로만            | 규칙상 누구나                 |

서버를 제거할 때는 서버의 역할을 목록으로 정리하고, 각 역할을 어디로 옮길지 하나씩 정해야 했다. =="누가 쓸 수 있는가"의 확인은 이 이전 뒤 아무 곳에서도 하지 않게 되었다==.

## 돌아보며

첫 커밋에 이미 "macOS 화면 안에 포트폴리오를 배치한다"는 설계가 담겨 있었다. 창, Dock, 상태 막대, 음악, Safari 안의 프로젝트다. 화면의 큰 틀은 지금도 그대로이고, 바뀐 것은 그 구조를 구현하는 코드다. 455줄짜리 파일 하나가 하던 일이 지금은 패키지와 앱 수십 개로 나뉘었다.

상태를 관리할 위치를 먼저 정한 작업과 그렇지 않은 작업의 차이가 컸다. 10월 13일 아침에 `AppContext`와 `Container`라는 기반을 먼저 만들었기 때문에, 크기 조절·애니메이션·맨 앞으로 올리기를 같은 날 하나씩 추가할 수 있었다. 반대로 음악은 창 밖으로 옮겼으면서 앱 상태의 `isRunning`은 같은 기준으로 바꾸지 않아, 그 불일치가 2년 뒤 버그로 드러났다.

서버는 사용할 곳보다 먼저 생겼다. 10월 13일의 Express 서버와 메일 경로, 15일의 메모 경로는 화면이 호출하지 않았고, 메일 앱은 결국 `mailto:`로 갔다. 서버를 삭제할 때는 반대로 서버가 맡던 권한 확인을 옮길 곳을 정하지 않았다. 2026년에 다시 서버를 구축할 때는 먼저 데이터베이스를 차단하고 편집을 잠근 뒤, 서버에 로그인과 권한 확인을 구현하고 나서 편집을 허용했다.

"무엇을 저장소에 보관하는가"에 대한 판단은 이틀 사이에 반대로 내려졌다. 10월 26일에는 있으면 안 되는 `.env`를 제외했고, 27일에는 없어도 되는 `node_modules`를 추가했다. 커밋 전에 `git status`로 변경 파일 목록을 확인했다면 11월 4일의 캐시 커밋도 생기지 않았을 것이다. 마지막으로, Vite 이전에서 `REACT_APP_` 이름이 남은 사례처럼 변경을 확인할 시험이 없었다. 1년 반 뒤 작업을 재개했을 때 가장 먼저 한 일이 시험을 추가하는 것이었고, 그 과정에서 한 번도 동작한 적 없던 기능이 나왔다.
