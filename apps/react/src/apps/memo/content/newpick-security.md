재배포하기 전에 가장 먼저 api의 모든 라우트를 읽었다. 컨트롤러마다 인증 데코레이터를 붙이는 방식이었는데, 붙이지 않은 라우트가 그대로 공개되어 있었다. 이 글은 리팩토링 1단계(api PR #2, web PR #3)에서 무엇이 열려 있었고 어떻게 막았는지 정리한다. 시리즈 전체 순서는 [첫 글](/memo/newpick-v2-start)에 있다.

## 열려 있던 것

| 경로                               | 문제          | 영향                                    |
| ---------------------------------- | ------------- | --------------------------------------- |
| `POST /mail/send-html`             | 인증 없음     | 누구나 팀 Gmail로 임의 메일 발송        |
| `GET /auth/users`                  | 인증 없음     | password 컬럼을 포함한 전체 사용자 노출 |
| `PATCH /admin/users/:id`           | 로그인만 확인 | 누구나 자기 자신을 admin으로 변경       |
| `POST /scheduler/manual/mail-send` | 인증 없음     | 전체 구독자에게 메일 발송               |
| `POST /ai-summary/summarize`       | 제한 없음     | 호출할 때마다 OpenAI 비용 발생          |

마지막 줄은 인증 문제가 아니라 비용 문제다. 홈 화면의 무료 체험은 로그인 없이 쓰는 기능이라 공개가 맞지만, 횟수 제한이 없어 반복 호출만으로 요금이 쌓일 수 있었다.

## 기본값을 "로그인 필요"로 뒤집기

원인은 하나였다. 보호가 "붙여야 생기는 것"이었기 때문에, 새 라우트를 만들고 데코레이터를 잊으면 공개된다. 그래서 기본값을 뒤집었다.

- 전역 `JwtAuthGuard`가 모든 라우트에 로그인 확인을 적용한다.
- 공개 라우트는 `@Public()`, 관리자 라우트는 `@AdminOnly()`로 명시한다.
- 위의 다섯 경로 중 쓰는 곳이 없는 메일 API, user 모듈(`/auth/users`, `/auth/register`), Sentry 테스트 라우트, `scheduler/mailtest`는 삭제했다.

이제 데코레이터를 잊으면 "공개"가 아니라 "로그인 필요"가 된다. 실수의 방향이 안전한 쪽으로 바뀐다.

## 정책을 표로 고정한 테스트

기본값을 뒤집어도, 누군가 `@Public()`을 잘못 붙이면 다시 열린다. 그래서 라우트 59개의 접근 정책을 표로 적고, 실제 등록된 라우트와 비교하는 테스트를 만들었다.

| 정책   | 라우트 수 |
| ------ | --------- |
| 공개   | 15        |
| 로그인 | 16        |
| 관리자 | 28        |

테스트는 컨트롤러의 데코레이터 메타데이터에서 라우트와 정책(`@Public`, `@AdminOnly`, 둘 다 없으면 로그인)을 읽어 표와 비교한다. 라우트를 추가하고 표에 정책을 적지 않으면 실패하고, 정책이 표와 다르면 실패한다. 접근 정책을 바꾸는 PR은 반드시 이 표의 diff를 포함하게 되므로, 리뷰에서 눈에 띈다.

## 관리자 권한 상승 막기

`PATCH /admin/users/:id`는 로그인만 확인했고, 요청 본문을 그대로 사용자 정보에 반영했다. 일반 사용자가 자기 id로 `{"role":"admin"}`을 보내면 관리자가 됐다.

- `AdminGuard`는 토큰에 적힌 값이 아니라 **DB의 role**을 확인한다. 관리자 권한을 DB에서 회수하면 같은 토큰으로도 바로 403이 된다.
- 수정 API는 DTO로 `role`만 받는다. 허용하지 않은 값(`superadmin`)은 400이다.
- 응답에서 password 필드를 뺐다.

2단계에서 DB를 띄운 뒤 실제 요청으로 다시 확인했다.

| 요청                                             | 비로그인 | 일반 사용자                 | 관리자                   |
| ------------------------------------------------ | -------- | --------------------------- | ------------------------ |
| `GET /admin/users`                               | 401      | 403                         | 200 (password 필드 없음) |
| `PATCH /admin/users/:id` `{"role":"admin"}`      |          | 403 (DB role은 그대로 user) |                          |
| `PATCH /admin/users/:id` `{"role":"superadmin"}` |          |                             | 400                      |
| 관리자 권한을 DB에서 회수한 직후 같은 토큰       |          |                             | 403                      |
| refresh 토큰을 access 쿠키에 넣은 경우           | 401      |                             |                          |

## 무료 체험 비용 막기

무료 체험 요약은 공개로 두되 세 가지를 더했다.

1. 요청 값과 관계없이 항상 체험 모드로 실행한다. 이전에는 요청 본문의 `test` 값이 `false`면 결과를 뉴스레터로 DB에 저장했다.
2. 같은 카테고리·기간 요청은 6시간 동안 캐시된 결과를 돌려준다.
3. IP당 10분에 5회로 제한한다. 6번째 요청은 429다.

## 비밀값과 그 밖의 버그

- 토큰과 Sentry DSN을 출력하던 로그를 지웠다.
- `JWT_SECRET`과 `JWT_REFRESH_SECRET`은 필수이고, 둘이 같으면 서버가 시작되지 않는다. 같은 값이면 refresh 토큰을 access 토큰으로 쓸 수 있기 때문이다.
- 구독을 취소하면 `feedback.deleteMany`로 북마크까지 전부 지워지던 문제를 고치고 트랜잭션으로 묶었다.
- 메일 발송 대상에 팀원 개인 메일이 하드코딩되어 있던 것을 환경 변수(`ADMIN_NOTIFY_EMAIL`)로 바꿨다.

## web: 기사 본문 XSS

기사 본문은 크롤링한 뉴스로 AI가 만든 HTML이고, 기사 상세 페이지는 이를 `dangerouslySetInnerHTML`로 그대로 렌더링했다. 원문이나 모델 출력에 스크립트가 섞이면 그 기사를 여는 모든 방문자의 브라우저에서 실행된다. 같은 HTML을 보여 주는 무료 체험 화면은 sanitize하고 있었지만 기사 상세는 빠져 있었다.

DOMPurify로 정리하는 공통 함수 `sanitizeHtml`을 만들어 두 화면이 같이 쓰게 했다. 서버 렌더링 중에는 DOM이 없으므로 빈 문자열을 돌려준다(실패하면 막는 쪽, fail closed).

| 입력                         | 결과                        |
| ---------------------------- | --------------------------- |
| `<h2>`, `<p>`, 일반 링크     | 유지 (`target` 속성만 제거) |
| `<img onerror=...>`          | `onerror` 제거              |
| `<script>...</script>`       | 제거                        |
| `<a href="javascript:...">`  | `href` 제거                 |
| `<svg><animate onbegin=...>` | 제거                        |
| `<iframe>`                   | 제거                        |

## 남은 것·배운 것

- 가장 효과가 큰 수정은 개별 라우트를 막은 것이 아니라 **기본값을 뒤집은 것**이었다. 이후 단계에서 라우트를 여럿 추가·삭제했지만, 정책 표 테스트 덕분에 매번 의도한 정책인지 확인할 수 있었다.
- `GET /auth/refresh`가 새 access token을 응답 본문에도 담아 보내는 문제는, 프론트 서버 쪽 재시도 코드가 그 값을 쓰고 있어서 4단계로 미뤘다([요청 경로를 하나로](/memo/newpick-api-client)에서 정리).
- web에는 아직 테스트 러너가 없어서, XSS 표는 수동으로 확인했다. 5단계에서 단위 테스트로 옮긴다.
