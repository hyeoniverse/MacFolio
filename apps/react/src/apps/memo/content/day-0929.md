## Safari를 포트폴리오로

Safari를 프로젝트 포트폴리오로 바꿨다. 프로젝트 목록을 GitHub 고정 저장소(프로필 상단에 고정해 둔 저장소)와 일치시키고, 프로젝트마다 탭이 하나씩 열리게 하고, 소개 페이지는 Apple 제품 페이지와 같은 구성으로 작성했다. 새싹 농장은 게임을 창 안에서 바로 실행하는 앱으로 추가했다([iframe 안 클릭을 window blur 이벤트로 감지해 창을 맨 앞으로 가져오기](/memo/game-in-iframe)).

![지금의 Safari](./images/day-0929-safari.jpg '프로젝트마다 탭이 열린 Safari의 현재 모습. 페이지 내용은 10월 4일에 대부분 재작성했다')

전날 만든 휴대폰 셸도 머지했다([#33](https://github.com/hyeoniverse/MacFolio/pull/33)).

## API 서버: 처음 만든 기능

이전까지 이 사이트는 정적 사이트였다. 정적 사이트는 미리 빌드한 HTML·JS·CSS 파일만 전달하므로, 방문자가 남긴 댓글이나 관리자가 쓴 글을 저장할 곳이 없다. 이를 위해 API 서버를 만들었다. API 서버는 브라우저의 요청(예: `POST /posts`에 글 내용을 담아 보냄)을 받아 권한을 확인하고 데이터베이스에 저장한 뒤 결과를 JSON으로 응답한다.

| 구성 요소                                      | 역할                                                               |
| ---------------------------------------------- | ------------------------------------------------------------------ |
| [NestJS](https://docs.nestjs.com/)             | Node.js 서버 프레임워크. 기능별 모듈·컨트롤러·가드로 코드를 나눈다 |
| [Prisma](https://www.prisma.io/docs)           | TypeScript 코드에서 데이터베이스를 타입이 있는 객체로 다루는 ORM   |
| [PostgreSQL](https://www.postgresql.org/docs/) | 글·댓글·세션을 저장하는 관계형 데이터베이스                        |

추가한 기능은 다음 순서다.

| 순서 | 추가한 기능                                                   | 글                                                                                                |
| ---- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 1    | NestJS + Prisma + PostgreSQL 기본 구조                        | -                                                                                                 |
| 2    | GitHub OAuth, DB 세션, 관리자만 통과하는 AdminGuard           | [GitHub OAuth와 토큰 해시만 저장하는 DB 세션으로 관리자 인증하기](/memo/admin-login-github-oauth) |
| 3    | 로그인 버튼 위치: Apple 메뉴, 제어 센터, 암호 앱, 설정의 계정 | [캡처 단계 리스너와 Touch Events로 구현한 전체 화면 스와이프 판정](/memo/control-center-swipe)    |
| 4    | 관리자가 정한 폴더 정리를 API에                               | [Markdown 글은 두고 서버 JSON 한 행으로 겹치는 메모 폴더 정리](/memo/memo-organization-api)       |
| 5    | 댓글                                                          | [scrypt 비밀번호 해시와 IP HMAC만 저장하는 가입 없는 댓글](/memo/post-comments)                   |
| 6    | 관리자 글쓰기·편집·삭제, 편집 버튼 없이 메모처럼 바로 수정    | [Markdown 블로그에 글쓰기 붙이기](/memo/post-editor)                                              |

2번의 [GitHub OAuth](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)는 사이트가 비밀번호를 직접 받지 않고 GitHub에 로그인을 맡기는 방식이다. 사용자가 GitHub에서 로그인과 승인을 마치면 GitHub가 사이트 서버에 일회용 코드를 넘기고, 서버는 그 코드로 사용자의 GitHub 계정 정보를 조회한다. NestJS의 [가드(Guard)](https://docs.nestjs.com/guards)는 요청이 컨트롤러에 도달하기 전에 실행되어 통과 여부를 결정하는 클래스로, `AdminGuard`는 세션이 관리자 계정의 것인지 확인한다.

### 세 계층의 입력 검증

글의 필수 항목(제목·날짜·폴더·본문)은 세 계층에서 같은 규칙으로 검증한다.

| 계층 | 검증 방법              | 막는 경우               |
| ---- | ---------------------- | ----------------------- |
| 화면 | 저장 전 입력 검사      | 일반적인 입력 실수      |
| API  | 같은 규칙으로 400 응답 | 화면을 거치지 않은 요청 |
| DB   | CHECK 제약             | API를 거치지 않은 쓰기  |

화면 검사만으로는 충분하지 않다. 브라우저의 화면 코드는 사용자가 수정하거나 건너뛸 수 있으므로, `curl`로 API에 직접 요청을 보내면 화면 검사를 거치지 않는다. [CHECK 제약](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS)은 PostgreSQL이 행을 쓸 때마다 조건식을 검사해, 조건을 만족하지 않는 쓰기를 거부하는 규칙이다.

![화면, API, DB 세 계층이 각각 다른 경로의 잘못된 쓰기를 거절하는 모습](./images/day-0929-validation-layers.svg '앞 계층을 우회한 요청도 뒤 계층에서 같은 규칙으로 거절된다')

API e2e는 GitHub만 가짜 응답으로 대체하고 실제 PostgreSQL에 연결해 실행한다. ==관리자가 아닌 계정이 차단되는지, 위조한 요청이 거절되는지==까지 확인한다. API e2e 30개, API 단위 시험 38개로 시작했다.

## 관리자 로그인: 아이디 대신 숫자 ID

로그인은 처음 구현한 뒤 같은 날 다시 고쳤다. 관리자 여부를 GitHub **아이디(login)**로 판단하고 있었는데, ==아이디는 변경할 수 있다.== GitHub 문서([Changing your GitHub username](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-user-account-settings/changing-your-github-username))는 아이디를 바꾸면 이전 아이디를 누구나 다시 등록할 수 있다고 명시한다. 관리자가 아이디를 바꾸면 이전 아이디를 다른 사람이 등록할 수 있고, 그 사람이 로그인하면 서버가 관리자로 인식한다.

GitHub의 사용자 정보 API([REST API: Users](https://docs.github.com/en/rest/users/users))는 `login`(아이디)과 함께 계정마다 부여되는 숫자 `id`를 반환한다. 숫자 `id`는 아이디를 바꿔도 그대로 유지된다.

| 기준             | 변경 가능 | 위험                                           |
| ---------------- | --------- | ---------------------------------------------- |
| 아이디 (`login`) | 가능      | 이전 아이디를 등록한 다른 사람이 관리자가 된다 |
| 숫자 ID (`id`)   | 불가능    | 계정마다 고정                                  |

![관리자가 아이디를 바꾼 뒤 다른 사람이 옛 아이디를 등록했을 때, login 비교는 통과시키고 id 비교는 차단하는 모습](./images/day-0929-login-takeover.svg '아이디는 다른 계정으로 옮겨 갈 수 있고, 숫자 id는 계정에 고정된다')

변경되지 않는 **숫자 ID**로 판단하도록 고치고(`ADMIN_GITHUB_ID` 환경 변수), 로그인 요청에는 IP별 횟수 제한을 적용했다. 횟수 제한은 같은 IP에서 짧은 시간에 로그인 요청을 반복하면 일정 시간 거절하는 규칙으로, 자동화된 반복 시도를 막는다.

## 돌아보며

- 서버 기본 구조부터 로그인, 편집, 댓글, 글쓰기까지 갖춰서, 다음 날에는 배포만 하면 되는 상태였다.
- 인증은 로그인 성공 여부보다 ==관리자가 아닌 사람이 확실히 차단되는지==를 먼저 확인해야 한다. 아이디 기준 판정도 관리자 본인의 로그인은 정상적으로 통과시켰다. 문제는 관리자가 아닌 사람이 통과하는 경로에 있었다.
- API의 PR 네 개([#41](https://github.com/hyeoniverse/MacFolio/pull/41)~[#44](https://github.com/hyeoniverse/MacFolio/pull/44))를 서로 의존하게 만들어서 다음 날 한꺼번에 머지해야 했다. 앞 PR을 고치면 뒤 PR을 모두 다시 맞춰야 하므로, 리뷰와 머지 순서가 모두 복잡해진다.
- 프로젝트 정보를 직접 작성하다가 NewPick 팀 구성(5인, 프론트엔드 2·백엔드 3)을 잘못 적었다. 그래서 10월 4일에 저장소를 근거로 수치를 다시 검증했다.
