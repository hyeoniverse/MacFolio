리팩토링 3단계는 "데이터가 서로 어긋나지 않게"가 목표였다. 이 글은 그중 데이터 모델 부분(PR #24, 19개 파일, +517 / −445줄)을 다룬다. 날짜·스케줄러·메일은 [다음 글](/memo/newpick-kst-scheduler)에 있다.

## 문제

| 데이터      | v1 구조                                | 문제                                                                 |
| ----------- | -------------------------------------- | -------------------------------------------------------------------- |
| 관심사      | `User.interests` (Json)                | 카테고리와 연결이 보장되지 않고, 네 곳이 같은 JSON을 각자 해석       |
| 북마크      | `feedbacks` 테이블의 `likes = true` 행 | 같은 이름의 `Bookmark` 모델은 비어 있는데, 관리자 화면은 그쪽을 조회 |
| 북마크 조회 | `usedNews contains newsId.toString()`  | URL 문자열 검색이라, id가 없으면 거의 모든 뉴스레터와 매칭           |
| 비밀번호    | `users.password` NOT NULL              | 로컬 로그인이 없는데, 채우려고 Google 계정 식별자를 저장             |

관심사를 JSON으로 두면 카테고리를 지워도 사용자 데이터에는 남고, 숫자 대신 `"IT"` 같은 문자열이 들어가도 DB가 막지 않는다. 실제로 JSON을 해석하는 코드가 네 군데에 있었고, 서로 처리 방식이 조금씩 달랐다.

## 조인 테이블로

```text
users ─┬─< user_interests (userId, categoryId) >── news_categories
       └─< bookmarks (userId, newsletterId, UNIQUE) >── newsletters
```

- 관심사: `user_interests(userId, categoryId)`. 두 FK와 복합 기본 키
- 북마크: `bookmarks(userId, newsletterId)` + 유니크 제약. `feedbacks` 테이블은 삭제
- `users.password`, `oauth_tokens.accessToken`(쓰는 곳 없음) 삭제

프론트는 이 단계에서 건드리지 않기로 했으므로, API 응답 형태는 그대로 유지했다. 프로필의 `interests: number[]`, `GET/PUT /mypage/interests`, `/mypage/bookmarks`, `POST/DELETE /feedback/bookmark`가 이전과 같은 모양으로 응답한다. 테이블은 바뀌어도 화면은 바뀌지 않는다.

## migration을 예전 데이터로 시험하기

스키마만 바꾸면 기존 데이터를 옮겨야 한다. MySQL 8의 `JSON_TABLE`로 JSON 배열을 행으로 펼쳐 `user_interests`에 넣고, `feedbacks`의 북마크를 `bookmarks`로 옮기는 SQL을 migration에 직접 썼다.

빈 DB에서는 이 SQL이 아무것도 하지 않으므로 시험이 되지 않는다. 그래서 **예전 형식의 데이터를 일부러 넣은 DB**에 migration을 적용해 확인했다.

| 기존 데이터                               | 결과                                    |
| ----------------------------------------- | --------------------------------------- |
| 관심사 `[2,3,3,99]`                       | 2, 3 (중복 제거, 없는 카테고리 99 제외) |
| 관심사 `"IT"` (배열 아님), `NULL`         | 건너뜀, 오류 없음                       |
| 같은 뉴스레터 북마크 2건                  | 1건, 가장 이른 날짜 유지                |
| `likes = false`, 뉴스레터가 없는 feedback | 제외                                    |

## 구독 시작: 저장하기 전에 확인

구독 시작 API는 관심사를 먼저 저장한 뒤 이미 구독 중인지 확인했다. 그래서 구독 중인 사용자가 다른 관심사로 다시 요청하면, 응답은 409(이미 구독 중)인데 관심사는 새 값으로 바뀌어 있었다. 실패한 요청이 데이터를 바꾼 것이다.

| 순서 | 이전                 | 이후                                          |
| ---- | -------------------- | --------------------------------------------- |
| 1    | 관심사 저장          | 중복 구독 확인 → 409면 여기서 끝              |
| 2    | 중복 구독 확인 → 409 | 카테고리 id 검증 → 없는 id면 400              |
| 3    | 구독 변경            | 관심사 교체 + 구독 변경을 **한 트랜잭션**으로 |

## 확인

| 요청                                       | 결과                           |
| ------------------------------------------ | ------------------------------ |
| `PUT /mypage/interests` `[5,1,1]`          | `[1,5]`                        |
| `PUT /mypage/interests` `[1,77]`, `["IT"]` | 400                            |
| 북마크 추가 → 같은 요청 → 없는 뉴스레터    | 201 → 409 → 404                |
| 북마크 삭제 → 다시 삭제                    | 200 → 404                      |
| 구독 시작 → 다른 관심사로 다시 시작        | 201 → 409, **관심사는 그대로** |
| 해지 → 재구독                              | 관심사 `[]` → 201              |

단위 테스트는 22개가 됐다(구독 시작·해지 5개, 북마크 5개 추가). 요청 DTO도 검증하게 바꿨다. 이전에는 대부분의 요청 본문이 인라인 타입이라 `ValidationPipe`가 아무것도 검사하지 않았다.

## 남은 것·배운 것

- migration을 빈 DB에서만 돌렸다면 "성공"이었을 것이다. 데이터를 옮기는 migration은 **옮길 데이터가 있는 DB**에서 시험해야 의미가 있다.
- `JSON_TABLE`은 MySQL 전용이다. 배포 때 PostgreSQL로 바꾸면(#12) migration 기록을 새로 만들어야 한다.
- `/mypage/bookmarks`는 북마크가 없으면 지금도 404를 돌려준다. 빈 목록으로 바꾸는 일은 프론트의 빈 상태 화면과 함께 처리한다(#17).
