폴더는 글 하나가 한 곳에만 들어간다. 'CSS'와 '리팩터링'에 모두 걸치는 글은 폴더로는 묶을 수 없다. macOS 메모는 이럴 때 태그를 쓴다. 본문 아무 데나 `#태그`를 쓰면 그것이 태그가 되고, 사이드바 아래에 태그 묶음이 생긴다. 같은 방식을 MacFolio 메모 앱에 넣었다([PR #67](https://github.com/hyeoniverse/MacFolio/pull/67)).

## 배경

블로그 글이 늘면서 폴더만으로는 글을 찾기 어려웠다. 예를 들어 CSS 층(`@layer`) 이야기는 '프론트엔드' 폴더에 있지만 '리팩터링' 글이기도 하다. 폴더를 더 잘게 나누면 한 글이 어디에 있어야 하는지 고민이 늘 뿐, 가로지르는 주제는 여전히 묶이지 않았다. 지금 이 블로그의 글 끝마다 `#MacFolio #리팩터링 #CSS` 같은 해시태그 줄을 두는 것도 이때부터다.

태그는 10월 1일 저녁에 최근 삭제된 항목·잠금과 함께 할 일로 올렸다. 처음 만든 화면을 열어 보니 예시 태그에 내 개인적인 내용이 들어가 있어 바로 개발 주제의 예시로 바꿨다. 다음 날에는 "선택된 태그를 모두 포함 / 일부 포함"을 고르는 칸 오른쪽의 화살표를 다른 메뉴처럼 chevron(⌄)으로 맞췄다.

어디에 태그를 둘지 세 가지를 놓고 봤다.

| 방법                           | 좋은 점                                 | 문제                                                                           |
| ------------------------------ | --------------------------------------- | ------------------------------------------------------------------------------ |
| Markdown 머리말에 `tags:` 칸   | 명시적이다                              | 머리말 형식·검사·API·DB 칸을 모두 늘려야 한다. 편집기에 따로 입력란이 필요하다 |
| DB에 태그 표와 글-태그 연결 표 | 질의가 빠르다                           | 저장소 Markdown 글은 DB에 없어서 두 곳을 맞춰야 한다                           |
| 본문의 `#태그`를 읽는다 (고름) | 저장 형식이 그대로다. macOS 메모와 같다 | 태그가 아닌 `#`을 거르는 규칙이 필요하다                                       |

이 블로그 글의 상당수는 저장소의 Markdown 파일이고, 나머지는 서버 DB에 있다. 두 출처를 같은 방식으로 다루려면 본문에서 읽는 쪽이 가장 단순했다. 대가는 거르기 규칙이다.

![태그로 보기](./images/memo-tags.jpg '사이드바 아래의 태그 묶음. 채운 칩은 포함, 테두리·취소선은 제외. 둘 이상 고르면 모두/일부 포함을 고른다')

## 저장하지 않는다

태그 칸을 따로 두지 않았다. 본문이 곧 태그의 출처다. 그래서 DB도, API도, 저장소의 Markdown 형식도 그대로다. 글을 고쳐서 `#태그`를 지우면 태그도 사라진다. 따로 맞춰 둘 것이 없다.

```ts
/** #태그: 줄 처음이나 공백·여는 괄호 뒤의 #, 바로 뒤에 이름 (# 뒤에 공백이 있으면 제목이다) */
export const TAG_PATTERN = /(^|[\s(（[])#([\p{L}\p{N}_-]+)/gu;
```

`\p{L}`(모든 글자)이라 한글 태그도 된다. `#` 바로 뒤에 공백이 있으면 Markdown 제목(`# 제목`)이므로 태그가 아니다.

## 태그가 아닌 `#`

규칙의 대부분은 "태그가 아닌 #"을 거르는 일이었다. 이 블로그에는 CSS 글이 많아서 `#edbb4d` 같은 색이 자주 나온다. 커밋 이야기에는 `#14` 같은 이슈 번호도 나온다.

| 쓴 것                                | 태그?  | 이유                                 |
| ------------------------------------ | ------ | ------------------------------------ |
| `#리팩터링`, `(#CSS)`                | 예     |                                      |
| `# 제목`                             | 아니오 | `#` 뒤에 공백 (제목)                 |
| 코드 블록·`인라인 코드` 안의 `#코드` | 아니오 | 코드                                 |
| `[글](#section)`, `https://a.b/#x`   | 아니오 | 링크 주소                            |
| `#14`                                | 아니오 | 숫자만 (이슈 번호)                   |
| `#115의`, `#96에서`, `#14로`         | 아니오 | 이슈 번호 + 조사                     |
| `#fff`, `#2b2100`, `#edbb4d`         | 아니오 | 색 (16진수 3·6·8자리)                |
| `C#언어`                             | 아니오 | 단어 가운데 (`#` 앞이 공백이 아니다) |

색을 거르는 규칙 때문에 `#cafe`나 `#face`처럼 16진수 글자로만 된 영어 태그는 쓸 수 없다. 블로그에 색이 나오는 일이 훨씬 많아서 그쪽을 골랐다.

이 규칙을 만든 뒤 지금까지 쓴 글 27편에 돌려 봤다. 태그로 읽힌 것은 하나도 없었다. 본문의 `#`은 모두 코드 블록 안의 색이었다.

### 이슈 번호에 붙은 조사

어느새 메모의 태그 목록에 `#115의`, `#116의`, `#96의`가 나타났다. "#115의 API 변경은…"처럼 이슈 번호 뒤에 조사를 바로 붙여 쓴 문장이었다. 숫자만인 이름은 거르지만, 한국어는 조사를 띄어 쓰지 않아서 `115의`가 이름 전체로 읽혔다.

숫자 뒤에 조사(의, 은, 는, 이, 가, 을, 를, 에, 에서, 으로, 로, 와, 과, 도, 만, 까지, 부터 …)만 붙은 이름도 거르게 했다. `#2026회고`처럼 숫자로 시작해도 뒤가 조사가 아니면 그대로 태그다. 시험에 `#115의 API, #96에서, #14로`를 더했고, 고치기 전 규칙으로 돌리면 세 개가 태그로 나오는 것을 확인했다.

거르는 일은 두 단계다. 먼저 본문에서 코드 블록, 인라인 코드, 링크 주소, HTML 태그를 공백으로 지운 뒤(`tagsOf`), 남은 글자에서 패턴으로 찾은 이름을 `isTagName`이 한 번 더 거른다.

```ts
const ISSUE_NUMBER = new RegExp(`^\\d+${PARTICLE}?$`);

export function isTagName(name: string): boolean {
	if (ISSUE_NUMBER.test(name)) return false;
	if (/^[0-9a-f]{3}([0-9a-f]{3})?([0-9a-f]{2})?$/i.test(name)) return false;
	return true;
}
```

## 세 곳에서 같은 규칙

![본문 → tagsInText → 세 화면](./images/memo-tags-pipeline.svg '색과 이슈 번호는 걸러지고, 남은 태그가 사이드바·읽기 화면·편집기에 같은 규칙으로 보인다')

태그는 세 곳에 보인다. 모두 같은 함수(`tagsInText`)로 찾는다. 이 함수와 거르기·정렬 함수는 처음에는 `apps/react`에 있었고, 지금은 React와 DOM에 의존하지 않는 순수 함수로 `packages/desktop-core/src/memo/tags.ts`에 옮겼다.

- **사이드바의 태그 묶음**: 모든 글의 본문에서 태그를 모아, 글이 많은 태그부터 늘어놓는다. 맨 앞의 '모든 태그'는 태그가 하나라도 있는 글이다
- **읽기 화면**: remark 플러그인이 Markdown 문법 나무의 글자 마디를 쪼개 `<span class="memo-tag">`로 감싼다. 코드·링크 마디는 들어가지 않는다. 누르면 그 태그의 글만 본다
- **편집기**: ProseMirror 꾸밈(decoration)으로 칠하기만 한다. 편집기에서 태그를 누르면 그 자리에 커서가 가야 하므로 다른 화면으로 넘어가지 않는다

## 포함, 제외, 미선택

처음에는 태그를 누르면 그 태그의 글만, 한 번 더 누르면 모든 글로 돌아갔다. macOS 메모는 태그를 누를 때마다 상태가 셋을 돈다.

| 누른 횟수 | 칩 모양               | 뜻                            |
| --------- | --------------------- | ----------------------------- |
| 0         | 회색                  | 고르지 않음                   |
| 1         | 강조 색으로 채움      | 이 태그가 있는 글 (포함)      |
| 2         | 강조 색 테두리·취소선 | 이 태그가 있는 글은 뺌 (제외) |
| 3         | 회색                  | 다시 고르지 않음              |

태그를 둘 이상 고르면 '태그' 옆에 "선택된 태그 중 모두 포함"이 생기고, 누르면 "일부 포함"으로 바꿀 수 있다. 오른쪽의 위아래 chevron 한 쌍은 macOS 팝업 버튼처럼 "누르면 고를 것이 펼쳐진다"는 표시다. 포함한 태그가 모두 있어야 하는지(그리고), 하나라도 있으면 되는지(또는)다. 제외한 태그는 어느 쪽이든 그 태그가 있는 글을 뺀다. 목록 위에는 무엇으로 걸렀는지 적는다.

- 하나만 포함: `선택된 태그(#디자인)와 일치하는 메모를 표시합니다.` 제목은 `#디자인`
- 여럿: `3개의 선택된 태그와 모두 일치하는 메모를 표시합니다.` 제목은 `3개의 태그`
- 제외만 있으면 안내 없이 제목만 `1개의 태그`

고른 상태는 `{ 태그: 'include' | 'exclude' }`와 모두/일부 하나로 둔다. 글이 맞는지 보는 함수는 이것뿐이다.

```ts
export function matchesTags(postTags: string[], selection: TagSelection): boolean {
	const has = (name: string) => postTags.some((tag) => sameTag(tag, name));
	if (selection.all) return postTags.length > 0;
	if (namesIn(selection, 'exclude').some(has)) return false;
	const included = namesIn(selection, 'include');
	if (included.length === 0) return true;
	return selection.match === 'all' ? included.every(has) : included.some(has);
}
```

태그로 보는 화면은 폴더로 보는 화면을 그대로 쓴다. 경로 자리에 `'\u0000tags'`를 넣고, 어떤 태그를 골랐는지는 따로 둔다. 폴더 이름에 쓸 수 없는 글자로 시작해서 사용자가 만든 폴더와 겹치지 않는다. 폴더를 고르면 태그 고르기는 풀린다.

본문의 `#디자인`처럼 줄 처음에 쓴 태그는 목록의 미리보기에서 `#`이 지워져 "디자인"으로 보였다. 미리보기를 만들 때 Markdown 제목 표시(`# `)를 걷어 내는 규칙이 `#` 뒤 공백 없이도 걸렸기 때문이다. `#` 뒤에 공백이 있을 때만 걷게 고쳤다.

## 확인

- `packages/desktop-core/src/memo/tags.test.ts`: "본문의 #태그를 처음 나온 순서로, 대소문자가 달라도 하나로", "제목, 코드, 링크 주소, 이슈 번호, 색, 단어 가운데의 #은 태그가 아니다", "#부터 이름 끝까지의 자리", "글이 많은 태그가 앞, 같으면 이름 순".
- `tagFilter.test.ts`: "누를 때마다 미선택 → 포함 → 제외 → 미선택", "모든 태그는 다른 태그를 풀고, 태그를 누르면 모든 태그가 풀린다", "포함은 모두/일부, 제외는 그 태그가 있으면 뺀다 (대소문자 무시)", "제목과 안내 문구".
- 태그 순서를 보는 시험이 처음에는 블로그 글의 태그를 썼다. 글을 쓸 때마다 태그 수가 바뀌어 시험이 흔들려서, 블로그 글에 없는 태그로 바꿨다(`8478ede2a`, `463b3edd6`). 칩을 찾을 때도 `#다`가 `#다크모드`와 겹쳐 이름이 정확히 같은 것으로 찾게 했다(`ddbce46cb`).
- 이 글을 고치는 지금, 블로그 글 201편의 끝줄 해시태그는 서로 다른 것이 138개다. 가장 많은 것은 `#MacFolio`(195편), `#리팩터링`(53편), `#회고`(33편), `#CSS`(28편)다.

## 남은 것·배운 것

- 태그는 매번 모든 글의 본문을 훑어 모은다. 글 200편 정도에서는 문제없지만, 글이 훨씬 많아지면 목록을 읽을 때 한 번 모아 두는 것을 생각해야 한다.
- `#cafe`처럼 16진수 글자로만 된 영어 태그는 쓸 수 없다. 이 블로그에서는 색이 훨씬 자주 나와서 받아들였다.
- 저장하지 않는 설계 덕분에 API·DB·저장소 형식을 하나도 바꾸지 않았다. 대신 "무엇이 태그가 아닌가"를 시험 표로 계속 늘려야 했다. 조사가 붙은 이슈 번호처럼 한국어 글에서만 생기는 경우가 그 예다.
- 휴대폰 메모의 태그 화면은 뒤에 iOS 메모처럼 바꿨다(`9d712f5bf`). 제목이 태그가 되고, 위에 옆으로 넘기는 칩 줄이 생겼다.
