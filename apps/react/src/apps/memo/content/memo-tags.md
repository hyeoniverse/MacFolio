## 배경: 폴더로 묶을 수 없는 주제

폴더는 글 하나가 한 곳에만 속하는 분류다. 'CSS'와 '리팩터링'에 모두 해당하는 글은 두 폴더에 동시에 넣을 수 없다. **태그**는 글 하나에 이름표를 여러 개 붙이는 분류 방식이다. 같은 글에 `#CSS`와 `#리팩터링`을 함께 붙이면, 어느 태그로 찾아도 그 글이 나온다.

macOS 메모는 본문의 어느 위치에든 `#태그`를 입력하면 그 단어를 태그로 인식하고, 사이드바 아래에 태그 목록을 표시한다. SNS의 해시태그와 같은 입력 방식이다. 같은 방식을 MacFolio 메모 앱에 구현했다([#67](https://github.com/hyeoniverse/MacFolio/pull/67)).

블로그 글이 늘면서 폴더만으로는 글을 찾기 어려웠다. 예를 들어 [캐스케이드 레이어(`@layer`) 글](/memo/css-layer-reset)은 '프론트엔드' 폴더에 있지만 '리팩터링' 주제이기도 하다. 폴더를 더 세분하면 글을 어느 폴더에 넣을지 판단할 일만 늘고, 여러 폴더에 걸친 주제는 여전히 한곳에 모이지 않았다. 이 블로그의 글 끝마다 `#MacFolio #리팩터링 #CSS` 같은 해시태그 줄을 넣는 규칙도 이 시점부터다.

![태그로 보기](./images/memo-tags.jpg '사이드바 아래의 태그 그룹. 채운 칩은 포함, 테두리·취소선은 제외. 둘 이상 선택하면 모두/일부 포함을 선택한다')

## 태그 저장 위치

태그를 어디에 저장할지 세 가지 방법을 비교했다.

| 방법                                   | 장점                                    | 단점                                                                             |
| -------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| Markdown 머리말에 `tags:` 필드         | 명시적이다                              | 머리말 형식·검증·API·DB 열을 모두 추가해야 한다. 편집기에 별도 입력란이 필요하다 |
| DB에 태그 테이블과 글-태그 연결 테이블 | 쿼리가 빠르다                           | 저장소 Markdown 글은 DB에 없어서 두 출처를 동기화해야 한다                       |
| **본문의 `#태그`를 추출 (선택)**       | 저장 형식이 그대로다. macOS 메모와 같다 | 태그가 아닌 `#`을 제외하는 규칙이 필요하다                                       |

이 블로그 글의 상당수는 저장소의 Markdown 파일이고, 나머지는 관리자가 사이트에서 쓴 서버 DB의 글이다. 두 출처를 같은 방식으로 처리하려면 본문에서 추출하는 방법이 가장 단순했다. 그 대가는 제외 규칙이다.

## 별도로 저장하지 않는다

태그 필드를 따로 만들지 않았다. ==본문이 태그의 유일한 출처다==. 그래서 DB, API, 저장소의 Markdown 형식이 모두 그대로다. 글을 수정해 `#태그`를 삭제하면 태그도 사라진다. 동기화할 데이터가 따로 없다.

본문에서 태그를 찾는 데는 **정규식(regular expression)**을 쓴다. 정규식은 "줄 처음이나 공백 뒤의 `#`, 그 뒤에 이어지는 글자들"처럼 문자열의 형태를 기호로 적은 검색 패턴이다.

```ts
/** #태그: 줄 처음이나 공백·여는 괄호 뒤의 #, 바로 뒤에 이름 (# 뒤에 공백이 있으면 제목이다) */
export const TAG_PATTERN = /(^|[\s(（[])#([\p{L}\p{N}_-]+)/gu;
```

| 패턴 조각         | 뜻                                                          | 예                      |
| ----------------- | ----------------------------------------------------------- | ----------------------- |
| `(^\|[\s(（[])`   | 줄 처음, 또는 공백·여는 괄호(반각·전각)·여는 대괄호 바로 뒤 | `(#CSS)`의 `(`          |
| `#`               | 태그 기호                                                   |                         |
| `[\p{L}\p{N}_-]+` | 글자·숫자·밑줄·하이픈이 하나 이상                           | `리팩터링`, `dark-mode` |
| `u` 플래그        | 유니코드 모드. `\p{…}`를 쓰려면 필요하다                    |                         |

`\p{L}`은 모든 언어의 문자(Letter)를, `\p{N}`은 숫자(Number)를 뜻하는 [유니코드 속성 이스케이프](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Regular_expressions/Unicode_character_class_escape)다. 영문 `[a-zA-Z]`만 쓰면 `#리팩터링`을 인식하지 못하므로 이 표기를 썼다. `#` 바로 뒤에 공백이 있으면 이름 부분이 비어 일치하지 않으므로, Markdown 제목(`# 제목`)은 태그가 아니다.

## 태그가 아닌 `#`

규칙의 대부분은 "태그가 아닌 #"을 제외하는 조건이었다. 이 블로그에는 CSS 글이 많아서 `#edbb4d` 같은 색 값이 자주 나온다. CSS의 [16진수 색 표기](https://developer.mozilla.org/en-US/docs/Web/CSS/hex-color)는 `#` 뒤에 0~9와 a~f로 된 3·4·6·8자리를 쓴다(`#fff`는 흰색, `#edbb4d`는 노란색). 커밋 기록에는 `#14` 같은 GitHub 이슈 번호도 나온다.

| 입력                                 | 태그?  | 이유                                 |
| ------------------------------------ | ------ | ------------------------------------ |
| `#리팩터링`, `(#CSS)`                | 예     |                                      |
| `# 제목`                             | 아니오 | `#` 뒤에 공백 (제목)                 |
| 코드 블록·`인라인 코드` 안의 `#코드` | 아니오 | 코드                                 |
| `[글](#section)`, `https://a.b/#x`   | 아니오 | 링크 주소                            |
| `#14`                                | 아니오 | 숫자만 (이슈 번호)                   |
| `#115의`, `#96에서`, `#14로`         | 아니오 | 이슈 번호 + 조사                     |
| `#fff`, `#2b2100`, `#edbb4d`         | 아니오 | 색 (16진수 3·6·8자리)                |
| `C#언어`                             | 아니오 | 단어 가운데 (`#` 앞이 공백이 아니다) |

> [!WARNING] 16진수 문자로만 된 태그
> 색을 제외하는 규칙 때문에 `#dad`(3글자), `#added`(5글자), `#decade`(6글자)처럼 a~f와 숫자로만 된 3·5·6·8글자 영어 태그는 사용할 수 없다. 블로그에 색 값이 나오는 빈도가 훨씬 높아서 색 제외를 우선했다. 반대로 4글자인 `#cafe`·`#face`는 규칙에 일치하지 않아 태그로 인식되고, 같은 이유로 투명도를 포함한 4자리 색(`#fffa`)도 태그가 된다.

이 규칙을 만든 뒤 당시까지 작성한 글 27편에 실행했다. 태그로 인식된 항목은 하나도 없었다. 본문의 `#`은 모두 코드 블록 안의 색 값이었다.

### 두 단계 필터링

필터링은 두 단계다.

1. `tagsOf`: 본문에서 코드 블록, 인라인 코드, 링크 주소, HTML 태그를 공백으로 치환한다.
2. `isTagName`: 남은 텍스트에서 패턴으로 찾은 이름을 한 번 더 검사해 이슈 번호와 색 값을 제외한다.

아래 그림은 네 줄짜리 본문이 두 단계를 거쳐 태그 두 개만 남는 과정이다.

![본문 네 줄에서 태그가 추출되는 과정](./images/memo-tags-filter-steps.svg '① 인라인 코드의 #fff와 링크 주소의 #배경은 공백으로 치환되어 검색 대상에서 빠진다. ② 패턴이 찾은 후보 네 개 중 색 값 edbb4d와 이슈 번호 115의는 isTagName이 제외하고 CSS와 리팩터링만 남는다')

```ts
const ISSUE_NUMBER = new RegExp(`^\\d+${PARTICLE}?$`);

export function isTagName(name: string): boolean {
	if (ISSUE_NUMBER.test(name)) return false;
	if (/^[0-9a-f]{3}([0-9a-f]{3})?([0-9a-f]{2})?$/i.test(name)) return false;
	return true;
}
```

색 검사 정규식 `^[0-9a-f]{3}([0-9a-f]{3})?([0-9a-f]{2})?$`는 16진수 3자리 뒤에 3자리와 2자리가 각각 선택적으로 붙은 형태와 일치한다(`i` 플래그로 대소문자 무시). 가능한 길이는 3, 3+2=5, 3+3=6, 3+3+2=8자리다. CSS 색에 없는 5자리도 일치하고, CSS 색인 4자리는 일치하지 않는다.

### 이슈 번호에 붙은 조사

이후 메모의 태그 목록에 `#115의`, `#116의`, `#96의`가 표시됐다. "#115의 API 변경은…"처럼 이슈 번호 뒤에 조사를 붙여 쓴 문장이었다. 숫자로만 된 이름은 제외하지만, ==한국어는 조사를 띄어 쓰지 않아서== `115의` 전체가 태그 이름으로 인식됐다. `\p{L}`이 한글 '의'를 문자로 인식하기 때문이다.

숫자 뒤에 조사(의, 은, 는, 이, 가, 을, 를, 에, 에서, 으로, 로, 와, 과, 도, 만, 까지, 부터 …)만 붙은 이름도 제외하게 했다(`PARTICLE`). `#2026회고`처럼 숫자로 시작해도 뒤가 조사가 아니면 태그로 인식한다.

| 입력        | 숫자 뒤   | 결과 |
| ----------- | --------- | ---- |
| `#115`      | 없음      | 제외 |
| `#115의`    | 조사      | 제외 |
| `#96에서`   | 조사      | 제외 |
| `#2026회고` | 일반 단어 | 태그 |

시험에 `#115의 API, #96에서, #14로`를 추가했고, 수정 전 규칙으로 실행하면 세 개가 태그로 인식되는 것을 확인했다.

## 세 화면에서 같은 규칙

![본문 → tagsInText → 세 화면](./images/memo-tags-pipeline.svg '색과 이슈 번호는 제외되고, 남은 태그가 사이드바·읽기 화면·편집기에 같은 규칙으로 표시된다')

태그는 세 곳에 표시된다. 모두 같은 함수(`tagsInText`)로 추출한다. 이 함수와 필터·정렬 함수는 처음에는 `apps/react`에 있었고, 현재는 React와 DOM에 의존하지 않는 순수 함수로 `packages/desktop-core/src/memo/tags.ts`로 옮겼다.

| 위치               | 구현                                                                                                                                                                          | 누르면                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 사이드바 태그 그룹 | 모든 글의 본문에서 태그를 수집해 글 수가 많은 순으로 나열. 맨 앞의 '모든 태그'는 태그가 하나라도 있는 글                                                                      | 태그 필터 적용                      |
| 읽기 화면          | [remark](https://github.com/remarkjs/remark) 플러그인이 Markdown 구문 트리(mdast)의 텍스트 노드를 분할해 `<span class="memo-tag">`로 감싼다. 코드·링크 노드는 탐색하지 않는다 | 그 태그의 글만 표시                 |
| 편집기             | ProseMirror [데코레이션](https://prosemirror.net/docs/ref/#view.Decorations)으로 스타일만 적용                                                                                | 그 위치에 커서 이동(화면 전환 없음) |

읽기 화면과 편집기의 구현 방식이 다른 이유는 두 화면이 문서를 다루는 방식이 다르기 때문이다.

- **mdast**는 Markdown을 제목·문단·텍스트·코드 같은 노드의 트리로 표현한 구조다([syntax-tree/mdast](https://github.com/syntax-tree/mdast)). 읽기 화면은 이 트리를 HTML로 바꾸기 전에, 텍스트 노드 `"…은 #리팩터링 대상"`을 `"…은 "`, 태그 노드 `#리팩터링`, `" 대상"` 세 개로 분할한다. 코드 노드와 링크 노드는 처음부터 탐색하지 않으므로 앞의 '코드·링크 주소 치환'과 같은 효과가 난다.
- **데코레이션**은 ProseMirror 편집기에서 문서 내용을 바꾸지 않고 특정 범위에 CSS 클래스만 덧입히는 기능이다. 편집기에서 태그를 노드로 분할하면 저장되는 Markdown이 바뀔 수 있으므로, 화면 표시만 바꾸는 데코레이션을 썼다. `tagsInText`가 반환하는 `start`·`end`(`#`부터 이름 끝까지의 위치)가 데코레이션의 범위가 된다.

## 포함, 제외, 미선택

처음 구현에서는 태그를 누르면 그 태그의 글만, 한 번 더 누르면 모든 글로 돌아갔다. macOS 메모는 태그를 누를 때마다 세 상태를 순환한다.

| 누른 횟수 | 칩 스타일             | 의미                            |
| --------- | --------------------- | ------------------------------- |
| 0         | 회색                  | 미선택                          |
| 1         | 강조 색으로 채움      | 이 태그가 있는 글 (포함)        |
| 2         | 강조 색 테두리·취소선 | 이 태그가 있는 글은 제외 (제외) |
| 3         | 회색                  | 다시 미선택                     |

태그를 둘 이상 선택하면 '태그' 옆에 "선택된 태그 중 모두 포함"이 표시되고, 누르면 "일부 포함"으로 바꿀 수 있다. 오른쪽의 위아래 chevron(⌄) 한 쌍은 macOS 팝업 버튼처럼 "누르면 선택지가 펼쳐진다"는 표시다. 처음에는 다른 모양의 화살표였고, 다음 날 다른 메뉴와 같은 chevron으로 통일했다.

모두 포함은 AND(포함한 태그가 모두 있어야 함), 일부 포함은 OR(하나라도 있으면 됨)이다. 제외한 태그는 두 경우 모두 그 태그가 있는 글을 숨긴다.

![세 상태 순환과 모두·일부 포함의 결과](./images/memo-tags-match.svg '위는 칩을 누를 때마다 미선택 → 포함 → 제외 → 미선택으로 바뀌는 순서. 아래는 #CSS·#리팩터링 포함, #회고 제외로 선택했을 때 글 네 편이 표시되는지 여부다')

목록 상단에는 적용한 필터를 안내한다.

| 선택                    | 안내 문구                                              | 목록 제목    |
| ----------------------- | ------------------------------------------------------ | ------------ |
| 하나만 포함 (`#디자인`) | `선택된 태그(#디자인)와 일치하는 메모를 표시합니다.`   | `#디자인`    |
| 셋 선택, 모두 포함      | `3개의 선택된 태그와 모두 일치하는 메모를 표시합니다.` | `3개의 태그` |
| 제외만 하나             | (없음)                                                 | `1개의 태그` |

선택 상태는 `{ 태그: 'include' | 'exclude' }` 객체와 모두/일부 값 하나로 저장한다. 위 그림의 선택이라면 `{ tags: { CSS: 'include', 리팩터링: 'include', 회고: 'exclude' }, match: 'all' }`이다. 글의 일치 여부를 판단하는 함수는 다음 하나뿐이다.

```ts
export function matchesTags(postTags: string[], selection: TagSelection): boolean {
	const has = (name: string) => postTags.some((tag) => sameTag(tag, name));
	if (selection.all) return postTags.length > 0;
	if (namesIn(selection, 'exclude').some(has)) return false;
	const included = namesIn(selection, 'include');
	if (included.length === 0) return true;
	return selection.match === 'all' ? included.every(has) : included.some(has);
}
```

`every`는 배열의 모든 항목이 조건을 만족하면 `true`(AND), `some`은 하나라도 만족하면 `true`(OR)를 반환한다. 제외 검사가 포함 검사보다 먼저 있으므로 제외한 태그가 있는 글은 포함 조건과 관계없이 숨겨진다.

태그 보기 화면은 폴더 보기 화면을 그대로 재사용한다. 경로 값으로 `'\u0000tags'`를 사용하고, 선택한 태그는 별도 상태로 저장한다. `\u0000`(NUL 문자)은 폴더 이름에 쓸 수 없는 문자이므로 사용자가 만든 폴더와 충돌하지 않는다. 폴더를 선택하면 태그 선택은 해제된다.

### 목록 미리보기의 `#` 누락

본문의 `#디자인`처럼 줄 처음에 쓴 태그가 목록 미리보기에서 `#`이 삭제된 "디자인"으로 표시됐다. 미리보기를 만들 때 Markdown 제목 기호(`# `)를 제거하는 정규식이 `#` 뒤에 공백이 없어도 일치했기 때문이다. `#` 뒤에 공백이 있을 때만 제거하도록 수정했다.
