빌드 구조를 정리하고, 테스트와 CI를 도입한 뒤, 그 테스트를 안전장치로 삼아 앱을 다시 만들었다. 진행 순서는 다음과 같다.

1. 빌드·배포 정리: 앱 단위 폴더, Firebase 제거, Cloudflare Workers 배포, 모노레포
2. 테스트와 CI: ESLint·Prettier, Playwright E2E, GitHub Actions
3. 앱 개편: 메모, 메시지, 터미널, 메일
4. 휴대폰 화면: 좁은 화면에서 iOS 홈 화면

==테스트를 앱 개편보다 먼저 도입해서, 앱 코드를 크게 바꿀 때마다 실패한 기능을 시험 결과로 즉시 확인했다.==

![9월 28일 작업 흐름](./images/day-0928-timeline.svg '새벽에는 빌드·배포 정리, 오전에는 테스트, 오후부터는 앱과 휴대폰')

## 앱 단위 폴더와 Firebase 제거

CRA에서 Vite로 이전한 뒤 남은 정리부터 진행했다([CRA에서 Vite로 옮기기](/memo/cra-to-vite)). 빌드 결과물과 `node_modules`를 git 추적에서 제외했다. 빌드 결과물은 소스에서 언제든 다시 만들 수 있으므로, 저장소에 포함하면 소스를 바꿀 때마다 압축된 결과 파일의 변경이 함께 기록되어 실제 코드 변경을 확인하기 어려워진다.

이어서 파일 종류별(`components/`, `styles/`)로 나뉘어 있던 폴더를 앱 단위(`apps/<앱>/`)로 재구성했다. 예를 들어 메일 앱은 `components/apps/Mail.tsx`와 `styles/Mail.css`로 두 폴더에 나뉘어 있었는데, 재구성 후에는 `apps/mail/` 한 폴더에 모였다. 앱 이름·아이콘·창 크기는 manifest, 앱 이름과 컴포넌트의 연결은 registry 한 곳에서 관리하게 했다.

![파일 종류별 폴더 구성과 앱 단위 폴더 구성 비교](./images/day-0928-folders.svg '메일 앱의 파일이 두 폴더에서 apps/mail 한 폴더로 모였다')

다음으로 Firebase를 제거했다. Firebase는 Google의 백엔드 서비스 모음으로, 이 사이트는 정적 파일 배포(Firebase Hosting)에 사용했고 메모 저장용 Realtime Database 코드도 있었다. 확인해 보니 배포된 사이트는 Realtime Database를 호출하지 않았고 데이터베이스 인스턴스도 없어서, 옮길 데이터가 없었다. 먼저 메모 저장 기능이 Firebase 설정 없이도 동작하도록 저장소 코드를 분리하고(API 서버가 생기기 전까지는 브라우저의 localStorage에 저장), 사이트 배포를 [Cloudflare Workers의 정적 자산 배포](https://developers.cloudflare.com/workers/static-assets/)로 이전한 뒤 `firebase` 패키지와 `firebase.json`·`.firebaserc`·`database.rules.json`을 삭제했다. 순서를 이렇게 정해, 어느 단계에서도 사이트가 동작하지 않는 상태가 없게 했다.

## pnpm workspaces와 Turborepo로 구성한 모노레포

모노레포(monorepo)는 여러 패키지(프론트엔드 앱, API 서버, 공용 라이브러리 등)를 저장소 하나에서 관리하는 구성이다. 패키지마다 저장소를 따로 만들면 공용 코드를 바꿀 때 저장소 여러 개에 각각 반영해야 하지만, 모노레포에서는 커밋 하나로 함께 바꾸고 함께 시험한다.

두 도구로 구성했다.

| 도구                                          | 역할                                                                     | 이 저장소의 설정                               |
| --------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------- |
| [pnpm workspaces](https://pnpm.io/workspaces) | 저장소 안의 여러 폴더를 각각의 패키지로 인식하고, 의존성을 한 번에 설치  | `pnpm-workspace.yaml`에 `apps/*`, `packages/*` |
| [Turborepo](https://turborepo.com/docs)       | 패키지마다 `build`·`test` 같은 작업을 의존 순서대로 실행하고 결과를 캐시 | `turbo.json`                                   |

기존 앱은 `apps/react`(`@macfolio/react`)로 옮기고, npm을 pnpm 10으로 바꾸고, 사용하지 않던 `axios`와 `react-router-dom`을 삭제했다. 설치 버전은 기존 `package-lock.json`과 같게 고정해, 빌드 결과가 기존 배포본과 같은지 비교했다. 차이는 압축기가 출력한 괄호 표기 한 곳뿐이었다.

![저장소 루트의 설정 파일 세 개와 apps/react, 다음 날 추가한 apps/api](./images/day-0928-monorepo.svg '같은 저장소에 프론트엔드와 API를 두는 구성')

이 구성 덕분에 다음 날 API 서버를 `apps/api`로 같은 저장소에 바로 추가했다.

## 테스트와 CI 도입, 그리고 발견한 버그

세 종류의 검사를 함께 도입했다.

| 도구                                                           | 검사하는 것                                         | 예시                                                                  |
| -------------------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------- |
| [ESLint](https://eslint.org/)·[Prettier](https://prettier.io/) | 코드 규칙 위반과 서식                               | `eslint-plugin-react-hooks`가 조건문 안의 hook 호출을 오류로 표시한다 |
| [Playwright](https://playwright.dev/) E2E                      | 실제 브라우저에서 사용자 조작부터 화면 결과까지     | Dock의 음악 아이콘을 눌러 창을 열고 닫은 뒤 Dock이 남아 있는지        |
| [GitHub Actions](https://docs.github.com/en/actions) CI        | 저장소에 코드를 올릴 때마다 위 검사를 자동으로 실행 | PR에 실패한 검사가 있으면 표시                                        |

E2E(End-to-End) 시험은 실제 브라우저를 열어 사용자가 하는 조작을 그대로 실행하고 결과 화면을 확인한다. CI(지속적 통합)는 코드를 올릴 때마다 정해진 검사를 서버에서 자동으로 실행하는 방식이다.

테스트를 처음 실행하자마자 버그를 찾았다. ==음악 창을 닫으면 그 창뿐 아니라 Dock까지 화면 전체가 사라졌다.== 음악 컴포넌트가 창이 닫힌 경우 중간에 `return null`로 빠져나가면서, 그 뒤의 `useEffect`가 호출되지 않았다. React는 hook의 상태를 호출 순서로 구분하므로 렌더링마다 hook 개수가 달라지면 오류를 발생시키고, 오류를 받아 줄 에러 경계가 없어서 화면 전체가 언마운트됐다. 처음부터 동작하지 않던 기능 몇 개도 이때 발견했다([리팩터링 전 E2E 시험 10개로 찾은 hook 순서·클로저·ICU 버그](/memo/bugs-found-by-tests)).

이어서 창 관련 코드를 리팩터링했다.

- 창 위치·크기와 쌓임 순서를 계산하는 부분을 순수 함수(같은 입력에 항상 같은 결과를 반환하고 외부 상태를 바꾸지 않는 함수)로 분리해 [Vitest](https://vitest.dev/)로 검증했다. 예를 들어 "창 세 개 중 두 번째를 누르면 그 창의 순서가 가장 앞이 된다"를 화면 없이 시험한다.
- 창을 상태 기반으로 재작성했다.
- 앱 하나에서 오류가 발생해도 화면 전체가 멈추지 않게 [에러 경계(Error Boundary)](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)를 추가했다. 에러 경계는 하위 컴포넌트의 렌더링 오류를 받아 대체 화면을 표시하는 컴포넌트로, 음악 창에서 오류가 나도 Dock과 다른 창은 그대로 남는다.

설정 앱과 다크 모드도 이때 만들었다. 하루를 마칠 시점에 E2E 시험은 0개에서 78개로, 단위 시험은 142개로 늘었다.

## 다섯 번 바뀐 메시지 앱

앱을 하나씩 다시 만들었다. 메모 앱은 블로그가 되었고, 별도로 있던 Blog 앱은 삭제했다. 터미널 앱은 명령어로 자기소개를 출력하고, 메일 앱은 방문자가 연락 메일을 작성하는 앱이 되었다.

메시지 앱만은 방향을 다섯 번 바꿨다.

| 차례 | 메시지 앱의 방향                          |
| ---- | ----------------------------------------- |
| 1    | 방명록으로 추가                           |
| 2    | 방문자별 공개 대화로 개편                 |
| 3    | 사람별 공개 방명록, macOS 26 디자인       |
| 4    | 방은 쓰기 버튼으로만 만든다               |
| 5    | 감상·의견·피드백 공간으로, 예전 목록 정리 |

최종 형태는 이슈 [#23](https://github.com/hyeoniverse/MacFolio/issues/23)에 처음 적은 내용과 거의 같았다. ==작업 전에 이슈를 다시 확인했다면 중간의 네 번은 필요하지 않았다.==

## 휴대폰 화면

화면이 좁으면 macOS 데스크톱 대신 iOS 홈 화면을 표시하도록 만들고, 상태 표시줄·제어 센터·음악 위젯·앱 전환기를 차례로 추가했다. 데스크톱과 휴대폰은 같은 앱 컴포넌트를 공유하고, 바깥 셸(창과 Dock, 또는 홈 화면과 상태 표시줄)만 화면 폭에 따라 바뀐다.

![지금의 휴대폰 홈 화면](./images/day-0928-mobile-home.jpg '이날 만든 휴대폰 홈 화면의 지금 모습. 위젯과 아이콘은 그 뒤에 더 바뀌었다')

메모 앱은 macOS 메모와 같은 구성으로 개선했다. 목록·갤러리 보기, 폴더 트리, 끌어서 옮기기, 고정, 코드 문법 강조를 넣고, 메모 편집은 관리자만 할 수 있게 바꿨다([정적 사이트의 편집 권한을 useCanEditMemo 하나로 관리자에게만 열기](/memo/read-only-memo)).

![지금의 데스크톱과 메모 앱](./images/day-0928-desktop.jpg '이날 다듬은 메모 앱의 지금 모습. 글 목록은 그 뒤에 쓴 글들이다')

## 돌아보며

1. 메시지 앱은 무엇을 위한 공간인지 정하기 전에 화면부터 만들어 다섯 번 바꿨다. 앱을 수정하기 전에 해당 앱의 이슈부터 다시 확인하기로 했다.
2. 휴대폰의 뒤로 가기는 공통 규칙 없이 앱마다 고치다가 같은 날 세 번 고쳤다. 나중에 내용 위에 표시하는 공통 버튼 하나로 통일했다.
3. E2E를 앱 개편보다 먼저 붙였다. 앱을 여러 번 다시 작성하는 동안 회귀(이전에 동작하던 기능이 다시 고장 나는 것)를 시험이 잡았다.
