블로그 글에는 조회수와 댓글이 있었지만, 읽은 사람이 가볍게 반응할 방법은 없었다. 그래서 글과 댓글에 좋아요를 달고, 반응이 많은 글을 모아 보는 '인기글' 폴더를 만들었다. 커밋 하나(`2bdb8d6da`)로 서버·화면·시험을 함께 넣었고, 38개 파일, 1,400줄 더하기, 47줄 지우기다.

## 좋아요는 누가, 몇 번

댓글처럼 **로그인 없이** 누른다. 같은 사람이 여러 번 누르지 못하게 하는 기준은 댓글을 "내 댓글"로 알아보는 데 쓰던 방문자 쿠키(`macfolio_visitor`)다. 서버는 쿠키 값을 그대로 두지 않고 비밀 키로 HMAC한 값만 저장한다.

```prisma
model PostLike {
  postSlug    String
  visitorHash String
  @@id([postSlug, visitorHash])
}

model CommentLike {
  commentId   String
  comment     PostComment @relation(fields: [commentId], references: [id], onDelete: Cascade)
  visitorHash String
  @@id([commentId, visitorHash])
}
```

- 기본 키가 (글, 방문자)라서 같은 브라우저가 두 번 눌러도 한 줄이다. 누르기는 `createMany({ skipDuplicates: true })`, 취소는 `deleteMany`라서, 두 번 눌러도 오류 없이 그대로다.
- 글은 저장소의 Markdown 파일일 수도 있어서 `Post` 표와 잇지 않고 주소(slug)로만 둔다. 댓글 수를 셀 때와 같은 방식이다.
- 댓글 좋아요는 댓글을 지우면 함께 지워진다(`onDelete: Cascade`).
- 쿠키를 지우거나 다른 브라우저로 오면 다시 누를 수 있다. 로그인 없이 누르는 좋아요의 한계이고, 개인 블로그에서는 이 정도면 충분하다고 봤다.

| 요청                            | 하는 일                           |
| ------------------------------- | --------------------------------- |
| `GET /posts/:slug/likes`        | `{ count, liked }`                |
| `PUT /posts/:slug/like`         | 누르기 (이미 눌렀으면 그대로)     |
| `DELETE /posts/:slug/like`      | 취소                              |
| `PUT·DELETE /comments/:id/like` | 댓글에 누르기·취소                |
| `GET /posts/stats`              | 글마다 댓글 수·좋아요 수 (인기글) |

댓글 목록에는 댓글마다 `likes`(수)와 `liked`(이 브라우저가 눌렀는지)가 붙는다. 누가 눌렀는지(방문자 해시)는 응답에 담지 않는다. 기존 API 시험이 댓글 응답의 키 목록을 정확히 확인하고 있어서, 새 키가 생긴 것을 그 시험에도 적었다.

## 요청 제한

댓글 쓰기는 IP마다 1분에 5번으로 막아 두었는데, 좋아요는 눌렀다 취소했다를 반복할 수 있어서 이 제한은 너무 빡빡하다. 그래서 `like`라는 제한을 따로 두었다(`LIKE_RATE_LIMIT`, 기본 30).

NestJS의 요청 제한은 **경로마다** 센다. 처음에는 "누르기와 취소를 합쳐 30번"이라고 적고 시험도 그렇게 썼는데 통과하지 않았다. 누르기 경로와 취소 경로를 따로 센다는 것을 확인하고, 설명과 시험을 "경로마다"로 고쳤다.

제한을 하나 더 만들면, `ThrottlerGuard`를 쓰는 다른 경로(로그인, 댓글, 메시지)도 새 제한을 건너뛰도록 `@SkipThrottle({ ..., like: true })`를 붙여야 한다. 붙이지 않으면 댓글 쓰기가 좋아요 제한에도 걸린다.

## 화면

- 글 아래, 이전·다음 글 위에 가운데 정렬한 캡슐 버튼 `♡ 4`. Apple 앱처럼 테두리 없이 옅은 회색 바탕(iOS의 tertiarySystemFill)에 하트와 수만 둔다. 누르면 하트와 바탕이 systemPink(`#ff2d55`, 다크 모드 `#ff375f`)로 바뀌고, 누르는 동안 살짝 작아졌다가 하트가 스프링처럼 튄다.
- 댓글마다 본문 아래에 작은 하트. 수가 0이면 숫자는 숨기고, 올려 두면 같은 옅은 회색 바탕이 생긴다.
- 누르는 즉시 화면을 바꾸고, 서버의 답으로 맞춘다. 실패하면 누르기 전으로 되돌린다.
- 서버가 없으면(로컬에서 API 없이) 좋아요 버튼도 인기글 폴더도 보이지 않는다.

## 인기글: 순위는 화면에서

순위를 어디서 매길지 셋을 놓고 골랐다.

| 방법                         | 좋은 점                                             | 걸리는 점                                                                    |
| ---------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------- |
| 서버가 순위까지              | 화면이 가볍다                                       | 서버는 저장소의 Markdown 글 목록을 모른다. 글 목록을 서버에 따로 올려야 한다 |
| 빌드할 때 계산               | 요청이 없다                                         | 좋아요가 실시간으로 반영되지 않는다                                          |
| **서버는 수만, 화면이 순위** | 저장소 글과 서버 글을 같이 다룬다, 누르면 바로 반영 | 글이 많아지면 수를 모두 받아야 한다                                          |

서버는 저장소의 Markdown 글을 모른다. 서버가 아는 글은 관리자가 쓰거나 고친 글뿐이다. 그래서 서버가 "인기글 10개"를 바로 돌려줄 수는 없다. 대신 서버는 **글마다 수**만 주고, 순위는 화면에서 매긴다.

- 조회수: 원래 있던 `GET /analytics/views?app=memo`
- 댓글 수·좋아요 수: 새 `GET /posts/stats`

점수는 이렇게 매긴다.

```
점수 = 조회 × 1 + 좋아요 × 3 + 댓글 × 5
```

![인기글 순위를 매기는 흐름](./images/memo-likes-popular-ranking.svg '서버는 글마다 수만 주고, 점수와 순위는 화면이 계산한다')

![점수 예](./images/memo-likes-popular-score.svg '조회가 많아도 반응이 있는 글이 가까이 따라온다')

조회가 가장 흔하므로 가장 가볍게 두었다. 좋아요는 누르기만 하면 되지만, 댓글은 글을 써야 하므로 가장 무겁게 두었다. 점수가 같으면 좋아요, 댓글, 조회가 많은 순서이고, 그래도 같으면 최근 글이 먼저다. 반응이 하나도 없는 글은 넣지 않는다.

이 계산은 프레임워크와 상관없는 `desktop-core`의 `popularPosts()`에 두고, 단위 시험으로 순서와 10개 제한을 확인했다.

```ts
export function popularPosts(posts: Post[], stats: Record<string, Partial<PostStats>>, limit = POPULAR_LIMIT): Post[] {
	return posts
		.map((post) => ({ post, stats: statsOf(stats, post.slug) }))
		.map((entry) => ({ ...entry, score: popularityScore(entry.stats) }))
		.filter((entry) => entry.score > 0)
		.sort(
			(a, b) =>
				b.score - a.score ||
				b.stats.likes - a.stats.likes ||
				b.stats.comments - a.stats.comments ||
				b.stats.views - a.stats.views ||
				b.post.date.localeCompare(a.post.date)
		)
		.slice(0, limit)
		.map((entry) => entry.post);
}
```

## 인기글 폴더

사이드바의 '모든 글' 바로 아래에 **인기글**이 있다. 다른 폴더와 같은 폴더 아이콘을 쓴다. 태그 보기, 최근 삭제된 항목처럼 폴더가 아니라 보기라서, 경로에 쓸 수 없는 글자로 시작하는 이름(`\u0000popular`)을 쓴다. 그래서 같은 이름의 폴더와 겹치지 않는다.

- 정렬 설정, 고정, 날짜별 묶음을 따르지 않고 **순위 그대로** 보인다.
- 제목 앞에 순위가 붙는다. 1~3위는 주황이다.
- 날짜·요약 자리에는 `조회 42 · 댓글 3 · 좋아요 5`가 보인다. 0인 항목은 뺀다.
- 검색어로 걸러도 순위 번호는 그대로다. 걸러진 목록에서 다시 1, 2, 3으로 매기지 않는다.
- 이 화면에서 좋아요를 누르거나 댓글을 쓰면, 서버에 다시 묻지 않고 그 수를 바로 고쳐 순위에 반영한다.

## 시험

- 단위: 점수, 반응이 없는 글 빼기, 같은 점수의 순서, 10개 제한, 인기글 보기의 순위 유지(정렬·고정 무시, 검색)
- API e2e: 브라우저마다 한 번, 다시 눌러도 그대로, 취소, 댓글 목록의 `likes`·`liked`, 댓글을 지우면 좋아요도 지워짐, `/posts/stats`, 요청 제한 429
- E2E: 글 좋아요 누르기·취소, 댓글 좋아요, 서버가 없으면 숨김, 인기글 순위·반응·좋아요를 누르면 순위가 바뀜, 10개 제한과 검색해도 그대로인 순위

## 그 뒤: 병합에서 빠진 좋아요

같은 무렵 쓰기 경로 전체에 요청 제한을 거는 일([#162](https://github.com/hyeoniverse/MacFolio/pull/162))이 다른 브랜치에서 진행 중이었다. 그 브랜치에 main을 합치면서 좋아요 모듈과 `like` 제한이 빠졌고, 바로 되살렸다. 되살리면서 서버의 경로 표 시험(`routes.e2e.test.ts`)에 좋아요 경로 여섯 개를 적었다. 이 표는 GET이 아닌 경로마다 제한이 걸려 있는지 확인하므로, 다음에 같은 일이 생기면 이 시험이 실패한다.

그때 위의 `@SkipThrottle({ ..., like: true })` 방식도 없앴다. 이제 경로마다 `@RateLimit('like')`처럼 이름 하나만 붙이고, 제한 이름과 값은 `common/rate-limit.ts` 한 곳에 있다(`like`: 30). 제한 이름이 일곱이 되자 건너뛸 이름을 여섯 개씩 적어야 해서 한 줄로 묶은 것이다. 그 이야기는 [쓰기 경로 33개에 요청 제한](/memo/rate-limit-all-writes)에 있다.

## 남은 것·배운 것

- 쿠키를 지우면 다시 누를 수 있다. 숫자를 겨루는 곳이 아니라서 받아들였다.
- 글이 수백 편이 되면 화면이 모든 글의 수를 받는 것이 무거워진다. 그때는 서버가 상위 몇십 개만 주는 방법을 다시 본다.
- 점수의 무게(1·3·5)는 감으로 정했다. 실제로 쌓인 수를 보고 다시 정할 일이다.
- 모듈 등록처럼 빠져도 컴파일은 되는 것은 경로 표 같은 시험으로 지킨다.
