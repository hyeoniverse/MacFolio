## OS와 관계없이 같은 글꼴

macOS·iOS는 시스템 글꼴(SF Pro, Apple SD Gothic Neo)을, 그 밖의 기기는 `public/fonts/`에서 배포하던 Apple SD Gothic Neo Regular 한 굵기를 받아, 같은 화면이 OS마다 다른 글꼴로 그려졌다. Apple 글꼴은 웹 배포 허락도 없었다. 26일 [#384](https://github.com/hyeoniverse/MacFolio/pull/384)에서 본문·고정폭·명조를 SIL OFL 1.1의 Pretendard·JetBrains Mono·Noto Serif KR로 바꾸고, CSS 34개 파일의 글꼴 지정을 변수 셋으로 모았다. ==그 대가로 데스크톱 첫 화면의 글꼴 전송량이 397KB에서 1,187KB로 늘었고==, 같은 날 밤 [#385](https://github.com/hyeoniverse/MacFolio/pull/385)에서 명조 한글을 Safari 창에 입력이 있는 시각에 받고 Pretendard core를 이 사이트가 쓰는 1,093자로 줄여 568KB로 낮췄다. 글꼴은 그린 글자에 따라 받아 빌드 결과만으로 크기를 알 수 없어, 예산은 실제 브라우저 E2E(데스크톱 600KB, 휴대폰 410KB)로 걸었다.

## 메모 검색 순위

27일 [#393](https://github.com/hyeoniverse/MacFolio/pull/393)에서 검색을 날짜 순서의 부분 일치에서 낱말별 AND와 칸 무게(제목 10, 주소 8, 태그 6, 초성 5, 요약 4, 본문 1) 순위로 바꾸고, 글 주소와 초성으로도 찾게 했다. 글마다 정규화한 검색용 문자열을 `WeakMap`에 한 번 저장해, 238편에서 글자 하나 입력 시 필터링이 4.5~5.1ms에서 0.5ms가 되었다. 결과가 0개이면 자모 단위 편집 거리로 비슷한 글 5편을 보인다. 순위 결과를 기존 날짜 묶음으로 나누자 같은 묶음 제목이 여러 번 생겨 React key가 겹쳤고, 휴대폰에서 결과가 0개인데 이전 글이 남았다. 검색 결과는 순위대로 한 줄로 늘어놓도록 바꿨다.

자세한 내용: [10월 27일](/memo/day-1027), [메모 다듬기](/memo/notes-polish)

## 연재를 제목 대신 칸으로

트래픽 분석 11편, 보안 점검 12편처럼 이어지는 글이 날짜순 목록에 흩어져 있었다. 29일 [#404](https://github.com/hyeoniverse/MacFolio/pull/404)의 첫 구현은 제목 형식(`이름 번호 - 제목`)으로 연재를 판별했는데, 제목을 고치면 연재가 깨지는 구조라 1시간 23분 만에 `series`·`seriesOrder` 칸으로 옮겼다. 마이그레이션은 nullable 열과 CHECK 제약뿐이라 배포가 이미지를 되돌려도 이전 코드가 동작한다. 제목 아래 연재 블록은 연재 순서대로 최대 5편을 보이고 줄인 자리를 `⋮`로 표시한다. 이 규칙은 커밋 10개에 걸쳐 정했다. 아코디언은 30ms 간격으로 높이를 재 변화의 77%가 첫 30ms에 끝나는 것을 확인하고, 400ms와 새 곡선 `--ease-in-out`으로 바꿔 목차·접기 블록에도 적용했다.

자세한 내용: [10월 29일](/memo/day-1029)

## 주소 한 줄을 임베드로

30일 [#405](https://github.com/hyeoniverse/MacFolio/pull/405)에서 문단에 주소 링크 하나만 있으면 YouTube·Vimeo·Spotify 등 21곳의 iframe으로 그리게 했다. `embedOf`가 공유 주소에서 ID만 뽑아 임베드 주소를 새로 만들고, CSP `frame-src`는 판별과 같은 `EMBED_ORIGINS` 목록에서 만든다. 같은 PR에서 영상·음악 파일 재생기와, 첨부 파일을 미리보기·텍스트 편집기·Safari로 여는 기능을 더했다. HTML 첨부 파일은 sandbox iframe의 `srcdoc`으로 그려 스크립트를 막는다. 편집기의 주소 맞추기가 표 칸과 코드 글자에도 링크를 걸어, 관리자가 글을 열기만 해도 임시 저장되던 문제를 같은 날 찾아 저장 0회를 확인하는 E2E를 더했다.

## 메모 목록과 첫 화면 성능

31일에 성능 PR 둘을 머지했다. 메모 목록은 글 247편의 원문 묶음(brotli 805KB)을 받아야 그려졌고, CPU만 제한하면 창과 목록이 같은 시각에 나타나 ==병목이 처리량이 아니라 전송량==임이 드러났다. [#407](https://github.com/hyeoniverse/MacFolio/pull/407)에서 빌드 시각에 만든 목록용 색인으로 목록을 먼저 그리고 연 글의 청크만 받아, 중급 휴대폰 조건의 목록 표시를 8.27초에서 2.53초로 줄였다. Lighthouse 모바일 FCP 2.8초는 관찰한 첫 렌더링 0.58초와 달랐다. simulate가 렌더링을 막는 `theme-boot.js`를 받는 사이 도착한 번들 38개까지 계산에 넣은 결과였다. [#409](https://github.com/hyeoniverse/MacFolio/pull/409)에서 테마 스크립트를 CSP 해시와 함께 인라인으로 넣고 첫 화면 HTML을 엣지 캐시에 보관해, 모바일 점수를 91에서 100으로 올리고 FCP·LCP를 2.8초에서 1.0초로 줄였다.

![목록용 색인 전후 요청 순서](./images/memo-post-list-index-waterfall.svg '전에는 메모 앱 청크 다음에 원문 묶음을 받아야 목록을 그렸다. 후에는 색인으로 목록을 먼저 그리고 연 글의 청크만 받는다')

## 돌아보며

- #384 본문에 글꼴 전송량(397KB → 1,187KB)을 기록한 덕분에, 같은 날 후속 PR의 목표와 측정 방법을 바로 정할 수 있었다. 그린 글자에 따라 달라지는 자원은 빌드 결과가 아니라 실제 브라우저로 예산을 건다.
- 목차 글자색 다섯 번, 연재 줄인 목록 열 번, 영상 버튼 자리 일곱 번은 모두 기준 화면을 정하거나 상대 UI의 크기를 재기 전에 구현부터 시작해서 생긴 반복이다. 다음에는 기준을 먼저 정하고 구현한다.
- 점수 순서 목록에 날짜 묶음을 그대로 적용해 React key가 겹쳤다. 표시 구조가 데이터 순서를 전제로 한다는 점을 놓쳤다. 정렬 기준을 바꾸면 그 목록을 그리는 구조도 함께 확인한다.
- 느린 메모 목록은 제한 조건을 하나씩 걸어 병목을 갈랐고, Lighthouse FCP는 도구가 계산한 값과 관찰한 값을 나눠 원인을 찾았다. 로컬은 HTTP/1.1과 늘 찬 캐시 때문에 차이가 보이지 않아, 배포 뒤 측정을 기준으로 삼았다.
- 편집기 플러그인 하나 때문에 관리자가 글을 열기만 해도 임시 저장이 생겼다. 문서를 고치는 플러그인을 더하면 기존 글을 연 뒤 저장 0회인지 시험한다.
