## 글꼴: OS와 관계없이 같은 글꼴로 (26일)

### 교체 ([#384](https://github.com/hyeoniverse/MacFolio/pull/384))

같은 화면이 macOS·iOS와 Windows·Android·Linux에서 다른 글꼴로 그려졌다. 글꼴 지정이 `-apple-system`으로 시작해 Apple 기기는 시스템 글꼴(SF Pro, Apple SD Gothic Neo)을, 그 밖의 기기는 `public/fonts/`에서 배포하던 Apple SD Gothic Neo **Regular 한 굵기**를 받았다. 굵은 글씨 약 500곳은 Apple 기기가 아니면 브라우저가 합성한 굵기였다. 그리고 Apple 글꼴은 웹 배포 허락이 없다.

![고치기 전: macOS와 Linux](./images/open-fonts-before-os.jpg '고치기 전. 같은 빌드를 macOS Chromium과 Linux Chromium에서 열었다. 영문·숫자·고정폭·굵은 글씨가 다르다')

![고친 뒤: macOS와 Linux](./images/open-fonts-after-os.jpg '고친 뒤. 두 OS가 같은 글꼴을 받는다')

| 용도       | 고치기 전 (Apple 기기 / 그 밖)                 | 고친 뒤 (모두 SIL OFL 1.1)                                 |
| ---------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 본문       | SF Pro + Apple SD Gothic Neo / Regular 웹 글꼴 | Pretendard Variable (굵기 45~920)                          |
| 고정폭     | SF Mono / Consolas·DejaVu Sans Mono 등         | JetBrains Mono Variable                                    |
| 명조       | AppleMyungjo / 기기마다 다름                   | Noto Serif KR Variable                                     |
| PDF 이력서 | Apple SD Gothic Neo                            | Pretendard OTF (react-pdf가 woff를 풀려면 `Buffer`가 필요) |
| 공유 카드  | Apple SD Gothic Neo                            | Pretendard woff (satori는 woff2를 읽지 못함)               |

CSS 34개 파일의 글꼴 지정을 `src/styles/fonts.css`의 변수 셋(`--font-sans`·`--font-mono`·`--font-serif`)으로 바꾸고, Apple 글꼴 파일 11개를 저장소에서 삭제했다. 입력 칸·버튼은 브라우저 기본값이 시스템 글꼴이라 `reset` 층에 `font-family: inherit`를 넣었다.

<details>
<summary>Pretendard 동적 서브셋(92조각)을 쓰지 않은 이유</summary>

처음에는 Pretendard가 제공하는 동적 서브셋을 시도했다. 메모 앱 첫 화면은 글 234편의 제목·요약을 한 화면에 그려 92조각 거의 전부(약 1.7MB)를 받았고, `@font-face` CSS 14.6KB 때문에 첫 방문 번들이 271.4KB로 상한 265KB를 넘었다. `scripts/subset-font.py`로 core(영문·문장 부호·자모·KS X 1001 2,350자) 하나와 나머지 한글 ext 8조각으로 직접 나눴다. 저장소 전체에서 KS X 1001 밖 한글은 '긂·똠·햏' 세 글자뿐이었다.

</details>

### 전송량 줄이기와 예산 ([#385](https://github.com/hyeoniverse/MacFolio/pull/385))

같은 글꼴을 그리는 대가로 데스크톱 첫 화면의 글꼴 전송량이 397KB(Chromium)에서 1,187KB로 늘었다. 교체 PR 본문에 이 수치를 기록했고, 같은 날 밤 후속 PR로 줄였다.

| 화면 (`vite preview`, 글꼴 응답 합계) |          교체 전 | #384 직후 | #385 적용 |
| ------------------------------------- | ---------------: | --------: | --------: |
| 데스크톱 첫 화면                      | 397KB (Chromium) |   1,187KB | **568KB** |
| 휴대폰 홈 (iPhone 15, WebKit)         |   136KB (WebKit) |     591KB | **382KB** |

1. **한글 명조는 Safari 창에 사용자 입력이 있는 시각에 받는다.** 바탕화면은 Safari 창이 처음부터 열려 있어 `ProjectPage.css`의 정적 `@import`로 첫 방문자 모두가 명조 한글 약 440KB를 받았다. 창 안을 누르거나 스크롤하는 등 사용자 입력이 있으면 `import()`로 불러온다. 그 전에는 같은 Pretendard 파일에 `size-adjust: 111.8%`(한글 폭 Noto Serif KR 0.966em ÷ Pretendard 0.864em)를 준 대체 글꼴로 그려, 명조로 바뀌는 시각에 제목 상자가 571×87px로 같다.
2. **Pretendard core를 이 사이트가 쓰는 글자로 줄였다.** 저장소의 글·화면 문구에 나오는 KS X 1001 1,093자만 core(456KB → 246KB)에 남기고, 나머지 1,257자는 `ksx` 조각(253KB)으로 분리했다.
3. **첫 화면 글꼴 예산.** 글꼴은 그린 글자에 따라 받아 빌드 결과만으로 크기를 알 수 없다. 그래서 `budget.mjs`가 아니라 E2E에 실제 브라우저 시험 3개를 넣었다: 데스크톱 첫 화면 600KB, 휴대폰 홈 410KB 상한, 데스크톱 첫 화면에 명조 한글 조각이 없는지.

![명조를 받기 전과 후](./images/open-fonts-serif-swap.jpg '첫 화면의 Safari 창. 왼쪽은 명조를 받기 전(폭을 맞춘 Pretendard), 오른쪽은 창을 누른 뒤의 Noto Serif KR. 제목의 줄바꿈과 높이가 같다')

대체 글꼴의 처음 이름 `'Serif Fallback'`은 동작하지 않았다. CSS 압축이 `font-family` 값의 따옴표를 제거하자 첫 낱말이 일반 글꼴 키워드 `serif`로 해석되어 규칙 전체가 무효가 되었다. 이름을 `'Pretendard Serif Fallback'`으로 바꿨다. 과정 전체는 [오픈 라이선스 글꼴로 바꾸고 첫 화면 글꼴을 1,187KB에서 568KB로 줄이기](/memo/open-fonts)에 적었다.

### 순위와 속도

주소 검색을 넣으면서 검색 로직을 `packages/desktop-core/src/memo/search.ts`로 모으고, 결과를 날짜 순서가 아니라 점수 순서로 바꿨다.

| 규칙      | 내용                                                                                  |
| --------- | ------------------------------------------------------------------------------------- |
| 낱말      | 공백으로 나눈 낱말이 모두 있어야 한다(AND). 하이픈·밑줄로 이은 낱말은 한 덩어리       |
| 입력 중   | 마지막 글자는 입력 중으로 보고 넓게 받는다 ('프론트에' → 프론트엔드)                  |
| 초성      | 초성만 두 글자 이상이면 제목의 초성에서 찾는다 (`ㅁㅊ` → 목차)                        |
| 칸 무게   | 제목 10, 주소 8, 태그 6, 초성 5, 요약 4, 본문 1. 제목·주소가 검색어와 같으면 +30      |
| 표기 사전 | `react`·`리액트`, `github`·`깃허브`처럼 기술 용어 40여 개의 표기를 묶고, 무게는 0.9배 |

| 측정 (저장소 글 238편, 본문 약 205만 자) | 전        | 후                     |
| ---------------------------------------- | --------- | ---------------------- |
| 글자 하나 입력 시 필터링                 | 4.5~5.1ms | 0.5ms                  |
| 검색용 문자열 생성                       | -         | 31ms (첫 검색에 한 번) |
| 결과가 0개일 때 추천 계산                | -         | 약 11ms                |

전에는 글자를 입력할 때마다 모든 글의 제목·본문에 `toLowerCase()`를 실행했다. 이제 글마다 정규화한 검색용 문자열(NFKC·소문자)을 `WeakMap`에 한 번 저장하고, 목록은 `useDeferredValue`로 검색어를 한 박자 늦게 따라간다.

결과가 0개이면 '혹시 ○○를 찾으셨나요?'와 비슷한 글 5편을 보인다. 자모 단위 편집 거리(Damerau–Levenshtein, 이웃 글자 맞바꾸기 비용 1)로 제목·주소·태그의 낱말과 비교한다. 본문은 비교하지 않는다. 긴 본문에는 어떤 검색어와도 비슷한 부분이 있기 때문이다.

### 휴대폰에서 결과가 0개인데 이전 글이 남던 문제

휴대폰에서 `리액트`로 찾은 뒤 한 글자 틀린 표기로 바꾸면 결과는 0개인데 목록에 앞 검색의 글이 남았다. 원인은 순위 결과를 기존처럼 날짜 묶음('오늘', '어제', '지난 7일')으로 나눈 데 있었다.

| 단계                                | 결과                                                                  |
| ----------------------------------- | --------------------------------------------------------------------- |
| 점수 순서의 글을 날짜 묶음으로 나눔 | 날짜가 섞여 있어 같은 묶음 제목이 여러 번 생긴다 (오늘 → 어제 → 오늘) |
| 묶음 제목을 React key로 사용        | 같은 key가 둘 이상 생긴다                                             |
| 결과가 0개가 되어 목록을 다시 그림  | React가 중복 key의 DOM 노드를 정리하지 못해 이전 글이 화면에 남는다   |

인기글처럼 검색 결과도 순위대로 한 줄로 늘어놓도록 바꿨다(`useNoteView.ts`의 `ranked`). 결과가 없으면 빈 목록 칸(휴대폰의 흰 카드)도 그리지 않는다. `mobile-memo-search.spec.ts`가 검색 결과에 묶음 제목이 0개인지, 결과가 없어지면 목록이 0개인지 확인한다.

### 최근 검색과 쌓임 맥락

목록 검색어를 최근 검색으로 5개까지 `localStorage`(`macfolio:memo:recent-searches`)에 저장하고, 빈 검색 칸에 초점이 가면 칸 아래(휴대폰은 위)에 목록을 펼친다. 이 목록이 본문 칸 오른쪽 위의 목차 버튼에 가렸다.

목록의 z-index는 `var(--z-menu)`로 충분히 컸다. 문제는 부모 `.memo-search`의 `position: relative; z-index: 4`다. z-index가 있는 위치 지정 요소는 쌓임 맥락(stacking context)을 만들고, 그 안의 자식은 맥락 밖의 요소와 직접 비교되지 않는다. 메모 창 안에서는 검색 칸 4와 목차 버튼이 비교되므로 목록이 아래에 그려졌다.

![쌓임 맥락 전후](./images/day-1027-stacking.svg '도식. 목록이 열린 동안만 :has()로 검색 칸을 10으로 올리고, 목차 버튼 9, 글자 크기 버튼 8로 다시 배정했다')

처음에는 목록이 열린 검색 칸을 `z-index: 20`으로 올렸는데, stylelint 규칙(부품 안의 겹침은 -1~10, 화면 전체의 층은 `--z-*` 토큰)에 걸려 CI가 실패했다. 같은 시각 [#396](https://github.com/hyeoniverse/MacFolio/pull/396)이 목차 버튼을 11로 올리고 있어 두 PR에서 순서를 다시 정했다.

| 최근 검색 목록이 열린 검색 칸 |                 4 |  10 |
| 목차 버튼·창                  |                11 |   9 |
| 글자 크기 버튼                |                10 |   8 |

## 목차와 이미지 배치 (27일)

### 글 목차와 이미지 정렬·띄우기 ([#391](https://github.com/hyeoniverse/MacFolio/pull/391))

저장소 글 238편의 `##`·`###` 제목 수는 중앙값 9개, 최대 32개이고, 10개 이상인 글이 99편이다. 읽기 화면에 목차가 없어 원하는 절을 찾으려면 끝까지 스크롤해야 했다. 이미지는 본문 가운데에 한 줄씩만 놓을 수 있어, 세로로 긴 캡처 옆에 설명을 둘 수 없었다.

| 기능          | 표기·동작                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| 목차          | 본문 맨 위 단계의 `h2`·`h3`로 자동 생성, 제목 3개 이상일 때만. 스크롤해 목차가 지나가면 오른쪽 위에 ≡ 버튼 |
| 이미지 정렬   | `![설명](주소#left)`, `#right`                                                                             |
| 이미지 띄우기 | `#float-left`, `#float-right`: 본문 폭의 40%, 문단이 옆으로 흐른다. 휴대폰·좁은 창에서는 띄우지 않는다     |

배치 표기는 HTML `align` 속성, 속성 문법(`{.float-right}`), 캡션 덧붙이기를 비교해 주소의 `#` 조각으로 정했다. `#` 조각은 요청에 포함되지 않아 GitHub 등 다른 뷰어에서도 이미지는 그대로 보이고 배치만 무시된다. 편집기에서는 이미지를 고르면 배치 버튼 다섯 개가 나타나고, 누르면 `src`의 `#` 조각만 바꾼다.

![왼쪽에 띄운 이미지](./images/memo-toc-image-layout-float.jpg '#float-left로 띄운 이미지 옆으로 문단이 흐른다. 시험용 글로 촬영했다')

처음 구현에서는 목차가 비어 있었다. `MemoToc` 안의 `useLayoutEffect`에서 본문 ref로 제목을 읽었는데, React는 layout 단계에서 형제를 앞에서부터 처리하며 ref도 그 순서로 연결한다. 본문보다 앞에 그리는 목차의 layout effect 시각에는 본문 ref가 아직 비어 있었다. 부모(`ReaderBody`)의 layout effect에서 읽도록 옮겼다.

### 제목 대신 series·seriesOrder 칸 ([#404](https://github.com/hyeoniverse/MacFolio/pull/404))

트래픽 분석 11편, 보안 점검 12편처럼 이어지는 글이 날짜순 목록에 흩어져 있어, 한 연재를 처음부터 이어 읽기 어려웠다. 29일 오전의 첫 구현은 제목이 `이름 번호 - 제목` 형식인 글을 연재로 판별했다. 제목을 고치다 형식이 깨지면 연재에서 빠지고 제목이 연재 정보를 겸해서, 같은 날 연재를 별도 칸으로 옮겼다.

| 위치                            | 칸                                                                     |
| ------------------------------- | ---------------------------------------------------------------------- |
| 저장소 글 (`memo/content/*.md`) | 머리말 `series`, `seriesOrder`                                         |
| `Post`                          | 게시본 `series`·`seriesOrder`, 임시본 `draftSeries`·`draftSeriesOrder` |
| `PostRevision`                  | 게시 시각의 `series`·`seriesOrder`                                     |

- **마이그레이션** `20261029120000_post_series`: nullable 열 추가와 CHECK 제약 둘(이름은 공백 문자열이 아님, 순서는 1 이상)뿐이라, 배포가 이미지를 되돌려도 이전 코드가 동작한다.
- **contracts**: `series` 40자, `seriesOrder` 1~999 정수.
- **판별** (desktop-core `series.ts`): 같은 이름의 글이 두 편 이상일 때만 연재로 본다. `seriesOrder` 오름차순이고 순서가 없는 글은 뒤에 날짜·첫 게시 시각·제목 순으로 놓는다. 화면의 번호는 정렬 위치라 순서 값이 건너뛰어도 1, 2, 3…으로 표시한다.

### 아코디언의 길이와 곡선

줄인 편은 DOM에 항상 렌더링해 두고, 묶음마다 `grid-template-rows: 0fr ↔ 1fr`로 그 자리에서 펼친다. 접힌 묶음은 `visibility: hidden`이라 Tab 이동과 접근성 트리에서 빠진다. 처음 값(280ms, `--ease-out`)으로는 움직임이 보이지 않았다. 30ms 간격으로 잰 높이가 403 → 579 → 612 → 631px로, ==높이 변화의 77%가 첫 30ms 안에 끝났다==.

| 항목             | 전                                  | 후                                                         |
| ---------------- | ----------------------------------- | ---------------------------------------------------------- |
| 길이             | 280ms                               | `--duration-slow` 400ms                                    |
| 곡선             | `--ease-out`                        | 새 토큰 `--ease-in-out` (`cubic-bezier(0.65, 0, 0.35, 1)`) |
| 연재 더보기 높이 | 403 → 579 → 612 → 631px (30ms 간격) | 375 → 391 → 447 → 557 → 604 → 627 → 631px (40ms 간격)      |

같은 움직임을 목차, 읽기 화면의 `<details>`, 편집 화면의 토글 블록에도 적용했다. `<details>`는 `::details-content`의 `block-size`를 `interpolate-size: allow-keywords`로 0 ↔ auto 전환한다. 편집 화면 토글은 ProseMirror가 접힌 내용을 `display: none`으로 감추는데, `@starting-style`을 늘 걸어 두면 편집기를 열거나 토글 안에 문단을 쓸 때도 움직였다. › 를 누른 순간에만 편집기 루트에 `.memo-details-animating`을 450ms 붙여 그동안만 전환한다. 루트의 속성 변화는 ProseMirror가 글 변경으로 읽지 않는다.

| CSP와 같은 목록    | `frame-src`에 `EMBED_ORIGINS`(출처 22개, Twitch는 재생기와 클립 출처가 다름)만 더한다. 판별과 CSP가 같은 목록이라 사이트를 더할 때 한 곳만 고친다 |
| YouTube            | 쿠키를 남기지 않는 `youtube-nocookie.com`, `referrerPolicy="strict-origin-when-cross-origin"`(Referer가 없으면 재생을 거부한다)                   |
| 넣지 않은 사이트   | X·GitHub Gist(스크립트 삽입 방식), Bandcamp·SlideShare(내부 ID를 알려면 API 요청), Dailymotion(Player ID 없이는 403)                              |

편집기는 주소 문단을 높이 0으로 숨기고, 그 뒤에 ProseMirror 위젯 장식으로 같은 iframe을 붙인다. 글(Markdown)은 주소 한 줄 그대로다. 위젯 key를 iframe 주소로 정해 다른 곳에 입력해도 iframe을 다시 불러오지 않는다. 높이 0인 문단은 브라우저의 위·아래 화살표가 건너뛰어 `handleKeyDown`이 커서를 직접 넣는다.

| 편집기 증상                                      | 원인                                                                                     | 수정                                                                       |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 주소 글자를 고치면 `[새 주소](예전 주소)`로 저장 | 링크 글자만 바뀌고 href는 그대로                                                         | `appendTransaction`이 https 주소 하나뿐인 문단의 링크를 글자 주소로 맞춘다 |
| 글을 열기만 해도 임시 저장                       | 위 맞추기가 표 칸 안 문단과 코드 글자(`` `https://…` ``)에도 링크를 걸어 문서가 바뀌었다 | 표는 건너뛰고 코드 글자에는 링크를 걸지 않는다. E2E가 연 뒤 저장 0회 확인  |

### 영상·음악 재생기

사이트 재생기가 없는 영상(`mp4`·`webm`·`mov` 등)·음악(`mp3`·`m4a`·`flac` 등) 파일은 `<video controls>`·`<audio controls>`로 그린다. 바깥 파일은 주소 경로의 확장자로, 편집기로 올린 파일은 링크 제목 '첨부 파일'과 링크 글자(파일 이름)의 확장자로 판별한다. API는 바꾸지 않았다. `Content-Disposition`은 링크로 열 때만 적용되고 Range 요청은 이미 지원한다. CSP `media-src`에는 `https:`를 더했다.

편집기에서 영상 위 주소 바꾸기·삭제 버튼의 자리는 커밋 7개에 걸쳐 옮겼다(오른쪽 위 → 재생기 아래 → 음량 줄 아래 → 왼쪽 → 전체 화면·PiP 버튼 오른쪽 …). 매번 Safari 기본 재생기의 위쪽 버튼 줄과 겹쳤다. 마지막에 Playwright WebKit에서 재생기를 그려 위쪽 줄을 픽셀로 재고(모서리에서 6px 안쪽, 높이 46px) 자리를 정했다.

| 상태             | 버튼 자리                                                               |
| ---------------- | ----------------------------------------------------------------------- |
| 처음 재생 전     | 왼쪽 위 모서리 (Safari가 위쪽 줄을 보이지 않는다)                       |
| `play` 이벤트 뒤 | 전체 화면·PiP 버튼 오른쪽(왼쪽에서 100px), 위쪽 줄과 수직 중심을 맞춘다 |

영상·음악 파일을 올리면 링크를 따로 한 문단에 두고 커서를 다음 줄로 옮긴다. 문장 중간에 넣으면 단독 링크 문단이 아니라서 재생기로 바뀌지 않았다.

### 첨부 파일을 사이트 안 앱으로 열기

| 파일                        | 여는 앱                       |
| --------------------------- | ----------------------------- |
| `pdf`, 그림                 | 미리보기                      |
| `md`                        | 텍스트 편집기 (Markdown 서식) |
| `txt`·`log`·`csv`·`json` 등 | 텍스트 편집기 (고정폭)        |
| `html`                      | Safari 새 탭                  |
| 그 밖 (`zip` 등)            | 새 탭 (내려받기)              |

올린 파일 주소에는 확장자가 없어 링크 글자(파일 이름)로 정한다. HTML은 `sandbox="allow-popups"` iframe의 `srcdoc`으로 그려 스크립트·양식 제출·같은 출처 접근을 막는다. 시험에서 파일 안의 `parent.hacked = 1`이 실행되지 않는 것을 확인했다.

> [!WARNING] 다른 출처 주소에는 적용되지 않는 download 속성
> 첨부 파일은 API 서버 출처라 `<a download>`가 무시된다. `fetchFileBlob`으로 받은 `Blob`의 임시 주소에 `download="<파일 이름>"`을 붙여 저장하고, 받지 못하면 새 탭에서 연다(API가 `Content-Disposition: attachment`로 응답한다).

내려받기 버튼은 링크 안에 둘 수 없어 링크 바로 뒤의 형제로 두고, 배지의 오른쪽 여백(34px) 안으로 음수 여백(-28px)으로 당긴다. 편집 화면은 위젯 장식으로 붙이는데, `marks: []`를 주지 않으면 위젯이 `<a>` 안에 그려져 링크 끝의 커서가 버튼 뒤로 잡혔다. 시험 도구의 `addInitScript`는 모든 프레임에서 실행되어 sandbox iframe에서 `localStorage` 접근 오류를 냈고, 맨 바깥 창에서만 실행하게 했다.

같은 PR에서 편집 중인 이미지에 삭제 버튼(크게 보기 왼쪽)을 더했고, [#406](https://github.com/hyeoniverse/MacFolio/pull/406)에서 본문 이미지의 내려받기 아이콘을 첨부 파일과 같은 `fa-download`로 맞췄다. 자세한 과정은 [임베드 글](/memo/memo-link-embed)과 [첨부 파일 글](/memo/memo-attachment-apps)에 적었다.

## 메모 목록을 원문 묶음보다 먼저 (31일, [#407](https://github.com/hyeoniverse/MacFolio/pull/407))

배포 사이트에서 메모 앱을 열면 창은 바로 뜨지만 목록이 비어 있는 시간이 길었다. 목록 하나를 그리려고 글 247편의 원문 전체(`contentFiles` 청크, 압축 전 3.76MB, brotli 805KB)를 받았다.

| 배포 사이트, Dock에서 열기               |    창 |  목록 |
| ---------------------------------------- | ----: | ----: |
| 제한 없음                                | 0.3초 | 0.5초 |
| CPU만 4배 느리게                         | 1.3초 | 1.3초 |
| 네트워크만 10Mbps, 지연 100ms            | 0.8초 | 3.1초 |
| CPU 6배, 5Mbps, 지연 150ms (중급 휴대폰) | 2.9초 | 8.3초 |

CPU만 제한하면 창과 목록이 같은 시각에 표시된다. ==병목은 처리량이 아니라 전송량==이다. 목록이 본문에서 읽는 것은 첫 그림, `#태그`, 검색 조건(체크리스트·표·코드 등이 있는지)뿐이고, 원문 전체가 필요한 곳은 본문 검색 하나다.

![목록용 색인 전후 요청 순서](./images/memo-post-list-index-waterfall.svg '전에는 메모 앱 청크 다음에 원문 묶음을 받아야 목록을 그렸다. 후에는 색인으로 목록을 먼저 그리고 연 글의 청크만 받는다')

1. **목록용 색인** `virtual:post-list`: 빌드 시각에 모든 글의 `Post`를 JSON으로 내보낸다. `body`에는 목록이 읽는 줄만 남기고(`listBody`) `bodyPending: true`를 붙인다. `listing.test.ts`가 원문과 색인 본문에서 `firstImage`·`tagsOf`·`POST_FILTERS`의 답이 같은지 검사한다.
2. **글별 청크**: `import.meta.glob('../content/*.md', { query: '?raw&single' })`. `contentFiles.ts`가 같은 파일을 `?raw`로 import해, 모듈 ID가 같으면 Rollup이 동적 `import()`를 큰 청크로 보낸다. 쿼리를 달리해 다른 모듈로 만들었다. Flux 글 청크는 brotli 10KB다.
3. **전체 원문은 뒤에서**: 마운트 직후 `contentFiles`를 동적 `import()`로 받아 본문 검색과 관리자 편집에 쓴다.

> [!WARNING] 색인 본문을 편집기에 열면 그대로 서버에 저장된다
> `bodyPending`인 글은 관리자 편집기에 열지 않고 원문이 온 뒤에 연다. 처음에는 관리자 화면 전체를 원문이 올 때까지 읽기 화면으로 두었는데, 그사이 누른 "새 메모"의 편집기 초점이 사라져 E2E 3건이 실패했다.

`loadPostBody`를 처음에 글 저장소 모듈에 두자, Finder도 쓰는 그 모듈에 247편의 `import()` 목록이 들어가 첫 방문 번들이 267.8KB로 예산(265KB)을 넘었다. 메모 앱만 import하는 `postBody.ts`로 옮겨 263.2KB가 되었다. 빌드 결과 JS 파일은 325개에서 572개가 되었다.

| 배포 뒤 (3회 중앙값)          | 전: 목록 | 후: 목록 |
| ----------------------------- | -------: | -------: |
| 네트워크만 10Mbps, 지연 100ms |   3.09초 |   1.31초 |
| CPU 6배, 5Mbps, 지연 150ms    |   8.27초 |   2.53초 |
| 같은 조건, 글 주소로 들어옴   |   2.43초 |   1.10초 |

자세한 과정은 [목록용 색인 글](/memo/memo-post-list-index)에 적었다.

## 첫 화면 성능과 Lighthouse 권장사항 (31일)

### 테마 스크립트 인라인과 CSP 해시 ([#409](https://github.com/hyeoniverse/MacFolio/pull/409))

배포 사이트의 Lighthouse 모바일 점수는 91(FCP·LCP 2.8초)이었다. 관찰한 첫 렌더링은 0.58초(TTFB 394ms + 렌더링 지연 186ms)인데 simulate는 2.8초를 계산했다. simulate는 관찰한 첫 렌더링 전에 수신을 마친 요청을 모두 첫 렌더링에 필요한 것으로 보고 느린 4G로 다시 계산한다. 렌더링을 막는 `theme-boot.js`(2KB)를 받는 사이 modulepreload 번들 38개가 먼저 도착해, 요청 39개·145KB가 FCP 계산에 들어갔다.

`theme-boot.js`는 CSP가 인라인 스크립트를 막아 파일로 분리했던 다크 모드 스크립트다. 빌드 시각에 `index.html`의 `<!--theme-boot-->` 자리를 `<script>`로 바꾸고, CSP `script-src`에는 `'unsafe-inline'` 없이 그 SHA-256 해시 하나만 더한다. `themeBoot.test.ts`가 해시와 스크립트 내용이 같은지 검사해, 스크립트를 고치고 해시를 갱신하지 않으면 시험이 실패한다.

### 첫 화면 HTML의 엣지 캐시

TTFB의 원인은 새로 뜬 Worker가 HTML을 만들기 전에 API `/site`·`/posts`와 정적 자산 `seo/posts.json`(압축 전 4MB)을 기다리는 데 있었다. isolate 안의 1분 캐시는 isolate가 새로 뜨거나 PoP가 바뀌면 사라진다.

![엣지 캐시 흐름](./images/week-1026-edge-cache.svg '도식. 1분 안이면 보관본, 1분이 지났으면 보관본을 먼저 주고 뒤에서 새로 만든다. 키에 ETag가 있어 배포하면 새 키가 된다')

| 배포 뒤 (Lighthouse 12.8.2, 5회 중앙값) |       전 |          후 |
| --------------------------------------- | -------: | ----------: |
| 모바일 점수                             |       91 |     **100** |
| 모바일 FCP·LCP                          |    2.8초 |   **1.0초** |
| 데스크톱 점수                           |       97 |     **100** |
| 데스크톱 FCP·LCP                        |   0.98초 |  **0.30초** |
| 첫 화면 서버 처리 시간                  | 약 320ms | **52~82ms** |

로컬에서는 차이가 보이지 않았다. 로컬 정적 서버(HTTP/1.1)는 첫 렌더링 전에 번들을 모두 받아 양쪽 모두 FCP 3.2초 안팎이고, `wrangler dev`는 캐시가 늘 차 있어 TTFB가 3ms 안팎이다.

### zod의 eval과 방문자의 401 ([#410](https://github.com/hyeoniverse/MacFolio/pull/410))

권장사항 점수 92에서 실패한 감사 항목 두 개를 화면 변경 없이 고쳤다.

| 감사 항목           | 기록                      | 원인                                                                                     | 수정                                                               |
| ------------------- | ------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `inspector-issues`  | CSP 위반 `kEvalViolation` | zod v4가 객체 스키마를 처음 검사하는 시각에 `new Function('')`으로 eval 가능 여부를 확인 | 스키마보다 먼저 `z.config({ jitless: true })`                      |
| `errors-in-console` | `GET /auth/me 401`        | 로그인하지 않은 방문자도 시작 시각에 관리자 세션을 묻는다                                | 로그인 표시(`STORAGE_KEYS.adminSignedIn`)가 있는 브라우저만 묻는다 |

> [!NOTE] 서버에서는 eval이 실제로 실행되고 있었다
> 브라우저는 CSP가 막아 시도만 기록되었지만, Node에는 CSP가 없어 zod가 `new Function`으로 검사 함수를 만들고 있었다. 재료는 스키마 정의뿐이라 요청 값이 코드가 되지는 않지만, 서버·브라우저 모두 jitless로 바꿨다.

로그인 표시는 물어볼 이유가 있다는 힌트일 뿐이고, 권한은 서버가 매 요청 세션 쿠키로 확인한다(`AdminGuard`). 배포 직후 이미 로그인해 둔 관리자는 표시가 없어 한 번 다시 로그인해야 한다. 같은 PR에서 CI의 `pnpm audit --prod --audit-level=high`가 새로 공개된 follow-redirects 1.16.1 취약점(GHSA-mrwp-f3q8-3g9p, 사용자 지정 인증 헤더가 다른 호스트로 리다이렉트를 따라감. 경로 API > msedge-tts > axios)으로 실패해 overrides로 1.16.2를 지정했다.

### 저장소 글의 category 변경과 서버의 정리 내용 (26일, [#389](https://github.com/hyeoniverse/MacFolio/pull/389))

저장소 글의 `category`를 바꿀 때는 서버 쪽 정리 내용과의 관계를 먼저 확인해야 한다. 화면은 저장소 `category`에 관리자가 메모 앱에서 바꾼 폴더 이름·글 지정(서버의 `GET /memo/organization`)을 차례로 적용하므로, 배포 API를 조회만 해서 영향을 확인했다.

| 항목                     | 값                                     | 영향                                                                               |
| ------------------------ | -------------------------------------- | ---------------------------------------------------------------------------------- |
| `moves` (폴더 이름 변경) | `개발기` → `개발 기록`                 | 저장소 이름을 `개발 기록`으로 바꿔도 표시는 같다                                   |

### 브라우저형 도구 막대 ([#399](https://github.com/hyeoniverse/MacFolio/pull/399))

프로젝트 앱 창에는 제목 표시줄만 있어, iframe 안에서 링크를 따라가면 이전 페이지로 돌아갈 수단이 없었다. 게임이 아닌 프로젝트(HYEONIVERSE, NewPick, QRU, WTD)는 Safari처럼 뒤로·앞으로, 주소창, 새로 고침이 있는 도구 막대를 둔다. 게임(새싹 농장)은 화면을 넓게 쓰도록 제목 표시줄만 둔다.

![프로젝트 앱 도구 막대 전후](./images/day-1027-project.jpg '창을 chrome="unified"로 열어 신호등 버튼이 도구 막대 위에 겹친다. 사이트 내용은 Playwright로 대체한 시험용 페이지다')

iframe의 페이지는 다른 출처라서 `iframe.contentWindow.history`에 접근할 수 없다. 대신 iframe 안의 이동이 바깥 문서의 세션 기록에 함께 쌓이는 성질을 이용한다. MacFolio는 주소 막대를 `replaceState`로만 바꾸므로, 바깥 `history.length`가 늘어난 수가 iframe이 쌓은 기록 수다.

![바깥 문서의 세션 기록으로 iframe 기록 위치 추정](./images/day-1027-frame-history.svg '도식. base·length·index로 위치를 관리하고, 뒤로·앞으로는 바깥 문서의 history.back()·forward()로 iframe을 이동한다')

<details>
<summary>기록 위치를 갱신하는 신호</summary>

| 신호                                     | 처리                                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `history.length` 증가 (400ms 간격 조회)  | iframe에 초점이 있거나 방금 load가 끝났으면 이 iframe의 기록으로 집계, 아니면 다른 창의 기록으로 보고 `base`를 옮긴다 |
| iframe의 `load`                          | 새 이동으로 처리. 앞쪽 기록이 하나 남은 위치에서 이동하면 `history.length`가 그대로라 load로 판별한다                 |
| 뒤로·앞으로·새로 고침 뒤 3초 안의 `load` | 이동이 아니므로 무시. bfcache로 돌아가면 load가 오지 않아 시간으로 끊는다                                             |

`pushState`는 알려 주는 이벤트가 없어 `history.length`를 주기적으로 조회한다. 순수 계산은 `frameHistory.ts`(단위 시험 7개), 브라우저 신호 연결은 `useFrameHistory.ts`에 있다.

</details>

새로 고침은 `iframe.src`를 다시 지정하지 않고 `contentWindow.location.replace(src)`를 호출한다. `src`를 바꾸면 세션 기록이 하나 더 쌓이기 때문이다. 다른 출처의 현재 주소는 읽을 수 없어, 새로 고침은 처음 주소를 다시 불러온다.

한계는 세션 기록이 문서 전체에 하나라는 점이다. 프로젝트 앱 두 개를 열고 번갈아 이동하면, 뒤로 가기는 마지막에 기록을 쌓은 iframe을 이동한다. 휴대폰은 페이지가 화면 전체를 쓰는 기존 구성을 유지하고 도구 막대는 데스크톱에만 둔다. 프로젝트 앱의 처음 구성은 [PROJECTS 데이터에서 생성하는 iframe 앱과 ProjectAppName 브랜드 타입](/memo/project-apps)에 있다.

## 돌아보며

**화면을 통일한 대가를 수치로 기록해, 같은 날 줄일 수 있었다.** #384 본문에 화면별 글꼴 전송량(397KB → 1,187KB)을 기록했기 때문에, 후속 PR의 목표와 결과(568KB)를 같은 측정 방법으로 비교할 수 있었다. 번들 예산(`budget.mjs`)은 빌드 결과만 검사해 글꼴 전송량 증가를 잡지 못했다. 그린 글자에 따라 달라지는 자원은 실제 브라우저 시험으로 예산을 걸어야 한다.

**패치 버전 하나가 관리자 편집 화면을 막았다.** 읽기 화면만 시험했다면 배포 후에야 발견했을 오류를 편집기 E2E가 잡았다. 고정한 버전은 `dependabot.yml`에 해제 조건과 함께 기록해, 다음 버전에서 다시 확인하도록 했다.

**PR 셋을 나란히 진행하면서 같은 CSS 층을 서로 다르게 바꿨다.** 쌓임 맥락 안에서는 자식의 z-index를 아무리 올려도 부모의 값으로 비교되고, stylelint의 -1~10 범위 때문에 값을 계속 올리는 방법도 막혔다. 한 화면의 떠 있는 요소들(검색 목록, 목차 버튼·창, 글자 크기 버튼)의 순서를 표 하나로 정하고 두 PR이 그 표를 따르게 한 뒤에야 끝났다.

**목차 글자색을 한 시간 안에 다섯 번 바꿨다.** 대비 수치, 본문과의 진하기 관계, 마우스 올림 색이 커밋마다 바뀌었다. [10월 23일](/memo/week-1019)에 정한 "기준 화면과 수치를 먼저 정한다"는 원칙을 다시 지키지 못했다. 다음에는 Apple 문서 화면 캡처와 후보 색 두세 개의 대비 표를 먼저 만들고 고른 뒤 구현한다.

**표시 구조가 데이터 순서와 맞지 않으면 화면 오류로 나타난다.** 날짜 묶음은 날짜 순서 목록을 전제로 하는데, 점수 순서 목록에 그대로 적용해 묶음 제목과 React key가 중복되었다. 정렬 기준을 바꾸면 그 목록을 그리는 구조(묶음, key)도 함께 확인한다.

**구조를 바꾸는 PR은 기본 크기 화면으로 먼저 확인한다.** 폴더 4단은 PR 본문에 '디자인 시…' 말줄임을 적어 두고도 머지한 뒤 3단으로 되돌리기로 했다. #389의 삭제 커밋도 머지 뒤에 올라가 main에서 빠졌다. push 직전에 `gh pr view --json state`로 PR 상태를 확인하는 단계를 넣는다.

**도구가 계산한 값과 관찰한 값을 나눠 확인했다.** Lighthouse의 FCP 2.8초는 관찰한 첫 렌더링 0.58초와 달랐다. simulate가 어떤 요청을 계산에 넣는지 확인하고 나서야, 원인이 렌더링을 막는 2KB 파일과 그사이 도착한 번들 38개라는 것을 찾았다. 로컬은 HTTP/1.1과 늘 찬 캐시 때문에 차이가 보이지 않아, 배포 뒤 같은 방법으로 다시 잰 값을 PR에 남겼다.

**제한 조건을 하나씩 걸어 병목을 갈랐다.** 메모 목록이 느린 원인을 CPU 제한과 네트워크 제한으로 나눠 재자, CPU만 느린 조건에서는 창과 목록이 같은 시각에 표시되어 전송량 문제라는 것이 바로 드러났다. 원문 묶음은 성능 최적화 2편에서 첫 화면에서만 뺐고, 글이 199편에서 247편으로 늘며 2.4MB에서 3.76MB가 되었다. 첫 화면 밖의 묶음 크기도 예산으로 관리할 대상이다.

**버튼 자리를 측정 없이 옮기는 일이 다시 반복되었다.** 영상 위 편집 버튼을 커밋 7개에 걸쳐 옮겼고, Safari 재생기의 위쪽 줄을 픽셀로 잰 뒤에야 끝났다. 27일의 목차 글자색 다섯 번과 같은 양상이다. 남의 UI와 겹치는 요소는 그 UI의 크기를 먼저 재고 자리를 정한다.

**글을 열기만 해도 바뀌는 편집기는 시험으로 막는다.** 주소 링크를 맞추는 `appendTransaction`이 표 칸과 코드 글자에도 적용되어, 관리자가 글을 열기만 해도 임시 저장이 생겼다. 문서를 고치는 플러그인을 더할 때는 기존 글을 연 뒤 저장 횟수가 0인지 확인하는 E2E를 함께 둔다.
