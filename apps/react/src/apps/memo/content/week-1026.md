## OS와 관계없이 같은 글꼴

웹 페이지의 글꼴은 CSS의 `font-family` 목록에서 기기에 설치된 첫 글꼴을 쓰거나, `@font-face`로 지정한 파일을 내려받아 쓴다. 이전에는 macOS·iOS는 시스템 글꼴(SF Pro, Apple SD Gothic Neo)을, 그 밖의 기기는 `public/fonts/`에서 배포하던 Apple SD Gothic Neo Regular 한 굵기를 받았다. 그래서 같은 화면이 OS마다 다른 글꼴로 그려졌다. 예를 들어 Windows에서는 굵은 제목도 Regular 한 굵기를 브라우저가 인위적으로 두껍게 만들어 그렸다. Apple 글꼴은 웹 배포 허락도 없었다.

26일 [#384](https://github.com/hyeoniverse/MacFolio/pull/384)에서 본문·고정폭·명조를 Pretendard·JetBrains Mono·Noto Serif KR로 바꾸고, CSS의 글꼴 지정을 변수 셋으로 모았다. 세 글꼴은 SIL OFL 1.1 라이선스로, 웹 페이지에 포함해 배포할 수 있다.

==그 결과 데스크톱 첫 화면의 글꼴 전송량이 397KB에서 1,187KB로 늘었고==, 같은 날 밤 [#385](https://github.com/hyeoniverse/MacFolio/pull/385)에서 568KB로 낮췄다. 명조 한글은 Safari 창에 입력이 있는 시각에 받게 하고, Pretendard core를 이 사이트가 쓰는 1,093자로 줄였다.

![화면별 글꼴 전송량](./images/open-fonts-transfer.svg '교체 직후, 명조 지연 적용, 글자 수 축소까지 적용한 단계별 전송량. 아래에 E2E 상한을 적었다')

브라우저는 글꼴 파일을 페이지에 실제로 그린 글자에 따라 받으므로, 빌드 결과만으로는 전송량을 알 수 없다. 그래서 예산은 실제 브라우저로 페이지를 열어 측정하는 E2E(데스크톱 600KB, 휴대폰 410KB)로 걸었다.

## 메모 검색 순위

27일 [#393](https://github.com/hyeoniverse/MacFolio/pull/393) 전의 검색은 검색어가 들어 있는 글을 날짜순으로 나열했다. 검색어가 본문에 한 번 나온 글과 제목에 나온 글이 같은 무게였다. 이를 낱말별 AND와 칸 무게 순위로 바꿨다. 낱말별 AND는 "리액트 목차"를 "리액트"와 "목차"로 나눠 두 낱말이 모두 들어 있는 글만 남기는 방식이다. 남은 글은 낱말이 나온 칸의 무게(제목 10, 주소 8, 태그 6, 초성 5, 요약 4, 본문 1)를 더한 점수로 정렬한다. 글 주소와 초성(예: "ㄹㅇㅌ"로 "리액트")으로도 찾게 했다.

![검색어 '리액트 목차'의 글별 점수 계산 예](./images/day-1027-search-score.svg '낱말이 나온 칸의 무게를 더해 순위를 정한다')

글마다 정규화한 검색용 문자열을 `WeakMap`에 한 번 저장해, 238편에서 글자 하나 입력 시 필터링이 4.5~5.1ms에서 0.5ms가 되었다. `WeakMap`은 객체를 키로 쓰는 저장소로, 글 객체가 더 이상 쓰이지 않으면 저장한 값도 함께 메모리에서 해제된다. 결과가 0개이면 자모 단위 편집 거리로 비슷한 글 5편을 보인다. 편집 거리는 한 문자열을 다른 문자열로 바꾸는 데 필요한 삽입·삭제·교체 횟수다.

순위 결과를 기존 날짜 묶음으로 나누자 같은 묶음 제목이 여러 번 생겨 React key가 겹쳤고, 휴대폰에서 결과가 0개인데 이전 글이 남았다. 검색 결과는 순위대로 한 줄로 늘어놓도록 바꿨다.

## 연재를 제목 대신 칸으로

트래픽 분석 11편, 보안 점검 12편처럼 이어지는 글이 날짜순 목록에 흩어져 있었다. 29일 [#404](https://github.com/hyeoniverse/MacFolio/pull/404)의 첫 구현은 제목 형식(`이름 번호 - 제목`)으로 연재를 판별했는데, 제목을 고치면 연재가 깨지는 구조라 곧바로 `series`·`seriesOrder` 칸으로 옮겼다.

![제목 형식 판별과 별도 칸의 비교](./images/week-1026-series-field.svg '제목 형식으로 판별하면 제목을 고친 글이 연재에서 빠진다. 별도 칸이면 제목과 연재 정보가 독립이다')

배포가 실패하면 서버 이미지는 이전 버전으로 돌아가지만 DB 마이그레이션은 되돌리지 않는다. 그래서 새 열은 비어 있어도 되는(nullable) 열로 추가하고 CHECK 제약만 더했다. 이전 코드는 새 열을 읽지 않으므로 그대로 동작한다.

제목 아래 연재 블록은 연재 순서대로 최대 5편을 보이고 줄인 자리를 `⋮`로 표시한다. 아코디언은 30ms 간격으로 높이를 재 변화의 77%가 첫 30ms에 끝나는 것을 확인하고, 400ms와 새 곡선 `--ease-in-out`으로 바꿔 목차·접기 블록에도 적용했다.

![연재 블록](./images/week-1026-series-reader.jpg '트래픽 분석 2편. 제목 위 연재 표시, 제목 아래 연재 블록과 이전 편·다음 편 카드')

## 주소 한 줄을 임베드로

임베드는 다른 사이트의 영상·음악 재생기를 iframe으로 페이지 안에 넣는 방식이다. 30일 [#405](https://github.com/hyeoniverse/MacFolio/pull/405)에서 문단에 주소 링크 하나만 있으면 YouTube·Vimeo·Spotify 등 21곳의 iframe으로 그리게 했다.

`embedOf`는 사용자가 붙여 넣은 공유 주소를 그대로 iframe에 넣지 않고, 주소에서 ID만 뽑아 임베드 주소를 새로 만든다. 예를 들어 YouTube 공유 주소에서 영상 ID와 시작 시각을 꺼내 `https://www.youtube-nocookie.com/embed/<ID>?start=90`을 만든다. 이렇게 하면 허용한 사이트의 정해진 형식 주소만 iframe에 들어간다. CSP의 `frame-src`(iframe으로 불러올 수 있는 출처 목록)는 판별과 같은 `EMBED_ORIGINS` 목록에서 만들어, 두 목록이 어긋나지 않는다.

![공유 주소에서 임베드 주소를 만드는 과정](./images/memo-link-embed-url-to-src.svg '공유 주소에서 영상 ID와 시작 시각만 꺼내 임베드 주소를 새로 만든다')

같은 PR에서 영상·음악 파일 재생기와, 첨부 파일을 미리보기·텍스트 편집기·Safari로 여는 기능을 더했다. HTML 첨부 파일은 sandbox iframe의 `srcdoc`(iframe 내용을 주소 대신 HTML 문자열로 지정하는 속성)으로 그려 스크립트를 막는다. 편집기의 주소 맞추기가 표 칸과 코드 글자에도 링크를 걸어, 관리자가 글을 열기만 해도 임시 저장되던 문제를 같은 날 찾아 저장 0회를 확인하는 E2E를 더했다.

![읽기 화면의 YouTube 임베드](./images/memo-link-embed-reader.jpg 'Flux 글에 주소 한 줄로 적은 F8 2014 발표 영상. 본문 폭의 16:9 재생기와 아래의 "YouTube에서 열기" 링크')

## 메모 목록과 첫 화면 성능

메모 목록은 글 247편의 원문 묶음(brotli 805KB)을 받아야 그려졌다. 원인을 가르려고 조건을 하나씩 걸었다. 네트워크는 그대로 두고 CPU만 느리게 하면 창과 목록이 같은 시각에 나타났다. 즉 ==병목이 처리량이 아니라 전송량==이었다. [#407](https://github.com/hyeoniverse/MacFolio/pull/407)에서 빌드 시각에 목록용 색인(목록 표시에 필요한 제목·주소 같은 정보만 모은 배열)을 만들어 목록을 먼저 그리고, 연 글의 청크만 받게 했다. 중급 휴대폰 조건의 목록 표시는 8.27초에서 2.53초로 줄었다.

![목록용 색인 전후 요청 순서](./images/memo-post-list-index-waterfall.svg '전에는 메모 앱 청크 다음에 원문 묶음을 받아야 목록을 그렸다. 후에는 색인으로 목록을 먼저 그리고 연 글의 청크만 받는다')

FCP(First Contentful Paint)는 페이지에서 글자나 이미지가 처음 그려진 시각이다. Lighthouse의 simulate 모드는 실제로 측정한 요청 기록을 느린 4G 조건으로 다시 계산해 FCP를 추정한다. 모바일 FCP는 2.8초였지만 실제로 관찰한 첫 렌더링은 0.58초였다. simulate가 렌더링을 막는 `theme-boot.js`를 받는 사이 도착한 번들 38개까지 첫 렌더링에 필요한 요청으로 계산에 넣은 결과였다.

![관찰한 첫 렌더링과 simulate가 계산한 FCP](./images/week-1026-fcp-simulate.svg '렌더링을 막는 2KB 파일 하나 때문에 그사이 도착한 요청 39개가 계산에 들어갔다. 인라인으로 넣자 1.0초가 되었다')

[#409](https://github.com/hyeoniverse/MacFolio/pull/409)에서 테마 스크립트를 CSP 해시와 함께 HTML 안에 인라인으로 넣고, 첫 화면 HTML을 Cloudflare 엣지 캐시(방문자와 가까운 Cloudflare 서버의 캐시)에 보관했다. 모바일 점수는 91에서 100으로, FCP·LCP는 2.8초에서 1.0초로 줄었다.

## 돌아보며

- #384 본문에 글꼴 전송량(397KB → 1,187KB)을 기록한 덕분에, 같은 날 후속 PR의 목표와 측정 방법을 바로 정할 수 있었다. 그린 글자에 따라 달라지는 자원은 빌드 결과가 아니라 실제 브라우저로 예산을 건다.
- 목차 글자색, 연재 줄인 목록, 영상 버튼 자리를 거듭 바꾼 것은 모두 기준 화면을 정하거나 상대 UI의 크기를 재기 전에 구현부터 시작해서 생긴 반복이다. 다음에는 기준을 먼저 정하고 구현한다.
- 점수 순서 목록에 날짜 묶음을 그대로 적용해 React key가 겹쳤다. 표시 구조가 데이터 순서를 전제로 한다는 점을 놓쳤다. 정렬 기준을 바꾸면 그 목록을 그리는 구조도 함께 확인한다.
- 느린 메모 목록은 제한 조건을 하나씩 걸어 병목을 갈랐고, Lighthouse FCP는 도구가 계산한 값과 관찰한 값을 나눠 원인을 찾았다. 로컬은 HTTP/1.1과 늘 찬 캐시 때문에 차이가 보이지 않아, 배포 뒤 측정을 기준으로 삼았다.
- 편집기 플러그인 하나 때문에 관리자가 글을 열기만 해도 임시 저장이 생겼다. 문서를 고치는 플러그인을 더하면 기존 글을 연 뒤 저장 0회인지 시험한다.
