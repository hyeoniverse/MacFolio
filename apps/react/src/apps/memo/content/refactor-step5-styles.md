리팩터링 계획([#150](https://github.com/hyeoniverse/MacFolio/issues/150))의 5단계는 CSS였다. 값은 하나도 바꾸지 않고 이름을 붙이고, 나누고, 지웠다.

## 왜

CSS가 26,464줄이었다. 직접 쓴 hex 색 650곳, CSS 변수 309종, `border-radius`는 6·8·10·14·999px 등이 섞여 있었고, `z-index` 값은 23가지였다. `Memo.css` 하나가 4,166줄이었다.

숫자가 흩어져 있으니 새 화면을 만들 때마다 같은 질문을 했다. 새 팝업의 `z-index`를 얼마로 줘야 Dock 위에 뜨는지 알려면 `Dock.css`, `StatusBar.css`, `Menu.css`, `LoadingScreen.css`를 차례로 열어 숫자를 비교해야 했다. 모서리는 6px·8px·10px이 같은 뜻으로 섞였고, 다크 모드 색은 파일마다 따로 적혀 있었다. `Memo.css`는 편집기를 고치는 PR마다 diff가 커서, 휴대폰 화면 규칙과 데스크톱 규칙이 같은 파일의 수천 줄 사이에 섞여 있었다.

## 고른 방법과 버린 방법

| 방법                                  | 좋은 점                               | 걸린 점                                                                               |
| ------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------- |
| Tailwind 같은 유틸리티 CSS로 옮기기   | 토큰이 클래스 이름이 되어 강제된다    | 26,000줄 넘는 CSS와 컴포넌트를 다시 써야 하고, 화면이 바뀌지 않았다고 증명하기 어렵다 |
| 값을 정리해 가까운 값끼리 합치기      | 토큰 수가 줄어 체계가 깔끔해진다      | 1~2px씩 움직이는 화면이 생겨, 동작을 바꾸지 않는다는 이번 규칙을 어긴다               |
| 값은 그대로 두고 이름만 붙이기 (고름) | 화면이 그대로라 기계로 비교할 수 있다 | 비슷한 값이 각자 이름 없이 남는다                                                     |

1~6단계의 규칙은 "동작을 바꾸지 않는다"였다. 값을 합치는 일은 화면을 보며 하나씩 정해야 해서 따로 미뤘다. 이번에는 이미 같은 값으로 되풀이된 것만 이름을 붙였다.

## 구현

토큰은 모두 `src/styles/theme.css`의 `:root`에 둔다. 층은 숫자 대신 뜻으로 읽힌다.

```css
/* apps/react/src/styles/theme.css */
--radius-xs: 4px;
--radius-sm: 6px;
--radius-md: 8px;
--radius-lg: 10px;
--radius-xl: 14px;
--radius-full: 999px; /* 알약 */

--z-dock: 1000;
--z-menubar: 1001;
--z-alert: 2500; /* 화면 한가운데 경고창: 창·Dock·메뉴 막대 위 */
--z-menu: 10000; /* 펼친 메뉴·팝오버·라이트박스: 어떤 창보다 위 */
--z-login: 20000; /* 로그인: 가장 위 */
```

글자 크기는 Apple의 글자 크기 이름(`caption2`~`title2`)을 따라 여덟 개를 두었다. 간격은 반대로 `--space-8`처럼 px 숫자를 이름에 넣었다. 간격은 2px 단위로 열 칸이 촘촘해서 `sm`·`md`로는 나누기에 모자랐다.

바꾸는 기준은 "글자까지 같은 값만"이었다. 간격은 선언의 값이 모두 열 값일 때만 바꿨고, `0`이나 `auto`가 섞인 줄임 표기는 그대로 두었다. 메모의 버전 목록 버튼 하나를 보면 이렇다.

```css
/* apps/react/src/apps/memo/styles/note.css */
.memo-format-panel .memo-revision-list button {
	gap: 1px; /* 열 값에 없어 그대로 */
	padding: var(--space-6) var(--space-10); /* 6px 10px */
	border-radius: var(--radius-md); /* 8px */
}
```

`Memo.css`는 도구 막대·사이드바·목록·본문·편집기·휴대폰 화면 같은 구역 경계에서 잘라 `memo/styles/` 열다섯 파일로 나누고, 원래 파일에는 차례대로 불러오는 목록만 남겼다. 규칙의 차례가 바뀌면 같은 점수의 규칙끼리 이기는 쪽이 바뀌므로, 자르기만 하고 순서는 건드리지 않았다.

### 같은지 보기

모든 PR의 확인 방법은 "같은지 보기"였다. 토큰은 값을 그대로 둔 채 이름만 붙였고, `Memo.css`는 빌드한 CSS가 바이트까지 같은지, 중복 제거는 요소마다 계산된 스타일이 라이트·다크 × 데스크톱·휴대폰에서 같은지 비교했다.

![이름 붙이기, 파일 나누기, 중복 지우기를 확인한 세 방법](./images/refactor-step5-styles-checks.svg '세 방법 모두 다르면 실패하는 기계 비교다')

쓰지 않는 선택자(#242)는 다르게 찾았다. CSS의 클래스 이름 2,761개 중 코드 어디에도 글자가 없는 150개를 뽑고, `이름-${…}`처럼 코드가 조립하는 이름과 라이브러리(highlight.js, ProseMirror)가 붙이는 이름을 걸러 9개를 남겼다. 9개는 하나씩 코드를 읽어 확인한 뒤 규칙 24개를 지웠다.

## 일부러 남긴 것

- 프로젝트 소개 페이지의 브랜드 색은 일부러 따로 쓰는 값이라 토큰으로 묶지 않았다. `rgb()`·`rgba()` 425곳도 범위에서 뺐다.
- 같은 뜻의 `z-index` 값을 합치면 그리는 순서가 바뀔 수 있어 보류했다.
- 메모의 `late.css`는 옮기면 적용 차례가 바뀌어 그대로 두었다.
- Stylelint는 CSS만 읽어 클래스를 쓰는지 알 수 없어 들이지 않았다.

## 확인과 남은 것

- 토큰 PR마다 계산된 스타일 비교에서 차이 0, `Memo.css` 나누기는 빌드한 CSS의 md5가 같았다.
- 지금 CSS에서 `var(--space-`는 1,908곳, `var(--color-`는 863곳, `var(--text-`는 646곳, `var(--radius-`는 246곳 쓰인다. 5단계가 끝난 뒤에 생긴 화면도 토큰을 쓰고 있다는 뜻이다.
- 토큰을 쓰지 않은 새 값을 막는 장치는 아직 없다. Stylelint의 `declaration-property-value-allowed-list` 같은 규칙으로 막을 수 있지만, 일부러 남긴 값이 많아 예외 목록부터 정해야 한다.

## 배운 것

- **이름 붙이기와 값 고치기를 나눈다.** 이름만 붙이면 기계로 증명할 수 있고, 값을 고치는 일은 그 뒤에 화면을 보며 한다.
- **차례가 곧 규칙이다.** CSS는 같은 점수면 나중 규칙이 이긴다. 파일을 나눌 때도, 중복을 지울 때도 차례를 지키는 것이 가장 큰 조건이었다.
