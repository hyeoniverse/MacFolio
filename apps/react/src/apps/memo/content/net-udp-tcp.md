## 들어가기 전에

IP는 패킷을 목적지 호스트까지 전달하지만, 호스트 안의 어느 프로그램이 그 패킷을 받아야 하는지는 알려 주지 않는다. 웹 브라우저, 메신저, DNS 질의가 같은 IP 주소를 공유하는 상황에서 도착한 바이트를 올바른 프로세스로 넘기려면 IP 위에 프로세스를 구분하는 계층이 하나 더 필요하다. 또 IP는 패킷을 잃어버리거나 순서를 뒤바꿔도 아무 조치를 하지 않는다. 파일 1MB를 보내다가 중간의 패킷 하나가 사라지면, 수신 측 프로그램은 어느 부분이 빠졌는지조차 알 수 없다.

전송 계층(transport layer)은 이 두 문제를 서로 다른 수준으로 해결한다. UDP(User Datagram Protocol)는 포트 번호와 선택적인 체크섬만 더해 IP를 거의 그대로 응용에 노출한다. TCP(Transmission Control Protocol)는 연결을 맺고, 바이트마다 순서 번호를 붙이고, 확인 응답과 재전송으로 신뢰성을 만든다.

이 글이 답하려는 질문은 다음과 같다. UDP는 무엇을 하지 않기에 단순하고, 그 단순함 때문에 응용은 무엇을 직접 고려해야 하는가. TCP는 연결을 어떻게 맺고 끊으며, 그 과정에서 생기는 상태(TIME_WAIT, 절반 폐쇄, 절반 개방)는 왜 필요한가.

| 순서 | 내용                                                                          |
| ---- | ----------------------------------------------------------------------------- |
| 1    | UDP 헤더와 체크섬(가상 헤더, 1의 보수 합)                                     |
| 2    | IP 단편화, ICMP 단편화 요구 오류, UDP를 이용한 Path MTU 발견                  |
| 3    | UDP와 ARP의 상호 작용, UDP 데이터그램의 최대 크기                             |
| 4    | TCP 서비스와 TCP 헤더(순서 번호, 확인 응답 번호, 플래그)                      |
| 5    | 연결 확립과 종료, 연결 확립 타임아웃, MSS, 절반 폐쇄                          |
| 6    | TCP 상태 전이도, TIME_WAIT, FIN_WAIT_2                                        |
| 7    | 재설정(RST) 세그먼트, 절반 개방, TIME_WAIT Assassination, 동시 개방·동시 폐쇄 |
| 8    | TCP 옵션과 TCP 서버 설계(포트, 주소 제한, 수신 연결 큐)                       |

IP 헤더의 Identification, Flags, Fragment Offset, TTL 필드와 ARP의 동작은 [IP 헤더와 서브넷, ARP 주소 변환](/memo/net-ip-arp)에서, ICMP 오류 메시지의 형식은 [ICMP와 traceroute, IP 라우팅 테이블](/memo/net-traceroute-routing)에서 다룬다. 계층별 캡슐화의 개념은 [TCP/IP 계층 모델과 캡슐화](/memo/net-tcpip-model)을 기준으로 한다.

## UDP

### UDP의 성격

UDP는 RFC 768(1980)에 정의된 데이터그램 지향(datagram-oriented) 전송 계층 프로토콜이다. 응용이 한 번 쓴 데이터는 정확히 하나의 UDP 데이터그램이 되고, 그 데이터그램은 하나의 IP 데이터그램에 담긴다. UDP는 신뢰성(reliability)을 전혀 제공하지 않는다. 응용이 보낸 데이터그램이 IP 계층까지 전달되는 것은 보장하지만, 목적지에 도착한다는 보장은 어디에도 없다.

![IP 헤더 20바이트, UDP 헤더 8바이트, UDP 데이터로 이루어진 UDP 데이터그램의 캡슐화](./images/net-udp-tcp-udp-encap.svg 'UDP 데이터그램 하나가 IP 데이터그램 하나에 담긴다')

이 단순함 때문에 UDP 응용은 최종 IP 데이터그램의 크기를 직접 고려해야 한다. 링크의 MTU(Maximum Transmission Unit)를 넘는 UDP/IP 데이터그램은 IP 계층에서 단편화(fragmentation)되고, 단편 하나만 잃어도 데이터그램 전체가 사라진다. 이 문제는 아래 IP 단편화 절에서 계산 예와 함께 다룬다.

| 비교 항목      | UDP                               | TCP                              |
| -------------- | --------------------------------- | -------------------------------- |
| 연결           | 없음                              | 3-way handshake로 확립           |
| 전달 단위      | 데이터그램(메시지 경계 유지)      | 바이트 스트림(경계 없음)         |
| 신뢰성         | 없음                              | 확인 응답, 재전송, 순서 정렬     |
| 흐름·혼잡 제어 | 없음                              | 윈도우 기반 흐름 제어, 혼잡 제어 |
| 헤더 크기      | 8바이트 고정                      | 20~60바이트                      |
| 체크섬         | IPv4에서 선택(실제로는 기본 사용) | 필수                             |
| 대표 응용      | DNS, DHCP, TFTP, RIP, 스트리밍    | HTTP, SSH, SMTP, FTP             |

### UDP 헤더

UDP 헤더는 16비트 필드 네 개, 합계 8바이트다.

![출발지 포트, 목적지 포트, UDP 길이, UDP 체크섬 네 필드와 데이터로 이루어진 UDP 헤더](./images/net-udp-tcp-header.svg 'UDP 헤더는 고정 8바이트이고 옵션이 없다')

| 필드             | 비트 | 의미                                                    |
| ---------------- | ---- | ------------------------------------------------------- |
| Source Port      | 16   | 송신 프로세스의 포트 번호(응답이 필요 없으면 0 가능)    |
| Destination Port | 16   | 수신 프로세스의 포트 번호                               |
| Length           | 16   | UDP 헤더와 데이터를 합한 바이트 수(최소 8)              |
| Checksum         | 16   | 가상 헤더, UDP 헤더, 데이터 전체에 대한 1의 보수 체크섬 |

포트 번호는 송신 프로세스와 수신 프로세스를 구별한다. TCP 포트 번호와 UDP 포트 번호는 서로 독립적이다. ==전송 계층 프로토콜이 다르면 같은 포트 번호를 동시에 사용할 수 있다.== DNS 서버가 TCP 53번과 UDP 53번을 함께 여는 구성이 그 예다. IANA는 포트 범위를 다음과 같이 나눈다.

| 구분                    | 범위        | 예                                                                   |
| ----------------------- | ----------- | -------------------------------------------------------------------- |
| Well-Known(System) 포트 | 0~1023      | FTP 20·21, SSH 22, Telnet 23, DNS 53, DHCP 67·68, HTTP 80, HTTPS 443 |
| Registered(User) 포트   | 1024~49151  | Oracle DB 1521, MySQL 3306, 원격 데스크톱 3389                       |
| Dynamic(Private) 포트   | 49152~65535 | 클라이언트가 임시로 할당받는 포트                                    |

Length 필드는 UDP 헤더와 데이터를 합한 길이다. 데이터가 비어도 되므로 최솟값은 8이다. 사실 IP 헤더의 Total Length에서 IP 헤더 길이를 빼면 UDP 데이터그램의 길이가 나오고, UDP 헤더에는 옵션도 없으므로 이 필드는 정보 측면에서 중복이다.

### UDP 체크섬

IP 헤더의 체크섬은 IP 헤더만 검사하지만, UDP 체크섬은 UDP 헤더와 데이터 전체를 검사한다. 계산 방식은 IP 체크섬과 같은 16비트 워드 단위의 1의 보수 합(one's complement sum)이지만 세 가지가 다르다.

1. IP 헤더는 언제나 4바이트의 배수라서 16비트 워드로 나누어떨어지지만, UDP 데이터그램은 홀수 바이트일 수 있다. 홀수이면 끝에 0으로 채운 패딩 바이트 하나를 덧붙여 계산한다. 패딩은 계산에만 쓰고 실제로 전송하지 않는다.
2. IP 헤더의 일부 필드로 12바이트의 가상 헤더(pseudo header)를 만들어 계산에 포함한다. 이 과정에서 UDP 길이가 두 번(가상 헤더와 UDP 헤더) 들어간다.
3. 전송된 체크섬 필드 값이 0이면 송신자가 체크섬을 계산하지 않았다는 뜻이다. 계산 결과가 정확히 0이면 모든 비트가 1인 `0xFFFF`를 대신 보낸다. 1의 보수 체계에서 둘은 같은 값이다.

![가상 헤더(출발지·목적지 IP 주소, 0, 프로토콜 17, UDP 길이), UDP 헤더, 데이터, 패딩 바이트로 이루어진 체크섬 계산 범위](./images/net-udp-tcp-checksum.svg '가상 헤더와 패딩 바이트는 체크섬 계산에만 쓰고 전송하지 않는다')

가상 헤더를 넣는 이유는 잘못된 호스트로 배달된 데이터그램을 걸러 내기 위해서다. UDP 헤더 자체에는 IP 주소가 없으므로, 라우팅 오류로 엉뚱한 호스트에 도착한 데이터그램도 UDP 헤더만 보면 멀쩡해 보인다. 체크섬에 출발지와 목적지 IP 주소, 프로토콜 번호(UDP는 17)를 섞어 두면 이런 데이터그램은 체크섬 검사에서 탈락한다.

#### 계산 예

출발지 `192.0.2.1`의 5000번 포트에서 목적지 `198.51.100.2`의 echo 포트(7)로 3바이트 문자열 `Hi!`를 보내는 경우를 직접 계산한다. UDP 길이는 `8 + 3 = 11`(0x000B)이고, 데이터가 홀수 바이트이므로 패딩 바이트 0x00을 하나 덧붙인다.

| 구분      | 16비트 워드                                      |
| --------- | ------------------------------------------------ |
| 가상 헤더 | C000, 0201, C633, 6402, 0011, 000B               |
| UDP 헤더  | 1388(5000), 0007(7), 000B(11), 0000(체크섬 자리) |
| 데이터    | 4869(`Hi`), 2100(`!` + 패딩 0x00)                |

```math
\begin{aligned}
\text{합} &= \texttt{0x26955} \\
\text{자리올림 접기} &= \texttt{0x6955} + \texttt{0x2} = \texttt{0x6957} \\
\text{체크섬} &= \lnot\,\texttt{0x6957} = \texttt{0x96A8}
\end{aligned}
```

수신 측은 체크섬 필드에 `0x96A8`이 들어간 상태로 같은 합을 구한다. 결과가 `0xFFFF`이면 오류가 없다. `0x6957 + 0x96A8 = 0xFFFF`이므로 검증을 통과한다.

<details>
<summary>1의 보수 합을 계산하는 Python 코드</summary>

```python
import socket
import struct


def internet_checksum(data: bytes) -> int:
    if len(data) % 2:
        data += b'\x00'  # 홀수 바이트면 패딩
    total = sum(struct.unpack(f'!{len(data) // 2}H', data))
    while total >> 16:  # 자리올림을 하위 16비트에 더한다
        total = (total & 0xFFFF) + (total >> 16)
    return ~total & 0xFFFF


src, dst = socket.inet_aton('192.0.2.1'), socket.inet_aton('198.51.100.2')
payload = b'Hi!'
length = 8 + len(payload)
pseudo = src + dst + struct.pack('!BBH', 0, socket.IPPROTO_UDP, length)
header = struct.pack('!HHHH', 5000, 7, length, 0)
print(hex(internet_checksum(pseudo + header + payload)))  # 0x96a8
```

`struct.unpack('!...H'){:python}`는 네트워크 바이트 순서(빅 엔디언)로 16비트 정수를 읽는다. `while` 문이 자리올림을 다시 더하는 끝자리 올림(end-around carry) 과정이다.

</details>

UDP 체크섬은 종단 간(end-to-end) 체크섬이다. 송신자와 수신자 사이의 누군가가 헤더나 데이터를 바꾸었는지 확인하며, 체크섬 오류가 난 데이터그램은 조용히 폐기되고 송신자에게 아무 통지도 가지 않는다.

RFC 768은 UDP 체크섬을 선택 사항으로 두지만, Host Requirements RFC(RFC 1122)는 체크섬 계산을 기본으로 켜 두도록 요구한다. TCP는 표준 문서 단계부터 체크섬이 필수다. 1980년대에는 속도를 위해 UDP 체크섬을 끈 구현이 있었다. 링크 계층 체크섬이 있는 LAN에서는 문제가 드러나지 않았지만, 인터넷 구간에서는 라우터 버그로 비트가 바뀌는 사례가 실제로 있었고, SLIP처럼 링크 계층 체크섬이 없는 링크도 있었다. IPv6에서는 IP 헤더에 체크섬이 없어지면서 UDP 체크섬이 필수가 되었다.

```text
1   0.0                  sun.1900 > gemini.echo: udp 9 (UDP cksum=6e90)
2   0.303755 ( 0.3038)   gemini.echo > sun.1900: udp 9 (UDP cksum=0)
3  17.392480 (17.0887)   sun.1904 > aix.echo: udp 9 (UDP cksum=6e3b)
4  17.614371 ( 0.2219)   aix.echo > sun.1904: udp 9 (UDP cksum=6e3b)
5  32.092454 (14.4781)   sun.1907 > solaris.echo: udp 9 (UDP cksum=6e74)
6  32.314378 ( 0.2219)   solaris.echo > sun.1907: udp 9 (UDP cksum=6e74)
```

2번 줄의 `cksum=0`은 응답 호스트 gemini가 UDP 체크섬을 계산하지 않았다는 뜻이다.

위 출력에서 3번과 4번, 5번과 6번 줄은 요청과 응답의 체크섬이 같다. 요청과 응답은 출발지와 목적지의 주소·포트만 서로 바뀌었을 뿐이고, 1의 보수 합은 덧셈의 교환 법칙 때문에 워드의 순서가 바뀌어도 같은 값을 낸다. 같은 이유로 이 체크섬은 16비트 워드 두 개의 위치가 뒤바뀐 오류를 탐지하지 못한다.

체크섬 오류가 실제로 얼마나 일어나는지는 40일 동안 가동한 NFS 서버의 통계[^mogul]에서 확인할 수 있다.

| 계층     | 체크섬 오류 수 | 전체 패킷 수(근사) |
| -------- | -------------- | ------------------ |
| Ethernet | 446            | 170,000,000        |
| IP       | 14             | 170,000,000        |
| UDP      | 5              | 140,000,000        |
| TCP      | 350            | 30,000,000         |

TCP는 패킷 수 대비 오류가 UDP보다 훨씬 많은데, 이 서버의 TCP 트래픽은 원거리 연결이 많았고 UDP 트래픽은 링크 계층 체크섬이 있는 근거리 구간이 대부분이었기 때문으로 해석된다. 그래도 오류는 0이 아니다. 패킷 하나를 1KB로 잡으면 1억 4천만 개는 약 140GB이고, 그 안에서 5개가 손상되어 도착했다. 체크섬을 껐다면 이 5개는 아무도 모르게 응용으로 올라갔을 것이다. 결론은 단순하다. UDP 체크섬은 켜 둔다.

> [!NOTE] NAT와 체크섬
> NAT 장비는 IP 헤더의 주소를 바꾼다. 출발지나 목적지 주소는 UDP·TCP 체크섬의 가상 헤더에 들어가므로, NAT는 IP 헤더 체크섬뿐 아니라 전송 계층 체크섬도 다시 계산해야 한다. 전체를 다시 더하지 않고 바뀐 워드의 차이만 반영하는 증분 갱신(incremental update) 방식이 RFC 1624에 정리되어 있다. 체크섬이 0인 UDP 데이터그램은 체크섬을 쓰지 않는다는 뜻이므로 NAT도 0으로 남긴다.

## IP 단편화

### 단편화와 재조합

상위 계층이 내려보낸 데이터는 원칙적으로 IP 데이터그램 하나에 담긴다. IP 단편화(IP fragmentation)는 최초 송신 호스트나 중간 라우터가 이 데이터그램을 여러 개로 나누는 과정이다. IP 데이터그램의 크기가 내보낼 링크의 MTU보다 크면 단편화가 일어나며, 경로 위의 여러 홉에서 거듭 일어날 수도 있다. 링크 계층의 MTU는 인터페이스에 질의해 얻는다.

IP 재조합(reassembly)은 단편들을 원래 데이터그램으로 되돌리는 과정이며 최종 목적지에서만 수행한다. 다음 홉에서 재조합하는 프로토콜도 있지만, IP는 중간 라우터의 부담을 줄이고 단편이 서로 다른 경로로 가도 되도록 목적지에서만 합친다. 목표는 전송 계층이 단편화를 의식하지 않도록 투명하게 나누고 합치는 데 있다.

단편화에 쓰이는 IP 헤더 필드는 다음과 같다.

| 필드            | 비트 | 단편화에서의 역할                                                                 |
| --------------- | ---- | --------------------------------------------------------------------------------- |
| Identification  | 16   | 송신자가 원래 데이터그램마다 붙이는 식별자. 단편마다 같은 값이 복사된다           |
| Flags: DF       | 1    | Don't Fragment. 설정되면 단편화하지 않고 폐기한 뒤 ICMP 오류를 보낸다             |
| Flags: MF       | 1    | More Fragments. 뒤에 단편이 더 있음을 뜻한다. 마지막 단편만 0                     |
| Fragment Offset | 13   | 이 단편의 데이터가 원래 데이터의 몇 번째 바이트부터인지를 8바이트 단위로 나타낸다 |
| Total Length    | 16   | 원래 데이터그램이 아니라 각 단편의 전체 길이                                      |

Fragment Offset이 13비트이고 8바이트 단위이므로, 마지막 단편을 제외한 모든 단편의 데이터 크기는 8의 배수여야 한다. 13비트로 표현하는 최대 오프셋은 `(2^{13} - 1) \times 8 = 65528{:math}`바이트이고, 이는 16비트 Total Length가 허용하는 최대 크기와 맞물린다.

각 단편은 자신의 IP 헤더를 가진 독립된 패킷으로 라우팅된다. 다른 경로로 가서 다른 순서로 도착할 수 있지만, Identification, 오프셋, MF 비트만 있으면 목적지에서 재조립할 수 있다.

#### 계산 예: 4000바이트 데이터를 MTU 1500 링크로 보내기

IP 헤더가 20바이트이면 한 단편에 담을 수 있는 데이터는 `1500 - 20 = 1480`바이트이고, 1480은 8의 배수(185 × 8)이므로 그대로 쓴다.

![4000바이트 데이터를 1480, 1480, 1040바이트 단편 세 개로 나눈 결과와 각 단편의 오프셋 필드 값](./images/net-udp-tcp-fragment.svg '오프셋 필드는 바이트 오프셋을 8로 나눈 값이고 마지막 단편만 MF가 0이다')

| 단편 | 데이터 바이트 범위 | 데이터 크기 | Total Length | Offset 필드 | MF  |
| ---- | ------------------ | ----------- | ------------ | ----------- | --- |
| 1    | 0~1479             | 1480        | 1500         | 0           | 1   |
| 2    | 1480~2959          | 1480        | 1500         | 185         | 1   |
| 3    | 2960~3999          | 1040        | 1060         | 370         | 0   |

세 단편의 Total Length를 더하면 4060바이트로, 원래 데이터그램(4020바이트)보다 IP 헤더 두 개분인 40바이트가 늘어난다.

### 단편화의 단점

단편 하나만 잃어도 원래 데이터그램 전체를 다시 보내야 한다. 그런데 IP에는 재전송이나 타임아웃이 없다. IP는 보낸 데이터그램을 기억하지 않으므로 재전송은 상위 계층의 책임이다. TCP라면 해당 세그먼트 전체를 다시 보내고, UDP라면 응용이 직접 처리해야 한다. 게다가 중간 라우터에서 단편화가 일어났다면 송신자는 데이터그램이 나뉘었다는 사실조차 알 수 없다. 이런 이유로 Kent와 Mogul은 1987년 논문 "Fragmentation Considered Harmful"에서 단편화를 피해야 한다고 주장했다.[^kent]

> [!WARNING] 단편화와 보안
> 단편은 첫 단편에만 UDP·TCP 헤더가 있다. 두 번째 이후 단편에는 포트 번호가 없어서, 포트 기준으로 걸러 내는 방화벽은 단편을 정확히 판단하기 어렵다. 겹치는 오프셋으로 재조합 결과를 바꾸는 공격(overlapping fragment), 재조합 버퍼를 고갈시키는 공격이 이 구조를 노린다. 방화벽과 IDS가 단편을 먼저 재조합한 뒤 검사하는 이유가 여기에 있다.

### 단편화 실험

Ethernet의 MTU는 1500바이트이므로 단편화 없이 보낼 수 있는 UDP 데이터의 최대 크기는 `1500 - 20(IP 헤더) - 8(UDP 헤더) = 1472`바이트다. UDP 데이터를 1471바이트부터 1474바이트까지 한 바이트씩 늘려 보내면 1473바이트부터 단편화가 일어난다.

![UDP 데이터 1471~1474바이트 전송의 tcpdump 출력과 1473바이트 데이터그램이 1480바이트, 1바이트 단편으로 나뉜 구조](./images/net-udp-tcp-fragment-1473.svg 'frag 26304:1480@0+는 ID 26304, 데이터 1480바이트, 오프셋 0, MF 설정이라는 뜻이다')

tcpdump의 `frag 26304:1480@0+` 표기는 Identification 26304, 이 단편의 IP 데이터 1480바이트, 오프셋 0, `+`는 MF 비트 설정을 뜻한다. 1473바이트 UDP 데이터에 UDP 헤더 8바이트를 더한 IP 데이터는 1481바이트이므로, 첫 단편에 1480바이트(UDP 헤더 8 + UDP 데이터 1472)가, 두 번째 단편에 나머지 1바이트가 들어간다(`frag 26304:1@1480`). 두 번째 단편에는 UDP 헤더가 없으므로 tcpdump도 포트 번호를 출력하지 못한다.

```text
1  23:42:43.562452  10.0.0.5.46530 > 10.0.0.3.9: udp 1471 (DF) (ttl 64, id 61350, len 1499)
2  23:42:50.267424  10.0.0.5.46531 > 10.0.0.3.9: udp 1472 (DF) (ttl 64, id 62020, len 1500)
3  23:42:57.814555  10.0.0.5 > 10.0.0.3: udp (frag 37671:1@1480) (ttl 64, len 21)
4  23:42:57.814715  10.0.0.5.46532 > 10.0.0.3.9: udp 1473 (frag 37671:1480@0+) (ttl 64, len 1500)
5  23:43:04.368677  10.0.0.5 > 10.0.0.3: udp (frag 37672:2@1480) (ttl 64, len 22)
6  23:43:04.368838  10.0.0.5.46535 > 10.0.0.3.9: udp 1474 (frag 37672:1480@0+) (ttl 64, len 1500)
```

같은 실험을 Linux에서 하면 마지막 단편이 먼저 나간다. 재조합하는 쪽은 마지막 단편의 오프셋과 길이로 원래 데이터그램의 총길이를 바로 알 수 있으므로 버퍼를 미리 할당하기 좋다. 반대로 첫 단편에만 UDP 포트 번호가 있으므로 첫 단편을 먼저 보내는 편이 낫다는 의견도 있다. 이 출력의 1번, 2번 줄에는 `(DF)`가 붙어 있다. Linux는 기본으로 Path MTU 발견을 수행하며 DF를 설정한다.

## ICMP 단편화 요구 오류와 Path MTU 발견

### ICMP 도달 불가: 단편화 필요

라우터가 MTU보다 큰 데이터그램을 받았는데 DF 비트가 설정되어 있으면, 단편화하지 않고 폐기한 뒤 송신자에게 ICMP 도달 불가(type 3) 오류의 코드 4 "fragmentation needed and DF set"을 보낸다. RFC 1191의 Path MTU 발견(Path MTU Discovery) 메커니즘은 이 오류를 이용해 경로상 가장 작은 MTU를 알아낸다.

다만 이 메커니즘이 작동하지 않는 상황도 있다. 아래 구성에서 solaris는 기본으로 DF를 설정해 600바이트 데이터의 ping을 보낸다. 실제 SLIP 링크의 MTU는 552인데, netb의 SLIP 인터페이스가 MTU를 1500으로 잘못 설정하고 있었다. netb는 단편화가 필요 없다고 판단해 600바이트 에코 요청을 그대로 내보내고, 요청은 sun을 거쳐 bsdi에 도착한다. 문제는 돌아오는 길에서 생긴다. bsdi가 보낸 에코 응답(echo reply)도 DF가 설정된 600바이트 데이터그램이므로, sun은 이를 MTU 552인 SLIP 링크로 내보내지 못하고 응답을 보낸 bsdi에게 ICMP 단편화 필요 오류를 돌려보낸다. 오류가 정작 ping을 보낸 solaris가 아니라 엉뚱한 지점에서 발생해 solaris는 응답을 받지 못한다.

![bsdi, sun, netb, solaris 사이의 SLIP 링크와 MTU 값, ICMP 에코 요청·응답과 ICMP 도달 불가(단편화 필요) 오류의 흐름](./images/net-udp-tcp-mtu-misconfig.svg 'netb의 MTU 설정이 잘못되면 단편화 필요 오류가 엉뚱한 지점에서 발생한다')

### UDP로 Path MTU 발견하기

MTU 설정이 바르면 IP는 Path MTU 발견으로 경로의 MTU를 학습할 수 있다. 아래 구성에서 solaris는 DF를 설정한 650바이트 UDP 데이터그램을 slip으로 보낸다. 경로에는 MTU 552인 SLIP 링크와 MTU 296인 SLIP 링크가 있다.

![slip, bsdi, sun, netb, solaris로 이어진 네트워크와 MTU 값, DF 비트를 설정한 650바이트 UDP 데이터그램과 ICMP 단편화 불가 오류](./images/net-udp-tcp-pmtud.svg 'tcpdump는 가운데 sun에서 실행한다')

sun에서 수집한 tcpdump 출력은 다음과 같다.

```text
 1   0.0                solaris.36196 > slip.discard: udp 650 (DF)
 2   0.004218 (0.0042)  bsdi > solaris: icmp: slip unreachable - need to frag, mtu = 0 (DF)
 3   4.980528 (4.9763)  solaris.36196 > slip.discard: udp 650 (DF)
 4   4.984503 (0.0040)  bsdi > solaris: icmp: slip unreachable - need to frag, mtu = 0 (DF)
 5   9.870407 (4.9763)  solaris.36196 > slip.discard: udp 650 (frag 47942:552@0+)
 6   9.960056 (0.0896)  solaris > slip: (frag 47942:106@552)
 7  14.940338 (4.9763)  solaris.36196 > slip.discard: udp 650 (DF)
 8  14.944466 (0.0040)  bsdi > solaris: icmp: slip unreachable - need to frag, mtu = 0 (DF)
 9  19.890015 (4.9763)  solaris.36196 > slip.discard: udp 650 (frag 47944:552@0+)
10  19.950463 (0.0604)  solaris > slip: (frag 47944:106@552)
    ...
19  44.940485 (5.0100)  solaris.36196 > slip.discard: udp 650 (DF)
20  44.944432 (0.0040)  bsdi > solaris: icmp: slip unreachable - need to frag, mtu = 0 (DF)
```

출력을 순서대로 해석한다.

1. 1~4번 줄에서 solaris는 DF가 설정된 650바이트 데이터그램을 보내고, bsdi는 ICMP 단편화 필요 오류를 돌려준다. 그런데 오류에 `mtu=0`이 적혀 있다. RFC 1191은 이 오류의 사용하지 않던 16비트 필드에 다음 홉 MTU를 담도록 정했지만, bsdi는 그 이전 구현이라 이 값을 채우지 않는다.
2. 5번 줄에서야 solaris가 학습해 552바이트 단편으로 나누어 보낸다. 다음 홉 MTU를 모르므로 Host Requirements RFC가 정한 최소 재조합 크기 576을 경로 MTU로 가정한 결과다. `mtu=0`인 상황에서 합리적인 선택이다. bsdi가 296을 알려 주도록 수정하면 solaris는 576 대신 296을 쓴다.
3. 7번 줄에서 solaris는 다시 DF를 설정해 보낸다. Solaris의 IP 계층은 학습한 경로 MTU를 30초 뒤에 폐기하고 더 큰 값을 다시 시도한다. RFC 1191은 이 주기로 10분을 권장한다.

그런데 solaris가 학습한 576은 실제 경로 MTU보다 크다. 목적지 slip에서 본 출력에서는 solaris가 보낸 552바이트 단편을 bsdi가 MTU 296인 링크에 맞추어 다시 272, 272, 8바이트로 나누었다. 오프셋 272와 544가 모두 8의 배수이고, 마지막 552부터 106바이트는 solaris가 보낸 두 번째 단편이다. 데이터 합은 `272 + 272 + 8 + 106 = 658`로, UDP 헤더 8바이트와 데이터 650바이트의 합과 같다.

정리하면 Path MTU 발견 메커니즘이 있으면 UDP에서도 단편화 문제를 피해 데이터를 전송할 수 있다. 그러나 학습 중에 버려진 데이터그램은 응용이 직접 재전송해야 하고, 학습한 경로 MTU는 타임아웃으로 사라질 수 있다는 점을 UDP 응용이 세심히 고려해야 한다.

> [!TIP] PMTUD 블랙홀
> 방화벽이 ICMP를 일괄 차단하면 단편화 필요 오류가 송신자에게 돌아오지 못한다. 송신자는 DF를 설정한 큰 패킷을 계속 보내고 라우터는 계속 폐기하므로, 작은 패킷(연결 설정)은 통과하지만 큰 패킷(본문 전송)부터 멈추는 증상이 나타난다. ICMP 도달 불가의 코드 4는 차단 목록에서 빼야 한다. 이 문제를 피하려고 ICMP에 의존하지 않고 패킷 크기를 늘려 가며 탐색하는 방식(PLPMTUD, RFC 4821)도 있다.

## UDP와 ARP의 상호 작용

어떤 구현(bsdi)은 단편마다 ARP 요청을 따로 만든다. 목적지의 MAC 주소를 아직 모르는 상태에서 단편 여섯 개를 연속으로 보내면 같은 IP 주소를 묻는 ARP 요청이 여섯 번 나간다. RFC 1122는 이런 ARP 플러딩(같은 IP 주소에 대한 ARP 요청을 빠르게 반복하는 것)을 막기 위해 목적지마다 1초에 요청 하나만 보내도록 권고한다.

또 RFC 1122는 ARP 응답을 기다리는 동안 같은 목적지로 가는 패킷이 여러 개 도착하면 적어도 하나는 보관하도록(SHOULD) 요구한다. 대부분의 구현은 가장 마지막 패킷 하나만 보관한다. 버퍼가 하나라는 뜻이다. 두 동작이 겹치면 문제가 커진다. 단편들이 ARP 응답 전에 모두 도착하면 마지막 단편만 남고 나머지는 폐기되며, 목적지는 단편 하나만으로는 재조합할 수 없어 결국 데이터그램 전체를 잃는다. 이 현상은 Linux에서는 관찰되지 않았다고 보고된다. 다만 코드 분석이 아니라 실험으로 얻은 결과다.

## UDP 데이터그램의 최대 크기

IPv4 헤더의 Total Length 필드는 16비트이므로 IP 데이터그램의 최대 크기는 65,535바이트다. 따라서 UDP 데이터의 이론상 최대 크기는 다음과 같다.

```math
65535 - 20\ (\text{IP 헤더 최소}) - 8\ (\text{UDP 헤더}) = 65507\ \text{바이트}
```

IPv6에는 Total Length가 없고 IPv6 기본 헤더(40바이트)를 제외한 길이를 나타내는 16비트 Payload Length가 있다. 확장 헤더가 없다면 UDP 데이터의 최대 크기는 `65535 - 8 = 65527`바이트다. 이보다 큰 데이터그램을 보내는 점보그램(jumbogram, RFC 2675)은 쓰지 않는다고 가정한 값이다.

실제로 이론상 최대 크기로 보내는 일은 거의 없다. 이유는 두 가지다.

1. 구현의 한계. 소켓 API는 송신·수신 버퍼 크기를 정하는 옵션(`SO_SNDBUF`, `SO_RCVBUF`)을 제공하며, 이 크기가 응용이 읽고 쓸 수 있는 UDP 데이터그램의 최대 크기를 결정한다. 기본값이 최대 IP 데이터그램 크기보다 작은 구현도 있다.
2. 수신 측의 한계. 호스트는 최소 576바이트의 IP 데이터그램을 받을 수 있어야 한다. 바꾸어 말하면 576바이트를 넘는 데이터그램을 받지 못하는 호스트가 있을 수 있다. 그래서 DNS, DHCP 같은 많은 UDP 응용은 응용 데이터를 512바이트 이하로 제한한다.

> [!NOTE] 데이터그램 절단
> 수신 응용이 준비한 버퍼보다 큰 UDP 데이터그램이 도착하면 대부분의 구현은 넘치는 부분을 잘라 버린다(datagram truncation). 남은 부분을 다음 `read()`에서 돌려주는 구현, 잘린 양을 알려 주는 구현, 잘렸다는 사실만 알려 주는 구현이 섞여 있다. Linux의 `recvmsg(){:c}`는 잘린 경우 `MSG_TRUNC` 플래그를 설정한다. UDP 응용은 예상 최대 크기보다 넉넉한 버퍼를 준비해야 한다.

UDP가 응용에 제공하는 서비스는 결국 포트 번호와 선택적인 체크섬뿐이다. ICMP 도달 불가 오류는 Path MTU 발견에 쓰이고, 단편화는 ARP와 맞물리면 데이터그램 전체를 잃는 원인이 될 수 있다. 신뢰성이 필요하면 응용이 직접 만들거나 TCP를 쓴다.

## TCP 서비스

### 연결 지향, 신뢰성, 바이트 스트림

TCP의 사양은 RFC 793(1981)에 처음 정의되었고, 몇 가지 오류 수정과 추가 요구 사항(예: 혼잡 제어 알고리즘)은 RFC 1122에서 보완되었다. 2022년에는 그동안의 수정 사항을 통합한 RFC 9293이 RFC 793을 대체했다.

TCP는 UDP와 같은 IP를 사용하지만 응용 계층에 전혀 다른 서비스를 제공한다. 한 문장으로 요약하면 ==TCP provides a connection-oriented, reliable, byte stream service.== 세 단어가 각각 하나의 서비스다.

연결 지향(connection-oriented)은 두 응용 프로세스(보통 클라이언트와 서버)가 데이터를 주고받기 전에 TCP 연결을 먼저 확립한다는 뜻이다. 전화를 걸면 "여보세요"를 주고받아 서로 준비되었음을 확인한 뒤 용건을 말하는 것과 같다. 이 확인 과정이 3-way handshake다.

신뢰성(reliability)은 다음 일곱 가지 동작으로 만든다.

| 번호 | 동작                                                                                                                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | 응용 데이터를 TCP가 전송하기 적합한 크기의 세그먼트(segment)로 나누어 IP로 보낸다. UDP는 응용이 쓴 크기 그대로 보낸다                |
| 2    | 세그먼트마다 타이머를 설정하고, 확인 응답(ACK)이 오지 않으면 재전송한다                                                              |
| 3    | 데이터를 받으면 확인 응답을 보낸다. 보통 짧은 시간(지연 ACK, 최대 0.5초 이내) 지연한 뒤 보낸다                                       |
| 4    | 헤더와 데이터 전체에 대한 종단 간 체크섬을 계산한다. 오류가 난 세그먼트는 버리고 ACK를 보내지 않는다                                 |
| 5    | IP 데이터그램은 순서가 바뀌어 도착할 수 있으므로, 수신 측 TCP가 재정렬해 올바른 순서로 응용에 넘긴다                                 |
| 6    | IP 단계에서 중복된 데이터는 수신 측 TCP가 폐기한다                                                                                   |
| 7    | 흐름 제어(flow control). 수신 측의 빈 버퍼 공간만큼만 송신 측이 보내도록 해서, 빠른 송신자가 느린 수신자의 버퍼를 넘치게 하지 않는다 |

![IP 헤더 20바이트, TCP 헤더 20바이트, TCP 데이터로 이루어진 TCP 세그먼트의 캡슐화](./images/net-udp-tcp-tcp-encap.svg 'TCP 헤더는 옵션이 없으면 20바이트, 최대 60바이트다')

바이트 스트림(byte stream)은 양방향으로 8비트 바이트의 흐름을 주고받는다는 뜻이다. 입력 스트림과 출력 스트림은 서로 독립된 full-duplex 서비스다. TCP는 레코드 구분자를 전혀 넣지 않는다. 송신 응용이 10바이트, 20바이트, 30바이트를 세 번 써도 수신 응용은 60바이트를 한 번에 읽을 수도, 1바이트씩 60번 읽을 수도 있다. 메시지 경계가 필요하면 응용이 길이 필드나 구분 문자를 직접 넣어야 한다. TCP는 바이트의 내용을 전혀 해석하지 않는다.

> [!NOTE] 혼잡 제어는 왜 세 서비스에 없는가
> Kurose와 Ross는 혼잡 제어를 "호출한 응용에 제공하는 서비스라기보다 인터넷 전체를 위한 서비스, 공공의 이익을 위한 서비스"라고 설명한다. 또 세 서비스는 RFC 793(1981)에 정해진 것이고, 그 시절 TCP에는 혼잡 제어가 없었다. 혼잡 제어는 1986년 인터넷 혼잡 붕괴 이후 Van Jacobson의 알고리즘으로 도입되었다.

### 포트 번호와 소켓 쌍

포트 번호는 TCP 세그먼트를 보내고 받는 응용을 구분한다. IP 주소 하나와 포트 번호 하나의 조합을 소켓(socket)이라 하고, 클라이언트와 서버의 두 소켓을 묶은 것을 소켓 쌍(socket pair)이라 한다. 소켓 쌍, 즉 `(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)`의 4-tuple은 인터넷에서 TCP 연결 하나를 유일하게 식별한다. 웹 서버가 80번 포트 하나로 수천 개의 연결을 동시에 처리할 수 있는 이유가 여기에 있다. 서버 쪽 소켓은 같아도 클라이언트 쪽 IP나 포트가 달라 소켓 쌍이 모두 다르다.

### 순서 번호와 확인 응답 번호

순서 번호(sequence number)는 송신 TCP에서 수신 TCP로 가는 데이터 스트림의 바이트마다 붙는 번호다. 바이트 단위로 주소가 붙은 메모리로 생각하면 이해하기 쉽다. 32비트 부호 없는 정수라 `2^{32} - 1{:math}`을 넘으면 0으로 돌아간다.

새 연결을 확립하면서 SYN 플래그를 설정한 세그먼트의 순서 번호 필드에는 호스트가 이 연결에 고른 초기 순서 번호(ISN, Initial Sequence Number)를 기록한다. SYN 플래그는 순서 번호를 1 소비한다. 그래서 송신 측의 첫 데이터 바이트 번호는 ISN + 1이다. FIN도 마찬가지로 1을 소비한다.

확인 응답 번호(acknowledgment number)는 수신한 마지막 바이트의 순서 번호에 1을 더한 값, 즉 다음에 받기를 기대하는 첫 바이트의 순서 번호다. ACK 플래그가 설정된 세그먼트에서만 유효하며, 연결이 확립된 뒤에는 모든 세그먼트에 ACK 플래그가 설정된다.

TCP는 full-duplex이므로 각 종단은 방향마다 순서 번호를 따로 관리한다. 또 TCP는 누적 확인 응답(cumulative ACK)만 쓰는 슬라이딩 윈도우 프로토콜이다. 확인 응답 번호는 "여기까지는 빠짐없이 받았다"만 알릴 수 있어서, 순서보다 먼저 도착한 세그먼트나 손상된 세그먼트에 대한 정보는 전달할 수 없다. 선택적 확인 응답(SACK)은 나중에 옵션으로 추가되었다(RFC 2018). 부정 확인 응답(NACK)은 TCP에 없다.

#### 계산 예: 핸드셰이크와 데이터 교환의 번호

클라이언트의 ISN을 100, 서버의 ISN을 2000으로 놓고 연결을 맺은 뒤 클라이언트가 100바이트를 보내는 과정을 계산한다.

![SYN, SYN+ACK, ACK, PSH+ACK 100바이트, ACK 다섯 세그먼트의 순서 번호와 확인 응답 번호](./images/net-udp-tcp-seq.svg 'SYN은 1을 소비하고, 데이터는 길이만큼 소비한다')

| 순서 | 방향              | 플래그  | Seq  | Ack  | 데이터 | 계산                      |
| ---- | ----------------- | ------- | ---- | ---- | ------ | ------------------------- |
| 1    | 클라이언트 → 서버 | SYN     | 100  | 0    | 0      | 클라이언트 ISN            |
| 2    | 서버 → 클라이언트 | SYN+ACK | 2000 | 101  | 0      | 서버 ISN, 100 + 1(SYN)    |
| 3    | 클라이언트 → 서버 | ACK     | 101  | 2001 | 0      | 2000 + 1(SYN)             |
| 4    | 클라이언트 → 서버 | PSH+ACK | 101  | 2001 | 100    | 데이터는 101~200번 바이트 |
| 5    | 서버 → 클라이언트 | ACK     | 2001 | 201  | 0      | 101 + 100                 |

3번과 4번은 Seq와 Ack가 같다. 3번 ACK는 데이터가 없어서 순서 번호를 소비하지 않기 때문이다. 규칙으로 정리하면 다음과 같다. 같은 쪽이 연이어 보내면 Seq는 앞 세그먼트의 Seq + 데이터 길이(SYN·FIN은 1)이고, 상대에게 답하는 세그먼트의 Ack는 받은 Seq + 받은 데이터 길이다.

### 헤더 길이와 플래그

4비트 헤더 길이 필드는 헤더 길이를 32비트 워드 단위로 나타낸다. 옵션 때문에 헤더 길이가 변하므로 필요하다. 최댓값 15는 `15 \times 4 = 60{:math}`바이트이므로 헤더는 60바이트, 옵션은 40바이트로 제한된다. 옵션이 없는 일반적인 경우 값은 5(20바이트)다.

| 플래그 | 의미                                                 |
| ------ | ---------------------------------------------------- |
| URG    | 긴급 포인터가 유효하다                               |
| ACK    | 확인 응답 번호가 유효하다                            |
| PSH    | 수신 측은 이 데이터를 가능한 한 빨리 응용으로 넘긴다 |
| RST    | 연결을 재설정한다                                    |
| SYN    | 연결을 초기화하기 위해 순서 번호를 동기화한다        |
| FIN    | 송신 측이 데이터 전송을 마쳤다                       |

16비트 윈도우 크기는 확인 응답 번호부터 수신 측이 더 받을 수 있는 바이트 수이며, 흐름 제어의 핵심이다. 최댓값이 65,535바이트로 제한되므로 고속 장거리 링크를 위해 윈도우 스케일 옵션이 추가되었다.

### 체크섬과 긴급 포인터

TCP 체크섬은 TCP 헤더와 데이터 모두를 대상으로 하며 필수 필드다. 송신 측이 계산해 기록하고 수신 측이 검사하며, UDP 체크섬과 같은 가상 헤더(프로토콜 번호만 6)를 이용한다.

긴급 포인터(urgent pointer)는 URG 플래그가 설정되었을 때만 유효하며, 이 세그먼트의 순서 번호에 더하면 긴급 데이터의 끝을 가리키는 양수 오프셋이다. 송신 측이 상대에게 긴급한 데이터를 알리는 수단이지만, 구현마다 해석이 달라서 요즘은 거의 쓰이지 않는다. RFC 6093은 새 응용에서 사용하지 말 것을 권고한다. 오히려 IDS와 종단 호스트의 해석 차이를 이용한 탐지 회피에 쓰일 수 있다.

### 3-way handshake

연결 확립 절차는 다음과 같다.

1. 요청하는 종단(클라이언트)이 접속할 서버의 포트 번호와 클라이언트의 ISN을 담은 SYN 세그먼트를 보낸다. 이 종단은 능동 개방(active open)을 수행한다.
2. 서버는 자신의 ISN을 담은 SYN 세그먼트로 응답하면서, 클라이언트 ISN + 1을 ACK로 보내 클라이언트의 SYN을 확인한다. 서버는 수동 개방(passive open)을 수행한다.
3. 클라이언트는 서버 ISN + 1을 ACK로 보내 서버의 SYN을 확인한다.

세그먼트 세 개로 연결이 확립되므로 이 과정을 3-way handshake라 부른다. 두 번이 아니라 세 번인 이유는 양쪽 모두 자신의 ISN을 보내고 상대로부터 확인받아야 하기 때문이다. SYN+ACK는 서버의 SYN과 클라이언트 SYN에 대한 ACK를 한 세그먼트에 합친 것이다.

> [!IMPORTANT] ISN은 예측할 수 없어야 한다
> RFC 793은 ISN을 4마이크로초마다 1씩 증가하는 32비트 시계로 고르도록 했다. 이 방식은 이전 연결의 지연된 세그먼트와 번호가 겹치지 않게 하는 데 목적이 있었지만, ISN을 예측할 수 있게 만든다. 공격자가 ISN을 맞히면 상대의 응답을 보지 않고도 위조한 출발지 주소로 연결을 완성하거나 기존 연결에 세그먼트를 끼워 넣을 수 있다. 현재 구현은 RFC 6528에 따라 4-tuple과 비밀 키의 해시 값에 시계를 더해 ISN을 만든다. 이 공격은 [TCP 공격](/memo/net-tcp-attacks)에서 자세히 다룬다.

### 연결 종료

연결을 확립하는 데는 세그먼트 3개가 필요하지만 종료하는 데는 4개가 필요하다. TCP 연결은 full-duplex라서 방향마다 따로 닫아야 하기 때문이다.

1. 능동 폐쇄(active close). 클라이언트 응용이 `close(){:c}`를 호출해 더 보낼 데이터가 없다고 선언하면, TCP는 그 전에 맡겨진 데이터를 모두 보낸 뒤 FIN을 보낸다.
2. 수동 폐쇄(passive close). 서버 TCP는 앞의 데이터를 모두 받고 FIN을 수신하면 응용에 EOF(end-of-file)를 전달하고, FIN의 순서 번호 + 1로 ACK를 보낸다.
3. 서버 응용은 `read(){:c}`가 EOF를 반환하면 보통 `close(){:c}`를 호출하도록 작성되어 있다. 이때 서버도 FIN을 보낸다.
4. 클라이언트는 FIN을 받으면 FIN의 순서 번호 + 1로 ACK를 보낸다.

클라이언트와 서버의 역할이 바뀌어도 문제가 없다. 다만 요청과 응답으로 이루어진 응용에서는 클라이언트가 먼저 닫는 경우가 많다. 서버가 2번 ACK와 3번 FIN을 한 세그먼트로 합쳐 보내면 종료도 세 세그먼트로 끝난다.

### 연결 확립 타임아웃

서버 호스트가 꺼져 있으면 SYN에 아무 응답도 오지 않는다. 이 경우 클라이언트 TCP는 SYN을 재전송한다. 예시 출력에서 첫 SYN 후 5.8초 뒤에 두 번째 SYN을, 다시 24초 뒤에 세 번째 SYN을 보냈다. 간격이 점점 늘어나는 지수 백오프(exponential backoff)다. 버클리 계열 구현은 최대 75초 동안 연결을 시도한 뒤 포기한다. Linux는 `net.ipv4.tcp_syn_retries`(기본 6회)로 재시도 횟수를 정하며, 1초부터 두 배씩 늘어나는 간격으로 약 2분 동안 시도한다.

이 출력의 SYN에는 `[tos 0x10]`이 붙어 있다. IP 헤더의 서비스 유형(TOS) 필드에서 최소 지연(minimize delay) 비트를 설정한 값으로, telnet이나 rlogin 같은 대화형 응용이 지연을 줄이기 위해 설정한다.

### 최대 세그먼트 크기

MSS(Maximum Segment Size)는 TCP가 상대에게 한 번에 보낼 수 있는 데이터의 최대 크기다. 연결 확립 과정에서 각 종단은 SYN 세그먼트의 MSS 옵션으로 자신이 받기를 원하는 MSS를 알린다.

```math
\text{MSS} = \text{MTU} - \text{IP 헤더}(20) - \text{TCP 헤더}(20)
```

Ethernet(MTU 1500)이면 1460바이트, IEEE 802.3 캡슐화(MTU 1492)이면 1452바이트다. 상대가 MSS를 알리지 않으면 기본값 536바이트(576 − 40)를 쓴다.

![slip과 bsdi 사이는 MTU 296인 SLIP 링크, bsdi와 sun 사이는 MTU 1500인 이더넷이고, sun은 SYN에 mss 1460을, slip은 SYN+ACK에 mss 256을 알린다](./images/net-udp-tcp-mss.svg 'MSS는 협상이 아니라 각자 받을 수 있는 크기를 알리는 값이다')

```text
1  0.0          sun.1093 > slip.discard: S 517312000:517312000(0) <mss 1460>
2  0.10 (0.00)  slip.discard > sun.1093: S 509556225:509556225(0) ack 517312001 <mss 256>
3  0.10 (0.00)  sun.1093 > slip.discard: . ack 1
```

sun은 MSS로 1460을 알렸지만 slip은 MTU 296인 SLIP 링크에 맞추어 256(296 − 40)을 알렸다. 따라서 sun은 slip에게 256바이트보다 큰 세그먼트를 보내지 않는다. MSS는 양 끝의 링크만 반영하므로, 중간 라우터의 MTU가 더 작으면 여전히 단편화가 발생한다. TCP는 이 문제를 Path MTU 발견으로 해결하며, Linux는 TCP 세그먼트에 기본으로 DF를 설정한다.

### TCP 절반 폐쇄

절반 폐쇄(half-close)는 한쪽 종단이 데이터 출력을 끝낸 뒤에도 상대로부터 데이터를 계속 받을 수 있는 기능이다. BSD 소켓 API에서 응용은 `close(){:c}` 대신 두 번째 인자를 1(`SHUT_WR`)로 준 `shutdown(){:c}`을 호출해 절반 폐쇄를 수행한다.

![클라이언트가 shutdown으로 FIN을 보낸 뒤에도 서버의 데이터를 read로 받고, 서버가 close하면 FIN과 ACK로 연결이 끝나는 세그먼트 흐름](./images/net-udp-tcp-half-close.svg '클라이언트는 FIN을 보낸 뒤에도 read로 서버의 데이터를 받는다')

> [!CAUTION] close()는 절반 폐쇄가 아니다
> `close(){:c}`는 송신과 수신을 모두 닫는다. 클라이언트가 `close(){:c}`를 호출한 뒤 서버가 데이터를 보내면 클라이언트 TCP는 받을 응용이 없으므로 RST로 응답하고 데이터는 전달되지 않는다. 데이터를 다 보냈다는 신호만 주고 응답은 계속 받아야 한다면 `shutdown(fd, SHUT_WR){:c}`을 써야 한다. 절반 폐쇄가 있어도 많은 응용은 종료 시 `close(){:c}`로 양방향을 한 번에 닫는다.

절반 폐쇄가 필요한 대표적인 예는 원격 정렬이다. sun에서 `rsh bsdi sort < datafile`을 실행하면 datafile의 내용이 TCP 연결을 통해 bsdi의 `sort` 프로그램으로 전달된다.

![호스트 sun의 rsh가 데이터 파일을 표준 입력으로 읽어 TCP 연결로 호스트 bsdi의 sort에 전달하고 정렬 결과를 표준 출력인 터미널로 받는 구조](./images/net-udp-tcp-rsh.svg 'sort는 입력의 끝(EOF)을 받아야 정렬을 시작할 수 있다')

`sort`는 입력을 끝까지 읽어야 정렬 결과를 낼 수 있다. sun의 rsh 클라이언트는 datafile의 끝에 도달하면 절반 폐쇄로 FIN을 보내고, bsdi의 `sort`는 EOF를 받아 정렬한 결과를 같은 연결로 sun에 돌려준다. 결과를 모두 보낸 bsdi가 연결을 닫으면 종료가 끝난다. 절반 폐쇄가 없다면 입력이 끝났음을 알리기 위해 응용 수준의 별도 표시가 필요하다.

## TCP 상태 전이도

TCP의 동작은 상태 11개와 그 사이의 전이로 표현된다. 전이마다 원인(응용 동작 appl 또는 세그먼트 수신 recv)과 결과(보내는 세그먼트 send)가 붙는다.

![CLOSED, LISTEN, SYN-RCVD, SYN-SENT, ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSING, TIME-WAIT, CLOSE-WAIT, LAST-ACK 상태와 전이](./images/net-udp-tcp-state-diagram.svg '파란 실선은 클라이언트의 일반적인 전이, 빨간 점선은 서버의 일반적인 전이다')

| 상태        | 의미                                                 |
| ----------- | ---------------------------------------------------- |
| CLOSED      | 연결 없음                                            |
| LISTEN      | 서버가 연결 요청을 기다림(수동 개방)                 |
| SYN-SENT    | SYN을 보내고 SYN+ACK를 기다림(능동 개방)             |
| SYN-RCVD    | SYN을 받고 SYN+ACK를 보낸 뒤 ACK를 기다림            |
| ESTABLISHED | 연결 확립, 데이터 전송 상태                          |
| FIN-WAIT-1  | 능동 폐쇄로 FIN을 보내고 ACK를 기다림                |
| FIN-WAIT-2  | 내 FIN은 확인받았고 상대의 FIN을 기다림              |
| CLOSE-WAIT  | 상대 FIN을 받음, 응용의 `close(){:c}` 호출을 기다림  |
| LAST-ACK    | 수동 폐쇄 쪽이 FIN을 보내고 마지막 ACK를 기다림      |
| CLOSING     | 양쪽이 동시에 FIN을 보낸 경우, 내 FIN의 ACK를 기다림 |
| TIME-WAIT   | 능동 폐쇄 쪽이 마지막 ACK를 보낸 뒤 2MSL 동안 대기   |

클라이언트가 먼저 능동 폐쇄한다고 가정하면, 일반적인 연결 확립과 종료에서 두 종단은 다음 상태를 거친다.

![클라이언트와 서버가 SYN J, SYN K ack J+1, ack K+1, FIN M, ack M+1, FIN N, ack N+1을 주고받으며 바뀌는 상태](./images/net-udp-tcp-open-close-states.svg '능동 폐쇄한 쪽만 TIME_WAIT를 거친다')

### TIME_WAIT 상태

TIME_WAIT 상태는 2MSL 대기 상태라고도 한다. MSL(Maximum Segment Lifetime)은 세그먼트가 네트워크에 존재할 수 있는 최대 시간이다. RFC 793은 MSL을 2분으로 정했지만 구현은 30초, 1분, 2분 등 다른 값을 쓴다. IP 헤더의 TTL도 패킷의 수명을 제한하지만, 그 단위는 실제 시간이 아니라 홉 수라는 점에 주의한다.

TCP가 능동 폐쇄를 수행하고 마지막 ACK를 보내면 그 연결은 2MSL 동안 TIME_WAIT 상태에 머문다. 이 기간에는 같은 소켓 쌍으로 연결을 다시 만들 수 없다. 이유는 두 가지다.

1. 마지막 ACK가 손실될 수 있다. 그러면 상대는 FIN을 재전송하고, TIME_WAIT 상태의 종단은 ACK를 다시 보내야 한다. 이미 CLOSED라면 RST로 응답해 상대 응용에 오류가 전달된다.
2. 이전 연결의 지연된 세그먼트가 같은 소켓 쌍의 새 연결에 섞이는 것을 막는다. 2MSL을 기다리면 양방향의 옛 세그먼트가 모두 네트워크에서 사라지며, TIME_WAIT 동안 도착한 세그먼트는 폐기한다.

==TIME_WAIT은 능동 폐쇄한 쪽에만 생긴다.== 서버가 먼저 닫으면 서버에 TIME_WAIT이 쌓이고, 이 상태가 서버 운영에 문제를 일으킨다. 서버를 갑자기 종료하고 재시작하면 서버는 능동 폐쇄한 쪽이 되므로, 잘 알려진 포트를 최대 4분(MSL 2분 기준) 동안 다시 쓰지 못한다.

TCP 표준은 같은 연결(소켓 쌍)의 재사용만 막지만, BSD와 이를 따른 구현은 로컬 포트 번호 자체의 재사용을 막는다. 아래 예는 서버를 실행하고 클라이언트를 연결한 뒤 서버를 종료(`^?`)하고 바로 재시작한 결과다.

```text
sun % sock -v -s 6666
connection on from ... (클라이언트 bsdi의 1081번 포트)
^?
sun % sock -s 6666
can't bind local address: Address already in use
sun % netstat
Proto Recv-Q Send-Q  Local Address    Foreign Address   (state)
tcp        0      0  sun.6666         bsdi.1081         TIME_WAIT
```

클라이언트도 마찬가지다. 클라이언트는 보통 임시 포트를 쓰므로 문제가 드러나지 않지만, 방금 TIME_WAIT에 들어간 로컬 포트 1162를 `-b1162`로 지정해 다시 연결하려 하면 같은 `Address already in use` 오류가 난다.

`SO_REUSEADDR` 소켓 옵션을 설정하면 TIME_WAIT 상태인 포트에 다시 `bind(){:c}`할 수 있다. 서버 프로그램이 이 옵션을 거의 항상 켜는 이유다. 다만 이 옵션은 포트 재사용을 허용할 뿐이고, 같은 소켓 쌍의 연결 재사용은 원래 TCP 표준에서 허용하지 않았다. 이후 RFC 1122는 새 SYN의 ISN이 이전 연결의 마지막 순서 번호보다 크면, RFC 6191은 타임스탬프 옵션으로 옛 세그먼트를 구별할 수 있으면 TIME_WAIT 상태의 연결을 재사용하도록 허용했다.

```bash
# 소켓 상태별 연결 수 조회 (Linux)
ss -tan | awk 'NR > 1 {print $1}' | sort | uniq -c
# TIME-WAIT 상태 연결만 조회
ss -tan state time-wait
```

> [!NOTE] Quiet time
> TIME_WAIT 상태의 호스트가 재부팅되면 2MSL 상태 정보가 사라진다. RFC 793은 이 경우 재부팅 후 MSL 동안 새 연결을 만들지 않도록 권고한다. 이를 quiet time이라 한다. 다만 재부팅 자체가 보통 MSL보다 오래 걸리므로 이 권고를 따르는 구현은 드물다.

### FIN_WAIT_2 상태

능동 폐쇄한 쪽은 자신의 FIN을 확인받으면 FIN_WAIT_2 상태에서 상대의 FIN을 기다린다. 상대가 끝내 FIN을 보내지 않으면 연결은 영원히 이 상태에 머문다. 절반 폐쇄를 허용하려면 정당한 동작이지만, 상대 응용이 `close(){:c}`를 잊었거나 호스트가 사라졌다면 자원이 낭비된다.

그래서 BSD 계열 구현은 응용이 `close(){:c}`로 완전히 닫은 경우(더는 받을 응용이 없는 경우)에 한해 타이머를 설정하고, 연결이 일정 시간 휴지 상태이면 CLOSED로 옮긴다. Linux에서는 `net.ipv4.tcp_fin_timeout`(기본 60초)이 이 시간이다. 표준에 없는 동작이지만 현실적인 절충이다.

## 재설정(RST) 세그먼트

RST 플래그가 설정된 세그먼트를 재설정 세그먼트라 한다. TCP는 참조 연결(reference connection, 4-tuple로 지정되는 연결)에 대해 올바르지 않은 세그먼트가 도착하면 RST를 보낸다.

### 존재하지 않는 포트에 대한 연결 요청

연결 요청이 목적지 호스트에 도착했지만 목적지 포트에 LISTEN 중인 프로세스가 없으면 RST로 응답한다. UDP에서 같은 상황이면 ICMP 포트 도달 불가 오류가 돌아오지만, TCP는 RST를 쓴다.

```text
1  0.0       bsdi.1087 > svr4.20000: S 297416193:297416193(0) win 4096 <mss 1024>
2  0.003771  svr4.20000 > bsdi.1087: R 0:0(0) ack 297416194 win 0
```

RST 세그먼트의 순서 번호는 0이고, 확인 응답 번호는 받은 SYN의 ISN + 1이다. 클라이언트 응용은 `Connection refused` 오류를 받는다.

> [!TIP] 포트 스캐닝과의 관계
> 열린 포트는 SYN에 SYN+ACK로, 닫힌 포트는 RST로, 방화벽에 막힌 포트는 무응답이나 ICMP 오류로 응답한다. nmap의 SYN 스캔은 이 차이로 포트 상태를 판별한다. 방화벽이 닫힌 포트에 RST 대신 무응답을 택하는 이유는 공격자가 호스트의 존재와 정책을 추론하기 어렵게 만들기 위해서다.

### 연결 중단

연결을 끝내는 방법은 두 가지다.

| 방법                        | 동작                          | 데이터                                                   |
| --------------------------- | ----------------------------- | -------------------------------------------------------- |
| 정규 해제(orderly release)  | FIN을 보내 종료               | 대기 중인 데이터를 모두 보낸 뒤 FIN을 보내므로 손실 없음 |
| 중단 해제(abortive release) | FIN 대신 RST를 보내 즉시 중단 | 대기 중인 데이터를 바로 폐기                             |

연결 중단으로 응용이 얻는 이점은 두 가지다. 대기 중인 데이터를 즉시 버리고 바로 RST를 보낼 수 있고, RST를 받은 쪽 TCP는 상대가 연결을 정상 종료가 아니라 중단했다는 사실을 응용에 알릴 수 있다. 따라서 소켓 API는 응용이 연결을 중단할 수단을 제공해야 하며, BSD 소켓에서는 `SO_LINGER` 옵션이 그 수단이다. linger 시간을 0으로 설정하고 `close(){:c}`하면 FIN 대신 RST가 나간다.

```text
bsdi % sock -L0 svr4 8888        svr4 % sock -s 8888
hello, world                     hello, world
^D                               read error: connection reset by peer
```

```text
1  0.0                bsdi.1099 > svr4.8888: S 671112193:671112193(0) <mss 1024>
2  0.004975 (0.0050)  svr4.8888 > bsdi.1099: S 322495489:322495489(0) ack 671112194 <mss 1024>
3  0.006656 (0.0017)  bsdi.1099 > svr4.8888: . ack 1
4  4.833024 (4.8263)  bsdi.1099 > svr4.8888: P 1:14(13) ack 1
5  5.026224 (0.1932)  svr4.8888 > bsdi.1099: . ack 14
6  9.527634 (4.5014)  bsdi.1099 > svr4.8888: R 14:14(0) ack 1
```

1~3번이 연결 확립, 4~5번이 `hello, world` 전송이다. 클라이언트에서 EOF를 입력하자 6번 세그먼트로 FIN이 아니라 R(RST)이 나가고, 서버는 `connection reset by peer`를 받는다.

```c
struct linger lg = { .l_onoff = 1, .l_linger = 0 };
setsockopt(fd, SOL_SOCKET, SO_LINGER, &lg, sizeof lg);
close(fd); /* FIN 대신 RST를 보내고 송신 버퍼를 폐기한다 */
```

RST 세그먼트에는 ACK 응답이 오지 않는다. RST를 받은 쪽은 연결을 즉시 정리하고, 서버 응용은 `read(){:c}`에서 `ECONNRESET`(connection reset by peer) 오류를 받는다.

### 절반 개방 연결

절반 개방(half-open)은 한쪽 호스트가 상대에게 알리지 않고 연결을 닫거나 중단한 상태다. 호스트가 고장 나거나 재부팅되면 이런 상태가 생긴다. 상대가 데이터를 보내지 않는 한, 남은 쪽은 연결이 이미 사라졌다는 사실을 알 수 없다. 남은 쪽이 절반 개방 연결로 세그먼트를 보내면, 재부팅된 호스트의 TCP는 그 연결을 모르므로 RST로 응답해야 한다.

```text
1    0.0                   bsdi.1102 > svr4.discard: S 1591752193:1591752193(0)
2    0.004811 (0.0048)     svr4.discard > bsdi.1102: S 26368001:26368001(0) ack 1591752194
3    0.006516 (0.0017)     bsdi.1102 > svr4.discard: . ack 1
4    5.167679 (5.1612)     bsdi.1102 > svr4.discard: P 1:11(10) ack 1
5    5.201662 (0.0340)     svr4.discard > bsdi.1102: . ack 11
6  194.909929 (189.7083)   bsdi.1102 > svr4.discard: P 11:25(14) ack 1
7  194.914957 (0.0050)     arp who-has bsdi tell svr4
8  194.915678 (0.0007)     arp reply bsdi is-at 0:0:c0:6f:2d:40
9  194.918225 (0.0025)     svr4.discard > bsdi.1102: R 26368002:26368002(0)
```

1~3번이 연결 확립, 4~5번이 `hi there` 전송, 6번이 서버 재부팅 뒤의 `another line` 전송이다. 재부팅으로 ARP 캐시도 비었으므로 서버는 7~8번에서 ARP를 다시 한 뒤 9번에서 RST를 보낸다.

예에서 클라이언트는 연결을 맺고 `hi there`를 보낸 뒤, 서버가 재부팅되는 동안 아무것도 보내지 않았다. 약 190초 뒤 `another line`을 보내자 서버는 먼저 ARP로 클라이언트의 MAC 주소를 다시 알아낸 뒤 RST로 응답했다. 클라이언트 telnet은 `Connection closed by foreign host`를 출력한다. 데이터를 오래 주고받지 않는 연결에서 상대의 소멸을 먼저 감지하려면 keepalive 옵션(`SO_KEEPALIVE`)을 쓴다.

### TIME_WAIT Assassination

RFC 1337은 TIME_WAIT 상태가 RST로 일찍 끝나 버리는 문제를 다룬다. 클라이언트가 TIME_WAIT 상태에 있는데, 서버가 오래전에 보낸 세그먼트가 늦게 도착한다. 클라이언트가 그 세그먼트에 ACK로 응답하면, 이미 연결을 닫은 서버는 그 ACK를 모르는 연결의 세그먼트로 보고 RST를 보낸다. RST를 받은 클라이언트는 TIME_WAIT를 일찍 끝내고 CLOSED로 간다. 결과적으로 TIME_WAIT가 막으려던 옛 세그먼트 혼입 위험이 되살아난다.

![TIME_WAIT 상태의 클라이언트가 늦게 도착한 옛 세그먼트에 ACK로 응답하고 서버의 RST를 받아 일찍 CLOSED가 되는 과정](./images/net-udp-tcp-time-wait-assassination.svg 'RST가 TIME_WAIT를 강제로 끝내는 것이 Assassination이다')

대부분의 구현은 이 문제를 막기 위해 TIME_WAIT 상태에서 도착한 RST 세그먼트를 무시한다.

## 동시 개방과 동시 폐쇄

### 동시 개방

상태 전이도를 보면 두 호스트가 서로에게 동시에 SYN을 보내는 경로가 있다. 이를 동시 개방(simultaneous open)이라 한다. TCP 표준은 이 경우 연결을 두 개가 아니라 하나만 만들도록 설계되었다. OSI 전송 프로토콜은 같은 상황에서 연결 두 개를 만든다.

양쪽은 SYN을 보내 SYN_SENT 상태가 되고, 상대의 SYN을 받으면 SYN_RCVD 상태로 옮기면서 SYN+ACK를 다시 보낸다. 상대의 SYN+ACK를 받으면 ESTABLISHED가 된다. 세그먼트는 3개가 아니라 4개가 오간다.

![두 호스트가 동시에 SYN J와 SYN K를 보내 SYN_RCVD가 되고 SYN J ack K+1, SYN K ack J+1을 주고받아 ESTABLISHED가 되는 동시 개방, 그리고 각자 NAT 뒤에 있는 클라이언트 A와 B](./images/net-udp-tcp-simultaneous-open.svg '양쪽 NAT 뒤의 두 호스트가 직접 연결할 때 동시 개방이 쓰인다')

동시 개방은 한때 이론상의 시나리오였다. 그러나 각자 NAT 뒤에 있어 바깥에서 먼저 연결을 받을 수 없는 두 호스트가 서로 직접(peer-to-peer) TCP 연결을 맺으려면, 양쪽이 동시에 바깥으로 SYN을 보내 각자의 NAT에 매핑을 만들어야 한다. 이 기법을 TCP hole punching이라 하며 RFC 5128에 정리되어 있다.

실험에서는 bsdi의 8888번 포트와 vangogh의 7777번 포트에서 서로를 향해 동시에 연결을 시도했다. 세그먼트 1~4에서 양쪽 SYN과 SYN+ACK가 오가며 하나의 연결이 확립되고, 이후 양방향 데이터 전송과 일반적인 종료가 이어진다.

### 동시 폐쇄

양쪽이 동시에 능동 폐쇄를 수행할 수도 있다. 두 종단은 FIN을 보내 FIN_WAIT_1이 되고, ACK가 아니라 상대의 FIN을 먼저 받으면 CLOSING 상태로 옮기며 ACK를 보낸다. 자신의 FIN에 대한 ACK를 받으면 TIME_WAIT으로 간다. 양쪽 모두 능동 폐쇄를 했으므로 양쪽 모두 TIME_WAIT을 거친다. 교환하는 세그먼트 수는 일반적인 종료와 같은 4개다.

![양쪽이 FIN J와 FIN K를 동시에 보내 FIN_WAIT_1에서 CLOSING으로 가고, ack K+1과 ack J+1을 받아 TIME_WAIT에 들어가는 동시 폐쇄](./images/net-udp-tcp-simultaneous-close.svg '동시 폐쇄에서는 양쪽 모두 TIME_WAIT을 거친다')

## TCP 옵션

TCP 헤더 뒤에는 옵션이 올 수 있다. RFC 793이 기본 옵션을, RFC 1323(현재 RFC 7323)이 윈도우 스케일과 타임스탬프를 정의했다. 각 옵션은 첫 바이트 kind 값으로 종류를 구분하고, kind 0과 1을 제외하면 두 번째 바이트 len에 옵션 전체 길이를 담는다.

![kind 0(옵션 목록의 끝), 1(NOP), 2(MSS, len 4), 3(윈도우 스케일, len 3), 8(타임스탬프, len 10)의 바이트 구조](./images/net-udp-tcp-options.svg 'len은 kind와 len 바이트를 포함한 옵션 전체 길이다')

| kind | len  | 이름               | 내용                                                    | 정의     |
| ---- | ---- | ------------------ | ------------------------------------------------------- | -------- |
| 0    | 없음 | End of Option List | 옵션 목록의 끝                                          | RFC 793  |
| 1    | 없음 | No-Operation(NOP)  | 다음 옵션을 4바이트 경계에 맞추기 위한 채움             | RFC 793  |
| 2    | 4    | MSS                | 받을 수 있는 최대 세그먼트 크기(2바이트), SYN에만 사용  | RFC 793  |
| 3    | 3    | Window Scale       | 윈도우 크기를 왼쪽으로 이동할 비트 수(1바이트, 최대 14) | RFC 7323 |
| 4    | 2    | SACK Permitted     | 선택적 확인 응답 사용 가능                              | RFC 2018 |
| 5    | 가변 | SACK               | 받은 불연속 블록의 범위                                 | RFC 2018 |
| 8    | 10   | Timestamps         | 타임스탬프 값(4바이트)과 에코 응답(4바이트)             | RFC 7323 |

예를 들어 `<mss 512, nop, wscale 0, nop, nop, timestamp 146647 0>`의 길이는 `4 + 1 + 3 + 1 + 1 + 10 = 20`바이트로 4의 배수다. NOP를 빼면 18바이트가 되어 4의 배수가 아니고, 타임스탬프 옵션도 4바이트 경계에서 시작하지 못한다.

윈도우 스케일 옵션은 16비트 윈도우 필드의 한계(65,535바이트)를 넘기 위해 쓴다. 스케일 값이 7이면 윈도우 필드 값에 `2^7 = 128{:math}`을 곱한다. 최대 스케일 14를 적용하면 윈도우는 약 1GiB(`65535 \times 2^{14}{:math}`)까지 커진다.

## TCP 서버 설계

TCP 서버는 보통 병행(concurrent) 서버로 설계한다. 새 연결 요청이 도착하면 서버는 연결을 받아들이고 그 클라이언트를 처리할 새 프로세스나 스레드를 만든다. 이 절은 병행 서버가 포트와 주소를 어떻게 사용하는지 다룬다.

### 서버 포트 번호

`netstat -a -n`은 모든 종단점을 숫자 형식(IP 주소와 포트 번호)으로 출력한다. telnet 서버가 실행 중인 호스트에서 조회하면 다음과 같다. 예시 주소는 문서용 주소로 바꾸었다.

```text
Proto Recv-Q Send-Q  Local Address        Foreign Address        (state)
tcp        0      0  192.0.2.33.23        198.51.100.65.1030     ESTABLISHED
tcp        0      0  192.0.2.33.23        198.51.100.65.1029     ESTABLISHED
tcp        0      0  *.23                 *.*                    LISTEN
```

LISTEN 줄의 로컬 주소 `*.23`은 모든 로컬 인터페이스에서 23번 포트로 오는 연결을 받는다는 뜻이고, 외부 주소 `*.*`는 아직 상대가 정해지지 않았다는 뜻이다. 연결이 들어오면 TCP는 그 연결을 위해 새 종단점(ESTABLISHED 줄)을 만들고, LISTEN 종단점은 다음 연결을 기다리며 그대로 남는다. 같은 클라이언트 호스트에서 두 번째 연결이 들어와도 클라이언트 포트(1029, 1030)가 달라서 소켓 쌍이 구별된다.

### 로컬 IP 주소와 외부 IP 주소의 제한

서버가 로컬 IP 주소를 와일드카드 대신 특정 주소로 `bind(){:c}`하면, 그 주소로 들어온 연결만 받는다. 인터페이스가 여러 개인 멀티홈 호스트에서 관리용 서비스를 내부 인터페이스에만 여는 데 쓴다.

| 로컬 주소     | 외부 주소       | 의미                                         |
| ------------- | --------------- | -------------------------------------------- |
| localIP.lport | foreignIP.fport | 클라이언트 하나로 제한(보통 지원하지 않음)   |
| localIP.lport | `*.*`           | 로컬 인터페이스 localIP에 도착한 연결로 제한 |
| `*.lport`     | `*.*`           | lport로 오는 모든 연결을 받음                |

### 수신 연결 큐

병행 서버는 각 클라이언트를 위해 새 프로세스를 만들 수 있지만, LISTEN 중인 서버 자체는 `accept(){:c}`로 한 번에 연결 하나만 꺼낸다. 여러 연결 요청이 동시에 들어오거나, 연결을 완성하지 않는 요청이 대량으로 들어온다면 TCP는 이를 어떻게 처리하는가.

이런 연결은 두 종류다. (1) SYN은 받았지만 아직 핸드셰이크가 끝나지 않은 연결(SYN_RCVD), (2) 핸드셰이크는 끝났지만 서버가 아직 `accept(){:c}`하지 않은 연결(ESTABLISHED). 운영체제의 TCP 구현은 두 상황을 위한 큐를 각각 가진다.

![SYN 큐와 accept 큐, listen backlog와 accept의 관계](./images/net-udp-tcp-queue.svg 'SYN 큐는 핸드셰이크 중인 연결, accept 큐는 완성되어 꺼내기를 기다리는 연결을 담는다')

Linux의 규칙은 다음과 같다.

1. 시스템 파라미터 `net.ipv4.tcp_max_syn_backlog`가 SYN_RCVD 상태로 보관할 수 있는 연결 수를 정한다. 이 값을 넘으면 새 연결 요청을 거절한다.
2. LISTEN 소켓마다 (2)번 연결을 위한 고정 크기 큐가 있으며, 그 크기를 backlog라 한다. 응용이 `listen(fd, backlog){:c}`로 정하고, `net.core.somaxconn`을 넘을 수 없다. somaxconn의 기본값은 오래 128이었고 Linux 5.4부터 4096이다.
3. (2)번 큐에 공간이 있으면 TCP는 SYN에 SYN+ACK로 응답해 핸드셰이크를 완료하려 한다.
4. (2)번 큐에 공간이 없으면 Linux는 SYN에 대한 응답을 지연시킨다. 서버가 곧 `accept(){:c}`로 큐를 비울 것이라 기대한 설계다. `net.ipv4.tcp_abort_on_overflow`를 설정하면 지연하지 않고 RST를 보내 연결을 중단한다.

BSD 소켓 API는 전통적으로 두 큐의 합을 backlog로 정했지만, 최신 Linux에서 backlog는 (2)번 큐의 크기만 정한다.

> [!IMPORTANT] accept()가 반환한 시각에 핸드셰이크는 이미 끝났다
> 응용이 연결 도착을 알게 되는 시각, 즉 `accept(){:c}`가 연결 소켓을 반환한 시각에는 3-way handshake가 이미 끝나 있다. 응용은 핸드셰이크에 관여하지 않으므로 SYN 단계에서 특정 클라이언트를 거부할 수 없다. 또 클라이언트의 `connect(){:c}`는 SYN+ACK를 받으면 반환되므로, 서버가 연결 소켓을 받기 전에 클라이언트가 이미 데이터를 보냈을 수 있다. (1)번 큐를 위조한 SYN으로 가득 채우는 공격이 SYN 플러딩이며, [TCP 공격](/memo/net-tcp-attacks)에서 SYN 쿠키와 함께 다룬다.

```bash
# 수신 연결 큐 관련 파라미터 조회 (Linux)
sysctl net.ipv4.tcp_max_syn_backlog net.core.somaxconn net.ipv4.tcp_abort_on_overflow
# LISTEN 소켓의 accept 큐 사용량(Recv-Q)과 backlog(Send-Q)
ss -ltn
```

## 정리

| 주제           | 핵심                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| UDP            | 포트 번호와 선택적 체크섬만 제공. 단편화, 재전송, 데이터그램 크기는 응용의 몫 |
| 체크섬         | 가상 헤더를 포함한 16비트 1의 보수 합. 워드 순서 바뀜은 탐지하지 못함         |
| IP 단편화      | 오프셋은 8바이트 단위, 단편 하나만 잃어도 전체 손실. Path MTU 발견으로 회피   |
| TCP 서비스     | 연결 지향, 신뢰성, 바이트 스트림                                              |
| 순서 번호      | 바이트마다 번호, SYN과 FIN은 1 소비, ACK는 다음에 기대하는 번호               |
| 연결 확립·종료 | 3-way handshake, 방향별 FIN으로 4번 교환, 절반 폐쇄는 `shutdown(){:c}`        |
| TIME_WAIT      | 능동 폐쇄 쪽이 2MSL 동안 대기. 마지막 ACK 재전송과 옛 세그먼트 차단           |
| RST            | 없는 포트, 연결 중단(SO_LINGER 0), 절반 개방 연결에 대한 응답                 |
| 서버 설계      | LISTEN 종단점과 연결 종단점의 분리, SYN 큐와 accept 큐                        |

연결 확립의 각 단계에서 TCP가 무엇을 믿는지(ISN, 큐 크기, RST의 순서 번호)를 알면 TCP를 노리는 공격의 원리도 보인다. 원시 소켓으로 이런 세그먼트를 직접 만들고 수집하는 방법은 [스니핑과 스푸핑](/memo/net-sniffing-spoofing)에서 이어진다.
