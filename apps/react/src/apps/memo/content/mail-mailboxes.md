[메일 앱이 서버로 메일을 보내게](/memo/contact-mail) 한 다음, 두 가지가 아쉬웠다. 방문자는 보낸 뒤에 무엇을 보냈는지 다시 볼 수 없었고, 나는 답장하려면 Gmail로 가야 했다. 메일 앱에 사서함 두 개를 더했다.

- **보낸 편지함** (방문자): 이 브라우저에서 보낸 메일과, 거기에 내가 쓴 답장
- **받은 편지함** (관리자): 받은 모든 메일. 메일을 열면 아래에 답장 칸이 있다

## "본인"을 어떻게 가를까

| 방법                               | 좋은 점                            | 걸리는 점                                                              |
| ---------------------------------- | ---------------------------------- | ---------------------------------------------------------------------- |
| 브라우저 저장소에 보낸 메일을 둔다 | 서버 일이 없다                     | 관리자 답장을 받을 수 없다. 저장소를 지우면 끝                         |
| 메일 주소 + 확인 링크              | 기기가 바뀌어도 본다               | 보낸 메일함을 보려고 메일을 한 번 더 열어야 한다. 데모 사이트에 과하다 |
| **방문자 쿠키의 HMAC**             | 메시지·댓글과 같은 방식, 가입 없음 | 쿠키를 지우거나 다른 브라우저면 안 보인다                              |

마지막을 골랐다. 메일 자체는 방문자의 메일함에도 가니, 사이트의 보낸 편지함은 "이 브라우저에서 보낸 것을 다시 보는 곳" 정도면 된다고 봤다.

## 누가 무엇을 보나: 서버가 쿠키로 거른다

보낸 편지함은 **본인 메일만** 보여야 한다. 회원 가입이 없는 사이트에서 "본인"을 가리는 방법은 이미 있었다. 메시지 앱과 댓글이 쓰는 방문자 쿠키다. 처음 쓰는 브라우저에 무작위 토큰을 쿠키(httpOnly, 1년)로 주고, DB에는 그 토큰의 HMAC만 둔다.

메일을 보낼 때 이 HMAC을 메일과 함께 저장하고, `GET /contact/mine`은 요청에 실린 쿠키의 HMAC과 같은 메일만 돌려준다. 화면에서 감추는 게 아니라 서버가 거르므로, 요청을 꾸며도 남의 메일은 받을 수 없다.

```ts
// contact.service.ts
async mine(visitor: Visitor | null): Promise<ContactMailView[]> {
	if (!visitor) return [];
	const mails = await this.prisma.contactMail.findMany({
		where: { visitorHash: visitor.hash },
		orderBy: { createdAt: 'desc' },
		include: INCLUDE,
	});
	return mails.map(toView);
}
```

`GET /contact/mine`은 쿠키를 읽기만 한다(`visitors.peek`). 쿠키가 없는 사람에게 새 쿠키를 주지 않고 빈 목록을 돌려준다. 쿠키를 새로 주는 것은 메일을 보낼 때(`visitors.identify`)뿐이다. 메일 하나를 번호로 읽는 경로는 아예 만들지 않았다. 방문자가 읽는 길은 자기 목록 하나뿐이다. 응답에는 HMAC을 담지 않는다.

![방문자와 관리자가 메일을 읽고 쓰는 경로](./images/mail-mailboxes-flow.svg '방문자는 자기 HMAC의 메일만, 관리자는 모든 메일을 받는다')

받은 편지함(`GET /contact/inbox`)과 답장(`POST /contact/:id/reply`)은 관리자 세션을 확인하는 `AdminGuard`를 건다.

사이트의 보내기 요청에 `credentials: 'include'`를 더하는 것을 잊으면 안 됐다. 쿠키 없이 보내면 서버가 보낼 때마다 새 방문자로 여겨, 보낸 편지함이 늘 비어 있게 된다.

## 관리자 답장

받은 편지함에서 메일을 열면 아래에 "받는 사람: 민수 <minsu@example.com>"과 답장 칸이 있다. 보내면 서버가 두 가지를 한다.

1. Resend로 **방문자의 주소**에 메일을 보낸다. 제목은 `Re: [MacFolio] 원래 제목`, 본문 아래에 받은 메일을 `>`로 인용한다. Reply-To는 내 주소라, 방문자가 메일에서 답장하면 나에게 온다
2. 답장을 그 메일 아래에 저장한다. 그래서 방문자가 사이트의 보낸 편지함을 열어도 내 답장이 보인다

메일이 먼저다. 보내기에 실패하면 저장하지 않고 이유를 보여 준다. 저장만 되고 메일이 안 가면, 방문자는 답장을 받았는지 모르기 때문이다.

```ts
const { subject, text } = buildReply(mail, parsed.value.body);
const sent = await this.deliver({ to: mail.email, replyTo: this.config.contact.to!, subject, text });
if (!sent) throw new BadGatewayException('답장을 보내지 못했습니다. 잠시 뒤 다시 시도해 주세요.');
await this.prisma.contactReply.create({ data: { mailId: id, body: parsed.value.body } });
```

![관리자 답장의 순서](./images/mail-mailboxes-reply-order.svg '보내기가 실패하면 저장하지 않고 502')

반대 경우(메일은 갔는데 저장이 실패)는 남는다. 그러면 방문자는 메일함에서는 답장을 받고 사이트의 보낸 편지함에는 보이지 않는다. 둘 중 하나를 고르라면 메일이 가는 쪽이 낫다고 봤다.

목록의 안 읽음 표시는 관리자에게는 **아직 답장하지 않은 메일**을 뜻하게 했다. 사이드바의 숫자가 답장할 메일 수다. 방문자에게는 예전처럼 열어 보지 않은 메일이다.

## 1년만 둔다

메일을 서버에 두게 되면서 개인정보 문서(`docs/privacy.md`)를 고쳤다. 받은 메일과 답장은 1년이 지나면 지운다. 따로 작업 도구를 두지 않고 메일을 보낼 때와 관리자가 받은 편지함을 열 때 지난 것을 지운다. 방문자가 쿠키를 지우면 그 브라우저에서도 더는 보이지 않는다. 받은 편지함은 한 번에 최근 500통까지 읽는다.

DB에는 표 두 개(`ContactMail`, `ContactReply`)를 더했다. 메일에는 보낸 사람 이름·주소·제목·본문과 `visitorHash`가, 답장에는 메일 id와 본문이 있다. 지우는 쿼리는 이렇다.

```ts
await this.prisma.contactMail.deleteMany({ where: { createdAt: { lt: new Date(now.getTime() - RETENTION_MS) } } });
```

답장은 메일에 딸려 있어 함께 지워진다.

## 휴대폰

좁은 창과 휴대폰에서는 사이드바가 숨으니, 목록 위에 받은 편지함·보낸 편지함을 고르는 분할 버튼을 두었다. 서버 주소가 없는 빌드에는 보낸 편지함이 없다(보낼 곳이 방문자의 메일 앱이라 사이트가 알 수 없다).

## 시험

서버 쪽은 커밋 하나(`60e89137c`)로 10개 파일, 513줄 더하기, 27줄 지우기다. 그중 137줄이 `apps/api/test/contact.e2e.test.ts`다.

- API 단위(`apps/api/src/contact/rules.test.ts`): 답장 검사(빈 값·길이·제어 문자), 답장 메일의 제목과 인용
- API e2e: A가 보낸 두 통은 A의 보낸 편지함에만, B의 것은 B에게만, 쿠키가 없으면 빈 목록, 응답에 HMAC이 없는지. 받은 편지함·답장은 방문자에게 401, 관리자에게는 모든 메일. 답장이 방문자의 주소로 가고 Reply-To가 주인인지, 그 메일에 답장이 붙는지, 없는 메일 404, 빈 답장 400
- 화면: 보낸 메일이 보낸 편지함에 들어가고 방문자에게 답장 칸이 없음, 주인의 답장이 보낸 편지함에 보임, 관리자가 앱에서 답장하면 그 메일 아래에 붙고 안 읽음 숫자가 사라짐

## 휴대폰은 iOS 메일처럼

휴대폰 메일은 데스크톱의 세 칸(메일상자 · 목록 · 읽기)을 한 칸씩 보여 주던 모양이었다. 첫 화면이 받은 편지함이었고, 보낸 편지함은 위쪽 탭으로 골랐다. iOS 메일 스크린샷과 나란히 놓고 따로 짰다(`MailMobile`). 메일 목록, 읽음, 보내기, 답장은 데스크톱과 같이 쓴다.

- **메일상자**가 첫 화면이다. 큰 제목, "지금 업데이트됨", 받은 편지함(안 읽은 수)과 보낸 편지함의 흰 카드 목록이 있다
- **메일 한 통**: 위에 뒤로 가기와 ↑·↓(이전·다음 메일), 둥근 네모 아바타, 보낸 사람, "받는 사람:", 날짜, 큰 제목, 본문. 아래에 답장 알약과 새로운 메시지
- **답장**을 누르면 먼저 메일 동작 시트가 올라온다(답장, 방문자는 읽지 않음으로 표시). 관리자는 답장 시트에서 바로 답장한다. 제목은 "Re: …"이고, 아래에 원래 메일을 인용한다. 방문자는 주인에게 "Re: …" 제목의 새 메일을 쓴다
- **쓰기**는 아래에서 올라오는 시트다. 왼쪽 위 ×, 오른쪽 위 ↑(다 쓰면 파랗게), 큰 제목은 쓴 제목을 따른다

처음 화면을 찍어 보니 메일 한 통이 한 글자씩 세로로 쌓였다. 휴대폰 화면의 바깥 상자에 화면 이름을 클래스로 붙였는데(`mail-phone mail`), `mail`이 데스크톱 메일의 세 칸 격자 클래스와 같은 이름이었다. 화면 이름은 `data-screen`으로 옮겼다.

### 넘어갈 때 움직임

화면이 바뀔 때 뚝 끊기지 않게 했다.

- 더 깊은 화면(메일상자 → 목록 → 메일)으로 가면 오른쪽에서 밀려 들어오고, 뒤로 가면 왼쪽에서 돌아온다. 화면마다 새로 그려 애니메이션을 다시 돌린다(`data-direction`)
- 시트는 아래에서 올라오고, 뒤는 서서히 어두워진다. 닫을 때도 바로 지우지 않는다. 내려가는 애니메이션(240ms)이 끝난 뒤에 지운다
- 움직임 줄이기 설정을 켰으면 애니메이션 없이 바로 닫는다

## 남은 것·배운 것

- 다른 기기나 브라우저에서는 보낸 편지함이 비어 보인다. 화면에 "이 브라우저에서 보낸 메일만 보입니다" 같은 안내가 있으면 덜 헷갈린다.
- 관리자에게 환영 메일이 보이지 않던 것은 열이틀 뒤에 고쳤다. 환영 메일은 주인이 보낸 것이니 관리자에게는 보낸 편지함에 둔다([Finder 배경화면과 QuickTime 열기 창](/memo/finder-wallpaper-persist)).
- 쿠키 이름 하나를 메시지·댓글·메일이 함께 쓰니, 방문자 식별을 한 곳(`visitors`)에서 고치면 세 기능이 같이 따라온다.
- 휴대폰 화면의 클래스 이름이 데스크톱 클래스와 겹쳐 깨진 일은 CSS 이름을 앱마다 접두어로 나누는 것만으로는 막지 못한다. 같은 앱 안에서도 겹친다. 상태는 `data-*` 속성에 두는 편이 안전하다.
