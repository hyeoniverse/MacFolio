## 리팩터링 계획 1~3단계

계획의 항목마다 PR 하나와 글 한 편을 작성했다. 10월 7일에 트래픽 분석을 PR 4개로 나눈 방식을 리팩터링에도 적용했다.

| 단계           | 내용                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2. 구조        | 순환 의존 2개를 제거하고 madge 검사를 CI에 추가 ([#188](https://github.com/hyeoniverse/MacFolio/pull/188)). 1,861줄·970줄 데모 파일과 700줄 안팎의 사이드바·사진 앱을 분할 ([#189](https://github.com/hyeoniverse/MacFolio/pull/189), [#190](https://github.com/hyeoniverse/MacFolio/pull/190), [#193](https://github.com/hyeoniverse/MacFolio/pull/193)). 앱 내부 파일 이름 규칙 ([#191](https://github.com/hyeoniverse/MacFolio/pull/191)) |
| 3. 공통 기반   | 서버 요청을 `api()`·`apiFetch()`로 통합 ([#196](https://github.com/hyeoniverse/MacFolio/pull/196)), 브라우저 저장소 접근을 `storage.ts`로 ([#198](https://github.com/hyeoniverse/MacFolio/pull/198)), `matchMedia`·`innerWidth` 접근을 `media.ts`로 ([#199](https://github.com/hyeoniverse/MacFolio/pull/199))                                                                                                                               |

### 진행 순서: 2 → 3 → 1

계획의 번호와 반대로 2단계부터 진행했다. 순환 의존(파일 A가 B를 import하고, B가 다시 A를 import하는 관계)을 먼저 제거하고 큰 파일을 먼저 분할해 두어야, 타입을 옮길 때 수정할 파일의 범위가 작아진다. 처음에는 "타입과 데이터 구조가 먼저여야 하지 않나"라는 의문이 있어 진행을 멈추고 다시 검토했다. 검토 결과 2 → 3 → 1 순서가 불가피했다. 2단계 안에서 두 가지 방법 중 하나를 고를 때는 작업량이 아니라 코드 품질을 기준으로 판단했다.

### PR 본문에 목적을 기록하기

리팩터링 PR은 외부 동작이 바뀌지 않아서, 나중에 다시 보면 왜 했는지 알 수 없다. 그래서 각 PR 본문에 목적, 이유, 관련 이슈·PR 링크를 적었다. 공통 UI 문서 PR은 처음에 "개수가 많아도 형태·의미가 다르니 보류"라고 적었다. 그런데 버튼은 공통 컴포넌트의 기본인데 공통 컴포넌트가 없다는 점이 걸려, 실제 사용처가 몇 곳인지 집계했다. 이 집계는 다음 날 Modal 추출로 이어진다.

## contracts: 이전하면서 드러난 불일치

1단계의 중심은 `packages/contracts`다. API 요청·응답 형식을 zod 스키마로 한 번 정의하고, 서버는 요청 검증에, 화면은 타입 추론에 함께 사용한다([응답 타입을 두 번 적지 않기](/memo/contracts-comments)). 댓글부터 시작해 글, 메시지, 연락 메일, 배경화면, 업로드 파일, 분석, 사이트 프로필까지 8개 도메인을 PR 8개로 이전했다.

```text
전: 서버 DTO ─┐                후: packages/contracts (zod 스키마 1개)
             ├ 따로 정의                ├─ 서버: parse(Schema, body)로 검증
   화면 type ─┘                         └─ 화면: z.infer로 타입 추론
```

이전 작업 자체보다, 두 곳에 따로 정의된 값이 서로 달랐다는 것을 발견한 것이 더 중요했다.

| 도메인    | 화면                          | 서버                     | 글                                               |
| --------- | ----------------------------- | ------------------------ | ------------------------------------------------ |
| 메시지    | `mine?: boolean` (선택)       | `mine: boolean` (필수)   | [메시지 도메인 옮기기](/memo/contracts-messages) |
| 연락 메일 | "30자까지 입력할 수 있습니다" | "30자까지입니다"         | [같은 뜻, 다른 문구](/memo/contracts-contact)    |
| 배경화면  | "API와 같은 한도" 주석과 40   | 서버 규칙 40, DB 제약 40 | [숫자 40이 세 곳에](/memo/contracts-wallpapers)  |

마지막은 브랜드 타입이었다. 글 주소와 폴더 경로가 모두 `string`이라, 주소창에서 읽은 문자열을 검증 없이 `movePost`에 넘겨도 컴파일됐다. 이제는 `postSlug()`·`folderPath()`를 거쳐야 해당 타입이 된다. 런타임에는 일반 문자열이라 동작은 바뀌지 않는다([PostSlug·FolderPath 브랜드 타입](/memo/branded-ids)).

## 코드 수정 없이 바꾸는 사이트 정보

이 저장소를 내려받아 배포하는 사람은 이름과 메일 주소를 바꾸려면 코드를 수정해야 했다. 프로필을 서버에 저장하고, 관리자가 시스템 설정 › 정보에서 수정하게 했다. 상수를 읽던 15곳은 구독 가능한 store를 읽게 바꿨다([#180](https://github.com/hyeoniverse/MacFolio/pull/180), [코드를 고치지 않고 프로필 바꾸기](/memo/site-profile-editing)).

![시스템 설정 › 정보](./images/day-1011-profile.jpg '시스템 설정의 정보 화면. 관리자는 오른쪽 위 편집 버튼으로 이 내용을 수정한다')

다음 대상은 프로젝트였다. #187에서 Safari의 프로젝트 페이지와 프로젝트 앱을 시스템 설정 › 프로젝트에서 관리한다. 서버에는 코드의 기본값과 다른 필드만 저장하고, Cloudflare Worker가 첫 화면 HTML에 그 값을 삽입하고 데모 주소를 CSP에 추가한다. 이날 이 브랜치에서 편집 모드, 기간 달력, 기술 칩과 후보 1,700여 개, npm 패키지 검색을 구현했다.

새 프로젝트용 페이지 템플릿은 이날 세 번 바뀌었다.

1. 어느 프로젝트에나 맞는 기본 템플릿 하나
2. 기존 7개 프로젝트의 페이지를 템플릿으로 다시 작성
3. 읽는 방식이 서로 다른 템플릿 12개

기존 7개 프로젝트는 직접 작성한 페이지를 그대로 사용하게 했다. 템플릿 작업은 12일과 13일에도 이어진다.

![템플릿 12개 중 cinema](./images/day-1011-cinema.jpg '이날 #187 브랜치의 템플릿 12개 중 cinema. 한 화면씩 고정되는 장면 단위로 읽는다. 13일에 키노트 템플릿으로 통합됐다')

## 블로그 글이 시험을 실패시킨 일

이날 main이 한 번 실패했다. 블로그 폴더를 '개발기 › MacFolio' 아래로 재구성한 PR([#192](https://github.com/hyeoniverse/MacFolio/pull/192))과, 그 전에 작성한 글을 포함한 PR들이 각자 CI를 통과한 뒤 main에서 합쳐졌다. 이전 카테고리를 지정한 글 한 편 때문에 '인프라' 폴더가 둘로 나뉘었고, 메모 E2E에서 '인프라' 버튼이 두 개 선택되어 실패했다. 해당 글의 카테고리를 수정하고, 아직 머지하지 않은 PR의 글도 함께 수정했다.

브랜치에서도 같은 유형의 실패가 있었다. 데모 파일 분할 글에 쓴 'Fast Refresh'라는 단어가 메모 검색 E2E에 영향을 줬다. 그 시험은 이 단어로 검색하면 글이 하나만 나와야 했다. 블로그 글은 메모 앱 E2E의 시험 데이터이기도 하다.

macOS에서만 실패한 경우도 있었다. 데모 파일을 분할하면서 같은 폴더에 `Slides.tsx`와 `slides.ts`가 생겼다. 파일 이름의 대소문자를 구분하는 Linux CI는 통과했지만, 구분하지 않는 macOS(APFS 기본값)에서는 `./Slides`가 `slides.ts`로 해석되어 타입 검사와 빌드가 실패했다. 목록 파일을 `slideDeck.ts`로 변경하고([#197](https://github.com/hyeoniverse/MacFolio/pull/197)), CONTRIBUTING에 파일 이름의 대소문자 규칙을 추가했다.

## 서버 하드닝 점검

서버 하드닝 상태를 문서 대신 `ops/audit.sh`가 직접 읽어 출력하게 했다([#183](https://github.com/hyeoniverse/MacFolio/pull/183), [#186](https://github.com/hyeoniverse/MacFolio/pull/186), [서버 하드닝은 스크립트로](/memo/server-hardening-audit)).

#183을 머지한 뒤 새벽 1시 반에 서버에 접속해 스크립트를 실행했다. 첫 결과에서 "확인" 항목이 두 개였다. SSH(22) 외에 `0.0.0.0:111`(rpcbind)이 외부 인터페이스에서 수신 대기 중이었고, 호스트 방화벽 규칙을 읽지 못했다.

```bash
cd ~/macfolio && git pull && ops/audit.sh
# [포트] 외부에서 수신 대기 중인 포트
#         tcp 0.0.0.0:111      ← rpcbind
#         tcp 0.0.0.0:22
#   확인  SSH 외에 외부에서 수신 대기 중인 포트가 있다
sudo systemctl disable --now rpcbind.socket rpcbind.service
sudo reboot
```

| 단계               | 확인 방법                          | 결과                                                        |
| ------------------ | ---------------------------------- | ----------------------------------------------------------- |
| 재부팅 후 컨테이너 | `cd ~/deploy && docker compose ps` | api·db·tunnel 실행 중 (api는 `health: starting` 후 healthy) |
| 포트               | `ops/audit.sh` 재실행              | `OK SSH(22) 말고 바깥에서 듣는 포트 없음`                   |
| 방화벽             | `sudo iptables -S INPUT`           | 22번만 허용하는 규칙                                        |

스크립트 자체의 오류도 두 가지 발견했다. cloudflared 이미지에는 `id`·`sh`가 없어서 "root가 아닌 사용자" 검사가 오류 메시지를 OK로 출력했고, 방화벽 규칙은 sudo 없이 읽을 수 없었다. 이 두 가지를 수정한 것이 #186이고, 재실행해 모든 항목이 OK로 나왔다. 점검 항목과 대응 방법은 [docs/deployment.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/deployment.md)의 '서버 하드닝 점검'과 [ops/audit.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/audit.sh)에 있다.

전날 활성화한 GitHub Push protection은 화면에 "Block commits that contain supported secrets" 문구가 별도로 표시되지 않았는데, Secret Protection과 함께 이미 활성화된 상태였다.

## 돌아보며

계획을 미리 작성해 둔 것이 이날의 진행 속도를 만들었다. 항목마다 무엇을 어디로 옮길지 정해져 있어서, PR마다 범위를 다시 정할 필요 없이 이전 작업만 하면 됐다. 그리고 이전 작업은 단순한 정리가 아니었다. 두 곳에 따로 정의된 값은 시간이 지나면 조금씩 달라진다. `mine?`와 `mine`, 두 가지 문구, 세 곳의 40은 모두 한 곳으로 통합하면서 처음 드러났다.

PR이 몰려 머지되는 동안 main CI는 대부분 끝까지 실행되지 못했다. 같은 브랜치에 새 push가 오면 이전 실행을 취소하도록(`concurrency.cancel-in-progress`) 설정해 두어서, 이날 main의 CI 실행 28회 중 18회가 취소됐다. 연속으로 머지한 PR들은 마지막 머지 커밋에서만 시험을 거쳤다. 블로그 카테고리 문제는 그 마지막 실행이 실패해서 드러났다. 전날 "머지한 뒤 main의 CI까지 확인해야 머지가 끝난다"라고 적었는데, 머지를 몰아서 하면 확인할 수 있는 실행 자체가 줄어든다.

블로그 글과 시험이 서로 연결되어 있다는 점도 이날 두 번 확인했다. 글은 문서이지만 메모 앱에서는 시험 데이터다. 글을 추가하는 PR도 메모 E2E를 실행한 뒤 올려야 한다.
