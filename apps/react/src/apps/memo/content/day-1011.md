전날 새벽에 적은 리팩터링 계획([#150](https://github.com/hyeoniverse/MacFolio/issues/150))은 일곱 단계였다. 이날 그중 1단계(타입과 데이터 구조), 2단계(폴더 구조와 의존), 3단계(공통 기반 코드)의 체크박스가 모두 채워졌다. 같은 날 사이트 주인의 프로필을 코드 대신 시스템 설정에서 고치게 했고, 프로젝트까지 그렇게 하는 PR [#187](https://github.com/hyeoniverse/MacFolio/pull/187)을 열었다.

![10월 11일 작업 흐름](./images/day-1011-timeline.svg '오전까지는 main에 리팩터링 PR, 그 뒤로는 #187 브랜치에서 프로젝트 편집. 커밋한 시각 기준')

## 계획 세 단계를 PR 하나씩

계획의 항목마다 PR 하나와 글 한 편을 두었다. 10월 7일에 트래픽 분석을 PR 네 개로 나눈 방식을 리팩터링에도 썼다.

| 단계           | 한 일                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2. 구조        | 순환 의존 둘을 끊고 madge를 CI에 ([#188](https://github.com/hyeoniverse/MacFolio/pull/188)). 1,861줄·970줄 데모 파일과 700줄 안팎의 사이드바·사진 앱을 나눔 ([#189](https://github.com/hyeoniverse/MacFolio/pull/189), [#190](https://github.com/hyeoniverse/MacFolio/pull/190), [#193](https://github.com/hyeoniverse/MacFolio/pull/193)). 앱 안 파일 이름 규칙 ([#191](https://github.com/hyeoniverse/MacFolio/pull/191)) |
| 3. 공통 기반   | 서버 요청을 `api()`·`apiFetch()` 하나로 ([#196](https://github.com/hyeoniverse/MacFolio/pull/196)), 브라우저 저장소를 `storage.ts`로 ([#198](https://github.com/hyeoniverse/MacFolio/pull/198)), `matchMedia`·`innerWidth`를 `media.ts`로 ([#199](https://github.com/hyeoniverse/MacFolio/pull/199))                                                                                                                        |
| 1. 타입·데이터 | API 모양을 contracts로 여덟 도메인 ([#200](https://github.com/hyeoniverse/MacFolio/pull/200)~[#207](https://github.com/hyeoniverse/MacFolio/pull/207)), 1,629줄 `profile.ts`를 폴더로 ([#208](https://github.com/hyeoniverse/MacFolio/pull/208)), 글 주소·폴더 경로를 브랜드 타입으로 ([#209](https://github.com/hyeoniverse/MacFolio/pull/209))                                                                            |

순서는 계획과 반대로 2단계부터 했다. 순환 의존을 먼저 끊고 큰 파일을 먼저 나눠 두어야 타입을 옮길 때 고칠 파일이 작아지기 때문이다.

줄 수는 대체로 줄었다. 서버 요청은 346줄이 179줄이 되었고([fetch 33곳을 client.ts 하나로](/memo/shared-api-client)), 저장소 접근은 134줄이 53줄이 되었다([try/catch 열두 개를 하나로](/memo/shared-storage)). `profile.ts`는 프로젝트마다 한 파일로 나눴지만 `index.ts`가 다시 내보내서, 바깥 27곳의 import 경로는 바뀌지 않았다([1,629줄 한 파일을 폴더로](/memo/profile-split)).

## contracts: 옮기다 보니 어긋난 곳이 나왔다

1단계의 중심은 `packages/contracts`다. API 요청·응답 모양을 zod 스키마로 한 번 적고, 서버는 검증에, 화면은 타입 추론에 같이 쓴다([응답 타입을 두 번 적지 않기](/memo/contracts-comments)). 댓글부터 시작해 글, 메시지, 연락 메일, 배경화면, 올린 파일, 분석, 사이트 프로필까지 여덟 도메인을 PR 여덟 개로 옮겼다.

옮기는 일 자체보다, 옮기면서 두 곳에 따로 적혀 있던 것이 서로 다르다는 것을 찾은 것이 더 컸다.

- 메시지의 `mine`이 화면에서는 `mine?: boolean`, 서버에서는 `mine: boolean`이었다([메시지 도메인 옮기기](/memo/contracts-messages)).
- 연락 메일의 글자 수 한도는 같은데 문구가 달랐다. 화면은 "30자까지 입력할 수 있습니다", 서버는 "30자까지입니다"([같은 뜻, 다른 문구](/memo/contracts-contact)).
- 배경화면 이름 한도 40자가 DB 제약, 서버 규칙, 화면 세 곳에 따로 적혀 있었다. 화면에는 "API와 같은 한도"라는 주석만 있었다([숫자 40이 세 곳에](/memo/contracts-wallpapers)).

마지막은 브랜드 타입이었다. 글 주소와 폴더 경로가 모두 `string`이라 주소창에서 온 문자열을 그대로 `movePost`에 넘겨도 컴파일이 됐다. 이제는 `postSlug()`·`folderPath()`를 지나야 그 타입이 된다. 실행할 때는 그냥 문자열이라 동작은 바뀌지 않았다([PostSlug·FolderPath 브랜드 타입](/memo/branded-ids)).

## 코드를 고치지 않고 바꾸는 사이트

이 저장소를 가져다 띄우는 사람은 이름과 메일 주소를 바꾸려면 코드를 고쳐야 했다. 프로필을 서버에 두고, 관리자가 시스템 설정 › 정보에서 고치게 했다. 상수를 읽던 열다섯 곳을 반응형 저장소로 바꿨다([#180](https://github.com/hyeoniverse/MacFolio/pull/180), [코드를 고치지 않고 프로필 바꾸기](/memo/site-profile-editing)).

![시스템 설정 › 정보](./images/day-1011-profile.jpg '시스템 설정의 정보. 관리자는 오른쪽 위 편집으로 이 내용을 고친다')

다음은 프로젝트였다. #187에서 Safari의 프로젝트 페이지와 프로젝트 앱을 시스템 설정 › 프로젝트에서 관리한다. 서버에는 코드의 기본값과 다른 필드만 두고, Cloudflare Worker가 첫 화면 HTML에 그 값을 넣고 데모 주소를 CSP에 더한다. 이날 이 브랜치에서 편집 모드, 기간 달력, 기술 칩과 후보 1,700여 개, npm 검색을 만들었다.

새 프로젝트용 페이지 모양도 이날 세 번 바뀌었다. 어디에나 맞는 기본 모양 하나를 만들고, 기존 일곱 모양을 처음부터 다시 쓰고, 다시 "읽는 방식이 다른" 열두 모양으로 짰다. 기존 일곱 프로젝트는 직접 짠 페이지를 그대로 쓰게 했다. 이 페이지 모양 이야기는 12일과 13일에도 이어진다.

![열두 모양 중 cinema](./images/day-1011-cinema.jpg '이날 #187 브랜치의 열두 모양 중 cinema. 한 화면씩 고정되는 장면으로 읽는다. 이 모양은 13일에 키노트 템플릿으로 합쳐졌다')

## 블로그 글이 시험을 깨뜨렸다

main은 이날 한 번 깨졌다. 블로그 폴더를 '개발기 › MacFolio' 아래로 다시 짠 PR([#192](https://github.com/hyeoniverse/MacFolio/pull/192))과, 그 전에 쓴 글을 담은 PR들이 각자 통과한 뒤 main에서 만났다. 옛 카테고리를 단 글 한 편이 '인프라' 폴더를 둘로 가르자, 메모 E2E에서 '인프라' 버튼이 두 개 잡혀 실패했다. 그 글의 카테고리 한 줄을 고쳤고, 아직 머지하지 않은 PR의 글도 같이 고쳤다.

같은 일이 브랜치에서도 있었다. 데모 파일을 나눈 글에 쓴 'Fast Refresh'라는 말이 메모 검색 E2E에 걸렸다. 그 시험은 이 말로 검색하면 글이 하나만 나와야 했다. 블로그 글은 메모 앱 E2E의 데이터이기도 하다.

또 하나는 macOS에서만 깨졌다. 데모 파일을 나누며 같은 폴더에 `Slides.tsx`와 `slides.ts`가 생겼다. 대소문자를 가리는 리눅스 CI는 통과했지만, 가리지 않는 macOS에서는 `./Slides`가 `slides.ts`로 읽혀 타입 검사와 빌드가 깨졌다. 목록 파일을 `slideDeck.ts`로 바꾸고([#197](https://github.com/hyeoniverse/MacFolio/pull/197)), CONTRIBUTING에 파일 이름의 대소문자 규칙을 적었다.

- 서버 하드닝 상태를 문서 대신 `ops/audit.sh`가 읽어서 보여 준다([#183](https://github.com/hyeoniverse/MacFolio/pull/183), [#186](https://github.com/hyeoniverse/MacFolio/pull/186), [서버 하드닝은 스크립트로](/memo/server-hardening-audit)).

## 돌아보며

계획을 먼저 적어 둔 것이 이날의 속도를 만들었다. 항목마다 무엇을 어디로 옮길지가 이미 정해져 있어서, PR마다 범위를 고민하지 않고 옮기는 일만 하면 됐다. 그리고 옮기는 일은 단순한 정리가 아니었다. 두 곳에 따로 적힌 것은 시간이 지나면 조금씩 달라진다. `mine?`와 `mine`, 두 가지 문구, 세 곳의 40은 모두 한 곳으로 모으면서 처음 보였다.

main CI는 PR이 몰려 들어오는 동안 거의 돌지 못했다. 같은 브랜치에 새 push가 오면 앞의 실행을 취소하게 해 두었기 때문에, 이날 main의 CI 실행 28번 중 18번이 취소되었다. 한꺼번에 머지한 PR 묶음은 마지막 머지 커밋에서만 시험을 거쳤다. 블로그 카테고리 문제는 그 마지막 실행이 실패해서 드러났다. 전날 "머지한 뒤 main의 CI를 다시 보는 것까지가 머지다"라고 적었는데, 머지를 몰아서 하면 볼 수 있는 실행 자체가 줄어든다.

블로그 글과 시험이 서로 얽혀 있다는 것도 이날 두 번 겪었다. 글은 문서이지만 메모 앱에서는 데이터다. 글을 더하는 PR도 메모 E2E를 돌려 보고 올려야 한다.
