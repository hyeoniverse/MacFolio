전날 작성한 리팩터링 계획([#150](https://github.com/hyeoniverse/MacFolio/issues/150))은 7단계였다. 그중 1단계(타입과 데이터 구조), 2단계(폴더 구조와 의존 관계), 3단계(공통 기반 코드)의 항목을 모두 마쳤다. 리팩터링은 동작을 바꾸지 않고 코드의 구조만 바꾸는 작업이다. 예를 들어 한 파일에 1,600줄이 몰려 있으면 기능은 같게 두고 파일을 나누고, 같은 코드가 여러 곳에 복사되어 있으면 한 곳으로 모은다.

사이트 운영자의 프로필도 코드 대신 시스템 설정에서 수정하게 했고, 프로젝트까지 같은 방식으로 관리하는 PR [#187](https://github.com/hyeoniverse/MacFolio/pull/187)을 열었다.

### 진행 순서: 2 → 3 → 1

계획의 번호와 반대로 2단계부터 진행했다. 순환 의존은 파일 A가 B를 import하고, B가 다시 A를 import하는 관계다. 이 관계가 있으면 한쪽 파일의 타입을 옮길 때 반대쪽 파일까지 함께 고쳐야 한다. 순환을 먼저 제거하고 큰 파일을 먼저 분할해야 ==타입을 옮길 때 수정할 파일의 범위가 작아진다.==

#188에서 찾은 순환은 두 개였다. 그중 메일 앱의 경우를 그림으로 옮기면 다음과 같다.

![순환 의존과 제3의 파일로 끊는 방법](./images/day-1011-import-cycle.svg 'Mail.tsx와 MailMobile.tsx가 서로를 import하던 구조를, 두 파일이 함께 쓰는 타입을 model.ts로 옮겨 한 방향으로 바꿨다')

madge는 소스 파일의 import 관계를 그래프로 만들어 순환을 찾는 도구다. CI에 넣어 두면 새 순환이 생기는 PR은 실패한다. 처음에는 "타입과 데이터 구조가 먼저여야 하지 않나"라는 의문이 들어 진행을 멈추고 다시 검토했는데, 위 이유로 2 → 3 → 1 순서가 불가피했다. 2단계 안에서 두 가지 방법 중 하나를 고를 때는 작업량이 아니라 코드 품질을 기준으로 판단했다.

### 공통 컴포넌트 후보 집계

공통 UI 문서 PR에는 처음에 "개수가 많아도 형태·의미가 다르니 보류"라고 적었다. 그런데 버튼은 공통 컴포넌트의 기본인데 공통 Button을 쓰는 곳이 적다는 점이 걸려서, 실제 사용처가 몇 곳인지 집계했다. 이 집계를 근거로 다음 날 Modal을 추출했다.

## contracts: 이전하면서 드러난 불일치

### 배경: 같은 형식을 두 곳에 정의하는 문제

화면(프론트엔드)과 서버(API)는 같은 데이터를 주고받는다. 예를 들어 댓글을 보낼 때 화면은 `{ name, body }`를 보내고 서버는 그 값이 맞는 형식인지 검증한다. 이 형식이 화면에는 TypeScript 타입으로, 서버에는 검증 규칙(DTO)으로 따로 정의되어 있으면, 한쪽만 고쳤을 때 둘이 어긋난다.

1단계의 중심은 `packages/contracts`다. zod는 "이 값은 1~30자 문자열"처럼 데이터의 형식을 코드로 적는 검증 라이브러리이고, 그 정의에서 TypeScript 타입도 자동으로 만들어 준다(`z.infer`). API 요청·응답 형식을 zod 스키마로 한 번 정의하고, 서버는 요청 검증에, 화면은 타입 추론에 함께 사용한다([zod 스키마 패키지 @macfolio/contracts로 서버 검증과 화면 타입 공유하기](/memo/contracts-package#댓글좋아요-스키마-200)).

```ts
// packages/contracts/src/contact.ts를 간단히 줄인 형태
// (실제 코드는 superRefine으로 칸마다 첫 실패 문구 하나만 반환한다)
export const ContactInput = z.object({ name: z.string().max(30, '이름은 30자까지 입력할 수 있습니다.') });
export type ContactInput = z.infer<typeof ContactInput>; // { name: string }

// 서버: const body = parse(ContactInput, req.body);   이름이 31자면 400과 위 문구
// 화면: import type { ContactInput } from '@macfolio/contracts';
```

댓글부터 시작해 글, 메시지, 연락 메일, 배경화면, 업로드 파일, 분석, 사이트 프로필까지 8개 도메인을 차례로 이전했다.

```text
전: 서버 DTO ─┐                후: packages/contracts (zod 스키마 1개)
             ├ 따로 정의                ├─ 서버: parse(Schema, body)로 검증
   화면 type ─┘                         └─ 화면: z.infer로 타입 추론
```

### 찾은 불일치

옮기는 작업 자체보다, ==두 곳에 따로 정의된 값이 서로 달랐다는 것==을 찾은 것이 더 컸다.

| 도메인    | 화면                          | 서버                     | 글                                                                                                                                         |
| --------- | ----------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 메시지    | `mine?: boolean` (선택)       | `mine: boolean` (필수)   | [메시지 도메인 옮기기](/memo/contracts-package#메시지-스키마와-두-저장소-구현-202)                                                         |
| 연락 메일 | "30자까지 입력할 수 있습니다" | "30자까지입니다"         | [zod superRefine으로 첫 실패 문구만 반환하는 화면·서버 공통 검사](/memo/contracts-validation#연락-메일-칸마다-첫-실패-문구-하나-203)       |
| 배경화면  | "API와 같은 한도" 주석과 40   | 서버 규칙 40, DB 제약 40 | [DB CHECK·서버·화면에 흩어진 이름 한도를 contracts 정리 함수로 통합하기](/memo/contracts-validation#배경화면-이름-한도-40과-정리-함수-204) |

메시지의 경우 화면은 `mine`(내가 보낸 메시지인지)이 없을 수도 있다고 정의했지만, 서버는 항상 값을 보냈다. 연락 메일은 같은 규칙인데 화면에서 막히면 앞 문구, 서버에서 막히면 뒤 문구가 표시됐다. 배경화면 이름 한도 40은 세 곳에 숫자로 따로 적혀 있어, 한 곳만 바꾸면 화면은 통과시키고 DB가 거부하는 상태가 될 수 있었다.

contracts 패키지에는 단위 시험 33개가 새로 생겼고, 서버의 검증 규칙 시험 일부가 contracts로 옮겨 가 API 단위 시험은 4개 줄었다.

### 브랜드 타입

마지막은 브랜드 타입이었다. 글 주소(slug)와 폴더 경로가 모두 `string`이라, 주소창에서 읽은 문자열을 검증 없이 `movePost`에 넘겨도 컴파일됐다. 브랜드 타입은 `string`에 컴파일러만 아는 표식을 붙여, 검증 함수를 거친 값만 그 타입으로 인정하게 하는 기법이다.

```ts
movePost('../etc', folder); // 전: 컴파일됨
movePost(postSlug(fromUrl), folderPath('개발 기록/MacFolio')); // 후: 검증 함수를 거쳐야 컴파일됨
```

런타임에는 일반 문자열이라 동작은 바뀌지 않는다([PostSlug·FolderPath 브랜드 타입](/memo/branded-ids)).

## 코드 수정 없이 바꾸는 사이트 정보

그전에는 이 저장소를 내려받아 배포하는 사람이 이름과 메일 주소를 바꾸려면 코드를 수정해야 했다. 프로필을 서버에 저장하고, 관리자가 시스템 설정 › 정보에서 수정하게 했다. 상수를 읽던 15곳은 구독 가능한 store를 읽게 바꿨다([#180](https://github.com/hyeoniverse/MacFolio/pull/180), [코드를 고치지 않고 프로필 바꾸기](/memo/site-profile-editing)). store는 값과 "값이 바뀌면 알려 달라"는 구독 목록을 함께 보관하는 객체다. 관리자가 이름을 저장하면 store가 구독한 화면에 바뀐 값을 전달하고, 새로고침 없이 화면이 갱신된다.

![시스템 설정 › 정보](./images/day-1011-profile.jpg '시스템 설정의 정보 화면. 관리자는 오른쪽 위 편집 버튼으로 이 내용을 수정한다')

다음 대상은 프로젝트였다. #187에서는 Safari의 프로젝트 페이지와 프로젝트 앱을 시스템 설정 › 프로젝트에서 관리하게 했다. 서버에는 코드의 기본값과 다른 필드만 저장하고, Cloudflare Worker가 첫 화면 HTML에 그 값을 삽입하고 데모 주소를 CSP에 추가한다. 예를 들어 관리자가 프로젝트의 데모 주소를 새 도메인으로 바꾸면, 그 도메인이 CSP의 iframe 허용 목록(`frame-src`)에 들어가야 프로젝트 앱 창에 페이지가 열린다. 이 브랜치에서 편집 모드, 기간 달력, 기술 칩과 후보 1,700여 개, npm 패키지 검색을 구현했다.

새 프로젝트용 페이지 템플릿은 하루 동안 방향을 세 번 바꿨다.

1. 어느 프로젝트에나 맞는 기본 템플릿 하나
2. 기존 7개 프로젝트의 페이지를 템플릿으로 다시 작성
3. 읽는 방식이 서로 다른 템플릿 12개

결국 기존 7개 프로젝트는 직접 작성한 페이지를 그대로 사용하게 했다. 템플릿 작업은 12일과 13일에도 이어졌다.

![템플릿 12개 중 cinema](./images/day-1011-cinema.jpg '#187 브랜치의 템플릿 12개 중 cinema. 한 화면씩 고정되는 장면 단위로 읽는다. 13일에 키노트 템플릿으로 통합됐다')

## 블로그 글이 메모 E2E를 실패시킨 일

메모 앱은 저장소의 `content/*.md` 파일을 글로 읽는다. 메모 앱의 E2E 시험(실제 브라우저로 화면을 조작하는 시험)도 이 글들을 그대로 사용한다. 예를 들어 "'인프라' 폴더를 누르면 그 폴더의 글이 나온다"는 시험은 실제 글의 카테고리에 의존한다.

이날 main이 한 번 실패했다. 블로그 폴더를 '개발기 › MacFolio' 아래로 재구성한 PR([#192](https://github.com/hyeoniverse/MacFolio/pull/192))과, 그 전에 작성한 글을 담은 PR들이 각자 CI를 통과한 뒤 main에서 합쳐졌다. 이전 카테고리를 지정한 글 한 편 때문에 '인프라' 폴더가 둘로 나뉘었고, 메모 E2E에서 '인프라' 버튼이 두 개 선택되어 실패했다. 해당 글의 카테고리를 고치고, 아직 머지하지 않은 PR의 글도 함께 고쳤다.

브랜치에서도 같은 유형의 실패가 있었다. 데모 파일 분할 글에 쓴 'Fast Refresh'라는 단어가 메모 검색 E2E에 영향을 줬다. 그 시험은 이 단어로 검색하면 글이 하나만 나와야 했다. ==블로그 글은 메모 앱 E2E의 시험 데이터이기도 하다.==

## 대소문자를 구분하지 않는 macOS

macOS에서만 실패한 경우도 있었다. 데모 파일을 분할하면서 같은 폴더에 `Slides.tsx`(컴포넌트)와 `slides.ts`(슬라이드 목록)가 생겼다. 파일 시스템에 따라 `Slides`와 `slides`를 같은 이름으로 보기도 하고 다른 이름으로 보기도 한다. CI가 쓰는 Linux의 ext4는 둘을 다른 파일로 보고, macOS의 기본 APFS 볼륨은 대소문자를 구분하지 않아 같은 이름으로 본다.

![대소문자를 구분하지 않는 파일 시스템에서 import가 다른 파일로 해석되는 과정](./images/day-1011-case-insensitive.svg '모듈 해석은 확장자 .ts를 .tsx보다 먼저 시도한다. Linux에서는 Slides.ts가 없어 Slides.tsx로 넘어가고, macOS에서는 slides.ts가 Slides.ts로 일치해 목록 파일을 불러왔다')

> [!WARNING] Linux CI가 잡지 못하는 실패
> Linux CI는 통과했지만, macOS에서는 `./Slides`가 `slides.ts`로 해석되어 타입 검사와 빌드가 실패했다. 목록 파일을 `slideDeck.ts`로 변경하고([#197](https://github.com/hyeoniverse/MacFolio/pull/197)), CONTRIBUTING에 파일 이름의 대소문자 규칙을 추가했다.

## 서버 하드닝 점검

하드닝(hardening)은 서버에서 쓰지 않는 서비스를 끄고, 외부에 열린 포트와 권한을 최소로 줄이는 작업이다. 서버 하드닝 상태를 문서에 적어 두는 대신 `ops/audit.sh`가 서버에서 직접 읽어 출력하게 했다([#183](https://github.com/hyeoniverse/MacFolio/pull/183), [#186](https://github.com/hyeoniverse/MacFolio/pull/186), [서버 하드닝은 스크립트로](/memo/server-hardening-audit)). 문서는 서버 상태가 바뀌어도 그대로 남지만, 스크립트는 실행할 때마다 현재 상태를 읽는다.

#183을 머지한 뒤 서버에 접속해 스크립트를 실행했다. 첫 결과에서 "확인" 항목이 두 개였다. SSH(22) 외에 `0.0.0.0:111`(rpcbind)이 외부 인터페이스에서 수신 대기 중이었고, 호스트 방화벽 규칙을 읽지 못했다. rpcbind는 NFS(네트워크 파일 공유) 같은 RPC 서비스가 어느 포트에서 동작하는지 알려 주는 서비스다. 이 서버는 NFS를 쓰지 않으므로 필요 없고, `0.0.0.0`은 "모든 네트워크 인터페이스"라는 뜻이라 외부에서도 접속을 시도할 수 있었다.

```bash
cd ~/macfolio && git pull && ops/audit.sh
# [포트] 외부에서 수신 대기 중인 포트
#         tcp 0.0.0.0:111      ← rpcbind
#         tcp 0.0.0.0:22
#   확인  SSH 외에 외부에서 수신 대기 중인 포트가 있다
sudo systemctl disable --now rpcbind.socket rpcbind.service
sudo reboot
```

`rpcbind.socket`까지 함께 끈 이유는, systemd가 소켓을 열어 두고 있다가 접속이 오면 서비스를 다시 시작하기 때문이다. 재부팅한 뒤 다음을 확인했다.

| 단계               | 확인 방법                          | 결과                                                        |
| ------------------ | ---------------------------------- | ----------------------------------------------------------- |
| 재부팅 후 컨테이너 | `cd ~/deploy && docker compose ps` | api·db·tunnel 실행 중 (api는 `health: starting` 후 healthy) |
| 포트               | `ops/audit.sh` 재실행              | `OK SSH(22) 말고 바깥에서 듣는 포트 없음`                   |
| 방화벽             | `sudo iptables -S INPUT`           | 22번만 허용하는 규칙                                        |

스크립트 자체의 오류도 두 가지 찾았다. cloudflared 이미지에는 `id`·`sh` 명령이 없어서 "root가 아닌 사용자" 검사가 ==오류 메시지를 OK로 출력했고==, 방화벽 규칙은 sudo 없이 읽을 수 없었다. 이 두 가지를 #186에서 고치고 다시 실행하자 모든 항목이 OK로 나왔다. 점검 항목과 대응 방법은 [docs/deployment.md](https://github.com/hyeoniverse/MacFolio/blob/main/docs/deployment.md)의 '서버 하드닝 점검'과 [ops/audit.sh](https://github.com/hyeoniverse/MacFolio/blob/main/ops/audit.sh)에 있다.

전날 활성화한 GitHub Push protection은 화면에 "Block commits that contain supported secrets" 문구가 별도로 표시되지 않았는데, Secret Protection과 함께 이미 활성화된 상태였다.

## 그 밖의 변경

- PR 미리보기 주소에는 CORS로 읽기만 허용하고 관리자 쿠키는 허용하지 않는다([#182](https://github.com/hyeoniverse/MacFolio/pull/182), [미리보기 주소에는 읽기만](/memo/preview-cors-read-only)). CORS는 브라우저가 다른 출처(도메인·포트·프로토콜이 다른 주소)의 응답을 페이지 코드에 넘겨도 되는지 서버의 허락을 확인하는 규칙이다. 미리보기 주소에서 보낸 요청은 쿠키 없이 공개 데이터만 읽을 수 있고, 관리자 경로는 허용 목록에 정확히 등록된 출처가 아니면 403으로 거부한다
- 휴지통이 비면 Dock과 휴지통 창에 빈 휴지통 아이콘을 표시한다([#184](https://github.com/hyeoniverse/MacFolio/pull/184), [같은 탭에는 오지 않는 storage 이벤트를 주기 확인으로 보완하기](/memo/bin-app#빈-휴지통-아이콘과-빈-창))
- 시스템 설정에서 스크롤 영역이 이중으로 생기던 문제를 수정하고, 창의 최소 크기를 680×420으로 지정했다([#195](https://github.com/hyeoniverse/MacFolio/pull/195), [스크롤이 두 번 되던 것](/memo/settings-double-scroll))

## 돌아보며

계획을 미리 작성한 덕분에 빠르게 진행했다. 항목마다 무엇을 어디로 옮길지 정해져 있어서, PR마다 범위를 다시 정할 필요 없이 옮기기만 하면 됐다. 그리고 옮기는 작업은 단순한 정리가 아니었다. 두 곳에 따로 정의된 값은 시간이 지나면 조금씩 달라진다. `mine?`와 `mine`, 두 가지 문구, 세 곳의 40은 모두 한 곳으로 통합하면서 처음 드러났다.

PR이 몰려 머지되는 동안 main CI는 대부분 끝까지 실행되지 못했다. CI 설정의 `concurrency.cancel-in-progress`는 같은 브랜치에 새 push가 오면 이전 실행을 취소한다. PR 브랜치에서는 낡은 커밋의 검사를 생략해 시간을 아끼는 설정이지만, main에서는 다음 그림처럼 동작한다.

![concurrency cancel-in-progress로 연속 머지의 CI가 취소되는 과정](./images/day-1011-ci-cancel.svg '연속으로 머지하면 앞의 실행이 모두 취소되고, 마지막 머지 커밋만 끝까지 검사된다')

```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

==이날 main의 CI 실행 28회 중 18회가 취소됐다.== 연속으로 머지한 PR들은 마지막 머지 커밋에서만 시험을 거쳤다. 블로그 카테고리 문제는 그 마지막 실행이 실패해서 드러났다. 전날 "머지한 뒤 main의 CI까지 확인해야 머지가 끝난다"라고 적었는데, 머지를 몰아서 하면 확인할 수 있는 실행 자체가 줄어든다.

블로그 글과 시험이 서로 연결되어 있다는 점도 두 번 확인했다. 글은 문서이지만 메모 앱에서는 시험 데이터다. 다음부터는 글을 추가하는 PR도 메모 E2E를 실행한 뒤 올린다.
