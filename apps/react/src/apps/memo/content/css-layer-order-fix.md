메일 앱에서 서버 응답이 실패하면 "서버에서 문제가 생겼습니다."가 뜬다. 이 문구가 데스크톱과 휴대폰 모두 12px로 작고, 위아래 목록에 여백 없이 붙어 있었다. 이 문구를 고치면서 같은 화면의 다른 여백도 살펴보다가, 본문 아래 "김정현에게 답장" 버튼의 파란 바탕이 글자에 딱 붙어 있는 것을 찾았다.

## 버튼의 안쪽 여백이 0이었다

아래에서 보겠지만 이 문제는 빌드한 결과에서만 생긴다. 개발 서버는 CSS를 import 순서대로 넣기 때문이다.

버튼의 계산된 스타일을 보니 `padding`이 `0px`였다. 이 버튼은 공통 컴포넌트 `Button`이고, 여백은 `.ui-button { padding: 5px 14px }`로 정해 두었다. 이 값을 이긴 규칙은 `index.css`의 `* { padding: 0 }`이었다.

둘 다 CSS 층(cascade layer) 안에 있다. [앱 루트 기본값을 reset 층으로 옮긴 글](/memo/css-layer-reset)에서 정한 순서는 이렇다.

```css
/* styles/layers.css: main.tsx가 가장 먼저 불러온다 */
@layer reset, components;
```

층끼리는 나중에 정한 층이 이긴다. 선택자 점수는 같은 층 안에서만 비교한다. 그래서 `.ui-button`(점수 0,1,0)이든 `*`(0,0,0)든 상관없이, `components` 층의 여백이 `reset` 층을 이겨야 한다. 이 순서를 믿고 `Button.css`는 `!important` 없이 여백을 적었다.

```css
/* shared/ui/button/Button.css */
@layer components {
	.ui-button {
		padding: var(--ui-button-padding, 5px 14px);
		/* … */
	}
}
```

## 층 순서는 문서에서 처음 나온 곳이 정한다

![빌드한 HTML에서 CSS 파일이 붙는 순서와 층 순서](./images/css-layer-order-fix.svg '공통 컴포넌트 CSS가 든 파일이 먼저 붙어 components 층이 먼저 정해졌다')

`@layer reset, components;`라는 선언이 있어도, 브라우저는 문서 안에서 그 층 이름이 처음 나온 순서로 층 순서를 정한다. 빌드한 `index.html`을 보니 CSS 파일이 이렇게 붙어 있었다.

```html
<link rel="stylesheet" href="/assets/repository-….css" /> <link rel="stylesheet" href="/assets/main-….css" />
```

`repository-….css`는 여러 앱이 함께 쓰는 코드를 묶은 파일이고, 공통 컴포넌트의 CSS가 들어 있다. 첫 줄이 `@layer components { … }`다. 이 파일이 `main-….css`보다 먼저 붙으니, 문서에 처음 나온 층은 `components`이고 `reset`은 그다음이다. 그러면 순서가 `components, reset`으로 정해져 `reset`이 이긴다.

왜 공통 컴포넌트 CSS가 먼저 붙었나. Vite(Rollup)는 여러 진입점이 함께 쓰는 모듈을 따로 묶어 공용 덩어리(chunk)를 만들고, 그 덩어리의 CSS도 따로 뺀다. 공통 `Button`은 앱 여러 개가 불러 쓰니 공용 덩어리로 갔다. HTML에는 의존 순서대로 공용 덩어리의 CSS가 먼저, 진입점(`main`)의 CSS가 나중에 붙는다. 개발 서버는 모듈마다 `<style>`을 import 순서대로 넣기 때문에 `main.tsx`가 가장 먼저 부르는 `layers.css`가 맨 앞에 와서 문제가 없었다.

`layers.css`의 순서 선언은 `main-….css` 안에 들어가 있어서 너무 늦었다. 게다가 빌드 결과에는 선언 한 줄이 따로 남지 않고 바로 뒤의 `@layer reset { … }`과 합쳐져 있었다.

![개발 서버는 layers.css가 맨 앞, 빌드는 공용 CSS가 맨 앞이라 층 순서가 뒤집혔다. 인라인 선언이 이를 고친다](./images/css-layer-order-fix-dev-vs-build.svg '같은 코드라도 개발 서버와 빌드 결과에서 층 순서가 달랐다')

## 고를 수 있던 방법

| 방법                                                      | 좋은 점                           | 나쁜 점                                                              |
| --------------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------- |
| `.ui-button`에 `!important`                               | 한 줄로 끝난다                    | 층을 만든 이유(점수 싸움 없애기)를 버린다. 다른 공통 컴포넌트도 같다 |
| 공통 컴포넌트 CSS마다 맨 앞에 `@layer reset, components;` | 어느 파일이 먼저 와도 순서가 같다 | 파일이 늘 때마다 잊지 않고 적어야 한다                               |
| 빌드 설정으로 CSS 파일 순서를 고정                        | HTML이 바뀌지 않는다              | 덩어리 나누기를 건드려야 한다. 버전마다 동작이 다를 수 있다          |
| `index.html` 인라인 `<style>` 맨 앞에 선언                | 모든 CSS보다 앞. 한 곳            | 개발 서버용 `layers.css`와 두 곳에 같은 줄이 생긴다                  |

마지막을 골랐다. HTML 문서에서 인라인 스타일은 빌드가 어떻게 파일을 나누든 맨 앞에 있다. 같은 줄이 두 곳에 생기는 것은 주석으로 서로를 가리켜 두었다.

## 고친 것

층 순서 선언을 `index.html`의 `<style>` 맨 앞으로 옮겼다. 이 인라인 스타일은 빌드가 붙이는 어떤 CSS 파일보다 앞에 있다.

```html
<style>
	@layer reset, components;
	…
</style>
```

이 사이트의 보안 헤더(CSP)는 `style-src`에 `'unsafe-inline'`을 허용하고, 이미 로딩 화면용 인라인 스타일이 있어서 따로 바꿀 것이 없었다. `styles/layers.css`는 개발 서버용으로 그대로 둔다.

고친 뒤 답장 버튼의 `padding`은 `5px 14px`로 돌아왔다. 같은 파일에 묶인 다른 공통 컴포넌트도 이제 설계한 층 순서대로 그려진다.

![메일 앱 본문 아래 "김정현에게 답장" 버튼. 파란 바탕 안에 좌우 여백이 있다](./images/css-layer-order-fix-mail-button.jpg '고친 뒤의 답장 버튼. 안쪽 여백 5px 14px')

## 확인

이 글을 다듬으며 지금 빌드(main)를 미리보기 서버로 열어 다시 확인했다. 브라우저에서 `document.styleSheets`를 순서대로 읽고, 각 시트에 처음 나오는 층 이름을 뽑았다.

| 순서 | 시트                     | 처음 나오는 층        |
| ---- | ------------------------ | --------------------- |
| 1    | 인라인 `<style>`         | `reset, components`   |
| 2    | `MobileNavigation-….css` | `components`          |
| 3    | `boot-….css`             | `reset`, `components` |

공용 덩어리의 CSS(지금 이름은 `MobileNavigation-….css`)는 여전히 진입점 CSS보다 먼저 온다. 파일 이름은 빌드마다 바뀌지만 "공용 CSS가 먼저"라는 모양은 그대로다. 인라인 선언이 없었다면 지금도 같은 일이 생긴다는 뜻이다. 답장 버튼의 계산된 `padding`은 `5px 14px`였다.

PR은 [#221](https://github.com/hyeoniverse/MacFolio/pull/221)이고, 커밋은 파일 7개, +136/−2다. 이 중 층 고치기는 `index.html`의 7줄(주석 포함)이 전부다.

## 메일 불러오기 오류

목록 전체를 불러오지 못했다는 오류는 입력 칸 하나의 오류와 무게가 다르다. 칸 오류(`.mail-error`, 12px)를 그대로 쓰지 않고 `.mail-load-error`를 따로 두었다.

|           | 데스크톱                      | 휴대폰                             |
| --------- | ----------------------------- | ---------------------------------- |
| 글자 크기 | 13px                          | 15px (본문 크기)                   |
| 바깥 여백 | 위 4px, 아래 10px, 좌우 12px  | 위 16px (메일상자 묶음과 떨어지게) |
| 모양      | 흐린 글자, 빨간 느낌표 아이콘 | 같은 모양                          |

처음에는 연한 빨간 바탕의 상자로 감쌌지만, 목록 위에 빨간 덩어리가 놓여 화면에서 가장 눈에 띄는 것이 오류가 되었다. 바탕을 빼고 글자는 흐린 색(`--mail-muted`)으로, 빨간색은 아이콘에만 남겼다. 여백과 크기만으로도 목록과 충분히 구분된다.

## 쓰기 창의 칸 오류

빈 칸으로 보내기를 누르면 칸마다 "이름을 입력해주세요." 같은 문구가 칸 아래 줄로 내려가고, 칸 밑줄이 빨갛게 바뀌었다. 칸마다 줄이 하나씩 늘어 화면이 출렁이고, 빨간 밑줄 네 개가 겹쳐 보였다.

같은 줄 오른쪽 끝, **필수** 배지, 칸 아래 별도 줄, 안내 글자(placeholder) 바꾸기, 이름표만 빨갛게를 차례로 시도했지만 모두 칸 사이에 오류가 끼어 산만했다. 결국 macOS 메일처럼 칸 사이에는 아무것도 적지 않기로 했다.

- **빈 칸**: 네 칸이 모두 차야 보내기 버튼이 눌린다(`disabled`). 공백만 있는 칸도 빈 칸으로 본다. 무엇을 채워야 하는지는 칸 이름표가 이미 말해 준다.
- **형식·길이 오류**: 보내기를 누르면 공통 경고창(`AlertDialog`)에 "이메일 형식을 확인해주세요." 같은 문구 하나를 띄운다. 확인을 누르면 경고창만 닫히고 쓰던 내용은 그대로 남는다. 서버가 보내기를 거절했을 때도 같은 경고창을 쓴다.
- **Esc**: 쓰기 창은 Esc로 닫히는데, 경고창이 떠 있을 때는 경고창만 닫도록 쓰기 창의 Esc 처리를 건너뛴다.

## 남은 것과 배운 것

- 층 순서를 지키는 자동 시험은 아직 없다. E2E는 개발 서버가 아니라 빌드 결과로 도는데도, 버튼 여백을 재는 시험이 없어서 이번 일을 잡지 못했다. 공통 버튼 하나의 계산된 `padding`을 보는 시험을 더하면 같은 일이 다시 생길 때 바로 안다.
- `styles/layers.css`와 `index.html`에 같은 선언이 있다. 층을 하나 더 만들 때 두 곳을 같이 고쳐야 한다. 두 파일의 주석이 서로를 가리킨다.

배운 것: CSS 층 순서는 "선언한 곳"이 아니라 "문서에서 처음 나온 곳"이 정한다. 그리고 그 "처음"은 개발 서버와 빌드 결과에서 다를 수 있다. 빌드 도구가 파일을 나누는 방식이 CSS 결과를 바꾼다는 것을 이번에 처음 겪었다. 이후로 스타일 문제는 빌드 결과로 한 번 더 본다.
