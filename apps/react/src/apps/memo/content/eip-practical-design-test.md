## 들어가기 전에

정보처리기사 실기는 보기 없이 답을 직접 쓰는 필답형 시험이다. 필기에서는 "다음 중 결합도가 가장 약한 것은?" 같은 문제에 네 보기 중 하나를 고르면 되지만, 실기에서는 "결합도를 약한 것부터 순서대로 쓰시오"처럼 용어를 정확한 철자로 직접 써야 한다. 영문 약어(MC/DC, EAI, CCB)나 영문 원어(Stub, Driver)를 쓰라는 문제도 나온다. 그래서 실기 공부는 "개념을 안다"에서 끝나지 않고 "빈칸에 들어갈 단어를 손으로 쓸 수 있다"까지 가야 한다.

이 글은 실기 출제기준의 주요 항목 가운데 요구사항 확인, 통합 구현, 인터페이스 구현, 화면 설계, 애플리케이션 테스트 관리, 제품 소프트웨어 패키징(형상 관리)과 서버 프로그램 구현의 설계 부분을 묶어 다룬다. 이 영역은 소프트웨어 공학이라고 부르는 분야로, 코드를 작성하기 전에 무엇을 만들지 정하고(요구사항), 어떻게 나눌지 그리고(설계), 만든 결과가 맞는지 확인하는(테스트) 방법을 다룬다. 실기 시험 전체 구조와 답안 작성 요령은 연재의 9편인 [정보처리기사 실기 시험 구조와 답안 작성](/memo/eip-practical-overview)에서 다룬다.

## 요구사항 확인

### 요구사항 개발 4단계

요구사항(Requirement)은 소프트웨어가 해결해야 할 문제와 갖춰야 할 기능·성질을 적은 것이다. 요구사항이 잘못되면 그 위에 쌓은 설계와 코드가 모두 쓸모없어지기 때문에, 요구공학(Requirements Engineering)이라는 별도 분야가 이 일을 체계화한다. 요구공학은 요구사항을 만드는 요구사항 개발과, 만든 요구사항의 변경을 추적하는 요구사항 관리로 나뉜다. 요구사항 개발은 다음 4단계를 거친다.

| 단계 | 영문          | 하는 일                                                | 산출물·도구 예                           |
| ---- | ------------- | ------------------------------------------------------ | ---------------------------------------- |
| 도출 | Elicitation   | 이해관계자에게서 요구를 수집한다                       | 인터뷰, 설문, 관찰, 브레인스토밍, 워크숍 |
| 분석 | Analysis      | 수집한 요구의 충돌·누락·모호함을 찾고 범위를 정한다    | 자료 흐름도, 자료 사전, 유스케이스       |
| 명세 | Specification | 분석 결과를 검토 가능한 문서로 작성한다                | 요구사항 명세서(SRS)                     |
| 확인 | Validation    | 명세가 이해관계자의 의도와 맞는지, 빠짐없는지 검토한다 | 검토 회의, 프로토타입, 추적표            |

온라인 서점 프로젝트로 예를 들면, 도출 단계에서는 고객·물류 담당자·회계 담당자를 인터뷰해 "책을 검색하고 싶다", "재고가 0이면 주문을 막아야 한다" 같은 요구를 수집한다. 분석 단계에서는 "주문 즉시 배송"과 "결제 확인 후 배송"처럼 서로 부딪히는 요구를 찾아 하나로 정한다. 명세 단계에서는 "검색 결과는 2초 안에 표시한다"처럼 측정 가능한 문장으로 바꿔 명세서에 적고, 확인 단계에서는 이 명세서를 이해관계자와 함께 검토한다.

> [!NOTE] 확인(Validation)과 검증(Verification)
> 확인은 "올바른 제품을 만들고 있는가", 즉 사용자의 의도와 맞는지 따진다. 검증은 "제품을 올바르게 만들고 있는가", 즉 명세서대로 구현했는지 따진다. 테스트 절에서 다시 나오는 짝이다.

### 기능 요구사항과 비기능 요구사항

| 구분            | 뜻                                             | 온라인 서점 예                                                                      |
| --------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- |
| 기능 요구사항   | 시스템이 무엇을 하는지: 입력, 처리, 출력, 저장 | 도서 검색, 장바구니 담기, 주문 취소, 재고 차감                                      |
| 비기능 요구사항 | 시스템이 어떻게 동작해야 하는지: 품질과 제약   | 검색 응답 2초 이내, 연중 가동률 99.9%, 비밀번호 암호화 저장, 스마트폰 브라우저 지원 |

비기능 요구사항은 성능, 보안, 가용성, 신뢰성, 사용성, 유지보수성, 이식성처럼 품질 특성으로 분류한다. 소프트웨어 품질 특성의 국제 표준인 ISO/IEC 25010:2011은 기능 적합성, 성능 효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성의 8가지를 정의한다. ISO/IEC 25010의 전신인 ISO/IEC 9126은 기능성, 신뢰성, 사용성, 효율성, 유지보수성, 이식성의 6가지를 정의했고, 국내 수험서와 시험에는 이 6가지가 여전히 자주 나온다. 하드웨어 구성, 사용할 DBMS, 준수할 법규처럼 개발에 걸리는 제약 조건도 비기능 요구사항에 넣는다.

==구분 기준은 "기능이 있는가 없는가"가 아니라 "무엇을 하는가인가, 얼마나 잘 하는가인가"==다. "로그인 기능을 제공한다"는 기능 요구사항이고, "로그인 실패가 5회 이어지면 계정을 10분간 잠근다"는 보안 정책이지만 시스템이 수행하는 동작을 적었으므로 기능 요구사항으로 분류하기도 한다. 반면 "비밀번호는 단방향 해시로 저장한다"는 품질(보안) 제약이라 비기능 요구사항이다.

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 요구사항 문장 여러 개를 주고 기능과 비기능으로 나누게 하거나, 요구사항 개발 단계를 순서대로 쓰게 한다. 예: "다음 빈칸에 들어갈 단계를 쓰시오. 도출 → ( ① ) → 명세 → ( ② )" 정답은 ① 분석, ② 확인(검증).

### 구조적 분석 도구: 자료 흐름도와 자료 사전

객체지향 이전의 구조적 분석에서는 시스템을 데이터의 흐름으로 표현했다. 자료 흐름도(DFD, Data Flow Diagram)는 4가지 요소로 그린다.

| 요소        | 영문       | 기호           | 예           |
| ----------- | ---------- | -------------- | ------------ |
| 프로세스    | Process    | 원             | 주문 처리    |
| 자료 흐름   | Data Flow  | 화살표         | 주문 정보    |
| 자료 저장소 | Data Store | 평행한 두 직선 | 주문 파일    |
| 단말        | Terminator | 사각형         | 고객, 택배사 |

자료 사전(DD, Data Dictionary)은 자료 흐름도에 나온 데이터의 구성을 기호로 정의한다.

| 기호     | 뜻   | 예                                        |
| -------- | ---- | ----------------------------------------- |
| `=`      | 정의 | `주문 = 주문번호 + 고객명 + {주문항목}`   |
| `+`      | 연결 | `주소 = 시도 + 시군구 + 상세주소`         |
| `[ \| ]` | 선택 | `결제수단 = [카드 \| 계좌이체 \| 포인트]` |
| `{ }`    | 반복 | `{주문항목}`: 주문항목이 여러 번 반복     |
| `( )`    | 생략 | `(배송메모)`: 있어도 없어도 된다          |
| `* *`    | 주석 | `* 주문번호는 날짜 8자리 + 일련번호 *`    |

## UML

### UML의 구성

UML(Unified Modeling Language)은 소프트웨어 구조와 동작을 그림으로 표현하는 표준 모델링 언어다. 1990년대에 부치(Booch), 럼바우(Rumbaugh), 야콥슨(Jacobson)이 각자의 객체지향 표기법을 합쳐 만들었고, 지금은 표준화 단체 OMG(Object Management Group)가 관리한다. UML은 사물(Things), 관계(Relationships), 다이어그램(Diagrams)의 세 요소로 구성된다. 사물은 클래스·유스케이스·상태처럼 그림에 등장하는 대상이고, 관계는 사물 사이의 연결이며, 다이어그램은 사물과 관계를 목적에 맞게 모아 그린 그림이다.

### 관계 6가지

![UML 관계 6가지의 선과 화살표 모양](./images/eip-practical-design-test-uml-relations.svg '실선·점선 구분과, 마름모·삼각형·열린 화살표가 붙는 위치를 비교한다')

| 관계       | 영문           | 표기                             | 뜻                                                 | 예                         |
| ---------- | -------------- | -------------------------------- | -------------------------------------------------- | -------------------------- |
| 연관       | Association    | 실선 (방향이 있으면 열린 화살표) | 두 사물이 서로 관련되어 있다                       | 학생 ― 강의                |
| 집합       | Aggregation    | 실선 + 전체 쪽에 빈 마름모       | 전체와 부분이지만 부분이 독립적으로 존재할 수 있다 | 팀과 선수                  |
| 포함(합성) | Composition    | 실선 + 전체 쪽에 채운 마름모     | 전체가 사라지면 부분도 함께 사라진다               | 주문과 주문항목            |
| 일반화     | Generalization | 실선 + 부모 쪽에 빈 삼각형       | 자식이 부모의 한 종류다 (is-a)                     | 고양이 → 동물              |
| 의존       | Dependency     | 점선 + 열린 화살표               | 한 사물이 다른 사물을 잠깐 사용한다 (매개변수 등)  | 주문서비스 → 결제API       |
| 실체화     | Realization    | 점선 + 빈 삼각형                 | 클래스가 인터페이스의 기능을 구현한다              | 카드결제 → 결제 인터페이스 |

집합과 포함은 둘 다 "전체와 부분" 관계라서 헷갈린다. 구분 기준은 생명주기다. 팀이 해체되어도 선수는 다른 팀으로 옮겨 계속 존재하므로 집합이고, 주문을 삭제하면 그 주문의 주문항목 행은 의미가 없어 함께 삭제되므로 포함이다. 연관과 의존의 차이는 관계가 유지되는 기간이다. 연관은 한 클래스가 다른 클래스를 멤버 변수로 보관해 계속 참조하는 관계이고, 의존은 메서드의 매개변수나 지역 변수로 잠깐 사용하고 끝나는 관계다.

연관 선 양 끝에는 다중도(Multiplicity)를 적어 몇 개가 연결되는지 표시한다.

| 표기            | 뜻           |
| --------------- | ------------ |
| `1`             | 정확히 1개   |
| `0..1`          | 0개 또는 1개 |
| `*` 또는 `0..*` | 0개 이상     |
| `1..*`          | 1개 이상     |

### 클래스 다이어그램

클래스 다이어그램은 시스템을 구성하는 클래스와 그 속성·연산, 클래스 사이의 관계를 표현한다. 클래스 상자는 세 칸으로 나뉘며 위부터 이름, 속성, 연산을 적는다. 속성과 연산 앞의 기호는 접근 제어자다.

| 기호 | 접근 제어자 | 접근 범위                 |
| ---- | ----------- | ------------------------- |
| `+`  | public      | 어디서나                  |
| `-`  | private     | 클래스 내부만             |
| `#`  | protected   | 같은 패키지와 하위 클래스 |
| `~`  | package     | 같은 패키지               |

![온라인 주문 시스템의 클래스 다이어그램](./images/eip-practical-design-test-class-diagram.svg '한 그림 안에 연관·합성·일반화·의존·실체화 다섯 관계가 모두 나온다')

위 그림을 문장으로 읽으면 다음과 같다. 회원 1명은 주문을 0개 이상 가진다(연관, 다중도 1 대 `*`). 주문은 주문항목을 1개 이상 포함하고 주문이 사라지면 주문항목도 사라진다(합성). VIP회원은 회원의 한 종류다(일반화). 주문은 결제 인터페이스를 사용하며(의존), 카드결제 클래스가 결제 인터페이스를 구현한다(실체화).

### 다이어그램 종류

UML 2는 14가지 다이어그램을 정의하며 크게 구조 다이어그램과 행위 다이어그램으로 나눈다. 구조 다이어그램은 시스템의 정적인 구성을, 행위 다이어그램은 시간에 따른 동작을 표현한다. 행위 다이어그램 가운데 객체 사이의 메시지 교환을 다루는 4가지를 따로 상호작용 다이어그램이라고 부른다.

| 구분     | 다이어그램                           | 표현하는 것                                              |
| -------- | ------------------------------------ | -------------------------------------------------------- |
| 구조     | 클래스 (Class)                       | 클래스, 속성, 연산, 클래스 사이의 관계                   |
| 구조     | 객체 (Object)                        | 특정 시각의 객체(인스턴스)와 그 값, 연결                 |
| 구조     | 컴포넌트 (Component)                 | 실제 구현 모듈(컴포넌트)과 인터페이스                    |
| 구조     | 배치 (Deployment)                    | 서버·기기 같은 물리적 노드와 그 위에 배치된 산출물       |
| 구조     | 복합체 구조 (Composite Structure)    | 클래스·컴포넌트의 내부 구조                              |
| 구조     | 패키지 (Package)                     | 요소를 묶은 패키지와 패키지 사이의 의존                  |
| 구조     | 프로파일 (Profile)                   | UML을 특정 분야에 맞게 확장하는 스테레오타입             |
| 행위     | 유스케이스 (Use Case)                | 사용자(액터) 관점에서 본 시스템의 기능                   |
| 행위     | 활동 (Activity)                      | 처리 흐름과 조건 분기, 병렬 처리                         |
| 행위     | 상태 (State Machine)                 | 한 객체가 사건에 따라 상태를 바꾸는 과정                 |
| 상호작용 | 시퀀스 (Sequence)                    | 객체 사이 메시지를 시간 순서로                           |
| 상호작용 | 커뮤니케이션 (Communication)         | 객체 사이 메시지를 연결 구조 중심으로 (번호로 순서 표시) |
| 상호작용 | 상호작용 개요 (Interaction Overview) | 여러 상호작용 다이어그램을 활동 다이어그램 형태로 연결   |
| 상호작용 | 타이밍 (Timing)                      | 객체 상태가 바뀌는 시각과 시간 제약                      |

국내 수험서는 프로파일을 빼고 구조 6가지, 행위 7가지로 정리하는 경우가 많다. 시험에서는 구조와 행위 중 어느 쪽인지 고르게 하거나, 설명을 주고 다이어그램 이름을 쓰게 한다. 아래에서 자주 나오는 다이어그램 4가지를 예시로 그린다.

#### 유스케이스 다이어그램

유스케이스 다이어그램은 사용자가 시스템으로 무엇을 할 수 있는지를 기능 단위로 보여 준다. 요구사항 분석 단계에서 이해관계자와 범위를 합의하는 데 쓴다.

![도서 대출 시스템의 유스케이스 다이어그램](./images/eip-practical-design-test-usecase.svg 'include 화살표는 기본 유스케이스에서 나가고, extend 화살표는 확장 유스케이스에서 기본 쪽으로 들어온다')

| 구성 요소      | 뜻                                                                   |
| -------------- | -------------------------------------------------------------------- |
| 액터 (Actor)   | 시스템 밖에서 시스템과 상호작용하는 사람이나 외부 시스템 (사람 모양) |
| 유스케이스     | 사용자가 얻는 기능 하나 (타원)                                       |
| 시스템 경계    | 시스템 범위를 나타내는 사각형                                        |
| 포함 (include) | 기본 유스케이스를 수행할 때마다 ==반드시== 함께 수행하는 기능        |
| 확장 (extend)  | 특정 조건을 만족하는 경우에만 추가로 수행하는 기능                   |

그림에서 "도서 대출"은 매번 "회원 인증"을 거치므로 포함 관계이고, "연체료 결제"는 연체가 있는 경우에만 "반납 처리"에 덧붙으므로 확장 관계다. 화살표 방향이 반대라는 점이 시험 포인트다. 포함은 기본 → 포함되는 쪽, 확장은 확장하는 쪽 → 기본으로 그린다.

#### 시퀀스 다이어그램

시퀀스 다이어그램은 객체들이 주고받는 메시지를 위에서 아래로 시간 순서대로 표현한다.

![로그인 과정의 시퀀스 다이어그램](./images/eip-practical-design-test-sequence.svg '세로 점선이 생명선, 그 위의 흰 막대가 실행 중인 구간, 점선 화살표가 응답 메시지다')

| 구성 요소              | 뜻                                                       |
| ---------------------- | -------------------------------------------------------- |
| 액터·객체              | 맨 위 상자. 객체는 `이름:클래스` 또는 `:클래스`로 적는다 |
| 생명선 (Lifeline)      | 객체가 존재하는 기간을 나타내는 세로 점선                |
| 실행 사양 (Activation) | 객체가 동작 중인 구간을 나타내는 가늘고 긴 사각형        |
| 메시지                 | 실선 화살표: 호출, 점선 화살표: 응답(반환)               |
| 자체 메시지            | 객체가 자기 자신에게 보내는 메시지 (그림의 5번)          |

#### 활동 다이어그램

활동 다이어그램은 처리 흐름을 순서도처럼 표현하되, 병렬로 동시에 수행되는 흐름까지 그릴 수 있다.

![주문 처리 활동 다이어그램](./images/eip-practical-design-test-activity.svg '재고 조건에 따라 갈라지고, 재고가 있으면 결제 승인과 포장이 병렬로 진행된 뒤 합쳐진다')

조건 분기는 마름모(결정 노드)로, 병렬 분기와 병합은 굵은 막대(포크·조인 노드)로 그린다. 조건 분기는 여러 갈래 중 하나만 진행하지만, 포크는 모든 갈래를 동시에 진행하고 조인에서 모든 갈래가 끝날 때까지 기다린다. 담당 부서별로 영역을 세로로 나누는 스윔레인(Swimlane)을 추가하면 누가 어떤 활동을 맡는지도 표현할 수 있다.

#### 상태 다이어그램

상태 다이어그램은 한 객체가 사건(Event)에 따라 어떤 상태에서 어떤 상태로 옮겨 가는지 표현한다. 주문, 회원 계정, 신호등처럼 상태가 분명한 대상을 모델링하는 데 쓴다.

![주문 객체의 상태 다이어그램](./images/eip-practical-design-test-state.svg '배송중 상태에서는 취소로 가는 화살표가 없으므로 배송중에 취소 요청은 허용되지 않는다')

이 그림은 뒤에 나오는 상태 전이 테스트의 입력이 된다. 다이어그램에 없는 전이(배송중 → 취소)를 시도하면 시스템이 거부하는지도 테스트 대상이다.

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 다이어그램 그림을 주고 이름을 쓰게 하거나, 관계 화살표에 번호를 붙여 관계 이름을 쓰게 한다. 예: "클래스 A가 인터페이스 B의 연산을 구현하며, 점선과 속이 빈 삼각형으로 표시하는 관계를 쓰시오." 정답은 실체화(Realization).

## 모듈화, 결합도와 응집도

### 모듈화

모듈(Module)은 시스템을 기능 단위로 나눈 독립적인 부분이다. C 언어의 함수와 소스 파일, Java의 클래스와 패키지가 모듈에 해당한다. 모듈화(Modularity)는 시스템을 모듈로 나눠 각 모듈을 따로 개발·테스트·수정할 수 있게 만드는 설계 원리다. 모듈을 잘 나눴는지는 두 기준으로 평가한다.

| 기준   | 영문     | 무엇을 재는가                     | 바람직한 방향 |
| ------ | -------- | --------------------------------- | ------------- |
| 결합도 | Coupling | 모듈과 모듈 사이의 의존 정도      | 낮게 (약하게) |
| 응집도 | Cohesion | 한 모듈 내부 요소들이 관련된 정도 | 높게 (강하게) |

결합도가 높으면 한 모듈을 고칠 때마다 연결된 다른 모듈도 함께 고쳐야 한다. 응집도가 낮으면 한 모듈 안에 서로 관계없는 기능이 섞여 있어, 그 모듈의 역할을 한 문장으로 설명할 수 없다.

![결합도 6단계와 응집도 7단계의 순서](./images/eip-practical-design-test-coupling-cohesion.svg '결합도는 왼쪽(자료)이 가장 좋고, 응집도도 왼쪽(기능적)이 가장 좋다')

### 결합도 6가지

약한(좋은) 것부터 강한(나쁜) 순서다.

| 순서 | 결합도 | 영문              | 뜻                                                                     | 예                                                          |
| ---- | ------ | ----------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------- |
| 1    | 자료   | Data Coupling     | 모듈 사이에 단순한 값(자료 요소)만 주고받는다                          | `area(width, height)`                                       |
| 2    | 스탬프 | Stamp Coupling    | 배열·구조체 같은 자료 구조를 통째로 넘기고, 받는 쪽은 그중 일부만 쓴다 | 학생 구조체 전체를 넘겨 학번만 사용                         |
| 3    | 제어   | Control Coupling  | 상대 모듈의 처리 흐름을 결정하는 제어 신호(플래그)를 넘긴다            | `print(data, mode)`에서 mode가 1이면 PDF, 2면 화면          |
| 4    | 외부   | External Coupling | 외부에서 정한 데이터 형식, 통신 프로토콜, 장치 인터페이스를 공유한다   | 두 모듈이 같은 외부 파일 형식에 맞춰 읽고 쓴다              |
| 5    | 공통   | Common Coupling   | 여러 모듈이 같은 전역 변수(공통 데이터 영역)를 사용한다                | 전역 변수 `total`을 세 함수가 읽고 쓴다                     |
| 6    | 내용   | Content Coupling  | 한 모듈이 다른 모듈의 내부 데이터나 코드를 직접 참조·수정한다          | 다른 모듈 내부로 goto, 다른 객체의 private 필드를 직접 변경 |

국내 수험서는 외부 결합도를 "한 모듈에서 선언한 데이터(변수)를 외부의 다른 모듈에서 참조하는 경우"로 설명하는 경우가 많으므로, 두 설명을 모두 알아 두면 안전하다.

순서를 외우려면 첫 글자를 이어 "자스제외공내"로 외운다. 자료 결합도와 스탬프 결합도의 차이는 넘기는 것이 값 하나인지 묶음인지다. 제어 결합도가 나쁜 이유는 호출하는 쪽이 호출당하는 쪽의 내부 처리 방식을 알아야 플래그 값을 정할 수 있기 때문이다.

### 응집도 7가지

강한(좋은) 것부터 약한(나쁜) 순서다.

| 순서 | 응집도         | 영문                   | 뜻                                                                         | 예                                                       |
| ---- | -------------- | ---------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------- |
| 1    | 기능적         | Functional Cohesion    | 모든 요소가 하나의 기능을 수행하기 위해 모여 있다                          | `calculateTax()`                                         |
| 2    | 순차적         | Sequential Cohesion    | 한 활동의 출력이 다음 활동의 입력으로 이어진다                             | 파일 읽기 → 파싱 → 검증                                  |
| 3    | 교환적(통신적) | Communication Cohesion | 같은 입력이나 같은 출력을 사용하는 서로 다른 기능이 모여 있다              | 같은 주문 데이터로 영수증 출력과 통계 갱신               |
| 4    | 절차적         | Procedural Cohesion    | 정해진 순서로 수행해야 하는 여러 기능이 모여 있지만 데이터는 넘기지 않는다 | 문 잠금 확인 → 경보 켜기 → 조명 끄기                     |
| 5    | 시간적         | Temporal Cohesion      | 같은 시각에 함께 실행된다는 이유로 모여 있다                               | 프로그램 시작 시각의 초기화 모듈                         |
| 6    | 논리적         | Logical Cohesion       | 성격이 비슷한 처리들이 한 모듈에 모여 있고, 플래그로 하나를 골라 실행한다  | 모든 입력(키보드·파일·네트워크)을 처리하는 `input(type)` |
| 7    | 우연적         | Coincidental Cohesion  | 요소 사이에 아무 관련이 없다                                               | `Utils` 클래스에 날짜 변환과 이메일 발송이 함께 있다     |

외우는 순서는 "기순교절시논우"다. 결합도는 약한 것이, 응집도는 강한 것이 좋으므로 ==두 표 모두 1번이 가장 좋은 설계==라는 점에서 방향이 같다. 시험에서 "가장 바람직한 것부터 쓰시오"라고 하면 두 표 모두 위에서부터 쓰면 된다.

> [!WARNING] 헷갈리는 짝
> 순차적 응집도와 절차적 응집도는 둘 다 순서가 있다. 앞 단계의 ==출력 데이터가 다음 단계의 입력==으로 이어지면 순차적, 순서만 있고 데이터는 이어지지 않으면 절차적이다. 논리적 응집도와 제어 결합도는 둘 다 플래그가 나온다. 모듈 안에서 플래그로 기능을 고르는 구조는 논리적 응집도, 모듈 사이에서 플래그를 넘기는 관계는 제어 결합도다.

### 팬인과 팬아웃

팬인(Fan-In)은 어떤 모듈을 호출(제어)하는 상위 모듈의 수이고, 팬아웃(Fan-Out)은 어떤 모듈이 호출하는 하위 모듈의 수다. 예를 들어 모듈 `log()`를 `login()`, `order()`, `pay()` 세 모듈이 호출하면 `log()`의 팬인은 3이다. 팬인이 높으면 재사용이 잘 되는 모듈이지만 그만큼 고장 나면 영향이 크고, 팬아웃이 높으면 그 모듈이 너무 많은 일을 직접 지휘하고 있다는 신호다. 일반적으로 팬인은 높이고 팬아웃은 낮추는 설계를 권장한다.

<details>
<summary>팬인·팬아웃 계산 예제</summary>

모듈 호출 관계가 다음과 같다고 하자. 화살표는 "호출한다"는 뜻이다.

| 호출하는 모듈 | 호출당하는 모듈 |
| ------------- | --------------- |
| Main          | A, B, C         |
| A             | D, E            |
| B             | E               |
| C             | E, F            |

1. E를 호출하는 모듈은 A, B, C이므로 E의 팬인은 3이다.
2. Main이 호출하는 모듈은 A, B, C이므로 Main의 팬아웃은 3이다.
3. C의 팬인은 1(Main), 팬아웃은 2(E, F)다.

</details>

## 디자인 패턴

### GoF 디자인 패턴이란

디자인 패턴(Design Pattern)은 소프트웨어 설계에서 반복해서 나타나는 문제와 그 해법을 이름 붙여 정리한 것이다. 1994년 감마(Gamma), 헬름(Helm), 존슨(Johnson), 블리시디스(Vlissides) 네 사람이 쓴 책 『Design Patterns: Elements of Reusable Object-Oriented Software』가 23개 패턴을 정리했고, 저자 네 명을 GoF(Gang of Four)라고 부르는 데서 GoF 디자인 패턴이라는 이름이 붙었다. 패턴 이름을 알면 "여기는 옵서버로 하자"처럼 설계 의도를 한 단어로 전달할 수 있다.

GoF는 패턴을 목적에 따라 생성, 구조, 행위의 세 가지로 나눈다.

![GoF 디자인 패턴 23개의 세 분류](./images/eip-practical-design-test-gof-map.svg '생성 5개, 구조 7개, 행위 11개를 한눈에 비교한다')

| 분류 | 영문       | 개수 | 다루는 문제                                 |
| ---- | ---------- | ---- | ------------------------------------------- |
| 생성 | Creational | 5    | 객체를 만드는 방법을 감추거나 유연하게 한다 |
| 구조 | Structural | 7    | 클래스와 객체를 조합해 더 큰 구조를 만든다  |
| 행위 | Behavioral | 11   | 객체 사이의 책임 분배와 통신 방법을 정한다  |

### 23개 패턴 한 줄 정리

| 분류 | 패턴                    | 한 줄 설명                                                              |
| ---- | ----------------------- | ----------------------------------------------------------------------- |
| 생성 | Abstract Factory        | 관련 객체 묶음(예: 윈도우용 버튼·체크박스)을 구체 클래스 지정 없이 생성 |

| 구조 | Composite               | 개별 객체와 객체 묶음을 같은 방식으로 다루는 트리 구조 (파일과 폴더)    |
| 구조 | Decorator               | 객체를 감싸 기능을 동적으로 덧붙인다 (상속 없이 기능 추가)              |

| 행위 | Chain of Responsibility | 요청을 처리할 수 있는 객체가 나올 때까지 사슬을 따라 넘긴다             |

| 행위 | Iterator                | 내부 구조를 노출하지 않고 컬렉션 요소에 순서대로 접근한다               |

| 행위 | Template Method         | 상위 클래스가 알고리즘 골격을 정하고 일부 단계를 하위 클래스가 구현한다 |
| 행위 | Visitor                 | 객체 구조는 그대로 두고 새로운 연산을 방문자 클래스로 추가한다          |

### 대표 패턴의 구조

![싱글턴, 어댑터, 옵서버 패턴의 클래스 구조](./images/eip-practical-design-test-pattern-structure.svg '생성·구조·행위 분류에서 하나씩 골라 클래스 다이어그램으로 그렸다')

싱글턴은 생성자를 `private`으로 막아 외부에서 `new`로 만들 수 없게 하고, 정적 메서드 `getInstance()`가 처음 호출된 시각에만 객체를 만든 뒤 이후에는 같은 객체를 돌려준다. 설정 정보나 데이터베이스 연결 풀처럼 프로그램 전체에서 하나만 있어야 하는 객체에 쓴다. 다음 Java 코드는 두 번 받아 온 참조가 같은 객체인지 확인한다.

```java
class Config {
    private static Config instance;
    private int count = 0;

    private Config() {}

    public static Config getInstance() {
        if (instance == null) instance = new Config();
        return instance;
    }

    public int next() { return ++count; }
}

public class Main {
    public static void main(String[] args) {
        Config a = Config.getInstance();
        Config b = Config.getInstance();
        a.next();
        b.next();
        System.out.println(a == b);
        System.out.println(a.next());
    }
}
```

실행 결과는 다음과 같다(OpenJDK로 실행).

```text
true
3
```

`a`와 `b`가 같은 객체이므로 `a == b`는 `true`이고, `a.next()`와 `b.next()`가 같은 `count`를 1씩 올려 세 번째 호출의 반환값이 3이 된다. 실기의 Java 코드 문제는 이런 식으로 패턴 코드를 주고 출력값을 묻기도 한다.

어댑터는 이미 있는 클래스(Adaptee)의 메서드 이름이나 매개변수가 새 시스템이 기대하는 인터페이스(Target)와 맞지 않으면, 중간에 Adapter를 두어 `request()` 호출을 `oldCall()` 호출로 바꿔 준다. 해외 여행용 전원 변환 플러그가 하는 일과 같은 구조다.

옵서버는 Subject(관찰 대상)가 Observer 목록을 보관하고, 상태가 바뀔 때마다 `notify()`가 목록의 모든 `update()`를 호출한다. 주문 상태가 바뀔 때마다 메일 알림과 앱 푸시를 동시에 보내는 기능이 이 구조다. 새 알림 수단을 추가하는 경우 Subject 코드를 고치지 않고 Observer 구현 클래스만 추가하면 된다는 점이 장점이다.

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 패턴 설명을 주고 이름을 쓰게 하거나, 패턴 이름 여러 개를 주고 생성·구조·행위로 분류하게 한다. 예: "기존 클래스를 수정하지 않고 객체를 감싸 새로운 책임을 동적으로 추가하는 구조 패턴을 쓰시오." 정답은 Decorator. 영문으로 쓰라는 조건이 붙는 경우가 많으므로 철자까지 외운다.

## 인터페이스 구현과 EAI

### 연계 방식

기업에는 회계, 인사, 주문, 물류처럼 따로 만든 시스템이 여러 개 있고, 이 시스템들이 데이터를 주고받아야 업무가 돌아간다. 송신 시스템이 데이터를 보내고 수신 시스템이 받아 반영하는 구조를 연계라고 하며, 중간에서 데이터 형식을 변환하는 연계 서버를 둘 수도 있다.

| 구분      | 방식                                                  | 설명                                                                       |
| --------- | ----------------------------------------------------- | -------------------------------------------------------------------------- |
| 직접 연계 | DB Link, DB Connection, API/Open API, JDBC, 화면 링크 | 중간 솔루션 없이 시스템끼리 직접 연결한다. 빠르고 단순하지만 결합도가 높다 |
| 간접 연계 | EAI, ESB, 웹 서비스, 소켓                             | 중간에 연계 솔루션을 둔다. 여러 시스템을 다루기 쉽지만 구축이 복잡하다     |

웹 서비스는 HTTP 위에서 XML 메시지로 서비스를 주고받는 방식으로, 메시지 형식을 정하는 SOAP(Simple Object Access Protocol), 서비스의 이름·주소·매개변수를 기술하는 WSDL(Web Services Description Language), 서비스를 등록·검색하는 UDDI(Universal Description, Discovery and Integration)로 구성된다. 요즘 웹 API는 XML 대신 JSON(JavaScript Object Notation) 형식을 많이 쓰며, 브라우저가 페이지 전체를 새로 받지 않고 필요한 데이터만 비동기로 받아 화면 일부를 갱신하는 기술을 AJAX(Asynchronous JavaScript and XML)라고 부른다.

### EAI 구축 유형 4가지

EAI(Enterprise Application Integration)는 기업 안의 여러 애플리케이션을 연결해 데이터와 프로세스를 통합하는 솔루션이다. 연결 구조에 따라 4가지 유형으로 나눈다.

![EAI 구축 유형 4가지의 연결 구조](./images/eip-practical-design-test-eai.svg '애플리케이션이 직접 연결되는지, 허브나 버스를 거치는지에 따라 유형이 갈린다')

| 유형                   | 구조                                                                | 장점                                 | 단점                                                             |
| ---------------------- | ------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------- |
| Point-to-Point         | 애플리케이션끼리 1:1로 직접 연결, 미들웨어 없음                     | 구조가 단순하고 소규모에서 빠르다    | 시스템이 n개면 연결이 최대 n(n−1)/2개로 늘어나고 재사용이 어렵다 |
| Hub & Spoke            | 중앙 허브를 거쳐 연결 (허브와 바퀴살 모양)                          | 확장과 유지보수가 쉽다               | 허브에 장애가 나면 전체 연계가 멈춘다                            |
| Message Bus (ESB 방식) | 애플리케이션 사이에 미들웨어 버스를 두고 버스로 메시지를 주고받는다 | 확장성이 좋고 대용량 처리에 유리하다 | 버스 구축 비용이 크다                                            |
| Hybrid                 | 그룹 안은 Hub & Spoke, 그룹 사이는 Message Bus                      | 상황에 맞게 혼합해 유연하다          | 구조가 복잡해진다                                                |

Point-to-Point에서 시스템이 4개면 연결은 최대 4×3/2 = 6개, 10개면 45개로 빠르게 늘어난다. 그림 왼쪽 위의 선 6개가 4개 시스템의 경우다. 이 문제를 줄이려고 허브나 버스로 연결을 한곳에 모은다.

ESB(Enterprise Service Bus)는 애플리케이션보다 서비스 단위로 통합하는 방식으로, 표준 프로토콜 기반의 버스에 서비스를 연결해 애플리케이션 사이 결합도를 낮춘다. EAI가 애플리케이션 통합에 초점을 둔다면 ESB는 서비스 지향 아키텍처(SOA)의 기반이 되는 서비스 통합에 초점을 둔다.

### 인터페이스 보안과 검증

| 구분          | 항목     | 설명                                                       |
| ------------- | -------- | ---------------------------------------------------------- |
| 네트워크 보안 | IPsec    | 네트워크 계층에서 IP 패킷 단위로 암호화·인증               |
| 네트워크 보안 | SSL/TLS  | 전송 계층과 응용 계층 사이에서 통신 구간을 암호화          |

## 화면 설계

### UI의 종류

UI(User Interface)는 사용자와 시스템이 정보를 주고받는 접점이고, UX(User Experience)는 사용자가 시스템을 쓰면서 느끼는 경험 전체다. 버튼 모양과 배치가 UI라면, "결제가 몇 번 만에 끝나서 편했다"는 느낌이 UX다.

| 종류 | 영문                     | 입력 방식                   | 예                        |
| ---- | ------------------------ | --------------------------- | ------------------------- |
| CLI  | Command Line Interface   | 명령어 텍스트               | 터미널, 명령 프롬프트     |
| GUI  | Graphical User Interface | 마우스, 아이콘, 창          | Windows, macOS 데스크톱   |
| NUI  | Natural User Interface   | 터치, 제스처 같은 신체 동작 | 스마트폰 손가락 확대·축소 |
| VUI  | Voice User Interface     | 음성                        | AI 스피커                 |
| OUI  | Organic User Interface   | 모든 사물이 입출력 장치     | 형태가 바뀌는 디스플레이  |

### UI 기본 원칙 4가지

| 원칙   | 무엇을 요구하는가                                                           | 예                                           |
| ------ | --------------------------------------------------------------------------- | -------------------------------------------- |
| 직관성 | 설명서 없이 보기만 해도 기능과 사용법을 알 수 있다                          | 휴지통 아이콘을 보면 삭제 기능임을 바로 안다 |
| 유효성 | 사용자가 하려던 일을 빠짐없이 정확하게 끝낼 수 있다                         | 주문 버튼을 누르면 실제로 주문이 완료된다    |
| 학습성 | 처음 쓰는 사람도 짧은 시간에 사용법을 익힐 수 있다                          | 한 번 써 본 메뉴 구조가 다른 화면에서도 같다 |
| 유연성 | 사용자의 다양한 요구와 사용 방식을 받아들이고, 실수를 줄이고 되돌릴 수 있다 | 삭제 전 확인 창, 실행 취소 기능              |

네 원칙의 첫 글자를 이어 "직유학유"로 외운다. 유효성과 유연성은 둘 다 '유'로 시작하므로, 목적 달성(유효성)과 요구 수용·실수 방지(유연성)를 구분해 둔다.

| 도구          | 뜻                                                           |

| 목업 (Mockup) | 실제 화면과 비슷하게 색과 이미지까지 넣은 정적인 모형        |
| 스토리보드    | 와이어프레임에 설명, 화면 흐름, 기능 정의까지 적은 설계 문서 |
| 프로토타입    | 실제처럼 눌러 볼 수 있게 만든 동적인 모형                    |
| 유스케이스    | 사용자 관점의 기능 요구를 시나리오로 정리한 것               |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> UI 원칙의 설명을 주고 원칙 이름을 쓰게 한다. 예: "사용자가 처음 사용하는 기능도 쉽게 배우고 익힐 수 있어야 한다는 UI 설계 원칙을 쓰시오." 정답은 학습성.

## 애플리케이션 테스트

### 테스트 기본 원리

테스트는 소프트웨어가 요구사항대로 동작하는지 확인하고 결함을 찾는 활동이다. 국제 소프트웨어 테스트 자격 위원회 ISTQB(International Software Testing Qualifications Board)는 테스트의 일반 원리 7가지를 정리했다.

| 원리                 | 뜻                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------- |
| 결함 존재 증명       | 테스트는 결함이 있음을 보여 줄 수 있지만, 결함이 없음을 증명할 수는 없다            |
| 완벽한 테스트 불가능 | 모든 입력과 경로를 시험하는 것은 불가능하므로 위험도와 우선순위로 범위를 정한다     |
| 초기 집중            | 요구사항·설계 단계부터 테스트를 시작할수록 결함 수정 비용이 줄어든다                |
| 결함 집중            | 결함 대부분이 소수 모듈에 몰려 있다 (파레토 법칙: 20%의 모듈에서 80%의 결함)        |
| 살충제 패러독스      | 같은 테스트 케이스를 반복하면 새로운 결함을 찾지 못하므로 케이스를 계속 고쳐야 한다 |
| 정황 의존            | 은행 시스템과 게임처럼 소프트웨어 성격에 따라 테스트 방법이 달라야 한다             |
| 오류-부재의 궤변     | 결함을 모두 고쳐도 사용자 요구를 만족하지 못하면 품질이 높다고 할 수 없다           |

### 테스트 분류

| 분류 기준          | 종류                                     | 설명                                                                |
| ------------------ | ---------------------------------------- | ------------------------------------------------------------------- |
| 프로그램 실행 여부 | 정적 테스트                              | 실행하지 않고 코드·문서를 검토 (워크스루, 인스펙션, 정적 분석 도구) |
| 프로그램 실행 여부 | 동적 테스트                              | 프로그램을 실행해 결과를 확인 (블랙박스, 화이트박스)                |
| 테스트 기반        | 명세 기반 (블랙박스)                     | 요구사항 명세를 보고 입력과 기대 출력을 정한다                      |
| 테스트 기반        | 구조 기반 (화이트박스)                   | 소스 코드의 내부 구조를 보고 경로를 정한다                          |
| 테스트 기반        | 경험 기반                                | 테스터의 경험과 직관으로 정한다 (오류 예측, 탐색적 테스트)          |
| 목적               | 회복, 안전, 강도, 성능, 구조, 회귀, 병행 | 무엇을 확인하려는지에 따른 분류                                     |

목적별 테스트 가운데 회귀 테스트(Regression Test)는 결함을 고치거나 기능을 추가한 뒤, 이전에 통과하던 기능이 여전히 정상인지 다시 확인하는 테스트다. 강도 테스트(Stress Test)는 정상 범위를 넘는 부하를 걸어 시스템이 어디서 무너지는지 확인한다.

### 테스트 오라클

테스트 오라클(Test Oracle)은 테스트 결과가 맞는지 판단하기 위해 기대 결과를 계산하거나 확인하는 기준·메커니즘이다. 계산기 앱의 `2 + 3`을 시험하는 경우 "5가 나와야 한다"고 판정하는 근거가 오라클이다.

| 종류               | 영문              | 뜻                                                          |
| ------------------ | ----------------- | ----------------------------------------------------------- |
| 참 오라클          | True Oracle       | 모든 입력에 대해 기대 결과를 제공해 발생한 모든 오류를 검출 |
| 샘플링 오라클      | Sampling Oracle   | 특정 입력 몇 개에 대해서만 기대 결과를 제공                 |
| 추정 오라클        | Heuristic Oracle  | 특정 입력에는 기대 결과를 제공하고 나머지는 추정으로 판단   |
| 일관성 검사 오라클 | Consistent Oracle | 수정 전후의 결과가 같은지 비교 (회귀 테스트에 사용)         |

### V 모델

V 모델은 폭포수 모델을 확장해, 개발 단계 하나하나에 대응하는 테스트 단계를 짝지은 모델이다. 왼쪽으로 내려가며 요구사항과 설계를 구체화하고, 코딩 후 오른쪽으로 올라가며 각 단계에서 만든 산출물을 기준으로 테스트한다.

![V 모델의 개발 단계와 테스트 단계 대응](./images/eip-practical-design-test-v-model.svg '같은 높이에 있는 왼쪽 개발 단계의 산출물이 오른쪽 테스트의 기준이 된다')

| 개발 단계     | 대응 테스트   | 테스트 기준               |
| ------------- | ------------- | ------------------------- |
| 요구사항 분석 | 인수 테스트   | 사용자 요구사항           |
| 시스템 설계   | 시스템 테스트 | 시스템 기능·비기능 명세   |
| 아키텍처 설계 | 통합 테스트   | 모듈 사이 인터페이스 설계 |
| 모듈 설계     | 단위 테스트   | 모듈의 상세 설계          |

### 블랙박스 테스트

블랙박스 테스트(Black Box Test)는 프로그램 내부 코드를 보지 않고 명세만 보고 입력과 기대 출력을 정하는 테스트다. 기능이 명세대로 동작하는지 확인하는 데 쓰며, 명세 기반 테스트라고도 부른다.

#### 동등 분할과 경계값 분석

시험 점수를 입력받아 0~100이면 저장하고 그 밖이면 오류를 내는 기능이 있다고 하자.

![점수 입력 기능의 동등 분할과 경계값](./images/eip-practical-design-test-boundary.svg '분할마다 대표값 하나를 고르는 것이 동등 분할, 경계 바로 양옆까지 고르는 것이 경계값 분석이다')

동등 분할(Equivalence Partitioning, 동치 분할)은 입력 범위를 같은 결과가 나오는 그룹(분할)으로 나누고, 그룹마다 대표값 하나만 시험하는 기법이다. 같은 분할 안의 값은 프로그램이 같은 방식으로 처리한다고 가정하므로, 50이 통과하면 37도 통과한다고 본다. 점수 예에서 분할은 음수(무효), 0~100(유효), 101 이상(무효) 세 개이고, 테스트 입력은 −20, 50, 150처럼 3개면 된다.

경계값 분석(Boundary Value Analysis)은 결함이 분할의 경계에서 많이 생긴다는 경험에 근거해 경계와 그 바로 양옆을 시험하는 기법이다. 개발자가 `score >= 0`을 `score > 0`으로 잘못 쓰면 50은 정상 처리되지만 0은 오류가 난다. 이런 결함은 경계값 0을 넣어야 잡힌다. 점수 예의 경계값 입력은 −1, 0, 1, 99, 100, 101의 6개다.

| 기법        | 입력                   | 개수 | 잡을 수 있는 결함 예                     |
| ----------- | ---------------------- | ---- | ---------------------------------------- |
| 동등 분할   | −20, 50, 150           | 3    | 범위 검사 자체가 빠진 경우               |
| 경계값 분석 | −1, 0, 1, 99, 100, 101 | 6    | `>=`를 `>`로 잘못 쓴 경우 같은 경계 오류 |

#### 원인-결과 그래프와 결정 테이블

원인-결과 그래프(Cause-Effect Graph)는 입력 조건(원인)과 출력(결과)의 관계를 그래프로 그린 뒤, 효용성이 높은 조합을 골라 테스트 케이스를 만드는 기법이다. 그래프를 표로 옮긴 것이 결정 테이블(Decision Table)이다. 조건이 여러 개 얽혀 결과가 달라지는 업무 규칙을 빠짐없이 시험하는 데 쓴다.

쇼핑몰 할인 규칙이 "회원이면서 주문 금액이 5만 원 이상이면 10% 할인, 회원이지만 5만 원 미만이면 5% 할인, 비회원은 할인 없음"이라고 하자. 조건이 2개(참·거짓)이므로 조합은 2² = 4개다.

| 규칙                  | R1  | R2  | R3  | R4  |
| --------------------- | --- | --- | --- | --- |
| 조건: 회원인가        | Y   | Y   | N   | N   |
| 조건: 5만 원 이상인가 | Y   | N   | Y   | N   |
| 결과: 10% 할인        | X   |     |     |     |
| 결과: 5% 할인         |     | X   |     |     |
| 결과: 할인 없음       |     |     | X   | X   |

R3과 R4는 금액과 관계없이 결과가 같으므로 "회원 N이면 할인 없음" 하나로 합쳐 테스트 케이스를 3개로 줄일 수 있다.

#### 상태 전이 테스트

상태 전이 테스트(State Transition Test)는 상태 다이어그램을 보고 상태와 사건의 조합을 시험하는 기법이다. 앞의 주문 상태 다이어그램으로 테스트 케이스를 만들면 다음과 같다.

| 번호 | 현재 상태 | 사건      | 기대 결과       | 종류      |
| ---- | --------- | --------- | --------------- | --------- |
| 1    | 결제대기  | 결제      | 결제완료        | 유효 전이 |
| 2    | 결제완료  | 출고      | 배송중          | 유효 전이 |
| 3    | 배송중    | 수령      | 배송완료        | 유효 전이 |
| 4    | 결제대기  | 취소 요청 | 취소            | 유효 전이 |
| 5    | 배송중    | 취소 요청 | 거부, 상태 유지 | 무효 전이 |

5번처럼 다이어그램에 없는 전이를 시도하는 케이스가 결함을 잘 찾는다.

#### 그 밖의 블랙박스 기법

| 기법              | 영문               | 뜻                                                            |
| ----------------- | ------------------ | ------------------------------------------------------------- |
| 오류 예측         | Error Guessing     | 과거 경험과 감각으로 결함이 생길 만한 입력을 골라 시험        |
| 비교 검사         | Comparison Testing | 같은 입력을 여러 버전의 프로그램에 넣어 결과를 비교           |
| 페어와이즈        | Pairwise Testing   | 모든 조합 대신 변수 두 개씩의 조합이 한 번 이상 나오도록 축소 |
| 유스케이스 테스트 | Use Case Testing   | 유스케이스 시나리오를 따라 시험                               |

### 화이트박스 테스트

화이트박스 테스트(White Box Test)는 소스 코드의 내부 구조와 논리 흐름을 보고 모든 경로가 실행되는지 확인하는 테스트다. 구조 기반 테스트라고도 부르며, 기초 경로 검사와 제어 구조 검사(조건 검사, 루프 검사, 데이터 흐름 검사)가 대표적이다.

#### 기초 경로 검사와 순환 복잡도

기초 경로 검사(Basis Path Testing)는 맥케이브(McCabe)가 제안한 기법으로, 코드의 논리적 복잡도를 측정해 그 수만큼 독립 경로를 시험한다. 복잡도는 순환 복잡도(Cyclomatic Complexity)로 계산한다.

![if-else와 while이 있는 코드의 제어 흐름 그래프](./images/eip-practical-design-test-cfg.svg '코드의 번호 붙은 문장이 그래프의 노드가 되고, 실행이 옮겨 가는 방향이 간선이 된다')

| 기호   | 뜻                                               |
| ------ | ------------------------------------------------ |
| `V(G)` | 그래프 G의 순환 복잡도                           |
| `E`    | 간선(Edge) 수: 화살표 개수                       |
| `N`    | 노드(Node) 수: 문장·조건 블록 개수               |
| `P`    | 조건 노드(Predicate) 수: 갈림길이 되는 노드 개수 |

1. 그래프의 간선을 집계한다. 1→2, 1→3, 2→4, 3→4, 4→5, 5→4, 4→6으로 7개다.
2. 노드는 ①~⑥으로 6개다.
3. 공식에 대입한다.

```math
V(G) = E - N + 2 = 7 - 6 + 2 = 3
```

4. 조건 노드 공식으로 검산한다. 조건 노드는 `if`(①)와 `while`(④) 2개다.

```math
V(G) = P + 1 = 2 + 1 = 3
```

| 결과             | 값                                       |
| ---------------- | ---------------------------------------- |
| 순환 복잡도      | 3                                        |
| 독립 경로 예     | 1-2-4-6, 1-3-4-6, 1-2-4-5-4-6            |
| 필요한 테스트 수 | 최소 3개 (예: a=1·b=0, a=0·b=0, a=1·b=1) |

그래프가 평면에 그려졌다면 간선으로 둘러싸인 영역 수 + 1(바깥 영역)로도 같은 값을 얻는다.

#### 커버리지 기준

커버리지(Coverage)는 테스트가 코드를 얼마나 실행했는지 나타내는 기준이다. 실기에서는 기준의 이름과 정의, 그리고 특정 기준을 만족하는 최소 테스트 케이스를 묻는다. 다음 코드로 비교한다.

```c
if (A && B)
    x = 1;
```

| 커버리지                | 영문                                         | 만족 조건                                                                              | 최소 테스트 예 (A, B)  |
| ----------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------- |
| 구문 커버리지           | Statement Coverage                           | 모든 문장을 한 번 이상 실행                                                            | (T, T)                 |
| 결정 커버리지 (분기)    | Decision / Branch Coverage                   | 결정(전체 조건식)이 참·거짓을 각각 한 번 이상                                          | (T, T), (F, T)         |
| 조건 커버리지           | Condition Coverage                           | 각 개별 조건이 참·거짓을 각각 한 번 이상                                               | (T, F), (F, T)         |
| 조건/결정 커버리지      | Condition/Decision Coverage                  | 결정 커버리지와 조건 커버리지를 동시에 만족                                            | (T, T), (F, F)         |
| 변경 조건/결정 커버리지 | MC/DC (Modified Condition/Decision Coverage) | 조건/결정 커버리지 + 각 조건이 다른 조건과 무관하게 결과에 독립적으로 영향을 줌을 보임 | (T, T), (F, T), (T, F) |
| 다중 조건 커버리지      | Multiple Condition Coverage                  | 모든 조건 조합을 시험                                                                  | 4가지 조합 모두        |

조건 커버리지 행을 보면 (T, F)와 (F, T)는 A와 B가 각각 참·거짓을 한 번씩 가져 조건 커버리지를 만족하지만, 두 케이스 모두 `A && B`가 거짓이라 `x = 1`이 한 번도 실행되지 않는다. ==조건 커버리지를 만족해도 결정 커버리지나 구문 커버리지는 만족하지 못할 수 있다==는 점이 자주 나오는 함정이다.

MC/DC는 항공 소프트웨어 지침 DO-178C가 가장 높은 등급(Level A)에 요구하는 기준이다. 조건 3개짜리 `A && (B || C)`에서 최소 테스트 집합을 프로그램으로 모든 조합을 탐색해 구하면 4개가 나온다.

| 케이스 | A   | B   | C   | 결과 |
| ------ | --- | --- | --- | ---- |
| 1      | T   | T   | F   | T    |
| 2      | T   | F   | T   | T    |
| 3      | T   | F   | F   | F    |
| 4      | F   | T   | F   | F    |

1. A의 독립 영향: 케이스 1과 4는 A만 다르고 결과가 T와 F로 갈린다.
2. B의 독립 영향: 케이스 1과 3은 B만 다르고 결과가 갈린다.
3. C의 독립 영향: 케이스 2와 3은 C만 다르고 결과가 갈린다.

조건이 3개인데 다중 조건 커버리지는 2³ = 8개가 필요한 반면 MC/DC는 4개로 끝난다. AND·OR로만 이뤄진 조건식에서 MC/DC의 최소 케이스 수는 일반적으로 조건 수 + 1이다.

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 커버리지 이름과 정의를 짝짓게 하거나, 코드와 테스트 케이스를 주고 어떤 커버리지를 만족하는지 쓰게 한다. 블랙박스 기법과 화이트박스 기법을 섞어 놓고 분류하게 하는 문제도 많다.

블랙박스와 화이트박스는 기법 이름이 섞여 나오므로 한 표로 비교해 둔다.

| 구분      | 블랙박스 테스트                                                                        | 화이트박스 테스트                                      |
| --------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 다른 이름 | 명세 기반, 기능 테스트                                                                 | 구조 기반, 코드 기반 테스트                            |
| 보는 것   | 요구사항 명세, 입력과 출력                                                             | 소스 코드, 제어 흐름                                   |
| 대표 기법 | 동등 분할, 경계값 분석, 원인-결과 그래프, 결정 테이블, 상태 전이, 오류 예측, 비교 검사 | 기초 경로 검사, 조건 검사, 루프 검사, 데이터 흐름 검사 |
| 측정 기준 | 요구사항 커버리지                                                                      | 구문·결정·조건·MC/DC 커버리지                          |
| 잡는 결함 | 누락된 기능, 잘못된 기능, 인터페이스 오류, 성능 오류                                   | 실행되지 않는 코드, 잘못된 논리 경로, 반복문 경계 오류 |

### 테스트 레벨

테스트 레벨은 개발 단계에 따라 테스트를 나눈 것으로, V 모델 오른쪽 단계와 같다.

| 레벨          | 영문             | 대상과 목적                                                                   | 수행 주체      |
| ------------- | ---------------- | ----------------------------------------------------------------------------- | -------------- |
| 단위 테스트   | Unit Test        | 함수·클래스 같은 최소 단위가 상세 설계대로 동작하는지                         | 개발자         |
| 통합 테스트   | Integration Test | 모듈을 결합한 상태에서 인터페이스와 상호작용에 결함이 없는지                  | 개발자·테스터  |
| 시스템 테스트 | System Test      | 완성된 시스템이 기능·비기능 요구사항을 만족하는지 (실제 운영 환경과 비슷하게) | 독립 테스트 팀 |
| 인수 테스트   | Acceptance Test  | 사용자가 요구한 대로 만들어졌는지 확인하고 인수 여부를 결정                   | 사용자·고객    |

인수 테스트에는 알파 테스트와 베타 테스트가 있다. 알파 테스트는 ==개발자의 장소==에서 사용자가 개발자와 함께 통제된 환경으로 시험하고, 베타 테스트는 ==사용자의 장소==에서 개발자 없이 실제 사용 환경으로 시험한다. 게임의 "공개 베타"가 베타 테스트의 예다.

### 테스트 하네스

테스트 하네스(Test Harness)는 테스트를 실행하기 위해 만드는 코드와 데이터, 도구의 묶음이다. 하네스는 원래 말에 씌우는 마구를 뜻하며, 테스트 대상을 붙잡아 실행할 수 있게 하는 장치라는 의미다.

| 구성 요소       | 영문        | 뜻                                                                             |
| --------------- | ----------- | ------------------------------------------------------------------------------ |
| 테스트 드라이버 | Test Driver | 테스트 대상 하위 모듈을 ==호출하는== 임시 상위 모듈. 입력을 넣고 결과를 받는다 |
| 테스트 스텁     | Test Stub   | 테스트 대상 상위 모듈이 ==호출하는== 임시 하위 모듈. 정해진 값만 돌려준다      |
| 테스트 슈트     | Test Suite  | 테스트 케이스를 묶은 집합                                                      |
| 테스트 케이스   | Test Case   | 입력값, 실행 조건, 기대 결과를 정리한 명세                                     |
| 테스트 스크립트 | Test Script | 테스트 실행 절차를 자동화한 코드                                               |
| 목 오브젝트     | Mock Object | 호출 순서·횟수 같은 행위까지 미리 정해 두고 검증하는 가짜 객체                 |

### 통합 테스트: 하향식과 상향식

통합 테스트는 모듈을 어떤 순서로 결합하는지에 따라 나뉜다. 한꺼번에 모두 결합해 시험하는 빅뱅 방식은 결함이 나와도 어느 모듈 사이에서 생겼는지 찾기 어려워, 보통 점진적으로 결합한다.

![하향식 통합의 스텁과 상향식 통합의 드라이버](./images/eip-practical-design-test-integration.svg '하향식은 아래쪽 빈자리를 스텁으로, 상향식은 위쪽 빈자리를 드라이버로 채운다')

| 방식   | 영문                  | 결합 순서                                         | 필요한 가짜 모듈 | 특징                                                  |
| ------ | --------------------- | ------------------------------------------------- | ---------------- | ----------------------------------------------------- |
| 하향식 | Top Down Integration  | 최상위 모듈부터 아래로. 깊이 우선 또는 너비 우선  | 스텁             | 주요 제어 흐름과 화면을 일찍 확인할 수 있다           |
| 상향식 | Bottom Up Integration | 최하위 모듈부터 위로. 하위 모듈을 클러스터로 묶음 | 드라이버         | 하위 모듈의 결함을 일찍 발견, 전체 모습은 늦게 나온다 |
| 혼합식 | Sandwich Integration  | 상위는 하향식, 하위는 상향식                      | 둘 다            | 두 방식의 장점을 취하지만 비용이 크다                 |

상향식 통합 테스트는 다음 순서로 진행한다.

1. 하위 모듈들을 특정 기능을 수행하는 클러스터(Cluster)로 묶는다.
2. 클러스터를 시험하기 위한 드라이버를 작성한다.
3. 클러스터 단위로 테스트한다.
4. 테스트가 끝나면 드라이버를 제거하고 클러스터를 상위 모듈과 결합해 위로 올라간다.

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> "하향식 통합 테스트에서 아직 개발되지 않은 하위 모듈을 대신하는 임시 모듈을 쓰시오"처럼 스텁과 드라이버를 구분해 쓰게 한다. 하향식 = 스텁, 상향식 = 드라이버로 외운다. 스텁은 "호출당하는 쪽", 드라이버는 "호출하는 쪽"이다.

## 형상 관리

### 형상 관리란

형상 관리(SCM, Software Configuration Management)는 소프트웨어 개발 과정에서 만들어지는 소스 코드, 문서, 설정 파일 같은 산출물(형상 항목)의 변경을 식별하고 통제해, 누가 언제 무엇을 왜 바꿨는지 추적할 수 있게 하는 활동이다. 형상 관리가 없으면 "어제는 됐는데 오늘은 안 된다"는 상황에서 무엇이 바뀌었는지 알 수 없고, 고객에게 배포한 버전의 소스를 다시 찾지 못한다.

형상 관리의 기준점을 기준선(Baseline)이라고 한다. 기준선은 정식으로 검토·승인되어 이후 변경은 공식 절차를 거쳐야만 할 수 있는 산출물 상태다. 요구사항 명세서가 고객 승인을 받으면 그 시각의 명세서가 기준선이 된다.

### 형상 관리 절차

| 절차             | 하는 일                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------ |
| 형상 식별        | 관리할 형상 항목을 정하고 이름과 버전 번호를 붙인다                                                          |
| 버전 제어        | 형상 항목의 버전을 기록·관리해 이전 버전으로 되돌리거나 비교할 수 있게 한다                                  |
| 형상 통제        | 변경 요청을 검토해 기준선에 반영할지 결정한다. 형상 통제 위원회(CCB, Configuration Control Board)가 승인한다 |
| 형상 감사        | 승인된 변경이 요청 내용대로 정확히 반영되어 기준선이 온전한지 검토한다                                       |
| 형상 기록 (보고) | 식별·통제·감사 결과를 기록하고 보고서로 작성한다                                                             |

변경 하나가 처리되는 흐름은 다음과 같다. 개발자가 "로그인 실패 메시지 문구 변경"을 요청하면 CCB가 영향 범위를 검토해 승인하고(형상 통제), 개발자가 수정해 새 버전으로 등록하면(버전 제어), 검토자가 요청대로 반영됐는지 확인하고(형상 감사), 그 이력을 변경 기록에 남긴다(형상 기록).

### 버전 관리 도구

| 방식            | 도구                 | 특징                                                                       |
| --------------- | -------------------- | -------------------------------------------------------------------------- |
| 공유 폴더       | RCS, SCCS            | 개발자가 공유 폴더의 파일을 복사해 작업. 파일 단위 잠금으로 동시 수정 방지 |
| 클라이언트/서버 | CVS, SVN(Subversion) | 중앙 서버 저장소 하나에 커밋. 서버에 접속해야 이력 조회·커밋 가능          |
| 분산 저장소     | Git, Mercurial       | 개발자마다 전체 이력을 가진 로컬 저장소를 두고, 원격 저장소와 동기화       |

> [!IMPORTANT] 시험에서는 이렇게 묻는다
> 형상 관리 절차를 설명과 짝짓게 하거나 빈칸에 쓰게 한다. 예: "형상 항목의 변경 요청을 심사해, 승인된 변경만 기준선에 반영되도록 관리하는 활동을 쓰시오." 정답은 형상 통제.
