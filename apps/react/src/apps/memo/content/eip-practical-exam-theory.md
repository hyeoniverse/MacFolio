이 글은 정보처리기사 실기에서 코드 읽기를 뺀 나머지 영역, 즉 SQL, 요구사항·설계·테스트 용어, 보안·네트워크·신기술 용어, 계산 문제를 실제 시험 형식으로 풀어 보는 예제 모음이다. 2020년 NCS 개편 이후 2023년 3회까지의 실기에서 자주 나온 주제를 15문제로 골랐고, 문제마다 위에 출제 회차와 주제를 밝혔다. 정답 토글 아래에는 같은 주제의 다른 문제가 나와도 풀 수 있도록 개념 요약을 붙였다.

SQL 정답은 모두 SQLite 3로 실행해 확인했다. SQLite가 지원하지 않는 `ALL` 서브쿼리, `GRANT`·`REVOKE`, `DROP VIEW … CASCADE`는 같은 뜻의 SQLite 문장을 실행해 결과를 확인하고, 표준 SQL 문법은 해설로 설명한다. 계산 문제는 파이썬 `ipaddress` 모듈과 직접 짠 스케줄링 시뮬레이션으로 검산했다.

## SQL

SQL 문제는 회차마다 2~3문항씩 나오고, 형식은 크게 셋이다. 빈칸에 키워드 쓰기, 실행 결과(행 수나 값) 쓰기, 요구 사항을 읽고 SQL 문장 전체 쓰기다. 아래 네 문제에는 형식마다 NULL, 비교 연산자의 등호, WHERE와 HAVING의 실행 순서처럼 실기에서 자주 틀리는 함정이 하나씩 들어 있다.

### 예제 1. 조인 조건과 LIKE·정렬 빈칸

> 출제: 2021년 실기 2회 · JOIN의 ON 조건 빈칸, LIKE·DESC 빈칸

다음은 [사원] 테이블과 [부서] 테이블이다.

[사원]

| 사번 | 이름   | 부서코드 | 급여 |
| ---- | ------ | -------- | ---- |
| 101  | 김하늘 | D1       | 420  |
| 102  | 이도윤 | D2       | 380  |
| 103  | 김민준 | NULL     | 450  |
| 104  | 박김솔 | D1       | 500  |
| 105  | 김서   | D3       | 310  |
| 106  | 김지아 | D2       | 390  |

[부서]

| 부서코드 | 부서명 |
| -------- | ------ |
| D1       | 개발   |
| D2       | 영업   |
| D3       | 인사   |

성이 '김'인 사원의 이름, 부서명, 급여를 급여가 높은 순으로 조회하려고 한다. (1) 빈칸 ①~④에 알맞은 키워드나 식을 쓰고, (2) 완성한 SQL을 실행했을 때 결과 행 수를 쓰시오.

```sql
SELECT 사원.이름, 부서.부서명, 사원.급여
FROM 사원 JOIN 부서
  ( ① ) 사원.부서코드 = 부서.( ② )
WHERE 사원.이름 ( ③ ) '김%'
ORDER BY 사원.급여 ( ④ );
```

<details>
<summary>정답과 해설</summary>

정답: (1) ① ON, ② 부서코드, ③ LIKE, ④ DESC (2) 3행

**빈칸 해설**

| 빈칸 | 정답     | 이유                                                                              |
| ---- | -------- | --------------------------------------------------------------------------------- |
| ①    | ON       | `JOIN` 뒤에서 두 테이블을 잇는 조건을 적는 키워드                                 |
| ②    | 부서코드 | 사원의 외래 키 `부서코드`가 부서의 기본 키 `부서코드`를 참조한다                  |
| ③    | LIKE     | `%`(0글자 이상), `_`(정확히 1글자) 같은 와일드카드 패턴 비교는 `LIKE`로만 한다    |
| ④    | DESC     | 높은 순은 내림차순이다. 오름차순 `ASC`는 생략할 수 있지만 `DESC`는 생략할 수 없다 |

①에 `WHERE`를 쓰면 문법 오류다. 조인 조건을 WHERE에 쓰는 것은 `FROM 사원, 부서 WHERE …`처럼 쉼표로 테이블을 나열하는 옛 문법이고, `JOIN`을 쓰면 반드시 `ON`(또는 `USING`)이 따라온다.

**결과 행 수 해설**

1단계. `JOIN`(내부 조인)은 양쪽 테이블에서 조건이 참인 짝만 남긴다. 김민준은 부서코드가 NULL이라 `NULL = 'D1'` 같은 비교가 참도 거짓도 아닌 UNKNOWN이 되어 어떤 부서와도 짝을 이루지 못한다.

| 사번 | 이름   | 부서코드 | 짝이 되는 부서 | 조인 결과에 남는가 |
| ---- | ------ | -------- | -------------- | ------------------ |
| 101  | 김하늘 | D1       | 개발           | 남음               |
| 102  | 이도윤 | D2       | 영업           | 남음               |
| 103  | 김민준 | NULL     | 없음           | ==빠짐==           |
| 104  | 박김솔 | D1       | 개발           | 남음               |
| 105  | 김서   | D3       | 인사           | 남음               |
| 106  | 김지아 | D2       | 영업           | 남음               |

2단계. `LIKE '김%'`는 첫 글자가 '김'인 문자열만 고른다. 이도윤은 첫 글자가 다르고, 박김솔은 '김'이 가운데 있어서 빠진다.

3단계. 남은 세 행을 급여 내림차순으로 정렬한다. SQLite 실행 결과는 다음과 같다.

| 이름   | 부서명 | 급여 |
| ------ | ------ | ---- |
| 김하늘 | 개발   | 420  |
| 김지아 | 영업   | 390  |
| 김서   | 인사   | 310  |

> [!WARNING] 이 문제의 함정
> 부서코드가 NULL인 행은 내부 조인에서 사라진다. 사원 테이블만 보고 '김'씨를 세면 4명이라 4를 쓰기 쉽다. 외부 조인(`LEFT JOIN`)이어야 김민준이 부서명 NULL로 남는다.

시험에서 실수하는 지점은 두 가지다. 하나는 `LIKE` 자리에 `=`를 쓰는 것이다. `이름 = '김%'`는 이름이 글자 그대로 "김%"인 행을 찾으므로 결과가 0행이다. 다른 하나는 `DESC`를 `DESCENDING`이나 `DEC`로 쓰는 철자 실수다.

</details>

> [!NOTE] 개념 요약
>
> - 내부 조인(`JOIN … ON`)은 조건이 참인 짝만 남긴다. 조인 열이 NULL인 행은 어떤 행과도 짝이 되지 않아 빠지고, 남기려면 `LEFT JOIN` 같은 외부 조인을 쓴다
> - `JOIN` 뒤에는 `ON 조건`이나 `USING(열)`이 온다. 조인 조건을 WHERE에 쓰는 것은 `FROM A, B`처럼 쉼표로 나열한 경우뿐이다
> - `LIKE` 와일드카드는 `%`(0글자 이상)와 `_`(정확히 1글자)다. `'김%'`는 김으로 시작, `'%김%'`는 김을 포함, `'김_'`는 김으로 시작하는 두 글자
> - `ORDER BY`는 `ASC`(오름차순, 생략 가능)와 `DESC`(내림차순, 생략 불가)이고, 열을 여러 개 쓰면 앞 열부터 정렬 기준이 된다

### 예제 2. NULL이 섞인 COUNT와 ALL 서브쿼리

> 출제: 2022년 실기 2회 · NULL이 있는 열의 COUNT, 다중 행 서브쿼리의 ALL

(1) 다음 [T] 테이블에 대해 SQL을 실행한 결과를 쓰시오.

| c1  | c2   |
| --- | ---- |
| 1   | 10   |
| 2   | NULL |
| 2   | 30   |
| 3   | NULL |
| 3   | 10   |
| 4   | 20   |
| 5   | NULL |

```sql
SELECT COUNT(c2) FROM T WHERE c1 IN (2, 3) OR c2 IN (10, NULL);
```

(2) 다음 [제품] 테이블에서 제조사 'H'가 만든 ==모든== 제품의 단가보다 비싼 제품의 이름을 조회하려고 한다. 빈칸에 들어갈 키워드를 쓰고, 결과로 나오는 제품명을 모두 쓰시오.

| 제품명 | 제조사 | 단가 |
| ------ | ------ | ---- |
| P1     | H      | 300  |
| P2     | H      | 500  |
| P3     | H      | 450  |
| P4     | K      | 600  |
| P5     | K      | 480  |
| P6     | S      | 520  |
| P7     | S      | 200  |
| P8     | K      | 500  |

```sql
SELECT 제품명 FROM 제품
WHERE 단가 > ( ① ) (SELECT 단가 FROM 제품 WHERE 제조사 = 'H');
```

<details>
<summary>정답과 해설</summary>

정답: (1) 3 (2) ① ALL, 결과는 P4, P6

**(1) 해설**

`COUNT`는 괄호 안에 무엇을 넣는지에 따라 집계 대상이 다르다. `COUNT(*)`는 행의 개수를, `COUNT(c2)`는 c2가 NULL이 아닌 행의 개수를 집계한다.

1단계. WHERE 조건을 행마다 판정한다. `c2 IN (10, NULL)`은 `c2 = 10 OR c2 = NULL`과 같다. `c2 = NULL`은 c2 값이 무엇이든 UNKNOWN이므로, 목록에 NULL을 넣어도 NULL인 행을 찾아 주지 않는다.

| c1  | c2   | `c1 IN (2,3)` | `c2 IN (10, NULL)` | OR 결과 | 남는가 |
| --- | ---- | ------------- | ------------------ | ------- | ------ |
| 1   | 10   | 거짓          | 참                 | 참      | 남음   |
| 2   | NULL | 참            | UNKNOWN            | 참      | 남음   |
| 2   | 30   | 참            | UNKNOWN            | 참      | 남음   |
| 3   | NULL | 참            | UNKNOWN            | 참      | 남음   |
| 3   | 10   | 참            | 참                 | 참      | 남음   |
| 4   | 20   | 거짓          | UNKNOWN            | UNKNOWN | 빠짐   |
| 5   | NULL | 거짓          | UNKNOWN            | UNKNOWN | 빠짐   |

`c2 = 30`은 거짓이지만 `c2 = NULL`이 UNKNOWN이라 `거짓 OR UNKNOWN`이 UNKNOWN이 된다. 3값 논리에서 OR는 하나라도 참이면 참이고, 참이 없으면서 UNKNOWN이 하나라도 있으면 UNKNOWN이다. WHERE는 참인 행만 남기므로 UNKNOWN은 빠진 것과 같다.

2단계. 남은 5행의 c2는 10, NULL, 30, NULL, 10이다. `COUNT(c2)`는 NULL 두 개를 빼고 집계하므로 3이다. SQLite로 실행하면 `COUNT(c2)`는 3, 같은 조건의 `COUNT(*)`는 5가 나온다.

**(2) 해설**

다중 행 서브쿼리는 값을 여러 개 돌려주므로 `>` 같은 비교 연산자 뒤에 바로 쓸 수 없고, `ALL`이나 `ANY`(`SOME`)를 붙여 "목록 전체와 비교할지, 하나라도 만족하면 될지"를 정해야 한다.

| 연산자  | 뜻                                | 이 문제에서 같은 조건     |
| ------- | --------------------------------- | ------------------------- |
| `> ALL` | 목록의 모든 값보다 크다           | `단가 > 500` (H의 최댓값) |
| `> ANY` | 목록의 값 중 하나보다만 크면 된다 | `단가 > 300` (H의 최솟값) |

1단계. 서브쿼리 결과는 H 제품의 단가 목록 {300, 500, 450}이다.

2단계. "모든 제품보다 비싼"은 세 값 모두보다 커야 하므로 `> ALL`이고, 결국 최댓값 500보다 커야 한다.

| 제품명 | 단가 | `> 300` | `> 500` | `> 450` | `> ALL` |
| ------ | ---- | ------- | ------- | ------- | ------- |
| P1     | 300  | 거짓    | 거짓    | 거짓    | 거짓    |
| P2     | 500  | 참      | 거짓    | 참      | 거짓    |
| P3     | 450  | 참      | 거짓    | 거짓    | 거짓    |
| P4     | 600  | 참      | 참      | 참      | ==참==  |
| P5     | 480  | 참      | 거짓    | 참      | 거짓    |
| P6     | 520  | 참      | 참      | 참      | ==참==  |
| P7     | 200  | 거짓    | 거짓    | 거짓    | 거짓    |
| P8     | 500  | 참      | 거짓    | 참      | 거짓    |

SQLite는 `ALL`·`ANY`를 지원하지 않아 `> ALL`을 쓰면 구문 오류가 난다. 그래서 같은 뜻의 두 문장을 실행해 결과를 확인했다. `단가 > (SELECT MAX(단가) … WHERE 제조사 = 'H')`와, "H 제품 중 이 제품보다 비싸거나 같은 것이 하나도 없다"는 `NOT EXISTS` 문장 모두 P4, P6을 돌려줬다. `> ANY`에 해당하는 `EXISTS` 문장은 P2, P3, P4, P5, P6, P8의 6행을 돌려줬다.

> [!WARNING] 이 문제의 함정
> P8의 단가 500은 H의 최고가 500과 같다. "비싼"은 `>`이므로 같은 값은 빠진다. `>= ALL`이었다면 P2, P4, P6, P8이 나온다. 또 서브쿼리가 0행이면 `> ALL`은 모든 행에서 참, `> ANY`는 모든 행에서 거짓이 된다. `MAX`로 바꾼 문장은 이 경우 NULL과 비교하게 되어 0행이 나오므로, `ALL`과 `MAX`가 완전히 같지는 않다.

시험에서 실수하는 지점은 `ALL`과 `ANY`를 바꿔 쓰는 것이다. 문장에서 "모든 ~보다"는 ALL, "어느 하나보다", "적어도 하나보다"는 ANY다.

</details>

> [!NOTE] 개념 요약
>
> - 집계 함수 중 `COUNT(*)`만 NULL 행을 포함해 집계하고, `COUNT(열)`, `SUM`, `AVG`, `MIN`, `MAX`는 NULL을 제외한다
> - NULL과의 비교(`=`, `<>`, `IN` 목록 안의 NULL)는 모두 UNKNOWN이다. NULL인 행은 `IS NULL`, `IS NOT NULL`로만 고른다
> - 3값 논리에서 AND는 거짓이 하나라도 있으면 거짓, OR는 참이 하나라도 있으면 참이고, 그 밖에 UNKNOWN이 섞이면 UNKNOWN이다. WHERE는 참인 행만 남긴다
> - 다중 행 비교: `> ALL`은 최댓값보다 큼, `> ANY`(`SOME`)는 최솟값보다 큼, `< ALL`은 최솟값보다 작음, `< ANY`는 최댓값보다 작음, `= ANY`는 `IN`과 같다

### 예제 3. GROUP BY와 HAVING의 결과 표 쓰기

> 출제: 2020년 실기 3회 · GROUP BY와 HAVING으로 과목별 최소·최대 점수 조회

다음 [성적] 테이블에 SQL을 실행한 결과를 표로 쓰시오. 행 순서는 과목명 오름차순이다.

| 학번 | 과목     | 점수 |
| ---- | -------- | ---- |
| 1    | 자료구조 | 92   |
| 2    | 자료구조 | 88   |
| 3    | 자료구조 | NULL |
| 1    | 운영체제 | 75   |
| 2    | 운영체제 | 95   |
| 4    | 운영체제 | 58   |
| 3    | 네트워크 | 90   |
| 4    | 네트워크 | 84   |
| 5    | 네트워크 | 96   |
| 5    | 자료구조 | 70   |

```sql
SELECT 과목, MIN(점수) AS 최소점수, MAX(점수) AS 최대점수
FROM 성적
GROUP BY 과목
HAVING AVG(점수) >= 80
ORDER BY 과목;
```

<details>
<summary>정답과 해설</summary>

정답:

| 과목     | 최소점수 | 최대점수 |
| -------- | -------- | -------- |
| 네트워크 | 84       | 96       |
| 자료구조 | 70       | 92       |

SELECT 문은 적힌 순서가 아니라 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY` 순서로 실행된다.

![SQL 문장이 FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY 순서로 실행되며 행이 걸러지고 묶이는 흐름](./images/eip-practical-exam-theory-sql-order.svg '적힌 순서와 실행 순서가 다르다. WHERE는 묶기 전 행을, HAVING은 묶은 뒤 그룹을 거른다')

1단계(FROM, GROUP BY). 10행을 과목 값이 같은 행끼리 묶는다.

| 그룹     | 묶인 점수        |
| -------- | ---------------- |
| 네트워크 | 90, 84, 96       |
| 운영체제 | 75, 95, 58       |
| 자료구조 | 92, 88, NULL, 70 |

2단계. 그룹마다 집계 함수를 계산한다. 집계 함수는 `COUNT(*)`를 빼고 모두 NULL을 제외하고 계산한다. 자료구조의 평균은 4명이 아니라 점수가 있는 3명으로 나눈다.

| 그룹     | `COUNT(*)` | `COUNT(점수)` | `SUM` | `AVG`  | `MIN` | `MAX` |
| -------- | ---------- | ------------- | ----- | ------ | ----- | ----- |
| 네트워크 | 3          | 3             | 270   | 90.0   | 84    | 96    |
| 운영체제 | 3          | 3             | 228   | 76.0   | 58    | 95    |
| 자료구조 | 4          | 3             | 250   | 83.33… | 70    | 92    |

3단계(HAVING). 평균이 80 이상인 그룹만 남긴다. 운영체제(76.0)가 빠진다.

4단계(SELECT, ORDER BY). 남은 두 그룹의 과목, 최소, 최대를 과목명 순으로 출력한다.

**문장을 조금 바꾸면 결과가 달라진다**

| 바꾼 부분                                | 실행 결과                                    | 이유                                                      |
| ---------------------------------------- | -------------------------------------------- | --------------------------------------------------------- |
| `WHERE 점수 >= 60`을 GROUP BY 앞에 추가  | 네트워크, ==운영체제(75, 95)==, 자료구조 3행 | 58점 행이 묶기 전에 빠져 운영체제 평균이 85.0이 된다      |
| `AVG(점수)`를 `AVG(COALESCE(점수, 0))`로 | 네트워크 1행                                 | NULL을 0으로 바꾸면 자료구조 평균이 250 ÷ 4 = 62.5가 된다 |
| `HAVING` 대신 `WHERE AVG(점수) >= 80`    | 오류 `misuse of aggregate: AVG()`            | WHERE는 묶기 전에 실행되어 집계 함수를 쓸 수 없다         |

> [!WARNING] 이 문제의 함정
> 자료구조 평균을 250 ÷ 4 = 62.5로 계산하면 자료구조를 빼고 네트워크 한 행만 쓰게 된다. `AVG`는 NULL인 행을 분모에서도 뺀다.

</details>

> [!NOTE] 개념 요약
>
> - 실행 순서는 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`다
> - WHERE는 묶기 전 행 조건이라 집계 함수를 쓸 수 없고, HAVING은 묶은 뒤 그룹 조건이라 집계 함수를 쓴다. "평균이", "인원이"는 HAVING, "점수가", "학년이"는 WHERE
> - `AVG`는 NULL 행을 분자와 분모에서 모두 뺀다. NULL을 0으로 계산하려면 `COALESCE(열, 0)`을 쓴다
> - GROUP BY를 쓰면 SELECT에는 그룹 기준 열과 집계 함수만 쓴다

### 예제 4. 열 추가, 권한 연쇄 회수, 뷰 연쇄 삭제

> 출제: 2020년 실기 3회 · ALTER TABLE로 속성 추가, 2021년 실기 3회 · GRANT 명령어, 2023년 실기 2회 · DROP VIEW의 CASCADE

(1) [고객] 테이블에 길이 20의 문자열 열 '연락처'를 추가하는 SQL의 빈칸을 쓰시오.

```sql
( ① ) TABLE 고객 ( ② ) 연락처 VARCHAR(20);
```

(2) 데이터베이스 관리자(DBA)가 다음 순서로 권한 명령을 실행했다. 빈칸 ③, ④를 쓰고, 마지막 REVOKE 실행 후 [고객] 테이블을 SELECT할 수 있는 사용자를 kim, lee, park 중에서 모두 쓰시오.

```sql
-- DBA가 실행
GRANT SELECT ON 고객 TO kim WITH GRANT ( ③ );
-- kim이 실행
GRANT SELECT ON 고객 TO lee;
-- DBA가 실행
GRANT SELECT ON 고객 TO park;
-- DBA가 실행
REVOKE SELECT ON 고객 ( ④ ) kim CASCADE;
```

(3) 뷰 V_VIP를 기반으로 뷰 V_VIP_NAME을 만들었다. V_VIP를 삭제하면서 V_VIP_NAME도 함께 삭제되게 하는 옵션을 쓰시오.

```sql
DROP VIEW V_VIP ( ⑤ );
```

<details>
<summary>정답과 해설</summary>

정답: ① ALTER, ② ADD, ③ OPTION, ④ FROM, ⑤ CASCADE. REVOKE 후 SELECT할 수 있는 사용자는 park

**(1) 해설**

이미 있는 테이블의 구조를 바꾸는 DDL은 `ALTER TABLE`이고, 열을 추가하는 동작은 `ADD`다. 표준 SQL은 `ADD COLUMN`이라고 쓰고 `COLUMN`은 생략할 수 있다. SQLite에서 실행한 뒤 테이블 정보를 조회하면 네 번째 열로 `연락처 VARCHAR(20)`이 생기고, 기존 행의 연락처 값은 NULL이 된다.

①에 `UPDATE`를 쓰는 답안이 많다. `UPDATE`는 행의 ==값==을 바꾸는 DML이고, 열을 늘리고 줄이는 ==구조== 변경은 DDL인 `ALTER`다.

**(2) 해설**

SQLite는 사용자 계정이 없는 파일형 DBMS라서 `GRANT`·`REVOKE`를 실행할 수 없다. 아래는 표준 SQL(ISO/IEC 9075)의 동작으로 추적한다.

| 순서 | 명령                            | kim               | lee                     | park                    |
| ---- | ------------------------------- | ----------------- | ----------------------- | ----------------------- |
| 1    | DBA → kim, `WITH GRANT OPTION`  | SELECT + 재부여권 | 없음                    | 없음                    |
| 2    | kim → lee                       | SELECT + 재부여권 | SELECT (kim에게서 받음) | 없음                    |
| 3    | DBA → park                      | SELECT + 재부여권 | SELECT (kim에게서 받음) | SELECT (DBA에게서 받음) |
| 4    | DBA가 kim에게서 회수, `CASCADE` | 없음              | ==없음==                | SELECT                  |

`WITH GRANT OPTION`은 받은 권한을 다른 사용자에게 다시 줄 수 있는 권한까지 준다는 뜻이다. 2단계에서 kim이 lee에게 권한을 줄 수 있었던 것도 이 옵션 덕분이다. 4단계의 `CASCADE`는 kim의 권한을 회수하면서 kim이 다른 사용자에게 준 권한까지 연쇄로 회수한다. 그래서 lee도 권한을 잃는다. park은 DBA에게서 직접 받았으므로 kim과 관계없이 권한이 남는다.

| 비교                | `CASCADE`                               | `RESTRICT`                                |
| ------------------- | --------------------------------------- | ----------------------------------------- |
| REVOKE에서          | 회수 대상이 재부여한 권한까지 연쇄 회수 | 재부여한 권한이 있으면 REVOKE 자체를 거부 |
| DROP VIEW·TABLE에서 | 의존하는 뷰·제약 조건까지 함께 삭제     | 의존하는 개체가 있으면 삭제를 거부        |

이 문제에서 `RESTRICT`로 바꾸면 kim이 lee에게 준 권한이 남아 있으므로 REVOKE가 실패하고 세 사람 모두 권한을 유지한다. Oracle처럼 재부여된 권한을 `CASCADE` 키워드 없이 자동으로 함께 회수하는 DBMS도 있지만, 시험은 표준 문법으로 채점한다.

**(3) 해설**

V_VIP_NAME은 V_VIP를 조회하는 뷰이므로 V_VIP에 의존한다. 표준 SQL에서 `DROP VIEW V_VIP CASCADE`는 V_VIP와 그 뷰에 의존하는 V_VIP_NAME을 함께 삭제하고, `RESTRICT`는 의존하는 뷰가 있으면 삭제를 거부한다.

SQLite는 `DROP VIEW … CASCADE`를 지원하지 않아 구문 오류가 나지만, 옵션 없이 V_VIP만 삭제해 보면 이 옵션이 왜 필요한지 확인할 수 있다.

| 단계 | SQLite에서 실행한 것                      | 결과                                               |
| ---- | ----------------------------------------- | -------------------------------------------------- |
| 1    | V_VIP, V_VIP_NAME 생성 후 V_VIP_NAME 조회 | 한서윤, 문가온 2행                                 |
| 2    | `DROP VIEW V_VIP;`                        | 성공. 카탈로그에는 고객 테이블과 V_VIP_NAME만 남음 |
| 3    | V_VIP_NAME 조회                           | 오류 `no such table: main.V_VIP`                   |

옵션이 없는 DBMS에서는 의존하는 뷰가 깨진 채로 남는다. `CASCADE`와 `RESTRICT`는 각각 함께 삭제하거나 삭제를 막아 이 상태를 피한다.

> [!WARNING] 이 문제의 함정
> ④는 `TO`가 아니라 `FROM`이다. 권한은 "누구에게(TO) 주고", "누구로부터(FROM) 회수한다". ③은 `WITH GRANT OPTION` 세 단어가 한 덩어리이므로 `OPTION`만 쓴다.

</details>

> [!NOTE] 개념 요약
>
> - SQL 분류: DDL은 구조(`CREATE`, `ALTER`, `DROP`, `TRUNCATE`), DML은 행의 값(`SELECT`, `INSERT`, `UPDATE`, `DELETE`), DCL은 권한(`GRANT`, `REVOKE`), TCL은 트랜잭션(`COMMIT`, `ROLLBACK`, `SAVEPOINT`)이다. 세 분류 체계에서는 COMMIT, ROLLBACK도 DCL에 넣는다
> - 열 추가는 `ALTER TABLE 테이블 ADD 열 타입`, 열 삭제는 `ALTER TABLE 테이블 DROP COLUMN 열`이다
> - 권한 문법은 `GRANT 권한 ON 객체 TO 사용자 [WITH GRANT OPTION]`과 `REVOKE 권한 ON 객체 FROM 사용자 [CASCADE | RESTRICT]`다
> - `CASCADE`는 걸린 것까지 연쇄 처리(재부여한 권한, 의존하는 뷰), `RESTRICT`는 걸린 것이 있으면 명령을 거부한다. CASCADE는 회수 대상에서 시작된 권한만 따라간다

## 요구사항·설계·테스트

이 영역은 설명을 읽고 용어를 쓰는 문제가 대부분이다. 보기가 주어지면 기호로 고르고, 보기가 없으면 한글이나 영문으로 직접 쓴다. 문제에서 "영문으로", "약어로"를 지정하면 그 형식을 지켜야 정답으로 인정된다.

### 예제 5. 코드로 결합도 판별하기

> 출제: 2021년 실기 1회 · 설명에 맞는 결합도 쓰기, 2021년 실기 3회 · 제어 결합도

다음 C 코드 조각 (가)~(라)에서 함수 사이의 결합도를 각각 쓰시오.

```c
/* (가) */
int area(int w, int h) { return w * h; }
int main(void) { printf("%d", area(3, 4)); }

/* (나) */
struct Order { int id; int qty; int price; char memo[100]; };
int total(struct Order o) { return o.qty * o.price; }

/* (다) */
void print_report(int mode) {
    if (mode == 1) print_summary();
    else print_detail();
}

/* (라) */
int g_tax_rate;            /* 전역 변수 */
void set_rate(void) { g_tax_rate = 10; }
int calc(int price) { return price * g_tax_rate / 100; }
```

<details>
<summary>정답과 해설</summary>

정답: (가) 자료 결합도, (나) 스탬프 결합도, (다) 제어 결합도, (라) 공통 결합도

결합도(Coupling)는 모듈 사이에 주고받는 정보의 종류와 양으로 판정한다. 무엇을 넘기는지를 먼저 보고, 다음 표의 판정 질문에 차례로 답하면 된다.

| 코드 | 넘기는 것                   | 판정 질문                                          | 결합도        |
| ---- | --------------------------- | -------------------------------------------------- | ------------- |
| (가) | 정수 두 개                  | 필요한 값만 인자로 넘기는가                        | 자료(Data)    |
| (나) | 구조체 전체                 | 묶음을 넘기고 그중 일부만 쓰는가                   | 스탬프(Stamp) |
| (다) | 동작을 고르는 플래그 `mode` | 호출하는 쪽이 호출당하는 쪽의 처리 흐름을 정하는가 | 제어(Control) |
| (라) | 인자 없음, 전역 변수 공유   | 여러 모듈이 같은 전역 데이터를 읽고 쓰는가         | 공통(Common)  |

(나)의 `total`은 qty와 price 두 값만 쓰는데 memo 100바이트를 포함한 구조체 전체를 받는다. Order 구조체에 필드가 추가되거나 바뀌면, `total`은 그 필드를 쓰지 않아도 다시 컴파일해야 한다. 이것이 자료 결합도보다 나쁜 이유다.

(다)의 `mode`는 데이터가 아니라 "요약을 출력하라", "상세를 출력하라"는 지시다. 호출하는 쪽이 `print_report` 내부에 분기가 두 개 있다는 사실을 알아야 값을 고를 수 있다.

(라)의 `set_rate`와 `calc`는 인자를 하나도 주고받지 않지만 전역 변수 `g_tax_rate`를 통해 연결된다. 어느 모듈이 값을 바꿨는지 추적하기 어렵다.

**헷갈리는 오답 후보와 구별법**

| 헷갈리는 짝                 | 구별법                                                                                                                         |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 자료 ↔ 스탬프               | 넘긴 것이 낱개 값이면 자료, 구조체·배열·레코드 같은 묶음이면 스탬프                                                            |
| 제어 결합도 ↔ 논리적 응집도 | 플래그가 모듈 ==사이==를 오가면 제어 결합도, 한 모듈 ==안에서== 플래그로 기능을 고르는 구조는 논리적 응집도                    |
| 공통 ↔ 외부                 | 전역 데이터 영역을 여러 모듈이 공유하면 공통, 외부에서 정한 형식(파일 형식, 통신 프로토콜, 장치 인터페이스)을 함께 따르면 외부 |

> [!WARNING] 이 문제의 함정
> (다)에는 `if`가 있어서 "분기가 있으니 제어 흐름 문제"라고만 보고 답을 못 쓰는 경우가 있다. 질문은 함수 ==사이== 관계이므로 `print_report`를 부르는 쪽이 `mode`를 넘기는 관계를 본다. 같은 코드를 "print_report 함수의 응집도"로 물으면 답은 논리적 응집도다.

시험에서 실수하는 지점은 "결합도"를 빼고 "자료", "스탬프"만 쓰는 답안이다. 문제가 "결합도의 이름"을 물으면 "자료 결합도"처럼 끝까지 쓴다. 영문을 요구하면 Data Coupling처럼 쓴다.

</details>

> [!NOTE] 개념 요약
>
> - 결합도는 모듈 사이의 의존 정도이고, 약한(좋은) 것부터 자료 → 스탬프 → 제어 → 외부 → 공통 → 내용 순이다. 첫 글자로 "자스제외공내"
> - 판정: 낱개 값만 넘기면 자료, 구조체·배열 같은 묶음이면 스탬프, 처리 흐름을 정하는 플래그면 제어, 외부에서 정한 형식을 함께 따르면 외부, 전역 데이터를 공유하면 공통, 다른 모듈의 내부를 직접 참조하거나 고치면 내용
> - 좋은 설계는 결합도는 낮게, 응집도는 높게 만든다

### 예제 6. 응집도를 보기에서 골라 쓰기

> 출제: 2021년 실기 2회 · 설명에 맞는 응집도 쓰기

다음 설명 ①~③에 해당하는 응집도를 〈보기〉에서 골라 쓰시오.

① 하나의 모듈 안에 회원 조회, 회원 등급 계산, 등급별 쿠폰 발급이 순서대로 들어 있는데, 세 작업이 주고받는 데이터는 없고 실행 순서만 정해져 있다.
② 하나의 모듈이 같은 고객 레코드를 입력으로 받아, 그 레코드로 주소 라벨을 출력하는 기능과 구매 이력 통계를 내는 기능을 함께 수행한다.
③ 프로그램을 시작하는 시각에 실행해야 하는 설정 파일 읽기, 로그 파일 열기, 캐시 초기화를 한 모듈에 모았다.

〈보기〉 기능적, 순차적, 교환적, 절차적, 시간적, 논리적, 우연적

<details>
<summary>정답과 해설</summary>

정답: ① 절차적 응집도, ② 교환적 응집도, ③ 시간적 응집도

응집도(Cohesion)는 한 모듈 안의 요소들이 얼마나 하나의 목적으로 묶여 있는지를 나타낸다. 판정은 "요소들이 무엇을 공유하는가"로 한다.

| 설명 | 요소 사이에 공유하는 것                  | 응집도                  |
| ---- | ---------------------------------------- | ----------------------- |
| ①    | 실행 순서만 공유, 데이터 전달 없음       | 절차적(Procedural)      |
| ②    | 같은 입력 데이터를 공유, 순서는 상관없음 | 교환적(Communicational) |
| ③    | 실행 시각(프로그램 시작 시각)만 공유     | 시간적(Temporal)        |

**헷갈리는 오답 후보와 구별법**

| 오답 후보           | 왜 아닌가                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------ |
| ①을 순차적으로 답함 | 순차적은 앞 작업의 ==출력이 다음 작업의 입력==이 된다. ①은 "주고받는 데이터는 없다"고 했다 |
| ②를 순차적으로 답함 | 라벨 출력 결과가 통계 계산에 쓰이지 않는다. 같은 입력을 나눠 쓰기만 하므로 교환적이다      |
| ②를 기능적으로 답함 | 기능적은 모듈 전체가 하나의 기능만 한다. ②는 서로 다른 기능 두 개를 수행한다               |
| ③을 절차적으로 답함 | 세 작업 사이에 정해진 순서가 없다. 같은 시각에 실행된다는 점만 같다                        |

> [!WARNING] 이 문제의 함정
> ①에 "순서대로"라는 말이 있어서 순차적 응집도를 쓰기 쉽다. "순서"라는 단어보다 "데이터가 이어지는가"를 먼저 확인한다.

시험에서 실수하는 지점은 교환적 응집도를 "통신적 응집도"로 쓰는 경우다. 영문 Communicational을 그대로 옮긴 말이라 의미는 같지만, 〈보기〉가 주어진 문제는 보기에 있는 말로 써야 한다.

</details>

> [!NOTE] 개념 요약
>
> - 응집도는 한 모듈 안 요소들의 관련 정도이고, 강한(좋은) 것부터 기능적 → 순차적 → 교환적 → 절차적 → 시간적 → 논리적 → 우연적 순이다
> - 판정: 하나의 기능만 하면 기능적, 앞 작업의 출력이 다음 입력이면 순차적, 같은 입력·출력 데이터를 공유하면 교환적, 실행 순서만 공유하면 절차적, 같은 시각에 실행될 뿐이면 시간적, 비슷한 성격의 기능을 플래그로 고르면 논리적, 아무 관련이 없으면 우연적
> - 실기는 가운데 구간(교환적, 절차적, 시간적)의 구별을 자주 묻는다. "순서"라는 단어보다 데이터가 이어지는지를 먼저 확인한다

### 예제 7. 설명을 보고 디자인 패턴 이름 쓰기

> 출제: 2022년 실기 3회 · Bridge·Observer, 2023년 실기 2회 · Singleton·Visitor, 2021년 실기 3회 · Factory Method

다음 설명에 해당하는 GoF 디자인 패턴의 이름을 영문으로 쓰시오.

① 결제 수단(카드, 계좌 이체)과 결제 화면(웹, 모바일 앱)이 각각 늘어날 때 조합마다 클래스를 만들지 않도록, 화면 계층과 결제 수단 계층을 따로 두고 화면 객체가 결제 수단 객체를 참조하게 한다.
② 문서를 이루는 요소(문단, 표, 그림) 클래스는 고치지 않고, 글자 수 집계, PDF 변환 같은 새 연산을 별도 클래스로 추가해 요소 구조를 순회하며 적용한다.
③ 상위 클래스는 객체를 만드는 메서드의 형식만 정하고, 어떤 클래스의 객체를 만들지는 하위 클래스가 그 메서드를 재정의해 결정한다.

<details>
<summary>정답과 해설</summary>

정답: ① Bridge, ② Visitor, ③ Factory Method

GoF(Gang of Four) 디자인 패턴은 감마(Gamma) 등 네 저자가 1994년 책에서 정리한 23개 설계 패턴이고, 생성·구조·행위 세 분류로 나뉜다. 설명에서 핵심 단어를 찾아 분류부터 정하면 후보가 줄어든다.

| 설명 | 핵심 단어                                   | 분류 | 패턴           |
| ---- | ------------------------------------------- | ---- | -------------- |
| ①    | 두 계층을 분리, 조합 폭발 방지, 참조로 연결 | 구조 | Bridge         |
| ②    | 요소 클래스는 그대로, 새 연산을 밖에서 추가 | 행위 | Visitor        |
| ③    | 생성 메서드, 하위 클래스가 결정             | 생성 | Factory Method |

①을 상속으로만 조합하면 화면 2종 × 수단 2종 = 4개 클래스가 필요하고, 화면 3종, 수단 4종이면 12개가 된다. Bridge는 두 계층을 분리해 3 + 4 = 7개로 줄인다.

**헷갈리는 오답 후보와 구별법**

| 헷갈리는 짝                       | 구별법                                                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Bridge ↔ Adapter                  | Adapter는 ==이미 있는== 호환되지 않는 인터페이스를 맞춰 주는 변환기, Bridge는 ==처음부터== 두 계층을 분리하는 설계                |
| Visitor ↔ Iterator                | Iterator는 요소를 하나씩 꺼내는 방법만 제공, Visitor는 요소마다 수행할 연산을 외부 클래스로 분리                                  |
| Visitor ↔ Strategy                | Strategy는 하나의 알고리즘을 통째로 바꿔 끼움, Visitor는 요소 타입마다 다른 연산을 구조 전체에 적용                               |
| Factory Method ↔ Abstract Factory | Factory Method는 ==메서드 하나==를 하위 클래스가 재정의, Abstract Factory는 관련 객체 ==여러 개의 묶음==을 만드는 공장 인터페이스 |

> [!WARNING] 이 문제의 함정
> ③을 "Factory"나 "Factory Pattern"으로만 쓰면 Abstract Factory와 구별되지 않아 오답 처리될 수 있다. "Method"까지 정확히 쓴다.

시험에서 실수하는 지점은 영문을 요구하는데 "브리지", "방문자"처럼 한글로 쓰거나, Observer를 Obsever처럼 철자를 틀리는 것이다.

</details>

> [!NOTE] 개념 요약
>
> - 생성(객체를 만드는 방법) 5개: Abstract Factory, Builder, Factory Method, Prototype, Singleton
> - 구조(클래스·객체를 조합하는 방법) 7개: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy
> - 행위(객체 사이의 책임 분배와 통신) 11개: Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor
> - 설명에서 분류부터 정하면 후보가 줄어든다. 영문으로 쓰게 하는 문제가 많아 철자까지 외운다

### 예제 8. 테스트 커버리지 판정과 블랙박스 기법

> 출제: 2023년 실기 2회 · 조건 커버리지, 2021년 실기 3회 · 원인-결과 그래프, 2022년 실기 2회 · 회귀 테스트

(1) 다음 함수에 테스트 세트 A와 B를 각각 실행했다. 각 세트가 만족하는 커버리지를 〈보기〉에서 모두 고르시오. 커버리지는 단락 평가(앞 조건만으로 결과가 정해지면 뒤 조건을 계산하지 않는 것)를 고려하지 않고 조건식 단위로 판정한다.

```c
int check(int a, int b) {
    if (a > 0 && b > 0)
        return 1;
    return 0;
}
```

| 세트 | 테스트 입력 (a, b) |
| ---- | ------------------ |
| A    | (1, −1), (−1, 1)   |
| B    | (1, 1), (−1, 1)    |

〈보기〉 ㄱ. 구문 커버리지 ㄴ. 결정 커버리지 ㄷ. 조건 커버리지

(2) 다음 설명에 해당하는 테스트 기법이나 테스트 종류를 쓰시오.

① 입력 조건(원인)과 출력(결과)의 관계를 그래프로 표현하고, 그 그래프를 결정 테이블로 바꿔 테스트 케이스를 도출하는 블랙박스 기법
② 결함을 수정하거나 기능을 추가한 뒤, 그 변경 때문에 기존에 잘 되던 기능에 새로운 결함이 생기지 않았는지 다시 확인하는 테스트

<details>
<summary>정답과 해설</summary>

정답: (1) A: ㄷ, B: ㄱ, ㄴ (2) ① 원인-결과 그래프(Cause-Effect Graph), ② 회귀 테스트(Regression Test)

**(1) 해설**

먼저 세 커버리지의 기준을 정리한다.

| 커버리지 | 영문               | 만족 조건                                                                        |
| -------- | ------------------ | -------------------------------------------------------------------------------- |
| 구문     | Statement Coverage | 모든 문장이 한 번 이상 실행된다                                                  |
| 결정     | Decision Coverage  | 결정문(if 전체 조건식)의 결과가 참, 거짓 모두 한 번 이상 나온다                  |
| 조건     | Condition Coverage | 결정문 안의 개별 조건식(`a > 0`, `b > 0`)이 각각 참, 거짓 모두 한 번 이상 나온다 |

다음으로 입력마다 개별 조건과 결정 결과를 표로 계산한다.

| 세트 | 입력    | `a > 0` | `b > 0` | 결정 `a>0 && b>0` | 실행된 문장 |
| ---- | ------- | ------- | ------- | ----------------- | ----------- |
| A    | (1, −1) | 참      | 거짓    | 거짓              | `return 0`  |
| A    | (−1, 1) | 거짓    | 참      | 거짓              | `return 0`  |
| B    | (1, 1)  | 참      | 참      | 참                | `return 1`  |
| B    | (−1, 1) | 거짓    | 참      | 거짓              | `return 0`  |

세트별로 판정하면 다음과 같다.

| 세트 | 구문                       | 결정                 | 조건                                   |
| ---- | -------------------------- | -------------------- | -------------------------------------- |
| A    | 불만족 (`return 1` 미실행) | 불만족 (거짓만 나옴) | ==만족== (두 조건 모두 참·거짓이 나옴) |
| B    | 만족                       | ==만족== (참, 거짓)  | 불만족 (`b > 0`이 참만 나옴)           |

세트 A는 개별 조건이 각각 참과 거짓을 모두 가졌는데도 결정 전체는 거짓만 나왔다. 조건 커버리지를 만족해도 결정 커버리지가 보장되지 않는 대표적인 예다. 이 함수에서 MC/DC는 (1, 1), (−1, 1), (1, −1) 세 입력으로 만족한다.

**(2) 해설**

| 설명 | 정답             | 헷갈리는 오답 후보    | 구별법                                                                                              |
| ---- | ---------------- | --------------------- | --------------------------------------------------------------------------------------------------- |
| ①    | 원인-결과 그래프 | 결정 테이블 테스트    | 결정 테이블은 조건 조합을 표로 바로 만든다. "그래프로 표현"이 있으면 원인-결과 그래프               |
| ②    | 회귀 테스트      | 재테스트(확인 테스트) | 재테스트는 ==고친 결함 자체==가 해결됐는지 확인, 회귀 테스트는 ==다른 기능==에 부작용이 없는지 확인 |

> [!WARNING] 이 문제의 함정
> (1)에서 "조건 커버리지가 결정 커버리지보다 강하다"고 외워 두고 A에 ㄴ까지 고르는 실수가 많다. 조건과 결정은 서로 포함 관계가 아니다.

시험에서 실수하는 지점은 커버리지 이름을 "분기 커버리지"와 "결정 커버리지" 중 어느 쪽으로 써야 하는지다. 둘은 같은 기준이므로 문제가 보기를 주지 않으면 "결정(분기) 커버리지"처럼 함께 써도 된다.

</details>

> [!NOTE] 개념 요약
>
> - 화이트박스 커버리지: 구문(모든 문장), 결정·분기(결정 결과 참·거짓), 조건(개별 조건 참·거짓), 조건/결정(두 기준 모두), MC/DC(변형 조건/결정, 각 조건이 결정 결과에 독립적으로 영향), 다중 조건(조건 조합 전부)
> - 결정 커버리지를 만족하면 구문 커버리지도 만족하지만, 조건과 결정은 서로 포함 관계가 아니다
> - 블랙박스 기법: 동등 분할, 경계값 분석, 결정 테이블, 원인-결과 그래프, 상태 전이, 오류 예측, 비교 검사
> - 재테스트(확인 테스트)는 고친 결함 자체를, 회귀 테스트는 변경 때문에 다른 기능에 생긴 부작용을 확인한다

### 예제 9. UML 관계와 다이어그램 빈칸

> 출제: 2021년 실기 3회 · 클래스 간 관계(집약, 일반화), 2023년 실기 3회 · 패키지 다이어그램, 2022년 실기 3회 · UML 구성 요소

다음 설명의 빈칸 ①~⑤에 들어갈 용어를 쓰시오.

UML의 구성 요소는 사물(Things), ( ① ), 다이어그램 세 가지다. 클래스 사이의 관계 중 '대학교'와 '학과'처럼 전체가 삭제되면 부분도 함께 삭제되는 강한 전체-부분 관계는 ( ② )이고, '동아리'와 '학생'처럼 전체가 없어져도 부분이 독립적으로 존재하는 관계는 ( ③ )이다. '결제'와 '카드결제'처럼 상위 개념과 하위 개념의 관계는 ( ④ )이며, 속이 빈 삼각형 화살표로 그린다. 서로 관련된 클래스나 유스케이스를 묶은 그룹과 그 그룹 사이의 의존 관계를 표현하는 구조 다이어그램은 ( ⑤ ) 다이어그램이다.

<details>
<summary>정답과 해설</summary>

정답: ① 관계(Relationships), ② 합성(Composition, 포함), ③ 집약(Aggregation), ④ 일반화(Generalization), ⑤ 패키지(Package)

UML(Unified Modeling Language)은 OMG가 표준으로 관리하는 소프트웨어 모델링 언어다.

| 빈칸 | 정답   | 표기법                                  | 생명 주기 의존          |
| ---- | ------ | --------------------------------------- | ----------------------- |
| ②    | 합성   | 전체 쪽에 ==채운== 마름모(◆)            | 부분이 전체와 함께 삭제 |
| ③    | 집약   | 전체 쪽에 ==빈== 마름모(◇)              | 부분이 독립적으로 존재  |
| ④    | 일반화 | 하위에서 상위로 향하는 빈 삼각형 화살표 | 해당 없음 (상속 관계)   |

![합성은 채운 마름모, 집약은 빈 마름모, 일반화는 빈 삼각형, 실체화는 점선과 빈 삼각형으로 그리는 UML 관계 표기](./images/eip-practical-exam-theory-uml-relations.svg '마름모는 전체 쪽에 붙고, 삼각형은 상위 개념 쪽을 가리킨다')

**헷갈리는 오답 후보와 구별법**

| 헷갈리는 짝                  | 구별법                                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| 합성 ↔ 집약                  | "전체가 삭제되면 부분도 삭제되는가"를 묻는다. 예이면 합성, 아니오이면 집약                               |
| 일반화 ↔ 실체화              | 일반화는 클래스가 클래스를 상속(실선 + 빈 삼각형), 실체화는 클래스가 인터페이스를 구현(점선 + 빈 삼각형) |
| 패키지 ↔ 컴포넌트 다이어그램 | 패키지는 설계 요소를 ==논리적==으로 묶은 그룹, 컴포넌트는 실행 가능한 소프트웨어 부품과 인터페이스       |

> [!WARNING] 이 문제의 함정
> ②와 ③의 순서를 바꿔 쓰는 실수가 가장 많다. 대학교가 폐교되면 그 대학교의 학과도 사라지므로 합성이고, 동아리가 해체돼도 학생은 학교에 남으므로 집약이다.

시험에서 실수하는 지점은 ②를 "포함"으로 쓸지 "합성"으로 쓸지다. 둘 다 Composition을 옮긴 말이므로 영문을 함께 써 두면 안전하다.

</details>

> [!NOTE] 개념 요약
>
> - UML 구성 요소는 사물(Things), 관계(Relationships), 다이어그램(Diagrams) 세 가지다
> - 관계와 표기: 연관(실선), 집약(빈 마름모), 합성(채운 마름모), 일반화(실선 + 빈 삼각형), 의존(점선 + 열린 화살표), 실체화(점선 + 빈 삼각형)
> - 구조 다이어그램은 클래스, 객체, 컴포넌트, 배치, 복합체 구조, 패키지이고, 행위 다이어그램은 유스케이스, 시퀀스, 커뮤니케이션, 상태, 활동, 상호작용 개요, 타이밍이다
> - 합성과 집약은 "전체가 삭제되면 부분도 삭제되는가"로 가른다

## 보안·네트워크·신기술

이 영역은 한 회차에 4~6문항이 나오고, 보기 없이 영문 약어나 용어를 직접 쓰게 하는 비율이 높다. 아래 문제는 한 줄짜리 정의 대신 실제 상황 묘사에서 단서를 찾아 용어를 쓰는 형식이다.

### 예제 10. 사고 대응 상황에서 보안 솔루션과 공격 이름 쓰기

> 출제: 2022년 실기 3회 · SIEM, 타이포스쿼팅, TrustZone

다음은 한 회사의 보안 사고 대응 기록이다. 빈칸 ①~③에 들어갈 용어를 쓰시오.

> 월요일 오전, 방화벽·웹 서버·DB 서버·백신이 남긴 로그를 한곳에 수집해 상관 분석하는 ( ① ) 콘솔에 경보가 떴다. 서로 다른 장비의 로그를 시간순으로 이어 보니, 직원 한 명이 회사 메일 서비스 주소 `mail.corp-example.com` 대신 `mail.corp-exampel.com`에 접속해 로그인 정보를 입력한 기록이 있었다. 공격자가 사람들이 자주 내는 오타를 노려 비슷한 철자의 도메인을 미리 등록해 둔 ( ② ) 공격이었다. 회사는 이후 업무용 스마트폰에서 지문 정보와 인증 키를 일반 운영체제와 분리된 프로세서의 보안 구역에 보관하도록 정책을 바꿨다. 이 하드웨어 기반 격리 기술은 ARM 프로세서의 ( ③ )이다.

<details>
<summary>정답과 해설</summary>

정답: ① SIEM(Security Information and Event Management), ② 타이포스쿼팅(Typosquatting), ③ 트러스트존(TrustZone)

| 빈칸 | 정답         | 판단 근거가 된 단어                                   |
| ---- | ------------ | ----------------------------------------------------- |
| ①    | SIEM         | 여러 장비의 로그 수집, 상관 분석, 경보                |
| ②    | 타이포스쿼팅 | 오타를 노림, 비슷한 철자의 도메인을 미리 등록         |
| ③    | TrustZone    | ARM 프로세서, 일반 구역과 보안 구역으로 하드웨어 분리 |

SIEM은 보안 정보 관리(SIM)와 보안 이벤트 관리(SEM)를 합친 솔루션이다. 장비 하나의 로그로는 정상처럼 보이는 행위도 여러 장비의 기록을 시간순으로 이어 보면(상관 분석) 공격의 흐름이 드러난다.

TrustZone은 프로세서를 일반 구역(Normal World)과 보안 구역(Secure World)으로 나눠, 일반 운영체제가 해킹당해도 보안 구역 메모리에는 접근하지 못하게 한다.

**헷갈리는 오답 후보와 구별법**

| 빈칸 | 오답 후보 | 구별법                                                                                                    |
| ---- | --------- | --------------------------------------------------------------------------------------------------------- |
| ①    | ESM       | ESM은 여러 보안 장비를 한 콘솔에서 ==관리==하는 통합 관리, SIEM은 로그를 수집해 ==분석==                  |
| ①    | IDS       | IDS는 네트워크나 호스트의 트래픽을 직접 감시하는 장비 하나, SIEM은 여러 장비의 로그를 모으는 쪽           |
| ②    | 피싱      | 피싱은 가짜 사이트로 유인하는 공격 전체를 가리키는 넓은 말. 문제가 "오타", "철자"를 강조하면 타이포스쿼팅 |
| ②    | 파밍      | 파밍은 사용자가 ==올바른 주소==를 입력해도 DNS나 hosts 파일을 조작해 가짜 사이트로 보낸다                 |
| ③    | TPM       | TPM은 메인보드에 붙는 별도 보안 칩, TrustZone은 프로세서 내부를 나누는 기술                               |

> [!WARNING] 이 문제의 함정
> 사용자가 직접 주소를 잘못 입력했다는 점이 파밍과의 결정적 차이다. "주소를 정확히 입력했는데도"라는 말이 있으면 파밍, "오타"나 "비슷한 철자"가 있으면 타이포스쿼팅이다.

시험에서 실수하는 지점은 SIEM을 SEIM으로 쓰는 철자 실수다. Security Information and Event Management의 앞 글자를 순서대로 떠올려 쓴다.

</details>

> [!NOTE] 개념 요약
>
> - 보안 솔루션: 방화벽(허용·차단 규칙), IDS(침입 탐지), IPS(탐지 후 차단), ESM(여러 보안 장비를 한 콘솔에서 통합 관리), SIEM(여러 장비의 로그를 수집해 상관 분석)
> - 가짜 사이트로 유도하는 공격: 피싱(메일·메시지로 가짜 사이트에 유인), 스미싱(문자 메시지 피싱), 파밍(DNS·hosts 조작으로 올바른 주소를 입력해도 가짜 사이트로 이동), 타이포스쿼팅(오타 도메인을 미리 등록)
> - 하드웨어 보안: TrustZone은 ARM 프로세서 내부를 일반 구역과 보안 구역으로 분리하고, TPM은 메인보드에 붙는 별도 보안 칩이다

### 예제 11. 암호 알고리즘 분류와 소프트웨어 위변조 방지

> 출제: 2022년 실기 2회 · IDEA·SKIPJACK, 2023년 실기 2회 · 대칭키·비대칭키 알고리즘 분류, 템퍼프루핑

(1) 다음 〈보기〉의 알고리즘을 대칭키 암호, 비대칭키(공개키) 암호, 해시 함수로 분류하시오.

〈보기〉 AES, RSA, SHA-256, SEED, ECC, ARIA, MD5, DES, ElGamal

(2) 다음 설명에 해당하는 대칭키 블록 암호를 쓰시오.

① 미국 국가안보국(NSA)이 개발해 음성 통신 암호화용 클리퍼 칩에 넣었고, 64비트 블록과 80비트 키를 사용한다.
② 스위스에서 개발된 PES를 개선한 알고리즘으로, 64비트 블록과 128비트 키를 사용하며 PGP 초기 버전에 쓰였다.

(3) 배포한 앱의 실행 파일이 변조되면 이를 탐지해 실행을 멈추도록, 실행 파일의 해시 값을 검사하는 코드와 코드 난독화를 함께 넣었다. 이처럼 소프트웨어가 위조·변조되는 것을 막거나 변조를 탐지하는 기술을 통틀어 무엇이라 하는지 쓰시오.

<details>
<summary>정답과 해설</summary>

정답:

| 분류     | 알고리즘             |
| -------- | -------------------- |
| 대칭키   | AES, SEED, ARIA, DES |
| 비대칭키 | RSA, ECC, ElGamal    |
| 해시     | SHA-256, MD5         |

(2) ① SKIPJACK, ② IDEA (3) 템퍼프루핑(Tamper Proofing)

**(1) 해설**

분류 기준은 "암호화와 복호화에 같은 키를 쓰는가"와 "복호화가 가능한가"다.

| 분류     | 키                               | 복호화 | 판단 단서                                        |
| -------- | -------------------------------- | ------ | ------------------------------------------------ |
| 대칭키   | 암호화와 복호화에 같은 비밀키    | 가능   | 블록 크기(64·128비트), 라운드 수가 함께 설명된다 |
| 비대칭키 | 공개키로 암호화, 개인키로 복호화 | 가능   | 소인수분해, 이산대수, 타원곡선 같은 수학 문제    |
| 해시     | 키 없음                          | 불가능 | 고정 길이 출력, 일방향, 충돌                     |

**(2) 해설**

| 알고리즘 | 개발                            | 블록   | 키      | 구별 단서                            |
| -------- | ------------------------------- | ------ | ------- | ------------------------------------ |
| SKIPJACK | 미국 NSA                        | 64비트 | 80비트  | 클리퍼 칩, 음성 통신                 |
| IDEA     | 스위스 라이(Lai)와 메시(Massey) | 64비트 | 128비트 | PES 개선, PGP                        |
| DES      | IBM, 미국 표준                  | 64비트 | 56비트  | 16라운드 페이스텔 구조, AES로 대체됨 |

세 알고리즘은 블록 크기가 모두 64비트라서 블록 크기로는 구별할 수 없다. 키 길이와 개발 주체로 구별한다.

**(3) 해설**

템퍼프루핑은 소프트웨어의 위변조를 방지하는 기술의 총칭이다. 해시 값 비교로 변조를 탐지하는 무결성 검사, 코드를 읽기 어렵게 바꾸는 난독화, 디버거가 붙으면 실행을 멈추는 안티 디버깅이 여기에 속한다.

| 오답 후보       | 구별법                                                                                    |
| --------------- | ----------------------------------------------------------------------------------------- |
| 코드 난독화     | 난독화는 템퍼프루핑의 한 수단이다. 문제가 "통틀어"라고 물으면 상위 용어를 쓴다            |
| 디지털 워터마킹 | 저작권자 정보를 콘텐츠에 숨겨 넣어 출처를 증명한다. 변조 탐지와 실행 중단이 목적이 아니다 |

> [!WARNING] 이 문제의 함정
> MD5와 SHA-256은 "암호"라는 말 때문에 대칭키로 분류하기 쉽다. 키를 쓰지 않고 되돌릴 수 없으므로 해시 함수다.

시험에서 실수하는 지점은 SKIPJACK과 IDEA를 바꿔 쓰는 것이다. "NSA, 클리퍼 칩"은 SKIPJACK, "PES, PGP"는 IDEA로 단서와 이름을 짝지어 외운다.

</details>

> [!NOTE] 개념 요약
>
> - 대칭키 블록 암호: DES(64비트 블록, 56비트 키), AES(128비트 블록, 128·192·256비트 키), SEED·ARIA(국내 개발, 128비트 블록), IDEA, SKIPJACK. 스트림 암호는 RC4, LFSR
> - 비대칭키 암호는 RSA(소인수분해), ElGamal(이산대수), ECC(타원곡선)이고, Diffie-Hellman은 이산대수에 기반한 키 교환 방식이다
> - 해시 함수는 MD5(128비트 출력), SHA-1(160비트), SHA-256, HAS-160처럼 키 없이 고정 길이 값을 만들고 되돌릴 수 없다
> - 소프트웨어 보호에서 템퍼프루핑은 위변조 방지 기술의 총칭(무결성 검사, 난독화, 안티 디버깅), 워터마킹은 저작권 정보를 숨겨 넣는 기술이다

### 예제 12. 인증·인가와 접근 통제 정책

> 출제: 2021년 실기 3회 · AAA, 2023년 실기 3회 · OAuth, 접근 통제 MAC·RBAC·DAC

(1) 사내 VPN 접속 과정의 설명 ①~③에 해당하는 AAA 기능을 영문으로 쓰시오.

① 사용자가 아이디와 OTP를 입력하자 서버가 등록된 사용자인지 확인했다.
② 확인된 사용자가 영업팀 소속이라 영업 서버에는 접속할 수 있고 개발 서버에는 접속할 수 없도록 했다.
③ 접속 시각, 접속 시간, 전송한 데이터양을 기록해 월말에 부서별 사용량을 집계했다.

(2) 다음 상황 ④~⑥에 맞는 접근 통제 정책을 〈보기〉에서 골라 쓰시오.

④ 파일을 만든 사람이 직접 다른 직원에게 읽기·쓰기 권한을 줄지 정한다.
⑤ 문서마다 '대외비', '비밀' 같은 보안 등급을 붙이고, 사용자의 인가 등급이 문서 등급 이상일 때만 열람을 허용한다. 문서 작성자도 이 규칙을 바꿀 수 없다.
⑥ '회계 담당자'라는 직무에 전표 조회·승인 권한을 묶어 두고, 직원이 부서를 옮기면 직무만 바꿔 준다.

〈보기〉 MAC, DAC, RBAC

(3) 사용자가 사진 인화 웹사이트에서 "클라우드 사진함에서 가져오기"를 누르자, 클라우드 사이트의 로그인 화면이 열렸고 로그인 후 "사진 읽기 권한을 허용할까요?"라는 동의 화면이 나왔다. 인화 사이트는 사용자의 비밀번호를 받지 않고 토큰으로 사진만 읽어 갔다. 이 권한 위임에 쓰인 개방형 표준 프로토콜을 쓰시오.

<details>
<summary>정답과 해설</summary>

정답: (1) ① Authentication, ② Authorization, ③ Accounting (2) ④ DAC, ⑤ MAC, ⑥ RBAC (3) OAuth (OAuth 2.0)

**(1) 해설**

| 설명 | 기능           | 한글            | 묻는 질문            |
| ---- | -------------- | --------------- | -------------------- |
| ①    | Authentication | 인증            | 누구인가             |
| ②    | Authorization  | 인가            | 무엇을 할 수 있는가  |
| ③    | Accounting     | 계정 관리(과금) | 무엇을 얼마나 했는가 |

인증과 인가는 순서가 정해져 있다. 누구인지 확인(인증)해야 그 사람에게 어떤 권한이 있는지 정할(인가) 수 있다. ③을 "Auditing"으로 쓰면 틀린다. AAA의 세 번째 A는 Accounting이다.

**(2) 해설**

| 정책 | 영문                         | 권한을 정하는 주체              | 판단 단서                        |
| ---- | ---------------------------- | ------------------------------- | -------------------------------- |
| DAC  | Discretionary Access Control | 데이터 소유자                   | "만든 사람이", "소유자 재량"     |
| MAC  | Mandatory Access Control     | 시스템(관리자가 정한 보안 등급) | "등급", "레이블", "바꿀 수 없다" |
| RBAC | Role-Based Access Control    | 관리자가 정의한 역할(직무)      | "직무", "역할", "부서 이동"      |

⑤의 "문서 작성자도 이 규칙을 바꿀 수 없다"가 MAC과 DAC를 가르는 문장이다. DAC에서는 소유자가 권한을 마음대로 줄 수 있지만, MAC에서는 소유자라도 등급 규칙을 넘어설 수 없다.

**(3) 해설**

| 오답 후보      | 구별법                                                                                            |
| -------------- | ------------------------------------------------------------------------------------------------- |
| SSO            | 한 번 로그인으로 여러 서비스를 이용하는 ==사용자 편의== 기술. 제3자에게 권한을 넘기는 것이 아니다 |
| OpenID Connect | OAuth 2.0 위에서 사용자가 누구인지(ID 토큰) 알려 주는 ==인증== 계층. 사진만 읽어 간 것은 인가다   |

> [!WARNING] 이 문제의 함정
> (3)에는 "로그인 화면"이 나와서 SSO나 인증 기술로 답하기 쉽다. 핵심은 "비밀번호를 받지 않고", "사진 읽기 권한", "토큰"이다. 인화 사이트가 얻은 것은 사용자의 신원이 아니라 제한된 범위의 권한이다.

시험에서 실수하는 지점은 Authentication과 Authorization의 철자를 섞어 쓰는 것이다. 인증은 "진짜인지(authentic)" 확인하는 일, 인가는 "권한(authority)"을 주는 일로 어원과 함께 외운다.

</details>

> [!NOTE] 개념 요약
>
> - AAA는 Authentication(인증, 누구인가) → Authorization(인가, 무엇을 할 수 있는가) → Accounting(계정 관리, 무엇을 얼마나 했는가) 순서로 동작하고, 대표 프로토콜은 RADIUS와 TACACS+다
> - 접근 통제: DAC는 소유자 재량(신분 기반), MAC는 시스템이 보안 등급·레이블로 강제, RBAC는 역할에 권한을 묶고 사용자에게 역할을 부여한다
> - OAuth 2.0은 제3자에게 토큰으로 제한된 권한을 위임하는 인가 표준, OpenID Connect는 그 위의 인증 계층, SSO는 한 번 로그인으로 여러 서비스를 쓰는 방식이다

### 예제 13. 라우팅 프로토콜과 클라우드 서비스 모델

> 출제: 2022년 실기 2회 · IGP·EGP·OSPF·BGP 빈칸, 2023년 실기 3회 · RIP, IaaS·PaaS·SaaS

(1) 빈칸 ①~④에 들어갈 용어를 영문 약어로 쓰시오.

인터넷은 하나의 기관이 같은 정책으로 운영하는 라우터 묶음인 자율 시스템(AS)이 서로 연결된 구조다. AS 내부에서 쓰는 라우팅 프로토콜을 ( ① ), AS 사이에서 쓰는 것을 EGP라고 한다. AS 내부 프로토콜 중 ( ② )는 거리 벡터 방식으로 목적지까지 거치는 라우터 수(홉 수)를 거리로 삼고 최대 15홉까지만 표현할 수 있어 소규모 망에 쓴다. ( ③ )는 링크 상태 방식으로 망 전체의 연결 상태를 데이터베이스로 만들고 다익스트라 알고리즘으로 최단 경로를 계산한다. 오늘날 인터넷의 AS 사이 경로는 경로 벡터 방식의 ( ④ )가 정한다.

(2) 다음 상황 ⑤~⑦에 해당하는 클라우드 서비스 모델을 쓰시오.

⑤ 스타트업이 가상 서버 4대와 블록 스토리지를 빌려, 운영체제 설치와 보안 패치, 웹 서버 설정까지 직접 한다.
⑥ 개발팀이 코드만 올리면 클라우드가 런타임, 데이터베이스 연결, 자동 확장을 맡아 주고, 운영체제는 신경 쓰지 않는다.
⑦ 회사가 웹 브라우저로 접속하는 메일·문서 협업 서비스를 계정 수만큼 월 요금을 내고 쓴다.

<details>
<summary>정답과 해설</summary>

정답: (1) ① IGP, ② RIP, ③ OSPF, ④ BGP (2) ⑤ IaaS, ⑥ PaaS, ⑦ SaaS

**(1) 해설**

| 빈칸 | 프로토콜 | 분류 | 방식      | 경로 선택 기준        | 판단 단서                 |
| ---- | -------- | ---- | --------- | --------------------- | ------------------------- |
| ②    | RIP      | IGP  | 거리 벡터 | 홉 수 (최대 15)       | "홉 수", "15", "소규모"   |
| ③    | OSPF     | IGP  | 링크 상태 | 링크 비용, 다익스트라 | "링크 상태", "다익스트라" |
| ④    | BGP      | EGP  | 경로 벡터 | AS 경로와 정책        | "AS 사이", "경로 벡터"    |

**(2) 해설**

클라우드 서비스 모델은 "사용자가 어디까지 관리하는가"로 구별한다.

| 관리 대상            | IaaS   | PaaS   | SaaS   |
| -------------------- | ------ | ------ | ------ |
| 애플리케이션         | 사용자 | 사용자 | 제공자 |
| 런타임·미들웨어      | 사용자 | 제공자 | 제공자 |
| 운영체제             | 사용자 | 제공자 | 제공자 |
| 가상화·서버·스토리지 | 제공자 | 제공자 | 제공자 |

⑤는 운영체제부터 사용자가 관리하므로 IaaS, ⑥은 애플리케이션 코드만 관리하므로 PaaS, ⑦은 완성된 소프트웨어를 쓰기만 하므로 SaaS다.

**헷갈리는 오답 후보와 구별법**

| 헷갈리는 짝 | 구별법                                                                            |
| ----------- | --------------------------------------------------------------------------------- |
| PaaS ↔ SaaS | 사용자가 ==자기 코드==를 올리면 PaaS, 남이 만든 소프트웨어를 ==그대로 쓰면== SaaS |

> [!WARNING] 이 문제의 함정
> ⑤에 "웹 서버 설정"이 있어서 PaaS로 답하기 쉽다. 운영체제 설치와 보안 패치를 사용자가 직접 한다면 IaaS다.

시험에서 실수하는 지점은 IaaS, PaaS, SaaS의 대소문자다. 가운데 'aa'는 "as a"의 앞 글자이므로 소문자로 쓴다.

</details>

> [!NOTE] 개념 요약
>
> - IGP(AS 내부)는 RIP(거리 벡터, 홉 수, 최대 15홉, 30초마다 라우팅 표 교환)와 OSPF(링크 상태, 다익스트라, 대규모 망)이고, EGP(AS 사이)의 대표는 BGP(경로 벡터)다
> - 거리 벡터는 이웃 라우터에게 자기 라우팅 표를 주기적으로 보내고, 링크 상태는 링크 정보를 망 전체에 퍼뜨려 각 라우터가 최단 경로를 직접 계산한다
> - 클라우드 서비스 모델은 IaaS(인프라 대여, 사용자가 운영체제부터 관리), PaaS(플랫폼 제공, 사용자는 코드만), SaaS(완성된 소프트웨어 사용)로, 사용자가 관리하는 범위로 구별한다

## 계산

계산 문제는 회차마다 0~2문항으로 많지는 않지만, 공식만 알면 확실히 점수를 얻는 문항이다. 서브네팅은 매년 한 번 이상 나왔고, CPU 스케줄링은 기법 이름을 쓰게 하거나 대기 시간을 계산하게 한다.

### 예제 14. 호스트 주소로 서브넷 정보 구하기

> 출제: 2022년 실기 2회 · IP 주소와 서브넷 마스크로 네트워크 주소, 호스트 수 구하기

IP 주소가 172.20.37.165이고 서브넷 마스크가 255.255.255.224인 호스트가 있다. 다음을 쓰시오.

(1) 이 호스트가 속한 서브넷의 네트워크 주소
(2) 이 서브넷의 브로드캐스트 주소
(3) 이 서브넷에서 호스트에 할당할 수 있는 주소의 개수
(4) 172.20.37.0/24를 이 마스크로 나눴을 때 만들어지는 서브넷 수와, 이 호스트가 속한 서브넷이 몇 번째인지(첫 서브넷을 1번으로)

<details>
<summary>정답과 해설</summary>

정답: (1) 172.20.37.160 (2) 172.20.37.191 (3) 30개 (4) 8개, 6번째

| 기호 | 뜻                                       |
| ---- | ---------------------------------------- |
| $p$  | 프리픽스 길이(마스크에서 1인 비트 수)    |
| $h$  | 호스트 비트 수 = $32 - p$                |
| $B$  | 블록 크기(서브넷 하나의 주소 수) = $2^h$ |
| $x$  | 호스트 주소의 마지막 옥텟 값             |
| $N$  | 네트워크 주소의 마지막 옥텟              |

1. 마스크의 마지막 옥텟 224를 2진수로 바꿔 프리픽스 길이를 구한다.

```math
224 = 11100000_2 \;\Rightarrow\; p = 8 + 8 + 8 + 3 = 27
```

2. 호스트 비트 수와 블록 크기를 구한다.

```math
h = 32 - 27 = 5,\qquad B = 2^5 = 32
```

3. 네트워크 주소는 마지막 옥텟을 블록 크기의 배수로 내림한 값이다. 165를 32로 나눈 몫을 구해 다시 32를 곱한다.

```math
N = \left\lfloor \frac{165}{32} \right\rfloor \times 32 = 5 \times 32 = 160
```

같은 결과를 비트 AND로 확인하면 다음과 같다. 호스트 주소와 마스크를 비트 단위로 AND 하면 호스트 비트가 모두 0이 된다.

```math
\begin{aligned}
165 &= 10100101_2 \\
224 &= 11100000_2 \\
165 \;\text{AND}\; 224 &= 10100000_2 = 160
\end{aligned}
```

4. 브로드캐스트 주소는 호스트 비트를 모두 1로 채운 주소, 즉 네트워크 주소에 블록 크기를 더하고 1을 뺀 값이다.

```math
N + B - 1 = 160 + 32 - 1 = 191
```

5. 할당 가능한 호스트 수는 네트워크 주소와 브로드캐스트 주소 두 개를 뺀다.

```math
2^5 - 2 = 30
```

6. /24를 /27로 나누면 빌린 비트가 3개이므로 서브넷 수는 $2^3 = 8$이다. 160은 0부터 32씩 늘어나는 시작 주소 중 여섯 번째다.

| 번호 | 네트워크 주소     | 할당 가능 범위 | 브로드캐스트 |
| ---- | ----------------- | -------------- | ------------ |
| 1    | 172.20.37.0       | .1 ~ .30       | .31          |
| 2    | 172.20.37.32      | .33 ~ .62      | .63          |
| 3    | 172.20.37.64      | .65 ~ .94      | .95          |
| 4    | 172.20.37.96      | .97 ~ .126     | .127         |
| 5    | 172.20.37.128     | .129 ~ .158    | .159         |
| 6    | ==172.20.37.160== | .161 ~ .190    | ==.191==     |
| 7    | 172.20.37.192     | .193 ~ .222    | .223         |
| 8    | 172.20.37.224     | .225 ~ .254    | .255         |

| 결과                | 값            |
| ------------------- | ------------- |
| 프리픽스            | /27           |
| 네트워크 주소       | 172.20.37.160 |
| 브로드캐스트 주소   | 172.20.37.191 |
| 할당 가능 호스트 수 | 30            |
| 서브넷 수, 위치     | 8개 중 6번째  |

> [!WARNING] 이 문제의 함정
> 172.20.x.x는 B 클래스 사설 대역(172.16.0.0~172.31.255.255)이라 기본 마스크 /16을 떠올리고 셋째 옥텟부터 계산하는 실수가 있다. 마스크가 주어지면 클래스는 무시하고 마스크만으로 계산한다.

시험에서 실수하는 지점은 (3)에 32를 쓰는 것이다. "주소의 개수"와 "할당 가능한 호스트 수"를 구별해서 읽는다.

</details>

> [!NOTE] 개념 요약
>
> - 프리픽스가 $p$이면 블록 크기는 $2^{32-p}$, 할당 가능한 호스트 수는 네트워크 주소와 브로드캐스트 주소를 뺀 $2^{32-p} - 2$다
> - 네트워크 주소는 해당 옥텟을 블록 크기의 배수로 내림한 값(주소 AND 마스크), 브로드캐스트 주소는 네트워크 주소 + 블록 크기 − 1이다
> - 서브넷 수는 $2^{\text{빌린 비트 수}}$다. 마지막 옥텟 128, 192, 224, 240, 248, 252는 /25~/30이고 블록 크기는 128, 64, 32, 16, 8, 4다
> - 마스크가 주어지면 A·B·C 클래스는 무시하고 마스크로만 계산한다

### 예제 15. SJF와 SRT의 평균 대기 시간

> 출제: 2022년 실기 3회 · SJF·RR·SRT 스케줄링 기법

다음 네 프로세스가 단일 CPU에 도착했다. (1) 비선점 SJF와 (2) 선점 SRT로 스케줄링했을 때 각각의 평균 대기 시간을 구하시오. 실행 시간이 같으면 먼저 도착한 프로세스를 먼저 실행하고, 문맥 교환 시간은 0으로 본다.

| 프로세스 | 도착 시각 | 실행 시간 |
| -------- | --------- | --------- |
| P1       | 0         | 6         |
| P2       | 1         | 3         |
| P3       | 2         | 8         |
| P4       | 4         | 2         |

<details>
<summary>정답과 해설</summary>

정답: (1) SJF 4.5 (2) SRT 3.5

| 기호  | 뜻                                    |
| ----- | ------------------------------------- |
| $A_i$ | 프로세스 $i$의 도착 시각              |
| $S_i$ | 프로세스 $i$의 실행 시간(서비스 시간) |
| $C_i$ | 프로세스 $i$의 종료 시각              |
| $T_i$ | 반환 시간 = $C_i - A_i$               |
| $W_i$ | 대기 시간 = $T_i - S_i$               |

| 기법 | 선점 여부 | 다음 실행 프로세스를 고르는 기준                                   |
| ---- | --------- | ------------------------------------------------------------------ |
| SJF  | 비선점    | CPU가 비는 시각에 도착해 있는 프로세스 중 실행 시간이 가장 짧은 것 |
| SRT  | 선점      | 새 프로세스가 도착할 때마다 ==남은== 실행 시간이 가장 짧은 것      |

**(1) SJF**

1. 시각 0에는 P1만 도착해 있으므로 P1이 0부터 6까지 끝까지 실행한다. 비선점이라 중간에 도착한 P2, P4가 더 짧아도 P1을 멈추지 않는다.
2. 시각 6에 대기 중인 프로세스는 P2(3), P3(8), P4(2)다. 가장 짧은 P4가 6부터 8까지 실행한다.
3. 시각 8에는 P2(3), P3(8) 중 P2가 8부터 11까지, 마지막으로 P3가 11부터 19까지 실행한다.

| 구간 | 0~6 | 6~8 | 8~11 | 11~19 |
| ---- | --- | --- | ---- | ----- |
| 실행 | P1  | P4  | P2   | P3    |

| 프로세스 | $A_i$ | $S_i$ | $C_i$ | $T_i = C_i - A_i$ | $W_i = T_i - S_i$ |
| -------- | ----- | ----- | ----- | ----------------- | ----------------- |
| P1       | 0     | 6     | 6     | 6                 | 0                 |
| P2       | 1     | 3     | 11    | 10                | 7                 |
| P3       | 2     | 8     | 19    | 17                | 9                 |
| P4       | 4     | 2     | 8     | 4                 | 2                 |

```math
\overline{W}_{\text{SJF}} = \frac{0 + 7 + 9 + 2}{4} = \frac{18}{4} = 4.5
```

**(2) SRT**

1. 시각 0에 P1이 실행을 시작한다.
2. 시각 1에 P2(3)가 도착한다. P1의 남은 시간은 5이므로 더 짧은 P2가 CPU를 빼앗는다.
3. 시각 2에 P3(8)가 도착하지만 P2의 남은 시간 2보다 길어서 P2가 계속 실행하고, 시각 4에 끝난다.
4. 시각 4에 P4(2)가 도착한다. 대기 중인 남은 시간은 P1 5, P3 8, P4 2이므로 P4가 4부터 6까지 실행한다.
5. 시각 6에 P1(남은 5)이 6부터 11까지, P3가 11부터 19까지 실행한다.

| 구간 | 0~1 | 1~4 | 4~6 | 6~11 | 11~19 |
| ---- | --- | --- | --- | ---- | ----- |
| 실행 | P1  | P2  | P4  | P1   | P3    |

![SJF와 SRT의 간트 차트를 위아래로 놓아, SRT에서는 P1이 1에서 멈췄다가 6에 다시 실행되는 것을 비교한 그림](./images/eip-practical-exam-theory-scheduling.svg 'SRT는 짧은 프로세스가 도착하면 실행 중인 P1을 멈추므로 P2와 P4의 대기 시간이 0이 된다')

| 프로세스 | $A_i$ | $S_i$ | $C_i$ | $T_i$ | $W_i$ |
| -------- | ----- | ----- | ----- | ----- | ----- |
| P1       | 0     | 6     | 11    | 11    | 5     |
| P2       | 1     | 3     | 4     | 3     | 0     |
| P3       | 2     | 8     | 19    | 17    | 9     |
| P4       | 4     | 2     | 6     | 2     | 0     |

```math
\overline{W}_{\text{SRT}} = \frac{5 + 0 + 9 + 0}{4} = \frac{14}{4} = 3.5
```

**결과 비교**

| 기법 | 평균 대기 시간 | 평균 반환 시간 | 실행 순서              |
| ---- | -------------- | -------------- | ---------------------- |
| SJF  | 4.5            | 9.25           | P1 → P4 → P2 → P3      |
| SRT  | ==3.5==        | 8.25           | P1 → P2 → P4 → P1 → P3 |

SRT는 짧은 작업을 바로 끼워 넣으므로 평균 대기 시간이 SJF보다 짧지만, 선점할 때마다 문맥 교환이 일어나 실제 시스템에서는 그 비용이 더해진다.

> [!WARNING] 이 문제의 함정
> P1의 SRT 대기 시간을 "6에 다시 시작했으니 6"으로 쓰는 실수가 많다. 대기 시간은 반환 시간에서 실행 시간을 뺀 값(11 − 6 = 5)이다. 시각 0~1에 이미 1만큼 실행했으므로 실제로 기다린 구간은 1~6의 5다.

시험에서 실수하는 지점은 대기 시간을 종료 시각에서 실행 시간만 빼고 도착 시각을 빼지 않는 것이다. P3를 19 − 8 = 11로 계산하면 틀리고, 도착 시각 2를 빼 17 − 8 = 9로 계산해야 한다.

</details>

> [!NOTE] 개념 요약
>
> - 비선점 기법은 FCFS(도착 순서), SJF(실행 시간이 짧은 순), HRN(응답률 = (대기 시간 + 실행 시간) ÷ 실행 시간이 큰 순)이다
> - 선점 기법은 RR(정해진 시간 할당량만큼 돌아가며 실행), SRT(남은 실행 시간이 가장 짧은 것), 다단계 큐, 다단계 피드백 큐다
> - 반환 시간 = 종료 시각 − 도착 시각, 대기 시간 = 반환 시간 − 실행 시간
> - SJF·SRT는 긴 프로세스가 계속 밀리는 기아 현상이 생길 수 있고, HRN과 에이징(오래 기다린 프로세스의 우선순위 상승)이 이를 보완한다
