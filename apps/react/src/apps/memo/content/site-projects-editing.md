프로필에 이어 프로젝트도 코드에서 꺼냈다. 프로젝트는 Safari 탭, Finder의 프로젝트 폴더, 터미널 `projects`, 사진 앨범, 그리고 데모를 창 안에 띄우는 **프로젝트 앱**(Dock·Launchpad)이 함께 쓰는 목록이다. 이제 관리자가 **시스템 설정 › 프로젝트**에서 순서를 바꾸고, 숨기고, 고치고, 새 프로젝트를 더한다.

## 서버에는 덮어쓸 값만

코드의 프로젝트 하나는 길다. 주요 기능, 장, 화면 모음, 출처까지 들어 있다. 이것을 통째로 서버에 옮기지 않고, 코드를 **기본값**으로 두고 서버에는 바꾼 것만 둔다.

```ts
interface ProjectEntry {
	id: string;
	hidden?: boolean;
	/** 코드의 기본값에 덮어쓸 맨 위 필드. null은 고를 수 있는 필드를 지운다 (예: 앱을 끈다) */
	override?: { [K in keyof Project]?: Project[K] | null };
}
```

- 서버 목록의 순서대로 보이고, 서버 목록에 없는 코드의 프로젝트는 끝에 붙는다. 나중에 코드에 프로젝트를 더해도 보인다.
- 코드에 없는 id는 새 프로젝트다. 빈 바탕에 덮어쓸 값을 채운다.
- 저장할 때는 기본값과 **다른 필드만** 남긴다(`overrideOf`). 이름 하나만 바꾸면 `{ id: 'macfolio', override: { name: '…' } }` 한 줄이다.

## 검사: 링크는 https만

이 값은 링크(`<a href>`)와 iframe 주소, 그림 주소가 된다. 서버와 화면이 함께 쓰는 `parseProjects()`(desktop-core)가 작은 스키마로 모든 필드를 검사한다.

- 저장소·데모·출처 링크는 `https:` 주소만. `javascript:` 같은 주소는 여기서 걸린다.
- 그림·영상은 사이트 안 경로(`/imgs/…`)나 https만. 따옴표·괄호·공백은 받지 않는다.
- 앱 아이콘은 이미지 폴더 기준 경로(`..` 없이)나 https, 색은 `#rrggbb`·`rgb()`만.
- id는 영어 소문자·숫자·`-`이고, 이 사이트의 앱 이름(`safari`, `finder`…)과 겹치면 안 된다. 프로젝트 앱의 이름이 곧 id이기 때문이다.
- 틀린 곳은 `프로젝트 newpick.url: https:// 주소여야 합니다.`처럼 경로와 함께 모두 돌려준다.

규칙을 만들고 나서 코드의 프로젝트를 모두 이 검사에 넣어 보는 시험을 더했더니, 바로 하나가 걸렸다. 한 장의 테마 팔레트가 18개라 처음 정한 한도 12개를 넘었다. 고급 JSON으로 그대로 저장할 수 있어야 하므로 한도를 30개로 올렸다.

## 앱 목록은 시작할 때 한 번 정해진다

어려운 것은 서버가 아니라 화면이었다. 프로필은 컴포넌트가 `useProfile()`로 읽으면 끝이었는데, 프로젝트는 여러 모듈이 **불러올 때** 계산해 둔다.

```ts
// apps/manifest.ts: 모듈을 불러올 때 한 번
export const PROJECT_APPS = PROJECTS.filter((project) => project.app && project.demo);
export const APP_NAMES = [...BUILTIN, ...PROJECT_APPS.map((project) => project.id), ...];
```

앱 목록, Dock, 창 컴포넌트 표, 사진 앨범이 모두 이렇다. 이것을 모두 반응형으로 바꾸는 대신, **이 모듈들을 불러오기 전에** 서버의 내용을 합치게 했다.

```ts
// main.tsx
void loadSiteContent().finally(() => import('./boot'));
```

`main.tsx`는 사이트 콘텐츠만 읽고, 앱은 `boot.tsx`에서 동적으로 불러온다. `PROJECTS` 배열은 바꾸지 않고 **안을 채운다**(`splice`). 혹시 먼저 읽어 간 모듈이 있어도 같은 배열을 본다. 그래서 저장한 내용은 새로고침하면 적용된다. 설정 화면도 저장한 뒤 "지금 새로고침" 단추를 보여 준다.

## 기다리지 않게: Worker가 HTML에 넣는다

앱을 그리기 전에 API를 기다리면 첫 화면이 그만큼 늦어진다. 배포한 사이트에서는 Cloudflare Worker가 첫 화면(index.html)을 줄 때 API의 `GET /site`를 받아 HTML에 넣는다.

```html
<script type="application/json" id="site-content">
	{"profile":null,"projects":{…}}
</script>
```

- `type="application/json"`이라 실행되지 않는 데이터다. CSP가 인라인 스크립트를 막아도 상관없다.
- 글 안의 `</script>`로 빠져나가지 못하게 `<`를 `<`로 바꾼다.
- 화면은 이 태그가 있으면 바로 쓰고, 없으면(로컬·E2E) API에 2.5초까지 묻는다. 그래도 안 되면 코드의 기본값으로 연다.
- Worker는 받은 값을 1분 동안 다시 쓰고, API에 닿지 않으면 1.5초 만에 포기하고 콘텐츠 없이 준다.

첫 화면은 원래 Worker를 거치지 않는 정적 파일이었다. `run_worker_first: ["/", "/index.html"]`로 첫 화면만 Worker를 먼저 거치게 했다. 그림·코드 같은 나머지 파일은 그대로 Worker를 거치지 않는다.

## 새 데모 주소와 CSP

사이트의 CSP는 빌드할 때 코드의 데모 주소로 `frame-src`를 만들었다. 그런데 관리자가 새 프로젝트 앱을 더하면 그 데모 주소는 빌드에 없으니 iframe이 막힌다.

같은 Worker가 첫 화면을 줄 때, 받은 콘텐츠의 데모 주소를 더해 CSP를 다시 만든다. CSP는 문서(HTML) 응답에 붙은 것이 그 페이지에 적용되므로, 첫 화면만 맞추면 된다. `wrangler dev`에 가짜 API를 붙여 보니, 콘텐츠가 HTML에 들어가고 가짜 데모 주소가 `frame-src`에 더해졌다.

```
frame-src 'self' https://challenges.cloudflare.com https://newpick-tan.vercel.app … https://stub-demo.example.com …
```

## 어디에나 맞는 페이지 모양

페이지 모양 7가지는 저마다 한 프로젝트에 맞춰 짠 것이다(신문 1면, 칸반 보드, 게임 크레딧, 터미널 일지…). 새 프로젝트에 그중 하나를 고르면 그 프로젝트 이야기에 맞춘 빈자리가 어색하게 남았다. 그래서 어떤 내용에나 맞는 **기본 (카드)** 모양(`showcase`)을 더하고 새 프로젝트의 기본값으로 삼았다. 큰 제목과 링크, 숫자, 대표 화면, 주요 기능·만든 방식·쓰는 법 카드, 화면 모음, 진행 과정, 기술 사양 순서이고, 없는 묶음은 통째로 빠져서 적은 내용만 있어도 빈자리가 없다. 로고가 있으면 이름 대신 로고를, 프로젝트 아이콘이 있으면 이름 옆에 작게 둔다.

## 모양을 통째로 다시 짜다

기본 모양을 새로 짜고 나니 나머지 일곱이 옆에서 밋밋해 보였다. 한 번 틀만 새로 써 봤지만 결국 "제목 → 섹션 → 섹션" 세로 스크롤에 색만 다른 꼴이었다. 피드백도 그랬다: 색·타이포가 밋밋하고, 다 비슷한 세로 스크롤이고, 움직임이 없다. 그래서 **읽는 방식 자체가 다른 모양 열두 가지**를 짰다. 마음에 안 드는 건 빼면 된다는 전제로 넷 갈래를 섞었다.

규칙은 같다. 어떤 프로젝트든 어떤 모양이나 고를 수 있으니 없는 필드는 그 부분이 통째로 빠지고, 한 프로젝트 전용 장식(게임 스프라이트, 몽이, 이 사이트의 화면 크기 시뮬레이터)은 그 프로젝트에서만 그린다. 움직임은 `prefers-reduced-motion`에서 즉시 상태로 떨어지고, E2E는 그 상태로 돈다.

데모 조각(포트폴리오의 번역·요약·파형·테마 데모, 터미널 셸, 화면 크기 시뮬레이터, 요청 경로 그림)은 어느 모양에서든 꽂을 수 있게 색 변수(`--cr-*`, `--pd-*`)만 읽도록 떼어 두었다.

### 기존 프로젝트는 그대로, 템플릿은 새 프로젝트용

모양은 템플릿이다. 코드에 있는 일곱 프로젝트는 처음부터 그 프로젝트를 위해 짠 페이지(이 사이트의 제품 페이지, NewPick의 신문 1면, WTD의 칸반, QRU의 명함, SproutFarm의 타이틀 화면과 크레딧, DevCourse의 터미널, 포트폴리오의 장과 몽이)가 있고, 그건 바꾸지 않는다. 그래서 `custom` 모양을 두었다: `apps/safari/project/custom/`에 프로젝트 id로 컴포넌트를 등록하면 그 프로젝트가 `custom`을 골랐을 때 그 코드로 그린다. 기존 일곱 프로젝트는 모두 여기에 등록돼 `custom`이 기본값이고, 등록이 없는 프로젝트가 `custom`을 고르면 기본 모양으로 그리며 편집 화면이 그 사실을 알려 준다. 열두 템플릿은 새 프로젝트를 더할 때 고르는 것이다.

## 편집 화면

**시스템 설정 › 프로젝트**는 관리자에게만 보인다.

- 목록: 평소에는 이름과 `id · 앱 · 고침 · 숨김` 같은 표시만 보인다. GitHub 항목과 같은 모양으로, **편집**을 누르면 줄 오른쪽에 숨기기(눈)·고치기(ⓘ)와 ≡ 손잡이(끌거나 ↑·↓ 키로 순서)가 나오고, 맨 아래 칸에 id를 적어 새 프로젝트를 더한다(GitHub 항목의 owner/이름으로 더하기처럼). 새로 더한 프로젝트는 숨기기 대신 빨간 ⊖로 뺀다. **취소**·**완료**로 끝내고, 완료가 한 번에 저장한다.
- 편집 › **소개**: 이름, 소개, 큰 제목, 기간, 페이지 모양, 저장소·데모 주소, 주 언어, 기술.
- 편집 › **내용**: 묶음마다 항목이 번호 배지가 붙은 카드이고(제목·설명·작은 그림 고르기, 오른쪽 위 ↑·↓·×), 점선 "더하기"로 늘린다.
- 편집 › **앱**: "이 사이트 안에서 창으로 열기"를 켜면 프로젝트 앱이 된다. 앱 이름, 아이콘, Dock에 고정, 게임('여기서 플레이'), 뜨기 전 창 바탕, 창 크기. 앱은 데모 주소가 있어야 한다. 처음에는 게임 표시('여기서 플레이')와 뜨기 전 창 바탕(밝게·어둡게) 칸도 있었는데, 쓰는 프로젝트가 SproutFarm 하나뿐이고 차이가 작아 폼에서 뺐다. 값은 데이터에 그대로 있고 JSON 탭에서 고친다.
- 편집 › **고급 (JSON)**: 프로젝트 전체를 JSON으로 고친다. 폼에 없는 주요 기능, 장, 화면 모음도 여기서 고친다. 기본으로 돌아가면 JSON에서 고친 값이 폼에 보인다.
- 프로젝트 편집의 **완료**는 서버와 같은 규칙으로 검사하고 목록으로 돌아간다. 실제 저장은 목록의 **완료**가 한 번에 한다.
- 꼭 적어야 하는 칸(이름, 저장소, 새 프로젝트의 id, 앱을 켜면 앱 이름·아이콘)에는 빨간 **필수** 표시를 붙이고, 비었으면 저장 전에 알려 준다.
- 기간은 달력에서 시작일·끝날을 고른다. 끝 대신 '진행 중'처럼 글을 쓸 수도 있다. 저장하는 모양은 코드에 적힌 것과 같은 `2024.12.26 – 2025.02.05`이고, 날짜 모양이 아닌 예전 값은 글 칸으로 그대로 고친다.
- 주 언어는 기술 칸과 같은 목록에서 하나를 고른다. 칸을 누르면 후보 전체가 뜨고, 입력하면 걸러진다. 후보는 프로젝트들이 쓴 언어, 자주 쓰는 언어 50개, 그다음 GitHub linguist(`languages.yml`)에 등록된 프로그래밍·마크업 언어 634개 순서이다. 처음에는 브라우저 기본 자동완성(`datalist`)에 50개만 있어서, 칸을 눌러도 목록이 뜨지 않고 브라우저마다 생김새가 달랐다.
- 기술은 칩으로 고른다. 이름 줄 아래 고른 칩이 줄지어 있고, 그 아래 찾는 칸이 따로 있다. 칸에 초점을 두면 후보(프로젝트들의 기술과 사이트 주인의 기술, 많이 쓴 것부터, 그다음 자주 쓰는 기술 1,700여 개 — 프레임워크·라이브러리·클라우드·DB·도구·AI·게임·결제·국내 서비스·개념까지)가 칸 아래에 뜬다. 칸만 눌러도 후보 전체가 목록에 있어 굴려 보며 고를 수 있고, 치면 맞는 것 전부로 걸러진다(몇 개가 맞는지 알려 준다). 처음엔 40개까지만 보여 줘서, 굴려 봐도 끝이 금방 나와 후보가 적은 줄 알았다는 말을 들었다가 칸 아래에 떠서 설정 창의 스크롤이나 칸 경계에 잘리지 않고, 몇 글자 치면 걸러진다. ↑·↓와 Enter로 고르거나 쉼표·Enter로 목록에 없는 것도 더한다. 처음에는 라벨 옆 한 줄에 칩과 입력이 섞여 있고 후보가 칸 안에 끼어 있어 좁은 창에서 보이지 않았다. 그래도 목록에 적어 둔 것만으로는 모자라서, 두 글자부터 **npm 레지스트리 검색**(`registry.npmjs.org/-/v1/search`)을 함께 돌려 코드의 후보 뒤에 붙인다(오른쪽에 `npm` 표시). 치기를 멈추면 0.25초 뒤 한 번 묻고 앞 요청은 끊으며, 실패하면 조용히 코드의 후보만 보여 준다. 이를 위해 CSP connect-src에 레지스트리를 열었고, E2E는 레지스트리를 가짜 응답으로 막는다.
- 그림(프로젝트 아이콘, 앱 아이콘)은 큰 미리 보기 타일과 설명, 고르기·올리기·지우기·주소 도구 줄이 있는 카드로 두었고, 미리 보기 옆에서 사이트 안 그림을 폴더별로 골라도 되고, 파일을 올려도 된다. 올리기는 메모 글의 첨부와 같은 `POST /files`를 쓰고, 올린 그림의 주소(`/files/<id>`)가 저장된다. 이 주소는 운영에서는 https지만 로컬에서는 http라, 검사 규칙에 "자기 API 출처는 받는다"를 더했다(서버는 `API_URL`, 화면은 `VITE_API_URL`). Dock·홈 화면이 앱 아이콘을 이미지 폴더 기준으로만 읽던 것도 절대 주소를 받게 했다.
- 대표 화면(`image`)은 폼에서 따로 고르지 않는다. 처음엔 '화면 캡처' 칸이 있었지만, 화면 모음 폴더를 고르면 첫 그림이 대표 화면이 되니 칸이 하나 남는 셈이라 뺐다. 다른 장을 대표로 쓰려면 폴더의 파일 이름 순서를 바꾸거나 JSON의 `image`를 적는다. 둘 다 없으면 대표 화면을 그리지 않는다(영상은 건너뛴다).
- 처음에는 프로젝트 아이콘 옆에 글자 로고(가로로 긴 워드마크) 칸도 두었는데, 로고를 쓰는 프로젝트가 NewPick 하나뿐이고 새 프로젝트를 더할 때 아이콘과 헷갈리기만 해서 폼에서 뺐다. 데이터의 `logo`는 그대로라 NewPick의 제호는 그대로이고, 필요하면 JSON 탭에서 적는다.

## 화면 모음은 폴더 하나로

화면 모음(차례로 넘겨 보는 화면)은 그림마다 주소와 설명을 적어야 했다. 그림이 열 장이면 열 줄이다. 그래서 폴더 하나를 고르면 그 안의 그림을 모두 쓰게 했다.

- 빌드할 때 `public/imgs` 아래 폴더마다 그림·영상 목록을 이름 순으로 모아 둔다(Vite 플러그인이 만드는 `virtual:public-images` 모듈).
- 프로젝트의 `galleryFolder`에 폴더 경로(예: `/imgs/projects/qru/screens`)를 두면, 앱을 그리기 전에 그 폴더의 그림으로 화면 모음을 채운다. 설명은 파일 이름에서 앞 번호와 확장자를 떼고 만든다(`02-login_page.png` → login page).
- 편집 화면에서는 폴더를 고르는 칸과 미리 보기(12장까지)가 보인다. 고를 수 있는 폴더는 프로젝트 그림을 두는 `/imgs/projects` 아래뿐이다(배경화면·앱 아이콘 폴더는 빼고).
- 폴더 경로는 `/imgs` 아래만 받는다(`..` 없이).

그림은 사이트와 함께 배포되는 파일이라, 새 그림을 더하려면 저장소의 그 폴더에 넣고 배포해야 한다.

## 저장하면 바로

처음에는 저장한 뒤 "지금 새로고침"을 눌러야 Safari에 바뀐 모양이 보였다. 프로젝트 목록(`PROJECTS`)은 시작할 때 한 번 채우고 여러 모듈이 그 배열을 읽기 때문이다. 이제 저장이 끝나면 같은 배열을 다시 채우고, 바뀐 횟수를 담은 작은 저장소(`useSyncExternalStore`)를 올려 Safari와 Finder가 다시 그린다. Safari 탭도 저장한 순서로 맞추고, 숨긴 프로젝트의 탭은 닫고, 새 프로젝트는 끝에 연다. 다만 Dock·Launchpad의 앱 목록과 사진 앨범은 시작할 때 한 번 정해지므로, 저장으로 그것들이 바뀐 경우에만 새로고침을 권한다.

## 모양 전용 칸은 그 모양에서만

장면 그림, 대화창 배경, 조작법, 커밋 규칙은 몇몇 모양만 쓰는 칸이었다. 그림·내용 탭에 늘 있으니 다른 모양을 고른 프로젝트에서는 입력해도 화면에 나오지 않는 칸이었다. 그래서 공통 칸에서 빼고, 소개 탭의 페이지 모양 카드 바로 아래에 그 모양을 골랐을 때만 나오게 했다. 모양을 바꿔도 값은 지우지 않아서, 되돌아오면 그대로 있다.

## 칸을 다 채우면 꽉 차게

템플릿은 어떤 프로젝트에나 쓰이니, 편집 화면의 칸을 다 채웠을 때 빈 곳이 없어야 한다. 템플릿 열세 개가 실제로 읽는 필드를 표로 정리해 보니 장, 조작법, 폴더 구조, 출처, 항목의 자세히·여러 장·영상 같은 것이 JSON으로만 들어갔다. 그 칸들을 편집 화면에 더하고, 모양마다 가상의 예시 프로젝트(북클럽, 픽셀팜, 스테이션 같은 것)를 만들어 '예시로 채우기'로 새 프로젝트를 시작하게 했다. 그 예시로 템플릿을 하나씩 열어 빈 칸(항목 수와 맞지 않는 격자, 그림 없는 항목의 빈 그림 자리, 한쪽만 찬 열)을 메우고, 입력했는데 화면 어디에도 안 나오던 필드(주 언어, 자세히, 쓰는 법, 진행 과정 등)를 그 모양의 화풍으로 넣었다.

예시를 채우며 확인 창을 띄우다 보니 공통 경고창의 여백이 0이었다. 빌드한 CSS에서 `@layer reset, components;` 선언이 빠지고 components 층이 reset 층보다 먼저 나와, 초기화 규칙(`* { padding: 0 }`)이 공통 컴포넌트를 이기고 있었다. 층 순서는 처음 나온 곳에서 정해지므로 `index.html`의 인라인 `<style>` 맨 앞에서 선언해 모든 CSS보다 먼저 정한다.

## 브랜드 랜딩 페이지처럼

템플릿이 여전히 정보 나열처럼 보인다는 말을 듣고, 브랜드 제품 랜딩 페이지를 기준으로 다시 손봤다. 부족한 점은 넷이었다. 첫 화면이 약하고, 구역이 제목과 목록의 반복이고, 시각 디테일이 엉성하고, 그림이 없으면 빈약했다.

먼저 템플릿들이 함께 쓸 랜딩 키트(`project/landing/`)를 만들었다. 기기 틀(브라우저·노트북·휴대폰), 히어로 뒤 빛 번짐, 큰 숫자 띠, 기술 로고 줄, 빈 칸 없는 벤토, 마무리 CTA가 들어 있다. 핵심은 **그림이 없을 때 쓰는 가짜 제품 화면**이다. 프로젝트의 이름·아이콘 색·주요 기능·숫자로 대시보드·목록·채팅·편집기·모바일·게임 화면을 그린다. 화면 속 글은 모두 프로젝트 데이터에서 오고, 시험이 그것을 확인한다.

그다음 템플릿을 세 갈래 톤으로 나눠 키트로 손봤다. Apple 쪽(시네마·폰·아틀리에·설정 도우미), Linear·Vercel 쪽(가로·저장소·발표·아케이드), Stripe·Notion 쪽(기본·메일함·할 일·브루탈)이다. 모두 큰 메시지와 제품 화면이 있는 히어로, 기능을 하나씩 보여 주는 구역, 마무리 CTA를 갖췄다. RPG 대화창은 게임 화면 컨셉을 지키려고 첫 화면만 게임 타이틀처럼 다듬었다.

## 번들거림을 걷고, 다시 가볍게

랜딩 키트로 꾸민 첫 결과는 "번들번들하다"는 말을 들었다. 빛 번짐, 그라데이션 글자, 기기 반사, 기울기, 유리 효과, 색 그림자가 한꺼번에 들어가 있었다. 진짜 브랜드 페이지는 오히려 절제되어 있어서, 효과를 모두 걷어 내고 단색 바탕·큰 타이포·강조색 하나·얕은 그림자 한 벌만 남겼다. 아케이드의 네온은 간판 한 곳에만 둔다.

그랬더니 이번에는 "무겁고 칙칙하다"는 말이 돌아왔다. 원인은 셋이었다. 여러 템플릿이 사이트 테마와 상관없이 어두운 바탕을 강제했고, 강조색 채도를 너무 낮춰 회색빛이 돌았고, 제목이 700~800으로 너무 굵었다. 그래서 라이트 테마에서는 흰 바탕을 쓰고 사이트 테마를 따르게 했다(시네마·발표는 어두운 장면 한두 곳만 남긴다). 강조색은 아이콘 색의 채도를 되살리되 흰 바탕과의 대비가 3 이상이 되도록 밝기를 맞추고, 큰 제목은 600, 본문은 #424245와 17px로, 구역 여백은 넉넉하게 했다. 회색 바탕 위 회색 카드 대신 흰 페이지와 아주 옅은 면의 대비를 쓴다.

## 넣은 그림이 안 보이던 주요 기능

이미 있는 주요 기능에 그림을 넣어도 페이지가 그대로인 경우가 있었다. 편집 화면은 값을 잘 저장했는데, 그리는 쪽이 다른 것을 먼저 골랐다. 그림보다 갈래 도식(variants)을 먼저 그렸고, 다크 테마 그림(imageDark)은 옛 그림의 짝이라 그림을 바꿔도 밀대 반쪽에 옛 화면이 남았다. 칸반(WTD)과 터미널(DevCourse) 페이지는 아예 항목의 그림을 그리지 않았다. 그래서 그림을 갈래 도식보다 먼저 그리고, 그림을 바꾸면 다크 그림을 함께 지우고, 두 페이지도 그림을 그리게 했다. 영상은 편집 화면에 보이는 칸이라 그대로 그림보다 먼저 보이되, 영상이 있는 항목의 그림 칸에 그 사실을 알린다.

## 항목은 시트에서, 화면 모음은 그림마다

주요 기능·만든 방식·쓰는 법·장·출처 같은 목록은 줄을 고르면 그 항목의 칸이 목록 아래에 열렸다. 목록이 길면 칸이 화면 밖으로 밀려나 스크롤을 오르내려야 했고, 편집 칸이 목록 아래에 뜨는 방식이 불편하다는 말을 들었다. 그래서 macOS 시스템 설정처럼 **시트**로 바꿨다.

- 줄을 한 번 누르면 고르기만 한다(빼기·끌기·⌥↑↓는 그대로). 줄 끝의 ⓘ, 두 번 누르기, 줄에서 Enter로 그 항목의 시트가 열리고, ＋로 더한 빈 항목도 바로 시트로 열려 첫 칸에 초점이 간다.
- 시트는 편집 화면을 살짝 어둡게 덮고 도구 막대 아래에서 내려오는 둥근 판이다. 제목은 '주요 기능 2'처럼 항목 이름이고, 칸은 편집 화면과 같은 줄 모양이다. 고치는 대로 바로 반영되므로 아래에는 **완료** 하나만 둔다. Esc로도 닫고, 닫으면 연 줄로 초점이 돌아온다. 열린 동안 초점은 시트 안을 돌고, 뒤의 편집 화면은 `inert`로 막는다.
- 시트는 `document.body`가 아니라 설정 창 안에 그린다. 창을 끌면 함께 움직이고, 폼 밖이라 칸에서 Enter를 쳐도 프로젝트 편집이 끝나지 않는다.
- 장 안의 항목처럼 시트 안에 또 목록이 있으면, 시트를 겹치지 않고 같은 시트 안에 다음 페이지로 민다. 왼쪽 위의 '‹ 장 1'로 돌아온다. 앞 페이지는 숨겨 두기만 해서 고친 값과 고른 줄이 그대로 남는다.
- 화면 여러 장(그림과 설명)은 칸이 둘뿐이라 시트를 열지 않고 줄에서 바로 고친다. 썸네일을 누르면 크게 보고, 설명 칸과 주소 칸 옆에 고르기·올리기가 있다. 그림 칸과 같은 고르기 팝업과 올리기 훅을 함께 쓴다.

써 보니 줄 끝의 작은 ⓘ를 찾아 누르는 일이 번거로웠고, 고르기만 하는 한 번 누르기와 여는 두 번 누르기를 구분해야 하는 것도 어색했다. 그래서 macOS 시스템 설정의 이동 목록처럼 줄 전체를 단추로 바꿔, 줄을 한 번 누르면 시트가 열리고 줄 끝에는 › 표시만 남겼다. 순서는 왼쪽 ≡ 손잡이를 끌거나 손잡이에서 ↑·↓ 키로 바꾸고, 아래의 − 단추 대신 시트 왼쪽 아래의 빨간 **항목 삭제**로 지운다. 지우면 시트가 닫히고 초점은 다음 줄로, 남은 줄이 없으면 ＋로 간다. 장 안 항목처럼 밀린 페이지에서 누른 항목 삭제는 그 페이지의 항목만 지우고 장의 페이지로 돌아온다.

그림 탭의 화면 모음에서는 **폴더 고르기를 뺐다**. 폴더는 저장소의 `public/imgs/projects`에 그림을 넣고 배포해야만 생기므로, 사이트에서 고치는 관리자에게는 쓸모가 없었다. 대신 화면 여러 장과 같은 목록으로 그림을 한 장씩 고르거나 올린다. 첫 그림이 대표 화면이 되는 것은 그대로이고, 설명을 비우면 저장할 때 파일 이름에서 짓는다. 데이터의 `galleryFolder`와 검사는 그대로 두어 JSON에서는 여전히 폴더를 적을 수 있다. 폴더만 있는 프로젝트를 열면 그 사실을 한 줄로 알리고, 목록에 그림을 더하면 폴더 대신 목록을 쓴다.

화면 모음만 남기니 무엇을 하는 칸인지 드러나지 않았다. 대표 화면이 그 목록의 첫 그림이라는 규칙을 알아야 했기 때문이다. 그래서 그림 탭을 둘로 나눴다. 위에는 페이지 첫 화면과 Finder 미리 보기에 쓰는 '대표 화면' 한 칸을 두고, 아래에는 '화면 더 보기' 목록을 둔다. 대표 화면을 비우면 예전처럼 목록의 첫 그림을 쓴다.

## 내용은 하나로, 템플릿은 넷으로

템플릿이 열세 개로 늘어나면서 두 가지 문제가 쌓였다. 하나는 템플릿마다 읽는 칸이 달랐다는 점이다. 어떤 모양은 폴더 구조를 그리고 어떤 모양은 그리지 않았고, 커밋 규칙이나 조작법처럼 한 모양만 쓰는 칸도 있었다. 관리자는 칸을 채워도 모양을 바꾸면 그 내용이 사라지는 일을 겪었다. 다른 하나는 디자인이었다. 열세 개를 고루 다듬을 수 없어서 어느 것도 완성도가 높지 않았고, 템플릿 디자인 자체가 별로라는 말을 들었다.

그래서 먼저 **공통 내용 모델**을 만들었다. `landingOf(project)`는 어떤 프로젝트든 첫 화면, 차례가 정해진 구역들, 마무리로 바꾸는 순수 함수다. 구역은 한눈에 보는 숫자, 주요 기능, 화면 모음, 쓰는 법, 만든 방식, 더 들려줄 이야기, 조작법, 진행 과정, 기술 사양, 맡은 일, 출처 열한 가지이고, 값이 없는 구역은 아예 생기지 않는다. 항목의 그림은 영상, 그림, 화면 여러 장 차례로 한 목록에 모으고, 대표 화면이 비면 화면 모음의 첫 그림을 쓴다. 단위 시험은 편집 화면이 고치는 칸이 하나도 버려지지 않는지까지 확인한다.

템플릿은 이 내용만 읽는다. 구역마다 그리는 함수를 모은 묶음은 구역 종류를 하나도 빠뜨릴 수 없게 타입으로 막았다. 그래서 어떤 템플릿을 골라도 채운 칸이 모두 보이고, 조작법과 폴더 구조와 출처도 모든 템플릿이 그린다. 조작법 칸은 이제 모양 전용 칸이 아니라 내용 탭에 있다.

그다음 템플릿을 **넷으로 줄였다**. 각각 콘셉트가 분명한 레퍼런스를 하나씩 정했다. 제품(Apple 제품 페이지)은 큰 화면과 짧고 큰 문장, 카드(Stripe)는 밝은 카드와 아이콘과 단계 흐름, 문서(Notion)는 따뜻한 흰 문서와 토글과 알림 상자, 벤토(Framer·Raycast 템플릿)는 크기가 다른 타일과 가는 선과 고정폭 글자다. 템플릿마다 폴더 하나로 나눠 서로를 가져오지 않게 했고, 지켜야 할 계약(모든 구역, 빈 구역 없음, 구역 이름, 라이트·다크, 좁은 창, 움직임 줄이기, 효과 절제)은 `templates/README.md`에 적었다. RPG 대화창은 공들인 게임 콘셉트라 그대로 두고 출처를 읽는 선택지만 더했고, 직접 짠 일곱 페이지도 그대로다.

새 프로젝트의 기본 모양은 카드로 정했다. 제품 모양은 큰 화면이 있어야 살아나는데, 막 더한 프로젝트에는 그림이 없는 경우가 많다. 카드 모양은 그림이 없어도 아이콘 카드로 꽉 차 보인다.

예전 모양 이름으로 서버에 저장해 둔 프로젝트도 그대로 보여야 했다. 그래서 검사 규칙(`parseProjects`)에 옛 이름을 지금 이름으로 바꾸는 표를 두었다. 기본·설정 도우미는 카드로, 시네마·폰은 제품으로, 아틀리에·메일함·할 일 앱은 문서로, 가로·저장소·발표·아케이드·브루탈은 벤토로 옮긴다. 서버와 화면이 같은 규칙을 쓰므로 저장할 때도 읽을 때도 옛 이름이 지금 이름으로 바뀐다. 예시 프로젝트도 열세 개에서 하나로 줄여 네 템플릿이 함께 쓰고, RPG 대화창만 배경과 장면 그림이 있는 자기 예시를 둔다.

네 템플릿은 담당을 나눠 같은 기준으로 다듬었다. 예시를 다 채운 프로젝트, 그림을 모두 뺀 프로젝트, 이름과 소개와 기능 두 개만 있는 프로젝트를 라이트·다크와 좁은 창에서 모두 찍어 보고, 어느 경우에도 빈 자리가 보이지 않게 했다. 제품은 그림이 없으면 큰 아이콘 타일로, 카드는 프로젝트 내용으로 그린 앱 화면 모형으로, 문서는 태그 색을 깐 표지로, 벤토는 아이콘 타일과 명령 팔레트로 그 자리를 채운다. 예시 그림도 배경화면 대신 실제 앱 화면 캡처로 바꿨다. 배경화면을 넣으면 제품 페이지가 아니라 사진첩처럼 보였기 때문이다. 마무리 문장은 첫 화면 제목을 되풀이하지 않도록, 써 볼 곳이 있는지에 따라 권하는 문장을 따로 둔다.

네 템플릿을 보여 주자 정돈되어 보인다는 말과 함께 템플릿을 더 늘려 달라는 말, 카드와 RPG는 별로라는 말이 돌아왔다. 그래서 키노트(어두운 무대의 발표 장면), 매거진(명조와 큰 사진의 케이스 스터디), 개발자 도구(복사되는 clone 명령, 커밋 목록, 기여 그래프), 놀이(색 면과 둥근 도형, 스티커)를 더했다. 같은 내용 모델 위에 있으니 새 템플릿은 폴더 하나와 E2E 한 파일이면 된다. 예전 모양 이름도 더 가까운 새 템플릿으로 다시 맞췄다(cinema·deck은 키노트, atelier는 매거진, repo는 개발자 도구, arcade는 놀이). 카드는 Stripe 실제 페이지와 견주어 약한 곳을 짚고(탁한 겨자색, 싸 보이는 베이지 띠, 창 하나뿐인 첫 화면) 비스듬한 띠와 줄무늬, 창 위에 겹친 숫자·기능 카드로 다시 그렸다. RPG 대화창은 아늑한 픽셀 농장 풍에서 고전 RPG로 바꿨다. 라이트는 포켓몬처럼 흰 상자와 두 열 선택지, 다크는 언더테일처럼 검은 상자와 흰 테두리, 빨간 하트 커서다.

매거진은 명조 웹 글꼴을 쓰고 싶었지만 사이트의 CSP가 바깥 글꼴을 막는다. 그래서 기기에 있는 명조(맥에서는 애플명조)를 쓴다.

저장소 모양은 개발자 도구로 옮겼다가 다시 살렸다. GitHub 저장소를 흉내 낸 그 모양은 괜찮았다는 말을 들었기 때문이다. 다만 예전 코드는 프로젝트 칸을 직접 읽고 탭마다 다른 내용을 보여 줬으므로, 공통 내용 모델 위에서 다시 짰다. Code 탭이 저장소 첫 화면이고, 모든 구역은 README 안에 차례대로 들어간다. 숫자는 README 첫머리의 지표 칸, 진행 과정은 v0.1.0부터 v1.0.0까지의 릴리스 목록, 기술 사양은 Built with 주제와 표와 폴더 구조 코드 블록, 맡은 일은 할 일 목록이 된다. 위의 파일 상자는 폴더 구조로 만든 트리라서 폴더를 눌러 펼칠 수 있고, DevCourse는 예전처럼 실제 저장소를 탐색한다. Commits 탭은 진행 과정을 커밋 그래프로 그리고 타입으로 거르며, 커밋 규칙이 있으면 Conventions 탭이 생긴다. 터미널 서랍의 셸도 폴더 구조를 ls와 cd로 돌아본다. 저장소 탭은 Safari 창의 탭과 섞이지 않게 탭 역할 대신 내비게이션과 현재 표시 단추로 두었다. 예전 이름 표에서 repo를 빼서, 저장소 모양으로 저장해 둔 프로젝트는 다시 이 모양으로 보인다.

그런데 저장소 모양을 다시 보니 두 가지가 아쉬웠다. 하나는 README 하나에 모든 구역이 길게 이어져, 실제 저장소처럼 보이기보다 긴 랜딩 페이지를 상자에 넣은 것처럼 보인다는 점이었다. 그래서 GitHub가 README 상자 위에 README, Contributing, License 탭을 두는 것처럼 구역을 문서로 나눴다. README.md에는 큰 제목과 소개, 대표 화면, 숫자, 목차가 남고, 나머지 구역은 docs/FEATURES.md, docs/USAGE.md, docs/CHANGELOG.md처럼 하나씩 제 문서가 된다. 문서 탭을 누르거나 파일 트리의 docs/ 폴더에서 파일을 누르면 그 문서가 열리고, 경로 줄에 blob/main/docs/FEATURES.md가 보인다. 터미널에서도 ls docs와 cat docs/USAGE.md가 된다. 다른 하나는 맨 위의 랜딩식 첫 화면(가운데 배지, 큰 제목, clone 명령, 창 속 화면)이 개발자 도구 템플릿과 너무 닮았다는 점이었다. 그 첫 화면을 걷어 내고 페이지가 처음부터 저장소 화면으로 열리게 했다. 큰 제목은 README의 h1이 되고, 링크 단추는 About 칸으로, clone 주소는 가지 줄의 초록 Code 단추 안으로 들어갔다. 공통 시험은 모든 구역이 한꺼번에 보이기를 기대하므로, 저장소 모양의 시험만 문서 탭을 차례로 열며 구역의 차례와 내용을 확인하도록 바꿨다.

옆 칸의 Languages도 손봤다. 지금까지는 프로젝트에 적어 둔 주 언어 하나를 100%로 그렸는데, GitHub 링크가 있으니 실제 언어 비율을 보여 주면 좋겠다는 말을 들었다. 브라우저가 GitHub API를 직접 부르면 방문자마다 요청 제한을 나눠 쓰게 되므로, 사이트의 API에 GET /github/languages/{owner}/{이름}을 두고 서버가 대신 묻는다. 다만 누구나 부를 수 있는 경로가 아무 저장소나 대신 묻는 통로가 되면 안 된다. 그래서 코드의 프로젝트가 가리키는 저장소와 관리자가 저장한 프로젝트 주소의 저장소만 받고, 그 밖은 GitHub에 묻지 않고 404로 답한다. 코드의 프로젝트 목록은 화면 코드에 있어 서버가 읽을 수 없으므로, 공용 패키지에 저장소 이름만 따로 두고 화면의 시험이 두 목록이 같은지 확인한다. 받은 비율은 저장소마다 6시간(없는 저장소라는 답은 30분) 들고 있고, GitHub에 닿지 못하면 마지막 값을 준다. 비율은 소수 첫째 자리까지 반올림하되 합이 꼭 100이 되게 맞추고, 0.5%보다 작거나 일곱째부터인 언어는 Other로 묶는다. 화면은 GitHub처럼 언어마다 한 토막인 막대와 색 점 목록을 그리고, 받는 동안이나 받지 못하면 예전처럼 주 언어 하나로 그린다.

## 대화창의 풍경을 걷어 내다

RPG 대화창은 콘셉트는 좋은데 못생겼다는 말을 들었다. 다시 보니 싸 보이는 곳은 대화 상자가 아니라 그 위의 장면이었다. CSS로 그린 나무와 구름, 땅 타일, 열네 가지 배경 테마, 대표 화면을 픽셀로 뭉갠 그림이 서로 다른 화풍으로 겹쳐 있었다. 그 풍경 때문에 편집 화면에도 RPG 대화창만 따로 고르는 칸(대화창 배경, 배경 그림, 장면 그림)이 생겨, 다른 모양과 달리 이 모양만 손이 더 갔다. 그래서 풍경을 통째로 걷어 내고 언더테일의 대화 화면처럼 단순하게 다시 그렸다. 라이트·다크 모두 새까만 무대에 흰 테두리(6px, 각진 모서리) 대화 상자 하나를 두고, 갈무리11 글꼴은 격자에 딱 맞는 11px과 22px로만 쓴다. 대사 앞에는 별표, 제목은 노랑, 선택지는 넓은 창에서 세 열과 빨간 하트 커서다. 그림은 픽셀로 바꾸지 않고 원래 모습 그대로 흰 액자에 띄우며, 그림이 없으면 프로젝트 아이콘 하나만 가운데 둔다. 상자 아래 한 줄에는 이름과 HP 막대 같은 노란 읽음 막대가 있다.

데이터에서는 backdrop 필드와 열네 테마 목록을 지웠다. 예전에 저장해 둔 값에 backdrop이 있어도 검사 규칙이 모르는 필드를 버리므로 오류 없이 읽힌다. 장면 그림(art)은 SproutFarm의 직접 짠 페이지가 쓰므로 데이터에는 남기고 편집 화면에서만 뺐다. 대화창만의 칸이 없어졌으니 예시도 따로 두지 않고 다른 템플릿과 같은 북클럽 예시를 쓴다.

## 포트폴리오가 늘 묻는 것들을 칸으로

프로젝트를 소개하는 글에는 거의 정해진 항목이 있다. 기능, 기술 스택, 트러블슈팅, 구현 방법, 팀원, 배포 결과물, 내 역할, 진행 과정이다. 지금까지의 칸은 기능, 기술, 구현, 역할, 진행 과정까지는 갖췄지만 트러블슈팅, 팀원, 배포 결과물은 적을 곳이 없어서, 관리자가 장(chapters)에 억지로 넣거나 빼 버렸다. 세 가지를 프로젝트 데이터의 필드로 더했다. 트러블슈팅은 제목, 문제, 원인, 해결, 결과에 그림과 아이콘을 곁들이고, 팀원은 이름, 역할, GitHub 주소, 사진, 나 표시를 적는다. 배포 결과물은 이름, 주소, 플랫폼, 설명, 그림이다. 서버와 화면이 같은 검사(parseProjects)를 쓰므로 주소는 https만 받고 javascript: 같은 주소는 거절하며, 개수와 글자 수에도 이웃 칸과 같은 한도를 둔다.

공통 내용 모델에는 구역 세 개를 더하고 차례를 포트폴리오를 읽는 순서로 다시 정했다. 무엇인지(숫자, 주요 기능, 화면 모음, 쓰는 법)를 먼저 보이고, 어떻게 만들었는지(구현 방법, 트러블슈팅, 더 들려줄 이야기, 조작법, 기술 사양), 누가 만들었는지(팀원, 내 역할), 언제 만들었는지(진행 과정), 어디서 볼 수 있는지(배포 결과물)를 지나 출처로 끝난다. 구역 이름도 만든 방식은 구현 방법으로, 맡은 일은 내 역할로 바꿨다. 이미지가 하나도 없어도 비어 보이지 않게 하는 것이 목표였다. 트러블슈팅은 아이콘과 번호 아래에 문제, 원인, 해결, 결과를 한 줄로 잇는 단계 띠를 그리고 해결부터는 강조색으로 칠한다. 팀원은 사진이 없으면 이름 첫 글자를 담은 동그라미를 그리고, 나는 강조색 테두리와 작은 표시로 구분한다. 배포 결과물은 올린 곳(Vercel, App Store, npm, Docker 등)에 맞는 아이콘과 공개 상태, 호스트 이름을 보여 주는 링크 카드다. 짜임은 랜딩 키트의 공통 조각 하나로 두고, 아홉 템플릿은 변수와 접두사 클래스로 자기 색과 모양을 입힌다. 저장소 모양만은 GitHub답게 그렸다. 트러블슈팅은 docs/TROUBLESHOOTING.md에서 GitHub의 알림 상자(WARNING, NOTE, TIP, IMPORTANT)로, 팀원은 docs/TEAM.md의 사진 달린 표와 옆 칸의 Contributors로, 배포 결과물은 docs/DEPLOYMENT.md와 옆 칸의 Deployments로 보인다. RPG 대화창은 세 주제를 선택지로 더했다. 편집 화면의 내용 탭에는 세 목록을 다른 목록처럼 시트로 고치게 더했고, 북클럽 예시도 트러블슈팅 세 건(그림이 있는 것과 없는 것), 팀원 네 명, 배포 결과물 세 곳으로 채웠다.

RPG 대화창은 그림이 없으면 무대에 아이콘 하나만 서 있어 심심했다. 그래서 주제마다 고전 RPG 화면을 하나씩 데이터로 그려 대화 상자 위에 세웠다. 인사는 큰 픽셀 글자 이름과 PRESS Z가 깜빡이는 타이틀 화면, 주요 기능은 퀘스트 목록, 구현 방법은 스킬 트리, 쓰는 법은 튜토리얼, 트러블슈팅은 버그 몬스터와의 전투다. 몬스터는 16칸 격자에 글자로 찍은 그림 세 가지를 SVG 사각형으로 그리고, 문제에서 나타나 원인에서 약점이 잡히고 해결에서 기술을 맞아 결과에서 쓰러지는 동안 HP가 100에서 0으로 줄어든다. 팀원은 파티 카드(나는 ★ 나), 기술 사양은 장비 칸과 쓴 기술 가방(아는 기술은 Font Awesome 브랜드 아이콘, 모르면 첫 글자 칸), 내 역할은 상태 창, 진행 과정은 월드 맵, 배포 결과물은 실제로 열리는 링크가 달린 보물 상자, 숫자는 점수판이다. 대사가 지금 말하는 항목을 노랗게 짚고, 상태 창의 숫자는 맡은 일, 팀원, 기술, 해결한 문제의 수와 기간의 날수처럼 데이터에서 센 것만 이름 그대로 적었다(지어낸 레벨은 없다). 그림이 있는 장은 그림을 원래 모습 그대로 액자에 두고 게임 화면을 옆에 작게 붙인다. 보통 창에서는 무대가 넓고 낮아서(250~300px) 세로로 쌓던 것을 옆으로 늘어놓고, 목록은 무대 높이를 재서 들어가는 만큼만 지금 항목 둘레로 보인다.

구성은 나아졌는데 여전히 못생겨 보였다. 이유는 크기가 제각각이라서였다. 11px 글자 옆에 22px 글자가 있고, 단추는 웹 크기, 몬스터는 작았다. 고전 게임이 보기 좋은 건 화면 전체를 낮은 해상도 하나로 그린 뒤 정수 배로 키워서, 글자와 테두리와 그림이 한 픽셀 격자를 나눠 쓰기 때문이다. 그래서 무대, 대화 상자, 상태 줄을 480×270 게임 화면 하나로 묶고 안의 크기를 모두 게임 칸으로 다시 잡았다. 글자는 갈무리11의 제 크기인 11px(큰 이름과 숫자만 22px), 테두리는 3칸, 한 줄은 14칸이다. 그런 다음 Safari 페이지에 들어가는 가장 큰 정수 배를 ResizeObserver로 재서 CSS zoom으로 키운다. 1440 창은 두 배, 780 창은 한 배이고, 한 배도 안 들어가는 아주 좁은 창만 키우지 않는 단순한 배치로 바꾼다. 상자 안의 상자도 걷어 냈다. 틀은 대화 상자 하나뿐이고, 무대는 틀 없이 회색 머리줄 한 줄 아래에 주제의 큰 그림 하나를 둔다. 버그 몬스터는 32×32로 다시 그려 세 배로 띄웠고, 팀원은 이름으로 머리, 피부, 옷 색을 정한 16×24 픽셀 사람으로 한 줄에 세웠다. 사진은 언더테일의 말하는 얼굴처럼 대화 상자 왼쪽에만 띄운다. 보물은 큰 상자가 열리며 결과물 아이콘이 튀어나오고, 월드 맵은 점선 길 위 지금 칸에 내가 서 있다. 주황 웹 단추는 지우고, 전투의 네 칸은 언더테일의 아래 줄처럼 고른 칸만 ♥과 노랑으로 칠했다. 색은 검정, 하양, 노랑, 빨강만 쓰고 HP 막대는 빨강 위에 노랑이다. 선택지는 왼쪽에서 오른쪽으로 채우는 세 열이고, 네 줄보다 길면 상자 안에서 줄 단위로 넘어가며 ▲와 ▼로 더 있음을 알린다. 포커스는 테두리 대신 게임 커서(♥과 노랑)로 그린다.

격자는 맞았는데 이번에는 전체 분위기가 너무 칙칙하다는 말을 들었다. 새까만 바탕에 흰 그림과 노랑만 있으니 밤새 켜 둔 터미널 같았다. 그래서 포켓몬 GBA 전투 화면을 기준으로 다시 칠했다. 무대 뒤에는 주제마다 납작한 색 띠 두세 개(하늘, 지평선 띠, 바닥)만 깔고, 나무나 구름 같은 풍경은 그리지 않았다. 인사는 해 질 녘의 주황과 분홍, 주요 기능은 풀밭, 트러블슈팅은 전투 들판, 팀원은 돌바닥이 체크로 깔린 마을 광장, 기술 사양은 선반이 한 줄 걸린 상점, 내 역할은 옅은 파랑 메뉴, 진행 과정은 모래색 길이 난 초록 지도, 배포 결과물은 라벤더와 청록의 동굴, 숫자는 보라 오락실, 출처는 별이 몇 개 뜬 밤하늘이다. 몬스터와 파티원, 보물 상자, 상태 창의 초상은 포켓몬처럼 납작한 타원 발판 위에 세웠다. 발판도 칸 그림이라 타원을 계산해 테두리, 바탕, 위쪽의 밝은 면 세 색으로 찍는다. 밝은 하늘에서도 그림이 읽히게 모든 스프라이트에 한 칸짜리 짙은 외곽선을 자동으로 두르고, 몬스터는 빨간 무당벌레, 초록 슬라임, 보라 유령으로 색을 입혔다. 대화 상자는 크림색 바탕에 두꺼운 청록 테두리, 계단처럼 깎은 모서리, 안쪽의 밝은 줄을 두고, 글은 먹색에 한 칸 밝은 그림자를 붙였다. 전투의 이름과 HP는 왼쪽 위의 작은 이름표 상자로 옮겼고, HP 막대는 남은 만큼 초록, 노랑, 빨강으로 바뀐다. 다크는 같은 장면의 밤이다. 남색과 쪽빛 띠에 별 몇 개를 찍고, 발판은 차분한 청보라, 대화 상자는 남색 바탕에 흰 테두리, 고른 것은 노랑이다. 게임 화면 밖의 페이지도 검정 대신 라이트는 옅은 하늘색, 다크는 짙은 남색으로 바꿨다.

밝아지긴 했지만 배경을 색 띠로만 바꾸니 예쁘지 않다는 말과 함께, 아이콘도 픽셀로 해 달라는 주문을 받았다. 예전에 CSS 도형(둥근 상자 나무, 타원 구름)으로 풍경을 만들었다가 싸 보인다는 말을 들은 적이 있어서, 이번에는 도트 작업자가 하듯 칸 단위로 그렸다. 무대 뒤는 480×272 판 하나를 16×16 타일 30×17칸(풀밭 세 가지, 포켓몬의 긴 풀, 돌바닥, 가로 판자 바닥, 세로 판자 벽, 물, 동굴 바닥, 오락실 카펫)과 손으로 놓은 소품으로 칠한다. 소품은 원 여러 개를 겹친 덩어리에 빛 쪽으로 비낀 원 두 개로 밝은 면과 그늘을 나누는 나무와 덤불, 보로노이 조각으로 금을 낸 동굴 바위 벽, 기와 줄이 있는 집, 둥근 돌 분수, 울타리, 수정, 횃불, 선반 위 물건, 오락 기계, 눈 덮인 산맥 같은 것이다. 빛은 늘 왼쪽 위, 외곽선은 채운 색보다 짙게, 섞이는 곳은 점 무늬로 하고, 뒤쪽 산과 숲은 대비를 낮춰 주인공 그림이 앞에 서게 했다. 장면은 해 질 녘 언덕과 흙길(타이틀, 나무 표지판에 아이콘을 건다), 구름과 나무가 선 풀밭(퀘스트 게시판), 숲을 등진 전투 들판, 집과 분수가 있는 마을 광장, 선반과 계산대가 있는 상점, 침대와 창이 있는 여관 방, 바다와 산맥과 숲이 보이는 월드 맵, 수정과 횃불의 동굴, 네온 간판의 오락실, 달과 반딧불의 밤하늘 열 가지다. 칸마다 색 대신 팔레트 글자를 두어서 다크는 같은 그림을 밤 팔레트로 바꿔 칠하고(별과 불 켠 창만 더한다), 안쪽 장면은 푸른 달빛 대신 등잔불처럼 따뜻하게 어둡힌다. 장면은 해시로만 흩뿌려 늘 같은 모습이고, 한 번 칠한 판은 기억해 두었다가 낮과 밤 캔버스 두 장에 올리면 CSS가 테마에 맞는 한 장만 보인다. 발판은 위 가장자리에 풀이 난 흙 자리로 바꿨다. 아이콘은 Font Awesome을 모두 걷어 내고 12×12 픽셀 아이콘(칼, 방패, 돋보기, 가방, 하트, 별, 두루마리, 책, 톱니, 망치, 버그, 사람들, 지구본, 로켓, 서버, 데이터베이스, 구름, 열쇠, 상자, 동전, 깃발, 지도, 시계 등)과 기술 로고(React, TypeScript, JavaScript, Node, Python, Docker, Git, GitHub, Vercel, Firebase, PostgreSQL, Figma, Vite, Next.js 등)를 그렸다. 모르는 기술은 3×5 픽셀 글자로 첫 글자를 찍은 색 칸이고, 항목의 fa-* 이름은 가장 가까운 픽셀 아이콘으로 옮기며 모르면 별이다. 프로젝트 아이콘과 팀원 사진은 네 배 크기로 줄여 그린 뒤 색을 16개로 줄이고 4×4칸마다 가장 많은 색 하나를 골라(섞인 색을 만들지 않는다) 24×24 픽셀 그림으로 바꾸고, 투명한 둘레나 네모 가장자리에는 짙은 외곽선을 두른다. 액자 안의 화면 그림은 그대로 둔다. 장면이 바빠진 만큼 글은 장면 위에 바로 두지 않고 GBA 창처럼 작은 틀 상자와 이름표에 담았다.

## 시험

- 단위(desktop-core): 다듬기와 모르는 필드 버리기, `javascript:`·`data:`·http 거절, id 규칙, 안쪽 필수·열거·숫자·색, `null` 지우기, 길이·개수, 합치기 순서, 기본값과 다른 필드만, 데모 출처
- 단위(화면): 기간 읽기·쓰기, 언어·기술 후보와 거르기, 화면 모음 폴더와 화면 캡처 대신 첫 그림, 코드의 프로젝트가 모두 검사를 통과, 이 사이트의 앱 이름이 모두 막힌 id에 있음, `PROJECTS` 배열은 그대로 두고 안만 바뀜
- 단위(Worker): 콘텐츠 넣기와 `</script>` 막기, 새 데모 주소가 frame-src에, API가 없거나 실패하면 콘텐츠 없이, 1분 캐시, 옛 코드 파일은 404
- API e2e: 401·400과 이유, 저장·읽기·지우기, 경로 표에 두 경로
- 단위(랜딩 내용): 빈 구역은 빠지고, 구역 차례가 정해져 있고, 첫 화면 그림은 대표 화면이나 화면 모음의 첫 그림이고, 편집 화면이 고치는 칸을 하나도 버리지 않음 / 예전 모양 이름은 지금 모양으로 바뀜
- E2E: 템플릿마다 한 파일(`e2e/looks/`)로 예시의 모든 구역이 차례대로 보이고, 빈 프로젝트도 빈 구역 없이 그려지고, 링크가 열리고, 사이트 테마를 따르는지 본다.
