메모 앱에서 글을 읽다가 한 문장만 모양이 이상한 걸 봤다.

```text
이번엔 실패가 아니라 **취소(cancelled)**가 떴다.
```

다른 곳의 `**굵게**`는 잘 되는데, 이 문장만 별표가 글자 그대로 보였다. 오타도 아니고 별표 개수도 맞았다.

![고치기 전 읽기 화면](./images/cjk-emphasis-before.jpg '괄호로 끝난 굵게 뒤에 조사 "가"가 붙은 곳만 별표가 그대로 보인다')

## 규칙대로라면 굵게가 아니다

CommonMark는 `**`가 강조를 **여는지·닫는지**를 앞뒤 글자로 정한다. 닫는 `**`가 되려면 "오른쪽에 붙은(right-flanking)" 구분자여야 하는데, 조건은 이렇다.

- 바로 앞이 공백이 아니고,
- 바로 앞이 문장부호라면, 바로 뒤는 **공백이나 문장부호**여야 한다

`**취소(cancelled)**가`에서 닫는 `**`의 앞은 `)`(문장부호), 뒤는 `가`(글자)다. 두 번째 조건에 걸려 닫는 구분자가 되지 못하고, 짝을 못 찾은 `**`는 글자로 남는다.

![닫는 구분자의 앞뒤 글자](./images/cjk-emphasis-rule.svg '영어는 닫는 ** 뒤에 공백이 와서 닫히지만, 한국어는 조사가 바로 붙어 닫히지 않는다')

영어라면 `**done (really)** now`처럼 닫는 별표 뒤에 공백이 오니 문제가 없다. 한국어는 조사를 바로 붙여 쓰니 **괄호·따옴표·코드로 끝나는 굵게** 뒤에서 자주 깨진다.

```markdown
**`dragover`**를 ← 코드로 끝남
*“기울임”*은 ← 따옴표로 끝남
```

저장소의 글을 모두 Markdown 트리로 읽어서, 강조가 되지 못하고 글자로 남은 `*`를 찾아봤다. 저장소 글에는 이 한 곳뿐이었다. 하지만 편집기로 쓴 글은 서버에 있어 이렇게 세어 볼 수 없고, 앞으로 쓸 글도 똑같이 깨질 수 있다. 글을 고쳐 피하는 대신 **읽는 규칙을 고치기로 했다.**

| 방법                                     | 좋은 점                      | 문제                                                          |
| ---------------------------------------- | ---------------------------- | ------------------------------------------------------------- |
| 글을 고치기 (`**취소**(cancelled)가`)    | 코드가 그대로                | 쓸 때마다 규칙을 기억해야 한다. 서버 글은 찾을 수도 없다      |
| 닫는 `**` 뒤에 폭 없는 공백(U+200B) 넣기 | 규칙 안에서 해결             | 보이지 않는 글자가 글에 남는다. 검색·복사가 어긋난다          |
| 직접 remark 플러그인 쓰기                | 원하는 만큼만 바꾼다         | 구분자 판정은 micromark 깊은 곳이라 쓰기 쪽까지 맞추기 어렵다 |
| remark-cjk-friendly (고른 방법)          | 읽기·쓰기 규칙을 함께 고친다 | 의존성 하나. 한중일 글자 옆에서만 규칙이 달라진다             |

## 읽기 화면: remark 플러그인 하나

[remark-cjk-friendly](https://github.com/tats-u/markdown-cjk-friendly)는 한중일 글자 옆에서는 위 조건을 풀어 주는 플러그인이다. 영어 글에서는 CommonMark와 똑같이 동작한다. 글을 그리는 곳이 세 군데(읽기 화면, 편집 중 미리보기, 버전 기록)여서 목록을 한 파일에 모았다.

```ts
// markdownPlugins.ts
export const REMARK_PLUGINS: Options['remarkPlugins'] = [remarkGfm, remarkCjkFriendly];
```

![고친 뒤 읽기 화면](./images/cjk-emphasis-after.jpg '글은 그대로 두고 읽는 규칙만 바꿨다')

## 편집기: 읽을 때와 쓸 때 모두

편집기(Milkdown)도 안에서 remark로 Markdown을 읽고 쓴다. 읽기 화면만 고치면 편집기에서는 여전히 별표가 보인다.

![고치기 전 편집기](./images/cjk-emphasis-editor-before.jpg '관리자로 열면 바로 편집기가 뜨는데, 여기서도 별표가 그대로다')

그리고 더 조용한 문제가 하나 있었다.

플러그인 없이 편집기에서 이 글을 열어 한 글자만 고쳐 저장하면, 편집기가 문서를 다시 Markdown으로 쓸 때 **"이대로 쓰면 굵게가 안 된다"는 걸 알고** 뒤 글자를 문자 참조로 바꿔 버린다.

```markdown
**취소(cancelled)**&#xAC00; 떴다.
```

화면에는 똑같이 보이지만 저장된 글이 망가진다. remark-cjk-friendly는 쓰는 쪽 규칙(`mdast-util-to-markdown`)도 함께 고쳐서, 편집기에 `$remark`로 걸면 읽기와 쓰기가 같이 맞춰진다.

```ts
const cjkFriendly = $remark('cjkFriendly', () => remarkCjkFriendly);

Editor.make().use(commonmark).use(gfm).use(cjkFriendly);
```

![규칙을 거는 곳](./images/cjk-emphasis-where.svg '읽는 세 곳은 같은 목록을 쓰고, 편집기는 같은 플러그인을 따로 건다')

## 테스트

고친 것은 PR [#52](https://github.com/hyeoniverse/MacFolio/pull/52)의 커밋 하나다. 8개 파일에 221줄을 더했는데, 81줄은 `pnpm-lock.yaml`, 66줄은 이 글이다. 코드는 `markdownPlugins.ts`(10줄)와 편집기 7줄, 메모 화면 8줄이 바뀌었다.

- **단위 테스트** (`src/apps/memo/markdownPlugins.test.ts`의 **문장부호로 끝난 굵게 뒤에 조사가 붙어도 굵게로 그린다**, **영어 글과 GFM은 그대로다**): `**취소(cancelled)**가`, ``**`dragover`**를``, `*“기울임”*은`이 `<strong>`/`<em>`으로 그려지는지, 영어 글과 취소선은 그대로인지 본다. 플러그인을 빼고 돌리면 실패하는 것도 확인했다
- **E2E** (`e2e/memo-editor.spec.ts`의 '한국어 사이의 굵게' 묶음): 읽기 화면에서 굵게로 보이는지, 관리자로 편집기에서 열어 그 문단에 이어 써도 저장된 Markdown에 `**취소(cancelled)**가`가 그대로 있고 `&#x`가 없는지 본다. 편집기 쪽 플러그인만 빼면 이 테스트가 실패한다

테스트를 쓰다 하나 더 배웠다. 처음엔 글 맨 끝 빈 줄에 `' 끝.'`을 쳤더니 저장된 글에 `&#x20;끝.`이 들어가 테스트가 실패했다. 줄 맨 앞의 공백은 Markdown에서 사라지니 편집기가 문자 참조로 지킨 것이다. 이번 문제와는 상관없는, 올바른 동작이었다. 굵게가 있는 문단 끝에 이어 쓰도록 테스트를 고쳤다.

## 그 뒤, 남은 것

- 읽기 규칙을 한 파일에 모아 둔 덕에, 뒤에 더한 규칙도 같은 자리에 들어갔다. 지금 `REMARK_PLUGINS`에는 `~` 하나짜리 취소선 끄기(`220~440px`이 취소선이 되던 문제), `<details>` 접기 블록, `#태그`가 함께 있다. 단위 시험도 7개로 늘었다.
- 편집기는 같은 목록을 그대로 쓰지 못하고 플러그인을 하나씩 따로 건다. Milkdown이 remark 플러그인을 `$remark`로 감싸야 해서다. 읽기에 규칙을 더하면 편집기에도 더해야 하는지 매번 따져야 한다.
- 이번에 가장 값진 발견은 "편집기가 조용히 글을 바꾼다"였다. 화면에서는 아무 차이가 없어서, 저장된 Markdown을 직접 읽는 E2E가 없었다면 몰랐을 것이다. 편집기를 시험할 때는 화면이 아니라 저장된 글을 본다.
