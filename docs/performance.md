# 성능 측정

사이트(macfolio.hyeoniverse.com)의 첫 방문 성능을 재고, 느린 원인을 고친 뒤 같은 조건으로 다시 잰 기록이다. 2026년 10월 22일 기준이다. 1차는 #319, 2차는 그 뒤의 PR이다.

## 요약

로컬에서 같은 조건으로 잰 값이다 (Lighthouse 5번의 가운데값).

### 운영 사이트

운영 주소(Cloudflare)를 같은 Lighthouse로 5번씩 잰 값이다. 진짜 망이라 로컬보다 들쭉날쭉하다.

| 항목              | 휴대폰 전 | 1차 배포 뒤 | 데스크톱 전 | 1차 배포 뒤 |
| ----------------- | --------- | ----------- | ----------- | ----------- |
| Lighthouse 성능   | 53        | **73**      | 60          | **89**      |
| FCP               | 15.0초    | **2.4초**   | 2.9초       | **0.9초**   |
| LCP               | 31.5초    | **7.1초**   | 5.8초       | **2.1초**   |
| 첫 방문에 받는 양 | 6,342KB   | **1,239KB** | 7,134KB     | **3,229KB** |

운영의 "전"은 #319를 배포하기 전 main이다. 데스크톱은 운영이 그림을 더 받는다(2.2MB, 로컬 1.0MB). 관리자가 고친 프로젝트 내용(서버)이 처음 열리는 Safari 페이지에 들어가서다. 2차는 배포한 뒤 다시 재서 더한다.

### 실제로 느리게 한 휴대폰

Lighthouse의 기본(simulate)은 빠르게 받은 기록으로 느린 망을 계산한다. 브라우저를 실제로 느리게 해서(`--throttling-method=devtools`, 같은 느린 4G·4배 CPU) 3번씩 재면 이렇다.

| ----------------- | ------- | --------- |
| Lighthouse 성능   | 65      | **78**    |
| FCP               | 9.2초   | **1.2초** |
| LCP               | 12.1초  | **6.0초** |
| 첫 방문에 받는 양 | 5,932KB | **782KB** |

## 측정 방법

### 조건

- **도구:** Lighthouse 12.8.2 (성능만), Playwright 1.64 (Chromium 156)
- **휴대폰:** Lighthouse 기본값. 느린 4G(왕복 150ms, 1.6Mbps)와 CPU 4배 느림을 흉내 낸 값(simulated throttling)이다
- **데스크톱:** `--preset=desktop` (왕복 40ms, 10Mbps, CPU 그대로)
- **서버:** 빌드한 `dist`를 로컬 정적 서버(`apps/react/scripts/perf/serve.mjs`)로 내준다. 글자 파일은 brotli로 압축하고, 화면 주소는 `index.html`, 없는 `/assets/*`는 404를 준다. 운영의 Cloudflare Worker와 같은 방식이지만, Worker의 첫 화면 내용 넣기(SEO)와 CSP는 하지 않는다
- **횟수:** 전·후를 같은 컴퓨터에서 차례로 5번씩 돌리고 가운데값을 쓴다. 빌드나 다른 측정과 겹치지 않게 한 번에 하나씩 돌렸다
- **전:** `52f493bb2` (#311 머지) 빌드. **1차:** #319의 빌드. **2차:** 1차 뒤 main에 2차를 얹은 빌드

운영 사이트는 같은 `measure.mjs`에 운영 주소를 넘겨 쟀다.

### 숫자 읽는 법

- **simulate의 FCP:** 로컬에서는 첫 그림(47ms)이 그려지기 전에 미리 받기로 적은 묶음 33개(약 400KB)까지 다 받아 버린다. simulate는 "첫 그림 전에 받은 것"을 첫 그림에 필요한 것으로 보고 느린 망 시간을 계산해서, 휴대폰 FCP가 4.0초로 나온다. 실제로 느리게 하면 HTML의 첫 그림은 1.2초에 뜬다(위 표). 그래서 휴대폰 FCP는 두 값을 함께 본다
- **로컬 서버는 HTTP/1.1:** 한 번에 6개씩만 받는다. 실제로 느리게 한 측정에서 묶음 33개가 줄을 서서 마지막 묶음이 5.1초에 끝났다. 운영(Cloudflare)은 HTTP/2라 한 연결로 함께 받는다. 운영 휴대폰 FCP(2.4초)가 로컬 simulate(4.0초)보다 빠른 것도 그 영향으로 본다

### 다시 재기

```bash
pnpm build
cd apps/react
node scripts/perf/serve.mjs dist 4810 &
node scripts/perf/measure.mjs http://localhost:4810 perf.json 5
```

`measure.mjs`는 휴대폰·데스크톱마다 Lighthouse를 N번 돌리고(`pnpm dlx lighthouse@12.8.2`, 크롬은 Playwright가 받은 것), Playwright로 들어가기도 N번 잰다. 들어가기는 스로틀 없이 로딩 화면이 뜰 때까지·눌러서 바탕화면(휴대폰은 홈 화면)이 뜰 때까지의 시간, 그때까지 받은 양, JS 힙을 본다. 결과는 가운데값과 매번의 값을 JSON으로 남긴다. 앞에 `THROTTLING=devtools`를 붙이면 브라우저를 실제로 느리게 해서 재고, 주소 자리에 운영 주소(`https://macfolio.hyeoniverse.com`)를 넘기면 운영을 잰다.

## 무엇이 느렸나

고치기 전 Lighthouse의 요청 목록과 빌드 결과를 보면 원인은 다섯이었다.

| 원인                                          | 크기 (압축)                          | 영향                                                                          |
| --------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------- |
| 본문 글꼴 `AppleSDGothicNeoR.ttf` (TTF 한 벌) | 3.8MB (1.7MB)                        | 받는 양의 1/3. 첫 화면 글자가 이 글꼴을 기다린다                              |
| 블로그 글 199편의 원문이 첫 묶음에            | 2.4MB (740KB)                        | `import.meta.glob(..., { eager: true })`라 바탕화면 아이콘이 불러도 딸려 온다 |
| 모든 앱 코드가 첫 묶음(`boot`)에              | 890KB (250KB)                        | 메모·Finder·텍스트 편집기만 따로 떼어 있었다                                  |
| 큰 그림·영상                                  | 아이콘 1.2MB, 배경화면 JPG, 영상 1MB | 2560px 아이콘, 처음 열린 Safari 페이지의 영상·첫 화면 그림을 한꺼번에         |
| 로딩 화면을 JS가 그린다                       | -                                    | 휴대폰은 첫 묶음을 다 받기까지 14초 동안 검은 화면                            |

그 밖에 음악 앱이 곡 길이를 재려고 첫 방문에 MP3 일곱 개의 앞부분을 받았고, 휴대폰은 쓰지 않는 데스크톱 배경화면(2048px)도 받았다.

## 고친 것

### 1차 (#319)

| 한 일                                                                                                   | 줄어든 것                                                         |
| ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 모든 앱을 처음 열 때 불러온다 (`apps/registry.ts`의 `lazy`)                                             | 첫 묶음 250KB → 47KB (압축)                                       |
| 블로그 원문은 목록을 처음 물을 때 받는다 (`memo/repository/contentFiles.ts`)                            | 첫 방문에서 740KB                                                 |
| 바탕화면 아이콘·Dock 휴지통은 블로그 글을 받지 않는다 (`useLocations({ posts: false })`)                | 데스크톱 첫 방문에서 600KB                                        |
| 저장소 문서는 경로만 먼저, 원문은 Finder가 열 때 (`finder/docPaths.ts`)                                 | 첫 방문에서 75KB                                                  |
| 글꼴을 woff2 두 조각으로 (`scripts/subset-font.py`, `unicode-range`)                                    | 1.7MB → 149KB (드문 한글이 있을 때만 232KB 더)                    |
| 앱 아이콘을 256px로 (`scripts/optimize-icons.py`)                                                       | 아이콘 파일 1,171KB → 428KB                                       |
| 배경화면을 WebP로 (`scripts/optimize-wallpapers.py`)                                                    | 파일 7.9MB → 2.3MB (기본 데스크톱 563 → 348KB, 휴대폰 308 → 60KB) |
| 휴대폰에서는 바탕에도 휴대폰 배경화면 (`index.css`)                                                     | 휴대폰 첫 방문에서 348KB                                          |
| 곡 길이는 미리 적어 두고, 곡은 누르기 전에 받지 않는다 (`music/library.ts`의 `TRACK_SECONDS`)           | MP3 앞부분 (운영 휴대폰 측정에서 560KB)                           |
| 프로젝트 페이지의 영상·첫 화면 그림은 화면 가까이 올 때 (`safari/project/useNearView.ts`)               | 데스크톱 첫 방문에서 영상 1MB와 그림 수십 장                      |
| 로딩 화면의 사과를 글꼴 대신 SVG로, 스크립트 전에 HTML로 먼저 그린다 (`index.html`의 `#boot-splash`)    | 휴대폰 FCP 14.3초 → 4.0초                                         |
| `boot` 묶음과 그 묶음이 쓰는 묶음을 `index.html`에 미리 받기로 (`vite.config.ts`의 `bootPreloadPlugin`) | `main`을 실행한 뒤에야 받던 것을 함께 받는다                      |

글꼴은 KS X 1001 완성형 2,350자와 영문·문장 부호·자모를 `core`(149KB)에, 나머지 한글 8,822자를 `ext`(232KB)에 담았다. 같은 이름의 `@font-face` 두 개를 두고, 브라우저가 `core`에서 글자를 못 찾을 때만 `ext`를 받는다. PDF 이력서는 TTF를 그대로 쓴다.

### 2차

| 한 일                                                                      | 줄어든 것                                    |
| -------------------------------------------------------------------------- | -------------------------------------------- |
| 앱 아이콘을 192px WebP로 (`scripts/optimize-icons.py`), 화면은 WebP를 쓴다 | 아이콘 428KB → 51KB                          |
| 음악 앨범 그림을 512px WebP로                                              | 742KB → 146KB                                |
| 메뉴 막대의 사과를 SVG 부품으로 (`shared/ui/AppleLogo.tsx`)                | 데스크톱 첫 화면의 Font Awesome brands 113KB |

아이콘 PNG는 지우지 않았다. 관리자가 서버에 저장한 프로젝트 내용에는 예전 PNG 주소가 들어 있을 수 있어서다.

묶음 수를 줄이려고 Rolldown의 `codeSplitting.groups`로 작은 공용 모듈을 한 묶음에 모아 보기도 했다. 의존 모듈까지 따라 들어와 672KB짜리 묶음이 생기고, 의존을 빼면 블로그 글 하나하나(작은 모듈)까지 모여 596KB가 되어 그만뒀다. 운영은 HTTP/2라 묶음 수의 손해가 로컬보다 작다.

### 같이 고친 문제

앱을 처음 열 때 불러오게 바꾸자 E2E가 16개 깨졌다.

- **셸이 앱의 CSS를 빌려 쓰고 있었다.** 홈 인디케이터와 앱 전환기는 `desktop/window/Window.css`의 모양을 쓰는데, 이 CSS를 부르는 것은 창 틀(`Window.tsx`)이고 창 틀은 앱만 불렀다. 앱이 첫 묶음에 있을 때는 우연히 늘 실려 있었다. 이제 셸(`Desktop.tsx`)이 처음부터 싣는다
- **상태 표시줄 색이 잠깐 늦다.** 앱을 연 순간에는 앱 화면이 아직 없어 밑의 홈 화면 색을 읽는다. 0.8초마다 다시 읽으므로 곧 맞는다
- **시험이 너무 일찍 읽었다.** 창이 뜨자마자 목록 수를 세거나 단축키를 누르던 시험은 앱이 그려질 때까지 기다리게 했다. 메모는 글 원문 묶음을 앱과 함께 받아 목록이 비어 보이는 순간이 없다

## 남은 것

- **휴대폰 LCP 5.8초:** 홈 화면은 JS가 그린다. 첫 묶음(압축 220KB, 33개)을 받아 실행해야 홈 화면의 아이콘을 요청한다. 남은 큰 것은 Font Awesome solid 글꼴(117KB)인데, 프로젝트 내용(서버)에서 아이콘 이름을 고를 수 있어 쓰는 모양만 남기기가 어렵다
- **운영에서 2차 재기:** 2차를 배포한 다음 운영 주소로 다시 잰다
- **CI에서 재기:** 지금은 손으로 돌린다. 성능 예산(첫 방문 받는 양 등)을 CI에 두면 다시 무거워지는 것을 막을 수 있다
