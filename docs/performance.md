3차는 전송량을 줄인 것이 아니라 **진입 후로 지연했다**. 진입 후까지의 전송량은 2차와 같다. 로딩 화면에 가려 보이지 않던 바탕화면(휴대폰은 홈 화면)을, 로딩 화면을 누른 뒤 진행 막대가 차는 2.5초 동안 렌더링한다.

휴대폰 점수는 3차와 4차 모두 회차별 편차가 컸다. React가 렌더링한 시작 안내가 LCP로 다시 집계되는 회차가 있었기 때문이다(LCP 4.5초). 5차에서 원인을 찾아 해결했다([5차](#5차-lcp-재집계-해결과-성능-예산)). 5차의 남은 편차(1.7\~3.4초)는 첫 렌더링 전에 수신을 마친 번들 수에 따라 simulate가 계산한 값이 달라지는 것이다([측정값 해석](#측정값-해석)).

5차의 첫 방문 전송량 감소(휴대폰 487 → 278KB, 데스크톱 775 → 278KB)는 수신을 **누른 뒤로 지연한** 것이다. 본문 글꼴(149KB)과 배경화면(휴대폰 60KB, 데스크톱 348KB)을 로딩 화면을 누른 뒤 진행 막대가 차는 2.5초 동안 수신한다. 진입 후까지의 전송량은 4차와 같다.

### 운영 사이트

운영 주소(Cloudflare)를 같은 Lighthouse로 5회씩 측정한 값이다. 실제 네트워크라 로컬보다 편차가 크다.

| 항목            | 휴대폰 개선 전 | 1차 배포 후 | 3차 배포 후 (재측정) | 데스크톱 개선 전 | 1차 배포 후 | 3차 배포 후 (재측정)  |
| --------------- | -------------- | ----------- | -------------------- | ---------------- | ----------- | --------------------- |
| Lighthouse 성능 | 53             | 73          | **98** (86\~98)      | 60               | 89          | **97** (96\~100)      |
| FCP             | 15.0초         | 2.4초       | **1.9초** (1.8\~3.3) | 2.9초            | 0.9초       | **1.0초** (0.6\~1.05) |
| LCP             | 31.5초         | 7.1초       | **1.9초** (1.8\~3.3) | 5.8초            | 2.1초       | **1.0초** (0.6\~1.05) |
| 첫 방문 전송량  | 6,342KB        | 1,239KB     | **602KB**            | 7,134KB          | 3,229KB     | **889KB**             |

- "개선 전"은 [#319](https://github.com/hyeoniverse/MacFolio/pull/319)를 배포하기 전 main이다.
- "3차 배포 후"는 2026년 10월 23일 운영(명언 위젯 포함, 4차의 첫 번들 개선은 미배포)이다.
- 운영의 첫 방문 전송량은 로컬보다 약 100KB 크다. 원인은 둘이다.
  - Cloudflare가 JS를 로컬 측정 서버(brotli 최고 압축)보다 낮은 압축 수준으로 전송한다. 같은 파일이 10\~15% 크다.
  - 운영 Worker가 HTML에 검색엔진용 본문을 삽입한다. 로컬 `index.html` 2KB → 운영 15KB.
- 진입 후 데스크톱 이미지 전송량은 운영 1.9MB, 로컬 1.0MB다. 관리자가 수정한 프로젝트 내용(서버)이 처음 열리는 Safari 페이지에 들어가기 때문이다.

### 실제로 느리게 한 휴대폰

Lighthouse의 기본값([simulated throttling](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md))은 빠른 네트워크에서 수신한 기록으로 느린 네트워크의 시간을 계산한다. 브라우저를 실제로 느리게 해서(`--throttling-method=devtools`, 같은 느린 4G·4배 CPU) 측정하면 다음과 같다.

| 항목            | 개선 전 | 2차   | 3차        | 4차 (재측정)            |
| --------------- | ------- | ----- | ---------- | ----------------------- |
| Lighthouse 성능 | 65      | 78    | 92         | **100** (5회 중 1회 92) |
| FCP             | 9.2초   | 1.2초 | 1.2\~2.7초 | **1.2초**               |
| LCP             | 12.1초  | 6.0초 | 1.2\~2.7초 | **1.2초**               |
| 첫 방문 전송량  | 5,932KB | 782KB | 483KB      | **485KB**               |

3차부터 LCP가 FCP와 같다. 첫 렌더링(HTML의 사과와 시작 안내)이 곧 최대 콘텐츠다.

## 4차: 재측정에서 찾은 것

3차 이후 기능을 더하면서 첫 방문 전송량이 다시 늘었다(휴대폰 483KB → 505KB, 데스크톱 771KB → 793KB). 3차를 머지한 시점(`3e0c919ca`)과 현재 main의 빌드를 같은 방법으로 열어 파일별 전송량을 비교하니, 달라진 파일은 `boot` 번들 하나였다(압축 46KB → 65KB).

| 원인                                                                                                                                      | 크기                         | 개선                                                                                                                               |
| ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 명언 위젯([#330](https://github.com/hyeoniverse/MacFolio/pull/330))의 명언 365개(`desktop/widgets/quotes.ts`)가 위젯과 함께 `boot`에 포함 | 원문 66KB, `boot` 압축 +19KB | 명언 위젯을 [`React.lazy`](https://react.dev/reference/react/lazy)로 분리 (`Widget.tsx`). 위젯을 처음 렌더링할 때 별도 청크로 수신 |

명언 위젯은 로딩 화면을 누른 뒤 바탕화면과 함께 표시되므로, 첫 방문에서 미리 내려받을 필요가 없다. 개선 후 `boot`는 압축 47KB, 첫 방문 전송량은 휴대폰 485KB, 데스크톱 772KB로 3차 수준이다.

이런 증가는 측정하지 않으면 드러나지 않는다. 그래서 5차에서 CI [성능 예산](#성능-예산)을 추가했다.

## 5차: LCP 재집계 해결과 성능 예산

### 휴대폰 LCP가 4초대로 다시 집계되던 원인

로컬 simulate 휴대폰 측정에서 LCP가 3.3초 또는 4.5\~4.7초로 갈렸다. 4초대 회차의 LCP 요소는 HTML의 시작 안내(`#boot-splash p`)가 아니라 React가 렌더링한 시작 안내(`p.loading-text`)였다. Lighthouse trace의 `largestContentfulPaint::Candidate`와 `PaintTimingVisualizer::LayoutObjectPainted` 이벤트로 회차를 분류했다.

| 회차             | HTML 시작 안내    | React가 `#boot-splash` 삭제·렌더링 | LCP 후보                         | simulate LCP |
| ---------------- | ----------------- | ---------------------------------- | -------------------------------- | ------------ |
| 정상 (main 30회) | 22\~79ms에 렌더링 | HTML 안내의 LCP 기록 **뒤**        | HTML 시작 안내 (렌더링 +9\~28ms) | 2.6\~3.3초   |
| 4초대 (main 7회) | 29\~55ms에 렌더링 | HTML 안내의 LCP 기록 **전**        | React 시작 안내만                | 4.4\~4.7초   |

- HTML의 시작 안내는 두 경우 모두 렌더링되었다. 다만 LCP 후보 기록은 렌더링 뒤 9\~28ms에 나타났고, 그 전에 `App.tsx`가 `#boot-splash`를 삭제한 회차에는 HTML 안내의 후보가 기록되지 않았다
- 그러면 다음에 렌더링된 React의 시작 안내가 첫 LCP 후보가 된다. simulate는 그 시각 전에 실행된 앱 스크립트와 그 사이 수신한 웹 글꼴(149KB)까지 LCP에 필요한 작업으로 계산해 4.5초대가 되었다
- 글꼴 교체로 글자 영역이 커진다는 이전 추정은 원인이 아니었다. 4초대 회차의 React 안내는 HTML 안내와 같은 3,078px²이거나(웹 글꼴) 더 작았다(2,754px², 대체 글꼴)
- 4초대 회차의 비율은 측정 컴퓨터의 부하에 따라 달랐다. 같은 날 앞선 측정에서는 약 절반, 번갈아 측정한 28회에서는 3회였다

| 변경                                                                                                  | 효과                                                                                               |
| ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `#boot-splash`를 React가 처음 렌더링하는 시각이 아니라 로딩 화면을 **누르는 시각**에 삭제 (`App.tsx`) | HTML 안내의 LCP 기록이 사라지지 않는다. 누르면 LCP 기록이 끝나므로 그 뒤의 삭제는 영향이 없다      |
| 로딩 화면의 시작 안내를 `#boot-splash`와 같은 시스템 글꼴로 (`LoadingScreen.css`)                     | 글자 영역이 같아 React의 안내가 새 LCP 후보가 되지 않는다. 누르기 전에는 웹 글꼴을 수신하지 않는다 |

React의 로딩 화면은 `#boot-splash`와 같은 위치·크기에 DOM 순서상 뒤에 렌더링되어 그 위를 덮는다. 두 화면의 상자와 글자 영역이 같은지는 `e2e/mobile-loading.spec.ts`가 확인한다.

| 로컬 휴대폰 simulate (번갈아 28회씩) | 전 (main)     | 후 (5차)              |
| ------------------------------------ | ------------- | --------------------- |
| LCP 4초 이상                         | 3회           | **0회**               |
| LCP 범위                             | 2.6\~4.7초    | **1.7\~3.4초**        |
| LCP 중앙값                           | 3.3초         | 3.3초                 |
| 성능 점수 범위                       | 77\~93        | **85\~99**            |
| LCP 요소                             | 회차마다 다름 | 항상 `#boot-splash p` |

데스크톱도 같은 원인으로 5회 중 1회 LCP가 1.2초였고(React 안내), 5차에서는 5회 모두 0.5\~0.7초다.

### 휴대폰 로딩 화면 밖으로 배경화면이 비치던 문제

휴대폰(특히 iOS Safari)에서 로딩 화면이 화면을 다 덮지 않아 아래쪽에 홈 화면 배경이 비쳤다. Playwright(Chromium)의 휴대폰 흉내로는 재현되지 않아, 원인 후보 두 가지를 모두 처리했다.

- **상자 크기:** 로딩 화면은 `width: 100vw; height: 100vh`, 홈 화면(`.mobile-home`)은 `inset: 0; height: 100dvh`였다. iOS Safari의 `vh`는 도구 막대가 접힌 상태(가장 큰 뷰포트) 기준이고 `dvh`는 지금 보이는 영역 기준이라, 도구 막대가 나타나고 사라질 때 두 상자의 크기가 다르다([MDN: 뷰포트 단위](https://developer.mozilla.org/en-US/docs/Web/CSS/length#relative_length_units_based_on_viewport))
- **상자 밖의 배경:** 도구 막대 뒤나 화면을 끌어 내린 영역처럼 상자 밖이 보이면 html·body 배경이 표시된다. 로딩 화면이 표시되는 즉시 `booting` 클래스를 해제해 그 배경이 배경화면이었다

로딩 화면과 `#boot-splash`를 홈 화면과 같은 `inset: 0; height: 100dvh`로 바꾸고, html·body는 로딩 화면을 누르기 전까지 검은색(`booting`)으로 유지한다. 상자 밖이 보여도 로딩 화면과 같은 검은색이다. 시험(`e2e/mobile-loading.spec.ts`)은 390×844, 430×932, 375×667에서 로딩 화면이 뷰포트 전체를 덮는지, 화면 가장자리·아래쪽 점의 최상위 요소가 로딩 화면인지(누른 뒤 홈 화면을 렌더링하는 동안 포함), html 배경이 검은색인지를 확인한다. 실제 iPhone Safari의 도구 막대 동작은 실기기에서 확인한다.

### 성능 예산

4차의 회귀(명언 위젯 +19KB)는 재측정에서만 발견했다. 이런 증가를 PR에서 바로 드러내려고 CI의 `check` 작업이 빌드 뒤에 `apps/react/scripts/perf/budget.mjs`로 첫 방문 번들의 크기를 검사한다.

| 항목                                                                                                     | 측정값 (2026년 10월 23일) | 상한      | 여유           |
| -------------------------------------------------------------------------------------------------------- | ------------------------- | --------- | -------------- |
| `boot` 번들 (`assets/boot-*.js`)                                                                         | 49.4KB                    | **55KB**  | 5.6KB (약 10%) |
| 첫 방문 번들 합계 (`index.html`의 `<script type="module">`·`modulepreload`·`preload`·`stylesheet`, 41개) | 251.6KB                   | **265KB** | 13.4KB (약 5%) |

- 크기는 brotli 9단계(측정 서버 `serve.mjs`와 같다)로 압축한 크기이고, KB는 1,024바이트다
- 상한은 4차의 회귀(+19KB)가 두 항목 모두에서 실패하도록 정했다. 합계는 번들이 많아 작은 증가가 누적되므로 여유를 더 작게 두었다
- 글꼴·이미지는 대상이 아니다. 5차부터 첫 방문(누르기 전)에 수신하지 않는다

넘으면 CI 로그와 실패 요약(annotation)에 어느 항목이 얼마나 넘었는지와 크기 상위 파일을 출력한다. 아래는 상한을 낮춰 실패시킨 예다.

```text
$ BUDGET_BOOT_KB=45 BUDGET_INITIAL_KB=240 pnpm --filter @macfolio/react perf:budget
boot 번들(assets/boot-wshPrf4V.js)이 49.4KB로, 상한 45.0KB보다 4.4KB 큽니다.

첫 방문 번들(index.html이 처음부터 요청하는 41개)이 251.7KB로, 상한 240.0KB보다 11.7KB 큽니다.
크기 상위 8개:
    59.4KB  assets/jsx-runtime-C2l8KVV-.js
    49.4KB  assets/boot-wshPrf4V.js
    34.6KB  assets/boot-DhNtOT2g.css
    28.8KB  assets/preload-helper-qmxL7HwO.js
    ...
```

**넘었을 때의 대응**

1. 로컬에서 `pnpm build` 뒤 `pnpm --filter @macfolio/react perf:budget`으로 같은 결과를 확인한다
2. 상위 파일 목록에서 커진 번들을 찾고, 그 번들에 새로 포함된 모듈을 확인한다. 4차처럼 첫 화면에 필요 없는 컴포넌트·데이터를 정적 import한 경우가 대부분이다
3. 로딩 화면을 누른 뒤에 필요한 것이면 [`React.lazy`](https://react.dev/reference/react/lazy)나 `import()`로 분리한다
4. 첫 화면에 꼭 필요한 증가라면 이 문서의 표와 `budget.mjs`의 `BUDGET`을 함께 올리고, PR에 이유와 측정값을 적는다. `BUDGET_BOOT_KB`·`BUDGET_INITIAL_KB` 환경 변수로 상한을 바꿔 로컬에서 시험할 수 있다

### 측정값 해석

- **simulate의 휴대폰 FCP:**
  - 로컬에서는 첫 렌더링(47ms) 전에 [modulepreload](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/modulepreload)로 지정한 번들 33개(약 400KB)까지 모두 수신한다.
  - simulate는 "첫 렌더링 전에 수신한 것"을 첫 렌더링에 필요한 것으로 보고 느린 네트워크 시간을 계산한다. 그래서 휴대폰 FCP가 3초대로 나온다.
  - 실제로 느리게 하면 HTML의 첫 렌더링은 1.2초다(위 표). 따라서 휴대폰 FCP는 두 값을 함께 참고한다.
- **휴대폰 LCP 편차의 원인 (4차까지):**
  - React가 `#boot-splash`를 너무 일찍 삭제한 회차에는 HTML 시작 안내의 LCP 후보가 기록되지 않고, React의 시작 안내가 LCP가 되었다(4.5초). 5차에서 해결했다([5차](#5차-lcp-재집계-해결과-성능-예산)).
- **5차의 남은 편차(1.7\~3.4초):**
  - LCP 요소는 항상 HTML의 시작 안내다. simulate는 그 렌더링 전에 수신을 마친 요청을 LCP에 필요한 것으로 계산하므로, 로컬에서 modulepreload 번들이 첫 렌더링 전에 얼마나 도착했는지에 따라 값이 달라진다.
- **로컬 서버는 HTTP/1.1:**
  - 브라우저의 출처당 동시 연결이 6개라 번들 33개가 대기열에 쌓인다.
  - 운영(Cloudflare)은 HTTP/2라 한 연결로 함께 수신한다. 운영 휴대폰 FCP(1.9초)가 로컬 simulate(3.2초)보다 빠른 것도 이 영향으로 본다.

### 다시 측정하기

```bash
pnpm build
cd apps/react
node scripts/perf/serve.mjs dist 4810 &
node scripts/perf/measure.mjs http://localhost:4810 perf.json 5
```

`measure.mjs`는 다음을 측정하고, 중앙값과 회차별 값을 JSON으로 저장한다.

- 휴대폰·데스크톱마다 Lighthouse를 N회 실행한다(`pnpm dlx lighthouse@12.8.2`, 크롬은 Playwright가 내려받은 것).
- Playwright로 진입 과정을 N회 측정한다. 스로틀링 없이 다음 값을 기록한다.
  - 로딩 화면이 표시되기까지의 시간
  - 누른 뒤 바탕화면(휴대폰은 홈 화면)이 표시되기까지의 시간
  - 그때까지의 전송량
  - JS 힙

옵션은 다음과 같다.

- `THROTTLING=devtools`를 붙이면 브라우저를 실제로 느리게 해서 측정한다.
- 주소 자리에 운영 주소(`https://macfolio.hyeoniverse.com`)를 넘기면 운영을 측정한다.
- 포트가 이미 사용 중이면 `serve.mjs`가 시작되지 않는다. 그러면 `measure.mjs`는 그 포트의 다른 서버를 측정하게 되므로 사용하지 않는 포트를 지정한다.

### 3차 (#323)

2차까지 휴대폰 LCP 요소는 홈 화면의 "파일" 아이콘이었다. 그런데 첫 방문에는 로딩 화면("탭하여 로딩을 시작하세요")이 홈 화면을 덮고 있어 이 아이콘은 보이지 않는다. 크롬은 가려진 요소도 LCP 후보로 집계한다. 보이지 않는 화면을 렌더링하려고 앱 코드를 실행하고 아이콘·위젯 이미지·날씨 데이터까지 수신해 첫 방문의 네트워크와 CPU를 사용했다.

| 변경                                                                                               | 효과                                                      |
| -------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 바탕화면(휴대폰은 홈 화면)은 로딩 화면을 누른 뒤 렌더링 (`App.tsx`, `LoadingScreen`의 `onStart`)   | 진입 전 전송량 휴대폰 725 → 483KB, 데스크톱 1,848 → 771KB |

### 함께 수정한 문제

앱을 처음 실행할 때 로드하도록 바꾸자 E2E 16개가 실패했다.

- **셸이 앱의 CSS에 의존하고 있었다.** 홈 인디케이터와 앱 전환기는 `desktop/window/Window.css`의 스타일을 쓰는데, 이 CSS를 import하는 것은 창 프레임(`Window.tsx`)이고 창 프레임은 앱만 import했다. 앱이 첫 번들에 있을 때는 이 CSS가 의도와 무관하게 항상 로드되었다. 이제 셸(`Desktop.tsx`)이 처음부터 로드한다
- **상태 표시줄 색이 잠시 늦게 바뀐다.** 앱을 연 직후에는 앱 화면이 아직 없어 아래의 홈 화면 색을 읽는다. 0.8초마다 다시 읽으므로 0.8초 안에 맞춰진다
- **시험이 렌더링 전에 확인했다.** 창이 표시되자마자 목록 수를 확인하거나 단축키를 누르던 시험은 앱이 렌더링될 때까지 기다리도록 수정했다. 메모는 글 원문 번들을 앱과 함께 수신해 목록이 비어 보이는 순간이 없다

## 남은 과제

- **진입 후의 글꼴·배경화면:** 5차부터 본문 글꼴과 배경화면을 누른 뒤 수신한다. 느린 네트워크에서 데스크톱 배경화면(348KB)이 진행 막대가 차는 2.5초 안에 도착하지 않으면, 로딩 화면이 걷힌 직후 잠시 검은 바탕이 보일 수 있다. 실제로 느리게 한 측정으로 확인한다
- **실기기 확인:** 로딩 화면이 iPhone Safari의 도구 막대 아래까지 덮는지는 실기기에서 확인한다
- **진입 후의 휴대폰 전송량:** 769KB는 그대로다. 첫 번들 33개와 Font Awesome solid 글꼴(117KB)이 남았다. 아이콘 글꼴은 프로젝트 내용(서버)에서 아이콘 이름을 고를 수 있어, 사용하는 아이콘만 남기기 어렵다
- **4차·5차의 운영 측정:** 배포한 뒤 운영 주소로 다시 측정한다
